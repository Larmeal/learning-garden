## A build that changes though nobody touched the code

Mr. A's app uses a library called `shop-utils`. In the file of dependencies he wrote `^1.2.0`, which means "the newest 1.x from 1.2.0 up, but below 2.0.0". The other form is `~1.2.0`, meaning "the newest 1.2.x". Suppose the registry holds versions 1.2.0, 1.2.3, 1.3.0, 1.9.9 and 2.0.0 (run: `exercises/11_supply_chain_secrets.py`). `^1.2.0` gets 1.9.9 and `~1.2.0` gets 1.2.3.

A week later the maintainer releases 1.9.10. `^1.2.0` installs 1.9.10 by itself, with Mr. A changing nothing. The exercise confirms that the same line gives different results a week apart. That is the point: **a build with no lock is not the same build twice**. It is a problem when the new library has a bug, or when somebody with bad intentions slipped code into it.

Change how the dependency is asked for in the lab below, one option at a time, then press next week. The bracket above the shelf covers the versions that the way of asking accepts. The box that is picked moves with `^`, but stays put with `==1.2.3` or with a lock file. Press "swapped" and the seal of the file that arrives changes, and only a lock file with a hash can put the two seals side by side and catch it.

## A lock file with a hash

Locking the version fixes the case where the version moves by itself, but the file of that same version can be swapped, for example when a maintainer's account is taken over and somebody uploads over it. This is where the **hash** comes in. A lock file keeps the SHA-256 of the file we have checked, and the installer compares it every time.

The exercise makes a one line toy package and records its SHA-256. A file that is the same matches the lock. A file with one line of harmful code added (`import os; os.system(...)`) does not match, and the installer stops. In the lab, switch the lock file on and choose "swapped": the install cannot succeed. But with the lock file off, the swapped file is installed and nobody knows (book: Web Application Security chapter 27 page 278 on secure package management).

A hash catches only a change to a file we have already checked. If the file we checked at the start held bad code already, a hash cannot say so. That is a matter of assessing a dependency when we choose it, and the book Web Application Security discusses assessing the tree of dependencies and CVEs as well (book: Web Application Security chapter 15 page 180).

</Step>

## A name that looks like the real one

Another thing attackers do is name a package so that it looks like a popular one, for example `reqeusts` instead of `requests`. Someone who makes one typo installs theirs. The exercise writes a function that measures the edit distance between names, against a list of five popular packages. The result: `reqeusts`, `numpyy` and `pydantlc` are no more than two letters away from the real names, while `flask`, which is unrelated to the list, and `requests`, which is the real name, are not flagged.

This only warns when a new name arrives. It is not a tool that catches every case, for example names that use look-alike letters from another alphabet, or packages whose names differ a lot but act as though they were the real thing. The exercise does not cover those.

</Step>

## A key that is deleted and still there

Mr. A commits `config.py` by mistake, with a cloud key in it. When he notices, he changes the file to take the value from the environment and commits again. He thinks that is the end of it (run: `exercises/11_supply_chain_secrets.py` in a throwaway repository, where the key is a sample value of the shape `AKIAIOSFODNN7EXAMPLE`).

The exercise checks three things. First, the file in the folder no longer has the key. Second, `git show <first commit>:config.py` still shows the whole key, and anyone who cloned the repository has that commit too. And last, `git log -S<key>` says that the commit named `add config` added it. Step through it in the lab below. The history of the repository is a chain of commit cards, the file in the folder is at the bottom left, and someone else's clone, with a copy of every commit, is at the bottom right.

<SecretGitLab client:visible lang="en" />

What really works is to **revoke the key** at the provider and issue a new one. Rewriting history keeps new clones from seeing it, but whoever cloned it already, and any copy that was backed up elsewhere, still has it (rewriting history was not run in this lesson).

</Step>

## A scanner for secrets

So teams often add a scanner that checks every commit before a push. The exercise writes a small one with two methods. The **shape** is a regex that matches the keys providers issue, for example `AKIA` followed by sixteen capital letters or digits, and the `-----BEGIN ... PRIVATE KEY-----` block. The **randomness** is the entropy per character: a long string that has more than 4.0 bits per character, and is not all letters, looks suspicious.

On three sample lines the scanner finds two things: a key of the AWS shape and the random string `x7Kp9Qv2...`. The ordinary long name `a_perfectly_ordinary_long_name_here` is not caught, because its entropy is about 3.8, below the line, while the random 32 character string has about 5.0 bits per character. These numbers are printed by the exercise.

Real scanners have far more patterns than this, and they are wrong in both directions: they miss a key that has changed shape, and flag a random value that is not a secret. A scanner helps, but it does not replace never keeping secrets in code in the first place. It is better to pass values through the environment or a secret store.
