## Log in once, yet be recognised every time

HTTP has no memory. Every request that reaches a server is brand new. Mr. A logs in to the bank with his password, and if the server did not remember who he is, he would have to type the password again each time he looked at his balance.

The most common way out is for the server, after checking the password, to make up a long random **session id**, store in its own table that this id means Ann, and send the id to the browser to keep in a **cookie**. From then on the browser attaches the cookie to every request by itself, and the server looks the id up to see who it is, like the queue ticket the bank gives you when you walk in (run: `exercises/05_sessions_csrf.py`).

```text
Set-Cookie: sid=ZXaHJ6PlxVqhxeKZp5vAcIdtwiSTW3Ea7AOUV5jeYv0; HttpOnly; Secure; Path=/; SameSite=Lax
```

The session id in the exercise comes from `secrets.token_urlsafe(32)`. It is 43 characters long, which is 256 bits, and two calls never give the same value. The end of the header holds three **flags** that should always be set: HttpOnly, Secure and SameSite. We will see what each of them stops. The book API Security in Action says that Secure and HttpOnly should be set on any cookie used for security (book: API Security in Action chapter 4 page 122).

The most important fact about this system is that **whoever holds this session id is that user**. Anyone who gets the id does not need the password at all.

</Step>

## A session id can be taken in two ways

Choose the stories in the lab below one at a time. Start with "A normal login" to see the user send the password once and the cookie do the rest, then look at the other four.

<CookieSessionLab client:visible lang="en" />

In the story **XSS steals the cookie**, suppose the site has an XSS hole, which we cover in a later lesson. A script that was planted runs in the user's browser and can read `document.cookie`. If the cookie has no `HttpOnly`, the script sends the sid out to the attacker, who can use it at once. If the cookie does have `HttpOnly`, the script cannot read it. The exercise checks both cases with a model of the browser.

**Session fixation** turns this around. The attacker steals nothing: he chooses the id. He asks the server for an id (`A`) and tricks the user into using it. If the server keeps the same id after the user logs in, the `A` that the attacker already knows becomes Ann's session at once. The exercise runs both ways and finds that keeping the id lets the attacker in, while issuing a new id at login keeps him out (book: API Security in Action section 4.3.1 page 119).

In the shortest form, `HttpOnly` stops reading by script, and a new id at login stops planting an id. The two do not replace each other.

</Step>

## CSRF: another site uses our cookie for us

Picture this. Mr. A has left the bank logged in on another tab, and opens `evil.test`, a site the attacker made. On that page a hidden form orders a transfer of 500 to the attacker's account, and a script submits it the moment the page opens.

The attacker does not see the cookie and does not know the password. But the browser is the one sending the request to `bank.test`, and the browser attaches the cookie of `bank.test` every time a request goes there, whichever page it comes from. The bank sees a valid cookie and believes that the user meant to transfer. This is **CSRF (cross-site request forgery)** (book: Web Application Security chapter 11 page 131).

Pick the defences in the lab one at a time. Start with "nothing at all" to see the money flow, then go through the other three.

<CsrfLab client:visible lang="en" />

What the exercise found: with no defence and the cookie set to `SameSite=None`, the bank sends 500 to the attacker (200). With `SameSite=Lax` the browser does not attach the cookie to a POST from another site, and the bank answers 401. If the bank checks a **CSRF token**, a random value that it gives only to its own pages and other sites cannot read, a request without it is refused with 403. And if the bank checks the **Origin**, which the browser adds to say which site the request came from, it gets 403 too (book: Web Application Security chapter 23 page 247 for header checking and page 249 for tokens, and API Security in Action page 127 for SameSite).

The bank's own page, which sends the token and comes from its own origin, still manages to transfer money when all three defences are on. The exercise checks that too.

<Callout type="warn" title="A model of a browser is not a browser">

The SameSite rules in the exercise (Lax leaves the cookie off a cross-site POST, Strict leaves it off every cross-site request) are written in code from what the books and the documentation describe. We did not open a real browser and send a cross-site request. The result says that if a browser follows those rules, this is what happens. It was not confirmed on Chrome or Firefox.

</Callout>
