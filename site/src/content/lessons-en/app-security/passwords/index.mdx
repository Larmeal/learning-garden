## The users table that left the building

Suppose Mr. A's shop is broken into and somebody takes the whole `users` table. Mr. A did not store passwords as they are. He stored SHA-256 of them, because he remembered from the last lesson that a hash cannot be reversed. The leaked table looks like this (run: `exercises/04_passwords.py`).

```text
ann  e4ad93ca07acb8d908a3...
bob  e4ad93ca07acb8d908a3...
cat  48486e1514e842346ff4...
dan  1c8bfe8f801d79745c46...
eve  65e84be33532fb784c48...
```

Does anything look odd? Ann and Bob have exactly the same hash, which means they chose the same password. The attacker does not need to know what it is to know the two share one. If one is cracked, both are cracked at once.

Worse, the attacker does not have to try users one by one. He builds a **lookup table** once, by hashing the 1,000 passwords people most often choose, and then matches the leaked values against it. What ran: 4 of 5 users were cracked (ann, bob, dan, eve). Only cat survived, whose password `Tr0ub4dor&3` is not on the list.

</Step>

<Step>

## A salt makes equal passwords look different

The fix is to add a **salt**, a random text for each user, in front of the password before hashing. With a different salt the hash differs even when the password is the same. The book API Security in Action says that password storage should use a random salt for each password (book: API Security in Action chapter 3 page 78).

Flip the salt in the lab below. On the left is the leaked table and on the right the lookup book the attacker made in advance. With the salt off, a row whose hash seal matches an entry in the book gets a line to it, and the password is read off. Ann and Bob have the same seal (a bracket marks it) and both are cracked, four rows in all with one book. With the salt on, every seal changes, no line reaches the book, and the attacker has to make a new book for each user.

<SaltLab client:visible lang="en" />

What the lab shows is what the exercise confirms in three checks. First, Ann's and Bob's hashes differ once there is a salt. Second, the table built earlier finds nothing. Third, the attacker's work grows from one pass over the 1,000 word list to a new pass for every user, which is 5,000 hashes. In this example the exercise derives the salt from the user name so the numbers repeat. A real one is 16 new random bytes each time (`secrets.token_bytes(16)`, which the exercise checks gives a different value on each call).

A salt does not have to be secret. It can sit next to the hash in the table. Its job is to make the attacker repeat the work for every user.

</Step>

## But a fast hash can still be guessed fast

A salt stops a table being shared, but the attacker can still guess one user's password at a time. How fast? The exercise measured how many guesses per second each method allows on one core of the computer that ran it. (The numbers below are from the run used for the lab. Another computer or another run will differ.)

| How it is stored | Guesses per second (one core) |
|---|---|
| plain SHA-256 | about 1,300,000 |
| PBKDF2 (SHA-256, 600,000 rounds) | about 7 |
| scrypt (N=32768, r=8, p=1) | about 3 |

The exercise asserts that PBKDF2 and scrypt are at least 1,000 times slower than plain SHA-256 (in the run measured, several hundred thousand times slower), and that one login with these slow hashes still takes under a second, which a real user does not notice but an attacker who has to guess a million times certainly does. That is why we use a hash that is **slow on purpose** for passwords, the opposite of what we want from an ordinary hash.

The lab below takes those speeds and works out how much of the space of possible passwords the attacker has walked. Each long bar is every password of the kind you pick, and the red part is what he has tried. Pick a kind of password, then switch the attacker's cores and working time, and see that the bar for plain SHA-256 turns red first, while the scrypt bar under the same conditions is still only a thin red line.

<PasswordCrackLab client:visible lang="en" />

For example, a password of 8 letters and digits (47.6 bits) stored as plain SHA-256 is half exhausted by one core in about 2.5 years, but behind scrypt it takes about a million years. These numbers depend on the computer that measured them and on the number of cores the attacker has (which, in the lab, is the author's example). What does not change is the ratio between the two methods.

<Callout type="note" title="bcrypt and Argon2">

Books and guides commonly recommend bcrypt, scrypt and Argon2, which share one idea: slow, and adjustable in how slow. This exercise uses scrypt and PBKDF2 because they are in Python's standard library with nothing to install. bcrypt and Argon2 were not run.

</Callout>

## Store it and check it the right way

Three things have to be stored: the algorithm, the salt and the hash. The exercise puts them into one text of the form `scrypt$salt$hash`, so that checking needs nothing from anywhere else.

```python
def hash_password(pw, salt):
    return "scrypt$" + salt.hex() + "$" + hashlib.scrypt(pw.encode(), salt=salt, n=2**14, r=8, p=1, maxmem=64*1024*1024).hex()

def verify_password(pw, stored):
    _, salt_hex, digest_hex = stored.split("$")
    again = hashlib.scrypt(pw.encode(), salt=bytes.fromhex(salt_hex), n=2**14, r=8, p=1, maxmem=64*1024*1024)
    return hmac.compare_digest(again.hex(), digest_hex)
```

`hash_password` runs the password and the salt through scrypt and joins the parts into one text. `verify_password` splits the salt out of the stored text, computes again with the password it was given, and compares with `hmac.compare_digest`, as we compared tags in the last lesson. What was asserted: the right password passes, and `tr0ub4dor&3` (lower case) does not.

In real work we do not write this ourselves. We use a library that has seen heavy use, and pick the parameters from current advice. The exercise writes it out only to show what is inside. The book Web Application Security covers hashing credentials and 2FA as well (book: Web Application Security chapter 18 page 197).

</Step>

## The length of a password still matters

Once storage is right, the password the user picks still counts. We measure strength in **bits**, the log base 2 of the number of passwords that are possible. Every extra bit doubles what the attacker must guess.

| Kind | Bits |
|---|---|
| 6 digits | 19.9 (about a million possibilities) |
| 8 lower case letters | 37.6 |
| 8 letters and digits | 47.6 |
| 4 random words from a list of 2,048 | 44.0 |

Notice that four random words, which are much easier to remember, are about as strong as eight mixed characters, which are hard to remember. The condition is that the words really are random. If the user picks them, such as joining the names of favourite songs, the 44 bits is no longer true (the author's observation, not run on passwords people chose).

</Step>
