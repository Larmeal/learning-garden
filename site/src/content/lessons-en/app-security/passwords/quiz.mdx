## Check yourself

<Question
  client:visible
  lang="en"
  q="A leaked table shows the same hash for two users. What can an attacker tell at once, without cracking anything?"
  options={['What both passwords are', 'Both users chose the same password, and if one is cracked both are', 'Both users own the same account']}
  answer={1}
  why="A hash always gives the same value for the same text, so equal values mean equal texts. In the exercise Ann and Bob have the same hash, and cracking one cracks both. A salt per user makes the hashes differ even when the passwords are the same."
/>

</Step>

<Step kind="question">

<Question
  client:visible
  lang="en"
  q="Where should the salt be kept?"
  options={['Separately, in a secret place, because if it leaks the attacker can crack the passwords', 'Next to the hash in the same table. A salt does not have to be secret', 'It need not be kept, because it can be recomputed from the password']}
  answer={1}
  why="A salt makes each user's hash different and makes a ready made table useless. It does not hide anything. It is kept next to the hash because, to check a password, we need the same salt to compute the hash again. The scrypt$salt$hash format in the exercise keeps all three in one value."
/>

</Step>

<Step kind="question">

<Question
  client:visible
  lang="en"
  q="Why do we choose a hash that is slow on purpose for passwords, when general hashes like SHA-256 are designed to be fast?"
  options={['Because a slow hash creates the salt by itself', 'Because one login taking slightly longer does not matter, but an attacker who has to guess a million times is slowed a million times', 'Because a slow hash cannot be reversed, while SHA-256 can']}
  answer={1}
  why="A real user pays the cost once per login, while an attacker pays the same cost for every guess. The exercise measures a scrypt login at well under a second, yet only a few guesses a second, while SHA-256 does about a million. Neither can be reversed directly."
/>

</Step>
