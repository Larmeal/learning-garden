## Coffee shop Wi-Fi and a password anyone can read

Mr. A is working at a coffee shop and logs in to his company's site, which is still plain `http://`. The request that leaves his computer looks something like this (an example the author wrote, not captured from anything real).

```text
POST /login HTTP/1.1
Host: intranet.example.test

user=mr-a&password=hunter2
```

Everything crosses the shop's router, and every other stop on the way, as ordinary text. Anyone on the same Wi-Fi with a capture tool can read the password. This is the first attack in the lab of the first lesson, at the network stop, and TLS is the fix.

TLS has to solve two problems at once. The first is to make the data in flight secret, which we do with encryption such as the AES-GCM of the last lesson. But encryption needs a key, and both sides need the same one, so the remaining problem is how to agree on that key while Mallory listens to every word. The other is that the browser needs to know it is talking to the real server and not one that somebody quietly set up in its place.

</Step>

## The handshake, message by message

The lab below shows the TLS 1.3 handshake that really ran in the exercise, between a client and a server in memory, where the server uses a certificate signed by our CA. The handshake finished with TLS 1.3 and the cipher `TLS_AES_256_GCM_SHA384`, and there were four turns of speaking: client, server, client, then the server once more.

Play the normal scenario first and see that message 2 is the biggest, because the certificate travels with it. After message 2 the browser checks three things about the certificate, and only if they pass does it send the very small message 3 (80 bytes). Then switch to the other scenarios one at a time and see that the browser stops the moment one of those three fails. The error you see is the real one from the exercise.

<TlsHandshakeLab client:visible lang="en" />

Message 4, the session ticket the server sends after everything is done, exists to make the next connection faster. The exercise checks only that it exists and that the server sends it.

## A secret number that never crosses the wire

A question is left over. We said both sides get the same key, yet Mallory hears every message. Why does Mallory not get the key as well? This is called **key exchange**, here the Diffie-Hellman kind, and it is easiest to understand by computing with small numbers.

Both sides agree on two public numbers, p = 23 and g = 5. Alice picks the secret 6 and sends Bob `5^6 mod 23 = 8`. Bob picks the secret 15 and sends Alice `5^15 mod 23 = 19`. Then Alice raises 19 to the power 6 and Bob raises 8 to the power 15, both take the remainder mod 23, and both get 2. That matches what the exercise computed and asserted. Slide the two secrets in the lab. The dashed box of each person is where the secret lives, and it never leaves that machine. On the wire only the two numbers that were sent are visible. The shared numbers of the two sides always get the same colour. The row of small tiles at the bottom is the eavesdropper, who sees only the numbers on the wire and has to try the secrets one tile at a time until one fits, which is short only because p is tiny.

<KeyExchangeLab client:visible lang="en" />

The box at the bottom is an eavesdropper who knows only p, g and the two numbers on the wire. He can find Alice's secret by trying 1, 2, 3 and so on, which ends quickly because p is tiny: there are only 22 secrets to try. In real TLS the browser uses X25519, with about 2^255 possible secrets, so searching is not possible. The author does not go into why finding the secret from the sent number is hard in mathematical terms. What the exercise confirms is that both sides get the same 32 byte secret from X25519, and that this secret is not equal to either of the two values that were sent.

</Step>

## What a certificate says

The key is settled, but one thing is left. Could Mallory set up a fake server and do a handshake with the browser himself? Key exchange only says that we and the other side hold the same key. It does not say who the other side is. That is the job of the **certificate**, a file that ties a host name to a public key and carries the signature of a **CA (certificate authority)** that the browser already trusts. The signature is the thing we met in the last lesson.

The exercise creates our own CA and a certificate for `shop.example.test`, and checks that

- the certificate names its subject as `CN=shop.example.test`
- the issuer is our CA, and the CA's public key verifies the signature on the certificate
- the CA's own certificate signs itself (issuer equals subject), which is the root of trust
- the certificate lasts 90 days and has a 32 byte SHA-256 fingerprint

So "trust" for a browser means that it already has the root CA's certificate on its list. If the signature on the server's certificate leads back to a CA on that list, the check passes. Certificates with several levels (intermediate CAs) were not run in this lesson. The book Web Application Security discusses SSL and TLS as well (book: Web Application Security chapter 18 page 195).

</Step>

## Three ways to be refused

The handshake that passed in the lab used a certificate that was right in every way. The exercise then kept the same server and changed the client or the certificate, one thing at a time. The client refused all three with an `SSLCertVerificationError`.

| Situation | Real error message (shortened) |
|---|---|
| The client does not trust our CA | `certificate verify failed: unable to get local issuer certificate` |
| The client means to visit `evil.example.test` but the certificate names `shop.example.test` | `certificate verify failed: Hostname mismatch` |
| A certificate that began 100 days ago and lasts 30 | `certificate verify failed: certificate has expired` |

The second case matters a great deal. A certificate from a trusted CA is no good if its name does not match the one we asked for. Otherwise Mallory could get a certificate for his own site from the same CA and use it to stand in for the bank. The author's own view is that this is why name checking should always be on, and why checking should never be switched off in code, even for a test (the author's opinion, not demonstrated).
