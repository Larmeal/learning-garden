## A password that is ' OR '1'='1

Mr. A's shop wrote its login form by joining strings into SQL, because that is the way most examples show (run: `exercises/08_injection.py`).

```python
def login_naive(name, password):
    sql = f"SELECT name, role FROM users WHERE name = '{name}' AND password = '{password}'"
    return sql, db.execute(sql).fetchall()
```

If the user enters `ann` and `pw-ann`, the query is right and returns one row. But if the user enters the password `' OR '1'='1`, the query becomes

```sql
SELECT name, role FROM users WHERE name = 'ann' AND password = '' OR '1'='1'
```

The `'` the user typed closed the password string early. The `OR '1'='1'` that follows is no longer text. It became a condition of the SQL that is always true. What was asserted: the attacker logs in without knowing the password and gets two rows back. Another way is to put `admin' --` as the name, where `--` turns the rest of the line (including the password check) into a comment, and the row of `admin` comes straight back.

All of it is **data typed by a user becoming part of the code**. It is the same cause as in the first lesson: the code believes what the customer sent a little too much (book: Web Application Security chapter 13 page 147).

</Step>

## Put the two ways side by side

In the lab below pick a form and what is typed. The left side is the query built by joining strings, with the part the user typed highlighted. Watch the `'` push the highlighted part out of the string. The right side is the same query with the values sent as **parameters**, where the database receives the SQL and the values separately, so a value can never become a command.

Switch to the search form and choose UNION. The attacker types text that closes the string and appends `UNION SELECT name, password FROM users`, which makes the product search return the names and passwords of users (what was asserted: the row `('admin', 'S3cretAdm1n')` is in the search result). The attacker needs the appended query to have the same number of columns as the original, which is two here. If the numbers differ SQLite reports an error, which is also how an attacker counts the columns (the exercise checks both).

<SqlInjectionLab client:visible lang="en" />

On the right side, whatever is typed, a user with a wrong password gets an empty result, and the UNION text is treated as the name of a product that does not exist. A normal login, and a search for `pen`, still work as before.

## Reading a password from a page that says only found or not found

Sometimes the page prints nothing from the query, only "found" or "not found". The attacker still gets data out, because he asks questions that can be answered yes or no. For example: does the first character of the admin password have an ASCII code greater than 79? Then he halves the range with every question.

The exercise does it. The admin password is `S3cretAdm1n`, 11 characters. The attacker asks with a query that hides the question inside the condition of the SQL, and looks only at whether any row comes back. The result rebuilt the whole password, using 85 requests: for each character one question asking whether a character exists at that place, then 6 or 7 questions to cut the 95 possible values down to one. Press play in the lab below and watch how every question cuts the range in half.

<BlindSqliLab client:visible lang="en" />

Notice that guessing the whole password in one go would be very hard, yet when characters can be asked one at a time the work falls from about 95 to the power 11 to 85 requests. Data that leaks a bit at a time is still data that leaks.

</Step>

## The fix, and what a parameter cannot do

The main fix is the **parameterised query**: `db.execute("SELECT name, role FROM users WHERE name = ? AND password = ?", (name, password))`. The exercise confirms that the earlier attack text (`' OR '1'='1`) gets nothing back, and that an honest user can still log in. The UNION text in the search box becomes plain text matched against product names, and no product has such a name.

But a parameter can replace only a **value**, not a column name or a table name. A user choice in `ORDER BY`, for example, cannot be written as `?`. The right way is an **allow list**, a list of names we permit ourselves (in the exercise `name` and `price`). Anything else is refused before it reaches SQL. The result: `price` passes, `price; DROP TABLE products` is refused, and the table still has its three rows (book: Web Application Security chapter 25 pages 259 to 265).

</Step>

<Step>

## Command injection: the same thing through a shell

The same problem appears when we join a user's text into a command of the operating system. The exercise uses our own Python as a program that prints the arguments it receives, and lets the user send the file name `report.txt & echo INJECTED`.

When we join the text onto the command and run it through a shell (`shell=True`), the shell reads the `&` sign as a separator of commands and runs the second one, `echo INJECTED`, as well. The output holds both `ARGS= ['report.txt']` and a line `INJECTED`, which nobody meant to happen. But if we pass a **list of arguments** and let the system call the program directly without a shell, the whole text arrives as one argument (`ARGS= ['report.txt & echo INJECTED']`) and nothing extra runs (book: Web Application Security chapter 13 page 155).

The principle is the same as for SQL. Data and commands must travel apart. Use the way the system gives for keeping them apart before thinking about filtering characters.

<Callout type="note" title="What we did not try">

The exercise ran against SQLite and the shell of Windows. Other databases such as MySQL and PostgreSQL differ in the details (for example the way comments are written and the names of functions). NoSQL injection and injection through other languages, such as LDAP, were not run in this lesson.

</Callout>
