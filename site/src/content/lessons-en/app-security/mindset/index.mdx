## A shop that believes everything the customer sends

Mr. A opens a small online shop over a weekend. He writes all the code himself and is sure nobody will care about such a small shop. Let us look at what he wrote. The shop sells a `pen` for 20, a `book` for 150 and a `bag` for 900, and has two orders: order 1 belongs to Ann and order 2 belongs to Bob, who bought the bag.

The first function reads an order by the number it is given (run: `exercises/01_mindset.py`).

```python
def get_order_naive(order_id: int, who: str):
    return ORDERS.get(order_id)

leak = get_order_naive(2, "ann")     # ann asks for order 2
# {'owner': 'bob', 'item': 'bag', 'qty': 1}
```

Ann logs in and asks for order 2, and the function hands it over, although the order is Bob's. The argument `who` is passed in and never used.

The second function works out the price at checkout. Mr. A lets the browser send the price, "so we do not have to look it up again".

```python
def checkout_naive(cart):
    return sum(line["price"] * line["qty"] for line in cart)

checkout_naive([{"item": "bag", "qty": 1, "price": 1}])     # 1
```

The 900 baht bag is charged 1 baht, because the customer said so. The third function is the search, which takes a number `limit` from the URL and passes it straight to the database. If someone sends 10,000,000, the database does that much work (`search_naive(10_000_000)` returns 10,000,000).

The three functions fail in different ways, but they share one cause: **they believe what the customer sent a little too much**. We will see that almost every flaw on this path comes from that same cause.

</Step>

## The three things to protect

Look back at the three functions. Each one loses something different. The first lets Bob's data reach Ann. The second lets data that nobody should change (the price) be changed. The third could keep other customers out, because the database is busy with one person's job.

The book API Security in Action calls these three the **CIA Triad** (book: API Security in Action section 1.4.2 page 14).

| Letter | Name | Means | Mr. A's function |
|---|---|---|---|
| C | Confidentiality | information can be read only by the people who should read it | reading Bob's order |
| I | Integrity | nobody creates, changes or deletes data without permission | setting the price |
| A | Availability | legitimate users can get in when they need to | asking for 10,000,000 rows |

The book adds that there are other goals too, such as accountability (knowing who did what) and non-repudiation (not being able to deny what you did). Still, the three above are the ones we ask about whenever we look at a flaw: what does it destroy?

The fix is the same shape in all three cases: move the rule to the server. `get_order_checked` compares `order["owner"] == who`, `checkout_checked` looks the price up in `PRICES` and ignores the `price` that was sent, and `search_checked` caps `limit` at 100. What ran: Ann is refused, the bag is charged 900, and the request for 10,000,000 rows gets 100.

</Step>

## How many places does one request pass

When a customer presses the order button, the request does not go straight to the database. It passes five stops: the browser, the network, the web server, the app code and then the database. Two of those hops cross from a place we do not control into our own system, and each crossing is called a **trust boundary**. The five stops and the two crossings are asserted in `01_mindset.py`.

Pick the attacks in the lab below one at a time and press play. The red stop is where that attack lands. The bar at the bottom says what is lost (C, I or A) and which defence stops it. Notice that the attacks do not all sit at the same stop: SQL injection and IDOR happen in the app code, while XSS and CSRF happen on the browser side.

## Four questions before writing code (a threat model)

Before we go through the flaws one by one, there is a way of thinking that works for any system, called **threat modelling**. You look at a diagram of the system and ask a few questions: what has value (the assets), who or what could harm it (the threats), how could they get in (the attack surface), and what do we have in the way (the defences). API Security in Action offers a way of sorting threats called **STRIDE**. It has six letters, and each one destroys something different (book: API Security in Action chapter 1 page 18).

| Threat | What it destroys | In Mr. A's shop |
|---|---|---|
| Spoofing | authentication | someone pretends to be Ann |
| Tampering | integrity | setting the price at checkout |
| Repudiation | non-repudiation | deleting an order and saying it was not you, because there is no log |
| Information disclosure | confidentiality | Ann reads Bob's order |
| Denial of service | availability | asking for 10,000,000 rows |
| Elevation of privilege | authorization | an ordinary user deletes another user |

The exercise checks that the six really destroy six different things. The most useful habit is to put this table next to the diagram of five stops and ask, stop by stop, "can all six happen here?" You do not have to answer everything in one round. The aim is to see what we forgot to think about.

<Callout type="note" title="Why start with a way of thinking and not a tool">

Web Application Security says in chapter 7 that what separates a safe architecture from an unsafe one is often a simple signal you can see from outside: are there several layers of defence, or was the authentication system written from scratch although a tested one exists (book: Web Application Security chapter 7 page 99). So we spend this lesson on the way of looking, and meet the tools in the next one.
