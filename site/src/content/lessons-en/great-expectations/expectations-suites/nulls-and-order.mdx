## Nulls in the age column

The script `19_catalog_nulls.py` uses `age = [10, None, 30, 40, 400]` (one null row) and a `plan` column with one null row. The result of each expectation (GX 1.24.1):

| Expectation | Result | `element_count` | `missing_count` | `unexpected_count` / `observed_value` |
|---|---|---|---|---|
| `ExpectColumnValuesToNotBeNull(age)` | fail | 5 | this key is absent | unexpected 1 (the null row) |
| `ExpectColumnValuesToBeNull(age)` | fail | 5 | this key is absent | unexpected 4 (rows that are not null) |
| `ExpectColumnValuesToBeBetween(age, 0..120)` | fail | 5 | 1 | unexpected 1 (the value 400) |
| `ExpectColumnValuesToBeInSet(plan, [free, pro])` | fail | 5 | 1 | unexpected 1 (`gold`) |
| `ExpectColumnValuesToBeUnique(id)` | pass | 5 | 0 | unexpected 0 |
| `ExpectColumnValuesToMatchRegex(plan)` | pass | 5 | 1 | unexpected 0 |
| `ExpectColumnMaxToBeBetween(age, 0..120)` | fail | | | observed 400.0 |
| `ExpectColumnMeanToBeBetween(age, 0..120)` | pass | | | observed 120.0 |

What we see in the table:

1. Expectations that test a range, a set of values or a pattern do not count null as wrong, but they report `missing_count` separately.
2. The pair `NotBeNull` and `BeNull` treat null as their own target, so there is no `missing_count` in the result, and `BeNull` counts rows that are not null as wrong.
3. Aggregates (`max`, `mean`) are computed from values that are not null: the reported mean is 120.0, which equals (10 + 30 + 40 + 400) ÷ 4. If you divided by 5 you would get 96.0.

## The order of results is not the order of the suite

When we read the results as a list, we tend to assume that `result.results[i]` matches `suite.expectations[i]`. Script `19` prints the two orders side by side.

```text
suite order : not_be_null(age), be_null(age), between(age), in_set(plan), unique(id),
              regex(plan), max(age), mean(age), distinct(plan), pair, compound, row_count, column_count
result order: not_be_null(age), be_null(age), between(age), max(age), mean(age),
              in_set(plan), regex(plan), distinct(plan), unique(id), pair, compound, row_count, column_count
```

`max(age)` and `mean(age)` moved up next to the other `age` rules, and `in_set`, `regex` and `distinct` of `plan` went together too.

The cause is in the source of `Validator.process_expectations_for_validation` (read from the source). It groups expectations by the value of the argument named `column` before it evaluates them (the method name says "sort by column"). The order of the groups is the order in which each column first appears. Inside a group the original order is kept. Expectations that have no `column` argument (table rules, column pair rules) are put together as one more group that follows the same rule: ordered by first appearance.

<Callout type="warn" title="Match results to rules through the config">
If you write code that zips `suite.expectations` with `result.results` by position, the results get the wrong labels when the suite switches between columns. Match them with `r.expectation_config.type` and `kwargs`, as `16_defect_catalog.py` and `19_catalog_nulls.py` do. In [lesson 0](/en/great-expectations/foundations/) there is one more case where the order changes: an expectation that raised an exception is moved to the front.
</Callout>
