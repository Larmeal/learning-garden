## GX does three things

1. Reads one batch of data (a DataFrame, a table, a file)
2. Computes facts about that data and compares them with the rules
3. Sends the result back with a report

There is no fourth step that fixes the data, moves the data, or stops the pipeline for you. The script `16_defect_catalog.py` compared the DataFrame before and after validation in all nine cases and got the same values every time. And when the data fails, `Checkpoint.run` returns a `CheckpointResult` with `success=False`. It does not raise (`03_traps.py`). The pipeline has to read the result and decide for itself.

</Step>

## Where to put the check

This table is design guidance. It was not tested. The choice depends on which part of the pipeline you control.

| Check point | What it can catch | Limit |
|---|---|---|
| After receiving raw data, before transforming | The source sent data in the wrong shape or incomplete | Cannot see errors made by our own transforms |
| After transforming, before writing to the target | Errors from joins, dropped rows, wrong calculations | Whatever is wrong at the source is mixed with our own errors, so it is hard to find the cause |
| Before users read (the target table) | The data users really see | The bad data has already been written. You need a way to roll back |

Using a different suite for each of the first two points is one option, because the rules for raw data and for transformed data are not the same. [Lesson 10](/en/great-expectations/pipeline-integration/#where-to-put-it) goes into how to write the code.

<Callout type="note" title="GX is not a data store">
GX stores validation results, the definitions of the rules, and reports. It does not store the data it checks. The DataFrame passed in as a parameter at run time is not saved with the batch definition (tested in `01_first_validation.py`).
</Callout>
