## One result, four meanings

When you read the result of a suite, there are four cases to tell apart, because each one needs a different response.

| case | caused by | what to do |
|---|---|---|
| the data has a problem | a value in the data breaks a rule (`success=False`) | find the bad rows, decide whether to stop or quarantine the data |
| the expectation is broken | the rule cannot be used, for example a column is missing (`success=False` with `exception_info`) | fix the rule, or find out whether the data structure changed |
| the suite is empty | there are no rules to evaluate at all (`success=True`, `evaluated_expectations=0`) | treat it as a failure and find out why the rules are gone |
| a quiet pass on an empty table | every rule is a column map rule (`success=True`) | add a row count rule, see the page "[Passing with no data: who passes?](/en/great-expectations/reading-results/vacuous/)" |

The last two make `success` `True` even though nothing was really checked. So looking only at the `success` value is not enough.

</Step>

## The order of the questions

The order matters. First check that there are rules to evaluate, then check for exceptions, and only then read whether the data is wrong.

## A function that was tested

```python
def triage(result) -> str:
    if result.statistics["evaluated_expectations"] == 0:
        return "empty suite"
    broken = [
        x for x in result.results
        if any(isinstance(v, dict) and v.get("raised_exception")
               for v in (x.exception_info or {}).values())
    ]
    if broken:
        return f"broken expectation ({len(broken)})"
    if not result.success:
        return "data problem"
    return "ok"
```

The results from `21_formats_empty.py` part 5 (GX 1.24.1):

| case | result of `triage` |
|---|---|
| good data, the `age` rule, not empty | `ok` |
| the value 20 is over the rule `max=15` | `data problem` |
| the rule refers to a column `nope` that does not exist | `broken expectation (1)` |
| a suite with no expectations at all | `empty suite` |

The code has to walk through the values of `exception_info` and filter with `isinstance(v, dict)`, because its shape comes in two forms. An expectation that broke gets a dict whose keys are the metrics that failed (seen on the page "[What kinds of bad data GX can catch](/en/great-expectations/foundations/defects/)" in [lesson 0](/en/great-expectations/foundations/)). An expectation that did not break gets a flat dict `raised_exception: False, exception_traceback: None, exception_message: None`, whose values are a boolean and `None`, not dicts.

<Callout type="note" title="Scope">
Tested on pandas and an ephemeral context. This function is an example of grouping the outcomes. It is not a GX API.
</Callout>

## One expectation cannot be used in two suites

After an expectation has been added to a suite, you cannot add it to another suite directly (part 6 of the script).

```text
RuntimeError: Cannot add Expectation because it already belongs to an ExpectationSuite.
              If you want to update an existing Expectation, please call Expectation.save().
              If you are copying this Expectation to a new ExpectationSuite, please copy it first ...
after copy + id=None: second suite has 1 expectation(s)
```

The way that was tested: `copied = shared.copy()`, then set `copied.id = None` before `add_expectation`. The second suite then has this expectation (1 in total). An easier way is to create a new object with the same parameters every time. The script `21` uses a factory function like this.

</Step>
