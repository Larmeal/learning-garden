## Four levels, how the results differ

The data is `age = [10, None, 30, 400]`. The rules are `ExpectColumnValuesToBeBetween(0..120)` (column map) and `ExpectColumnMaxToBeBetween(0..120)` (aggregate), run at all four `result_format` levels (`21_formats_empty.py` part 1, GX 1.24.1). Switch tabs to see the keys of `result`.

/>

Two observations. `BOOLEAN_ONLY` makes `result` an empty dict (even `element_count` is gone). And the aggregate expectation does not change from BASIC upward, because it has only one value to report.

A higher level means more metrics to compute (the main page of [lesson 4](/en/great-expectations/reading-results/#result_format-more-detail-costs-more) has the numbers 10, 13, 19, 19 for the example suite). So COMPLETE is slower than BOOLEAN_ONLY on big data. The real speed on big data was not measured on this path.

## Finding the bad rows

At the COMPLETE level there are three extra options. We tried them together (part 2 of the script).

```python
vd.run(
    batch_parameters={"dataframe": df},
    result_format={
        "result_format": "COMPLETE",
        "include_unexpected_rows": True,
        "return_unexpected_index_query": True,
        "unexpected_index_column_names": ["id"],
    },
)
```

The result:

```text
unexpected_index_list:  [{'age': 400.0, 'id': 4}]
unexpected_rows:           id    age
                        3   4  400.0
unexpected_index_query: df.filter(items=[3], axis=0)
```

- `unexpected_index_column_names` makes `unexpected_index_list` a list of dicts that hold the values of the columns you chose (here `id`), instead of raw position numbers. So a bad row can be traced back to its record in the source system with a business key.
- `include_unexpected_rows` puts the whole rows into `unexpected_rows` as a DataFrame.
- `unexpected_index_query` is the command that pulls out the bad rows. On pandas it is `df.filter(...)`. On SQL it is a SQL statement ([lesson 12](/en/great-expectations/custom-expectations/column-map/#the-sql-that-gx-builds-from-that-condition) shows an example that GX builds on SQLite).

<Callout type="warn" title="Whole rows are big">
`include_unexpected_rows` stores all the bad rows in the result. If a million rows are bad, the result saved to the store is big too. The real size was not measured.
</Callout>

## How many bad values are in the sample

The data is 60 rows that are all bad (`x = 200..259`, rule 0..100), run at SUMMARY (part 3).

| `partial_unexpected_count` set to | `unexpected_count` | size of `partial_unexpected_list` |
|---|---|---|
| 3 | 60 | 3 |
| 20 | 60 | 20 |
| not set | 60 | 20 |

`unexpected_count` always counts every row. What gets cut is the list of examples. The default is 20, as the experiment showed.
