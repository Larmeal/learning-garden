## Three pages to know

`28_data_docs_text.py` builds a file context with a suite of two rules (`name` is not null, `age` between 0 and 120) and a checkpoint that has `UpdateDataDocsAction`. It runs on data that fails both rules, then extracts the visible text from the HTML (GX 1.24.1). This is what it found.

| page | text you see |
|---|---|
| `index.html` | the heading "Data Docs created by Great Expectations", the tabs "Validation Results" and "Expectation Suites", a Clear Filters button, and a footer that invites you to subscribe to a newsletter (it can be turned off with `show_how_to_buttons`) |
| `expectations/people_suite.html` | the suite name, the GX version, "This Expectation suite currently contains 2 total Expectations across 2 columns.", then one section per column, for example `age`: "values must be greater than or equal to 0.0 and less than or equal to 120.0." and `name`: "values must never be null." |
| `validations/.../<run>/<batch>.html` | the status Failed or Passed, a Statistics table (Evaluated, Successful, Unsuccessful, Success Percent), the run and batch information, then one section per column |

The suite page is the expectations written in human language. A data owner can read it and check the rules without reading any code.

## The validation result page: result_format changes what you see

We ran the same checkpoint twice, changing only the `result_format` of the checkpoint. Switch tabs to see the text of the `age` and `name` sections on the validation result page.

If you give Data Docs to a team, the `BOOLEAN_ONLY` level gives a page that can only say that something failed, and the team has to find the cause on their own. The `COMPLETE` level gives the bad values and the bad rows on one page. This matches what [lesson 4](/en/great-expectations/reading-results/) said: a detailed result costs extra computation.
