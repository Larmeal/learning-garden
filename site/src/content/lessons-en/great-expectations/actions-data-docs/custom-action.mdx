## An action that writes a status file

The main lesson showed the outline of a `ValidationAction`. Here it is run for real (`27_actions_notify.py` part 3, GX 1.24.1).

```python
class WriteStatus(ValidationAction):
    type: str = "write_status"
    name: str = "write_status"
    path: str = ""

    def run(self, checkpoint_result, action_context=None):
        Path(self.path).write_text("ok" if checkpoint_result.success else "failed")
        return {"written": self.path}

cp = gx.Checkpoint(name="cp_custom", validation_definitions=[vd],
                   actions=[WriteStatus(path=str(out))])
cp.run(batch_parameters={"dataframe": df})
```

The printed result:

```text
file content: failed | saw: {'context_type': 'ActionContext', 'success': False}
```

- The data made the suite fail, so the file contains `failed`.
- `run` receives the full `CheckpointResult` (you can read `.success` and reach `run_results`, as on the "[Read a CheckpointResult](/en/great-expectations/validation-checkpoints/checkpoint-result/)" page of [lesson 7](/en/great-expectations/validation-checkpoints/)) and an `ActionContext`.
- The fields of an action (here `path`) are declared as pydantic fields and passed when you create it.
- The `type` field is the name of the action's type when a checkpoint is saved to a file. (The class is put into a registry by its `type` value when it is defined, according to a comment in `MetaValidationAction` in the source.)

Part 5 of the script tests the trap that custom expectations fall into ([lesson 12](/en/great-expectations/custom-expectations/)), this time with actions. Process A creates a checkpoint that contains `WriteStatus` in a file context. Then process B, which did not import this class, loads the context.

```text
B: ValidationActionRegistryRetrievalError | Invalid action configuration; no action of type write_status found.
```

This differs from a custom expectation, where the suite loads quietly empty. For an action, `get_context()` raises at once and names the type it could not find, so the problem shows up sooner. Both cases have the same root cause: the class must be imported before it is in the registry.

## An action that raises

`Boom.run` raises `RuntimeError("webhook is down")` on purpose. The script runs a checkpoint that has `Boom` as its only action.

```text
run raised: RuntimeError | webhook is down
results stored anyway: 1
```

So a Slack outage does not make the validation result disappear. But it does make `cp.run()` raise, and the actions after it do not run (tested in `06_actions_docs.py`). A pipeline that has no `try/except` around it will fail the whole job because of an optional notification.

## A safe pattern

```python
def run(self, checkpoint_result, action_context=None):
    try:
        post_to_my_service(checkpoint_result)
    except Exception as e:
        logging.warning("notification failed: %s", e)
    return {}
```

This pattern is a suggestion based on the behavior that was tested (an action that raises drags the checkpoint down). The code itself was not run.

<Callout type="note" title="Side effect of swallowing the error">
An action that swallows the error will not tell anyone that the notification failed. Always write a log. Otherwise the team will think nothing happened, when in fact the message never arrived.
</Callout>
