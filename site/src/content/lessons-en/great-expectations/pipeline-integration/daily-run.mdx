## Set up the situation

The folder has the files for 1 and 3 January 2024. The file for 2 January never arrives (`29_pipeline_policies.py` part 2, GX 1.24.1). The checkpoint checks that the row count is at least 1, through a daily batch definition whose regex is anchored at the start and the end (see the page "File name regex" of [lesson 6](/en/great-expectations/datasources-batches/#two-families-of-partitioner)).

def run_for(day: date):
    return daily_cp.run(batch_parameters={"year": day.year, "month": day.month, "day": day.day})

The second case is the trap from [lesson 6](/en/great-expectations/datasources-batches/#which-file-does-get_batch-pick), confirmed here at the checkpoint level too. The result tells you which file was checked in `meta["batch_spec"]["path"]` of each validation result. The script uses this field to print the file name.

## Run the same day again

Run `run_for(date(2024, 1, 3))` twice. The number of results in the results store goes up by 2 (not 1). The older result is not overwritten, and every run has its own `run_time` (see the page "[Running Again](/en/great-expectations/first-validation/run-again/#things-to-know-when-you-run-every-day)" of [lesson 2](/en/great-expectations/first-validation/)). The consequences:

- A backfill is direct: just pass an old date. The results of the older runs are all kept.
- If you want to know whether a day passed, you must choose the latest result of that day yourself. GX does not do this for you.
- Repeated results of the same day can contradict each other (the first run failed, the second passed after the file was fixed). The system that reads the results must know which run to trust.

<Callout type="warn" title="Not tested">
I tested only CSV files in one folder with an ephemeral context. I did not test a real scheduler, two jobs running at the same time, or a data source that is a SQL table, although the principle of passing all the parameters applies in the same way.
</Callout>
