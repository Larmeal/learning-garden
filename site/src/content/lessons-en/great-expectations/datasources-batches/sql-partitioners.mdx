## The table used for the experiment

The table `events` in SQLite has 5 rows. The column `day` stores the date as text, `YYYY-MM-DD`.

```text
id  day         amount
1   2024-01-30  5
2   2024-01-31  7
3   2024-02-01  9
4   2024-02-01  11
5   2024-02-02  3
```

```python
src = context.data_sources.add_sqlite("sq", connection_string=f"sqlite:///{db}")
asset = src.add_table_asset("events", table_name="events")
by_month = asset.add_batch_definition_monthly("monthly", column="day")
```

The same table can be cut into batches at three levels. The method name says the level, and it takes the name of the date column through the parameter `column`. Results from part 1 of `24_batch_details.py` (GX 1.24.1).

## Which rows one batch becomes

When you call `get_batch(batch_parameters={"year": 2024, "month": 2, "day": 1})`, GX does not pull the whole table and filter it in Python. It sends the condition to the database, and the database filters. In the test in `24`, this batch gave 2 rows, matching the table, and the `batch_spec` of the batch names the partitioner as `partition_on_year_and_month_and_day`.

## Things to know

- No parameters: on files you get the latest batch. On SQL, script `24` called `get_batch()` with no parameters and got no error, but did not check which batch it got. If your daily pipeline reads a table, always pass the full parameters, as in the file case.
- SQL identifiers are numbers (`'year': 2024`), unlike files, where they are strings (see the main lesson).
- This example stores the date as text in SQLite. Other databases that store a real date type were not tested.
