## Change only the DataFrame

Script `18_result_anatomy.py`, part 3, uses the same validation definition and runs it twice.

```python
day1 = pd.DataFrame({"id": [1, 2, 3, 4], "age": [10, None, 30, 400], "name": ["a", "b", None, "d"]})
day2 = pd.DataFrame({"id": [1, 2, 3, 4], "age": [10, 20, 30, 40],   "name": ["a", "b", "c", "d"]})

r1 = vd.run(batch_parameters={"dataframe": day1})
r2 = vd.run(batch_parameters={"dataframe": day2})
```

The printed result (GX 1.24.1):

```text
day1 success: False | day2 success: True
run ids differ: True
results kept in the store: 2
```

One suite and one validation definition give different results depending on the data. The results of both runs are kept in the validation results store, and they do not overwrite each other.

## Things to know when you run every day

1. Every run computes everything again. GX does not remember metrics between runs (measured in `02`: running again gave 19 and 19 metrics).
2. `run_id` has the `run_time` of each run. You can use it to tell old results from new ones.
3. The results store in an ephemeral context lives in memory and disappears when the script ends. If you want to keep results across days, you need a file context ([lesson 5](/en/great-expectations/context-stores/#two-kinds-of-context-you-can-actually-use)).
4. The data in the DataFrame must come from your own code. In this example it is passed as a variable. If the data comes from a file or a table, the batch definition does the job of choosing the batch ([lesson 6](/en/great-expectations/datasources-batches/#a-batch-definition-is-a-recipe-not-data)).
