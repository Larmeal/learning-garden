## Two layers of running

| Layer | Job | Result |
|---|---|---|
| Validation Definition | Validates one piece of data with one suite | `ExpectationSuiteValidationResult` |
| Checkpoint | Runs several validation definitions with shared parameters, then fires actions | `CheckpointResult` |

A validation definition is good for experiments and one-off checks. A checkpoint is the main way in production, because it attaches actions and joins several checks into one job.

```python
vd = context.validation_definitions.add(
    gx.ValidationDefinition(name="users_vd", data=batch_definition, suite=suite)
)
checkpoint = context.checkpoints.add(
    gx.Checkpoint(name="users_daily", validation_definitions=[vd])
)
result = checkpoint.run(batch_parameters={"dataframe": df})
```

</Step>

## CheckpointResult

```python
result = checkpoint.run(batch_parameters={"dataframe": df})
result.success            # True when every validation passes
result.run_results        # dict: ValidationResultIdentifier -> ExpectationSuiteValidationResult
result.describe()         # a summary as JSON
```

`run_results` has one entry per validation definition. The key is made of the suite name, the `run_id` and the batch id. Every validation in a checkpoint gets the same `run_id`, so you can tell they are in the same run.

The parameters `batch_parameters` and `expectation_parameters` that you pass to `run()` are given to every validation definition in the same way. `result_format` is a field of `Checkpoint` itself. If two validation definitions use different kinds of batch definition (one daily, one the whole table), a single set of parameters must be compatible with both.

</Step>

## The trap: no raise when the data fails

```python
result = checkpoint.run(batch_parameters={"dataframe": bad_df})
# no exception, result.success == False
```

Measured in `03_traps.py`: the checkpoint returns a result with `success=False` as normal, without raising. GX treats failing data as a result of the check. The side effect is that a pipeline that calls `checkpoint.run(...)` and does not check `.success` always keeps going ([lesson 10](/en/great-expectations/pipeline-integration/) is about how to block it).

<Callout type="warn" title="What does make it raise">
Failing data does not make it raise, but these things do: no validation definition in the checkpoint, a referenced object that has not been added to the context, a batch that was asked for but does not exist (`NoAvailableBatchesError`), and an action that errors ([lesson 9](/en/great-expectations/actions-data-docs/)).
</Callout>
