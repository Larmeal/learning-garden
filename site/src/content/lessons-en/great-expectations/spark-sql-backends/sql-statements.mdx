## Capture the statements as SQLite sees them

The table `sales` has four rows. The column `d` holds the date as text. The suite has one rule: `amount` is not null. We run the batch of 2024-01-02. The script `30_sql_where_support.py` wraps `SqlAlchemyExecutionEngine.execute_query` and compiles each statement with the dialect of the engine itself. What you see is the SQL that SQLite really received (GX 1.24.1).

```sql
-- 1. Find the batches that exist
SELECT distinct(CAST(CAST(STRFTIME('%Y', d) AS INTEGER) AS VARCHAR) || CAST(CAST(STRFTIME('%m', d) AS INTEGER) AS VARCHAR)
                || CAST(CAST(STRFTIME('%d', d) AS INTEGER) AS VARCHAR)) AS concat_distinct_values,
       CAST(CAST(STRFTIME('%Y', d) AS INTEGER) AS INTEGER) AS year,
       CAST(CAST(STRFTIME('%m', d) AS INTEGER) AS INTEGER) AS month,
       CAST(CAST(STRFTIME('%d', d) AS INTEGER) AS INTEGER) AS day
FROM sales

-- 2. Count the rows of the batch
SELECT count(*) AS "table.row_count"
FROM (SELECT * FROM sales WHERE CAST(STRFTIME('%Y', d) AS INTEGER) = 2024
        AND CAST(STRFTIME('%m', d) AS INTEGER) = 1 AND CAST(STRFTIME('%d', d) AS INTEGER) = 2) AS anon_1

-- 3. Count the nulls of amount in the batch
SELECT sum(CASE WHEN (amount IS NULL) THEN 1 ELSE 0 END) AS "column_values.nonnull.unexpected_count"
FROM (SELECT * FROM sales WHERE ... the same condition ...) AS anon_1
```

The result is `success: False`, because day 2 has one row where `amount` is null.

## What to notice

1. Statement 1 has no WHERE. To find the batches, GX must sweep the whole column `d`. On a small table you do not feel it. On a table of hundreds of millions of rows this is a cost on its own, separate from checking the real batch. Whether the next run repeats it was not tried.
2. Statements 2 and 3 have a WHERE. The database filters first, so the data of other days is not counted in the result.
3. The date expression differs by dialect. On SQLite it is `CAST(STRFTIME('%Y', d) AS INTEGER)`. Other databases use their own function (not tried with other databases). An expression that wraps the column `d` generally makes an index on this column unusable. This is an inference from the shape of the SQL; the execution plan was not measured.
4. The main lesson once showed SQL in the form `EXTRACT(year FROM d)`. That is the neutral form that SQLAlchemy compiles when no dialect is given. The one that SQLite received is the `STRFTIME` above.

<Callout type="warn" title="Not tried">
We did not try any database other than SQLite. We did not look at the execution plan (EXPLAIN), and we did not measure the time of statement 1 as the table grows. So the conclusion about cost is about the shape of the statements, not a measured number.
</Callout>
