## The experiment

The main lesson read from the source that `ValidationGraph` retries a metric up to 3 times. Part 4 of the script `26_registry_domains.py` tests this with a metric that always fails (GX 1.24.1, pandas).

```python
CALLS = [0]

class ColumnAlwaysFails(ColumnAggregateMetricProvider):
    metric_name = "column.always_fails"

    @column_aggregate_value(engine=PandasExecutionEngine)
    def _pandas(cls, column, **kwargs):
        CALLS[0] += 1
        raise RuntimeError("this metric never works")

class ExpectColumnAlwaysFails(ColumnAggregateExpectation):
    metric_dependencies = ("column.always_fails",)
    args_keys = ("column",)
    def _validate(self, metrics, runtime_configuration=None, execution_engine=None):
        return {"success": True, "result": {"observed_value": metrics["column.always_fails"]}}
```

The suite has two rules: `ExpectColumnAlwaysFails(column="x")` and `ExpectColumnMaxToBeBetween(column="x", 0..10)`, on the data `x=[1, 2, 3]`.

```text
calls to the failing metric function: 3
column_always_fails          success=False raised=True
column_max_to_be_between     success=True  raised=False
```

## How to use this

- If you see `success=False` and an `exception_info` that came from a metric computation, do not go and search the data yet. Read the exception message first (the sequence of questions in [lesson 4](/en/great-expectations/reading-results/)).
- A metric function that is slow or that calls the outside (for example, a call to a service) can be called up to 3 times when it fails. Design it to have no side effects.
- The number 3 matches `MAX_METRIC_COMPUTATION_RETRIES`, read from the source `validation_graph.py`. I did not test whether there is a delay between the attempts.

<Callout type="warn" title="Not tested">
I tested only an aggregate metric on pandas. A metric that fails on SQL or Spark (for example, the database drops the connection halfway) may be retried differently. I did not test that.
</Callout>
