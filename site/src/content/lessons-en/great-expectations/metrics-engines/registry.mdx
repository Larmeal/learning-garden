## What is in the registry

Every metric written as a class (for example `ColumnMax`) registers itself at import time in `registry._registered_metrics`. The key is the metric name, and the list `providers` says which engines have an implementation. Part 1 of the script `26_registry_domains.py` counts this for the installed GX 1.24.1.

| What is counted | Number |
|---|---|
| Registered metric names | 315 |
| With an implementation for pandas | 241 |
| With an implementation for SQL (SQLAlchemy) | 255 |
| With an implementation for Spark | 254 |
| With all three engines | 184 |
| On pandas but not on SQL | 57 |

The numbers are counted from the registered implementations. I did not run every metric on every engine, and Spark was not run at all on this path.

## What happens when an implementation is missing

If an expectation needs a metric that has no implementation for the engine that is running, GX does not raise. It stores the result as `success=False` with the message `No provider found` in `exception_info` (measured with a custom expectation whose condition was written only for pandas and then run on SQLite, in lesson 12). The result looks like "the data did not pass", but the real problem is that the engine does not support it.

An example from the count: the metrics of the family `column_values.dateutil_parseable.*` exist on pandas but not on SQL (the first five in the list of 57 are `column.parameterized_distribution_ks_test_p_value` and the four `dateutil_parseable` metrics). So expectations that need those metrics should not be run on data that lives in a database.

<Callout type="warn" title="Before you put a suite on SQL or Spark">
Having an expectation name to use does not mean your engine supports it. Run the suite on sample data on that engine first, then read every `success=False` result and check whether it has `No provider found` (use the sequence of questions from the page "Read a failed result in a systematic way" in lesson 4). This registry is only a shortcut for a look ahead.
</Callout>
