## There is no Spark cluster manager

Kubernetes has no role like a Master or a ResourceManager that Spark has to talk to. What Spark talks to is the **API server** of Kubernetes, to create and watch pods. Choosing which node a pod goes to is the job of `kube-scheduler`, and Spark is not involved in that.

| Part involved | Does |
|---|---|
| `spark-submit` | Builds the driver pod from the config (several feature steps), creates the pod and a ConfigMap, then watches the pod status (`KubernetesClientApplication`) |
| API server | The only place where everyone reads and writes the pod status |
| driver pod | A pod that runs `spark-submit` again inside itself, in client mode (from `entrypoint.sh`, the command `driver`) |
| `ExecutorPodsAllocator` (in the driver) | Compares the number of executors wanted with the pods that exist, and creates more executor pods itself |
| executor pod | A JVM that registers with the driver and then receives tasks |

The important difference from YARN is that **the driver itself orders the executors to be created**. There is no AM in between. See the sequence (switch to the scenario where the driver pod is deleted).

## How many executor pods the driver asks for at a time

The driver does not create them all at once. `ExecutorPodsAllocator` works in rounds. Each round creates no more than `spark.kubernetes.allocation.batch.size` pods (default 20), then waits `spark.kubernetes.allocation.batch.delay` (1 second) before the next round. Try changing the number wanted.

<K8sBatchLab client:visible lang="en" />

What to know:

- If you ask for many executors (hundreds), creating the requests takes several seconds before Kubernetes even starts placing the first pod. You can adjust `batch.size` if the cluster can take it.
- `spark.kubernetes.allocation.maxPendingPods` (unlimited by default) limits the number of pods that are stuck in Pending at the same time. It stops one app from flooding the scheduler with requests.
- Spark does not fix a pod that is stuck in Pending for too long. If the nodes are not enough, the pod waits for the cluster autoscaler or until a node is free. `spark.kubernetes.allocation.executor.timeout` (600 seconds) deletes only the pods that Kubernetes has not yet shown in the Pending state.

</Step>

## Why the executors disappear when the driver pod is deleted

The executor pod that `BasicExecutorFeatureStep` builds has an **ownerReference that points to the driver pod** (set as the controller). When the driver pod is deleted or gone, the garbage collector of Kubernetes deletes the objects whose owner is gone. The result is that no cluster manager has to chase the remaining executors. In Kubernetes, "shutting down the app" means deleting the driver pod.

The ConfigMap of the Spark conf and the other resources that the driver needs are tied to the driver pod with an ownerReference in the same way (`KubernetesClientApplication.run`).

An executor that dies on its own along the way is different. The driver watches the pod status through a watch (`ExecutorPodsWatchSnapshotSource`) and, as a backup, through polling (`ExecutorPodsPollingSnapshotSource`). When it learns that a pod is gone, it asks for a new pod to replace it, until `spark.executor.maxNumFailures` is reached and the app fails.

</Step>

## Compare with YARN and Standalone

| | standalone | YARN | Kubernetes |
|---|---|---|---|
| Who divides the resources | Spark's Master | ResourceManager | kube-scheduler |
| Who asks for executors for the app | `StandaloneAppClient` in the driver | ApplicationMaster | `ExecutorPodsAllocator` in the driver |
| Unit that runs | process started by a Worker | container | pod |
| Driver can be in the cluster | No, for Python | Yes (cluster mode, in the AM) | Yes (the driver pod) |
| Shut down the app by | the driver ends | the driver or AM ends | deleting the driver pod (the executors go with it) |

Kubernetes needs some extra settings that the other cluster managers do not have. For example, the image that contains Spark (`spark.kubernetes.container.image`), the namespace, a service account that has the right to create pods, and the resources of the pod (`spark.kubernetes.executor.request.cores` is different from `spark.executor.cores`, which is the number of tasks that run at the same time).

</Step>
