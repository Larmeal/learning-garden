## Who does what

A Spark application has three roles: the driver, which holds your program and makes the plan; the executors, which do the computing; and the cluster manager, which allocates machines. See when each role comes in and what it does, along the timeline of one application (you can choose to end with `collect()` or `write`).

<RolesFlowLab client:visible lang="en" />

Summary from the picture:

| Role | Does | Does not do |
|---|---|---|
| Driver | Holds your code, builds the plan, asks for executors, splits the work into tasks, sends the tasks and collects the status | Does not compute the data (unless you tell it to pull the result back) |
| Cluster manager | Knows how much free capacity each machine has, and starts executors as the driver asks | Does not hold data, does not hand out tasks, and is not between the driver and the executors once the executors are started |
| Executor | Receives tasks, reads partitions from storage, computes, keeps the cache and writes the result | Does not decide what work to do |

Your PySpark code runs in a Python process and talks to Spark's JVM through Py4J. The heavy computing happens in the JVM on the executor side, except for Python UDFs, which have to call an extra Python process (lesson 8).

## How your machine runs

`get_spark()` in `spark_session.py` creates a `local[*]` session. The driver and the executors are in one process, and the executors are threads, as many as the cores of the machine.

<Callout type="try" title="Try it on your machine">

```python
from spark_session import get_spark

spark = get_spark("arch")
sc = spark.sparkContext
print(sc.master, sc.defaultParallelism, spark.version)
```

On the machine used to test this lesson, the output was `local[*] 16 4.2.0`. The number 16 is the number of cores of that machine. Your machine may give another number.

</Callout>

Because of this, you can learn the ideas of distributed computing on one machine: many tasks really do run at the same time, but there is no network in between. On a real cluster, the cost of sending data between machines is higher than what you see here. Switch between local and cluster to see the difference, and click each part to read what it does.

## Which cluster managers are there

When you run on a real cluster, the driver needs to know whom to ask for executors. You tell it with `--master`. The order "the driver asks, then the executors contact it back" is the same in all of them. What differs is who allocates and who starts the executors.

| `--master` | Allocator | Unit that runs | Read more |
|---|---|---|---|
| `local[N]` | None (one process) | thread | The previous section |
| `spark://host:7077` | Spark's own Master | process started by a Worker | [Standalone](/en/spark/architecture/standalone/) (actually run) |
| `yarn` | Hadoop's ResourceManager (with an ApplicationMaster in between) | container | [YARN](/en/spark/architecture/yarn/) (read from the source) |
| `k8s://https://...` | kube-scheduler (the driver asks for pods itself through the API server) | pod | [Kubernetes](/en/spark/architecture/kubernetes/) (read from the source) |

Each page has an animation of the sequence from submitting the job to getting a task, and a lab that belongs to that cluster manager. Deploy mode, the Spark UI and dynamic allocation are in lesson 11.

</Step>

## SparkSession

`SparkSession` is the single entry point for reading data, creating DataFrames and running SQL. You create it with `SparkSession.builder...getOrCreate()`. If a session already exists, you get the same one back. In a notebook or on Databricks, a variable named `spark` is usually already there for you.

</Step>

## When data reaches the driver

Normally the data stays on the executors and does not pass through the driver. Only a few commands pull data to the driver.

- `show()` pulls the first 20 rows and prints them.
- `collect()` and `toPandas()` pull the whole result.
- `write` lets the executors write the files themselves, without going through the driver.

<Callout type="warn" title="Be careful with collect() on big data">
The result of `collect()` and `toPandas()` has to fit in the memory of the one driver. If the result is bigger than the memory the driver has, the program crashes. Filter or aggregate the data to make it smaller before you call these two commands.
</Callout>
