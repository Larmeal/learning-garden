## Two kinds of commands

| Kind | Examples | What happens |
|---|---|---|
| transformation | `filter`, `select`, `withColumn`, `groupBy().agg()`, `join` | Returns a new DataFrame that remembers the plan. It does not process any data yet |
| action | `show`, `count`, `collect`, `write` | Actually runs the whole plan |

A DataFrame cannot be changed. So every transformation returns a new DataFrame that remembers the commands of the old one. This chain of connected commands is called the lineage.

</Step>

<Step>

## Write the plan yourself

<LazyLab client:visible lang="en" />

Spark works this way because, when it sees the whole plan before it runs, it can choose a cheaper way to run it. For example, it can skip columns that nobody uses ([lesson 6](/en/spark/catalyst-aqe/#what-pushdown-looks-like-in-a-file-plan)).

</Step>

<Step>

## A repeated action means repeated work

Spark does not keep the result of earlier actions. If you call `count()` twice on the same DataFrame, it reads the file and processes the data twice. If you need an intermediate result again and again, use `cache()`. The next run then does not read the file again. How to choose where to cache is in [the Cache and Persist page](/en/spark/performance-tuning/cache-persist/).

<Callout type="tip" title="cache() is lazy too">
Calling `cache()` does not store the data right away. The data is stored when the first action runs through that point. So the first action is still as slow as before. The benefit starts from the second action.
</Callout>

</Step>

<Step>

## What else lineage is used for

Lineage is not only there so that Spark can plan before it runs. Spark also uses it when a partition is lost, for example when the executor that holds the result dies. Spark does not keep copies of the data in several places and does not start the whole job over. It walks back along the chain of commands and rebuilds only the partition that is gone. Pick a recipe, pick the partition that is lost, and see what Spark has to go back and do.

<LineageLab client:visible lang="en" />

Two things in the picture are worth noticing. First, `filter` and `withColumn` use the partition with the same number in the step before (a narrow dependency), so the walk back is very narrow. `groupBy` and `join` need data from every partition (a wide dependency), which is a shuffle. Second, Spark saves the result of the part before the shuffle as shuffle files, so it does not have to run that part again, unless the files are gone too. The details of dependencies and stages are in [lesson 13](/en/spark/internals/#rdd-and-lineage).

</Step>

## When the error shows up

The same mechanism makes two kinds of errors show up at different times.

<ErrorTiming client:visible lang="en" />

A wrong column name is caught as soon as you write the command, because Spark can check it against the schema without touching the data. A malformed value in the data is only found when an action reaches that row. The result is that sometimes the error appears at a single `show()` line, but the cause is in a command written many lines earlier.

<Callout type="note" title="About cast that raises an error">
The reason `cast("int")` on `abc` raises an error is ANSI mode, which is the default in Spark 4. If you turn this mode off, you get NULL instead.
</Callout>

</Step>

## Try it on your machine

<Callout type="try" title="See an error that shows up late">

```python
from pyspark.sql import functions as F
from spark_session import get_spark

spark = get_spark("lazy")
bad = spark.createDataFrame([("1",), ("abc",)], "x string")

step = bad.select(F.col("x").cast("int").alias("n"))   # no error
print("defined, still no error")
step.show()                                            # the error is here
```

Another experiment: open http://localhost:4040 while the session is still alive, then call `count()` several times. You will see the list of jobs in the Jobs tab grow every time you call an action.
