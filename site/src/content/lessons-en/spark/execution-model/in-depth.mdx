## Which operations shuffle: measured from the real plan

The main page says narrow operations do not shuffle and wide ones do. This is the result of checking every operation with `explain()` and counting the `Exchange` lines.

| Operation | Exchange in the plan |
|---|---|
| `filter`, `select`, `withColumn` | none |
| `union` | none |
| `coalesce(4)` | none (merges neighboring partitions) |
| `sample` | none |
| a final `limit(5)` | none (it is a `CollectLimit`) |
| `repartition(8)` | `RoundRobinPartitioning` |
| `repartition(8, "k")` | `hashpartitioning` |
| `groupBy("k").count()` | `hashpartitioning` |
| `distinct`, `dropDuplicates` | `hashpartitioning` |
| a window with `partitionBy("k")` | `hashpartitioning` |
| `orderBy("v")` | `rangepartitioning` |
| `agg(sum(...))` (no groupBy) | `SinglePartition` |
| a sort-merge `join` | two `hashpartitioning` (one for each side) |

Three things to notice:

- **`coalesce` does not shuffle but `repartition` does**, even though both change the number of partitions.
- **An aggregate with no `groupBy`** still has an Exchange, because the partial results from every partition must be combined in a single partition (`SinglePartition`). This means that last task is a bottleneck for the whole aggregation, but the data it receives is very small (a partial result from each partition).
- **A normal `join` has two Exchanges**, but if one side is small enough to be broadcast, there is no Exchange of the rows of either side at all. There is only a `BroadcastExchange` (checked, see chapters 6 and 7).

</Step>

## Number of stages = Exchange + 1

Every `Exchange` is a stage boundary, so the number of stages of one job is the number of Exchanges plus one. Measured by counting the stages created by `collect()` for each operation above.

| Operation | Exchange | stages |
|---|---|---|
| `filter`, `select`, `withColumn`, `union`, `coalesce(4)` | 0 | 1 |
| `repartition`, `groupBy`, `distinct`, `dropDuplicates`, window, `agg(sum)` | 1 | 2 |
| `join` (sort-merge) | 2 | 3 |
| `orderBy` | 1 | **3** |
| `limit(5)` | 0 | 1 |

The exception is `orderBy`: it gets 3 stages, not 2, because range partitioning must **sample the data first** to find the boundaries that split the value ranges so that the partitions have about the same size. This sampling is one more stage. In the Spark UI you see the job of `orderBy` with one extra stage that runs first.

Try chaining operations yourself and compare with the rule.

<PipelineStagesLab client:visible lang="en" />

**A case where the rule overestimates**: if you join two tables that were each grouped with `groupBy` on the same key, and they already have the same number of partitions (both sides are already `hashpartitioning(k, 200)`), Spark does not add another Exchange for the join. Measured: two `groupBy` and then a join gave stages `[4, 4, 200]`, which is **3 stages** (not 5), because the join can reuse the partitioning it already has. This is why choosing the key and the number of partitions to match before a join can reduce shuffles.

</Step>

## Tasks per stage and shuffle bytes

Run `range(0, 2_000_000, 1, 8).groupBy(id % 7).count()` (AQE off) and read from the REST API.

| stage | tasks | shuffle write | shuffle read |
|---|---|---|---|
| 0 (map side) | **8** | 3,496 bytes | 0 |
| 1 (reduce side) | **200** | 0 | 3,496 bytes |

- The number of tasks of the first stage equals the number of partitions of the source data (8). The stage after the shuffle has `spark.sql.shuffle.partitions` tasks (200).
- **The bytes that stage 0 writes are exactly the bytes that stage 1 reads** (3,496 bytes). The data is shrunk by a partial aggregate before it is sent: only 7 groups from 8 partitions remain, not 2 million rows. This is why a `groupBy` that can aggregate shuffles less than `distinct` or `repartition`, which send every row.
- Most of the 200 tasks get empty or very little data (7 keys spread over at most 7 partitions). This is the reason AQE merges them in chapter 6.

A purely narrow job `range(8 partitions).filter().select().collect()` gives **1 stage with 8 tasks**, which matches what the main page says: you can chain any number of narrow operations and they stay in one stage.

</Step>

## Partitions that change along the way

| Situation | Number of partitions |
|---|---|
| `spark.range(1_000_000)` (16 cores) | 16 (follows the number of cores) |
| result of `groupBy(...)`, AQE off | **200** (`spark.sql.shuffle.partitions`) |
| result of `groupBy(...)`, AQE on (small data) | **1** (AQE merges) |
| `coalesce(4)` | 4 |

When AQE is on, calling `explain()` before an action starts with `AdaptiveSparkPlan isFinalPlan=false`, which says the plan can still change (see chapter 6). The numbers 1 and 200 above are the source of a question that learners often ask: "why does `explain` show 200 but the UI shows fewer?" The answer is AQE.

<Callout type="tip" title="When to use these numbers">
When you meet a slow job: open the Spark UI, count the stages, and compare with the number of Exchanges in `explain()`. If there are more stages than Exchange + 1 by more than you expect, there may be an extra job (for example the sampling of `orderBy`) or a repeated stage from a retry. Then look at the shuffle bytes of the biggest stage. That is where to reduce first (chapter 7).
</Callout>
