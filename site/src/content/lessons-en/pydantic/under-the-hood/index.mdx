## The big picture: two halves

Pydantic V2 is split into two parts written in different languages.

- **pydantic** (Python) reads the type hints, config and decorators of your class and turns them into a description of the checks
- **pydantic-core** (Rust, connected to Python through PyO3) takes that description and builds the validator and serializer that do the work

The thing between the two halves is the **core schema**, which is a plain Python `dict`. This lesson follows the trail from class creation to a call of `validate_python`, and every step can be checked in `exercises/10_under_the_hood.py`.

The files named here come from the knowledge graph of the 2.13.0 source in `subjects/pydantic/graphs/pydantic-current/` (230 files, split into the layers Public API, Internal Schema Generation, Core Python Bindings and the Rust layers). The version the exercises run is 2.13.0 as well (`verify.py` checks it).

</Step>

## At class creation: the metaclass builds a validator

```python
class Item(BaseModel):
    sku: str
    qty: int = Field(gt=0, default=1)

class Order(BaseModel):
    id: int
    items: list[Item]
```

`BaseModel` uses a metaclass named `ModelMetaclass` (`type(Order).__name__`), which runs as soon as Python finishes reading the `class Order` statement. According to the graph, the file `_internal/_model_construction.py` does this work: it inspects the namespace, collects fields, handles private attributes, builds a core schema, and then builds the validator and serializer.

The results are stored on the class:

```python
Order.__pydantic_complete__          # True   fully built
Order.__pydantic_validator__         # SchemaValidator   (this type lives in pydantic_core._pydantic_core, compiled Rust code)
Order.__pydantic_serializer__        # SchemaSerializer
Order.__pydantic_core_schema__       # the dict handed to Rust
```

When you write `Order(id=1, ...)`, what is called under the hood is `Order.__pydantic_validator__.validate_python(...)`. The exercise calls it directly to show that you get an `Order` back just the same.

</Step>

## What the core schema looks like

Open `Order.__pydantic_core_schema__`:

```python
schema["type"]                         # 'model'
schema["cls"] is Order                 # True
schema["schema"]["type"]               # 'model-fields'
{k: v["schema"]["type"] for k, v in schema["schema"]["fields"].items()}
# {'id': 'int', 'items': 'list'}
```

The structure is a `model` layer wrapping `model-fields`, which holds a dict of each field with the schema of its type. The field `items` is of type `list`, and its `items_schema` is the whole schema of `Item` (`inner["cls"] is Item`). Constraints and defaults are in there too:

```python
Item.__pydantic_core_schema__["schema"]["fields"]["qty"]["schema"]
# {'type': 'default', 'schema': {'type': 'int', 'gt': 0}, 'default': 1}
```

`Field(gt=0, default=1)` in Python becomes two layers: the outer one is `default` with the value 1, and the inner one is an `int` with the condition `gt: 0`. This knowledge pays off, because **JSON Schema** ([lesson 9](/en/pydantic/adapters/)) and **serialization** ([lesson 7](/en/pydantic/serialization/)) read from this same core schema and not directly from the Python class.

The file that defines the shape of these dicts is `pydantic_core/core_schema.py` (TypedDicts for every schema type, and constructor functions such as `int_schema`, `list_schema`, `model_schema`). The file that walks your types and writes the dict is `_internal/_generate_schema.py`, which the graph describes as the largest module on the Python side.

</Step>

## You can skip the Python half and talk to Rust directly

Because a core schema is just a dict, you can write one yourself and hand it to Rust, without going through `BaseModel`.

```python
from pydantic_core import SchemaValidator, core_schema as cs

v = SchemaValidator(cs.list_schema(cs.int_schema(gt=0)))
v.validate_python(["1", 2])      # [1, 2]
v.validate_python([0])           # ValidationError of type greater_than
v.validate_json("[1, 2]")        # [1, 2]
```

The results match everything you have seen: lax converts `"1"` to `1`, and errors have the same `type` names. That is the evidence that `BaseModel`, `TypeAdapter` and `validate_call` are all thin shells that build a core schema and hand it to this `SchemaValidator`.

On the Rust side, per the graph, `validators/mod.rs` holds `SchemaValidator` (the thing Python calls) and a build step that reads the `type` tag of a schema and builds the matching validator. There is one file per type in the same folder: `int.rs`, `string.rs`, `list.rs`, `model.rs`, `union.rs`, `function.rs` and so on. When an outer validator runs, it calls its inner ones in turn, which matches the nesting of the schema.

</Step>

## Input: why Python data and JSON differ in strict mode

In Rust a validator does not read Python objects or JSON directly. It goes through a middle layer, the `Input` trait (`input/input_abstract.rs`). There are three implementations: Python data (`input_python.rs`), parsed JSON (`input_json.rs`) and strings (used for the keys of a JSON object). Each method has a strict version and a lax version.

This is the reason for the behavior in [lesson 3](/en/pydantic/types/#strict-is-different-for-json-input-and-python-input), where strict decides differently depending on the source. The exercise uses a field `pair: tuple[int, int]` in a strict model:

```python
Strict.model_validate_json('{"pair": [1, 2]}').pair    # (1, 2)  passes, JSON has only arrays
Strict.model_validate({"pair": [1, 2]})                # error of type tuple_type  a Python list is not a tuple
Strict.model_validate({"pair": (1, 2)}).pair           # (1, 2)  passes
```

`model_validate_json` lets the JSON parser (the graph says it uses `jiter`) hand values straight to the validator. That means no Python `dict` and `list` need to be built first, which is the reason behind the advice to use `model_validate_json` when the data starts as a JSON string. A real speed measurement was not done in this lesson.

</Step>

## When a class cannot finish building in one go

Sometimes Pydantic cannot build the validator when the `class` statement ends, because a type hint refers to a name that does not exist yet (a forward reference).

```python
class A(BaseModel):
    b: "B"          # B has not been declared yet

A.__pydantic_complete__                      # False
type(A.__pydantic_validator__).__name__      # 'MockValSer'
A(b=1)    # PydanticUserError: `A` is not fully defined; you should define `B`, then call `A.model_rebuild()`.
```

At that point `__pydantic_validator__` is a stand-in (`MockValSer`, from `_internal/_mock_val_ser.py` according to the graph) that waits to be used, then tries to build the real thing, or tells you what is missing.

After you declare `B`, calling `A.model_rebuild()` gives a real validator (`A(b={"x": "1"}).b.x == 1`). In some cases you do not even need to call it: a class `C` refers to `D`, which is declared right after it, and on the first call `C(d={"x": 1})` Pydantic tries to rebuild by itself, and `C.__pydantic_complete__` becomes `True`.

If you already know you want to postpone the build, use `defer_build`:

```python
class Lazy(BaseModel):
    model_config = ConfigDict(defer_build=True)
    x: int

Lazy.__pydantic_complete__    # False
Lazy(x=1)
Lazy.__pydantic_complete__    # True   built on first use
```

It suits a program with hundreds of models of which only a few are used in a given run, since the build cost of the unused ones is postponed indefinitely.

</Step>

## The cost is in creating the class, not in validating

The exercise times two things on the machine that ran it:

```text
create 200 classes 42 ms, validate 200 times 0.30 ms
```

Creating 200 classes took 42 ms, and validating 200 times with an already built validator took 0.30 ms. The numbers depend on the machine, and the two operations do different work. The conclusion the exercise can `assert` is that creating costs more than 20 times what validating does.

What this means for how you write code:

- Declare models at module level, once. Do not create classes or a `TypeAdapter` inside a function that is called repeatedly ([lesson 9](/en/pydantic/adapters/)).
- Slow program startup comes from building models. If you have many, try `defer_build`.
- `import pydantic` itself is cheap, because `pydantic/__init__.py` loads names lazily: at first `'pydantic.main' in sys.modules` is `False`, and it becomes `True` the first time you touch `pydantic.BaseModel`.

<Callout type="note" title="A validator can describe itself">
`repr(Order.__pydantic_validator__)` prints the structure of the validator Rust actually built. The exercise gets 117 lines, starting with `SchemaValidator(title="Order", validator=Model(` and containing a `ModelFieldsValidator`. It is a way to see what a schema was turned into when you are in doubt.
</Callout>
