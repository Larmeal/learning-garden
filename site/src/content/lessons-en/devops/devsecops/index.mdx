## Security is the job of every gate

So far we have a pipeline that checks the code and makes an artifact whose origin we know. The question left is how safe what we deploy is. In the old world this was often the last step, where a security team checked before release, which meant a queue as we saw in [lesson 0](/en/devops/overview/), and the problems were found close to the release day.

The DevOps Handbook tells that organisations that do well put security checks into the daily work and tools of developers, because that lowers risk, lowers the chance of vulnerabilities in the system, and teaches developers to write more secure code (book: The DevOps Handbook chapter 22). It also stresses that the software we write does not come entirely from our own code. We assemble it from open source parts, which has become the software supply chain that we rely on, and when we use a library we inherit both its abilities and its vulnerabilities (book: The DevOps Handbook chapter 22).

In this lesson there are three gates to try. Each catches a different kind of thing, at a different point on the line. For the details of each kind of threat go to [lesson 11 of App Security](/en/app-security/supply-chain-secrets/), which explains dependencies and secrets. Here we care only about where those gates sit in a pipeline.

</Step>

<Step>

## Gate one: a secret that was removed from the files is still there

In [lesson 2](/en/devops/ci/) the stage `secret-scan` checked only the files in the pushed commit. But a secret that leaked once and was removed later has not gone anywhere. In the exercise we build a repository where one commit adds a fake AWS style key and the next removes it. The result (ran):

```text
scan of the files as they are now  →  nothing found
scan of git log -p --all            →  finds AKIAIOSFODNN7EXAMPLE
git log -S AKIAIOSFODNN7EXAMPLE     →  two commits (the one that added, the one that removed)
git show HEAD~1:settings.py         →  the key is still in the object store
```

A scanner that reads only the current files says all is safe, while the key sits in the history, which everyone who clones the repository takes away. A gate that checks secrets must therefore read the whole history, and when it finds a key that once leaked, we must treat it as leaked and rotate the key, not just delete the file (the deeper reasons are in [lesson 11 of App Security](/en/app-security/supply-chain-secrets/#a-key-that-is-deleted-and-still-there)).

</Step>

## Gate two: an SBOM that can be matched again at any time

The second gate comes from the observation that the risk of built code is not fixed. A vulnerability found after the build can make the same artifact riskier without anybody touching it. The way to deal with it is to keep the list of the components of the artifact, called an SBOM (software bill of materials). The DevOps Handbook cites a survey that high performers often keep a central record of all deployed artifacts, to produce an SBOM for each application and to scan all deployed artifacts centrally for security and licence compliance (book: The DevOps Handbook chapter 22).

In the exercise we make an SBOM in the CycloneDX format from a lock file of five packages, and match it twice against a list of advisories that we made up (not real CVEs) (ran).

```text
day 1 :  [('EXAMPLE-0001', 'pyyaml', 'critical')]
day 30:  [('EXAMPLE-0002', 'requests', 'high'),
          ('EXAMPLE-0003', 'jinja2', 'medium'),
          ('EXAMPLE-0001', 'pyyaml', 'critical')]
```

The bytes of the artifact did not change between the two days, but what we know about it did. On day 1 a gate set to fail from `high` stops the build (because pyyaml is critical), while a gate that fails only on `critical` lets a build with just a medium finding pass, and on day 30 the gate at `high` fails because of requests and pyyaml (ran). This is why we keep the SBOM: otherwise we would have to build again every time a new vulnerability appears, only to find out whether we are affected.

</Step>

<Step>

## Gate three: scan the image with a real tool

The last gate scans the whole image, including the operating system inside, not only the dependencies of the app. In the exercise we ran Trivy 0.67.2 in Docker with its real vulnerability database, and scanned `nginx:1.21-alpine`, an old image. The result (ran):

```text
nginx:1.21-alpine: 101 known vulnerabilities, 11 critical   (Alpine 3.15 out of support: EOSL)
nginx:1.28-alpine: 287 known vulnerabilities, 6 critical
```

Ask yourself why the newer image has more vulnerabilities detected. The author did not check the cause, but noticed that Trivy flags the old image with `EOSL` (end of support life), which is more important than the numbers. One possible reason is that the maintainers of the operating system stop publishing vulnerabilities for a release that is out of support, so a small number does not mean safer (this is a guess, the author did not check it). What is certain is that a scan result is the answer of today. Scan the same tag tomorrow and the numbers may differ (so the exercise checks only that the result has the name of the package, the installed version and the severity, and that the old image is flagged EOSL).

Choose a threat in the lab one at a time and see which gate stops it, which gates it has already passed, and which ones it never has to reach.

<Callout type="note" title="What was not tried">
Signing an image or an artifact to prove where it came from, static analysis of our own code (SAST), dynamic testing (DAST) or scanning a running container were not tried. Neither was managing the secrets that the pipeline itself uses, which is the topic of The DevOps Handbook chapter 23 (Protecting the Deployment Pipeline), and the author did not read it in detail.
</Callout>
