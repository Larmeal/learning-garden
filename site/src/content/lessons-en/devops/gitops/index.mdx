## Orchestration is compare and fix, again and again

The book Fundamentals of DevOps and Software Delivery compares orchestration to the conductor of an orchestra, who tells each member when to start or stop and when to play louder or softer. In software, an orchestration tool does that for a whole set of apps: it tells them to start or stop, increases or decreases the resources they get, and increases or decreases the number of replicas of each. The word orchestration is often tied to Kubernetes, but the problems it solves have been there since the first programmer ran an app for others (book: Fundamentals of DevOps and Software Delivery, chapter 3, page 82).

The book lists the core problems of anyone who runs a real app: deployment, scheduling, rollback, auto scaling, auto healing, load balancing, configuration, secrets, communication between services and disk management (book: same, pages 82 to 83). Two of them connect to earlier lessons: rollback, which is the topic of [lesson 5](/en/devops/release/), and configuration and secrets, which are in [lesson 3](/en/devops/config-secrets/).

In this lesson we care about the one at the centre, auto healing, which works as a loop. **First** look at what the real state is. **Next** compare it with the state we want. **Last** fix only the part that differs, and go back to looking. This loop is called a reconciliation loop, and it is the heart of the Kubernetes controllers under everything we see on a cluster (in the [Kubernetes](/en/kubernetes/why-kubernetes/) path we stop a real controller and see what stops with it, in the [control plane lesson](/en/kubernetes/control-plane/)).

</Step>

## Git holds what we want

GitOps ties that loop to Git. The book GitOps Cookbook defines it as a method that uses a Git repository as the single source of truth to deliver infrastructure as code, with three pillars: Git is the single source of truth, treat everything as code, and every operation goes through Git workflows (book: GitOps Cookbook, section 1.1, pages 1 to 2).

The OpenGitOps community sets four principles. The desired state is written declaratively (say what we want, not how to do it). It is stored versioned and immutable. Agents pull the desired state automatically. And the agents observe the actual state and try to make it match the desired state all the time (continuously reconciled) (book: same, page 2).

Let's build the smallest thing that does those four. In the exercise a remote repository holds a file `desired.json` that says web must have two replicas at version 1 and worker one. We write a short program (`gitops.py`) that does three things again and again: read that file from the `main` branch of the repository, look at the Docker containers that carry the label of this group, and create, remove or replace them to match (ran). We chose Docker instead of Kubernetes because Kubernetes does not exist in this garden yet as this lesson is written, and our program is a **model** of the loop that Argo CD or Flux run, not those tools.

</Step>

<ReconcileLab client:visible lang="en" />

The results of each situation in the exercise match the picture (ran). In the first pass the cluster is empty and the controller creates three. In the second pass nothing needs doing, the sign that the system has converged. Then we `docker rm` web-2 by hand. In the next pass the controller sees it is missing and creates web-2 again. Then we start a container named debug-1 that nobody asked for. In the next pass the controller removes it. A container stopped by hand with `docker stop` is replaced too.

The result is that a direct change by hand does not live long, whether it removes or adds. A team that uses GitOps gets the safety advantage the book mentions, seeing and fixing drift before it reaches production (book: GitOps Cookbook, section 1.2, page 2). It also gets a downside to know about: in an emergency, when you want to fix something by hand, you must fix it in Git or the fix gets overwritten.

</Step>

## A release is a commit and a rollback is git revert

The last two situations are the most interesting. We commit a new file that changes web to version 2 and makes it three replicas, then push. The controller replaces web-1 and web-2 and creates web-3, and the worker is not touched at all (ran). So a release is not running a deploy script. It is changing one file in Git.

```text
replace  web-1
replace  web-2
create   web-3
```

To go back we run `git revert` on that commit and push. The controller replaces web-1 and web-2 with version 1 again and removes web-3. The state of the cluster is exactly what it was before the release (ran), and the history in Git reads as a story (ran).

```text
Revert "release web v2, three replicas"
release web v2, three replicas
web v1 x2, worker v1 x1
```

This is the benefit the book mentions: every change is recorded and can be audited in Git (book: same, page 2). Two things to think about next. First, the commit that releases should be reviewed like code (as we saw in [lesson 1](/en/devops/version-control/)). Second, the repository holding `desired.json` is a different one from the repository of the app code, which is how the exercise of [lesson 13](/en/devops/capstone/) does it, so that the pipeline of the app and the decision to deploy stay separate.

<Callout type="note" title="This model is much smaller than the real thing">
Our controller compares only the name, the image version and the environment. It has no health checks, no ordering, no one-at-a-time rolling that waits until each is ready, and no handling of secrets. Kubernetes controllers and Argo CD do these things and much more. The author has not tried the real tools. What the exercise confirms is the structure of the loop: read the desired state from Git, compare with the real state, act only on the difference.
</Callout>
