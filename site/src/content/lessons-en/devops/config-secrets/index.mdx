## The same file, three places, different results

In [lesson 2](/en/devops/ci/) our pipeline makes one artifact per commit. Now if a team has several environments, the next question is whether we have to build again every time we change environment. The book Fundamentals of DevOps and Software Delivery says most companies have at least three: production, which users reach; staging, which is nearly the same as production but scaled down to save money; and development, which the team uses to test while developing. They are often shortened to dev, stage, prod (book: Fundamentals of DevOps and Software Delivery, chapter 6, pages 228 to 229).

If we build again for each, the file tested in staging is not the file that runs in prod, so we can never know whether what we tested works on the real thing. The way out is to build once and let what differs come from outside. In the exercise we write a short program that reads its values from environment variables, and run the same file three times with different sets of values (ran).

```text
$ APP_ENV=dev DATABASE_URL=sqlite:///dev.db LOG_LEVEL=debug python app.py
env=dev db=sqlite:///dev.db log=debug

$ APP_ENV=staging DATABASE_URL=postgres://staging-db/shop LOG_LEVEL=info python app.py
env=staging db=postgres://staging-db/shop log=info

$ APP_ENV=prod DATABASE_URL=postgres://prod-db/shop LOG_LEVEL=warning python app.py
env=prod db=postgres://prod-db/shop log=warning
```

The three lines differ, but the `app.py` that ran is the same file, byte for byte (sha256 starting `3f00593d55ea`). What we pull out of the code like this is called config, and keeping it in environment variables is a widely used approach (related to the 12-factor principles that The DevOps Handbook mentions as a pattern of modern web architecture; the author of this lesson did not read those principles in detail).

## If a value is missing, stop at once

Pulling config out creates a new risk: an environment may forget a value. If the program carries on silently with a default, we may connect to the wrong database without knowing. So the exercise makes the program check at startup that the required variables are there, and stop immediately if not (ran).

```text
$ APP_ENV=prod python app.py
missing configuration: DATABASE_URL
```

The exit code is 2 and the message names the missing variable. Teams also check parity: every environment must define the same set of variables (only the values differ). In the exercise the function found that dev, staging and prod have the same keys, and when we made staging lose `LOG_LEVEL`, the check said at once that staging lacked `LOG_LEVEL` (ran).

</Step>

## How is a secret different from other config

The `DATABASE_URL` above may contain a password, which is a secret, and secrets need more care than other config. The book sets the first rule of secrets management as "do not store secrets as plaintext", and repeats it as the second rule in capital letters. The reason is that if we put a secret in version control, copies go to the computers of everyone on the team, those that run the version control, those that run CI, those used for deployment and those used for backups, and a vulnerability in the software of any one of them can leak the secret (book: same, chapter 8, pages 348 to 349).

The book divides secrets into three groups: personal secrets (such as website passwords), infrastructure secrets (such as database passwords, API keys, TLS certificates) and customer secrets, each kept with a different kind of tool (book: same, page 349). The secret our program needs is the middle group, and one important advice is that the best way is not to store it at all, when that is possible (book: same, page 350).

## Let's prove with Docker who can see what

The exercise keeps the same password in three ways and tries to read it from three angles (ran). The first writes it in a Dockerfile with `ENV DB_PASSWORD=...`. Then `docker history` on the image, which shows every line used to build it, shows the password at once. So anybody who pulls the image can read the password without running it, and a container made from this image also has it in `docker inspect` (more on image layers in [lesson 2 of Docker](/en/docker/images-and-layers/)).

The second passes it at run time with `docker run -e DB_PASSWORD=...`. This time the image is clean and `docker history` does not have the password, but `docker inspect` of the container shows it as an environment variable of the container. Anyone allowed to use Docker on that computer can read it.

The third keeps it in a file mounted at `/run/secrets/db_password`, read-only. Now `docker inspect` shows only that a file is mounted at that path, not its content, and `docker history` has nothing either. The program inside the container can still `cat` the file as usual.

Be careful not to conclude too much here. Mounting a file only keeps the secret out of the image and out of `docker inspect`. Anyone who can run commands inside the container (for example `docker exec`) can still read the file, and the file on the host has its own permissions. The author did not try real secret tools such as Vault or Kubernetes Secrets, which the book recommends when we must store secrets.
