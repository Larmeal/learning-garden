<Question
  client:visible
  lang="en"
  q="Why does the exercise stop the program with exit code 2 and the name of the variable when DATABASE_URL is missing, instead of using a default and carrying on?"
  options={['Because defaults are hard to write', 'Because carrying on silently could connect to the wrong database without anyone knowing. Stopping makes the problem show at startup, not when data is damaged', 'Because Python forces a stop when a variable is missing']}
  answer={1}
  why="Failing early is the same idea as fail fast in the pipeline of [lesson 2](/en/devops/ci/). A config problem that is let through often does not crash the program at once, it makes it do the wrong thing in the wrong place, which is much harder to find."
/>

</Step>

<Question
  client:visible
  lang="en"
  q="The parity check in the exercise found that staging lacks LOG_LEVEL. What is the problem?"
  options={['All three environments must have exactly the same LOG_LEVEL value', 'All three environments must define the same set of keys (the values may differ). If the keys differ, the behaviour of staging no longer represents prod', 'LOG_LEVEL is not needed in staging']}
  answer={1}
  why="Parity does not mean equal values (dev uses sqlite and prod uses postgres). It means the same keys. If staging falls back to a default LOG_LEVEL while prod sets warning, what we test differs from the real thing and nobody sees it."
/>

</Step>
