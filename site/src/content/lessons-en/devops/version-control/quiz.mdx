## Check yourself

<Question
  client:visible
  lang="en"
  q="In the exercise git bisect points at the merge commit as the first commit where the tests fail. What does this tell us?"
  options={['One of the feature commits of Bob is written wrongly', 'No feature commit is wrong on its own. The problem appeared when two correct pieces of work were combined', 'Bisect is wrong, because a merge commit should never be the answer']}
  answer={1}
  why="Every commit of Alice's branch and of Bob's branch passes its own tests. The tests start to fail only at the merge commit. So what is wrong is how the two pieces fit together, which Git cannot see, and that is why the tests must run on the merged result."

<Question
  client:visible
  lang="en"
  q="Which answer best explains why a short-lived branch makes merge conflicts less painful?"
  options={['Git computes conflicts faster when the branch is short', 'Fewer files change, so files overlap less often, and if they do the conflict is small and the code is still fresh in our heads', 'A short branch never has conflicts']}
  answer={1}
  why="The book uses a repository of 10,000 files. After one day each developer changed about 10 files, so the chance that those 20 files overlap is very small. After three months and 500 files each the chance is much higher, and the conflict is larger and harder to understand because it is old (book: Fundamentals of DevOps and Software Delivery, chapter 5, pages 178 to 179). The last option is wrong: conflicts always remain possible when several people change the same code. The question is how painful they are."
/>

</Step>
