## Mr. A finished the code on Monday

Say Mr. A is a developer who fixed the payment page on Monday morning. The change is tiny and writing it took less than a day, yet customers only got it the week after, and nobody was lazy.

Let's see where the time went. The table below is one change travelling through several teams the old way, where the developer writes the code and hands it on step by step (the numbers are examples set by the author, computed in `exercises/00_value_stream.py`).

| Step | Somebody is working (hours) | Waiting in a queue (hours) |
|---|---|---|
| Write the code | 8 | 0 |
| Code review | 1 | 16 |
| Hand to the test team, test by hand | 6 | 40 |
| Ask Ops for a deploy window | 1 | 90 |
| Ops deploys by hand | 2 | 24 |
| Look at it in production | 1 | 8 |
| **Total** | **19** | **178** |

The number to stop at is the last row. Only 19 hours of the 197 had a person working on this change. The other 178 sat in a queue until somebody was free, which makes about 8 days, with someone working on it for 10% of the time.

Ask yourself the question here: if we want a change to reach users sooner, which part should we speed up? Making the developer type faster hardly helps, because typing is 8 hours of 197.

</Step>

## Why releases get rarer and rarer

The book Fundamentals of DevOps and Software Delivery tells where this comes from. Most companies used to have a Dev team that wrote the software and an Ops team that ran the machines and the live system, and the two had opposing goals. Ops was measured on security and stability, Dev on shipping features fast (book: Fundamentals of DevOps and Software Delivery, preface, page xvi).

Dev wrote code and "tossed it over the wall", Ops deployed it by hand, and things broke. Ops, tired of waking up at 3 a.m., released less often. Each release then became bigger and more complicated, so it broke more often, so releases became rarer still, and so on until the company ground to a halt (book: same, page xvi).

Put that cycle next to the lab and it is the same picture. A rarer release puts more changes into each release, and that is what makes every release riskier. [Lesson 1](/en/devops/version-control/) and [lesson 5](/en/devops/release/) come back to this batch size.

</Step>

## What DevOps answers

The same book says DevOps started to be discussed openly around 2007 to 2008, together with three shifts over the next ten years. The first was the move to the cloud, so that both Dev and Ops reach live systems through the same software. The second was automation instead of manual work. The third was Dev and Ops working together in one team with shared goals and tooling (book: same, page xvii).

The author defines it briefly: the goal of DevOps is to make software delivery vastly more efficient. DevOps is not the name of a team, a job title or one technology, even though people use the word for all three (book: same, page xvii).

The gap is huge. The DORA table of 2024 in the book says elite teams deploy 182 times more often than low performers, have a lead time 127 times shorter and recover 2,293 times faster (book: same, page xv). We will go through these metrics in [lesson 12](/en/devops/metrics/).

<Callout type="note" title="The author did not measure this">
The figures 182 and 127 come from a report that the book cites. The author of this lesson did not check them against the original report and did not measure a real team. The hours in the table and in the lab are examples set to show the proportions.
</Callout>

## The loop we will follow

If we write the road that code travels as a sequence we get eight stretches, and the data from the last one runs back to the first, which is why the line makes a loop.

```text
 Plan ─► Code ─► Build ─► Test ─► Release ─► Deploy ─► Operate ─► Monitor
   ▲                                                                │
   └──────────────── Feedback (alert, incident, metric) ◄───────────┘
```

The tools we touch in passing at each stretch, and the lesson that explains it, are these.

| Stretch of the loop | Lesson | Tools touched |
|---|---|---|
| Code | [lesson 1](/en/devops/version-control/) | Git |
| Build and Test | [lesson 2](/en/devops/ci/) and [lesson 3](/en/devops/config-secrets/) | A pipeline (a small one that we write in the labs), GitHub Actions as an example of the real thing |
| Release | [lesson 4](/en/devops/artifacts/) and [lesson 5](/en/devops/release/) | Docker, a registry |
| Deploy | [lesson 6](/en/devops/iac/) and [lesson 7](/en/devops/gitops/) | Terraform, GitOps |
| Operate and Monitor | [lesson 8](/en/devops/observability/) to [lesson 10](/en/devops/incidents/) | Prometheus |
| Improve the whole loop | [lesson 11](/en/devops/devsecops/) to [lesson 13](/en/devops/capstone/) | Trivy, the DORA metrics |

This path explains tools only enough to see where each one sits on the loop. For the details of Docker and Git go to their own subjects, for example [lesson 1 of Docker](/en/docker/containers/) on what a container is. Kubernetes does not exist in this garden yet as this lesson is written, so [lesson 7](/en/devops/gitops/) uses small Docker containers instead.

## Three principles under the loop

The DevOps Handbook sums up the principles under this loop as the Three Ways (book: The DevOps Handbook, [chapter 1](/en/devops/version-control/)), and we can use them as a map of this path.

| Way | Idea | Where in this path |
|---|---|---|
| The First Way (Flow) | Make work flow from Dev to the user fast and smoothly: make work visible, reduce batch sizes, build quality in from the start | [Lessons 1](/en/devops/version-control/) to 7 |
| The Second Way (Feedback) | Let information flow back from production to the people who wrote the code, fast enough to fix things before the damage is big | [Lessons 8](/en/devops/observability/) to [10](/en/devops/incidents/) |
| The Third Way (Continual Learning) | Keep learning from failure and keep experimenting | [Lessons 10](/en/devops/incidents/) to 13 |

Against the loop above, the First Way is the top line going right, the Second Way is the lower line coming back, and the Third Way is what the team does with the information that returned, after every round.
