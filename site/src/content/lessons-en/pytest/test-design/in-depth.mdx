## The method used on this page

Most badly written tests do not fail, so nobody notices. This page therefore takes tests with a problem and runs them in a temporary project with `pytester`, to see what happens (ran: `exercises/08_design/test_smells.py`, 12 tests, all passing). Each item has a fixed version to compare.

</Step>

<Step>

## 1. Depending on order

Two tests share a list created at module level (like `demos/08_order_dependent` in [lesson 15](/en/pytest/test-design/#tests-must-be-independent)):

```python
cart = []
def test_add():
    cart.append("apple")
    assert cart == ["apple"]
def test_total():
    assert len(cart) == 1
```

Run the whole file and both pass, but run `test_total` alone by node id and it fails. The fixed version has each test ask for the cart from a fixture and add its own item, so `test_total` passes when run alone (ran). You can test independence by running tests one at a time now and then, or in parallel with `-n` ([lesson 7](/en/pytest/project/#parallel-runs-with-pytest-xdist)).

</Step>

<Step>

## 2. Random values

A test that uses Python's random generator without fixing it gives a different result every run. If the code takes the random generator as a parameter (`make_discount(rng)`), the test can pass in `random.Random(7)` and get the same set of values every time (ran). If the code uses the global generator of `random`, call `random.seed(7)` in the test itself. Both ways are repeatable, while a test that does not fix it fails on some runs, which is the symptom of a **flaky test** (the last section of this page).

</Step>

<Step>

## 3. Computing the expected value with the same code

```python
def test_smell_the_expected_value_is_computed_with_the_same_code():
    prices, qtys = [10, 20], [3, 1]
    assert total_of(prices, qtys) == sum(p * q for p, q in zip(prices, qtys))
```

This test passes even if the formula in `total_of` is wrong, because both sides use the same formula. The fixed version writes the expected value down, worked out by hand:

```python
assert total_of([10, 20], [3, 1]) == 50      # 3 * 10 + 1 * 20
```

A rule that is easy to remember: if the expected side can be turned into a copy of the code, the test says nothing. The expected value should come from somewhere else (a number worked out by hand, an example from the spec, or a confirmed result).

</Step>

<Step>

## 4. An assert that cannot fail

Three forms you see often (ran):

| Form | Result |
|---|---|
| `assert (1 == 2, 'message')` | passes, because a non-empty tuple is true. pytest issues the warning `assertion is always true, perhaps remove parentheses?` ([lesson 13](/en/pytest/assertion-rewriting/#traps-and-other-helpers)) |
| a test with no `assert` at all (`1 + 1`) | always passes, proving only that no exception was raised |
| `return 1 == 2` instead of `assert` | passes with the warning `Did you mean to use assert instead of return?` ([lesson 12](/en/pytest/run-protocol/)) |

All three give green. The way to guard against them is `-W error` or `filterwarnings = ["error"]`, so these warnings fail ([lesson 8](/en/pytest/builtin-plugins/#warnings-the-summary-at-the-end)).

</Step>

<Step>

## 5. One test, several things

A test with `assert 1 == 2` followed by `assert 3 == 4` reports only the first. `3 == 4` is never evaluated (ran: the text `3 == 4` is not in the output). Split into two tests you get `2 failed` and see both. This is why the lesson [Designing good tests](/en/pytest/test-design/) recommends one test per behaviour.

If you really must check several points in one run (such as each row of some data), use subtests, which report each round separately ([lesson 8](/en/pytest/builtin-plugins/#subtests-several-results-inside-one-test)).

</Step>

## A flaky test: fails some runs

A test that fails one run in five looks green almost all the time. The exercise simulates it with a counter that grows on every run and a test that fails when the counter is divisible by five. If you parametrize it to run 10 times, the result is `8 passed, 2 failed` (ran). Repeating is how you make a periodic problem visible. The usual causes are time, random values, order and shared state, which the first four items on this page cover.

While fixing a flaky test, do not retry until it passes: rerunning until green hides the fault. Find the cause (author).
