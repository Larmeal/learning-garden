## Configure once, in pyproject.toml

Instead of typing the same options every time, put them in `[tool.pytest.ini_options]` in `pyproject.toml` (Pytest also reads `pytest.ini`). These are the settings of the exercise project:

```toml
[tool.pytest.ini_options]
pythonpath = ["src"]
testpaths = ["exercises"]
addopts = "-ra"
markers = [
    "slow: a test that takes a while",
    "integration: a test that uses more than one module",
]
```

| key | What it does |
|---|---|
| `pythonpath` | adds a folder to `sys.path` so `import shop` works without installing the package |
| `testpaths` | where to look for tests when you just run `pytest` |
| `addopts` | options added every time; `-ra` prints the reasons for skips, xfails and so on |
| `markers` | registers markers ([lesson 5](/en/pytest/markers/#register-markers-so-typos-get-caught)) |

The report header says where the settings came from: `rootdir: ...` and `configfile: pyproject.toml`.

`pythonpath` matters. If you turn it off (`pytest -o pythonpath= exercises/01_first_test`) you get `ModuleNotFoundError: No module named 'shop'` at collection time (ran: `verify.py`).

</Step>

## Folder layout

```text
code/
  pyproject.toml
  src/shop/            the code under test
  exercises/NN_name/   tests that must pass (each folder may have its own conftest.py)
  demos/NN_name/       tests that fail on purpose, to read the output
```

`testpaths = ["exercises"]` makes a plain `pytest` leave `demos/` alone, so the whole suite is green: **188 passed, 3 skipped, 6 xfailed** (ran: `verify.py`). A demo has to be run by naming its path.

Thoughts on where to put tests (author):

- Keep tests structurally close to the code (`tests/` or `exercises/`, with folder names that mirror features), and put `conftest.py` in the folder whose tests share that fixture.
- Separate slow or externally dependent tests with a marker (`slow`, `integration`) rather than a folder. It is easier to select by situation.

</Step>

## Choosing what to run: path, node id and -k

| You want | Command | Result (ran: `verify.py`) |
|---|---|---|
| a whole folder | `pytest exercises/05_markers/test_markers.py` | 6 passed, 2 skipped, 2 xfailed |
| a whole file | `pytest exercises/03_fixtures/test_fixtures.py` | 12 passed |
| one test by node id | `pytest exercises/03_fixtures/test_fixtures.py::test_save_and_load_with_tmp_path` | 1 passed |
| by name | `pytest -k coupon exercises/04_parametrize/test_parametrize.py` | 3 passed, 19 deselected |
| by marker | `pytest -m "not slow" exercises/05_markers/test_markers.py` | 4 passed, 2 skipped, 2 xfailed, 2 deselected |

`-k` accepts `and`, `or` and `not`, and matches parts of the test name (including the ids from parametrize). If you are not sure what you can select, use `--collect-only -q` to list all tests without running them.

If an option selects nothing, the exit code is 5 ([lesson 1](/en/pytest/first-test/#exit-codes-what-ci-reads)).

</Step>

## The fix-it loop: -x, --lf, --ff

While fixing a bug you want to rerun the tests that failed, not the whole suite.

| option | What it does | Result for `demos/01_failures` (3 failed, 1 error) |
|---|---|---|
| `-x` | stop after the first failure | `1 failed`, and the remaining tests are not run |
| `--lf` (last failed) | run only the tests that failed last time | reruns 3 failed, 1 error |
| `--ff` (failed first) | run last time's failures first, then the rest | |

(ran: `verify.py`) Pytest remembers the previous result in the `.pytest_cache` folder, which should stay out of git.

</Step>

## Parallel runs with pytest-xdist

With thousands of tests you can use several CPUs with `pytest-xdist`:

```bash
uv run pytest -n 2 exercises/04_parametrize/test_parametrize.py
```

The result is the same as a serial run: 21 passed, 1 xfailed (ran: `verify.py`). The important condition is that the tests are independent, because the order and which tests run together change, and tests that share state start to fail at random ([lesson 15](/en/pytest/test-design/#tests-must-be-independent)).

</Step>

## coverage: which lines never ran

`pytest-cov` measures which lines of your code ran during the tests:

```bash
uv run pytest --cov=shop --cov-report=term-missing
```

```text
Name                   Stmts   Miss  Cover   Missing
----------------------------------------------------
src\shop\__init__.py       0      0   100%
src\shop\cart.py          48      0   100%
src\shop\checkout.py      14      0   100%
src\shop\net.py            2      0   100%
src\shop\pricing.py       15      1    93%   21
src\shop\rates.py         10      0   100%
src\shop\receipt.py        9      0   100%
src\shop\sale.py           7      0   100%
----------------------------------------------------
TOTAL                    105      1    99%
```

The `Missing` column points at lines that never ran. Now only one is left: line 21 of `pricing.py` (`with_tax`, which nobody calls). `cart.py` is at 100% because a test now passes a negative price to `Cart.add` (`exercises/02_assertions/test_assertions_in_depth.py`) (ran: `verify.py`).

<Callout type="warn" title="Coverage says what is not tested, not that it is tested well">
99% does not mean the tests are good. A line run by a test with no assert still counts as covered. Use coverage to find **gaps** (the lines in Missing), not as a target to push to 100% (author).
</Callout>

<Callout type="try" title="Try it in this repo">
Write a test for `with_tax(100)` in `exercises/01_first_test`, then run `uv run pytest --cov=shop --cov-report=term-missing` and see whether the Missing entry of `pricing.py` goes away and what TOTAL becomes. After that remove the `assert` from the new test and see whether coverage is still 100%.
</Callout>
