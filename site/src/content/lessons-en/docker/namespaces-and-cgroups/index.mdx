## A namespace is a view of the kernel given to each process

In [lesson 1](/en/docker/containers/#a-container-is-a-process-that-sees-a-small-world) we saw that a container is an ordinary process that sees itself as PID 1, and we called the mechanism the PID namespace without opening it. Now is the time. The book Container Security puts it briefly: if cgroups control the resources a process can use, namespaces control what it can see. Putting a process in a namespace restricts what that process can see (book: Container Security chapter 4, page 31). Linux supports seven kinds, `cgroup`, `ipc`, `mnt` (mount points), `net`, `pid`, `user` and `uts` (host name), and a process is always in exactly one namespace of each kind (book: Container Security chapter 4, page 32).

We can look at them for real in the file `/proc/self/ns`, which shows the number of each namespace that process is in. In the exercise we start two containers at the same time, and compare them with a container that asks for the namespaces of the Linux that runs the engine (ran).

| Namespace | Two containers compared | A container against the Linux that runs the engine |
|---|---|---|
| `cgroup`, `ipc`, `mnt`, `net`, `pid`, `uts` | differ | differ |
| `user` | the same | the same |

The first six differ everywhere, which means each container has its own full set. But `user` is the same for all, which means Docker does not use a user namespace by default. The `root` user inside a container is the same UID 0 as `root` of the Linux that runs the engine. We come back to that in [the last lesson of this path](/en/docker/capstone-pipeline/#lock-down-the-container-of-the-loader-layer-by-layer) (to separate them we would have to turn on `userns-remap`, which we have not tried and did not run).

<Callout type="warn" title="A mistake we made while measuring">
At first we ran the containers one after another and compared their namespace numbers, and they were all the same, which is wrong. We suppose that when the first container ends its namespace is released and the kernel gives that number to the namespace of the next one (that is our inference, and we did not read the kernel code). What we are sure of is the result we saw, and that the comparison has to be done with containers that are running at the same time, so we changed the exercise to do that (ran).
</Callout>

Switch the options in the lab. For each kind, choose between a namespace of the container's own and sharing that of the host with `--pid=host`, `--net=host` and `--uts=host`. What is seen from inside changes accordingly. For example, the process table goes from a handful of processes to the whole Linux.

## Share a namespace on purpose, and make one without Docker

Since a namespace is something that others can join, Docker lets us choose. With `--pid=container:A`, container B is in the same PID namespace as A and sees A's processes, and the exercise saw the `sleep 300` of A from B (ran). `--network=container:A` puts B in the same network namespace as A, with the same IP address (ran). This pattern is used when we want to attach an inspection tool to a running container without changing its image.

Another interesting thing is that we can make a namespace ourselves without Docker. The Linux command `unshare` does what Docker does. In the exercise we run a `--privileged` container and use `unshare -u` to change the host name inside a new namespace. The result is

```text
inside=made-by-unshare
outside=d4377a1e8f5a was=d4377a1e8f5a
```

Inside we could change it to `made-by-unshare`, while outside it kept its old name, and `unshare -p` made `ps` count from PID 1 (ran). So a container that Docker makes is several calls of this same mechanism at once, plus the other parts the book listed in [lesson 1](/en/docker/containers/), such as changing the root of the file system, dropping privileges and cgroups (book: Docker in Action section 1.1.4, page 6).

## A cgroup is a limit written as a file

Namespaces control what is seen, and the amount that can be used is the job of cgroups. The book says cgroups limit resources such as memory, CPU and network I/O that a group of processes can use, and there is a pid cgroup that limits the total number of processes, which stops the effect of a fork bomb. It adds that because a container is an ordinary process, cgroups can limit the resources of each container (book: Container Security chapter 3, page 23). The kernel passes information about cgroups as files in the folder `/sys/fs/cgroup`. The book explains with cgroup v1, which has files such as `memory.limit_in_bytes`, while this computer is on v2, where the file names are a little different. We give options to Docker and read these files from inside (ran).

| File | No options | `--memory 64m --cpus 0.5 --pids-limit 20` |
|---|---|---|
| `memory.max` | `max` | `67108864` |
| `cpu.max` | `max 100000` | `50000 100000` |
| `pids.max` | `max` | `20` |

The Docker options translate straight into the values in the files. `--memory 64m` is 67,108,864 bytes, and `--cpus 0.5` is a quota of 50,000 microseconds in every 100,000, which means the program may run half of each period. `docker inspect` reads the same limit from outside (ran). Now let us see what a program that hits a limit meets.

We let a Python program ask for memory 10 MB at a time up to 120 MB, under several limits (ran).

| Memory limit | Last MB printed | Result |
|---|---|---|
| none | 120 | finished |
| 256 MB | 120 | finished |
| 64 MB | 50 | killed (`OOMKilled`, exit code 137) |
| 32 MB | 20 | killed |

When memory runs out the kernel kills the program on the spot, which matches the exit code 137 that we saw in the lesson on [the life of a container](/en/docker/container-lifecycle/) is SIGKILL. CPU is different. We let a program spin in an empty loop for 2.5 seconds and measured how much CPU time it got per unit of real time (ran).

| CPU limit | CPU time per real time | Times it was paused |
|---|---|---|
| none | 1.01 | 0 |
| `--cpus 1` | 1.01 | 0 |
| `--cpus 0.5` | 0.52 | 25 |
| `--cpus 0.25` | 0.26 | 26 |

The program does not die. The kernel only pauses it in turns until it matches the quota. The last one is the number of processes. We set `--pids-limit 10` and let a shell open 30 background processes, and the shell reported `can't fork: Resource temporarily unavailable` (ran). A fork past the limit was refused, which is what stops a fork bomb, as the book says. Choose limits in the lab to compare the two different ways of running out of a resource: being killed and being paused.
