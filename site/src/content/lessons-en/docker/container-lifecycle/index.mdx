## The states of a container and the commands that move it

In [lesson 1](/en/docker/containers/#a-container-lives-as-long-as-its-process) we saw that a container ends when the program inside ends. Now let us look at the whole cycle. The book says a container is in one of six states: created, running, restarting, paused, removing and exited (and exited is also used for a container that was never started) (book: Docker in Action section 2.5.1, page 41). In the exercise we ran the commands one at a time and read the state after each.

```text
command         state afterwards  exit code
docker create   created           0
docker start    running           0
docker pause    paused            0
docker unpause  running           0
docker stop     exited            0
docker start    running           0
docker kill     exited            137
```

Three things are worth noticing. First, `docker create` makes a container but does not run the program. The state is `created` and there is no process yet (the Pid is 0). The `docker run` we have used all along is `create` followed by `start`. Second, `docker pause` does not end the program. It only freezes the process, and the process is still there (ran). Third, a container that ended stays in the list until we run `docker rm`, and `docker start` makes it run the same program again (ran).

Press the commands in the lab in order. A command that is not allowed in the current state is disabled, for example you cannot pause a container that was never started. If you press `docker stop`, a clock appears below, and we will come back to it in a moment.

## The exit code says how the program ended

When a container ends, Docker keeps the exit code of the program. It is the first number to look at when we ask why a container ended. In the exercise we ran short programs that end in different ways (ran).

| Program | Exit code of `docker run` |
|---|---|
| `true` | 0 |
| `false` | 1 |
| `sh -c 'exit 3'` | 3 |
| `sh -c nosuchcmd` (the shell cannot find the command) | 127 |
| `nosuchcmd` (no such program in the image) | 127 |
| `/etc/passwd` (the file exists but is not a program) | 126 |

0 means it ended normally. Other numbers are codes the program chose, except 126 and 127, which are commonly used for "cannot run that file" and "command not found" (ran). Rows four and five differ in who reports it. When `sh` cannot find a command, the shell reports 127 itself. When there is no such program in the image, Docker says `executable file not found` and returns 127. A number above 128 means a signal killed the program, and the number is 128 plus the signal. So 137 is 128 + 9 (SIGKILL) and 143 is 128 + 15 (SIGTERM), which we meet in the next part.

</Step>

## docker stop asks politely first, then kills

The book says `docker stop` sends SIGTERM to the process and waits for it to close itself politely. With `-t 25`, if the program has not stopped after 25 seconds, Docker sends SIGKILL (book: Docker Up and Running, Stopping a Container, page 105). What the book does not say is what happens when the PID 1 program does not answer SIGTERM. Let us try.

In the exercise we ran three kinds of program and gave each one `docker stop -t 5` (ran).

| The program that is PID 1 | Time (s) | Exit code |
|---|---|---|
| `sleep 300` | 5.3 | 137 |
| Python with a handler for SIGTERM | 0.4 | 0 |
| `sleep 300` started with `--init` | 0.3 | 143 |

The first `sleep` answered nothing, so Docker waited the whole 5 seconds and sent SIGKILL, which gives 137. The reason is that the kernel treats a process with PID 1 like init. The book says any process with PID 1 is treated like an init process by the Linux kernel, even if it is not technically an init system (book: Docker in Action section 2.5.2, page 42). For such a process a signal that has no handler does not kill it the way it kills an ordinary process (this is general Linux knowledge that we did not check in the documentation). The second one has a handler, so it closes itself at once with the code it chose. The third uses `--init`, where Docker puts a small init program in as PID 1, and it passes SIGTERM on to `sleep`, which dies of that signal, so the code is 143.

Without `-t`, on this engine, `docker stop` on the same `sleep` took about 3.3 seconds. That is a number we measured, and we did not look for whether it comes from the default of this engine or of Docker Desktop. What it teaches is that the wait is a setting, not a fixed number. If a service has to finish its work before closing, give it an explicit `-t`.

<Callout type="tip" title="Our program should handle SIGTERM">
If we write a service that has to flush data to disk before it closes, catch SIGTERM in the program itself, or run it behind an init such as `--init`. Otherwise Docker waits until the time is up and kills it, and unfinished work is lost. The book says the popular inits include tini, dumb-init and supervisord (book: Docker in Action section 2.5.2, page 42).
</Callout>

</Step>

## Logs, exec and stdin

Three more commands are used every day. The first is `docker logs`, which reads what the program printed on stdout and stderr. In the exercise we ran a program that prints `to-stdout` on stdout and `to-stderr` on stderr, and `docker logs` printed them on the matching streams. A container that already ended still has its logs (ran). The option `-t` puts the time in front of every line (ran). One caution: stdout and stderr are two channels, and the order of lines across them is not guaranteed to follow what the program printed. We saw `--tail 1` return the stderr line although the last line the program printed went to stdout (ran).

The second is `docker exec`, which starts one more process in a container that is running. The exit code of the command we run comes back to us (we ran `exit 5` and got 5), and the container does not end because its main process is still there. If the container has already ended, `exec` is refused (ran). The third is the option `-i`, which connects our stdin to the program. When we pipe text into `docker run -i alpine cat`, the same text comes back. Without `-i` the program does not see what we send (ran).

</Step>

## A restart policy lets Docker start the program again when it crashes

When a service crashes for a temporary reason, starting it again on its own brings the system back faster. Docker does this with the option `--restart`. The book lists never restart (the default), restart on failure, restart on failure a limited number of times, and always restart (book: Docker in Action section 2.5.1, page 41). In the exercise we ran programs that end at once, in three ways (ran).

| Policy and program | Restarts | Final state |
|---|---|---|
| `on-failure:2`, the program ends with 1 | 2 | exited |
| `on-failure:2`, the program ends with 0 | 0 | exited |
| `always`, the program ends with 1 | keeps growing (4 when we stopped looking, after a few seconds) | never stops |

`on-failure:2` restarts only on failure and stops after two restarts. If the program ends with 0 it does not restart. `always` restarts every time, whatever the reason. The book explains that Docker does not restart at once but uses exponential backoff, waiting twice as long each time, so the system does not do nothing but restart a crashing program (book: Docker in Action section 2.5.1, page 41). While it waits, the container is in the state `restarting`, and `docker exec` cannot be used then. The exercise saw the refusal that says the container is restarting (ran). That is why the book suggests combining a policy with an init or a startup script that keeps the program inside running, instead of letting the whole container restart in a loop.

</Step>
