## Every container has an IP, but does not know the names of the others

The book says a container attached to a Docker network gets a unique IP address that other containers on the same network can reach, and that Docker treats a network as a thing with a life of its own, created and managed with the `docker network` commands (book: Docker in Action section 5.2, page 83). Every Docker installation comes with three networks: `bridge`, `host` and `none` (ran).

We run two containers without naming a network, which puts both on the default `bridge`, and let A ping B in two ways (ran).

| How we call | Result |
|---|---|
| Ping the IP of B (`172.17.x.x`) | reached |
| Ping the container name of B | not reached |

Both got addresses in the range `172.17.0.0/16` and can call each other by IP, but not by name, because the default bridge has no name resolution. The trouble is that the IP of a container changes every time it is created, so we cannot write an IP into a program. That leads to the next part.

How a container is wired to the bridge, and with what address tables, is already explained in the Networking subject, in [lesson 13](/en/networking/proxies-and-containers/#a-container-is-a-network-namespace-plugged-into-a-bridge). This lesson looks from the side of someone using Docker.

</Step>

## A network we make has DNS

The answer to the name problem is to make our own network with `docker network create` and let the containers join it (`--network name`). In the exercise we do that, and container A reaches B by name (ran). In the file `/etc/resolv.conf` inside the container the name server is `127.0.0.11`, which is a DNS that Docker puts there, and the new network gets an IP range of its own (in this run `172.19.0.0/16`), different from the default bridge (ran).

The second thing we see is that each network is separate from the others. We made another network, `dlab-net2`, and put container C in it. A cannot reach C by name or by IP, but when we run `docker network connect dlab-net2 A`, so A joins the second one as well, A reaches C by name (ran). Here is everything in one table.

| Layout | A calls B by IP | A calls B by name |
|---|---|---|
| Default bridge | reached | not reached |
| The same network we made | reached | reached |
| Different networks we made | not reached | not reached |
| A joined both networks | reached | reached |

Choose the layout and the caller in the lab one at a time. The arrow runs to the target or stops at the edge of a network, according to what was measured.

<NetworkLab client:visible lang="en" />

Two practical rules follow. First, if we want containers to call each other by name, we make our own network and do not use the default bridge. Second, a network can be used to keep apart containers that should not talk, for example to separate a database from services that do not need it (we did not try finer firewall rules between containers on one network, which was not run).

</Step>

## Publish a port so that our computer can call in

Now from the other side. We run two simple web servers (`python -m http.server 8000`) on one network. One has `-p 127.0.0.1:60808:8000` and the other does not, and we try to call them from our computer (Windows) and from another container on the same network (ran).

| Who calls | To where | Result |
|---|---|---|
| Our computer | the published port (`127.0.0.1:60808`) | reached |
| Our computer | the container with no `-p` (through the container IP) | not reached |
| Another container on the same network | the one with `-p`, by name | reached |
| Another container on the same network | the one with no `-p`, by name | reached |

A published port is only a door opened on our computer that forwards into the container. If we do not publish, our computer cannot call in, but containers on the same network can always reach each other without publishing. The `127.0.0.1` in the command says to open the door only on that address, which only our computer can call. `docker port` confirms the port is bound to `127.0.0.1` as we said (ran). If we write just `-p 8000:8000`, Docker opens it on every address, and other computers on our network may be able to call in. We did not try that case (not run).

What is underneath publishing is an iptables DNAT rule, which we already followed in [lesson 13 of the Networking subject](/en/networking/proxies-and-containers/#coming-in-a-published-port-is-a-dnat-rule). This lesson does not run it again.

<Callout type="note" title="Why we cannot call the IP of a container from Windows directly">
The containers live in the network of the Linux that Docker Desktop starts, and not in the network of Windows, so the `172.x.x.x` address of a container cannot be called from Windows directly, and the exercise saw that it was not reached. On a real Linux host it may behave differently, which we did not try.
</Callout>

## Aliases, none and host

Three short things come up often. First, aliases. We give a container an extra name with `--network-alias`, and we can give the same name to two containers. In the exercise we gave the alias `workers` to two containers, and `nslookup workers` answered with two addresses, which match the IPs of those two containers (ran). That is the simplest kind of spreading work with DNS: the client gets several addresses and picks one.

The second and third are two special networks, which the book says are really kinds of attachment with a special meaning, and not real networks (book: Docker in Action section 5.3, page 89). `--network none` gives a container no network at all, and in the exercise we saw only the interface `lo`. `--network host` lets the container use the network of the host directly, with no separate network namespace, and the exercise saw the interfaces of the whole Linux that runs the engine, including `docker0` (ran). The book says it can see and bind every interface of the host. On this computer the host is the Linux inside Docker Desktop, and not Windows.

| Kind of attachment | Interfaces seen inside the container |
|---|---|
| Normal (bridge) | `eth0` and `lo` |
| `--network none` | `lo` only |
| `--network host` | all of the host's, including `docker0` and other bridges |

</Step>

## A program finds its database by name

This is the pattern used every day in data work. In the exercise we run Postgres named `dlab-db` on a network we made, and start another container on the same network to call `pg_isready -h dlab-db` (ran).

```text
dlab-db:5432 - accepting connections
```

The caller finds the database by the container name and port 5432, and we never published a port. Our own computer also cannot call `127.0.0.1:5432` (ran). So a database that is not published is hidden from the world outside, but the programs of ours on the same network can call it, which is a safer way than leaving a port open. We will see this pattern again in the lesson where we join several containers with Compose.

</Step>
