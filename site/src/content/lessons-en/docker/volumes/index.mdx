## Data written in a container goes away with the container

In [lesson 1](/en/docker/containers/#an-image-is-a-template-a-container-is-what-we-make-from-it) we saw that a new container from the same image does not see the file of the old one, and from [lesson 2](/en/docker/images-and-layers/#a-container-sees-the-files-of-every-layer-together) we know that a file a container writes lives in its own writable layer, which belongs to that one container. Data we want to keep, such as the tables of a database, has to live somewhere else. The book says the three most common kinds of storage are bind mounts, in-memory storage and volumes (book: Docker in Action section 4.1, page 63).

In the exercise we try four places. We write a file `note.txt` into the folder `/place` and check whether it is still there after two events: `docker restart`, and removing the container and starting a new one on the same storage (ran).

| Storage | After `docker restart` | After removing the container and starting a new one |
|---|---|---|
| The writable layer of the container | still there | gone |
| A named volume | still there | still there |
| A bind mount | still there | still there |
| tmpfs (memory) | gone | gone |

Try it in the lab. Choose a storage and press write file, restart and remove container in order. You will see that for the first and last kinds, where the file lives inside the container (the writable layer and tmpfs), the file goes with the box that is thrown away. For the two kinds where the file lives outside the container (a volume and a bind mount), the new box attaches to the old storage and sees the file at once.

## A bind mount shares real files with our computer

A bind mount attaches a folder that we name from the host to a place in the container. The book says it is useful when the host has a file the program in the container needs, or when the program makes a file that people or programs outside the container will process (book: Docker in Action section 4.2, page 64). We try it by making a folder on Windows and attaching it to `/work`.

```bash
docker run -d --name b --mount type=bind,source=C:\Users\me\share,target=/work alpine:3.22 sleep 300
```

In the exercise, a file we made on Windows appears in the container, a file the container makes appears on Windows, and when we edit the file on Windows the inside sees the change at once without a restart (ran). That is why people use bind mounts while developing: we edit code in the tool we like and the container sees it straight away. If we do not want the container to overwrite our files, add `readonly`, and the exercise found that writes are refused with the message `Read-only file system` (ran).

On this computer the folder we attach is a Windows folder, but the container works in the Linux that Docker Desktop starts, so files are passed between two systems. We did not measure the speed or the file permissions in that case (not run).

</Step>

## A volume lets Docker keep the data for us

A volume is a named folder that Docker manages. The book says it separates the storage from a specific location on the file system of the host, so a set of containers can run on any computer without caring whether a location on disk collides with other software (book: Docker in Action section 4.4, page 68). We create one with `docker volume create` and attach it with `--mount type=volume`. In the exercise there are three things that differ from a bind mount.

First, an empty volume is filled by Docker with the files that the image has at that place. We build an image that has `/data/seed.txt` and attach a new volume at `/data`, and the inside sees `seed.txt`. But if we attach a bind mount of an empty folder at the same place, the inside sees an empty folder, and the file of the image is hidden (ran).

| What is attached at `/data` | What the container sees |
|---|---|
| Nothing | `seed.txt` |
| A new empty volume | `seed.txt` (Docker filled it) |
| A bind mount of an empty folder | empty (the file of the image is hidden) |

Second, a volume can be shared by containers that run at the same time. We let one write `live.txt` and another read it at once (ran). Third, Docker refuses to remove a volume that a container still uses. The reply says the volume is in use, and it can be removed once no container uses it (ran).

<Callout type="note" title="Where a volume really is">
On this computer a volume lives in the file system of the Linux that Docker Desktop starts, not in a Windows folder we can open directly. The book says that by default Docker creates a folder to hold the content in a part of the host file system that the engine controls, and `docker volume inspect` shows the place (book: Docker in Action section 4.4, page 68). We did not open that folder (not run).
</Callout>

## An anonymous volume piles up if we do not clean it

There is another way a volume comes into being that people often do not know. If a Dockerfile has the line `VOLUME /data`, Docker creates an anonymous volume for every container run from that image. We ran two containers from such an image without `--rm` and counted the new volumes (ran).

| Event | Anonymous volumes left |
|---|---|
| Run two containers | 2 |
| `docker rm` the first (no `-v`) | 2 |
| `docker rm -v` the second | 1 |

An anonymous volume is not deleted with its container unless we run `docker rm -v` or run the container with `--rm`. The book says the same: an anonymous volume is deleted automatically when the container that created it is deleted in those two ways, and a named volume always has to be deleted by hand (book: Docker in Action section 4.6, page 77). That can fill the disk of Docker without our noticing, because a leftover volume is harder to see than a leftover container. Check `docker volume ls` from time to time.

</Step>

## A database whose data is on a volume survives the removal of its container

This is the main reason a data engineer needs to know about volumes. In the exercise we run Postgres 17 with a volume attached at its data folder (`/var/lib/postgresql/data`), create a table `orders` and insert two rows. Then we remove the container completely and start a new Postgres on the same volume (ran).

| Step | Rows in the table `orders` |
|---|---|
| The first container, after the insert | 2 |
| A new container on the same volume | 2 |

The table and its data are all there, because Postgres writes its data files into the volume, which is outside the container. Without the volume, those files would be in the writable layer of the first container and would be gone with its removal. What we did not test is backing up a volume, and upgrading the version of Postgres on the same volume, which needs a check of whether the data files are compatible (not run).

</Step>
