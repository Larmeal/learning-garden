## Run a first container and meet something odd

Say we use a Windows computer and have just installed Docker. Type a short command that asks which kernel is running.

```bash
docker run --rm alpine:3.22 uname -r
```

```text
6.18.58.1-microsoft-standard-WSL2
```

The command has four parts. `docker run` tells Docker to create a container and start it. `--rm` removes the container when it ends. `alpine:3.22` is the image we use (the name Alpine and the tag `3.22`), and the last part is the program to run inside, here `uname -r`, which prints the version of the kernel.

Wait. The answer is a Linux kernel with Microsoft in its name, although we never installed Linux, and the image we ran is Alpine, which is yet another operating system. If we run two more images and read `/etc/os-release`, the file that names the operating system, we get this (ran).

| Image | `uname -r` | Operating system named in `/etc/os-release` |
|---|---|---|
| `alpine:3.22` | 6.18.58.1-microsoft-standard-WSL2 | Alpine Linux v3.22 |
| `busybox:1.37` | 6.18.58.1-microsoft-standard-WSL2 | the file does not exist |
| `python:3.13-slim` | 6.18.58.1-microsoft-standard-WSL2 | Debian GNU/Linux 13 (trixie) |

All three report the same kernel, yet the system files inside are different. Stop for a moment and ask how that can be. If each container were a "new computer", it would have its own kernel.

</Step>

<Step>

## A container does not boot an operating system

The answer is that a container is not a virtual machine. A virtual machine imitates a whole set of hardware and installs a complete operating system on it. That often takes minutes and costs a lot, because a whole operating system runs next to the program we actually want. A container uses no hardware imitation at all. The program in it talks to the kernel of the computer that runs it, directly (book: Docker in Action section 1.1.3, page 5).

Pick a number of programs in the lab and compare the two sides. On the virtual machine side the number of kernels grows with the number of programs. On the container side there is one kernel, and each program only adds its own files.

<KernelStackLab client:visible lang="en" />

So why does a Windows computer have a Linux kernel for the containers to use? Docker Desktop starts a Linux behind the scenes (WSL2 on this computer) and runs Docker Engine and all the containers inside it. The book says the same: people who use Docker on Mac and Windows, and nearly everyone in the cloud, run Docker inside a virtual machine, so the two technologies work together (book: Docker in Action section 1.1.3, page 5). That is why the word host in this course means that Linux, and we do not mean Windows.

<Callout type="note" title="Docker did not invent container technology">
Docker uses things that are already in the Linux kernel. The book lists ten that Docker uses to build a container: namespaces for PIDs, host name, the file system, communication between processes, the network and users, then `chroot`, `cgroups`, dropping privileges (CAP Drop) and security modules (book: Docker in Action section 1.1.4, page 6). We will open these up one by one later on this path. For now it is enough to know that they are kernel features that Docker makes easy to use.
</Callout>

</Step>

## A container is a process that sees a small world

If a container is not a new computer, it should be something smaller. Let us check. Start a container that keeps busy for five minutes (`-d` runs it in the background and `--name` gives it an easy name), then ask what is running inside.

```bash
docker run -d --name a alpine:3.22 sleep 300
docker exec a ps -o pid,args
```

```text
PID   COMMAND
    1 sleep 300
    7 ps -o pid,args
```

`docker exec` runs one more command inside a container that is already running. We see `sleep 300`, the program we asked for, with PID 1, and the `ps` we just called as the only other process. So this is everything the container holds (ran).

Now look from the outside. In the exercise we start three containers from different images and run `ps` again from a container with `--pid=host`, which lets it see every process of the engine. The result is

```text
  2746  sleep 300
  2795  sleep 301
  2840  python -c import time; time.sleep(302)
```

The program that was PID 1 inside is an ordinary process with its own number outside (the numbers change on every run), and `docker top a` shows the same process from the engine's side. This matches what the book says: the state of a container is tied to the one program that runs in it (book: Docker in Action section 1.1.1, page 3). What lets it see itself as PID 1 is a mechanism called the PID namespace, one of the ten mentioned above.

Switch where you stand in the lab. Standing in room a, you see only our own program and it is PID 1. The other rooms and the other processes of the engine disappear. Standing outside, everything comes back, and no program of any container is PID 1.

## A container lives as long as its process

Once a container is a process, its life is tied to that process. Run a program that sleeps for only three seconds, and ask for the state at the start and again after five seconds.

```bash
docker run -d --name short alpine:3.22 sleep 3
docker inspect -f '{{.State.Status}}' short      # running
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' short   # after 5 seconds: exited 0
```

While `sleep` is still asleep the container is `running`. When `sleep` ends, it becomes `exited` with exit code 0, the code a program returns when it finishes (ran). If we run `docker start short`, Docker runs the same program again and the state goes back to `running` (ran). The book puts it this way: if the program runs, the container runs, and if the program stops, the container stops (book: Docker in Action section 1.1.1, page 3).

This explains something beginners meet often: they start a container and it ends at once. Usually the program we asked for finished its work and left, and that does not mean Docker has a problem. We will come back to states, exit codes and stopping a container in the next lessons.

</Step>

## An image is a template, a container is what we make from it

We have used one more word without explaining it, the image `alpine:3.22`. Run a container that writes a file and reads it back, then run a new container from the same image and try to read the same file.

```bash
docker run --name w1 alpine:3.22 sh -c 'echo hello > /note.txt && cat /note.txt'
docker run --rm alpine:3.22 cat /note.txt
```

```text
hello
cat: can't open '/note.txt': No such file or directory
```

The first container can write and read the file. The second one does not see it at all, although both come from the same image. When we go back to the first with `docker start -a w1`, `note.txt` is still there (ran). The picture to keep is that an image is a read-only template and each container has its own place to write. The book uses the shipping container as its picture: an image is the box packed and ready to ship, and containers made from one image do not share the changes they make to their file systems (book: Docker in Action section 1.1.5, page 7).

Every `docker run` creates a new container. The old ones that have ended stay in the list until we remove them, which is why `w1` and `short` show as `Exited` in `docker ps -a`, and why we add `--rm` to commands whose result we do not need to keep. What an image is made of, and why it does not change when we write a file, is the subject of [the next lesson](/en/docker/images-and-layers/).

<Callout type="warn" title="Some commands in the book do not work on Docker 29">
The book we cite was printed in 2019. It has the command `docker inspect -f '{{.NetworkSettings.IPAddress}}'` to read the IP address of a container, and it no longer works on Docker 29.2.1. That field was removed, and Docker answers `map has no entry for key "IPAddress"`. Read the address under the network's name instead, for example `{{.NetworkSettings.Networks.bridge.IPAddress}}` (ran). If a command from a book breaks like this, compare it with the full output of `docker inspect` first.
</Callout>

</Step>
