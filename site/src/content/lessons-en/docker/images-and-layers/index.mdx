## An image is a stack of layers

In [lesson 1](/en/docker/containers/#an-image-is-a-template-a-container-is-what-we-make-from-it) we called an image a read-only template. This time let us open it and see how the template is kept. The command `docker image inspect` tells us how many layers an image has, and for the three images we have used so far the answer is (ran)

| Image | Layers | Size (MB) |
|---|---|---|
| `alpine:3.22` | 1 | 8.3 |
| `busybox:1.37` | 1 | 4.4 |
| `python:3.13-slim` | 4 | 118.4 |

Alpine has one layer because it is the files of a whole system packed into one piece. Python has four, stacked one after another by the steps its author took. The book explains that a layer is a set of files plus the metadata of those files, packaged and shipped as one unit, and that most layers are built on a parent layer by recording which files changed. The files a container sees are therefore the union of every layer in the lineage of its image (book: Docker in Action section 3.3, page 56, and section 3.3.2, page 58).

Each layer has an id that is the sha256 of its content. An image has a 64 character id too, and Docker shows only the first twelve so that it is easy to read (ran). The fact that an id comes from content is exactly what makes the next part possible.

</Step>

## Two images share the same layer

Let us build two images on the same Alpine. The first, `dlab-app1`, adds one file of 1 MB. The second, `dlab-app2`, adds one file of 2 MB (we write Dockerfiles in the next lessons, so for now look only at the result). When we run `docker image inspect` on all three, the layer ids differ at the top and are identical at the bottom (ran).

```text
image        layer 1       layer 2
alpine:3.22  fdc5834cb53a
dlab-app1    fdc5834cb53a  e799cedb75df
dlab-app2    fdc5834cb53a  b458dafe34ef
```

Layer 1 of all three images has the same id. Docker does not keep two copies of Alpine. It keeps one and lets both images point at it. Switch the lab and compare. With one image, the figure stored and the figure if each image kept its own copy are the same. Add the second image and the base layer is still one box, while the two numbers move apart at once.

<SharedLayersLab client:visible lang="en" />

The book tells the same story with two Java programs on a common base image. When the second one is installed, Docker sees the base layer is already there and downloads only the part that differs, less than one megabyte, and with virtual machines the repeated files would be stored once for every machine (book: Docker in Action section 3.3.1, page 57, and section 3.3.4, page 60). For a user this benefit comes for free. For the author of an image, choosing the same base image as other images saves both download time and disk space.

</Step>

## A container sees the files of every layer together

An image is read-only, so how does a container write files? Docker puts an empty writable layer on top of the stack and uses a union file system to put all the layers together so they look like one folder. On this computer Docker uses one called `overlay2`. We checked that a running container has a mount made of one read-only folder for each layer of the image, one more folder that Docker adds itself (we did not open it to see what is inside), and one folder to write in (ran). When a file is read, the system looks from the top layer down until it finds it (book: Docker in Action section 7.2.1, page 131).

Let us see what happens when a container changes files in three ways. We start a container from `dlab-app1`, which has two layers, and do one thing at a time: add a new file, change a file of Alpine, and delete a file that lives in the second layer. Press Next in the lab one step at a time and watch the right side to see what changes in the writable layer.

<UnionLab client:visible lang="en" />

The command `docker diff` reports the changes in the writable layer with three letters. `A` is a file that was added, `C` is a file or folder that changed, and `D` is a file that was deleted. The folder holding the file always shows `C` too (ran). Every line matches what the book shows (book: Docker in Action section 7.2.1, page 131). Notice two things. First, no step touched the image. When we start a new container from the same image, it still sees the original `/etc/passwd` and `/data1` (ran). Second, deleting does not remove the file from the lower layer. The writable layer only notes that the file was deleted, which hides it from the container and nothing more.

</Step>

<Step>

## Change one byte, copy the whole file

One thing surprises people when they change a file of a lower layer. A lower layer cannot be changed, so Docker first copies the file up into the writable layer and changes the copy. The book calls this copy-on-write and says it hurts run-time performance and image size (book: Docker in Action section 7.2.1, page 131). In the exercise we build an image with one file of 20 MB and start two containers. One only reads the file, and the other appends one character and a new line (two bytes). Then we look at the size of the writable layer of each (ran).

| Container | Writable layer (bytes) |
|---|---|
| reads the file only | 0 |
| appends two bytes | 20,971,522 |

Reading does not make the writable layer grow at all, but adding two bytes made the whole 20 MB file get copied up (the original 20,971,520 bytes plus the two we added). That is why a big file that changes often should not live in an image for a container to edit in place. That kind of data belongs in a volume, which is the subject of a later lesson.

<Callout type="note" title="Other storage drivers use the same idea">
Docker picks a union file system that suits the system, and the book warns that each has limits. For example Btrfs and OverlayFS do not support the extended attributes that SELinux needs, and files read with `mmap` are hard to support on copy-on-write (book: Docker in Action section 3.3.5, page 60). We only tried `overlay2`, so we did not check that the others follow all of this (not run).
</Callout>

</Step>

## Layers only add, deleting later gives nothing back

This is what people writing a Dockerfile get wrong most often. If the layers of an image are read-only, deleting a file in a later layer can only hide it, and the original bytes stay in the layer below. We build two images. The first creates a 10 MB file on one `RUN` line and deletes it on another. The second creates and deletes it on the same `RUN` line. The result (ran):

| Image | Size (MB) | Layers |
|---|---|---|
| `alpine:3.22` | 8.3 | 1 |
| create then delete, two `RUN` lines | 18.8 | 3 |
| create and delete on one `RUN` line | 8.3 | 2 |

The first is 10.5 MB bigger than Alpine, although a container from it can no longer see the file (`ls /big` answers that there is no such file). The second is exactly as big as Alpine, because the file was deleted before the layer was closed and so it was never recorded. Press play in the lab to see the height of the two stacks.

<AdditiveLab client:visible lang="en" />

The book sums it up: whenever an image changes, a new layer is added, and old layers are never removed (book: Docker in Action section 7.2.3, page 137). In practice, if you want a small image, do the work that makes a temporary file and deletes it inside one `RUN` line. We will come back to this when we write Dockerfiles and shrink images.

</Step>

## A tag is only a name, the id is the identity

We now know an image is a stack of layers identified by an id. So what is a name such as `alpine:3.22`? It is the name of a repository (`alpine`) and a tag (`3.22`), and it is only a label that points at the id of one image. We gave the same image another name with `docker tag alpine:3.22 dlab-alias:1` and looked at the ids. Both names point at one image, and when we deleted the new name the image stayed, because the other name still pointed at it (ran). The book draws the same picture: a repository holds tags, and each tag points at the top layer of an image (book: Docker in Action section 7.2.2, page 134).

Another fact about ids: if we build the same Dockerfile twice, we get the same image id, character for character, because the second build reuses every layer made the first time (ran). Reusing layers at build time is the subject of the lesson on the build cache that is coming on this path.

<Callout type="tip" title="Images without a name">
The book says `docker images` normally shows only repositories. With `-a` it also shows images that have no name, displayed as `<none>`, and those can be referred to only by their id, for example an image built without a tag (book: Docker in Action section 3.3.1, page 57, not run).
</Callout>
