## The pipeline we will put in containers

In this last lesson we bring together everything we learned into one job. Say there is a file `orders.csv` with five rows to load into Postgres, and one row has a negative quantity and must be rejected. We write the loader (`etl`) in short Python that reads the file, checks the rows, and inserts the rows that pass into the table `orders`, and we put everything in one Compose file.

```yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: {test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U postgres"], interval: 2s, retries: 40}
    networks: [backend]
  etl:
    build:
      context: ./etl
    depends_on: {db: {condition: service_healthy}}
    secrets: [db_password]
    volumes: ["./data:/data:ro"]
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    mem_limit: 128m
    pids_limit: 64
    networks: [backend]
networks:
  backend: {internal: true}
secrets:
  db_password: {file: ./db_password.txt}
volumes:
  pgdata:
```

The Dockerfile of `etl` uses what we learned in the lesson on [small and safe images](/en/docker/small-and-safe-images/#run-the-container-as-a-user-that-is-not-root): a slim base image, packages installed without keeping the cache, a user `etl` (UID 10001), `COPY --chown` so that user owns the files, and then `USER etl`.

When we run `docker compose up -d --build`, Compose builds the image, starts `db`, waits until its state is `healthy` (the lesson on [Docker Compose](/en/docker/compose/#depends_on-has-to-wait-until-the-service-is-ready)), and then starts `etl`. What the exercise saw is that `etl` ends with exit code 0, prints `loaded 4 rejected 1 rows in table: 4`, and the table in Postgres holds rows 1, 2, 4 and 5, with no row 3, the one with the negative quantity (ran).

## Lock down the container of the loader, layer by layer

In the Compose file above, several lines do not make the pipeline faster. They make it safer. We checked that each line really works, from outside with `docker inspect` and from inside by trying things that should not be possible (ran).

| Line in Compose | What we found |
|---|---|
| `USER etl` in the Dockerfile | `id -u` inside gives `10001` |
| `read_only: true` | writing `/x` fails with `Read-only file system` |
| `tmpfs: [/tmp]` | but writing `/tmp` works |
| `volumes: ["./data:/data:ro"]` | writing into `/data` fails |
| `cap_drop: [ALL]` | `CapEff` in `/proc/self/status` is `0000000000000000` |
| `mem_limit: 128m`, `pids_limit: 64` | `docker inspect` gives 128 MB and 64 |

The interesting one is `cap_drop`. In the lesson on namespaces we saw that a container has no user namespace of its own, so `root` in a container is the same UID 0 as in the Linux that runs the engine. So limiting the powers of root inside a container to what is really needed matters. The special powers of root are split into smaller pieces called capabilities, and Docker lets a container hold only some of them. The book says the Linux kernel, from version 2.2, began to split the powers of root into smaller pieces with this mechanism, instead of having only root and not root (book: Container Security chapter 2, page 19). A normal container with nothing set has a `CapEff` of `00000000a80425fb`, which means it holds several capabilities, while `etl`, with all of them dropped, is all zeros (ran).

The option `no-new-privileges` protects in another way: it stops a program from gaining privileges through a file that has the setuid bit. The book explains that setuid is a path to raising privileges, so some image scanners warn when they find files with that bit, and it can be prevented with the option `--no-new-privileges` of `docker run` (book: Container Security chapter 2, page 16). The exercise only checked that the option is set in `docker inspect`. We did not try an attack with a real setuid file (not run).

## The secret as a file, and a network with no way out

In the lesson on safe images we passed a secret into the build without leaving a trace. At run time there is a way too. Compose gives a secret to a container as a file under `/run/secrets`. In the exercise the password is in the file `db_password.txt`. Postgres reads it through the variable `POSTGRES_PASSWORD_FILE`, which points at the file, and the program `etl` opens the same file. What we could verify is that the value of the password is not in the environment of either container (seen from `docker inspect`), is not in the `docker history` of the built image, and can be read from the file under `/run/secrets` as intended (ran). The advantage over putting it in a variable is that environment variables are often printed into logs or error reports by accident, while a file has to be opened on purpose (that is the opinion of the author, and was not tested).

The last thing is the network. We declare `backend` as `internal: true`, which lets the containers on that network talk to each other but not go out to the internet. The exercise asked `etl` to call `example.com` and it did not succeed, and `docker network inspect` confirmed `Internal` is true (ran). So a loader that is broken into cannot send data out directly, and the database never published a port in the first place, which matches what we saw in the lesson on [Docker networks](/en/docker/networks/#a-program-finds-its-database-by-name).

<Callout type="note" title="What this pipeline does not yet protect">
All this locking reduces the damage if the loader is broken into, but it does not make the system completely safe. We did not try seccomp and AppArmor, which limit system calls, rootless Docker, which does not let the engine run as root, scanning an image for vulnerabilities, or keeping passwords in a real secret manager (not run). And the pipeline is a small example, a CSV of five rows.
</Callout>

## When it breaks, find the cause from status, log and inspect

A good pipeline has to be quick to diagnose when it breaks. We broke it three ways by setting Compose environment variables, and looked at which command says what (ran).

| Broken by | `docker compose ps -a` | Exit code | OOMKilled | Last line of the log |
|---|---|---|---|---|
| A wrong host name | `etl exited 1` | 1 | false | `failed to resolve host 'dbx'` |
| A wrong password | `etl exited 1` | 1 | false | `password authentication failed for user "postgres"` |
| Too little memory | `etl exited 137` | 137 | true | (empty) |

First, the first two cases get exit code 1, yet the causes differ. The status from `compose ps` is not enough, and we have to open the log, which gives the cause directly. Second, the memory case gets exit code 137 with `OOMKilled` true in `docker inspect`, which matches what we saw in the lesson on [namespaces and cgroups](/en/docker/namespaces-and-cgroups/#a-cgroup-is-a-limit-written-as-a-file), and the log is empty because the program was killed before it could print anything. Knowing that an empty log carries meaning in itself saves us from reading the code of the program. `docker events` also recorded the `oom` event of the container in this case (ran). When we put the settings back, the pipeline ran again, and the table in the volume still had its four rows (ran).

The order of the search is therefore a ladder of four steps: the status and exit code first, then the log, then `docker inspect` for `OOMKilled` and the real exit code, and last `docker events`. If it is still unclear, choose a way of breaking it in the lab and see where the arrow stops and what each command prints.
