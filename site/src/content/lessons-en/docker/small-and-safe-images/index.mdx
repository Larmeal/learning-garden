## The same image can weigh about twenty times more

Our program is tiny. It has three lines that print the version of the package `six`, but the size of the image depends almost entirely on which base image we start from. In the exercise we build the same program three times on three kinds of Python (ran).

| Base image | Image size (MB) | Prints the same? |
|---|---|---|
| `python:3.13` | 1121.1 | prints `six 1.17.0` |
| `python:3.13-slim` | 126.8 | prints `six 1.17.0` |
| `python:3.13-alpine` | 54.1 | prints `six 1.17.0` |

All three do the same work, but the first is about nine times heavier than the second (the gap between 126.8 and the 118.4 MB of a bare `slim` comes from the `pip install` line, and we did not check what it adds). The difference exists because the full image carries tools for building software, and the exercise confirms that `gcc` is in `python:3.13` but not in `slim` (ran). The running program never uses a compiler, so those tools are dead weight.

The weight has two sides. One is size, which takes disk, makes downloads slow, and costs time when the image is pulled elsewhere. The other is security. The book says an all-in-one image that holds both the build tools and the run tools gives an attacker more options to exploit the application, and has to be updated more often because there is more to patch (book: Docker in Action section 10.2.1, page 200). Its example starts at 614 MB and ends at 708 MB.

<Callout type="note" title="Alpine is the smallest, but not always the answer">
The 54.1 MB of Alpine is attractive, but we only tested a program that compiles nothing. Alpine uses a different C library from Debian (musl against glibc), and many Alpine users find that some packages have to be compiled by hand. We did not try that (not run).
</Callout>

</Step>

## Multi-stage builds build on a big image and ship on a small one

Sometimes we really need build tools at build time, such as a compiler, but not at run time. The answer is a multi-stage build, which the book calls the Build Plus Runtime pattern: one build image, separate from a smaller runtime image (book: Docker in Action section 10.2, page 199). One Dockerfile can have several `FROM` lines. Each starts a new stage, and the image that ships is the last stage.

```dockerfile
FROM python:3.13 AS build
RUN pip install --no-cache-dir --target /deps six==1.17.0

FROM python:3.13-slim
COPY --from=build /deps /deps
ENV PYTHONPATH=/deps
COPY app.py /app/app.py
CMD ["python", "/app/app.py"]
```

The first stage is named `build`. It uses the big image to install the package into the folder `/deps`. The second stage starts from `slim` and uses `COPY --from=build` to take only that folder across stages. The result is (ran)

| Dockerfile | Image size (MB) |
|---|---|
| Single stage on `python:3.13` | 1121.1 |
| Multi-stage (build on `python:3.13`, ship on `slim`) | 118.4 |

The multi-stage image still runs the program with the same output. It has no `gcc`, and not one layer of the big image came along, which we checked by comparing the layer lists (ran). If we want to stop at the first stage to look at it, `docker build --target build` gives the big image of that stage (ran). Press through the lab to see what is left behind.

<MultiStageLab client:visible lang="en" />

One thing to understand correctly: the build stage does not disappear. It is still on our computer and uses the cache on repeat builds, but it is not shipped, and whoever receives our image does not see it.

## Run the container as a user that is not root

By default a container runs as root. In the exercise `id -u` in `python:3.13-slim` with no `USER` gave 0 (ran). Running as root is a risk, because if the program is broken into, the attacker gets the highest privileges in there at once. The book says the known ways of breaking out of a container all rely on administrator privileges inside it (book: Docker in Action section 8.6.2, page 169). So the practice is to create another user and drop privileges as early as we can.

In the exercise we create a user `app` (UID 10001) and try two ways. In the first, we `COPY` the program into the folder `/app`, which root owns, and use `USER app`, and the program tries to write a file in that folder (ran).

```text
PermissionError: [Errno 13] Permission denied: '/app/out.txt'
```

The program has no permission to write in root's folder. In the second way we set the owner explicitly: `chown` on the folder when creating it, and `COPY --chown=app:app` for the file, because from [lesson 4](/en/docker/dockerfile/#copy-add-and-who-owns-the-files) we know that `COPY` always makes root the owner. The program runs as UID 10001 and writes its file normally (ran).

Two more things to know. First, whoever runs `docker run` can always override the user of the image with `--user`. The exercise ran `--user 0` and got root even though the image says `USER app` (ran). The book says the same: an image cannot stop a container from running as root, and the best an image author can do is create a non-root user and make it the default (book: Docker in Action section 8.6.2, page 169). Second, if we drop privileges too early, steps in the Dockerfile may stop working, for example `USER 1000` followed by a `touch` on a file that root owns. The book gives that example (book: Docker in Action section 8.6.2, page 169, not run). It gives another one, that a program that needs a port below 1024 needs more privileges, which we did not try.

</Step>

## A build secret must not stay in the image

In [lesson 4](/en/docker/dockerfile/) we saw that a value passed through `ARG` and used on a `RUN` line shows up in `docker history`. If a build really needs a secret, such as a token to download a private package, BuildKit has a way that leaves no trace: `RUN --mount=type=secret`, which puts the secret file in place for that one line while it runs and removes it at once.

```dockerfile
RUN --mount=type=secret,id=tok sh -c 'wc -c < /run/secrets/tok > /length.txt'
```

```bash
docker build --secret id=tok,src=token.txt -t dlab-secret .
```

In the exercise we create a file `token.txt` with a 25 character secret, and let the `RUN` line write its length into a file (ran). The result is that the line really could read the secret at build time, since the result file says 25, but the secret itself is not in `docker history`, and there is no `/run/secrets` folder in the running container. We also saved the image as a `.tar` file and searched every byte, and the value is nowhere (ran).

<Callout type="warn" title="What was and was not checked">
We checked only that the secret is not in the history, not in the container and not in the saved files of that image. If the `RUN` line deliberately writes the secret into a file, it can still stay behind, and mounting a secret does not prevent that. We also did not try passing secrets at run time (for example through Compose or a Docker secret), which is a different matter.
</Callout>

</Step>
