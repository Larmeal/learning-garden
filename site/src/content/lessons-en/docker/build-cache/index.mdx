## The second build is fast because Docker reuses the layers

In [lesson 4](/en/docker/dockerfile/#a-dockerfile-is-a-recipe-that-docker-reads-line-by-line) we built an example and got an image straight away. Now let us build a Python program that has to install a package with `pip install`, which is slower because it downloads from the internet. We start with a first build that bypasses the cache, then build again without changing anything (ran).

| Build | Time | Steps that used the cache |
|---|---|---|
| The first (cache off) | 3.7 s | none (except `WORKDIR`) |
| Again, nothing changed | 0.5 s | every step |

The second build is about seven times faster, because Docker ran nothing new. It saw that every line, and everything that line reads, is the same as before, so it took the layers it had already built. The book puts it this way: when a line fails in the middle of a job, the builder can restart from the same position after the fix (book: Docker in Action section 8.1, page 145). Another book measured a build with and without the cache and saw a big gap, because the order of the lines in a Dockerfile has a large effect on the average build time (book: Docker Up and Running, Optimizing for the Cache, page 79).

To force everything to run again, use the option `--no-cache`, which makes the `COPY` and `RUN` steps run again (ran).

<Callout type="note" title="Something we did not look into">
When we build with `--no-cache`, the `WORKDIR` line still says `CACHED`. That is what BuildKit in Docker 29.2.1 really did (ran). We did not look into why, so all we can say is not to expect `--no-cache` to skip every line, especially the lines that do not run a command.
</Callout>

</Step>

## The order of the lines decides how many steps run again

The cache of Docker is a chain. Each step depends on the one before it, and if one step changes, every step after it has to run again, even if it did not change itself. In the exercise we edit one file and compare two Dockerfiles that differ only in order (ran).

```dockerfile
# version A                              # version B
FROM python:3.13-slim                    FROM python:3.13-slim
WORKDIR /app                             WORKDIR /app
COPY . .                                 COPY requirements.txt .
RUN pip install -r requirements.txt     RUN pip install -r requirements.txt
CMD ["python", "app.py"]                 COPY app.py .
                                         CMD ["python", "app.py"]
```

| Order | Edit `app.py` | Edit `requirements.txt` |
|---|---|---|
| A: `COPY . .` first | 3.5 s (`pip install` runs again) | 3.5 s |
| B: `requirements.txt` first | 0.8 s (`pip install` uses the cache) | 3.8 s |

When we edit `app.py`, which is what we change most while writing a program, version A has to install the packages again every time. `COPY . .` reads every file, so it changes with `app.py`, and the chain breaks before `pip install`. Version B copies only `requirements.txt` before installing and puts `app.py` last. When `app.py` is edited, the chain breaks at the final step, and the slow `pip install` still uses the old result. Switch the options in the lab. You will see that version B still breaks the chain when `requirements.txt` is edited, because the packages really changed, and that is correct.

<CacheLab client:visible lang="en" />

The rule is to copy only the files the expensive step needs, run that step, and only then copy the rest.

</Step>

## The cache looks at the content of a file, not at the clock

Two facts help us predict the cache better. First, Docker looks at the content of the files that `COPY` reads, not at their modification date. We changed the modification time of `app.py` to an hour ahead with the same content and built again, and every step still used the cache (ran). Second, the chain of the cache breaks all the way down. We edited only the first `RUN` line of a Dockerfile with three `RUN` lines, and all three had to run again, although the last two did not change by one character (ran). The reason is that each layer is built on the layer before it, and if the base layer changes, the layers that follow are no longer the same ones.

These two facts give a simple practical rule: put the lines that change least at the top and the lines that change most at the bottom, which is what we saw in version B.

</Step>

## The build context is what is sent to the builder

The `.` at the end of `docker build` is more than the place of the Dockerfile. It is the build context, the folder that `COPY` can see. The book advises that the first thing to do on a new project is to decide which files must never be copied into an image, with a `.dockerignore` file (book: Docker in Action section 8.2.1, page 149). In the exercise we put a 20 MB file `big.bin` next to the Dockerfile and measure how many bytes were sent to the builder (ran).

| Dockerfile | Bytes sent to the builder |
|---|---|
| `COPY small.txt /` (`big.bin` not used) | 38 |
| `COPY . /ctx/` | 20,980,000 |
| `COPY . /ctx/` and a `.dockerignore` that lists `big.bin` | 106 |

The book was printed when Docker still used the old builder, and says the whole folder is sent every time, which is the message `Sending build context to Docker daemon` in its output (book: Docker in Action section 8.1, page 145). BuildKit in Docker 29.2.1 is smarter. If the Dockerfile uses only `small.txt`, it sends just that file (38 bytes). The real problem is `COPY . .`, which pulls in every file in the folder, including ones we did not mean to include, such as big data, a `.git` folder or a secret file. The result is a slower build and those files inside the image. `.dockerignore` fixes both. With `big.bin` listed, the build context drops to 106 bytes and the image does not hold that file (ran).

The other side of the same thing is that `COPY` cannot see anything outside the build context. We tried `COPY ../secret.txt /` and the build failed, saying `/secret.txt` was not found (ran). To use a file from outside, move it into the folder that is the context, or change the context so that it covers that file (we did not try the second way).

</Step>
