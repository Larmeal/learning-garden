## A Deployment suits only things that run for ever

The Deployment we have used was made for programs that should stay up all the time. If a Pod ends it makes a new one. But much of a data engineer's work is not like that: a load that runs and finishes, a job that runs every night, a log collector that must be on every node, or a database that needs a name and data of its own. Kubernetes has a workload for each (book: Kubernetes Patterns, Batch Job page 63, Periodic Job page 69, Daemon Service page 73 and Stateful Service page 87). Choose by what must stay true, and let us go through them one by one in this lab.

## Job: succeed a number of times, then stop

A Job creates Pods that run to the end, and counts how many succeeded (book: Kubernetes Up and Running, Job Patterns, page 140). We set `completions: 6` and `parallelism: 2`, meaning six successes are needed, with at most two running together. In the real run at most 2 Pods ran at once, and it ended `Complete` after about 18 seconds. Finished Pods are not deleted. All six were left as `Succeeded`, so their logs can be read later (ran).

What if the program fails? We made a Job with `backoffLimit: 2` and a program that exits with code 1 every time. The Job tried until 3 Pods had failed and then gave up, with the reason `BackoffLimitExceeded` (ran). For a Job we usually set `restartPolicy` to `Never` or `OnFailure`, and not `Always` as a Deployment does, because otherwise a Pod that ends would be started again for ever.

</Step>

<Step>

## CronJob: Jobs created on a schedule

A CronJob only makes Jobs on a schedule like Linux cron. It runs nothing itself (book: Kubernetes Up and Running, CronJobs, page 150). In the exercise we set `"* * * * *"`, every minute. A few seconds after the CronJob was made, a new Job called `tick-<number>` was created from the template by itself (ran). We can also make a Job from a CronJob by hand with `kubectl create job --from=cronjob/<name>`, handy for tests or an extra run, and the Job is marked as owned by the CronJob through `ownerReference` (ran).

Two settings are worth knowing. `concurrencyPolicy: Forbid` skips a round if the last one has not finished, and `successfulJobsHistoryLimit` sets how many Jobs are kept. We use a real CronJob in the [capstone](/en/kubernetes/capstone-pipeline/) to run the loader again.

</Step>

<Step>

## DaemonSet: one per node

A DaemonSet has no `replicas` number. The number of Pods follows the number of nodes that qualify. It suits log collectors, system metrics and networking programs (book: Kubernetes Up and Running, DaemonSet Scheduler, page 132). In the exercise a plain DaemonSet put a Pod on both workers, but not on the control plane, because of its taint (ran). After we added a toleration that tolerates everything, the control plane got one too, three in all (ran). This is how `kube-proxy` and `kindnet`, which we saw in the first lesson, run on every node including the control plane.

</Step>

<Step>

## StatefulSet: a name and a disk that go with the Pod

A database differs from a web server because each member has its own identity and its own data. A StatefulSet gives a Pod three things: a fixed name with a number, a one by one start order, and a volume of its own made from a template (book: Kubernetes Patterns, Stateful Service page 87, and Kubernetes Up and Running, Kubernetes-Native Storage with StatefulSets, page 186).

In the real run a StatefulSet of 3 got Pods called `db-0`, `db-1` and `db-2`, created in order (start times rising), and three PersistentVolumeClaims called `data-db-0`, `data-db-1` and `data-db-2`, one each (ran). We wrote a file to the disk of `db-1` and then deleted the Pod `db-1`. The StatefulSet made `db-1` again with the same name (and a new `uid`), and it found the file that the earlier Pod wrote, because the claim is tied to the Pod name and not to the Pod itself (ran).

<Callout type="warn" title="In the exercise we pinned the Pods to one worker">
The volume that minikube makes is a folder on the node where the Pod runs. If `db-1` were created again on another node it would find an empty folder. So the exercise gives all the Pods a `nodeSelector` and keeps them on one worker. The lesson [Volumes and storage](/en/kubernetes/storage/) has the details. In a real cluster that uses network disks there is no need to pin.
</Callout>

</Step>
