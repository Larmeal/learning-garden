## Data that must outlive a Pod

In the lesson [Pod](/en/kubernetes/pods/) we saw that an `emptyDir` is born with the Pod and dies with it. If we want to keep the data of a database, we need something that lives longer. Kubernetes splits this into three objects. A PersistentVolume (PV) is one piece of real storage. A PersistentVolumeClaim (PVC) is a Pod's request for what kind of storage and how big. And a StorageClass is the recipe that says how to make a PV when somebody asks (book: Core Kubernetes, section 8.1 pages 153 to 159). The team that writes the app writes only a claim, and who prepares the real disk is a matter for whoever looks after the cluster, much like the way a Service was separated from Pods in an earlier lesson.

In the minikube cluster we use there is a StorageClass called `standard` as the default, using the provisioner `k8s.io/minikube-hostpath`, with `reclaimPolicy` set to `Delete` (ran). We created a PVC asking for 32Mi without naming a StorageClass. A PV was created by itself and bound to the claim at once, before any Pod used it (ran). This is dynamic provisioning (book: Kubernetes Up and Running, Dynamic Volume Provisioning, page 185).

</Step>

## Where does the data really live

Let us look at what the PV is. In the real run it was a `hostPath` folder at `/tmp/hostpath-provisioner/<namespace>/data` with no `nodeAffinity` at all (ran). That means it is an ordinary folder on one particular node, not a disk floating on the network. Let us prove what that means.

We created a Pod on `garden-m02`, wrote a file `note` into the claim, and deleted the Pod. A new Pod on the same node found the file `note` (ran). A Pod that used an `emptyDir` wrote a file and was deleted, and the next Pod found an empty folder (ran). So far this is as expected. But when we made the new Pod run on `garden-m03` using exactly the same claim, it saw an empty folder with 0 files (ran). The claim is bound to a real PV, but that PV is a folder on `garden-m02`. When the Pod lands on another node, the kubelet of that node creates a new empty folder with the same name, and the scheduler cannot know, because the PV never said `nodeAffinity`.

This is fine only for experiments on one computer. A real cluster uses network disks or a CSI driver (Container Storage Interface), where a Pod can mount the same disk whichever node it lands on (book: Core Kubernetes, section 7.4 page 144). We did not try that in the exercise.

## When the claim is deleted, and when the scheduler follows the data

If we delete a PVC whose `reclaimPolicy` is `Delete`, the PV object is deleted with it. But in the exercise the file `note` in the folder on the worker was still there (ran), because the minikube provisioner runs on the control plane and cleans up only there. This is behaviour specific to minikube, and the reason the exercise of this lesson must clear the folder itself every run.

If we want the scheduler to know where the data is, the PV must say so. We made a `local` PV that points at a folder on `garden-m03`, with a `nodeAffinity` naming that node, and a StorageClass with `volumeBindingMode: WaitForFirstConsumer`. The claim stayed `Pending` until a Pod used it, and when a Pod with no `nodeSelector` at all came, the scheduler placed it on `garden-m03` by itself, because the data is there, and the Pod read the file (ran). When the Pod and the claim were deleted, the PV that was set to `Retain` went to the state `Released` and its file stayed (ran).

Last, if a claim names a StorageClass that does not exist, the claim stays `Pending` and the event says `storageclass.storage.k8s.io "does-not-exist" not found` (ran).

</Step>
