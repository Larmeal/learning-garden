## The scheduler writes a node into a Pod, once

When we create a new Pod it has no node in the field `spec.nodeName`. The scheduler is the component that looks for such Pods and chooses a node for them, by writing the node name into that field, and that is all. It does not run containers and does not create Pods. The rest is the job of the kubelet on the chosen node (book: Core Kubernetes, section 2.3 page 29, kube-scheduler on page 31). In the real run an ordinary Pod got a worker as its node and never landed on the control plane, because the control plane carries a taint (ran).

What if no node is suitable? We created a Pod that asks for 64 CPUs although each node has 16. The Pod stayed `Pending` with no node. In its events we find a message that says why each node was rejected (ran).

```text
0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: },
2 Insufficient cpu.
```

It reads: of 3 nodes, 1 fell because of a taint the Pod does not tolerate and 2 fell because the CPU requested was not available. This message is the main tool whenever a Pod sits in Pending, because it names both the condition that failed and how many nodes failed it.

</Step>

## The scheduler adds up requests, not real use

The scheduler decides by the sum of the requests of all Pods on a node, not by how much CPU is used right now (book: Kubernetes Up and Running, Resource Requests, page 56). In the exercise each worker had 15,900m of CPU free out of 16,000m (100m was requested by system Pods). We created six Pods that each asked for 6360m, two fifths of what is free. Each worker took two (12,720m together). A third would go over the ceiling, so 4 Pods found a place and 2 waited in Pending (ran).

An interesting point is that these Pods run `sleep`, which uses almost no CPU, yet the node counts as "full" because the quota of requests is already reserved. If requests are set far too high the cluster fills up while CPU is idle. If they are set too low, nodes get packed until they are slow. So this value should be close to what the program really uses.

Pick a request size and a taint in the lab. The Pods that find no place wait in the queue at the top, and the text below gives the reason the scheduler gives.

## Choosing with tags: nodeSelector, taints and tolerations

There are three tools to tell the scheduler where a Pod should or should not go.

**nodeSelector** says this Pod must go to a node with this label. In the exercise we put the label `klab-disk=ssd` on one node, and a Pod with the matching `nodeSelector` always landed there (ran).

**A taint** works the other way round. It is a tag on a node that says "do not put a Pod here unless it tolerates this tag". We put the taint `klab-team=data:NoSchedule` on both workers, and a new ordinary Pod stayed Pending because no node was left, while a Pod with a matching **toleration** could land (ran). A toleration does not attract a Pod to the node. It only allows it. A tolerating Pod may still land on another node.

Two details to remember. First, `NoSchedule` does not throw out Pods that were already running. They stay (ran). To evict them you need `NoExecute`. Second, when we removed the taint, the Pod that had been waiting was placed by itself (ran), because the scheduler looks at Pods without a node again and again.

</Step>

## Spreading Pods: the control plane counts as an empty place

To spread the replicas of a Deployment over all nodes we use `topologySpreadConstraints`, with a `maxSkew`, the largest allowed difference in the number of Pods between two places. In the exercise we set `maxSkew: 1` by hostname for a Deployment of 6. The first result was only 1 Pod per worker, and the other 4 stuck (ran). Hmm, why?

The reason is that the control plane is counted as a place holding 0 Pods, although our Pods cannot land there because of its taint. Once each worker has its first Pod, a second one on a worker would make the difference from the control plane (0) equal to 2, which is over `maxSkew` for both, so no more can be placed. The fix is `nodeTaintsPolicy: Honor`, so the scheduler ignores nodes the Pod cannot tolerate. After that the 6 Pods split 3 and 3 (ran). It is a good example of a default that looks sensible but gives a surprise when the cluster has taints.

</Step>

<Step>

## cordon, drain and a PodDisruptionBudget

To repair or upgrade a node we have three commands in order. `kubectl cordon` makes the node `SchedulingDisabled`: no new Pods, but the existing ones stay. In the exercise, when we raised replicas to 8, the extra Pods did not land on the cordoned node (ran). Then `kubectl drain` asks Pods to leave the node politely (evicts them), and a controller creates new ones elsewhere.

If everything is evicted at once the service goes down. That is the job of a PodDisruptionBudget (PDB), which says how many Pods must always be Ready. In the exercise we set `minAvailable: 6` for a Deployment of 6, meaning not even one may be lost. The result was that `drain` could not evict any Pod and failed after waiting until it timed out (ran). When we removed the PDB the drain succeeded, and all 6 Pods moved to the worker that was left (ran). A PDB is the owner of a service telling whoever looks after the cluster how far they may go.

</Step>
