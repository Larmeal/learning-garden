## The kubelet gives the order, the runtime does the work

In the lesson [Control plane](/en/kubernetes/control-plane/) the kubelet is the part that sees a Pod assigned to its own node and makes it run. But the kubelet does not run containers itself. It talks to the container runtime through a standard called the CRI (Container Runtime Interface), which is the reason the runtime can be swapped without the kubelet knowing (book: Core Kubernetes, section 9.3 page 182 and 9.4 page 185). In the real run on a worker, the kubelet's config file pointed at `unix:///run/containerd/containerd.sock`, and `containerd` was really listening on that socket (ran). It is the same low level runtime that Docker uses inside. In the Docker path we saw a container as a process on a kernel that Docker prepared rooms for, and the lesson [Namespaces and cgroups](/en/docker/namespaces-and-cgroups/) tells about those rooms. This time we see how Kubernetes uses the same rooms to make a Pod.

We created a Pod with two containers (`a`, which loops using all the CPU it can, and `b`, which just sleeps) and asked `containerd` through the tool `crictl` on the node. A Pod turned out to be one sandbox plus the containers `a` and `b` (ran), and the process of the sandbox is `/pause`, a tiny program that does nothing except hold the namespaces for the other containers to join (ran). This is why `ps` in a Pod with `shareProcessNamespace` shows `/pause` as PID 1 (book: Core Kubernetes, section 9.3 page 184, on the pause container).

</Step>

## One namespace in common, but not all of them

Let us ask the kernel which namespaces `/pause` and the two containers are in, by reading the links `/proc/<pid>/ns/<kind>` of the processes on the node. The result (ran):

| Kind of namespace | The three processes (pause, a, b) |
|---|---|
| `net` | the same number for all, 1 shared |
| `mnt` | all three different, 3 in all |
| `pid` | all three different, 3 in all |

This fits the lesson [Pod](/en/kubernetes/pods/) exactly. Containers of one Pod share the network, so they reach each other over `localhost`, but have separate mount and PID namespaces, so they do not see each other's files and processes (book: Core Kubernetes, section 2.2 page 22). The remaining mechanisms are cgroups and the network. Step through them one at a time in the lab below.

## Requests and limits become files in a cgroup

The Pod has a container `a` with a CPU request of 50m, a CPU limit of 100m and a memory limit of 64Mi, and `b` with nothing set. The kubelet makes it real by writing files in a cgroup that the kernel reads. In the exercise we opened the Pod's folder under `/sys/fs/cgroup/kubepods/burstable/pod<uid>/` (the folder `burstable` is the QoS class of this Pod) and read the values (ran).

| File | Value for container a | Meaning |
|---|---|---|
| `memory.max` | 67108864 | a memory ceiling of 64Mi, killed when exceeded |
| `cpu.max` | `10000 100000` | may use 10 ms in every 100 ms, which is 10% of one CPU |
| `cpu.weight` | 2 | its share when CPU is contended, from the 50m request |

Container `b` has no limit, so its `memory.max` is `max` and `cpu.max` has no ceiling. And `a`, which wants all the CPU, is really squeezed. Over three seconds it used about 10% of one CPU and was throttled in every 100 ms period (31 of 31) (ran). This matches what the Docker lesson [Namespaces and cgroups](/en/docker/namespaces-and-cgroups/) explains about `cpu.max` (book: Core Kubernetes, section 4.4 page 79 and section 4.5 page 83 on QoS classes). That a container over its memory is killed with code 137 we already saw in the lesson [Pod](/en/kubernetes/pods/).

</Step>

## The network: a veth, routes and two hops

A Pod gets an IP from the range that its node owns. In the real run the three nodes each had a different `/24` Pod CIDR (`10.244.0.0/24`, `10.244.1.0/24`, `10.244.2.0/24`), and a Pod's IP fell in the range of the node it runs on (ran). On the Pod side we see an `eth0`, which is one end of a veth pair whose other end is on the node (ran). If we go back to the lesson [Ethernet, switches and ARP](/en/networking/link-layer/) on layer 2 and [Proxies, load balancers and container networks](/en/networking/proxies-and-containers/), where containers join a bridge, we see that this time it is different.

The CNI that minikube uses is kindnet, configured as the `ptp` plugin together with `host-local` and `portmap` (ran). The `ptp` type means a direct veth with no bridge. The result is two groups of routes on the node (ran).

```text
10.244.0.0/24 via 192.168.67.2 dev eth0      # CIDR of another node, sent through that node's IP
10.244.1.123 dev veth3a83eacd scope host      # a Pod on this node, sent straight into its veth
10.244.2.0/24 via 192.168.67.4 dev eth0
```

We measured the number of hops with the TTL used in the lesson [Routers, TTL and the path of a packet](/en/networking/ip-routing/). When we pinged from a Pod to a Pod on the same node, the answer came back with TTL 63 (one less at the node), and when we pinged a Pod on another node the TTL was 62 (reduced twice, by passing two nodes) (ran), which fits what the routes say (book: Core Kubernetes, section 5.4 page 104, on the architecture of a CNI plugin).

</Step>

## Restarting the kubelet does not kill containers

One last thing to know. When the kubelet dies or is restarted, the containers that are running do not die with it, because a container is a process that `containerd` looks after. In the exercise we ran `systemctl restart kubelet` on a worker. After the node was Ready again the list of containers of the Pod had the same ids, the process of `a` had the same number, and the `restartCount` of the Pod was still 0 (ran). This is why a kubelet can be upgraded without interrupting the service.

<Callout type="note" title="What this lesson did not try">
We looked at one CNI, kindnet in `ptp` mode. Other CNIs such as Calico or Antrea use bridges, tunnels or overlays differently (book: Core Kubernetes, section 5.3 page 102 and 5.4 page 103), and we did not try cgroup v1.
</Callout>
