## A Deployment does not look after Pods directly

We met the Deployment in the first lesson. This time let us ask who owns whom. In the real run we created a Deployment of four Pods and read the `ownerReferences` of each layer. A Pod is owned by a ReplicaSet, and that ReplicaSet is owned by the Deployment called `app`. The names hint at it already: the Pod name is the ReplicaSet name plus a random suffix, and the ReplicaSet name is the Deployment name plus a hash of the template (ran).

The book says a ReplicaSet is the layer responsible for making the number of Pods match what is wanted, by comparing them in a reconciliation loop (book: Kubernetes Up and Running, Reconciliation Loops, page 104). A Deployment works one layer higher, looking after the change from one revision of the template to the next (book: Kubernetes Up and Running, Deployment Internals, page 114). Two layers are needed because a ReplicaSet remembers only one template. To have two revisions side by side during an update, there must be two ReplicaSets.

</Step>

<Step>

## Rolling update: move one step at a time

When we change the Pod template (say the message the program prints, or the image), the Deployment makes a new ReplicaSet and slowly adds Pods to the new one and removes them from the old one, under two numbers: `maxSurge`, how many Pods may exist above the target, and `maxUnavailable`, how many may be missing from it (book: Kubernetes Up and Running, RollingUpdate Strategy, page 123). In the exercise we set both to 1 with a Deployment of 4 Pods, and watched the ReplicaSet counts every half second (ran).

| Time | Old ReplicaSet | New ReplicaSet |
|---|---|---|
| before | 4 Pods, Ready 4 | none |
| 0.1 s | 3 Pods, Ready 3 | 2 Pods, Ready 0 |
| 4.7 s | 1 Pod, Ready 1 | 4 Pods, Ready 2 |
| 8.0 s | 0 | 4 Pods, Ready 4 |

At no moment were there more than 5 Pods in all (4 plus `maxSurge` 1), and never fewer than 3 Ready (4 minus `maxUnavailable` 1) (ran). One thing to notice is that a new Pod must pass its readiness probe before it counts as Ready, which is why the probes in the lesson [Pod](/en/kubernetes/pods/) matter for updates.

The old ReplicaSet is not deleted when the update finishes. It is kept at 0 Pods so that we can go back. With `kubectl rollout undo` the Deployment brings the old template back, reusing the same ReplicaSet and recording it as revision 3 (ran). History does not go backwards. It moves on, reusing the old thing.

</Step>

<Step>

## Recreate: accept a moment with nothing running

`strategy: Recreate` stops every old Pod first, and only then creates the new ones. In the exercise Ready went down to 0 (ran). It is used when old and new Pods must not run together, for example when both versions would lock the same file or the data schemas are incompatible, accepting that for a moment nothing serves (book: Kubernetes Up and Running, Recreate Strategy, page 123).

</Step>

<Step>

## With a bad image the update stops, and users do not notice

This is the main reason a rolling update is safe. We changed the image to `busybox:no-such-tag`, which does not exist. In the real run the two new Pods stuck in `ImagePullBackOff`, while the 3 old Pods stayed Ready, because the Deployment will not remove more old Pods if that would take Ready below the promise (ran). After `progressDeadlineSeconds` (we set 20 s) the Deployment reported `ProgressDeadlineExceeded` and `kubectl rollout status` exited abnormally, while users could carry on, because the old Pods still took requests. Then `kubectl rollout undo` brought back all four Pods (ran).

This is where the two numbers saved us. If `maxUnavailable` is set too high, for instance equal to the number of Pods, a rolling update turns into Recreate without anyone meaning it to.
