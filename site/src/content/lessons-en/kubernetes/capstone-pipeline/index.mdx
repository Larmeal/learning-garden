## The map of the pipeline

In the Docker path, the lesson [Capstone](/en/docker/capstone-pipeline/) put a data pipeline into containers with Compose on one computer. This time we do the same on a cluster, with the pieces we have learned.

- A Secret `db` holds the database password, and a ConfigMap `load-sql` holds the SQL of the loader (lesson [ConfigMaps and Secrets](/en/kubernetes/config-secrets/)).
- A StatefulSet `db` runs one Postgres 17, with a PVC `data-db-0` for the data and a readiness probe using `pg_isready`, and a Service `db` gives a fixed name (lessons [Job, CronJob, DaemonSet and StatefulSet](/en/kubernetes/jobs-and-stateful/) and [Services and DNS](/en/kubernetes/services/)).
- A loader Job has an init container that waits for the database to be ready, and then the main container runs `psql` to load the data, and a CronJob `nightly` uses the same template to run it again.
- A NetworkPolicy lets only Pods labelled `role=loader` reach the database (lesson [RBAC and security](/en/kubernetes/rbac-security/)).

Look at the map in this lab, and keep the normal situation chosen for now. We come back to the broken ones later.

In the real run the database was ready within seconds to tens of seconds after `apply` (depending on whether the image had been pulled already), and the PVC was bound to a PV (ran).

## The loader: wait, load, and be safe to run again

The loader Job has two stages. An init container called `wait-for-db` loops on `pg_isready -h db` until the database accepts connections (the log shows `accepting connections`) and then ends. Then the main container starts, creates the table, inserts 1000 rows and counts them (ran).

```text
CREATE TABLE
INSERT 0 1000
1000
```

The SQL is written to be **safe to run again**, with `CREATE TABLE IF NOT EXISTS` and `INSERT ... ON CONFLICT (id) DO NOTHING`. We proved it by making a new Job from the CronJob with `kubectl create job --from=cronjob/nightly`. The second round inserted `INSERT 0 0` and the table still had 1000 rows (ran). This is an important condition for work that can be retried, like a Job with a `backoffLimit`, taught in the lesson [Job, CronJob, DaemonSet and StatefulSet](/en/kubernetes/jobs-and-stateful/), because a Pod that fails half way is run again from the start. Work that inserts twice and duplicates the data would distort the result.

</Step>

## Locking down: the loader and the database

The loader is set to be able to do as little as possible. We checked from the Job object that was really created (ran).

- It runs as uid 70 (`runAsUser: 70`, `runAsNonRoot: true`), not root.
- `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true` and `capabilities: drop: [ALL]`.
- It has no `env` at all. The password comes from a file mounted read only from the Secret at `/secrets/password` and is passed to `psql` through a temporary variable of the command (so that the password is not in an environment variable of the Pod that can be seen through the API).

The other layer is the network. The NetworkPolicy lets only Pods labelled `role=loader` reach port 5432 of the database. We created a Pod `stranger` without that label and tried `pg_isready -h db`, which gave `no response` (ran), while the loader got in and loaded the data as usual.

</Step>

## Break it in three ways

Choose a situation in the lab above to see which box turns orange, and then read each way we did it in the exercise.

**The first way is a misspelled key of the Secret.** We made a new loader that refers to a key called `pasword` in the Secret volume. The Pod never even reached the init container, because the kubelet could not mount the volume. The Pod's event said `FailedMount ... references non-existent secret key: pasword` (ran). The Job did not finish and no data came from it. This differs from a wrong key in an environment variable, seen in the lesson [ConfigMaps and Secrets](/en/kubernetes/config-secrets/), which gave `CreateContainerConfigError`. Here we use a volume, so we see `FailedMount`. Read it in the events of the Pod.

**The second way is deleting the Pod of the database.** We deleted `db-0`. The StatefulSet made `db-0` again (the same name and a new `uid`) and mounted the old claim again. It took only about 3 seconds, and the table still had 1000 rows (ran), because the data lives in the PVC and not in the Pod, as seen in the lesson [Volumes, PVCs and StorageClasses](/en/kubernetes/storage/).

**The third way is a loader with the wrong label.** We made a loader labelled `role=etl` instead of `role=loader`. The NetworkPolicy blocked it, so the init container waited and waited. Its log printed `db:5432 - no response` and `waiting for db` again and again. The Pod stayed at `Init:0/1` and the Job never finished. There was no failure or restart to see, only waiting (ran). When we deleted that Job and created it again with `role=loader`, it finished, and the table still had 1000 rows (ran). A symptom of "waiting with no error" like this needs a look at the log of the init container, and a thought about NetworkPolicy.

<Callout type="warn" title="This is not yet a production pattern">
The database is pinned to one worker because minikube volumes are folders on a node (the lesson [Volumes, PVCs and StorageClasses](/en/kubernetes/storage/)), and there is one database, no backup, no encryption of Secrets in `etcd`, and Postgres starts as root, so it lives in a namespace set to Pod Security level `baseline` and not `restricted`.
</Callout>

If you want to see Kubernetes in the setting of Spark, a program that asks for Pods itself through the API, read the page [Kubernetes cluster manager](/en/spark/architecture/kubernetes/) of the Spark path, and the lesson [Orchestration and GitOps](/en/devops/gitops/) of the DevOps path, where we wrote the same kind of controller by hand before Kubernetes was there to use.

</Step>
