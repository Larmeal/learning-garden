## What does a cluster look like

In the Docker path we put containers on one computer and used [Docker Compose](/en/docker/compose/) to tell Docker which services exist. If that computer goes down, every container goes with it, and we have to log in and start them again ourselves. In the lesson [Orchestration and GitOps](/en/devops/gitops/) of the DevOps path we wrote a small controller of our own, to show how "compare what we want with what exists, and fix the difference" works. Kubernetes is the system that does exactly this, but for many computers at once.

In this path we use a real cluster that minikube set up on our own computer. It has three computers: one is a control plane and two are workers. Let us ask the cluster who is in it (ran).

```bash
kubectl get nodes
```

```text
NAME         STATUS   ROLES           VERSION   CONTAINER-RUNTIME
garden       Ready    control-plane   v1.31.0   containerd://1.7.21
garden-m02   Ready    <none>          v1.31.0   containerd://1.7.21
garden-m03   Ready    <none>          v1.31.0   containerd://1.7.21
```

`kubectl` is the program we use to talk to the cluster. The command `get nodes` asks for the list of nodes, which are the computers of the cluster. Every one runs the same Kubernetes version, and runs containers with `containerd`, the low level container runtime that Docker itself uses inside (book: Core Kubernetes section 1.6 page 9).

The computer marked `control-plane` is not there to run our programs. It is the brain of the cluster. The other two are workers that take Pods to run. In Kubernetes we do not start containers directly. We run Pods, which are groups of containers that live together. [The next lesson](/en/kubernetes/pods/) looks at what a Pod is. For now, think of one Pod as one program of ours.

</Step>

## We do not say "run this", we say how many we want

Let us tell the cluster that we want three copies of a program called `web`, through an object called a Deployment. The YAML looks like this (shortened).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels: {app: web}
  template:
    metadata:
      labels: {app: web}
    spec:
      containers:
      - name: web
        image: busybox:1.37
```

The line `replicas: 3` is the number we want, and `template` is the mould of the Pods that will be made. After `kubectl apply -f web.yaml` all three Pods come up, spread over the two workers, and none lands on the control plane (ran).

Hmm, what if somebody deletes one Pod? Let us try.

```bash
kubectl delete pod web-6947b489d8-f6hlk
```

In the real run a new Pod called `web-6947b489d8-glpbx` came up in its place and was ready within 2.3 seconds. The name is different from the old one, because the Pod was not repaired and brought back. It was made again, whole. Nobody told anything to create it. We only deleted a Pod, and something noticed that two numbers were different (we want 3, we found 2) and fixed it. If we open the events of the namespace we can see several parties working together: `replicaset-controller` creates the Pod, `default-scheduler` picks a node, and the `kubelet` of that node runs the container (ran).

Press play in the lab below and switch to the second accident, and watch when the two numbers on the card change, and who makes them equal again.

<ClusterLab client:visible lang="en" />

This is the core of the whole Kubernetes system. We write what we want (the desired state) as YAML, and a loop keeps comparing it with what really exists (the actual state) and fixes the difference all the time. The book Core Kubernetes calls the problem this solves infrastructure drift: the real state of a system slowly moves away from what we meant (book: Core Kubernetes section 1.2 page 2 and section 1.4 page 5).

<Callout type="note" title="Scaling is changing one number">
In the exercise we ran `kubectl scale deployment/web --replicas=5` and the Pods grew to 5. Scaling down to 2 shrank them. `spec.replicas` and `status.readyReplicas` were equal at the end. We never said which Pod starts and which stops (ran).
</Callout>

</Step>

## Who lives inside the cluster

To see who does what, let us list the system Pods in the namespace `kube-system` and group them by the node they run on (ran).

| Node | System Pods on it |
|---|---|
| `garden` (control plane) | `etcd`, `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`, `coredns`, `storage-provisioner`, `kindnet`, `kube-proxy` |
| `garden-m02` (worker) | `kindnet`, `kube-proxy` |
| `garden-m03` (worker) | `kindnet`, `kube-proxy` |

Four of the control plane parts are the core. `etcd` stores all the data of the cluster. `kube-apiserver` is the one door everybody uses to talk to the cluster. `kube-scheduler` decides which node a new Pod goes to. `kube-controller-manager` bundles many loops that compare numbers, like the one we just saw. Every node, worker or not, has `kube-proxy`, which does the networking of Services, and `kindnet`, which connects the network for Pods. Every node also has a kubelet, which is not a Pod but a program of the operating system. It takes the Pods that were assigned to its node and tells the container runtime to run them (book: Core Kubernetes section 1.6 page 9 and section 2.3 page 29).

One thing to notice. In the exercise no worker had a control plane Pod, and the control plane took no ordinary Pod, because it carries a label called a taint. The lesson [Scheduler](/en/kubernetes/scheduling/) explains it.

All of this is separate from our own programs. We come back to open the [control plane](/en/kubernetes/control-plane/) and the [node](/en/kubernetes/node-inside/) piece by piece in the later part of the path.

</Step>

## Things break at three levels, and a different party fixes each

Let us break things in three ways and see who fixes each one.

**The first way** is a container that dies inside a Pod. In the exercise we stopped the container of one Pod with `crictl stop`. The same Pod stayed on the same node, with `restartCount` at 1. The one that started the container again was the kubelet of that node, with nobody else involved (ran).

**The second way** is a Pod that is deleted, as we saw above. We got a new Pod with a new name. The one that created it was the ReplicaSet controller, which is part of the controller manager.

**The third way** is a whole computer that stops. We stopped the worker that had two Pods (ran). The control plane did not know at once. It waited until the node had been silent for about 43 seconds before declaring it `NotReady`, because the kubelet of each node has to renew a Lease as a heartbeat about every 10 seconds, and when it is silent for 40 seconds the node controller marks the node not ready. After that the Pods that had been on that node were created again on the worker that was left, until all three were ready at 61 seconds.

<Callout type="warn" title="In the exercise we wait less than usual">
By default Kubernetes keeps Pods on a lost node for another 300 seconds before creating them again. In the exercise we gave our Pods `tolerationSeconds: 10` so as not to wait five minutes. The 61 seconds is therefore the time with this setting, not the normal time.
</Callout>

The third case is slower because the control plane cannot tell "the node is really dead" from "the network cable came loose for a moment". If it created copies too early, two Pods doing the same job could end up running at the same time. We come back to leases in the lesson [Control Plane](/en/kubernetes/control-plane/).

</Step>
