## Helm: pack a whole set as one release

In the earlier lessons we wrote YAML one file at a time, but a real app has a Deployment, a Service, a ConfigMap and more, together ten files, and needs different values in each place it runs. Helm is a tool that packs those files into a chart, with templates and default values (`values.yaml`), and turns it into a release that has a name and a history (book: Learning Helm, Resources, Installations, and Releases, page 18).

We wrote a small chart called `webapp` with a Deployment template, a Service template and three default values, `replicas`, `message` and `image` (ran). `helm lint` passed, and `helm template` printed the YAML without creating anything in the cluster (ran). Values are filled in by priority. The defaults are lowest, next comes a file passed with `-f`, and `--set` is highest. In the real run replicas was 2 (default), 5 (`--set`), 7 (`-f prod.yaml`), and 9 when both `-f` and `--set` were used (ran) (book: Learning Helm, Configuration at Installation Time, page 30).

</Step>

## A release has a history, and can be rolled back

Press through this lab one step at a time to see how the revisions of a release stack up.

<HelmLab client:visible lang="en" />

`helm install` creates a release at revision 1. We get a Deployment and a Service labelled `managed-by: Helm`, and Helm stores each revision as a Secret of type `helm.sh/release.v1` named `sh.helm.release.v1.demo.v1` (ran) (book: Learning Helm, How Helm Stores Release Information, page 37). `helm upgrade` gives revision 2 and revision 1 becomes `superseded`, while `helm rollback 1` does not wind the history back. It creates revision 3 with the content of revision 1, so history only moves forward (ran).

What if an upgrade breaks? We tried an upgrade with an image that does not exist, with `--wait`. The command failed with `UPGRADE FAILED: context deadline exceeded` and the release was marked `failed` (revision 4), but the Pods of the revision before were still ready, 2 of them, because the rolling update seen in the lesson [Deployments](/en/kubernetes/deployments/) does not remove old Pods until the new ones are ready. Then `helm rollback 3` gave revision 5 with the status `deployed` (ran). Last, `helm uninstall` removed the Deployment, the Service and the Secrets of every revision (ran).

</Step>

## Autoscaling: up fast, down slowly

Normally we set the number of Pods by hand, but a HorizontalPodAutoscaler (HPA) adjusts it to the load. It reads the average CPU of the Pods from metrics-server and computes the number wanted = round up (current number × use ÷ target), limited by a minimum and a maximum (book: Kubernetes Patterns, Elastic Scale, page 203, and Kubernetes Up and Running, Autoscaling a ReplicaSet, page 110).

In the exercise we made one container loop using all the CPU it could, but with a limit of 200m while its request was 100m, and set an HPA with a target of 50% and replicas from 1 to 4. The reading was 200% of the request against a target of 50%, which gives exactly 4 wanted, and the HPA went from 1 to 4 (ran). When we stopped the load the value fell to almost 0, and the HPA went back to 1 after the wait window (stabilization) that we set to 20 seconds, taking 120 seconds in all (ran).

<AutoscaleLab client:visible lang="en" />

Two things to remember. First, most of the 78 seconds was waiting for metrics-server to take its first reading, and the real scale down window is 5 minutes by default, which we shortened to 20 seconds so as not to wait. Second, requests must make sense, because the HPA measures as a percent of the request. If no request is set, the HPA cannot compute.

</Step>

## A broken Pod: the status tells which layer has the problem

The last topic is finding the cause when something is wrong. The status shown by `kubectl get pods` tells the layer of the problem, and then we ask the object with the command that fits that layer (book: Kubernetes Up and Running, Debugging Commands, page 40). In the real run we broke things in several ways. The results (ran):

| Status seen | Caused by | Command that reveals the cause |
|---|---|---|
| `ImagePullBackOff` | the image name or tag is wrong | `kubectl describe pod` gives `Failed to pull image "busybox:no-such-tag"` |
| `CrashLoopBackOff` | the program keeps ending with a bad exit code | `kubectl logs --previous` gives the output of the earlier run (`boom`) |
| `Pending` with no container status | no node can take it | `kubectl describe pod`, in the Events, gives `Insufficient cpu` |
| `CreateContainerConfigError` | the Secret or key referred to is missing | read the message in `state.waiting.message` |
| `OOMKilled` | memory used went over the limit | `state.terminated` gives exit code 137 |
| a Service with no endpoints | the selector does not match the labels | `kubectl get endpoints` is empty |

Pick a symptom in the lab below to see the chain of question and answer for each.

<DebugLab client:visible lang="en" />

A simple rule: if the Pod has no node yet (`Pending`), the problem is with the scheduler. If the Pod has a node but the container does not come up (`ImagePullBackOff`, `CreateContainerConfigError`), the problem is with the image or the values it refers to. If the container comes up and dies (`CrashLoopBackOff`, `OOMKilled`), the problem is with the program or the resources. And if the Pod is Running but gets no work (Not Ready, or no endpoints), the problem is with a probe or a label.
