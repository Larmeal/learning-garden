## Everything is stored in etcd, and the only door is the API server

In the [first lesson](/en/kubernetes/why-kubernetes/) we named the components of the control plane. This time we go down to see how they talk. Start by finding where they run. In the exercise we opened the folder `/etc/kubernetes/manifests` on the control plane and found four files: `etcd.yaml`, `kube-apiserver.yaml`, `kube-controller-manager.yaml` and `kube-scheduler.yaml` (ran). The kubelet of that node reads this folder directly and runs them as Pods called static Pods, without waiting for an API server. That answers the question of who creates the API server when there is no API server yet. The Pods we see in `kube-system` are only mirror Pods that the kubelet reflects into the API, with the Node as their owner (ran) (book: Core Kubernetes, section 11.1 page 206).

The API server is started with the parameter `--etcd-servers=https://127.0.0.1:2379` (ran), and it is the only one that talks to `etcd`. Every other component talks to the API server, the same way `kubectl` does (book: Core Kubernetes, section 11.2 page 207). We can read `etcd` directly. One of our Pods is a single key, `/registry/pods/<namespace>/<name>`, and under `/registry/` there are 30 top level kinds of object in all, such as `pods`, `services`, `deployments`, `secrets` and `leases` (ran). That means the whole state of the cluster is this one key and value database (book: Core Kubernetes, section 12.2 page 227).

</Step>

## Watches, and optimistic locking

If every part kept asking the API server "has anything changed?", the system would be heavy. Kubernetes uses a watch instead: it opens an HTTP request and leaves it open, and the API server sends an event each time something changes. In the exercise we opened a watch on a Pod, then added a label and deleted the Pod, and received the events `ADDED`, several `MODIFIED`, and `DELETED` in order (ran). This is why the cluster reacts fast without asking again and again (book: Core Kubernetes, section 12.2 page 228, and Programming Kubernetes, The HTTP Interface of the API Server, page 20).

When several parts edit the same object at once, we do not want one to overwrite another without knowing. Every object has a `resourceVersion` that changes at every edit. If we send an edit that quotes an old number, the API server refuses with `Conflict`. In the exercise we did a `replace` of a ConfigMap with an old `resourceVersion` and got the message `the object has been modified; please apply your changes to the latest version`, and the stored value was not overwritten (ran). This is optimistic concurrency, where the loser must read the new value and try again (book: Programming Kubernetes, Optimistic Concurrency, page 14).

</Step>

## Stop them one at a time: the scheduler and the controller manager

One of the best ways to understand something is to take a component away and see what breaks. In the exercise we moved the manifest of the scheduler out of the kubelet's folder, so that Pod stopped running, and then created a new Pod. The Pod was created and stored in the API, but stayed `Pending` with no `nodeName` and not one event, not even `FailedScheduling`, because nobody tried to place it. When we moved the file back the scheduler woke up, saw the waiting Pod, and placed it within seconds (ran).

Then we did the same to the controller manager. While it was stopped, a Pod of a Deployment that we deleted was not replaced (2 left out of 3), and when we raised `replicas` to 5 the API server accepted and stored the number, yet there were still only 2 Pods (ran). When the controller manager came back it saw the difference and filled up to 5 Ready Pods within a few tens of seconds (ran).

Try it in the lab below. Pick which component to stop and press Next through the creation of a Deployment, and see which step does not happen.

<ControlPlaneLab client:visible lang="en" />

The lesson of this experiment is that the control plane is not a boss giving orders. It is several loops that each watch one kind of object and write the next one. When one stops, what comes before it keeps working (values are still stored) and what comes after waits, and when it returns it catches up by itself, because it looks at the current state and not at the events it missed. The book Programming Kubernetes calls this level-driven, as against edge-driven, which must never miss an event (book: Programming Kubernetes, Edge- Versus Level-Driven Triggers, page 9).

</Step>

## Heartbeats, leaders and deleted owners

Back to the first lesson, where a node was declared `NotReady` after about 40 seconds of silence. In the exercise we looked at the namespace `kube-node-lease`, which has one Lease per node, `garden`, `garden-m02` and `garden-m03`, and the `renewTime` of `garden-m02` moved on by about 10 seconds each time (ran). This is the heartbeat the kubelet sends, and what the node controller looks at before it marks a node NotReady (book: Core Kubernetes, section 9.3 page 180).

In a cluster with several control plane nodes, the scheduler and the controller manager use a Lease of the same kind to elect a leader, so that only one really works. But minikube starts these two with `--leader-elect=false` because it has only one control plane node (ran), so there was no leader Lease to look at in the exercise.

The last thing is garbage collection by `ownerReferences`, which we have seen since the Deployment lesson. When we deleted a Deployment with `--cascade=orphan`, the ReplicaSet and all 5 Pods stayed (ran), while deleting a ReplicaSet the normal way removes the Pods it owns (ran). Even with no controller manager that time, there was still a collector doing this job.

</Step>
