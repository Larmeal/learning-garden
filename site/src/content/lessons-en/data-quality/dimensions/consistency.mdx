## Consistency asks whether two things that should agree really do

Picture two clocks hanging in the same house. If both show the same time, we can say they are consistent with each other. If one runs ten minutes fast, they are not. Either way, the two clocks still do not tell us what time it really is.

Consistency in data quality looks at data the same way: do two pieces of data that should be in step with each other actually match? DMBOK2 describes it as values being represented the same way within a dataset or between datasets. It can also mean the size and composition of datasets across systems or across time. DAMA UK words it as the absence of difference when comparing two or more representations of a thing against a definition (book: DMBOK2 Table 29, page 458, and section 1.3.3, page 457).

Look at two orders in `orders`.

| order_id | status | order_ts | shipped_ts |
|---:|---|---|---|
| 84 | SHIPPED | 2026-07-03 06:01 | (empty) |
| 816 | SHIPPED | 2026-10-02 03:26 | 2026-10-01 03:26 |

Order 84 says it has shipped, but has no shipping time. Order 816 shipped on 1 October, the day before the customer ordered it on 2 October. If we look at `order_ts` and `shipped_ts` of order 816 one at a time, each is a perfectly good date. The problem shows only when we look at two columns together, and a rule that checks one column at a time will never see it.

</Step>

## Three levels

The book splits consistency into three levels, by what we compare (book: DMBOK2 Table 29, page 458).

| Level | What is compared with what | Rule in our dataset | Fails |
|---|---|---|---:|
| Record-level | two fields in the same row | an order that is SHIPPED must have `shipped_ts` | 25 of 1,794 |
| Record-level | two fields in the same row | `shipped_ts` must not be before `order_ts` | 10 of 1,769 |
| Cross-record | the same field across rows or datasets | the same country must be written the same way in every row | 25 rows written five other ways |
| Temporal | the same field at different times | today's order count should be close to recent days | see the page [Reasonability](/en/data-quality/dimensions/reasonability/) |

The first two lines are orders 84 and 816, which we just saw. The cross-record line can be seen by counting the values in `customers.country`.

| country | rows |
|---|---:|
| TH | 330 |
| SG | 58 |
| JP | 56 |
| US | 31 |
| THA, T.H., th, Thailand, ไทย | 5 each |

The five values at the bottom are Thailand written in different ways. Counting `TH` too, that is six spellings for one country (run: `02_dimensions.py`, `13_dimension_pitfalls.py`). A revenue report by country would show Thailand as six small groups instead of one.

We measure a rule of the first level with this query.

```sql
-- shipping time must not be before the order time
SELECT count(*) FILTER (WHERE shipped_ts < order_ts), count(shipped_ts) FROM orders;
-- 10 of 1,769
```

The denominator is `count(shipped_ts)`, which counts only orders that have a shipping time, because an order without one has nothing to compare. Now write the rule "an order that is still PLACED must not have `shipped_ts`" and run it. We get 0 rows, which is useful information too, because it tells us the system never puts a shipping time on an order that has not shipped. Keep the rule. If one day it starts finding rows, something has changed (run: `13_dimension_pitfalls.py`).

</Step>

## Two values that agree are not necessarily right

Back to the two clocks. If both run ten minutes fast by the same amount, they still agree with each other, but the time they show is wrong. Data behaves the same way. This table has 3 made-up orders, comparing the total in `orders` with two other places. The first is a copy of the total in a report table, and the second is the payment system.

| order_id | total_amount in `orders` | total in the report table | amount the payment system received |
|---:|---:|---:|---:|
| 1 | 100.00 | 100.00 | 90.00 |
| 2 | 250.00 | 250.00 | 250.00 |
| 3 | 80.00 | 80.00 | 70.00 |

The total in `orders` matches the report table on all 3 orders, but matches the payment system on only 1 (run: `13_dimension_pitfalls.py`). It matches the report table every time because the report table was copied from `orders` in the first place, and a copy always agrees with the thing it was copied from. If two systems share the same bug, every consistency check between them passes. This is why DMBOK2 warns us not to confuse consistency with accuracy. Comparing against a source we trust, such as the payment system, is the job of [Accuracy](/en/data-quality/dimensions/accuracy/) (book: DMBOK2 Table 29, page 458).

</Step>

<Step>

## The measurement reports a difference, a definition decides who is right

Counting six spellings for Thailand in country is a finding. Deciding to use `TH` and convert the other five to it is a further step, which the book calls standardization: conditioning the incoming data so that it meets the rules for content and format (book: DMBOK2 Table 29, page 458). The measurement cannot choose for us which form is the right one, and that is why the DAMA UK wording includes the words "against a definition".

Profiling `order_ts` and `shipped_ts` one column at a time without seeing anything wrong ([lesson 3](/en/data-quality/profiling/#profile-every-column-without-knowing-what-it-means) covers that kind of profiling) is what always happens with record-level consistency. A rule that checks the relationship between two fields has to start from what the business expects that relationship to be, and that knowledge is often in the head of someone who works with the data every day. Go and ask them.

</Step>

<Step>

## The same rule can sit under different labels

The rule "an order must be shipped after it was ordered", which we file as consistency, matches the record-level definition in DMBOK2, which compares two fields in the same row. Ten Steps puts the same example under referential integrity, because it uses the word integrity in a broader sense: the consistency of data inside a relationship (book: Ten Steps chapter 4, pages 128 to 135). Both can be defended. The rule is the same and only the label differs. If two teams in one organization use different labels, their reports are hard to compare, so it is worth agreeing on one label first.

The third level in the book, temporal, uses the example that the number of transactions in a day should not exceed 105% of the running average of the previous 30 days (book: DMBOK2 Table 29, page 458). Many teams call that kind of check volume monitoring or reasonability. The [Reasonability page](/en/data-quality/dimensions/reasonability/#a-threshold-built-from-the-average-alone-fires-on-normal-days) shows how a bar like that behaves on our dataset.

Ten Steps also treats consistency across several data stores as a dimension of its own, called consistency and synchronization, so that we plan time and people for profiling every store and comparing them (book: Ten Steps chapter 4, pages 146 to 148). In this path, comparing two systems is covered in [lesson 8](/en/data-quality/reconciliation/#reconcile-with-row-counts-and-sums).

</Step>

<Step>

## How it differs from the other dimensions

Consistency differs from validity in that validity checks one value against a domain, while consistency needs two values to compare. Order 816 has two timestamps that are both valid and not consistent with each other. And the value `ไทย` in country fails validity against the list, and is also inconsistent with the `TH` that other rows use. See the page [Validity](/en/data-quality/dimensions/validity/) as well.

Consistency differs from accuracy as explained earlier: two values that agree can both be wrong, if there is no trusted reference to compare against.

</Step>
