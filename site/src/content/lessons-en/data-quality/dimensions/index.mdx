## A dimension is a word for talking about a rule

Suppose you have just joined an online shop. On the first day the marketing team tells you "the customer data is terrible, our emails don't arrive". The same day the finance team tells you "the order data is wrong, the totals don't match the money we actually received". Both teams say "bad data", but they are talking about two different problems, and we cannot fix anything until we know what to measure.

A **data quality dimension** is the name we give to one kind of problem, so that everyone talks about the same thing and we can put a number on it. DMBOK2 defines it as a measurable feature of data. The word is borrowed from measuring objects, where length, width and height are three angles for describing the same box. The same data can be measured from several angles in the same way (book: DMBOK2 section 1.3.3, pages 454 to 460).

The book's own example matches the marketing team's problem. If the email field of customers is incomplete, we cannot send product information by email and we lose sales. So we measure the percent of customers who have a usable email, and improve the process until it reaches at least 98%. In this example the dimension (completeness) says what we measure, and the lost sales say why it is worth measuring (book: DMBOK2 section 1.3.3, pages 454 to 460).

</Step>

## No single set of dimensions is agreed

People in the field have proposed many sets of dimensions, and the book describes the three most influential. The set by Strong and Wang (1996) starts from how the users of data see it and has 15 dimensions. Redman's set (1996) starts from the structure of data and has more than two dozen. English's set (1999) separates characteristics that do not depend on use (inherent) from those that depend on presentation and use (pragmatic). In 2013 DAMA UK produced a shorter set of six core dimensions: completeness, uniqueness, timeliness, validity, accuracy and consistency. The book concludes that there is no single set everyone agrees on, although all the sets share some ideas (book: DMBOK2 section 1.3.3, pages 454 to 460).

Other books choose differently. Ten Steps groups dimensions by how they are assessed, so it puts completeness and validity in one dimension called data integrity fundamentals, because a single round of profiling finds both. Governance and FoDE keep only three characteristics: accuracy, completeness and timeliness (book: Ten Steps chapter 3, pages 42 to 46; Governance chapter 5, page 113; FoDE chapter 2, pages 54 to 56).

In this path we use the six dimensions of DAMA UK, plus integrity and reasonability, which DMBOK2 Table 29 adds, because SQL can measure them most directly. The names are only the team's shared language. If your team uses another set, that works just as well as long as everyone means the same thing by each word (book: DMBOK2 Table 29, pages 458 to 459).

We also do not have to measure every dimension. Ten Steps asks two questions of each one: would the result give us something to act on, and can we really assess it? If either answer is no, we can skip it. [Lesson 12](/en/data-quality/ten-steps/#choose-what-to-assess-and-what-to-skip) comes back to this.

</Step>

## Completeness, validity, uniqueness

**Completeness** asks whether the data that should be there is all there. In the `customers` table above, customer 14 has no email at all. If marketing needs to email every customer, this row is a customer they cannot reach. We measure it with this query.

```sql
SELECT count(*) FILTER (WHERE email IS NULL), count(*) FROM customers;
-- 40 of 500
```

`count(*) FILTER (WHERE ...)` counts only the rows that meet the condition, while the second `count(*)` has no condition and counts every row. So one query gives us both the number of bad rows (40) and the total (500). That means 92% of the emails are present and 8% are empty. Besides columns, completeness can be measured at the row level and at the dataset level, which the page [Completeness](/en/data-quality/dimensions/completeness/) explains (book: DMBOK2 Table 29, page 458).

**Validity** asks whether the value in a field is one that the field allows. A field might allow only values from a list, values inside a range, or values that follow a pattern. Customer 23 has the email `user23example.com`, which has no `@`, so it does not look like an email. Customer 36 has the country `THA`, although the system accepts only TH, SG, JP and US (book: DMBOK2 Table 29, page 459).

```sql
-- email must look like a@b.c (only rows where email is not empty)
SELECT count(*) FILTER (WHERE NOT regexp_matches(email, '^[^@\s]+@[^@\s]+\.[^@\s]+$')), count(email) FROM customers;
-- 15 of 460

-- country must be in the list
SELECT count(*) FILTER (WHERE country NOT IN ('TH','SG','JP','US')), count(*) FROM customers;
-- 25 of 500
```

The text `'^[^@\s]+@[^@\s]+\.[^@\s]+$'` is a pattern that says an email has at least one character, then `@`, then more characters, then a dot, then another group of characters, with no spaces or extra `@` in between. Notice that the total of the first rule is 460, which counts only the emails that are not empty. The empty ones were already counted in completeness, and we do not want one empty cell to fail two rules at once.

**Uniqueness** asks whether each thing is recorded only once. In `orders`, order 267 is in two rows that are identical in every column. If we add up sales directly, this order is counted twice. In `customers`, customers 1 and 491 share one email, which may be one person who registered twice (book: DMBOK2 Table 29, page 459).

```sql
SELECT count(*) - count(DISTINCT order_id), count(*) FROM orders;
-- 20 extra rows of 3,020
```

This query takes the number of all rows and subtracts the number of different `order_id` values, so the result is the number of extra rows, not the number of orders that are repeated (run: `02_dimensions.py`, every number above matches what was planted).

## Consistency, integrity

**Consistency** asks whether two pieces of data that should agree really do agree. The book separates three levels: comparing within one row (record-level), across rows or datasets (cross-record), and across time (temporal). It also warns us not to confuse it with accuracy, because two values that agree can both be wrong (book: DMBOK2 Table 29, page 458).

In the `orders` table above, order 84 has the status SHIPPED but no shipping time. Order 816 was shipped on 1 October, the day before it was ordered on 2 October. Each column looks fine on its own, and the problem appears only when we look at two columns together.

```sql
-- status SHIPPED must have a shipping time
SELECT count(*) FILTER (WHERE status = 'SHIPPED' AND shipped_ts IS NULL),
       count(*) FILTER (WHERE status = 'SHIPPED') FROM orders;
-- 25 of 1,794

-- shipping time must not be before the order time
SELECT count(*) FILTER (WHERE shipped_ts < order_ts), count(shipped_ts) FROM orders;
-- 10 of 1,769
```

A rule like this cannot be found by checking one column at a time, because each column is fine when we look at it alone.

**Integrity** asks whether data that points to data in another table points to something that really exists. In most books it means referential integrity, which is consistency between two tables through a reference key. If a key points to nothing, we call it an orphan. In `orders` above, order 65 points to customer 9017, but our `customers` table has only the numbers 1 to 500 (book: DMBOK2 Table 29, page 459).

```sql
SELECT count(*) FILTER (WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id)),
       count(customer_id)
FROM orders o WHERE customer_id IS NOT NULL;
-- 30 orphans of 3,005
```

<Callout type="warn" title="Use NOT EXISTS instead of NOT IN">
If this rule is written with `NOT IN (SELECT customer_id FROM customers)`, there are two traps. First, an order whose `customer_id` is NULL (such as order 344) is not counted as an orphan, because SQL answers "unknown" instead of "not there". That is actually correct, since those rows are a completeness problem. The second trap is worse. If the list we compare against holds even one NULL, the whole query returns nothing, and the rule reports clean data when it is not. Use `NOT EXISTS`, and count the NULL rows separately in a completeness rule.
</Callout>

</Step>

## Timeliness, accuracy

**Timeliness** asks whether the data we have reflects reality at the time we need it. It always has to be read together with how often the data changes (volatility). The book separates two things: *currency*, which asks whether this value is the latest version, and *latency*, which asks how long it took from the moment the data was created until it was ready to use (book: DMBOK2 Table 29, page 459).

An example of latency is order 135. It was placed on 22 October at 12:07 and reached the warehouse on 26 October at 12:07, four days later, while a normal order takes only a few minutes.

```sql
-- row level: did the order reach the warehouse within 24 hours?
SELECT count(*) FILTER (WHERE ingested_at - order_ts > INTERVAL 24 HOUR), count(*) FROM orders;
-- 40 of 3,020
```

At table level the picture is different. The newest order in the table was placed on 29 October at 23:59, and the time we ask is 1 November at 08:00, which is 56 hours later. If we promised the consumer that the data would be at most 24 hours old, that promise is broken, even though 98.68% of the rows arrived on time (run: `02_dimensions.py`).

**Accuracy** asks how closely the data matches reality. The book says plainly that this is hard to measure, because we need something we are sure is right to compare with, such as the system where the data originates (the system of record). So we use the payment system as the reference and compare the total of each order with the sum of its payments. For example, order 91 records a total of 487.71, but the payments actually received add up to 437.71, a difference of 50 (book: DMBOK2 Table 29, page 458).

```sql
WITH o AS (SELECT DISTINCT order_id, total_amount FROM orders WHERE status <> 'CANCELLED'),
     p AS (SELECT order_id, sum(amount) AS paid FROM payments GROUP BY order_id)
SELECT count(*) FILTER (WHERE abs(o.total_amount - p.paid) > 0.005), count(*)
FROM o JOIN p USING (order_id);
-- 35 mismatches of 2,533
```

This query leaves out cancelled orders, then matches each remaining order with the sum of its payments. If the two values differ by more than 0.005, we count a mismatch. The book adds a warning that data can be valid without being accurate. A birth date of 1990-01-01 passes a rule about the range of years, but if the customer was born in 1985, the value is wrong.

</Step>

## All 14 rules together

This table gathers the 14 rules we have measured so far. Each line shows how many rows fail, how many rows were checked, and the percent on both sides.

| dimension | rule | fail | total | pass % | fail % |
|---|---|---:|---:|---:|---:|
| completeness | customers.email is populated | 40 | 500 | 92.00 | 8.00 |
| completeness | orders.customer_id is populated | 15 | 3,020 | 99.50 | 0.50 |
| validity | email has the shape a@b.c | 15 | 460 | 96.74 | 3.26 |
| validity | country is in the list | 25 | 500 | 95.00 | 5.00 |
| validity | birth_date is between 1900 and today | 6 | 500 | 98.80 | 1.20 |
| validity | orders.total_amount is not negative | 12 | 3,020 | 99.60 | 0.40 |
| uniqueness | one email per customer | 10 | 460 | 97.83 | 2.17 |
| uniqueness | one row per order_id | 20 | 3,020 | 99.34 | 0.66 |
| consistency | SHIPPED must have shipped_ts | 25 | 1,794 | 98.61 | 1.39 |
| consistency | shipped_ts is not before order_ts | 10 | 1,769 | 99.43 | 0.57 |
| integrity | orders.customer_id exists in customers | 30 | 3,005 | 99.00 | 1.00 |
| integrity | payments.order_id exists in orders | 20 | 2,553 | 99.22 | 0.78 |
| timeliness | order arrives within 24 h | 40 | 3,020 | 98.68 | 1.32 |
| accuracy | amount matches the payment system | 35 | 2,533 | 98.62 | 1.38 |

The "total" column is not the same on every line, because each rule picks its own denominator. Emails with a bad format are counted out of 460, not 500, because the blank emails were already caught by the completeness rule. "SHIPPED must have shipped_ts" counts out of 1,794 because only SHIPPED orders are relevant to it. Choosing denominators this way keeps one error from being counted twice in two rules.

## Try the matching yourself

<DimensionLab lang="en" client:visible />

One defective row can belong to several dimensions. For example, `ไทย` in the country field is outside the list, which is a validity problem, and it is also written differently from the `TH` that other rows use, which is a consistency problem. DMBOK2 Figure 92 draws dimensions overlapping like this, so we do not need to worry about finding "the one right answer". What matters more is that the team agrees which dimension a rule counts under, so the report does not count it twice.

<Callout type="try" title="Try it in this repo">
Run `uv run python 02_dimensions.py` and add a rule of your own, such as "total_amount is at most 10,000" or "signup_date is not in the future". Both should return 0, because we did not plant that kind of defect. This is how you check that your rule does not raise false alarms.
