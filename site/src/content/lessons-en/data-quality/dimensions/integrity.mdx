## Integrity asks whether what is referred to really exists

Think of a library loan card. One card says you borrowed the book with code 9017, but the library's catalog has no book with that code. The card is filled in completely and in the right format, yet it points at something that does not exist. Our data has the same situation in `orders`.

| order_id | customer_id | status | total_amount |
|---:|---:|---|---:|
| 65 | 9017 | SHIPPED | 1882.76 |

Order 65 says it belongs to customer number 9017, but our `customers` table has only the customer numbers 1 to 500. Nobody is called 9017. A key that points at something that does not exist is called an **orphan**. The `payments` side has the same case: payments 2534, 2535 and 2536 point to orders 9001, 9002 and 9003, which are not in `orders`.

DMBOK2 describes data integrity as a concept that includes ideas from completeness, accuracy and consistency. In practice it usually means one of two things. One is referential integrity, which is consistency between two tables through a reference key that both contain. The other is internal consistency within a dataset, so that it has no holes or missing parts. A dataset without referential integrity has orphans (reference keys that point at nothing) or duplicates (identical rows that may distort aggregation), and the level of orphans can be measured as a raw count or as a percentage of the dataset (book: DMBOK2 Table 29, page 459).

</Step>

<Step>

## One word, three meanings

Before measuring integrity, we should agree which meaning our team uses, because at least three are in circulation.

| Where | What integrity means |
|---|---|
| DMBOK2 | Mainly referential integrity, plus having no holes inside a dataset (book: DMBOK2 Table 29, page 459) |
| Ten Steps | Data integrity fundamentals is a much wider dimension. It covers existence, validity, structure and content, which we learn from profiling, and referential integrity is only one row in it (book: Ten Steps chapter 4, pages 128 to 135) |
| A database | An integrity constraint, such as a foreign key that the database enforces so that no orphan can appear |

A report that says "integrity 99%" therefore means three different things, depending on which one its author had in mind. This path uses the DMBOK2 meaning.

Our `orders` and `customers` tables were made with `CREATE TABLE ... AS`, so no foreign key is declared. Nothing in the database stops an order from pointing to a customer who does not exist, and that is why we have to check with a query ourselves.

</Step>

<Step>

## Measuring it

```sql
-- orders whose customer_id points to a customer that does not exist
SELECT count(*) FILTER (WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id)),
       count(customer_id)
FROM orders o WHERE customer_id IS NOT NULL;
-- 30 of 3,005
```

For each order, this query asks whether a customer with the same `customer_id` exists in the `customers` table. If not, that order is an orphan. We leave out orders whose `customer_id` is empty with `WHERE customer_id IS NOT NULL`, because an empty cell is a completeness matter, not an integrity matter. That is why the denominator is 3,005 and not 3,020.

The `payments` side uses the same kind of query. 20 of 2,553 payments point to an order that does not exist, and both counts match what was planted (run: `02_dimensions.py`).

</Step>

<Step>

## NOT IN reports a clean table when it is not

Many people write this rule with `NOT IN`, because it is easy to read.

```sql
SELECT count(*) FROM orders
WHERE customer_id NOT IN (SELECT customer_id FROM customers);
-- 30
```

Right now it gives 30, the same as `NOT EXISTS`. But suppose the list of customers we compare against contains just one NULL.

```sql
SELECT count(*) FROM orders
WHERE customer_id NOT IN (SELECT customer_id FROM customers UNION ALL SELECT NULL);
-- 0
```

The result becomes 0 at once, although the 30 orphan rows are still there. The reason is that in SQL, comparing with NULL answers "unknown", not "yes" or "no". When the list has a NULL in it, the question "this value is not in the list" can only be answered "unknown" for every row, so no row is counted at all. The check reports a clean table when it is not (run: `13_dimension_pitfalls.py`).

So we use `NOT EXISTS`, which does not have this problem, as the query in the previous section does.

</Step>

## An empty key and a key that points at nothing

Compare two kinds of orders that cannot be tied to a customer.

| order_id | customer_id | What is the problem? |
|---:|---:|---|
| 344 | (empty) | there is no key at all, which is completeness |
| 65 | 9017 | there is a key, but it points at nothing, which is integrity |

The two cases have the same effect: we do not know whose order it is. A revenue report by customer will miss both groups. Here `orders.customer_id` is empty in 15 rows and is an orphan in 30 rows, which makes 45 orders that cannot be tied to a customer (run: `13_dimension_pitfalls.py`). Report the two groups separately, because the fixes are different. An empty key has to be fixed at the source that did not send it, while an orphan means we have to find out where the customer went, or whether the key was entered wrongly. When someone asks how many rows of data are unusable, we then add the two groups together.

</Step>

<Step>

## Checking from the child to the parent

In `orders` and `customers`, the `orders` table is called the child because it refers to `customers`, which is the parent. An integrity check has a direction: it starts from the child table and asks whether what it refers to exists in the parent table.

A customer who has never placed an order is not a violation, unless the business has a rule that every customer must have ordered something. In our dataset there are no such customers (0), and if there were, they would just be people who have not bought yet. So we should write the direction into the rule: "from the child to the parent".

Integrity has one more limit. A key that points at something that exists can still be the wrong key. Suppose an order belongs to customer 56 but was recorded as customer 55. Both numbers exist in `customers`, so our rule passes, because integrity checks only that the key lands somewhere, and not that it lands in the right place. That question belongs to [Accuracy](/en/data-quality/dimensions/accuracy/), and it needs a trusted source to compare with.

</Step>

<Step>

## How it differs from the other dimensions

Integrity is close to completeness, because an empty key is an empty cell that should have a value, as we saw in the section on empty keys. It is also close to uniqueness, because DMBOK2 puts repeated rows in the description of integrity as well (book: DMBOK2 Table 29, page 459). If we already count repeated rows under [Uniqueness](/en/data-quality/dimensions/uniqueness/#measuring-it), we should not count them again here, or the scorecard counts the same rows twice. The two differ in that integrity looks for keys that point at something that does not exist, while uniqueness looks for keys that appear too often. In our dataset there are 30 orphan rows and 20 extra order rows.

Integrity and consistency can also share a label. The Ten Steps example that an order date must come before the ship date sits under referential integrity in that book, but we file it as consistency in this path. See the page [Consistency](/en/data-quality/dimensions/consistency/) for the details.

</Step>
