## Accuracy asks whether the data matches the real thing

Think of a thermometer that reads 31.4 degrees. The number is within a possible range and written in the right format. But is the room really 31.4 degrees? We cannot answer that from the number itself. We need a second thermometer we trust, or someone who already knows.

DMBOK2 defines accuracy as the degree to which data correctly represents real-life entities. It says plainly that accuracy is hard to measure, unless we can reproduce the data collection or confirm records by hand. Most measures therefore compare the data with a source that has been verified as accurate, such as a system of record or reliable external reference data (book: DMBOK2 Table 29, page 458). DAMA UK says the same in other words: the degree to which data correctly describes the real world object or event (book: DMBOK2 section 1.3.3, page 457).

Ten Steps opens its accuracy step with the observation that many people use "accuracy" as a synonym for data quality as a whole, while data professionals know that the two are not the same (book: Ten Steps chapter 4, pages 135 to 140).

</Step>

## What profiling can and cannot tell us

Ten Steps gives three examples of the line between what profiling can see and what only a comparison with the real thing can show (book: Ten Steps chapter 4, pages 135 to 140).

| Profiling can see | Only a comparison with the real thing can show |
|---|---|
| Every part has a valid code, M (make) or B (buy) | Whether that code matches how the part is actually sourced |
| Postal codes sit in the postal code field and follow valid patterns | Whether it is the right postal code for this customer |
| The stock count has the right data type | Whether the number matches what is on the shelf |

In our dataset the comparison is between two systems. We treat the payment system as the source of truth, and compare the total of each order that is not cancelled with the sum of that order's payments.

| order_id | total_amount in `orders` | What the payment system received | Difference |
|---:|---:|---:|---:|
| 91 | 487.71 | 437.71 | -50.00 |
| 122 | 2029.28 | 1979.28 | -50.00 |
| 412 | 4147.84 | 4146.84 | -1.00 |
| 438 | 1716.14 | 1836.14 | 120.00 |

```sql
WITH o AS (SELECT DISTINCT order_id, total_amount FROM orders WHERE status <> 'CANCELLED'),
     p AS (SELECT order_id, sum(amount) AS paid FROM payments GROUP BY order_id)
SELECT count(*) FILTER (WHERE abs(o.total_amount - p.paid) > 0.005), count(*)
FROM o JOIN p USING (order_id);
-- 35 of 2,533, so 98.62% accurate against payments
```

This query leaves out cancelled orders, because a cancelled order has no payment to compare. It matches each remaining order with the sum of its payments, and if the two values differ by more than 0.005, it counts a mismatch.

</Step>

<Step>

## Without a source of truth, accuracy cannot be measured

If there is nothing to compare with, we can check validity but we cannot check accuracy. Ten Steps lays out a decision flow with four questions. Can we identify an authoritative source? Can we get access to it? Do the stakeholders agree that it is the authority? Can we afford the assessment? If any answer is no, the book says we cannot or should not assess accuracy, and should use other dimensions instead (book: Ten Steps chapter 4, pages 135 to 140).

Comparing with the real thing is often done by hand and is expensive. The book suggests asking whether assessing only some records or some fields would still give a meaningful result. In our dataset the comparison is only a join, which costs nothing, and that is the exception, not the usual case.

The sentence "we are 98.62% accurate" therefore has a hidden clause: "against the payment system". And the number can be trusted only as far as the payment system can.

</Step>

<Step>

## A mismatch says two sources disagree, not which one is wrong

Order 91 records a total of 487.71, and the payment system says it received 437.71. We call order 91 inaccurate because we agreed beforehand that payments are the source of truth. But the truth could be the other way round: the total in `orders` is right and the payment was recorded wrongly.

The reference has problems of its own, too. In `payments` there are 20 payments that point to orders that do not exist (run: `13_dimension_pitfalls.py`), which is a matter for [Integrity](/en/data-quality/dimensions/integrity/). If we trust payments as the truth, we also need to know where it is weak. The book stresses that if the team does not agree on the authoritative source, nobody will trust the results of the assessment.

</Step>

<Step>

## The tolerance changes the number

The query above counts a difference of more than 0.005 as a mismatch. If we change that threshold, the number changes with it (run: `13_dimension_pitfalls.py`).

| Tolerance (difference we accept) | Mismatches of 2,533 |
|---:|---:|
| 0.005 | 35 |
| 1.00 | 27 |
| 11.00 | 18 |
| 60.00 | 11 |

None of these four lines is the right answer. A difference of 1.00 and a difference of 120.00 are different problems, and the people who own the money decide where the line goes. Write the tolerance into the rule every time.

Data that passes a validity rule can still be inaccurate. The 35 wrong totals are all positive, so every one passes the rule `total_amount >= 0`. DMBOK2 uses a date of birth as its example: a value inside the allowed range can still be wrong for the person it describes (book: DMBOK2 Table 29, page 459). Comparing with a copy of ourselves, which does not help with accuracy at all, is explained on the page [Consistency](/en/data-quality/dimensions/consistency/).

The word accuracy is also the name of a model metric in machine learning, where it means the share of predictions that are correct. It does not mean the data used for training is accurate in the sense used here, so we should say which one we mean (this remark is the author's).

</Step>

<Step>

## How it differs from the other dimensions

Accuracy differs from [Validity](/en/data-quality/dimensions/validity/) in that validity asks whether the value is allowed, while accuracy asks whether it is true. All 35 wrong totals pass validity.

Accuracy differs from consistency in that two sources that agree do not prove that either one is right.

Reconciliation, which [lesson 8](/en/data-quality/reconciliation/#reconcile-with-row-counts-and-sums) teaches, is the process of comparing two systems. Accuracy is what a good match tells us about one of them, when the other is an agreed source of truth. The order totals against the payment totals on this page are exactly that example.

</Step>
