## A rule is a promise you can check

DMBOK2 says data quality rules and standards are an important kind of metadata and should be managed as metadata (book: DMBOK2 §2.7.1). Defining rules early has four benefits:

- It sets clear expectations for the quality characteristics.
- It gives the system a requirement to have edits and controls that keep bad data out from the start.
- It gives a requirement to pass on to vendors or outside parties who supply data.
- It is the basis for ongoing measurement and reporting.

In lesson 3 we got "proposed rules" from a profile. This lesson turns a proposal into a usable rule, and decides when we trust the rule enough to let it stop a pipeline.

</Step>

<Step>

## Six properties of a good rule

DMBOK2 §2.7.1 says an effective rule should be as follows (book). The right-hand column matches each property to a field of the exercise's `Rule` (author).

| A good rule must | Meaning | Field in `Rule` |
|---|---|---|
| Be recorded consistently | Use one template so the meaning is the same everywhere | Every rule has the same set of fields |
| Be defined by dimension | The reader knows what is being measured | `dimension` |
| Be tied to business impact | A dimension is not a goal in itself. Do not measure what is not tied to a business process | `impact` |
| Be backed by data analysis | Analysts should not guess a rule. Test it on real data | `origin` and the profile result |
| Be confirmed by an expert | A rule describes what the data should look like, so someone who knows the process must confirm it | `confirmed_by`, `status` |
| Be accessible to data consumers | So they can ask questions and push back | The registry lives in a repo everyone can read |

The book also says that analysis may show that the rule itself is incomplete, not only that the data is wrong.

</Step>

<Step>

## Where rules come from

DMBOK2 §2.3 admits that rules are often not written down and must be traced back from business processes, policies, standards, laws, system code, triggers, the use of status codes, and common sense (book). It suggests asking stakeholders what happens if the data is missing or wrong, how they would know, and what bad data they have met before.

The exercise sorts the sources into three groups (**this grouping is the author's**):

| Source | Example in the registry | Who confirms |
|---|---|---|
| Business | A customer must have an email, SHIPPED must have a ship time | The data consumer or the process owner |
| Technical | order_id is unique, a foreign key must have something behind it | The engineer or system owner |
| Statistical | The amount is not negative (from looking at a profile) | Someone who knows the business must confirm before use |

Column-level rules are straightforward. Dataset-level rules are often harder to read, for example "every customer must have a usable mailing address" (book: DMBOK2 §2.3).

</Step>

## The rule registry: a query with an owner, a threshold and an impact

```python
@dataclass(frozen=True)
class Rule:
    id: str            # "ORD-ID-UNIQUE"
    dimension: str     # "uniqueness"
    table: str
    statement: str     # a sentence a business person can read and confirm
    sql: str           # returns (bad rows, rows this rule applies to)
    max_bad_pct: float # the accepted threshold
    severity: str      # "error" can block the pipeline, "warn" only reports
    owner: str
    impact: str
    origin: str        # business, technical, statistical
    status: str        # active, proposed
    confirmed_by: str | None
```

## The accepted threshold is not always zero

The same measurement can pass or fail depending on the threshold. Take duplicate emails at 2.17%:

| Threshold | Result |
|---|---|
| 0.0% | Fails |
| 0.5% | Fails |
| 2.0% | Fails |
| 5.0% | Passes |

DMBOK2 gives examples of this kind of status in Table 30: completeness below 80% is "unacceptable", and late arrival above 1% is "unacceptable". Those numbers are examples in the book, not thresholds that work everywhere. A threshold has to come from the data consumer (lesson 1), and DMBOK2 §4.4 calls this property **acceptability**. Two things are decided separately:

- **Threshold** (`max_bad_pct`): how much can be wrong and still be called acceptable.
- **Severity** (`severity`): if the threshold is exceeded, only report (`warn`) or stop the pipeline (`error`). In the exercise, 6 rules of severity error fail together. Only these 6 can stop anything, and `ORD-TOTAL-SIGN`, which is still `proposed`, reports but stops nothing, because nobody has confirmed that negative values are really wrong (they may be refunds, see lesson 3).

</Step>

<Step>

## Six properties of a good metric

DMBOK2 §4.4 lists the properties of a metric worth measuring (book). Review them against our rules:

| Property | Ask | If it is missing |
|---|---|---|
| Measurability | Can it be counted, with a defined range of results? | "The data is relevant" cannot be measured until a threshold is defined |
| Business relevance | Is it tied to how the business runs? | It can be measured but nobody cares |
| Acceptability | Is there a line for enough or not enough? | You get a number but cannot decide anything |
| Accountability | Did the business owner approve it, and does someone fix it when it fails? | An alert fires and nobody takes it |
| Controllability | If it goes out of range, can anyone do something? | The book says it "would probably not be useful" |
| Trending | Can you see the trend over time? | You only see a still photo (lessons 7 and 10) |

Controllability matters: if nobody can respond when a value goes out of range, it should not be measured. The exercise's `lint()` checks this through the `owner` and `impact` fields.

</Step>

## Too many rules that nobody believes

DQF warns about writing lots of tests without a reason behind them. If a developer adds a test because having a test seems better than none, and months later someone else breaks it and does not understand why it exists, they will delete the test to get CI to pass. A culture like that turns tests into obstacles, not insight. The book concludes that "if you are not going to take tests seriously, it is better to have no tests at all" (book: DQF ch.3).

So the registry has a `lint()` that rejects untrustworthy rules. The decoy rule `MKT-MAGIC`, written badly on purpose, is caught on five counts (ran: `04_rules.py`):

```text
MKT-MAGIC: dimension 'goodness' is not one of the agreed names
MKT-MAGIC: no owner: nobody is accountable when it fails
MKT-MAGIC: no business impact: why is this measured?
MKT-MAGIC: threshold must be a percentage between 0 and 100
MKT-MAGIC: active rule has not been confirmed by a subject matter expert
```

Tools such as GX and dbt store "rules that run", but fields like owner, impact and who confirmed it have to be the team's own discipline (lesson 5 covers these tools, and the Great Expectations path teaches writing rules in GX).

Open `dqrules.py` and add a rule of your own, such as "signup_date is not in the future". Give it an owner, an impact and a threshold, then run `04_rules.py`. If you forget any field, `lint()` will tell you. Try setting `status="active"` without a `confirmed_by` and see what happens.

## Check yourself

- The rule "the amount is not negative" is set to `proposed`. Who should change it to `active`, and what must they ask first?
- If the duplicate-email rule were set to `error` with a threshold of 0%, the pipeline would stop every night. Who is hurt? Who should decide whether it is `warn` or `error`?
- A rule that nobody is responsible for when it fails should be deleted or given an owner. Which do you choose, and what criterion decides it?
