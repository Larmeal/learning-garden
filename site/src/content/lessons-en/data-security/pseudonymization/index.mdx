## Replace the e-mail with a hash, and it is safe, right?

Mr. A's analytics team still wants to know how many times the same customer ordered, so it does not drop the e-mail column. It replaces it with `sha256(email)`, because it remembers from [the lesson on cryptography in Application Security](/en/app-security/crypto-basics/) that a hash cannot be reversed. Replacing an identifier with another value that still says "the same person" is called **pseudonymization** (book: Practical Data Privacy chapter 1 page 22).

The question is what somebody who has the table and wants to know whose row is whose will do. The attacker does not reverse anything. He guesses, hashes the guess and compares with the table. In Application Security we saw a four digit PIN found in 7,352 tries. Now something bigger (run: `exercises/02_pseudonymization.py`).

Suppose the table holds a 6 digit member number for each person, which has only 1,000,000 possibilities. The attacker computes the SHA-256 of every number once, and then compares.

```python
lookup = {sha(f"{n:06d}".encode()): f"{n:06d}" for n in range(1_000_000)}
undone = sum(1 for pid, h in hashed.items() if lookup.get(h) == members[pid])
```

The first line builds a table of all the million hashes, which took about 1.6 seconds on the computer that ran it. The second looks up the hashes of our table in it. The result: 2,000 of 2,000 people undone.

E-mail is not much safer, because an e-mail has a pattern: a first name, a dot, a last name, a number, @ and a domain. The exercise builds a dictionary from 20 first names, 15 last names, the numbers 1 to 2,000 and one domain, which gives 600,000 guesses, and it finds all 654 e-mails on that domain.

</Step>

## Four ways, and what each one costs

There are alternatives that do not fall over like a plain hash, but each costs something. Choose a method and what the attacker holds in the lab below and press play. The attacker tries a list of guessed e-mails one at a time, and a row that matches is cracked. Under it, the same customer appears in a second table: if the two values are equal, an analyst can join them. The point to notice is that whatever makes a join possible is also usable by an attacker who holds the right thing.

## A salt per row: safer, but no join

Just as a salt helps with passwords in Application Security, we put a different random salt in front of every row's hash, and a dictionary no longer works. The exercise checks that the same dictionary finds none of the hashes.

But there is a price. Suppose the orders table and the support tickets table each salt the e-mail of the same customer. The values in the two tables are not equal. The exercise counts matches on 0 of 2,000 people. The analyst who wants to know whether a customer who ordered also phoned in cannot find out. If no join across tables is needed at all, this method will do, but mostly we need one.

</Step>

## HMAC: joins work as long as the key is safe

HMAC mixes a secret key into the calculation, and nobody without the key can compute the value of a guessed e-mail. The exercise builds two tables with the same key. The values of the same e-mail match for all 2,000 of 2,000 people, so they join, and an attacker with a complete dictionary of e-mails but no key finds no value at all.

The value is shorter than a full hash (16 hex characters) and shows no part of the e-mail. The number of distinct people stays the same (2,000 values), so counting people is still right.

There are two downsides. First, the key is the one weak point of this system. If it leaks with the table, the attacker computes the HMAC of each guessed e-mail from a dictionary and undoes the table just as with a plain hash. Second, if the key is changed, everything made with the old key stops meaning anything. The exercise counts that after a key change no old token equals a new one (0 of 2,000), so tables made at different times can no longer be joined.

</Step>

<Step>

## A random token: nothing to attack, but there must be a vault

The last method does not compute anything from the e-mail. It makes up a new random value and writes the pair "e-mail and token" into a vault kept apart. An attacker who gets only the table has no formula to guess. The exercise builds two tables that tokenize the same e-mails separately, and the values never match (0 of 2,000), because each side picks its own random values, and the vault has to hold 4,000 entries that must be protected on their own.

In practice the vault answers "which token does this e-mail get" and returns the same value when it sees it again, which makes joins possible, but it costs everyone calling the vault, and the vault becomes the biggest target. The exercise did not run a vault like that.

<Callout type="note" title="Pseudonymization is not anonymization">

All four methods change only the direct identifiers. The quasi identifiers zip, birth date and sex are all still there, and from the last lesson we know that is enough to leave 1,992 of 2,000 people with nobody else the same. The author therefore calls data like this pseudonymized and not anonymized, as Practical Data Privacy treats it in chapter 1 (book: Practical Data Privacy chapter 1 page 22).

</Callout>

</Step>
