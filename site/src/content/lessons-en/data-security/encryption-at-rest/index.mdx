## Encrypt field by field

Two lessons ago we dealt with data that leaves the company. This lesson comes back to the data we hold ourselves. Suppose the national id numbers of customers are in a table. The first question people ask is: if the disk or a backup leaks, who can read it? Encrypting data at rest answers this.

We encrypt only the sensitive field, with the AES-GCM that we know from Application Security, using the row id as the associated data of each value (run: `exercises/07_encryption.py`).

```python
def enc(pid, value):
    nonce = os.urandom(12)
    return nonce + gcm.encrypt(nonce, value.encode(), str(pid).encode())
```

The function draws a fresh 12 byte nonce each time, encrypts the value, and gives the row id as associated data. A 9 character number becomes 37 bytes: nonce 12, text 9 and tag 16. Every value decrypts again when the right row id is used.

What is the associated data for? Try copying the ciphertext of row 2 into row 1. Decryption fails with `InvalidTag`, because the tag covers the row id too. Somebody who can write to the disk but has no key cannot swap values between rows. And encrypting the same value twice gives different results (different nonces), so nobody can see which rows hold equal values.

</Step>

<Step>

## Random encryption, or encryption you can search

Random encryption is very good, but it cannot be searched. To know how many rows have the same diagnosis, every row has to be decrypted first. The usual way out is **deterministic encryption**, where the same value always gives the same ciphertext. The exercise uses AES-SIV.

The result: the diagnosis column has 7 values and there are exactly 7 different ciphertexts, so an "equals" condition can be used to search the encrypted data. But the price is that equality is visible. An attacker who has the table and knows roughly which illness is common counts the frequency of the ciphertexts and guesses which ciphertext is which illness. The exercise checks that the most frequent ciphertext belongs to flu, which is the most common illness in the table (frequency analysis). Random encryption of the same column gives 300 different values for all 300 rows.

Choose by what has to be done. If no search is needed, use the random kind. If searching by exact value is needed, use deterministic encryption on a column with very many different values (such as an id number), and do not use it on a column with few values like a diagnosis. That last point is the author's opinion from the result, not from the book.

</Step>

## One key for everything is a problem

If we use one key for all the tables and want to rotate it (change to a new one by policy or because we suspect it leaked), we have to decrypt and encrypt every row again. The author's example has three tables of 100,000, 2,000,000 and 400,000 rows, 2,500,000 values of 37 bytes each, so 92,500,000 bytes must be rewritten, although the real data has not changed at all (book: Practical Data Privacy chapter 10 page 265 mentions key rotation among the frequently asked questions).

The fix is **envelope encryption** in two levels. Each table has a **data key (DEK)** of its own, used to encrypt the rows of that table. Then a **master key (KEK)**, which lives in a KMS or an HSM, wraps each DEK. What is stored beside the data is the wrapped DEK, 60 bytes long (nonce 12, key 32, tag 16). Press through the steps in the lab below.

<EnvelopeLab client:visible lang="en" />

Step four is where the benefit is. When the master key is rotated we unwrap the three DEKs with the old key and wrap them again with the new one: 180 bytes are rewritten, and the 2,500,000 rows are not touched. The exercise checks that the DEKs are unchanged and the rows still decrypt, and that the old master key can unwrap nothing any more.

</Step>

<Step>

## Delete a key to delete data

There is a second benefit that is less visible. When a request comes to delete data, we have several copies: the database, replicas, and a backup tape that cannot be edited. If a table was encrypted with a DEK of its own, deleting that DEK of 32 bytes makes every copy of the table unreadable. This is called **crypto-shredding**.

The exercise shows it for real. It makes a key store with the DEK of the table `customers`, encrypts 300 rows, and keeps a copy as a backup while the key still exists. The rows in the table and in the backup read normally. After the key is deleted from the key store, neither can be read at all, because there is no key to ask for, and trying another key does not decrypt the backup either (`InvalidTag`).

One thing to think about: the technique works when the DEK is separate for each group of data that we want to delete together. If we have to delete one person from a table of 2,000,000 rows, there is no DEK per person to delete. Another way is needed, which we discuss in the lesson on the life of data.

</Step>

<Step>

## What encrypting the disk does not help with

This kind of encryption protects a disk, a backup and a tape that leak. It does not protect against commands run in the name of the app, because the app has to hold the key to decrypt data for use. The exercise keeps 300 encrypted rows in SQLite and writes a function standing for the app, which takes a WHERE condition and decrypts every row returned. That is a place where an attacker can inject SQL, as in the lesson on injection in Application Security.

A normal query `pid = 1` returns one decrypted value. But when the attacker sends `pid = 1 OR 1 = 1`, the app decrypts all 300 values for him. Encrypting the disk did nothing in this case. The author concludes that encrypting stored data is one layer of defence and there have to be others, namely limiting who can read what, which [the next lesson](/en/data-security/access-masking/) covers.

<Callout type="note" title="What was not run">

A real KMS or HSM was not run, so the policy on who may call the master key was not tested. Encrypting the whole database file (transparent data encryption) was not tested, and neither was searching in a way that does not leak frequencies (searchable encryption).

</Callout>
