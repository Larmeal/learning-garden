## Open one request and look inside

When we call `requests.get("http://garden.test/hello.txt")` it looks as if the text floats to the server by itself, but a lot happens on the way. To see it, we build a small network in Linux: a client, a router and a server in a line (each is its own network namespace, with a virtual cable between them). The client sends a request to the server while `tcpdump` captures every packet that crosses the cable (ran: `exercises/01_big_picture.py`).

The request is 65 bytes of plain text. With the line endings written out, it looks like this.

```text
GET /hello.txt HTTP/1.1\r\n
Host: garden.test\r\n
Connection: close\r\n
\r\n
```

On the client side we capture ten packets of this connection.

| # | Direction | Type | Frame size |
|---|---|---|---|
| 1 | client to server | SYN | 74 bytes |
| 2 | server to client | SYN, ACK | 74 bytes |
| 3 | client to server | ACK | 66 bytes |
| 4 | client to server | PSH, ACK (the request is in this one) | 131 bytes |
| 5 | server to client | ACK | 66 bytes |
| 6 | server to client | PSH, ACK (the response is in this one) | 164 bytes |
| 7 | client to server | ACK | 66 bytes |
| 8 | server to client | FIN, ACK | 66 bytes |
| 9 | client to server | FIN, ACK | 66 bytes |
| 10 | server to client | ACK | 66 bytes |

We meant to send only two pieces of text (a request and a response), yet ten packets appeared. The rest is TCP's work: agreeing before sending (the first three packets), acknowledging what arrived, and closing the connection cleanly. Before the first packet there are also two ARP frames, where the client asks "who is 10.0.1.1?" and the router answers with its MAC address. We will go through each of these in the lessons that follow. For now, remember that 65 bytes of text do not travel alone.

</Step>

## A packet is a box wrapped in several layers

Think of sending a parcel across a city. The thing we want to send is the HTTP message. We put it in a box labelled with the department it is for (TCP and the port number), then wrap that box in another one labelled with the address of the building (IP). When it goes on a truck, each driver adds a new delivery slip that says only "from this depot to the next depot" (Ethernet). The slip is valid for that one leg. At the depot it is torn off and a new one is written for the next leg, and the boxes inside are never opened.

A real packet does the same. We measured each layer in the packet that the client sent out.

| Layer | Header added | Size | What identifies things at this layer |
|---|---|---|---|
| Application | the HTTP text | 65 bytes | URL, HTTP headers |
| Transport | TCP | 32 bytes | port (50000 to 8080) |
| Network | IP | 20 bytes | IP address (10.0.1.2 to 10.0.2.2) |
| Link | Ethernet | 14 bytes | MAC address |
| Whole frame | | 131 bytes | |

The TCP header here is 32 bytes because 20 bytes are always there and Linux adds 12 bytes of options to record timestamps (ran, book: TCPIP section 1.2.2, page 10).

How does each layer know what is inside it? Each header has a field that says so. The Type field of Ethernet is `0x0800`, which means IPv4 inside. The Protocol field of IP is `6`, which means TCP inside. The destination port of TCP is `8080`, which picks the program that is listening on that port. Choosing the next layer down the stack like this is called demultiplexing (ran, book: TCPIP section 1.3.2, page 16).

Two things to notice. First, the IP addresses and ports never change, because they say who is talking to whom, which is a matter for the two ends. Second, the MAC addresses and the TTL change at every router, because a MAC address only says who sends and who receives on this one cable, and TTL counts how many legs the packet has crossed (ran).

## Four layers and what each is responsible for

The four layers in the picture are the shape of the TCP/IP protocol suite (book: TCPIP section 1.3.1, page 13). Many networking texts also describe the seven-layer OSI model, which splits Link into cable and frame and splits Application into three layers (book: AIO Book 2 chapter 1, page 80). In practice four layers are enough to explain everything we capture.

| Layer | Job | Identified by | Who reads this header |
|---|---|---|---|
| Application | the meaning of the message (HTTP, DNS, TLS) | URL, domain name | the program at the end |
| Transport | get the data to the right program (TCP, UDP) | port | the two computers at the ends |
| Network | reach the right computer across many networks (IP) | IP address | the destination and every router on the way |
| Link | cross one cable to the neighbour (Ethernet) | MAC address | the two computers at the ends of that cable |

Each layer talks only to the same layer on the other side. The TCP of the client talks to the TCP of the server, and the router does not know TCP at all (it does not look). This idea is called the end-to-end argument: what needs to understand the data, such as ordering and resending, belongs at the two ends, not in the network in the middle. The middle only forwards, as simply and quickly as it can (book: TCPIP section 1.1.2, page 6). It also explains why the router in the lab touches only Ethernet and the TTL.

</Step>

## The OSI seven layers, and the words your infra team uses

You may have met the words L4 and L7 on the load balancer page of a cloud, or when talking to an infra team. Those numbers come from the OSI model, which splits a network into seven layers, where the TCP/IP model we just saw has four (book: AIO Book 2 chapter 1, page 80). The table puts the two side by side, with things we have already met in this lesson.

| Layer | Name | What lives here | Matches this TCP/IP layer |
|---|---|---|---|
| 7 | Application | HTTP, DNS | Application |
| 6 | Presentation | converting data formats, compressing and encrypting | Application |
| 5 | Session | opening and keeping a conversation between two computers | Application |
| 4 | Transport | TCP, UDP and ports | Transport |
| 3 | Network | IP addresses and routers | Network |
| 2 | Data Link | MAC addresses, Ethernet and switches | Link |
| 1 | Physical | cables, signals and hubs | Link |

The picture below draws the two models as stacks of boxes, OSI on the left and TCP/IP in the middle. You can see that the Application box of TCP/IP is as tall as the top three OSI layers, and the Link box as tall as the bottom two. Pick any of the things and the layers where it lives light up in both stacks. Try the switch first, then compare the L4 and L7 load balancers, or pick TLS to see why it does not fit one box exactly. You can also click a layer to read what it does.

<LayersLab lang="en" client:visible />

The layer numbers became the way people name devices too. A switch, which reads only MAC addresses, is called a layer 2 device (book: AIO Book 2 chapter 1, page 81), a router that reads IP addresses is layer 3, and load balancers borrow the same words. An L4 balancer looks only at the IP address and the port and spreads whole connections, while an L7 balancer reads the HTTP message and picks a backend for each request. We will compare the two in [lesson 13](/en/networking/proxies-and-containers/) (the names are the author's, the behaviour of both kinds was run in that lesson).

For DE work, almost everything we call every day sits at the top layer: JDBC into a database, reading a file from S3 as an HTTP request, and Kafka sending messages over TCP (this is the author's own understanding and was not run in an exercise). But when something breaks, the lower layers that we never write code for can still be the cause, so we can walk up through them one at a time: does a ping reach it (L3), can we open the port (L4), and only then look at the HTTP answer (L7). [Lesson 14](/en/networking/debugging-and-failure/) applies this way of working to real symptoms.

Do not expect every protocol to fit this table exactly. The same book admits that real protocols do not follow OSI to the letter (book: AIO Book 2 chapter 1, page 81). Take TLS, which we meet in [lesson 11](/en/networking/tls/). The job of encrypting belongs to the Presentation layer in the table (book: AIO Book 2 chapter 1, page 88), but the real TLS sits between TCP and HTTP, which matches no single layer. If people argue about which layer TLS is, you do not need to take it seriously. Treat OSI as a shared language for talking, and the author thinks the four TCP/IP layers match the packets we capture better.

</Step>

## A port and one connection

In the exercise the client opens two connections to the same server on port 8080. The first uses source port 50000 and the second 50001. The server can tell them apart because one connection is identified by four numbers together: source IP, source port, destination IP and destination port (ran, book: TCPIP section 1.3.3, page 17).

```text
('10.0.1.2', 50000, '10.0.2.2', 8080)
('10.0.1.2', 50001, '10.0.2.2', 8080)
```

In a real program we usually do not choose the source port. The operating system picks a free one. The exercise sets 50000 itself only so that the numbers it prints are the same on every run. Each connection still has its own handshake and its own sequence numbers, and the client asks ARP only once, because the second connection reuses the router's MAC address it already remembers.

<Callout type="note" title="Port numbers come in groups">

The server-side ports that people know are usually low numbers, such as 80 for HTTP and 443 for HTTPS. The client-side ports that the system picks are high numbers in a temporary (ephemeral) range. We come back to how wide that range is, and what happens when it runs out, in the lesson about sockets.

</Callout>
