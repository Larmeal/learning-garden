## The problem of a cable that everyone can listen to

All the HTTP we have captured so far was plain text. In [lesson 1](/en/networking/big-picture/) we could read `GET /hello.txt` straight out of the packet, which means anyone along the way, a router, the Wi-Fi we are on, or our internet provider, can read and change the data. TLS (Transport Layer Security) is what makes that stop being a problem. It does two things on top of the TCP we already have. First, it encrypts the data. Second, it proves that the server is the one we meant to talk to (book: TCPIP section 18.9.1, page 877).

In the exercise we build a small world with two certificate authorities, Garden Test CA and Other Test CA, and four certificates for the server: a valid one, one with the wrong name, an expired one, and one issued by the other authority. A client and a server using Python `ssl` talk across cables delayed 10 milliseconds each way, and we capture packets at the client (ran: `exercises/11_tls.py`). Since everything is made on the computer, these authorities do not exist on the real internet.

</Step>

## The handshake on a real cable

The client starts with the usual TCP handshake, and then the first data it sends is the **ClientHello**, which is still fully readable. We decoded it from the packet (ran, RFC: RFC 8446 section 4.1.2).

```text
server name (SNI): garden.test
versions offered:  TLS 1.3 (0x0304), TLS 1.2 (0x0303)
key share:         x25519, 32 bytes
cipher suites:     18
the ClientHello is 512 bytes long, in a record of 517 bytes
```

Three things are interesting. The name the client wants to talk to (SNI) is sent readable, because a server that holds several names must know which certificate to choose (book: TCPIP section 18.9.1, page 887). Anyone watching the cable knows which site we are visiting, even if not what we do there. Second, the key share: numbers for the key exchange, sent in the very first message, which is why TLS 1.3 can agree on a key so quickly. And last, the version field in the record header says `0x0301` although 1.3 is offered. It is a value put there so that old boxes in the middle are not confused, and the real version is in the `supported_versions` extension (ran, RFC 8446 section 4.1.2).

The server answers with a **ServerHello**, which is still readable, and from here on everything is encrypted (ran). In TLS 1.3 "all handshake messages after the ServerHello are now encrypted", as RFC 8446 section 1.2 says. We see this on the real wire.

| Server record | Type seen on the wire | Size |
|---|---|---|
| 1 | handshake (ServerHello) | 122 |
| 2 | change_cipher_spec | 1 |
| 3 to 7 | application_data | 23, 410, 96, 69, 250 |
| 8 to 9 | application_data | 250, 89 |

Every record after the ServerHello has the type `application_data`, like real data. A watcher cannot tell which one is the certificate and which is the application's data. The `change_cipher_spec` is a leftover so that old boxes in the middle understand. We can guess from the sizes that the 410-byte record is probably the certificate and the two 250-byte records probably session tickets, but that is the author's inference and we did not decrypt anything. What we can confirm is two things: the text `GET /hello` and `hello, garden` never appear on the wire, and the name `garden` appears only in the ClientHello going up, not in a single byte coming down (ran).

TLS 1.2 is different. When we captured a 1.2 handshake in the same exercise, the server's records were ServerHello, Certificate (390 bytes), ServerKeyExchange, ServerHelloDone and NewSessionTicket, all plain, up to the change_cipher_spec, and only then encrypted (ran, book: TCPIP section 18.9.1, pages 881 to 888). A watcher can see the certificate, and so who the server is.

## How many round trips before data can go

Press play in the lab and switch between TLS 1.3 and TLS 1.2 to see the order of messages, the round trips that pass, and what a watcher sees in each message.

<TlsLab client:visible lang="en" />

The numbers measured in the exercise, with a round trip of 20 milliseconds on the cable, counted from the start of `connect` to the first byte of the response (ran).

| Kind | Time (about, ±2 ms between runs) | Round trips |
|---|---|---|
| Plain HTTP | 42 ms | 2.1 |
| TLS 1.3 | 64 ms | 3.2 |
| TLS 1.2 | 84 ms | 4.2 |
| TLS 1.3 when the client does not set `TCP_NODELAY` | 84 ms | 4.2 |

Plain HTTP takes two round trips, one for TCP's handshake and one for the request and response. TLS 1.3 adds one, because the ClientHello brings a key share in the first message, so the server answers with everything the client needs in a single go. TLS 1.2 adds two, because the client has to wait for the ServerHello before it sends its part of the key exchange (book: TCPIP section 18.9.1, pages 881 to 888, RFC 8446 section 2). If there are thousands of new connections, the one round trip that is saved means a great deal.

The last row is something we did not expect. At first the exercise got 84 milliseconds with TLS 1.3 when it should have been 64. The cause is Nagle from [lesson 8](/en/networking/tcp-reliability/#nagle-wait-to-join-small-writes-into-a-bigger-block). The client's Finished is a small message that has not yet been acknowledged when the program writes the request right after it, so Nagle held the request back until the Finished was acknowledged, which took one more round trip. With `TCP_NODELAY` set it came back to 64. If our program writes sockets itself, it should set this option when it wants the first request to leave at once. It is a good example of how Nagle in [lesson 8](/en/networking/tcp-reliability/) comes back to affect TLS in this lesson (ran).

## What the client checks before it believes the server

Encryption alone is not enough. If we talk in perfect secrecy with the wrong party, there is no use in it. So TLS has the server send a certificate to prove its identity, a document that says "this public key belongs to the name garden.test" and carries the signature of an authority that we (or our operating system) already trust (book: TCPIP section 18.9.1, page 871 and RFC 8446 section 4.4.2). Our valid certificate looks like this (ran).

```text
subject  garden.test
issuer   Garden Test CA
SAN      DNS garden.test, IP 10.0.2.2
```

The client checks three things: that the chain of signatures leads up to an authority it trusts, that the name we connected to is in the certificate's list of names (SAN), and that the certificate has not expired. We tested each by letting different servers use a differently wrong certificate and looking at the message the client reports (ran).

| Case | The message from the client |
|---|---|
| A certificate for another name | Hostname mismatch, certificate is not valid for 'garden.test' |
| An expired certificate | certificate has expired |
| A certificate issued by an authority we do not trust | unable to get local issuer certificate |
| We trust the wrong authority (the wrong CA file) | unable to get local issuer certificate |
| A valid certificate, but we ask for another name | Hostname mismatch, certificate is not valid for 'other.test' |

All five fail after TCP has connected (the TCP `connect` time was normal, about 22 milliseconds). TCP does not care about these things. Only TLS does. One observation worth keeping is about the third and fourth rows. The message "unable to get local issuer certificate" often makes people think the certificate is bad. In fact the certificate may be fine, and the problem is that our side does not have that authority in its trusted list, for example when we use a certificate from the company's internal CA on a computer where that CA has not been installed. And setting "do not check the certificate" to make it pass throws half the benefit of TLS away, leaving only the encryption, which does not stop someone from pretending to be the server (book: TCPIP section 18.9.1, page 877, on anonymous connections being exposed to MITM).

`openssl s_client` gives the same result. Given the right authority, it checks the chain at depth 1 (the authority) and 0 (the server), and prints `verify return:1` for both (ran).

## What TLS does not do

TLS does not hide everything. From the exercise we already know that the server name in the ClientHello is still readable, the size and timing of the records are visible, and the destination IP address is in the IP header all the time (ran). A watcher therefore knows who we talk to, though not what about. There are newer extensions that hide the name, but we did not try them (not run). And TLS protects the journey between two ends. If the server itself is broken into, or a proxy in the middle decrypts for us, the data is read at that point, which is why in the later lessons of this subject we come back to what a load balancer in the middle does with TLS (author).

Two more topics that this lesson skips, but that working people meet for certain, are revoking a certificate that has leaked (CRL and OCSP) and the fact that a client can also have a certificate for the server to check (mTLS). Neither was run.

</Step>
