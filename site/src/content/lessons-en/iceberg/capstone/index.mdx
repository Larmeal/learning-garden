## The task

An online shop has one table `orders` that two writers feed. The first is a Spark batch that loads the daily orders. The second is a Python program that uses PyIceberg (for example a service that takes data from retail stores). The later batches sometimes contain wrong rows, such as a negative amount. We do not want readers to see such a row at all. We must be able to correct data afterwards, a downstream system wants to know only what changed, and the month-end snapshot must be kept as evidence (ran: `exercises/14_capstone_orders.py`).

The path below uses the tools of all the earlier lessons. The table is created as version 2, partitioned by day, with `write.merge.mode` and `write.delete.mode` set to merge-on-read ([lesson 6](/en/iceberg/row-level/#merge-on-read-writes-a-note-saying-which-row-to-skip)).

</Step>

<Step>

## Spark writes the first batch, and we note where the downstream system has read up to

Spark `INSERT`s 3 rows into the table, and the total amount is 242.5. Then we note the latest snapshot id as `bookmark`, which stands for the point the downstream system has read up to ([lesson 12](/en/iceberg/streaming/#read-only-the-rows-added-between-two-snapshots)).

</Step>

<Step>

## PyIceberg writes the second batch to a branch first

The PyIceberg side does not write to the main table directly. It writes to a branch called `audit` ([lesson 8](/en/iceberg/time-travel/#a-branch-separates-work-you-are-not-sure-about)):

```python
spark.sql("ALTER TABLE lab.db.orders CREATE BRANCH audit")
t.append(batch, branch="audit")        # batch has 3 rows and the last one has the amount -9.0
```

The main table still counts 3 rows as before, because the main branch did not move, so readers do not see the new batch yet. Then we check on the branch with `SELECT count(*) ... VERSION AS OF 'audit' WHERE amount < 0` and get 1 row, the wrong row we put there on purpose.

</Step>

<Step>

## Remove the bad row on the branch, then publish

When we find the bad row, we remove it on the branch first:

```python
spark.sql("DELETE FROM lab.db.orders.branch_audit WHERE amount < 0")
spark.sql("CALL lab.system.fast_forward('db.orders', 'main', 'audit')")
```

After the fast forward the main table has rows 1 to 5 and no row 6 at all. Readers never saw the wrong row. Then we drop the branch and put a tag called `month_end` on this snapshot, to be kept for 365 days.

</Step>

<Step>

## A late correction is a MERGE

Later the shop says the amount of order 2 must be 85.0, not 80.5. We correct it with a `MERGE INTO` that updates the matching row and adds the rows that do not match:

```python
spark.sql("""MERGE INTO lab.db.orders t USING (SELECT 2L AS order_id, 'bob' AS customer, 85.0 AS amount, TIMESTAMP'2026-01-01 15:30:00' AS ordered_at) s
             ON t.order_id = s.order_id WHEN MATCHED THEN UPDATE SET amount = s.amount WHEN NOT MATCHED THEN INSERT *""")
```

The total amount is 562.0 (120 + 85 + 42 + 300 + 15), and the table has at least one position delete file, because we set merge-on-read.

</Step>

<Step>

## Passing it on to the downstream system

The downstream system wants only what changed since `bookmark`. We first try the changelog view that we saw in [lesson 8](/en/iceberg/time-travel/#the-changelog-shows-what-changed):

```text
UnsupportedOperationException: Delete files are currently not supported in changelog scans
```

On the version we tried, the changelog cannot read a range of snapshots that has delete files, and our table has some now from merge-on-read. The incremental read of [lesson 12](/en/iceberg/streaming/) cannot be used either, because this range has snapshots that are not appends. So we choose a more direct way, which is to compare the table at `bookmark` with the table now, using time travel:

```python
old = spark.sql(f"SELECT order_id, amount FROM lab.db.orders VERSION AS OF {bookmark}")
new = spark.table("lab.db.orders")
```

The comparison gives: new rows 4 and 5, row 2 changed, nothing deleted, and the bad row 6 never appears (in the exercise we work it out from these two sets with Python dicts). This way reads both editions, so it costs more than reading only a difference. If the table is very large you may need a different design, for example a copy-on-write table, though we did not try whether the changelog works with one.

</Step>

## Maintenance: compact, then expire old snapshots but keep the tag

At the end we compact with `rewrite_data_files` in rewrite-all mode. 4 data files are rewritten as 3 files (one per partition that has data), and then we run `expire_snapshots` to keep only the latest snapshot:

```text
refs: main, month_end        the main table has 5 rows, total 562.0        month_end can still be read with 5 rows
```

The tag `month_end` lets that snapshot survive the removal, as we saw in the maintenance lesson. What the exercise found, and is interesting, is that after compaction **one delete file is left**, which points at a data file that is no longer in the current snapshot (we checked that the file name it refers to is not in the list of current data files). When we wrote this lesson the author understood that readers do not use this file and that it would go away by itself in a later maintenance round. We tried it afterwards and that is not true: a delete file like this does not go away by itself. You have to call `rewrite_data_files` again with `remove-dangling-deletes` set to `true`, which we show on the page [Copy-on-write and Merge-on-read in Depth](/en/iceberg/row-level/in-depth/). If you use merge-on-read, check this in your own real system as well.

In the end PyIceberg reads the table that went through all of this and gets all 5 rows with a total of 562.0, matching the Spark side.

</Step>
