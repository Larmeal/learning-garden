## Plan which files to open before reading

In [lesson 2](/en/iceberg/table-anatomy/#layer-3-the-manifest) we saw that a manifest keeps the min/max of each column per file, and in [lesson 3](/en/iceberg/schema-partitioning/#partition-transforms-and-hidden-partitioning) that partition values help skip files. In this lesson we measure how many files each one skips. The step where an engine decides which files to open is called **scan planning**, and it happens before a single data file is read (ran: `exercises/05_reads_scan_planning.py`).

The table has 8 data files in 4 days, 2 files a day, 5 rows each. `order_id` runs consecutively: the first file holds 1 to 5, the second 6 to 10 and so on up to 40, and the table is partitioned by the day of `ordered_at`. We built it with eight `INSERT`s, one file each, so there are also 8 manifests.

## How many files are skipped depends on the filter

We ask PyIceberg for `plan_files()`, which says which files it will open, with six kinds of condition:

```text
no filter                        8 of 8 files
one day (partition)              2 of 8 files
order_id = 7 (min/max)           1 of 8 files
order_id > 35 (min/max)          1 of 8 files
customer = 'cu1' (no help)       8 of 8 files
amount < 0 (nothing matches)     0 of 8 files
```

The condition on a day (on `ordered_at`) leaves 2 files because the partition value matches that day. `order_id = 7` leaves one file, the one with min 6 and max 10, and `order_id > 35` leaves the file whose max is above 35. So the min/max statistics of a column work even when the column is not a partition column, provided the data inside the files is ordered well enough. The condition `customer = 'cu1'` still has to open all 8 files, because `customer` is spread over every file (`cu0`, `cu1`, `cu2` in turn), so every file's min/max range covers `cu1`. Finally, a condition that no row matches, such as `amount < 0`, gives 0 files, because the min of `amount` in every file is above 0.

The lesson from this table is that how well statistics skip files depends on how the data is laid out in the files. If the values of the filter column are mixed into every file, statistics can do nothing. That is one reason there is a way to re-sort data in the maintenance lesson (this is the author's conclusion from the example above).

</Step>

## Whole manifests can be skipped too

Before the file level, an engine can skip manifests. Each row of the manifest list has `partition_summaries`, the range of partition values of all files in that manifest. From `t.inspect.manifests()` the exercise shows that the first manifest has the day range `2026-01-04` to `2026-01-04`, the same at both ends. When we ask for 2 January, only 2 of the 8 manifests have a range that covers that day, and the other 6 can be skipped without being opened (we worked this out from the ranges in `partition_summaries`, and did not measure how many manifests an engine really opens).

The whole sequence has a class of its own in the Iceberg source. From the class names we found, it starts by filtering manifests with `ManifestEvaluator`, using the partition ranges in the manifest list. Then it opens the remaining manifests and filters the files with the partition values and `InclusiveMetricsEvaluator`, which looks at the min/max statistics. And when it reads a file, the condition the file could not settle by itself (`ResidualEvaluator` computes that part) is applied again to the rows, so every returned row matches the condition. The exercise confirms the end of that chain: `order_id = 7` returns exactly one row. We did not read the code of each class.

</Step>

## Spark uses the same mechanism

When we run `SELECT * FROM lab.db.orders WHERE order_id = 7`, the Spark plan has a `BatchScan` node showing the filter that was pushed down to Iceberg:

```text
BatchScan lab.db.orders[order_id, customer, amount, ordered_at]
  IcebergScan(table=lab.db.orders, schemaId=0, snapshotId=6689959274796224701, branch=null, filters=order_id IS NOT NULL, order_id = 7 ...
```

You can see the `snapshotId` the scan is bound to. That suggests one query reads from one snapshot throughout, so even if someone commits while the query is still running, the results do not mix (we infer this from the `snapshotId` in the plan and from the principle that files are never edited. We did not try committing in the middle of a job). Choosing only some columns works as well: with `selected_fields=("order_id",)` PyIceberg returns an Arrow table with one column and 40 rows.

</Step>

## Looking at the table from the inside

We use these tools about as often as a normal `SELECT`. Spark gives metadata tables after the table name, and PyIceberg gives `table.inspect`:

| What you want to know | Spark | PyIceberg |
|---|---|---|
| Commit history | `lab.db.orders.snapshots` | `t.inspect.snapshots()` |
| Data files and statistics | `lab.db.orders.files` | `t.inspect.files()` |
| List of manifests | `lab.db.orders.manifests` | `t.inspect.manifests()` |
| Summary per partition | `lab.db.orders.partitions` | `t.inspect.partitions()` |

The exercise checks that both sides see the same files (8 files, 40 rows in total), and the `.partitions` table says 4 days with 10 rows in 2 files each. If you want readable statistics, Spark has the column `readable_metrics` in `.files`:

```text
order_id  lower_bound  upper_bound
1  5   |  6  10   |  11 15   |  16 20   |  21 25   |  26 30   |  31 35   |  36 40
```

which matches the ranges we designed in the first step. An Iceberg data file is plain Parquet. The exercise opened one directly with `pyarrow` and got 5 rows. PyIceberg also hands results to Pandas with `to_pandas()` (the exercise filters `order_id <= 5` and gets 1 to 5).

<Callout type="note" title="The Java and Python sides do not have the same tools">
`readable_metrics` belongs to Spark. PyIceberg exposes the same statistics through `inspect.files()`, but as bytes you must decode yourself. In this lesson we use the easiest to read on each side.
</Callout>

</Step>
