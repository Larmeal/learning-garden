## Files are never edited, so how do you delete a row

Iceberg data files are written once and never edited again ([lesson 2](/en/iceberg/table-anatomy/#layer-1-metadatajson-and-the-snapshot)). So when we run `DELETE FROM orders WHERE id = 3`, which has to make one row disappear, what does Iceberg do? There are two ways, and they differ in whether you pay at write time or at read time.

In the book picture, the first way is to reprint the whole page without the unwanted line and swap the table of contents to point at the new page. We call it **copy-on-write**. The second is to stick a note on the page that says "skip line 3 of this page", without touching the original page. Whoever reads has to look at the note too. We call it **merge-on-read**, and the note is a **delete file** (ran: `exercises/06_row_level.py`).

</Step>

<Step>

## Copy-on-write rewrites the whole file

The default for `DELETE`, `UPDATE` and `MERGE` in Iceberg is copy-on-write (source: `TableProperties.java`, the value `DELETE_MODE_DEFAULT` and its siblings. A new table created by Spark does not store this in its table properties, and the exercise checked that the result is empty). We create a table with 10 rows in 1 file and delete `id = 3`:

```python
spark.sql("DELETE FROM lab.db.cow WHERE id = 3")
```

```text
operation = overwrite
added-data-files: 1   deleted-data-files: 1   total-data-files: 1   total-delete-files: 0   total-records: 9
```

In the new snapshot, `deleted-data-files: 1` removes the original 10-row file from the table, and `added-data-files: 1` adds a new file with 9 rows instead. The benefit is that reading is fast afterwards, with nothing more to merge. The cost is that if you delete just one row from a large file, the whole large file is written again, which is the price of copy-on-write (this is the author's conclusion from the example, and our example is too small to time).

The old 10-row file is still on disk, and is still part of earlier snapshots (which is what makes time travel possible in the time travel lesson). Once no snapshot refers to it, table maintenance removes it.

</Step>

<Step>

## Merge-on-read writes a note saying which row to skip

If we set `'write.delete.mode' = 'merge-on-read'` (and the same for `update` and `merge`), what happens when we delete `id = 3` from a table with the same data?

```text
operation = delete
added-delete-files: 1   added-position-deletes: 1
total-data-files: 1     total-delete-files: 1       total-records: 10
```

No new data file. The original file is as it was (`total-records` is still 10), but there is one more **delete file**. The `.files` table tells them apart by the column `content`: `0` is a data file and `1` is a position delete (`2` is an equality delete, which this exercise does not create). The exercise found `[(0, 'PARQUET', 1), (1, 'PARQUET', 1)]`. When we read the table, Spark counts 9 rows because it takes the delete file off. If you open the `.position_deletes` table you see the note itself:

```text
position_deletes table: [(2, '00000-8-a81a...')]      pos = 2 in that data file
```

A **position delete** file records "which data file, which position". `id = 3` is the third row, so its position (counting from 0) is 2. This is the price of merge-on-read: every time the table is read, the engine has to read the notes and skip rows accordingly.

</Step>

## UPDATE and MERGE in merge-on-read

`UPDATE` is deleting the old row and writing a new one. In merge-on-read mode we therefore get both a delete file and a new data file in one go:

```python
spark.sql("UPDATE lab.db.mor2 SET v = 999 WHERE id = 5")
```

```text
operation = overwrite
added-data-files: 1   added-delete-files: 1   added-position-deletes: 2   total-data-files: 2   total-delete-files: 1
```

The new data file holds the row that was changed. The notes now cover 2 positions (the position of the `id = 3` we deleted earlier and the one of `id = 5`), but still in a single delete file, because Spark puts the notes for the same data file together. The number comes from `total-delete-files: 1` (the author infers that the old file was replaced by the combined one, and did not check that the old delete file was really removed).

`MERGE INTO` does both the update and the insert in one commit:

```python
spark.sql("""MERGE INTO lab.db.mor2 t USING (SELECT 5L AS id, 'even' AS grp, 5000L AS v UNION ALL SELECT 77L, 'odd', 770L) s
             ON t.id = s.id WHEN MATCHED THEN UPDATE SET v = s.v WHEN NOT MATCHED THEN INSERT *""")
```

The result is that `id = 5` becomes 5000 and a new `id = 77` appears, in a single snapshot (`operation = overwrite`). PyIceberg reads this table and sees the same as Spark although delete files exist (no `id = 3`, with `id = 5` and `id = 77`).

</Step>

## Format version 3: deletion vectors

A table declared with `'format-version' = '3'` stores the notes in a new form called a **deletion vector**, a bitmap of which rows of the data file are deleted, kept in a Puffin file instead of Parquet. We delete two rows:

```text
operation = delete
added-delete-files: 1   added-position-deletes: 2   added-dvs: 1
files of the v3 table: [(0, 'PARQUET', 1), (1, 'PUFFIN', 1)]
```

The delete file is a `PUFFIN` file and the summary has `added-dvs: 1`. There is no Parquet position delete file at all. Spark counts 8 rows, and PyIceberg 0.12.0 reads this table as 8 rows too. So on the versions we tried, deletion vectors work on both sides. What we did not try is other engines or versions, and the inside of Puffin.

<Callout type="note" title="If you will use format version 3">
Every engine that touches the table must support version 3. We only tried Spark 4.1.3, Iceberg 1.12.0 and PyIceberg 0.12.0. If there are older readers in your system, test before upgrading a table (this warning is the author's and was not tried with other engines).
</Callout>

</Step>

## A delete that covers whole files writes nothing

If the condition of a `DELETE` matches whole partitions, Iceberg does not need to write a new file or a delete file at all. It just takes the files off the list.

```python
# a table partitioned by the day d
spark.sql("DELETE FROM lab.db.byday WHERE d = DATE'2026-01-01'")
```

```text
operation = delete      deleted-data-files: 1      total-records: 1
```

There is no `added-data-files` or `added-delete-files`. Only metadata changed. So if your data is deleted by date range (for example you only keep 90 days), partitioning by day makes the delete cheap and fast.

</Step>

<Step>

## The PyIceberg side

PyIceberg deletes and upserts too, but not the way Spark does in merge-on-read:

```python
tc.delete("id = 4")
tc.upsert(arrow_table, join_cols=["id"])
```

`delete("id = 4")` on our table gives `operation = overwrite` with `added-data-files: 1` and `deleted-data-files: 1`, like Spark's copy-on-write: a new file without that row is written (we tried it on a table where the row sat in a file with other rows). The `upsert` we sent had 2 rows (one matching an existing `id = 1` and one new `id = 100`) and answered:

```text
UpsertResult(rows_updated=1, rows_inserted=1)
```

But in `.snapshots` we see that it committed **three times** (newest first): `append`, `append`, `overwrite`. The author reads this as: write a new file in place of the changed row, then add the changed row and the new row. The table ends with the correct data (one row per `id`, 9 rows in all), but a reader who opens the table in the middle may see an in-between state. Know this before using PyIceberg's `upsert` on a table with concurrent readers.

</Step>
