## A branch is one small file

People new to Git often think a branch copies the whole project to another place, so they worry about the cost. Let us look inside first to see what it really is (ran: `exercises/03_branches.py`).

```text
$ cat .git/refs/heads/main
e819934ad96cbaa6ec0215c7eba4450e0c82f64a

$ cat .git/HEAD
ref: refs/heads/main
```

The branch `main` is a file called `main` in the folder `.git/refs/heads`. Inside is only the full 40-character name of the latest commit and a newline, 41 bytes in all (book: VCWG chapter 3, page 61). The `HEAD` file does not hold the name of a commit. It holds the name of the branch we are on, `refs/heads/main`.

Seen like this, making a new branch is not scary.

```text
$ git branch feature
$ git branch
  feature
* main
```

The command only creates another file, `feature`, with the same commit name as `main`. No new object is made, and the files in our folder do not move. The star `*` says we are still on `main` (ran).

</Step>

<Step>

## A commit moves only the branch we are on

Let us switch to `feature` and commit one new file, and see what changes.

```text
$ git switch feature
$ cat .git/HEAD
ref: refs/heads/feature

# edit a file, then git add and git commit give a new commit, c3

$ git rev-parse feature        # moved to c3
$ git rev-parse main           # still where it was
```

**First**, `git switch` rewrites `HEAD` to point at `feature`. **Then**, `git commit` makes a commit and moves the branch file that `HEAD` points at, which is `feature`, to the new commit. `main` is not touched. That is what "branching off" means: both lines share the old history up to the split point, but the tip of each goes its own way.

The files in our folder change with it. The file the new commit added is there while we are on `feature`, disappears the moment we switch back to `main`, and comes back when we switch to `feature` again (ran), because `git switch` changes the working tree to match the snapshot at the tip of the branch we choose.

</Step>

## Switching when there is unfinished work

If we edited a file and have not committed, what happens when we switch branches? Git decides by whether that file differs between the two branches.

If we make a new branch with `git switch -c` while we have unfinished work, the work comes along, because the new branch points at the same commit and nothing needs to be overwritten (ran). But if we switch to a branch where that same file differs from the one we are on, Git refuses.

```text
$ git switch wip
error: Your local changes to the following files would be overwritten by checkout:
	app.txt
Please commit your changes or stash them before you switch branches.
Aborting
```

Git refuses because the switch would overwrite work that is not saved anywhere. We can commit first, or put it aside with `git stash`, which we will talk about in the lesson on getting work back.

</Step>

## A detached HEAD is a HEAD that points straight at a commit

We can run `git switch --detach` to any commit, and see how `HEAD` changes (book: VCWG chapter 3, page 74, and LG chapter 5, page 80).

```text
$ git switch --detach <name of c1>
$ cat .git/HEAD
<the full 40-character name of c1>

$ git branch
* (HEAD detached at <short name of c1>)
  main
```

This time the `HEAD` file does not point at a branch. It holds the name of a commit directly. If we commit from here, no branch follows the new commit. After we switch back to `main`, no name points at it any more (ran: `git branch --contains` gives nothing). To keep it, make a branch from the commit name before we forget it.

```text
$ git branch rescue <name of c5>
$ git branch --contains <name of c5>
  rescue
```

<Callout type="tip" title="Why this mode exists">

A detached HEAD is not a mistake. It is the way to go and look at an old snapshot without moving any branch. It is good for looking at what the code was like, or for trying something and throwing it away.

</Callout>

</Step>

<Step>

## Deleting a branch deletes the name, not the commits

```text
$ git branch -d feature
error: the branch 'feature' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feature'

$ git branch -D feature
```

`-d` refuses because `feature` has commits that are in no other branch, so after deleting there would be no name pointing at them. `-D` deletes without asking. After that the file `.git/refs/heads/feature` is gone, but commit `c3` that it pointed at is still in `.git/objects` (ran: `git cat-file -t` still says `commit`). We can only get that commit back if we still know its name, and the lesson on getting work back shows how to find the name again (for deleting branches, book: VCWG chapter 3, page 76).

Once the branch has been merged, `-d` deletes it without complaint, because all its commits are kept somewhere else.

</Step>
