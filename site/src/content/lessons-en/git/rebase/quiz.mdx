## Check yourself

<Question
  client:visible
  lang="en"
  q="A rebase can make the history a straight line while a merge cannot. Why?"
  options={['Rebase deletes the commits of Main that are in the way', 'Rebase replays our commits after the tip of the other line, so there is no commit with two parents', 'Rebase squashes all the commits into one']}
  answer={1}
  why="Rebase moves the base of the branch and replays the changes one by one, so we get a single line with no joining point. The exercise checks that after a rebase no commit has two parents and Main did not move at all. Squashing commits into one is what squash or fixup does, not an ordinary rebase."

<Question

  lang="en"
  q="We rebased and changed our mind. Can we go back to how it was before?"
  options={['No, the old commits were deleted', 'Yes, the old commits are still there, and Git noted the old position in Orig Head and in the reflog', 'Yes, but only by cloning the whole repository again']}
  answer={1}
  why="A rebase does not delete the old commits. It only leaves no branch pointing at them. The exercise checks that Orig Head holds the old tip, the old commit can still be read, and a hard reset to Orig Head brings back exactly what was there."

</Step>

<Step kind="question">

<Question
  client:visible
  lang="en"
  q="During a rebase that hits a conflict, whose side is Head in the file?"
  options={['Our own commit that is being replayed', 'The target branch we are rebasing onto', 'The common ancestor']}
  answer={1}
  why="During a rebase Git first moves us onto the target and then replays our commits one by one, so Head is the target and the other side is our commit being replayed. That is the opposite of a merge, where Head is ours. The exercise confirms it from a real file."
/>

</Step>
