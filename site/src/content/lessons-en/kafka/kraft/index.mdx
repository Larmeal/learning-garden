## Who knows which partition is on which broker

In [lesson 6](/en/kafka/replication/) we saw the leader, ISR and replicas of each partition change all the time as brokers come and go. The question is where that information is kept, and who decides that a given broker leads a given partition. The answer is the controller, a broker (or a special node) that looks after the state of the whole cluster, for example by choosing leaders when a broker disappears (book: Kafka: The Definitive Guide, section The Controller, page 136).

Older Kafka kept this information in a separate ZooKeeper. Newer Kafka keeps it itself, with a system called KRaft (Kafka plus Raft, an algorithm that elects a leader by majority vote). The book presents it as a project started in 2019 that is now ready to use, and the Kafka 4.4.0 that we use does not use ZooKeeper at all (book: Kafka: The Definitive Guide, section KRaft, page 137). Let us see what this cluster data looks like.

</Step>

## The data of the cluster is a log

We ask the quorum who leads it, with `kafka-metadata-quorum.sh describe --status` (the cluster has three nodes that are both broker and controller).

```text
LeaderId:       1
LeaderEpoch:    1
HighWatermark:  28
CurrentVoters:  [{"id": 1 ...}, {"id": 2 ...}, {"id": 3 ...}]
```

The words from the last lesson come back. The high watermark is a number in a log, and that log is a folder called `__cluster_metadata-0` in the data folder of each node. It holds `.log` and `.index` files just like an ordinary partition, and we can open it with `kafka-dump-log.sh --cluster-metadata-decoder`. Right after the cluster had started, the log held a little over thirty records, for example 3 `REGISTER_BROKER_RECORD` (brokers registering) and `FEATURE_LEVEL_RECORD`, which says which version of features the cluster has. It also holds `NO_OP_RECORD` records that the leader keeps appending every half second (ran).

Then we create a topic `orders` with 2 partitions and look at the log again.

```text
offset 39  TOPIC_RECORD      {"name":"orders","topicId": ...}
offset 40  PARTITION_RECORD  {"partitionId":0, ...}
offset 41  PARTITION_RECORD  {"partitionId":1, ...}
```

Creating a topic is nothing mysterious: it just appends three records to the end of a log (ran), and the other nodes copy them until they are the same. If we kill a broker the log gets new records too, a `BROKER_REGISTRATION_CHANGE_RECORD` (the broker is fenced) and `PARTITION_CHANGE_RECORD` for the partitions that it led or sat in the ISR of (ran). Every change of the cluster is a record in this log, and the current state of the cluster is what we get by replaying that log from the start, which is the same idea as the commit log we opened this path with.

</Step>

## The quorum leader, and a majority

The three controllers do not write the log together. One of them is the leader and the only one that appends to the log, and the other two are followers that copy it. If the leader fails, the followers must elect a new one, and every election has a round number called an epoch (the book says the controller uses an epoch to prevent a split brain in which two nodes each believe they are the controller: book: Kafka: The Definitive Guide, section The Controller, page 136). Let us kill the leader of the quorum with SIGKILL.

```text
killed node 1 (epoch 1); after 19.1 s the leader is node 3 in epoch 2
```

The epoch went from 1 to 2 and node 3 became the leader in that round. The two that were left could still create a new topic as usual (ran). The 19.1 seconds includes the delay of polling through `docker exec`, and in another run the epoch went up to 4. We did not check why, so all we can conclude is that the epoch rises and there is a new leader within some tens of seconds.

What matters more is what happens when we kill a second node and one controller out of three is left. We asked for a new topic and the command hung until it timed out (`createTopics ... timed out`) without succeeding (ran). Raft needs a majority, which is 2 of 3, before there can be a leader and the log can be appended to. Play with the lab below: stop controllers one at a time and press create topic.

<Callout type="warn" title="Nodes that are both broker and controller">
In a cluster where every node does both jobs, losing two nodes also loses the quorum, so even `kafka-topics.sh --describe` hangs. We met this while building the exercise of [lesson 6](/en/kafka/replication/), which is why that exercise uses one separate controller, so that brokers can be killed while the quorum survives. In real work a big cluster usually runs three dedicated controllers, while a small one may put both roles on the same computer to save money, but then it has to accept this trade-off.
</Callout>

## How a node knows itself

In the data folder of a node there is a file `meta.properties` that holds the id of the cluster (`cluster.id`), the number of the node (`node.id`) and a `directory.id` for the folder. These let a node refuse to join the wrong cluster or run on a folder that is not its own (ran). The metadata log folder also holds a file `quorum-state` with the latest leader and epoch, and `.snapshot` files that cut a picture of the state so that a new node does not have to replay the whole log. The command `kafka-features.sh describe` tells the version of the metadata in use, which in the exercise was `4.4-IV2` (ran).
