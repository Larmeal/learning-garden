## A producer sends in chunks, not one by one

When we call `produce()` we feel that we send one record at a time, but in fact the producer keeps records in memory first and groups those that go to the same partition into a batch, which it then sends in a single request. The benefit is that the network and the broker's disk work much better with big chunks than with many small pieces.

We can look at those chunks in the broker's own log file. The command `kafka-dump-log.sh` prints one line per batch:

```text
baseOffset: 0 lastOffset: 20 count: 21 baseSequence: -1 lastSequence: -1 producerId: -1 producerEpoch: -1
partitionLeaderEpoch: 0 isTransactional: false isControl: false position: 0 CreateTime: 1795188576548
size: 1969 magic: 2 compresscodec: none crc: 2213403328 isvalid: true
```

This line says that the batch holds 21 records, from offset 0 to 20, takes 1,969 bytes and is not compressed (`compresscodec: none`). The `producerId` and `baseSequence` of -1 have to do with idempotence, which we come back to at the end of the lesson (ran).

</Step>

## linger.ms: willing to wait for a bigger chunk

When does the producer decide that it is time to send a batch? There are two conditions. If the batch is full according to `batch.size`, it goes out at once. Or if the time that the first record has waited reaches `linger.ms`, it goes out as well. The Java producer defaults to `linger.ms=5` and `batch.size=16384` bytes (source: `ProducerConfig.java` of 4.4.0, lines 440 and 445). The book says `linger.ms` is the time the producer waits for more records before sending a batch (book: Kafka: The Definitive Guide, section Message Delivery Time, page 56).

We experiment by sending 600 orders, one every 2 milliseconds, like a service that sends an order each time a customer taps buy, and counting the batches that end up in the log.

| Setting | Batches in the log | Biggest batch | File size |
|---|---|---|---|
| `linger.ms=0` | 594 | 7 records | 90,592 bytes |
| `linger.ms=50` | 29 | 22 records | 56,127 bytes |

With `linger.ms=0` almost every record is a batch of its own. With 50 milliseconds the producer waits and packs about 20 records per batch, so there are almost twenty times fewer requests, and the file is smaller because the header of a batch is paid fewer times (ran). The price is that the first record of each batch has to wait longer. Press the buttons in the lab, and also change how often a record arrives: notice that when records arrive far apart, waiting buys nothing.

## Compress the whole batch

A producer can compress data with the option `compression.type`, and it compresses per batch, so a bigger batch compresses better. The broker stores a compressed batch as it is and passes it on to consumers without opening it. We sent 3,000 orders that look like real JSON (customer, item, quantity and price chosen at random) to one topic per codec and measured the size of the log file.

| Codec | Log size (approx.) | Compared with none |
|---|---|---|
| `none` | 275 KB | 100% |
| `gzip` | 42 KB | 15% |
| `zstd` | 48 KB | 17% |
| `snappy` | 77 KB | 28% |
| `lz4` | 79 KB | 29% |

The codec in use shows in the line of a batch (`compresscodec: gzip`). Every codec is smaller than no compression, and `gzip` and `zstd` leave less than half (ran). The numbers depend on the data: orders that repeat field names compress very well, while encrypted data or random binary compresses little. Each run also moves the numbers a little, because batches are not split the same way every time.

</Step>

## acks: when does the broker answer

After sending a batch the producer learns that it worked when the broker answers. The `acks` setting says when the broker should answer (book: Kafka: The Definitive Guide, section Message Delivery Time, page 55). With `acks=0` the producer sends and does not wait. With `acks=1` the leader answers as soon as it has written to its own log. With `acks=all` the leader answers after every replica in the ISR has the record. The Java producer defaults to `all` (source: `ProducerConfig.java`, line 430).

The result of sending one record with the three settings:

```text
acks=0   -> offset None
acks=1   -> offset 1
acks=all -> offset 2
```

`acks=0` brings no offset back, because the producer does not wait for the broker. The other two bring the position of the record back (ran). The difference between `1` and `all` shows when a leader crashes. Try the lab below: choose `acks` and the moment the leader crashes, then press next one step at a time. The words ISR and follower get a closer look in [lesson 6](/en/kafka/replication/).

## Idempotence: a stamp on every batch

If a producer sends a batch and gets no answer (a slow network, or a broker that did not answer in time), it sends again, and that can make a record get written twice. If we turn on `enable.idempotence`, the producer asks the broker for a `producerId` and numbers every record with a sequence number, so the broker can tell whether it has seen this batch before (book: Kafka: The Definitive Guide, section Idempotent Producer, page 182). We can see the stamp in the log:

```text
librdkafka default: producerId=-1 baseSequence=-1
enable.idempotence: producerId=0 producerEpoch=0 baseSequence=0 lastSequence=9
```

The 10 records sent with idempotence on carry sequence numbers 0 to 9 on the batch (ran). The defaults differ between libraries. The Java producer has it on already (source: `ProducerConfig.java`, line 574), but librdkafka had it off in the version we use, so with Python we must switch it on ourselves. How the broker uses this stamp to get rid of duplicates is the topic of [lesson 8](/en/kafka/delivery/).

<Callout type="note" title="A record that is too big">
The producer refuses a record above the limit before sending it. When we tried a record of 2 MB, `produce()` raised `MSG_SIZE_TOO_LARGE` at once and nothing went onto the network (ran). The biggest size that the broker accepts is another setting (`message.max.bytes`), and the two have to be set to fit each other.
</Callout>
