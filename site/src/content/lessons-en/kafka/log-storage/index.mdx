## A partition is a folder of segment files

In [lesson 1](/en/kafka/what-is-kafka/) we saw a single `.log` file in a partition. But if a partition keeps data for ever, one file grows without limit and deleting old data is awkward. So Kafka cuts the log of each partition into pieces called segments, and appends only to the newest one, the active segment. When a segment is full it is closed and a new file is opened (book: Kafka: The Definitive Guide, section Physical Storage, page 149).

Let us create a topic with very small segments so that we can see the cutting, and send 60 records one by one.

<Callout type="note" title="Segments this small need a special setting">
Kafka 4.x requires `segment.bytes` to be at least 1 MiB (read from `LogConfig.java` of the 4.4.0 source). We do not want to send megabytes of data just to see a segment roll, so we use `internal.segment.bytes`, a setting that Kafka itself keeps for tests and that can go lower. In the exercise it was 2,048 bytes. It should not be used in real work.
</Callout>

```text
00000000000000000000.log        00000000000000000026.log        00000000000000000052.log
00000000000000000013.log        00000000000000000039.log        leader-epoch-checkpoint
(and the .index and .timeindex of each)                          partition.metadata
```

The name of each file is the offset of the first record in it. We have five segments, starting at offsets 0, 13, 26, 39 and 52. The first four are 2,028 bytes each (a batch of 156 bytes per record, times 13), and the last is the active segment at 1,248 bytes (ran). A file stays under 2,048 because a batch that would not fit starts a new file instead.

</Step>

## Open a file, and find an offset

We open the segment that starts at offset 26 with `kafka-dump-log.sh`:

```text
baseOffset: 26 lastOffset: 26 count: 1 ... position: 0   ...
baseOffset: 27 lastOffset: 27 count: 1 ... position: 156 ...
baseOffset: 28 lastOffset: 28 count: 1 ... position: 312 ...
```

The first line of the file starts at offset 26, matching the file name, and `position` is the byte where that batch starts in the file (ran). Now when a consumer asks for offset 30, how does the broker find it? Reading batch by batch from the top of the file would be slow, so Kafka has an `.index` file that does not list every record but only some, at intervals of `index.interval.bytes` (we set 512). The book says an index lets Kafka find the position of an offset quickly (book: Kafka: The Definitive Guide, section Indexes, page 155). The index of segment 26 has just three entries:

```text
offset 30 -> byte 624
offset 34 -> byte 1248
offset 38 -> byte 1872
```

Finding offset 30 therefore takes three moves. **The first step** picks the file with the biggest name that is not above 30, which is file 26. **The next step** opens its index and picks the entry that is the biggest not above 30, which gives byte 624. **The last step** jumps to that byte and reads on batch by batch until the record is found, which here is at once. Slide the slider in the lab to see how each offset goes through these three moves.

## Retention deletes whole files

Kafka does not keep records for ever. We can set how many days to keep them (`retention.ms`) or how many bytes (`retention.bytes`), but what is deleted is a whole segment, not single records, and a segment is deleted when the newest record in that file is older than the limit. Let us see the real result.

First we waited until all five segments were old, then sent 5 new records into the active segment, and then set `retention.ms=15000`.

```text
segments before   [0, 13, 26, 39, 52]
segments after    [52]
log start offset 52, log end offset 65
```

The four files whose records were all old are gone. File 52 stays, because it has new records mixed in. An interesting consequence: the 8 records that were written at the beginning (offsets 52 to 59) can still be read, although they are older than the limit, because their file still has newer neighbours. The end offset of the topic is still 65, so offsets are never reused, and a new group that starts at the beginning of the log gets records from offset 52, not 0 (ran).

What if every record is old? The exercise kept waiting until the new records were older than 15 seconds too, and got a single segment named `00000000000000000065.log` of 0 bytes. Everything was deleted, including the old active segment, and the broker created a new empty file named after the next offset (ran). In the source there is a comment in `UnifiedLog.deleteSegments`: "we must always have at least one segment, so if we are going to delete all the segments, create a new one first" (source).

</Step>

## Compaction: keep the latest value of each key

For some topics all we care about is "the latest state of each key", for example customer profiles. We set `cleanup.policy=compact`, and Kafka no longer deletes by time. Instead a log cleaner removes old records of a key that has a newer value (book: Kafka: The Definitive Guide, section How Compaction Works, page 156). We sent `k1` to `k4` for twelve rounds (48 records), then a tombstone, a record whose value is `null`, for `k3`, followed by 40 other records so that the segment closed.

Press through the three moments in the lab to see what the cleaner keeps.

<CompactionLab client:visible lang="en" />

After the cleaner ran, what remained was the latest value of `k1`, `k2` and `k4` at offsets 44, 45 and 47. The offsets were not renumbered, so there are gaps between them. Of `k3` only the tombstone at offset 48 remained, and all twelve old values were gone (ran). A while after `delete.retention.ms` had passed the cleaner swept that tombstone too, and `k3` left no trace at all. In our run that took about another 13 seconds (ran). To see the "before" we set `min.compaction.lag.ms` to one hour first, because otherwise the cleaner works so fast that we cannot catch it, and then set it back to 0.
