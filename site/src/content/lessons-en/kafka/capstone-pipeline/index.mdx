## The task: lose nothing, count nothing twice

Our online shop receives orders all the time, and the accounting system has to record every order in a table exactly once. We have studied 11 lessons, so now we put everything together and then break it one piece at a time to see whether it survives. The structure is this.

On the sending side the producer turns idempotence on, sets `acks=all`, and uses the customer id as the key (with the partitioner set to `murmur2_random` to match Java, as we learned in [lesson 2](/en/kafka/topics-partitions/)). It sends 600 orders from 8 customers. In the cluster the topic `orders` has 6 partitions, 3 copies and `min.insync.replicas=2`, as seen in [lesson 6](/en/kafka/replication/). On the receiving side the group `ledger` has 3 workers. Each reads an order and writes it into a table whose primary key is `order_id` with `INSERT OR IGNORE`, and only then commits the offset, every 40 records. That is committing after processing, as recommended in [lesson 4](/en/kafka/consumer-groups/).

</Step>

<Step>

## Play it one event at a time

The run has three events. We send the first wave of 200 orders. Then worker `w2` crashes suddenly with 10 orders that it read and wrote but has not committed, and we send a second wave of 200. After that we kill the broker that leads partition 0 with SIGKILL while the last 200 orders are being sent, and start a new worker `w4` to replace the one that was lost. ## The result, and what saved us

At the end the table holds exactly 600 orders, from `o-0000` to `o-0599`, with none missing (ran). The producer got an ack for every order without a single error, although a broker was killed on the way, and the lag of the group is 0. Each outcome has a mechanism behind it.

**Nothing is missing** because the producer uses `acks=all` with `min.insync.replicas=2`, so every order that got an ack is on at least two copies, and when a broker dies another copy still exists. Idempotence means the retries while waiting for a new leader do not duplicate orders in the log ([lesson 6](/en/kafka/replication/) and [lesson 8](/en/kafka/delivery/)).

**Nothing is counted twice**, even though the workers received more than 600 deliveries in total (610 in one run and 650 in another). The reason is that `w2` read and wrote but had not committed, so the bookmark stayed where it was, and the workers that took over read those orders again. The table, with its primary key, rejected the duplicate rows with `INSERT OR IGNORE`, so the rows stayed at 600 (ran). We did not check why the number of repeats goes beyond the 10 orders of `w2`. We personally think it probably comes from a rebalance when the broker died, but we did not verify it.

**The order of each customer is kept** because the orders of one customer share one key and so one partition, and when we sort the table rows by (partition, offset), the order numbers of every customer go up (ran).

</Step>

<Step>

## What we found, and what we have not done

The first thing we saw is that the 8 customers spread over only 4 of the 6 partitions. The number of records per partition was `{0: 0, 1: 150, 2: 75, 3: 150, 4: 0, 5: 225}` (ran). Partitions 0 and 4 are empty, and the worker that got partition 5 works almost twice as hard as the others, because a hash of the key does not promise an even spread, as we saw in [lesson 2](/en/kafka/topics-partitions/). When there are few keys compared with partitions, a result like this is normal.

And here is what we have not done. The pipeline uses a SQLite table in the same process as its destination, while real work usually has a database outside the process that can be slow or fail. The workers, the brokers and Docker all sit on one computer, so we did not try a network that is cut or slow. We did not switch on TLS or SASL, as mentioned in [lesson 11](/en/kafka/operations/), and we did not write anything that watches metrics or raises an alarm when the lag is high. All of that is left to the person who will take this pipeline into real use.
