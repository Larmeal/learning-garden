## Open Python and ask about one million orders

Let us start with the real thing. Say we have an `orders` table with one million orders. It has `order_id`, `customer_id`, `qty`, `unit_price`, `status` and `order_ts`. The exercises of this path build the table with DuckDB itself, so the numbers are the same on every run. All of the data is synthetic.

```python
import duckdb

con = duckdb.connect()                      # a database in memory
# ... create the orders table with one million rows (see ddb.py)
con.sql("select status, count(*) from orders group by status order by status").fetchall()
```

```text
status     orders  revenue
---------  ------  -----------
cancelled  70156   10026036.39
paid       699821  99866243.04
refunded   30104   4284700.24
shipped    199919  28559172.37
```

`duckdb.connect()` opens one database, and with no file name it lives in memory. `con.sql(...)` sends the SQL, and `.fetchall()` brings the result back as a list of tuples. Notice what did not happen. We installed no server, set no password and wrote no host or port anywhere (ran).

</Step>

<Step>

## DuckDB lives inside our process

So where is the program that answers us? Let us check. Before we build the table we note how many child processes this Python has, how many ports it listens on, and how much memory it uses. Then we build one million rows and measure again. On this computer we get:

| What we measured | Before the table | After the table |
|---|---|---|
| Child processes | 0 | 0 |
| Listening ports | none | none |
| Memory of this Python process | (starting value) | grew by about 84 MB |

There is no new process and no new port, yet the memory of the Python process itself grew. DuckDB is a library that was loaded into our process (ran). The book calls this an embedded database: one that runs inside another process, such as our application or notebook, and is not reached over a network (book: DuckDB in Action section 1.1, page 2).

To picture it, think of a database like PostgreSQL as a restaurant we have to phone. The order travels to the restaurant, the kitchen cooks, and a courier brings the food back. DuckDB is a small kitchen in our own house, and we open the fridge ourselves with nobody travelling. Press through the lab below and compare, step by step, how many times the data is copied.

## A database is one file

To store a DuckDB database on disk we give `connect` a file name. This example keeps 100,000 orders and the customer table in a file called `shop.duckdb`.

```python
con = duckdb.connect("shop.duckdb")
# ... create the tables ...
con.close()
```

After closing the connection and looking in the folder, we see one file, `shop.duckdb`, of 1,323,008 bytes. There is no log file or config file beside it (ran). Opening it again with `duckdb.connect("shop.duckdb", access_mode="read_only")` finds all 100,000 orders. We can copy the file to a friend or upload it to the cloud like any other file, which is unlike PostgreSQL, where the data sits in many files inside the folder of the server.

How the file is laid out inside is the subject of the lesson [How the data is stored](/en/duckdb/storage/).

</Step>

## Against SQLite on a summary query

SQLite is also a database inside the process, and it also keeps one file. Python ships it as the `sqlite3` module. So we gave both engines the same question over the same one million rows.

```sql
select status, count(*), round(sum(qty * unit_price), 2)
from orders group by status order by status
```

Both returned the same four rows, the same counts, and the same revenue to the cent (ran). They differ in time. In one run on this computer DuckDB took about 22 ms and SQLite about 1,477 ms. The times are not asserted because they depend on the computer, and the SQLite in this test had no index, just as the DuckDB table had none.

The reason for such a gap is not anybody's skill. SQLite stores data row by row, which suits reading or changing one whole row. DuckDB stores data column by column and processes groups of rows at a time, which suits a question that reads many rows but uses few columns. We open both ideas in the lessons [How the data is stored](/en/duckdb/storage/) and [How a query runs](/en/duckdb/execution/).

The book sums it up: use DuckDB for analysis that can be written in SQL, on data that already exists (not data that keeps flowing in), up to a few hundred GB (book: DuckDB in Action section 1.3, page 4).

</Step>

<Step>

## What DuckDB does not like

Picture a web shop where every customer click inserts one row. We imitate that by inserting 2,000 rows with one statement each, against sending all 2,000 rows at once with `executemany`. On this computer:

| Method | Time |
|---|---|
| 2,000 separate `INSERT` statements | about 9,253 ms |
| `executemany` with 2,000 rows | about 749 ms |

The rows are the same, and the gap is more than ten times (ran). Each statement has to be parsed, planned and committed on its own, which DuckDB was not built for. The book says plainly that DuckDB has limited support for transactions and parallel writes, so it does not suit an application that stores input arriving at arbitrary moments, and it is not a streaming database (book: DuckDB in Action section 1.4, page 5).

If the data really does arrive row by row, collect it in small batches first and load a batch at a time. We try several processes writing at once in the lesson [Data bigger than memory, and many users](/en/duckdb/beyond-memory/).

</Step>
