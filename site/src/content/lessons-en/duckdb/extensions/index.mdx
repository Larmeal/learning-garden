## A small core, and extensions that load on demand

DuckDB keeps its core small and puts other abilities in extensions that load when needed. We can ask with `duckdb_extensions()`.

```sql
select extension_name, loaded, installed, install_mode from duckdb_extensions()
```

The list holds 30 extensions in the Python package of DuckDB 1.5.6 (ran), but only four are built into the package itself in `STATICALLY_LINKED` mode: `core_functions`, `icu`, `json` and `parquet` (ran). That is why we could read Parquet and JSON files in the earlier lessons without installing anything. The others, such as `httpfs`, `sqlite_scanner` and `fts`, are not built in. They are downloaded from the DuckDB repository the first time with `INSTALL`, and turned on with `LOAD`.

```sql
install httpfs; load httpfs;
```

After `INSTALL` and `LOAD` all three show as `loaded` (ran). An installed extension is a real file on our disk, in the folder `~/.duckdb/extensions` (ran). The first time needs the internet, and later runs use the file already downloaded. The book describes the extension system in section 2.4 (book: DuckDB in Action section 2.4, page 15).

</Step>

## Reading Parquet over HTTP: ask for little, get little

`httpfs` lets us put a URL where a file name goes. The interesting question is this: if a 16.9 MB Parquet file sits on a server, do we have to download all of it for every query? We tried it with a small web server that we wrote on this computer. It understands the header `Range: bytes=a-b`, and we counted the bytes it sent for each query, with the file cache switched off and a fresh connection every time.

| Query | Requests | Bytes the server sent | Against the file |
|---|---|---|---|
| `count(*)` | 2 | 65,536 | 0.4% |
| `sum(qty)` | 11 | 445,319 | 2.6% |
| `sum(qty)` with `order_ts >= '2025-12-26'` | 4 | 190,929 | 1.1% |
| `sum(qty), sum(unit_price)` | 11 | 2,606,099 | 15.4% |
| `select *` | 11 | 16,771,333 | 99.2% |

Read the table line by line. `count(*)` uses only the end of the file (the footer), which holds the metadata of every row group and already tells the number of rows, so it uses under 1% of the file. `sum(qty)` has to read the `qty` column of all nine row groups, 2.6%. Adding the column `unit_price` takes it to 15.4%, because decimal prices compress less well, and `select *` has to read nearly the whole file. The most interesting is the third row. When we add a filter on `order_ts` at the end of the year, DuckDB uses the minimum and maximum of each row group that we saw in [How the data is stored](/en/duckdb/storage/) to skip the unrelated groups, so it asks for only 4 requests and 190,929 bytes, less than half of the `sum(qty)` without a filter (ran). Pick a query in the lab below and see which parts of the file are asked for.

<RangeReadLab client:visible lang="en" />

The answers that came back through the server are the same as querying the table directly (ran). All of the numbers come from a web server on the same computer, not from S3 or a real network, so there is no network delay, no HTTPS and no authentication. What the exercise confirms is the number of bytes asked for. On S3 the number of requests could differ, because of caching and request merging.

<Callout type="note" title="The book and cloud storage">
The book explains that letting the storage layer fetch only the columns or parts of the data a query needs is especially useful in distributed environments (book: DuckDB in Action section 5.4, page 108), and it uses the New York taxi data read from S3 as an example in section 10.4 (book: DuckDB in Action section 10.4, page 251). The author did not try it with a real S3.
</Callout>

## Reading another database in place

Another common case is that part of the data still lives in an old database. We made a SQLite file with a table `customers_legacy` of 5,000 customers (the tier `gold` for customers whose id divides by 10, everyone else `basic`), and let DuckDB open it as an attached database.

```sql
install sqlite_scanner; load sqlite_scanner;
attach 'legacy.db' as legacy (type sqlite, read_only);
select l.tier, count(*)
from read_parquet('orders.parquet') o join legacy.customers_legacy l using (customer_id)
group by all order by all
```

One statement joined the Parquet file with a table inside SQLite, giving a total of one million rows split between `basic` and `gold`, and the number of `gold` equals the orders of customers 10, 20, 30 and so on counted from the original table (ran). If we want to bring the data into our own file, `create table customers_copy as select * from legacy.customers_legacy` copies all 5,000 rows (ran). The book teaches querying SQLite and other databases in section 5.6 (book: DuckDB in Action section 5.6, page 116). The author did not try `postgres_scanner` or `mysql_scanner`.

</Step>

## Searching text with full-text search

Another extension, `fts`, builds a text index and ranks results with BM25. The example has a table `docs` of four rows that we wrote.

```sql
install fts; load fts;
pragma create_fts_index('docs', 'id', 'body', stemmer = 'english', stopwords = 'english', overwrite = 1);
select id, fts_main_docs.match_bm25(id, 'duckdb parquet') as score from docs order by score desc nulls last
```

The document that has both words (`duckdb reads parquet files and csv files`) ranks first, next comes the document with only `duckdb`, and the document with neither word scores `NULL` (ran). The example is tiny, and we did not measure how fast a large table can be searched.

</Step>
