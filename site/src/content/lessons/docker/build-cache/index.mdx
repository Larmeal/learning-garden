## Build ครั้งที่สองเร็วเพราะ Docker ใช้ Layer เดิม

ใน[บท 4](/docker/dockerfile/#dockerfile-คือสูตรที่-docker-อ่านทีละบรรทัด) เรา Build ตัวอย่างหนึ่งแล้วได้ Image ทันที ทีนี้ลอง Build โปรแกรม Python ที่ต้องติดตั้งแพ็กเกจด้วย `pip install` ซึ่งช้ากว่า เพราะต้องโหลดของจากอินเทอร์เน็ต เราเริ่มจาก Build ที่ปิด Cache ครั้งแรก แล้ว Build อีกรอบโดยไม่เปลี่ยนอะไรเลย (รัน)

| การ Build | เวลา | ขั้นที่ใช้ Cache |
|---|---|---|
| ครั้งแรก (ปิด Cache) | 3.7 วินาที | ไม่มี (ยกเว้น `WORKDIR`) |
| ซ้ำโดยไม่แก้อะไร | 0.5 วินาที | ทุกขั้น |

ครั้งที่สองเร็วกว่าประมาณเจ็ดเท่า เพราะ Docker ไม่ได้รันอะไรใหม่เลย มันเห็นว่าแต่ละบรรทัดกับสิ่งที่บรรทัดนั้นอ่าน เหมือนเดิมทุกอย่าง จึงหยิบ Layer ที่ Build ไว้แล้วมาใช้ หนังสือสรุปเรื่องนี้ไว้ว่าเมื่อมีบรรทัดหนึ่งผิดพลาดตรงกลางงาน Builder เริ่มต่อจากจุดเดิมได้เลยหลังแก้ (หนังสือ: Docker in Action หัวข้อ 8.1 หน้า 145) และหนังสืออีกเล่มวัดเวลา Build ที่ใช้ Cache กับไม่ใช้ แล้วพบว่าต่างกันมาก เพราะลำดับของบรรทัดใน Dockerfile ส่งผลต่อเวลา Build เฉลี่ยอย่างมาก (หนังสือ: Docker Up and Running หัวข้อ Optimizing for the Cache หน้า 79)

ถ้าอยากบังคับให้ทำใหม่ทั้งหมด ใช้ตัวเลือก `--no-cache` ซึ่งทำให้ขั้น `COPY` และ `RUN` รันใหม่ (รัน)

<Callout type="note" title="ข้อสังเกตที่เรายังไม่ได้ไล่หาเหตุผล">
ตอน Build ด้วย `--no-cache` บรรทัด `WORKDIR` ยังขึ้นว่า `CACHED` ซึ่งเป็นสิ่งที่เราเห็นจริงใน BuildKit ของ Docker 29.2.1 (รัน) เรายังไม่ได้ดูว่าเป็นเพราะอะไร จึงบอกได้แค่ว่าอย่าคาดว่า `--no-cache` จะข้ามทุกบรรทัด โดยเฉพาะบรรทัดที่ไม่ได้รันคำสั่ง
</Callout>

## ลำดับบรรทัดตัดสินว่าต้องรันใหม่กี่ขั้น

Cache ของ Docker ทำงานเป็นสาย แต่ละขั้นขึ้นกับขั้นก่อนหน้า ถ้ามีขั้นหนึ่งเปลี่ยน ทุกขั้นที่อยู่หลังมันต้องรันใหม่หมด ไม่ว่าตัวมันเองจะไม่ได้เปลี่ยนเลยก็ตาม ในแบบฝึกเราแก้ไฟล์บรรทัดเดียวต่อไปนี้ แล้วเปรียบเทียบสอง Dockerfile ที่ต่างกันแค่ลำดับ (รัน)

```dockerfile
# แบบ A                                  # แบบ B
FROM python:3.13-slim                    FROM python:3.13-slim
WORKDIR /app                             WORKDIR /app
COPY . .                                 COPY requirements.txt .
RUN pip install -r requirements.txt     RUN pip install -r requirements.txt
CMD ["python", "app.py"]                 COPY app.py .
                                         CMD ["python", "app.py"]
```

| ลำดับ | แก้ `app.py` | แก้ `requirements.txt` |
|---|---|---|
| A: `COPY . .` ก่อน | 3.5 วินาที (`pip install` รันใหม่) | 3.5 วินาที |
| B: `requirements.txt` ก่อน | 0.8 วินาที (`pip install` ใช้ Cache) | 3.8 วินาที |

เมื่อแก้ `app.py` ซึ่งเป็นสิ่งที่เราแก้บ่อยที่สุดตอนเขียนโปรแกรม แบบ A ต้องติดตั้งแพ็กเกจใหม่ทุกครั้ง เพราะ `COPY . .` อ่านทุกไฟล์ จึงเปลี่ยนตามไปด้วย และสายก็ขาดก่อนถึง `pip install` ส่วนแบบ B คัดลอกเฉพาะ `requirements.txt` ก่อนติดตั้ง และเอา `app.py` มาหลังสุด ถ้าแก้ `app.py` สายจึงขาดที่ขั้นท้ายสุด และ `pip install` ที่ช้าก็ยังใช้ของเดิม กดสลับตัวเลือกใน Lab ดู จะเห็นว่าแบบ B ยังคงขาดสายตามเดิมเมื่อแก้ `requirements.txt` เพราะแพ็กเกจเปลี่ยนจริง นั่นคือสิ่งที่ถูกต้อง

<CacheLab client:visible />

หลักที่ได้คือ ให้คัดลอกเฉพาะไฟล์ที่ขั้นแพง ๆ ต้องใช้ แล้วรันขั้นนั้น จากนั้นค่อยคัดลอกส่วนที่เหลือ

</Step>

## Cache ดูเนื้อหาของไฟล์ ไม่ได้ดูนาฬิกา

มีสองข้อเท็จจริงที่ช่วยให้เดาผลของ Cache ได้แม่นขึ้น ข้อแรก Docker ดูเนื้อหาของไฟล์ที่ `COPY` ไม่ได้ดูวันที่แก้ไข เราลองเปลี่ยนเวลาแก้ไขของ `app.py` ให้เป็นอีกชั่วโมงข้างหน้าโดยเนื้อหาเหมือนเดิม แล้ว Build ซ้ำ ทุกขั้นยังใช้ Cache (รัน) ข้อที่สองคือสายของ Cache ขาดแบบต่อเนื่อง เราแก้แค่บรรทัด `RUN` บรรทัดแรกของ Dockerfile ที่มีสามบรรทัด `RUN` แล้วทั้งสามบรรทัดต้องรันใหม่ แม้สองบรรทัดหลังไม่ได้เปลี่ยนตัวอักษรเดียว (รัน) เหตุผลคือแต่ละ Layer สร้างบน Layer ก่อนหน้า ถ้า Layer ฐานเปลี่ยน Layer ที่ตามมาก็ไม่ใช่ตัวเดิมอีกต่อไป

สองข้อนี้ทำให้เกิดกฎปฏิบัติง่าย ๆ คือบรรทัดที่เปลี่ยนน้อยที่สุดให้อยู่ข้างบน และบรรทัดที่เปลี่ยนบ่อยที่สุดให้อยู่ข้างล่าง ซึ่งตรงกับสิ่งที่เราเห็นในลำดับแบบ B

</Step>

## Build Context คือสิ่งที่ถูกส่งเข้าไปให้ Builder

ตัวเลข `.` ที่ท้ายคำสั่ง `docker build` ไม่ได้บอกแค่ที่อยู่ของ Dockerfile แต่เป็น Build Context คือโฟลเดอร์ที่ `COPY` มองเห็น หนังสือแนะนำว่าเรื่องแรกที่ควรทำตอนเริ่มโปรเจกต์คือกำหนดว่าไฟล์ไหนไม่ควรถูกคัดลอกเข้า Image ด้วยไฟล์ `.dockerignore` (หนังสือ: Docker in Action หัวข้อ 8.2.1 หน้า 149) ในแบบฝึกเราวางไฟล์ขนาด 20 MB ชื่อ `big.bin` ไว้ข้าง Dockerfile แล้ววัดว่ามีกี่ไบต์ถูกส่งไปให้ Builder (รัน)

| Dockerfile | ไบต์ที่ส่งเข้า Builder |
|---|---|
| `COPY small.txt /` (ไม่ได้ใช้ `big.bin`) | 38 |
| `COPY . /ctx/` | 20,980,000 |
| `COPY . /ctx/` และ `.dockerignore` ที่มี `big.bin` | 106 |

หนังสือซึ่งพิมพ์สมัยที่ Docker ยังใช้ Builder แบบเก่า บอกว่าทุกครั้งจะส่งทั้งโฟลเดอร์ ซึ่งมีข้อความ `Sending build context to Docker daemon` ในผลลัพธ์ (หนังสือ: Docker in Action หัวข้อ 8.1 หน้า 145) แต่ BuildKit ใน Docker 29.2.1 ฉลาดกว่า ถ้า Dockerfile ใช้แค่ `small.txt` มันส่งแค่ไฟล์นั้น (38 ไบต์) ปัญหาจริงจึงเกิดตอน `COPY . .` ซึ่งดึงทุกไฟล์ในโฟลเดอร์ รวมถึงไฟล์ที่เราไม่ตั้งใจ เช่น ข้อมูลขนาดใหญ่ โฟลเดอร์ `.git` หรือไฟล์ความลับ และผลของมันคือทั้ง Build ช้าลงและไฟล์พวกนั้นไปอยู่ใน Image ด้วย `.dockerignore` แก้ทั้งสองเรื่อง ใส่ `big.bin` แล้ว Build Context เหลือ 106 ไบต์ และ Image ไม่มีไฟล์นั้น (รัน)

อีกด้านของเรื่องเดียวกันคือ `COPY` มองไม่เห็นอะไรที่อยู่นอก Build Context เลย เราลอง `COPY ../secret.txt /` และ Build ล้มด้วยข้อความว่าหาไฟล์ `/secret.txt` ไม่เจอ (รัน) ถ้าอยากใช้ไฟล์จากข้างนอก ต้องย้ายไฟล์นั้นเข้ามาในโฟลเดอร์ที่เป็น Context หรือเปลี่ยน Context ให้ครอบถึงไฟล์นั้น (เราไม่ได้ลองวิธีหลังนี้)
