## Image คือกองของ Layer

ใน[บท 1](/docker/containers/#image-คือแม่แบบ-container-คือของที่ทำออกมา) เราเรียก Image ว่าแม่แบบที่อ่านได้อย่างเดียว คราวนี้ลองเปิดดูข้างในกันว่าแม่แบบนั้นเก็บไว้อย่างไร คำสั่ง `docker image inspect` บอกจำนวน Layer ของ Image ได้ และเมื่อเราลองกับสามตัวที่ใช้มาแล้วก็ได้ผลอย่างนี้ (รัน)

| Image | จำนวน Layer | ขนาด (MB) |
|---|---|---|
| `alpine:3.22` | 1 | 8.3 |
| `busybox:1.37` | 1 | 4.4 |
| `python:3.13-slim` | 4 | 118.4 |

Alpine มี Layer เดียวเพราะมันคือไฟล์ของระบบทั้งชุดที่แพ็กเป็นก้อนเดียว ส่วน Python มีสี่ Layer ซึ่งถูกซ้อนขึ้นไปทีละขั้นตอนที่ผู้สร้าง Image ทำ หนังสืออธิบายว่า Layer คือชุดของไฟล์พร้อมข้อมูลของไฟล์ ที่ถูกแพ็กและส่งต่อเป็นหน่วยเดียว และ Layer ส่วนใหญ่สร้างบน Layer แม่โดยบอกว่าไฟล์ไหนเปลี่ยนไปจากเดิม ไฟล์ที่ Container เห็นจึงเป็นผลรวมของทุก Layer ในสายเลือดของ Image นั้น (หนังสือ: Docker in Action หัวข้อ 3.3 หน้า 56 และหัวข้อ 3.3.2 หน้า 58)

Layer แต่ละอันมี ID ที่เป็น sha256 ของเนื้อหาข้างใน ส่วน Image ก็มี ID ยาว 64 ตัวอักษร และ Docker แสดงให้เราดูแค่สิบสองตัวแรกเพื่อให้อ่านง่าย (รัน) การที่ ID มาจากเนื้อหานี่เองที่ทำให้เรื่องถัดไปเกิดขึ้นได้

## Image สองตัวใช้ Layer เดียวกันร่วมกัน

เราลอง Build Image สองตัวบน Alpine ตัวเดียวกัน ตัวแรกชื่อ `dlab-app1` เพิ่มไฟล์ขนาด 1 MB หนึ่งไฟล์ ตัวที่สองชื่อ `dlab-app2` เพิ่มไฟล์ขนาด 2 MB (เราจะเรียนการเขียน Dockerfile กันใน[บทต่อไป](/docker/container-lifecycle/) ตอนนี้ขอให้ดูแค่ผลลัพธ์) พอเปิด `docker image inspect` ทั้งสามตัว จะเห็น ID ของ Layer ที่ต่างกันที่ชั้นบน แต่ชั้นล่างเหมือนกันเป๊ะ (รัน)

```text
image        layer 1       layer 2
alpine:3.22  fdc5834cb53a
dlab-app1    fdc5834cb53a  e799cedb75df
dlab-app2    fdc5834cb53a  b458dafe34ef
```

Layer ที่หนึ่งของทั้งสาม Image มี ID เดียวกัน นั่นคือ Docker ไม่ได้เก็บ Alpine สองสำเนา มันเก็บชุดเดียวแล้วให้ทั้งสอง Image ชี้มาที่ชุดนั้น กดสลับใน Lab ดู ตอนมี Image ตัวเดียว ตัวเลขที่เก็บจริงกับตัวเลขถ้าแยกเก็บเท่ากัน พอเพิ่มตัวที่สอง Layer ฐานก็ยังเป็นกล่องเดียวและตัวเลขสองช่องห่างกันทันที

<SharedLayersLab client:visible />

หนังสือเล่าเรื่องเดียวกันด้วยตัวอย่าง Java สองโปรแกรมที่ใช้ Image ฐานร่วมกัน ตอนติดตั้งตัวที่สอง Docker เห็นว่ามี Layer ฐานอยู่แล้วจึงโหลดเฉพาะส่วนที่ต่างซึ่งเล็กกว่าหนึ่งเมกะไบต์ และถ้าเป็น Virtual Machine ไฟล์ที่ซ้ำกันจะถูกเก็บซ้ำเท่ากับจำนวนเครื่อง (หนังสือ: Docker in Action หัวข้อ 3.3.1 หน้า 57 และหัวข้อ 3.3.4 หน้า 60) ในมุมของคนใช้ ประโยชน์นี้เกิดเองโดยไม่ต้องทำอะไร แต่ในมุมของคนสร้าง Image การเลือก Image ฐานให้ตรงกันจะช่วยประหยัดทั้งเวลาดาวน์โหลดและที่เก็บ

## Container เห็นไฟล์จากทุก Layer รวมกัน

Image อ่านได้อย่างเดียวแล้ว Container เขียนไฟล์ได้อย่างไร คำตอบคือ Docker วางชั้นสำหรับเขียนว่าง ๆ ไว้บนสุดของกอง แล้วใช้สิ่งที่เรียกว่า Union Filesystem รวมทุกชั้นให้ดูเหมือนเป็นโฟลเดอร์เดียว ในเครื่องนี้ Docker ใช้ตัวที่ชื่อ `overlay2` ซึ่งเราตรวจแล้วว่า Container ที่รันอยู่มี Mount ที่ประกอบด้วยโฟลเดอร์ที่อ่านได้อย่างเดียวหนึ่งโฟลเดอร์ต่อหนึ่ง Layer ของ Image บวกอีกหนึ่งโฟลเดอร์ที่ Docker เติมให้เอง (เรายังไม่ได้เปิดดูว่าข้างในมีอะไร) และโฟลเดอร์สำหรับเขียนอีกหนึ่ง (รัน) ถ้าอ่านไฟล์ ระบบจะหาจากชั้นบนสุดลงมาจนเจอ (หนังสือ: Docker in Action หัวข้อ 7.2.1 หน้า 131)

ลองดูว่าเกิดอะไรขึ้นเมื่อ Container แก้ไฟล์สามแบบ เราเริ่ม Container จาก `dlab-app1` ซึ่งมีสอง Layer แล้วสั่งทีละอย่าง คือเพิ่มไฟล์ใหม่ แก้ไฟล์ของ Alpine และลบไฟล์ที่อยู่ใน Layer ที่สอง กดถัดไปใน Lab ทีละขั้น แล้วดูฝั่งขวาว่าอะไรเปลี่ยนในชั้นเขียนบ้าง

<UnionLab client:visible />

คำสั่ง `docker diff` บอกการเปลี่ยนแปลงในชั้นเขียนด้วยตัวอักษรสามตัว `A` คือไฟล์ที่เพิ่ม `C` คือไฟล์หรือโฟลเดอร์ที่เปลี่ยน และ `D` คือไฟล์ที่ถูกลบ โฟลเดอร์ที่ไฟล์นั้นอยู่จะขึ้น `C` ด้วยเสมอ (รัน) ผลที่เราได้ตรงกับที่หนังสือแสดงไว้ทุกบรรทัด (หนังสือ: Docker in Action หัวข้อ 7.2.1 หน้า 131) ขอให้สังเกตสองจุด จุดแรก ไม่มีขั้นไหนแตะ Image เลย พอเราสั่ง Container ใหม่จาก Image เดียวกัน ก็ยังเห็น `/etc/passwd` เดิมและ `/data1` ครบ (รัน) จุดที่สอง การลบไม่ได้เอาไฟล์ออกจาก Layer ล่าง ชั้นเขียนแค่จดว่าไฟล์นั้นถูกลบ ซึ่งทำให้ Container มองไม่เห็นเท่านั้น

</Step>

## แก้ไฟล์หนึ่งไบต์ ต้องคัดลอกทั้งไฟล์

มีเรื่องที่ทำให้คนแปลกใจเรื่องหนึ่งตอนแก้ไฟล์ของชั้นล่าง เพราะชั้นล่างแก้ไม่ได้ Docker จึงต้องคัดลอกไฟล์นั้นขึ้นมาไว้ในชั้นเขียนก่อนแล้วค่อยแก้ที่สำเนา หนังสือเรียกวิธีนี้ว่า Copy-on-write และบอกว่ามีผลเสียต่อความเร็วตอนรันและขนาดของ Image (หนังสือ: Docker in Action หัวข้อ 7.2.1 หน้า 131) ในแบบฝึกเราสร้าง Image ที่มีไฟล์ขนาด 20 MB หนึ่งไฟล์ แล้วรัน Container สองตัว ตัวหนึ่งแค่อ่านไฟล์ อีกตัวต่อท้ายไฟล์ด้วยตัวอักษรหนึ่งตัวกับขึ้นบรรทัดใหม่ (สองไบต์) จากนั้นดูขนาดชั้นเขียนของทั้งสอง (รัน)

| Container | ขนาดชั้นเขียน (ไบต์) |
|---|---|
| อ่านไฟล์อย่างเดียว | 0 |
| เพิ่มสองไบต์ท้ายไฟล์ | 20,971,522 |

การอ่านไม่ทำให้ชั้นเขียนโตเลย แต่การเพิ่มแค่สองไบต์ทำให้ไฟล์ทั้ง 20 MB ถูกคัดลอกขึ้นมา (ขนาดไฟล์เดิม 20,971,520 บวกสองไบต์ที่เราเพิ่ม) เหตุผลนี้ทำให้ไม่ควรเก็บไฟล์ก้อนใหญ่ที่ต้องแก้บ่อยไว้ใน Image แล้วให้ Container แก้ตรง ๆ ข้อมูลพวกนั้นควรไปอยู่ที่ Volume ซึ่งเป็นเรื่องของบทเรียนต่อ ๆ ไป

<Callout type="note" title="Storage Driver ตัวอื่นก็ใช้หลักนี้">
Docker เลือก Union Filesystem ที่เหมาะกับระบบให้เอง และหนังสือเตือนว่าแต่ละตัวมีข้อจำกัดต่างกัน เช่น Btrfs และ OverlayFS ไม่รองรับ Extended Attributes ที่ SELinux ต้องใช้ ส่วนไฟล์ที่ถูกอ่านด้วย `mmap` ก็ทำงานยากบน Copy-on-write (หนังสือ: Docker in Action หัวข้อ 3.3.5 หน้า 60) เราลองแค่ `overlay2` ตัวเดียว จึงไม่ได้ตรวจว่าตัวอื่นทำตามนี้ทุกข้อ (ไม่ได้รัน)
</Callout>

## Layer มีแต่เพิ่ม ลบทีหลังไม่ได้คืนที่

เรื่องนี้คือสิ่งที่คนเขียน Dockerfile พลาดบ่อยที่สุด ถ้า Layer ของ Image อ่านได้อย่างเดียว การลบไฟล์ใน Layer ถัดมาก็ทำได้แค่ซ่อน ไฟล์เดิมยังเก็บอยู่ใน Layer ข้างล่าง เราลองสร้าง Image สองแบบ แบบแรกสร้างไฟล์ 10 MB ใน `RUN` บรรทัดหนึ่ง แล้วลบมันใน `RUN` อีกบรรทัด แบบที่สองสร้างและลบในบรรทัด `RUN` เดียวกัน ผลคือ (รัน)

| Image | ขนาด (MB) | จำนวน Layer |
|---|---|---|
| `alpine:3.22` | 8.3 | 1 |
| สร้างแล้วลบ แยกสอง `RUN` | 18.8 | 3 |
| สร้างและลบใน `RUN` เดียว | 8.3 | 2 |

แบบแรกใหญ่กว่า Alpine 10.5 MB ทั้งที่ Container ที่รันจาก Image นั้นมองไม่เห็นไฟล์นั้นแล้ว (เราเปิด `ls /big` ดูแล้ว ตอบว่าไม่มีไฟล์) ส่วนแบบที่สองเท่ากับ Alpine เป๊ะ เพราะไฟล์ถูกลบก่อน Layer จะถูกปิด จึงไม่เคยถูกบันทึกลงไป กดเล่นใน Lab เพื่อเห็นความสูงของสองกอง

<AdditiveLab client:visible />

หนังสือสรุปไว้ว่าทุกครั้งที่เปลี่ยน Image ต้องเพิ่ม Layer ใหม่ และ Layer เก่าไม่เคยถูกเอาออก (หนังสือ: Docker in Action หัวข้อ 7.2.3 หน้า 137) ผลในทางปฏิบัติคือ ถ้าอยากให้ Image เล็ก ให้ทำงานที่สร้างของชั่วคราวแล้วลบมัน ให้จบใน `RUN` บรรทัดเดียวกัน เรื่องนี้จะกลับมาอีกตอนเราเรียนเขียน Dockerfile และทำให้ Image เล็กลง

</Step>

## Tag เป็นแค่ชื่อ ตัวตนของ Image คือ ID

ตอนนี้เรารู้แล้วว่า Image คือกองของ Layer และถูกระบุด้วย ID ทีนี้ชื่อแบบ `alpine:3.22` คืออะไร ชื่อนี้ประกอบด้วยชื่อ Repository (`alpine`) กับ Tag (`3.22`) และมันเป็นแค่ป้ายที่ชี้ไปที่ ID ของ Image หนึ่งตัว เราลองตั้งชื่อใหม่ให้ Image เดิมด้วย `docker tag alpine:3.22 dlab-alias:1` แล้วเปิดดู ID จะพบว่าสองชื่อชี้ไปที่ Image ตัวเดียวกัน และพอลบชื่อใหม่ทิ้ง Image ก็ยังอยู่เพราะยังมีอีกชื่อที่ชี้ (รัน) หนังสือใช้ภาพเดียวกัน Repository คือที่ที่เก็บ Tag ซึ่งแต่ละ Tag ชี้ไปที่ Layer ตัวบนสุดของ Image (หนังสือ: Docker in Action หัวข้อ 7.2.2 หน้า 134)

อีกเรื่องที่เกี่ยวกับ ID คือ ถ้า Build Dockerfile เดิมซ้ำสองรอบ เราจะได้ Image ID เดิมทุกตัวอักษร เพราะรอบที่สองใช้ Layer ที่ทำไว้แล้วทั้งหมด (รัน) เรื่องการใช้ Layer เดิมซ้ำตอน Build คือหัวข้อของบท [Build Cache](/docker/build-cache/) ที่จะมาถึงในเส้นทางนี้

<Callout type="tip" title="Image ที่ไม่มีชื่อ">
หนังสือบอกว่า `docker images` ตามปกติแสดงแค่ Repository ถ้าใส่ `-a` จะเห็น Image ที่ไม่มีชื่อซึ่งแสดงเป็น `<none>` ด้วย และ Image พวกนั้นอ้างถึงได้ทาง ID เท่านั้น เช่นตัวที่ Build ออกมาโดยไม่ตั้ง Tag (หนังสือ: Docker in Action หัวข้อ 3.3.1 หน้า 57 ไม่ได้รัน)
</Callout>

</Step>
