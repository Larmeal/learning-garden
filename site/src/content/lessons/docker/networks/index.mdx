## Container ทุกตัวมี IP แต่ยังไม่รู้จักชื่อของกันและกัน

หนังสือบอกว่า Container ที่ต่ออยู่กับ Docker Network จะได้ IP Address เฉพาะตัวที่ Container อื่นในเครือข่ายเดียวกันเรียกถึงได้ และ Docker ถือว่า Network เป็นของที่มีวงจรชีวิตของตัวเอง สร้างและจัดการได้ด้วยคำสั่งชุด `docker network` (หนังสือ: Docker in Action หัวข้อ 5.2 หน้า 83) ทุกครั้งที่ติดตั้ง Docker จะมีสาม Network ให้ ได้แก่ `bridge`, `host` และ `none` (รัน)

เรารัน Container สองตัวโดยไม่ระบุ Network เลย ซึ่งทำให้ทั้งคู่ไปอยู่ที่ `bridge` ตัวตั้งต้น แล้วให้ตัว A ลอง Ping ไปหา B สองแบบ (รัน)

| วิธีเรียก | ผล |
|---|---|
| Ping ด้วย IP ของ B (`172.17.x.x`) | ถึง |
| Ping ด้วยชื่อ Container ของ B | ไม่ถึง |

ทั้งคู่ได้ที่อยู่ในช่วง `172.17.0.0/16` และเรียกถึงกันด้วย IP ได้ แต่เรียกด้วยชื่อไม่ได้ เพราะ Default Bridge ไม่มีการแปลงชื่อเป็นที่อยู่ ปัญหาคือ IP ของ Container เปลี่ยนทุกครั้งที่สร้างใหม่ เราจึงเอา IP ไปเขียนไว้ในโปรแกรมไม่ได้ ซึ่งนำไปสู่หัวข้อต่อไป

เรื่องการต่อสายและตารางที่อยู่ว่า Container ถูกต่อเข้า Bridge ด้วยกลไกอะไร เป็นเรื่องที่ Subject Network อธิบายไว้แล้วใน[บท 13](/networking/proxies-and-containers/#container-ก็คือ-network-namespace-ที่ต่อสายเข้า-bridge) บทนี้จะดูจากฝั่งคนใช้ Docker

## Network ที่เราสร้างเองมี DNS

คำตอบของปัญหาชื่อคือสร้าง Network เองด้วย `docker network create` แล้วให้ Container เข้าร่วม (`--network ชื่อ`) ในแบบฝึกเราทำอย่างนั้น และ Container A เรียก B ด้วยชื่อได้ (รัน) ในไฟล์ `/etc/resolv.conf` ข้างใน Container เห็นว่า Name Server เป็น `127.0.0.11` ซึ่งเป็น DNS ที่ Docker ใส่ให้ และ Network ใหม่ได้ช่วง IP ของตัวเอง (ในรอบที่รันคือ `172.19.0.0/16`) ต่างจาก Default Bridge (รัน)

เรื่องที่สองที่เห็นคือ Network แต่ละวงแยกจากกัน เราสร้างอีกวงหนึ่งชื่อ `dlab-net2` แล้วให้ Container C อยู่ในนั้น A เรียก C ไม่ถึงทั้งด้วยชื่อและด้วย IP แต่พอสั่ง `docker network connect dlab-net2 A` ให้ A เข้าร่วมวงที่สองด้วย A ก็เรียก C ด้วยชื่อได้ (รัน) สรุปทั้งหมดเป็นตารางนี้

| การวาง | A เรียก B ด้วย IP | A เรียก B ด้วยชื่อ |
|---|---|---|
| Default Bridge | ถึง | ไม่ถึง |
| Network เดียวกันที่เราสร้างเอง | ถึง | ถึง |
| คนละ Network ที่เราสร้างเอง | ไม่ถึง | ไม่ถึง |
| A เข้าร่วมทั้งสอง Network | ถึง | ถึง |

กดเลือกการวางกับคนที่เรียกใน Lab ดูทีละแบบ ลูกศรจะวิ่งถึงปลายทางหรือหยุดที่ขอบของ Network ตามผลที่วัดได้จริง

ผลที่ได้คือกฎปฏิบัติสองข้อ ข้อแรก ถ้าอยากให้ Container เรียกกันด้วยชื่อ ให้สร้าง Network เอง ไม่ใช้ Default Bridge ข้อที่สอง Network ใช้กั้น Container ที่ไม่ควรคุยกันได้ เช่น แยกฐานข้อมูลออกจากบริการที่ไม่ต้องใช้มัน (เรายังไม่ได้ลองกฎของ Firewall ที่ละเอียดกว่านี้ระหว่าง Container ในวงเดียวกัน ซึ่งไม่ได้รัน)

## Publish พอร์ตเพื่อให้คอมพิวเตอร์ของเราเรียกเข้ามาได้

ทีนี้ลองจากอีกด้าน เรารันเว็บเซิร์ฟเวอร์ง่าย ๆ (`python -m http.server 8000`) สองตัวบน Network เดียวกัน ตัวหนึ่งใส่ `-p 127.0.0.1:60808:8000` อีกตัวไม่ใส่ แล้วลองเรียกจากคอมพิวเตอร์เรา (Windows) และจาก Container อีกตัวที่อยู่ใน Network เดียวกัน (รัน)

| ใครเรียก | ไปที่ไหน | ผล |
|---|---|---|
| คอมพิวเตอร์ของเรา | พอร์ตที่ Publish (`127.0.0.1:60808`) | ถึง |
| คอมพิวเตอร์ของเรา | Container ที่ไม่ใส่ `-p` (ผ่าน IP ของ Container) | ไม่ถึง |
| Container อื่นใน Network เดียวกัน | ตัวที่ใส่ `-p` ด้วยชื่อ | ถึง |
| Container อื่นใน Network เดียวกัน | ตัวที่ไม่ใส่ `-p` ด้วยชื่อ | ถึง |

พอร์ตที่ Publish คือช่องที่เปิดบนคอมพิวเตอร์ของเราเพื่อส่งต่อเข้า Container เท่านั้น ถ้าไม่ Publish คอมพิวเตอร์เราเรียกเข้าไม่ได้ แต่ Container ที่อยู่ในเครือข่ายเดียวกันเรียกถึงกันเองได้เสมอโดยไม่ต้อง Publish ตัวเลข `127.0.0.1` ในคำสั่งบอกว่าให้เปิดช่องเฉพาะบนที่อยู่นี้ซึ่งมีแต่คอมพิวเตอร์เราเรียกได้ คำสั่ง `docker port` ยืนยันว่าพอร์ตผูกกับ `127.0.0.1` ตามที่เราสั่ง (รัน) ถ้าเราเขียนแค่ `-p 8000:8000` Docker จะเปิดบนทุกที่อยู่ ซึ่งคอมพิวเตอร์เครื่องอื่นในเครือข่ายเดียวกับเราอาจเรียกเข้ามาได้ เราไม่ได้ลองกรณีหลังนี้ (ไม่ได้รัน)

กลไกข้างใต้ของการ Publish คือกฎ DNAT ของ Iptables ซึ่งเราไล่ดูแล้วใน[บท 13 ของ Subject Network](/networking/proxies-and-containers/#เข้ามาข้างใน-port-ที่-publish-คือกฎ-dnat) บทนี้ไม่ได้รันซ้ำ

<Callout type="note" title="ทำไมเรียก IP ของ Container จาก Windows ตรง ๆ ไม่ได้">
Container อยู่ในเครือข่ายของ Linux ที่ Docker Desktop เปิดไว้ ไม่ใช่ในเครือข่ายของ Windows ที่อยู่ `172.x.x.x` ของ Container จึงเรียกจาก Windows ตรง ๆ ไม่ได้ ซึ่งแบบฝึกเห็นว่าเรียกไม่ถึง บน Linux จริงอาจเรียกได้ต่างออกไป เราไม่ได้ลอง
</Callout>

## Alias, None และ Host

มีสามเรื่องสั้น ๆ ที่เจอบ่อย เรื่องแรก Alias เราตั้งชื่อเสริมให้ Container ด้วย `--network-alias` และตั้งชื่อเดียวกันให้สอง Container ได้ ในแบบฝึกเราตั้ง Alias ชื่อ `workers` ให้ Container สองตัว แล้ว `nslookup workers` ตอบกลับเป็นสองที่อยู่ ซึ่งตรงกับ IP ของสองตัวนั้น (รัน) นี่คือการกระจายงานแบบง่ายที่สุดด้วย DNS ที่ลูกค้าได้หลายที่อยู่แล้วเลือกเอง

เรื่องที่สองและสาม คือ Network พิเศษสองตัวที่หนังสือบอกว่าจริง ๆ แล้วเป็นชนิดการต่อที่มีความหมายพิเศษ ไม่ใช่เครือข่ายจริง (หนังสือ: Docker in Action หัวข้อ 5.3 หน้า 89) `--network none` ให้ Container ที่ไม่มีเครือข่ายเลย ในแบบฝึกเห็นแค่ Interface `lo` ตัวเดียว ส่วน `--network host` ให้ Container ใช้เครือข่ายของ Host ตรง ๆ ไม่มี Network Namespace แยก ซึ่งแบบฝึกเห็นรายชื่อ Interface ของ Linux ที่รัน Engine ทั้งหมด รวมถึง `docker0` (รัน) ตามที่หนังสือบอกว่าเห็นและผูกกับ Interface ของ Host ได้ทุกตัว บนเครื่องนี้ Host ที่ว่าคือ Linux ใน Docker Desktop ไม่ใช่ Windows

| ชนิดการต่อ | Interface ที่เห็นข้างใน Container |
|---|---|
| ปกติ (Bridge) | `eth0` กับ `lo` |
| `--network none` | `lo` อย่างเดียว |
| `--network host` | ทั้งหมดของ Host รวม `docker0` และ Bridge อื่น ๆ |

</Step>

## โปรแกรมหาฐานข้อมูลเจอด้วยชื่อ

นี่คือรูปแบบที่ใช้ทุกวันในงานข้อมูล ในแบบฝึกเรารัน Postgres ชื่อ `dlab-db` บน Network ที่เราสร้าง แล้วเปิด Container อีกตัวบน Network เดียวกันเพื่อเรียก `pg_isready -h dlab-db` (รัน)

```text
dlab-db:5432 - accepting connections
```

ตัวเรียกหาฐานข้อมูลเจอด้วยชื่อ Container และพอร์ต 5432 โดยเราไม่เคย Publish พอร์ตเลย และคอมพิวเตอร์ของเราเองก็เรียก `127.0.0.1:5432` ไม่ได้ (รัน) นั่นคือ ฐานข้อมูลที่ไม่ได้ Publish จะถูกซ่อนจากโลกข้างนอก แต่โปรแกรมของเราที่อยู่ใน Network เดียวกันเรียกได้ ซึ่งเป็นแนวทางที่ปลอดภัยกว่าเปิดพอร์ตทิ้งไว้ เราจะเห็นรูปแบบนี้ซ้ำในบทที่เรารวมหลาย Container ด้วย Compose

</Step>
