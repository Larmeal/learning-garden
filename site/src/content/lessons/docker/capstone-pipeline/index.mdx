## Pipeline ที่เราจะใส่ลง Container

บทสุดท้ายนี้เรารวมสิ่งที่เรียนมาทั้งหมดเป็นงานเดียว สมมติว่ามีไฟล์ `orders.csv` ห้าแถวที่ต้องโหลดเข้า Postgres และมีแถวหนึ่งที่จำนวนสินค้าติดลบซึ่งต้องถูกปฏิเสธ เราเขียนตัวโหลด (`etl`) ด้วย Python สั้น ๆ ที่อ่านไฟล์ ตรวจแถว และ Insert แถวที่ผ่านเข้าตาราง `orders` แล้วใส่ทั้งหมดไว้ในไฟล์ Compose เดียว

```yaml
services:
  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    volumes: [pgdata:/var/lib/postgresql/data]
    healthcheck: {test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U postgres"], interval: 2s, retries: 40}
    networks: [backend]
  etl:
    build:
      context: ./etl
    depends_on: {db: {condition: service_healthy}}
    secrets: [db_password]
    volumes: ["./data:/data:ro"]
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    mem_limit: 128m
    pids_limit: 64
    networks: [backend]
networks:
  backend: {internal: true}
secrets:
  db_password: {file: ./db_password.txt}
volumes:
  pgdata:
```

ส่วน Dockerfile ของ `etl` ใช้สิ่งที่เรียนในบทเรื่อง[Image ที่เล็กและปลอดภัย](/docker/small-and-safe-images/#ให้-container-รันด้วยผู้ใช้ที่ไม่ใช่-root)คือ Base Image แบบ Slim ติดตั้งแพ็กเกจแบบไม่เก็บ Cache สร้างผู้ใช้ `etl` (UID 10001) และ `COPY --chown` ให้ผู้ใช้นั้นเป็นเจ้าของไฟล์ แล้วสั่ง `USER etl`

เมื่อ `docker compose up -d --build` Compose Build Image แล้วเริ่ม `db` รอจนมันสถานะ `healthy` (บท[Docker Compose](/docker/compose/#depends_on-ต้องรอให้บริการพร้อมก่อน)) แล้วจึงเริ่ม `etl` ผลที่แบบฝึกเห็นคือ `etl` จบด้วย Exit Code 0 พิมพ์ว่า `loaded 4 rejected 1 rows in table: 4` และตารางใน Postgres มีแถวหมายเลข 1, 2, 4, 5 ครบ ไม่มีแถวที่ 3 ที่จำนวนติดลบ (รัน)

## ล็อก Container ของตัวโหลดทีละชั้น

ในไฟล์ Compose ข้างบนมีหลายบรรทัดที่ไม่ได้ทำให้ Pipeline ทำงานเร็วขึ้น แต่ทำให้ปลอดภัยขึ้น เราตรวจแต่ละบรรทัดว่าทำงานจริง ทั้งจากข้างนอกด้วย `docker inspect` และจากข้างในด้วยการลองทำสิ่งที่ไม่ควรทำได้ (รัน)

| บรรทัดใน Compose | สิ่งที่ตรวจเจอ |
|---|---|
| `USER etl` ใน Dockerfile | `id -u` ข้างในได้ `10001` |
| `read_only: true` | เขียน `/x` ไม่ได้ ได้ข้อความ `Read-only file system` |
| `tmpfs: [/tmp]` | แต่เขียน `/tmp` ได้ |
| `volumes: ["./data:/data:ro"]` | เขียนลง `/data` ไม่ได้ |
| `cap_drop: [ALL]` | `CapEff` ใน `/proc/self/status` เป็น `0000000000000000` |
| `mem_limit: 128m`, `pids_limit: 64` | `docker inspect` ได้ 128 MB กับ 64 |

ตัวที่น่าสนใจคือ `cap_drop` ในบท Namespace เราเห็นว่า Container ไม่มี User Namespace แยก ผู้ใช้ `root` ใน Container จึงเป็น UID 0 ตัวเดียวกับของ Linux ที่รัน Engine ดังนั้นการจำกัดสิทธิ์ของ Root ใน Container ให้เหลือเท่าที่ใช้จริงจึงสำคัญ สิทธิ์พิเศษของ Root ถูกแบ่งเป็นส่วนย่อยเรียกว่า Capability และ Docker ให้ Container ถือแค่บางส่วน หนังสือเล่าว่า Linux Kernel รุ่น 2.2 เริ่มแบ่งสิทธิ์ของ Root ออกเป็นส่วนย่อยด้วยกลไกนี้ แทนที่จะมีแค่ Root กับไม่ใช่ Root (หนังสือ: Container Security บทที่ 2 หน้า 19) Container ปกติที่ไม่ได้ตั้งอะไรมี `CapEff` เป็น `00000000a80425fb` ซึ่งหมายถึงถือ Capability หลายตัว ส่วน `etl` ที่ถอดทั้งหมดได้เป็นศูนย์ล้วน (รัน)

ตัวเลือก `no-new-privileges` ป้องกันอีกทางหนึ่ง คือกันไม่ให้โปรแกรมได้สิทธิ์เพิ่มผ่านไฟล์ที่ตั้ง Setuid ไว้ หนังสืออธิบายว่า Setuid เป็นช่องที่นำไปสู่การยกระดับสิทธิ์ ตัวสแกน Image บางตัวจึงเตือนเมื่อเจอไฟล์ที่ตั้งบิตนี้ และสามารถป้องกันด้วยตัวเลือก `--no-new-privileges` ของ `docker run` (หนังสือ: Container Security บทที่ 2 หน้า 16) แบบฝึกตรวจแค่ว่าตัวเลือกนี้ถูกตั้งไว้ใน `docker inspect` เรายังไม่ได้ลองโจมตีด้วยไฟล์ Setuid จริง (ไม่ได้รัน)

</Step>

## ความลับเป็นไฟล์ และ Network ที่ไม่มีทางออก

ในบทเรื่อง Image ที่ปลอดภัยเราส่งความลับเข้าตอน Build โดยไม่ทิ้งรอย ตอนรันก็มีวิธีเช่นกัน Compose ส่งความลับให้ Container เป็นไฟล์ใต้ `/run/secrets` ในแบบฝึกรหัสผ่านอยู่ในไฟล์ `db_password.txt` Postgres อ่านผ่านตัวแปร `POSTGRES_PASSWORD_FILE` ซึ่งชี้ไปที่ไฟล์ และโปรแกรม `etl` ก็เปิดไฟล์เดียวกันอ่าน ผลที่ตรวจได้คือค่ารหัสผ่านไม่ปรากฏในตัวแปรสภาพแวดล้อมของทั้งสอง Container (ดูจาก `docker inspect`) ไม่อยู่ใน `docker history` ของ Image ที่ Build และอ่านได้จากไฟล์ใต้ `/run/secrets` ตามที่ตั้งใจ (รัน) ข้อดีเทียบกับการใส่ในตัวแปรคือ ตัวแปรสภาพแวดล้อมมักถูกพิมพ์ลง Log หรือรายงานข้อผิดพลาดโดยไม่ตั้งใจ ส่วนไฟล์ต้องมีคนตั้งใจเปิดอ่าน (ข้อนี้เป็นความเห็นของผู้เขียน ไม่ได้ทดสอบ)

เรื่องสุดท้ายคือเครือข่าย เราประกาศ `backend` เป็น `internal: true` ซึ่งทำให้ Container ใน Network นั้นคุยกันเองได้แต่ออกอินเทอร์เน็ตไม่ได้ แบบฝึกลองให้ `etl` เรียก `example.com` แล้วไม่สำเร็จ ส่วน `docker network inspect` ก็ยืนยันว่า `Internal` เป็นจริง (รัน) ตัวโหลดข้อมูลที่ถูกเจาะจึงส่งข้อมูลออกไปข้างนอกตรง ๆ ไม่ได้ และฐานข้อมูลก็ไม่ได้ Publish พอร์ตไว้ตั้งแต่ต้น ตรงกับที่เราเห็นในบท[Network ของ Docker](/docker/networks/#โปรแกรมหาฐานข้อมูลเจอด้วยชื่อ)

<Callout type="note" title="สิ่งที่ Pipeline นี้ยังไม่ได้ป้องกัน">
การล็อกทั้งหมดนี้ลดความเสียหายถ้าตัวโหลดถูกเจาะ แต่ไม่ได้ทำให้ระบบปลอดภัยสมบูรณ์ เรายังไม่ได้ลอง Seccomp และ AppArmor ที่จำกัด System Call, Rootless Docker ที่ไม่ให้ Engine รันเป็น Root, การสแกนช่องโหว่ของ Image และการเก็บรหัสผ่านใน Secret Manager จริง (ไม่ได้รัน) และ Pipeline นี้เป็นตัวอย่างเล็ก ๆ ที่มี CSV ห้าแถว
</Callout>

## พังแล้วหาสาเหตุจากสถานะ Log และ Inspect

Pipeline ที่ดีต้องหาสาเหตุได้เร็วเวลาพัง เราลองทำให้พังสามแบบโดยตั้งตัวแปรสภาพแวดล้อมของ Compose แล้วดูว่าคำสั่งไหนบอกอะไร (รัน)

| ทำให้พังโดย | `docker compose ps -a` | Exit Code | OOMKilled | บรรทัดสุดท้ายของ Log |
|---|---|---|---|---|
| ชื่อ Host ผิด | `etl exited 1` | 1 | False | `failed to resolve host 'dbx'` |
| รหัสผ่านผิด | `etl exited 1` | 1 | False | `password authentication failed for user "postgres"` |
| Memory น้อยเกินไป | `etl exited 137` | 137 | True | (ว่างเปล่า) |

ข้อสังเกตแรก สองกรณีแรกได้ Exit Code 1 เหมือนกัน แต่สาเหตุต่างกัน แค่สถานะจาก `compose ps` ไม่พอ ต้องเปิด Log ซึ่งบอกสาเหตุตรง ๆ ข้อสังเกตที่สอง กรณี Memory ได้ Exit Code 137 กับ `OOMKilled` เป็นจริงใน `docker inspect` ซึ่งตรงกับสิ่งที่เราเห็นในบท[Namespace และ Cgroup](/docker/namespaces-and-cgroups/#cgroup-คือขีดจำกัดที่เขียนเป็นไฟล์) และ Log ว่างเปล่าเพราะโปรแกรมถูกฆ่าก่อนจะพิมพ์อะไรได้ การรู้ว่า Log ว่างสื่อความหมายในตัวมันเอง ช่วยไม่ให้เสียเวลาไล่ดูโค้ดตัวโปรแกรม ส่วน `docker events` บันทึกเหตุการณ์ `oom` ของ Container ในกรณีนี้ด้วย (รัน) และพอแก้ค่ากลับ Pipeline ก็รันผ่านอีกครั้ง โดยตารางใน Volume ยังมีสี่แถวเดิม (รัน)

ลำดับการหาสาเหตุที่ได้จึงเป็นบันไดสี่ขั้น ดูสถานะและ Exit Code ก่อน ต่อด้วย Log ต่อด้วย `docker inspect` เพื่อดู `OOMKilled` และ Exit Code ตัวจริง และสุดท้ายคือ `docker events` ถ้ายังไม่เห็นภาพ กดเลือกวิธีที่ทำให้พังใน Lab ดูว่าลูกศรหยุดตรงไหน และแต่ละคำสั่งพิมพ์อะไร
