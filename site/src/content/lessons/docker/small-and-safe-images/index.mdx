## Image ตัวเดียวกันหนักต่างกันประมาณยี่สิบเท่า

โปรแกรมของเราเล็กมาก มีแค่สามบรรทัดที่พิมพ์เวอร์ชันของแพ็กเกจ `six` แต่ขนาดของ Image ที่ได้ขึ้นกับว่าเราเริ่มจาก Image ฐานตัวไหนเกือบทั้งหมด ในแบบฝึกเรา Build โปรแกรมเดียวกันสามครั้งบน Python สามแบบ (รัน)

| Image ฐาน | ขนาด Image (MB) | พิมพ์ผลเหมือนกันหรือไม่ |
|---|---|---|
| `python:3.13` | 1121.1 | พิมพ์ `six 1.17.0` |
| `python:3.13-slim` | 126.8 | พิมพ์ `six 1.17.0` |
| `python:3.13-alpine` | 54.1 | พิมพ์ `six 1.17.0` |

ทั้งสามตัวทำงานได้ผลเดียวกัน แต่ตัวแรกหนักกว่าตัวที่สองประมาณเก้าเท่า (ส่วนต่างระหว่าง 126.8 กับ 118.4 MB ของ `slim` เปล่า ๆ มาจากบรรทัด `pip install` ซึ่งเรายังไม่ได้ตรวจว่ามีอะไรเพิ่มเข้ามา) ความต่างนี้เกิดเพราะ Image แบบเต็มมีเครื่องมือสร้างซอฟต์แวร์มาด้วย ซึ่งแบบฝึกยืนยันว่ามี `gcc` อยู่ใน `python:3.13` แต่ไม่มีใน `slim` (รัน) โปรแกรมที่รันอยู่ไม่ได้ใช้คอมไพเลอร์เลย ของพวกนี้จึงเป็นภาระเปล่า ๆ

ภาระนั้นมีสองด้าน ด้านแรกคือขนาด ซึ่งกินที่ดิสก์ ทำให้ดาวน์โหลดช้า และเสียเวลาตอนดึง Image ไปรันที่อื่น อีกด้านคือความปลอดภัย หนังสือบอกว่า Image แบบ All-in-One ที่ใส่เครื่องมือสร้างกับเครื่องมือรันไว้ด้วยกัน ทำให้ผู้โจมตีมีทางเลือกในการโจมตีโปรแกรมมากขึ้น และต้องอัปเดตบ่อยขึ้นเพราะมีของหลายอย่างที่ต้องตามแพตช์ (หนังสือ: Docker in Action หัวข้อ 10.2.1 หน้า 200) ตัวอย่างในหนังสือยกตัวอย่าง Image ที่เริ่มต้น 614 MB และจบที่ 708 MB

<Callout type="note" title="Alpine เล็กที่สุด แต่ยังไม่ใช่คำตอบเสมอไป">
ตัวเลข 54.1 MB ของ Alpine น่าสนใจ แต่เราได้ทดสอบแค่โปรแกรมที่ไม่ต้องคอมไพล์อะไร Alpine ใช้ไลบรารี C คนละตัวกับ Debian (Musl กับ Glibc) ซึ่งเป็นสิ่งที่ผู้ใช้ Alpine หลายคนเจอว่าแพ็กเกจบางตัวต้องคอมไพล์เอง แต่เรื่องนี้เรายังไม่ได้ลอง (ไม่ได้รัน)
</Callout>

</Step>

## Multi-stage Build ใช้ Image ใหญ่สร้าง แล้วส่งมอบด้วย Image เล็ก

บางครั้งเราต้องการเครื่องมือสร้างจริง ๆ ตอน Build เช่น คอมไพเลอร์ แต่ไม่ต้องการมันตอนรัน คำตอบคือ Multi-stage Build ซึ่งหนังสือจัดเป็นแพตเทิร์น Build Plus Runtime ที่ใช้ Image สร้างหนึ่งตัว แยกจาก Image รันที่เล็กกว่า (หนังสือ: Docker in Action หัวข้อ 10.2 หน้า 199) Dockerfile หนึ่งไฟล์มีหลายบรรทัด `FROM` ได้ ทุกบรรทัดเริ่ม Stage ใหม่ และ Image ที่ถูกส่งมอบคือ Stage สุดท้าย

```dockerfile
FROM python:3.13 AS build
RUN pip install --no-cache-dir --target /deps six==1.17.0

FROM python:3.13-slim
COPY --from=build /deps /deps
ENV PYTHONPATH=/deps
COPY app.py /app/app.py
CMD ["python", "/app/app.py"]
```

Stage แรกชื่อ `build` ใช้ Image ใหญ่ติดตั้งแพ็กเกจลงโฟลเดอร์ `/deps` Stage ที่สองเริ่มจาก `slim` แล้วใช้ `COPY --from=build` หยิบเฉพาะโฟลเดอร์นั้นข้าม Stage มา ผลที่ได้คือ (รัน)

| Dockerfile | ขนาด Image (MB) |
|---|---|
| Stage เดียวบน `python:3.13` | 1121.1 |
| Multi-stage (สร้างบน `python:3.13` ส่งมอบบน `slim`) | 118.4 |

Image แบบ Multi-stage ยังรันโปรแกรมได้ผลเดิม ไม่มี `gcc` และไม่มี Layer ของ Image ใหญ่ติดมาเลยสักชั้น เราตรวจเทียบรายการ Layer แล้ว (รัน) ถ้าอยากหยุดที่ Stage แรกเพื่อดูผล ใช้ `docker build --target build` ซึ่งได้ Image ขนาดใหญ่ของ Stage นั้น (รัน) กดเล่น Lab ทีละขั้นเพื่อดูว่าอะไรถูกทิ้งไว้ข้างหลัง

<MultiStageLab client:visible />

เรื่องที่ควรเข้าใจให้ตรงคือ Stage สร้างไม่ได้หายไปไหน มันยังอยู่ในเครื่องเราและใช้ Cache ตอน Build ซ้ำ แต่ไม่ถูกส่งมอบ และคนที่ได้ Image ของเราไม่เห็นมัน

</Step>

## ให้ Container รันด้วยผู้ใช้ที่ไม่ใช่ Root

ค่าตั้งต้นของ Container คือรันเป็น Root แบบฝึกลองรัน `id -u` ใน `python:3.13-slim` ที่ไม่ได้ตั้ง `USER` ได้ 0 (รัน) การรันด้วย Root เป็นความเสี่ยง เพราะถ้าโปรแกรมถูกเจาะ ผู้โจมตีได้สิทธิ์สูงสุดในนั้นทันที หนังสือบอกว่าวิธีโจมตีที่รู้จักเพื่อหลุดออกจาก Container พึ่งพาสิทธิ์ผู้ดูแลระบบภายใน Container ทั้งนั้น (หนังสือ: Docker in Action หัวข้อ 8.6.2 หน้า 169) หลักปฏิบัติจึงคือสร้างผู้ใช้อื่น แล้วลดสิทธิ์ให้เร็วที่สุดเท่าที่ทำได้

ในแบบฝึกเราสร้างผู้ใช้ `app` (UID 10001) แล้วลองสองแบบ แบบแรก `COPY` โปรแกรมเข้าโฟลเดอร์ `/app` ที่ Root เป็นเจ้าของ แล้วใช้ `USER app` ซึ่งโปรแกรมพยายามเขียนไฟล์ลงในโฟลเดอร์นั้น (รัน)

```text
PermissionError: [Errno 13] Permission denied: '/app/out.txt'
```

โปรแกรมไม่มีสิทธิ์เขียนในโฟลเดอร์ของ Root แบบที่สองเรากำหนดเจ้าของให้ชัดเจน ทั้งโฟลเดอร์ด้วย `chown` ตอนสร้างและไฟล์ด้วย `COPY --chown=app:app` เพราะจาก[บท 4](/docker/dockerfile/#copy-add-และเจ้าของไฟล์) เรารู้ว่า `COPY` ให้ Root เป็นเจ้าของเสมอ ผลคือโปรแกรมรันด้วย UID 10001 และเขียนไฟล์ได้ปกติ (รัน)

มีสองเรื่องที่ควรรู้เพิ่ม เรื่องแรก คนสั่ง `docker run` เปลี่ยนผู้ใช้ทับค่าของ Image ได้เสมอด้วย `--user` แบบฝึกสั่ง `--user 0` แล้วได้ Root ทั้งที่ Image ตั้ง `USER app` ไว้ (รัน) หนังสือก็บอกเรื่องเดียวกันว่า Image ป้องกันไม่ให้ Container รันเป็น Root ไม่ได้ สิ่งที่ผู้สร้าง Image ทำได้ดีที่สุดคือสร้างผู้ใช้ที่ไม่ใช่ Root และตั้งเป็นค่าตั้งต้น (หนังสือ: Docker in Action หัวข้อ 8.6.2 หน้า 169) เรื่องที่สอง ถ้าลดสิทธิ์เร็วเกินไป ขั้นตอนใน Dockerfile อาจทำงานไม่ได้ เช่น ตั้ง `USER 1000` แล้วจึงสั่ง `touch` ไฟล์ของ Root หนังสือยกตัวอย่างนี้ไว้ (หนังสือ: Docker in Action หัวข้อ 8.6.2 หน้า 169 ไม่ได้รัน) และยกอีกตัวอย่างว่าโปรแกรมที่ต้องใช้พอร์ตต่ำกว่า 1024 ก็ต้องใช้สิทธิ์สูงกว่า ซึ่งเราไม่ได้ลอง

## ความลับตอน Build ต้องไม่ติดอยู่ใน Image

ใน[บท 4](/docker/dockerfile/) เราเห็นว่าค่าที่ส่งผ่าน `ARG` และถูกใช้ในบรรทัด `RUN` ไปปรากฏใน `docker history` ถ้าตอน Build ต้องใช้ความลับจริง ๆ เช่น Token สำหรับดาวน์โหลดแพ็กเกจส่วนตัว BuildKit มีวิธีที่ไม่ทิ้งรอย คือ `RUN --mount=type=secret` ซึ่งเอาไฟล์ความลับมาติดตั้งไว้ให้เฉพาะบรรทัดนั้นตอนรัน แล้วถอดออกทันที

```dockerfile
RUN --mount=type=secret,id=tok sh -c 'wc -c < /run/secrets/tok > /length.txt'
```

```bash
docker build --secret id=tok,src=token.txt -t dlab-secret .
```

ในแบบฝึกเราสร้างไฟล์ `token.txt` ที่มีความลับ 25 ตัวอักษร และให้บรรทัด `RUN` เขียนความยาวของมันลงไฟล์ (รัน) ผลคือบรรทัดนั้นอ่านความลับได้จริงตอน Build ไฟล์ผลลัพธ์บอกว่ายาว 25 แต่ค่าความลับเองไม่ได้อยู่ใน `docker history` และไม่มีโฟลเดอร์ `/run/secrets` อยู่ใน Container ที่รัน และเรายังบันทึก Image ออกมาเป็นไฟล์ `.tar` แล้วค้นทุกไบต์ ก็ไม่พบค่านั้นที่ไหนเลย (รัน)

<Callout type="warn" title="ขอบเขตของสิ่งที่ตรวจ">
เราตรวจแค่ว่าค่าความลับไม่อยู่ในประวัติ ไม่อยู่ใน Container และไม่อยู่ในไฟล์ที่บันทึกออกมาของ Image ตัวนั้น ถ้าบรรทัด `RUN` เอาค่าความลับไปเขียนลงไฟล์เองอย่างจงใจ มันก็ยังค้างอยู่ได้ ซึ่งการ Mount ความลับไม่ได้ป้องกันตรงนั้น และเรายังไม่ได้ลองส่งความลับตอนรัน (เช่น ผ่าน Compose หรือ Docker Secret) ซึ่งเป็นอีกเรื่องหนึ่ง
</Callout>
