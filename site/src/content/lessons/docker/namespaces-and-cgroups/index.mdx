## Namespace คือมุมมองของ Kernel ที่แยกให้ Process แต่ละตัว

ใน[บท 1](/docker/containers/#container-คือ-process-ที่เห็นโลกเล็ก-ๆ) เราเห็นว่า Container คือ Process ธรรมดาที่เห็นตัวเองเป็น PID 1 และเราเรียกกลไกนั้นว่า PID Namespace โดยยังไม่ได้เปิดดู ตอนนี้ถึงเวลาแล้ว หนังสือ Container Security อธิบายสั้น ๆ ว่า ถ้า Cgroup คุมทรัพยากรที่ Process ใช้ได้ Namespace ก็คุมสิ่งที่มันมองเห็น การเอา Process ไปไว้ใน Namespace ทำให้จำกัดสิ่งที่ Process นั้นเห็นได้ (หนังสือ: Container Security บทที่ 4 หน้า 31) Namespace ที่ Linux รองรับมีเจ็ดชนิด คือ `cgroup`, `ipc`, `mnt` (จุดเชื่อมระบบไฟล์), `net`, `pid`, `user` และ `uts` (ชื่อเครื่อง) และ Process หนึ่งตัวอยู่ใน Namespace ชนิดละหนึ่งอันเสมอ (หนังสือ: Container Security บทที่ 4 หน้า 32)

เราเปิดดูได้จริงจากไฟล์ `/proc/self/ns` ที่แสดงหมายเลขของแต่ละ Namespace ที่ Process นั้นอยู่ ในแบบฝึกเราเริ่ม Container สองตัวพร้อมกัน แล้วเทียบกับ Container ที่ขอใช้ Namespace ของ Linux ที่รัน Engine (รัน)

| Namespace | Container สองตัวเทียบกัน | Container เทียบกับ Linux ที่รัน Engine |
|---|---|---|
| `cgroup`, `ipc`, `mnt`, `net`, `pid`, `uts` | ต่างกัน | ต่างกัน |
| `user` | เหมือนกัน | เหมือนกัน |

หกชนิดแรกต่างกันทุกตัว ซึ่งแปลว่า Container แต่ละตัวมีของตัวเองครบ ส่วน `user` เหมือนกันหมด ซึ่งแปลว่า Docker ไม่ใช้ User Namespace ในค่าตั้งต้น ผู้ใช้ `root` ใน Container คือ UID 0 ตัวเดียวกับ `root` ของ Linux ที่รัน Engine และนี่เป็นเรื่องที่เราจะกลับมาดูใน[บทสุดท้ายของเส้นทางนี้](/docker/capstone-pipeline/#ล็อก-container-ของตัวโหลดทีละชั้น) (ถ้าอยากแยกต้องเปิด `userns-remap` ซึ่งเรายังไม่ได้ลองและไม่ได้รัน)

<Callout type="warn" title="ข้อผิดพลาดที่เราเจอตอนวัด">
ตอนแรกเรารัน Container ทีละตัวแล้วเทียบเลข Namespace ปรากฏว่าเหมือนกันหมด ซึ่งผิด เราสันนิษฐานว่าเมื่อ Container ตัวแรกจบ Namespace ของมันถูกปล่อย แล้ว Kernel เอาหมายเลขนั้นกลับมาให้ Namespace ของตัวถัดไป (ข้อนี้เป็นการอนุมานของเรา ไม่ได้เปิดดูโค้ดของ Kernel) สิ่งที่แน่ใจคือผลที่เห็น และการเทียบต้องทำกับ Container ที่ยังรันอยู่พร้อมกัน เราจึงแก้ให้แบบฝึกทำอย่างนั้น (รัน)
</Callout>

กดสลับในแล็บดู เลือกให้ Container มี Namespace ของตัวเอง หรือใช้ของ Host ร่วมกันทีละอย่างด้วย `--pid=host`, `--net=host` และ `--uts=host` ภาพที่เห็นข้างในเปลี่ยนไปตามนั้น ตัวอย่างเช่น ตาราง Process ที่เห็นไม่กี่ตัวกลายเป็นของทั้ง Linux

## แชร์ Namespace โดยตั้งใจ และสร้างเองโดยไม่ใช้ Docker

เมื่อ Namespace เป็นของที่ให้ใครมาใช้ร่วมกันได้ Docker ก็ให้เราเลือกได้ ถ้าใช้ `--pid=container:A` Container B จะอยู่ใน PID Namespace เดียวกับ A และเห็น Process ของ A ซึ่งแบบฝึกเห็น `sleep 300` ของ A จาก B (รัน) และ `--network=container:A` ทำให้ B อยู่ใน Network Namespace เดียวกับ A ได้ที่อยู่ IP ตัวเดียวกัน (รัน) รูปแบบนี้ใช้เมื่ออยากแนบเครื่องมือสำหรับตรวจสอบเข้ากับ Container ที่รันอยู่ โดยไม่ต้องแก้ Image ของมัน

อีกเรื่องที่น่าสนใจคือ เราสร้าง Namespace เองได้โดยไม่ต้องมี Docker คำสั่ง `unshare` ของ Linux ทำสิ่งเดียวกับที่ Docker ทำ ในแบบฝึกเรารัน Container แบบ `--privileged` แล้วใช้ `unshare -u` เปลี่ยน Hostname ข้างใน Namespace ใหม่ ผลคือ

```text
inside=made-by-unshare
outside=d4377a1e8f5a was=d4377a1e8f5a
```

ข้างในเปลี่ยนเป็น `made-by-unshare` ได้ ส่วนข้างนอกยังเป็นชื่อเดิม และ `unshare -p` ก็ทำให้ `ps` เริ่มนับ PID จาก 1 (รัน) แปลว่า Container ที่ Docker สร้างคือการเรียกกลไกเดียวกันนี้หลายตัวพร้อมกัน แล้วเพิ่มส่วนอื่นที่หนังสือเล่าไว้ใน[บท 1](/docker/containers/) เช่นการเปลี่ยนรากของระบบไฟล์ การถอดสิทธิ์ และ Cgroup (หนังสือ: Docker in Action หัวข้อ 1.1.4 หน้า 6)

## Cgroup คือขีดจำกัดที่เขียนเป็นไฟล์

Namespace คุมสิ่งที่เห็น ส่วนปริมาณที่ใช้ได้เป็นหน้าที่ของ Cgroup หนังสือบอกว่า Cgroup จำกัดทรัพยากร เช่น Memory, CPU และ I/O ของเครือข่ายที่กลุ่ม Process ใช้ได้ และมี Cgroup ชนิด Pid ที่จำกัดจำนวน Process ทั้งหมด ซึ่งกันผลของ Fork Bomb ได้ นอกจากนี้ เพราะ Container ก็คือ Process ธรรมดา Cgroup จึงจำกัดทรัพยากรของแต่ละ Container ได้ (หนังสือ: Container Security บทที่ 3 หน้า 23) Kernel ส่งข้อมูลเรื่อง Cgroup ออกมาเป็นไฟล์ในโฟลเดอร์ `/sys/fs/cgroup` หนังสืออธิบายด้วยตัวอย่างของ Cgroup แบบ v1 ที่มีไฟล์เช่น `memory.limit_in_bytes` ส่วนในเครื่องนี้เป็น v2 ที่ชื่อไฟล์ต่างออกไปเล็กน้อย เราลองใส่ตัวเลือกของ Docker แล้วอ่านไฟล์เหล่านี้จากข้างใน (รัน)

| ไฟล์ | ไม่ใส่ตัวเลือก | `--memory 64m --cpus 0.5 --pids-limit 20` |
|---|---|---|
| `memory.max` | `max` | `67108864` |
| `cpu.max` | `max 100000` | `50000 100000` |
| `pids.max` | `max` | `20` |

ตัวเลือกของ Docker แปลงเป็นค่าในไฟล์โดยตรง `--memory 64m` คือ 67,108,864 ไบต์ และ `--cpus 0.5` คือโควตา 50,000 ไมโครวินาทีต่อทุก 100,000 ไมโครวินาที ซึ่งแปลว่าโปรแกรมรันได้ครึ่งหนึ่งของแต่ละช่วงเวลา ส่วน `docker inspect` อ่านขีดจำกัดเดียวกันจากข้างนอกได้ (รัน) ทีนี้ลองดูว่าโปรแกรมที่ชนขีดจำกัดเจออะไร

เราให้โปรแกรม Python ขอ Memory ทีละ 10 MB ไปถึง 120 MB ใต้ขีดจำกัดต่าง ๆ (รัน)

| ขีดจำกัด Memory | MB สุดท้ายที่พิมพ์ | ผล |
|---|---|---|
| ไม่จำกัด | 120 | จบ |
| 256 MB | 120 | จบ |
| 64 MB | 50 | ถูกฆ่า (`OOMKilled`, Exit Code 137) |
| 32 MB | 20 | ถูกฆ่า |

เมื่อ Memory หมด Kernel ฆ่าโปรแกรมทิ้งเลย ซึ่งตรงกับ Exit Code 137 ที่เราเห็นในบทวงจรชีวิตว่าคือ SIGKILL ส่วน CPU ต่างออกไป เราให้โปรแกรมวนลูปเปล่าเป็นเวลา 2.5 วินาทีแล้ววัดว่าได้เวลา CPU เท่าไรต่อเวลาจริง (รัน)

| ขีดจำกัด CPU | เวลา CPU ต่อเวลาจริง | จำนวนครั้งที่ถูกพัก |
|---|---|---|
| ไม่จำกัด | 1.01 | 0 |
| `--cpus 1` | 1.01 | 0 |
| `--cpus 0.5` | 0.52 | 25 |
| `--cpus 0.25` | 0.26 | 26 |

โปรแกรมไม่ตาย มันแค่ถูก Kernel พักเป็นช่วง ๆ จนได้เวลาตามโควตา ตัวสุดท้ายคือจำนวน Process เราสั่ง `--pids-limit 10` แล้วให้ Shell เปิด Process เบื้องหลัง 30 ตัว ผลคือ Shell แจ้งว่า `can't fork: Resource temporarily unavailable` (รัน) การ Fork ที่เกินขีดถูกปฏิเสธ นี่คือสิ่งที่กัน Fork Bomb ตามที่หนังสือบอกไว้ กดเลือกขีดจำกัดใน Lab เพื่อเทียบสองแบบของการหมดทรัพยากรที่ต่างกัน คือถูกฆ่ากับถูกพัก
