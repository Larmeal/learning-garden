## รัน Container แรก แล้วเจอเรื่องแปลก

สมมติว่าเราใช้คอมพิวเตอร์ Windows แล้วเพิ่งติดตั้ง Docker เสร็จ ลองพิมพ์คำสั่งสั้น ๆ ที่ถามว่า Kernel ที่กำลังรันอยู่คือรุ่นอะไร

```bash
docker run --rm alpine:3.22 uname -r
```

```text
6.18.58.1-microsoft-standard-WSL2
```

คำสั่งนี้มีสี่ส่วน `docker run` สั่งให้ Docker สร้าง Container ขึ้นมาแล้วเริ่มทำงาน `--rm` ให้ลบ Container ทิ้งเมื่อมันจบ `alpine:3.22` คือชื่อ Image ที่เราจะใช้ (ชื่อ Alpine กับ Tag `3.22`) และส่วนสุดท้ายคือโปรแกรมที่จะรันข้างใน ซึ่งก็คือ `uname -r` ที่พิมพ์เลขรุ่นของ Kernel

เอ๊ะ ผลลัพธ์ที่ได้กลับเป็น Kernel ของ Linux ที่มีคำว่า Microsoft อยู่ในชื่อ ทั้งที่เราไม่เคยติดตั้ง Linux และเรารัน Image ของ Alpine ซึ่งเป็นระบบปฏิบัติการอีกตัวหนึ่ง ถ้าลองรันกับ Image อีกสองตัวและอ่านไฟล์ `/etc/os-release` ที่บอกชื่อระบบปฏิบัติการ เราจะเห็นผลอย่างนี้ (รัน)

| Image | `uname -r` | ชื่อระบบปฏิบัติการใน `/etc/os-release` |
|---|---|---|
| `alpine:3.22` | 6.18.58.1-microsoft-standard-WSL2 | Alpine Linux v3.22 |
| `busybox:1.37` | 6.18.58.1-microsoft-standard-WSL2 | ไม่มีไฟล์นี้เลย |
| `python:3.13-slim` | 6.18.58.1-microsoft-standard-WSL2 | Debian GNU/Linux 13 (trixie) |

ทั้งสามตัวบอกว่าใช้ Kernel เดียวกัน แต่ไฟล์ของระบบที่อยู่ข้างในต่างกัน ตรงนี้อยากให้ตั้งคำถามในใจกันหน่อยว่าเป็นไปได้อย่างไร ถ้าแต่ละ Container เป็น "คอมพิวเตอร์เครื่องใหม่" มันก็น่าจะมี Kernel ของตัวเอง

## Container ไม่ได้บูตระบบปฏิบัติการใหม่

คำตอบของเรื่องข้างบนคือ Container ไม่ใช่ Virtual Machine Virtual Machine จำลองฮาร์ดแวร์ขึ้นมาทั้งชุดแล้วติดตั้งระบบปฏิบัติการลงไปทั้งตัว ซึ่งใช้เวลาสร้างหลักนาทีและกิน Resource เยอะเพราะต้องรันระบบปฏิบัติการทั้งตัวควบคู่กับโปรแกรมที่เราต้องการ ส่วน Container ไม่ได้ใช้การจำลองฮาร์ดแวร์เลย โปรแกรมที่รันอยู่ใน Container คุยกับ Kernel ของคอมพิวเตอร์ที่รันมันโดยตรง (หนังสือ: Docker in Action หัวข้อ 1.1.3 หน้า 5)

กดเลือกจำนวนโปรแกรมใน Lab แล้วเทียบสองฝั่งดู ฝั่ง Virtual Machine ต้องมี Kernel เพิ่มขึ้นทีละตัวตามจำนวนโปรแกรม ส่วนฝั่ง Container มี Kernel ตัวเดียวและแต่ละโปรแกรมแค่เพิ่มไฟล์ของตัวเองเข้ามา

<KernelStackLab client:visible />

แล้วทำไมคอมพิวเตอร์ Windows ของเราถึงมี Kernel ของ Linux ให้ Container ใช้ คำตอบคือ Docker Desktop เปิด Linux ขึ้นมาให้ตัวหนึ่งหลังฉาก (ในเครื่องนี้ใช้ WSL2) แล้วรัน Docker Engine และ Container ทั้งหมดอยู่ข้างใน ซึ่งหนังสือก็เล่าไว้ว่าผู้ใช้ Docker บน Mac และ Windows รวมถึงผู้ใช้ Cloud เกือบทั้งหมดรัน Docker อยู่ใน Virtual Machine อีกที เทคโนโลยีสองอย่างนี้จึงใช้ร่วมกันได้ (หนังสือ: Docker in Action หัวข้อ 1.1.3 หน้า 5) ดังนั้นคำว่า Host ในบทเรียนนี้จะหมายถึง Linux ตัวนั้นที่ Docker Engine รันอยู่ และเราจะไม่ได้หมายถึง Windows

<Callout type="note" title="Docker ไม่ได้สร้างเทคโนโลยี Container">
Docker ใช้ของที่อยู่ใน Kernel ของ Linux อยู่แล้ว โดยหนังสือไล่กลไกที่ Docker ใช้สร้าง Container ไว้สิบอย่าง ตั้งแต่ Namespace ของ PID, `hostname`, ระบบไฟล์, การสื่อสารระหว่าง Process, เครือข่ายและผู้ใช้ ไปจนถึง `chroot`, `cgroups`, การถอดสิทธิ์ (CAP Drop) และ Security Module (หนังสือ: Docker in Action หัวข้อ 1.1.4 หน้า 6) เดี๋ยวเราจะมาเปิดดูกลไกพวกนี้ทีละอันกันในช่วงหลังของเส้นทางนี้ ตอนนี้จำไว้แค่ว่ามันคือฟีเจอร์ของ Kernel ที่ Docker ทำให้ใช้ง่ายขึ้น
</Callout>

## Container คือ Process ที่เห็นโลกเล็ก ๆ

ถ้า Container ไม่ใช่คอมพิวเตอร์ตัวใหม่ มันก็ควรเป็นอะไรที่เล็กกว่านั้น เรามาลองพิสูจน์กันดู เริ่มจากรัน Container ที่ทำงานค้างไว้ห้านาที (`-d` คือให้ทำงานอยู่เบื้องหลัง และ `--name` ตั้งชื่อให้เรียกง่าย) แล้วถามว่าข้างในมี Process อะไรบ้าง

```bash
docker run -d --name a alpine:3.22 sleep 300
docker exec a ps -o pid,args
```

```text
PID   COMMAND
    1 sleep 300
    7 ps -o pid,args
```

`docker exec` ให้เรารันคำสั่งเพิ่มเข้าไปใน Container ที่ทำงานอยู่ จะเห็นว่าข้างในมี `sleep 300` ซึ่งเป็นโปรแกรมที่เราสั่งให้เริ่ม ตัวเลข PID ของมันคือ 1 และมีแค่ `ps` ที่เราเพิ่งเรียกเป็นอีกตัวหนึ่ง นั่นหมายถึงทั้ง Container มี Process อยู่เท่านี้ (รัน)

ทีนี้ลองมองจากข้างนอกบ้าง ในแบบฝึกเรารัน Container สามตัวที่ใช้ Image ต่างกัน แล้วเปิด `ps` อีกรอบจาก Container ที่ใช้ `--pid=host` ซึ่งทำให้มองเห็น Process ของ Engine ทั้งหมด ผลที่ได้คือ

```text
  2746  sleep 300
  2795  sleep 301
  2840  python -c import time; time.sleep(302)
```

โปรแกรมเดียวกันที่เคยเป็น PID 1 ข้างใน กลายเป็น Process ธรรมดาที่มีเลขของตัวเองข้างนอก (เลข PID เปลี่ยนไปทุกครั้งที่รัน) และ `docker top a` ก็แสดง Process เดียวกันนี้ให้เราจากฝั่ง Engine ด้วย เรื่องนี้ตรงกับที่หนังสืออธิบายว่าสถานะของ Container ผูกกับโปรแกรมตัวเดียวที่รันข้างใน (หนังสือ: Docker in Action หัวข้อ 1.1.1 หน้า 3) ส่วนที่ทำให้มันเห็นตัวเองเป็น PID 1 คือกลไกที่เรียกว่า PID Namespace ซึ่งเป็นหนึ่งในสิบอย่างที่เล่าไปเมื่อกี้

ลองกดสลับที่ยืนใน Lab ดู ถ้ายืนในห้อง a จะเห็นแค่โปรแกรมของเราตัวเดียวและมันเป็น PID 1 ห้องอื่นกับ Process อื่นของ Engine หายไปจากสายตาหมด แต่พอยืนข้างนอก ทุกอย่างกลับมา และไม่มีโปรแกรมของ Container ตัวไหนเป็น PID 1 เลย

## Container อยู่ได้เท่ากับที่ Process อยู่

เมื่อ Container คือ Process ตัวหนึ่ง ชีวิตของมันก็ผูกกับ Process ตัวนั้น ลองรันโปรแกรมที่หลับแค่สามวินาที แล้วถามสถานะตอนเริ่มกับตอนผ่านไปห้าวินาที

```bash
docker run -d --name short alpine:3.22 sleep 3
docker inspect -f '{{.State.Status}}' short      # running
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' short   # หลังผ่านไป 5 วินาที: exited 0
```

ตอน `sleep` ยังหลับอยู่ Container มีสถานะ `running` พอ `sleep` จบก็กลายเป็น `exited` และได้ Exit Code 0 ซึ่งเป็นรหัสที่โปรแกรมคืนตอนจบ (รัน) ถ้าเราสั่ง `docker start short` Docker จะรันโปรแกรมเดิมอีกรอบ และสถานะกลับไปเป็น `running` (รัน) หนังสือสรุปเรื่องนี้ไว้ว่า ถ้าโปรแกรมรันอยู่ Container ก็รันอยู่ และถ้าโปรแกรมหยุด Container ก็หยุด (หนังสือ: Docker in Action หัวข้อ 1.1.1 หน้า 3)

เรื่องนี้อธิบายอาการที่คนมือใหม่เจอบ่อย คือรัน Container แล้วมันจบทันที ซึ่งมักเป็นเพราะโปรแกรมที่สั่งให้รันทำงานเสร็จแล้วออกไปเอง ไม่ได้แปลว่า Docker มีปัญหา เดี๋ยวเราจะมาคุยเรื่องสถานะ Exit Code และการหยุด Container อย่างละเอียดกันในบทถัด ๆ ไป

</Step>

## Image คือแม่แบบ Container คือของที่ทำออกมา

มีอีกคำที่เราใช้มาตลอดโดยยังไม่ได้อธิบาย คือ Image `alpine:3.22` เราลองรัน Container ตัวหนึ่งที่เขียนไฟล์ลงไปแล้วอ่านกลับ จากนั้นรัน Container ตัวใหม่จาก Image เดิมแล้วลองอ่านไฟล์เดียวกัน

```bash
docker run --name w1 alpine:3.22 sh -c 'echo hello > /note.txt && cat /note.txt'
docker run --rm alpine:3.22 cat /note.txt
```

```text
hello
cat: can't open '/note.txt': No such file or directory
```

Container ตัวแรกเขียนและอ่านไฟล์ได้ แต่ Container ตัวที่สองไม่เห็นไฟล์นั้นเลย ทั้งที่มาจาก Image เดียวกัน และพอเราสั่ง `docker start -a w1` กลับไปที่ตัวแรก ไฟล์ `note.txt` ก็ยังอยู่ (รัน) ภาพที่ควรจำคือ Image เป็นแม่แบบที่อ่านได้อย่างเดียว ส่วน Container แต่ละตัวมีที่เขียนของตัวเอง หนังสือใช้ภาพของตู้คอนเทนเนอร์ขนส่งสินค้า Image คือตู้ที่ถูกแพ็กไว้พร้อมส่ง และ Container ที่สร้างจาก Image เดียวกันไม่แชร์การเปลี่ยนแปลงของระบบไฟล์ให้กัน (หนังสือ: Docker in Action หัวข้อ 1.1.5 หน้า 7)

ทุกครั้งที่เรารัน `docker run` Docker จะสร้าง Container ตัวใหม่เสมอ ตัวเก่าที่จบไปแล้วยังค้างอยู่ในรายการจนกว่าเราจะลบ เราจึงเห็น `w1` กับ `short` เป็น `Exited` อยู่ใน `docker ps -a` และนี่คือเหตุผลที่เราใส่ `--rm` ในคำสั่งที่ไม่ต้องการเก็บผลไว้ ส่วนข้างในของ Image ว่าประกอบด้วยอะไรและทำไมถึงไม่เปลี่ยนตอนเราเขียนไฟล์ เป็นเรื่องของ[บทถัดไป](/docker/images-and-layers/)

<Callout type="warn" title="คำสั่งในหนังสือบางตัวใช้ไม่ได้กับ Docker 29">
หนังสือที่เราอ้างพิมพ์เมื่อปี 2019 มีคำสั่ง `docker inspect -f '{{.NetworkSettings.IPAddress}}'` สำหรับดูที่อยู่ IP ของ Container ซึ่งใน Docker 29.2.1 ใช้ไม่ได้แล้ว ฟิลด์นั้นถูกเอาออก Docker ตอบว่า `map has no entry for key "IPAddress"` ต้องอ่านจากชื่อเครือข่ายแทน เช่น `{{.NetworkSettings.Networks.bridge.IPAddress}}` (รัน) ถ้าคำสั่งจากหนังสือเล่มไหนพังอย่างนี้ ให้ลองเทียบกับ `docker inspect` ตัวเต็มก่อน
</Callout>

</Step>
