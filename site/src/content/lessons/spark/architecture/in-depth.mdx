## local[*] คืออะไรกันแน่

`get_spark()` ในโปรเจกต์นี้สร้าง Session แบบ `local[*]` และเราตรวจเจอว่า

- `sc.master` คือ `local[*]` และ `defaultParallelism` เท่ากับจำนวน Core ของคอมพิวเตอร์ (16)
- ถ้าถาม Executor ผ่าน REST API ของ UI จะได้รายการเดียวคือ `driver` ที่มี `totalCores` = 16 นั่นคือ **ใน local mode driver เป็น Executor เพียงตัวเดียว** และ Task ทุกตัวรันเป็น Thread ใน JVM เดียวกัน
- `spark.range(1_000_000)` แตกเป็น 16 Partition ตามจำนวน Core
- ถ้าเรียก `SparkSession.builder.getOrCreate()` อีกครั้ง เราจะได้ **Object เดิม** (`is spark` เป็น True) ไม่ได้สร้างใหม่ จึงปลอดภัยที่จะเรียกซ้ำในหลายไฟล์

ผลก็คือบนคอมพิวเตอร์เครื่องเดียว คุณจะเห็นการรันแบบขนานจริง (Task ขนานกันหลาย Thread) แต่ไม่มีเครือข่ายคั่นกลาง ต้นทุนของ Shuffle ใน Cluster จริงจึงสูงกว่าที่เห็นที่นี่ (ดู[บทที่ 11](/spark/deployment-spark-ui/#cluster-manager-และ-deploy-mode) สำหรับ Cluster ที่เปิดเองได้)

</Step>

## PySpark คือ Client ของ JVM

Spark เขียนด้วย Scala/Java ดังนั้นโปรแกรม Python ของคุณจึงไม่ได้รัน Spark เอง แต่คุยกับ JVM ผ่าน **Py4J** (Gateway ที่ให้ Python เรียก Method ของ Object ใน JVM)

- `type(spark).__module__` คือ `pyspark.sql.session` และ `sc._jvm` เป็นทางเข้าสู่ JVM จากตรงนี้เราเรียกคลาสของ Spark ได้ตรง ๆ เช่น `sc._jvm.org.apache.spark.sql.SparkSession.active().version()` ได้ `4.2.0` และ `sc._jvm.java.lang.System.getProperty("java.version")` ได้ `21.0.13` (Spark 4 ต้องใช้ Java 17 ขึ้นไป)
- DataFrame ใน Python เก็บ **Handle** ของ Dataset ที่อยู่ใน JVM (`df._jdf` ซึ่งเป็น `JavaObject`) ทุก Transformation ที่คุณเรียกจึงเป็นการเรียก Method ฝั่ง JVM ผ่าน Gateway แล้วได้ Handle ใหม่กลับมา ข้อมูลไม่เคยอยู่ใน Python เลย ยกเว้นตอนที่สั่งดึง (หัวข้อสุดท้าย)
- การเรียกแต่ละครั้งเป็นแค่ข้อความเล็ก ๆ ผ่าน Socket โค้ด DataFrame ใน Python จึงไม่ช้ากว่า Scala ในส่วนที่เป็นแผน ส่วนที่ช้ากว่าคือตอนที่ข้อมูลต้องข้ามไป Python จริง ๆ เช่น Python UDF ([บทที่ 8](/spark/udf/#ข้อมูลเดินทางอย่างไร))

ลองเลือก Action แล้วกดเล่น เราจะเห็นว่าอะไรข้าม Gateway กลับมา และอะไรไม่ข้ามเลย

<Py4jLab client:visible />

เรื่องนี้ก็เป็นเหตุผลที่ Spark Connect ([บทที่ 11](/spark/deployment-spark-ui/#spark-connect-client-กับ-server-แยกกัน)) แยกฝั่ง Client ออกมาได้ คือเปลี่ยนจาก Py4J เป็น gRPC แต่ Client ก็ยังส่งแค่ "แผน" ไปให้ฝั่งที่มี JVM

</Step>

## Memory ของ Driver

Driver ของ Local Session ได้ Heap 1 GiB ตามค่าเริ่มต้น (`spark.driver.memory`) ตัวเลขที่ UI รายงานคือ **455,501,414 ไบต์** ซึ่งเป็นส่วนที่ Spark นำไปจัดการเอง และตรงกับสูตรเป๊ะ (ตรวจแล้ว)

```
(heap 1,073,741,824 - reserved 314,572,800) x 0.6 = 455,501,414
```

ลองเปลี่ยนขนาด Heap ดูว่าส่วนที่ Spark จัดการได้จริงเป็นสัดส่วนเท่าไร

<DriverMemoryLab client:visible />

ส่วนที่เหลือคือ Reserved (300 MiB ที่ Spark กันไว้) และ User Memory (ที่เหลือของ Heap) [บทที่ 13](/spark/internals/#unified-memory-storage-กับ-execution-แบ่งกัน) อธิบายสูตรนี้ไว้ละเอียดกว่านี้ และแสดงว่า Storage กับ Execution แบ่งกันอย่างไร ตอนนี้เราเอาไปใช้ได้ว่า Heap 1 GiB ไม่ได้แปลว่าข้อมูลของคุณจะใช้ได้ 1 GiB เพราะ Spark เอาไปจัดการจริงราวสองในห้า ส่วนที่เหลือของ Driver ใช้กับ Object อื่น

</Step>

## อะไรกลับมาที่ Driver

ข้อมูลอยู่ที่ Executor และจะถูกส่งกลับมา **เฉพาะตอนที่คุณสั่ง** เท่านั้น (ตรวจแล้ว)

- `collect()` คืน `Row` ทั้งหมดเป็น List ใน Memory ของ Driver (`[(0, 0), (1, 1), (2, 4), ...]`)
- `show()` พิมพ์ผล (ค่าเริ่มต้น 20 แถว) และคืน `None`
- `toPandas()` ก๊อปผลทั้งหมดเข้า Memory ของ Driver เป็น Pandas DataFrame (บน `limit(2)` ได้รูปร่าง `(2, 1)`)
- `write` ไม่ผ่าน Driver เพราะ Executor เขียนไฟล์เอง

ผลทั้งหมดของ `collect()` และ `toPandas()` ต้องพอดีกับ Memory ของ Driver (และต้องไม่เกิน `spark.driver.maxResultSize` ที่ตั้งไว้ 1g ตาม[บทที่ 7](/spark/performance-tuning/#ข้อห้ามที่มีหลักฐาน) ซึ่งตรวจแล้วว่าตั้ง 1m แล้ว `collect()` 2 ล้านแถวล้ม) เราจึงควรกรองหรือรวมข้อมูลให้เล็กลงก่อนดึงมา

<Callout type="tip" title="ทุกอย่างที่ตามมาใช้ภาพนี้">
Driver วางแผนและแจกงาน Executor ทำงานและถือข้อมูล Cluster Manager จัดสรรคอมพิวเตอร์ให้ ภาพนี้จะถูกใช้ต่อใน Scheduler ([บทที่ 13](/spark/internals/)), การ Deploy ([บทที่ 11](/spark/deployment-spark-ui/#cluster-manager-และ-deploy-mode)) และการตามหา Memory ที่หายไป ([บทที่ 7](/spark/performance-tuning/#spill-เมื่อ-memory-ไม่พอ))
</Callout>

</Step>
