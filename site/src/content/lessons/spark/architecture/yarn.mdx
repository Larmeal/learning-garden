## ใครทำอะไรบน YARN

YARN เป็น Cluster Manager ของ Hadoop ที่ใช้ได้ทั้งกับ Spark, Hive, MapReduce และงานอื่น ๆ รวมกันบน Cluster เดียว จึงมีบทบาทมากกว่า Standalone

| บทบาท | อยู่ที่ไหน | ทำอะไร |
|---|---|---|
| ResourceManager (RM) | 1 ตัวต่อ Cluster | ถือ Core และ Memory ของทั้ง Cluster และตัดสินว่า Container ของแอปไหนจะไปอยู่บนคอมพิวเตอร์เครื่องไหน |
| NodeManager (NM) | ทุกคอมพิวเตอร์ใน Cluster | เป็นตัวแทนของ RM บนคอมพิวเตอร์เครื่องนั้น คอยเปิดและเฝ้า Container ตามที่ได้รับสั่ง |
| Container | บน NM | เป็นกล่อง Process ที่ถูกจำกัด Core และ Memory ทุกส่วนของ Spark ที่รันใน Cluster ก็คือ Container |
| ApplicationMaster (AM) | Container แรกของแอป | เป็นตัวแทนของแอปที่คุยกับ RM โดยจะขอ Container เพิ่ม คืน Container และรายงานสถานะ |

สิ่งที่ต่างจาก Standalone คือ **มี AM คั่นกลาง** Driver ไม่ได้คุยกับ RM เอง แต่ AM เป็นคนทำให้ ซึ่งทำให้ YARN รู้จัก "แอป" ของ Spark เป็นหน่วยหนึ่งที่มี Container ตัวแรกของตัวเอง ลองดูลำดับตั้งแต่ส่งงานจนได้ Task ในแล็บนี้ (สลับระหว่าง Cluster Mode กับ Client Mode ได้)

## Client Mode กับ Cluster Mode ต่างกันที่ Driver อยู่ไหน

ทั้งสองแบบมี AM แต่ AM ทำงานไม่เหมือนกัน (`Client.scala:1139-1144` เลือก Class ที่ AM รัน)

| | cluster mode | client mode |
|---|---|---|
| Driver อยู่ที่ไหน | ใน AM Container เป็น Thread ชื่อ Driver | บนคอมพิวเตอร์ที่รัน `spark-submit` หรือ Notebook |
| Class ของ AM | `ApplicationMaster` (`runDriver`) | `ExecutorLauncher` (`runExecutorLauncher`) |
| AM ทำอะไร | เรียกโปรแกรมของคุณ รอ SparkContext แล้วขอ Container | ต่อกลับไปหา Driver แล้วขอ Container แทน Driver |
| ปิดคอมพิวเตอร์ที่ส่งงาน | แอปยังรันต่อ (ถ้าตั้ง `spark.yarn.submit.waitAppCompletion=false` Spark-submit จะออกเลย) | แอปจบ เพราะ Driver หายไป |
| Executor ต้องต่อกลับ Driver ที่ไหน | ในคอมพิวเตอร์ของ Cluster ด้วยกัน | คอมพิวเตอร์ของคุณ ซึ่งต้องเปิด Firewall และตั้ง `spark.driver.host` ให้ถูก |
| เหมาะกับ | งานที่ปล่อยทิ้งไว้ (Production, Schedule) | งานโต้ตอบ (Notebook, `pyspark` Shell) ที่อยากเห็น Output ตรง ๆ |

มีสองข้อที่คนผิดกันบ่อย

- **การรัน Client Mode จากคอมพิวเตอร์นอก Cluster** ทำให้ Executor ต่อกลับมาไม่ได้ (NAT, Firewall) แอปจึงค้างตอนรอ Executor ลงทะเบียน
- **การคิดว่าใช้ Cluster Mode แล้ว Log จะอยู่ที่ Terminal** เพราะ Driver อยู่ใน Container เราจึงต้องดู Log ผ่าน YARN (`yarn logs -applicationId ...`) หรือ UI ของ RM

ใน Cluster Mode ถ้า AM Container ตาย YARN เปิด AM ตัวใหม่ได้ตาม `spark.yarn.maxAppAttempts` (ถ้าไม่ตั้งจะใช้ค่าของ YARN เอง) แต่เพราะ Driver อยู่ในนั้น โปรแกรมของคุณจึงต้องเริ่มใหม่ตั้งแต่ต้น

</Step>

## AM ถาม RM ถี่แค่ไหน

AM ไม่ได้รอ RM ตอบแบบ Callback แต่มี Thread ชื่อ Reporter ที่เรียก `allocate()` ไปที่ RM เป็นช่วง ๆ การเรียกครั้งหนึ่งทำสองอย่างพร้อมกัน คือส่งคำขอ Container ที่ค้างอยู่ไป และรับ Container ที่ RM จัดให้ตอนนี้กลับมา (พร้อมรายการ Container ที่จบหรือตายไปแล้ว)

<YarnAllocLab client:visible />

กติกามีดังนี้ (จาก `ApplicationMaster.scala`) ขณะที่ยังมี Container ค้างขอ AM จะรอ 200 มิลลิวินาที แล้วเพิ่มเป็นเท่าตัวทุกครั้งจนถึงเพดาน `spark.yarn.scheduler.heartbeat.interval-ms` (3 วินาที) และเมื่อไม่มีอะไรค้างแล้ว AM ก็ยังเรียกทุก 3 วินาทีอยู่ดี เพราะ

- การเรียกนี้เป็น Heartbeat ที่บอก RM ว่า AM ยังอยู่ ถ้าเงียบนานเกิน RM จะถือว่า AM ตาย
- มันเป็นทางเดียวที่ RM จะบอก AM ว่า Container ไหนจบหรือถูกฆ่า

</Step>

## ขนาด Container และไฟล์ที่ต้องส่งไปด้วย

**ขนาด Container ของ Executor** ไม่ได้มีแค่ `spark.executor.memory` แต่เป็นผลรวมที่ `YarnAllocator` ขอจาก RM (`totalMemMiB` ใน `ResourceProfile`) คือ Heap บวก `spark.executor.memoryOverhead` (และ `spark.executor.pyspark.memory` ถ้าตั้งไว้) NodeManager จะฆ่า Container ที่ใช้ Memory เกินขนาดที่ขอ และ RM จะปฏิเสธคำขอที่ใหญ่เกินกว่าเพดานที่ Cluster ตั้งไว้ ดังนั้นอาการ "Executor ถูกฆ่าทั้งที่ Heap ไม่เต็ม" มักเป็นเรื่องของ Overhead (Python Worker, Buffer, Native) ไม่ได้เกิดจาก Heap

**ไฟล์ที่ต้องส่ง** เพราะ Container เปิดบนคอมพิวเตอร์เครื่องอื่น จึงต้องมี Jar ของ Spark และไฟล์ Conf ไปด้วย `Client.submitApplication()` จะอัปโหลดไปไว้ Staging Directory ใน HDFS (ใต้โฟลเดอร์บ้านของผู้ใช้ เปลี่ยนได้ด้วย `spark.yarn.stagingDir`) ถ้าไม่ได้ตั้ง `spark.yarn.jars` หรือ `spark.yarn.archive` Spark จะแพ็ก Jar ทั้งหมดใต้ `SPARK_HOME` ขึ้นไปทุกครั้งที่ส่งงาน (ซอร์สเตือนด้วย Log `falling back to uploading libraries under SPARK_HOME`) ถ้าตั้ง `spark.yarn.archive` ให้ชี้ไปที่ไฟล์ใน HDFS ก็จะข้ามขั้นนี้ได้

</Step>

## เมื่อมีอะไรตาย

| ตายอะไร | เกิดอะไรขึ้น |
|---|---|
| Executor Container | AM รู้จากรายการ Completed Containers ที่ RM ส่งมากับ `allocate()` (`YarnAllocator.processCompletedContainers`) แล้วขอ Container ใหม่แทน และนับจำนวนที่ล้มไว้ เมื่อถึง `spark.executor.maxNumFailures` (ค่าเริ่มต้น `max(3, 2 x จำนวน executor)`) AM จะปิดแอปด้วย `EXIT_MAX_EXECUTOR_FAILURES` |
| NodeManager หรือคอมพิวเตอร์ที่ล้ม | Container ทั้งหมดบนคอมพิวเตอร์เครื่องนั้นหายพร้อมกัน RM รายงานเป็น Container ที่จบ แล้ว AM ขอใหม่ที่อื่น |
| AM Container | RM เปิด AM ใหม่จนถึงจำนวนที่ตั้ง (`spark.yarn.maxAppAttempts`) ใน Cluster Mode Driver จะเริ่มใหม่ทั้งหมดเพราะอยู่ใน AM ส่วนใน client mode driver ยังอยู่บนคอมพิวเตอร์ของคุณ (ไม่ได้ตรวจรายละเอียดว่า Driver รับ AM ตัวใหม่อย่างไร) |
| Driver (Client Mode) | แอปจบ AM กับ Container ทั้งหมดถูกคืนให้ Cluster |

</Step>

<Step>

## เช็กตัวเอง

- บน YARN ใครคุยกับ RM แทนแอป และทำไมต้องมีตัวนั้น
- Client Mode กับ Cluster Mode ต่างกันที่ไหน และถ้าปิด Laptop ที่ส่งงาน แอปแต่ละแบบเป็นอย่างไร
- ตั้ง `spark.executor.memory = 4g` แต่ Executor ถูก NodeManager ฆ่า ควรดู Config ตัวไหนก่อน
- ทำไม AM ต้องเรียก `allocate()` ทุก 3 วินาทีแม้ไม่ขออะไรเพิ่ม

เมื่อมี Cluster จริง ลองเทียบกับภาพดู ใน Log ของ AM จะมีบรรทัด `Started progress reporter thread with (heartbeat: ..., initial allocation: ...)` และ `Launching container ... for executor with ID ...` ที่ตรงกับสองภาพด้านบน

</Step>
