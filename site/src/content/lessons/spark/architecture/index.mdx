## ใครทำอะไร

แอปพลิเคชัน Spark มีสามบทบาท driver ที่ถือโปรแกรมของคุณและวางแผน executor ที่ลงมือคำนวณ และ cluster manager ที่จัดสรรเครื่องให้ ดูว่าแต่ละบทบาทเข้ามาเมื่อไรและทำอะไร ตามลำดับเวลาของแอปหนึ่งตัว (เลือกได้ว่าจบด้วย `collect()` หรือ `write`)

<RolesFlowLab client:visible />

สรุปจากภาพ

| บทบาท | ทำอะไร | ไม่ทำอะไร |
|---|---|---|
| Driver | ถือโค้ดของคุณ สร้างแผน ขอ executor แบ่งงานเป็น task ส่ง task และรวมสถานะ | ไม่คำนวณข้อมูล (ยกเว้นเมื่อคุณสั่งดึงผลมา) |
| Cluster manager | รู้ว่าเครื่องไหนว่างเท่าไร และเปิด executor ให้ตามที่ driver ขอ | ไม่ถือข้อมูล ไม่แจก task ไม่อยู่ระหว่าง driver กับ executor หลังเปิด executor แล้ว |
| Executor | รับ task อ่าน partition จาก storage คำนวณ เก็บ cache และเขียนผล | ไม่ตัดสินว่าจะทำงานอะไร |

โค้ด PySpark ของคุณรันใน Python process แล้วคุยกับ JVM ของ Spark ผ่าน Py4J การคำนวณหนักเกิดใน JVM ฝั่ง executor ยกเว้น Python UDF ที่ต้องเรียก Python process เพิ่ม ([บทที่ 8](/spark/udf/#ข้อมูลเดินทางอย่างไร))

</Step>

## เครื่องคุณรันแบบไหน

`get_spark()` ใน `spark_session.py` สร้าง session แบบ `local[*]` driver และ executor อยู่ใน process เดียว และ executor คือ thread จำนวนเท่า core ของเครื่อง

<Callout type="try" title="ลองดูในเครื่อง">

```python
from spark_session import get_spark

spark = get_spark("arch")
sc = spark.sparkContext
print(sc.master, sc.defaultParallelism, spark.version)
```

บนเครื่องที่ใช้ทดสอบบทนี้ ได้ `local[*] 16 4.2.0` เลข 16 คือจำนวน core ของเครื่องนั้น เครื่องคุณอาจได้เลขอื่น

</Callout>

เพราะเหตุนี้ การเรียนแนวคิดแบบกระจายบนเครื่องเดียวจึงทำได้ task หลายตัวรันพร้อมกันจริง แต่ไม่มีเครือข่ายคั่นกลาง ใน cluster จริง ต้นทุนการส่งข้อมูลข้ามเครื่องจะสูงกว่าที่เห็นที่นี่ ตารางนี้เทียบสองแบบ บทบาทยังเป็นสามอย่างเดิม ที่ต่างคือแต่ละบทบาทอยู่ที่ไหน

| | `local[*]` (เครื่องคุณ) | cluster (หลายเครื่อง) |
|---|---|---|
| Driver | อยู่ใน process เดียวกับ executor | เป็น process ของตัวเอง ตัวเดียวต่อแอปพลิเคชัน |
| Executor | thread ใน process ของ driver จำนวนเท่า core ของเครื่อง | process (JVM) แยกกัน หลายตัว กระจายหลายเครื่อง |
| Cluster manager | ไม่ต้องมี | ต้องมี: standalone, YARN หรือ Kubernetes (แยกเป็นหน้าย่อยด้านล่าง) |
| Task ที่รันพร้อมกัน | ได้ ตามจำนวน core ของเครื่อง | ได้ ตามจำนวน core รวมของ executor ทั้งหมด |
| ข้อมูลที่ shuffle | ย้ายกันใน memory ของ process เดียว ไม่ผ่านเครือข่าย | ส่งข้ามเครื่องผ่านเครือข่าย จึงแพงกว่า |
| ข้อมูลต้นทาง | ไฟล์ใน disk ของเครื่อง | storage ที่ทุกเครื่องเข้าถึงได้ เช่น HDFS หรือ S3 |

</Step>

## Cluster Manager มีกี่แบบ

เมื่อรันบน cluster จริง driver ต้องรู้ว่าจะไปขอ executor จากใคร บอกผ่าน `--master` ลำดับ "driver ขอ แล้ว executor ติดต่อกลับ" เหมือนกันหมด สิ่งที่ต่างคือใครคือผู้จัดสรร และใครเป็นคนสั่งเปิด executor

| `--master` | ผู้จัดสรร | หน่วยที่รัน | อ่านต่อ |
|---|---|---|---|
| `local[N]` | ไม่มี (process เดียว) | thread | หัวข้อก่อนหน้า |
| `spark://host:7077` | Master ของ Spark เอง | process ที่ Worker เปิด | [Standalone](/spark/architecture/standalone/) (รันจริงแล้ว) |
| `yarn` | ResourceManager ของ Hadoop (มี ApplicationMaster คั่น) | container | [YARN](/spark/architecture/yarn/) (อ่านจากซอร์ส) |
| `k8s://https://...` | kube-scheduler (driver ขอ pod เองผ่าน API server) | pod | [Kubernetes](/spark/architecture/kubernetes/) (อ่านจากซอร์ส) |

แต่ละหน้ามีแอนิเมชันของลำดับตั้งแต่ส่งงานจนได้ task และแล็บเฉพาะของ cluster manager นั้น เรื่อง deploy mode, Spark UI และ dynamic allocation อยู่ใน[บทที่ 11](/spark/deployment-spark-ui/)

</Step>

## SparkSession

`SparkSession` เป็นจุดเข้าใช้งานเดียวสำหรับอ่านข้อมูล สร้าง DataFrame และรัน SQL สร้างด้วย `SparkSession.builder...getOrCreate()` ถ้ามี session อยู่แล้วจะได้ตัวเดิมกลับมา ใน notebook หรือ Databricks มักมีตัวแปร `spark` ให้ใช้เลย

</Step>

## ข้อมูลมาถึง Driver เมื่อไร

โดยปกติข้อมูลอยู่ที่ executor และไม่ผ่าน driver คำสั่งที่ดึงข้อมูลมาที่ driver มีไม่กี่ตัว

- `show()` ดึง 20 แถวแรกมาพิมพ์
- `collect()` และ `toPandas()` ดึงผลทั้งหมด
- `write` ให้ executor เขียนไฟล์เอง ไม่ผ่าน driver

<Callout type="warn" title="ระวัง collect() กับข้อมูลใหญ่">
ผลของ `collect()` และ `toPandas()` ต้องไปอยู่ในหน่วยความจำของ driver ตัวเดียว ถ้าผลใหญ่กว่าหน่วยความจำที่ driver มี โปรแกรมจะล้ม ให้กรองหรือรวมข้อมูลให้เล็กลงก่อนเรียกสองคำสั่งนี้
</Callout>

</Step>
