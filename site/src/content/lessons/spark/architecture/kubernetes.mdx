## ไม่มี Cluster Manager ของ Spark

Kubernetes ไม่มีบทบาทอย่าง Master หรือ ResourceManager ที่ Spark ต้องคุยด้วย สิ่งที่ Spark คุยด้วยคือ **API Server** ของ Kubernetes เพื่อสร้างและดู Pod ส่วนการเลือกว่า Pod จะไปอยู่ Node ไหนเป็นงานของ `kube-scheduler` ซึ่ง Spark ไม่เกี่ยวข้อง

| ของที่เกี่ยวข้อง | ทำอะไร |
|---|---|
| `spark-submit` | ประกอบ Driver Pod จาก Config (Feature Step หลายตัว) สร้าง Pod กับ ConfigMap แล้วเฝ้าดูสถานะ Pod (`KubernetesClientApplication`) |
| API Server | เป็นที่เดียวที่ทุกฝ่ายใช้อ่านและเขียนสถานะ Pod |
| Driver Pod | Pod ที่ข้างในรัน `spark-submit` แบบ Client Mode อีกชั้น (จาก `entrypoint.sh` คำสั่ง `driver`) |
| `ExecutorPodsAllocator` (ใน Driver) | เทียบจำนวน Executor ที่ต้องการกับ Pod ที่มีอยู่ แล้วสร้าง Executor Pod เพิ่มเอง |
| Executor Pod | JVM ที่ลงทะเบียนกับ Driver แล้วรับ Task |

ข้อสำคัญที่ต่างจาก YARN คือ **Driver เป็นคนสั่งสร้าง Executor เอง** ไม่มี AM คั่นกลาง ลองดูลำดับในแล็บนี้ (สลับไปดูสถานการณ์ที่ Driver Pod ถูกลบได้ด้วย)

## Driver ขอ Executor Pod ทีละกี่ตัว

Driver ไม่ได้สร้างครบทีเดียว `ExecutorPodsAllocator` ทำเป็นรอบ ๆ โดยแต่ละรอบจะสร้าง Pod ไม่เกิน `spark.kubernetes.allocation.batch.size` (ค่าเริ่มต้น 20) แล้วรอ `spark.kubernetes.allocation.batch.delay` (1 วินาที) ก่อนเริ่มรอบถัดไป ลองเปลี่ยนจำนวนที่ต้องการดู

<K8sBatchLab client:visible />

มีสามเรื่องที่ควรรู้

- ถ้าขอ Executor จำนวนมาก (หลักร้อย) การสร้างคำขอจะใช้เวลาหลายวินาทีก่อนที่ Kubernetes จะเริ่มวาง Pod แรกด้วยซ้ำ เราปรับ `batch.size` ได้ถ้า Cluster รับไหว
- `spark.kubernetes.allocation.maxPendingPods` (ค่าเริ่มต้นไม่จำกัด) จำกัดจำนวน Pod ที่ค้างอยู่ที่ Pending พร้อมกัน ช่วยไม่ให้แอปเดียวถมคำขอจน Scheduler ล้น
- Pod ที่ค้างที่ Pending นานเกินไป Spark ไม่ได้แก้ให้ ถ้า Node ไม่พอ Pod จะรอ Cluster Autoscaler หรือรอจน Node ว่าง ส่วน `spark.kubernetes.allocation.executor.timeout` (600 วินาที) จะลบเฉพาะ Pod ที่ Kubernetes ยังไม่เห็นในสถานะ Pending

</Step>

## ทำไมลบ Driver Pod แล้ว Executor หายตาม

Pod ของ Executor ที่ `BasicExecutorFeatureStep` ประกอบขึ้นมี **ownerReference ชี้ไปที่ Driver Pod** (ตั้งเป็น Controller) เมื่อ Driver Pod ถูกลบหรือหายไป Garbage Collector ของ Kubernetes จะลบ Object ที่ Owner หายไปด้วย ผลคือไม่ต้องมี Cluster Manager คอยตามเก็บ Executor ที่เหลือ ใน Kubernetes การ "ปิดแอป" จึงเท่ากับการลบ Driver Pod

ConfigMap ของ Spark Conf และ Resource อื่นที่ Driver ต้องใช้ ก็ผูก ownerReference กับ Driver Pod ในลักษณะเดียวกัน (`KubernetesClientApplication.run`)

ส่วน Executor ที่ตายกลางทางเองจะต่างออกไป Driver เฝ้าสถานะ Pod ผ่านการ Watch (`ExecutorPodsWatchSnapshotSource`) และ Polling สำรอง (`ExecutorPodsPollingSnapshotSource`) เมื่อรู้ว่า Pod หายไป ก็จะขอ Pod ใหม่มาแทน จนกว่าจะถึง `spark.executor.maxNumFailures` ซึ่งทำให้แอปล้ม

</Step>

## เทียบกับ YARN และ Standalone

| | standalone | YARN | Kubernetes |
|---|---|---|---|
| ใครแบ่ง Resource | Master ของ Spark | ResourceManager | Kube-scheduler |
| ใครขอ Executor แทนแอป | `StandaloneAppClient` ใน Driver | ApplicationMaster | `ExecutorPodsAllocator` ใน Driver |
| หน่วยที่รัน | Process ที่ Worker เปิด | Container | Pod |
| Driver ใน Cluster ได้ | ไม่ได้สำหรับ Python | ได้ (Cluster Mode ใน AM) | ได้ (Driver Pod) |
| ปิดแอปด้วย | Driver จบ | Driver/AM จบ | ลบ Driver Pod (Executor หายตาม) |

บน Kubernetes มีหลายเรื่องที่ต้องตั้งเพิ่ม ซึ่งไม่มีใน Cluster Manager อื่น เช่น Image ที่มี Spark (`spark.kubernetes.container.image`), Namespace, Service Account ที่มีสิทธิ์สร้าง Pod และเรื่อง Resource ของ Pod (`spark.kubernetes.executor.request.cores` ต่างจาก `spark.executor.cores` ที่เป็นจำนวน Task พร้อมกัน)

</Step>

<Step>

## เช็กตัวเอง

- บน Kubernetes ใครเป็นคนบอกให้สร้าง Executor Pod และผ่านใคร
- ทำไมลบ Driver Pod แล้ว Executor Pod หายไปด้วยโดยไม่มีใครสั่ง
- ขอ Executor 100 ตัวด้วยค่าเริ่มต้น ใช้กี่รอบ และกี่วินาทีกว่าจะสร้างคำขอครบ
- Pod ของ Executor ค้างที่ Pending ควรไปดูที่ไหน (Spark หรือ Kubernetes)

</Step>
