## Parquet อ่านน้อยกว่า CSV เท่าไร

ตารางทดลองมี 9 คอลัมน์ ได้แก่ `id`, `country` (5 ค่า), `status` (4 ค่า), `user` (5,000 ค่า), `amount`, `qty`, `ts` และสตริง Hash สุ่มสองคอลัมน์ (`token`, `note`) เราเขียนเป็น CSV (มี Header) และ Parquet (Snappy ค่าเริ่มต้น) แล้ววัด

| | CSV | Parquet |
|---|---|---|
| ขนาดบน Disk | 71.7 MiB | 48.9 MiB |
| ไบต์ที่อ่านตอน `agg(sum("amount"))` | **73.3 MiB** (ทั้งไฟล์) | **0.10 MiB** |

- **ขนาดไฟล์** Parquet เล็กกว่า CSV เพียงราวหนึ่งในสามในตารางนี้ เพราะสตริง Hash สุ่มบีบอัดไม่ได้เลย ถ้าข้อมูลมีค่าซ้ำเยอะ (Country, Status, ตัวเลขช่วงแคบ) ส่วนต่างจะมากกว่านี้ เนื่องจากตัวเลขขนาดไฟล์ขึ้นกับข้อมูลมาก เราจึงอย่าจำเป็นตัวคูณ
- **ไบต์ที่อ่าน** ตรงนี้คือความต่างที่ชัดที่สุด CSV ต้องอ่านทุกบรรทัดตั้งแต่ต้นจนจบเพื่อหาคอลัมน์เดียว จึงได้ 73.3 MiB (มากกว่าไฟล์นิดหน่อยเพราะนับ Header ของทุกไฟล์) ส่วน Parquet เก็บข้อมูลทีละคอลัมน์ Spark จึงอ่านเฉพาะ Column Chunk ของ `amount` ได้ **0.10 MiB** ราวหนึ่งในห้าร้อยของไฟล์
- แผนยืนยันว่า Spark รู้ล่วงหน้า คือ `ReadSchema: struct<amount:double>` (Column Pruning ของ[บทที่ 6](/spark/catalyst-aqe/#ผลของ-pushdown-ที่เห็นใน-plan-ของไฟล์))

"ไบต์ที่อ่าน" คือ `inputBytes` ที่ Spark UI แสดงในหน้า Stage ซึ่งเราอ่านผ่าน REST API ([บทที่ 11](/spark/deployment-spark-ui/#ทักษะที่สำคัญที่สุดคืออ่าน-spark-ui)) ส่วน "size of files read" ของ Node `Scan` ใน SQL Tab เป็นขนาดไฟล์ที่เปิด ไม่ใช่ไบต์ที่อ่านจริง ซึ่งให้ภาพที่ต่างกันได้

</Step>

## ข้างในไฟล์ Parquet: Row Group และสถิติ

ไฟล์ Parquet แบ่งแถวเป็นก้อนที่เรียกว่า **Row Group** แต่ละ Row Group จะเก็บข้อมูลทีละคอลัมน์ (Column Chunk) และบันทึก **สถิติของแต่ละคอลัมน์** คือ `min`, `max` และจำนวน Null ไว้ใน Footer ของไฟล์

ในการทดลองนี้ เราตั้ง `parquet.block.size` เป็น 256 KiB เพื่อให้ไฟล์ 600,000 แถวมี **290 Row Group ก้อนละ 2,072 แถว** (ค่าเริ่มต้นของ Parquet ใหญ่กว่านี้มาก ไฟล์จริงจึงมี Row Group น้อยกว่า) พออ่าน Footer ด้วย `pyarrow` ก็เห็น `min`/`max` ของ `id` ในแต่ละก้อน

Spark จะส่งเงื่อนไข Filter ไปให้ตัวอ่านไฟล์ (**Predicate Pushdown**) แล้วตัวอ่านก็เทียบกับ `min`/`max` ของแต่ละ Row Group และข้ามก้อนที่ไม่มีทางมีแถวที่ตรง ใน Plan เราจะเห็น

```
PushedFilters: [IsNotNull(id), GreaterThanOrEqual(id,1000), LessThanOrEqual(id,1999)]
```

และ **`Filter` ยังอยู่เหนือ Scan เหมือนเดิม** เพราะการข้ามทำระดับ Row Group เท่านั้น แถวที่เหลือจึงยังต้องกรองซ้ำ

ผลจะเป็นอย่างไรขึ้นกับว่าข้อมูลเรียงแบบไหน เราทดลองกับสองไฟล์ที่มีแถวชุดเดียวกัน ต่างกันที่ลำดับ (เรียงตาม `id` กับเรียงตามคอลัมน์สตริงอื่น) ใช้ Filter เดียวกันคือ `id BETWEEN 1000 AND 1999` แล้ววัดจำนวนแถวที่ตัวอ่านไฟล์ส่งออก (Metric `number of output rows` ของ Node Scan)

| ไฟล์ | แถวที่ตัวอ่านส่งออก |
|---|---|
| เรียงตาม `id` | **2,072** (Row Group เดียว) |
| เรียงตามคอลัมน์อื่น | **597,928** (เกือบทุก Row Group) |

<ParquetSkipLab client:visible />

จะเห็นว่า Pushdown ไม่ได้ช่วยเสมอไป เราต้องให้ข้อมูลเรียงหรือจัดกลุ่มตามคอลัมน์ที่ใช้ Filter บ่อย เพื่อให้ `min`/`max` ของแต่ละก้อนแคบ (ตรงกับที่ Table Format อย่าง Delta ทำด้วย OPTIMIZE และ Data Skipping ใน[บทที่ 10](/spark/table-formats/#performance-log-ให้ของแถม))

<Callout type="note" title="[บทที่ 6](/spark/catalyst-aqe/#ผลของ-pushdown-ที่เห็นใน-plan-ของไฟล์) เคยบอกว่ายังไม่ได้ทดสอบ">
[บทที่ 6](/spark/catalyst-aqe/#ผลของ-pushdown-ที่เห็นใน-plan-ของไฟล์) ใช้ CSV ในตัวอย่าง Pushdown เพราะตอนนั้นเขียน Parquet บน Windows ไม่ได้ ตอนนี้เราตรวจแล้วว่า Parquet ข้าม Row Group ได้ตามที่เขียนไว้ และใน Plan ของ Parquet `PushedFilters` กับ `Filter` อยู่คู่กันเหมือน CSV
</Callout>

## partitionBy และ Partition Pruning

`df.write.partitionBy("country").parquet(path)` ได้โฟลเดอร์ `country=id`, `country=jp`, `country=sg`, `country=th`, `country=vn` (วัดจริง) และ **ค่า `country` ไม่ได้อยู่ในไฟล์ Parquet** ถ้าเปิดไฟล์ในโฟลเดอร์ `country=th` ด้วย `pyarrow` จะไม่เจอคอลัมน์ `country` เพราะค่ามาจากชื่อโฟลเดอร์ ตอนอ่านทั้งโฟลเดอร์ Spark จะเติมคอลัมน์กลับให้

Filter ด้วยคอลัมน์ Partition จะถูกจัดการก่อนเปิดไฟล์ใด ๆ ใน Plan เราจะเห็น `PartitionFilters: [isnotnull(country#..), (country#.. = th)]` และผลที่วัดได้ (`number of output rows` ของ Scan) เป็นดังนี้

| Query | แถวที่อ่าน |
|---|---|
| ทั้งตาราง | 600,000 |
| `country = 'th'` | **120,000** (หนึ่งในห้า) |

สิ่งที่ต่างจาก Predicate Pushdown ข้างบนคือ Partition Pruning ไม่ต้องเปิดไฟล์ที่ถูกข้ามเลย (ข้ามทั้งโฟลเดอร์) ส่วน Pushdown ต้องเปิดไฟล์อ่าน Footer ก่อนจึงข้าม Row Group ได้

</Step>

## เขียนกี่ไฟล์

จำนวนไฟล์ที่ได้ขึ้นกับ **จำนวน Partition ของ DataFrame ตอนเขียน** โดยแต่ละ Task จะเขียนหนึ่งไฟล์ (วัดจริง)

| DataFrame | ไฟล์ Parquet |
|---|---|
| `range` 16 partition | 16 |
| `.repartition(50)` | 50 |
| `.coalesce(1)` | 1 |
| 16 Partition แล้ว `partitionBy("k")` ที่มี 5 ค่า | **80** (16 Task x 5 ค่า) |

แถวสุดท้ายคือกับดักไฟล์เล็ก เพราะทุก Task จะเขียนไฟล์แยกให้ทุกค่า Partition ที่มันถืออยู่ ถ้าแต่ละ Task มีข้อมูลของหลายค่า จำนวนไฟล์จึงเป็นผลคูณ วิธีแก้คือ `repartition("k")` ก่อนเขียน เพื่อให้ข้อมูลของค่าเดียวกันอยู่ใน Task เดียวกัน (ข้อนี้เป็นหลักการจากการดูจำนวนไฟล์ ยังไม่ได้วัดเวลาอ่าน)

ไฟล์เล็กจำนวนมากแย่ตรงที่ทุกไฟล์มีต้นทุนตอนเปิด (อ่าน Footer, สร้าง Task) และตอนอ่านก็จะได้ Task เยอะเกินจำเป็น

</Step>

## อ่านกี่ Partition

ตอนอ่านไฟล์ Spark จะแบ่งงานเป็น Partition ตามขนาดไฟล์ `spark.sql.files.maxPartitionBytes` มีค่าเริ่มต้น **128 MiB** (`134217728b` ที่อ่านจาก `spark.conf`) ไฟล์ที่ใหญ่กว่านั้นจะถูกหั่นเป็นช่วง ส่วนไฟล์เล็กอาจถูกรวมหลายไฟล์ต่อ Partition หรืออยู่ Partition ละไฟล์ ก็ขึ้นกับจำนวน Core และต้นทุนการเปิดไฟล์ (ผู้เขียนไม่ได้อ่านสูตรเต็ม ผลที่เห็นในแล็บคือหนึ่งไฟล์ต่อหนึ่ง Partition)

เราวัดจริงกับ 16 ไฟล์เล็ก ค่าเริ่มต้นได้ **16 Partition** (หนึ่งต่อไฟล์) แต่ถ้าตั้ง `maxPartitionBytes` เป็น 20,000 ไบต์จะได้ **32 Partition** (ไฟล์ถูกหั่นเป็นช่วง) ข้อนี้ปิดข้อสงสัยใน[บทที่ 7](/spark/performance-tuning/#จำนวน-partition-หลัง-shuffle) ที่เคยบอกว่ายังไม่ได้ทดสอบการแบ่ง Partition ตอนอ่านไฟล์

</Step>

## Write Mode

เราวัดจริงกับการเขียนซ้ำลงโฟลเดอร์เดิม

| Mode | พฤติกรรม |
|---|---|
| `error` (ค่าเริ่มต้น) | `AnalysisException: [PATH_ALREADY_EXISTS]` |
| `ignore` | ไม่ทำอะไร ข้อมูลเดิมอยู่ครบ (อ่านได้ 10 แถวเหมือนเดิม แม้สั่งเขียน 5 แถว) |
| `append` | เพิ่ม (10 เป็น 20 แถว) |
| `overwrite` | แทนที่ทั้งโฟลเดอร์ (เหลือ 3 แถว) |

`overwrite` จะลบของเดิมทั้งหมดก่อนเขียน ถ้า Job ล้มกลางทาง ข้อมูลเดิมก็หายไปแล้วด้วย ซึ่งเป็นเหตุผลหนึ่งที่ Table Format ([บทที่ 10](/spark/table-formats/#acid-ได้อย่างไรกับไฟล์ธรรมดา)) มี Transaction

</Step>

## inferSchema ทำอะไรเบื้องหลัง

`option("inferSchema", True)` ทำให้ Spark อ่านข้อมูลก่อนที่คุณจะเรียก Action ใด ๆ เพื่อเดาชนิด เราวัดด้วย Job Group และพบว่าการเรียก `read.csv(..., inferSchema=True)` อย่างเดียวเริ่ม **2 Job** ส่วนการให้ `schema` เองเริ่ม **0 Job** (ไม่แตะข้อมูลเลยจนกว่า Action จะมา)

ผลที่เดาได้ถูกในตารางนี้ (`qty` เป็น Int, `amount` เป็น Double) แต่การเดาต้องอ่านตัวอย่างข้อมูลทั้งหมดใน Partition (ทุก 4 ไฟล์ในแล็บ) ถ้าไฟล์ใหญ่ ต้นทุนนี้ก็ต้องจ่ายก่อนทุกอย่าง และถ้าไฟล์ใหม่มีค่าแปลกเพิ่มเข้ามา ชนิดที่เดาอาจเปลี่ยนไปเอง ในงานจริงเราจึงควรประกาศ Schema ไว้ในโค้ด

</Step>
