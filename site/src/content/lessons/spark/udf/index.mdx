## UDF คืออะไร และทำไมต้องระวัง

**UDF** (User-defined Function) คือฟังก์ชันที่คุณเขียนเอง แล้วเรียกใช้ในคำสั่ง DataFrame เหมือนฟังก์ชันของ Spark อย่าง `upper` หรือ `sum`

```python
from pyspark.sql.functions import udf

@udf("long")
def plus1(x):
    return x + 1

df.select(plus1("id"))
```

ความต่างที่สำคัญคือ `upper`, `+` และ `sum` เป็น **Expression ของ Catalyst** ที่ Spark รู้จักและรันใน JVM ภายใน Codegen ได้ แต่ฟังก์ชันของคุณเป็นโค้ด Python ซึ่ง Spark อ่านไม่ออก จึงทำได้แค่ส่งข้อมูลไปให้ Python Process รันแล้วรับผลกลับมา

เรื่องนี้ส่งผลตามมาสามข้อ ซึ่งเราจะพิสูจน์ด้วยการรันในบทนี้

1. UDF ช้ากว่า Built-in มาก เพราะต้องส่งข้อมูลข้าม Process
2. Catalyst มองเข้าไปในฟังก์ชันไม่ได้ จึงปรับแผนรอบ UDF ได้จำกัด
3. พฤติกรรมเรื่อง `NULL` และชนิดข้อมูลต่างจาก Built-in ในจุดที่เราไม่คาดคิด

<Callout type="warn" title="โปรเจกต์นี้ต้องมี Pandas และ Pyarrow">
ถ้า Environment มีแค่ `pyspark` การเขียน `@udf` จะ **ตกไปใช้เส้นทางเก่าเงียบ ๆ** พร้อม Warning ว่า "Arrow optimization failed to enable because PyArrow or Pandas is not installed" และ `pandas_udf` จะ Error `PACKAGE_NOT_INSTALLED` โปรเจกต์ `subjects/spark/code` ใส่ `pandas` และ `pyarrow` ไว้ให้แล้ว แต่ถ้าใช้ที่อื่นก็ต้องติดตั้งเองด้วย `uv add pandas pyarrow`
</Callout>

## UDF ในแผน: แยกได้จากสายตา

ใน `explain()` Python UDF จะแสดงเป็น Node แยกต่างหาก ส่วน Built-in ไม่เคยมี Node แบบนี้ (รัน: `exercises/08_udf.py`)

```
-- @udf("long")  (ค่าเริ่มต้นใน Spark 4.2) --
*(2) Project [pythonUDF0#4L AS plus1(id)#3L]
+- ArrowEvalPython [plus1(id#0L)#2L], [pythonUDF0#4L], 101
   +- *(1) Range (0, 10, step=1, splits=16)

-- @udf("long", useArrow=False) --
*(2) Project [pythonUDF0#7L AS plus1b(id)#6L]
+- BatchEvalPython [plus1b(id#0L)#5L], [pythonUDF0#7L]
   +- *(1) Range (0, 10, step=1, splits=16)

-- id + 1 (built-in) --
*(1) Project [(id#0L + 1) AS (id + 1)#17L]
+- *(1) Range (0, 10, step=1, splits=16)
```

ลองสังเกต `*(1)` และ `*(2)` ในสองแผนบน Node ของ UDF **คั่นกลาง** Whole-stage Codegen ทำให้แตกเป็นสองก้อน ส่วน Built-in อยู่ใน `*(1)` เดียว

| ชนิด | evalType | Node ในแผน |
|---|---|---|
| `@udf` ค่าเริ่มต้นใน 4.2 (Arrow-optimized) | 101 | `ArrowEvalPython` |
| `@udf(useArrow=False)` | 100 | `BatchEvalPython` |
| `@pandas_udf` (Series เป็น Series) | 200 | `ArrowEvalPython` |
| `pandas_udf` ที่คืนค่าเดียวต่อกลุ่ม (Grouped Agg) | 202 | `ArrowAggregatePython` |
| `df.mapInPandas(...)` | | `MapInPandas` |
| `groupBy(...).applyInPandas(...)` | | `FlatMapGroupsInPandas` |

มีสองข้อที่ควรจำไว้

- `@udf` ธรรมดาใน Spark 4.2 เป็น Arrow-optimized โดยค่าเริ่มต้น (`spark.sql.execution.pythonUDF.arrow.enabled = true`) ซึ่ง Docstring ใน `functions/builtin.py` ก็ยืนยันไว้ ส่วน Comment ใน `udf.py:99` ที่บอกว่า "ปิดเป็นค่าเริ่มต้น" เป็นข้อความเก่าที่ยังไม่ถูกแก้
- `applyInPandas` และ Grouped Agg มี `Sort` และ `Exchange hashpartitioning(…, 200)` ในแผน นั่นหมายความว่าต้อง Shuffle เต็มรูปแบบ ไม่ได้เป็นงานฝั่ง Map เบา ๆ

<Callout type="warn" title="ค่า Conf ถูกอ่านตอนสร้าง UDF">
Spark ตัดสินว่าจะเปิดหรือปิด Arrow ตอน **สร้าง Object UDF** ไม่ได้ตัดสินตอนรัน ถ้าตั้ง `arrow.enabled=false` ก่อนนิยาม จะได้ evalType 100 แต่ UDF ที่นิยามไว้ตอนยังเป็น `true` จะยังเป็น 101 ต่อให้ไปปิด Conf ทีหลัง (วัดจริง)
</Callout>

</Step>

## ข้อมูลเดินทางอย่างไร

Executor จะเปิด **Python Worker** (Process แยก) ให้แต่ละ Task แล้วต่อกันด้วย Socket โดย JVM จะส่ง Handshake ก่อน (เวอร์ชัน Python, ไฟล์, Broadcast, ฟังก์ชันที่ Pickle แล้ว) แล้วจึงส่งแถวตามไป เรามาลองดูสามเส้นทางเทียบกัน

เริ่มจากภาพรวมก่อน เป็น 24 แถวเท่ากัน ใช้งานเดียวกัน แต่เดินทางต่างกันสามแบบ ลองดูตัวนับใต้แต่ละเลน

| | แถวต่อก้อน | Worker เรียกฟังก์ชัน |
|---|---|---|

## ช้ากว่า Built-in เท่าไร

เราวัดโดยบังคับให้ข้อมูลอยู่ใน Partition เดียว (`spark.range(0, 5_000_000, 1, 1)`) เพื่อตัดค่าเริ่ม Worker หลายตัวออก แล้วใช้ `agg(sum(...))` คำนวณ `x + 1`

| วิธี | เวลา | เทียบ Built-in |
|---|---|---|
| Built-in `id + 1` | 0.05 วินาที | 1 เท่า |
| `pandas_udf` | 1.7 วินาที | ราว 35 เท่า |
| Python UDF แบบ Arrow | 2.1 วินาที | ราว 40 เท่า |
| Python UDF แบบ Pickle | 4.4 วินาที | ราว 85 เท่า |

ตัวเลขเหล่านี้มาจากคอมพิวเตอร์ของผู้เขียนในการรันครั้งเดียว ให้ดู **ลำดับและอันดับของขนาด** เท่านั้น ไม่ได้เป็น Benchmark สิ่งที่สคริปต์ยืนยันคือลำดับ Built-in เร็วกว่า pandas_udf อย่างน้อย 5 เท่า และ pandas_udf < Arrow UDF < Pickle UDF

ที่ช้าเพราะสามสาเหตุ คือต้อง Serialize ข้อมูลไปและกลับทุกแถว ต้องมี Python Process ต่อ Task และ (กับสองชนิดแรก) ต้องเรียกฟังก์ชัน Python ทีละแถว นอกจากนี้ Node ของ UDF ยังตัด Whole-stage Codegen อย่างที่เห็นในหัวข้อก่อนหน้าด้วย

<Callout type="note" title="บน Windows มีค่าเริ่ม Worker แพงกว่าที่คิด">
Spark ใช้ Daemon (`pyspark/daemon.py`) ที่ Fork Worker ให้เร็วบน Linux และ macOS แต่ Windows ไม่รองรับ `fork` จึงปิด Daemon (`PythonWorkerFactory.scala:96-99`) ทำให้ทุก Task ต้องเริ่ม `python.exe -m pyspark.worker` ใหม่ ต้นทุนคงที่ต่อ Task จึงเห็นได้ชัดเมื่อมี Partition เยอะ ถ้าคุณทดสอบ UDF บน Windows แล้วช้าผิดปกติแม้ข้อมูลเล็ก นี่คือเหตุผลหนึ่ง และเป็นเหตุผลที่การวัดในหัวข้อนี้ใช้ Partition เดียว
</Callout>

## UDF ขวางการ Optimize แค่ไหน

คำพูดที่ว่า "UDF ทำให้ Catalyst ปรับแผนไม่ได้" ถูกแค่บางส่วน เรามาลองดูทีละกรณี

<UdfBarrierLab client:visible />

สิ่งที่เห็นจากภาพมีดังนี้

- **Filter บนคอลัมน์อื่นลงไปอยู่ใต้ UDF ได้** ถ้า UDF เป็น Deterministic ซึ่งเป็นจุดที่คำพูดข้างบนมักพลาด
- Filter **บนผลของ UDF** อยู่ใต้ UDF ไม่ได้ และถ้ายังเลือกคอลัมน์ผลของ UDF ออกมาด้วย UDF จะถูกคำนวณ **สองรอบ** (วัดจากแผน: `ArrowEvalPython` สองตัว) ซึ่ง Docstring ของ `udf` ก็เตือนไว้ว่าฟังก์ชันอาจถูกเรียกมากกว่าจำนวนที่เขียน
- UDF ที่อยู่ **ในเงื่อนไข Filter** จะทำงานกับทุกแถวก่อน ไม่ได้ทำเฉพาะแถวที่ผ่านเงื่อนไขอื่น
- UDF ที่ประกาศ `asNondeterministic()` จะทำให้ Filter ไม่ถูกย้ายลงไปใต้มัน
- Catalyst **ไม่คิดค่าคงที่ให้ UDF** เช่น `F.lit(1) + F.lit(2)` กลายเป็น `3` แต่ `plus1(F.lit(1))` ยังเป็น Node ของ UDF

ส่วน Rule `ExtractPythonUDFs` ที่ดึง UDF ออกมาเป็น Node แยก ยังมีอีกสามเรื่อง

- UDF พี่น้องและ UDF ซ้อนกันของชนิดเดียวกันจะถูกรวมเป็น Node เดียว (`plus1(plus1(id))` กับ `plus1(v)` รวมเป็น `ArrowEvalPython` ตัวเดียว)
- UDF คนละชนิด (Pickle กับ Arrow) **ไม่ถูกรวม** จึงได้สอง Node ซ้อนกัน คือไป-กลับ Python สองรอบ
- ถ้า UDF ถูกห่อด้วย Expression เช่น `plus1("id") + 1` จะถูกดึงไปแค่ตัว UDF ส่วน `+ 1` อยู่ใน JVM

## กับดักเรื่อง NULL

เมื่อค่าเป็น NULL UDF จะได้รับ `None` เพราะ Spark ไม่ข้ามแถวให้เหมือนที่ Built-in ทำ

```python
inc = udf(lambda x: x + 1, "int")
df_with_null.select(inc("x")).collect()
# PythonException: ... TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'
```

เกิดขึ้นทั้งเส้นทาง Pickle และ Arrow (วัดทั้งสองแบบ) เราจึงต้องเขียนให้รองรับ `None` เอง เช่น `None if x is None else x + 1`

`pandas_udf` ยังมีกับดักเฉพาะตัวอีกข้อ คือคอลัมน์ Int ที่ **มี NULL** จะเปลี่ยนเป็น `float64` ใน Pandas (NULL กลายเป็น NaN) แต่ถ้าไม่มี NULL ในก้อนนั้นก็เป็น `int32` วัดจริงแล้ว Dtype ที่ฟังก์ชันเห็นคือ `float64` กับ `int32` ตามลำดับ ฟังก์ชันเดียวกันจึงเห็นชนิดต่างกันตามว่า Batch นั้นมี NULL หรือไม่ และ `s + 1` จึงให้ `2.0` ไม่ใช่ `2`

เอกสารของ `udf` ยังบอกด้วยว่า UDF **ไม่รองรับ Short-circuit** (`when(x.isNotNull(), my_udf(x))` ไม่ปกป้อง UDF จาก NULL) ข้อนี้อ้างจาก Docstring และยังไม่ได้รันพิสูจน์ จึงอย่าพึ่งการห่อ `when`

</Step>

## กับดักเรื่องชนิดของค่าที่คืน

ถ้าฟังก์ชันคืนค่าชนิดไม่ตรงกับที่ประกาศ สองเส้นทางจะให้ผลต่างกัน ซึ่งเป็นเหตุผลที่ Source เขียนไว้ว่าผลอาจไม่เหมือนกันเมื่อเปิดหรือปิด Arrow (วัดจริงด้วย Pandas 3.1.1 และ Pyarrow 26)

| ฟังก์ชันคืน | ประกาศ | Pickle (`useArrow=False`) | Arrow |
|---|---|---|---|
| `1.5` | Int | **NULL** | `1` (ตัดเศษเงียบ ๆ) |
| `"5"` | int | NULL | `5` |
| `"a"` | int | NULL | **PythonException** |
| `3` | double | NULL | `3.0` |
| `5` | string | `"5"` | `"5"` |
| `None` | int | NULL | NULL |
| `2**40` | Int | **0** (Overflow เงียบ) | PythonException |

บนเส้นทาง Pickle ค่าชนิดผิดจะกลายเป็น NULL แบบเงียบ ๆ จึงเป็นบั๊กที่หาเจอยาก ส่วนเส้นทาง Arrow ส่วนใหญ่จะ Cast ให้ หรือไม่ก็ Error ให้เห็นชัด ๆ ดังนั้นถ้าเปลี่ยน `useArrow` แล้วผลเปลี่ยน ให้สงสัยชนิดของค่าที่คืน

ส่วน pandas_udf เข้มกว่านั้น ถ้าคืน Series ที่ Cast เข้ากับชนิดที่ประกาศไม่ได้ (เช่นคืน `"a"` แต่ประกาศ `long`) จะได้ PythonException

### Error จาก Python กลับมาอย่างไร

ถ้าฟังก์ชัน Raise เช่น `ValueError("bad value 2")` Worker จะส่ง Traceback กลับ JVM ซึ่งโยนเป็น `PythonException` (Error Class `PYTHON_EXCEPTION`, SQLSTATE 38000) และ Job ล้มเหลว ฝั่ง Python จะได้ `pyspark.errors.PythonException` ที่ข้อความขึ้นต้นด้วย "An exception was thrown from the Python worker:" ตามด้วย Traceback ที่ชี้ไฟล์และบรรทัดของคุณ แต่ถ้า Process ของ Python ตายเอง (เช่นโดน OOM Kill) จะไม่มี Traceback ให้ JVM เจอการเชื่อมต่อขาดแล้วขึ้นว่า "Python worker exited unexpectedly (Crashed)" (ข้อหลังอ่านจาก Source ยังไม่ได้บังคับให้เกิด)

</Step>

## เลือกใช้อะไร

ให้ลองตามลำดับนี้

1. **Built-in ก่อนเสมอ** เพราะ `F.when`, `F.regexp_extract`, `F.transform` และ `F.expr(...)` ครอบคลุมกว่าที่คิด และ Catalyst ก็ปรับแผนให้ได้
2. **`pandas_udf`** เมื่อต้องใช้ Logic ที่ Built-in ไม่มี และทำได้แบบ Vectorized (Pandas, Numpy)
3. **Python UDF แบบ Arrow** (ค่าเริ่มต้น) เมื่อ Logic เป็น if/Else ต่อแถว หรือใช้ Library ที่รับค่าเดี่ยว
4. **`useArrow=False`** ใช้เมื่อจำเป็นต้องได้พฤติกรรมเดิมเท่านั้น

ถ้าต้องทำกับ "ทั้งกลุ่ม" ให้ใช้ `groupBy().applyInPandas(...)` แต่จำไว้สองข้อ คือต้อง Shuffle (มี `Exchange` ในแผน) และ **ทั้งกลุ่มต้องอยู่ใน Memory ของ Python Worker** ถ้ามี Key ที่ Skew ก็เสี่ยงล้มที่ Python (ข้อหลังเป็นหลักการ ยังไม่ได้ทดสอบ OOM) ส่วน `mapInPandas` รับ Iterator ของ Pandas DataFrame และไม่ต้อง Shuffle

</Step>

## Worker และ Memory

- **Worker ถูกใช้ซ้ำ** เพราะ `spark.python.worker.reuse` = True Worker ที่เสร็จแล้วจะกลับเข้า Pool ให้ Task ถัดไป ตัวแปร Global หรือ Cache ที่อยู่ระดับ Module ใน UDF จึงอยู่ข้าม Task ได้ใน Process เดียวกัน (บน Windows ที่ไม่มี Daemon จะไม่มีการใช้ซ้ำ ส่วนที่เหลือบอกตาม Source)
- **การปรับ Memory ที่ถูกต้อง** คือ `spark.executor.pyspark.memory` (ไม่ตั้งเป็นค่าเริ่มต้น หน่วย MiB) ซึ่งแบ่งให้ Worker ตามจำนวน Core และตั้งเป็นขีดจำกัดด้วย `RLIMIT_AS` แต่ Docstring ของ `worker_util.py` บอกว่า Windows ไม่รองรับ และ macOS ไม่บังคับ ผลคือบน Windows ของคอมพิวเตอร์เครื่องนี้ การตั้งค่านี้ไม่ได้จำกัดอะไรเลย
- **`spark.python.worker.memory` ไม่ใช่ปุ่มของ UDF** (ค่าเริ่มต้น 512m) เพราะใน Source ถูกอ่านโดย RDD API เท่านั้น (`rdd.py`, สำหรับ `groupByKey`/`combineByKey`) จึงไม่ต้องไปปรับเมื่อ UDF ใช้ Memory เกิน

## ลองทำและเช็กตัวเอง

```bash
cd subjects/spark/code
uv run python exercises/08_udf.py
```

สคริปต์จะยืนยันทุกข้อในบทนี้ให้ (ใช้เวลาราว 1 นาที) แล้วลองดัดแปลงดูตามนี้

1. เขียน UDF ที่คืน `float` แต่ประกาศ `int` แล้วเทียบ `useArrow=True` กับ `False`
2. เขียน `withColumn("u", f("id"))` แล้ว Filter ด้วย `u` ดูว่า `explain()` มี `ArrowEvalPython` กี่ตัว
3. ทำ `pandas_udf` ที่ Print `s.dtype` บน DataFrame ที่มี NULL กับไม่มี

ลองเช็กตัวเองด้วยคำถามเหล่านี้

- UDF แบบ Arrow เร็วกว่า Pickle เพราะอะไร และมันเป็น Vectorized หรือไม่
- ทำไม Filter บางตัวลงใต้ UDF ได้ บางตัวไม่ได้
- `pandas_udf` ที่คืนผลเป็น `2.0` แทน `2` มีสาเหตุจากอะไร
