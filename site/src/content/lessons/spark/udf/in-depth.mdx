## `ExtractPythonUDFs`: ดึง UDF ออกจากแผน

Python UDF เริ่มต้นเป็นแค่ Expression ที่ซ่อนอยู่ใน `Project`, `Filter` หรือ `Aggregate` จึงต้องมี Rule ที่ดึงมันออกมาเป็น Operator ที่รันแยกได้ ซึ่งก็คือ `ExtractPythonUDFs` (`ExtractPythonUDFs.scala`)

- **รันเมื่อไร** เป็น Batch "Extract Python UDFs" (`Once`) ใน `SparkOptimizer` (`SparkOptimizer.scala:75-91`) ลำดับกฎในนั้นคือ `ExtractPythonUDFFromJoinCondition`, `CheckCartesianProducts`, `ExtractPythonUDFFromAggregate`, `ExtractGroupingPythonUDFFromAggregate`, `ExtractPythonUDFs`, `ExtractPythonUDTFs` แล้วตามด้วย `ColumnPruning`, `LimitPushDown`, `PushPredicateThroughNonJoin` และอื่น ๆ อีกรอบ เพราะ Comment บรรทัด 85-86 บอกว่า Node Eval-python อาจอยู่ระหว่าง Project/Filter กับ Scan ทำให้ Column Pruning และ Filter Pushdown พัง จึงต้องรันกฎเหล่านั้นซ้ำ
- **ทำอะไร** (บรรทัด 267-378) ไล่จากล่างขึ้นบน ข้ามอันที่เป็น `BatchEvalPython`/`ArrowEvalPython` อยู่แล้ว ตั้งชื่อ Column ผลลัพธ์ว่า `pythonUDF0`, `pythonUDF1` (บรรทัด 322-324 ตรงกับที่เห็นใน Explain) แล้วแทน Expression เดิมด้วยการอ้างถึง Column นั้น และเติม `Project` ครอบถ้ามี Output ส่วนเกินที่ต้องตัด
- **รวม UDF** UDF พี่น้องและ UDF ซ้อนกันที่เป็น Eval Type เดียวกันไว้ใน Node เดียว ("Parallel Chaining", บรรทัด 209-231) ยกเว้นแบบ ITER ของ Pandas/Arrow ที่ไม่ถูกรวม (บรรทัด 224, 243-245) ถ้ามี Eval Type ต่างกันมาถึง Node เดียวกันจะ Throw (บรรทัด 326-331) วัดจริง: `select(plus1(plus1("id")), plus1("v"))` ได้ `ArrowEvalPython` ตัวเดียว ส่วนผสม `useArrow=False` กับ `True` ได้สอง Node ซ้อนกัน
- **เลือก Node ตาม Eval Type** (บรรทัด 333-347) `SQL_BATCHED_UDF` ไป `BatchEvalPython` ส่วน `SQL_SCALAR_PANDAS_UDF`, `PANDAS_ITER`, `SQL_ARROW_BATCHED_UDF`, `SQL_SCALAR_ARROW_UDF`, `ARROW_ITER` ไป `ArrowEvalPython`
- **ข้อจำกัด** (Comment ที่บรรทัด 152-161) จะดึงเฉพาะ UDF ที่ Input เป็น UDF ตัวเดียวหรือ Expression ที่ JVM ประเมินได้ ถ้า Input มาจากหลาย Operator ลูกจะใช้ไม่ได้
- **ตัวเลข Eval Type** `SQL_BATCHED_UDF` = 100, `SQL_ARROW_BATCHED_UDF` = 101, `SQL_SCALAR_PANDAS_UDF` = 200, `SQL_GROUPED_AGG_PANDAS_UDF` = 202 (`PythonRunner.scala:52-57`)

แล้วทำไม Filter ถึงลงไปใต้ UDF ได้ เพราะ `canPushThrough` ใน `Optimizer.scala` (บรรทัด 2285-2300) ระบุ `BatchEvalPython` (2297) และ `ArrowEvalPython` (2298) เป็น Node ที่ Filter ผ่านได้ โดยมีเงื่อนไขว่า `u.expressions.forall(_.deterministic)` (บรรทัด 2278-2279) นี่จึงเป็นสาเหตุที่ UDF แบบ Non-deterministic ขวาง Filter ได้

## เส้นทางข้อมูลของ Pickle และ Arrow

**pickle (evalType 100)**
- JVM: `BatchEvalPythonExec.getInputIterator` (บรรทัด 121-160) แปลงแต่ละ `InternalRow` เป็น Java object array แล้วทำ `.grouped(batchSize).map(pickle.dumps)` ด้วย Pyrolite `Pickler` โดย Batch Size คือ `spark.sql.execution.python.udf.maxRecordsPerBatch` ค่าเริ่มต้น **100** (`SQLConf.scala:4700-4708`)
- Python: `BatchedSerializer(CPickleSerializer(), batch_size)` (`worker.py:2489-2491`) และ `wrap_udf` (บรรทัด 371-378) ผลจะถูก Pickle กลับเป็น Batch และ JVM ทำ `unpickle.loads` แล้ว `fromJava` ทีละผล (`BatchEvalPythonExec.scala:103-112`) ถ้าไม่ตรงชนิดที่ประกาศ ผลคือ NULL (ข้อนี้เป็นข้อสรุปจากผลรัน ไม่ได้อ่าน `EvaluatePython.makeFromJava` เพื่อยืนยัน)

**Arrow (evalType 101, 200 ...)**
- JVM: `ArrowEvalPythonExec.scala:185-219` ใช้ Runner แบบ `BatchedPythonArrowInput` ที่เขียนแถวเป็น Arrow Batch ใน `PythonArrowInput.scala:114-157` ขนาดจาก `spark.sql.execution.arrow.maxRecordsPerBatch` ค่าเริ่มต้น **10,000** (`SQLConf.scala:4580-4588`, ค่า `0` หรือต่ำกว่าคือไม่จำกัด) และมีเพดานเป็นไบต์ (`maxBytesPerBatch`, Internal) ผลที่กลับมาถูกตรวจกับชนิดที่ประกาศ (บรรทัด 211-216, Error `arrowDataTypeMismatchError`)
- Python: Eval Type 101 ใช้ `ArrowStreamSerializer(write_start_stream=True)` (`worker.py:2460-2466`) แปลง Column เป็น List วนทีละแถว แล้วแปลงผลกลับด้วย `pa.array(..., type=...)` (บรรทัด 3049-3088, ลูปที่บรรทัด 3040-3043) ส่วนชนิด Pandas ใช้ `ArrowStreamPandasUDFSerializer` (บรรทัด 2467-2488)

**อ่านชนิดจาก Type Hint** `udf.py:127-135` เรียก `infer_eval_type_for_udf` เมื่อไม่ระบุ `useArrow` ฟังก์ชันที่มี Type Hint อย่าง `pd.Series` จึงอาจกลายเป็น Pandas UDF ได้ (Docstring ระบุ "Versionchanged 4.1.0") ข้อนี้ยังไม่ได้รัน

<Callout type="note" title="Comment และ Docstring ที่ล้าสมัยใน Source">
`udf.py:99` ยังเขียนว่า Arrow Optimization "disabled by default" และ `builtin.py:30616` เขียนว่า UDF "ไม่รองรับ Keyword Argument ฝั่งผู้เรียก" ทั้งที่ `udf.py:428-437` (`__call__` รับ `**kwargs`) และ `worker.py:1064-1075` รองรับ ส่วนข้อหลังยังไม่ได้รันยืนยันว่าเรียกด้วย Keyword ได้ใน 4.2.0

## Daemon และการใช้ Worker ซ้ำ

- `spark.python.worker.reuse` ค่าเริ่มต้น True และ `spark.python.use.daemon` ค่าเริ่มต้น True (`Python.scala:24-37`) แต่ `PythonWorkerFactory.scala:96-99` คำนวณ `useDaemon = !Utils.isWindows && useDaemonEnabled` ("ข้ามบน Windows เพราะ Fork ไม่ได้")
- บน Linux/macOS Daemon (`pyspark/daemon.py`) จะ Fork Worker ต่อ Task ใน Child วนอยู่ที่ `while True: code = worker(...)` เมื่อจบงานปกติก็กลับไปรอรับ Task ใหม่ เฉพาะเมื่อ `reuse` เปิด (`daemon.py:165`, `259-274`: ถ้า `not reuse or code` ก็ Break) แล้ว `gc.collect()`
- ฝั่ง JVM Worker ที่เสร็จจะเข้า Idle Pool (`releaseWorker`, `PythonWorkerFactory.scala:512-526`) แล้ว Task ต่อไปหยิบไปใช้ใน `create` (บรรทัด 132-156) โดยจะปล่อยคืนได้ก็ต่อเมื่อ Worker ตอบ `END_OF_STREAM` (`PythonRunner.scala:671-684`) ถ้า Worker เขียน `END_OF_DATA_SECTION` แทน (`worker.py:3644-3647`) ก็จะไม่ถูกใช้ซ้ำ
- บน Windows Worker ที่ไม่ใช่ Daemon จะถูกหยุดใน `releaseWorker` (บรรทัด 527-534) จึงไม่มีอะไรถูกใช้ซ้ำ หลักฐานจากการรันคือระหว่าง Job เห็น Process `python.exe -m pyspark.worker` ลูกของ JVM และไม่เห็น `pyspark.daemon` ส่วนพฤติกรรมของ Daemon บน Linux/macOS ยังไม่ได้ทดสอบที่นี่

ลองดูแปดงานบนสอง Slot ในสามการตั้งค่า ตัวเลข `n=` คือ Counter ระดับ Module ที่ UDF เพิ่มทุกครั้งที่ Task ใช้ Worker นั้น ซึ่งทำให้เห็นผลของการ Reuse ตรง ๆ

<WorkerReuseLab client:visible />

สำหรับโค้ดของคุณ ถ้า UDF เก็บ State ระดับ Module (Global, Cache) State นั้นจะอยู่ข้าม Task ได้เมื่อมีการใช้ Worker ซ้ำ ซึ่งแปลว่าผลของ UDF ไม่ควรพึ่ง State ที่แชร์แบบนั้น

</Step>

## Memory ของ Python ไปถึง Worker อย่างไร

`spark.executor.pyspark.memory` (`Python.scala:54-57`, `createOptional` หน่วย MiB) ไหลเป็น

`ResourceProfile.scala:433-434` → task local property → `PythonRunner.scala:271-273` หารด้วยจำนวน Core ของ Executor ("แต่ละ Worker ได้ส่วนเท่ากัน") → ตั้ง `PYSPARK_EXECUTOR_MEMORY_MB` (บรรทัด 307-311) → `worker.py:3571-3572` `setup_memory_limits` → `worker_util.py:95-127` ตั้ง `resource.RLIMIT_AS`

Docstring ที่บรรทัด 100 ของ `worker_util.py` บอกว่า Windows ไม่รองรับการจำกัด และ macOS ไม่บังคับจริง ส่วนบน YARN/Kubernetes ค่านี้ถูกบวกเข้า Container Request (จาก `configuration.md`) ถ้าไม่ตั้ง Spark ไม่จำกัด Memory ของ Python และมันต้องอยู่ใน Overhead Memory

ส่วน `spark.python.worker.memory` (512m) เมื่อค้นใน Source แล้วพบว่าถูกอ่านที่เดียวคือ `python/pyspark/core/rdd.py:3972` (`_memory_limit`, ใช้โดย `groupByKey` กับ `combineByKey`) การค้นนี้ไม่รวมโฟลเดอร์ Connect และ Pandas-on-spark แยกต่างหาก

`pandas_udf` ถือ Arrow Batch ทั้งก้อน (10,000 แถวเป็นค่าเริ่มต้น) เป็น Pandas ใน Memory (ตามจาก `PythonArrowInput.scala:119-122`) ส่วนฟังก์ชันแบบกลุ่มจะถือทั้งกลุ่ม ซึ่งเป็นหลักการทั่วไปของ Spark และยังไม่ได้ทดสอบ OOM

</Step>

## Error กลับมาอย่างไร

1. Worker จับ Exception (`worker.py:3629-3631`: `except BaseException → handle_worker_exception(e, outfile); sys.exit(-1)`) `handle_worker_exception` (`util.py:505-545`) เขียน `PYTHON_EXCEPTION_THROWN` (-2) แล้วตามด้วยข้อความ Traceback (บรรทัด 537-538) เราซ่อนหรือย่อ Traceback ได้ด้วย `SPARK_HIDE_TRACEBACK` / `SPARK_SIMPLIFIED_TRACEBACK` (บรรทัด 524-535 ตั้งโดย `PythonRunner.scala:299-304`)
2. JVM เห็น -2 (`PythonArrowOutput.scala:142-143`, `PythonUDFRunner.scala:131-132`) เรียก `handlePythonException` (`PythonRunner.scala:661-669`) สร้าง `PythonException` ที่มี Error Class `PYTHON_EXCEPTION` (`error-conditions.json:6123-6128`, SQLSTATE 38000)
3. executor log Java stack เต็มและ Job ล้มด้วย `Task N in stage 0.0 failed 1 times; aborting job` (ใน local mode retry 1 ครั้ง บน Cluster จริงลองใหม่ได้หลายรอบ)
4. Driver ฝั่ง Python ได้ `pyspark.errors.exceptions.captured.PythonException` ที่ `getCondition()` = `PYTHON_EXCEPTION` และ `getSqlState()` = `38000` และ `str(e)` ขึ้นต้นด้วย `An exception was thrown from the Python worker:` ตามด้วย Traceback ซึ่งชี้ไฟล์ของคุณ (ตรวจใน Exercise: `08_udf.py` อยู่ใน Traceback)

กรณี Pandas UDF ที่คืนรูปร่างผิด (ความยาวไม่ตรง หรือคืนค่าเดี่ยว) ก็รายงานเป็น `PythonException` เช่นกัน (ตรวจที่ `worker.py:384-405`) ส่วนกรณี Python ตายเองจะไม่มี -2 เพราะ JVM เจอ EOF แล้ว Throw `SparkException("Python worker exited unexpectedly (crashed)...")` (`PythonRunner.scala:686-712`)

</Step>

## ข้อควรระวังเรื่อง Determinism และผลกำหนดซ้ำ

- UDF ทุกตัวเป็น Deterministic โดยค่าเริ่มต้น `asNondeterministic()` เปลี่ยนเป็น Non-deterministic (`udf.py:550-560`) ตรวจแล้ว: `plus1.deterministic` เป็น True, `rnd.asNondeterministic().deterministic` เป็น False
- Docstring (`builtin.py:30603-30606`) เตือนว่าการเรียกอาจถูกกำจัดซ้ำหรือถูกเรียกมากกว่าจำนวนที่ปรากฏในคำสั่ง รวมกับกรณี Filter บนผลของ UDF ที่เห็น `ArrowEvalPython` สองตัว เราจึงไม่ควรใส่ Side Effect (นับ, เขียน, เรียก API) ใน UDF แล้วหวังว่าจะเกิด "หนึ่งครั้งต่อแถว" และข้อที่ไม่คาดคิดคือสำหรับ UDF deterministic Spark ก็ยังไม่ขจัดการเรียกซ้ำในกรณีนั้น (ดูจากแผน ไม่ได้นับจำนวนครั้งที่เรียกจริง)
- Arrow และ Pickle มี Type Coercion ต่างกัน ตามที่ Comment ที่ `udf.py:94-99` เขียนไว้ และมีชุดทดสอบอยู่ที่ `python/pyspark/sql/tests/udf_type_tests` (ยังไม่ได้อ่าน) ตารางในบทหลักรันกับ ANSI Mode เปิดตามค่าเริ่มต้น ชุดทดสอบเดียวกันกรณี `1.5` เป็น `int` ให้ผลเหมือนกันเมื่อปิด ANSI แถวอื่นยังไม่ได้ทดสอบ

</Step>

## สิ่งที่ยังไม่ได้พิสูจน์

- ผลของ Batch Size ต่อความเร็วต่อแถวของ `pandas_udf` (ต้องวัดแบบ Partition เดียว)
- ค่าใช้จ่ายของ Worker ต่อ Task บน Linux/macOS ที่มี Daemon (บน Windows ที่เห็นคือเริ่ม Process ใหม่ทุก Task)
- ขนาดของ Command ที่ Pickle เมื่อ Closure ใหญ่
- Python ตายเอง (Segfault, OOM Kill) ที่ไม่มี Traceback
- Pushdown ผ่าน UDF ไปถึงแหล่งข้อมูลไฟล์ (Parquet เขียนไม่ได้บนเครื่องนี้)
- ว่าการห่อ `when(x.isNotNull(), udf(x))` ไม่ปกป้อง UDF (เป็นข้อความใน Docstring)
- Spark บน Windows: บางครั้งการสร้าง DataFrame ด้วย `createDataFrame` แถวเดียวที่ถูกแบ่งเป็น 16 Partition แล้วรัน UDF ได้ Error "Python worker exited unexpectedly" จากการเชื่อมต่อ Socket ถูกตัด ผู้เขียนพบตอนเตรียม Exercise และหลีกเลี่ยงด้วย `coalesce(1)` ยังไม่ได้สืบหาสาเหตุ จึงไม่ถือเป็นพฤติกรรมของ Spark เอง
