<Step>

## นับ Job ทีละคำสั่ง

<JobCounterLab client:visible />

ตารางนี้คือผลที่ควรจำ

| คำสั่ง | Job |
|---|---|
| `spark.range(...)`, `filter`, `select`, `withColumn`, `where` | **0** |
| `df.explain()` | **0** |
| `cache()` | **0** (และ Storage ยังว่าง) |
| `count()` (Action) | อย่างน้อย 1 |
| `groupBy(...).count().collect()` ครั้งแรก | **2** |

แล้วทำไม `groupBy` ถึงเป็นสอง Job ล่ะ ที่เป็นแบบนี้เพราะเมื่อเปิด AQE แล้ว Spark จะตัดแผนที่มี Shuffle ออกเป็นช่วง โดยรัน Stage ที่เขียน Shuffle ให้เสร็จก่อนเป็น Job แรก แล้วค่อยตัดสินใจรัน Stage ผลลัพธ์เป็น Job ที่สอง ([บทที่ 6](/spark/catalyst-aqe/#aqe-ทำสามอย่าง)) ถ้าปิด AQE จะเหลือ Job เดียว (วัดจริงทั้งสองแบบ)

</Step>

<Step>

## Action ซ้ำคือคำนวณซ้ำ จริงแค่ไหน

บทหลักบอกว่าถ้าเรียก Action ซ้ำจะคำนวณซ้ำ ซึ่งถูกต้องในหลักการ แต่ตัวเลขที่วัดได้จริงละเอียดกว่านั้น โดยเฉพาะกับ Query `groupBy` ที่มี Shuffle

| การเรียก | Job |
|---|---|
| `agg.collect()` ครั้งแรก | 2 |
| `agg.collect()` ซ้ำบน DataFrame **ตัวเดิม** | **1** |
| สร้าง DataFrame ใหม่ด้วยโค้ดเดียวกันแล้ว `collect()` | 2 |

พอเรียกซ้ำบน Object ตัวเดิม จะเหลือ 1 Job เพราะไฟล์ Shuffle ที่รอบแรกเขียนไว้ยังอยู่ Spark จึงข้าม Stage ฝั่ง Map ไปได้ (ใน Spark UI จะเห็นเป็น "Skipped Stage") แต่ Stage ผลลัพธ์ยังต้องรันใหม่ ส่วน DataFrame ที่สร้างขึ้นใหม่จะไม่ได้ใช้ไฟล์เดิม จึงทำงานตั้งแต่ต้น

ตรงนี้มีสองข้อที่ควรระวัง

- สิ่งที่ถูก Reuse คือผลของ **Shuffle** ไม่ได้เป็น Cache ถ้าในแผนไม่มี Shuffle เลย (Query แบบ Narrow ล้วน) ทุก Action ก็จะอ่านและคำนวณใหม่หมด ไม่มีอะไรให้ข้าม (ตรวจแล้ว `count()` สองครั้งบน DataFrame แบบ Narrow ทั้งสองครั้งรัน)
- ไฟล์ Shuffle ถูกเก็บไว้แค่ชั่วคราว Spark จะลบเมื่อ DataFrame ถูกเก็บกวาดหรือเมื่อ Session จบ เพราะฉะนั้นเราไม่ควรพึ่งมันแทน `cache()`

</Step>

<Step>

## Action ไม่ได้อ่านทุกอย่างเสมอไป

`show()` และ `limit` ต้องการแค่ไม่กี่แถว Spark จึงหยุดทันทีที่ได้ครบ เรามาลองกับ `spark.range(0, 10**12, 1, 200)` (1 ล้านล้านแถวใน 200 Partition) แล้วเรียก `show(5)` ดู

- ได้ **1 Job** ที่มี **1 Task** จาก 200 Partition
- ใช้เวลา **ราว 0.1 วินาที**

ถ้า Spark อ่านทั้งหมดจะใช้เวลาหลายชั่วโมง แต่นี่มันเริ่มจาก Partition แรก ได้ 5 แถวแล้วก็หยุด (ถ้า Partition แรกมีแถวไม่พอ มันถึงจะขยับไปอ่านเพิ่ม) ด้วยเหตุนี้ `show()` และ `take(n)` จึงเร็วกว่า `count()` ที่ต้องแตะทุกแถวเสมอ และเป็นวิธีดูตัวอย่างข้อมูลที่ปลอดภัยเวลาเจอตารางใหญ่

</Step>

<Step>

## `cache()` เองก็ Lazy

ถ้าเราเขียน `c = df.filter(...).cache()` จะไม่มี Job เริ่มขึ้นเลย (วัดได้ 0 Job) แม้ `c.is_cached` จะเป็น `True` ทันที แต่ตัวติดตามพื้นที่เก็บของ Spark ก็ยังว่างอยู่ (`getRDDStorageInfo()` ไม่มีรายการ) จนกระทั่งหลัง Action แรก (`c.count()`) ถึงจะมีรายการหนึ่งรายการ ส่วนกับดักอื่นของ Cache (Partition ที่ถูกเก็บ, ความคุ้มค่า) ไปดูต่อได้ใน[บทที่ 7](/spark/performance-tuning/#cache-ช่วยเมื่อไร)

</Step>

<Step>

## Error โผล่ตอนไหน

ผลที่ตรวจได้เป็นดังนี้

| ความผิดพลาด | โผล่เมื่อ |
|---|---|
| ชื่อคอลัมน์ไม่มี (`select("no_such_column")`) | **ทันทีที่บรรทัดนั้นรัน** `AnalysisException: [UNRESOLVED_COLUMN...]` |
| ค่าในข้อมูลผิดรูป (`cast("int")` กับ `"abc"`) | **ตอน Action** `[CAST_INVALID_INPUT]` |

เหตุผลก็คือ Spark วิเคราะห์ชื่อและชนิดของ Column ตอนที่เราต่อ Transformation (ใช้ Schema ซึ่งไม่ต้องแตะข้อมูล) แต่ค่าจริงในข้อมูลจะรู้ก็ต่อเมื่อ Executor อ่านไปถึงแถวนั้น ผลก็คือ Error ของข้อมูลอาจโผล่ที่ `show()` ซึ่งอยู่ไกลจากบรรทัดที่เป็นต้นเหตุ

</Step>

## ANSI Mode ถูกล็อกตอนนิยาม DataFrame

อีกกับดักหนึ่งที่ตรวจแล้วและควรรู้ คือโหมด ANSI (ที่ทำให้ `cast("abc" as int)` Error) จะถูกอ่านตอน **สร้าง DataFrame** ไม่ได้อ่านตอนรัน Action

```python
spark.conf.set("spark.sql.ansi.enabled", "true")
on = spark.createDataFrame([("abc",)], "s string").selectExpr("cast(s as int) AS i")   # นิยามตอน ANSI เปิด
spark.conf.set("spark.sql.ansi.enabled", "false")
off = spark.createDataFrame([("abc",)], "s string").selectExpr("cast(s as int) AS i")  # นิยามตอน ANSI ปิด

on.collect()    # ยัง error: CAST_INVALID_INPUT  (ปิดทีหลังก็ไม่ช่วย)
off.collect()   # [Row(i=None)]  ได้ NULL
```

บทหลักเขียนไว้ว่า "ถ้าปิดโหมดนี้ ผลที่ได้จะเป็น NULL" ซึ่งจริงก็ต่อเมื่อเราปิด **ก่อน** นิยาม DataFrame ถ้าปิดหลังนิยามไปแล้วจะไม่มีผล ใครลองสลับลำดับดูก็อาจจะงงได้นะ สำหรับเหตุผลที่ลึกกว่านี้ (Analyzer เลือก Rule ตาม Mode ตอนวิเคราะห์) [บทที่ 6](/spark/catalyst-aqe/in-depth/#analyzer-และ-ansi-mode-ที่ถูกล็อกตอน-analyze) อธิบายไว้
