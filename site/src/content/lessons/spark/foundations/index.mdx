## เริ่มจากอะไรได้บ้าง

Spark ไม่ต้องใช้พื้นฐานเยอะ ถ้าเขียน SQL ได้ (`select`, `where`, `group by`, `join`) และอ่านโค้ด Python รู้เรื่อง ก็ข้ามไปบทถัดไปได้เลย ส่วนที่ควรคุ้นเพิ่มมีสองเรื่อง คือรูปแบบไฟล์ข้อมูล กับคำว่า partition และ serialization ที่จะเจอตลอดเส้นทาง

<Callout type="tip" title="ถ้าเคยใช้ pandas">
มาจาก pandas จะเรียนได้เร็ว ความต่างที่ต้องปรับมีสองข้อ ข้อมูลไม่ได้อยู่ในหน่วยความจำของเครื่องเดียว และคำสั่งส่วนใหญ่ไม่รันทันที ข้อหลังอธิบายใน[บทที่ 2](/spark/lazy-evaluation/)
</Callout>

</Step>

## ไฟล์ข้อมูล: CSV กับ Parquet

สองรูปแบบนี้ต่างกันที่วิธีวางข้อมูลบน disk และความต่างนั้นกำหนดว่า Spark ต้องอ่านมากแค่ไหน

- CSV เป็นข้อความธรรมดา แถวละบรรทัด ไม่มีชนิดข้อมูล ทุกอย่างเป็นข้อความจนกว่าจะมีคนเดาชนิด JSON คล้ายกันตรงที่เป็นข้อความ เก็บทีละระเบียน แต่ซ้อนโครงสร้างได้
- Parquet เก็บข้อมูลทีละคอลัมน์ มีชนิดข้อมูลอยู่ในไฟล์ และบีบอัดต่อคอลัมน์ได้ดี

## ทำไมงานจริงเลือก Parquet

Parquet อ่านเฉพาะคอลัมน์ที่ query ใช้ (เรียกว่า column pruning) ไม่ต้องเดาชนิดข้อมูล และไฟล์มักเล็กกว่า CSV ที่มีข้อมูลเท่ากัน งานจริงจึงมักเก็บเป็น Parquet ส่วน CSV เหมาะกับข้อมูลเล็กหรือข้อมูลที่รับมาจากระบบอื่น

ยิ่งตารางกว้าง ความต่างยิ่งมาก ตารางที่มี 200 คอลัมน์แต่ query ใช้ 3 คอลัมน์ Parquet อ่านประมาณ 3 ใน 200 ส่วน ส่วน CSV ต้องอ่านทุกบรรทัดจนครบ

ตัวเลขจริงจากการวัด: ตาราง 600,000 แถว 9 คอลัมน์ เขียนเป็น CSV 71.7 MiB และ Parquet 48.9 MiB เมื่อรวมค่าของคอลัมน์เดียว (`sum(amount)`) CSV ต้องอ่าน **73.3 MiB** (ทั้งไฟล์) ส่วน Parquet อ่านเพียง **0.10 MiB** รายละเอียดและวิธีวัดอยู่ใน [Data I/O แบบเจาะลึก](/spark/data-io/in-depth/)

</Step>

## Partition และ Serialization

Partition คือก้อนของข้อมูลที่ Spark ส่งให้ task หนึ่งตัวประมวลผล ข้อมูลชุดหนึ่งมีหลาย partition และ partition ต่างก้อนรันพร้อมกันได้ ตัวอย่างจากเครื่องที่ใช้ทดสอบ `spark.range(1_000_000)` แตกเป็น 16 partition (เห็นเป็น `splits=16` ในผล `explain()` ของ[บทที่ 5](/spark/execution-model/)) ตรงกับจำนวน core ของเครื่อง

Serialization คือการแปลงข้อมูลในหน่วยความจำให้เป็นไบต์ เพื่อส่งข้ามเครื่องหรือเขียนลง disk แล้วแปลงกลับตอนอ่าน ข้อมูลที่ต้องย้ายระหว่างเครื่องมีต้นทุนส่วนนี้เสมอ และเป็นเหตุผลหนึ่งที่ shuffle แพง ([บทที่ 5](/spark/execution-model/))

</Step>
