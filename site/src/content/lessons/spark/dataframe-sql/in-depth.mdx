## NULL คือ "ไม่รู้" ไม่ใช่ค่า

SQL มี logic สามค่า: TRUE, FALSE และ NULL (ไม่รู้) ลองกดแต่ละช่องของตาราง

<NullLogicLab client:visible />

ผลที่ตรวจ

| นิพจน์ | ผล |
|---|---|
| `NULL = NULL` | NULL |
| `NULL <=> NULL` (null-safe equal) | TRUE |
| `1 = NULL` | NULL |
| `NULL AND false` | FALSE |
| `NULL OR true` | TRUE |
| `NOT NULL` | NULL |

เหตุผล: ถ้าไม่รู้ค่าหนึ่ง แต่อีกค่าทำให้คำตอบแน่นอนอยู่แล้ว (`FALSE AND ...` ต้องเป็น FALSE เสมอ) ผลก็รู้ได้ ถ้าไม่ ผลก็ไม่รู้ และ `WHERE` เก็บแถวเฉพาะที่เงื่อนไขเป็น **TRUE** แถวที่ได้ NULL ถูกทิ้งเหมือน FALSE ทำให้ `!=` ก็ทิ้งแถวที่เป็น NULL ด้วย (วัดจริง: ตาราง 6 แถวที่หนึ่งแถวมี `sales` เป็น NULL, `sales != 100` ได้ 5 แถว ไม่ใช่ 6)

## NULL ในการรวมและการจัดกลุ่ม

บนตาราง `country, city, sales` ที่มี NULL ทั้งใน `country` และ `sales` ตรวจแล้ว

- `sum`, `avg` ข้าม NULL; `count(col)` นับเฉพาะที่ไม่ใช่ NULL ส่วน `count(*)` นับทุกแถว (กลุ่ม jp: total 200, n_sales 1, n_rows 2)
- ผลรวมของกลุ่มที่มีแต่ NULL คือ **NULL** ไม่ใช่ 0 (ตรวจแล้ว ต่างจากที่คนมักเดา)
- `groupBy("country")` เก็บ NULL เป็น **กลุ่มของตัวเอง** (หนึ่งกลุ่ม) ส่วน `distinct()` ก็เก็บ NULL หนึ่งค่า ในขณะที่ `count(distinct country)` **ไม่นับ** NULL (ได้ 3 ไม่ใช่ 4)
- `F.col("sales") == None` ไม่เจอแถวใดเลย (0 แถว) เพราะผลเป็น NULL เสมอ ใช้ `isNull()` (1 แถว) หรือ `eqNullSafe(None)` (1 แถว)
- เรียงลำดับ: `asc` วาง NULL **ก่อน** (nulls first) `desc` วาง NULL **ท้าย** ใช้ `asc_nulls_last()` เมื่อต้องการเปลี่ยน
- `coalesce(NULL, NULL, 3)` ได้ 3 และ `nullif(2, 2)` ได้ NULL

</Step>

## กับดัก NOT IN

```sql
SELECT x FROM a WHERE x NOT IN (SELECT y FROM b)      -- b มีค่า 1 และ NULL
```

กับ `a` = (1, 2, 3) และ `b` = (1, NULL) ผลคือ **ว่าง 0 แถว** (วัดจริง) ทั้งที่ 2 และ 3 ไม่อยู่ใน `b` เหตุผล: `2 NOT IN (1, NULL)` กลายเป็น `2 <> 1 AND 2 <> NULL` ซึ่งเป็น `TRUE AND NULL` คือ NULL จึงถูกทิ้ง

ทางแก้: `NOT EXISTS (SELECT 1 FROM b WHERE b.y = a.x)` ซึ่งได้ 2 และ 3 ตามที่คาด (วัดจริง) หรือกรอง NULL ออกจาก subquery ก่อน

</Step>

## Join กับ Key ที่เป็น NULL

ตารางซ้ายมี id (1, 2, NULL) ตารางขวามี id (1, 3, NULL) นับแถวผลลัพธ์ของแต่ละ join type

| join | แถว | อธิบาย |
|---|---|---|
| `inner` | 1 | จับคู่ได้เฉพาะ id = 1 (NULL ไม่เท่ากับ NULL) |
| `left` | 3 | ซ้ายทุกแถว |
| `right` | 3 | ขวาทุกแถว |
| `full` | 5 | ทุกแถวของทั้งสองฝั่ง (NULL สองตัวไม่จับคู่กัน จึงเป็นสองแถวแยก) |
| `left_semi` | 1 | แถวซ้ายที่มีคู่ |
| `left_anti` | 2 | แถวซ้ายที่ **ไม่มีคู่** รวมแถวที่ key เป็น NULL |
| `cross` | 9 | 3 x 3 |

ถ้าต้องการให้ NULL จับคู่กับ NULL ใช้ `left.id.eqNullSafe(right.id)` เป็นเงื่อนไข ได้ inner 2 แถว (id = 1 และ NULL กับ NULL)

</Step>

## Window: rank, dense_rank และ Frame

ข้อมูลกลุ่ม a มีค่า 10, 20, 20, 30 เรียงตาม `v` ผลของฟังก์ชัน ranking ที่ตรวจ

| v | `rank` | `dense_rank` | `row_number` |
|---|---|---|---|
| 10 | 1 | 1 | 1 |
| 20 | 2 | 2 | 2 หรือ 3 |
| 20 | 2 | 2 | 3 หรือ 2 |
| 30 | **4** | **3** | 4 |

- `rank` **ข้ามลำดับ** หลังค่าที่เท่ากัน (1, 2, 2, **4**)
- `dense_rank` ไม่ข้าม (1, 2, 2, **3**)
- `row_number` ไม่ซ้ำเลย แต่ลำดับระหว่างค่าที่เท่ากันไม่แน่นอน (เป็น 2 กับ 3 สลับกันได้) ถ้าต้องการผลที่แน่นอนต้องใส่คอลัมน์ที่ทำให้ไม่เท่ากันใน `orderBy`

เรื่อง **frame** ของ `sum(v).over(window ที่มี orderBy)`: ค่าเริ่มต้นคือ `RANGE` ซึ่งนับแถวที่ค่าเท่ากัน (peer) เป็นก้อนเดียวกัน ผลรวมสะสมได้ 10, 50, 50, 80 (สองแถวที่ v = 20 ได้ 50 ทั้งคู่) ส่วน `rowsBetween(unboundedPreceding, currentRow)` นับทีละแถว แถวที่ v = 20 ได้ 30 และ 50 ถ้าอยาก "running total ทีละแถว" ให้ระบุ frame เป็น `ROWS` เอง

</Step>

## ANSI Mode และฟังก์ชัน try_

Spark 4 เปิด ANSI mode เป็นค่าเริ่มต้น ผลที่เคยเป็น NULL เงียบๆ กลายเป็น error (ตรวจแล้ว)

| นิพจน์ | ผล |
|---|---|
| `1 / 0` | error `DIVIDE_BY_ZERO` |
| `CAST('abc' AS INT)` | error `CAST_INVALID_INPUT` |
| `2147483647 + 1` | error `ARITHMETIC_OVERFLOW` |
| `try_divide(1, 0)` | NULL |
| `try_cast('abc' AS INT)` | NULL |
| `try_add(2147483647, 1)` | NULL |

ใช้ `try_` เมื่อ **ตั้งใจ** ให้ข้อมูลเสียกลายเป็น NULL (แล้วกรองหรือนับทีหลัง) ส่วน error แบบ ANSI ดีกว่าสำหรับงานที่ผลผิดไม่ได้ เพราะไม่ปล่อยให้ค่าผิดไหลไปเงียบๆ จำไว้ด้วยว่าโหมดถูกล็อกตอนนิยาม DataFrame (ดูหน้า Lazy evaluation แบบเจาะลึก)

</Step>

## กับดักตัวเลขทศนิยม

- ตัวเลขใน **SQL** เขียน `0.1` เป็น **decimal** ไม่ใช่ double จึง `SELECT 0.1 + 0.2 = 0.3` ได้ **TRUE** (วัดจริง)
- แต่ column ที่เป็น `double` (เช่นสร้างจาก Python float) `0.1 + 0.2 == 0.3` ได้ **False** และ `CAST(0.1 AS DOUBLE) + CAST(0.2 AS DOUBLE)` = `0.30000000000000004`
- ชนิดของ literal: `1` เป็น `int`, `1L` เป็น `bigint`, `1.0` เป็น `decimal(2,1)`, `1D` เป็น `double`, `'x'` เป็น `string` (ตรวจจาก `dtypes`)
- `1 + 0.5` ได้ decimal ค่า 1.5 ส่วน `7 / 2` ได้ `3.500000` (decimal) ไม่ใช่ 3 ถ้าต้องการหารจำนวนเต็มใช้ `7 DIV 2` ซึ่งได้ 3

เงินและค่าที่ต้องเท่ากันเป๊ะควรใช้ decimal ส่วน double เหมาะกับค่าทางวิทยาศาสตร์ที่ยอมรับความคลาดเคลื่อนเล็กน้อย

<Callout type="note" title="DataFrame API กับ SQL ให้ผลเท่ากัน">
`groupBy("country").agg(sum("sales"))` กับ `SELECT country, SUM(sales) ... GROUP BY country` ให้ผลเหมือนกันทุกแถว (ตรวจแล้ว) และได้แผนที่ optimize แล้วเดียวกัน (บทที่ 6) `selectExpr` และ `where("sales > 100 AND country = 'th'")` ให้เขียนข้อความ SQL ใน DataFrame API ได้เมื่อ SQL อ่านง่ายกว่า
</Callout>
