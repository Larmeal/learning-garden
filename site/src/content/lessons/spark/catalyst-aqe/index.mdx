## Spark ไม่ได้รันสิ่งที่คุณเขียน

สมมติว่าเราเขียน `df.filter(...).select(...)` สองบรรทัดแล้วกด `show()` สิ่งที่ Executor รันจริงไม่ได้เป็นสองบรรทัดนั้นตรง ๆ Spark เอาโค้ดของคุณไปแปลงเป็นต้นไม้ของ Operator แล้วเขียนต้นไม้นั้นใหม่หลายรอบก่อนจะรัน เช่น ย้าย Filter ลงไปใกล้ข้อมูล ตัด Column ที่ไม่มีใครอ่าน และคิดค่าคงที่ให้เสร็จก่อน

ส่วนที่ทำงานนี้ชื่อ **Catalyst** ซึ่งเป็น Optimizer ของ Spark SQL ทุกอย่างที่คุณเขียนด้วย DataFrame หรือ SQL จะผ่านมันหมด ไม่ว่าจะเขียนด้วย Python, Scala หรือ SQL ล้วน

บทนี้จะตอบสามคำถาม

1. ระหว่างโค้ดของคุณกับ Task ที่รันจริง มีอะไรเกิดขึ้นบ้าง
2. เราอ่านผล `explain()` อย่างไรให้รู้ว่า Spark ตัดสินใจอะไร
3. AQE (Adaptive Query Execution) แก้อะไรให้ ที่ Catalyst ทำเองก่อนรันไม่ได้

บทนี้ต่อจากบทที่ [Execution Model](/spark/execution-model/#narrow-กับ-wide) ซึ่งสอนว่าแผนถูกตัดเป็น Stage ตรงที่ Shuffle ส่วนที่นี่เราจะดูว่าแผนนั้นมาจากไหนและเปลี่ยนได้อย่างไร

</Step>

## Query ผ่านห้าขั้น

ทุก Query มี Object ชื่อ `QueryExecution` ถือไว้ มันเดินผ่านห้าขั้นตามลำดับ และทุกขั้นเป็น `lazy` คือคำนวณเมื่อมีคนขอเท่านั้น (Source: `QueryExecution.scala:192-372`)

| ขั้น | ได้อะไร | ใครทำ |
|---|---|---|
| 1. Parse | **Parsed Logical Plan** คือต้นไม้ที่สร้างจากตัวอักษรของ SQL ซึ่งยังไม่รู้ว่าชื่อ Table หรือ Column มีจริงไหม | `SparkSqlParser`, `AstBuilder` |
| 2. Analyze | **Analyzed Logical Plan** ที่ทุกชื่อผูกกับของจริงแล้ว มีชนิดข้อมูล มี id | `Analyzer` |
| 3. Optimize | **Optimized Logical Plan** คือแผนเดิมที่ถูกเขียนใหม่ให้ถูกกว่า | `Optimizer` (Catalyst) |
| 4. Plan | **Physical Plan** ที่เลือก Operator ที่รันได้จริง เช่น `SortMergeJoin` หรือ `BroadcastHashJoin` | `SparkPlanner` + Strategies |
| 5. Prepare | เติมสิ่งที่ขาด ได้แก่ `Exchange`, `Sort`, Whole-stage Codegen, AQE | `preparations` ใน `QueryExecution` |

ขั้น 1 ถึง 3 พูดถึง "ต้องการอะไร" (Logical) ส่วนขั้น 4 และ 5 พูดถึง "ทำอย่างไร" (Physical) ที่ต้องแยกกันเพราะสิ่งที่ต้องการอย่าง Join สองตารางมีวิธีทำได้หลายแบบ และการเลือกวิธีต้องรู้ขนาดข้อมูล

<Callout type="note" title="DataFrame กับ SQL ไปถึงที่เดียวกัน">
ถ้าเราเขียน `spark.sql("... WHERE amt > 5 GROUP BY country")` กับ `df.filter(...).groupBy(...)` แล้วเทียบ Optimized Logical Plan จะได้แผนเดียวกัน (ตัด Expression id แล้วเท่ากันเป๊ะ รัน: `exercises/06_catalyst_aqe.py`) ที่ต่างกันมีแค่ Parsed Plan เพราะ DataFrame API ต่อแผนใหม่บนแผนที่ Resolve แล้วทุกครั้งที่เรียก Transformation ส่วน SQL เริ่มจากข้อความที่ยังมี `UnresolvedRelation` ดังนั้นเราจะเขียนแบบไหนก็ไม่มีผลต่อความเร็วของแผนที่รันจริง
</Callout>

</Step>

## อ่านแผนทั้งสี่ด้วย `explain(True)`

Query นี้ตั้งใจใส่เงื่อนไขที่ไม่มีความหมายอย่าง `1 = 1` เพื่อดูว่า Catalyst จัดการอย่างไร (รัน: `exercises/06_catalyst_aqe.py`)

```python
df = (spark.range(1000)
      .withColumn("x", F.col("id") * 2 + (1 + 2))
      .filter("id > 10 AND 1 = 1"))
df.explain(True)
```

```
== Parsed Logical Plan ==
'Filter (('id > 10) AND (1 = 1))
+- Project [id#0L, ((id#0L * cast(2 as bigint)) + cast(3 as bigint)) AS x#1L]
   +- Range (0, 1000, step=1, splits=Some(16))

== Analyzed Logical Plan ==
id: bigint, x: bigint
Filter ((id#0L > cast(10 as bigint)) AND (1 = 1))
+- Project [id#0L, ((id#0L * cast(2 as bigint)) + cast(3 as bigint)) AS x#1L]
   +- Range (0, 1000, step=1, splits=Some(16))

== Optimized Logical Plan ==
Project [id#0L, ((id#0L * 2) + 3) AS x#1L]
+- Filter (id#0L > 10)
   +- Range (0, 1000, step=1, splits=Some(16))

== Physical Plan ==
*(1) Project [id#0L, ((id#0L * 2) + 3) AS x#1L]
+- *(1) Filter (id#0L > 10)
   +- *(1) Range (0, 1000, step=1, splits=16)
```

ให้อ่านจากบนลงล่าง จะสังเกตเห็นสี่อย่าง

1. เครื่องหมาย `'` ใน `'Filter` ของ Parsed Plan แปลว่า "ยังไม่ Resolve" พอมาถึง Analyzed Plan เครื่องหมายนี้ก็หายไป และ `id` มี `#0L` (id ของ Attribute กับชนิด `L` = Bigint)
2. `cast(10 as bigint)` โผล่ใน Analyzed Plan เพราะ `id` เป็น Bigint ส่วน `10` เป็น Int Analyzer จึงเติม Cast ให้ชนิดตรงกัน (Type Coercion)
3. ใน Optimized Plan `1 = 1` หายไป `cast(2 as bigint)` กลายเป็น `2` และ `Filter` ย้ายลงไปอยู่ใต้ `Project`
4. ใน Physical Plan มี `*(1)` นำหน้า Operator แปลว่ารันใน whole-stage codegen stage หมายเลข 1

ตัวเลข `#0L`, `#1L` เปลี่ยนทุกครั้งที่รัน เราไม่ต้องจำมัน ให้อ่านแค่โครงของต้นไม้

<Callout type="warn" title="explain() ไม่ได้รัน Query">
เรียก `explain()` กี่ครั้งก็ไม่เกิด Spark Job (วัดจริงด้วย Job Group: 0 Job) มันแค่พิมพ์แผนที่ Spark มีอยู่ในมือ และถ้าเปิด AQE แผนที่พิมพ์ก่อน Action ก็ยังไม่ใช่แผนสุดท้าย ดูหัวข้อ AQE ข้างล่าง
</Callout>

</Step>

## โหมดของ `explain()`

| เรียกด้วย | พิมพ์อะไร |
|---|---|
| `explain()` | Physical Plan แบบย่อ |
| `explain(True)` หรือ `"extended"` | Parsed, Analyzed, Optimized และ Physical |
| `explain("formatted")` | **Physical Plan อย่างเดียว** แต่จัดเป็นต้นไม้มีเลข และมีบล็อกรายละเอียดของ Operator ทีละตัว |
| `explain("cost")` | Optimized Plan พร้อมสถิติ (`sizeInBytes`, `rowCount`) |
| `explain("codegen")` | โค้ด Java ที่ Whole-stage Codegen สร้าง |

คนมักสับสนว่า `formatted` แสดงมากกว่า `extended` แต่จริง ๆ แล้ว `formatted` ไม่พิมพ์ Parsed, Analyzed หรือ Optimized เลย ถ้าอยากได้สี่แผนต้องใช้ `explain(True)`

`formatted` อ่านง่ายกว่าเมื่อแผนยาว เพราะ Operator ถูกเลขกำกับ แล้วรายละเอียดอยู่ข้างล่างตามเลข

```
== Physical Plan ==
* Project (3)
+- * Filter (2)
   +- * Range (1)

(1) Range [codegen id : 1]
Output [1]: [id#0L]
Arguments: Range (0, 1000, step=1, splits=Some(16))

(2) Filter [codegen id : 1]
Input [1]: [id#0L]
Condition : (id#0L > 10)
```

</Step>

## Optimizer เขียนแผนใหม่ทีละกฎ

Optimizer ไม่ได้คิดแผนที่ดีที่สุดในครั้งเดียว แต่มี **Rule** เป็นร้อยตัว ซึ่งแต่ละตัวทำเรื่องเล็กมาก (ย้าย Filter, รวม Project สองชั้น, คิด `1 + 2` ให้เป็น `3`) แล้วรันซ้ำจนแผนไม่เปลี่ยน ลองกดไล่ดูทีละกฎ ในแล็บนี้เป็น Trace จริงของ Query หนึ่งตัวที่ใช้ View ซ้อนกัน

ก่อนดู Trace จริง ลองดูภาพรวมว่ากฎของ Optimizer ช่วยอะไรบ้าง ภาพนี้เป็น Query ที่มี Join กับ Filter จุดที่วิ่งขึ้นคือแถวที่ไหลผ่านแต่ละ Node

<PushdownFlowLab client:visible />

แล้วจึงดู Trace ของ Query จริงทีละกฎ

<PlanPipelineLab client:visible />

มีสามอย่างที่ควรสังเกต

- `1 = 1` ถูกกำจัดด้วยกฎสองตัวต่อกัน (`ConstantFolding` แล้ว `BooleanSimplification`) ไม่มีกฎไหนทำคนเดียว
- `PushDownPredicates` ทำให้ Filter ลงไปอยู่ติด `Range` ซึ่งถ้าเป็นไฟล์ Parquet ตรงนี้คือจุดที่ Filter ถูกส่งต่อให้ตัวอ่านไฟล์
- `ColumnPruning` ทำให้ Column `dbl` ที่ไม่มีใครอ่านถูกตัดทิ้ง ก่อนที่จะรวม Project ด้วย `CollapseProject`

กฎทั้งหมดอยู่ใน Batch ที่รันต่างกัน บาง Batch รันครั้งเดียว (`Once`) บาง Batch รันซ้ำจนแผนไม่เปลี่ยน (`FixedPoint` สูงสุด 100 รอบ) รายละเอียดของแต่ละ Batch อยู่ในหน้า [Catalyst ข้างใน](/spark/catalyst-aqe/in-depth/#batch-ของ-optimizer)

</Step>

## ผลของ Pushdown ที่เห็นใน Plan ของไฟล์

กฎอย่าง `ColumnPruning` และ `PushDownPredicates` ส่งผลไปถึงตัวอ่านไฟล์ ตัวอย่างนี้อ่านไฟล์ CSV 4 Column แล้วเลือกแค่ `name` กรองด้วย `amount` และ `country` (รัน: `exercises/06_catalyst_aqe.py`)

```python
spark.sql("SELECT name FROM orders WHERE amount > 100 AND country = 'th'").explain()
```

```
*(1) Project [name#18]
+- *(1) Filter (((isnotnull(amount#19) AND isnotnull(country#20)) AND (amount#19 > 100.0)) AND (country#20 = th))
   +- FileScan csv [name#18,amount#19,country#20] Batched: false, ...
      PushedFilters: [IsNotNull(amount), IsNotNull(country), GreaterThan(amount,100.0), EqualTo(country,th)],
      ReadSchema: struct<name:string,amount:double,country:string>
```

- `ReadSchema` มี 3 Column จาก 4 ตัว (`id` ถูกตัด) นี่คือ **Column Pruning**
- `PushedFilters` คือเงื่อนไขที่ Spark ส่งให้ตัวอ่านไฟล์ โดยมี `IsNotNull` ที่ Catalyst เติมเองด้วย (Rule `InferFiltersFromConstraints`) เพราะ `amount > 100` เป็นจริงไม่ได้ถ้า `amount` เป็น Null
- `Filter` ยังอยู่เหนือ Scan แม้ Push แล้ว

<Callout type="warn" title="Pushdown ไม่ได้แปลว่า Filter หายไป">
`PushedFilters` คือคำใบ้ที่ส่งให้ตัวอ่านไฟล์ ตัวอ่านบางชนิด (เช่น Parquet) ใช้มันข้ามข้อมูลได้ แต่ Spark ยังเก็บ `Filter` ไว้ตรวจซ้ำเสมอ ตัวอย่างนี้ใช้ CSV เพราะตรวจบนคอมพิวเตอร์เครื่องนี้ได้ ส่วนพฤติกรรมของ Parquet เช่นการข้าม Row Group ยังไม่ได้ทดสอบที่นี่ จึงไม่ขอยืนยันตัวเลข
</Callout>

Filter ยังถูกส่งข้ามไปอีกฝั่งของ Join ได้ด้วย ถ้าเราเขียน `WHERE a_id > 990` ครั้งเดียวบน `a JOIN c ON a_id = c_id` Optimized Plan จะมี `Filter (id > 990)` สองตัว ทั้งฝั่ง a และฝั่ง c เพราะเงื่อนไข Join ทำให้ `c_id > 990` เป็นจริงโดยปริยาย

</Step>

## Join ตัวไหน และใครเลือก

Catalyst เลือก **Physical Join** ตามขนาดข้อมูล ลำดับคร่าว ๆ ที่ `JoinSelection` ใช้เมื่อไม่มี Hint เป็นดังนี้ (Source: `SparkStrategies.scala:219-236`)

1. ถ้าฝั่งหนึ่งเล็กกว่า `spark.sql.autoBroadcastJoinThreshold` (ค่าเริ่มต้น **10 MB**) ก็ใช้ `BroadcastHashJoin`
2. ถ้าข้อมูลเรียงลำดับได้ ก็ใช้ `SortMergeJoin`
3. ที่เหลือคือ Cartesian หรือ Nested Loop ซึ่งช้ามาก

ลองเทียบ Plan ของ Join เดียวกันที่ต่างกันแค่ Threshold (รัน: `exercises/06_catalyst_aqe.py`, ตาราง `big` 5 ล้านแถวกับ `small` 100 แถว)

```
-- threshold ค่าเริ่มต้น --          -- spark.sql.autoBroadcastJoinThreshold = -1 --
BroadcastHashJoin [k], [k], Inner     SortMergeJoin [k], [k], Inner
:- Range (5000000)                    :- Sort [k]
+- BroadcastExchange                  :  +- Exchange hashpartitioning(k, 200)
   +- Range (100)                     :     +- Range (5000000)
                                      +- Sort [k]
                                         +- Exchange hashpartitioning(k, 200)
                                            +- Range (100)
```

Broadcast Join ไม่มี `Exchange` ฝั่งตารางใหญ่ ข้อมูลของตารางใหญ่จึงไม่ต้องย้ายเลย ส่วน Sort-merge ต้อง Shuffle และ Sort ทั้งสองฝั่ง

ถ้าใส่ Hint `F.broadcast(small)` Hint จะชนะ Threshold เสมอ ต่อให้ตั้ง Threshold เป็น -1 แล้วใส่ Hint ก็ยังได้ `BroadcastHashJoin`

<Callout type="note" title="Catalyst ไม่ได้เรียงลำดับ Join ตามขนาด">
มี 2 อย่างที่มักเข้าใจผิด Rule `ReorderJoin` ที่เปิดอยู่เสมอ แค่จัดลำดับเพื่อไม่ให้เกิด Cartesian Product (a join b โดยไม่มีเงื่อนไข) โดยไม่ดูขนาด ส่วน Cost-based Reorder (`CostBasedJoinReorder`) ต้องเปิด `spark.sql.cbo.enabled` กับ `spark.sql.cbo.joinReorder.enabled` ซึ่งปิดอยู่ทั้งคู่ (ตรวจแล้วเป็น `false`)
</Callout>

</Step>

## ปัญหาที่ Catalyst แก้ไม่ได้

ทั้งหมดข้างบนเกิด **ก่อน** รัน Catalyst จึงตัดสินใจจากสถิติที่รู้ล่วงหน้า เช่นขนาดไฟล์ แต่หลายครั้งมันรู้ไม่ได้ เช่น

- หลัง `filter` ซับซ้อนหรือ `groupBy` จะเหลือกี่แถว
- ข้อมูลหลัง Shuffle ที่แบ่งเป็น 200 Partition กระจายเท่ากันไหม
- ตารางที่ดูใหญ่ จริง ๆ แล้วหลังกรองจะเล็กพอ Broadcast ได้ไหม

ถ้าเดาผิด เราจะได้ Shuffle 200 Partition ที่แต่ละก้อนมีไม่กี่ไบต์ (เปลือง Task) หรือได้ Sort-merge Join ทั้งที่ฝั่งหนึ่งเล็กนิดเดียว

**AQE** แก้ตรงนี้ด้วยการ "รันไปก่อนครึ่งหนึ่ง แล้วค่อยตัดสินใจใหม่" โดยตัดแผนที่ Shuffle ออกเป็นช่วง ๆ เรียกว่า **Query Stage** รัน Stage แรกให้จบ อ่านขนาดข้อมูลจริงที่ออกมา แล้ว Optimize แผนส่วนที่เหลืออีกครั้งด้วยตัวเลขจริง

</Step>

## เปิดอยู่แล้ว: `AdaptiveSparkPlan`

`spark.sql.adaptive.enabled` เป็น `true` โดยค่าเริ่มต้น ผลที่เห็นคือ Plan ของ Query ที่มี Shuffle จะขึ้นต้นด้วย `AdaptiveSparkPlan` (รัน: `exercises/06_catalyst_aqe.py`)

```python
g = spark.range(1_000_000).groupBy((F.col("id") % 3).alias("k")).count()
g.explain()      # ก่อนรัน
g.collect()
g.explain()      # หลังรัน
```

```
-- ก่อนรัน --
AdaptiveSparkPlan isFinalPlan=false
+- HashAggregate(keys=[...], functions=[count(1)])
   +- Exchange hashpartitioning(..., 200), ENSURE_REQUIREMENTS
      +- HashAggregate(keys=[...], functions=[partial_count(1)])
         +- Project ...

-- หลังรัน --
AdaptiveSparkPlan isFinalPlan=true
+- == Final Plan ==
   ResultQueryStage 1
   +- *(2) HashAggregate(keys=[...], functions=[count(1)])
      +- AQEShuffleRead coalesced
         +- ShuffleQueryStage 0
            +- Exchange hashpartitioning(..., 200), ENSURE_REQUIREMENTS
               +- *(1) HashAggregate(...partial_count(1))
+- == Initial Plan ==
   HashAggregate(...) ...
```

- `isFinalPlan=false` ก่อนรัน แปลว่าแผนนี้ยังเปลี่ยนได้
- หลังรัน แผนจะมีสองส่วน คือ **Final Plan** (สิ่งที่รันจริง) และ **Initial Plan** (ที่ Spark วางไว้ตอนแรก)
- บรรทัด `Exchange ... 200` ยังอยู่ใน Final Plan แต่ไม่ได้แปลว่ามี 200 Task จริง ให้ดูบรรทัด `AQEShuffleRead coalesced` ที่รวม Partition แล้ว (วัดจริง: `getNumPartitions()` ได้ **1**)

<Callout type="warn" title="กับดักสามข้อของ isFinalPlan">
1. `isFinalPlan` จะพลิกเป็น `true` เฉพาะ DataFrame **ตัวที่รันจริง** ถ้าเรียก `g.count()` หรือ `g.show()` จะสร้าง Query ใหม่ (เพิ่ม Aggregate หรือ Limit) `g.explain()` หลังจากนั้นจึงยังเป็น `false` ต้องใช้ `g.collect()` หรือ `g.rdd` บน Object เดิม
2. ไม่ใช่ทุก Plan ที่มี `AdaptiveSparkPlan` ถ้า Query ไม่มี Shuffle และไม่มี Subquery (เช่น `range` กับ `filter`) Spark จะไม่ห่อด้วย AQE
3. AQE ทำให้ Action เดียวเกิดหลาย Job (วัดจริง: 2 Job คือ Map Stage แล้วค่อย Result Stage) ใน Spark UI จึงเห็น Job มากกว่าที่คิด
</Callout>

</Step>

## AQE ทำสามอย่าง

ทั้งสามอย่างทำตามลำดับเดียวกัน คือ Stage แรกรันจบ แล้ว AQE วัดขนาดจริง จากนั้นเขียนแผนใหม่ และ Stage ถัดไปรันตามแผนใหม่ แถบสี่ช่วงด้านบนของภาพบอกว่าตอนนี้อยู่ช่วงไหน และบรรทัดแผนใต้แถบก็เปลี่ยนตามเหมือนที่ `explain()` แสดง เลือกสถานการณ์แล้วกดเล่น หรือลาก Slider ได้เลย ตัวเลขของ Coalesce และ Join มาจากการรันจริง ส่วนขนาด Partition ใน Skew ใช้ตัวอย่างสมมติ (ชื่อ Config และสูตรเป็นของจริง)

<AqeFlowLab client:visible />

| ทำอะไร | Rule | Config หลัก (ค่าเริ่มต้น) |
|---|---|---|
| รวม Partition เล็กหลัง Shuffle | `CoalesceShufflePartitions` | `coalescePartitions.enabled` (True), `advisoryPartitionSizeInBytes` (64 MB), `minPartitionSize` (1 MB) |
| เปลี่ยน Join เป็น Broadcast | `DynamicJoinSelection` + `OptimizeShuffleWithLocalRead` | `autoBroadcastJoinThreshold` (10 MB), `localShuffleReader.enabled` (True) |
| แยก Partition ที่ Skew (ใหญ่ไม่สมดุลกับตัวอื่น) | `OptimizeSkewedJoin` | `skewJoin.enabled` (True), `skewedPartitionFactor` (5.0), `skewedPartitionThresholdInBytes` (256 MB) |

ทุก Config ข้างบนมีคำนำหน้า `spark.sql.adaptive.` ยกเว้น `autoBroadcastJoinThreshold` ที่มีคำนำหน้า `spark.sql.`

<Callout type="warn" title="สองสิ่งที่ AQE ไม่ได้สัญญา">
AQE ไม่ได้ Broadcast ฝั่งเล็กเสมอไป ถ้าฝั่งเล็กกระจายอยู่ใน Partition ที่ไม่ว่างน้อยกว่า 20% (`nonEmptyPartitionRatioForBroadcastJoin`) AQE ยังคง Sort-merge Join ไว้ (รันแล้วพบจริง: 4 แถวใน 200 Partition ไม่ถูกเปลี่ยน)

Skew Join ไม่ทำงานกับข้อมูลทดลองเล็ก ๆ เพราะ Threshold ค่าเริ่มต้นคือ 256 MB ในแล็บของบทนี้เราต้องลดเป็น 50 KB กับ Advisory 100 KB ถึงจะเห็น `SortMergeJoin(skew=true)` (Partition ของผลลัพธ์: 1 ตอนค่าเริ่มต้น, 23 ตอนลด Threshold, 8 ตอนปิด Skew Join)
</Callout>

</Step>

## Tungsten แบบย่อ

Catalyst เลือกว่าจะรันอะไร ส่วน **Tungsten** คือวิธีรันให้เร็วในระดับ CPU และ Memory มีสองเรื่องที่ควรรู้

- **Whole-stage Codegen** เป็นการรวม Operator ที่ต่อกันและไม่ต้อง Shuffle (เช่น `Range` → `Filter` → `Project`) ให้เป็นโค้ด Java ก้อนเดียวที่ลูปครั้งเดียว แทนที่จะส่งแถวต่อกันทีละ Operator ใน Plan จะเห็นเป็น `*(1)` ที่นำหน้า Operator ส่วน `Exchange` ไม่เคยอยู่ใน Codegen เพราะเป็นขอบเขตของ Stage
- **UnsafeRow** เก็บแถวข้อมูลเป็นไบต์ดิบ ไม่ใช่ Object ของ JVM ทำให้ลดภาระ Garbage Collector และเปรียบเทียบข้อมูลได้เร็ว (Off-heap Memory ปิดอยู่เป็นค่าเริ่มต้น: `spark.memory.offHeap.enabled=false`)

บทนี้ไม่อ้างตัวเลขว่า Codegen เร็วกี่เท่า เพราะยังไม่ได้วัดเอง

</Step>

## ลองทำ

```bash
cd subjects/spark/code
```

สคริปต์จะรันทุกตัวอย่างในบทและ `assert` ผลของแต่ละข้อ รันครั้งเดียวใช้เวลาราว 20 วินาที ถ้า Spark เวอร์ชันที่คุณใช้ให้ผลต่างจากบท สคริปต์ก็จะบอกว่าข้อไหนไม่ตรง

ลองเล่นเองดูได้เลย

1. เปลี่ยน `spark.sql.autoBroadcastJoinThreshold` เป็น `-1` แล้วดู `explain()` ของ Join ว่า `Exchange` โผล่มาสองตัวไหม

3. ตั้ง `spark.sql.planChangeLog.level=WARN` แล้วรัน Query ที่มี `WHERE 1 = 1` ดูกฎที่ทำงานใน Log

## เช็กตัวเอง

- ดู `explain(True)` แล้วชี้ได้ไหมว่า Filter ถูกย้ายตรงไหน และอ่านจากอะไร
- `PushedFilters` กับ `Filter` ที่ยังอยู่ใน Plan ต่างกันอย่างไร
- ทำไม AQE ถึงต้องรัน Stage แรกให้จบก่อนถึงเปลี่ยนแผนได้
- `isFinalPlan=false` หลัง `df.count()` แปลว่าอะไร
