## `QueryExecution` ทีละ Member

Class `QueryExecution` (`QueryExecution.scala:67`) ถือแผนทุกแบบไว้เป็น `lazy val` และไม่มี Member ชื่อ `parsedPlan` ส่วน Parsed ที่ `explain` พิมพ์ออกมาคือ Argument ชื่อ `logical` ที่ส่งเข้ามาตอนสร้าง

| Member | ทำอะไร | บรรทัด |
|---|---|---|
| `analyzed` | `analyzer.executeAndCheck(...)` | 192-213 |
| `commandExecuted` | รัน `Command` Node ทันที เช่นงานเขียนใน `CREATE TABLE AS SELECT` | 215-225 |
| `withCachedData` | แทนที่ส่วนที่ `cache()` ไว้ด้วยข้อมูลใน Cache | 289-307 |
| `optimizedPlan` | `optimizer.executeAndTrack(...)` | 311-331 |
| `sparkPlan` | `planner.plan(ReturnAnswer(plan)).next()` ซึ่งเอาตัวเลือกแรกเสมอ | 335-349 |

## `RuleExecutor`: Batch, `Once` และ `FixedPoint`

Analyzer และ Optimizer สืบจาก `RuleExecutor` (`RuleExecutor.scala:215-325`) ซึ่งทำงานดังนี้

1. มีรายการ **Batch** โดยแต่ละ Batch คือกลุ่มของ Rule กับ Strategy
2. ไล่ Batch ตามลำดับ ในแต่ละ Batch จะรัน Rule ทุกตัวหนึ่งรอบ
3. ถ้า Strategy เป็น `Once` (maxIterations = 1) ก็จบ
4. ถ้าเป็น `FixedPoint(n)` จะวนซ้ำจนแผนไม่เปลี่ยน (`curPlan.fastEquals(lastPlan)`, บรรทัด 312) หรือครบ n รอบ

ลองดู Batch หนึ่งทำงานจริงกับ Query ที่มี Subquery ซ้อนสี่ชั้น (รัน: `exercises/06b_rule_iterations.py`) Spark รายงานว่า Batch นี้วน **4 รอบ** กดเล่นหรือลาก Slider ดูได้เลยว่าแต่ละ Rule เปลี่ยนแผนตรงไหน และรอบสุดท้ายทำไมไม่มีอะไรเปลี่ยนแต่ยังต้องมี

<RuleLoopLab client:visible />

กับ Query ธรรมดาที่ไม่ซ้อน Batch เดียวกันนี้วนแค่ 2 รอบ (วัดจริงทั้ง Query ที่ใช้ View และ Query ที่ Join กับ Filter) รอบแรกเปลี่ยนแผน รอบที่สองพิสูจน์ว่านิ่งแล้ว ส่วนตัว Analyzer ของ Query ซ้อนสี่ชั้นใช้ Batch Resolution ถึง 9 รอบ เพราะแต่ละรอบ Resolve ได้ทีละชั้น

ค่าสูงสุดของ `FixedPoint` คือ `spark.sql.optimizer.maxIterations` และ `spark.sql.analyzer.maxIterations` ซึ่งทั้งคู่เป็น 100 ถ้าครบ 100 รอบแล้วแผนยังเปลี่ยนอยู่ Optimizer จะแค่เตือน (`errorOnExceed = false`) แต่ Analyzer ตั้ง `errorOnExceed = true` จึงเกิด Error

</Step>

## Analyzer และ ANSI Mode ที่ถูกล็อกตอน Analyze

Analyzer ทำงานเป็น Batch เหมือนกัน Batch ใหญ่คือ **Resolution** (`Analyzer.scala:539`, FixedPoint) ที่ประกอบด้วย `ResolveRelations`, `ResolveReferences`, Type Coercion และอื่น ๆ ส่วน Query เล็ก ๆ อย่าง `SELECT ... FROM v` ใช้แค่ `ResolveRelations`, `ResolveReferences`, `AnsiTypeCoercion`, `ResolveUpCast`, `ResolveTimeZone` (Trace จาก plan change log)

Rule ของ Type Coercion เลือกตาม ANSI Mode โดยใช้ `AnsiTypeCoercion` เมื่อเปิด และ `TypeCoercion` เมื่อปิด (`Analyzer.scala:506-510`) ค่าเริ่มต้นของ `spark.sql.ansi.enabled` คือ True เว้นแต่ตัวแปรสภาพแวดล้อม `SPARK_ANSI_SQL_MODE=false`

สิ่งที่คนมักพลาดคือ **ANSI Mode ถูกล็อกตอน Analyze ไม่ใช่ตอนรัน** (รัน)

```python
spark.conf.set("spark.sql.ansi.enabled", "true")
df = spark.createDataFrame([("abc",)], "s string").selectExpr("cast(s as int) AS i")
spark.conf.set("spark.sql.ansi.enabled", "false")
df.collect()     # ยัง error: CAST_INVALID_INPUT
```

DataFrame ถูก Analyze ตอนบรรทัดแรก ซึ่งตอนนั้น ANSI เปิดอยู่ ต่อให้ปิดทีหลังก็ไม่ช่วย ถ้าอยากเห็น `NULL` ต้องปิดก่อนสร้าง DataFrame

Plan Text ของ Cast ไม่ต่างกันระหว่างสองโหมด (ทั้งคู่เป็น `cast(s as int)`) ความต่างอยู่ที่โค้ดที่ Generate โดย `explain("codegen")` ของ `a + 1` จะมี `MathUtils.addExact` เมื่อเปิด ANSI และไม่มีเมื่อปิด

</Step>

## ลูปของ AQE

`AdaptiveSparkPlanExec` (`AdaptiveSparkPlanExec.scala:69`) คือ Leaf Node ที่ถือแผนเดิมไว้ ลูปหลักคือ `withFinalPlanUpdate` (บรรทัด 268-396)

1. **สร้าง Query Stage** โดยตัดแผนตรง `Exchange` เป็น `ShuffleQueryStage` และ `BroadcastQueryStage` (`createQueryStages`, บรรทัด 543)
2. **เริ่ม Materialize** Stage ที่พร้อม โดย Broadcast Stage ก่อน (บรรทัด 293-322) แล้วบล็อกรอ Event ว่ามี Stage ไหนเสร็จ (บรรทัด 328)
3. **แทน Stage ที่เสร็จ** เข้าไปใน Logical Plan ด้วยสถิติจริง (บรรทัด 357)
4. **`reOptimize`** (บรรทัด 805-835) ล้าง Cache ของสถิติ, รัน `AQEOptimizer`, วางแผนใหม่ด้วย Planner, รัน Physical Rule อีกชุด
5. **เทียบ Cost** แล้วรับแผนใหม่เมื่อ Cost ต่ำกว่า หรือเท่ากันแต่แผนต่างกัน (บรรทัด 367-379)
6. วนกลับไปข้อ 1 จนไม่เหลือ Stage ที่ต้องสร้าง แล้วตั้ง `_isFinalPlan = true` (บรรทัด 389)

ลองดูลูปนี้ทำงานกับ Query `groupBy(k).count()` ของบทหลัก ครั้งนี้เราจะเห็นครบหกข้อ และรอบที่สองที่สร้าง Stage สุดท้าย

<AqeLoopLab client:visible />

ใน 4.2 Stage สุดท้ายคือ `ResultQueryStage` (บรรทัด 345, 394) ซึ่งไม่มีในเอกสารเก่า

**Cost คืออะไร** ค่าเริ่มต้นคือ `SimpleCostEvaluator` ซึ่งนับ **จำนวน `ShuffleExchangeLike` ในแผน** เท่านั้น (`simpleCosting.scala:42-65`) ดังนั้น AQE จะยอมรับแผนใหม่ที่ Shuffle น้อยลง หรือเท่าเดิมแต่ต่างกัน โดยไม่ได้ดูขนาดข้อมูลหรือเวลาเลย

`AQEOptimizer` (Logical, `AQEOptimizer.scala:39-47`) มี Batch ได้แก่ Propagate Empty Relations, **Dynamic Join Selection** (Once), Eliminate Limits, Optimize One Row Plan ส่วน Rule ระดับ Physical ต่อ Stage (`AdaptiveSparkPlanExec.scala:137-145`) คือ `CoalesceShufflePartitions`, `OptimizeShuffleWithLocalRead`, `OptimizeSkewInRebalancePartitions` และ Rule ของ Dynamic Pruning กับ Subquery

</Step>

## ทำไมถึงรวมเหลือ 1 Partition

ตัวเลข "200 กลายเป็น 1" มาจากสูตรใน `ShufflePartitionsUtil.scala:60-62`

```
target = max( min( totalBytes / minNumPartitions , advisory ), minPartitionSize )
```

ใน Query ของบทหลัก Shuffle รวมกันแค่ 1,152 ไบต์ (48 แถว = 16 Map Task คูณ 3 Key หลัง Partial Aggregate) บนคอมพิวเตอร์เครื่องนี้ `defaultParallelism` = 16 (เมื่อ `parallelismFirst` เป็น True จะใช้ค่านี้เป็น `minNumPartitions`, `CoalesceShufflePartitions.scala:59-69`)

- `totalBytes / minNumPartitions` = 1152 / 16 = 72 ไบต์
- `min(72 B, advisory 64 MB)` = 72 ไบต์
- `max(72 B, minPartitionSize 1 MB)` = **1 MB**

เป้า 1 MB ใหญ่กว่าข้อมูลทั้งก้อนมาก Partition ที่อยู่ติดกันจึงถูกรวมเข้าหากันจนเหลือ 1 เราลองเปลี่ยนค่าดูได้ดังนี้ (รัน)

| ตั้งค่า | Partition ที่ได้ |
|---|---|
| ค่าเริ่มต้น | 1 |
| `spark.sql.adaptive.enabled=false` | 200 |
| `coalescePartitions.enabled=false` | 200 |
| `coalescePartitions.parallelismFirst=false` | 1 |
| Advisory = 1 Byte, minPartitionSize = 1 Byte | 3 (มีข้อมูลแค่ 3 จาก 200 Partition: Key 0, 1, 2) |

ตัวเลขนี้ขึ้นกับจำนวน Core และปริมาณข้อมูล บนข้อมูลจริงหลาย GB เป้าจะเป็นราว 64 MB ต่อ Partition ไม่ใช่ 1 Partition

</Step>

## เมื่อไหร่ที่ AQE ไม่ห่อแผน

`InsertAdaptiveSparkPlan` (`InsertAdaptiveSparkPlan.scala:44`) จะห่อแผนด้วย AQE เฉพาะเมื่อข้อใดข้อหนึ่งเป็นจริง (บรรทัด 99-124)

- แผนมี `Exchange` อยู่แล้ว
- มี Operator ที่ต้องการ Distribution ใหม่ ซึ่งจะทำให้เกิด `Exchange`
- มี Subquery
- `spark.sql.adaptive.forceApply` เป็น True (Internal, ค่าเริ่มต้น False)

และจะข้ามเสมอเมื่อเป็น Command (บรรทัด 52-58) หรือ Streaming แบบ Stateful (บรรทัด 62-70)

ดังนั้น `spark.range(100).filter("id > 5")` จึงไม่มี `AdaptiveSparkPlan` ในแผนเลย (รัน)

</Step>

## ข้อควรระวังเพิ่มเติม

1. **Join Strategy ที่ AQE เปลี่ยนใช้ขนาดจริงของ Shuffle Output** `canBroadcastBySize` (`joins.scala:367-375`) ใช้ `spark.sql.autoBroadcastJoinThreshold` หรือถ้าตั้ง `spark.sql.adaptive.autoBroadcastJoinThreshold` (ค่าเริ่มต้นไม่ตั้ง) ก็ใช้ตัวนั้นกับสถิติ Runtime
2. **เมื่อฝั่งเล็กมี Partition ว่างเกินไป** `DynamicJoinSelection` จะใส่ `NO_BROADCAST_HASH` ให้ฝั่งนั้น (`DynamicJoinSelection.scala:30-44`) ถ้าตั้ง `nonEmptyPartitionRatioForBroadcastJoin=0` แล้ว Query เดิมจะกลายเป็น `BroadcastHashJoin` (รัน)
3. **Skew Join ต้องมี Shuffled Join** เพราะ Broadcast Join ไม่มี Shuffle ให้แยก Threshold คือ `max(skewedPartitionThresholdInBytes, median × skewedPartitionFactor)` (`OptimizeSkewedJoin.scala:65-68`) Partition ที่ Skew จะถูกหั่นตามช่วงของ Map Task และ Partition อีกฝั่งถูกทำสำเนา ถ้าทั้งสองฝั่ง Skew จะกลายเป็น Cartesian ของชิ้นย่อย
4. **Filter ที่อนุมานข้าม Join ทำให้ขนาดฝั่งตรงข้ามเล็กลงโดยไม่คาดคิด** ในการทดลอง Filter บน Key ที่คำนวณจากฝั่งขวาทำให้ฝั่งซ้ายถูกกรองเหมือนกัน ถ้าต้องการให้ขนาดของฝั่งหนึ่ง "ไม่รู้" ให้ใช้ Non-deterministic Filter อย่าง `F.rand(42) < 0.000002` ซึ่งจะไม่ถูกอนุมานหรือ Push
5. **ชื่อ Scan ไม่เหมือนกันระหว่างโหมด** คือ `Scan csv` ใน `formatted` แต่เป็น `FileScan csv` ใน Tree แบบอื่น
6. **ค่า Config ที่อ่านใน Python มีหน่วยต่อท้าย** เช่น `spark.conf.get("spark.sql.adaptive.advisoryPartitionSizeInBytes")` ได้ `67108864b`
7. **สิ่งที่ยังไม่ได้ทดสอบ** ได้แก่ พฤติกรรม Pushdown ของ Parquet/ORC (คอมพิวเตอร์เครื่องนี้เขียน Parquet ไม่ได้ ตัวอย่างจึงใช้ CSV), การรวม Partition ของ `repartition(n)` (อ่านจาก `supportedShuffleOrigins` ไม่มี `REPARTITION_BY_NUM`), และตัวเลขความเร็วของ Tungsten/Codegen/AQE

</Step>
