## `RuleExecutor`: Batch, `Once` และ `FixedPoint`

Analyzer และ Optimizer สืบจาก `RuleExecutor` (`RuleExecutor.scala:215-325`) งานของมันคือ

1. มีรายการ **batch** แต่ละ batch คือกลุ่มของ rule กับ strategy
2. ไล่ batch ตามลำดับ ในแต่ละ batch รัน rule ทุกตัวหนึ่งรอบ
3. ถ้า strategy เป็น `Once` (maxIterations = 1) จบ
4. ถ้าเป็น `FixedPoint(n)` วนซ้ำจนแผนไม่เปลี่ยน (`curPlan.fastEquals(lastPlan)`, บรรทัด 312) หรือครบ n รอบ

ลองดู batch หนึ่งทำงานจริงกับ query ที่มี subquery ซ้อนสี่ชั้น (รัน: `exercises/06b_rule_iterations.py`) Spark รายงานว่า batch นี้วน **4 รอบ** กดเล่นหรือลาก slider ดูว่าแต่ละ rule เปลี่ยนแผนตรงไหน และรอบสุดท้ายทำไมไม่มีอะไรเปลี่ยนแต่ยังต้องมี

<RuleLoopLab client:visible />

กับ query ธรรมดาที่ไม่ซ้อน batch เดียวกันนี้วนแค่ 2 รอบ (วัดจริงทั้ง query ที่ใช้ view และ query ที่ join กับ filter) รอบแรกเปลี่ยนแผน รอบที่สองพิสูจน์ว่านิ่งแล้ว ส่วนตัว Analyzer ของ query ซ้อนสี่ชั้นใช้ batch Resolution ถึง 9 รอบ เพราะแต่ละรอบ resolve ได้ทีละชั้น

ค่าสูงสุดของ `FixedPoint` คือ `spark.sql.optimizer.maxIterations` และ `spark.sql.analyzer.maxIterations` ทั้งคู่ 100 ถ้าครบ 100 รอบแล้วแผนยังเปลี่ยนอยู่ Optimizer แค่เตือน (`errorOnExceed = false`) แต่ Analyzer ตั้ง `errorOnExceed = true` จึง error

</Step>

## Analyzer และ ANSI Mode ที่ถูกล็อกตอน Analyze

Analyzer ทำงานเป็น batch เหมือนกัน batch ใหญ่คือ **Resolution** (`Analyzer.scala:539`, FixedPoint) ที่ประกอบด้วย `ResolveRelations`, `ResolveReferences`, type coercion และอื่นๆ query เล็กๆ อย่าง `SELECT ... FROM v` ใช้แค่ `ResolveRelations`, `ResolveReferences`, `AnsiTypeCoercion`, `ResolveUpCast`, `ResolveTimeZone` (trace จาก plan change log)

rule ของ type coercion เลือกตาม ANSI mode: `AnsiTypeCoercion` เมื่อเปิด และ `TypeCoercion` เมื่อปิด (`Analyzer.scala:506-510`) ค่าเริ่มต้นของ `spark.sql.ansi.enabled` คือ true เว้นแต่ตัวแปรสภาพแวดล้อม `SPARK_ANSI_SQL_MODE=false`

สิ่งที่คนมักพลาดคือ **ANSI mode ถูกล็อกตอน analyze ไม่ใช่ตอนรัน** (รัน)

```python
spark.conf.set("spark.sql.ansi.enabled", "true")
df = spark.createDataFrame([("abc",)], "s string").selectExpr("cast(s as int) AS i")
spark.conf.set("spark.sql.ansi.enabled", "false")
df.collect()     # ยัง error: CAST_INVALID_INPUT
```

DataFrame ถูก analyze ตอนบรรทัดแรก ตอนนั้น ANSI เปิด ต่อให้ปิดทีหลังก็ไม่ช่วย ถ้าอยากเห็น `NULL` ต้องปิดก่อนสร้าง DataFrame

plan text ของ cast ไม่ต่างกันระหว่างสองโหมด (ทั้งคู่เป็น `cast(s as int)`) ความต่างอยู่ที่โค้ดที่ generate: `explain("codegen")` ของ `a + 1` มี `MathUtils.addExact` เมื่อเปิด ANSI และไม่มีเมื่อปิด

## ลูปของ AQE

`AdaptiveSparkPlanExec` (`AdaptiveSparkPlanExec.scala:69`) คือ leaf node ที่ถือแผนเดิมไว้ ลูปหลักคือ `withFinalPlanUpdate` (บรรทัด 268-396)

1. **สร้าง query stage**: ตัดแผนตรง `Exchange` เป็น `ShuffleQueryStage` และ `BroadcastQueryStage` (`createQueryStages`, บรรทัด 543)
2. **เริ่ม materialize** stage ที่พร้อม broadcast stage ก่อน (บรรทัด 293-322) แล้วบล็อกรอ event ว่ามี stage ไหนเสร็จ (บรรทัด 328)
3. **แทน stage ที่เสร็จ** เข้าไปใน logical plan ด้วยสถิติจริง (บรรทัด 357)
4. **`reOptimize`** (บรรทัด 805-835): ล้าง cache ของสถิติ, รัน `AQEOptimizer`, วางแผนใหม่ด้วย planner, รัน physical rule อีกชุด
5. **เทียบ cost** แล้วรับแผนใหม่เมื่อ cost ต่ำกว่า หรือเท่ากันแต่แผนต่างกัน (บรรทัด 367-379)
6. วนกลับไปข้อ 1 จนไม่เหลือ stage ที่ต้องสร้าง แล้วตั้ง `_isFinalPlan = true` (บรรทัด 389)

ลองดูลูปนี้ทำงานกับ query `groupBy(k).count()` ของบทหลัก ครั้งนี้เห็นครบหกข้อและรอบที่สองที่สร้าง stage สุดท้าย

<AqeLoopLab client:visible />

ใน 4.2 stage สุดท้ายคือ `ResultQueryStage` (บรรทัด 345, 394) ซึ่งไม่มีในเอกสารเก่า

**cost คืออะไร** ค่าเริ่มต้นคือ `SimpleCostEvaluator` ซึ่งนับ **จำนวน `ShuffleExchangeLike` ในแผน** เท่านั้น (`simpleCosting.scala:42-65`) ดังนั้น AQE ยอมรับแผนใหม่ที่ shuffle น้อยลง หรือเท่าเดิมแต่ต่างกัน ไม่ได้ดูขนาดข้อมูลหรือเวลาเลย

`AQEOptimizer` (logical, `AQEOptimizer.scala:39-47`) มี batch: Propagate Empty Relations, **Dynamic Join Selection** (Once), Eliminate Limits, Optimize One Row Plan ส่วน rule ระดับ physical ต่อ stage (`AdaptiveSparkPlanExec.scala:137-145`) คือ `CoalesceShufflePartitions`, `OptimizeShuffleWithLocalRead`, `OptimizeSkewInRebalancePartitions` และ rule ของ dynamic pruning กับ subquery

</Step>

## ทำไมถึงรวมเหลือ 1 Partition

ตัวเลข "200 กลายเป็น 1" มาจากสูตรใน `ShufflePartitionsUtil.scala:60-62`

```
target = max( min( totalBytes / minNumPartitions , advisory ), minPartitionSize )
```

ใน query ของบทหลัก shuffle รวมกันแค่ 1,152 ไบต์ (48 แถว = 16 map task คูณ 3 key หลัง partial aggregate) เครื่องนี้ `defaultParallelism` = 16 (เมื่อ `parallelismFirst` เป็น true ใช้ค่านี้เป็น `minNumPartitions`, `CoalesceShufflePartitions.scala:59-69`)

- `totalBytes / minNumPartitions` = 1152 / 16 = 72 ไบต์
- `min(72 B, advisory 64 MB)` = 72 ไบต์
- `max(72 B, minPartitionSize 1 MB)` = **1 MB**

เป้า 1 MB ใหญ่กว่าข้อมูลทั้งก้อนมาก partition ที่อยู่ติดกันจึงถูกรวมเข้าหากันจนเหลือ 1 ทดลองเปลี่ยนค่า (รัน)

| ตั้งค่า | partition ที่ได้ |
|---|---|
| ค่าเริ่มต้น | 1 |
| `spark.sql.adaptive.enabled=false` | 200 |
| `coalescePartitions.enabled=false` | 200 |
| `coalescePartitions.parallelismFirst=false` | 1 |
| advisory = 1 byte, minPartitionSize = 1 byte | 3 (มีข้อมูลแค่ 3 จาก 200 partition: key 0, 1, 2) |

ตัวเลขนี้ขึ้นกับจำนวน core และปริมาณข้อมูล บนข้อมูลจริงหลาย GB เป้าจะเป็นราว 64 MB ต่อ partition ไม่ใช่ 1 partition

</Step>

## เมื่อไหร่ที่ AQE ไม่ห่อแผน

`InsertAdaptiveSparkPlan` (`InsertAdaptiveSparkPlan.scala:44`) ห่อแผนด้วย AQE เฉพาะเมื่อข้อใดข้อหนึ่งเป็นจริง (บรรทัด 99-124)

- แผนมี `Exchange` อยู่แล้ว
- มี operator ที่ต้องการ distribution ใหม่ ซึ่งจะทำให้เกิด `Exchange`
- มี subquery
- `spark.sql.adaptive.forceApply` เป็น true (internal, ค่าเริ่มต้น false)

และข้ามเสมอเมื่อเป็น command (บรรทัด 52-58) หรือ streaming แบบ stateful (บรรทัด 62-70)

`spark.range(100).filter("id > 5")` จึงไม่มี `AdaptiveSparkPlan` ในแผนเลย (รัน)

</Step>

## ข้อควรระวังเพิ่มเติม

1. **Join strategy ที่ AQE เปลี่ยนใช้ขนาดจริงของ shuffle output** `canBroadcastBySize` (`joins.scala:367-375`) ใช้ `spark.sql.autoBroadcastJoinThreshold` หรือถ้าตั้ง `spark.sql.adaptive.autoBroadcastJoinThreshold` (ค่าเริ่มต้นไม่ตั้ง) ก็ใช้ตัวนั้นกับสถิติ runtime
2. **เมื่อฝั่งเล็กมี partition ว่างเกินไป** `DynamicJoinSelection` ใส่ `NO_BROADCAST_HASH` ให้ฝั่งนั้น (`DynamicJoinSelection.scala:30-44`) ตั้ง `nonEmptyPartitionRatioForBroadcastJoin=0` แล้ว query เดิมกลายเป็น `BroadcastHashJoin` (รัน)
3. **Skew join ต้องมี shuffled join** broadcast join ไม่มี shuffle ให้แยก threshold คือ `max(skewedPartitionThresholdInBytes, median × skewedPartitionFactor)` (`OptimizeSkewedJoin.scala:65-68`) partition ที่ skew ถูกหั่นตามช่วงของ map task และ partition อีกฝั่งถูกทำสำเนา ถ้าทั้งสองฝั่ง skew จะกลายเป็น cartesian ของชิ้นย่อย
4. **filter ที่อนุมานข้าม join ทำให้ขนาดฝั่งตรงข้ามเล็กลงโดยไม่คาดคิด** ในการทดลอง filter บน key ที่คำนวณจากฝั่งขวาทำให้ฝั่งซ้ายถูกกรองเหมือนกัน ถ้าต้องการให้ขนาดของฝั่งหนึ่ง "ไม่รู้" ให้ใช้ non-deterministic filter อย่าง `F.rand(42) < 0.000002` ซึ่งไม่ถูกอนุมานหรือ push
5. **ชื่อ scan ไม่เหมือนกันระหว่างโหมด** `Scan csv` ใน `formatted` แต่ `FileScan csv` ใน tree แบบอื่น
6. **ค่า config ที่อ่านใน Python มีหน่วยต่อท้าย** `spark.conf.get("spark.sql.adaptive.advisoryPartitionSizeInBytes")` ได้ `67108864b`
7. **สิ่งที่ยังไม่ได้ทดสอบ**: พฤติกรรม pushdown ของ Parquet/ORC (เครื่องนี้เขียน Parquet ไม่ได้ ตัวอย่างจึงใช้ CSV), การรวม partition ของ `repartition(n)` (อ่านจาก `supportedShuffleOrigins` ไม่มี `REPARTITION_BY_NUM`), และตัวเลขความเร็วของ Tungsten/codegen/AQE

</Step>
