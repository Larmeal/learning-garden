## `JoinSelection`: ลำดับการเลือก

`object JoinSelection` อยู่ที่ `SparkStrategies.scala:181` สำหรับ Equi-join ลำดับการเลือกเป็นดังนี้

เมื่อมี Hint (บรรทัด 321-329) Spark จะเลือกตามลำดับนี้

1. `BroadcastHashJoin` ถ้ามี Hint Broadcast และฝั่งนั้น Build ได้
2. `SortMergeJoin` ถ้ามี Hint Merge
3. `ShuffledHashJoin` ถ้ามี Hint shuffle_hash
4. `CartesianProduct` ถ้ามี Hint shuffle_replicate_nl
5. ไม่เข้าข้อไหน (Hint ใช้ไม่ได้) ก็ทำเหมือนไม่มี Hint

ส่วนเมื่อไม่มี Hint (`createJoinWithoutHint`, บรรทัด 305-319) ลำดับเป็นดังนี้

1. `BroadcastHashJoin` ถ้าฝั่งใดฝั่งหนึ่งเล็กพอและ Build ได้
2. `ShuffledHashJoin` ถ้าเข้าเงื่อนไข (ดูหัวข้อถัดไป)
3. `SortMergeJoin` ถ้า Key เรียงลำดับได้
4. `CartesianProduct` เฉพาะ Inner-like Join
5. สุดท้ายคือ `BroadcastNestedLoopJoin` (Build ฝั่งที่เล็กกว่า)

แต่ละวิธีมีข้อกำหนดของตัวเอง Broadcast และ Shuffle Hash ต้องการ Key ที่ `hashJoinSupported` (บรรทัด 240, `joins.scala:406`) Sort-merge ต้องการ Key ที่ `RowOrdering.isOrderable` (บรรทัด 286-293) ส่วน null-aware anti join (`NOT IN` ที่มีคอลัมน์เดียว) ทำได้แบบ Broadcast เท่านั้น (บรรทัด 331-334)

สำหรับ Join แบบไม่มีเงื่อนไข Equality (บรรทัด 336-420) ถ้ามี Hint จะได้ `BroadcastNestedLoopJoin` ถ้าไม่มี Hint และฝั่งเล็กก็ได้ BNLJ เหมือนกัน ถ้าไม่เล็กและเป็น Inner-like ก็ได้ `CartesianProduct` ส่วนที่เหลือคือ BNLJ อยู่ดี ซึ่ง Source เองเขียนไว้ว่าอาจช้ามากหรือ OOM วัดจริง: `big.k < small.k` ได้ `BroadcastNestedLoopJoin` ตอน Threshold ปกติ, `CartesianProduct` ตอน -1, และ Left Outer แบบเดียวกันที่ -1 ยังเป็น `BroadcastNestedLoopJoin` (เพราะ Cartesian ใช้ได้เฉพาะ Inner)

ฝั่งไหน Broadcast ได้ ขึ้นกับ Join Type (`joins.scala:377-390`)

| ฝั่ง | Join Type ที่ Build ได้ |
|---|---|
| ซ้าย | InnerLike, RightOuter |
| ขวา | InnerLike, LeftOuter, LeftSingle, LeftSemi, LeftAnti, ExistenceJoin |
| (ไม่มี) | FullOuter |

ลองเดินตามผังนี้ด้วยเงื่อนไขของคุณเองดูได้เลย เลือกตัวอย่างที่ติดคำว่า "วัดจริง" เพื่อดูกรณีที่ Exercise รันและตรวจแผนไว้ หรือจะปรับ Join Type, Hint และขนาดเองแล้วดูว่าเส้นทางเปลี่ยนที่ข้อไหนก็ได้

## ทำไมไม่เคยได้ Shuffled Hash Join โดยไม่ตั้งใจ

เงื่อนไขของ Shuffled Hash Join แบบไม่มี Hint (`joins.scala:318-359`, Helper 538-560) คือต้องครบทั้งหมดของข้อต่อไปนี้

- `spark.sql.join.preferSortMergeJoin` เป็น False ตัวนี้เป็น **Internal** และค่าเริ่มต้นเป็น **True**
- ฝั่งเล็กมี `sizeInBytes < autoBroadcastJoinThreshold * จำนวน shuffle partition`
- ฝั่งเล็กคูณ `spark.sql.shuffledHashJoinFactor` (3) แล้วยังไม่เกินฝั่งใหญ่
- Join Type ผ่าน `canBuildShuffledHashJoinLeft/Right`

ผลคือโดยค่าเริ่มต้น Spark จะไม่เลือก Shuffled Hash Join เอง ถ้าต้องการก็ต้องใส่ Hint `shuffle_hash` เอง วัดจริง: Threshold 100 กับ `preferSortMergeJoin=false` ได้ `ShuffledHashJoin ... BuildRight` พร้อม Exchange 2 ตัวและไม่มี Sort แต่ค่าเริ่มต้น (`preferSortMergeJoin=true`) ที่ Threshold เดียวกันได้ `SortMergeJoin` และถ้าตั้ง Threshold เป็น -1 เงื่อนไขขนาดจะเป็นลบเสมอ Shuffled Hash Join แบบไม่มี Hint จึงเป็นไปไม่ได้

</Step>

## Hint: ชื่อ ลำดับ และของที่ใช้ไม่ได้

Hint มีชื่อเรียกได้หลายแบบ (`hints.scala`)

| Hint | ชื่อที่ใช้ได้ |
|---|---|
| broadcast | `BROADCAST`, `BROADCASTJOIN`, `MAPJOIN` |
| merge | `SHUFFLE_MERGE`, `MERGE`, `MERGEJOIN` |
| shuffle hash | `SHUFFLE_HASH` |
| cartesian | `SHUFFLE_REPLICATE_NL` |

ลำดับความสำคัญเมื่อใส่หลาย Hint คือ BROADCAST > SHUFFLE_MERGE > SHUFFLE_HASH > SHUFFLE_REPLICATE_NL (Comment ที่ `hints.scala:117-123`) วัดจริง: ถ้าใส่ BROADCAST ที่ฝั่งหนึ่งและ MERGE อีกฝั่ง จะได้ `BroadcastHashJoin` และถ้าใส่ BROADCAST ทั้งสองฝั่ง Spark จะ Broadcast ฝั่งที่เล็กกว่า ใน PySpark เรียกด้วย `df.hint("broadcast")` หรือ `F.broadcast(df)` ส่วนใน SQL เขียน `/*+ BROADCAST(t) */`

ถ้าใส่ชื่อ Hint ที่ไม่รู้จัก (`hint("nonsense")`) จะ **ไม่ Error** แผนออกมาเป็นปกติ (อาจมี Log Warning ซึ่งยังไม่ได้ตรวจข้อความ)

Hint `shuffle_hash` บน Left Join ใส่ที่ฝั่งไหนก็ได้ผลเป็น `ShuffledHashJoin LeftOuter` โดย Build ฝั่งที่ใส่ Hint (วัดทั้ง BuildRight และ BuildLeft)

</Step>

## ลำดับการวางแผนของ Broadcast

ตารางที่ Broadcast จะถูกอ่านมาที่ Driver ผ่าน `BroadcastExchangeExec` (`BroadcastExchangeExec.scala:186`: `child.executeCollectIterator()`) แล้วสร้างเป็น Relation จึงส่งต่อไป Metric ที่เห็นใน SQL UI คือ Data Size, time to collect, time to build, time to broadcast (บรรทัด 129-133)

มีเพดานอยู่สองตัว คือ `spark.sql.broadcastTimeout` = 300 วินาที (`SQLConf.scala:1971`) และ `spark.sql.maxBroadcastTableSize` = 8 GiB ตั้งแต่ 4.1.0 (บรรทัด 1976)

`canBroadcastBySize` (`joins.scala:367-375`) ตรวจว่า `0 <= sizeInBytes <= threshold` ถ้าเป็นสถิติ Runtime ของ AQE จะใช้ `spark.sql.adaptive.autoBroadcastJoinThreshold` ก่อนถ้าตั้งไว้ มิฉะนั้นใช้ตัวปกติ และ `LogicalQueryStageStrategy` (บรรทัด 38-85) ป้องกันไม่ให้ Broadcast Stage ที่สร้างแล้วถูกกลับเป็น Shuffle

</Step>

## `OptimizeSkewedJoin` ละเอียด

กฎนี้อยู่ในไฟล์ `OptimizeSkewedJoin.scala` และมีรายละเอียดดังนี้

- เส้น Skew คือ `max(skewedPartitionThresholdInBytes, median × skewedPartitionFactor)` (บรรทัด 65-68) Partition ถือว่า Skew เมื่อใหญ่กว่าเส้นนี้ (บรรทัด 146, 148) โดย Median คำนวณจากขนาดผลลัพธ์ของ Map Task ต่อ Reduce Partition (บรรทัด 124-125)
- ขนาดชิ้นที่แยกคือ `max(advisoryPartitionSize, ขนาดเฉลี่ยของ partition ที่ไม่ skew)` (บรรทัด 75-83)
- ฝั่งที่แยกได้ (บรรทัด 85-92) คือฝั่งซ้ายสำหรับ Inner, Cross, LeftSemi, LeftAnti, LeftOuter และฝั่งขวาสำหรับ Inner, Cross, RightOuter ถ้าเป็น **FullOuter แยกไม่ได้ทั้งสองฝั่ง** จึงไม่มี Skew Handling
- กฎนี้ใช้กับ `SortMergeJoin` และ `ShuffledHashJoin` เท่านั้น (บรรทัด 225-240) โดย Child ทั้งสองต้องเป็น `ShuffleQueryStage` ที่มี Origin `ENSURE_REQUIREMENTS` (บรรทัด 286-293) ส่วนฝั่ง Stream ของ `BroadcastHashJoin` แยกได้เฉพาะเมื่อปิด local shuffle reader (บรรทัด 242-253)
- ถ้าการแยกจะทำให้เกิด Shuffle เพิ่ม กฎจะถูกยกเลิก เว้นแต่ `spark.sql.adaptive.forceOptimizeSkewedJoin` เป็น True (ค่าเริ่มต้น False, บรรทัด 262-283)
- ในกฎไม่มี Case ของ Aggregate จึงไม่แยก Key ที่ Skew ของ `groupBy` (อ่านจาก Match Case ของกฎ)

วัดจริง (2 ล้านแถว, 90% ที่ `k = 1`, Payload `rand()`, Threshold Broadcast -1, `shuffle.partitions=10`) ค่าเริ่มต้นไม่เกิด Skew Handling แต่พอลด Threshold และ Advisory เหลือ 1 MB ก็ได้ `SortMergeJoin(skew=true)` ฝั่งซ้าย `AQEShuffleRead coalesced and skewed` Metric ของ Node ได้ Skewed Partitions 1, Splits 16, Partitions 17 และ Join Stage รัน 17 Task จาก 10 Partition เดิม ที่ต้องใช้ `rand()` เป็น Payload ก็เพราะคอลัมน์ที่ซ้ำกันบีบอัดได้เกือบหมด ขนาดไฟล์ Shuffle จะเล็กจนไม่เกินเส้น

</Step>

## `CacheManager` ข้างใน

- `Dataset.cache()` เรียก `persist()` แล้ว `CacheManager.cacheQuery` (`Dataset.scala:1631-1640`) ซึ่งลงทะเบียน `CachedData(normalizedPlan, InMemoryRelation)` และกลับทันที (`CacheManager.scala:133-176`) ข้อมูลจะถูกสร้างเมื่อ `cachedColumnBuffers` ถูกเข้าถึงครั้งแรก (`InMemoryRelation.scala:288-293`, `buildBuffers` บรรทัด 343)
- คีย์ของ Cache คือ **Normalized Plan** (Comment ที่ `CacheManager.scala:133`) DataFrame ที่สร้างใหม่แต่แผนเหมือนกันจึงเจอ Cache
- ถ้าเรียก `persist` ซ้ำบนข้อมูลที่ Cache แล้ว Spark จะ Log ว่า "Asked to cache already cached data" และไม่เปลี่ยนระดับ (บรรทัด 147)
- ตอนสร้าง Cache ของแผนที่มี Shuffle `CacheManager.getOrCloneSessionWithConfigsOff` จะปิด `spark.sql.adaptive.applyFinalStageShuffleOptimizations` เว้นแต่ `spark.sql.optimizer.canChangeCachedPlanOutputPartitioning` เป็น True (Internal, ค่าเริ่มต้น False, `CacheManager.scala:638-648`) นี่คือเหตุผลที่ Partition ที่ Cache ไว้ยังเป็น 200 และไม่ถูกรวม
- ค่าเริ่มต้นของระดับเก็บคือ `spark.sql.defaultCacheStorageLevel` = `MEMORY_AND_DISK` (ตั้งแต่ 4.0.0, `SQLConf.scala:2312`) ส่วน `df.persist()` ใน PySpark ค่าเริ่มต้นคือ `MEMORY_AND_DISK_DESER` (`classic/dataframe.py:540-542`)

<Callout type="warn" title="ชื่อ StorageLevel ใน Scala กับ PySpark ไม่ตรงกัน">
`MEMORY_ONLY` ใน Scala เก็บแบบ Deserialized แต่ใน PySpark (`storagelevel.py:88-96`) `MEMORY_ONLY` และ `MEMORY_AND_DISK` เป็นแบบ Serialized ส่วนแบบ Deserialized ใช้ชื่อ `MEMORY_AND_DISK_DESER` ให้ดู `df.storageLevel` ว่าได้อะไรจริง ผลที่วัดคือ `Memory Serialized 1x`, `Disk Memory Serialized 1x`, `Disk Memory Deserialized 1x`, `Disk Serialized 1x` และ `Disk Memory Serialized 2x`
</Callout>

ก่อน `cache()` ที่ยังไม่เรียก `df.storageLevel` จะพิมพ์ `Serialized 1x Replicated` ซึ่งหมายถึงยังไม่ได้ Cache (NONE) พอหลัง `cache()` ทันทีและก่อน Action แรก `explain()` จะเห็น `InMemoryTableScan` แล้ว แต่ `getRDDStorageInfo` ยังว่าง ส่วน `CACHE LAZY TABLE t` ใน SQL ไม่สร้างอะไรเลย แต่ `CACHE TABLE t` สร้างทันที

</Step>

## กลไก Spill ใน Source

กลไก Spill มีสามชั้น

1. `Spillable.maybeSpill` (`Spillable.scala:86-111`) ทำงานทุก 32 Element ถ้า Memory ของ Collection ถึง Threshold มันจะขอเพิ่มจาก Pool สูงสุดเท่าตัว ถ้าได้ไม่พอก็ Spill และยัง Spill เมื่อถึง Threshold จำนวนแถวหรือขนาดที่บังคับ ใช้โดย `ExternalSorter` (`ExternalSorter.scala:102`, `maybeSpillCollection` บรรทัด 234-247)
2. `TaskMemoryManager.acquireExecutionMemory` (`TaskMemoryManager.java:159-215`) ถ้า Pool ให้ไม่ได้ จะสั่ง `spill()` กับ Consumer อื่น โดยเลือก Consumer ที่เล็กที่สุดที่มี Memory พอก่อน ถ้าไม่มีก็เลือกตัวใหญ่สุด และตัวที่ขอเองเป็นตัวสุดท้าย (`trySpillAndAcquire`, บรรทัด 249-262)
3. `UnsafeExternalSorter.spill` (`UnsafeExternalSorter.java:226-268`) ที่ SQL ใช้ใน `SortExec` และ Buffer ของ `SortMergeJoin` เพิ่มตัวนับ `memoryBytesSpilled` และ `diskBytesSpilled` (บรรทัด 265-266) ส่วน Shuffle Writer แบบ Serialized ใช้ `ShuffleExternalSorter.spill` (`ShuffleExternalSorter.java:301-313`)

Comment ใน `UnsafeExternalSorter.java:257-259` บอกว่าตัวเลข Memory ที่ Spill "ประมาณผลคูณของขนาด Page" และรวม Pointer Array จึงมากกว่า Disk ได้ ตัวนับไปแสดงที่ Stage Page (`StagePage.scala:190-198`) และ Metric `spill size` ของ `SortExec` (บรรทัด 61-63), `HashAggregateExec` (บรรทัด 71-72), `SortMergeJoinExec` (บรรทัด 50) และ `WindowExec` (บรรทัด 94)

`spark.shuffle.spill.numElementsForceSpillThreshold` และ `spark.sql.sortMergeJoinExec.buffer.spill.threshold` เป็น Internal ไม่ควรถือเป็นปุ่มปรับของผู้ใช้ ส่วนสูตรแบ่ง Memory ให้แต่ละ Task และการ Evict ข้อมูล Cache เมื่อ Memory ตึง เป็นเรื่องของ `UnifiedMemoryManager` (บทที่ Internals)

</Step>

## เลือก Shuffle Writer

`SortShuffleManager.registerShuffle` (`SortShuffleManager.scala:90-109`) เลือกตามลำดับดังนี้

1. `BypassMergeSortShuffleHandle` ถ้า `shouldBypassMergeSort` คือไม่มี Map-side Combine และ `numPartitions <= spark.shuffle.sort.bypassMergeThreshold` (200) (`SortShuffleWriter.scala:118-126`) วิธีนี้เขียนไฟล์ต่อ Partition แล้วต่อกัน ใช้ File Handle และ Buffer มากขึ้น
2. `SerializedShuffleHandle` ถ้า `canUseSerializedShuffle` (บรรทัด 227-246) คือ Serializer รองรับการย้ายข้อมูลที่ Serialize แล้ว, ไม่มี Map-side Combine และ Partition ไม่เกิน 16,777,216 ซึ่ง `UnsafeRowSerializer` ของ SQL รองรับ (`UnsafeRowSerializer.scala:48`)
3. ที่เหลือใช้ `SortShuffleWriter` ทั่วไป (ข้อมูลแบบ Deserialized, `ExternalSorter`)

ลองสลับชนิดของงานกับจำนวน Partition ดูว่า Writer เปลี่ยนที่ตัวเลขไหน และแต่ละแบบจัดแถวลงไฟล์ต่างกันอย่างไร

SQL Aggregation ทำ Partial Aggregate เป็น Operator `HashAggregate` แยกต่างหาก ไม่ได้ใช้ `mapSideCombine` ของ RDD (วัดได้ `mapSideCombine` เป็น False) Shuffle ของ SQL จึงเข้าข้อ 1 และ 2 ได้ วัดจริงจาก Handle ของ Exchange: 8 และ 200 Partition ได้ Bypass, 201 ได้ Serialized

## Data Locality (อ่านจาก Source เท่านั้น)

ระดับของ Task เรียงจากดีไปแย่ได้ดังนี้ `PROCESS_LOCAL`, `NODE_LOCAL`, `NO_PREF`, `RACK_LOCAL`, `ANY` (`TaskLocality.scala:25`) Scheduler ใช้ **Delay Scheduling** คือรอ Slot ที่ดีตามระดับที่อนุญาต แล้วค่อยยอมลดระดับเมื่อรอครบ (`TaskSetManager.getAllowedLocalityLevel` บรรทัด 621-682) เวลารออ่านจาก `spark.locality.wait.process/.node/.rack` ซึ่งแต่ละตัวใช้ `spark.locality.wait` เป็นค่าสำรอง ค่าเริ่มต้น **3 วินาที** (`getLocalityWait` บรรทัด 1339-1354) ส่วนระดับที่ไม่มีเวลารอ (NO_PREF, ANY) จะคืน 0

ลองสลับว่า Executor ไหนว่าง แล้วดูว่า Task รอนานแค่ไหนก่อนยอมลดระดับ

## `count(distinct)` ในแผน

วัดจากแผน (100,000 แถว, AQE เปิด) ได้ผลดังนี้

- `countDistinct("a")` ตัวเดียวได้ `HashAggregate(keys=[a])` → `Exchange hashpartitioning(a, 200)` → `HashAggregate` → Partial Count → `Exchange SinglePartition` → Final Count รวม Exchange สองตัว
- `countDistinct("a"), countDistinct("b")` สองตัว Catalyst จะเขียนใหม่ด้วย `Expand [[a, null, 1], [null, b, 2]]` และ Column `gid` แล้ว Aggregate บน `(a, b, gid)` จึงนับด้วย `FILTER (WHERE gid = ...)` จำนวนแถวหลัง `Expand` เท่ากับจำนวน Distinct Aggregate คูณแถวเข้า ถ้ามี `groupBy("g")` ด้วย Key ของ Shuffle ก็รวม `g` เข้าไป (`Exchange hashpartitioning(g, a, b, gid, 200)`)
- `approx_count_distinct("a")` ได้ Partial Aggregate → `Exchange SinglePartition` → Final ไม่มี Exchange ของ Key ที่ Distinct และไม่มี `Expand` (ค่า `rsd` 0.05 ปรากฏใน Plan)

เวลาของสามรูปแบบนี้ และความคลาดเคลื่อนของ `approx_count_distinct` ยังไม่ได้วัด

</Step>

## สิ่งที่ยังไม่ได้พิสูจน์

- ความเร็วที่ได้จริงจาก Salting, Skew Join, หรือ Cache กับ Pipeline ที่หนัก
- OOM เมื่อ Broadcast ตารางที่ใหญ่เกิน (มีแค่ Comment ใน Source ที่ `SparkStrategies.scala:156-158`)
- ความต่างของความเร็วระหว่าง Bypass กับ Serialized Shuffle Writer
- การแบ่ง Memory ต่อ Task และการ Evict Cache เมื่อ Memory ตึง
- Locality บน Cluster, ผลของ `spark.sql.files.maxPartitionBytes` (คอมพิวเตอร์เครื่องนี้เขียน Parquet ไม่ได้ จึงไม่มีตัวอย่างการแบ่ง Partition ตอนอ่านไฟล์)
- เหตุที่ `spark.range(n).groupBy("id")` ไม่มี Exchange (สังเกตได้ แต่ยังไม่ได้อ่าน `RangeExec.outputPartitioning`) ในตัวอย่างจึงใช้คีย์ที่คำนวณอย่าง `id % 7` เพื่อให้เห็น Exchange
- พฤติกรรมของ DataFrame Object เก่าหลัง `unpersist()` (การรันสองรอบให้ผลไม่ตรงกัน)

</Step>
