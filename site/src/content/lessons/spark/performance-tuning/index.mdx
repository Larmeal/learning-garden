## จูนคือการหาว่าเสียเวลาที่ไหน

ปัญหา Performance ส่วนใหญ่ของ Spark คือปัญหา Shuffle (บทที่ [Execution Model](/spark/execution-model/#ทำไม-shuffle-ถึงแพง)) บทนี้จึงเรียงตามคำถามที่ควรถามเมื่อ Job ช้า

1. มี `Exchange` กี่ตัวในแผน และแต่ละตัวส่งข้อมูลเท่าไร
2. หลัง Shuffle มีกี่ Partition และขนาดเท่ากันไหม
3. Join ใช้วิธีไหน และเลือกถูกไหม
4. มี Task ไหนที่ใหญ่กว่าเพื่อนมาก (Skew) หรือเขียน Disk (Spill) หรือเปล่า

มีกติกาสำคัญอยู่ข้อเดียว คือ **เปลี่ยนทีละอย่าง แล้ววัดใหม่** เครื่องมือสำหรับวัดคือ `explain()` (บทที่ [Catalyst และ AQE](/spark/catalyst-aqe/#โหมดของ-explain)) กับ Spark UI ตัวเลขทุกตัวในบทนี้รันบนคอมพิวเตอร์ 16 Core ด้วย Spark 4.2.0 ผ่านไฟล์ `exercises/07_performance_tuning.py` ส่วนเวลาที่พิมพ์ออกมาจะขึ้นกับคอมพิวเตอร์ที่ใช้ ให้ดูแนวโน้มเป็นหลัก อย่าไปยึดตัวเลข

<Callout type="note" title="บทนี้ไม่ซ้ำกับ[บทที่ 6](/spark/catalyst-aqe/)">
[บทที่ 6](/spark/catalyst-aqe/#aqe-ทำสามอย่าง) อธิบายว่า AQE ทำงานอย่างไร ส่วนบทนี้ใช้ AQE เป็นเครื่องมือ คือดูว่าปรับ Knob ไหนเพื่อให้ได้ผลอะไร และดูจากแผนอย่างไรว่าได้ผลแล้ว
</Callout>

## จำนวน Partition หลัง Shuffle

`spark.sql.shuffle.partitions` มีค่าเริ่มต้น **200** ซึ่งเป็นค่าที่เดาไว้ก่อนโดยไม่ขึ้นกับข้อมูลของคุณ ถ้าข้อมูลเล็กจะได้ Task จิ๋ว 200 ตัว ถ้าข้อมูลใหญ่จะได้ Partition ละหลาย GB

ถ้าเปิด AQE (ค่าเริ่มต้น) Spark จะรวม Partition เล็กให้ตอนรัน ผลที่วัดได้กับ `groupBy(id % 7).count()` บน 2 ล้านแถว (ดูผลของ `rdd.getNumPartitions()`)

| ตั้งค่า | Partition ที่ได้ |
|---|---|
| AQE ปิด | 200 |
| AQE เปิด (ค่าเริ่มต้น) | **1** |
| AQE เปิด แต่ `coalescePartitions.enabled=false` | 200 |
| AQE เปิด และ `df.repartition(200)` | **200** (ไม่ถูกรวม) |

แถวสุดท้ายสำคัญ เพราะ AQE รวมเฉพาะ Shuffle ที่ Spark แทรกเอง (`ENSURE_REQUIREMENTS`) กับ `repartition` ที่ระบุ Column ส่วน `repartition(n)` ที่เรากำหนดตัวเลขเองถือว่าเราตั้งใจ จึงไม่ถูกแตะ (Source: `CoalesceShufflePartitions.scala:38-40`)

การมี Partition มากเกินไปเสียเวลาจริง ๆ นะ ลองดูการวัดกับ groupBy บน 100,000 แถว (AQE ปิด, Median ของ 3 รอบ)

| `shuffle.partitions` | เวลา |
|---|---|
| 2 | ราว 0.1 วินาที |
| 200 | ราว 0.35 วินาที |
| 2000 | ราว 1.2 วินาที |

งานที่ทำกับแถวเท่ากันทุกครั้ง ต่างกันแค่จำนวน Task ที่ต้องเริ่มและเก็บผล ตัวเลขเหล่านี้เป็นของคอมพิวเตอร์ผู้เขียน ให้ดูว่าเวลาโตตามจำนวน Partition

<Callout type="tip" title="ถ้า AQE เปิดอยู่ ปรับอะไร">
ปกติเราไม่ต้องลดจำนวนเอง เพราะ AQE รวมให้ ถ้ายังได้ Partition ใหญ่เกิน (Spill, Task ช้า) ให้ปรับขึ้นด้วย `spark.sql.shuffle.partitions` หรือ `spark.sql.adaptive.coalescePartitions.initialPartitionNum` เพื่อให้ AQE มี Partition ตั้งต้นให้รวมมากขึ้น ส่วนเป้าขนาดต่อ Partition คือ `spark.sql.adaptive.advisoryPartitionSizeInBytes` (64 MB)
</Callout>

</Step>

## Spark เลือก Join อย่างไร

ลองเปลี่ยนเงื่อนไขทีละอย่าง ทุกช่องคือผลของ Join จริงที่รันแล้วอ่านจาก `explain()` ระหว่างตาราง 100 แถวกับตาราง 2 ล้านแถว

ก่อนจะดูว่า Spark เลือกอะไร ลองดูก่อนว่าสองวิธีหลักต่างกันตรงไหน จุดวงกลมคือตารางใหญ่ จุดสี่เหลี่ยมคือตารางเล็ก

<JoinFlowLab client:visible />

ทีนี้ดูว่า Spark เลือกวิธีไหนตามเงื่อนไข

<JoinPickerLab client:visible />

มีหลายกรณีที่ควรลองและสังเกต

- ค่าเริ่มต้น (ตารางเล็กอยู่ขวา, Inner) จะได้ `BroadcastHashJoin` และตารางใหญ่ไม่มี `Exchange`
- ถ้าปิด Threshold (-1) โดยไม่มี Hint จะเปลี่ยนเป็น `SortMergeJoin` ซึ่งทั้งสองฝั่งต้อง Shuffle และ Sort
- Hint `broadcast` ชนะ Threshold คือปิด Threshold แล้วก็ยัง Broadcast ได้
- `full outer` ไม่มีทาง Broadcast ได้ ต่อให้ใส่ Hint ก็ถูกข้ามเงียบ ๆ
- ถ้าตารางเล็กอยู่ซ้ายของ `left join` จะ Broadcast ไม่ได้ เพราะ Left Join ต้องเก็บแถวฝั่งซ้ายทั้งหมด จึงต้อง Build ฝั่งขวา แต่ถ้าเปลี่ยนเป็น `right join` ก็ทำได้
- `shuffle_replicate_nl` เป็น `CartesianProduct` ที่ไม่มี Shuffle เลยแต่จับคู่ทุกแถวกับทุกแถว ช้ามากกับข้อมูลใหญ่ และใช้กับ Inner Join เท่านั้น

<Callout type="warn" title="Hint ที่ใช้ไม่ได้ ไม่ Error">
Spark ข้าม Hint ที่ใช้ไม่ได้อย่างเงียบ ๆ แล้วเลือกเองตามปกติ ถ้าเราใส่ `broadcast` แล้วแผนยังเป็น `SortMergeJoin` ก็ไม่ได้แปลว่า Hint เสียเสมอไป อาจเป็นเพราะ Join Type หรือฝั่งนั้น Broadcast ไม่ได้ ดังนั้นควรตรวจด้วย `explain()` ทุกครั้ง
</Callout>

คำว่า "ขนาด" ในที่นี้คือขนาดที่ประเมิน ไม่ใช่ขนาดไฟล์ การเทียบกับ `autoBroadcastJoinThreshold` ใช้ขนาดประมาณของฝั่งนั้นของแผน หลัง Column Pruning และเป็น `<=` (วัดจริง: ตาราง 100 แถวประเมินได้ 800 ไบต์ ตั้ง Threshold เป็น 800 ยัง Broadcast ตั้งเป็น 799 ไม่ Broadcast) และถ้าตารางถูก Filter ให้เหลือ 100 แถว Spark ที่ไม่ได้เปิด Cost-based Optimizer ก็ยังประเมินว่าขนาดเท่าเดิม (`range(2,000,000).filter("id < 100")` ประเมินได้ 16,000,000 ไบต์) จึงเลือก Sort-merge ตรงนี้เองที่ AQE ช่วยได้ เพราะพอถึงเวลารันแล้วรู้ขนาดจริง ก็เปลี่ยนเป็น `BroadcastHashJoin` พร้อม `AQEShuffleRead local` ให้เอง

<Callout type="warn" title="Broadcast ไม่ฟรี">
ตารางที่ Broadcast จะถูกเก็บมาที่ Driver ก่อน แล้วสร้าง Hash Table แล้วส่งไปทุก Executor ถ้าใหญ่เกินไป Driver หรือ Executor จะเสียหน่วยความจำ และยังมีเพดานอีกด้วย คือ `spark.sql.broadcastTimeout` = 300 วินาที และ `spark.sql.maxBroadcastTableSize` = 8 GiB (ใน Spark UI แท็บ SQL ดู Data Size, time to collect, time to build, time to broadcast) ส่วนการ Broadcast ตารางที่ใหญ่เกินจะ OOM ไหม ยังไม่ได้ทดสอบที่นี่
</Callout>

</Step>

## Data Skew และ Salting

Shuffle ส่งแถวที่ Key เดียวกันไปที่ Partition เดียวกัน ถ้า Key หนึ่งมีข้อมูลเกือบทั้งหมด Task เดียวก็ต้องทำงานเกือบทั้งหมด เราวัดจริงบนข้อมูล 2 ล้านแถวที่ 90% มี `k = 1` หลัง `repartition(8, "k")`

```
partition   1      2      3      4      5      6          7      8
rows       22,936 29,112 25,328 28,713 22,726 1,821,935  22,334 26,916
```

Core ที่ว่างอยู่ช่วยอะไรไม่ได้ เพราะ Partition ที่ 6 เป็นของ Task เดียว

วิธีที่ 1 คือให้ AQE จัดการ (เฉพาะ Join) โดย `OptimizeSkewedJoin` จะแยก Partition ที่ใหญ่เกินเป็นชิ้นย่อย ที่ถือว่า Skew ต้อง "ใหญ่กว่า 256 MB **และ** ใหญ่กว่า Median 5 เท่า" ทั้งสองข้อ เพราะฉะนั้นกับข้อมูลทดลองเล็ก ๆ มันไม่ทำงานเอง (วัดจริง: ค่าเริ่มต้นไม่เกิด Skew Join ต้องลด Threshold ลง (ในแล็บของ[บทที่ 6](/spark/catalyst-aqe/#aqe-ทำสามอย่าง) ลดเหลือ 50 KB) ถึงเห็น `SortMergeJoin(skew=true)`) และกฎนี้ดูเฉพาะ Join ไม่ช่วยกรณีที่ `groupBy` Skew

วิธีที่ 2 คือ Salting ซึ่งเติม Column สุ่มเข้าไปใน Key เพื่อให้ Key ใหญ่แตกเป็นหลายกลุ่ม

<SaltingLab client:visible />

```python
salted = df.withColumn("salt", F.floor(F.rand() * 64).cast("int"))
salted.repartition(8, "k", "salt")           # partition ใหญ่สุดเหลือ 362,896 จาก 1,821,935 แถว

dim_salted = dim.crossJoin(spark.range(64).select(F.col("id").cast("int").alias("salt")))
salted.join(dim_salted, ["k", "salt"])        # ผลเท่ากับ join ปกติ: 2,000,000 แถว
```

มีข้อที่ควรจำสามข้อ ข้อแรก ให้ใช้ Salt **มากกว่า** จำนวน Partition เพราะถ้าใช้ Salt แค่ 8 ตัวกับ 8 Partition ผลที่ได้ยังกระจายไม่เท่า เนื่องจาก Hash ของคู่ `(k, salt)` ชนกันได้ (วัดแล้ว Partition หนึ่งได้ 700,214 แถว) ข้อที่สอง ราคาที่จ่ายคือฝั่งเล็กต้องถูกทำสำเนาเท่ากับจำนวน Salt และข้อที่สาม ความเร็วที่ได้จริงจาก Salting ยังไม่ได้วัดในบทนี้ ที่วัดแล้วคือการกระจายของแถว

</Step>

## `repartition` กับ `coalesce`

`repartition` กับ `coalesce` ต่างก็เปลี่ยนจำนวน Partition ของตาราง แต่ทำกันคนละแบบเลย ลองเลือกคำสั่งกับค่า n ในภาพข้างล่างนี้ แล้วดูว่าแถวต่าง ๆ ย้ายไปอยู่ Partition ไหน และ Spark ต้อง Shuffle หรือเปล่า

<RepartitionLab client:visible />

ส่วนแผนที่ Spark สร้างให้จริงของแต่ละคำสั่ง เป็นดังตารางนี้

| คำสั่ง | แผนที่ได้ | ผลต่อ Partition |
|---|---|---|
| `df.repartition(8)` | `Exchange RoundRobinPartitioning(8)` | 8 (shuffle) |
| `df.repartition(8, "id")` | `Exchange hashpartitioning(id, 8)` | 8 (shuffle) |
| `df.repartition("id")` | `Exchange hashpartitioning(id, 200)` | **200** (ใช้ `shuffle.partitions`) |
| `df.repartitionByRange(8, "id")` | `Exchange rangepartitioning(id ASC, 8)` | 8 (Shuffle, เรียงตามช่วง) |
| `df.coalesce(4)` | `Coalesce 4` ไม่มี Exchange | 4 (ไม่ Shuffle) |
| `df.coalesce(32)` บน 16 Partition | `Coalesce` | ยังเป็น 16 (Coalesce เพิ่มไม่ได้) |

`coalesce` ไม่ Shuffle จึงถูกกว่า แต่ก็มีกับดักอยู่ คือ `coalesce(1)` หลัง `withColumn(...)` ที่หนัก แผนจะเป็น `Coalesce 1` อยู่บนสุด และ `Project` ที่คำนวณอยู่ภายใต้มัน (จาก Plan: ไม่มี Exchange) ส่วน `repartition(1)` ใส่ `Exchange SinglePartition` **หลัง** การคำนวณ ดังนั้นถ้าอยากให้งานคำนวณยังขนานได้และค่อยรวมเป็นไฟล์เดียวตอนท้าย ให้ใช้ `repartition(1)` ไม่ใช่ `coalesce(1)` (ข้อนี้อ่านจากแผน ยังไม่ได้วัดจำนวน Task จริง)

</Step>

## `cache()` ช่วยเมื่อไร

`cache()` ไม่ได้ทำให้ทุกอย่างเร็วขึ้น มันแค่เก็บผลของแผนไว้ให้ใช้ซ้ำ จึงมีประโยชน์เมื่อ DataFrame เดียวถูกใช้หลาย Action และมีราคาที่ต้องจ่าย (วัดแล้ว บางงานไม่เร็วขึ้นเลย) ว่า Cache ตัด Recipe ตรงไหน ทำงานอย่างไรกับสายที่มี Shuffle และ Join และ `persist` มีระดับอะไรบ้าง อยู่ใน[หน้า Cache และ Persist](/spark/performance-tuning/cache-persist/)

</Step>

## Spill: เมื่อ Memory ไม่พอ

งานที่ต้องถือข้อมูลไว้ใน Memory เช่น Sort, `HashAggregate`, `SortMergeJoin` มี Memory ของ Task จำกัด ถ้าไม่พอ Spark จะเขียนส่วนที่ถืออยู่ลง Disk แล้วทำงานต่อ เรียกว่า **Spill**

<SpillLab client:visible />

Spill ไม่ใช่ Error Job ยังจบได้ตามปกติ เพียงแต่ช้าลง เพราะต้องเขียน Disk แล้ว Merge กลับ วัดจริง: Sort 6 ล้านแถวที่มี String บน `local[4]` และ Driver Memory 600 MB ได้ `memoryBytesSpilled` ราว 280 MiB และ `diskBytesSpilled` ราว 232 MiB (ตัวเลขขึ้นกับคอมพิวเตอร์)

แล้วเราดู Spill ได้ที่ไหนบ้าง

- Spark UI หน้า Stage จะมี **Spill (Memory)** กับ **Spill (Disk)** (แสดงเมื่อมากกว่า 0)
- แท็บ SQL จะมี Metric `spill size` ของ `Sort`, `HashAggregate`, `SortMergeJoin`
- ตัวเลข "Memory" มักมากกว่า "Disk" (ในการวัดข้างบน 280 เทียบ 232) เพราะตัวเลข Memory นับเป็นก้อนของ Page และรวม Pointer Array ตามที่ Comment ใน Source ของ `UnsafeExternalSorter` บอกไว้

ทางลด Spill เป็นเหตุผลเชิงหลักการ คือให้แต่ละ Task ถือข้อมูลน้อยลง (Partition มากขึ้น), เพิ่ม Memory ของ Executor, หรือลดข้อมูลก่อน Sort/Aggregate ส่วนสูตรแบ่ง Memory ของ Task อย่างละเอียดอยู่ในบทที่ [Internals](/spark/internals/#unified-memory-storage-กับ-execution-แบ่งกัน) (ส่วน Memory)

</Step>

## ที่ซ่อนอยู่: Shuffle Writer และค่า 200

ตัวเขียนไฟล์ Shuffle มีสามแบบ ซึ่ง Spark เลือกให้เอง

1. BypassMergeSort ใช้เมื่อไม่มี Map-side Combine และ Partition ไม่เกิน `spark.shuffle.sort.bypassMergeThreshold` (**200**) โดยเขียนไฟล์แยกต่อ Partition แล้วต่อกัน
2. Serialized (Unsafe) ใช้เมื่อไม่เข้าข้อ 1 แต่ Serializer ย้ายตำแหน่งข้อมูลที่ Serialize แล้วได้
3. Sort (ทั่วไป) ใช้กับที่เหลือ โดยใช้ `ExternalSorter`

วัดจริงจาก Handle ของ Exchange ได้ว่า `shuffle.partitions` = 8 และ 200 ได้ `BypassMergeSortShuffleHandle` ส่วน 201 ได้ `SerializedShuffleHandle` ค่าเริ่มต้น 200 จึงอยู่ที่ขอบพอดี ข้อควรรู้คือเลข 201 เปลี่ยนวิธีเขียน แต่วิธีไหนเร็วกว่าก็ขึ้นกับงาน (ยังไม่ได้วัด)

</Step>

## ข้อห้ามที่มีหลักฐาน

- ไม่ควร `collect()` กับข้อมูลใหญ่ เพราะผลทั้งหมดต้องเข้า Driver ตัวเดียว เพดาน `spark.driver.maxResultSize` (1 GB) ถ้าตั้งไว้ 1 MB แล้ว `collect()` 2 ล้านแถวจะขึ้น `Total size of serialized results ... is bigger than spark.driver.maxResultSize`
- ไม่ควรใช้ Python UDF แทน Built-in เพราะแผน `select(plus1("id"))` มี `BatchEvalPython` คั่นกลางสอง Codegen Block ส่วน `select(id + 1)` เป็น `Project` เดียวใน Codegen เดียว UDF ทำลาย Whole-stage Codegen และต้องส่งข้อมูลไป Python Process (เรื่องของ[บทที่ 8](/spark/udf/#ช้ากว่า-built-in-เท่าไร) ซึ่งวัดความเร็วอย่างเป็นระบบ)
- ไม่ควรมี Partition เล็กเป็นพัน เพราะเวลาโตตามจำนวน Task (ตารางข้างบน)
- ระวัง `countDistinct` หลายตัวใน Aggregation เดียว เพราะ Catalyst เขียนใหม่ด้วย `Expand` ที่คูณจำนวนแถวตามจำนวน Distinct Aggregate (วัดจากแผน: `countDistinct("a")` ตัวเดียวมี Exchange 2 ตัว ส่วนสองตัวมี `Expand`) ถ้ารับค่าประมาณได้ ให้ใช้ `approx_count_distinct` ซึ่งมี Exchange แค่ตัวเดียวและไม่มี `Expand` (ความคลาดเคลื่อนที่ยอมรับได้ ยังไม่ได้ทดสอบ)

</Step>
