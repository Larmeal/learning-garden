## ปัญหาของ "โฟลเดอร์ที่เต็มไปด้วย Parquet"

Data Lake แบบเดิมก็คือโฟลเดอร์ของไฟล์ Parquet ที่ Spark อ่านและเขียน ซึ่งใช้ได้ดีจนกว่าจะเจอเรื่องเหล่านี้ โดยเราทดลองให้เห็นจริงด้วย Spark 4.2.0

**1. ไม่มีใครตรวจ Schema** ถ้าเราเขียน Parquet เพิ่มด้วย DataFrame ที่มี Column เกินมา Spark จะไม่บ่นอะไร แต่ตอนอ่าน ผลจะขึ้นกับไฟล์ที่ Spark เลือกอ่าน Schema (วัดจริง: ส่วนใหญ่อ่านแล้ว Column `extra` หายไป แต่รันซ้ำบางครั้งได้ `['id', 'extra']` เพราะไฟล์ที่ถูกเลือกไม่คงที่ จึงต้องใส่ `mergeSchema` ถ้าต้องการผลที่แน่นอน)

```python
spark.range(3).write.parquet(p)
spark.range(3).withColumn("extra", F.lit(1)).write.mode("append").parquet(p)   # ไม่มี error
spark.read.parquet(p).columns                                                  # ['id'] ส่วนใหญ่ (บางครั้ง ['id', 'extra'])
spark.read.option("mergeSchema", "true").parquet(p).columns                    # ['id', 'extra']
```

**2. แก้แถวเดียวไม่ได้** ไฟล์ Parquet เป็น Immutable ถ้าอยากแก้ เราต้องเขียนไฟล์ใหม่และลบไฟล์เก่าเอง ซึ่งไม่ได้เป็นการกระทำเดียว ถ้าล่มกลางทางจะเหลือทั้งสองชุดหรือไม่เหลือเลย

**3. ผู้อ่านเห็นของที่ไม่สมบูรณ์** ระหว่างที่ Job เขียนไฟล์หลายไฟล์ ผู้อ่านอีกคนอาจเห็นไฟล์แค่บางส่วน

**4. ไม่มี History** เมื่อเขียนทับแล้ว ของเก่าจะหายไป

**Table Format** แก้ปัญหาทั้งหมดนี้ด้วยแนวคิดเดียว คือเก็บ **Log ของการเปลี่ยนแปลง** ไว้ข้างไฟล์ข้อมูล และนิยามว่า "ตารางตอนนี้" คือผลของการเล่น Log ไฟล์ Parquet ยังเป็นข้อมูลเหมือนเดิม แต่ Log จะเป็นเจ้าของคำตอบว่าไฟล์ไหนอยู่ในตาราง

<Callout type="warn" title="ตัวอย่างบทนี้รันใน WSL และต้องมีเน็ตครั้งแรก">
Hadoop เขียนไฟล์บน Windows ไม่ได้เพราะไม่มี `hadoop.dll` (ดู[บทที่ 9](/spark/structured-streaming/#streaming-คือ-dataframe-ที่ไม่มีวันจบ)) ตัวอย่างจึงรันด้วย `run_wsl.sh` และตอนรันครั้งแรกจะดาวน์โหลด Jar ของ Delta จาก Maven Central มาเก็บใน `~/.ivy2` ส่วนคอมพิวเตอร์ที่ใช้ Linux หรือ macOS ก็รันได้ตรง ๆ
</Callout>

## ผ่า Delta Table ดู

เราลองเขียนตาราง 100 แถวใน 4 ไฟล์ด้วย `write.format("delta")` จะได้โฟลเดอร์ที่มีไฟล์ Parquet 4 ไฟล์ กับโฟลเดอร์ `_delta_log/` (รัน: `exercises/10_table_formats.py`)

```
t/
  part-00000-....snappy.parquet   x4
  _delta_log/
    00000000000000000000.json
```

ไฟล์ `00000000000000000000.json` คือ Commit หมายเลข 0 โดยแต่ละบรรทัดคือหนึ่ง **Action**

| Action | ความหมาย |
|---|---|
| `commitInfo` | ใครทำอะไรเมื่อไร (เช่น WRITE, UPDATE) |
| `metaData` | schema, partition column, config |
| `protocol` | เวอร์ชัน Reader และ Writer ที่ต้องมี |
| `add` | ไฟล์นี้ **เข้า** ตาราง พร้อม Path, ขนาด และ **สถิติ** |
| `remove` | ไฟล์นี้ **ออก** จากตาราง |

`add` มีสถิติของแต่ละไฟล์ เช่น `{"numRecords":25,"minValues":{"id":0},"maxValues":{"id":24},"nullCount":{"id":0}}` ซึ่งใช้ข้ามไฟล์ตอนอ่าน (ดูหัวข้อ Performance)

**ตารางตอน Version N = ไฟล์ที่ `add` และยังไม่ถูก `remove` ในการเล่น Commit 0 ถึง N** ลองกดดูทีละ Commit นะ

<TableLogLab client:visible />

สิ่งสำคัญที่ภาพนี้บอกคือ **ไม่มีไฟล์ไหนถูกแก้ที่เดิม** `UPDATE` จะเขียนไฟล์ใหม่ที่มีค่าที่แก้แล้ว แล้ว Commit ว่า "เอาไฟล์เก่าออก ใส่ไฟล์ใหม่เข้า" ซึ่งเรียกว่า **Copy-on-write** วัดจริงแล้ว Commit 1 ของ `UPDATE` มี Action `commitInfo`, `add`, `remove` และไฟล์เก่ายังอยู่บน Disk

ลองพิสูจน์ดูว่าทำไมต้องมี Log ถ้าเราอ่านโฟลเดอร์นี้ด้วย `spark.read.parquet(path)` หลัง `UPDATE` จะได้ **125 แถว** (ไฟล์เก่า 100 แถวบวกไฟล์ที่เขียนใหม่ 25 แถว) แต่ถ้าอ่านผ่าน Delta จะได้ **100 แถว** ซึ่งถูกต้อง เพราะ Delta อ่านเฉพาะไฟล์ที่ Log บอก

</Step>

## ACID ได้อย่างไรกับไฟล์ธรรมดา

ตัวย่อ ACID ทั้งสี่ตัว Log ให้เราได้ดังนี้

- **Atomicity** การเปลี่ยนแปลงทั้งชุด (หลาย `add` และ `remove`) อยู่ใน Commit File เดียว และ Commit จะมีผลเมื่อไฟล์ `N.json` ถูกสร้างสำเร็จ ถ้าล่มก่อนหน้านั้นก็จะไม่มี Version ใหม่ ไฟล์ Parquet ที่เขียนไว้ก็เป็นแค่ไฟล์เด็กกำพร้าที่ผู้อ่านมองไม่เห็น
- **Isolation** ผู้อ่านเลือก Version หนึ่งแล้วเล่น Log ถึง Version นั้น จึงเห็นเป็นภาพนิ่ง และไม่เห็นผลของ Writer ที่ยังไม่เสร็จ
- **Consistency** จะตรวจ Schema ก่อน Commit (ดูหัวข้อ Schema)
- **Durability** Log และไฟล์ถูกเก็บอยู่ใน Storage ที่ทนทาน (ถ้า Object Store รับประกันการสร้างไฟล์แบบ Atomic)

เมื่อมี Writer สองคนพร้อมกัน Delta ใช้ **Optimistic Concurrency** คือต่างคนต่างอ่าน Version ปัจจุบัน ทำงาน แล้วพยายามสร้างไฟล์ Version ถัดไป คนที่สร้างได้ก่อนจะชนะ ส่วนคนที่ช้ากว่าต้องตรวจว่างานของตัวเองชนกับที่อีกคน Commit ไปหรือไม่ ถ้าชนก็ล้มเหลว

เราทดลองจริงด้วยสอง Thread ที่ `UPDATE` คนละแถวแต่อยู่ในไฟล์เดียวกัน (ไฟล์เดียว 3 ล้านแถว) พร้อมกัน

```
{'A': 'ok', 'B': 'ConcurrentAppendException'}     # ผลที่ได้
log มี 2 version: 0 (เขียนตาราง) กับ 1 (งานของ A)
แถวที่ถูกแก้: 1                                    # ตรงกับ A เท่านั้น
```

B ได้ `[DELTA_CONCURRENT_APPEND] Transaction conflict detected` เพราะไฟล์ที่ B อ่านถูก A เปลี่ยนไปแล้ว นี่คือเหตุที่ Log เป็น "ต้นฉบับของความจริง" เพราะจะไม่มีการเขียนทับกันเงียบ ๆ และผู้ใช้ต้องลองใหม่ (Retry) เอง การทดลองนี้ขึ้นกับจังหวะเวลา สคริปต์จึงลองได้สูงสุด 3 รอบ แล้วยืนยันว่าอย่างน้อยหนึ่งรอบเกิดการชน

</Step>

## Time Travel และราคาที่ต้องจ่าย

เพราะแต่ละ Version คือชุดไฟล์ที่ Log บอก การย้อนดู Version เก่าจึงทำได้ตราบที่ไฟล์เก่ายังอยู่

```python
spark.read.format("delta").option("versionAsOf", 0).load(p)
spark.sql("DESCRIBE HISTORY delta.`/path`")      # (3, MERGE) (2, DELETE) (1, UPDATE) (0, WRITE)
```

วัดจริงแล้ว จำนวนแถวที่ Version 0 ถึง 3 คือ 100, 100, 90, 90 และ `id = 5` ที่ Version 0 มี `g = 0` ส่วนปัจจุบันเป็น `g = 7`

แต่ไฟล์ที่ถูก `remove` ไม่ได้หายไปเอง ถ้าปล่อยไว้ก็จะกินที่ไปเรื่อย ๆ จึงมี `VACUUM` ที่ลบไฟล์ที่ Log ไม่อ้างถึงและเก่ากว่า Retention (ค่าเริ่มต้น 7 วัน) และเมื่อ Vacuum แล้ว Version เก่าที่ต้องใช้ไฟล์เหล่านั้นจะ **อ่านไม่ได้อีก** วัดจริงแล้วเมื่อตั้ง `RETAIN 0 HOURS` (ต้องปิด `retentionDurationCheck` ซึ่งปกติกันไม่ให้ทำ) จำนวนไฟล์บน Disk จาก 11 เหลือ 1 และ `versionAsOf = 0` ได้ `FILE_NOT_EXIST` ดังนั้นจึงเป็นการแลกกันระหว่างว่าจะเก็บ History นานเท่าไหร่ กับพื้นที่ที่เสียไป

</Step>

## Schema: ตรวจก่อนเขียน

ผลที่วัดจริงบนตารางที่มี `g` เป็น Bigint มีดังนี้

| เขียนอะไรเพิ่ม | ผลลัพธ์ |
|---|---|
| `g` เป็น String | `AnalysisException: [DELTA_FAILED_TO_MERGE_FIELDS]` |
| มี Column `extra` เพิ่ม | `AnalysisException: [DELTA_METADATA_MISMATCH]` |
| มี Column `extra` และ `option("mergeSchema", "true")` | สำเร็จ Schema กลายเป็น `id, g, extra` |

เมื่อเทียบกับ Parquet เปล่า ๆ ที่ยอมรับทุกอย่างเงียบ ๆ การเปลี่ยน Schema ในตารางเป็นการตัดสินใจที่เราต้องบอกให้ชัด (`mergeSchema`) และจะถูกบันทึกใน `metaData` ของ Commit ถัดไป

</Step>

## Performance: Log ให้ของแถม

ข้อมูลที่เก็บใน Log ยังช่วยให้อ่านเร็วขึ้นด้วย

- **Data Skipping** สถิติ `min` และ `max` ใน `add` ทำให้ข้ามไฟล์ที่ไม่มีทางมีแถวที่ต้องการได้ วัดจริงแล้ว ตาราง 4 ไฟล์ (id 0 ถึง 99) ที่ `where("id > 95")` อ่านแค่ **1 ไฟล์**
- **`OPTIMIZE`** รวมไฟล์เล็กเป็นไฟล์ใหญ่ วัดจริงแล้ว ตารางที่ผ่าน `UPDATE`, `DELETE`, `MERGE` มี 7 ไฟล์ หลัง `OPTIMIZE` เหลือ 1 (ไฟล์เก่ายังอยู่จนกว่าจะ `VACUUM`)
- **Checkpoint** ถ้าต้องเล่น Log ตั้งแต่ Commit 0 ทุกครั้ง ตารางที่มีล้าน Commit จะอ่านช้า Delta จึงเขียน Checkpoint (ไฟล์ Parquet ที่สรุปสถานะ) ทุก 10 Commit วัดจริงแล้ว หลัง 12 Commit มี `00000000000000000010.checkpoint.parquet` และ `_last_checkpoint` ผู้อ่านจะเริ่มจาก Checkpoint ล่าสุดแล้วเล่นเฉพาะส่วนที่ตามมา

</Step>

## Delta, Iceberg และ Hudi

ทั้งสามใช้แนวคิดเดียวกัน (Log + ไฟล์ข้อมูล + Protocol) ต่างกันที่การจัดโครงสร้าง Metadata ส่วนนี้ **ไม่ได้รันบนคอมพิวเตอร์เครื่องนี้** สรุปมาจากเอกสารของแต่ละโปรเจกต์ จึงเป็นเพียงภาพรวมและไม่ใช่ผลทดสอบ

| | Delta Lake | Apache Iceberg | Apache Hudi |
|---|---|---|---|
| ที่เก็บความจริง | Log JSON ต่อ Commit + Checkpoint Parquet | ไฟล์ Metadata JSON ชี้ Manifest List → Manifest → ไฟล์ข้อมูล | Timeline ของ Instant (`.hoodie/`) |
| การอัปเดต | Copy-on-write (ตามที่วัด) และ Deletion Vectors | Copy-on-write หรือ Merge-on-read ด้วย Delete File | Copy-on-write หรือ Merge-on-read (Base File + Log File) |
| จุดเด่นที่เอกสารเน้น | ผสมกับ Spark ลึก, `MERGE`, Streaming | Hidden Partitioning, ใช้กับหลาย Engine | Upsert เร็ว, Incremental Query |

**Merge-on-read** เป็นทางเลือกแทน Copy-on-write โดยแทนที่จะเขียนไฟล์ทั้งไฟล์ใหม่ทุกครั้งที่แก้ไม่กี่แถว ก็เขียนไฟล์เล็กที่บอกว่าแถวไหนถูกลบหรือเปลี่ยน แล้วค่อยรวมกันตอนอ่าน ทำให้เขียนได้เร็วขึ้น แต่ต้องไปจ่ายตอนอ่านและต้องมี Compaction

<Callout type="note" title="ผลที่พบจริงเรื่อง Version: Jar ต้องตรงกับ Spark">
ตอนเตรียมบทนี้ เราลองใช้ Iceberg Runtime ที่ Build สำหรับ Spark 4.1 (`iceberg-spark-runtime-4.1_2.13:1.12.0`) บน Spark 4.2.0 แล้ว `CREATE TABLE` ล้มด้วย `IncompatibleClassChangeError: class org.apache.iceberg.spark.source.SparkView can not implement org.apache.spark.sql.connector.catalog.View, because it is not an interface` ซึ่งใน Source ของ Spark 4.2 `View` เป็น Class (`View.java:43`) ไม่ใช่ Interface แล้ว และ Maven Central ไม่มี Runtime ของ Iceberg สำหรับ Spark 4.2 ณ วันที่ตรวจ (5 พ.ย. 2026) ในทางกลับกัน `delta-spark_2.13:4.4.1` อ้างอิง Spark 4.2.0 และใช้ได้ บทเรียนที่ได้คือ Table Format ผูกกับ Minor Version ของ Spark เสมอ จึงควรตรวจตารางความเข้ากันได้ก่อนอัปเกรด Spark
</Callout>

</Step>

## Spark เชื่อมกับ Table Format อย่างไร

Spark ไม่ได้รู้จัก Delta โดยตรง แต่ใช้ **Hook สองจุด** ที่ Spark เปิดไว้ให้ (วัดจริงว่าตั้ง Config เหล่านี้ใน Session)

```python
SparkSession.builder
  .config("spark.jars.packages", "io.delta:delta-spark_2.13:4.4.1")
  .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
  .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
```

1. **Extensions** (`SparkSessionExtensions`) เป็นปลั๊กอินที่แทรกเข้า Parser (รู้จักคำสั่งเช่น `OPTIMIZE`, `VACUUM`, `DESCRIBE HISTORY`), Analyzer และ Optimizer
2. **Catalog และ DataSource V2** ใน `org.apache.spark.sql.connector.*` เป็นชุด Interface ที่ Table Format ต้อง Implement

| Interface (ใน Spark 4.2) | หน้าที่ |
|---|---|
| `TableCatalog` | สร้าง โหลด ลบตาราง |
| `Table` และ `TableCapability` | ตาราง และสิ่งที่ทำได้ (`BATCH_READ`, `BATCH_WRITE`, `TRUNCATE`, `OVERWRITE_BY_FILTER`, `MICRO_BATCH_READ` ฯลฯ) |
| `SupportsRead`, `Scan`, `SupportsPushDownFilters`, `SupportsPushDownRequiredColumns` | อ่านข้อมูล และรับ Filter กับ Column ที่ Pushdown |
| `SupportsWrite`, `WriteBuilder`, `BatchWrite` | เขียนข้อมูลแบบ Commit ได้ทั้งก้อน |
| `SupportsRowLevelOperations`, `RowLevelOperation` | `DELETE`, `UPDATE`, `MERGE` โดย Source บอก Spark ว่าจัดการเป็นกลุ่มไฟล์ (Copy-on-write) หรือเป็น Delta ของแถว |

Spark เขียนแผนและ Optimize เหมือนเดิม ([บทที่ 6](/spark/catalyst-aqe/)) แต่เมื่อถึงขั้น "อ่านตารางนี้" หรือ "Commit การเขียนนี้" Spark ก็จะเรียก Interface เหล่านี้ ตัวอย่างเช่น `RowLevelOperation.Command` มีสามค่าคือ `DELETE`, `UPDATE`, `MERGE` ซึ่งเป็นสิ่งที่ Spark ส่งให้ตารางทำ (ผู้เขียนอ่านเฉพาะ Interface ของ Spark และไม่ได้อ่านโค้ดของ Delta จึงไม่ระบุว่า Delta ใช้ Interface ส่วนไหนบ้าง)

</Step>

## เลือกอะไร

ข้อนี้เป็นความเห็นของผู้เขียนเองนะ ไม่ใช่ผลทดสอบ

- ถ้าเราอยู่กับ Spark และ Databricks เป็นหลัก Delta เป็นทางที่ผสมลึกที่สุดและหาตัวอย่างง่ายที่สุด
- ถ้าต้องใช้ตารางเดียวกันกับหลาย Engine (Trino, Flink, Spark ฯลฯ) Iceberg ออกแบบมาเพื่อเรื่องนี้
- ถ้างานหลักคือ Upsert และ Streaming Ingestion ต่อเนื่อง Hudi เน้นด้านนี้

ก่อนเลือก ควรตรวจสามอย่างเสมอ คือ (1) มี Release ที่ตรงกับ Spark ของคุณไหน (ดูกรอบสีเหลืองข้างบน) (2) Engine อื่นที่ต้องอ่านตารางเดียวกันรองรับฟีเจอร์ที่คุณใช้ไหม (3) Storage ที่ใช้รับประกันการสร้างไฟล์แบบ Atomic หรือไม่ เพราะ Commit ของทั้งสามพึ่งสิ่งนี้

## ลองทำและเช็กตัวเอง

```bash
cd subjects/spark/code
uv run python exercises/10_table_formats.py
```

ครั้งแรกจะใช้เวลาดาวน์โหลด Jar ของ Delta จากนั้นใช้เวลาราว 2 ถึง 3 นาที แล้วลองดัดแปลงดูตามนี้ได้เลย

1. สร้างตาราง Delta แล้วเปิดไฟล์ใน `_delta_log/` ด้วยตา ดู `add` และ `remove` ของแต่ละ Commit
2. `UPDATE` หนึ่งแถวแล้วนับไฟล์ Parquet ในโฟลเดอร์ก่อนและหลัง
3. เขียน DataFrame ที่ Schema ต่างกันเข้าตารางและอ่าน Error ที่ได้

ลองเช็กตัวเองด้วยคำถามเหล่านี้

- ทำไมอ่านโฟลเดอร์ Delta ด้วย `spark.read.parquet` ถึงได้จำนวนแถวผิด
- สอง Writer แก้ไฟล์เดียวกันพร้อมกัน ผลเป็นอย่างไร และทำไมไม่มีข้อมูลเสียหาย
- `VACUUM` แลกอะไรกับอะไร
- ทำไมการอัปเกรด Spark อาจทำให้ Jar ของ Iceberg ใช้ไม่ได้

</Step>
