## ปัญหาของ "โฟลเดอร์ที่เต็มไปด้วย Parquet"

data lake แบบเดิมคือโฟลเดอร์ของไฟล์ Parquet ที่ Spark อ่านและเขียน ใช้ได้ดีจนกว่าจะเจอเรื่องเหล่านี้ ซึ่งทดลองให้เห็นจริงด้วย Spark 4.2.0

**1. ไม่มีใครตรวจ schema** เขียน Parquet เพิ่มด้วย DataFrame ที่มี column เกินมา Spark ไม่บ่น แต่ตอนอ่าน ผลขึ้นกับไฟล์ที่ Spark เลือกอ่าน schema (วัดจริง: ส่วนใหญ่อ่านแล้ว column `extra` หายไป แต่รันซ้ำบางครั้งได้ `['id', 'extra']` เพราะไฟล์ที่ถูกเลือกไม่คงที่ จึงต้องใส่ `mergeSchema` ถ้าต้องการผลที่แน่นอน)

```python
spark.range(3).write.parquet(p)
spark.range(3).withColumn("extra", F.lit(1)).write.mode("append").parquet(p)   # ไม่มี error
spark.read.parquet(p).columns                                                  # ['id'] ส่วนใหญ่ (บางครั้ง ['id', 'extra'])
spark.read.option("mergeSchema", "true").parquet(p).columns                    # ['id', 'extra']
```

**2. แก้แถวเดียวไม่ได้** ไฟล์ Parquet เป็น immutable ถ้าอยากแก้ต้องเขียนไฟล์ใหม่และลบไฟล์เก่าเอง ซึ่งไม่ใช่การกระทำเดียว: ถ้าล่มกลางทางจะเหลือทั้งสองชุดหรือไม่เหลือเลย

**3. ผู้อ่านเห็นของที่ไม่สมบูรณ์** ระหว่างที่ job เขียนไฟล์หลายไฟล์ ผู้อ่านอีกคนอาจเห็นไฟล์บางส่วน

**4. ไม่มี history** เขียนทับแล้วของเก่าหาย

**table format** แก้ทั้งหมดนี้ด้วยแนวคิดเดียว: เก็บ **log ของการเปลี่ยนแปลง** ไว้ข้างไฟล์ข้อมูล และนิยามว่า "ตารางตอนนี้" คือผลของการเล่น log ไฟล์ Parquet ยังเป็นข้อมูลเหมือนเดิม แต่ log เป็นเจ้าของคำตอบว่าไฟล์ไหนอยู่ในตาราง

<Callout type="warn" title="ตัวอย่างบทนี้รันใน WSL และต้องมีเน็ตครั้งแรก">
Hadoop เขียนไฟล์บน Windows ไม่ได้เพราะไม่มี `hadoop.dll` (ดู[บทที่ 9](/spark/structured-streaming/#streaming-คือ-dataframe-ที่ไม่มีวันจบ)) ตัวอย่างจึงรันด้วย `run_wsl.sh` และดาวน์โหลด jar ของ Delta จาก Maven Central มาเก็บใน `~/.ivy2` เมื่อรันครั้งแรก เครื่อง Linux หรือ macOS รันได้ตรงๆ
</Callout>

## ผ่า Delta Table ดู

เขียนตาราง 100 แถวใน 4 ไฟล์ด้วย `write.format("delta")` โฟลเดอร์ที่ได้มีไฟล์ Parquet 4 ไฟล์กับโฟลเดอร์ `_delta_log/` (รัน: `exercises/10_table_formats.py`)

```
t/
  part-00000-....snappy.parquet   x4
  _delta_log/
    00000000000000000000.json
```

ไฟล์ `00000000000000000000.json` คือ commit หมายเลข 0 บรรทัดละหนึ่ง **action**

| action | ความหมาย |
|---|---|
| `commitInfo` | ใครทำอะไรเมื่อไร (เช่น WRITE, UPDATE) |
| `metaData` | schema, partition column, config |
| `protocol` | เวอร์ชัน reader และ writer ที่ต้องมี |
| `add` | ไฟล์นี้ **เข้า** ตาราง: path, ขนาด และ **สถิติ** |
| `remove` | ไฟล์นี้ **ออก** จากตาราง |

`add` มีสถิติของแต่ละไฟล์ เช่น `{"numRecords":25,"minValues":{"id":0},"maxValues":{"id":24},"nullCount":{"id":0}}` ซึ่งใช้ข้ามไฟล์ตอนอ่าน (ดูหัวข้อ Performance)

**ตารางตอน version N = ไฟล์ที่ `add` และยังไม่ถูก `remove` ในการเล่น commit 0 ถึง N** ลองกดทีละ commit

<TableLogLab client:visible />

ข้อสำคัญที่ภาพบอก: **ไม่มีไฟล์ไหนถูกแก้ที่เดิม** `UPDATE` เขียนไฟล์ใหม่ที่มีค่าที่แก้แล้ว แล้ว commit ว่า "เอาไฟล์เก่าออก ใส่ไฟล์ใหม่เข้า" แบบนี้เรียกว่า **copy-on-write** วัดจริง: commit 1 ของ `UPDATE` มี action `commitInfo`, `add`, `remove` และไฟล์เก่ายังอยู่บน disk

พิสูจน์ว่าทำไมต้องมี log: ถ้าอ่านโฟลเดอร์นี้ด้วย `spark.read.parquet(path)` หลัง `UPDATE` จะได้ **125 แถว** (ไฟล์เก่า 100 แถวบวกไฟล์ที่เขียนใหม่ 25 แถว) แต่อ่านผ่าน Delta ได้ **100 แถว** ถูกต้อง เพราะ Delta อ่านเฉพาะไฟล์ที่ log บอก

</Step>

## ACID ได้อย่างไรกับไฟล์ธรรมดา

ตัวย่อ ACID แปลเป็นสิ่งที่ log ให้ได้ดังนี้

- **Atomicity**: การเปลี่ยนแปลงทั้งชุด (หลาย `add` และ `remove`) อยู่ใน commit file เดียว commit มีผลเมื่อไฟล์ `N.json` ถูกสร้างสำเร็จ ถ้าล่มก่อนนั้น ไม่มี version ใหม่ ไฟล์ Parquet ที่เขียนไว้เป็นแค่ไฟล์เด็กกำพร้า ผู้อ่านไม่เห็น
- **Isolation**: ผู้อ่านเลือก version หนึ่งแล้วเล่น log ถึง version นั้น เห็นภาพนิ่ง ไม่เห็นผลของ writer ที่ยังไม่เสร็จ
- **Consistency**: ตรวจ schema ก่อน commit (ดูหัวข้อ Schema)
- **Durability**: log และไฟล์อยู่ใน storage ที่ทนทาน (ถ้า object store รับประกันการสร้างไฟล์แบบ atomic)

เมื่อมี writer สองคนพร้อมกัน Delta ใช้ **optimistic concurrency**: ต่างคนต่างอ่าน version ปัจจุบัน ทำงาน แล้วพยายามสร้างไฟล์ version ถัดไป คนที่สร้างได้ก่อนชนะ คนที่ช้ากว่าต้องตรวจว่างานของตัวเองชนกับที่อีกคน commit ไปหรือไม่ ถ้าชนก็ล้มเหลว

ทดลองจริงด้วยสอง thread ที่ `UPDATE` คนละแถวแต่อยู่ในไฟล์เดียวกัน (ไฟล์เดียว 3 ล้านแถว) พร้อมกัน

```
{'A': 'ok', 'B': 'ConcurrentAppendException'}     # ผลที่ได้
log มี 2 version: 0 (เขียนตาราง) กับ 1 (งานของ A)
แถวที่ถูกแก้: 1                                    # ตรงกับ A เท่านั้น
```

B ได้ `[DELTA_CONCURRENT_APPEND] Transaction conflict detected` เพราะไฟล์ที่ B อ่านถูก A เปลี่ยนไปแล้ว นี่คือเหตุที่ log เป็น "ต้นฉบับของความจริง": ผลคือไม่มีการเขียนทับกันเงียบๆ ผู้ใช้ต้องลองใหม่ (retry) เอง การทดลองนี้ขึ้นกับจังหวะเวลา สคริปต์จึงลองได้สูงสุด 3 รอบแล้วยืนยันว่าอย่างน้อยหนึ่งรอบเกิดการชน

</Step>

## Time Travel และราคาที่ต้องจ่าย

เพราะแต่ละ version คือชุดไฟล์ที่ log บอก การย้อนดู version เก่าจึงทำได้ตราบที่ไฟล์เก่ายังอยู่

```python
spark.read.format("delta").option("versionAsOf", 0).load(p)
spark.sql("DESCRIBE HISTORY delta.`/path`")      # (3, MERGE) (2, DELETE) (1, UPDATE) (0, WRITE)
```

วัดจริง: จำนวนแถวที่ version 0 ถึง 3 คือ 100, 100, 90, 90 และ `id = 5` ที่ version 0 มี `g = 0` ส่วนปัจจุบันเป็น `g = 7`

แต่ไฟล์ที่ถูก `remove` ไม่หายไปเอง ใช้ที่เรื่อยๆ จึงมี `VACUUM` ลบไฟล์ที่ log ไม่อ้างถึงและเก่ากว่า retention (ค่าเริ่มต้น 7 วัน) เมื่อ vacuum แล้ว version เก่าที่ต้องใช้ไฟล์เหล่านั้น **อ่านไม่ได้อีก** วัดจริง: ตั้ง `RETAIN 0 HOURS` (ต้องปิด `retentionDurationCheck` ซึ่งปกติกันไม่ให้ทำ) จำนวนไฟล์บน disk จาก 11 เหลือ 1 และ `versionAsOf = 0` ได้ `FILE_NOT_EXIST` ตัวเลือกจึงเป็นการแลกกัน: เก็บ history นานเท่าไหร่ ต่อพื้นที่ที่เสียไป

</Step>

## Schema: ตรวจก่อนเขียน

วัดจริงบนตารางที่มี `g` เป็น bigint

| เขียนอะไรเพิ่ม | ผลลัพธ์ |
|---|---|
| `g` เป็น string | `AnalysisException: [DELTA_FAILED_TO_MERGE_FIELDS]` |
| มี column `extra` เพิ่ม | `AnalysisException: [DELTA_METADATA_MISMATCH]` |
| มี column `extra` และ `option("mergeSchema", "true")` | สำเร็จ schema กลายเป็น `id, g, extra` |

เทียบกับ Parquet เปล่าๆ ที่ยอมรับทุกอย่างเงียบๆ การเปลี่ยน schema ในตารางเป็นการตัดสินใจที่ต้องบอกชัด (`mergeSchema`) และถูกบันทึกใน `metaData` ของ commit ถัดไป

</Step>

## Performance: Log ให้ของแถม

ข้อมูลที่เก็บใน log ช่วยอ่านเร็วขึ้น

- **Data skipping**: สถิติ `min` และ `max` ใน `add` ทำให้ข้ามไฟล์ที่ไม่มีทางมีแถวที่ต้องการ วัดจริง: ตาราง 4 ไฟล์ (id 0 ถึง 99) ที่ `where("id > 95")` อ่านแค่ **1 ไฟล์**
- **`OPTIMIZE`** รวมไฟล์เล็กเป็นไฟล์ใหญ่ วัดจริง: ตารางที่ผ่าน `UPDATE`, `DELETE`, `MERGE` มี 7 ไฟล์ หลัง `OPTIMIZE` เหลือ 1 (ไฟล์เก่ายังอยู่จนกว่าจะ `VACUUM`)
- **Checkpoint**: ถ้าต้องเล่น log ตั้งแต่ commit 0 ทุกครั้ง ตารางที่มีล้าน commit จะอ่านช้า Delta จึงเขียน checkpoint (ไฟล์ Parquet ที่สรุปสถานะ) ทุก 10 commit วัดจริง: หลัง 12 commit มี `00000000000000000010.checkpoint.parquet` และ `_last_checkpoint` ผู้อ่านเริ่มจาก checkpoint ล่าสุดแล้วเล่นเฉพาะส่วนที่ตามมา

</Step>

## Delta, Iceberg และ Hudi

ทั้งสามเป็นแนวคิดเดียวกัน (log + ไฟล์ข้อมูล + protocol) ต่างที่การจัดโครงสร้าง metadata ส่วนนี้ **ไม่ได้รันบนเครื่องนี้** สรุปจากเอกสารของแต่ละโปรเจกต์ จึงเป็นภาพรวม ไม่ใช่ผลทดสอบ

| | Delta Lake | Apache Iceberg | Apache Hudi |
|---|---|---|---|
| ที่เก็บความจริง | log JSON ต่อ commit + checkpoint Parquet | ไฟล์ metadata JSON ชี้ manifest list → manifest → ไฟล์ข้อมูล | timeline ของ instant (`.hoodie/`) |
| การอัปเดต | copy-on-write (ตามที่วัด) และ deletion vectors | copy-on-write หรือ merge-on-read ด้วย delete file | copy-on-write หรือ merge-on-read (base file + log file) |
| จุดเด่นที่เอกสารเน้น | ผสมกับ Spark ลึก, `MERGE`, streaming | hidden partitioning, ใช้กับหลาย engine | upsert เร็ว, incremental query |

**merge-on-read** คือทางเลือกแทน copy-on-write: แทนที่จะเขียนไฟล์ทั้งไฟล์ใหม่ทุกครั้งที่แก้ไม่กี่แถว ก็เขียนไฟล์เล็กที่บอกว่าแถวไหนถูกลบหรือเปลี่ยน แล้วรวมตอนอ่าน ได้เขียนเร็วขึ้น ต้องจ่ายตอนอ่านและต้องมี compaction

<Callout type="note" title="ผลที่พบจริงเรื่อง version: jar ต้องตรงกับ Spark">
ตอนเตรียมบทนี้ ลองใช้ Iceberg runtime ที่ build สำหรับ Spark 4.1 (`iceberg-spark-runtime-4.1_2.13:1.12.0`) บน Spark 4.2.0 แล้ว `CREATE TABLE` ล้มด้วย `IncompatibleClassChangeError: class org.apache.iceberg.spark.source.SparkView can not implement org.apache.spark.sql.connector.catalog.View, because it is not an interface` ใน source ของ Spark 4.2 `View` เป็น class (`View.java:43`) ไม่ใช่ interface แล้ว และ Maven Central ไม่มี runtime ของ Iceberg สำหรับ Spark 4.2 ณ วันที่ตรวจ (5 พ.ย. 2026) ในทางกลับกัน `delta-spark_2.13:4.4.1` อ้างอิง Spark 4.2.0 และใช้ได้ บทเรียน: table format ผูกกับ minor version ของ Spark เสมอ ตรวจตารางความเข้ากันได้ก่อนอัปเกรด Spark
</Callout>

## Spark เชื่อมกับ Table Format อย่างไร

Spark ไม่รู้จัก Delta โดยตรง ใช้ **hook สองจุด** ที่ Spark เปิดไว้ (วัดจริงว่าตั้ง config เหล่านี้ใน session)

```python
SparkSession.builder
  .config("spark.jars.packages", "io.delta:delta-spark_2.13:4.4.1")
  .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
  .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
```

1. **Extensions** (`SparkSessionExtensions`): ปลั๊กอินที่แทรกเข้า parser (รู้จักคำสั่งเช่น `OPTIMIZE`, `VACUUM`, `DESCRIBE HISTORY`), analyzer และ optimizer
2. **Catalog และ DataSource V2** ใน `org.apache.spark.sql.connector.*` เป็นชุด interface ที่ table format ต้อง implement

| interface (ใน Spark 4.2) | หน้าที่ |
|---|---|
| `TableCatalog` | สร้าง โหลด ลบตาราง |
| `Table` และ `TableCapability` | ตาราง และสิ่งที่ทำได้ (`BATCH_READ`, `BATCH_WRITE`, `TRUNCATE`, `OVERWRITE_BY_FILTER`, `MICRO_BATCH_READ` ฯลฯ) |
| `SupportsRead`, `Scan`, `SupportsPushDownFilters`, `SupportsPushDownRequiredColumns` | อ่านข้อมูล และรับ filter กับ column ที่ pushdown |
| `SupportsWrite`, `WriteBuilder`, `BatchWrite` | เขียนข้อมูลแบบ commit ได้ทั้งก้อน |
| `SupportsRowLevelOperations`, `RowLevelOperation` | `DELETE`, `UPDATE`, `MERGE` โดย source บอก Spark ว่าจัดการเป็นกลุ่มไฟล์ (copy-on-write) หรือเป็น delta ของแถว |

Spark เขียนแผนและ optimize เหมือนเดิม ([บทที่ 6](/spark/catalyst-aqe/)) แต่เมื่อถึงขั้น "อ่านตารางนี้" หรือ "commit การเขียนนี้" ก็เรียก interface เหล่านี้ ตัวอย่างเช่น `RowLevelOperation.Command` มีสามค่าคือ `DELETE`, `UPDATE`, `MERGE` ซึ่งเป็นสิ่งที่ Spark ส่งให้ตารางทำ (ผู้เขียนอ่านเฉพาะ interface ของ Spark ไม่ได้อ่านโค้ดของ Delta จึงไม่ระบุว่า Delta ใช้ interface ส่วนไหนบ้าง)

</Step>

## เลือกอะไร

ข้อนี้เป็นความเห็นของผู้เขียน ไม่ใช่ผลทดสอบ

- **ถ้าอยู่กับ Spark และ Databricks เป็นหลัก** Delta เป็นทางที่ผสมลึกที่สุดและหาตัวอย่างง่ายที่สุด
- **ถ้าต้องใช้ตารางเดียวกันกับหลาย engine** (Trino, Flink, Spark ฯลฯ) Iceberg ออกแบบมาเพื่อเรื่องนี้
- **ถ้างานหลักคือ upsert และ streaming ingestion ต่อเนื่อง** Hudi เน้นด้านนี้

ก่อนเลือก ตรวจสามอย่างเสมอ: (1) มี release ที่ตรงกับ Spark ของคุณไหน (ดูกรอบสีเหลืองข้างบน) (2) engine อื่นที่ต้องอ่านตารางเดียวกันรองรับฟีเจอร์ที่คุณใช้ไหม (3) storage ที่ใช้รับประกันการสร้างไฟล์แบบ atomic หรือไม่ เพราะ commit ของทั้งสามพึ่งสิ่งนี้

</Step>
