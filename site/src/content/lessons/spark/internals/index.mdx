## RDD และ Lineage

DataFrame ที่คุณเขียน ถูกแปลงเป็นแผนของ operator (บทที่ 6) แล้วสุดท้ายรันเป็น **RDD** เสมอ RDD (`RDD.scala`) คือคอลเลกชัน immutable ที่แบ่งเป็น partition และนิยามด้วยห้าอย่าง

| อย่าง | ความหมาย |
|---|---|
| partitions | รายการ partition |
| `compute` | ฟังก์ชันคำนวณ partition หนึ่งก้อน |
| dependencies | RDD พ่อที่มันอ่าน |
| partitioner (ไม่บังคับ) | วิธีแบ่ง key ไป partition |
| preferred locations (ไม่บังคับ) | เครื่องที่ข้อมูลอยู่ ใช้เลือกว่าจะรัน task ที่ไหน |

transformation (`map`, `filter`, `union`) แค่สร้าง RDD ใหม่ที่จำว่ามาจากใคร ไม่รันอะไร (ตรงกับ lazy ในบทที่ 2) action (`collect`, `count`) เรียก `sc.runJob` ถึงเริ่มทำงาน

dependency มีสองแบบที่กำหนดทุกอย่างของ stage

- **NarrowDependency**: partition ลูกอ่าน partition พ่อไม่กี่ตัวที่รู้ล่วงหน้า ไม่ต้องย้ายข้อมูล จึง pipeline อยู่ในงานเดียวกันได้
- **ShuffleDependency** (`Dependency.scala`): ต้องการผลจาก partition พ่อ **ทุกตัว** นี่คือขอบเขตของ stage ตอนสร้างมันขอ `shuffleId` จาก SparkContext และลงทะเบียน handle กับ `ShuffleManager`

ดู lineage ได้ด้วย `toDebugString()` (รัน: `exercises/13_internals.py`)

```python
base = sc.parallelize(range(100), 4)
narrow  = base.map(...).filter(...).map(...)
reduced = base.map(lambda x: (x % 5, 1)).reduceByKey(lambda a, b: a + b)

narrow.toDebugString()    # ไม่มี ShuffledRDD
reduced.toDebugString()   # มี ShuffledRDD  <- ShuffleDependency อยู่ตรงนี้
narrow.partitioner        # None
reduced.partitioner       # มีค่า (reduceByKey กำหนด partitioner)
```

ข้อควรจำ: `Pipeline` ของ narrow transformation หลายตัวรวมเป็นก้อนเดียว ใน PySpark การ `map` กับ `filter` ต่อกันกลายเป็น `PythonRDD` เดียวที่รันฟังก์ชันต่อกันในรอบเดียว ส่วน `reduceByKey` เริ่ม shuffle

## DAGScheduler: ตัด Job เป็น Stage

เมื่อเรียก action `DAGScheduler` (ที่ driver, `DAGScheduler.scala:124`) สร้าง stage โดยไล่ย้อนจาก RDD สุดท้ายตาม dependency

- RDD สุดท้ายอยู่ใน **`ResultStage`** (stage สุดท้ายของ job) ซึ่งถือฟังก์ชันที่ต้องรันกับแต่ละ partition
- ถ้าเจอ narrow dependency ก็รวม RDD พ่อเข้า stage เดียวกัน
- ถ้าเจอ shuffle dependency สร้าง **`ShuffleMapStage`** ให้ฝั่งพ่อ stage นี้จบด้วยการเขียนไฟล์ shuffle แล้วทำซ้ำ
- ส่ง stage ได้เมื่อ stage พ่อที่ต้องการทุกตัวมี output ครบ ห่อ partition ที่ขาดเป็น `TaskSet` ส่งให้ TaskScheduler

ลองดูงานที่มี shuffle สองครั้ง (`reduceByKey` สองครั้งต่อกัน)

<SchedulerLab client:visible />

ผลที่วัดจริงจาก `statusTracker` (task ต่อ stage)

| งาน | stage (task) |
|---|---|
| `map().filter().map()` แล้ว `collect` | 1 stage (4) |
| `reduceByKey` แล้ว `collect` | 2 stage (4, 4) |
| `reduceByKey` สองครั้งต่อกัน | **3 stage (4, 4, 4)** |
| `pairs.join(other)` ของ RDD ใน PySpark | 2 stage (6, 6) |

แถวสุดท้ายน่าสนใจ: join ของสอง RDD น่าจะมี 3 stage (สองฝั่งพ่อกับหนึ่ง result) แต่ PySpark implement `join` ด้วยการ union สองฝั่ง (4 + 2 = 6 partition) แล้ว shuffle ครั้งเดียว จึงได้ 2 stage ข้อสรุปคือจำนวน stage มาจาก dependency ของ RDD ที่ถูกสร้างจริง ไม่ใช่จากชื่อของคำสั่ง

**เมื่อ executor หาย** ไฟล์ shuffle ที่อยู่บน disk ของมันหายไปด้วย task ฝั่ง reduce ที่พยายามอ่านจะได้ `FetchFailedException` DAGScheduler ตอบสนองโดยส่ง stage พ่อที่ขาด output ใหม่ (stage attempt ถัดไป) แล้วกลับมารัน stage ที่ล้ม โดยไม่เริ่ม job ทั้งก้อนใหม่ (อ่านจาก source ไม่ได้บังคับให้เกิดในการทดลองนี้)

</Step>

## TaskScheduler และ Executor

DAGScheduler ตัดสินใจว่า "รันอะไร" ส่วน **TaskSchedulerImpl** ตัดสินว่า "ให้ใครรัน"

- `submitTasks` สร้าง **`TaskSetManager`** หนึ่งตัวต่อ TaskSet แล้วเรียกให้ backend เสนอ resource
- `resourceOffers` เรียงลำดับ TaskSetManager ผ่าน **`Pool`** ที่ใช้ FIFO หรือ FAIR (ตาม `spark.scheduler.mode`) แล้วแจก task ตามระดับ locality (ดูบทที่ 7)
- `TaskSetManager` เก็บประวัติของแต่ละ task: ถ้า task ล้มจะลองใหม่จนถึง `maxTaskFailures` แล้ว **ยกเลิกทั้ง TaskSet** และเมื่อ task สำเร็จหมดมันกลายเป็น zombie

ฝั่ง executor (`Executor.scala`): ใช้ thread pool ที่ launch **`TaskRunner`** หนึ่งตัวต่อ task ลำดับของ `TaskRunner.run`

1. สร้าง `TaskMemoryManager` ของ task นี้ (ที่แบ่ง memory ให้ operator ใน task)
2. ดาวน์โหลด dependency (jar/ไฟล์) ถ้าขาด
3. deserialize `Task` ที่ driver ส่งมา แล้วรัน
4. serialize ผล บันทึก metrics แล้วส่งสถานะกลับ driver

และมี `Heartbeater` ส่งสัญญาณกลับ driver เป็นระยะ ทำให้ driver รู้ว่า executor ยังอยู่ และรวบรวม metric ของ task ที่กำลังรันมาแสดงใน Spark UI (บทที่ 11)

</Step>

## ไฟล์ Shuffle บน Disk

shuffle ไม่ใช่การส่งข้อมูลผ่านเครือข่ายตรงๆ แต่ผ่านไฟล์ ฝั่ง map เขียนไฟล์แล้วฝั่ง reduce ไปอ่าน (ข้อมูลเขียนด้วย writer ที่เลือกตามบทที่ 7) วัดจริงบน `groupBy` ที่มี 8 map task (ตั้ง `spark.local.dir` ให้ชี้โฟลเดอร์ที่ตรวจได้)

```
blockmgr-<uuid>/<hash>/shuffle_0_0_0.data
                       shuffle_0_0_0.index
                       shuffle_0_0_0.checksum.ADLER32
                       shuffle_0_1_0.data ...
```

รวม **24 ไฟล์ = 8 map task x 3 ชนิด** ชื่อ `shuffle_<shuffleId>_<mapId>_0`

- **`.data`**: ข้อมูลของ **ทุก reduce partition** จาก map task นั้น ต่อเรียงกันในไฟล์เดียว (`IndexShuffleBlockResolver`: ข้อมูลของทุก reduce block ของ map task หนึ่งอยู่ในไฟล์ `.data` ไฟล์เดียว)
- **`.index`**: offset ที่บอกว่า reduce partition ไหนเริ่มและจบตรงไหนของ `.data`
- **`.checksum.ADLER32`**: ค่า checksum ไว้ตรวจว่าไฟล์เสียหรือเปล่า

ทำไมไฟล์เดียวต่อ map task แทนที่จะเป็นไฟล์ต่อ reduce partition: ถ้ามี M map และ R reduce จะได้ M x R ไฟล์ซึ่งมากเกินไป ไฟล์เดียวบวก index ลดเหลือ M

ฝั่ง reduce: `MapOutputTracker` ที่ driver รู้ว่า map output แต่ละตัวอยู่ที่ executor ไหน reduce task ถามตำแหน่งแล้วใช้ `ShuffleBlockFetcherIterator` ดึงบล็อก มันแบ่งบล็อกเป็นกลุ่ม local และ remote ส่งคำขอ remote ได้ไม่เกิน `maxBytesInFlight`, `maxReqsInFlight` และ `maxBlocksInFlightPerAddress` เพื่อไม่ให้ท่วมเครือข่ายหรือ memory ถ้าบล็อกเสียหรือหายจะเกิด `FetchFailedException` ที่กล่าวไปข้างบน

</Step>

## Unified Memory: Storage กับ Execution แบ่งกัน

executor (หรือ driver ใน local mode) แบ่ง heap ตามสูตรที่วัดและยืนยันตรงตัว (heap 600 MiB)

```
unified = (heap - 300 MiB reserved) x spark.memory.fraction (0.6)
        = (629,145,600 - 314,572,800) x 0.6 = 188,743,680 B = 180 MiB
storage region = unified x spark.memory.storageFraction (0.5) = 90 MiB
```

ที่เหลือ 120 MiB เป็น user memory สำหรับ object ฝั่ง JVM ที่ไม่อยู่ใต้การจัดการของ Spark (เช่น โครงสร้างข้อมูลภายในของ library) ลองดูว่า storage กับ execution ยืมกันอย่างไร

<MemoryLab client:visible />

กฎของ `UnifiedMemoryManager` (บรรทัด 58 เป็นต้นไป) สรุปได้สามข้อ

1. มี **เส้นแบ่งนุ่ม**: storage ยืม execution ที่ว่างได้ และ execution ยืม storage ที่ว่างได้
2. **execution เอาคืนได้** โดย evict block ของ storage ที่ใช้เกินพื้นที่ของตัวเอง (`MemoryStore` ใช้ LRU และไม่ evict block ของ RDD เดียวกับที่กำลังเข้ามา)
3. **storage เอาคืนจาก execution ไม่ได้** เพราะ task กำลังใช้ memory นั้นอยู่ ผลคือถ้า execution ถือเกือบหมดการ cache ใหม่อาจใส่ไม่ได้

ผลวัด (`MEMORY_ONLY`): cache ข้อมูล 4 block ได้ storage ใช้ **153.9 MiB เกินเส้น 90 MiB** แล้วรัน sort 6 ล้านแถวที่ต้องการ memory ของ execution พบ storage ลดเหลือ **77.0 MiB** และ cache เหลือ 2 จาก 4 partition นี่คือเหตุผลที่ `MEMORY_ONLY` ไม่รับประกันว่า cache อยู่ครบ

**ระดับ task**: `TaskMemoryManager` (`TaskMemoryManager.java`) ดูแล memory แบบ Tungsten ของ task หนึ่ง มี page table 8192 ช่อง และเข้ารหัสเลข page กับ offset เป็นเลข 64 บิตตัวเดียว เพื่อให้ pointer ของ record ใช้ได้เหมือนกันทั้ง on-heap และ off-heap เมื่อ pool ให้ memory ไม่พอ มันสั่ง consumer (sorter, hash map) ให้ **spill** ตามที่เรียนในบทที่ 7

</Step>

## Whole-Stage Codegen: Java ที่ Spark เขียนให้

บทที่ 6 บอกว่า `*(1)` คือ operator ที่ถูกรวมใน codegen ลองดูโค้ดที่ได้จริงจาก `explain("codegen")` ของ `range(1000).filter("id % 3 = 0").selectExpr("id * 2")` (ตัดเหลือส่วนสำคัญ)

```java
final class GeneratedIteratorForCodegenStage1 extends BufferedRowIterator {
  protected void processNext() throws java.io.IOException {
    ...
    while (true) {
      ...                                       // ขอช่วงตัวเลขของ Range ทีละ 1000
      for (int range_localIdx_0 = 0; range_localIdx_0 < range_localEnd_0; range_localIdx_0++) {
        long range_value_0 = ((long)range_localIdx_0 * 1L) + range_nextIndex_0;

        // --- Filter: id % 3 = 0 ---
        filter_value_1 = (long)(range_value_0 % 3L);
        filter_value_0 = filter_value_1 == 0L;
        if (filter_isNull_0 || !filter_value_0) continue;

        // --- Project: id * 2 ---
        project_value_0 = MathUtils.multiplyExact(range_value_0, 2L, ...);
        range_mutableStateArray_0[2].write(0, project_value_0);
        append((range_mutableStateArray_0[2].getRow()));
        ...
      }
    }
  }
}
```

สังเกตสามอย่าง

1. **ทั้ง `Range`, `Filter`, `Project` อยู่ใน loop เดียว** ตัวแปร `range_value_0` ส่งต่อให้ filter และ project ตรงๆ ไม่มีการสร้าง object ต่อแถวและไม่มีการเรียก `next()` ของ iterator ทีละ operator เหมือนโหมดตีความ (volcano)
2. `MathUtils.multiplyExact` ปรากฏเพราะ ANSI mode เปิด (บทที่ 6) การคูณที่ล้นจึง error แทนที่จะวนค่า
3. แถวผลลัพธ์ถูกเขียนเป็น `UnsafeRow` ผ่าน `UnsafeRowWriter` (ไบต์ดิบ ไม่ใช่ object)

โครงที่เกี่ยวข้อง (จาก source)

| ส่วน | หน้าที่ |
|---|---|
| `CollapseCodegenStages` (`WholeStageCodegenExec.scala:914`) | rule ใน `preparations` เลือก operator ที่ codegen ได้ ครอบ operator ที่ทำไม่ได้ด้วย `InputAdapter` และใส่ `WholeStageCodegenExec` พร้อมหมายเลข stage |
| `WholeStageCodegenExec` (บรรทัด 643) | รวม subtree เป็นคลาส Java หนึ่งคลาส compile ด้วย Janino แล้วรัน **ถ้า compile ล้มจะถอยไปรันแบบตีความ (interpreted)** |
| `CodeGenerator` | ตัวสร้างโค้ดและ cache ของคลาสที่ compile แล้ว มีขีดจำกัดของ JVM เช่น method ที่ยาวเกิน 8000 ไบต์ bytecode จะไม่ถูก JIT ง่าย จึงมีการแบ่ง method |

`Exchange` ไม่เคยอยู่ใน codegen: ใน plan ของ `groupBy` มี `*(1)` ที่ฝั่งก่อน shuffle และ `*(2)` ที่ฝั่งหลัง โดย `Exchange` ที่คั่นกลางไม่มี `*` เพราะเป็นขอบเขตของ stage (ตรวจจริง) ปิด `spark.sql.codegen.wholeStage` แล้ว `*(n)` หายไปจากทุก operator

**เร็วขึ้นเท่าไร**: วัดบนเครื่องผู้เขียน `range(30 ล้านแถว).filter(...).agg(sum)` ใช้เวลาราว 0.09 วินาทีเมื่อเปิด whole-stage codegen และ 0.23 วินาทีเมื่อปิด (เร็วขึ้นราว 2.5 เท่า) เป็นตัวอย่างเล็กที่ CPU ทำงานล้วนๆ งานจริงที่มี I/O หรือ shuffle จะเห็นส่วนต่างน้อยกว่านี้ ตัวเลขนี้ขึ้นกับเครื่องและงาน จึงไม่ใช่ตัวคูณที่ใช้ทั่วไปได้

<Callout type="note" title="ไม่ใช่ทุกอย่างอยู่ใน codegen">
operator ที่ไม่ codegen (เช่น `Exchange`) และ expression ที่ implement ด้วยการตีความ (CodegenFallback) ตัดสาย codegen ออกเป็นสองก้อน Python UDF ก็ตัดด้วยเหตุผลต่างกัน (ต้องส่งข้อมูลไปนอก JVM ดูบทที่ 8) ใน plan คุณเห็นเลข `*(n)` ต่างกันคือขอบเขตเหล่านี้
</Callout>

</Step>

## ลองทำและเช็กตัวเอง

```bash
cd subjects/spark/code
uv run python exercises/13_internals.py
```

ใช้เวลาราว 1 ถึง 2 นาที (ส่วน memory เปิด JVM แยกที่มี heap 600 MiB) ลองดัดแปลง

1. เปลี่ยนจำนวน partition ของข้อมูลต้นทางแล้วนับไฟล์ shuffle (ต้องเท่ากับจำนวน map task x 3)
2. เปลี่ยน `spark.driver.memory` เป็นค่าอื่นแล้วตรวจสูตร unified memory กับ `SparkEnv.get.memoryManager.maxHeapMemory`
3. เปิด `explain("codegen")` ของ query ที่มี `groupBy` แล้วหาว่ามีกี่คลาสที่ generate

เช็กตัวเอง

- ทำไม `reduceByKey` สองครั้งต่อกันถึงได้ 3 stage ไม่ใช่ 2
- ไฟล์ `.index` มีไว้ทำอะไร และทำไมต้องไฟล์ `.data` ไฟล์เดียวต่อ map task
- ทำไม storage ยืม execution ได้ แต่ execution ถึงเอาคืนได้ฝ่ายเดียว
- ในโค้ด codegen ทำไมถึงไม่มี object ต่อแถว

</Step>
