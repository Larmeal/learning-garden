## RDD และ Lineage

DataFrame ที่เราเขียนจะถูกแปลงเป็นแผนของ Operator ([บทที่ 6](/spark/catalyst-aqe/#query-ผ่านห้าขั้น)) แล้วสุดท้ายก็รันเป็น **RDD** เสมอ RDD (`RDD.scala`) คือคอลเลกชัน Immutable ที่แบ่งเป็น Partition และนิยามด้วยห้าอย่าง

| อย่าง | ความหมาย |
|---|---|
| Partitions | รายการ Partition |
| `compute` | ฟังก์ชันคำนวณ Partition หนึ่งก้อน |
| Dependencies | RDD พ่อที่มันอ่าน |
| Partitioner (ไม่บังคับ) | วิธีแบ่ง Key ไป Partition |
| Preferred Locations (ไม่บังคับ) | คอมพิวเตอร์ที่ข้อมูลอยู่ ใช้เลือกว่าจะรัน Task ที่ไหน |

Transformation (`map`, `filter`, `union`) แค่สร้าง RDD ใหม่ที่จำว่ามาจากใคร ไม่ได้รันอะไร (ตรงกับ Lazy ใน[บทที่ 2](/spark/lazy-evaluation/#สองประเภทของคำสั่ง)) จนกว่า Action (`collect`, `count`) จะเรียก `sc.runJob` งานถึงเริ่มทำจริง

Dependency มีสองแบบ ซึ่งกำหนดทุกอย่างของ Stage

- NarrowDependency คือแบบที่ Partition ลูกอ่าน Partition พ่อไม่กี่ตัวที่รู้ล่วงหน้า ไม่ต้องย้ายข้อมูล จึง Pipeline อยู่ในงานเดียวกันได้
- ShuffleDependency (`Dependency.scala`) คือแบบที่ต้องการผลจาก Partition พ่อ **ทุกตัว** นี่คือขอบเขตของ Stage ตอนสร้าง มันจะขอ `shuffleId` จาก SparkContext และลงทะเบียน Handle กับ `ShuffleManager`

เราดู Lineage ได้ด้วย `toDebugString()` (รัน: `exercises/13_internals.py`)

```python
base = sc.parallelize(range(100), 4)
narrow  = base.map(...).filter(...).map(...)
reduced = base.map(lambda x: (x % 5, 1)).reduceByKey(lambda a, b: a + b)

narrow.toDebugString()    # ไม่มี ShuffledRDD
reduced.toDebugString()   # มี ShuffledRDD  <- ShuffleDependency อยู่ตรงนี้
narrow.partitioner        # None
reduced.partitioner       # มีค่า (reduceByKey กำหนด partitioner)
```

ข้อที่ควรจำคือ `Pipeline` ของ Narrow Transformation หลายตัวจะรวมเป็นก้อนเดียว ใน PySpark การ `map` กับ `filter` ต่อกันจะกลายเป็น `PythonRDD` เดียวที่รันฟังก์ชันต่อกันในรอบเดียว ส่วน `reduceByKey` จะเริ่ม Shuffle

</Step>

## DAGScheduler: ตัด Job เป็น Stage

เมื่อเราเรียก Action `DAGScheduler` (ที่ Driver, `DAGScheduler.scala:124`) จะสร้าง Stage โดยไล่ย้อนจาก RDD สุดท้ายตาม Dependency

- RDD สุดท้ายอยู่ใน **`ResultStage`** (Stage สุดท้ายของ Job) ซึ่งถือฟังก์ชันที่ต้องรันกับแต่ละ Partition
- ถ้าเจอ Narrow Dependency ก็รวม RDD พ่อเข้า Stage เดียวกัน
- ถ้าเจอ Shuffle Dependency ก็สร้าง **`ShuffleMapStage`** ให้ฝั่งพ่อ Stage นี้จะจบด้วยการเขียนไฟล์ Shuffle แล้วทำซ้ำแบบเดิม
- จะส่ง Stage ได้ก็ต่อเมื่อ Stage พ่อที่ต้องการทุกตัวมี Output ครบ จากนั้นห่อ Partition ที่ขาดเป็น `TaskSet` ส่งให้ TaskScheduler

ลองดูงานที่มี Shuffle สองครั้ง (`reduceByKey` สองครั้งต่อกัน)

<SchedulerLab client:visible />

ผลที่วัดจริงจาก `statusTracker` (Task ต่อ Stage) เป็นดังนี้

| งาน | Stage (Task) |
|---|---|
| `map().filter().map()` แล้ว `collect` | 1 Stage (4) |
| `reduceByKey` แล้ว `collect` | 2 Stage (4, 4) |
| `reduceByKey` สองครั้งต่อกัน | **3 Stage (4, 4, 4)** |
| `pairs.join(other)` ของ RDD ใน PySpark | 2 Stage (6, 6) |

แถวสุดท้ายน่าสนใจตรงที่ Join ของสอง RDD น่าจะมี 3 Stage (สองฝั่งพ่อกับหนึ่ง Result) แต่ PySpark Implement `join` ด้วยการ Union สองฝั่ง (4 + 2 = 6 Partition) แล้ว Shuffle ครั้งเดียว จึงได้ 2 Stage ข้อสรุปคือจำนวน Stage มาจาก Dependency ของ RDD ที่ถูกสร้างจริง ไม่ได้มาจากชื่อของคำสั่ง

ถ้า **Executor หาย** ไฟล์ Shuffle ที่อยู่บน Disk ของมันจะหายไปด้วย Task ฝั่ง Reduce ที่พยายามอ่านจะได้ `FetchFailedException` DAGScheduler จะตอบสนองโดยส่ง Stage พ่อที่ขาด Output ใหม่ (Stage Attempt ถัดไป) แล้วกลับมารัน Stage ที่ล้ม โดยไม่ต้องเริ่ม Job ทั้งก้อนใหม่ (ส่วนนี้อ่านจาก Source ไม่ได้บังคับให้เกิดในการทดลองนี้)

</Step>

## TaskScheduler และ Executor

DAGScheduler ตัดสินใจว่า "รันอะไร" ส่วน **TaskSchedulerImpl** ตัดสินว่า "ให้ใครรัน"

- `submitTasks` สร้าง **`TaskSetManager`** หนึ่งตัวต่อ TaskSet แล้วเรียกให้ Backend เสนอ Resource
- `resourceOffers` เรียงลำดับ TaskSetManager ผ่าน **`Pool`** ที่ใช้ FIFO หรือ FAIR (ตาม `spark.scheduler.mode`) แล้วแจก Task ตามระดับ Locality (ดู[บทที่ 7](/spark/performance-tuning/))
- `TaskSetManager` เก็บประวัติของแต่ละ Task ถ้า Task ล้มก็จะลองใหม่จนถึง `maxTaskFailures` แล้ว **ยกเลิกทั้ง TaskSet** และเมื่อ Task สำเร็จหมด มันก็กลายเป็น Zombie

ฝั่ง Executor (`Executor.scala`) ใช้ Thread Pool ที่ Launch **`TaskRunner`** หนึ่งตัวต่อ Task โดย `TaskRunner.run` ทำตามลำดับนี้

1. สร้าง `TaskMemoryManager` ของ Task นี้ (ที่แบ่ง Memory ให้ Operator ใน Task)
2. ดาวน์โหลด Dependency (Jar/ไฟล์) ถ้าขาด
3. Deserialize `Task` ที่ Driver ส่งมา แล้วรัน
4. Serialize ผล บันทึก Metrics แล้วส่งสถานะกลับ Driver

นอกจากนี้ยังมี `Heartbeater` ที่ส่งสัญญาณกลับ Driver เป็นระยะ ทำให้ Driver รู้ว่า Executor ยังอยู่ และรวบรวม Metric ของ Task ที่กำลังรันมาแสดงใน Spark UI ได้ ([บทที่ 11](/spark/deployment-spark-ui/#ทักษะที่สำคัญที่สุดคืออ่าน-spark-ui))

</Step>

## ไฟล์ Shuffle บน Disk

Shuffle ไม่ได้ส่งข้อมูลผ่านเครือข่ายตรง ๆ แต่ส่งผ่านไฟล์ คือฝั่ง Map เขียนไฟล์แล้วฝั่ง Reduce ไปอ่าน (ข้อมูลเขียนด้วย Writer ที่เลือกตาม[บทที่ 7](/spark/performance-tuning/#ที่ซ่อนอยู่-shuffle-writer-และค่า-200)) เราวัดจริงบน `groupBy` ที่มี 8 Map Task (ตั้ง `spark.local.dir` ให้ชี้โฟลเดอร์ที่ตรวจได้)

```
blockmgr-<uuid>/<hash>/shuffle_0_0_0.data
                       shuffle_0_0_0.index
                       shuffle_0_0_0.checksum.ADLER32
                       shuffle_0_1_0.data ...
```

รวมได้ **24 ไฟล์ = 8 map task x 3 ชนิด** โดยชื่อเป็นแบบ `shuffle_<shuffleId>_<mapId>_0`

- ไฟล์ `.data` เก็บข้อมูลของ **ทุก Reduce Partition** จาก Map Task นั้น ต่อเรียงกันในไฟล์เดียว (`IndexShuffleBlockResolver`: ข้อมูลของทุก Reduce Block ของ Map Task หนึ่งอยู่ในไฟล์ `.data` ไฟล์เดียว)
- ไฟล์ `.index` เก็บ Offset ที่บอกว่า Reduce Partition ไหนเริ่มและจบตรงไหนของ `.data`
- ไฟล์ `.checksum.ADLER32` เก็บค่า Checksum ไว้ตรวจว่าไฟล์เสียหายหรือเปล่า

แล้วทำไมถึงใช้ไฟล์เดียวต่อ Map Task แทนที่จะเป็นไฟล์ต่อ Reduce Partition ล่ะ ก็เพราะถ้ามี M Map และ R Reduce จะได้ M x R ไฟล์ ซึ่งมากเกินไป การใช้ไฟล์เดียวบวก Index จึงลดเหลือ M

ส่วนฝั่ง Reduce นั้น `MapOutputTracker` ที่ Driver รู้ว่า Map Output แต่ละตัวอยู่ที่ Executor ไหน Reduce Task จะถามตำแหน่งแล้วใช้ `ShuffleBlockFetcherIterator` ดึงบล็อกมา โดยมันแบ่งบล็อกเป็นกลุ่ม Local และ Remote และส่งคำขอ Remote ได้ไม่เกิน `maxBytesInFlight`, `maxReqsInFlight` และ `maxBlocksInFlightPerAddress` เพื่อไม่ให้ท่วมเครือข่ายหรือ Memory ถ้าบล็อกเสียหรือหายก็จะเกิด `FetchFailedException` ที่กล่าวไปข้างบน

</Step>

## Unified Memory: Storage กับ Execution แบ่งกัน

Executor (หรือ Driver ใน Local Mode) แบ่ง Heap ตามสูตรที่วัดและยืนยันตรงตัว (Heap 600 MiB)

```
unified = (heap - 300 MiB reserved) x spark.memory.fraction (0.6)
        = (629,145,600 - 314,572,800) x 0.6 = 188,743,680 B = 180 MiB
storage region = unified x spark.memory.storageFraction (0.5) = 90 MiB
```

ที่เหลืออีก 120 MiB เป็น User Memory สำหรับ Object ฝั่ง JVM ที่ไม่อยู่ใต้การจัดการของ Spark (เช่น โครงสร้างข้อมูลภายในของ Library) ทีนี้ลองดูว่า Storage กับ Execution ยืมกันอย่างไร

<MemoryLab client:visible />

กฎของ `UnifiedMemoryManager` (บรรทัด 58 เป็นต้นไป) สรุปได้สามข้อ

1. มีเส้นแบ่งนุ่ม คือ Storage ยืม Execution ที่ว่างได้ และ Execution ก็ยืม Storage ที่ว่างได้
2. Execution เอาคืนได้ โดย Evict Block ของ Storage ที่ใช้เกินพื้นที่ของตัวเอง (`MemoryStore` ใช้ LRU และไม่ Evict Block ของ RDD เดียวกับที่กำลังเข้ามา)
3. Storage เอาคืนจาก Execution ไม่ได้ เพราะ Task กำลังใช้ Memory นั้นอยู่ ผลคือถ้า Execution ถือเกือบหมด การ Cache ใหม่อาจใส่ไม่ได้

ผลที่วัดได้ (`MEMORY_ONLY`) คือเมื่อ Cache ข้อมูล 4 Block จะได้ Storage ใช้ **153.9 MiB เกินเส้น 90 MiB** แล้วพอรัน Sort 6 ล้านแถวที่ต้องการ Memory ของ Execution พบว่า Storage ลดเหลือ **77.0 MiB** และ Cache เหลือ 2 จาก 4 Partition นี่คือเหตุผลที่ `MEMORY_ONLY` ไม่รับประกันว่า Cache จะอยู่ครบ

ในระดับ Task นั้น `TaskMemoryManager` (`TaskMemoryManager.java`) ดูแล Memory แบบ Tungsten ของ Task หนึ่ง มี Page Table 8192 ช่อง และเข้ารหัสเลข Page กับ Offset เป็นเลข 64 บิตตัวเดียว เพื่อให้ Pointer ของ Record ใช้ได้เหมือนกันทั้ง On-heap และ Off-heap เมื่อ Pool ให้ Memory ไม่พอ มันจะสั่ง Consumer (Sorter, Hash Map) ให้ **Spill** ตามที่เรียนใน[บทที่ 7](/spark/performance-tuning/#spill-เมื่อ-memory-ไม่พอ)

</Step>

## Whole-Stage Codegen: Java ที่ Spark เขียนให้

[บทที่ 6](/spark/catalyst-aqe/#tungsten-แบบย่อ) บอกว่า `*(1)` คือ Operator ที่ถูกรวมใน Codegen ทีนี้ลองดูโค้ดที่ได้จริงจาก `explain("codegen")` ของ `range(1000).filter("id % 3 = 0").selectExpr("id * 2")` (ตัดเหลือส่วนสำคัญ)

```java
final class GeneratedIteratorForCodegenStage1 extends BufferedRowIterator {
  protected void processNext() throws java.io.IOException {
    ...
    while (true) {
      ...                                       // ขอช่วงตัวเลขของ Range ทีละ 1000
      for (int range_localIdx_0 = 0; range_localIdx_0 < range_localEnd_0; range_localIdx_0++) {
        long range_value_0 = ((long)range_localIdx_0 * 1L) + range_nextIndex_0;

        // --- Filter: id % 3 = 0 ---
        filter_value_1 = (long)(range_value_0 % 3L);
        filter_value_0 = filter_value_1 == 0L;
        if (filter_isNull_0 || !filter_value_0) continue;

        // --- Project: id * 2 ---
        project_value_0 = MathUtils.multiplyExact(range_value_0, 2L, ...);
        range_mutableStateArray_0[2].write(0, project_value_0);
        append((range_mutableStateArray_0[2].getRow()));
        ...
      }
    }
  }
}
```

มีสามอย่างที่น่าสังเกต

1. ทั้ง `Range`, `Filter`, `Project` อยู่ใน Loop เดียว ตัวแปร `range_value_0` ถูกส่งต่อให้ Filter และ Project ตรง ๆ ไม่มีการสร้าง Object ต่อแถว และไม่มีการเรียก `next()` ของ Iterator ทีละ Operator เหมือนโหมดตีความ (Volcano)
2. `MathUtils.multiplyExact` ปรากฏขึ้นเพราะ ANSI Mode เปิดอยู่ ([บทที่ 6](/spark/catalyst-aqe/in-depth/#analyzer-และ-ansi-mode-ที่ถูกล็อกตอน-analyze)) การคูณที่ล้นจึง Error แทนที่จะวนค่า
3. แถวผลลัพธ์ถูกเขียนเป็น `UnsafeRow` ผ่าน `UnsafeRowWriter` (ไบต์ดิบ ไม่ใช่ Object)

โครงที่เกี่ยวข้อง (จาก Source) มีดังนี้

| ส่วน | หน้าที่ |
|---|---|
| `CollapseCodegenStages` (`WholeStageCodegenExec.scala:914`) | Rule ใน `preparations` เลือก Operator ที่ Codegen ได้ ครอบ Operator ที่ทำไม่ได้ด้วย `InputAdapter` และใส่ `WholeStageCodegenExec` พร้อมหมายเลข Stage |
| `WholeStageCodegenExec` (บรรทัด 643) | รวม Subtree เป็นคลาส Java หนึ่งคลาส Compile ด้วย Janino แล้วรัน **ถ้า Compile ล้มจะถอยไปรันแบบตีความ (Interpreted)** |
| `CodeGenerator` | ตัวสร้างโค้ดและ Cache ของคลาสที่ Compile แล้ว มีขีดจำกัดของ JVM เช่น Method ที่ยาวเกิน 8000 ไบต์ Bytecode จะไม่ถูก JIT ง่าย จึงมีการแบ่ง Method |

`Exchange` ไม่เคยอยู่ใน Codegen ใน Plan ของ `groupBy` จะมี `*(1)` ที่ฝั่งก่อน Shuffle และ `*(2)` ที่ฝั่งหลัง โดย `Exchange` ที่คั่นกลางไม่มี `*` เพราะเป็นขอบเขตของ Stage (ตรวจจริง) และถ้าปิด `spark.sql.codegen.wholeStage` แล้ว `*(n)` จะหายไปจากทุก Operator

แล้วเร็วขึ้นเท่าไร เราวัดบนคอมพิวเตอร์ของผู้เขียน `range(30 ล้านแถว).filter(...).agg(sum)` ใช้เวลาราว 0.09 วินาทีเมื่อเปิด Whole-stage Codegen และ 0.23 วินาทีเมื่อปิด (เร็วขึ้นราว 2.5 เท่า) นี่เป็นตัวอย่างเล็กที่ CPU ทำงานล้วน ๆ งานจริงที่มี I/O หรือ Shuffle จะเห็นส่วนต่างน้อยกว่านี้ และตัวเลขนี้ขึ้นกับคอมพิวเตอร์และงาน จึงไม่ใช่ตัวคูณที่ใช้ทั่วไปได้

<Callout type="note" title="ไม่ใช่ทุกอย่างอยู่ใน Codegen">
Operator ที่ไม่ Codegen (เช่น `Exchange`) และ Expression ที่ Implement ด้วยการตีความ (CodegenFallback) จะตัดสาย Codegen ออกเป็นสองก้อน Python UDF ก็ตัดเหมือนกันแต่ด้วยเหตุผลต่างกัน (ต้องส่งข้อมูลไปนอก JVM ดู[บทที่ 8](/spark/udf/#ข้อมูลเดินทางอย่างไร)) เลข `*(n)` ที่ต่างกันใน Plan ก็คือขอบเขตเหล่านี้นั่นเอง
</Callout>
