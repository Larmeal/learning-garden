## Streaming คือ DataFrame ที่ไม่มีวันจบ

ใน Batch เราอ่านข้อมูลก้อนหนึ่ง คำนวณ แล้วก็จบ แต่ใน Structured Streaming เรามอง Input เป็นตารางที่ **แถวใหม่ถูกต่อท้ายเรื่อย ๆ** แล้วเขียน Query เหมือนกับ DataFrame ปกติ จากนั้น Spark จะรัน Query ซ้ำกับข้อมูลส่วนที่เพิ่มเข้ามาเป็นรอบ ๆ ซึ่งเราเรียกแต่ละรอบว่า **Micro-batch**

```python
events = (spark.readStream
          .schema("ts timestamp, user string, amt int")
          .json("/data/in"))                              # โฟลเดอร์ที่ไฟล์ใหม่ลงมาเรื่อยๆ

counts = events.groupBy("user").count()                   # transformation ปกติ

query = (counts.writeStream
         .outputMode("complete")
         .option("checkpointLocation", "/data/ck")
         .format("memory").queryName("counts")
         .start())                                        # เริ่มรัน
```

มีสามเรื่องที่ควรรู้ไว้ตั้งแต่ตอนนี้

- `events.isStreaming` เป็น `True` เราจึงเรียก Action อย่าง `events.count()` ไม่ได้ ถ้าเรียกจะได้ `AnalysisException: Queries with streaming sources must be executed with writeStream.start()` (วัดจริง)
- ทุกอย่างที่เรียนมาก่อนหน้านี้ยังใช้ต่อได้ Catalyst จะเขียนแผนใหม่ให้ และ `explain()` ก็ยังอ่านได้ เพียงแต่จะมี Operator ของ Streaming เพิ่มเข้ามา
- **Checkpoint** คือสิ่งที่ทำให้ Query หยุดแล้วกลับมารันต่อได้โดยไม่เสียความจำ เราจึงต้องระบุทุกครั้งที่ใช้งานจริง

<Callout type="warn" title="บน Windows ต้องรันใน WSL">
ถ้าไม่มี `hadoop.dll` Hadoop จะเขียน Checkpoint ลงคอมพิวเตอร์ที่ใช้ Windows ไม่ได้ ซึ่งคอมพิวเตอร์เครื่องนี้ได้ `UnsatisfiedLinkError: NativeIO$Windows.access0` ตอน `start()` ตัวอย่างในบทนี้เลยรันใน WSL (Ubuntu, Java 21, PySpark 4.2.0) ด้วยสคริปต์ `subjects/spark/code/run_wsl.sh` แต่ถ้าคุณใช้ Linux หรือ macOS ก็รันตรงได้เลย
</Callout>

</Step>

## หนึ่ง Micro-batch เกิดอะไรขึ้น

ลูปการทำงานอยู่ใน `MicroBatchExecution` (`MicroBatchExecution.scala:612-700`, ฟังก์ชัน `executeOneBatch`) ซึ่งทุกรอบจะทำตามลำดับนี้

1. **`constructNextBatch`** ถาม Source ว่ามีข้อมูลถึงไหนแล้ว เพื่อกำหนดช่วง Offset ของ Batch นี้ จากนั้น **เขียน `offsets/N` ลง Checkpoint** ก่อนที่จะทำอะไรกับข้อมูล (บรรทัด 909-1013, เขียนผ่าน `markMicroBatchStart`)
2. **`runBatch`** แปลง Query เป็นแผน Physical สำหรับช่วงข้อมูลนั้น แล้วรันเป็น Job ปกติ โดย Operator ที่มี State จะอ่านและเขียน State Store
3. ส่งผลให้ Sink
4. **`markMicroBatchEnd`** อัปเดต Watermark แล้ว **เขียน `commits/N`** (บรรทัด 1406-1530)

เรามาลองดูทีละขั้น และลองจำลองตอนที่โปรแกรมล่มก่อนจะเขียน `commits/N` กันดู

<MicroBatchLab client:visible />

หลังรันจริง (`exercises/09_streaming.py`) Checkpoint จะมีหน้าตาแบบนี้

```
ck/
  metadata                  # id ของ query
  offsets/0 1 2 ... 6       # ช่วงข้อมูลของแต่ละ batch (เขียนก่อนรัน)
  commits/0 1 2 ... 6       # batch ที่จบสมบูรณ์ (เขียนหลังรัน)
  sources/0/                # ข้อมูลของ source (ของ file source คือรายการไฟล์)
  state/0/<partition>/      # state ของ operator หมายเลข 0: ไฟล์ 1.delta 2.delta ...
```

ส่วนไฟล์ `offsets/1` จะเป็นข้อความสามบรรทัด

```
v1
{"batchWatermarkMs":..., "batchTimestampMs":..., "conf":{"spark.sql.streaming.stateStore.providerClass":"...", ...}}
{"logOffset": ...}                      # offset ของ source (ของ file source)
```

บรรทัดกลางบันทึกทั้ง Watermark และ Config สำคัญที่ใช้ตอนรัน Batch นั้นเอาไว้ เพื่อให้รันซ้ำได้เหมือนเดิม และเมื่อ Query สงบ จำนวนไฟล์ใน `offsets/` กับ `commits/` จะเท่ากัน

</Step>

## ทำไมรีสตาร์ทแล้วไม่ซ้ำ

คำสัญญา "Exactly-once" ของ Structured Streaming เกิดจากสามส่วนที่มาประกอบกัน

1. **Source ที่เล่นซ้ำได้** หมายถึงเราขอข้อมูลช่วง Offset เดิมได้เสมอ (ไฟล์, Kafka)
2. **Checkpoint** ที่จำได้ว่า Batch ไหนเริ่ม (`offsets/N`) และ Batch ไหนจบ (`commits/N`)
3. **Sink ที่เขียนซ้ำได้อย่างปลอดภัย** (Idempotent)

สองข้อแรก Spark ดูแลให้เรา ส่วนข้อสุดท้ายเป็นหน้าที่ของ Sink เราลองทดสอบจริงโดยจำลองการล่มด้วยการลบ `commits/1` ทิ้ง แล้วเริ่ม Query ใหม่ด้วย Checkpoint เดิม (รัน: `exercises/09_streaming.py`)

```python
def per_batch(df, batch_id):
    seen.append((batch_id, sorted((r.user, r["count"]) for r in df.collect())))

# ก่อนล่ม:  [(0, [("a",1), ("b",1)]), (1, [("a",2), ("b",1)])]
# ลบ commits/1 แล้วรีสตาร์ท แล้วเพิ่มข้อมูลใหม่ (user c):
# หลังรีสตาร์ท: [(1, [("a",2), ("b",1)]), (2, [("a",2), ("b",1), ("c",1)])]
```

- Batch 1 ถูกรัน **อีกครั้ง** ด้วยข้อมูลเดิม และได้ผลเท่าเดิม (`foreachBatch` ถูกเรียกด้วย `batch_id = 1` ซ้ำ)
- State ยังต่อเนื่องกัน ค่านับของ `a` ยังเป็น 2 ไม่ถูกรีเซ็ต
- Batch ใหม่เริ่มที่ 2

ดังนั้นถ้า Sink คือ `foreachBatch` ที่เขียนต่อท้ายตาราง คุณจะได้แถวซ้ำของ Batch 1 เราจึงต้องใช้ `batch_id` เป็นกุญแจ โดยเขียนแบบ Upsert หรือเก็บ `batch_id` ที่เขียนแล้วไว้เพื่อข้าม สำหรับ Sink แบบไฟล์ของ Spark จะทำเรื่องนี้ให้เองผ่าน Manifest แต่ Sink ที่คุณเขียนเองต้องคิดเรื่องนี้เอง

</Step>

## Output Mode: ส่งอะไรให้ Sink ในแต่ละ Batch

| Mode | ส่งอะไร | ใช้กับ |
|---|---|---|
| `append` | เฉพาะแถวที่ **ไม่เปลี่ยนอีกแล้ว** | Query ไม่มี Aggregation หรือ Aggregation ที่มี Watermark |
| `update` | เฉพาะแถวที่เปลี่ยนใน Batch นี้ | Aggregation |
| `complete` | ผลทั้งตารางทุก Batch | Aggregation (ต้องเก็บ State ทั้งหมดตลอดไป) |

`append` กับ Aggregation ที่ไม่มี Watermark ใช้ไม่ได้ เพราะ Spark ไม่มีทางรู้ว่ากลุ่มไหน "จบแล้ว" ซึ่งผลที่ได้ (วัดจริง) คือ `AnalysisException: [STREAMING_OUTPUT_MODE.UNSUPPORTED_OPERATION] Invalid streaming output mode: append. This output mode is not supported for streaming aggregations without watermark` ส่วน `complete` และ `update` เริ่มได้ปกติ

</Step>

## Event Time, Window และ Watermark

ข้อมูลที่มีเวลาของเหตุการณ์ (Event Time) มักมาไม่เรียงและมาช้า ถ้าเรานับ "ต่อ Window 5 นาที" Spark ก็ต้องเก็บ State ของทุก Window ที่ยังอาจได้ข้อมูลเพิ่ม และถ้าไม่มีกติกาปิด State ก็จะโตไปเรื่อย ๆ **Watermark** ก็คือกติกานั้นนั่นเอง

```python
agg = (events
       .withWatermark("ts", "10 minutes")
       .groupBy(F.window("ts", "5 minutes")).count())
```

โค้ดนี้แปลว่า "ยอมรับข้อมูลที่ช้าได้ไม่เกิน 10 นาทีเทียบกับ Event ที่ใหม่สุดที่เคยเห็น" โดย Spark ใช้ **Watermark = Event Time ที่ใหม่สุด ลบ 10 นาที** แล้ว Window ที่ปลายช่วงไม่เกิน Watermark จะถือว่าจบ ซึ่งจะส่งผลออกใน `append` Mode และถูกลบออกจาก State ส่วน Event ที่เก่ากว่า Watermark จะถูกทิ้ง

เรามาลองดูสี่ไฟล์ที่เข้ามาทีละไฟล์ โดยไฟล์สุดท้ายเป็น Event ที่มาช้า

ภาพนี้จะให้ Event ตกลงบนแกนเวลาของ Event เอง ลองเปลี่ยน Delay ดู แล้วสังเกตว่า Event ที่มาช้าถูกทิ้งหรือไม่ และผลออกเมื่อไร

<WatermarkFlowLab client:visible />

ส่วนภาพนี้จะเดินไปทีละ Batch ตามตารางที่วัดจริง

<WatermarkLab client:visible />

จากตัวเลขจริง (ตาราง `recentProgress` จากการรัน) เราเห็นอะไรบ้าง

```
batchId  numInputRows  watermark ที่ใช้
0        2             1970-01-01T00:00:00Z
1        0             11:53
2        1             11:53
3        0             11:56
4        1             11:56
5        0             12:10        <- window ปิดและถูกส่งออก
6        1             12:10        <- event ที่มาช้า
```

- **Watermark คำนวณตอนจบ Batch และถูกใช้ใน Batch ถัดไป** ไม่ได้ใช้ใน Batch เดียวกัน ผลของ Window จึงออกช้ากว่าที่คิดไว้หนึ่ง Batch
- Spark รัน **Batch ที่ไม่มีข้อมูลใหม่** (`numInputRows = 0`) เพื่อนำ Watermark ใหม่ไปใช้ ถ้าไม่มี Batch แบบนี้ Window จะไม่ปิดจนกว่าจะมีข้อมูลมาถึง (ควบคุมด้วย `spark.sql.streaming.noDataMicroBatches.enabled` ค่าเริ่มต้น True)
- ใน `append` Mode ผลของไฟล์ที่ 1 และ 2 ว่างเปล่า (วัดจริง) เพราะ Window ยังเปิดอยู่ จึงต้องรอ Event ที่ 12:20 มาดัน Watermark ไปถึง 12:10
- Event 12:01 ที่มาช้าถูกทิ้ง ผลที่ส่งออกไปแล้วจะไม่เปลี่ยน และ `numRowsDroppedByWatermark` ใน Progress จะเพิ่มขึ้น

<Callout type="note" title="Watermark ที่ใหญ่ขึ้นแลกกับอะไร">
ถ้า Watermark ยาว เราจะรับข้อมูลที่มาช้าได้มากขึ้น แต่ผลจะออกช้าลงและ State ก็ใหญ่ขึ้นด้วย (เพราะต้องเก็บ Window นานขึ้น) ในทางกลับกัน ถ้า Watermark สั้น ผลจะออกเร็ว แต่ข้อมูลที่มาช้าจะถูกทิ้ง เพราะฉะนั้นต้องเลือกตามว่าข้อมูลของคุณมาช้าได้แค่ไหน
</Callout>

## State อยู่ที่ไหน

Operator ที่ต้องจำค่าข้าม Batch (Aggregation, Dedup, Join ฝั่ง Stream) จะเก็บค่าไว้ใน **State Store** ซึ่งแผนของ Query ข้างบนมี Operator เฉพาะ Streaming อยู่ด้วย (วัดจากการ `explain()`)

```
StateStoreSave   [window#..-T600000ms], state info [... opId = 0, numPartitions = 4], Append, ...
+- StateStoreRestore [window#..-T600000ms], state info [...]
   +- EventTimeWatermark ..., ts#0: timestamp, 10 minutes
      +- StreamingRelation FileSource[...], [ts#0, user#1, amt#2]
```

ในทุก Batch `StateStoreRestore` จะอ่านค่าเดิมจาก State เวอร์ชันก่อน แล้ว `StateStoreSave` จะเขียนค่าใหม่เป็นเวอร์ชันถัดไป โดย State ถูกแบ่งตาม Partition ของ Shuffle (ที่นี่ 4) และเก็บใน `state/<operator>/<partition>/`

- **Provider ค่าเริ่มต้น** คือ `HDFSBackedStateStoreProvider` (`spark.sql.streaming.stateStore.providerClass`) ซึ่งเก็บ State ทั้งหมดของ Partition ไว้ใน Memory ของ Executor และเขียนการเปลี่ยนแปลงเป็นไฟล์ `.delta` ต่อเวอร์ชัน (บางเวอร์ชันรวมเป็น Snapshot)
- **RocksDB** เป็นทางเลือก (`RocksDBStateStoreProvider`) ที่เก็บ State ใน RocksDB บน Disk จึงรับ State ที่ใหญ่กว่า Memory ได้ วัดจริงแล้วว่าเมื่อเปลี่ยน Provider Query ก็ยังนับได้ปกติ และใน Checkpoint จะเห็นไฟล์ `.sst` และ `.zip` แทน `.delta`
- ตัวเลขดูได้ใน `lastProgress["stateOperators"]` ได้แก่ `numRowsTotal`, `numRowsUpdated`, `numRowsRemoved`, `numRowsDroppedByWatermark` และ `memoryUsedBytes` ซึ่งเอาไว้ติดตามว่า State โตเกินไปหรือไม่ ในการรัน Watermark ข้างบน `numRowsRemoved` = 2 ตอนที่ Window ปิด

</Step>

## Trigger: เมื่อไรถึงรัน Batch ถัดไป

| Trigger | พฤติกรรม |
|---|---|
| ไม่ระบุ | รัน Batch ถัดไปทันทีที่ Batch ก่อนจบและมีข้อมูล |
| `processingTime="1 second"` | เริ่ม Batch ทุกช่วงเวลา |
| `availableNow=True` | ประมวลผลข้อมูลที่ค้างอยู่ทั้งหมดแล้ว **หยุดเอง** |
| `once=True` | เหมือนข้างบนแต่ใน Batch เดียว (ประกาศเลิกใช้ตั้งแต่ Spark 3.4.0 ให้ใช้ `availableNow` แทน) |

`availableNow` เหมาะกับงานที่รันเป็นรอบ เช่น Cron ทุกชั่วโมง โดยที่เรายังได้ Checkpoint ครบ จากที่วัดจริง ตอนมี 3 ไฟล์ค้างและตั้ง `maxFilesPerTrigger=1` เราจะได้ Batch 0, 1, 2 แล้ว Query ก็จบเอง (`isActive` เป็น False) และถ้ารันใหม่ด้วย Checkpoint เดิมจะไม่เกิด Batch เลย เพราะ Checkpoint จำได้ว่าไฟล์ไหนอ่านแล้ว

Spark 4.2 ยังมี Trigger แบบ Real-time ใน Source (`RealTimeTrigger`) แต่ในบทนี้เราไม่ได้ทดสอบ

</Step>

2. เพิ่มไฟล์ที่ Event 12:08 หลัง Batch ที่ปิด Window ไปแล้ว ดูว่าถูกทิ้งไหม
3. ลบ `commits/N` ทุกตัวหลังตัวที่ 2 แล้วรีสตาร์ท ดูว่า Batch ไหนถูกรันซ้ำ

ลองเช็กตัวเองด้วยคำถามเหล่านี้

- ทำไม Spark ต้องเขียน `offsets/N` **ก่อน** รัน Batch
- รีสตาร์ทหลังล่มแล้ว Sink ได้ Batch เดิมสองครั้ง ต้องทำอย่างไรให้ไม่เกิดข้อมูลซ้ำ
- ทำไม `append` กับ `groupBy().count()` ที่ไม่มี Watermark ถึงใช้ไม่ได้

**ที่ยังไม่ครอบคลุม** ในบทนี้ ได้แก่ Stream-stream Join, `flatMapGroupsWithState`, Kafka Source/Sink (ไม่ได้ทดสอบ และส่วนที่เกี่ยวกับ Join/Arbitrary State ของ Stream ยังไม่อยู่ใน Knowledge Graph)

</Step>
