## MLlib คืออะไร และมีสองชุด

MLlib คือไลบรารี Machine Learning ของ Spark ไว้เทรนโมเดลกับข้อมูลที่ใหญ่เกินคอมพิวเตอร์เครื่องเดียว โดยให้ Executor หลายตัวช่วยกันทำงาน และมี API อยู่สองชุด

| แพ็กเกจ | ฐาน | สถานะ |
|---|---|---|
| `pyspark.ml` | DataFrame | **ตัวหลัก** ใช้ในบทนี้ |
| `pyspark.mllib` | RDD | **Maintenance Mode** ตั้งแต่ Spark 2.0 (ตาม `docs/ml-guide.md`: แก้บั๊กแต่ไม่เพิ่มฟีเจอร์ใหม่) |

เราจะเรียนกันเฉพาะ `pyspark.ml` ซึ่งอ่านและเขียนทุกอย่างด้วย DataFrame ที่เรียนมาแล้ว บทนี้ต้องมี `numpy` (`pyspark.ml` ใช้ใน Python) ซึ่งติดมากับ Pandas ในโปรเจกต์นี้อยู่แล้ว ตัวอย่างรันด้วย `exercises/12_mllib.py` บน WSL เพราะตอนบันทึกโมเดลต้องเขียนไฟล์ ([บทที่ 9](/spark/structured-streaming/#streaming-คือ-dataframe-ที่ไม่มีวันจบ))

ข้อมูลที่ใช้ในบทนี้เป็นข้อมูลสังเคราะห์ 2,000 แถว โดย `x1`, `x2` เป็นตัวเลข `c` เป็น Category (a, b, c) และ `label` เป็น 0 หรือ 1 ที่สร้างจากสูตรบวก Noise ทำให้เรารู้ล่วงหน้าว่า `x1` ควรดันไปทาง 1 และ `x2` ควรดันออก

</Step>

## สามชิ้นส่วนที่ต้องแยกให้ออก

| ชิ้น | ทำอะไร | ตัวอย่าง |
|---|---|---|
| **Transformer** | `transform(df)` รับ DataFrame แล้วคืน DataFrame ที่มี Column เพิ่ม | `VectorAssembler`, โมเดลที่เทรนแล้ว |
| **Estimator** | `fit(df)` เรียนรู้จากข้อมูล แล้วคืน **Model** ซึ่งเป็น Transformer | `StringIndexer`, `LogisticRegression` |
| **Pipeline** | ต่อ Stage เป็นลำดับ โดยเป็น Estimator ที่ `fit` แล้วได้ `PipelineModel` | `Pipeline(stages=[...])` |

เราดูได้จากชื่อใน `model.stages` หลัง `fit` ว่าอะไรเป็นอะไร (วัดจริง)

```python
pipe = Pipeline(stages=[StringIndexer(...), OneHotEncoder(...), VectorAssembler(...), LogisticRegression(...)])
model = pipe.fit(train)
[type(s).__name__ for s in model.stages]
# ['StringIndexerModel', 'OneHotEncoderModel', 'VectorAssembler', 'LogisticRegressionModel']
```

Estimator ทั้งสามตัวเปลี่ยนเป็น Model ส่วน `VectorAssembler` ไม่มีอะไรต้องเรียนรู้ จึงยังเป็นตัวเดิม ลองดูทีละขั้นได้ในแล็บนี้

## `fit` รัน Job, `transform` ไม่รัน

นี่คือความสับสนที่ใหญ่ที่สุดของคนที่เพิ่งเรียน (และตรงกับเรื่อง Lazy Evaluation ใน[บทที่ 2](/spark/lazy-evaluation/#สองประเภทของคำสั่ง)) เราลองนับ Job ด้วย `statusTracker` ระหว่างที่เรียก (รัน)

| คำสั่ง | Job ที่เกิด |
|---|---|
| `VectorAssembler.transform(train)` | **0** |
| `pipeline.fit(train)` | **14** |
| `model.transform(test)` | **0** |
| `BinaryClassificationEvaluator().evaluate(pred)` | เกิดตอนนี้ (นี่คือ Action) |

- `transform` แค่ต่อแผน ไม่ได้แตะข้อมูล แผนที่ได้จะเป็น `Project` ซ้อนกัน โดยแต่ละชั้นเรียก UDF ฝั่ง JVM (`UDF(features)`, `UDF(rawPrediction)`) ซึ่งเป็น UDF ที่ Spark เขียนเองใน Scala ไม่ใช่ Python UDF ของ[บทที่ 8](/spark/udf/#udf-คืออะไร-และทำไมต้องระวัง)
- `fit` เป็น Action เพราะต้องดูข้อมูลจริง เช่นนับ Category และวนปรับน้ำหนักหลายรอบ โดย `LogisticRegression` เป็นส่วนที่เกิดหลาย Job มากที่สุด

เพราะฉะนั้นเวลาที่ใช้ไปจึงอยู่ที่ `fit` ส่วน `transform` บนข้อมูลใหม่เป็นเรื่องเบาและทำขนานได้เหมือน Narrow Transformation

</Step>

## Param: ตั้งค่าอย่างมีชนิด

แต่ละ Estimator และ Transformer มี **Param** ซึ่งเป็นค่าที่ตั้งได้พร้อมชนิดและค่าเริ่มต้น เราดูได้ด้วย `explainParam` (รัน)

```python
lr = LogisticRegression(maxIter=20, regParam=0.01)
lr.explainParam("regParam")        # regularization parameter (>= 0). (default: 0.0, current: 0.01)
lr.getOrDefault("maxIter")         # 20  (ค่าเริ่มต้นของคลาสคือ 100)
lr.isSet("tol")                    # False  ยังไม่ได้ตั้ง ใช้ค่าเริ่มต้น
lr.copy({lr.regParam: 0.5})        # สำเนาที่เปลี่ยน param ตัวเดียว ตัวเดิมไม่เปลี่ยน
```

ค่าเริ่มต้นของ `LogisticRegression` ที่ควรรู้ มีดังนี้ `maxIter` = 100, `regParam` = 0.0, `elasticNetParam` = 0.0, `threshold` = 0.5, `tol` = 1e-6, `fitIntercept` = True, `standardization` = True (ปรับสเกล Feature ให้ก่อนโดยอัตโนมัติ) ส่วน `copy` ที่รับ Param Map เป็นพื้นฐานของ `CrossValidator` ที่ลองค่าหลายชุดโดยไม่แก้ Object เดิม

</Step>

<Step>

## ผลของโมเดลและการวัด

หลัง `fit` บน Train (80%) แล้ว เราจะ `transform` บน Test (20%) (ใช้ `randomSplit([0.8, 0.2], seed=7)`)

- **AUC บน Test = 0.981** (`BinaryClassificationEvaluator`, `areaUnderROC`)
- **Coefficients** = `[2.71, -1.87, 1.50, -0.14]` และ Intercept 0.118 ตัวแรก (`x1`) เป็นบวกและตัวที่สอง (`x2`) เป็นลบ ซึ่งตรงกับสูตรที่ใช้สร้างข้อมูล ส่วนสองตัวหลังเป็นของ Category `a` และ `b` (ตัว `c` ถูกตัดทิ้งเป็น Baseline)
- ผลลัพธ์แต่ละแถวมีสามคอลัมน์ คือ `rawPrediction` (คะแนนดิบ), `probability` (ความน่าจะเป็นของแต่ละ Class) และ `prediction` (Class ที่เลือก ใช้ Threshold 0.5)

มีเรื่องหนึ่งที่ต้องทำเสมอ คือแยก Train กับ Test ก่อน Fit ถ้า `StringIndexer` หรือ Scaler Fit บนข้อมูลทั้งหมดแล้วค่อยแยก ข้อมูล Test จะรั่วเข้าไปในโมเดล ทำให้ AUC ดูดีเกินจริง การใส่ทุกขั้นเตรียมข้อมูลไว้ใน Pipeline แล้ว `fit` เฉพาะ Train จึงปลอดภัยกว่าการทำทีละขั้นเอง

</Step>

## CrossValidator: ปรับ Parameter ตามต้นทุน

เราจะหาค่า `regParam` กับ `maxIter` ที่ดีที่สุดด้วยการลองทุกคู่ แล้ววัดด้วย Cross Validation

```python
grid = (ParamGridBuilder()
        .addGrid(lr.regParam, [0.0, 0.1, 1.0])
        .addGrid(lr.maxIter, [5, 20]).build())        # 3 x 2 = 6 ชุด
cv = CrossValidator(estimator=pipe, estimatorParamMaps=grid,
                    evaluator=BinaryClassificationEvaluator(), numFolds=3, parallelism=2)
cv_model = cv.fit(train)
```

ผลที่วัดได้จริงคือ `avgMetrics` ได้ 6 ค่า (AUC เฉลี่ยต่อชุด: 0.979, 0.980, 0.979, 0.979, 0.975, 0.975) และ **`cv.fit` เกิด 333 Job** เมื่อเทียบกับ `pipe.fit` ปกติที่เกิด 14 Job เพราะต้อง Fit Pipeline ทั้งอัน 6 ชุด คูณ 3 Fold = 18 ครั้ง แล้วบวกการ Fit ใหม่ด้วยชุดที่ดีที่สุดอีกครั้งบนข้อมูลทั้งหมด

ข้อสรุปเชิงปฏิบัติคือต้นทุนของ Tuning โตเป็นผลคูณ (ขนาด Grid x จำนวน Fold) ถ้ากริดมีสามตัวแปรตัวละห้าค่าก็เป็น 125 ชุด คูณ 3 Fold = 375 การ Fit เราลดต้นทุนได้ด้วยการใช้ข้อมูลตัวอย่างก่อน แคช Train ([บทที่ 7](/spark/performance-tuning/#cache-ช่วยเมื่อไร) เตือนว่า Cache มีราคา แต่ที่นี่ใช้ข้อมูลเดิมซ้ำเป็นร้อยรอบจึงคุ้ม) หรือเพิ่ม `parallelism` (ในแล็บใช้ 2)

</Step>

## กับดักที่เจอ

ข้อมูล Null จะหยุด `VectorAssembler` เพราะค่าเริ่มต้นคือ `handleInvalid = "error"` (ตรวจแล้ว) แถวที่มี Null ทำให้ Job ล้มด้วย `FAILED_EXECUTE_UDF ... Encountered null while assembling a row` เราใส่ `handleInvalid="skip"` เพื่อทิ้งแถวนั้นได้ (ตรวจแล้ว: แถวที่มี Null หายไป) หรือใส่ `"keep"` เพื่อเก็บเป็น NaN แต่ต้องรู้ด้วยว่าอัลกอริทึมต่อจากนั้นรับ NaN ได้ไหม

`OneHotEncoder` จะตัด Category สุดท้ายทิ้งด้วย `dropLast` (ค่าเริ่มต้น) `c` จึงออกมาเป็นเวกเตอร์ศูนย์ทั้งหมด เพื่อไม่ให้ Feature พึ่งพากันเองแบบสมบูรณ์ ซึ่งไม่ได้แปลว่าข้อมูลหายไป

ส่วนลำดับของ `StringIndexer` ค่าเริ่มต้นเรียงตามความถี่จากมากไปน้อย (`frequencyDesc` ตัวที่พบบ่อยสุดได้ 0 ถ้าความถี่เท่ากันเรียงตามตัวอักษร ตาม `StringIndexer.scala:64-70`) ผลในข้อมูลนี้คือ a, b, c แต่ถ้าข้อมูลของคุณมีความถี่ต่างกัน ลำดับ (และ Index) ก็จะต่างกันไปด้วย และอาจต่างกันระหว่างข้อมูลฝึกกับข้อมูลชุดอื่นได้ ถ้าไม่ใช้ Model ตัวเดิมกับทั้งสองชุด

สุดท้ายคือตัวเลือกอัลกอริทึมที่มีจำกัด MLlib ครอบคลุม Classification, Regression, Clustering, Recommendation (ALS) และ Feature Engineering แต่ไม่ได้ออกแบบมาแทนไลบรารี Deep Learning (ข้อนี้เป็นความเห็นผู้เขียน ไม่ได้ทดสอบ)

เมื่อข้อมูลไม่ได้ใหญ่เกินคอมพิวเตอร์เครื่องเดียว เครื่องมืออย่าง Scikit-learn มักสะดวกกว่า เราจึงเลือก MLlib เมื่อข้อมูลหรือจำนวนครั้งที่ต้อง Fit ใหญ่เกินคอมพิวเตอร์เครื่องเดียว หรือเมื่อ Pipeline ทั้งอันต้องอยู่ใน Spark อยู่แล้ว (ข้อนี้เป็นการตัดสินใจเชิงปฏิบัติ ไม่ใช่ผลทดสอบ)

</Step>

## ลองทำและเช็กตัวเอง

```bash
cd subjects/spark/code
uv run python exercises/12_mllib.py
```

ใช้เวลาราว 2 ถึง 3 นาที (เกือบทั้งหมดเป็น Cross Validation) แล้วลองดัดแปลงดูได้ตามนี้

1. เพิ่ม `StandardScaler` ต่อจาก `VectorAssembler` แล้วดูว่า `model.stages` เปลี่ยนอย่างไร
2. เปลี่ยน `handleInvalid` ของ `VectorAssembler` เป็น `"keep"` กับแถวที่มี Null แล้วดูผล
3. นับ Job ของ `cv.fit` เมื่อลด `numFolds` เหลือ 2

ลองเช็กตัวเองด้วยคำถามเหล่านี้

- ทำไม `pipeline.fit` ถึงเกิด Job แต่ `model.transform` ไม่เกิด
- `LogisticRegression` เป็น Estimator หรือ Transformer แล้วผลของ `fit` เป็นอะไร
- ทำไมต้อง Fit Pipeline บน Train เท่านั้น
- ขนาด Grid 4 ค่า x 5 ค่า กับ 3 Fold ต้อง Fit กี่ครั้ง (ไม่รวมการ Fit ใหม่ตอนท้าย)

</Step>
