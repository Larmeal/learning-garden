บทนี้คือจุดที่แยกคนที่ใช้ Spark เป็นออกจากคนที่เข้าใจว่ามันทำงานอย่างไร ถ้าเราเข้าใจบทนี้แล้ว การอ่าน `explain()` และ Spark UI รวมถึงการหาสาเหตุที่ Job ช้า ก็จะเริ่มเห็นภาพขึ้นมา

## เป้าหมายของบทนี้

- อธิบายความต่างของ Job, Stage และ Task ได้
- แยกได้ว่าคำสั่งไหนเป็น Narrow และคำสั่งไหนเป็น Wide (ต้อง Shuffle)
- ดูโค้ดสั้น ๆ แล้วทายจำนวน Stage ได้
- เห็นว่า Data Skew เกิดจาก Shuffle อย่างไร

## ศัพท์สามคำ

| คำ | ความหมาย |
|---|---|
| **Job** | งานที่เกิดขึ้นเมื่อคุณเรียก Action หนึ่งครั้ง เช่น `write`, `count`, `show` |
| **Stage** | ชุดของ Task ที่รันได้โดยไม่ต้องย้ายข้อมูลข้ามคอมพิวเตอร์ |
| **Task** | งานหนึ่งหน่วยที่ทำกับ Partition หนึ่งก้อน ทุก Task ใน Stage เดียวกันทำงานเหมือนกันแต่กับข้อมูลคนละก้อน |

ถ้าจะจำให้ง่าย ๆ ก็คือ Action สร้าง Job, Shuffle ตัด Job เป็น Stage และ Partition ทำให้ Stage แตกเป็น Task

## Narrow กับ Wide

คำสั่งแบ่งเป็นสองประเภทตามว่าต้องใช้ข้อมูลจากหลาย Partition หรือไม่

| ประเภท | ลักษณะ | ตัวอย่าง |
|---|---|---|
| **Narrow** | ผลของแต่ละ Partition ได้จาก Partition เดียว | `filter`, `select`, `withColumn`, `map` |
| **Wide** | ต้องเอาข้อมูลจากหลาย Partition มารวมกัน จึงเกิด Shuffle | `groupBy`, `join` (ปกติ), `distinct`, `orderBy`, `repartition` |

คำสั่ง Narrow ต่อกันกี่ตัวก็ยังอยู่ใน Stage เดียว แต่พอเจอคำสั่ง Wide ก็จะเกิดรอยตัดและเริ่ม Stage ใหม่

## ดูมันทำงานทีละขั้น

คราวนี้เราจะดูกันทีละแถว จุดแต่ละจุดคือหนึ่งแถว และสีคือ Key กดเล่นหรือลาก Slider ไปดูช่วงที่สนใจได้เลย ลองเปลี่ยนจำนวน Map Task แล้วดูว่าจำนวนช่องที่ Reduce ต้องดึงเปลี่ยนตามไปอย่างไร

มีสามอย่างที่น่าสังเกต

- ใน Stage 1 ไม่มีเส้นไขว้เลย เพราะแต่ละ Task จบงานของตัวเองได้
- ตอน Shuffle ทุก Task ต้องส่งข้อมูลให้ Task ปลายทางหลายตัว เส้นจึงไขว้กัน
- Stage 2 จะเริ่มไม่ได้จนกว่า Shuffle จะเสร็จทั้งหมด

## ทำไม Shuffle ถึงแพง

ข้อมูลที่ต้อง Shuffle จะถูกเขียนลง Disk ฝั่งผู้ส่ง แล้วฝั่งผู้รับต้องดึงผ่านเครือข่ายมาอ่าน โดยทั้งสองฝั่งต้องแปลงข้อมูลเป็นไบต์และแปลงกลับมาเป็นข้อมูลอีกที ส่วน Narrow ทำกับข้อมูลใน Memory ของตัวเองได้เลย ต้นทุนของสองแบบจึงต่างกันมาก

ด้วยเหตุนี้ เวลาพูดถึงการทำให้ Spark เร็ว คำถามแรกที่ควรถามคือ Shuffle กี่ครั้ง และแต่ละครั้งส่งข้อมูลเท่าไร

## เมื่อ Shuffle ไม่สมดุล: Data Skew

Shuffle ส่ง Key เดียวกันไปที่ Task เดียวกัน ถ้า Key หนึ่งมีข้อมูลมากผิดปกติ Task นั้นจะทำงานนานกว่าตัวอื่นมาก และทั้ง Stage ก็ต้องรอตัวที่ช้าที่สุด

ภาพนี้เป็นไทม์ไลน์ของ Task บน 4 Core ลองกดสลับระหว่างข้อมูลกระจายเท่ากัน ข้อมูล Skew (วัดจริง) และหลังเติม Salt แล้วดูว่า Core ที่ว่างช่วยอะไรไม่ได้

Core ที่ว่างอยู่ช่วยอะไรไม่ได้ เพราะ Key ก้อนนั้นต้องถูกประมวลผลโดย Task เดียว ส่วนเทคนิคแก้ เช่น Salting และการเปิด AQE จะอยู่ใน[บทที่ 7](/spark/performance-tuning/#data-skew-และ-salting)

## ลองทำใน Repo นี้

ให้สร้างไฟล์ที่ Root ของโปรเจกต์ (ข้าง ๆ `main.py`) เช่น `shuffle_lab.py`

```python
from spark_session import get_spark

spark = get_spark("shuffle-lab")

df = spark.range(1_000_000)                       # คอลัมน์ id
agg = df.groupBy((df.id % 3).alias("k")).count()  # wide: ต้อง shuffle

agg.explain()   # หาคำว่า Exchange ในแผน
agg.show()      # action: เริ่มทำงานจริง

input("เปิด http://localhost:4040 แล้วดูแท็บ Stages จากนั้นกด Enter")
spark.stop()
```

รันด้วย `uv run python shuffle_lab.py`

พอรันแล้วลองดูสามเรื่องนี้ และพยายามตอบให้ได้

1. ในผลของ `explain()` มีบรรทัด `Exchange hashpartitioning(...)` ซึ่งก็คือ Shuffle ลองลบ `groupBy` ออกแล้วรันใหม่ดูว่าบรรทัดนี้หายไปไหม
2. ใน Spark UI แท็บ Stages Job นี้แตกเป็นกี่ Stage และตรงกับที่ทายไว้หรือเปล่า
3. จำนวน Partition หลัง Shuffle คือเท่าไร ค่าเริ่มต้นของ `spark.sql.shuffle.partitions` คือ 200 แต่ AQE จะรวม Partition เล็กให้ตอนรัน บนคอมพิวเตอร์ 16 Core ที่ใช้ทดสอบ ผลของ `groupBy` ข้อมูลเล็กมี **1 Partition** เมื่อเปิด AQE และ **200** เมื่อปิด (`spark.sql.adaptive.enabled=false`) ถ้าเปิด AQE `explain()` ก่อนรันจะขึ้นต้นด้วย `AdaptiveSparkPlan isFinalPlan=false` ซึ่ง[บทที่ 6](/spark/catalyst-aqe/#เปิดอยู่แล้ว-adaptivesparkplan) อธิบายไว้

## เช็กตัวเอง

- ดูโค้ดสามบรรทัดแล้วบอกได้ไหมว่ามีกี่ Stage เพราะอะไร
- ถ้า Job ช้า จะดูที่ไหนเป็นอย่างแรกเพื่อรู้ว่าติดที่ Shuffle
- `repartition(10)` เป็น Narrow หรือ Wide เพราะอะไร
