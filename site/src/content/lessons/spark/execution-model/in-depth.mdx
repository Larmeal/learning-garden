## คำสั่งไหน Shuffle: วัดจากแผนจริง

บทหลักบอกไว้ว่า Narrow ไม่ Shuffle ส่วน Wide ต้อง Shuffle คราวนี้เราลองตรวจทุกคำสั่งด้วย `explain()` แล้วนับบรรทัด `Exchange` ดู

### ไม่ Shuffle

หลักคิดคือผลของแต่ละแถวคำนวณได้จาก Partition ที่แถวนั้นอยู่แล้ว จึงทำต่อกันใน Task เดียวได้เลยโดยไม่ต้องย้ายแถว

| คำสั่ง | Exchange ในแผน | เพราะอะไร |
|---|---|---|
| `filter`, `select`, `withColumn` | ไม่มี | ทำกับแต่ละแถวแยกกัน ไม่ต้องรู้ว่าแถวอื่นอยู่ที่ไหน |
| `union` | ไม่มี | แค่เอา Partition ของสองฝั่งมาต่อกัน ไม่มีแถวย้ายที่ |
| `coalesce(4)` | ไม่มี | รวม Partition ที่อยู่ติดกันเข้าด้วยกัน ไม่ได้แจกแถวใหม่ |
| `sample` | ไม่มี | สุ่มเลือกแถวภายใน Partition ของตัวเอง |
| `limit(5)` ขั้นสุดท้าย | ไม่มี (เป็น `CollectLimit`) | ต้องการแค่ 5 แถว จึงเก็บกลับมาที่ Driver ได้เลยโดยไม่ต้องจัดแถวใหม่ (วัดเฉพาะกรณีเป็นขั้นสุดท้าย) |

### Shuffle (มี Exchange)

หลักคิดคือแถวที่ต้องไปอยู่ด้วยกัน (Key เดียวกัน, ช่วงค่าเดียวกัน หรือ Partition เดียว) อาจกระจายอยู่หลาย Partition ก็ได้ จึงต้องส่งมารวมกันก่อน

| คำสั่ง | Exchange ในแผน | เพราะอะไร |
|---|---|---|
| `repartition(8)` | `RoundRobinPartitioning` | แจกแถวให้ Partition ใหม่ 8 ตัวเท่า ๆ กัน โดยไม่ดูค่าของแถว |
| `repartition(8, "k")` | `hashpartitioning` | แถวที่ `k` เท่ากันต้องไปอยู่ Partition เดียวกัน |
| `groupBy("k").count()` | `hashpartitioning` | ต้องรวมแถวของ `k` เดียวกันมาไว้ที่เดียวก่อนนับ |
| `distinct`, `dropDuplicates` | `hashpartitioning` | แถวที่ซ้ำกันอาจอยู่คนละ Partition จึงต้องมารวมกันก่อนถึงจะรู้ว่าซ้ำ |
| Window ที่ `partitionBy("k")` | `hashpartitioning` | ต้องมีแถวของ `k` เดียวกันครบใน Partition เดียวถึงจะคำนวณได้ |
| `orderBy("v")` | `rangepartitioning` | แบ่งช่วงของค่า `v` ให้แต่ละ Partition เก็บช่วงของตัวเอง เรียงในแต่ละ Partition แล้วเอามาต่อกันก็ได้ลำดับรวม (ต้องสุ่มข้อมูลหาขอบเขตก่อน ดูหัวข้อถัดไป) |
| `agg(sum(...))` (ไม่มี groupBy) | `SinglePartition` | ผลบางส่วนจากทุก Partition ต้องมารวมใน Partition เดียว |
| `join` แบบ Sort-merge | `hashpartitioning` สองตัว (ทั้งสองฝั่ง) | แถวของสองตารางที่ `key` เท่ากันต้องอยู่ Partition เดียวกัน จึงต้องจัดทั้งสองฝั่ง |

ถ้าดูตารางนี้ จะมีสามข้อที่น่าสังเกต

ข้อแรก `coalesce` ไม่ Shuffle แต่ `repartition` Shuffle ทั้งที่ทั้งคู่ปรับจำนวน Partition เหมือนกัน

ข้อที่สอง Aggregate ที่ไม่มี `groupBy` ก็ยังมี Exchange เพราะผลรวมจาก Partial Aggregate ของทุก Partition ต้องมารวมใน Partition เดียว (`SinglePartition`) ซึ่งแปลว่า Task สุดท้ายนั้นเป็นจุดคอขวดของการรวมทั้งหมด แต่ข้อมูลที่ส่งมามีขนาดเล็กมาก (ผลบางส่วนของแต่ละ Partition)

ข้อที่สาม `join` ปกติมี Exchange สองตัว แต่ถ้าฝั่งหนึ่งเล็กพอจนถูก Broadcast ก็จะไม่มี Exchange ของแถวทั้งสองฝั่งเลย เหลือเพียง `BroadcastExchange` (ตรวจแล้ว ตาม[บทที่ 6](/spark/catalyst-aqe/#join-ตัวไหน-และใครเลือก) และ [7](/spark/performance-tuning/#spark-เลือก-join-อย่างไร))

</Step>

## จำนวน Stage = Exchange + 1

ทุก `Exchange` คือขอบเขตของ Stage ดังนั้นจำนวน Stage ของงานหนึ่งชิ้นก็คือจำนวน Exchange บวกหนึ่ง เราวัดจริงโดยนับ Stage ที่เกิดจาก `collect()` ของแต่ละคำสั่งข้างบน

| คำสั่ง | Exchange | Stage |
|---|---|---|
| `filter`, `select`, `withColumn`, `union`, `coalesce(4)` | 0 | 1 |
| `repartition`, `groupBy`, `distinct`, `dropDuplicates`, window, `agg(sum)` | 1 | 2 |
| `join` (sort-merge) | 2 | 3 |
| `orderBy` | 1 | **3** |
| `limit(5)` | 0 | 1 |

ข้อยกเว้นคือ `orderBy` ซึ่งได้ 3 Stage ไม่ใช่ 2 เพราะ Range Partitioning ต้อง **สุ่มข้อมูลก่อน** เพื่อหาขอบเขตว่าจะแบ่งช่วงของค่าอย่างไรให้ Partition มีขนาดพอ ๆ กัน การสุ่มนี้เป็นอีก Stage หนึ่ง ใน Spark UI เราจะเห็น Job ของ `orderBy` มี Stage เพิ่มหนึ่งตัวที่ทำงานก่อน

ตัวอย่างการนับเมื่อต่อหลายคำสั่ง (คำนวณจากกฎข้างบน ไม่ได้วัดเป็นโซ่)

| โซ่คำสั่ง | Exchange | Stage |
|---|---|---|
| `filter` → `select` → `groupBy("k").count()` | 1 | 2 |
| `filter` → `groupBy("k").count()` → `orderBy` | 2 | **4** (2 + 1 และอีก 1 Stage สุ่มของ `orderBy`) |
| `filter` → `join` → `groupBy("k").count()` → `limit(5)` | 3 (Join สอง, groupBy หนึ่ง) | 4 |

ยังมีอีกกรณีที่กฎนี้ประมาณเกินจริง คือเมื่อ Join สองตารางที่ถูก `groupBy` ด้วย Key เดียวกันและจำนวน Partition เท่ากันอยู่แล้ว (ทั้งสองฝั่งถูกจัด `hashpartitioning(k, 200)` แล้ว) Spark จะไม่เพิ่ม Exchange ให้ Join อีก ผลที่วัดได้คือ `groupBy` สองตัวแล้ว Join ได้ Stage `[4, 4, 200]` คือ **3 Stage** (ไม่ใช่ 5) เพราะ Join ใช้ Partitioning ที่มีอยู่ได้เลย นี่คือเหตุผลที่การเลือก Key และจำนวน Partition ให้ตรงกันก่อน Join ช่วยลด Shuffle ได้

</Step>

## Task ต่อ Stage และไบต์ที่ Shuffle

ลองรัน `range(0, 2_000_000, 1, 8).groupBy(id % 7).count()` (AQE ปิด) แล้วอ่านจาก REST API

| stage | task | shuffle write | shuffle read |
|---|---|---|---|
| 0 (ฝั่ง Map) | **8** | 3,496 ไบต์ | 0 |
| 1 (ฝั่ง Reduce) | **200** | 0 | 3,496 ไบต์ |

- จำนวน Task ของ Stage แรกเท่ากับจำนวน Partition ของข้อมูลต้นทาง (8) ส่วน Stage หลัง Shuffle เท่ากับ `spark.sql.shuffle.partitions` (200)
- ไบต์ที่ Stage 0 เขียนเท่ากับที่ Stage 1 อ่านเป๊ะ (3,496 ไบต์) เพราะข้อมูลถูกย่อด้วย Partial Aggregate ก่อนส่ง จึงเหลือแค่ 7 กลุ่มจาก 8 Partition ไม่ใช่ 2 ล้านแถว ด้วยเหตุนี้ `groupBy` ที่ Aggregate ได้จึง Shuffle น้อยกว่า `distinct` หรือ `repartition` ซึ่งส่งทุกแถว
- Task ที่เหลือจาก 200 ตัวส่วนใหญ่ได้ข้อมูลว่างหรือน้อยมาก (7 Key กระจายไปแค่ไม่เกิน 7 Partition) ซึ่งเป็นเหตุผลที่ AQE เข้ามารวมให้ ดูใน[บทที่ 6](/spark/catalyst-aqe/#aqe-ทำสามอย่าง)

ส่วนงาน Narrow ล้วนอย่าง `range(8 partition).filter().select().collect()` ได้ **1 Stage 8 Task** ซึ่งตรงกับที่บทหลักบอกว่า Narrow ต่อกันกี่ตัวก็อยู่ใน Stage เดียว

</Step>

## Partition ที่เปลี่ยนไประหว่างทาง

| สถานการณ์ | จำนวน Partition |
|---|---|
| `spark.range(1_000_000)` (16 Core) | 16 (ตามจำนวน Core) |
| `groupBy(...)` ผลลัพธ์ ปิด AQE | **200** (`spark.sql.shuffle.partitions`) |
| `groupBy(...)` ผลลัพธ์ เปิด AQE (ข้อมูลเล็ก) | **1** (AQE รวม) |
| `coalesce(4)` | 4 |

และเมื่อเปิด AQE การเรียก `explain()` ก่อน Action จะขึ้นต้นด้วย `AdaptiveSparkPlan isFinalPlan=false` ซึ่งบอกว่าแผนยังเปลี่ยนได้ (อธิบายไว้ใน[บทที่ 6](/spark/catalyst-aqe/#เปิดอยู่แล้ว-adaptivesparkplan)) ตัวเลข 1 กับ 200 ข้างบนเป็นที่มาของคำถามที่หลายคนมักสงสัยว่า "ทำไม `explain` เห็น 200 แต่ UI เห็นน้อยกว่า" ซึ่งก็คือ AQE นั่นเอง

<Callout type="tip" title="ใช้ตัวเลขเหล่านี้ตอนไหน">
เวลาเจอ Job ช้า ให้เปิด Spark UI นับ Stage แล้วเทียบกับจำนวน Exchange ใน `explain()` ถ้า Stage มากกว่า Exchange + 1 เกินกว่าที่คาด อาจมี Job เสริม (เช่นการสุ่มของ `orderBy`) หรือ Stage ซ้ำจากการลองใหม่ จากนั้นดูไบต์ Shuffle ของ Stage ที่ใหญ่ที่สุด เพราะนั่นคือที่ที่ควรลดก่อน ([บทที่ 7](/spark/performance-tuning/#จูนคือการหาว่าเสียเวลาที่ไหน))
</Callout>
