## วัดอะไร ก่อนจะดูตัวเลข

คำว่า "Polars เร็ว" ลอยอยู่ทั่วไป ในบทนี้เราไม่ขอให้เชื่อ แต่วัดให้ดู และบอกก่อนว่าวัดอะไรบ้าง เพราะตัวเลขที่ไม่รู้ว่าวัดอะไรไม่มีประโยชน์ (รัน: `exercises/09_performance.py`)

ชุดข้อมูลคือออเดอร์สังเคราะห์ 5,000,000 แถว (ที่เราสร้างจาก Seed คงที่) คอมพิวเตอร์ที่วัดเป็น Windows ที่มี 16 Thread เวลาแต่ละค่าเป็นค่าต่ำสุดของการรันซ้ำสองถึงสามครั้ง เพราะค่าต่ำสุดถูกรบกวนด้วยงานอื่นของระบบน้อยที่สุด Assert ในแบบฝึกตั้งเป็นอัตราส่วนหลวม ๆ (เช่น Pandas ต้องช้ากว่า Polars เกิน 3 เท่า) ไม่ได้ตั้งเป็นเวลาตายตัว เพราะเวลาเปลี่ยนไปในแต่ละเครื่องและแต่ละรอบ ดังนั้นให้อ่านตัวเลขในบทนี้เป็น **ลำดับความต่าง** ไม่ใช่ค่าที่คุณจะได้บนเครื่องของคุณ

## group_by เทียบกับ Pandas

คำถามคือยอดขายรวมของแต่ละคู่ (สินค้า, ภาค) ซึ่งต้องคูณ `qty` กับ `price` ก่อนแล้วจึงรวม เราให้งานเท่ากันทั้งสองฝั่ง

```python
big.group_by("product", "region").agg((pl.col("qty") * pl.col("price")).sum().alias("t"))   # Polars
pdf.assign(t=pdf.qty * pdf.price).groupby(["product", "region"])["t"].sum()                  # pandas
```

```text
group_by: polars 34 ms, pandas 603 ms, ratio 18x
group_by: polars 38 ms, pandas 747 ms, ratio 20x
```

สองรอบที่รันได้ 18 และ 20 เท่า (ตอนที่เราลองเขียนแบบฝึกครั้งแรกได้ 24 เท่า) ตัวเลขเปลี่ยนตามรอบ แต่ระดับเดียวกันคือ **สิบกว่าเท่า** ผลของสองฝั่งตรงกันทุกค่า (Assert เทียบรายการผลรวมแล้วเท่ากัน) ข้อควรระวังคือการเทียบนี้เป็นกรณีเดียว (คูณแล้วรวมสองคีย์) บนข้อมูลที่ไม่มีค่าที่หายไปและมีคีย์ไม่กี่ค่า Pandas ที่ใช้ PyArrow Backend หรือกรณีอื่นอาจต่างออกไป เราไม่ได้วัด

</Step>

## ที่ได้เปรียบที่สุด: บอกว่าต้องการอะไรก่อนอ่านไฟล์

เราใช้ข้อมูลชุดเดียวกัน เขียนเป็นไฟล์ Parquet และ CSV แล้ววัดคำถามเดิม (ยอดรวมของ `qty` ต่อสินค้า เฉพาะภาค North) สองแบบ แบบแรกอ่านทั้งไฟล์เข้ามาแล้วค่อยกรองและเลือกคอลัมน์ แบบที่สองใช้ `scan` ให้ Optimizer ดันการกรองและการเลือกคอลัมน์ลงไปที่ตอนอ่าน ([บท 6](/polars/lazy/))

```text
parquet: read first 150 ms, scan 21 ms, ratio 7.2x
parquet: read first 134 ms, scan 18 ms, ratio 7.5x
csv:     read first 536 ms, scan 374 ms, ratio 1.4x
csv:     read first 450 ms, scan 406 ms, ratio 1.1x
```

Parquet ได้ประโยชน์ราว 7 เท่า เพราะอ่านเฉพาะคอลัมน์ที่ต้องใช้ได้จริง ไฟล์เก็บแยกตามคอลัมน์ ส่วน CSV ได้แค่ 1.1 ถึง 1.4 เท่า เพราะไฟล์เก็บทีละแถว ไม่ว่าเราจะต้องการคอลัมน์ไหน ก็ต้องอ่านและแยกวิเคราะห์ทุกตัวอักษรของทุกแถวอยู่ดี ก่อนจะรู้ว่าแถวไหนเป็น North ข้อสรุปที่ได้คือ Scan ให้ประโยชน์มากเมื่อรูปแบบไฟล์ช่วยให้ข้ามข้อมูลได้ (เรื่อง Row Group และสถิติ อยู่ใน [บท 7](/polars/io/))

</Step>

## จำนวน Thread

Polars แบ่งงานเป็นชิ้นแล้วใช้หลาย Thread พร้อมกัน เราจำกัดจำนวนด้วยตัวแปรสภาพแวดล้อม `POLARS_MAX_THREADS` แล้วรันงานเดียวกัน (`group_by("customer_id")` บน 5,000,000 แถว) ในโปรเซสใหม่ที่แยกกันสามครั้ง

```text
threads and seconds: {'1': (1, 0.2498), '4': (4, 0.103), 'default': (16, 0.0769)}
```

Thread เดียวใช้เวลา 0.25 วินาที สี่ Thread ใช้ 0.10 วินาที และค่าเริ่มต้น (16 Thread) ใช้ 0.077 วินาที จึงเร็วขึ้นราว 2.4 เท่าเมื่อไป 4 Thread และราว 3.2 เท่าเมื่อไป 16 Thread ไม่ได้เร็วขึ้น 16 เท่า เพราะบางส่วนของงานทำพร้อมกันไม่ได้ และมีงานรวมผลตอนท้าย เราไม่ได้ตรวจสอบว่าส่วนไหนใช้เวลาเท่าไร จึงได้แค่ผลที่เห็นว่าการเพิ่ม Thread ช่วยจริงแต่ไม่เป็นเส้นตรง

</Step>

## หน่วยความจำและสอง Engine

[บท 6](/polars/lazy/) บอกว่าค่าเริ่มต้นคือ Streaming Engine เราเลยลองวัดสิ่งที่คนมักคาดว่า Streaming ใช้หน่วยความจำน้อยกว่ามาก โดยรันคำถามเดียวกัน (อ่าน CSV 5 ล้านแถว แล้ว group_by สินค้า) แยกโปรเซสละ Engine และอ่านค่ายอดสูงสุดของหน่วยความจำที่โปรเซสใช้

```text
peak working set MB: import only 49, in-memory 438, streaming 400
```

ผลคือ In-memory ใช้ 438 MB และ Streaming ใช้ 400 MB ต่างกันเพียงเล็กน้อย (โปรเซสที่แค่ Import Polars ก็ใช้ 49 MB แล้ว) ด้วยข้อมูลขนาดนี้ ซึ่งเป็นแค่ CSV ราว 200 MB ผลสรุปจึงคือ **เรายังไม่ได้เห็นข้อได้เปรียบด้านหน่วยความจำของ Streaming ในตัวอย่างนี้** ข้อดีของมันน่าจะปรากฏเมื่อข้อมูลใหญ่กว่าหน่วยความจำ แต่เราไม่ได้วัดกรณีนั้น และไม่รับรองอะไรเกินที่วัด

ทั้งสอง Engine ให้คำตอบเดียวกัน (`equals` เป็นจริง) สิ่งที่เปลี่ยนคือวิธีรัน เราจะดูวิธีนั้นข้างในจริง ๆ ใน [บท 10](/polars/inside/)

<Callout type="warn" title="ตัวเลขไม่ใช่คำสัญญา">
ตัวเลขทั้งหมดในบทนี้มาจากคอมพิวเตอร์เครื่องเดียว ข้อมูลสังเคราะห์ และงานไม่กี่แบบ ถ้าจะตัดสินใจเรื่องจริง ให้วัดกับข้อมูลและงานของคุณเอง ด้วยโครงเดียวกับแบบฝึก 09 (รันซ้ำ เอาค่าต่ำสุด และเทียบผลลัพธ์ให้ตรงกันก่อนเทียบเวลา)
</Callout>

## ถ้ามันช้า ให้ดูตรงไหน

จากที่เราวัดและเห็นมาตลอดทั้งเส้นทางนี้ รายการที่น่าจะเป็นต้นเหตุของโค้ด Polars ที่ช้า เรียงตามที่ควรตรวจก่อน

**อย่างแรก** ดูว่าใช้ `map_elements` หรือวนลูปแถวด้วย Python อยู่หรือเปล่า ใน [บท 8](/polars/nested-strings/) เราวัดว่าช้ากว่า Expression ราว 6 เท่าแม้ในงานง่ายมาก **อย่างที่สอง** ดูว่าอ่านทั้งไฟล์ Parquet เข้ามาแล้วค่อยกรองหรือเปล่า เปลี่ยนเป็น `scan` ซึ่งในบทนี้ได้ราว 7 เท่า **อย่างที่สาม** ดูว่า Join แล้วแถวเพิ่มโดยไม่ตั้งใจหรือเปล่า ([บท 5](/polars/joins/)) เพราะข้อมูลที่ใหญ่ขึ้นเองทำให้ทุกอย่างหลังจากนั้นช้าลง **อย่างสุดท้าย** ถ้ามีเรื่องที่ตัวเลขด้านบนไม่ได้บอก ให้ดูแผนด้วย `explain()` ว่าอะไรถูกดันลงไปที่ Scan แล้วหรือยัง

</Step>
