## ระบบที่ Deploy ไปแล้ว เรามองเห็นมันอย่างไร

มาถึงตอนนี้ Commit ของเราผ่าน Pipeline กลายเป็น Image ถูกปล่อยด้วยวิธีที่ย้อนกลับได้ และมี Controller คอยดูแลให้ตรงกับ Git แต่ทั้งหมดนั้นไม่ได้บอกเราเลยว่าผู้ใช้จริงได้รับอะไรอยู่ [บทที่ 5](/devops/release/) ให้เห็นแล้วว่าบั๊กอาจโผล่เฉพาะคำขอจริงบางแบบ เราจึงต้องมองเห็นสิ่งที่เกิดขึ้นข้างใน

หนังสือ Fundamentals of DevOps and Software Delivery แบ่งสิ่งที่เรามองจากข้างนอกได้เป็นชนิดต่าง ๆ โดยเริ่มจาก Logs คือบันทึกว่าเกิดอะไรขึ้นในซอฟต์แวร์ ไม่ว่าจะเป็นเหตุการณ์สำคัญ ข้อผิดพลาด หรือข้อมูลสำหรับ Debug ใช้ได้ทั้ง Debug วิเคราะห์ และเป็นหลักฐานตรวจสอบย้อนหลัง (หนังสือ: Fundamentals of DevOps and Software Delivery บทที่ 10 หน้า 450) ส่วน Metrics คือการวัดเชิงปริมาณของสิ่งสำคัญในซอฟต์แวร์ ใช้ตรวจจับปัญหา เช่นค่า Latency ที่พุ่งขึ้นกะทันหันมักเป็นสัญญาณเตือนแรก (หนังสือ: เล่มเดิม หน้า 461)

ในแบบฝึกเราสร้างระบบเล็ก ๆ ที่มีสอง Service คือ Gateway ที่รับคำขอแล้วเรียก Inventory ต่อ ทั้งสองเขียน Log เป็นบรรทัด JSON หนึ่งบรรทัดต่อคำขอ นับจำนวนคำขอและเวลาตอบเป็น Metrics ที่เปิดอ่านได้ที่ `/metrics` และส่ง `trace id` ต่อกันตอน Gateway เรียก Inventory จากนั้นส่งคำขอ 60 ตัว เป็นคำขอปกติ 40 ตัว ตัวที่ช้า 15 ตัว (Inventory หน่วงไว้ 150 ms) และตัวที่ล้มเหลว 5 ตัว เรียงแบบสุ่มด้วย Seed คงที่ (รัน)

## Metrics: บอกว่ามีกี่ตัว แต่ไม่บอกว่าตัวไหน

หน้า `/metrics` ของ Gateway พิมพ์ข้อความอย่างนี้ ซึ่งเป็นรูปแบบข้อความที่ Prometheus อ่านได้ (รัน)

```text
# TYPE http_requests_total counter
http_requests_total{service="gateway",path="/order",status="200"} 55
http_requests_total{service="gateway",path="/order",status="500"} 5
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{service="gateway",path="/order",le="0.025"} 45
...
```

บรรทัดแรกคือ Counter คือตัวเลขที่นับขึ้นอย่างเดียว บอกว่ามีคำขอที่ตอบ 200 อยู่ 55 ตัว และ 500 อยู่ 5 ตัว ส่วนเวลาตอบเก็บเป็น Histogram ที่มี Bucket ซ้อนกันแบบสะสม (Cumulative) ตัวเลขใน `le="0.1"` คือจำนวนคำขอที่ตอบใน 0.1 วินาทีหรือน้อยกว่า และ Bucket สุดท้าย `+Inf` เท่ากับจำนวนทั้งหมดเสมอ (หนังสือ: Prometheus Up and Running บทที่ 3 หน้า 43 ถึง 55) ในแบบฝึก Bucket ที่ 0.025, 0.05 และ 0.1 ได้ 45 ทั้งสามตัว ส่วน 0.25 กับ `+Inf` ได้ 60 แปลว่าคำขอเร็วทั้ง 45 ตัวตอบทันใน 25 ms และอีก 15 ตัวตอบหลัง 100 ms

ทีนี้มีกับดักข้อหนึ่ง เวลาตอบเฉลี่ย (ผลรวมหารจำนวน) ของคำขอทั้งหมดคือราว 39 ms ซึ่งดูดีมาก ทั้งที่หนึ่งในสี่ของคำขอรอ 150 ms ถ้าอ่านเฉพาะค่าเฉลี่ยเราจะไม่เห็นความช้านั้น ส่วนเปอร์เซ็นไทล์ที่ 95 จาก Histogram อยู่ใน Bucket 0.25 ทันที (รัน) Histogram จึงบอกความช้าของส่วนท้ายได้ดีกว่าค่าเฉลี่ย

แต่ Metrics ตอบอีกอย่างไม่ได้ มันรู้ว่ามีคำขอที่พัง 5 ตัว แต่ไม่รู้ว่าเป็นตัวไหน เพราะมันเก็บแค่ผลรวม

</Step>

## Logs และ Trace ช่วยกันหาตัวที่พัง

เลือกมุมมองใน Lab ทีละอัน และเลือกคำขอที่จะตาม ดูว่าอะไรเปลี่ยนไปเมื่อสลับมุมมอง

<ThreeViewsLab client:visible />

มุมมอง Logs ตอบคำถามว่า "ตัวไหน" แต่ละ Service เขียนบรรทัด JSON ของตัวเอง มี `trace_id`, `span_id`, `status` และ `ms` ในแบบฝึก Log ของ Gateway ระบุคำขอที่ล้มเหลวได้พอดีห้าบรรทัด ซึ่งตรงกับตัวนับ 5 ใน Metrics (รัน)

มุมมอง Trace ตอบคำถามที่สามคือ "ล้มหรือช้าที่ Service ไหน" `trace id` ที่ Gateway สร้างถูกส่งต่อให้ Inventory ในหัวข้อ HTTP และ Inventory ระบุว่า Span แม่คือของ Gateway (รัน) ผลคือเราตามคำขอพังหนึ่งตัวข้ามสอง Service ได้ จะเห็นว่า Inventory ตอบ 500 เองก่อน (ใช้เวลา 0.0 ms) แล้ว Gateway รับต่อและตอบ 500 กลับไป จึงรู้ว่าต้นเหตุอยู่ที่ Inventory ไม่ใช่ Gateway เช่นเดียวกัน คำขอที่ช้าเสียเวลา 150.4 ms ใน Inventory จาก 152 ms ทั้งหมดของ Gateway (รัน) ตรงกับที่ Metrics บอกไว้ว่ามีคำขอช้า แต่ไม่ได้บอกว่าช้าที่ไหน

ทั้งสามอย่างจึงใช้ต่อกันเป็นลำดับ **ขั้นแรก** Metrics บอกว่ามีปัญหา (ตัวเลข 500 ขึ้น) **ขั้นต่อมา** Logs บอกว่าคำขอไหนบ้าง และ **ขั้นสุดท้าย** Trace บอกว่าปัญหาอยู่ที่ Service ไหน ผู้เขียนไม่ได้ลองเครื่องมือจริงอย่าง OpenTelemetry, Jaeger หรือ Loki ซึ่งทำสามอย่างนี้ในระบบใหญ่ แบบฝึกส่ง `trace id` เองด้วยหัวข้อ HTTP

</Step>

## Prometheus ตัวจริงเก็บตัวเลขเดียวกัน

หน้า `/metrics` ที่เขียนเองเป็นแค่ข้อความ Prometheus ตัวจริงคือโปรแกรมที่เข้ามาอ่านหน้านี้ซ้ำ ๆ เรียกว่า Scrape และเก็บค่าตามเวลา ในแบบฝึกเรารัน Prometheus (Image `prom/prometheus:v3.5.0` ใน Docker) ให้ Scrape ทั้งสอง Service ทุกวินาที แล้วถามด้วยภาษา Query ของมัน ผลที่ได้ตรงกับที่เรานับเอง (รัน)

```text
sum(http_requests_total{service="gateway",status="500"})   →  5
sum(http_requests_total{service="gateway"})                →  60
count(up == 1)                                             →  2
histogram_quantile(0.95, ...)                              →  มากกว่า 0.1 วินาที
```

ตัวเลขห้าที่ Prometheus บอกคือจำนวนเดียวกับที่ Log ระบุชื่อคำขอไว้ห้าตัว ซึ่งเป็นการตรวจว่าสองมุมมองนี้ไม่ขัดกัน และผล `count(up == 1)` ที่เท่ากับสองบอกว่ามัน Scrape ได้ทั้งสอง Service

<Callout type="note" title="ของที่ไม่ได้ลอง">
ไม่ได้รัน Grafana สำหรับทำ Dashboard, Alertmanager (เป็นเรื่องของ[บทที่ 9](/devops/slo/)), ระบบรวม Log อย่าง Loki หรือ Elasticsearch และ OpenTelemetry Collector ผู้เขียนสร้าง Metrics, Log และ Trace id ด้วยโค้ดสั้น ๆ เองเพื่อให้เห็นรูปแบบ ในระบบจริงมักใช้ไลบรารีอย่าง `prometheus_client` ที่ Prometheus Up and Running สอนไว้ (หนังสือ: Prometheus Up and Running [บทที่ 3](/devops/config-secrets/))
</Callout>
