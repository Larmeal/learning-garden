## บั๊กที่ Smoke Test มองไม่เห็น

เรามี Artifact ที่ผ่าน Pipeline และ Digest ที่รู้ว่าคือไบต์ไหน ([บทที่ 4](/devops/artifacts/)) เหลือคำถามสุดท้ายคือ จะเอามันขึ้น Production อย่างไรให้ถ้ามีปัญหา ผู้ใช้เจอน้อยที่สุด

ในแบบฝึกเรารัน Server HTTP จริงสองตัว ตัวแรกคือเวอร์ชัน 1 ที่ตอบปกติเสมอ ตัวที่สองคือเวอร์ชัน 2 ที่มีบั๊ก คือคำขอที่ใช้ Feature ตัวหนึ่ง (ในแบบฝึกสุ่มได้ 112 คำขอจากทั้งหมด 400 หรือราวหนึ่งในสี่) จะได้ผล 500 แต่คำขอธรรมดาตอบ 200 เหมือนเดิม (รัน)

```text
a plain request to version 2 works (this is all a smoke test sends)    ok
a request that uses the feature fails on version 2                    ok
the same request works on version 1                                   ok
```

Smoke Test คือการยิงคำของ่าย ๆ ครั้งสองครั้งหลัง Deploy เพื่อดูว่าระบบยังตอบ และ Health Check คือการที่ Load Balancer ถามเครื่องว่ายังรอดอยู่ไหม ทั้งสองอย่างจะผ่านกับเวอร์ชัน 2 เพราะมันตอบคำขอธรรมดาได้ บั๊กอย่างนี้จะโผล่เฉพาะกับคำขอจริงของผู้ใช้ ซึ่งแปลว่าเรามีตัวตรวจที่จะบอกได้ก็ต่อเมื่อผู้ใช้เจอปัญหาแล้วเท่านั้น คำถามจึงเป็นว่าจะให้ผู้ใช้เจอกี่คน

</Step>

## ห้าวิธี Release

หนังสือ Fundamentals of DevOps and Software Delivery แบ่งกลยุทธ์ออกเป็นสองกลุ่ม กลุ่มหลักคือวิธีที่ใช้ Deploy จริง ๆ ได้แก่ Downtime Deployment ที่ปิดระบบเพื่ออัปเดต, Rolling Deployment ที่ค่อย ๆ เพิ่มเวอร์ชันใหม่แล้วเอาเวอร์ชันเก่าออกเมื่อผ่าน Health Check และ Blue-green ที่ยกเวอร์ชันใหม่ (Green) ขึ้นให้พร้อมก่อน แล้วสลับทราฟฟิกจากเก่า (Blue) ไปใหม่ในพริบตา ส่วนกลุ่มเสริมใช้ร่วมกับกลุ่มหลักเพื่อให้ปลอดภัยขึ้น ได้แก่ Canary ที่ปล่อยเวอร์ชันใหม่ไปแค่หนึ่งเครื่องก่อนแล้วเทียบกับเวอร์ชันเก่า และ Feature Toggle ที่ห่อฟีเจอร์ใหม่ไว้หลังสวิตช์ซึ่งปิดอยู่ตอน Deploy (หนังสือ: Fundamentals of DevOps and Software Delivery บทที่ 5 หน้า 200 ถึง 205)

หนังสือเตือนว่า Blue-green ให้ประสบการณ์ของผู้ใช้ดีที่สุดสำหรับแอปที่ไม่เก็บสถานะ แต่ต้องใช้ Server เป็นสองเท่า ซึ่งไม่ใช่ทุกบริษัทจะรับไหว (หนังสือ: เล่มเดิม หน้า 203 ถึง 204) ในแบบฝึกเราจำลองห้าวิธีด้วยตัวเลือกง่าย ๆ ว่าคำขอข้อไหนไปเวอร์ชันไหน (ผู้เขียนไม่ได้ลองเครื่องมือจริงอย่าง Nginx, Argo Rollouts หรือ Istio)

| วิธี | คำขอไปเวอร์ชันใหม่อย่างไรในแบบฝึก |
|---|---|
| ทีเดียวทั้งหมด | ทุกคำขอตั้งแต่ที่ 100 |
| Blue-green | ทุกคำขอตั้งแต่ที่ 100 (สลับตัวชี้ ตัวเก่ายังเปิดอยู่) |
| Rolling | เปลี่ยนทีละเครื่องจากสี่เครื่อง ทุก 25 คำขอ คำขอแบบหมุนเวียนไปทีละเครื่อง |
| Canary | คำขอที่สุ่มเลือก 10% |
| Feature Flag | เวอร์ชันใหม่อยู่ทุกที่แล้ว แต่ Flag เปิดให้ 10% ของคำขอ |

ผู้ตัดสินในแบบฝึกดูที่คำขอที่ 200 ว่าคำขอที่ไปถึงเวอร์ชันใหม่ล้มเหลวเกิน 10% หรือไม่ ถ้าเกินก็ Rollback

</Step>

## กดดูว่าใครโดนบ้าง

เลือกวิธีแล้วกดเล่น ในสองแถวแต่ละขีดคือหนึ่งคำขอ แถวบนบอกว่าเวอร์ชันไหนตอบ แถวล่างบอกว่าสำเร็จหรือไม่ ให้ดูกว้างของแถบสีส้มในแถวล่าง และเปรียบเทียบสามวิธี คือทีเดียวทั้งหมด Rolling และ Canary

<ReleaseLab client:visible />

ผลที่ได้ในแบบฝึกคือ (รัน)

| วิธี | คำขอที่ไปเวอร์ชันใหม่ | คำขอที่พัง |
|---|---|---|
| ทีเดียวทั้งหมด | 100 | 32 |
| Blue-green | 100 | 32 |
| Rolling | 64 | 18 |
| Canary 10% | 11 | 3 |
| Feature Flag 10% | 11 | 3 |

ความเสียหายขึ้นกับสองอย่างคูณกัน คือคำขอกี่ส่วนไปถึงเวอร์ชันใหม่ กับนานแค่ไหนกว่าจะ Rollback ทีเดียวทั้งหมดกับ Blue-green เสียหายเท่ากันทุกประการ (32 คำขอ ตรงกับ 100 คำขอที่ไปเวอร์ชันใหม่) เพราะผู้ใช้เห็นสิ่งเดียวกันในช่วง 100 คำขอนั้น ความต่างของ Blue-green อยู่ที่ว่ามันย้อนกลับได้เร็วมาก ไม่ได้อยู่ที่จำนวนผู้ใช้ที่โดน

มีข้อสังเกตอีกสองข้อ **ข้อแรก** Canary ที่ได้คำขอไปเวอร์ชันใหม่แค่ 11 คำขอ ได้อัตรา Error 27% ซึ่งผู้ตัดสินเห็นว่าเกินเกณฑ์ แต่ตัวอย่างขนาดนี้เล็กจนตัวเลขเปลี่ยนได้มาก ถ้า Canary ได้คำขอแค่สอง ผลก็ตัดสินไม่ได้ ในระบบจริงจึงต้องมีคำขอมากพอก่อนจะเชื่อตัวเลข **ข้อสอง** Rolling ที่เราคิดว่าปลอดภัยเพราะเปลี่ยนทีละเครื่อง ไม่หยุดเองเลย เพราะแต่ละเครื่องใหม่ผ่าน Health Check (แบบฝึกตรวจว่าคำขอธรรมดาไปเวอร์ชัน 2 ได้ผล 200) คนหรือ Metric ที่วัดจากผู้ใช้จริงต้องเป็นฝ่ายสั่งหยุด

</Step>

## ถ้าจะย้อนกลับ ต้องทำอะไร

ตารางสุดท้ายเทียบสิ่งที่แต่ละวิธีต้องใช้ตอน Rollback (ข้อมูลจากแบบฝึกคือไม่มีคำขอพังหลัง Rollback ในทุกวิธี ส่วนคอลัมน์ความเร็วเป็นสิ่งที่ผู้เขียนสรุปจากกลไก ไม่ได้จับเวลา)

| วิธี | Rollback คือ | สิ่งที่ต้องมีไว้ |
|---|---|---|
| ทีเดียวทั้งหมด | Deploy เวอร์ชัน 1 ลงไปอีกรอบ | Artifact เก่า ([บทที่ 4](/devops/artifacts/) เก็บไว้ให้แล้ว) |
| Blue-green | สลับตัวชี้กลับ | Server ของเวอร์ชันเก่ายังเปิดอยู่ (ค่าใช้จ่ายสองเท่า) |
| Rolling | ย้อน Instance ที่เปลี่ยนไปแล้วกลับทีละตัว | เวลาและ Artifact เก่า |
| Canary | ตั้งสัดส่วนของเวอร์ชันใหม่เป็น 0% | ตัวแยกทราฟฟิกที่ปรับสัดส่วนได้ |
| Feature Flag | ปิด Flag | บริการ Flag ที่เปลี่ยนค่าได้ทันที ไม่ต้อง Deploy |

เมื่อลองเรียงตามความเสียหายและตามความเร็วของการย้อนกลับ จะเห็นว่า Feature Flag ดีทั้งสองด้านในตัวอย่างนี้ แต่มันมีราคาที่ตัวเลขข้างบนไม่เห็น โค้ดของทั้งสองเวอร์ชันต้องอยู่ในไบนารีเดียว และ Flag ที่ลืมเก็บกวาดจะกลายเป็นโค้ดค้าง ซึ่งหนังสือก็พูดถึง Feature Toggle ใน[บทที่ 5](/devops/release/) ในฐานะเทคนิคที่ใช้ได้ทั้งตอน Merge โค้ดใหญ่เข้า `main` และตอน Deploy (หนังสือ: เล่มเดิม หน้า 205)

</Callout>
