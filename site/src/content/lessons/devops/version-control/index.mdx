## สถานีอวกาศที่ประกอบกันตอนสุดท้าย

หนังสือ Fundamentals of DevOps and Software Delivery เปิดเรื่องนี้ด้วยภาพสถานีอวกาศนานาชาติ สมมติว่าเรารับผิดชอบสร้างสถานีที่มีหลายสิบชิ้นส่วน และต้องให้ทีมจากหลายประเทศแยกกันทำคนละชิ้น วิธีแรกคือออกแบบทุกชิ้นให้เสร็จก่อน แล้วให้แต่ละทีมไปทำชิ้นของตัวเองจนเสร็จโดยไม่คุยกัน พอเสร็จครบค่อยปล่อยทุกชิ้นขึ้นอวกาศแล้วต่อกัน ส่วนวิธีที่สองคือให้แต่ละทีมทดสอบชิ้นของตัวเองกับชิ้นของทีมอื่นเป็นระยะ ๆ แล้วปล่อยขึ้นไปทีละชิ้น (หนังสือ: Fundamentals of DevOps and Software Delivery บทที่ 5 หน้า 177)

วิธีแรกฟังดูตลก แต่หนังสือบอกว่านั่นคือวิธีที่หลายบริษัทเขียนซอฟต์แวร์จริง ๆ Developer ทำงานบน Feature Branch ที่อยู่ยาวเป็นสัปดาห์หรือเป็นเดือน แล้วค่อยเอาทุกสาขามารวมกันตอนใกล้ Release ซึ่งเรียกว่า Late Integration และมักลงเอยด้วยการนั่งแก้ Merge Conflict กันหลายสัปดาห์ (หนังสือ: เล่มเดิม หน้า 177)

เรามาลองพิสูจน์กันดูว่ามันเจ็บอย่างไรกันแน่ ในแบบฝึกของบทนี้เราสร้างโปรเจกต์เล็ก ๆ ที่มีไฟล์ `shop.py` กับฟังก์ชัน `price(item)` แล้วให้คนสองคนทำงานบนสาขายาวห้า Commit คนละสาขา Alice เปลี่ยนชื่อ `price` เป็น `unit_price` ที่ Commit ที่สองของเธอ ส่วน Bob เขียนไฟล์ใหม่ `invoice.py` ที่เรียก `price` (ซึ่งยังเป็นชื่อเดิมบนสาขาของเขา) แล้ว Test ของแต่ละสาขาผ่านหมดเมื่ออยู่ลำพัง (รัน)

</Step>

## Git บอกว่ารวมได้ แต่ Test พัง

พอรวมสาขาของ Bob เข้ากับ `main` ที่มีงานของ Alice อยู่แล้ว Git ตอบกลับมาเรียบร้อยดี (รัน)

```bash
git merge bob
```

```text
Merge made by the 'ort' strategy.
 invoice.py      | 11 +++++++++++
 test_invoice.py |  7 +++++++
 2 files changed, 18 insertions(+)
 create mode 100644 invoice.py
 create mode 100644 test_invoice.py
```

บรรทัดแรกบอกว่า Git รวมให้ด้วยกลยุทธ์ `ort` ซึ่งเป็นกลยุทธ์ปกติ และไม่มีคำว่า CONFLICT เลย สาเหตุคือ Alice แก้ `shop.py` ส่วน Bob เพิ่มไฟล์ใหม่ คนละไฟล์กัน Git ไม่มีทางรู้ว่าไฟล์ใหม่ของ Bob ไปเรียกชื่อที่ Alice เพิ่งลบ ลองรัน Test ดูจะเห็นว่า

```bash
python -m unittest discover -q
```

```text
ImportError: cannot import name 'price' from 'shop'
```

ตรงนี้อยากให้ตั้งคำถามในใจกันหน่อยว่า Commit ไหนเป็นตัวที่ทำให้พัง Commit ของ Alice ก็ผ่าน Test ของมัน Commit ของ Bob ก็ผ่าน Test ของมันเหมือนกัน ลองให้ `git bisect` ช่วยหา ซึ่งเป็นเครื่องมือที่ใช้ค้นหาแบบแบ่งครึ่งว่า Commit ไหนเป็น Commit แรกที่ Test เริ่มล้มเหลว (ดูรายละเอียดของมันที่ [บทที่ 10 ของ Git](/git/finding-commits/#ให้สคริปต์ตอบแทนเรา))

```bash
git bisect start HEAD <commit แรก>
git bisect run sh -c "python -m unittest discover -q"
```

```text
Bisecting: 2 revisions left to test after this (roughly 2 steps)
Bisecting: 0 revisions left to test after this (roughly 1 step)
8439bfd8a0c762af2cb9869b1da5a43f7fa5675a is the first 'bad' commit
Merge: e5340ec 66f431d
    Merge branch 'bob'
```

Bisect รัน Test สามรอบแล้วชี้ไปที่ Commit Merge เอง ซึ่งแปลว่าไม่มี Commit ฟีเจอร์ตัวไหนผิด ความผิดเกิดตอนสองงานที่ถูกต้องมาเจอกัน และเราต้องสงสัยทั้งหมด 11 Commit คือสิบ Commit ของสองคนกับ Commit Merge (รัน)

</Step>

## เทียบกับการรวมทีละน้อย

ทีนี้ลองเล่าเรื่องเดียวกันใหม่ ในแบบที่ทั้งสองคน Push ลง `main` บ่อย ๆ และรัน Test ก่อน Push ทุกครั้ง กดดูทีละขั้นใน Lab แล้วเทียบสองแถว แถวบนคือเรื่องเมื่อกี้ ส่วนแถวล่างคือวิธีใหม่ ในแต่ละขั้นให้ดูว่าวงกลมสีเขียวหรือสีแดง และมีกี่วงที่ถูกระบายว่า "ต้องสงสัย"

<BatchLab client:visible />

สังเกตขั้นสุดท้าย แถวล่าง Bob เจอ Test แดงตอนที่เขามี Commit ที่ยังไม่ได้ Push อยู่แค่สองอัน เขารู้ทันทีว่าปัญหามาจากชื่อ `price` ที่ Alice เพิ่ง Push ไป เพราะ Commit เดียวที่เปลี่ยนมาตั้งแต่ครั้งที่แล้วคือของเธอ และเขาแก้ได้ด้วยอีกหนึ่ง Commit (รัน) เรื่องที่เกิดขึ้นเหมือนกันทุกอย่าง ต่างกันแค่ว่าเราปล่อยให้ Change เก็บสะสมนานแค่ไหนก่อนจะรวมกัน

</Step>

## Trunk-based Development

วิธีทำงานของแถวล่างมีชื่อเรียกว่า Trunk-based Development หนังสืออธิบายว่าทุกคนทำงานบน Branch เดียวกันที่ปกติชื่อ `main` โดยใช้ Branch อายุสั้น ซึ่งยืนอยู่ตั้งแต่ไม่กี่ชั่วโมงถึงไม่กี่วัน แล้วเปิด Pull Request เพื่อรวมกลับเข้า `main` เป็นประจำ (หนังสือ: เล่มเดิม หน้า 178) หนังสือยกตัวอย่างว่า LinkedIn ย้ายจาก Feature Branch ไปทำแบบนี้ ซึ่งจำเป็นต่อการขยายบริษัทจากราว 100 คนเป็นกว่า 1,000 คน ส่วน Google ใช้วิธีนี้กับ Developer หลายหมื่นคน (หนังสือ: เล่มเดิม หน้า 178)

คำถามที่คนมักถามก่อนเป็นอย่างแรกคือ ทำงานบน Branch เดียวกันแบบนี้ Merge Conflict ต้องเกิดตลอดเวลาแน่ ๆ ใช่ไหม หนังสือตอบว่า Merge Conflict ที่เจ็บปวดเกิดเพราะ Branch อยู่ยาวต่างหาก ถ้า Branch สั้นโอกาสที่ไฟล์จะทับกันก็ต่ำ ตัวอย่างในหนังสือคือ Repository ที่มีไฟล์หมื่นไฟล์ ผ่านไปวันเดียวแต่ละคนแก้ราว 10 ไฟล์ โอกาสที่ 20 ไฟล์นั้นจะทับกันมีน้อยมาก แต่ถ้าทำงานแยกกันสามเดือนแล้วแก้คนละ 500 ไฟล์ โอกาสทับกันสูงขึ้นมาก (หนังสือ: เล่มเดิม หน้า 178 ถึง 179) ที่สำคัญกว่านั้น Conflict เล็ก ๆ ของ Branch ที่อายุแค่หนึ่งวันยังแก้ง่าย เพราะโค้ดยังสดอยู่ในหัวเรา

แต่ตัวอย่างของเราสอนอีกอย่างหนึ่งที่ลึกกว่านั้น คือต่อให้ไม่มี Conflict เลย Test ก็ยังพังได้ เพราะงานสองชิ้นที่ถูกต้องคนละไฟล์อาจเข้ากันไม่ได้ นี่คือเหตุผลที่ Trunk-based ต้องมี Test อัตโนมัติรันก่อนทุกครั้งที่รวม ซึ่งเป็นเรื่องของ[บทที่ 2](/devops/ci/)

<Callout type="note" title="Pull Request ของจริงไม่ได้ลอง">
บทนี้รันกับ Git จริงในคอมพิวเตอร์เครื่องเดียว Repository ปลายทางเป็นโฟลเดอร์ ไม่ใช่เว็บ Hosting จึงไม่ได้ลองหน้า Pull Request, การ Review และ Branch Protection ซึ่ง[บทที่ 7 ของ Git](/git/team-workflow/)เล่าไว้แล้ว
</Callout>

</Step>

## ทำอย่างไรในการทำงานจริง

ในแบบฝึก Bob ทำสามอย่างก่อนทุกครั้งที่ Push ซึ่งเป็นเรื่องที่ทีมส่วนใหญ่ตกลงกันเป็นธรรมเนียม **อย่างแรก** เขาดึงงานล่าสุดมาวางงานของตัวเองต่อท้าย ด้วย `git pull --rebase origin main` ซึ่งทำให้ประวัติเป็นเส้นตรง (ดู Rebase ที่[บทที่ 5 ของ Git](/git/rebase/)) **อย่างที่สอง** เขารัน Test ทั้งชุดบนผลที่รวมแล้ว ไม่ใช่บนโค้ดเดิมของเขา เพราะจุดที่พังคือผลของการรวม และ **อย่างสุดท้าย** เขาจึงค่อย `git push` ถ้า Test ไม่ผ่านเขาแก้ในเครื่องก่อนแล้ว Commit เล็ก ๆ เพิ่ม

Commit ที่ผ่านขั้นตอนนี้แล้วจะเล็กและตรวจง่าย แต่ทุกอย่างพึ่งความเข้มงวดของคนทำ เรามีเครื่องมือที่ทำแทนได้ นั่นคือ Server ที่รัน Test ให้ทุก Push ซึ่งเป็นหัวข้อของ[บทถัดไป](/devops/ci/)
