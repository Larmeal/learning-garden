## สี่ตัวเลขที่ทีมนับได้จากประวัติที่มีอยู่แล้ว

ใน[บทที่ 0](/devops/overview/) เราเห็นตาราง DORA ที่บอกว่าทีมระดับ Elite ต่างจากทีมระดับต่ำเป็นร้อยเท่า ทีนี้คำถามคือทีมของเราอยู่ตรงไหน หนังสือ Fundamentals of DevOps and Software Delivery แนะนำว่าถ้ามีทรัพยากรวัดตัวชี้วัดของทีมได้เพียงไม่กี่ตัว ให้เริ่มจากตัวชี้วัด DORA สี่ตัว คือความถี่ในการ Deploy (Deployment Frequency) Lead Time อัตรา Deploy ที่ล้ม (change failure rate) และเวลากู้คืน (Recovery Time) เพราะถ้าปรับปรุงสี่ตัวนี้ได้ ก็เร่งกระบวนการพัฒนาซอฟต์แวร์ได้มาก (หนังสือ: Fundamentals of DevOps and Software Delivery บทที่ 10 หน้า 466)

ข่าวดีคือเราไม่ต้องซื้อเครื่องมือเพื่อเริ่มนับ ข้อมูลที่ต้องใช้มีอยู่ใน Git อยู่แล้ว ถ้าเราจด Deploy เป็น Tag แบบที่เราทำมาตั้งแต่[บทที่ 10](/devops/incidents/) ในแบบฝึกเราสร้าง Git Repository จริงสองที่ ที่มีการ Commit กับ Tag ที่กำหนดวันที่ไว้ แปดสัปดาห์ ทีมแรกชื่อ Batch Release ทุกสองสัปดาห์ ทีมที่สองชื่อ Flow Release ราววันละสองครั้ง (วันทำงานเท่านั้น) ทั้งสองทีมมี Commit เท่ากัน วันละหกอัน และแต่ละ Tag บอกในข้อความว่า Deploy นั้นล้มหรือไม่ และถ้าล้มกู้คืนเมื่อไร

ตัวอ่านของแบบฝึกทำตามที่เครื่องมือจริงทำ (รัน)

| ตัวชี้วัด | อ่านจากอะไร |
|---|---|
| ความถี่ในการ Deploy | นับ Tag แล้วหารด้วยจำนวนสัปดาห์ |
| Lead Time | วันที่ของ Tag ลบวันที่ของแต่ละ Commit ที่ Tag นั้นเอาออก (`git log tagก่อน..tagนี้`) แล้วหาค่ากลาง |
| อัตรา Deploy ที่ล้ม | Tag ที่ข้อความขึ้นต้นด้วย `failed` หารด้วยจำนวน Tag ทั้งหมด |
| เวลากู้คืน | เวลาที่จดในข้อความของ Tag ลบเวลาของ Tag นั้น แล้วเฉลี่ย |

## เปรียบสองทีมบนข้อมูลเดียวกัน

เลือกตัวชี้วัดใน Lab แล้วดูสองแถบ แต่ละจุดคือหนึ่งการ Deploy จุดสีส้มที่มีกากบาทคือ Deploy ที่ล้ม ส่วนกล่องใต้แถบบอกตัวเลขของตัวชี้วัดที่เลือก

<DoraLab client:visible />

ผลที่แบบฝึกอ่านได้ (รัน)

| | ทีม Batch | ทีม Flow |
|---|---|---|
| ความถี่ในการ Deploy | 3 ครั้ง (0.4 ต่อสัปดาห์) | 80 ครั้ง (10 ต่อสัปดาห์) |
| Lead Time (ค่ากลาง) | 200 ชั่วโมง (ประมาณ 8 วัน) | 10 ชั่วโมง |
| อัตรา Deploy ที่ล้ม | 33% (1 จาก 3) | 10% (8 จาก 80) |
| เวลากู้คืนเฉลี่ย | 305 นาที | 10 นาที |

ตัวเลขของทีม Batch ตรงกับสิ่งที่เราเห็นใน Lab ของ[บทที่ 0](/devops/overview/) ว่าการ Release ห่างทำให้ Change รอนาน และรอบละมี Commit มาก (60 Commit ต่อรอบ เทียบกับ 3 ของ Flow) แต่ต้องระวังว่าตัวเลขเหล่านี้มาจากการที่เราเลือกค่าเอง ในแบบฝึก Release ที่ล้มคือครั้งที่สามของ Batch และทุกครั้งที่สิบของ Flow ส่วนเวลากู้คืนก็ตั้งไว้ราว 300 นาทีกับ 20 นาที

ตรงนี้อยากให้แยกสองเรื่องให้ชัดนะ เรื่องแรกที่แบบฝึกยืนยันได้คือ **การคำนวณถูก** เช่น ทีม Batch Deploy สามครั้งในแปดสัปดาห์ และ Lead Time ของทีม Flow ต่ำกว่าหนึ่งวัน (ค่ากลาง 10 ชั่วโมงเพราะ Commit ที่ทำตอนเย็นต้องรอรอบเช้าวันถัดไป) ส่วนเรื่องที่สอง **ว่าทีม Batch เล็กล้มน้อยกว่าจริงหรือไม่** แบบฝึกไม่ได้พิสูจน์ เพราะเราเป็นคนตั้งอัตราการล้มเอง ข้อเรียกร้องนี้เป็นของหนังสือ ซึ่งอ้างรายงานว่าทีมระดับ Elite Deploy บ่อยกว่า 182 เท่า มี Lead Time สั้นกว่า 127 เท่า และมีอัตราล้มต่ำกว่า 8 เท่า (หนังสือ: เล่มเดิม คำนำ หน้า xv) ผู้เขียนไม่ได้ตรวจกับรายงานต้นฉบับ

<Callout type="note" title="ตัวชี้วัดที่ใช้ผิดวิธีกลายเป็นเป้าหมายที่บิดเบือน">
ตัวชี้วัดทั้งสี่ควรใช้ดูแนวโน้มของทีมเอง ไม่ใช่เอามาจัดอันดับทีมหรือผูกกับโบนัส เพราะเมื่อตัวเลขกลายเป็นเป้า คนก็หาทางทำให้ตัวเลขดีโดยไม่ได้ทำให้ส่งมอบดีขึ้น เช่นแตก Deploy เป็นชิ้นเล็กไร้ความหมายเพื่อเพิ่มความถี่ ข้อนี้เป็นความเห็นของผู้เขียน ไม่ได้มาจากหนังสือเล่มไหน

## เมื่อทีมโตขึ้น คำตอบมักเป็น Platform ภายใน

บทเรียนทั้งสิบสองบทที่ผ่านมามีของให้ต้องทำมาก ทั้ง Pipeline, Registry, IaC, Controller, Observability, SLO, ด่านความปลอดภัย ถ้าทีมแอปทุกทีมต้องตั้งเองทั้งหมด จะเสียเวลาเกินไป หนังสือ Fundamentals of DevOps and Software Delivery สังเกตว่าบริษัทแทบทุกแห่งที่ทำงานด้วยลงเอยด้วยการสร้างแพลตฟอร์มภายใน (Internal Developer Platform หรือ IDP) คือชุดของ Workflow เครื่องมือ และหน้าจอที่ปรับให้เข้ากับบริษัท มักวางซ้อนอยู่บนเครื่องมือเดิม จนนักพัฒนาแทบไม่แตะ Cloud หรือ Kubernetes ตรง ๆ แต่ผ่านชั้นนี้แทน (หนังสือ: เล่มเดิม บทที่ 11 หน้า 501)

หนังสือบอกด้วยว่า Platform Engineering คือชื่อของศาสตร์การสร้าง IDP ซึ่งบางคนเสนอว่าเป็นผู้สืบทอดของ DevOps แต่ความจริงคือบริษัทสร้าง IDP กันมาหลายสิบปี ก่อนจะมีคำว่า DevOps ด้วยซ้ำ สิ่งใหม่คือมีเครื่องมือโอเพนซอร์สและเชิงพาณิชย์ที่ใช้ซ้ำได้ เช่น Backstage, Humanitec และ OpsLevel (หนังสือ: เล่มเดิม หน้า 501) IDP ในอุดมคติควรให้นักพัฒนาสร้างและจัดการแอปกับทุกอย่างที่แอปต้องการได้ในที่เดียว ซึ่งก็คือเกือบทุกอย่างที่เส้นทางนี้ไล่มา เช่น Hosting, IaC, Orchestration และ Version-Build-Test (หนังสือ: เล่มเดิม หน้า 501 ถึง 502)

ผู้เขียนไม่ได้ลองเครื่องมือ IDP ใด ๆ ที่หนังสือยกตัวอย่าง สิ่งที่บทนี้บอกได้แค่ว่า Pipeline ที่เราต่อกันใน[บทที่ 13](/devops/capstone/) ก็คือแกนกลางของ IDP ตัวเล็ก ๆ ที่ทำงานได้จริง และสิ่งที่ต้องคิดต่อคือใครจะดูแลมัน
