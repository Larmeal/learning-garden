## เหตุการณ์หนึ่งครั้ง เก็บร่องรอยได้จากสามที่

ใน[บทที่ 9](/devops/slo/) เราเห็นว่ากฎ Burn Rate เตือนครั้งเดียวสี่นาทีหลัง Deploy ที่พัง บทนี้ตามเหตุการณ์เดียวกันต่อ ตั้งแต่ Deploy จนถึงรายงานหลังเหตุการณ์ โดยเก็บร่องรอยจากสามที่ที่เรามีอยู่แล้ว

**ที่แรก** คือ Git การ Deploy และ Rollback เป็น Tag แบบมีวันที่ ในแบบฝึกเราสร้าง Repository ที่มี Tag `v1.0` (สามวันก่อน), `v1.1` ที่ 14:00 ของวันที่ 12 และ `v1.1.1` ที่ 14:19 ซึ่งเป็น Commit ที่ `git revert` Commit ของ v1.1 อ่านกลับมาด้วย `git for-each-ref --sort=creatordate` ได้ผลตรงกับที่ตั้ง (รัน)

```text
v1.0   2026-01-09T14:00:00Z
v1.1   2026-01-12T14:00:00Z
v1.1.1 2026-01-12T14:19:00Z
```

**ที่ที่สอง** คือข้อมูลการวัด ซึ่งก็คือกฎ Burn Rate จาก[บทที่ 9](/devops/slo/) ที่เตือนตอนนาทีที่ 4 หลัง Deploy และ **ที่ที่สาม** คือสิ่งที่คนทำ ซึ่งไม่มีเครื่องมือไหนบันทึกให้เอง ในแบบฝึกเราตั้งข้อสมมติว่าคนที่เข้าเวรใช้เวลา 5 นาทีนับจากกระดิ่งเพื่อรับเรื่องและเปิด Dashboard และอีก 10 นาทีเพื่อตัดสินใจและเริ่ม Rollback ตัวเลขสองตัวนี้ผู้เขียนตั้งเอง ไม่ได้วัดจากทีมจริง แล้วนำทั้งหมดมาเรียงเป็นรายการเหตุการณ์ได้ (รัน)

| เวลา | เหตุการณ์ | มาจาก |
|---|---|---|
| 14:00 | Deploy เวอร์ชัน 1.1 | Tag v1.1 |
| 14:04 | กฎ Burn Rate เตือน | ข้อมูลการวัด |
| 14:09 | คนเข้าเวรรับเรื่อง | ข้อสมมติ (5 นาที) |
| 14:19 | Tag v1.1.1 และ Pipeline Deploy | Tag v1.1.1 (ข้อสมมติ 10 นาที) |
| 14:21 | อัตรา Error กลับมาปกติ | ข้อมูลการวัด |

## ตัวเลขสามตัวที่ใช้วัดเหตุการณ์

จากตารางข้างบนคำนวณได้สามเวลา เวลาตรวจจับ (Time to Detect) คือเวลาจาก Deploy ถึงกระดิ่ง 4 นาที เวลารับเรื่อง (Time to Acknowledge) คือจากกระดิ่งถึงคนรับ 5 นาที และเวลากลับมาปกติ (Time to Mitigate หรือ Recover) จาก Deploy ถึงอัตรา Error ปกติ 21 นาที (รัน)

เรามาลองเปรียบเทียบสามวิธีทำงานบนบั๊กเดียวกัน กดเลือกใน Lab แล้วดูแถบสีส้ม ซึ่งคือช่วงเวลาที่คำขอยังล้ม และแท่งด้านล่างที่บอกว่าเหตุการณ์กินงบของเดือนไปเท่าไร

<IncidentLab client:visible />

ผลของสามวิธีในแบบฝึก (รัน) วิธีแรกไม่มีกฎเตือน ต้องรอลูกค้าเขียนมาแจ้งในนาทีที่ 35 แล้ว Rollback อีก 10 นาที กลับมาปกติที่นาทีที่ 45 กินงบของเดือน 34% วิธีที่สองคือมีกระดิ่งและ Rollback ด้วยมือ กลับมาปกติที่นาทีที่ 21 กินงบ 16% และวิธีที่สามคือมีกระดิ่งกับ Rollback คำสั่งเดียว (ซึ่งตรงกับ `git revert` ผ่าน Pipeline ที่เราเห็นใน[บทที่ 7](/devops/gitops/)) ใช้เวลา 3 นาทีหลังรับเรื่อง กลับมาปกติที่นาทีที่ 12 กินงบ 9% บั๊กเดียวกันแต่ความเสียหายต่างกันเกือบสี่เท่า ตัวเลขชี้ให้เห็นสองอย่างที่ทำให้ต่าง คือรู้ปัญหาเร็วแค่ไหน และทางย้อนกลับสั้นแค่ไหน

</Step>

## Postmortem ที่ไม่ตามหาคนผิด

หลังเหตุการณ์จบ ทีมควรนั่งดูมันกัน The DevOps Handbook เรียกวิธีนี้ว่า Blameless Post-mortem ซึ่งเป็นแนวทางสร้างวัฒนธรรมแบบ Just Culture เหตุผลที่หนังสือให้ไว้คือ ถ้าเราลงโทษวิศวกรที่ทำพลาด ทุกคนจะไม่อยากเล่ารายละเอียดที่จำเป็นต่อการเข้าใจว่าความล้มเหลวเกิดอย่างไร ซึ่งรับประกันว่ามันจะเกิดอีก แต่ถ้าวิศวกรไม่ถูกลงโทษ เขาจะเต็มใจและกระตือรือร้นช่วยให้ทั้งบริษัทเลี่ยงความผิดพลาดเดียวกัน นั่นคือสิ่งที่สร้างการเรียนรู้ขององค์กร (หนังสือ: The DevOps Handbook บทที่ 19)

ในแบบฝึกเราสร้างรายงานจากรายการเหตุการณ์ด้านบนด้วยโค้ด โดยมีหัวข้อ Summary, Impact, Timeline, What went well, What went wrong และ Action Items และเขียนให้ตรวจได้ว่าไม่มีชื่อคน (รัน)

```markdown
# Postmortem: failed requests after release 1.1

## Summary
Release 1.1 (`add coupon search`) made about 20 percent of requests fail
from 14:00 until the rollback was live at 14:21.

## Impact
16% of the 30 day error budget of an SLO of 99.9 percent.

## Timeline (UTC)
- 14:00 deploy: version 1.1 is released (tag v1.1)
- 14:04 page: the burn rate alert fires
...
## Action items
- Add a test for requests with a coupon (owner: the team that owns search).
- Release search changes to 10 percent of the traffic first (lesson 5).
```

สังเกตสองอย่าง **อย่างแรก** ตัวเลขใน Impact มาจากข้อมูลจริงของเหตุการณ์ (16%) ไม่ได้เขียนด้วยความรู้สึก และ **อย่างที่สอง** ไม่มีชื่อคนอยู่เลย (แบบฝึกตรวจว่าชื่อผู้เขียน Commit ไม่ปรากฏในรายงาน) Action Items มีเจ้าของเป็นทีม ไม่ใช่คนผิด และชี้กลับไปที่ช่องโหว่ของระบบ คือไม่มี Test ที่ครอบคลุมคำขอที่ใช้คูปอง และเปลี่ยนที่ Release ไปทีเดียวทั้งหมด ซึ่งตรงกับที่[บทที่ 5](/devops/release/) เสนอ (Canary หรือ Flag)

<Callout type="note" title="ส่วนที่ไม่ได้ลอง">
แบบฝึกสร้าง Postmortem จากข้อมูลได้ แต่ไม่ได้ทดลองการประชุมจริง การเข้าเวร (On-call) การสลับเวร หรือเครื่องมือจัดการ Incident อย่าง PagerDuty ผู้เขียนยังไม่ได้ตรวจว่าหัวข้อที่เลือกตรงกับแม่แบบใดโดยเฉพาะ The DevOps Handbook ไม่ได้ให้แม่แบบรายหัวข้อให้ตรวจเทียบ
</Callout>
