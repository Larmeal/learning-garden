## ทำไมต้องเขียนโครงสร้างพื้นฐานเป็นโค้ด

จนถึงตอนนี้เราไม่ได้พูดถึงว่า Server, Network, ฐานข้อมูลที่ Artifact ของเรารันอยู่ ถูกสร้างขึ้นมาอย่างไร ถ้าคนคลิกสร้างในหน้าเว็บของ Cloud ทุกครั้ง เราจะมีปัญหาเดิมกับที่เจอใน[บทที่ 0](/devops/overview/) คือคิวรอคนว่างและขั้นตอนที่ทำด้วยมือซ้ำ ๆ

หนังสือ Fundamentals of DevOps and Software Delivery ให้เหตุผลที่ควรเขียนโครงสร้างพื้นฐานเป็นโค้ด (Infrastructure as Code หรือ IaC) ไว้หลายข้อ **ข้อแรก** คือความเร็วและความปลอดภัย เพราะคอมพิวเตอร์ทำขั้นตอน Deploy ได้เร็วกว่าและผิดพลาดน้อยกว่าคน **ข้อที่สอง** คือเป็นเอกสาร เพราะสภาพของระบบอยู่ในไฟล์ที่ทุกคนอ่านได้ ไม่ได้อยู่ในหัวของใครคนใดคนหนึ่ง และ **ข้อที่สาม** คือเก็บไว้ใน Version Control ได้ ทำให้ดูประวัติ ย้อนกลับ และ Review ได้เหมือนโค้ดทั่วไป ที่เหลือคือ Validation, Self-service และ Reuse (หนังสือ: Fundamentals of DevOps and Software Delivery บทที่ 2 หน้า 39 ถึง 40)

เครื่องมือกลุ่มที่เราจะลองคือ Provisioning Tool อย่าง Terraform ที่อ่านโค้ดซึ่งบอกว่าอยากได้ทรัพยากรอะไร แล้วสร้างให้ (หนังสือ: เล่มเดิม หน้า 61) ในบทนี้เรารัน Terraform ของจริงในคอมพิวเตอร์เครื่องนี้ แต่ทรัพยากรที่สร้างเป็นไฟล์บนดิสก์สองไฟล์ผ่าน Provider ชื่อ `local` เพราะนั่นคือสิ่งที่รันได้โดยไม่ต้องมีบัญชี Cloud วงจรที่เห็นเป็นอย่างเดียวกันกับตอนสร้างเครื่องหรือฐานข้อมูลจริง

</Step>

## โค้ด แผน และการ Apply

ไฟล์ `main.tf` ของแบบฝึกบอกว่าอยากได้ไฟล์สองไฟล์ ตัวแรกชื่อ `config.json` ซึ่งเนื้อหามาจากตัวแปร `app_version` ตัวที่สองชื่อ `motd.txt`

```hcl
variable "app_version" {
  type    = string
  default = "1.0.0"
}

resource "local_file" "config" {
  filename = "${path.module}/out/config.json"
  content  = jsonencode({ version = var.app_version, replicas = 2 })
}

resource "local_file" "motd" {
  filename = "${path.module}/out/motd.txt"
  content  = "welcome to the shop"
}
```

เราสั่ง `terraform plan` ก่อน ซึ่งไม่แก้อะไรเลย แค่บอกว่าจะทำอะไร แล้วค่อย `terraform apply` ลงมือทำจริง (รัน)

```text
Plan: 2 to add, 0 to change, 0 to destroy.
Apply complete! Resources: 2 added, 0 changed, 0 destroyed.
```

ก่อน Apply โฟลเดอร์ `out/` ยังไม่มี และหลัง Apply มีไฟล์สองไฟล์ตามโค้ด พร้อมกับไฟล์ `terraform.tfstate` ที่จดไว้ว่า Terraform สร้างอะไรไปบ้าง คำสั่ง `terraform state list` ตอบว่า `local_file.config` กับ `local_file.motd` ถ้าเรารัน `plan` อีกรอบ จะได้ `No changes. Your infrastructure matches the configuration.` และ `apply` ซ้ำก็ได้ 0 Added, 0 Changed, 0 Destroyed ซึ่งเรียกว่า Idempotent คือสั่งกี่รอบก็ได้ผลเท่ากับสั่งครั้งเดียว ต่างจากสคริปต์ที่เขียนว่า "สร้างเซิร์ฟเวอร์หนึ่งตัว" ซึ่งรันซ้ำแล้วได้ตัวที่สองทันที

</Step>

## ทำไมต้องมีไฟล์ State

ถ้า Terraform เทียบแค่ "โค้ด" กับ "ของจริง" มันก็น่าจะพอ แต่ในโลกจริงของจริงมีเป็นหมื่นชิ้นที่ไม่ใช่ของเรา เช่นเครื่องของทีมอื่นในบัญชีเดียวกัน Terraform ต้องรู้ว่า "ชิ้นไหนเป็นของฉัน" ไฟล์ State คือสมุดที่จดว่าเคยสร้างอะไรไว้ แล้ว Terraform เทียบสามฝั่งเสมอ คือโค้ด State และของจริงที่อ่านมาใหม่ตอน Refresh

เลือกเหตุการณ์ใน Lab ด้านล่างทีละอัน ดูว่าคอลัมน์ไหนต่างจากคอลัมน์อื่น และบรรทัดแผนเปลี่ยนไปอย่างไร

<IacLab client:visible />

เหตุการณ์ "แก้โค้ด" (เปลี่ยน `app_version` เป็น `1.1.0`) ทำให้แผนเป็น `Plan: 1 to add, 0 to change, 1 to destroy.` โดยมีบรรทัด `local_file.config must be replaced` ส่วน `motd.txt` ไม่ถูกกล่าวถึงเลย เพราะไม่ต่างจากที่จดไว้ ซึ่งตรงกับสิ่งที่ผู้อ่านน่าจะอยากให้เป็น แก้เฉพาะที่ต่าง ไม่ใช่สร้างใหม่หมด (รัน)

</Step>

## เมื่อมีคนแก้ของจริงด้วยมือ

สถานการณ์ที่ IaC ต้องรับมือบ่อยที่สุดคือมีคนเข้าไปแก้ของจริงโดยไม่ผ่านโค้ด ซึ่งเกิดบ่อยกว่าการเปลี่ยนโค้ดเสียอีก ในแบบฝึกเราเปิดไฟล์ `config.json` แล้วแก้เป็น `version 9.9.9` กับ `replicas 50` ด้วยมือ จากนั้นสั่ง Plan ผลที่ได้น่าสนใจ (รัน)

```text
  # local_file.config will be created
Plan: 1 to add, 0 to change, 0 to destroy.
```

แผนไม่ได้บอกว่า "ไฟล์เปลี่ยนไป" แต่บอกว่า "จะสร้าง" เพราะ Provider ชื่อ `local` ตอน Refresh เปิดอ่านไฟล์ เห็นว่าเนื้อหาไม่ตรงกับที่จดไว้ จึงถือว่าทรัพยากรนั้นหายไปจาก State แล้วแผนก็เป็นสร้างใหม่ให้ตรงโค้ด เมื่อ Apply เนื้อหากลับเป็น `{"version":"1.1.0","replicas":2}` เหมือนเดิม คือแก้ด้วยมือถูกทับกลับ ส่วนถ้ามีคนลบ `motd.txt` ทิ้ง แผนก็เป็น `1 to add` เพื่อสร้างใหม่ (รัน)

ตรงนี้อยากให้ระวังข้อสรุปไม่ให้ไกลเกินไปนะ วิธีที่ Terraform ตรวจพบการแก้ด้วยมือและทำแผนออกมาต่างกันตาม Provider และชนิดของทรัพยากร สิ่งที่รันยืนยันคือพฤติกรรมของ `local_file` ใน Provider รุ่นที่ใช้ ไม่ได้ลอง EC2 หรือฐานข้อมูลบน Cloud จริง ซึ่งอาจแสดง Drift เป็น "will be updated in-place" แทน แนวคิดที่เอาไปใช้ได้คือให้โค้ดเป็นแหล่งความจริงและรัน Plan เป็นประจำเพื่อเห็นว่าโลกจริงเดินออกนอกโค้ดไปไหน

เมื่อจบ เราสั่ง `terraform destroy` และไฟล์ทั้งสองถูกลบ กับ State กลับว่าง (รัน)

<Callout type="note" title="อย่างอื่นใน IaC ที่ไม่ได้ลอง">
หนังสือจัดกลุ่มเครื่องมือเป็น Ad Hoc Script, Configuration Management (เช่น Ansible), Server Templating (เช่น Packer) และ Provisioning (เช่น Terraform, OpenTofu) และบอกว่าทีมจริงมักใช้หลายอย่างร่วมกัน (หนังสือ: เล่มเดิม [บทที่ 2](/devops/ci/)) ผู้เขียนลองเฉพาะ Terraform กับ Provider `local` ไม่ได้ลอง Ansible, Packer, OpenTofu, Remote State หรือการจัดการ State ของทีมที่ทำงานพร้อมกัน
</Callout>
