## นาย A เขียนโค้ดเสร็จตั้งแต่วันจันทร์

สมมติว่านาย A เป็น Developer ที่แก้โค้ดหน้าชำระเงินเสร็จตั้งแต่เช้าวันจันทร์ โค้ดที่แก้นั้นเล็กมาก ใช้เวลาเขียนจริงไม่ถึงหนึ่งวัน แต่ลูกค้าเพิ่งได้ใช้ของใหม่นี้ในสัปดาห์ถัดไป ทั้งที่ไม่มีใครขี้เกียจเลยสักคน

เรามาดูกันว่าเวลาหายไปไหน ตารางข้างล่างคือ Change หนึ่งอันที่เดินทางผ่านทีมต่าง ๆ ตามวิธีทำงานแบบเดิม ที่ Dev เขียนโค้ดแล้วส่งต่อให้คนอื่นเป็นทอด ๆ (ตัวเลขเป็นตัวอย่างที่ผู้เขียนตั้งขึ้นเอง คำนวณใน `exercises/00_value_stream.py`)

| ขั้นตอน | มีคนทำจริง (ชั่วโมง) | รอคิว (ชั่วโมง) |
|---|---|---|
| เขียนโค้ด | 8 | 0 |
| Code Review | 1 | 16 |
| ส่งให้ทีมทดสอบ ทดสอบด้วยมือ | 6 | 40 |
| ขอ Ops เปิดช่วงเวลา Deploy | 1 | 90 |
| Ops Deploy ด้วยมือ | 2 | 24 |
| เปิดดูบน Production | 1 | 8 |
| **รวม** | **19** | **178** |

ตัวเลขที่ควรหยุดมองคือแถวสุดท้าย ชั่วโมงที่มีคนทำงานกับ Change นี้จริง ๆ มีแค่ 19 ชั่วโมง ส่วนอีก 178 ชั่วโมงมันนอนอยู่ในคิวรอใครสักคนว่าง รวมแล้ว Change นี้ใช้เวลา 197 ชั่วโมง หรือประมาณ 8 วัน โดยมีคนทำงานอยู่แค่ 10% ของเวลาทั้งหมด

ตรงนี้อยากให้ตั้งคำถามในใจกันหน่อยว่า ถ้าเราอยากให้ Change ถึงผู้ใช้เร็วขึ้น เราควรไปเร่งส่วนไหน เร่งให้ Dev พิมพ์เร็วขึ้นช่วยได้ไม่มากเลย เพราะมันคือ 8 ชั่วโมงจาก 197

</Step>

## วาดเวลาให้เห็นเป็นแท่ง

ลองเทียบสองวิธีที่ใช้ Change เดียวกันในภาพข้างล่าง แท่งบนคือวิธีส่งต่อกันเป็นขั้นอย่างตารางเมื่อกี้ ส่วนแท่งล่างคือวิธีที่ Build, ทดสอบ และ Deploy ด้วย Pipeline อัตโนมัติ ([บทที่ 2](/devops/ci/) จะเล่าว่า Pipeline หน้าตาเป็นอย่างไร) ทั้งสองแท่งวาดด้วยมาตราส่วนเดียวกัน สีทึบคือชั่วโมงที่มีคนทำงาน ส่วนลายขีดคือชั่วโมงที่รอคิว

ส่วนครึ่งล่างของภาพคือเรื่องที่ซ่อนอยู่ในตัวเลข 90 ชั่วโมงของแถว "ขอ Ops เปิดช่วงเวลา Deploy" เมื่อ Release ออกเป็นรอบ Change ที่เสร็จแล้วต้องรอรถรอบถัดไป กดเลือกว่าจะ Release ทุกกี่วัน แล้วดูเส้นประที่ลากจากแต่ละจุดไปหาเส้นสีส้มที่เป็นรอบ Release

<WaitLab client:visible />

สังเกตว่าตอน Release ทุกวัน Change ที่เสร็จแล้วรอเฉลี่ยประมาณ 11 ชั่วโมง แต่พอเปลี่ยนเป็นทุกสี่สัปดาห์ ทั้งยี่สิบ Change ต้องไปรวมกันขึ้นรถคันเดียว และแต่ละอันรอเฉลี่ยกว่า 349 ชั่วโมง ประมาณสองสัปดาห์ครึ่ง

## ทำไมถึงเกิดวงจรที่ Release ห่างขึ้นเรื่อย ๆ

หนังสือ Fundamentals of DevOps and Software Delivery เล่าที่มาของเรื่องนี้ไว้ว่า บริษัทส่วนใหญ่ในอดีตมีทีม Dev ที่รับผิดชอบการเขียนซอฟต์แวร์ กับทีม Ops ที่รับผิดชอบเครื่องและระบบจริง ทั้งสองทีมมีเป้าหมายที่ขัดกัน Ops ถูกวัดด้วยความปลอดภัยและความเสถียร ส่วน Dev ถูกวัดด้วยการส่งฟีเจอร์ให้เร็ว (หนังสือ: Fundamentals of DevOps and Software Delivery คำนำ หน้า Xvi)

เมื่อ Dev เขียนโค้ดแล้ว "โยนข้ามกำแพง" ไปให้ Ops ที่ต้อง Deploy ด้วยมือ ก็มักจะเกิดความพังขึ้น ทีม Ops ที่เหนื่อยกับการตื่นตีสามมาแก้ปัญหาจึงลดจำนวนรอบ Release ลง แต่ Release แต่ละรอบจะใหญ่ขึ้นและซับซ้อนขึ้น ซึ่งยิ่งพังบ่อยขึ้น พอพังบ่อยก็ยิ่งลดรอบ วนอย่างนี้ไปเรื่อย ๆ จนบริษัทเดินต่อไม่ไหว (หนังสือ: เล่มเดิม หน้า Xvi)

ถ้าเราเอาวงจรนี้ไปวางเทียบกับ Lab เมื่อกี้ จะเห็นว่ามันคือภาพเดียวกัน Release ห่างขึ้นทำให้แต่ละรอบมี Change มากขึ้น ซึ่งเป็นตัวที่ทำให้ความเสี่ยงของแต่ละรอบสูงขึ้นด้วย [บทที่ 1](/devops/version-control/) กับ[บทที่ 5](/devops/release/) จะกลับมาที่เรื่องขนาดของ Batch นี้

</Step>

## DevOps เป็นคำตอบของอะไร

หนังสือเล่มเดิมสรุปว่า DevOps เริ่มพูดถึงกันอย่างเปิดเผยราวปี 2007 ถึง 2008 พร้อมกับการเปลี่ยนแปลงสามอย่างในรอบสิบปีถัดมา อย่างแรกคือการย้ายไป Cloud ที่ทำให้ทั้ง Dev และ Ops เข้าถึงระบบจริงผ่านซอฟต์แวร์ชุดเดียวกัน อย่างที่สองคือการเปลี่ยนมาใช้ Automation แทนการทำด้วยมือ และอย่างที่สามคือการให้ Dev กับ Ops ทำงานร่วมกันในทีมเดียวที่มีเป้าหมายและเครื่องมือเดียวกัน (หนังสือ: เล่มเดิม หน้า Xvii)

ผู้เขียนหนังสือให้ความหมายของมันไว้สั้น ๆ ว่า เป้าหมายของ DevOps คือทำให้การส่งมอบซอฟต์แวร์มีประสิทธิภาพขึ้นอย่างมาก และบอกด้วยว่า DevOps ไม่ใช่ชื่อทีม ไม่ใช่ตำแหน่งงาน และไม่ใช่เทคโนโลยีตัวใดตัวหนึ่ง แม้คำนี้จะถูกใช้เรียกทั้งสามอย่างก็ตาม (หนังสือ: เล่มเดิม หน้า Xvii)

ส่วนความต่างที่ได้จริงนั้นใหญ่มาก ตาราง DORA ของปี 2024 ในหนังสือบอกว่าทีมระดับ Elite Deploy บ่อยกว่าทีมระดับต่ำ 182 เท่า มี Lead Time สั้นกว่า 127 เท่า และกู้ระบบคืนได้เร็วกว่า 2,293 เท่า (หนังสือ: เล่มเดิม หน้า xv) เราจะไล่ดูตัวชี้วัดเหล่านี้กันจริง ๆ ใน[บทที่ 12](/devops/metrics/)

<Callout type="note" title="ผู้เขียนไม่ได้วัดเอง">
ตัวเลข 182 เท่ากับ 127 เท่ามาจากรายงานที่หนังสืออ้างถึง ผู้เขียนบทเรียนนี้ไม่ได้ตรวจกับรายงานต้นฉบับ และไม่ได้วัดจากทีมจริง ตัวเลขชั่วโมงในตารางและ Lab ด้านบนเป็นตัวอย่างที่ตั้งขึ้นเพื่อให้เห็นสัดส่วนนะ
</Callout>

</Step>

## วงจรที่เราจะเดินตามตลอดเส้นทางนี้

ถ้าจะเขียนวงจรที่โค้ดเดินทางให้เป็นลำดับ เราจะได้แปดช่วง และข้อมูลจากช่วงสุดท้ายจะวิ่งกลับไปหาช่วงแรก ซึ่งเป็นที่มาของเส้นที่วนเป็นวง

```text
 Plan ─► Code ─► Build ─► Test ─► Release ─► Deploy ─► Operate ─► Monitor
   ▲                                                                │
   └──────────────── Feedback (alert, incident, metric) ◄───────────┘
```

เครื่องมือที่เราจะแตะผ่าน ๆ ในแต่ละช่วง และบทที่อธิบายช่วงนั้น เป็นอย่างนี้

| ช่วงของวงจร | บทที่อธิบาย | เครื่องมือที่แตะ |
|---|---|---|
| Code | [บทที่ 1](/devops/version-control/) | Git |
| Build และ Test | [บทที่ 2](/devops/ci/) และ [บทที่ 3](/devops/config-secrets/) | Pipeline (ใน Lab ใช้ตัวเล็ก ๆ ที่เขียนเอง), GitHub Actions เป็นตัวอย่างที่ใกล้เคียงของจริง |
| Release | [บทที่ 4](/devops/artifacts/) และ [บทที่ 5](/devops/release/) | Docker, Registry |
| Deploy | [บทที่ 6](/devops/iac/) และ [บทที่ 7](/devops/gitops/) | Terraform, GitOps |
| Operate และ Monitor | [บทที่ 8](/devops/observability/) ถึง [บทที่ 10](/devops/incidents/) | Prometheus |
| ปรับปรุงทั้งวงจร | [บทที่ 11](/devops/devsecops/) ถึง [บทที่ 13](/devops/capstone/) | Trivy, ตัวชี้วัด DORA |

เส้นทางนี้เลือกอธิบายเครื่องมือแค่ให้พอเห็นว่าแต่ละตัวอยู่ตรงไหนของวงจร ส่วนรายละเอียดของ Docker กับ Git ให้ไปอ่านที่ Subject ของมันเอง เช่น [บทที่ 1 ของ Docker](/docker/containers/) ที่เล่าว่า Container คืออะไร ส่วน Kubernetes ยังไม่มีในสวนนี้ตอนที่เขียนบทนี้ เราจึงใช้ Docker ตัวเล็ก ๆ แทนใน[บทที่ 7](/devops/gitops/)

</Step>

## หลักสามข้อที่อยู่เบื้องหลังวงจร

The DevOps Handbook สรุปหลักการที่อยู่ใต้วงจรนี้เป็น Three Ways (หนังสือ: The DevOps Handbook [บทที่ 1](/devops/version-control/)) ซึ่งเราจะใช้เป็นแผนที่ของเส้นทางนี้ได้เลย

| Way | ใจความ | อยู่ในบทไหน |
|---|---|---|
| The First Way (Flow) | ทำให้งานไหลจาก Dev ไปถึงผู้ใช้เร็วและไม่สะดุด ด้วยการทำให้งานมองเห็นได้ ลดขนาด Batch และฝังคุณภาพไว้ตั้งแต่ต้นทาง | [บทที่ 1](/devops/version-control/) ถึง 7 |
| The Second Way (Feedback) | ให้ข้อมูลไหลกลับจาก Production มาหาคนเขียน เร็วพอที่จะแก้ก่อนความเสียหายใหญ่ | [บทที่ 8](/devops/observability/) ถึง [10](/devops/incidents/) |
| The Third Way (Continual Learning) | เรียนรู้จากความล้มเหลวและทดลองอย่างต่อเนื่อง | [บทที่ 10](/devops/incidents/) ถึง 13 |

เมื่อเทียบกับวงจรด้านบน The First Way คือเส้นด้านบนที่ไปทางขวา The Second Way คือเส้นล่างที่วนกลับมา ส่วน The Third Way คือสิ่งที่ทีมทำกับข้อมูลที่ไหลกลับมานั้นหลังจากแต่ละรอบ
