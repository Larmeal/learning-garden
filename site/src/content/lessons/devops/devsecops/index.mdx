## ความปลอดภัยเป็นงานของทุกด่าน

ที่ผ่านมาเรามี Pipeline ที่ตรวจโค้ดและสร้าง Artifact ที่รู้ที่มา ยังเหลือคำถามว่า สิ่งที่เรา Deploy ปลอดภัยแค่ไหน ในโลกเก่าเรื่องนี้มักเป็นขั้นตอนท้ายสุด ที่ทีมความปลอดภัยมาตรวจก่อนปล่อย ซึ่งหมายถึงคิวรอตามที่เห็นตั้งแต่[บทที่ 0](/devops/overview/) และกว่าจะเจอปัญหาก็ใกล้วัน Release แล้ว

The DevOps Handbook เล่าว่าองค์กรที่ทำได้ดีเอาการตรวจความปลอดภัยเข้าไปอยู่ในงานประจำวันและเครื่องมือของนักพัฒนา เพราะช่วยลดความเสี่ยง ลดโอกาสที่จะมีช่องโหว่ในระบบ และสอนให้นักพัฒนาเขียนโค้ดปลอดภัยขึ้น (หนังสือ: The DevOps Handbook บทที่ 22) ส่วนที่หนังสือเน้นอีกเรื่องคือซอฟต์แวร์ที่เราเขียนไม่ได้มาจากโค้ดของเราทั้งหมด เราประกอบมันจากชิ้นส่วนโอเพนซอร์ส ซึ่งกลายเป็น Software Supply Chain ที่เราพึ่งพาอยู่ และเมื่อใช้ไลบรารีก็ได้ทั้งความสามารถและช่องโหว่ของมันมาด้วย (หนังสือ: เล่มเดิม บทที่ 22)

ในบทนี้เรามีสามด่านให้ลอง ซึ่งแต่ละด่านจับสิ่งต่างชนิดกัน และอยู่คนละจุดของเส้น ถ้าต้องการรายละเอียดของภัยแต่ละแบบ ให้ไปที่ [บทที่ 11 ของ App Security](/app-security/supply-chain-secrets/) ที่อธิบาย Dependency กับ Secret ไว้ ที่นี่เราสนใจแค่ว่าด่านเหล่านั้นอยู่ตรงไหนของ Pipeline

</Step>

## ด่านที่หนึ่ง: Secret ที่ลบไฟล์แล้วก็ยังอยู่

ใน[บทที่ 2](/devops/ci/) Stage `secret-scan` ตรวจแค่ไฟล์ใน Commit ที่ Push เข้ามา แต่ Secret ที่เคยหลุดแล้วถูกลบทีหลังยังไม่หายไปไหน ในแบบฝึกเราสร้าง Repository ที่ Commit หนึ่งใส่ Key ปลอมรูปแบบ AWS ลงไปแล้วอีก Commit ตามมาลบมัน ผลที่ได้ (รัน)

```text
สแกนไฟล์ในสภาพปัจจุบัน        →  ไม่พบอะไรเลย
สแกน git log -p --all          →  พบ AKIAIOSFODNN7EXAMPLE
git log -S AKIAIOSFODNN7EXAMPLE →  สอง Commit (ที่เพิ่ม และที่ลบ)
git show HEAD~1:settings.py     →  Key ยังอยู่ใน Object Store
```

ตัวสแกนที่อ่านแค่ไฟล์ปัจจุบันบอกว่าปลอดภัย ทั้งที่ Key ยังอยู่ในประวัติ ซึ่งเป็นสิ่งที่ทุกคนที่ Clone Repository เอาไปได้ ด่านที่ตรวจ Secret จึงต้องอ่านทั้ง History และเมื่อพบ Key ที่เคยหลุด ต้องถือว่ามันรั่วแล้วและหมุนเปลี่ยน Key ไม่ใช่แค่ลบไฟล์ (เหตุผลลึกกว่านี้อยู่ใน [บทที่ 11 ของ App Security](/app-security/supply-chain-secrets/#key-ที่ลบไฟล์แล้วก็ยังอยู่))

</Step>

## ด่านที่สอง: SBOM ที่จับคู่ใหม่ได้ทุกเมื่อ

ด่านที่สองมาจากข้อสังเกตว่า ความเสี่ยงของโค้ดที่ Build แล้วไม่ได้คงที่ ช่องโหว่ที่ถูกค้นพบหลัง Build ทำให้ Artifact เดิมเสี่ยงขึ้นได้โดยไม่มีใครแตะมัน วิธีรับมือคือเก็บรายการส่วนประกอบของ Artifact ไว้ เรียกว่า SBOM (Software Bill of Materials) หนังสือ The DevOps Handbook ยกผลสำรวจว่าทีมที่ทำได้ดีมักมีบันทึกส่วนกลางของ Artifact ที่ Deploy ทั้งหมด เพื่อสร้าง SBOM ของแต่ละแอป และสแกนตรวจความปลอดภัยกับสัญญาอนุญาตได้ทั้งหมดจากส่วนกลาง (หนังสือ: เล่มเดิม บทที่ 22)

ในแบบฝึกเราสร้าง SBOM รูปแบบ CycloneDX จาก Lock File ห้าแพ็กเกจ แล้วจับคู่กับรายการช่องโหว่ที่เราแต่งขึ้น (ไม่ใช่ CVE จริง) สองครั้ง (รัน)

```text
วันที่ 1 :  [('EXAMPLE-0001', 'pyyaml', 'critical')]
วันที่ 30:  [('EXAMPLE-0002', 'requests', 'high'),
             ('EXAMPLE-0003', 'jinja2', 'medium'),
             ('EXAMPLE-0001', 'pyyaml', 'critical')]
```

ไบต์ของ Artifact ไม่เปลี่ยนเลยระหว่างสองวัน แต่ความรู้ของเราเกี่ยวกับมันเปลี่ยน วันแรก Gate ที่ตั้งให้ล้มตั้งแต่ระดับ `high` จะหยุด Build (เพราะ Pyyaml เป็น Critical) ส่วน Gate ที่ล้มเฉพาะ `critical` ปล่อย Build ที่มีแค่ระดับ Medium ผ่านไป และวันที่ 30 Gate ระดับ `high` ล้มเพราะ Requests กับ Pyyaml (รัน) นี่คือเหตุผลที่ต้องเก็บ SBOM ไว้ ไม่เช่นนั้นเราต้อง Build ใหม่ทุกครั้งที่มีช่องโหว่ใหม่เพียงเพื่อรู้ว่าตัวเองได้รับผลกระทบหรือไม่

</Step>

## ด่านที่สาม: สแกน Image ด้วยเครื่องมือจริง

ด่านสุดท้ายคือสแกนตัว Image ทั้งก้อน รวมถึงระบบปฏิบัติการที่อยู่ข้างใน ไม่ใช่แค่ Dependency ของแอป ในแบบฝึกเรารัน Trivy 0.67.2 ใน Docker กับฐานข้อมูลช่องโหว่จริง สแกน `nginx:1.21-alpine` ซึ่งเป็น Image รุ่นเก่า ผลที่ได้ (รัน)

```text
nginx:1.21-alpine: 101 known vulnerabilities, 11 critical   (Alpine 3.15 หมดการสนับสนุน: EOSL)
nginx:1.28-alpine: 287 known vulnerabilities, 6 critical
```

ตรงนี้อยากให้ตั้งคำถามในใจกันหน่อยว่า ทำไม Image ที่ใหม่กว่าถึงมีช่องโหว่ที่ตรวจพบ "เยอะกว่า" ผู้เขียนไม่ได้ตรวจสาเหตุ แต่สังเกตว่า Trivy ติดธง `EOSL` (End of Support Life) ให้ Image เก่า ซึ่งเป็นข้อมูลที่สำคัญกว่าตัวเลข เหตุผลที่เป็นไปได้ข้อหนึ่งคือผู้ดูแลระบบปฏิบัติการเลิกประกาศช่องโหว่สำหรับรุ่นที่หมดการสนับสนุนแล้ว ตัวเลขน้อยจึงไม่ได้แปลว่าปลอดภัยกว่า (ข้อนี้เป็นการคาดเดา ผู้เขียนไม่ได้ตรวจ) บทเรียนที่แน่นอนคือผลสแกนเป็นคำตอบของวันนี้ ถ้าสแกน Tag เดิมพรุ่งนี้ก็อาจได้ตัวเลขอื่น (แบบฝึกจึงตรวจแค่ว่าผลมีชื่อแพ็กเกจ รุ่นที่ติดตั้ง และระดับความรุนแรง และ Image เก่าถูกติดธง EOSL)

เลือกสิ่งที่เป็นภัยใน Lab ทีละแบบ แล้วดูว่าด่านไหนหยุดมัน ด่านก่อนหน้าที่มันผ่านไปแล้ว และด่านหลังที่มันไม่ต้องไปถึง
