## ตารางเดียว สามบทบาท

การเข้ารหัสที่ดิสก์ไม่กันคนที่มีสิทธิ์ผ่านแอปอยู่แล้ว ชั้นถัดไปจึงเป็นการจำกัดว่าใครเห็นอะไร ตารางลูกค้าของนาย A มี 600 แถว (คนสมมติ) และมีคนสามกลุ่มต้องใช้ **Admin** ที่ดูแลระบบ **Support** ที่ตอบลูกค้าทางโทรศัพท์ และ **Analyst** ที่ทำรายงาน สามกลุ่มต้องการข้อมูลไม่เหมือนกัน

Support ต้องรู้ชื่อกับวิธีติดต่อ แต่เห็นอีเมลกับเบอร์แบบปิดบางส่วนก็พอ และดูเฉพาะลูกค้าของภูมิภาคตัวเอง Analyst ไม่ต้องรู้ว่าเป็นใคร ต้องการแค่ลักษณะของลูกค้า ส่วน Admin เห็นหมด ในแบบฝึกเราสร้าง **View** ของ SQLite หนึ่งตัวต่อบทบาท (รัน: `exercises/08_access_masking.py`)

```sql
CREATE VIEW v_support AS SELECT id, name, mask_email(email) AS email, mask_phone(phone) AS phone, zip
  FROM customers WHERE substr(zip, 1, 3) IN ('101', '102', '103');
CREATE VIEW v_analyst AS SELECT tok(email) AS person, substr(zip, 1, 3) AS zip3,
  substr(birth, 1, 4) AS birth_year, band(salary, 10000) AS salary_band, diagnosis FROM customers;
```

View แรกเลือกห้าคอลัมน์ ปิดอีเมลกับเบอร์ และกรองแถวให้เหลือสามพื้นที่ View ที่สองเอาชื่อ อีเมล และเบอร์ออกทั้งหมด แทนที่อีเมลด้วย Token (HMAC ที่เราเห็นแล้วในบท Pseudonymization) ลดความละเอียดของ Zip และวันเกิด และแปลงเงินเดือนเป็นช่วง 10,000

ผลที่ Assert ไว้ Admin เห็น 9 คอลัมน์ 600 แถว Support เห็น 5 คอลัมน์ 307 แถว อีเมลเหลือตัวแรก สามดาว และโดเมน เบอร์โทรเหลือสองตัวหน้าและสองตัวหลัง ส่วน Analyst เห็น 5 คอลัมน์ 600 แถวไม่มีชื่อเลย เงินเดือนเป็นช่วง เลือกบทบาทในแล็บข้างล่างเพื่อเทียบ

## บังคับจริง ไม่ใช่แค่ตกลงกัน

View ทำให้บทบาทหนึ่งใช้ View ของตัวเองได้ แต่ถ้า Analyst ยังเขียน `SELECT * FROM customers` ตรง ๆ ได้ ทุกอย่างก็ไม่มีความหมาย เราต้องบังคับ SQLite มีกลไกที่เรียกว่า **Authorizer** ซึ่งเป็นฟังก์ชันที่ถูกเรียกก่อนอ่านทุกตารางทุกคอลัมน์ และตอบได้ว่าอนุญาตหรือปฏิเสธ แบบฝึกเขียนกฎว่า ตารางจริง `customers` อ่านได้ก็ต่อเมื่อการอ่านเกิดจาก View ที่บทบาทนั้นได้รับ (หรือเป็น Admin)

ผลที่ Assert ไว้ `SELECT * FROM customers` ของ Analyst ถูกปฏิเสธ ถ้าห่อด้วย Sub Query (`SELECT name FROM (SELECT * FROM customers)`) ก็ถูกปฏิเสธเหมือนกัน Support อ่าน View ของ Analyst ไม่ได้ และมีแต่ Admin ที่อ่านตาราง Log (`audit`) ได้

### ช่องโหว่ที่เราเจอเอง

ตอนเขียนแบบฝึกครั้งแรก การตรวจว่า Support อ่าน View ของ Analyst ไม่ได้ **ผ่านทั้งที่ไม่ควร** เหตุผลคือ Authorizer ของ SQLite ทำงานตอน **คอมไพล์** Statement ไม่ใช่ตอนรันทุกครั้ง และ Python เก็บ Statement ที่คอมไพล์แล้วไว้ใน Cache พอ Analyst รัน `SELECT * FROM v_analyst` ครั้งหนึ่ง คอมไพล์ไว้ภายใต้สิทธิ์ของ Analyst แล้วเมื่อ Support ส่งข้อความเดียวกัน Python ใช้ Statement ที่คอมไพล์ไว้ซ้ำ Authorizer จึงไม่ถูกเรียกอีก

แบบฝึกทำให้เห็นเป็นกรณีแยก เจ้าของตารางลับอ่านก่อน แล้วแขกส่งข้อความเดียวกัน ด้วย Cache ปกติของ Python แขกอ่านได้ ถ้าตั้ง `cached_statements=0` ทุกข้อความถูกคอมไพล์ใหม่และแขกถูกปฏิเสธ นี่คือเหตุผลที่เราต้องเขียนทดสอบให้ลองกรณีที่ควรถูกปฏิเสธเสมอ นอกเหนือจากกรณีที่ควรผ่าน

## วัตถุประสงค์ของการใช้ข้อมูล Token กับ Mask และกลุ่มเล็ก

สิทธิ์ที่เป็นแค่บทบาทยังไม่พอ เรายังต้องบอกว่าใช้ข้อมูลไปเพื่ออะไร แบบฝึกกำหนดว่า Analyst ใช้ได้เพื่อ `reporting` เท่านั้น ถ้าส่งวัตถุประสงค์ `marketing` มา คำขอถูกปฏิเสธก่อนรัน Query ใด ๆ และบันทึกลงตาราง Log ด้วย นี่คือแนวคิดของการจำกัดตามวัตถุประสงค์ที่ตัวกฎหมายอย่าง GDPR ให้ความสำคัญ ซึ่งเราจะกลับไปดูในบทวงจรชีวิตของข้อมูล

ลองดูว่าสิ่งที่ปิดไว้ยังใช้ทำอะไรได้ **Token** ในคอลัมน์ `person` ของ Analyst เท่ากันในทุก Query จึงตามคนเดียวกันข้ามตารางได้ โดยไม่รู้ว่าเป็นใคร ส่วน **Mask** ของ Support ทำไม่ได้ เพราะอีเมลที่ปิดแล้วอย่าง `a***@mail.test` ซ้ำกันได้หลายคน แบบฝึกเช็กว่าค่าที่ปิดแล้วมีไม่ซ้ำน้อยกว่าจำนวนแถว สิ่งที่ปิดไว้ให้คนอ่านดูเฉย ๆ ใช้ Mask ได้ สิ่งที่ต้องคำนวณต่อใช้ Token

ถ้า Analyst ถาม `GROUP BY zip3, birth_year, diagnosis` จะได้กลุ่มจำนวนมากที่มีคนไม่ถึงห้า ซึ่งคือ Linkage Attack ที่เราเห็นแล้วในอีกรูป แบบฝึกกันกลุ่มที่เล็กกว่า 5 คนไม่ให้แสดง ได้ 509 กลุ่มที่ถูกกันไว้ ส่วน `GROUP BY diagnosis` อย่างเดียวได้ 7 กลุ่มที่ใหญ่ทุกกลุ่ม ไม่ต้องกันอะไร

## สแกนสิ่งที่กำลังจะออกไป

ชั้นสุดท้ายคือตรวจสิ่งที่ออกจากระบบ เรียกว่า **Data Loss Prevention (DLP)** (หนังสือ: Practical Data Privacy บทที่ 4 หน้า 104) แบบฝึกเขียนตัวสแกนเล็ก ๆ ที่หาอีเมลและเบอร์โทรด้วย Regex และหาเลขบัตรด้วยการตรวจเลขตรวจสอบแบบ Luhn ซึ่งต่างจาก Regex ตรงที่ไม่ใช่ทุกตัวเลขสิบหกหลักที่เป็นเลขบัตรจริง

ผลที่ Assert ไว้ ไฟล์ที่ Support ส่งออกไป (ปิดแล้ว) ผ่านการสแกน ไม่มีอีเมลหรือเบอร์ดิบเหลือ แต่ที่ Admin ส่งออกคอลัมน์ `notes` ซึ่งมีอีเมลกับเบอร์ที่พนักงานพิมพ์เข้าไป สแกนเจอ 60 เบอร์โทรกับ 32 อีเมล จึงบล็อกการส่งออก และเลขบัตรที่ผ่านการตรวจ Luhn อย่าง `4539 1488 0343 6467` ถูกจับ ส่วนเลขที่ผิดหนึ่งหลักไม่ถูกจับ

Log การ Query ปิดท้าย ทุกคำขอถูกบันทึก รวมถึงที่ถูกปฏิเสธ แบบฝึกนับว่ามีตอบสำเร็จ 8 ครั้ง และถูกปฏิเสธ 5 ครั้ง (สี่ครั้งโดย Authorizer และหนึ่งครั้งโดยการตรวจวัตถุประสงค์) ซึ่ง Log ที่ดีเป็นสิ่งที่ทำให้ตอบได้ว่า "เมื่อวานใครดูข้อมูลของลูกค้าคนนี้" (ที่มาของแนวคิด Safe People และ Safe Settings ใน Five Safes ของหนังสือ Building an Anonymization Pipeline บทที่ 3 หน้า 49 และ 52)

<Callout type="warn" title="ของที่เขียนเองเพื่อเรียน">

กลไกสิทธิ์ในแบบฝึกเขียนบน Authorizer ของ SQLite เพื่อให้เห็นว่าบังคับอย่างไร ในงานจริงใช้ระบบสิทธิ์ของฐานข้อมูลเอง (Role, Column Privilege, Row Level Security) ผู้เขียนไม่ได้รันสิ่งเหล่านั้น และ DLP ที่ใช้ Regex กับ Luhn เป็นแค่ตัวอย่าง ตัวจริงมีรูปแบบและการจัดการผลบวกลวงที่ซับซ้อนกว่านี้มาก
