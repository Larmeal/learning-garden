## เข้ารหัสทีละช่อง

สองบทที่แล้วเราจัดการกับข้อมูลที่ปล่อยออกไปนอกบริษัท บทนี้กลับมาที่ข้อมูลที่เราถืออยู่เอง สมมติว่าเลขบัตรประชาชนของลูกค้าอยู่ในตาราง คำถามแรกที่ถามกันคือ ถ้าดิสก์หรือ Backup หลุดออกไป ใครจะอ่านได้ การเข้ารหัสข้อมูลที่เก็บ (Encryption at Rest) ตอบคำถามนี้

เราเข้ารหัสแค่ช่องที่อ่อนไหวด้วย AES-GCM ที่เรารู้จักมาจากวิชา Application Security โดยใช้เลขแถวเป็นข้อมูลกำกับ (Associated Data) ของแต่ละค่า (รัน: `exercises/07_encryption.py`)

```python
def enc(pid, value):
    nonce = os.urandom(12)
    return nonce + gcm.encrypt(nonce, value.encode(), str(pid).encode())
```

ฟังก์ชันสุ่ม Nonce 12 ไบต์ใหม่ทุกครั้ง เข้ารหัสค่า และให้เลขแถวเป็น Associated Data ค่าตัวเลข 9 ตัวอักษรกลายเป็น 37 ไบต์ คือ Nonce 12, ข้อความ 9 และ Tag 16 และถอดรหัสได้ครบทุกค่าเมื่อใช้เลขแถวที่ถูก

Associated Data มีไว้ทำอะไร ลองคัดลอก Ciphertext ของแถวที่ 2 ไปแปะในแถวที่ 1 ผลคือถอดรหัสไม่ผ่านด้วย `InvalidTag` เพราะ Tag ครอบคลุมเลขแถวด้วย ผู้ที่เขียนลงดิสก์ได้แต่ไม่มี Key จึงสลับค่าระหว่างแถวไม่ได้ และเข้ารหัสค่าเดียวกันสองครั้งก็ได้ผลต่างกัน (Nonce ต่างกัน) ใครมองก็ไม่รู้ว่าแถวไหนมีค่าเหมือนกัน

</Step>

## เข้ารหัสแบบสุ่ม หรือแบบที่ค้นหาได้

การเข้ารหัสแบบสุ่มดีมาก แต่มันค้นหาไม่ได้ ถ้าอยากรู้ว่ามีกี่แถวที่ผลวินิจฉัยเป็นโรคเดียวกัน ต้องถอดรหัสทุกแถวก่อน ทางที่ใช้กันคือ **การเข้ารหัสแบบกำหนดผลตายตัว** (Deterministic Encryption) ที่ค่าเดียวกันได้ Ciphertext เดียวกันเสมอ แบบฝึกใช้ AES-SIV

ผลที่ได้ คอลัมน์ผลวินิจฉัยมี 7 ค่า และ Ciphertext ที่ต่างกันก็มี 7 แบบพอดี ทำให้ใช้เงื่อนไข "เท่ากับ" ค้นบนข้อมูลที่เข้ารหัสได้ แต่ราคาคือความเท่ากันมองเห็นได้ ผู้โจมตีที่มีตารางและรู้คร่าว ๆ ว่าโรคไหนพบบ่อย ก็นับความถี่ของ Ciphertext แล้วเดาว่า Ciphertext ไหนคือโรคอะไร แบบฝึกเช็กว่า Ciphertext ที่พบมากที่สุดเป็นของไข้หวัดใหญ่ ซึ่งเป็นโรคที่พบบ่อยที่สุดในตาราง (Frequency Analysis) ส่วนการเข้ารหัสแบบสุ่มของช่องเดียวกันได้ 300 ค่าต่างกันทั้ง 300 แถว

เลือกตามสิ่งที่ต้องทำ ถ้าไม่ต้องค้นหา ใช้แบบสุ่ม ถ้าต้องค้นด้วยค่าตรง ๆ ใช้แบบกำหนดผลตายตัวกับช่องที่มีค่าหลากหลายมาก (เช่นเลขบัตร) และอย่าใช้กับช่องที่มีไม่กี่ค่าอย่างผลวินิจฉัย ข้อสุดท้ายเป็นความเห็นของผู้เขียนจากผลที่ได้ ไม่ได้มาจากหนังสือ

</Step>

## Key เดียวสำหรับทุกอย่าง มีปัญหา

ถ้าเราใช้ Key เดียวเข้ารหัสทุกตารางแล้วอยากหมุน Key (เปลี่ยนเป็นตัวใหม่ตามนโยบายหรือเพราะสงสัยว่าหลุด) เราต้องถอดรหัสและเข้ารหัสใหม่ทุกแถว ตัวอย่างสมมติของผู้เขียนมีสามตาราง 100,000, 2,000,000 และ 400,000 แถว รวม 2,500,000 ค่า ค่าละ 37 ไบต์ ต้องเขียนใหม่ 92,500,000 ไบต์ ทั้งที่ข้อมูลจริงไม่ได้เปลี่ยนเลย (หนังสือ: Practical Data Privacy บทที่ 10 หน้า 265 พูดถึงเรื่องการหมุน Key ในคำถามที่พบบ่อย)

ทางแก้คือ **Envelope Encryption** สองชั้น แต่ละตารางมี **Data Key (DEK)** ของตัวเอง ใช้เข้ารหัสแถวของตาราง จากนั้น **Master Key (KEK)** ที่อยู่ใน KMS หรือ HSM หุ้ม DEK แต่ละตัวอีกที ที่เก็บข้างข้อมูลคือ DEK ที่ถูกหุ้มแล้ว ยาว 60 ไบต์ (Nonce 12, Key 32, Tag 16) ลองกดทีละขั้นในแล็บข้างล่าง

<EnvelopeLab client:visible />

ขั้นที่สี่คือสิ่งที่ได้ประโยชน์ เมื่อหมุน Master Key เราถอดห่อ DEK ทั้งสามตัวด้วย Key เก่าและหุ้มใหม่ด้วย Key ใหม่ เขียนใหม่ 180 ไบต์ แถวทั้ง 2,500,000 ไม่ถูกแตะ แบบฝึกเช็กว่า DEK ยังเหมือนเดิมและแถวยังถอดรหัสได้ และ Master Key เก่าถอดห่ออะไรไม่ได้อีกแล้ว

## ลบ Key เพื่อลบข้อมูล

มีประโยชน์ที่สองที่ไม่เห็นชัด เมื่อมีคำขอให้ลบข้อมูล เรามีสำเนาหลายที่ ทั้งฐานข้อมูล Replica และ Backup บนเทปที่แก้ไม่ได้ ถ้าตารางหนึ่งเข้ารหัสด้วย DEK ของมันเอง การลบ DEK เพียง 32 ไบต์ทำให้ทุกสำเนาของตารางนั้นอ่านไม่ได้ เรียกว่า **Crypto-shredding**

แบบฝึกทำให้ดูจริง สร้าง Key Store ที่มี DEK ของตาราง `customers` เข้ารหัส 300 แถว แล้วเก็บสำเนาไว้เป็น Backup ตอนที่ Key ยังอยู่ แถวในตารางและใน Backup อ่านได้ปกติ แต่หลังจากลบ Key จาก Key Store ทั้งสองอ่านไม่ได้เลย เพราะไม่มี Key ให้ขอ และลอง Key ตัวอื่นก็ถอดรหัส Backup ไม่ผ่าน (`InvalidTag`)

ข้อควรคิด เทคนิคนี้ใช้ได้เมื่อ DEK ถูกแยกต่อกลุ่มข้อมูลที่เราอยากลบพร้อมกัน ถ้าต้องลบคนเดียวออกจากตารางที่มี 2,000,000 แถว เราไม่มี DEK ต่อคนให้ลบ ต้องมีวิธีอื่น ซึ่งเราจะคุยกันในบทว่าด้วยวงจรชีวิตของข้อมูล

</Step>

## สิ่งที่การเข้ารหัสที่ดิสก์ไม่ช่วย

การเข้ารหัสแบบนี้ปกป้องดิสก์ Backup และเทปที่หลุดออกไป แต่ไม่ได้ปกป้องจากคำสั่งที่รันในนามของแอป เพราะแอปต้องถือ Key เพื่อถอดรหัสไว้ใช้งาน แบบฝึกเก็บค่าที่เข้ารหัสแล้ว 300 แถวไว้ใน SQLite และเขียนฟังก์ชันที่เป็นตัวแทนของแอป รับเงื่อนไข WHERE แล้วถอดรหัสทุกแถวที่ได้ ซึ่งเป็นที่ที่ผู้โจมตีแทรก SQL ได้อย่างในบท Injection ของวิชา Application Security

คำค้นปกติ `pid = 1` ได้ค่าถอดรหัสแล้วหนึ่งค่า แต่เมื่อผู้โจมตีส่ง `pid = 1 OR 1 = 1` แอปถอดรหัสให้ทั้ง 300 ค่า การเข้ารหัสที่ดิสก์ไม่ได้กันอะไรเลยในกรณีนี้ ผู้เขียนสรุปว่าการเข้ารหัสที่เก็บเป็นชั้นหนึ่งของการป้องกัน ที่ต้องมีชั้นอื่นอีก ซึ่งได้แก่การจำกัดว่าใครอ่านอะไรได้ ที่[บทถัดไป](/data-security/access-masking/)จะดู

<Callout type="note" title="ที่ไม่ได้รัน">

ไม่ได้รัน KMS หรือ HSM จริง จึงไม่ได้ทดสอบการตั้งนโยบายว่าใครเรียก Master Key ได้ ไม่ได้ทดสอบการเข้ารหัสที่ฐานข้อมูลทั้งไฟล์ (Transparent Data Encryption) และไม่ได้ทดสอบการค้นหาแบบที่ไม่รั่วความถี่ (Searchable Encryption)

</Callout>
