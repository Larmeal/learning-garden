## ข้อมูลของคนหนึ่งคนอยู่ที่ไหนบ้าง

ที่ผ่านมาเราปกป้องข้อมูล ณ จุดใดจุดหนึ่ง บทนี้ถามว่าข้อมูลของคนหนึ่งคนเดินทางไปที่ไหนตลอดชีวิต เมื่อใครสักคนสมัครกับบริษัทของนาย A ข้อมูลของเขาไปอยู่ในตาราง `users` ตาราง `orders` และ `events` จากนั้นถูกรวมเข้าตารางที่คำนวณต่อ `customer_360` ถูกส่งไปให้พาร์ทเนอร์ในไฟล์ `partner_export` และถูกคัดลอกลงเทป Backup ทุกคืน

พอวันหนึ่งเขามาขอให้ลบข้อมูลของตัวเอง คำถามคือเราต้องไปลบที่ไหนบ้าง ถ้าจำไม่ได้ว่าข้อมูลไปอยู่ที่ไหน เราลบไม่ครบ บทนี้เราทำแพลตฟอร์มเล็ก ๆ ด้วย SQLite ที่มีทุกอย่างข้างบน ผู้ใช้สมมติ 200 คน เพื่อลองทีละขั้น (รัน: `exercises/10_lifecycle.py`)

เริ่มจากต้นทาง คือเรื่องที่ข้อมูลถูกเก็บมาเพื่ออะไร

</Step>

## Consent ผูกกับวัตถุประสงค์

ผู้ใช้ให้ความยินยอมเป็นเรื่อง ๆ (เช่น "ใช้ข้อมูลเพื่อให้บริการ" กับ "ส่งโฆษณา") และถอนได้ แบบฝึกมีตาราง `consents` ที่บันทึกวัตถุประสงค์ วันที่ให้ และวันที่ถอน ผลที่นับได้ จาก 200 คน มี 115 คนที่ยินยอมให้ใช้เพื่อการตลาดอยู่ 19 คนเคยยินยอมแต่ถอนแล้ว และ 66 คนไม่เคยให้ (หนังสือ: Practical Data Privacy บทที่ 3 หน้า 66 เรื่องการเก็บข้อมูล Consent ไปกับข้อมูล)

ทีมการตลาดที่สร้างแคมเปญ ถ้า Join กับตาราง `consents` และเลือกเฉพาะที่ยินยอมและยังไม่ถอน ได้ผู้รับ 115 คนตรงกับจำนวนที่ยินยอม แต่ถ้าสร้างจากตาราง `users` อย่างเดียวก็ได้ 200 คน ซึ่งส่งหาคนที่ไม่ยินยอมอีก 85 คน การควบคุมนี้ไม่ได้อยู่ในตัวข้อมูล ต้องบังคับด้วยวิธีที่ใช้ข้อมูล เช่น View ที่บังคับ Join กับ Consent ตามที่[บทที่แล้ว](/data-security/secure-computation/)เห็น

</Step>

## เก็บนานแค่ไหน

ข้อมูลที่ไม่จำเป็นแล้วควรถูกลบ แบบฝึกตั้งนโยบายเก็บ `events` 90 วัน มี 1,000 แถว เก่ากว่า 90 วัน 696 แถว หลังรันงานลบเหลือ 304 แถว ตรงกับจำนวนที่นับก่อนลบ

แต่มีกับดัก ตาราง `customer_360` ที่คำนวณจากตารางเหล่านี้ยังเก็บ `events_count` ซึ่งรวมจาก Event เก่าเข้าไปแล้ว แบบฝึกเช็กว่าผลรวมใน `customer_360` ยังเท่ากับ 1,000 เหมือนก่อนลบ งานลบข้อมูลเก่าที่ไม่รู้ว่าตารางไหนคำนวณต่อจากตารางที่ลบ ได้แค่ลบต้นทาง ปล่อยค่าที่สรุปไว้ค้างอยู่ ซึ่งบางกรณีก็ถูกต้อง (เป็นแค่สถิติ) บางกรณีไม่ (ถ้าไล่กลับไปหาตัวบุคคลได้)

</Step>

## ลบผู้ใช้คนหนึ่งออกให้หมด

มีผู้ใช้คนหนึ่ง (id 2) ที่ขอให้ลบข้อมูลของเขา ก่อนลบ เขามีแถวอยู่ 6 ตาราง คือ `users` 1 แถว `consents` 2 `orders` 3 `events` 3 `customer_360` 1 และ `partner_export` 1 วิธีที่คนมักทำคือ `DELETE FROM users WHERE id = 2` แล้วถือว่าจบ ผลที่ได้ ตาราง `users` ไม่เหลือเขา แต่อีก 5 ตารางยังเก็บเขาไว้ครบ

ภาพต่อไปนี้คือแพลตฟอร์มของเรา เส้นระหว่างตารางคือ **Lineage** (เส้นทางที่ข้อมูลไหลจากที่หนึ่งไปอีกที่ ซึ่งแบบฝึกกำหนดไว้เองโดยบันทึกว่าตารางไหนสร้างมาจากตารางไหน) ลองเลือกวิธีจัดการทีละแบบ ดูว่าตารางไหนยังเก็บเขาอยู่ และลองกดปุ่มกู้ Backup ที่ใช้ Log การลบ

<LineageLab client:visible />

วิธีที่ถูกคือไล่ตามเส้นทางจากตารางต้นทาง แบบฝึกเดิน Graph จาก `users`, `orders`, `events` และ `consents` ไปตามเส้นจนครบ ได้ 6 ตาราง แล้วลบแถวของผู้ใช้ในทุกตารางที่เจอ ผลคือไม่มีตารางสดไหนเก็บเขาอีก สิ่งที่ทำให้ใช้ได้คือต้องรู้ว่าข้อมูลไหลไปที่ไหน ถ้ามีไฟล์ส่งออกที่ไม่มีใครบันทึกว่ามีอยู่ จะไม่ถูกลบ

</Step>

## Backup บนเทป

เหลืออีกที่ที่เส้นทางข้อมูลของเราไม่ได้ลบ คือ Backup ที่ถ่ายไว้ก่อนคำขอ แบบฝึกเก็บสำเนาของทั้งหกตารางไว้เป็นเทป ซึ่งยังเก็บผู้ใช้คนนั้นครบหลังจากลบจากตารางสดแล้ว เราลบจากเทปไม่ได้ (เทปแก้ไขไม่ได้) และถ้ากู้ Backup ขึ้นมา ผู้ใช้ที่ลบไปแล้วกลับมาทั้งหมด

ทางออกที่แบบฝึกลองคือเก็บ **Log การลบ** ที่มีแค่ id ของผู้ที่ถูกลบ (ไม่มีข้อมูลอื่นของเขา) แล้วใช้ Log นี้ทุกครั้งที่กู้ Backup คือกู้ขึ้นมาแล้วลบ id เหล่านั้นออกทันที ผลที่ Assert ไว้ หลังกู้พร้อมใช้ Log ไม่เหลือผู้ใช้คนนั้นในทั้งหกตาราง (ทั้งที่เทปมีเขาอยู่ครบหกตารางก่อนหน้านั้น) และถ้ากู้โดยไม่ใช้ Log เขากลับมาครบหกตาราง

อีกทางคือใช้ Crypto-shredding ที่เห็นในบทเรื่องเข้ารหัสข้อมูล ถ้าข้อมูลของคนหนึ่งเข้ารหัสด้วย Key ของเขาเอง การลบ Key ทำให้ทุกสำเนาอ่านไม่ได้ แต่แบบฝึกนี้ไม่ได้เข้ารหัสต่อคน

<Callout type="warn" title="ส่วนที่เป็นกฎหมาย">

ในบทนี้ "คำขอให้ลบ" เป็นสิ่งที่ผู้เขียนสมมติขึ้นเพื่อเรียน GDPR ให้สิทธิ์เจ้าของข้อมูลหลายข้อ รวมถึงสิทธิ์ขอให้ลบและสิทธิ์ขอดูข้อมูลของตัวเอง (หนังสือ: Practical Data Privacy บทที่ 8 หน้า 202) และแยกบทบาทของผู้ควบคุมข้อมูลกับผู้ประมวลผล (หนังสือ: Practical Data Privacy บทที่ 8 หน้า 204) แต่ข้อยกเว้น กำหนดเวลา และวิธีปฏิบัติกับ Backup ในกฎหมายจริงละเอียดกว่านี้มาก ผู้เขียนไม่ได้รันอะไรเกี่ยวกับกฎหมาย และเรื่องจริงต้องปรึกษานักกฎหมาย

</Callout>

## สิทธิ์ขอดูข้อมูลใช้แผนที่เดียวกัน

แผนที่ของข้อมูลที่เราสร้างเพื่อลบใช้ตอบอีกคำขอได้ด้วย เมื่อผู้ใช้ขอสำเนาข้อมูลของตัวเอง เราต้องรวมทุกอย่างที่เก็บเกี่ยวกับเขา แบบฝึกใช้ Lineage เดิมกับผู้ใช้อีกคน (id 4) แล้วเจอแถวของเขาครบ 6 ตาราง ถ้าเราไม่มีแผนที่นี้ เราตอบทั้งสองคำขอไม่ได้

บทเรียนของบทนี้คือข้อมูลที่ปลอดภัยไม่ได้หมายถึงแค่ถูกเข้ารหัสหรือถูกปิดไว้ แต่หมายถึงเรารู้ว่ามันอยู่ที่ไหน ใช้เพื่ออะไร จนถึงเมื่อไร และลบได้อย่างไร หนังสือ Practical Data Privacy เสนอการเก็บแหล่งที่มาและ Consent ไปกับข้อมูลตั้งแต่ตอนเก็บ (หนังสือ: Practical Data Privacy บทที่ 3 หน้า 66) ซึ่งทำให้งานเหล่านี้ง่ายขึ้นมาก

</Step>
