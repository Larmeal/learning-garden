## เมื่อไม่มีใครไว้ใจใคร

สามเรื่องที่ผ่านมา ทุกอย่างอาศัยว่ามีใครสักคนถือข้อมูลดิบไว้ ซึ่งเราไว้ใจให้ใส่ Noise ให้ปิดคอลัมน์ให้ แต่บางครั้งไม่มีใครควรถือข้อมูลของทุกคน ตัวอย่างที่ผู้เขียนใช้ในบทนี้มีสองข้อ สามเพื่อนร่วมงานอยากรู้ผลรวมเงินเดือนของทั้งสามคน แต่ไม่มีใครอยากบอกเงินเดือนตัวเอง และสองบริษัทอยากรู้ว่ามีลูกค้าที่ซ้ำกันกี่ราย แต่ไม่อยากส่งรายชื่อทั้งหมดให้อีกฝ่าย

หนังสือ Practical Data Privacy เรียกกลุ่มเทคนิคที่ตอบโจทย์แบบนี้ว่า **Encrypted Computation** คือคำนวณผลลัพธ์จากข้อมูลที่แต่ละฝ่ายซ่อนไว้ โดยไม่มีฝ่ายไหนเห็นข้อมูลของอีกฝ่าย (หนังสือ: Practical Data Privacy บทที่ 7 หน้า 163) หนังสือแยก "ความเป็นส่วนตัว" ออกจาก "ความลับ" ด้วย ความลับคือข้อมูลต้องไม่ถูกเห็น ส่วนความเป็นส่วนตัวคือสิ่งที่ผลลัพธ์เปิดเผยได้ แม้เราจะคำนวณโดยไม่เห็นข้อมูลเลย ผลลัพธ์ก็ยังบอกอะไรเกี่ยวกับข้อมูลได้ (หนังสือ: Practical Data Privacy บทที่ 7 หน้า 166)

บทนี้เราลองสามเทคนิคด้วยโค้ดที่รันได้ Homomorphic Encryption ที่หนังสืออธิบายในหน้า 179 ผู้เขียนไม่ได้รัน

## Secret Sharing: แบ่งความลับเป็นเศษสุ่ม

แนวคิดของ **Additive Secret Sharing** ง่ายมาก ถ้า Ann มีเงินเดือน 52,000 เธอสุ่มตัวเลขสองตัว แล้วคำนวณตัวที่สามให้ผลรวมทั้งสามเท่ากับ 52,000 (หารเอาเศษด้วยจำนวนเฉพาะ M ที่ใหญ่ ซึ่งแบบฝึกใช้ 2 ยกกำลัง 61 ลบ 1) แล้วแจก **Share** หนึ่งตัวให้แต่ละคน ไม่มีใครเห็นเงินเดือนของ Ann (รัน: `exercises/09_secure_computation.py`)

```python
def share(secret, parties, rnd):
    parts = [rnd.randrange(M) for _ in range(parties - 1)]
    return parts + [(secret - sum(parts)) % M]
```

ฟังก์ชันสุ่มตัวเลข n−1 ตัว แล้วตัวสุดท้ายคือส่วนต่างที่ทำให้ผลรวมเท่าความลับ ทั้งสามคนทำแบบนี้กับเงินเดือนของตัวเอง ได้ Share หนึ่งตัวต่อคนต่อเจ้าของ จากนั้นแต่ละคนบวก Share ทั้งหมดที่ตนได้รับ ได้ผลรวมย่อยหนึ่งตัว แล้วทั้งสามเอาผลรวมย่อยมารวมกัน ผลที่ได้คือ 161,000 ซึ่งเท่ากับเงินเดือนสามคนบวกกันพอดี โดยที่ไม่มีใครเห็นเงินเดือนของคนอื่น

ลองเลื่อนเงินเดือนในแล็บข้างล่าง ดูว่าทุก Share เปลี่ยนไปหมดแต่ผลรวมยังถูก แล้วเปลี่ยนมุมมองเป็นคนที่ 1 คนที่ 2 หรือคนที่ 3 ดูว่าแต่ละคนถือแค่คอลัมน์ของตัวเอง ซึ่งเป็นตัวเลขสุ่ม ปุ่ม "ทั้งสามคนรวมกัน" แสดงว่าถ้าเอาครบทั้งสามคอลัมน์ ก็ได้เงินเดือนกลับมา

<SecretShareLab client:visible />

ทำไมคนหนึ่งเห็น Share เดียวแล้วไม่รู้อะไร แบบฝึกตรวจจริงด้วยสถิติ ทำซ้ำ 30,000 ครั้งสำหรับความลับ 0, 52,000 และ 1,000,000,000 แล้วดูเลขท้ายของ Share ที่ 1 ผลคือทุกเลขท้ายปรากฏราว 10% (อยู่ระหว่าง 9% ถึง 11%) ไม่ว่าความลับจะเป็นเท่าไร และสอง Share จากสามบวกกันก็กระจายสม่ำเสมอเหมือนกัน ทั้งสำหรับความลับ 0 และ 100,000 ดังนั้นต้องได้ครบทั้งสามถึงจะรู้ความลับ นี่คือสิ่งที่แล็บแสดงเมื่อเลือกคนเดียว

## Secure Aggregation: Mask ที่หักล้างกัน

เมื่อมีผู้เข้าร่วมเป็นร้อย เช่นสมาร์ทโฟนที่รายงานจำนวนก้าวต่อวัน การแบ่ง Share ระหว่างทุกคู่เป็นภาระ วิธีที่ใช้กันคือ **Secure Aggregation** (หนังสือ: Practical Data Privacy บทที่ 7 หน้า 189) แต่ละคู่ของ Client ตกลงเลขสุ่มร่วมกันหนึ่งตัว Client ที่มีลำดับต่ำกว่าบวกเลขนั้นเข้ากับค่าของตัวเอง ส่วน Client ที่ลำดับสูงกว่าลบออก ผลคือ Server ได้รับแต่ค่าที่ถูกปิด แต่เมื่อรวมทั้งหมด Mask ทุกตัวถูกบวกหนึ่งครั้งและลบหนึ่งครั้ง จึงหักล้างกันหมด

แบบฝึกทำกับ 100 Client ผลที่ Assert ไว้ Server รวมค่าที่ปิดแล้ว 100 ตัว ได้ผลรวมของค่าจริงเป๊ะ และค่าที่ปิดของแต่ละ Client ห่างจากค่าจริงเกิน 10 ยกกำลัง 12 ซึ่ง Server เรียนรู้อะไรเกี่ยวกับ Client คนเดียวจากค่าที่ปิดไม่ได้

จุดอ่อนที่รู้กันดีคือ **การหลุดออก** ถ้า Client คนที่ 17 ปิดแอปหลังจากที่คนอื่นปิดค่าไปแล้ว Mask ที่คนที่ 17 ควรช่วยหักล้างหายไป ผลรวมของอีก 99 คนจึงผิด แบบฝึกเช็กว่าผลรวมผิดจริง โปรโตคอลจริงมีขั้นตอนกู้ Mask ของคนที่หลุด ซึ่งผู้เขียนไม่ได้รัน และเป็นส่วนที่ซับซ้อนที่สุดของโปรโตคอลเหล่านั้น

</Step>

## Private Set Intersection: หาของที่ซ้ำโดยไม่ส่งรายชื่อ

สองบริษัทอยากรู้ว่ามีลูกค้าที่ซ้ำกันกี่ราย **Private Set Intersection (PSI)** ตอบโจทย์นี้ (หนังสือ: Practical Data Privacy บทที่ 7 หน้า 186) เครื่องมือที่เราใช้คือการยกกำลังที่สลับที่ได้ (x ยกกำลัง a) ยกกำลัง b เท่ากับ (x ยกกำลัง b) ยกกำลัง a

ทั้งสองฝ่ายมี Key ลับของตัวเอง (a ของ A และ b ของ B) ฝ่ายหนึ่งยกกำลัง Hash ของลูกค้าทุกรายด้วย Key ของตัวเองแล้วส่งให้อีกฝ่าย อีกฝ่ายยกกำลังซ้ำด้วย Key ของตัวเองแล้วส่งกลับ ลูกค้าที่อยู่ในทั้งสองรายชื่อจะได้ตัวเลขเดียวกันไม่ว่าจะยกกำลังตามลำดับไหน ลองกดทีละขั้นในแล็บข้างล่าง ซึ่งใช้ตัวอย่างเล็ก (p เท่ากับ 1019 และลูกค้าสี่คน) ที่แบบฝึกคำนวณ

<PsiLab client:visible />

แบบฝึกทำจริงกับจำนวนเฉพาะ 127 บิตและอีเมล 300 รายการต่อฝั่ง ซึ่งทับกัน 120 ราย ผลคือส่วนร่วมที่ได้คือ 120 ราย ถูกต้องพอดี และ B เห็นตัวเลข 300 ตัวจาก A ที่ไม่มีตัวไหนตรงกับ Hash ธรรมดาของอีเมลใดเลย พจนานุกรมของอีเมลจึงช่วยไม่ได้ เพราะ B ไม่รู้ Key ของ A

## สิ่งที่ยังรั่วอยู่

PSI ไม่ได้ซ่อนทุกอย่าง แบบฝึกเช็กสิ่งที่รั่ว ข้อแรก แต่ละฝ่ายรู้ขนาดรายชื่อของอีกฝ่าย (300 และ 300) และขนาดของส่วนร่วม (120) ข้อที่สอง ผู้ที่ใส่รายการเพิ่มของตัวเองเข้าไปสอบถามได้ว่าอีกฝ่ายมีลูกค้าคนนี้ไหม ส่วนร่วมจะเพิ่มขึ้นหนึ่งถ้าอีกฝ่ายมี และไม่เพิ่มถ้าไม่มี แบบฝึกลองใส่อีเมลหนึ่งรายการที่อยู่ใน B ส่วนร่วมเป็น 121 และอีกรายการที่ไม่อยู่ ส่วนร่วมยังเป็น 120 โปรโตคอลนี้จึงใช้ได้เมื่อฝ่ายที่ถามมีสิทธิ์ถามเรื่องลูกค้าแต่ละรายอยู่แล้ว

และอย่าลืมความต่างระหว่างความลับกับความเป็นส่วนตัว ผลลัพธ์ที่ถูกต้องของ PSI เองบอกข้อมูลบางอย่างได้ ถ้าต้องการจำกัดสิ่งที่ผลลัพธ์บอก ต้องใช้เทคนิคอย่าง Differential Privacy ร่วมด้วย

<Callout type="note" title="ที่ไม่ได้รัน">

Homomorphic Encryption ที่คำนวณบน Ciphertext ได้โดยตรง และ Federated Learning ที่ฝึกโมเดลโดยข้อมูลอยู่ที่เดิม ผู้เขียนไม่ได้รัน และโปรโตคอลทั้งหมดในบทนี้สมมติว่าผู้เข้าร่วมทำตามขั้นตอน (Semi-honest) ไม่ได้ทดสอบกับผู้ที่โกงขั้นตอน

</Callout>
