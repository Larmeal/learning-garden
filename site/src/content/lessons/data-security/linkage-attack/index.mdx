## ตารางสองใบที่ไม่เคยตั้งใจจะเจอกัน

บริษัทประกันของนาย A ปล่อยตารางประวัติการรักษาให้นักวิจัย โดยลบชื่อออกแล้ว เหลือ Zip วันเกิด เพศ และผลวินิจฉัย ในเมืองเดียวกันมีรายชื่อผู้มีสิทธิ์โหวตที่ใครก็ซื้อหรือขอดูได้ มีชื่อ Zip วันเกิด และเพศของคนที่ลงทะเบียน สองตารางนี้ไม่เคยถูกออกแบบมาให้เจอกัน แต่มีคอลัมน์ที่ตรงกันอยู่สามคอลัมน์

การเอาตารางที่ปล่อยออกไปมาเชื่อมกับตารางอื่นเพื่อระบุตัวคน เรียกว่า **Linkage Attack** หนังสือ Practical Data Privacy เล่าตัวอย่างที่โด่งดังเรื่อง Netflix Prize ที่นักวิจัยเชื่อมประวัติการให้คะแนนหนังที่ไม่มีชื่อกับรีวิวสาธารณะแล้วระบุตัวผู้ใช้ได้ (หนังสือ: Practical Data Privacy บทที่ 4 หน้า 85 และหน้า 88) เราไม่ได้รันตัวอย่างนั้น แต่เราทำเรื่องเดียวกันกับข้อมูลสมมติของเราเอง

สมมติว่ารายชื่อผู้โหวตครอบคลุมคนในตารางของเรา 1,413 จาก 2,000 คน (70.5%) ซึ่งสร้างจากคนในตารางเองด้วย Random แบบกำหนด Seed (รัน: `exercises/03_linkage.py`)

</Step>

## Join แล้วได้อะไร

ผู้โจมตีทำง่าย ๆ จัดผู้โหวตเป็นกลุ่มตาม (Zip, วันเกิด, เพศ) แล้วดูว่าแถวของตารางการแพทย์แต่ละแถวตรงกับผู้โหวตกี่คน ถ้าตรงกับคนเดียว ก็เดาว่าแถวนั้นคือคนนั้น

```python
voter_groups[(zip, birth, sex)].append(name)
cands = voter_groups.get((p.zip, p.birth, p.sex), [])
if len(cands) == 1:      # มีผู้โหวตแค่คนเดียวที่เข้ากับแถวนี้
    named += 1
```

ผลที่ได้ ตารางการแพทย์ที่ลบชื่อแล้ว ถูก Join ได้แถวที่เหลือผู้โหวตคนเดียว 1,410 แถว และ 1,409 แถวในนั้นชื่อถูกต้อง จึงเท่ากับ 70.5% ของคนทั้งตาราง ซึ่งเกือบเท่ากับสัดส่วนคนที่อยู่ในรายชื่อโหวตพอดี นั่นคือเกือบทุกคนที่ถูกระบุได้ก็ถูกระบุแล้ว การลบชื่อแทบไม่ป้องกันใครเลยในกลุ่มนี้ และผู้โจมตีรู้ผลวินิจฉัยของพวกเขาทันที

มีแถวหนึ่งที่ผิด ผู้โจมตีระบุชื่อคนหนึ่ง แต่เจ้าของแถวจริงไม่อยู่ในรายชื่อโหวต เขาบังเอิญมี Zip วันเกิด และเพศตรงกับผู้โหวตอีกคน ซึ่งเป็นเรื่องที่ต้องจำไว้ เพราะการ Join แล้วเจอคนเดียวไม่ได้แปลว่าถูกเสมอ เดี๋ยวเราจะเห็นว่าตัวเลขนี้ยิ่งผิดบ่อยเมื่อข้อมูลหยาบลง

## หยาบวันเกิดกับ Zip ลงแล้วเป็นอย่างไร

วิธีป้องกันแรกที่คนนึกถึงคือเก็บข้อมูลให้หยาบลง เช่น เก็บแค่เดือนกับปีเกิด หรือเก็บ Zip สามหลักแรก ลองเลือกระดับต่าง ๆ ในแล็บข้างล่าง หกแถวทางซ้ายเป็นแถวจริงของตารางที่ไม่มีชื่อ และข้างแถวแต่ละแถวคือผู้มีสิทธิ์เลือกตั้งที่มีค่าตรงกัน ถ้ามีผู้มีสิทธิ์คนเดียวที่ตรง แถวนั้นจะได้ชื่อกลับมาพร้อมโรคของเขา ส่วนตัวเลขใต้แถวนับจากคนทั้ง 2,000 คน

<LinkageLab client:visible />

ผลที่ Assert ไว้ เมื่อวันเกิดเหลือเดือนกับปี ยังระบุชื่อถูก 1,294 คน (65%) เมื่อเหลือแค่ปี ยังถูก 502 คน คือผลวินิจฉัยของคนราวหนึ่งในสี่ยังผูกกับชื่ออยู่ เมื่อเหลือปีกับ Zip สามหลัก ถูก 273 คน และเมื่อเหลือปีกับ Zip สองหลัก ไม่มีใครถูกระบุเลย เพราะทุกกลุ่มมีผู้โหวตหลายคน

ที่น่าสังเกตมีอีกข้อ การทำ Zip สั้นลงอย่างเดียวช่วยน้อยมากเมื่อยังเก็บวันเกิดเต็ม Zip สองหลักยังระบุถูก 1,363 คน เพราะวันเกิดกับเพศแยกคนออกจากกันได้แทบหมดอยู่แล้ว วิธีป้องกันที่ได้ผลคือทำให้ค่าที่แยกคนได้ดีที่สุดหยาบลง ไม่ใช่ค่าที่เราทำสะดวกที่สุด

## ผู้โจมตีผิดได้ และผิดบ่อยขึ้นเมื่อข้อมูลหยาบ

ลองเปรียบเทียบสองตัวเลขที่แบบฝึกนับ ตัวแรกคือแถวที่ Join แล้วเหลือผู้โหวตคนเดียว (ผู้โจมตีกล้าระบุชื่อ) ตัวที่สองคือจำนวนที่ชื่อถูกจริง เมื่อเก็บวันเกิดเต็มกับ Zip ห้าหลัก สองตัวนี้เกือบเท่ากัน (1,410 กับ 1,409) แต่เมื่อเหลือแค่ปีเกิดกับ Zip ห้าหลัก ผู้โจมตีกล้าระบุ 711 แถว และถูกแค่ 502 แถว นั่นคือผิดไปราว 209 ครั้ง

ผู้ปล่อยข้อมูลมักพูดว่า "ผู้โจมตีไม่แน่ใจหรอก" ซึ่งจริงเมื่อข้อมูลหยาบพอ แต่ไม่ใช่ข้อแก้ตัวที่ดี เพราะผู้โจมตีที่ผิดไป 30% ก็ยังได้ผลวินิจฉัยของคนที่ถูกอีก 70% ผู้เขียนจึงไม่เสนอให้ใช้อัตราที่ผู้โจมตีผิดเป็นตัววัดความปลอดภัยอย่างเดียว ควรดูว่าคนที่ถูกระบุถูกต้องมีกี่คน และเป็นใครบ้าง

หนังสือ Practical Data Privacy จัดการโจมตีแบบ Singling Out ไว้อีกประเภท คือไม่ได้ต้องการรู้ชื่อ แต่ต้องการชี้ว่าแถวนี้เป็นคนเดียวที่มีลักษณะเฉพาะ ซึ่งเราเห็นแล้วจาก[บทที่แล้ว](/data-security/pseudonymization/)ตอนนับคนที่อยู่ตัวคนเดียว (หนังสือ: Practical Data Privacy บทที่ 4 หน้า 90)

<Callout type="note" title="ข้อมูลของเราเป็นกรณีง่าย">

รายชื่อผู้โหวตของเราสร้างจากคนในตารางเอง จึงครอบคลุมคนที่ต้องการระบุอย่างสมบูรณ์ ของจริงผู้โจมตีอาจมีแหล่งที่ครอบคลุมน้อยกว่า หรือมากกว่าในบางคอลัมน์ ผู้เขียนไม่ได้ทดสอบกับแหล่งข้อมูลจริง และไม่ได้ลองแหล่งที่มีข้อมูลผิด
