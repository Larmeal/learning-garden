## หนึ่ง Exception ที่พกทุกปัญหา

ลองส่งข้อมูลที่ผิดสี่จุดในโครงสร้างซ้อนกันสามชั้น (รัน: `exercises/06_errors.py`)

```python
class Item(BaseModel):
    sku: str
    qty: int

class Order(BaseModel):
    id: int
    items: list[Item]
    meta: dict[str, int] = {}

bad = {"id": "x",
       "items": [{"sku": "A", "qty": 1}, {"sku": 5, "qty": "y"}],
       "meta": {"k": "v"}}
Order.model_validate(bad)
```

`ValidationError` ที่ได้จะถือสี่ Error ไว้ด้วยกัน โดย `e.error_count()` ได้ 4 และ `e.title` เป็น `"Order"` อีกอย่างคือ `ValidationError` เป็น Subclass ของ `ValueError` ดังนั้น `except ValueError` ของโค้ดเก่าก็จับมันได้ด้วย

ส่วน `e.errors()` จะคืน List ของ Dict หนึ่งตัวต่อหนึ่งปัญหา

```python
{'type': 'int_parsing',
 'loc': ('id',),
 'msg': 'Input should be a valid integer, unable to parse string as an integer',
 'input': 'x',
 'url': 'https://errors.pydantic.dev/2.13/v/int_parsing'}
```

| Key | ความหมาย |
|---|---|
| `type` | รหัสของปัญหา เสถียรกว่าข้อความ ใช้ในโค้ดที่ต้องตัดสินใจตามชนิดของปัญหา |
| `loc` | ตำแหน่งใน Input เป็น Tuple ของ Key และดัชนี |
| `msg` | ข้อความสำหรับคนอ่าน |
| `input` | ค่าที่ทำให้ล้ม |
| `ctx` | ข้อมูลประกอบ (ถ้ามี) เช่น `{'gt': 0}` |
| `url` | ลิงก์ไปหน้าเอกสารของ Error ชนิดนั้น |

</Step>

## Loc: ตามรอยลงไปในโครงสร้างซ้อน

สี่ Error ของตัวอย่างข้างบนมี `loc` ดังนี้

```python
[('id',), ('items', 1, 'sku'), ('items', 1, 'qty'), ('meta', 'k')]
```

อ่านได้ว่า Field `id`, สมาชิกตัวที่ 1 (นับจาก 0) ของ `items` ที่ Field `sku`, ตัวเดียวกันที่ `qty`, และ Key `k` ของ `meta` โดย Loc ใน `list` จะใช้ดัชนีเป็นตัวเลข ส่วนใน `dict` จะใช้ Key เป็นข้อความ และในการแสดงผลแบบข้อความจะเขียนต่อกันด้วยจุด เช่น `items.1.sku`

ถ้า Input มาเป็น JSON ผ่าน `model_validate_json` ตำแหน่งก็รายงานแบบเดียวกัน เช่น `'{"id": 1, "items": [{"sku": "A"}]}'` จะได้ `loc == ("items", 0, "qty")` ชนิด `missing`

ถ้า JSON ผิดไวยากรณ์ ก็เป็น `ValidationError` เหมือนกัน ชนิด `json_invalid` โดย `loc` จะว่าง และข้อความจะบอกตำแหน่งในข้อความ JSON เช่น `Invalid JSON: EOF while parsing a list at line 1 column 20` ผู้เรียกจึงไม่ต้องจับ `json.JSONDecodeError` แยกต่างหาก

</Step>

## errors(), json() และ str() ใช้ต่างกัน

| เมธอด | คืน | ใช้เมื่อ |
|---|---|---|
| `str(e)` | ข้อความหลายบรรทัดอ่านง่าย | แสดงให้คน เช่นใน Log หรือ Traceback |
| `e.errors()` | `list[dict]` | โค้ดที่ต้องประมวลผลต่อ เช่น แปลงเป็นรูปแบบ Response ของ API |
| `e.json()` | JSON String | ส่งต่อเป็นข้อความ |

บรรทัดแรกของ `str(e)` คือ `4 validation errors for Order` ตามด้วยชื่อ Field ที่ผิดทีละบรรทัด (แบบเดียวกับที่เห็นใน [บท 1](/pydantic/first-model/#เมื่อข้อมูลผิด-validationerror))

นอกจากนี้ `errors()` ยังปรับได้สามทาง

```python
e.errors(include_url=False)       # ไม่เอา url
e.errors(include_input=False)     # ไม่เอาค่าที่ผิด
e.errors(include_context=False)   # ไม่เอา ctx
```

<Callout type="warn" title="errors() ที่มี Ctx ไม่ได้เป็น JSON เสมอไป">
เมื่อ Validator โยน `ValueError` เราจะเห็น Exception ตัวเดิมอยู่ใน `ctx["error"]` (แบบฝึกยืนยัน `isinstance(ctx["error"], ValueError)`) แต่ Exception Object ส่งเข้า `json.dumps` ไม่ได้ และจะได้ `TypeError` ถ้าต้องการ JSON ให้ใช้ `e.json()` ซึ่งแปลง `ctx["error"]` เป็นข้อความ `{"error": "too big"}` ให้ หรือจะใช้ `include_context=False` ก็ได้
</Callout>

</Step>

## สร้าง Error ของตัวเอง

ถ้าเรา `raise ValueError("...")` ใน Validator `type` จะเป็น `value_error` เสมอ และข้อความจะมี `Value error, ` นำหน้า ถ้าอยากได้รหัสของตัวเองและข้อความที่ปรับได้ ก็ใช้ `PydanticCustomError` จาก `pydantic_core`

```python
from pydantic_core import PydanticCustomError

@field_validator("code")
@classmethod
def known(cls, v):
    if v not in {"SAVE10"}:
        raise PydanticCustomError(
            "unknown_coupon",                        # type
            "coupon {code} does not exist",          # template
            {"code": v},                             # ctx
        )
    return v
```

`Coupon(code="NOPE")` จะได้ `type='unknown_coupon'`, `msg='coupon NOPE does not exist'`, `ctx={'code': 'NOPE'}` โดยข้อความเป็น Template ที่เติมค่าจาก `ctx` ส่วน `type` เป็นรหัสที่ฝั่ง Client เอาไปจับคู่กับข้อความภาษาของตัวเองได้

ถ้าอยากใช้ Error ชนิดที่ Pydantic มีอยู่แล้ว ก็ใช้ `PydanticKnownError("greater_than", {"gt": 0})` จะได้ `type` เป็น `greater_than` พร้อมข้อความมาตรฐาน

**Exception ที่ถูกแปลงเป็น `ValidationError`** มีแค่ `ValueError` กับ `AssertionError` (และสองคลาสข้างบน) ส่วน Exception อื่นจะหลุดออกไปเหมือนเดิม แบบฝึกโยน `ZeroDivisionError` ใน Validator แล้วก็ได้ `ZeroDivisionError` ออกมาตรง ๆ ซึ่งเป็นแนวคิดเดียวกับ `TypeError` ใน [บท 5](/pydantic/validators/#exception-ชนิดไหนกลายเป็น-validationerror)

</Step>

## ซ่อนค่าที่ผิด: อย่าให้ Password หลุดเข้า Log

`str(e)` แสดง `input_value` ของทุก Error ดังนั้นถ้า Input คือ Password ที่พิมพ์ผิด มันก็จะถูกเขียนลง Log ไปด้วย แบบฝึกยืนยันด้วย Field `pw: int` ที่ส่ง `"hunter2"`

การซ่อนทำได้สองระดับ ระดับที่เรียก `errors()` ให้ใช้ `include_input=False` (ค่าจะหายจากผลที่ได้) ส่วนระดับ Model ให้ตั้งใน Config

```python
class Hidden(BaseModel):
    model_config = {"hide_input_in_errors": True}
    pw: int

Hidden(pw="hunter2")
```

ข้อความที่ได้จะไม่มี `hunter2` เหลืออยู่ บรรทัดของ Error จะเหลือ `Input should be a valid integer, unable to parse string as an integer [type=int_parsing]` และไม่มีส่วน `input_value`

ถ้าใช้ `SecretStr` ([บท 3](/pydantic/types/#ชนิดสำเร็จรูป-ตัวเลขที่มีเงื่อนไข-url-email-secretstr)) ค่าก็ถูกซ่อนใน `repr` อยู่แล้ว แต่ Error จาก Validator ที่คุณเขียนเองก็ควรระวังไม่ใส่ค่าลงใน Message ดังที่ Capstone ใน [บท 12](/pydantic/capstone/#วิธีจ่ายเงิน-discriminated-union-และความลับ) ทำกับเลขบัตร (ข้อความ `card number must be 16 digits` ไม่เอาตัวเลขมาด้วย)

</Step>

## แปลง Error เป็น Response ของ API

รูปแบบที่ใช้บ่อยคือแปลง `errors()` เป็นรายการที่ Client เอาไปแสดงต่อได้ โดยไม่เปิดเผยค่าที่ส่งมา ลองดูตัวอย่างจาก Capstone

```python
def problems(raw: str) -> list[dict]:
    try:
        Order.model_validate_json(raw)
    except ValidationError as e:
        return [
            {"field": ".".join(str(p) for p in x["loc"]),
             "code": x["type"],
             "message": x["msg"]}
            for x in e.errors(include_url=False, include_context=False, include_input=False)
        ]
    return []
```

ฝั่ง Client จะได้ `field` สำหรับชี้จุดในฟอร์ม `code` สำหรับแปลเป็นภาษาของผู้ใช้ และ `message` เป็นข้อความสำรอง โดยข้อมูลที่ผู้ใช้พิมพ์จะไม่ถูกสะท้อนกลับไป ส่วน [บท 12](/pydantic/capstone/#เมื่อข้อมูลผิดทุกจุด-รายการปัญหา) ก็ใช้โครงเดียวกันนี้กับ Order ที่ผิดเก้าจุด

</Step>

## เช็กตัวเอง

- ถ้าส่ง `{"id": "x", "items": [{"sku": 5}]}` เข้า `Order` คุณคิดว่า `loc` ของแต่ละ Error จะเป็นอะไร (ลองเขียนก่อนรัน)
- ทำไม `json.dumps(e.errors())` ถึงล้มเมื่อ Error มาจาก `raise ValueError` ใน Validator และเราแก้ได้สองวิธีอย่างไร
- ถ้าทีมของคุณอยากให้แอปมือถือแสดงข้อความ "คูปองนี้ไม่มีอยู่" เป็นภาษาไทย ควรผูกกับ `msg` หรือ `type` เพราะอะไร

</Step>
