## Required, Optional และ Nullable คนละเรื่องกัน

คำสามคำนี้มักถูกใช้ปนกัน แต่ใน Pydantic V2 มันแยกจากกันอย่างชัดเจน (รัน: `exercises/02_fields.py`)

```python
class A(BaseModel):
    required: int                       # ต้องส่ง, ห้ามเป็น None
    with_default: int = 5               # ไม่ต้องส่ง
    nullable_required: Optional[int]    # ต้องส่ง, แต่เป็น None ได้
    nullable_default: Optional[int] = None   # ไม่ต้องส่ง, เป็น None ได้
    ellipsis: int = Field(...)          # เหมือน required
```

ถ้าเรียก `A()` โดยไม่ส่งอะไรเลย จะได้ Error `missing` สามจุด คือ `required`, `nullable_required` และ `ellipsis` ส่วน `with_default` กับ `nullable_default` ผ่านได้

จุดที่ทำให้คนที่ย้ายมาจาก V1 สะดุดคือ `nullable_required` เพราะใน V1 การเขียน `Optional[int]` เฉย ๆ ทำให้ Field ไม่ต้องส่งและมี Default เป็น `None` แต่ใน V2 `Optional[int]` บอกแค่ว่า **ค่าเป็น `None` ได้** ถ้าอยากให้ไม่ต้องส่งด้วย เราต้องเขียน `= None` เอง

ตอนออกแบบ Field ให้ลองถามตัวเองแยกกันสองข้อ คือผู้เรียกต้องส่งมาไหม และค่าที่ส่งเป็น `None` ได้ไหม สองข้อนี้ตอบได้สี่แบบ ซึ่งสี่แบบข้างบนก็ครอบคลุมครบแล้ว

## Default ทำงานยังไง

**Default ไม่ถูกตรวจ** ค่า Default ที่คุณเขียนในคลาสจะถูกใช้ตามที่เขียนไว้ โดยไม่ผ่านการ Validate

```python
class B(BaseModel):
    tags: list[str] = []
    n: int = "not checked"

B().n    # 'not checked'  ยังเป็น str ทั้งที่ประกาศ int
```

ถ้าอยากให้ Default ผ่านการตรวจด้วย ก็ใช้ `Field("5", validate_default=True)` แล้ว `B2().n` จะเป็น `5`

**Default แบบ Mutable ปลอดภัย** `tags: list[str] = []` ใน Python ธรรมดาเป็นบั๊กคลาสสิก เพราะทุกคนใช้ List ตัวเดียวกัน แต่ Pydantic จะคัดลอกค่า Default ให้แต่ละ Instance แบบฝึกพิสูจน์ไว้ว่า `b1.tags.append("x")` ไม่กระทบ `b2.tags`

**`default_factory`** จะเรียกฟังก์ชันหนึ่งครั้งต่อหนึ่ง Instance จึงเหมาะกับค่าที่ต้องคำนวณใหม่ทุกครั้ง เช่นเวลาปัจจุบัน

```python
class Stamp(BaseModel):
    created: datetime = Field(default_factory=datetime.now)
```

ถ้า Factory รับ Argument หนึ่งตัว มันจะได้ Dict ของ Field ที่ Validate เสร็จแล้วมา (ใช้ได้ตั้งแต่ V2.10)

```python
class WithData(BaseModel):
    first: str
    slug: str = Field(default_factory=lambda data: data["first"].lower())

WithData(first="Ann").slug    # 'ann'
```

## เงื่อนไขของค่า

`Field` รับเงื่อนไขเป็น Keyword ได้ตรง ๆ เลย

```python
class Line(BaseModel):
    sku: str = Field(min_length=3, max_length=8, pattern=r"^[A-Z]+-\d+$")
    qty: int = Field(gt=0, le=100)
    price: float = Field(ge=0)
    note: str = Field("", max_length=10)
```

| Keyword | ใช้กับ | Error Type ที่ได้เมื่อไม่ผ่าน |
|---|---|---|
| `gt`, `ge`, `lt`, `le` | ตัวเลข, วันที่ | `greater_than`, `greater_than_equal`, `less_than`, `less_than_equal` |
| `min_length`, `max_length` | string, list, set, dict | `string_too_short`, `string_too_long`, `too_short`, `too_long` |
| `pattern` | string | `string_pattern_mismatch` |
| `multiple_of` | ตัวเลข | `multiple_of` |
| `max_digits`, `decimal_places` | `Decimal` | `decimal_max_digits`, `decimal_max_places` |

ถ้าส่ง `Line(sku="ab", qty=0, price=-1)` จะได้ Error สามจุดตามลำดับ คือ `string_too_short`, `greater_than`, `greater_than_equal` และ Error แต่ละตัวจะพก `ctx` ที่บอกเงื่อนไขมาด้วย เช่น `{'gt': 0}` กับข้อความ `Input should be greater than 0`

`pattern` ใช้ Regex Engine ของ Rust เป็นค่าเริ่มต้น ซึ่งไม่รองรับ Lookahead ถ้าเขียน `(?=a)` ใน Pattern จะได้ `SchemaError` **ตอนสร้างคลาส** โดยไม่ต้องรอถึงตอน Validate ทางออกมีสองทาง คือตั้ง `regex_engine="python-re"` ใน Config เพื่อใช้ `re` ของ Python หรือเขียน Validator ([บท 5](/pydantic/validators/#เมื่อเงื่อนไขของ-field-ไม่พอ)) แทน

</Step>

## Annotated: เอาเงื่อนไขไปติดกับชนิด แล้วใช้ซ้ำ

ถ้าเงื่อนไขเดียวกันถูกใช้กับหลาย Field การเขียนซ้ำทุกที่ก็น่าเบื่อและแก้ยาก `Annotated` ช่วยให้เราตั้งชื่อชนิดใหม่ที่พกเงื่อนไขไปด้วยได้

```python
from typing import Annotated

Qty = Annotated[int, Field(gt=0, le=100)]
Sku = Annotated[str, Field(pattern=r"^[A-Z]+-\d+$")]

class Line2(BaseModel):
    sku: Sku
    qty: Qty
    backorder: Qty = 1
    parts: list[Qty] = []
```

เงื่อนไขของ `Qty` ทำงานกับสมาชิกของ List ด้วย ถ้าส่ง `Line2(sku="X-1", qty=5, parts=[1, 0, 101])` จะได้สอง Error ที่ตำแหน่ง `parts.1` (`greater_than`) และ `parts.2` (`less_than_equal`) ซึ่งตำแหน่งในรายงานชี้ถึงสมาชิกที่ผิดพอดี

รูปแบบนี้ใช้กับ Validator ได้เหมือนกัน ([บท 5](/pydantic/validators/#validator-แบบ-annotated-ใช้ซ้ำและซ้อนกันได้)) และเป็นวิธีที่ Pydantic เองใช้สร้างชนิดสำเร็จรูปอย่าง `PositiveInt` ([บท 3](/pydantic/types/#ชนิดสำเร็จรูป-ตัวเลขที่มีเงื่อนไข-url-email-secretstr))

</Step>

## Alias: ชื่อใน Input ไม่ตรงกับชื่อใน Python

JSON จาก API ภายนอกมักใช้ `userId` แต่โค้ด Python ของเราอยากได้ `user_id` ซึ่ง `alias` ช่วยแก้ปัญหานี้ได้

```python
class Alias(BaseModel):
    user_id: int = Field(alias="userId")

Alias(userId=1).user_id    # 1
Alias(user_id=1)           # error: field "userId" missing
```

เมื่อมี `alias` Pydantic จะรับ Input ด้วยชื่อ Alias เท่านั้น ถ้าอยากให้รับชื่อจริงด้วย ก็เปิด `populate_by_name=True` ใน Config ([บท 8](/pydantic/models-config/#configdict-ตั้งค่าทั้ง-model))

ตอน Dump ตามค่าเริ่มต้นจะใช้ชื่อ Field จริง และถ้าอยากได้ชื่อ Alias กลับไปก็ส่ง `by_alias=True`

```python
a.model_dump()                 # {'user_id': 1}
a.model_dump(by_alias=True)    # {'userId': 1}
```

Alias มีสามระดับ ซึ่งใช้แยกกันได้เมื่อชื่อขาเข้ากับขาออกไม่เหมือนกัน

```python
class Kinds(BaseModel):
    a: int = Field(validation_alias="in_a", serialization_alias="out_a")
    b: int = Field(validation_alias=AliasChoices("b", "bee", "B"), default=0)
    city: str = Field(validation_alias=AliasPath("address", "city"))

k = Kinds(in_a=1, bee=2, address={"city": "Chiang Mai"})
k.model_dump(by_alias=True)    # {'out_a': 1, 'b': 2, 'city': 'Chiang Mai'}
```

`validation_alias` กำหนดชื่อขาเข้า ส่วน `serialization_alias` กำหนดชื่อขาออก `AliasChoices` รับได้หลายชื่อ (ตัวแรกที่เจอชนะ) และ `AliasPath` ดึงค่าจากข้างในโครงสร้างซ้อน ดังที่เห็นว่า `city` มาจาก `address.city` โดยไม่ต้องสร้าง Model ของ Address

</Step>

## ตัวเลือกอื่นของ Field ที่ใช้บ่อย

```python
class Account(BaseModel):
    user: str
    password: str = Field(exclude=True, repr=False, description="never leaves the process")
    token: str = Field(frozen=True, default="t")
```

- `exclude=True` ทำให้ Field ไม่ออกมาใน `model_dump()` และ `model_dump_json()` โดยผลของ `Account(user="u", password="p").model_dump()` คือ `{'user': 'u', 'token': 't'}`
- `repr=False` ซ่อน Field จาก `repr` ทำให้ `password` ไม่ปรากฏเวลา Log Object
- `frozen=True` ห้ามแก้ Field นั้นหลังสร้าง ถ้าเขียน `acc.token = "new"` จะได้ `ValidationError` ชนิด `frozen_field`
- `description`, `examples`, `title` จะไปอยู่ใน JSON Schema ([บท 9](/pydantic/adapters/#json-schema-จาก-model))

ข้อมูลของแต่ละ Field เก็บไว้ที่ `Model.model_fields` ซึ่งเป็น Dict ของ `FieldInfo` เช่น `Account.model_fields["user"]` พิมพ์ออกมาเป็น `annotation=str required=True` และเรียก `.is_required()` ได้

<Callout type="warn" title="Exclude ไม่ได้ทำให้ค่าปลอดภัยทั้งหมด">
`exclude=True` กับ `repr=False` ซ่อนค่าจากการ Dump และจาก `repr` เท่านั้น ค่ายังอยู่ใน `acc.password` และใน Error ถ้า Validation ล้ม (Error แสดง `input_value`) ถ้าเป็นความลับจริง ๆ ให้ดู `SecretStr` ([บท 3](/pydantic/types/#ชนิดสำเร็จรูป-ตัวเลขที่มีเงื่อนไข-url-email-secretstr)) และ `hide_input_in_errors` ([บท 6](/pydantic/errors/#ซ่อนค่าที่ผิด-อย่าให้-password-หลุดเข้า-log))
</Callout>

</Step>

## เช็กตัวเอง

- `x: Optional[int]` กับ `x: Optional[int] = None` ต่างกันตรงไหน และถ้าย้ายโค้ดมาจาก V1 แบบไหนที่พฤติกรรมเปลี่ยน
- `n: int = "5"` ผ่านไหม และ `n` เป็นชนิดอะไรเมื่อสร้าง Model โดยไม่ส่ง `n`
- ถ้าต้องการรับ JSON Key `userId` แต่ในโค้ดเรียก `user.user_id` และตอนส่งกลับให้ Client ใช้ `userId` เราต้องตั้งอะไรบ้าง

</Step>
