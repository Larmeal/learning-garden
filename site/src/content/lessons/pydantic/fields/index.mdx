## Required, Optional และ Nullable คนละเรื่องกัน

คำสามคำนี้ถูกใช้ปนกันบ่อย แต่ใน Pydantic V2 มันแยกกันชัด (รัน: `exercises/02_fields.py`)

```python
class A(BaseModel):
    required: int                       # ต้องส่ง, ห้ามเป็น None
    with_default: int = 5               # ไม่ต้องส่ง
    nullable_required: Optional[int]    # ต้องส่ง, แต่เป็น None ได้
    nullable_default: Optional[int] = None   # ไม่ต้องส่ง, เป็น None ได้
    ellipsis: int = Field(...)          # เหมือน required
```

เรียก `A()` ไม่ส่งอะไรเลยจะได้ error `missing` สามจุด คือ `required`, `nullable_required` และ `ellipsis` ส่วน `with_default` กับ `nullable_default` ผ่าน

จุดที่ทำให้คนที่ย้ายมาจาก V1 สะดุดคือ `nullable_required` ใน V1 การเขียน `Optional[int]` เฉย ๆ ทำให้ field ไม่ต้องส่งและมี default เป็น `None` ใน V2 `Optional[int]` บอกแค่ว่า **ค่าเป็น `None` ได้** ถ้าอยากให้ไม่ต้องส่งด้วย ต้องเขียน `= None` เอง

ถามตัวเองสองข้อแยกกันตอนออกแบบ field: ผู้เรียกต้องส่งมาไหม และค่าที่ส่งเป็น `None` ได้ไหม สองข้อนี้ตอบได้สี่แบบ และสี่แบบข้างบนครอบคลุมครบ

</Step>

## Default ทำงานยังไง

**Default ไม่ถูกตรวจ** ค่า default ที่คุณเขียนในคลาสถูกใช้ตามที่เขียน ไม่ผ่านการ validate

```python
class B(BaseModel):
    tags: list[str] = []
    n: int = "not checked"

B().n    # 'not checked'  ยังเป็น str ทั้งที่ประกาศ int
```

ถ้าอยากให้ default ผ่านการตรวจด้วย ใช้ `Field("5", validate_default=True)` แล้ว `B2().n` จะเป็น `5`

**Default แบบ mutable ปลอดภัย** `tags: list[str] = []` ใน Python ธรรมดาเป็นบั๊กคลาสสิก เพราะทุกคนใช้ list ตัวเดียวกัน Pydantic คัดลอกค่า default ให้แต่ละ instance แบบฝึกพิสูจน์ว่า `b1.tags.append("x")` ไม่กระทบ `b2.tags`

**`default_factory`** เรียกฟังก์ชันหนึ่งครั้งต่อหนึ่ง instance เหมาะกับค่าที่ต้องคำนวณใหม่ทุกครั้ง เช่นเวลาปัจจุบัน

```python
class Stamp(BaseModel):
    created: datetime = Field(default_factory=datetime.now)
```

factory ที่รับ argument หนึ่งตัวจะได้ dict ของ field ที่ validate เสร็จแล้ว (ใช้ได้ตั้งแต่ V2.10)

```python
class WithData(BaseModel):
    first: str
    slug: str = Field(default_factory=lambda data: data["first"].lower())

WithData(first="Ann").slug    # 'ann'
```

## เงื่อนไขของค่า

`Field` รับเงื่อนไขเป็น keyword ได้ตรง ๆ

```python
class Line(BaseModel):
    sku: str = Field(min_length=3, max_length=8, pattern=r"^[A-Z]+-\d+$")
    qty: int = Field(gt=0, le=100)
    price: float = Field(ge=0)
    note: str = Field("", max_length=10)
```

| keyword | ใช้กับ | error type ที่ได้เมื่อไม่ผ่าน |
|---|---|---|
| `gt`, `ge`, `lt`, `le` | ตัวเลข, วันที่ | `greater_than`, `greater_than_equal`, `less_than`, `less_than_equal` |
| `min_length`, `max_length` | string, list, set, dict | `string_too_short`, `string_too_long`, `too_short`, `too_long` |
| `pattern` | string | `string_pattern_mismatch` |
| `multiple_of` | ตัวเลข | `multiple_of` |
| `max_digits`, `decimal_places` | `Decimal` | `decimal_max_digits`, `decimal_max_places` |

ส่ง `Line(sku="ab", qty=0, price=-1)` ได้สามจุดตามลำดับ `string_too_short`, `greater_than`, `greater_than_equal` และ error แต่ละตัวพก `ctx` ที่บอกเงื่อนไขมาด้วย เช่น `{'gt': 0}` กับข้อความ `Input should be greater than 0`

`pattern` ใช้ regex engine ของ Rust เป็นค่าเริ่มต้น ซึ่งไม่รองรับ lookahead ถ้าเขียน `(?=a)` ใน pattern จะได้ `SchemaError` **ตอนสร้างคลาส** ไม่ต้องรอถึงตอน validate มีสองทางออก ตั้ง `regex_engine="python-re"` ใน config เพื่อใช้ `re` ของ Python หรือเขียน validator ([บท 5](/pydantic/validators/)) แทน

</Step>

## Annotated: เอาเงื่อนไขไปติดกับชนิด แล้วใช้ซ้ำ

ถ้าเงื่อนไขเดียวกันใช้หลาย field เขียนซ้ำทุกที่น่าเบื่อและแก้ยาก `Annotated` ให้เราตั้งชื่อชนิดใหม่ที่พกเงื่อนไขไปด้วย

```python
from typing import Annotated

Qty = Annotated[int, Field(gt=0, le=100)]
Sku = Annotated[str, Field(pattern=r"^[A-Z]+-\d+$")]

class Line2(BaseModel):
    sku: Sku
    qty: Qty
    backorder: Qty = 1
    parts: list[Qty] = []
```

เงื่อนไขของ `Qty` ทำงานกับสมาชิกของ list ด้วย `Line2(sku="X-1", qty=5, parts=[1, 0, 101])` ได้สอง error ที่ตำแหน่ง `parts.1` (`greater_than`) และ `parts.2` (`less_than_equal`) ตำแหน่งในรายงานชี้ถึงสมาชิกที่ผิดพอดี

รูปแบบนี้ใช้กับ validator ได้เหมือนกัน ([บท 5](/pydantic/validators/)) และเป็นวิธีที่ Pydantic เองใช้สร้างชนิดสำเร็จรูปอย่าง `PositiveInt` ([บท 3](/pydantic/types/))

</Step>

## Alias: ชื่อใน Input ไม่ตรงกับชื่อใน Python

JSON จาก API ภายนอกมักใช้ `userId` แต่โค้ด Python ของเราอยากได้ `user_id` `alias` แก้ปัญหานี้

```python
class Alias(BaseModel):
    user_id: int = Field(alias="userId")

Alias(userId=1).user_id    # 1
Alias(user_id=1)           # error: field "userId" missing
```

เมื่อมี `alias` Pydantic รับ input ด้วยชื่อ alias เท่านั้น ถ้าอยากให้รับชื่อจริงด้วย เปิด `populate_by_name=True` ใน config ([บท 8](/pydantic/models-config/))

ตอน dump ตามค่าเริ่มต้นจะใช้ชื่อ field จริง ส่ง `by_alias=True` เมื่ออยากได้ชื่อ alias กลับไป

```python
a.model_dump()                 # {'user_id': 1}
a.model_dump(by_alias=True)    # {'userId': 1}
```

alias มีสามระดับ ใช้แยกกันได้เมื่อชื่อขาเข้ากับขาออกไม่เหมือนกัน

```python
class Kinds(BaseModel):
    a: int = Field(validation_alias="in_a", serialization_alias="out_a")
    b: int = Field(validation_alias=AliasChoices("b", "bee", "B"), default=0)
    city: str = Field(validation_alias=AliasPath("address", "city"))

k = Kinds(in_a=1, bee=2, address={"city": "Chiang Mai"})
k.model_dump(by_alias=True)    # {'out_a': 1, 'b': 2, 'city': 'Chiang Mai'}
```

`validation_alias` กำหนดชื่อขาเข้า `serialization_alias` กำหนดชื่อขาออก `AliasChoices` รับได้หลายชื่อ (ตัวแรกที่เจอชนะ) และ `AliasPath` ดึงค่าจากข้างในโครงสร้างซ้อน ดังที่เห็นว่า `city` มาจาก `address.city` โดยไม่ต้องสร้าง model ของ address

</Step>

## ตัวเลือกอื่นของ Field ที่ใช้บ่อย

```python
class Account(BaseModel):
    user: str
    password: str = Field(exclude=True, repr=False, description="never leaves the process")
    token: str = Field(frozen=True, default="t")
```

- `exclude=True` ทำให้ field ไม่ออกมาใน `model_dump()` และ `model_dump_json()` ผลของ `Account(user="u", password="p").model_dump()` คือ `{'user': 'u', 'token': 't'}`
- `repr=False` ซ่อน field จาก `repr` ตัว `password` จึงไม่ปรากฏเวลา log object
- `frozen=True` ห้ามแก้ field นั้นหลังสร้าง `acc.token = "new"` ได้ `ValidationError` ชนิด `frozen_field`
- `description`, `examples`, `title` ไปอยู่ใน JSON Schema ([บท 9](/pydantic/adapters/))

ข้อมูลของแต่ละ field เก็บไว้ที่ `Model.model_fields` เป็น dict ของ `FieldInfo` เช่น `Account.model_fields["user"]` พิมพ์ออกมาเป็น `annotation=str required=True` และเรียก `.is_required()` ได้

<Callout type="warn" title="exclude ไม่ได้ทำให้ค่าปลอดภัยทั้งหมด">
`exclude=True` กับ `repr=False` ซ่อนค่าจากการ dump และจาก `repr` เท่านั้น ค่ายังอยู่ใน `acc.password` และใน error ถ้า validation ล้ม (error แสดง `input_value`) ถ้าเป็นความลับจริง ให้ดู `SecretStr` ([บท 3](/pydantic/types/)) และ `hide_input_in_errors` ([บท 6](/pydantic/errors/))
</Callout>

</Step>

## เช็กตัวเอง

- `x: Optional[int]` กับ `x: Optional[int] = None` ต่างกันตรงไหน และถ้าย้ายโค้ดมาจาก V1 อันไหนที่พฤติกรรมเปลี่ยน
- `n: int = "5"` ผ่านไหม และ `n` เป็นชนิดอะไรเมื่อสร้าง model โดยไม่ส่ง `n`
- ต้องการรับ JSON key `userId` แต่ในโค้ดเรียก `user.user_id` และตอนส่งกลับให้ client ใช้ `userId` ต้องตั้งอะไรบ้าง

</Step>
