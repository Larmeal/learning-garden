## ภาพรวมสองครึ่ง

Pydantic V2 แยกเป็นสองส่วนที่คนละภาษา

- **pydantic** (Python) อ่าน type hint, config และ decorator ของคลาสคุณ แล้วแปลงเป็นคำอธิบายของการตรวจ
- **pydantic-core** (Rust, ต่อกับ Python ผ่าน PyO3) รับคำอธิบายนั้นไปสร้าง validator กับ serializer ที่ทำงานจริง

ตัวกลางระหว่างสองส่วนคือ **core schema** ซึ่งเป็น `dict` ธรรมดาของ Python บทนี้ตามรอยตั้งแต่ตอนสร้างคลาส จนถึงตอนเรียก `validate_python` โดยทุกข้อเช็กได้จาก `exercises/10_under_the_hood.py`

เรื่องไฟล์ที่เอ่ยถึง มาจาก knowledge graph ของ source เวอร์ชัน 2.13.0 ใน `subjects/pydantic/graphs/pydantic-current/` (230 ไฟล์ แยกเป็นชั้น Public API, Internal Schema Generation, Core Python Bindings และชั้นของ Rust) เวอร์ชันที่แบบฝึกรันก็คือ 2.13.0 เช่นกัน (`verify.py` เช็กให้)

</Step>

## ตอนสร้างคลาส: Metaclass สร้าง Validator

```python
class Item(BaseModel):
    sku: str
    qty: int = Field(gt=0, default=1)

class Order(BaseModel):
    id: int
    items: list[Item]
```

`BaseModel` ใช้ metaclass ชื่อ `ModelMetaclass` (`type(Order).__name__`) ซึ่งทำงานทันทีที่ Python อ่านคำสั่ง `class Order` จนจบ ตามกราฟ ไฟล์ `_internal/_model_construction.py` ทำหน้าที่นี้: ตรวจ namespace, รวบรวม field, เก็บ private attribute, สร้าง core schema แล้วสร้าง validator กับ serializer

ผลของมันเก็บไว้ที่ attribute ของคลาส

```python
Order.__pydantic_complete__          # True   สร้างเสร็จแล้ว
Order.__pydantic_validator__         # SchemaValidator   (ชนิดนี้อยู่ใน pydantic_core._pydantic_core คือโค้ด Rust ที่ compile แล้ว)
Order.__pydantic_serializer__        # SchemaSerializer
Order.__pydantic_core_schema__       # dict ที่ส่งให้ Rust
```

ตอนเขียน `Order(id=1, ...)` สิ่งที่ถูกเรียกใต้ฝากระโปรงคือ `Order.__pydantic_validator__.validate_python(...)` แบบฝึกเรียกตรง ๆ ให้เห็นว่าได้ `Order` กลับมาเหมือนกัน

</Step>

## Core Schema หน้าตาเป็นอย่างไร

ลองเปิดดู `Order.__pydantic_core_schema__`

```python
schema["type"]                         # 'model'
schema["cls"] is Order                 # True
schema["schema"]["type"]               # 'model-fields'
{k: v["schema"]["type"] for k, v in schema["schema"]["fields"].items()}
# {'id': 'int', 'items': 'list'}
```

โครงสร้างคือชั้น `model` ห่อ `model-fields` ซึ่งมี dict ของ field แต่ละตัวพร้อม schema ของชนิดมัน field `items` เป็นชนิด `list` และ `items_schema` ของมันคือ schema ของ `Item` ทั้งก้อน (`inner["cls"] is Item`) เงื่อนไขกับ default ก็อยู่ในนั้น

```python
Item.__pydantic_core_schema__["schema"]["fields"]["qty"]["schema"]
# {'type': 'default', 'schema': {'type': 'int', 'gt': 0}, 'default': 1}
```

`Field(gt=0, default=1)` ใน Python กลายเป็นโครงสร้างสองชั้น: ชั้นนอก `default` กับค่า 1 ชั้นใน `int` ที่มีเงื่อนไข `gt: 0` ความรู้นี้ใช้ได้จริง เพราะ **JSON Schema** ([บท 9](/pydantic/adapters/#json-schema-จาก-model)) และ **การ serialize** ([บท 7](/pydantic/serialization/)) อ่านจาก core schema ตัวเดียวกันนี้ ไม่ได้อ่านจากคลาส Python โดยตรง

ไฟล์ที่กำหนดรูปร่างของ dict เหล่านี้คือ `pydantic_core/core_schema.py` (TypedDict ของทุกชนิด schema กับฟังก์ชันสร้างอย่าง `int_schema`, `list_schema`, `model_schema`) ส่วนไฟล์ที่เดินชนิดของคุณแล้วเขียน dict ออกมาคือ `_internal/_generate_schema.py` ซึ่งกราฟระบุว่าเป็นโมดูลที่ใหญ่ที่สุดของฝั่ง Python

</Step>

## ข้ามฝั่ง Python ไปคุย Rust ตรง ๆ ได้

เพราะ core schema เป็นแค่ dict เราจึงเขียนเองแล้วส่งให้ Rust ได้เลย โดยไม่ผ่าน `BaseModel`

```python
from pydantic_core import SchemaValidator, core_schema as cs

v = SchemaValidator(cs.list_schema(cs.int_schema(gt=0)))
v.validate_python(["1", 2])      # [1, 2]
v.validate_python([0])           # ValidationError ชนิด greater_than
v.validate_json("[1, 2]")        # [1, 2]
```

ผลที่ได้เหมือนที่เคยเห็นทุกอย่าง: lax แปลง `"1"` เป็น `1`, error มี `type` ชื่อเดียวกัน นั่นคือหลักฐานว่า `BaseModel`, `TypeAdapter` และ `validate_call` ล้วนเป็นเปลือกบาง ๆ ที่สร้าง core schema ให้ แล้วส่งให้ `SchemaValidator` ตัวนี้

ใน Rust ตามกราฟ `validators/mod.rs` มี `SchemaValidator` (ตัวที่ Python เรียก) กับขั้น build ที่อ่านแท็ก `type` ของ schema แล้วสร้าง validator ที่ตรงกัน โดยมีไฟล์ต่อชนิดในโฟลเดอร์เดียวกัน: `int.rs`, `string.rs`, `list.rs`, `model.rs`, `union.rs`, `function.rs` และอื่น ๆ เมื่อ validator ตัวนอกทำงาน มันเรียกตัวในของมันต่อเป็นลำดับชั้น ตรงกับโครงสร้างซ้อนของ schema

</Step>

## Input: ทำไมข้อมูลจาก Python กับ JSON ต่างกันที่ strict

ใน Rust validator ไม่ได้อ่านออบเจ็กต์ Python หรือ JSON ตรง ๆ แต่ผ่านชั้นกลางที่เรียกว่า trait `Input` (`input/input_abstract.rs`) มี implementation สามแบบ: ข้อมูล Python (`input_python.rs`), JSON ที่ parse แล้ว (`input_json.rs`) และ string (ใช้กับ key ของ JSON object) แต่ละ method มีเวอร์ชัน strict กับ lax

นี่คือเหตุผลของพฤติกรรมใน [บท 3](/pydantic/types/#strict-กับข้อมูลจาก-json-ไม่เหมือนกับข้อมูลจาก-python) ที่ strict ตัดสินต่างกันตามแหล่ง แบบฝึกใช้ field `pair: tuple[int, int]` ใน model strict

```python
Strict.model_validate_json('{"pair": [1, 2]}').pair    # (1, 2)  ผ่าน JSON มีแต่ array
Strict.model_validate({"pair": [1, 2]})                # error ชนิด tuple_type  list ของ Python ไม่ใช่ tuple
Strict.model_validate({"pair": (1, 2)}).pair           # (1, 2)  ผ่าน
```

การที่ `model_validate_json` ให้ parser JSON ส่งค่าเข้า validator โดยตรง (กราฟระบุว่าใช้ `jiter`) แปลว่าไม่ต้องสร้าง `dict` และ `list` ของ Python ก่อน ซึ่งเป็นที่มาของคำแนะนำให้ใช้ `model_validate_json` กับข้อมูลที่เป็น JSON string ตั้งแต่ต้น การวัดความเร็วจริงไม่ได้ทำในบทนี้

</Step>

## เมื่อคลาสสร้างไม่เสร็จในรอบเดียว

บางครั้ง Pydantic สร้าง validator ตอน `class` จบไม่ได้ เพราะ type hint อ้างถึงชื่อที่ยังไม่มี (forward reference)

```python
class A(BaseModel):
    b: "B"          # B ยังไม่ถูกประกาศ

A.__pydantic_complete__                      # False
type(A.__pydantic_validator__).__name__      # 'MockValSer'
A(b=1)    # PydanticUserError: `A` is not fully defined; you should define `B`, then call `A.model_rebuild()`.
```

ตอนนั้น `__pydantic_validator__` เป็นตัวแทน (`MockValSer`, จาก `_internal/_mock_val_ser.py` ตามกราฟ) ที่รอเรียกใช้แล้วค่อยพยายามสร้างจริง หรือบอกสิ่งที่ขาด

หลังประกาศ `B` แล้ว เรียก `A.model_rebuild()` ก็ได้ validator จริง (`A(b={"x": "1"}).b.x == 1`) หรือบางกรณีไม่ต้องเรียกเอง: คลาส `C` ที่อ้าง `D` ซึ่งประกาศต่อท้ายทันที พอเรียก `C(d={"x": 1})` ครั้งแรก Pydantic ลอง rebuild ให้เอง `C.__pydantic_complete__` ก็เปลี่ยนเป็น `True`

ถ้ารู้ว่าอยากเลื่อนการสร้างอยู่แล้ว ใช้ `defer_build`

```python
class Lazy(BaseModel):
    model_config = ConfigDict(defer_build=True)
    x: int

Lazy.__pydantic_complete__    # False
Lazy(x=1)
Lazy.__pydantic_complete__    # True   สร้างตอนใช้ครั้งแรก
```

เหมาะเมื่อโปรแกรมมี model เป็นร้อย แต่ใช้จริงในแต่ละรอบไม่กี่ตัว จึงเลื่อนต้นทุนการสร้างของตัวที่ไม่ได้ใช้ไปเลย

</Step>

## ต้นทุนอยู่ตอนสร้างคลาส ไม่ใช่ตอน Validate

แบบฝึกจับเวลาสองอย่างบนเครื่องที่รัน

```text
create 200 classes 42 ms, validate 200 times 0.30 ms
```

สร้างคลาส 200 ตัวใช้เวลา 42 ms ส่วน validate ด้วย validator ที่สร้างไว้แล้ว 200 ครั้งใช้ 0.30 ms ตัวเลขขึ้นกับเครื่อง และสองอย่างนี้ทำงานต่างกัน ข้อสรุปที่ `assert` ได้คือสร้างแพงกว่า validate มากกว่า 20 เท่า

ผลต่อการเขียนโค้ด

- ประกาศ model ที่ระดับ module ครั้งเดียว อย่าสร้างคลาสหรือ `TypeAdapter` ในฟังก์ชันที่ถูกเรียกซ้ำ ([บท 9](/pydantic/adapters/#typeadapter-ตรวจชนิดอะไรก็ได้))
- การ import ที่ช้าตอนเริ่มโปรแกรมมาจากการสร้าง model ถ้ามีมาก ให้ลอง `defer_build`
- `import pydantic` เองถูก เพราะ `pydantic/__init__.py` โหลดชื่อแบบ lazy: ตอนแรก `'pydantic.main' in sys.modules` เป็น `False` และกลายเป็น `True` เมื่อเข้าถึง `pydantic.BaseModel` ครั้งแรก

<Callout type="note" title="Validator พิมพ์อธิบายตัวเองได้">
`repr(Order.__pydantic_validator__)` พิมพ์โครงสร้างของ validator ที่ Rust สร้างจริง แบบฝึกได้ 117 บรรทัด เริ่มด้วย `SchemaValidator(title="Order", validator=Model(` และมี `ModelFieldsValidator` อยู่ข้างใน เป็นวิธีดูว่า schema ถูกแปลงเป็นอะไรเมื่อสงสัย
</Callout>

## เช็กตัวเอง

- `Order.__pydantic_validator__` คืออะไร สร้างตอนไหน และเขียนด้วยภาษาอะไร
- ทำไม JSON Schema กับ serializer จึงรู้เรื่อง `Field(gt=0)` ทั้งที่ไม่ได้อ่านคลาส Python ตอนทำงาน
- model หนึ่งอ้าง forward reference ที่ยังไม่ประกาศ จะเกิดอะไรขึ้นถ้าสร้าง instance ทันที และแก้อย่างไร
