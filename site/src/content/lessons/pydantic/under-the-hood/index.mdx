## ภาพรวมสองครึ่ง

Pydantic V2 แยกเป็นสองส่วนที่เขียนด้วยคนละภาษา

- ส่วนแรกคือ **Pydantic** (Python) ซึ่งอ่าน Type Hint, Config และ Decorator ของคลาสคุณ แล้วแปลงเป็นคำอธิบายของการตรวจ
- ส่วนที่สองคือ **Pydantic-core** (Rust, ต่อกับ Python ผ่าน PyO3) ซึ่งรับคำอธิบายนั้นไปสร้าง Validator กับ Serializer ที่ทำงานจริง

ตัวกลางระหว่างสองส่วนคือ **Core Schema** ซึ่งเป็น `dict` ธรรมดาของ Python ในบทนี้เราจะตามรอยตั้งแต่ตอนสร้างคลาส ไปจนถึงตอนเรียก `validate_python` โดยทุกข้อเช็กได้จาก `exercises/10_under_the_hood.py`

ไฟล์ที่เอ่ยถึงในบทนี้มาจาก Knowledge Graph ของ Source เวอร์ชัน 2.13.0 ใน `subjects/pydantic/graphs/pydantic-current/` (230 ไฟล์ แยกเป็นชั้น Public API, Internal Schema Generation, Core Python Bindings และชั้นของ Rust) เวอร์ชันที่แบบฝึกรันก็คือ 2.13.0 เช่นกัน (`verify.py` เช็กให้)

</Step>

## ตอนสร้างคลาส: Metaclass สร้าง Validator

```python
class Item(BaseModel):
    sku: str
    qty: int = Field(gt=0, default=1)

class Order(BaseModel):
    id: int
    items: list[Item]
```

`BaseModel` ใช้ Metaclass ชื่อ `ModelMetaclass` (`type(Order).__name__`) ซึ่งจะทำงานทันทีที่ Python อ่านคำสั่ง `class Order` จนจบ ตามกราฟ ไฟล์ `_internal/_model_construction.py` ทำหน้าที่นี้ โดยตรวจ Namespace, รวบรวม Field, เก็บ Private Attribute, สร้าง Core Schema แล้วสร้าง Validator กับ Serializer

ผลของมันจะถูกเก็บไว้ที่ Attribute ของคลาส

```python
Order.__pydantic_complete__          # True   สร้างเสร็จแล้ว
Order.__pydantic_validator__         # SchemaValidator   (ชนิดนี้อยู่ใน pydantic_core._pydantic_core คือโค้ด Rust ที่ compile แล้ว)
Order.__pydantic_serializer__        # SchemaSerializer
Order.__pydantic_core_schema__       # dict ที่ส่งให้ Rust
```

ตอนเราเขียน `Order(id=1, ...)` สิ่งที่ถูกเรียกอยู่ข้างใต้คือ `Order.__pydantic_validator__.validate_python(...)` ซึ่งแบบฝึกเรียกตรง ๆ ให้เห็นว่าได้ `Order` กลับมาเหมือนกัน

</Step>

## Core Schema หน้าตาเป็นอย่างไร

ลองเปิดดู `Order.__pydantic_core_schema__`

```python
schema["type"]                         # 'model'
schema["cls"] is Order                 # True
schema["schema"]["type"]               # 'model-fields'
{k: v["schema"]["type"] for k, v in schema["schema"]["fields"].items()}
# {'id': 'int', 'items': 'list'}
```

โครงสร้างคือชั้น `model` ห่อ `model-fields` ซึ่งมี Dict ของ Field แต่ละตัวพร้อม Schema ของชนิดมัน Field `items` เป็นชนิด `list` และ `items_schema` ของมันคือ Schema ของ `Item` ทั้งก้อน (`inner["cls"] is Item`) ส่วนเงื่อนไขกับ Default ก็อยู่ในนั้นด้วย

```python
Item.__pydantic_core_schema__["schema"]["fields"]["qty"]["schema"]
# {'type': 'default', 'schema': {'type': 'int', 'gt': 0}, 'default': 1}
```

`Field(gt=0, default=1)` ใน Python กลายเป็นโครงสร้างสองชั้น โดยชั้นนอกคือ `default` กับค่า 1 ส่วนชั้นในคือ `int` ที่มีเงื่อนไข `gt: 0` ความรู้นี้ใช้ได้จริง เพราะ **JSON Schema** ([บท 9](/pydantic/adapters/#json-schema-จาก-model)) และ **การ Serialize** ([บท 7](/pydantic/serialization/)) อ่านจาก Core Schema ตัวเดียวกันนี้ ไม่ได้อ่านจากคลาส Python โดยตรง

ไฟล์ที่กำหนดรูปร่างของ Dict เหล่านี้คือ `pydantic_core/core_schema.py` (TypedDict ของทุกชนิด Schema กับฟังก์ชันสร้างอย่าง `int_schema`, `list_schema`, `model_schema`) ส่วนไฟล์ที่เดินชนิดของคุณแล้วเขียน Dict ออกมาคือ `_internal/_generate_schema.py` ซึ่งกราฟระบุว่าเป็นโมดูลที่ใหญ่ที่สุดของฝั่ง Python

</Step>

## ข้ามฝั่ง Python ไปคุย Rust ตรง ๆ ได้

เพราะ Core Schema เป็นแค่ Dict เราจึงเขียนเองแล้วส่งให้ Rust ได้เลย โดยไม่ผ่าน `BaseModel`

```python
from pydantic_core import SchemaValidator, core_schema as cs

v = SchemaValidator(cs.list_schema(cs.int_schema(gt=0)))
v.validate_python(["1", 2])      # [1, 2]
v.validate_python([0])           # ValidationError ชนิด greater_than
v.validate_json("[1, 2]")        # [1, 2]
```

ผลที่ได้เหมือนที่เราเคยเห็นทุกอย่าง คือ Lax แปลง `"1"` เป็น `1` และ Error มี `type` ชื่อเดียวกัน ซึ่งเป็นหลักฐานว่า `BaseModel`, `TypeAdapter` และ `validate_call` ล้วนเป็นเปลือกบาง ๆ ที่สร้าง Core Schema ให้ แล้วส่งให้ `SchemaValidator` ตัวนี้

ฝั่ง Rust ตามกราฟ `validators/mod.rs` มี `SchemaValidator` (ตัวที่ Python เรียก) กับขั้น Build ที่อ่านแท็ก `type` ของ Schema แล้วสร้าง Validator ที่ตรงกัน โดยมีไฟล์ของแต่ละชนิดอยู่ในโฟลเดอร์เดียวกัน เช่น `int.rs`, `string.rs`, `list.rs`, `model.rs`, `union.rs`, `function.rs` และอื่น ๆ เมื่อ Validator ตัวนอกทำงาน มันจะเรียกตัวในของมันต่อเป็นลำดับชั้น ตรงกับโครงสร้างซ้อนของ Schema

</Step>

## Input: ทำไมข้อมูลจาก Python กับ JSON ต่างกันที่ Strict

ใน Rust ตัว Validator ไม่ได้อ่านออบเจ็กต์ Python หรือ JSON ตรง ๆ แต่อ่านผ่านชั้นกลางที่เรียกว่า Trait `Input` (`input/input_abstract.rs`) ซึ่งมี Implementation สามแบบ ได้แก่ ข้อมูล Python (`input_python.rs`), JSON ที่ Parse แล้ว (`input_json.rs`) และ String (ใช้กับ Key ของ JSON Object) โดยแต่ละ Method มีเวอร์ชัน Strict กับ Lax

นี่คือเหตุผลของพฤติกรรมใน [บท 3](/pydantic/types/#strict-กับข้อมูลจาก-json-ไม่เหมือนกับข้อมูลจาก-python) ที่ Strict ตัดสินต่างกันตามแหล่งข้อมูล แบบฝึกใช้ Field `pair: tuple[int, int]` ใน Model Strict

```python
Strict.model_validate_json('{"pair": [1, 2]}').pair    # (1, 2)  ผ่าน JSON มีแต่ array
Strict.model_validate({"pair": [1, 2]})                # error ชนิด tuple_type  list ของ Python ไม่ใช่ tuple
Strict.model_validate({"pair": (1, 2)}).pair           # (1, 2)  ผ่าน
```

การที่ `model_validate_json` ให้ Parser JSON ส่งค่าเข้า Validator โดยตรง (กราฟระบุว่าใช้ `jiter`) แปลว่าไม่ต้องสร้าง `dict` และ `list` ของ Python ก่อน ซึ่งเป็นที่มาของคำแนะนำให้ใช้ `model_validate_json` กับข้อมูลที่เป็น JSON String ตั้งแต่ต้น ส่วนการวัดความเร็วจริงไม่ได้ทำในบทนี้

</Step>

## เมื่อคลาสสร้างไม่เสร็จในรอบเดียว

บางครั้ง Pydantic ก็สร้าง Validator ตอน `class` จบไม่ได้ เพราะ Type Hint อ้างถึงชื่อที่ยังไม่มี (Forward Reference)

```python
class A(BaseModel):
    b: "B"          # B ยังไม่ถูกประกาศ

A.__pydantic_complete__                      # False
type(A.__pydantic_validator__).__name__      # 'MockValSer'
A(b=1)    # PydanticUserError: `A` is not fully defined; you should define `B`, then call `A.model_rebuild()`.
```

ตอนนั้น `__pydantic_validator__` จะเป็นตัวแทน (`MockValSer`, จาก `_internal/_mock_val_ser.py` ตามกราฟ) ที่รอให้เรียกใช้ แล้วค่อยพยายามสร้างจริง หรือบอกสิ่งที่ขาด

หลังประกาศ `B` แล้ว เราเรียก `A.model_rebuild()` ก็จะได้ Validator จริง (`A(b={"x": "1"}).b.x == 1`) หรือบางกรณีก็ไม่ต้องเรียกเอง เช่นคลาส `C` ที่อ้าง `D` ซึ่งประกาศต่อท้ายทันที พอเรียก `C(d={"x": 1})` ครั้งแรก Pydantic จะลอง Rebuild ให้เอง และ `C.__pydantic_complete__` ก็เปลี่ยนเป็น `True`

ถ้ารู้อยู่แล้วว่าอยากเลื่อนการสร้างออกไป ก็ใช้ `defer_build`

```python
class Lazy(BaseModel):
    model_config = ConfigDict(defer_build=True)
    x: int

Lazy.__pydantic_complete__    # False
Lazy(x=1)
Lazy.__pydantic_complete__    # True   สร้างตอนใช้ครั้งแรก
```

วิธีนี้เหมาะเมื่อโปรแกรมมี Model เป็นร้อย แต่ใช้จริงในแต่ละรอบไม่กี่ตัว เพราะต้นทุนการสร้างของตัวที่ไม่ได้ใช้จะถูกเลื่อนออกไปเลย

</Step>

## ต้นทุนอยู่ตอนสร้างคลาส ไม่ใช่ตอน Validate

แบบฝึกจับเวลาสองอย่างบนคอมพิวเตอร์ที่รันแบบฝึก

```text
create 200 classes 42 ms, validate 200 times 0.30 ms
```

สร้างคลาส 200 ตัวใช้เวลา 42 ms ส่วน Validate ด้วย Validator ที่สร้างไว้แล้ว 200 ครั้งใช้ 0.30 ms ตัวเลขนี้ขึ้นกับคอมพิวเตอร์ที่รัน และสองอย่างนี้ทำงานต่างกัน ข้อสรุปที่ `assert` ได้คือการสร้างแพงกว่า Validate มากกว่า 20 เท่า

เรื่องนี้ส่งผลต่อการเขียนโค้ดสามอย่าง

- ประกาศ Model ที่ระดับ Module ครั้งเดียว และอย่าสร้างคลาสหรือ `TypeAdapter` ในฟังก์ชันที่ถูกเรียกซ้ำ ([บท 9](/pydantic/adapters/#typeadapter-ตรวจชนิดอะไรก็ได้))
- การ Import ที่ช้าตอนเริ่มโปรแกรมมักมาจากการสร้าง Model ถ้ามี Model มาก ให้ลอง `defer_build`
- ส่วน `import pydantic` เองนั้นเบา เพราะ `pydantic/__init__.py` โหลดชื่อแบบ Lazy โดยตอนแรก `'pydantic.main' in sys.modules` เป็น `False` และจะกลายเป็น `True` เมื่อเข้าถึง `pydantic.BaseModel` ครั้งแรก

<Callout type="note" title="Validator พิมพ์อธิบายตัวเองได้">
`repr(Order.__pydantic_validator__)` พิมพ์โครงสร้างของ Validator ที่ Rust สร้างจริง แบบฝึกได้ 117 บรรทัด เริ่มด้วย `SchemaValidator(title="Order", validator=Model(` และมี `ModelFieldsValidator` อยู่ข้างใน จึงเป็นวิธีที่ใช้ดูได้ว่า Schema ถูกแปลงเป็นอะไร เมื่อเราสงสัย
</Callout>

## เช็กตัวเอง

- `Order.__pydantic_validator__` คืออะไร สร้างตอนไหน และเขียนด้วยภาษาอะไร
- ทำไม JSON Schema กับ Serializer จึงรู้เรื่อง `Field(gt=0)` ทั้งที่ไม่ได้อ่านคลาส Python ตอนทำงาน
- Model หนึ่งอ้าง Forward Reference ที่ยังไม่ประกาศ จะเกิดอะไรขึ้นถ้าสร้าง Instance ทันที และแก้อย่างไร
