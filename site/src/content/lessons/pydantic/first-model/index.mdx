## Type Hint ไม่ได้ตรวจอะไรเลย

ใน Python เราเขียน `id: int` ได้ แต่ Interpreter ไม่เคยเอาไปเช็ก มันมีไว้ให้คนอ่านกับ Type Checker อย่าง Mypy ลองดูทั้งคลาสธรรมดาและ `dataclass` (รัน: `exercises/01_first_model.py`)

```python
from dataclasses import dataclass

class Plain:
    id: int
    def __init__(self, id):
        self.id = id

@dataclass
class Row:
    id: int

Plain("not a number").id    # 'not a number'
Row(id="not a number").id   # 'not a number'
```

ทั้งสองแบบรับ String ไปเก็บใน Field ที่ประกาศว่าเป็น `int` โดยไม่บ่นสักคำ ถ้าข้อมูลนี้มาจาก JSON ของ Request หรือจากไฟล์ CSV ความผิดพลาดจะไปโผล่ที่อื่นไกลจากต้นเหตุ เช่นตอนบวกเลขแล้วได้ `TypeError` ในฟังก์ชันที่อยู่ลึกลงไปสามชั้น

Pydantic เข้ามาแก้ตรงจุดนี้ โดยตรวจข้อมูลที่ขอบของโปรแกรม ตรงที่ข้อมูลจากข้างนอกเข้ามา แล้วส่งต่อเข้าไปข้างในเฉพาะข้อมูลที่ผ่านแล้ว

</Step>

## Model แรก

Model คือคลาสที่สืบทอดจาก `BaseModel` แล้วประกาศ Field ด้วย Type Hint

```python
from pydantic import BaseModel

class Customer(BaseModel):
    id: int
    name: str
    email: str
    is_vip: bool = False

c = Customer(id="42", name="Ann", email="ann@example.com")
c.id            # 42
type(c.id)      # <class 'int'>
```

ผู้เรียกส่ง `"42"` ซึ่งเป็น String เข้ามา แต่ `c.id` เป็น `int` จริง ๆ Pydantic ตรวจแล้วแปลงให้ เพราะ `"42"` อ่านเป็นจำนวนเต็มได้ Field ที่มีค่า Default (`is_vip`) ไม่ต้องส่ง ส่วน Field ที่ไม่มี Default ต้องส่ง

ลองพิมพ์ดู

```text
repr: Customer(id=42, name='Ann', email='ann@example.com', is_vip=False)
str : id=42 name='Ann' email='ann@example.com' is_vip=False
```

`repr` ให้ชื่อคลาสกับ Field ครบ ใช้ Debug ได้เลยโดยไม่ต้องเขียน `__repr__` เอง และ `==` ของ Model เปรียบเทียบทั้งชนิดของ Model และค่าทุก Field

</Step>

## Lax Mode: แปลงให้ถ้าแปลงได้อย่างปลอดภัย

โหมดเริ่มต้นของ Pydantic เรียกว่า **Lax** มันรับค่าที่ชนิดไม่ตรงเป๊ะได้ ถ้ามีวิธีแปลงที่ชัดเจนและไม่เสียข้อมูล เรามาลองดูกันว่า `int` กับ `bool` รับอะไรได้บ้าง

| ส่งเข้า Field `int` | ผล |
|---|---|
| `"42"` | `42` |
| `3.0` | `3` |
| `"3.0"` | `3` |
| `True` | `1` |
| `3.5` | Error `int_from_float` (ทิ้งเศษไม่ได้) |
| `"abc"` | error `int_parsing` |
| `None` | error `int_type` |

| ส่งเข้า Field `bool` | ผล |
|---|---|
| `"yes"`, `"1"`, `"T"`, `1` | `True` |
| `"no"`, `"off"` | `False` |
| `"maybe"` | error `bool_parsing` |

หลักของมันคือ Pydantic จะแปลงให้เมื่อค่าเดิมมีความหมายเดียวที่ชัดเจนในชนิดปลายทาง `3.0` คือสามพอดี แต่ `3.5` ถ้าแปลงเป็น `3` ข้อมูลจะหายไปเงียบ ๆ มันจึงปฏิเสธ ส่วน [บท 3](/pydantic/types/#ตารางแปลงของ-lax-mode) จะลงรายละเอียดของตารางนี้ทั้งหมด รวมถึงวิธีปิดการแปลงด้วย Strict Mode

<Callout type="warn" title="ตัวเลขไม่ถูกแปลงเป็น String">
`str` ไม่รับตัวเลขนะ ถ้าส่ง `123` เข้า Field `str` จะได้ Error `string_type` ส่วนฝั่ง V1 เคยแปลงให้ ดังนั้นถ้าโค้ดเก่าของคุณพึ่งพฤติกรรมนั้น จะเจอ Error ตอนย้าย ([บท 11](/pydantic/migration/#พวกที่-3-เปลี่ยนเงียบ-ๆ))
</Callout>

</Step>

## เมื่อข้อมูลผิด: ValidationError

ส่งข้อมูลที่ผิดสี่จุดในครั้งเดียว

```python
Customer(id=3.5, name=None, is_vip="maybe")
```

```text
4 validation errors for Customer
id
  Input should be a valid integer, got a number with a fractional part [type=int_from_float, input_value=3.5, input_type=float]
name
  Input should be a valid string [type=string_type, input_value=None, input_type=NoneType]
email
  Field required [type=missing, input_value={'id': 3.5, 'name': None, 'is_vip': 'maybe'}, input_type=dict]
is_vip
  Input should be a valid boolean, unable to interpret input [type=bool_parsing, input_value='maybe', input_type=str]
```

สังเกตสองอย่าง อย่างแรก Pydantic **รายงานทุกจุดที่ผิดในครั้งเดียว** ไม่ได้หยุดที่จุดแรก ผู้ใช้ฟอร์มจึงแก้ได้ครบในรอบเดียว อย่างที่สอง แต่ละบรรทัดมี `type` (เช่น `int_from_float`) ซึ่งเป็นรหัสที่โปรแกรมเอาไปจัดการต่อได้ ข้อความ `msg` อาจเปลี่ยนตามเวอร์ชัน แต่ `type` นิ่งกว่า

`ValidationError` เป็น Subclass ของ `ValueError` จึงถูกจับด้วย `except ValueError` ได้ เราใช้ `e.error_count()` นับจำนวน และใช้ `e.errors()` ดึงเป็น List ของ Dict ได้ ซึ่ง [บท 6](/pydantic/errors/#errors-json-และ-str-ใช้ต่างกัน) จะลงลึกเรื่องนี้ให้

</Step>

## สามทางเข้า และสองทางออก

สร้าง Model ได้สามทาง

```python
Customer(id=1, name="Ann", email="a@x")                       # keyword argument
Customer.model_validate({"id": 1, "name": "Ann", "email": "a@x"})   # dict หรือ object
Customer.model_validate_json('{"id": 1, "name": "Ann", "email": "a@x"}')   # JSON text
```

ทั้งสามทางได้ผลเท่ากัน ซึ่งแบบฝึกยืนยันด้วย `==` แล้ว ส่วนที่ต่างกันคือ `model_validate_json` จะให้ตัว Parser JSON ส่งค่าเข้า Validator โดยตรง ไม่ได้สร้าง `dict` ของ Python ก่อน และมีกฎเรื่อง Strict ที่ต่างจากข้อมูลที่เป็น Python ([บท 3](/pydantic/types/#strict-กับข้อมูลจาก-json-ไม่เหมือนกับข้อมูลจาก-python) และ [บท 10](/pydantic/under-the-hood/#input-ทำไมข้อมูลจาก-python-กับ-json-ต่างกันที่-strict))

ขาออกก็มีสองทาง

```python
c.model_dump()        # {'id': 1, 'name': 'Ann', 'email': 'a@x', 'is_vip': False}
c.model_dump_json()   # '{"id":1,"name":"Ann","email":"a@x","is_vip":false}'
```

ทางแรกคืน `dict` ส่วนทางที่สองคืน JSON String ที่ไม่มีช่องว่าง ซึ่ง [บท 7](/pydantic/serialization/) จะว่าด้วยการควบคุมสิ่งที่ออกมา

</Step>

## สิ่งที่ Model ทำเมื่อไม่ได้สั่ง

Model มีพฤติกรรมเริ่มต้นอยู่สี่ข้อ ซึ่งแบบฝึกยืนยันแล้ว และมักทำให้คนที่เพิ่งเริ่มประหลาดใจ

**ข้อแรก** Key ที่ไม่รู้จักจะถูกทิ้งไป เช่น `Customer(id=1, name="a", email="e", nickname="x")` ยังสำเร็จ แต่ Object ที่ได้ไม่มี `nickname` เลย ถ้าอยากให้ Error หรืออยากเก็บไว้ เราต้องตั้ง `extra` ใน Config ([บท 8](/pydantic/models-config/#configdict-ตั้งค่าทั้ง-model))

**ข้อที่สอง** Field เป็น Keyword-only `Customer(1, "a", "e")` จึงโยน `TypeError` เพราะ `BaseModel.__init__()` รับ Positional Argument ได้ตัวเดียวคือ `self` ข้อดีคือเราเปลี่ยนลำดับ Field ในคลาสได้โดยไม่ทำให้โค้ดที่เรียกพัง

**ข้อที่สาม** การ Assign ภายหลังไม่ถูกตรวจ หลังสร้าง `c` แล้ว `c.id = "oops"` ก็สำเร็จ และ `c.id` เป็น `"oops"` เพราะมันตรวจเฉพาะตอนสร้าง ถ้าต้องการให้ตรวจทุกครั้งที่ Assign ให้เปิด `validate_assignment` ([บท 8](/pydantic/models-config/#configdict-ตั้งค่าทั้ง-model))

**ข้อสุดท้าย** Model จำได้ว่าผู้เรียกส่ง Field ไหนมา โดย `model_fields_set` เป็น Set ของชื่อ Field ที่ถูกส่งเข้ามาจริง

```python
Customer(id=1, name="a", email="e").model_fields_set
# {'id', 'name', 'email'}   ไม่มี is_vip เพราะใช้ค่า default
Customer(id=1, name="a", email="e", is_vip=False).model_fields_set
# {'id', 'name', 'email', 'is_vip'}
```

ข้อมูลนี้ใช้แยก "ไม่ได้ส่งมา" ออกจาก "ส่งมาเป็นค่า Default" ซึ่งสำคัญกับ PATCH Request เพราะถ้าผู้ใช้ส่งมาแค่ `name` เราควรแก้แค่ `name` ไม่ควรรีเซ็ต Field อื่นเป็นค่า Default ซึ่ง [บท 7](/pydantic/serialization/#เลือก-field-include-exclude-และ-exclude_) จะเอามันไปใช้กับ `exclude_unset`

## เช็กตัวเอง

- ข้อมูล JSON ของ Request ที่มี `"qty": "3"` ผ่านเข้า Field `qty: int` ได้ไหม และถ้าส่ง `"qty": 3.5` ล่ะ เพราะอะไร
- ส่งข้อมูลผิดห้าจุดเข้า Model จะได้ Error กี่ครั้ง และเกิดอะไรขึ้นกับจุดที่สองถึงห้าถ้า Pydantic หยุดที่จุดแรก
- `Customer(id=1, name="a", email="e")` กับ `Customer(id=1, name="a", email="e", is_vip=False)` ให้ `model_dump()` เท่ากัน แล้วมีอะไรที่ต่างกัน

</Step>
