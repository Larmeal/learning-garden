## ConfigDict: ตั้งค่าทั้ง Model

ที่ผ่านมาเราเห็น `populate_by_name`, `strict`, `hide_input_in_errors` ไปบ้างแล้ว ซึ่งทั้งหมดนี้อยู่ใน `model_config`

```python
class Forbid(BaseModel):
    model_config = ConfigDict(extra="forbid")
    a: int
```

บทนี้จะรวมตัวที่ใช้บ่อยที่สุดไว้ให้ครบ (รัน: `exercises/08_models_config.py`)

ตัวแรกคือ **Extra** ซึ่งตัดสินว่าจะทำอย่างไรกับ Key ที่ Model ไม่รู้จัก

| ค่า | ผลเมื่อส่ง `a=1, b=2` |
|---|---|
| `"ignore"` (ค่าเริ่มต้น) | `b` ถูกทิ้ง `model_dump()` ได้ `{"a": 1}` |
| `"forbid"` | Error ชนิด `extra_forbidden` |
| `"allow"` | `b` ถูกเก็บ อ่านได้ที่ `x.b` และรวมใน `model_dump()` ส่วน `x.model_extra` ได้ `{"b": 2}` |

`forbid` เหมาะกับ Input ที่คุณคุมสัญญาเอง เพราะถ้าสะกดชื่อ Field ผิดก็จะโดนจับทันที ส่วนค่าเริ่มต้นที่ทิ้งเงียบ ๆ จะทำให้ `Customer(id=1, nmae="Ann")` ดูเหมือนสำเร็จทั้งที่ชื่อหายไป (ถ้า `name` มีค่า Default)

ตัวต่อมาคือ **Frozen** ที่ทำให้ Model เป็น Immutable และ Hashable

```python
class Point(BaseModel):
    model_config = ConfigDict(frozen=True)
    x: int

p = Point(x=1)
p.x = 2                                  # ValidationError ชนิด frozen_instance
hash(p) == hash(Point(x=1))              # True  ใช้เป็น key ของ dict หรือใส่ set ได้
```

ส่วน **validate_assignment** จะตรวจทุกครั้งที่ Assign

```python
class Checked(BaseModel):
    model_config = ConfigDict(validate_assignment=True)
    n: int

c = Checked(n=1)
c.n = "5"       # c.n เป็น 5 (แปลงด้วย lax ตามปกติ)
c.n = "x"       # ValidationError ชนิด int_parsing, c.n ยังเป็น 5
```

ถ้า Assign ล้มเหลว ค่าเดิมจะไม่เสีย Model จึงยังอยู่ในสถานะที่ถูกต้อง และ Validator จาก [บท 5](/pydantic/validators/#ที่ควรรู้เพิ่ม) ก็จะทำงานตอน Assign เมื่อเปิดตัวเลือกนี้ด้วย

สุดท้ายคือ **ตัวจัดการ String ทั้ง Model**

```python
class Clean(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True, str_to_lower=True, str_min_length=1)
    name: str

Clean(name="  ANN ").name     # 'ann'
Clean(name="   ")             # error string_too_short  (ตัดช่องว่างแล้วว่าง)
```

ลำดับการทำงานคือตัดช่องว่างก่อน แล้วค่อยเช็กความยาว เราจึงจับ String ที่มีแต่ช่องว่างได้

## from_attributes: อ่านจาก Object แทน Dict

ข้อมูลไม่ได้มาเป็น Dict เสมอไป เพราะผลลัพธ์จาก ORM หรือ Dataclass เป็น Object ที่มี Attribute ซึ่ง `from_attributes` จะบอกให้ Model อ่านจาก Attribute เหล่านั้น

```python
@dataclass
class Row:
    id: int
    name: str

class Out(BaseModel):
    model_config = ConfigDict(from_attributes=True)
    id: int
    name: str

Out.model_validate(Row(1, "a")).name     # 'a'
```

ถ้า Model ไม่เปิดตัวเลือกนี้จะได้ Error `model_type` เพราะ Input ไม่ได้เป็น Dict หรือ Instance ของ Model นั้น ส่วนถ้าอยากเปิดเฉพาะการเรียกครั้งเดียว ก็ทำได้ด้วย `Out.model_validate(Row(1, "a"), from_attributes=True)`

</Step>

## Model ซ้อน Model

Field ที่เป็น Model รับได้ทั้ง Dict และ Instance

```python
class Address(BaseModel):
    city: str

class Person(BaseModel):
    name: str
    address: Address

home = Address(city="BKK")
Person(name="a", address=home).address is home                  # True  ใช้ instance เดิม ไม่คัดลอก
Person(name="a", address={"city": "CNX"}).address.city          # 'CNX'  สร้างใหม่จาก dict
```

ถ้าเราส่ง Instance ที่ถูกต้องอยู่แล้วเข้าไป Pydantic จะใช้ตัวนั้นเลยโดยไม่ตรวจซ้ำ ซึ่งเร็ว แต่ก็แปลว่าถ้ามีใครแก้ `home` ทีหลัง `person.address` จะเปลี่ยนตามไปด้วย เพราะเป็นตัวเดียวกัน

`revalidate_instances` เปลี่ยนพฤติกรรมนี้ได้ โดยมีสามค่าคือ `"never"` (ค่าเริ่มต้น), `"always"` และ `"subclass-instances"` ซึ่งแบบฝึกพบว่า **ค่านี้อ่านจาก Config ของ Model ที่กำลังถูกตรวจ (ตัวใน) ไม่ใช่ของตัวนอก**

```python
class Revalidating(BaseModel):
    model_config = ConfigDict(revalidate_instances="always")
    city: str

class Holder(BaseModel):
    inner: Revalidating

r = Revalidating(city="BKK")
Holder(inner=r).inner is r        # False  ตรวจและสร้างใหม่

class Outer(BaseModel):
    model_config = ConfigDict(revalidate_instances="always")
    address: Address

Outer(address=home).address is home    # True  ตั้งที่ตัวนอก ไม่มีผลกับ Address
```

ส่วน `"subclass-instances"` ตรวจใหม่เฉพาะเมื่อ Instance เป็น Subclass ของชนิดที่ประกาศ และผลคือถูกสร้างเป็นชนิดที่ประกาศ เช่นถ้าส่ง `LooseChild` เข้า Field ชนิด `Loose` จะได้ `type(...) is Loose`

</Step>

## Inheritance

Field จะถูกสืบทอดและต่อท้าย โดยเรียงของ Base ก่อนแล้วตามด้วยของ Subclass

```python
class Base(BaseModel):
    id: int

class Child(Base):
    name: str = "x"

list(Child.model_fields)    # ['id', 'name']
```

`model_config` ของ Subclass จะ **ผสาน** กับของ Base ไม่ได้แทนที่ ถ้า Base ตั้งอย่างหนึ่งและ Subclass ตั้งอีกอย่าง เราจะได้ทั้งสองอย่าง (ถ้าเป็น Key เดียวกัน Subclass ชนะ) เช่น `Strictish(Base)` ที่ตั้ง `extra="forbid"` จะได้ `model_config["extra"] == "forbid"` และได้ Error ชนิด `extra_forbidden` เมื่อส่ง Key เกิน

ลำดับ Field ใน Dump จะตามลำดับที่ประกาศในคลาส ไม่ว่าผู้เรียกจะส่งมาลำดับไหน ยกตัวอย่าง `class Order: b: int = 0; a: int = 0` แล้ว `Order(a=1).model_dump()` จะมี Key ตามลำดับ `["b", "a"]`

</Step>

## RootModel: Model ที่ค่าไม่ใช่ Dict

บางครั้งข้อมูลทั้งก้อนเป็น List หรือค่าเดี่ยว แต่เราอยากได้ Method และ Validator ของ Model ซึ่ง `RootModel` เอาไว้ใช้ในกรณีนี้

```python
class Tags(RootModel[list[str]]):
    def first(self):
        return self.root[0]

t = Tags(["a", "b"])
t.first()                 # 'a'
t.model_dump()            # ['a', 'b']
t.model_dump_json()       # '["a","b"]'
Tags.model_validate_json('["z"]').root    # ['z']
```

ข้อมูลจะอยู่ที่ `.root` และ Dump ออกมาเป็นค่าตรง ๆ โดยไม่ครอบด้วย Key `root` เราจึงใช้มันเมื่อ API ส่ง Array ที่ชั้นบนสุดมา หรือเมื่ออยากให้ชนิดค่าเดี่ยวมีพฤติกรรมของตัวเอง

</Step>

## Generic Model

บางครั้งเรามี Model ที่เหมือนกันหมดยกเว้นชนิดข้างใน เช่น Response แบบแบ่งหน้า

```python
T = TypeVar("T")

class Page(BaseModel, Generic[T]):
    items: list[T]
    total: int

Page[int](items=["1", 2], total=2).items       # [1, 2]  แปลงตาม int
Page[int](items=["x"], total=1)                # error int_parsing
Page(items=["1"], total=1).items               # ['1']   ไม่ระบุ T ถือเป็น Any ไม่แปลง
Page[int].__name__                             # 'Page[int]'
```

`Page[int]` จะสร้างคลาสใหม่ที่ตรวจสมาชิกเป็น `int` แต่ถ้าลืมระบุ `[int]` ก็จะไม่มีการตรวจชนิดสมาชิกเลย ซึ่งเป็นเรื่องที่ลืมกันง่ายนะ

</Step>

## Private Attribute และ model_construct

Attribute ที่ขึ้นต้นด้วย `_` จะไม่นับเป็น Field เอาไว้เก็บสถานะภายในที่ไม่ผ่านการตรวจและไม่ออกใน Dump

```python
class WithPrivate(BaseModel):
    a: int
    _cache: dict = PrivateAttr(default_factory=dict)

w = WithPrivate(a=1)
w._cache["k"] = 1
w.model_dump()     # {'a': 1}
```

ส่วน **model_construct** จะสร้าง Model **โดยข้ามการตรวจทั้งหมด**

```python
m = Out.model_construct(id="not an int", name=5)
m.id                 # 'not an int'
m.model_fields_set   # {'id', 'name'}
```

ใช้ได้เมื่อข้อมูลมาจากแหล่งที่เชื่อถือได้ 100% และต้องการความเร็ว เช่นอ่านกลับจากที่ตัวเองเพิ่งเขียน แต่ห้ามใช้กับ Input ของผู้ใช้เด็ดขาด เพราะจะไม่มีอะไรจับค่าผิดเลย

การใช้ `==` ระหว่าง Model จะเทียบทั้งชนิดและค่า `Address(city="a") == Address(city="a")` เป็น `True` แต่ `Address(city="a") == {"city": "a"}` เป็น `False`

<Callout type="try" title="ลองทำใน Repo นี้">
ลองเปลี่ยน `revalidate_instances` ในแบบฝึกจาก `Outer` ให้ไปอยู่ที่ `Address` แล้วดูว่า `assert Outer(address=home).address is home` ยังจริงอยู่ไหม พร้อมลองอธิบายว่าทำไม
</Callout>

## เช็กตัวเอง

- API ภายนอกส่ง Key ที่ Model ไม่รู้จักมา คุณอยากให้ทิ้ง เก็บ หรือ Error แต่ละแบบเหมาะกับสถานการณ์ไหน
- `Page(items=["1"], total=1)` กับ `Page[int](items=["1"], total=1)` ได้ `items` ต่างกันยังไง
- ตั้ง `revalidate_instances="always"` ที่ Model ตัวนอก แล้วคาดหวังว่าตัวในถูกตรวจซ้ำ จะได้ผลไหม

</Step>
