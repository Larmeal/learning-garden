## ปัญหา: ค่า "5" ควรเป็น Int หรือ Str

`Union[int, str]` บอกว่ารับได้ทั้งสองชนิด แล้วถ้าส่ง `"5"` เข้าไป ผลควรเป็น `5` หรือ `"5"` กันนะ ถ้า Pydantic ลองตามลำดับ ซึ่งก็คือ `int` ก่อน เราก็จะได้ `5` ซึ่งหลายคนไม่คาดคิด เพราะ `"5"` เป็น String อยู่แล้ว

Pydantic V2 เลือกวิธีที่เรียกว่า **Smart Mode** เป็นค่าเริ่มต้น (รัน: `exercises/04_unions.py`)

```python
ok(Union[int, str], "5")    # '5'   ชนิด str
ok(Union[int, str], 5)      # 5     ชนิด int
```

กติกาแบบง่ายคือ ถ้ามีสมาชิกของ Union ที่ชนิดตรงเป๊ะกับค่า (ไม่ต้องแปลง) ตัวนั้นจะชนะ และลำดับที่เขียนไม่สำคัญ เช่น `ok(Union[float, int], 5)` ได้ `int` เพราะ `5` เป็น `int` อยู่แล้ว

ถ้าไม่มีตัวไหนตรงเป๊ะ Pydantic ถึงจะมาลองแปลงแบบ Lax เช่น `ok(Union[int, float], "5")` ได้ `5` (ชนิด `int`) และ `ok(Union[str, int], 5.0)` ได้ `5` เพราะ `float` ที่ไม่มีเศษแปลงเป็น `int` ได้ แต่แปลงเป็น `str` ไม่ได้

</Step>

<Step>

## left_to_right: ลองตามลำดับ

ถ้าอยากได้พฤติกรรมแบบ "ตัวแรกที่สำเร็จชนะ" ให้ตั้ง `union_mode`

```python
class LeftToRight(BaseModel):
    x: Union[int, str] = Field(union_mode="left_to_right")

LeftToRight(x="5").x    # 5  ชนิด int
```

คราวนี้ลำดับมีผลแล้ว `"5"` จะลองเป็น `int` ก่อน พอสำเร็จก็เลยได้ `5` เราใช้ Mode นี้เมื่อตั้งใจให้ลำดับเป็นตัวตัดสิน และเมื่อต้องการให้ผลคาดเดาง่ายกว่า Smart Mode ซึ่งพิจารณาหลายปัจจัยพร้อมกัน

`Optional[X]` ก็คือ `Union[X, None]` นั่นเอง `ok(int | None, None)` ได้ `None` และ `ok(int | None, "3")` ได้ `3` ส่วนไวยากรณ์ `X | Y` ของ Python 3.10 ขึ้นไปก็ใช้ได้เหมือนกัน

</Step>

## Error ของ Union: หนึ่งรายการต่อหนึ่งสมาชิก

เมื่อไม่มีสมาชิกไหนรับค่าได้ Pydantic จะรายงานเหตุผลของทุกตัว

```python
errs(Union[int, list[int]], "x")
# [('int', 'int_parsing'), ('list[int]', 'list_type')]
```

ตัวแรกในแต่ละคู่คือ `loc` ซึ่งต่อชื่อชนิดของสมาชิกเข้าไป เพื่อบอกว่า Error มาจากสมาชิกตัวไหน ถ้าสมาชิกเป็นชนิดง่าย ๆ ก็อ่านชัดเจนดี แต่ถ้าเป็น Model ใหญ่ ๆ รายงานจะยาวมาก ซึ่งเราจะแก้ด้วย Discriminated Union ในหัวข้อข้างล่าง

</Step>

<Step>

## Model หลายตัวใน Union

เมื่อสมาชิกเป็น Model คำถามจะเปลี่ยนเป็น "ข้อมูลนี้ตรงกับ Model ไหนที่สุด"

```python
class Cat(BaseModel):
    name: str
    lives: int = 9

class Dog(BaseModel):
    name: str
    good_boy: bool = True

ok(Union[Cat, Dog], {"name": "x", "good_boy": False})   # Dog
ok(Union[Cat, Dog], {"name": "x", "lives": 3})          # Cat
```

Smart Mode จะนับว่าแต่ละ Model ได้รับ Field จากข้อมูลกี่ตัว (`model_fields_set` จาก [บท 1](/pydantic/first-model/#สิ่งที่-model-ทำเมื่อไม่ได้สั่ง)) และ Model ที่ได้ Field มากกว่าจะชนะ

ถ้าเสมอกัน จะได้ตัวทางซ้ายก่อน เช่นส่ง `{"name": "x"}` ซึ่งทั้งสอง Model ได้ Field เดียว แบบฝึกได้ `Cat` จาก `Union[Cat, Dog]` และได้ `Dog` เมื่อสลับเป็น `Union[Dog, Cat]` กรณีเสมอกันจึงพึ่งลำดับ ถ้าข้อมูลของคุณมีกรณีแบบนี้ ลำดับที่เขียนจะกลายเป็นตัวตัดสินที่ซ่อนอยู่ และเราควรใช้ Discriminated Union แทน

</Step>

<Step>

## Discriminated Union: ดู Field เดียวแล้วเลือกให้ตรง

ถ้าข้อมูลแต่ละแบบมี Field ที่บอกชนิดอยู่แล้ว เช่น `"kind": "card"` เราก็บอก Pydantic ให้ดู Field นั้นแล้วเลือก Model ได้เลย ไม่ต้องลองทีละตัว

```python
class CardPay(BaseModel):
    kind: Literal["card"]
    number: str

class QrPay(BaseModel):
    kind: Literal["qr"]
    ref: str

Pay = Annotated[Union[CardPay, QrPay], Field(discriminator="kind")]

ok(Pay, {"kind": "qr", "ref": "r1"})      # QrPay(kind='qr', ref='r1')
```

ผลที่เห็นได้ชัดที่สุดคือตอนเกิด Error ลองส่ง `{"kind": "card"}` ซึ่งขาด `number` ดู

```text
union ธรรมดา: [('CardPay.number', 'missing'),
               ('QrPay.kind', 'literal_error'),
               ('QrPay.ref', 'missing')]
discriminated: [('card.number', 'missing')]
```

Union ธรรมดารายงานสามเรื่อง ซึ่งสองเรื่องหลังไม่เกี่ยวเลย เพราะข้อมูลนี้ไม่ได้เป็น `QrPay` มาตั้งแต่ต้น ส่วน Discriminated Union จะเลือก `CardPay` จาก `kind` แล้วรายงานเฉพาะสิ่งที่ผิดใน `CardPay` โดย `loc` จะใช้ Tag (`card`) นำหน้า

ส่วนเมื่อ Tag ใช้ไม่ได้ ก็มี Error เฉพาะของมันอยู่สองแบบ

- `{"kind": "cash"}` ได้ `union_tag_invalid` (Tag ไม่ตรงกับตัวไหน)
- `{"ref": "r1"}` ได้ `union_tag_not_found` (ไม่มี Field `kind` เลย)

วิธีนี้ใช้กับ JSON ได้เหมือนกัน เช่น `TypeAdapter(Pay).validate_json('{"kind":"card","number":"4111"}')` ได้ `CardPay`

นอกจาก Error จะอ่านง่ายกว่าแล้ว Discriminated Union ยังเร็วกว่าด้วย เพราะ Validator ไม่ต้องลองหลายตัว และ JSON Schema ที่ได้ก็บอก Client ชัดเจนว่า Field ไหนเป็นตัวแยก ([บท 9](/pydantic/adapters/#json-schema-จาก-model) และ [บท 12](/pydantic/capstone/#สัญญาสำหรับฝั่งที่ส่งมา-json-schema))

<Callout type="tip" title="ใช้เมื่อไหร่">
ถ้า Union ของ Model มี Field ที่เป็นตัวบอกชนิดอยู่แล้ว ให้ใช้ Discriminated Union เสมอ ยกเว้นข้อมูลไม่มี Tag จริง ๆ ซึ่งก็มีทางออกให้ในหัวข้อถัดไป
</Callout>

</Step>

## Callable Discriminator: เมื่อข้อมูลไม่มี Tag

บางครั้งไม่มี Field ไหนบอกชนิดตรง ๆ เราต้องดูจากรูปร่างของค่าแทน เช่นรับ `int` หรือ `str` ในกรณีนี้ให้ใช้ `Discriminator` กับฟังก์ชันที่ตอบชื่อ Tag และใช้ `Tag` ติดป้ายสมาชิกแต่ละตัว

```python
def which(v):
    if isinstance(v, int):
        return "int"
    if isinstance(v, str):
        return "str"
    return None

Either = Annotated[
    Union[Annotated[int, Tag("int")], Annotated[str, Tag("str")]],
    Discriminator(which),
]

ok(Either, "5")   # '5'
ok(Either, 5)     # 5
ok(Either, 5.5)   # error union_tag_not_found  (ฟังก์ชันคืน None)
```

ฟังก์ชันจะคืน `None` เมื่อไม่รู้จักค่า ซึ่งกลายเป็น `union_tag_not_found` วิธีนี้ยืดหยุ่นกว่า แต่เราต้องเขียนฟังก์ชันเอง และฟังก์ชันนั้นต้องจัดการ Input ได้ทุกแบบที่เป็นไปได้ (Dict, Object หรืออื่น ๆ)

</Step>

<Step>

## เช็กตัวเอง

- ทำไม `ok(Union[int, str], "5")` ถึงได้ `"5"` และถ้าเปลี่ยนเป็น `Field(union_mode="left_to_right")` ผลเป็นอะไร
- Model สองตัวมี Field ร่วมกันเยอะ และข้อมูลที่ส่งมามีแต่ Field ร่วม Smart Mode เลือกตัวไหน และคุณจะเลี่ยงความคลุมเครือนี้ยังไง
- Error ของ `Union[CardPay, QrPay]` กับ `Annotated[Union[CardPay, QrPay], Field(discriminator="kind")]` ต่างกันยังไงเมื่อ `kind="card"` แต่ขาด `number`

</Step>
