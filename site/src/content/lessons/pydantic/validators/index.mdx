## เมื่อเงื่อนไขของ Field ไม่พอ

`Field(gt=0)` และ `pattern` ตรวจได้ทีละค่า แต่บางกฎต้องใช้ตรรกะเพิ่ม เช่น Username ต้องเป็นตัวอักษรกับตัวเลขเท่านั้นแล้วแปลงเป็นตัวเล็ก หรือ Password สองช่องต้องตรงกัน สำหรับกรณีนี้ Pydantic ให้ Validator มาสองตัวหลัก คือ `field_validator` (ตรวจ Field) และ `model_validator` (ตรวจทั้ง Model)

```python
class Signup(BaseModel):
    username: str
    password: str
    password2: str

    @field_validator("username")
    @classmethod
    def clean_username(cls, v: str) -> str:
        if not v.isalnum():
            raise ValueError("must be letters and digits only")
        return v.lower()

    @field_validator("password2")
    @classmethod
    def same_password(cls, v: str, info: ValidationInfo) -> str:
        if "password" in info.data and v != info.data["password"]:
            raise ValueError("passwords do not match")
        return v
```

(รัน: `exercises/05_validators.py`) มีสามอย่างที่ต้องจำ อย่างแรก ค่าที่ Validator **คืน** จะแทนค่าเดิม (`"Ann99"` กลายเป็น `"ann99"`) อย่างที่สอง Validator จะโยน `ValueError` เมื่อไม่ผ่าน และอย่างสุดท้าย ต้องใส่ `@classmethod` ไว้ใต้ `@field_validator`

ถ้าส่ง `username="a b", password="x", password2="y"` จะได้สอง Error ทั้งคู่ชนิด `value_error` โดยข้อความขึ้นต้นว่า `Value error, ` ตามด้วยข้อความที่เราเขียน

## After, Before, Wrap, Plain

`field_validator` มีสี่ Mode ซึ่งต่างกันที่ว่าทำงานตอนไหนเมื่อเทียบกับการตรวจชนิดของ Pydantic

| Mode | ทำงานเมื่อ | รับอะไร | ใช้กับ |
|---|---|---|---|
| `after` (ค่าเริ่มต้น) | หลัง Pydantic ตรวจชนิดผ่านแล้ว | ค่าที่ตรวจแล้ว (ชนิดถูกต้อง) | กฎของธุรกิจ, ทำความสะอาดค่า |
| `before` | ก่อนตรวจชนิด | Input ดิบ ชนิดอะไรก็ได้ | แปลงรูปแบบ Input ให้ Pydantic รับได้ |
| `wrap` | ห่อรอบการตรวจ | Input ดิบ และ `handler` ที่เรียกการตรวจเดิม | ดักผลหรือ Error ของการตรวจเดิม |
| `plain` | แทนที่การตรวจเดิมทั้งหมด | Input ดิบ | ชนิดที่ Pydantic ไม่รู้จัก |

**After** ไว้ใจชนิดของค่าได้เสมอ ถ้าส่ง `username=123` เข้า Model ข้างบน Validator จะไม่ถูกเรียกเลย เพราะ Pydantic ตัดที่ `string_type` ไปแล้ว ผลคือได้ Error เดียวที่ไม่มี `Value error, ` นำหน้า เราจึงเขียน Validator แบบ After ให้สั้นได้ โดยไม่ต้องกลัวว่าค่าจะผิดชนิด

ส่วน **Before** ใช้เมื่อ Input ต้องจัดรูปก่อนเข้าตรวจ

```python
class Tags(BaseModel):
    tags: list[str]

    @field_validator("tags", mode="before")
    @classmethod
    def split(cls, v):
        return v.split(",") if isinstance(v, str) else v

Tags(tags="a,b").tags      # ['a', 'b']
Tags(tags=["c"]).tags      # ['c']
```

หลังจาก Before คืนค่ามาแล้ว Pydantic ยังตรวจชนิดต่อ ดังนั้นถ้าฟังก์ชันคืน List ของตัวเลข ก็จะติดที่ `list[str]` ตามปกติ

## ValidationInfo: อ่าน Field ที่ผ่านมาแล้ว และ Context

Validator รับ Argument ตัวที่สองเป็น `ValidationInfo` ได้ ซึ่งข้างในมี `data` (Field ที่ตรวจเสร็จและผ่านแล้ว) `field_name` และ `context`

`info.data` มีข้อจำกัดสองข้อที่ต้องรู้ ข้อแรก มีเฉพาะ Field ที่ **ประกาศก่อน** Field ที่กำลังตรวจ (ตามลำดับในคลาส) เพราะ Pydantic ตรวจตามลำดับนั้น ข้อสอง Field ที่ตรวจไม่ผ่านจะ **ไม่อยู่ใน** `info.data` ซึ่งแบบฝึกพิสูจน์ข้อสองให้ดู

```python
class Order(BaseModel):
    qty: int
    note: str

    @field_validator("note")
    @classmethod
    def look(cls, v, info: ValidationInfo):
        seen["keys"] = sorted(info.data)
        return v

Order(qty="x", note="n")   # ล้มที่ qty → seen["keys"] == []
Order(qty=1, note="n")     # → seen["keys"] == ["qty"]
```

ตัวอย่าง `same_password` ข้างบนจึงเขียน `"password" in info.data` ก่อนอ่านค่า เพราะถ้า `password` ล้ม ตัวนี้จะไม่อยู่ใน `info.data` และถ้าไม่เช็กก็จะเจอ `KeyError`

ส่วน **Context** คือ Dict ที่ผู้เรียกส่งเข้ามาตอน Validate เพื่อให้ Validator ใช้ข้อมูลที่ไม่ได้อยู่ในตัว Input

```python
class Ctx(BaseModel):
    price: float

    @field_validator("price")
    @classmethod
    def vat(cls, v, info: ValidationInfo):
        rate = (info.context or {}).get("vat", 0)
        return round(v * (1 + rate), 2)

Ctx.model_validate({"price": 100}).price                          # 100
Ctx.model_validate({"price": 100}, context={"vat": 0.07}).price   # 107.0
```

ระวังว่า `info.context` จะเป็น `None` ถ้าผู้เรียกไม่ส่งมา เราจึงต้องจัดการกรณีนั้นด้วย

</Step>

## Validator แบบ Annotated: ใช้ซ้ำและซ้อนกันได้

Validator ที่ผูกกับ Field ผ่านชื่อจะใช้ได้ในคลาสเดียว ถ้าอยากใช้กฎเดียวกันกับหลายคลาส ให้ผูกกับ **ชนิด** ด้วย `Annotated` แบบที่ [บท 2](/pydantic/fields/#annotated-เอาเงื่อนไขไปติดกับชนิด-แล้วใช้ซ้ำ) ทำกับ `Field`

```python
from pydantic import AfterValidator, BeforeValidator, PlainValidator, WrapValidator

Stacked = Annotated[
    int,
    BeforeValidator(mark("before1")),
    BeforeValidator(mark("before2")),
    AfterValidator(mark("after1")),
    AfterValidator(mark("after2")),
]
```

เมื่อซ้อนหลายตัว ลำดับการทำงานที่แบบฝึกได้คือ

```text
['before2', 'before1', 'after1', 'after2']
```

`after` ทำงานตามลำดับที่เขียน (บนลงล่าง) ส่วน `before` ทำงานย้อนกลับ (ล่างขึ้นบน) จำง่าย ๆ ได้ว่า Validator ถูกห่อซ้อนกันเป็นชั้น ตัวที่เขียนทีหลังจะอยู่นอกสุดสำหรับ Before และอยู่ในสุดสำหรับ After

**WrapValidator** จะได้ `handler` ที่เรียกการตรวจเดิม แล้วจับผลหรือ Error ได้

```python
def default_on_error(v, handler):
    try:
        return handler(v)
    except ValidationError:
        return 0

class Lenient(BaseModel):
    n: Annotated[int, WrapValidator(default_on_error)]

Lenient(n="x").n    # 0
Lenient(n="7").n    # 7
```

**PlainValidator** จะแทนที่การตรวจเดิมทั้งหมด เช่น `Annotated[int, PlainValidator(lambda v: int(v) * 2)]` รับ `"4"` แล้วได้ `8` และ Pydantic ไม่ได้ตรวจอะไรอีก ถ้าฟังก์ชันคืนผิดชนิดก็ถือว่าผ่าน จึงควรใช้เมื่อคุณรู้ว่ากำลังทำอะไรอยู่เท่านั้นนะ

</Step>

## model_validator: กฎที่คร่อมหลาย Field

กฎอย่าง "`low` ต้องไม่เกิน `high`" เกี่ยวกับสอง Field เราจึงตรวจที่ระดับ Model

```python
class Range(BaseModel):
    low: int
    high: int

    @model_validator(mode="after")
    def ordered(self):
        if self.low > self.high:
            raise ValueError("low must not be above high")
        return self
```

Validator แบบ `after` จะได้ Instance ที่สร้างเสร็จแล้ว (`self`) และต้องคืน `self` ผลจาก `Range(low=5, high=1)` คือได้ Error เดียว ที่ `loc` ว่าง (ไม่ผูกกับ Field ไหน) และมีข้อความ `Value error, low must not be above high`

มีข้อควรรู้อย่างหนึ่งคือ ถ้ามี Field ใดตรวจไม่ผ่าน `after` Validator จะ **ไม่ทำงาน** เลย `Range(low="x", high=1)` จึงได้ `int_parsing` อย่างเดียว กฎคร่อม Field เลยไม่รบกวนรายงานของข้อผิดพื้นฐาน และเราเขียนโดยไว้ใจได้ว่าทุก Field ถูกต้องแล้ว

ส่วน `mode="before"` จะได้ Input ดิบของทั้ง Model ซึ่งเป็นอะไรก็ได้ ไม่จำเป็นต้องเป็น Dict

```python
class Point(BaseModel):
    x: int
    y: int

    @model_validator(mode="before")
    @classmethod
    def from_tuple(cls, data):
        if isinstance(data, (list, tuple)):
            return {"x": data[0], "y": data[1]}
        return data

Point.model_validate((1, 2))    # Point(x=1, y=2)
```

</Step>

## Exception ชนิดไหนกลายเป็น ValidationError

ใน Validator เราโยน Exception ได้หลายแบบ แต่ Pydantic จับแค่บางชนิด ซึ่งแบบฝึกลองโยนสามแบบดังนี้

| โยน | ผล |
|---|---|
| `ValueError` | `ValidationError` ชนิด `value_error` |
| `AssertionError` (ผ่าน `assert`) | `ValidationError` ชนิด `assertion_error` |
| `TypeError` | **หลุดออกมาเป็น `TypeError` ตรง ๆ** ไม่ถูกห่อ |

เหตุผลของข้อสามคือ `TypeError` ใน Validator มักเป็นบั๊กของโค้ด (เรียกฟังก์ชันผิด Argument) ไม่ใช่ข้อมูลผิด Pydantic จึงปล่อยให้มันดังขึ้นมา จะได้ไม่ไปปนกับข้อผิดของผู้ใช้ ([บท 6](/pydantic/errors/#สร้าง-error-ของตัวเอง) ยืนยันแบบเดียวกันกับ `ZeroDivisionError`)

<Callout type="warn" title="Assert ถูกตัดทิ้งเมื่อรันด้วย -O">
ถ้ารัน Python ด้วย `python -O` คำสั่ง `assert` จะถูกตัดออก ทำให้ Validator ที่ใช้ `assert` เป็นตัวตรวจไม่ตรวจเลย ดังนั้นสำหรับกฎที่ต้องทำงานเสมอให้ใช้ `raise ValueError(...)` ข้อนี้เป็นพฤติกรรมของ Python ที่เอกสาร Pydantic เตือนไว้เช่นกัน และแบบฝึกในบทนี้ไม่ได้รันด้วย `-O`
</Callout>

</Step>

## ที่ควรรู้เพิ่ม

**ตรวจสมาชิกของ List หรือหลาย Field พร้อมกัน** เราใส่ชื่อ Field ใน `@field_validator` ได้หลายตัว และ Validator ของ Field ที่เป็น List จะได้ List ทั้งก้อน

```python
@field_validator("skus")
@classmethod
def unique(cls, v):          # v คือ list ทั้งหมด
    if len(set(v)) != len(v):
        raise ValueError("duplicate sku")
    return v

@field_validator("first", "second")
@classmethod
def upper(cls, v):           # ใช้กับสอง field
    return v.upper()
```

**Validator ไม่ทำงานกับ Default** เช่น `code: str = "abc"` ที่มี Validator แปลงเป็นตัวใหญ่ `D().code` จะยังเป็น `"abc"` แต่ `D(code="abc").code` เป็น `"ABC"` ถ้าอยากให้ Default ผ่านด้วย ให้ใช้ `validate_default=True` ใน `Field` ([บท 2](/pydantic/fields/#default-ทำงานยังไง))

**ไม่ทำงานตอน Assign** เว้นแต่เราจะเปิด `validate_assignment` ([บท 8](/pydantic/models-config/#configdict-ตั้งค่าทั้ง-model))

**ใช้ใน Subclass ได้** เพราะ Validator ถูกสืบทอดจากคลาสแม่ และ Subclass Override ได้โดยประกาศฟังก์ชันชื่อเดียวกัน

</Step>

## เช็กตัวเอง

- Validator แบบ After บน Field `n: int` ถูกเรียกไหม ถ้าผู้ใช้ส่ง `"abc"` เข้ามา แล้ว Validator แบบ Before ล่ะ
- ทำไม `same_password` ต้องเช็ก `"password" in info.data` ก่อนอ่าน และ Field ไหนที่ไม่อยู่ใน `info.data`
- คุณต้องการ Model ที่เรียก `Order.model_validate(raw, context={"vat": 0.07})` แล้ว Validator ใช้อัตราภาษีนั้น ถ้าผู้เรียกลืมส่ง Context Validator ควรทำอะไร

</Step>
