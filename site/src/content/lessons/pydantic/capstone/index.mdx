## โจทย์

ระบบสั่งซื้อของเรารับ Order เป็น JSON จากหลายช่องทาง และเราอยากได้ด่านเดียวที่ทำสามอย่างนี้ได้

- รับ JSON ดิบเข้ามา แล้วคืน `Order` ที่ข้อมูลถูกต้องแน่นอน หรือไม่ก็รายการปัญหาที่ผู้ส่งอ่านแล้วรู้เรื่อง
- ไม่สะท้อนค่าที่ผู้ใช้ส่งมากลับไป และไม่ทำให้เลขบัตรหลุดลง Log
- ออก JSON Schema ให้ฝั่งที่ส่งมาใช้เป็นสัญญา

โค้ดเต็มอยู่ใน `exercises/12_capstone.py` และทุกข้อในบทนี้มี `assert` ยืนยัน ส่วนแต่ละหัวข้อข้างล่างก็ย้อนไปยังบทที่สอนเรื่องนั้นไว้

## ชนิดที่ใช้ซ้ำ และ Line

```python
Sku = Annotated[str, Field(pattern=r"^[A-Z]{2,4}-\d{1,5}$")]
Money = Annotated[Decimal, Field(ge=0, max_digits=10, decimal_places=2)]

class Line(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)

    sku: Sku
    qty: int = Field(gt=0, le=1000)
    unit_price: Money

    @computed_field
    @property
    def subtotal(self) -> Decimal:
        return self.unit_price * self.qty
```

ในโค้ดนี้เราใช้ของจาก [บท 2](/pydantic/fields/#annotated-เอาเงื่อนไขไปติดกับชนิด-แล้วใช้ซ้ำ) (`Annotated` พก `Field` ไปด้วย), [บท 3](/pydantic/types/#decimal-uuid-path-enum-และ-literal) (`Decimal` สำหรับเงิน), [บท 8](/pydantic/models-config/#configdict-ตั้งค่าทั้ง-model) (`extra="forbid"` ให้สะกด Key ผิดแล้วโดนจับ และ `frozen` ให้ Line แก้ไม่ได้หลังสร้าง) และ [บท 7](/pydantic/serialization/#computed_field-เอา-property-เข้าไปในผลลัพธ์) (`computed_field` ให้ `subtotal` ออกไปในผลลัพธ์)

`unit_price="1.999"` จะถูกปฏิเสธด้วย `decimal_max_places` เพราะ `decimal_places=2` ส่วน `5` (จำนวนเต็ม) ผ่านได้และกลายเป็น `Decimal("5")`

</Step>

## วิธีจ่ายเงิน: Discriminated Union และความลับ

```python
class Card(BaseModel):
    method: Literal["card"]
    number: SecretStr

    @field_validator("number")
    @classmethod
    def sixteen_digits(cls, v: SecretStr) -> SecretStr:
        digits = v.get_secret_value()
        if not (digits.isdigit() and len(digits) == 16):
            raise PydanticCustomError("card_number", "card number must be 16 digits")
        return v

class Transfer(BaseModel):
    method: Literal["transfer"]
    reference: str = Field(min_length=6)

Payment = Annotated[Union[Card, Transfer], Field(discriminator="method")]
```

ในโค้ดนี้มีสามเรื่องที่เราตั้งใจทำ

**ใช้ Discriminated Union** ([บท 4](/pydantic/unions/#discriminated-union-ดู-field-เดียวแล้วเลือกให้ตรง)) เพื่อให้ `{"method": "cash"}` ได้ `union_tag_invalid` ตรง ๆ แทนที่จะได้รายงานของทุกสมาชิก

**เลขบัตรเป็น `SecretStr`** ([บท 3](/pydantic/types/#ชนิดสำเร็จรูป-ตัวเลขที่มีเงื่อนไข-url-email-secretstr)) แบบฝึกยืนยันไว้ว่า `"4111"` ไม่ปรากฏทั้งใน `repr(order)` และ `order.model_dump_json()`

**ตรวจรูปแบบเลขบัตรใน Validator** เพราะ `Field(pattern=...)` บน `SecretStr` ใช้ไม่ได้ผล ผู้เขียนลองแล้วในร่างแรกและได้ `TypeError: Unable to apply constraint 'pattern' ... for schema of type 'lax-or-strict'` (ไม่ได้เก็บกรณีนี้ไว้ในแบบฝึก) นอกจากนี้ Validator ตัวนี้โยน `PydanticCustomError` ที่ข้อความไม่ใส่ตัวเลขเข้าไป ([บท 6](/pydantic/errors/#สร้าง-error-ของตัวเอง)) ถ้าเราไปใช้ `ValueError(f"bad card {digits}")` เลขบัตรก็จะไปอยู่ใน Error และ Log

</Step>

## Order: ประกอบทุกอย่าง

```python
class Order(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    id: int = Field(gt=0)
    email: EmailStr
    placed_at: Annotated[datetime, AfterValidator(not_in_past)]
    channel: Channel = Channel.WEB
    lines: list[Line] = Field(min_length=1)
    payment: Payment
    callback: HttpUrl | None = None

    @field_validator("lines")
    @classmethod
    def unique_skus(cls, v):
        skus = [x.sku for x in v]
        if len(skus) != len(set(skus)):
            raise ValueError("a sku appears on more than one line")
        return v

    @model_validator(mode="after")
    def store_needs_transfer_or_card(self):
        if self.channel is Channel.STORE and self.callback is not None:
            raise ValueError("store orders cannot have a callback")
        return self

    @computed_field
    @property
    def total(self) -> Decimal:
        return sum((x.subtotal for x in self.lines), Decimal(0))
```

ข้อมูลที่ถูกต้อง (`GOOD` ในแบบฝึก) จะผ่านทุกด่านพร้อมการแปลงดังนี้

| ที่ส่งมา | ที่ได้ |
|---|---|
| `"id": "1001"` | `1001` (`int`) |
| `"email": " Ann@Example.com "` | `"Ann@example.com"` (ตัดช่องว่างด้วย `str_strip_whitespace`, Domain เป็นตัวเล็ก) |
| `"placed_at": "2026-03-01T09:30:00+07:00"` | `datetime` มี Timezone |
| Line ที่สอง `"qty": "1"`, `"unit_price": 5` | `qty=1`, `Decimal("5")` |
| ไม่ส่ง `channel` | `Channel.WEB` |
| `payment.method == "card"` | `Card` |

`order.total == Decimal("44.80")` (19.90 × 2 + 5) และ JSON ที่ Dump ออกมามี `"total": "44.80"` กับ `"subtotal": "39.80"` ของ Line แรก ซึ่งเป็น String ตามที่ `Decimal` ออก JSON ([บท 7](/pydantic/serialization/#สองโหมดของขาออก))

ส่วนกฎที่คร่อมหลายค่าก็อยู่ใน Validator ระดับ List (Sku ซ้ำ) และระดับ Model (Store กับ Callback) ตามที่ [บท 5](/pydantic/validators/#model_validator-กฎที่คร่อมหลาย-field) สอน

</Step>

## เมื่อข้อมูลผิดทุกจุด: รายการปัญหา

```python
def problems(raw: str) -> list[dict]:
    try:
        Order.model_validate_json(raw)
    except ValidationError as e:
        return [
            {"field": ".".join(str(p) for p in x["loc"]),
             "code": x["type"],
             "message": x["msg"]}
            for x in e.errors(include_url=False, include_context=False, include_input=False)
        ]
    return []
```

ลองส่ง Order ที่ผิดเก้าจุดในคราวเดียว ผลที่แบบฝึกยืนยันไว้เป็นดังนี้ (เรียงตามที่ Pydantic รายงาน)

| field | code |
|---|---|
| `surprise` | `extra_forbidden` |
| `id` | `greater_than` |
| `email` | `value_error` |
| `placed_at` | `date_too_old` |
| `lines.0.color` | `extra_forbidden` |
| `lines.0.sku` | `string_pattern_mismatch` |
| `lines.0.qty` | `greater_than` |
| `lines.0.unit_price` | `decimal_max_places` |
| `payment` | `union_tag_invalid` |

ลองสังเกตลำดับดู Key ที่เกินมาจะอยู่ก่อน Field ปกติของ Model เดียวกัน (`surprise` มาก่อน `id`, `lines.0.color` มาก่อน `lines.0.sku`) เพราะฉะนั้นอย่าเขียนโค้ดที่พึ่งลำดับของ Error ให้ตรงกับลำดับ Field ในคลาส ถ้า Client ต้องเรียง ก็ให้เรียงเอง

ในรายการจะไม่มีค่าที่ผู้ใช้ส่งมาเลย (เพราะใช้ `include_input=False`) และ `placed_at` ได้ `date_too_old` ซึ่งเป็น Code ของเราเอง มาจาก `PydanticCustomError` ใน `not_in_past` ([บท 6](/pydantic/errors/#สร้าง-error-ของตัวเอง))

กฎที่คร่อมค่าจะทำงานต่อเมื่อค่าพื้นฐานผ่านแล้ว ([บท 5](/pydantic/validators/#model_validator-กฎที่คร่อมหลาย-field)) ดังนั้น

- ส่ง Line ซ้ำสองบรรทัด (ที่ทุก Field ถูกต้อง) ได้ `value_error` อันเดียว
- ส่ง `channel="store"` พร้อม `callback` ได้ข้อความ `Value error, store orders cannot have a callback`
- ส่ง `lines=[]` ได้ `too_short`
- ส่งข้อความที่ไม่ใช่ JSON (`"{not json"`) ได้ `json_invalid`

</Step>

## สัญญาสำหรับฝั่งที่ส่งมา: JSON Schema

```python
schema = Order.model_json_schema()
schema["required"]                                   # ['id', 'email', 'placed_at', 'lines', 'payment']
schema["properties"]["payment"]["discriminator"]["propertyName"]   # 'method'
schema["additionalProperties"]                       # False
set(schema["$defs"])                                 # {'Card', 'Channel', 'Line', 'Transfer'}
```

Schema นี้บอกฝั่ง Client ว่า Field ไหนต้องส่ง ส่ง Key ที่เกินมาไม่ได้ (`additionalProperties: False` มาจาก `extra="forbid"`) และ `payment` เลือกชนิดด้วย `method` ตามที่ [บท 9](/pydantic/adapters/#json-schema-จาก-model) อธิบาย

แต่ Validator ที่เราเขียนเอง (Sku ซ้ำ, `placed_at` ต้องหลังปี 2020, เลขบัตรต้อง 16 หลัก, Store ห้ามมี Callback) **ไม่อยู่ใน Schema** เราจึงต้องเขียนไว้ใน `description` หรือในเอกสารแยก ไม่อย่างนั้นฝั่งที่ส่งมาจะเพิ่งรู้ก็ตอนโดนปฏิเสธ

ถ้ามี Order มาเป็นชุด ก็สร้าง Adapter ครั้งเดียวแล้วใช้ซ้ำ

```python
Batch = TypeAdapter(list[Order])
two = Batch.validate_json(json.dumps([GOOD, dict(GOOD, id=1002)]))   # [Order(id=1001...), Order(id=1002...)]
Batch.validate_json(json.dumps([GOOD, dict(GOOD, id=-1)]))           # error ที่ loc (1, 'id')
```

`loc` จะขึ้นต้นด้วยดัชนีของ Order ในชุด ผู้ส่งจึงรู้ว่าตัวที่สองผิด

</Step>

## เช็กตัวเอง

- ถ้าเปลี่ยน `Card.number` เป็น `str` ธรรมดา และ Validator โยน `ValueError(f"bad {digits}")` เลขบัตรจะไปปรากฏที่ไหนบ้าง
- ทำไม `problems(json.dumps(dup))` ที่ส่ง Line ซ้ำ จึงได้ Error เดียว ทั้งที่ Order นั้นอาจมีปัญหาอื่นร่วมด้วยถ้า Field พื้นฐานผิด
- ถ้าฝั่ง Client บอกว่า "Schema ของคุณไม่บอกว่า Sku ห้ามซ้ำ" คุณจะแก้ที่ใด
