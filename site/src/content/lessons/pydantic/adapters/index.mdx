## TypeAdapter: ตรวจชนิดอะไรก็ได้

ข้อมูลบางอย่างไม่จำเป็นต้องห่อเป็น `BaseModel` เสมอไป ถ้าเราต้องตรวจแค่ `list[int]` หรือ `dict[str, int]` การสร้างคลาสเพิ่มก็เป็นภาระเปล่า ๆ `TypeAdapter` จึงรับชนิดนั้นเข้าไป แล้วให้ Validator, Serializer และ JSON Schema ของชนิดนั้นกลับมา (รัน: `exercises/09_adapters.py`)

```python
ta = TypeAdapter(list[int])
ta.validate_python(["1", 2])       # [1, 2]
ta.validate_json("[1, 2, 3]")      # [1, 2, 3]
ta.dump_python([1, 2])             # [1, 2]
ta.dump_json([1, 2])               # b'[1,2]'   คืน bytes ไม่ใช่ str
ta.json_schema()                   # {'type': 'array', 'items': {'type': 'integer'}}
```

ชื่อเมธอดต่างจาก Model เล็กน้อย โดยใช้ `validate_python` แทน `model_validate` และ `dump_python` แทน `model_dump` ส่วนข้อควรระวังมีอย่างเดียวคือ `dump_json` คืน `bytes`

เงื่อนไขจาก [บท 2](/pydantic/fields/#annotated-เอาเงื่อนไขไปติดกับชนิด-แล้วใช้ซ้ำ) ก็ใช้ภายในชนิดได้เหมือนกัน

```python
Users = TypeAdapter(dict[str, Annotated[int, Field(ge=0)]])
Users.validate_python({"a": "1"})     # {'a': 1}
Users.validate_python({"a": -1})      # error ที่ loc ('a',) ชนิด greater_than_equal
```

**สร้างครั้งเดียว ใช้ซ้ำ** การสร้าง `TypeAdapter` เป็นขั้นที่แพง เพราะต้องเดินดูชนิดและสร้าง Core Schema ([บท 10](/pydantic/under-the-hood/#ต้นทุนอยู่ตอนสร้างคลาส-ไม่ใช่ตอน-validate)) ส่วนการเรียก `validate_python` เป็นขั้นที่ถูก แบบฝึกจึงวัดดู 200 ครั้งของ `[1, 2, 3]` บนคอมพิวเตอร์ที่รัน

```text
build each call 6.9 ms, reuse 0.09 ms for 200 calls, ratio 77x
```

ตัวเลขนี้ขึ้นกับคอมพิวเตอร์ที่รัน สิ่งที่แบบฝึก `assert` ไว้คืออัตราส่วนมากกว่า 20 เท่า เพราะฉะนั้นเราควรประกาศ Adapter เป็นตัวแปรระดับ Module แทนที่จะสร้างในฟังก์ชันที่ถูกเรียกบ่อย

</Step>

## TypedDict และ NamedTuple

ชนิดมาตรฐานของ Python ที่ไม่ใช่ Class ธรรมดาก็ตรวจได้เหมือนกัน และผลที่ได้ก็ยังเป็นชนิดเดิม

```python
class Movie(TypedDict):
    title: str
    year: int

m = TypeAdapter(Movie).validate_python({"title": "x", "year": "1999"})
m                 # {'title': 'x', 'year': 1999}
type(m) is dict   # True   ไม่ได้กลายเป็น object ของ Pydantic

class Pt(NamedTuple):
    x: int
    y: int

TypeAdapter(Pt).validate_python(("1", "2"))    # Pt(x=1, y=2)
```

วิธีนี้เหมาะเมื่อโค้ดเดิมส่ง Dict หรือ Tuple กันอยู่แล้ว และเราอยากเพิ่มการตรวจที่ขอบ โดยไม่ต้องเปลี่ยนชนิดข้อมูลที่เหลือของโปรแกรม

</Step>

## Pydantic Dataclass

`dataclass` ธรรมดาไม่ได้ตรวจอะไรเลย ([บท 1](/pydantic/first-model/#type-hint-ไม่ได้ตรวจอะไรเลย)) แต่เราเปลี่ยนเป็นของ Pydantic ได้โดยแค่เปลี่ยนที่ Import

```python
from pydantic.dataclasses import dataclass as pdataclass

@pdataclass
class Item:
    sku: str
    qty: PositiveInt = 1

Item("A", "3").qty                  # 3
dataclasses.is_dataclass(Item)      # True
Item("A", 0)                        # ValidationError ชนิด greater_than
dataclasses.asdict(Item("A", 2))    # {'sku': 'A', 'qty': 2}
TypeAdapter(Item).validate_python({"sku": "A", "qty": "2"})   # Item(sku='A', qty=2)
```

ผลที่ได้ยังเป็น Dataclass ที่ใช้กับเครื่องมืออื่นได้ (`asdict`, `fields`) และ Type Checker ก็เห็นเป็น Dataclass ตามปกติ ส่วนข้อต่างจาก `BaseModel` คือไม่มีเมธอด `model_*` ถ้าต้องการ Dump หรือ JSON Schema ก็ให้ใช้ `TypeAdapter` แทน

แล้วจะเลือกอย่างไรดี ถ้าเราต้องการพวก `model_dump`, `model_json_schema`, ConfigDict เต็มรูปแบบ หรือ Field ที่ต้อง Alias ก็ใช้ `BaseModel` แต่ถ้าโค้ดอยู่ในสไตล์ Dataclass อยู่แล้วและอยากเพิ่มการตรวจ ก็ใช้ Pydantic Dataclass (คำแนะนำของผู้เขียน)

</Step>

## validate_call: ตรวจ Argument ของฟังก์ชัน

```python
@validate_call
def add(a: int, b: int = 1) -> int:
    return a + b

add("2", b="3")    # 5
```

Decorator ตัวนี้ตรวจ Argument ทุกตัวด้วยกฎเดียวกับ Model ถ้าผิดก็จะได้ `ValidationError` ที่ `loc` ใช้ตำแหน่งหรือชื่อของ Argument

| เรียก | Error |
|---|---|
| `add("x")` | `loc == (0,)` ชนิด `int_parsing` |
| `add(1, 2, 3)` | `unexpected_positional_argument` |
| `add(1, c=3)` | `unexpected_keyword_argument` |

ตามค่าเริ่มต้น ค่าที่ฟังก์ชันคืนจะไม่ถูกตรวจ ถ้าอยากให้ตรวจด้วยก็ใส่ `@validate_call(validate_return=True)` แล้วฟังก์ชันที่คืน `"not an int"` จะได้ `int_parsing` ฟังก์ชันที่ห่อแล้วยังคงชื่อเดิม (`add.__name__ == "add"`) และถ้าอยากเรียกตัวต้นฉบับโดยไม่ผ่านการตรวจ ก็เรียกได้ที่ `add.raw_function`

Argument ที่เป็น Model ก็รับ Dict ได้เหมือนกับที่ Model ปกติรับ

```python
@validate_call
def use(cfg: Cfg) -> int:
    return cfg.n

use({"n": "4"})    # 4
```

<Callout type="tip" title="เหมาะกับงานแบบไหน">
`validate_call` สะดวกกับฟังก์ชันที่เป็นทางเข้าของ Library หรือ CLI ซึ่งผู้เรียกเป็นคนอื่น ส่วนฟังก์ชันที่เรียกกันเองในโค้ดที่ Type Checker ตรวจอยู่แล้ว การตรวจซ้ำทุกครั้งที่เรียกจะเป็นต้นทุนที่ไม่จำเป็น
</Callout>

</Step>

## JSON Schema จาก Model

`Model.model_json_schema()` (หรือ `TypeAdapter(...).json_schema()`) สร้าง JSON Schema ที่ฝั่ง Client เอาไปใช้ตรวจ ทำเอกสาร API หรือสร้างฟอร์มได้

```python
class Product(BaseModel):
    """A product in the catalogue."""

    sku: str = Field(min_length=3, description="stock keeping unit", examples=["AB-1"])
    price: float = Field(gt=0)
    tags: list[str] = []
    note: str | None = None
```

ผลที่ได้มีสิ่งเหล่านี้จริง (ยืนยันด้วย `assert` ในแบบฝึก)

- `required` คือ `["sku", "price"]` เพราะ Field ที่มี Default ไม่อยู่ในรายการ
- `sku` มี `minLength: 3` พร้อมกับ `description` และ `examples`
- `price` มี `exclusiveMinimum: 0` (จาก `gt=0`)
- `note` เป็น `anyOf: [{"type": "string"}, {"type": "null"}]`
- `title` เป็น `"Product"` และ `description` มาจาก Docstring ของคลาส

ส่วน Model ที่ซ้อนกันจะไปอยู่ใน `$defs` แล้วอ้างถึงด้วย `$ref`

```python
class Basket(BaseModel):
    items: list[Product]

schema["properties"]["items"]["items"]   # {'$ref': '#/$defs/Product'}
```

**สองโหมด** `model_json_schema(mode="validation")` (ค่าเริ่มต้น) อธิบายสิ่งที่ Model **รับ** ส่วน `mode="serialization"` อธิบายสิ่งที่ **ส่งออก** โดยสองโหมดนี้ต่างกันตรงที่ Computed Field ([บท 7](/pydantic/serialization/#computed_field-เอา-property-เข้าไปในผลลัพธ์)) จะอยู่ในแบบ Serialization เท่านั้น และใน Serialization `required` ก็ยังเป็น `["sku", "price"]` เพราะ Field ที่มี Default ยังไม่บังคับ ถ้าอยากให้ Field ที่มี Default ถือว่ามีอยู่เสมอในผลที่ส่งออก ก็ตั้ง `json_schema_serialization_defaults_required` เป็น `True` แล้ว `required` จะได้ครบสี่ Field

<Callout type="warn" title="Validator ที่เป็นโค้ด Python มองไม่เห็นใน JSON Schema">
`field_validator` ที่ตรวจว่าเลขเป็นเลขคู่ จะไม่ปรากฏใน Schema เลย แบบฝึกยืนยันไว้ว่า `n` ยังเป็น `{"title": "N", "type": "integer"}` เท่านั้น JSON Schema ที่สร้างจึงบอกได้เฉพาะเงื่อนไขที่ Pydantic เข้าใจ (ชนิด `Field(...)` `Annotated`) ถ้ามี Validator ที่สำคัญ เราต้องบอกไว้ใน `description` เอง ไม่อย่างนั้น Client ที่เชื่อ Schema จะส่งค่าที่ Server ปฏิเสธมา
</Callout>

</Step>

## เช็กตัวเอง

- ถ้าฟังก์ชันที่ถูกเรียกพันครั้งต่อวินาทีสร้าง `TypeAdapter(list[int])` ข้างในทุกครั้ง จะมีปัญหาตรงไหน และแก้อย่างไร
- `TypeAdapter(Movie).validate_python(...)` (Movie เป็น `TypedDict`) คืนอะไรกลับมา และต่างจากการใช้ `BaseModel` ตรงไหน
- Schema ของ `Product` ในโหมด Validation กับ Serialization ต่างกันในกรณีใด และ Validator ที่คุณเขียนเองจะเห็นใน Schema ไหม

</Step>
