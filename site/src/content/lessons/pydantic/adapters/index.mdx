## TypeAdapter: ตรวจชนิดอะไรก็ได้

ไม่ใช่ทุกอย่างที่ต้องห่อเป็น `BaseModel` ถ้าต้องตรวจแค่ `list[int]` หรือ `dict[str, int]` การสร้างคลาสเพิ่มเป็นภาระ `TypeAdapter` รับชนิดแล้วให้ validator, serializer และ JSON Schema ของชนิดนั้น (รัน: `exercises/09_adapters.py`)

```python
ta = TypeAdapter(list[int])
ta.validate_python(["1", 2])       # [1, 2]
ta.validate_json("[1, 2, 3]")      # [1, 2, 3]
ta.dump_python([1, 2])             # [1, 2]
ta.dump_json([1, 2])               # b'[1,2]'   คืน bytes ไม่ใช่ str
ta.json_schema()                   # {'type': 'array', 'items': {'type': 'integer'}}
```

ชื่อเมธอดต่างจาก model เล็กน้อย `validate_python` แทน `model_validate`, `dump_python` แทน `model_dump` ข้อควรระวังอย่างเดียวคือ `dump_json` คืน `bytes`

เงื่อนไขจาก [บท 2](/pydantic/fields/) ใช้ได้ภายในชนิด

```python
Users = TypeAdapter(dict[str, Annotated[int, Field(ge=0)]])
Users.validate_python({"a": "1"})     # {'a': 1}
Users.validate_python({"a": -1})      # error ที่ loc ('a',) ชนิด greater_than_equal
```

**สร้างครั้งเดียว ใช้ซ้ำ** การสร้าง `TypeAdapter` คือขั้นแพง เพราะต้องเดินชนิดและสร้าง core schema ([บท 10](/pydantic/under-the-hood/)) การเรียก `validate_python` เป็นขั้นถูก แบบฝึกวัด 200 ครั้งของ `[1, 2, 3]` บนเครื่องที่รัน

```text
build each call 6.9 ms, reuse 0.09 ms for 200 calls, ratio 77x
```

ตัวเลขนี้ขึ้นกับเครื่อง สิ่งที่แบบฝึก `assert` คืออัตราส่วนมากกว่า 20 เท่า ดังนั้นให้ประกาศ adapter เป็นตัวแปรระดับ module แทนการสร้างในฟังก์ชันที่ถูกเรียกบ่อย

</Step>

## TypedDict และ NamedTuple

ชนิดมาตรฐานของ Python ที่ไม่ใช่ class ธรรมดาก็ตรวจได้ และผลที่ได้ยังเป็นชนิดเดิม

```python
class Movie(TypedDict):
    title: str
    year: int

m = TypeAdapter(Movie).validate_python({"title": "x", "year": "1999"})
m                 # {'title': 'x', 'year': 1999}
type(m) is dict   # True   ไม่ได้กลายเป็น object ของ Pydantic

class Pt(NamedTuple):
    x: int
    y: int

TypeAdapter(Pt).validate_python(("1", "2"))    # Pt(x=1, y=2)
```

เหมาะเมื่อโค้ดเดิมส่ง dict หรือ tuple กันอยู่แล้วและอยากเพิ่มการตรวจที่ขอบ โดยไม่เปลี่ยนชนิดข้อมูลที่เหลือของโปรแกรม

</Step>

## Pydantic Dataclass

`dataclass` ธรรมดาไม่ตรวจอะไร ([บท 1](/pydantic/first-model/#type-hint-ไม่ได้ตรวจอะไรเลย)) เปลี่ยนเป็นของ Pydantic ได้โดยเปลี่ยนที่ import

```python
from pydantic.dataclasses import dataclass as pdataclass

@pdataclass
class Item:
    sku: str
    qty: PositiveInt = 1

Item("A", "3").qty                  # 3
dataclasses.is_dataclass(Item)      # True
Item("A", 0)                        # ValidationError ชนิด greater_than
dataclasses.asdict(Item("A", 2))    # {'sku': 'A', 'qty': 2}
TypeAdapter(Item).validate_python({"sku": "A", "qty": "2"})   # Item(sku='A', qty=2)
```

ยังเป็น dataclass ที่ใช้กับเครื่องมืออื่นได้ (`asdict`, `fields`) และ type checker เห็นเป็น dataclass ตามปกติ ข้อต่างจาก `BaseModel` คือไม่มีเมธอด `model_*` ใช้ `TypeAdapter` เมื่อต้องการ dump หรือ JSON Schema

เลือกอย่างไร: ถ้าต้องการพวก `model_dump`, `model_json_schema`, ConfigDict เต็มรูปแบบ หรือ field ที่ต้อง alias ใช้ `BaseModel` ถ้าโค้ดอยู่ในสไตล์ dataclass อยู่แล้วและอยากเพิ่มการตรวจ ใช้ pydantic dataclass (คำแนะนำของผู้เขียน)

</Step>

## validate_call: ตรวจ Argument ของฟังก์ชัน

```python
@validate_call
def add(a: int, b: int = 1) -> int:
    return a + b

add("2", b="3")    # 5
```

decorator ตรวจ argument ทุกตัวด้วยกฎเดียวกับ model ผิดแล้วได้ `ValidationError` ที่ `loc` ใช้ตำแหน่งหรือชื่อ

| เรียก | error |
|---|---|
| `add("x")` | `loc == (0,)` ชนิด `int_parsing` |
| `add(1, 2, 3)` | `unexpected_positional_argument` |
| `add(1, c=3)` | `unexpected_keyword_argument` |

ค่าที่คืนไม่ถูกตรวจตามค่าเริ่มต้น ถ้าต้องการให้ตรวจด้วย ใส่ `@validate_call(validate_return=True)` แล้วฟังก์ชันที่คืน `"not an int"` จะได้ `int_parsing` ฟังก์ชันที่ห่อแล้วยังชื่อเดิม (`add.__name__ == "add"`) และเรียกตัวต้นฉบับโดยไม่ผ่านการตรวจได้ที่ `add.raw_function`

argument ที่เป็น model รับ dict ได้ตามที่ model ปกติรับ

```python
@validate_call
def use(cfg: Cfg) -> int:
    return cfg.n

use({"n": "4"})    # 4
```

<Callout type="tip" title="เหมาะกับงานแบบไหน">
`validate_call` สะดวกกับฟังก์ชันที่เป็นทางเข้าของ library หรือ CLI ซึ่งผู้เรียกเป็นคนอื่น กับฟังก์ชันที่เรียกกันเองในโค้ดที่ type checker ตรวจอยู่แล้ว การตรวจซ้ำทุกครั้งที่เรียกเป็นต้นทุนที่ไม่จำเป็น
</Callout>

</Step>

## JSON Schema จาก Model

`Model.model_json_schema()` (หรือ `TypeAdapter(...).json_schema()`) สร้าง JSON Schema ที่ให้ฝั่ง client ใช้ตรวจ ทำเอกสาร API หรือสร้างฟอร์ม

```python
class Product(BaseModel):
    """A product in the catalogue."""

    sku: str = Field(min_length=3, description="stock keeping unit", examples=["AB-1"])
    price: float = Field(gt=0)
    tags: list[str] = []
    note: str | None = None
```

สิ่งที่ผลมีจริง (ยืนยันด้วย `assert` ในแบบฝึก)

- `required` คือ `["sku", "price"]` field ที่มี default ไม่อยู่ในรายการ
- `sku` มี `minLength: 3` พร้อม `description` และ `examples`
- `price` มี `exclusiveMinimum: 0` (จาก `gt=0`)
- `note` เป็น `anyOf: [{"type": "string"}, {"type": "null"}]`
- `title` เป็น `"Product"` และ `description` ได้จาก docstring ของคลาส

model ที่ซ้อนกันไปอยู่ใน `$defs` แล้วอ้างด้วย `$ref`

```python
class Basket(BaseModel):
    items: list[Product]

schema["properties"]["items"]["items"]   # {'$ref': '#/$defs/Product'}
```

**สองโหมด** `model_json_schema(mode="validation")` (ค่าเริ่มต้น) อธิบายสิ่งที่ model **รับ** ส่วน `mode="serialization"` อธิบายสิ่งที่ **ส่งออก** ต่างกันตรงที่ computed field ([บท 7](/pydantic/serialization/)) อยู่ในแบบ serialization เท่านั้น ใน serialization `required` ยังเป็น `["sku", "price"]` เพราะ field ที่มี default ยังไม่บังคับ ถ้าอยากให้ field ที่มี default ถือว่ามีเสมอในผลที่ส่ง ตั้ง `json_schema_serialization_defaults_required` เป็น `True` แล้ว `required` จะได้ครบสี่ field

<Callout type="warn" title="validator ที่เป็นโค้ด Python มองไม่เห็นใน JSON Schema">
`field_validator` ที่ตรวจว่าเลขเป็นเลขคู่ ไม่ปรากฏใน schema เลย แบบฝึกยืนยัน: `n` ยังเป็น `{"title": "N", "type": "integer"}` เท่านั้น JSON Schema ที่สร้างจึงบอกได้เฉพาะเงื่อนไขที่ Pydantic เข้าใจ (ชนิด `Field(...)` `Annotated`) ถ้ามี validator ที่สำคัญ ต้องบอกใน `description` เอง ไม่เช่นนั้น client ที่เชื่อ schema จะส่งค่าที่ server ปฏิเสธ
</Callout>

</Step>

## เช็กตัวเอง

- ฟังก์ชันที่ถูกเรียกพันครั้งต่อวินาทีสร้าง `TypeAdapter(list[int])` ข้างในทุกครั้ง มีปัญหาตรงไหน และแก้อย่างไร
- `TypeAdapter(Movie).validate_python(...)` (Movie เป็น `TypedDict`) คืนอะไร ต่างจากการใช้ `BaseModel` ตรงไหน
- schema ของ `Product` ในโหมด validation กับ serialization ต่างกันในกรณีใด และ validator ที่คุณเขียนเองเห็นใน schema ไหม

</Step>
