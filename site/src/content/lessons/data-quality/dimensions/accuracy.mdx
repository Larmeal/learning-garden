## Accuracy ถามว่าข้อมูลตรงกับของจริงไหม

ลองนึกถึงเทอร์โมมิเตอร์ที่อ่านได้ 31.4 องศา ตัวเลขนี้อยู่ในช่วงที่เป็นไปได้ และเขียนในรูปแบบที่ถูกต้อง แต่ห้องนั้นร้อน 31.4 องศาจริงหรือเปล่า เราตอบไม่ได้จากตัวเลขเอง ต้องมีเทอร์โมมิเตอร์อีกตัวที่เราเชื่อถือ หรือคนที่รู้อยู่แล้วมาเทียบ

DMBOK2 นิยาม accuracy ว่าระดับที่ข้อมูลแทน entity ในชีวิตจริงได้ถูกต้อง และบอกตรงๆ ว่าวัดยาก เว้นแต่เราจะเก็บข้อมูลนั้นซ้ำได้ หรือยืนยัน record ด้วยมือได้ การวัดส่วนใหญ่จึงทำโดยเทียบกับแหล่งที่ได้รับการยืนยันแล้วว่าถูก เช่น system of record หรือ reference data ภายนอกที่เชื่อถือได้ (หนังสือ: DMBOK2 Table 29 หน้า 458) DAMA UK พูดไว้ในความหมายเดียวกัน คือระดับที่ข้อมูลอธิบายวัตถุหรือเหตุการณ์ในโลกจริงได้ถูกต้อง (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 457)

Ten Steps เปิดขั้นตอน accuracy ด้วยข้อสังเกตว่า หลายคนใช้คำว่า accuracy เป็นคำเดียวกับ data quality ทั้งหมด แต่มืออาชีพด้านข้อมูลรู้ว่าสองคำนี้ไม่เหมือนกัน (หนังสือ: Ten Steps บทที่ 4 หน้า 135 ถึง 140)

</Step>

## Profiling บอกอะไรได้ และบอกอะไรไม่ได้

Ten Steps ยกสามตัวอย่างที่แสดงเส้นแบ่งระหว่างสิ่งที่ profiling เห็น กับสิ่งที่ต้องเทียบกับของจริงถึงจะรู้ (หนังสือ: Ten Steps บทที่ 4 หน้า 135 ถึง 140)

| profiling เห็นได้ | ต้องเทียบกับของจริงถึงจะรู้ |
|---|---|
| ทุกชิ้นส่วนมี code ที่ valid คือ M (ผลิตเอง) หรือ B (ซื้อมา) | code นั้นตรงกับวิธีที่ชิ้นส่วนนั้นได้มาจริงหรือเปล่า |
| postal code อยู่ในช่อง postal code และมี pattern ที่ valid | เป็น postal code ที่ถูกของลูกค้าคนนี้ไหม |
| จำนวนสินค้าคงคลังมี data type ที่ถูก | ตัวเลขตรงกับของที่วางอยู่บนชั้นจริงไหม |

ใน dataset ของเรา การเทียบเกิดขึ้นระหว่างสองระบบ เรากำหนดให้ payment system เป็นแหล่งความจริง แล้วเทียบยอดของ order แต่ละรายการที่ไม่ถูกยกเลิก กับผลรวม payment ของ order นั้น

| order_id | total_amount ใน `orders` | ที่ payment system รับจริง | ส่วนต่าง |
|---:|---:|---:|---:|
| 91 | 487.71 | 437.71 | -50.00 |
| 122 | 2029.28 | 1979.28 | -50.00 |
| 412 | 4147.84 | 4146.84 | -1.00 |
| 438 | 1716.14 | 1836.14 | 120.00 |

```sql
WITH o AS (SELECT DISTINCT order_id, total_amount FROM orders WHERE status <> 'CANCELLED'),
     p AS (SELECT order_id, sum(amount) AS paid FROM payments GROUP BY order_id)
SELECT count(*) FILTER (WHERE abs(o.total_amount - p.paid) > 0.005), count(*)
FROM o JOIN p USING (order_id);
-- 35 จาก 2,533 หรือ accurate 98.62% เมื่อเทียบกับ payment
```

query นี้ตัด order ที่ถูกยกเลิกออก เพราะ order ที่ยกเลิกไม่มี payment ให้เทียบ ส่วนที่เหลือเอามาจับคู่กับผลรวม payment ของ order เดียวกัน ถ้าสองค่าต่างกันเกิน 0.005 ก็นับว่าไม่ตรง

</Step>

## ไม่มีแหล่งความจริง ก็วัด Accuracy ไม่ได้

ถ้าไม่มีอะไรให้เทียบ เราตรวจ validity ได้ แต่ตรวจ accuracy ไม่ได้ Ten Steps วาง decision flow ไว้สี่คำถาม คือ เราระบุแหล่งที่มีอำนาจได้ไหม เข้าถึงมันได้ไหม stakeholder เห็นพ้องกันไหมว่ามันคือแหล่งที่มีอำนาจ และเราจ่ายไหวไหมกับการ assess ถ้าคำถามใดตอบว่าไม่ หนังสือบอกว่าเราทำไม่ได้หรือไม่ควรประเมิน accuracy และให้ใช้ dimension อื่นแทน (หนังสือ: Ten Steps บทที่ 4 หน้า 135 ถึง 140)

การเทียบกับของจริงมักทำมือและแพง หนังสือแนะนำให้ถามด้วยว่า ถ้าประเมินแค่บาง record หรือบาง field จะได้ผลที่มีความหมายพอไหม ใน dataset ของเรา การเทียบเป็นแค่ join ซึ่งไม่มีต้นทุนเลย นั่นเป็นข้อยกเว้น ไม่ใช่เรื่องปกติ

ประโยค "เรา accurate 98.62%" จึงมีอนุประโยคซ่อนอยู่ว่า "เมื่อเทียบกับ payment system" และตัวเลขนี้เชื่อถือได้เท่าที่ payment system เชื่อถือได้

</Step>

## ความไม่ตรง บอกว่าสองแหล่งขัดกัน ไม่ได้บอกว่าแหล่งไหนผิด

order 91 บันทึกยอดไว้ 487.71 ส่วน payment system บอกว่ารับมา 437.71 เราเรียก order 91 ว่าไม่ accurate เพราะเราตกลงกันไว้ก่อนว่า payment เป็นแหล่งความจริง แต่ความจริงอาจเป็นอีกแบบก็ได้ ยอดใน `orders` ถูก แล้ว payment ถูกบันทึกผิด

และ reference เองก็มีปัญหาของมัน ใน `payments` มี payment 20 รายการที่ชี้ไปหา order ที่ไม่มีอยู่จริง (รัน: `13_dimension_pitfalls.py`) ซึ่งเป็นเรื่องของ [Integrity](/data-quality/dimensions/integrity/) ถ้าเราเชื่อ payment เป็นความจริง ก็ต้องรู้ด้วยว่ามันมีจุดอ่อนตรงไหน หนังสือย้ำว่าถ้าทีมไม่ตกลงกันเรื่องแหล่งที่มีอำนาจ ผลการประเมินจะไม่มีใครเชื่อ

</Step>

## ค่า Tolerance เปลี่ยนตัวเลข

query ข้างบนนับส่วนต่างที่มากกว่า 0.005 ว่าไม่ตรง ถ้าเราเปลี่ยนเกณฑ์นี้ ตัวเลขก็เปลี่ยนตาม (รัน: `13_dimension_pitfalls.py`)

| tolerance (ส่วนต่างที่ยอมรับได้) | จำนวนที่ไม่ตรง จาก 2,533 |
|---:|---:|
| 0.005 | 35 |
| 1.00 | 27 |
| 11.00 | 18 |
| 60.00 | 11 |

ตาราง 4 บรรทัดนี้ไม่มีบรรทัดไหนเป็นคำตอบที่ถูก ส่วนต่าง 1.00 กับส่วนต่าง 120.00 เป็นคนละปัญหา และคนที่เป็นเจ้าของเงินเป็นคนกำหนดว่าเส้นแบ่งอยู่ตรงไหน ให้เขียน tolerance ลงใน rule ทุกครั้ง

ข้อมูลที่ผ่าน rule ของ validity ก็ยังไม่ accurate ได้ ยอดผิด 35 รายการเป็นเลขบวกทั้งหมด จึงผ่าน rule `total_amount >= 0` ทุกรายการ DMBOK2 ยกวันเกิดเป็นตัวอย่าง ค่าที่อยู่ในช่วงที่อนุญาตก็ยังผิดสำหรับคนที่มันอธิบายได้ (หนังสือ: DMBOK2 Table 29 หน้า 459) ส่วนการเทียบกับสำเนาของตัวเอง ซึ่งไม่ช่วยเรื่อง accuracy เลย อธิบายไว้ที่หน้า [Consistency](/data-quality/dimensions/consistency/)

คำว่า accuracy ยังเป็นชื่อ metric ของ model ใน machine learning ด้วย ซึ่งหมายถึงสัดส่วนของผลทำนายที่ถูก มันไม่ได้แปลว่าข้อมูลที่ใช้ train accurate ในความหมายที่ใช้ที่นี่ จึงควรบอกให้ชัดว่าเราหมายถึงอย่างไหน (ข้อสังเกตนี้เป็นของผู้เขียน)

</Step>

<Step>

## ต่างจาก Dimension อื่นอย่างไร

accuracy ต่างจาก [Validity](/data-quality/dimensions/validity/) ตรงที่ validity ถามว่าค่านี้ยอมให้มีได้ไหม ส่วน accuracy ถามว่าค่านี้จริงไหม ยอดผิด 35 รายการผ่าน validity ครบ

accuracy ต่างจาก consistency ตรงที่สองแหล่งที่ตรงกันไม่ได้พิสูจน์ว่าแหล่งใดถูก

ส่วน reconciliation ที่ [บท 8](/data-quality/reconciliation/#reconcile-ด้วยจำนวน-row-และผลรวม) สอน เป็น process ที่เทียบสองระบบกัน accuracy คือสิ่งที่ผลการเทียบที่ดีบอกเราเกี่ยวกับระบบหนึ่ง เมื่ออีกระบบหนึ่งเป็นแหล่งความจริงที่ตกลงกันไว้ ยอด order เทียบกับยอด payment ในหน้านี้ก็คือตัวอย่างนั้น

</Step>

<Step>

## เช็กตัวเอง

- ตัวเลขที่ทีมคุณรายงานสำคัญที่สุด แหล่งความจริงของมันคืออะไร และใครเห็นด้วยกับแหล่งนั้นบ้าง
- สองระบบไม่ตรงกัน 1% ของ row คุณต้องมีอะไรก่อนจะบอกได้ว่าระบบไหนผิด
- มีคนขอให้ "ทำ accuracy ให้ถึง 99%" คุณถามอะไรเป็นอย่างแรก

</Step>
