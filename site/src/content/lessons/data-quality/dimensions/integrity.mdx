## Integrity ถามว่าสิ่งที่ถูกอ้างถึง มีอยู่จริงไหม

ลองนึกถึงบัตรยืมหนังสือของห้องสมุด บัตรใบหนึ่งบอกว่าคุณยืมหนังสือรหัส 9017 ไป แต่ในแคตตาล็อกของห้องสมุดไม่มีหนังสือรหัสนี้เลย บัตรใบนั้นกรอกครบและรูปแบบถูกต้องทุกช่อง แต่มันชี้ไปหาของที่ไม่มีอยู่ ข้อมูลของเราเจอเรื่องเดียวกันนี้ใน `orders`

| order_id | customer_id | status | total_amount |
|---:|---:|---|---:|
| 65 | 9017 | SHIPPED | 1882.76 |

order 65 บอกว่าเป็นของ customer หมายเลข 9017 แต่ตาราง `customers` ของเรามี customer แค่หมายเลข 1 ถึง 500 ไม่มีใครชื่อ 9017 เลย key ที่ชี้ไปหาของที่ไม่มีแบบนี้เรียกว่า **orphan** ฝั่ง `payments` ก็เป็นแบบเดียวกัน payment หมายเลข 2534, 2535 และ 2536 ชี้ไปหา order หมายเลข 9001, 9002 และ 9003 ที่ไม่มีอยู่ใน `orders`

DMBOK2 อธิบาย data integrity ว่าเป็นแนวคิดที่รวมเรื่อง completeness, accuracy และ consistency เข้าด้วยกัน และในทางปฏิบัติมักหมายถึงสองอย่าง อย่างแรกคือ referential integrity คือความสอดคล้องระหว่างสองตารางผ่าน reference key ที่ทั้งคู่มี อย่างที่สองคือความสอดคล้องภายใน data set ที่ไม่มีช่องโหว่หรือส่วนที่หายไป data set ที่ไม่มี referential integrity จะมี orphan (reference key ที่ชี้ไปหาของที่ไม่มี) หรือ duplicate (row ที่เหมือนกันเป๊ะซึ่งอาจทำให้ aggregation เพี้ยน) และระดับของ orphan วัดได้ทั้งเป็นจำนวนดิบหรือเป็นเปอร์เซ็นต์ของ data set (หนังสือ: DMBOK2 Table 29 หน้า 459)

</Step>

## หนึ่งคำ สามความหมาย

ก่อนจะวัด integrity ให้ตกลงกันก่อนว่าทีมของเราใช้ความหมายไหน เพราะมีอย่างน้อยสามความหมายที่ใช้กันอยู่

| ที่ไหน | integrity หมายถึง |
|---|---|
| DMBOK2 | หลักๆ คือ referential integrity บวกการไม่มีช่องโหว่ภายใน data set (หนังสือ: DMBOK2 Table 29 หน้า 459) |
| Ten Steps | data integrity fundamentals เป็น dimension ที่กว้างกว่ามาก ครอบคลุม existence, validity, structure และ content ซึ่งได้จากการ profile ส่วน referential integrity เป็นแค่หนึ่งแถวในนั้น (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135) |
| ฐานข้อมูล | integrity constraint เช่น foreign key ที่ database บังคับให้ไม่ให้เกิด orphan |

รายงานที่เขียนว่า "integrity 99%" จึงหมายถึงสามอย่างต่างกัน ขึ้นกับว่าผู้เขียนนึกถึงความหมายไหน เส้นทางนี้ใช้ความหมายของ DMBOK2

ตาราง `orders` กับ `customers` ของเราสร้างจากคำสั่ง `CREATE TABLE ... AS` จึงไม่มี foreign key ประกาศไว้ ไม่มีอะไรในฐานข้อมูลห้าม order ไม่ให้ชี้ไปหา customer ที่ไม่มีอยู่ เราจึงต้องตรวจด้วย query เอง

</Step>

## วัดอย่างไร

```sql
-- order ที่ customer_id ชี้ไปหา customer ที่ไม่มีอยู่
SELECT count(*) FILTER (WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id)),
       count(customer_id)
FROM orders o WHERE customer_id IS NOT NULL;
-- 30 จาก 3,005
```

query นี้เอาแต่ละ order มาถามว่า มี customer ที่มี `customer_id` ตรงกันอยู่ในตาราง `customers` ไหม ถ้าไม่มี order นั้นก็เป็น orphan เราตัด order ที่ `customer_id` ว่างออกด้วย `WHERE customer_id IS NOT NULL` เพราะช่องว่างเป็นเรื่องของ completeness ไม่ใช่ integrity ตัวหารจึงเป็น 3,005 ไม่ใช่ 3,020

ฝั่ง `payments` ก็ใช้ query แบบเดียวกัน ผลคือ payment 20 จาก 2,553 รายการชี้ไปหา order ที่ไม่มี ทั้งสองจำนวนตรงกับที่ฝังไว้ (รัน: `02_dimensions.py`)

</Step>

<Step>

## NOT IN รายงานว่าสะอาดทั้งที่ไม่ใช่

หลายคนเขียน rule นี้ด้วย `NOT IN` เพราะอ่านง่าย

```sql
SELECT count(*) FROM orders
WHERE customer_id NOT IN (SELECT customer_id FROM customers);
-- 30
```

ตอนนี้ได้ 30 เท่ากับ `NOT EXISTS` แต่ลองสมมติว่ารายการ customer ที่ใช้เทียบมี NULL อยู่แค่ตัวเดียว

```sql
SELECT count(*) FROM orders
WHERE customer_id NOT IN (SELECT customer_id FROM customers UNION ALL SELECT NULL);
-- 0
```

ผลกลายเป็น 0 ทันที ทั้งที่ orphan 30 row ยังอยู่เหมือนเดิม เหตุผลคือใน SQL การเทียบกับ NULL ตอบว่า "ไม่รู้" ไม่ใช่ "ใช่" หรือ "ไม่ใช่" และเมื่อรายการมี NULL ปน คำถาม "ค่านี้ไม่อยู่ในรายการ" จะตอบได้แค่ "ไม่รู้" กับทุก row ไม่มี row ไหนถูกนับเลย check จึงรายงานว่า table สะอาดทั้งที่ไม่ใช่ (รัน: `13_dimension_pitfalls.py`)

ดังนั้นให้ใช้ `NOT EXISTS` ซึ่งไม่มีปัญหานี้ ตามที่ query ในหัวข้อก่อนหน้าทำ

</Step>

## Key ที่ว่าง กับ Key ที่ชี้ไปที่ไม่มี

ลองเทียบ order สองแบบที่ผูกกับ customer ไม่ได้

| order_id | customer_id | ปัญหาคืออะไร |
|---:|---:|---|
| 344 | (ว่าง) | ไม่มี key เลย เป็นเรื่อง completeness |
| 65 | 9017 | มี key แต่ชี้ไปหาของที่ไม่มี เป็นเรื่อง integrity |

สองกรณีนี้มีผลเหมือนกัน คือเราไม่รู้ว่า order นี้เป็นของใคร รายงานรายได้แยกตาม customer จะขาด order สองกลุ่มนี้ไป ในที่นี้ `orders.customer_id` ว่าอยู่ 15 row และเป็น orphan อยู่ 30 row รวมแล้ว 45 order ที่ผูกกับ customer ไม่ได้ (รัน: `13_dimension_pitfalls.py`) ให้รายงานสองกลุ่มนี้แยกกัน เพราะวิธีแก้ต่างกัน key ที่ว่างต้องไปแก้ที่ต้นทางที่ไม่ได้ส่งมา ส่วน orphan ต้องไปดูว่า customer หายไปไหน หรือ key ถูกกรอกผิด แล้วเมื่อมีคนถามว่ามีข้อมูลที่ใช้ไม่ได้กี่ row ค่อยบวกสองกลุ่มเข้าด้วยกัน

</Step>

## ตรวจจากฝั่งลูกไปหาฝั่งแม่

ใน `orders` กับ `customers` ตาราง `orders` เรียกว่าตารางลูก (child) เพราะมันอ้างถึง `customers` ซึ่งเป็นตารางแม่ (parent) การตรวจ integrity มีทิศทาง คือเริ่มจากตารางลูกแล้วถามว่าสิ่งที่มันอ้างถึงมีอยู่ในตารางแม่ไหม

ถ้ามี customer ที่ไม่เคยมี order เลย นั่นไม่ใช่การละเมิด เว้นแต่ธุรกิจจะมีกฎว่าทุก customer ต้องเคยสั่งของ ใน dataset ของเราไม่มี customer แบบนั้นเลย (0 คน) ถ้ามี ก็คือคนที่ยังไม่เคยซื้อ เราจึงควรเขียนทิศทางไว้ใน rule ให้ชัดว่า "จากลูกไปหาแม่"

integrity ยังมีข้อจำกัดอีกข้อ key ที่ชี้ไปหาของที่มีอยู่ ก็ยังเป็น key ที่ผิดตัวได้ ลองสมมติว่า order หนึ่งเป็นของ customer 56 แต่ถูกบันทึกเป็น customer 55 ทั้งสองหมายเลขมีอยู่ใน `customers` rule ของเราผ่าน เพราะ integrity ตรวจแค่ว่า key ไปลงที่ไหนสักแห่ง ไม่ได้ตรวจว่าลงถูกที่หรือเปล่า คำถามนั้นเป็นของ [Accuracy](/data-quality/dimensions/accuracy/) และต้องมีแหล่งที่เชื่อถือได้มาเทียบ

</Step>

## ต่างจาก Dimension อื่นอย่างไร

integrity อยู่ใกล้ completeness เพราะ key ที่ว่างก็เป็นช่องว่างที่ควรมีค่า ตามที่ดูไปแล้วในหัวข้อ key ที่ว่าง และอยู่ใกล้ uniqueness เพราะ DMBOK2 ใส่ row ซ้ำไว้ในคำอธิบายของ integrity ด้วย (หนังสือ: DMBOK2 Table 29 หน้า 459) ถ้าเราเอา row ที่ซ้ำไปนับใน [Uniqueness](/data-quality/dimensions/uniqueness/#วัดอย่างไร) แล้ว ก็อย่านับอีกรอบที่นี่ ไม่งั้น scorecard จะนับ row ชุดเดียวกันสองครั้ง สองกรณีต่างกันตรงที่ integrity หา key ที่ชี้ไปหาของที่ไม่มี ส่วน uniqueness หา key ที่โผล่มากเกินไป ใน dataset ของเรา orphan 30 row ส่วน order ที่ซ้ำเกินมา 20 row

integrity กับ consistency ก็ใช้ป้ายทับกันได้ ตัวอย่างของ Ten Steps ที่ว่า order date ต้องมาก่อน ship date อยู่ใต้ referential integrity ในหนังสือเล่มนั้น แต่เราจัดมันเป็น consistency ในเส้นทางนี้ ดูรายละเอียดที่หน้า [Consistency](/data-quality/dimensions/consistency/)

</Step>

## เช็กตัวเอง

- ทีมของคุณใช้ความหมายไหนใน 3 ความหมายของ integrity และมีเขียนไว้ที่ไหนบ้างไหม
- ผู้ review เขียน check orphan ของคุณใหม่ด้วย `NOT IN` แล้วได้ 0 บน table ที่คุณรู้ว่ามี orphan คุณจะดูอะไรเป็นอย่างแรก
- customer 55 กับ customer 56 มีอยู่ทั้งคู่ใน table คุณจะรู้ได้อย่างไรว่า order นี้ควรชี้ไปหาคนไหน

</Step>
