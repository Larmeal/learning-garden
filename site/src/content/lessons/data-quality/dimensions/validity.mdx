## คำนี้ถามอะไร

DMBOK2 นิยาม validity ว่าค่าของข้อมูลสอดคล้องกับ domain ของค่าที่กำหนดไว้หรือไม่ domain อาจเป็นชุดค่าที่ยอมรับ เช่น reference table เป็นช่วงของค่า หรือค่าที่ตัดสินได้ด้วย rule data type, format และ precision ล้วนเป็นส่วนของนิยาม domain (หนังสือ: DMBOK2 Table 29 หน้า 459) DAMA UK พูดสั้นกว่า: ข้อมูลเป็นไปตาม syntax (format, type, range) ของนิยามของมัน (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 457)

นึกถึงคนถือรายชื่อแขกที่หน้าประตู เขาบอกได้ว่าชื่อนี้อยู่ในรายชื่อ แต่บอกไม่ได้ว่าคนที่ยืนอยู่ตรงหน้าเป็นคนนั้นจริงหรือเปล่า validity เป็นแค่ด่านแรก

</Step>

## Domain สามแบบบน Row จริง

| แบบของ domain | rule ใน data ของเรา | ไม่ผ่าน | row ตัวอย่างที่ไม่ผ่าน |
|---|---|---:|---|
| รายการ | `country` เป็น TH, SG, JP หรือ US | 25 จาก 500 | 36 `THA`, 101 `T.H.`, 135 `Thailand`, 138 `ไทย` |
| ช่วง | `birth_date` อยู่ระหว่าง 1900-01-01 ถึงวันนี้ | 6 จาก 500 | 367 `1890-05-01`, 80 `2030-01-01` |
| ช่วง | `total_amount` ไม่ติดลบ | 12 จาก 3,020 | order 321 `-187.35`, order 436 `-94.01` |
| รูปแบบ | `email` หน้าตาเป็น `a@b.c` (เฉพาะ row ที่ไม่ NULL) | 15 จาก 460 | 23 `user23example.com`, 88 `user88example.com` |

```sql
SELECT count(*) FILTER (WHERE country NOT IN ('TH','SG','JP','US')), count(*) FROM customers;
-- 25 จาก 500
```

ทุกตัวเลขตรงกับที่ generator ฝังไว้ (รัน: `02_dimensions.py`) row ที่ไม่ผ่านพังคนละแบบ บางตัวเป็นขยะ (`1850-01-01`) บางตัวเป็นการสะกดอีกแบบของสิ่งที่มีจริง (`ไทย`) และบางตัวอาจเป็น row ที่ถูกต้องก็ได้ ซึ่งขั้นถัดไปจะกลับมาพูดถึง

</Step>

## ความหมายที่ถูกเข้าใจผิดบ่อย

<Callout type="warn" title="1. Valid ไม่ใช่ accurate">
ในจำนวน 35 order ที่ยอดไม่ตรงกับ payment system ทั้ง 35 ผ่าน `total_amount >= 0` และในจำนวน 20 customer ที่ใช้ email ซ้ำกับคนอื่น ทั้ง 20 มี email รูปแบบถูกต้อง (รัน: `13_dimension_pitfalls.py`) validity 100% บอกแค่ว่าไม่มีสิ่งที่เป็นไปไม่ได้หลุดเข้ามา ไม่ได้บอกว่าสิ่งที่เข้ามาถูก DMBOK2 เตือนเรื่องเดียวกัน: ข้อมูลอาจ valid แต่ไม่ accurate หรือถูกผูกกับ record ผิดตัวก็ได้ (หนังสือ: DMBOK2 Table 29 หน้า 459)
</Callout>

**2. rule ที่หลวมรับขยะได้** pattern `^[^@\s]+@[^@\s]+\.[^@\s]+$` รับ `a@b.c` และ `nobody@nowhere.zz` ใน table email สมมติ 6 ค่า มันรับ 4 ค่า รวมถึง `a@b.c` กับ `x@y.z` (รัน: `13_dimension_pitfalls.py`) การผ่านแปลว่า "หน้าตาเป็น email" ส่วนว่า mailbox นั้นมีจริงไหม เป็นอีกคำถาม และมีแต่การส่งเมลยืนยันที่ตอบได้

**3. rule คือคำพูดของธุรกิจ ไม่ใช่คำพูดของข้อมูล** เราถือว่า `total_amount` ติดลบคือ defect ได้ 12 row ถ้าร้านบันทึกการคืนเงินเป็น order ติดลบ row เหล่านั้นถูกต้อง และ rule ผิดเอง ข้อมูลตัดสินเรื่องนี้ไม่ได้ เจ้าของข้อมูลตัดสินได้ ขอบล่างปี 1900 ของ `birth_date` ก็เช่นกัน มันเป็นการเลือก customer ที่เกิดปี 1899 จะตก rule ที่เป็นแค่ธรรมเนียม ควรจดว่าใครเขียนแต่ละ rule และใครเห็นด้วย (การเลือก rule เป็นของผู้เขียน)

**4. วันที่ valid ได้สองแบบพร้อมกัน** `09/05/2026` คือ 9 พฤษภาคม ถ้าวันมาก่อน และ 5 กันยายน ถ้าเดือนมาก่อน ใน table วันที่สมมติ 3 string parser แบบวันก่อนรับ 2 ค่า parser แบบเดือนก่อนรับ 2 ค่า และ `09/05/2026` ผ่านทั้งสองแบบทั้งที่หมายถึงคนละวัน (รัน: `13_dimension_pitfalls.py`) Ten Steps บอกให้ชัดเรื่อง format ของวันที่ด้วยเหตุผลนี้ (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135)

**5. validity หมดอายุได้** หนังสือบอกว่าข้อมูลบางชนิด valid เฉพาะช่วงเวลาหนึ่ง เช่น ข้อมูลจาก RFID หรือ data set ทางวิทยาศาสตร์บางชุด (หนังสือ: DMBOK2 Table 29 หน้า 459) rule ที่ผ่านปีที่แล้วอาจตกปีนี้โดยไม่มี row ไหนเปลี่ยน

**6. ค่านอกรายการอาจเป็นอีกปัญหาหนึ่งด้วย** `ไทย` อยู่นอกรายการจึงตก validity และมันเขียนประเทศเดียวกับที่ `TH` เขียน ซึ่งเป็นปัญหา consistency คุณจะปฏิเสธมัน หรือ map เป็น `TH` ก็ได้ การวัดไม่ได้เลือกให้ ดู[หน้า consistency](/data-quality/dimensions/consistency/#สามระดับ)

</Step>

## ที่มักสับสนด้วย

| ดูคล้ายกับ | แยกอย่างไร | ใน data ของเรา |
|---|---|---|
| Accuracy | Validity เช็กกับ rule Accuracy เช็กกับของจริงหรือแหล่งที่เชื่อถือได้ | 35 ยอดผิด ทุกตัว valid |
| Consistency | Validity ต้องมี domain ที่กำหนดไว้ Consistency ต้องมีสอง representation มาเทียบกัน | `ไทย` ไม่ valid เทียบกับรายการ และไม่ consistent กับ `TH` |
| Completeness | NULL คือไม่มีค่า ไม่ใช่ค่าที่ invalid | email NULL 40 ตัวไม่ถูกนับใน 15 จาก 460 |

แถวสุดท้าย: เราตัด NULL ออกจากตัวหารของ validity โดยตั้งใจ เพื่อให้ email ที่ว่างหนึ่งช่องตก completeness ครั้งเดียว ไม่ใช่สองครั้ง Ten Steps รายงาน validity แบบนี้ เช่น "fill rate 95% และใน row ที่มีค่า 90% เป็นไปตามรูปแบบ" (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135)

</Step>

<Step>

## เช็กตัวเอง

- เขียน domain ของ column หนึ่งที่คุณใช้อยู่ มันเป็นรายการ ช่วง หรือรูปแบบ นิยามอยู่ที่ไหน และใครแก้ล่าสุด
- validity ของ `email` เป็น 100% หลังคุณทำ rule ให้เข้มขึ้น คุณยังไม่รู้อะไรเกี่ยวกับ column นี้อีก
- rule หนึ่งตก 12 row คุณจะถามอะไรก่อนเรียกมันว่า defect

</Step>

| row ที่ไม่ผ่าน 25, 6, 12 และ 15; row ตัวอย่าง | รัน: `02_dimensions.py` และ query บน data ชุดเดียวกัน |
