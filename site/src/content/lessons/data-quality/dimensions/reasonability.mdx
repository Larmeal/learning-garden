## คำนี้ถามอะไร

DMBOK2 บอกว่า reasonability ถามว่า pattern ของข้อมูลเป็นไปตามที่คาดหรือไม่ ตัวอย่างของหนังสือคือ การกระจายของยอดขายข้ามพื้นที่ภูมิศาสตร์สมเหตุสมผลไหม เมื่อดูจากสิ่งที่รู้เกี่ยวกับ customer ในพื้นที่นั้น การวัดทำได้หลายรูปแบบ: เทียบกับ benchmark data หรือเทียบกับ data set ชุดคล้ายกันในอดีต เช่น ยอดขายไตรมาสก่อน เมื่อมีค่า benchmark แล้ว ก็ใช้เทียบ data set ชุดใหม่แบบเดียวกันเพื่อจับการเปลี่ยนแปลงได้ (หนังสือ: DMBOK2 Table 29 หน้า 459)

นึกถึงเจ้าของร้านที่ดูม้วนใบเสร็จตอนปิดร้าน ทุกใบดูปกติ แต่ยอดรวมเป็น 1% ของวันอังคารทั่วไป เจ้าของรู้ว่ามีอะไรผิดโดยไม่ต้องอ่านใบเสร็จสักใบ ความคาดหวังนั้นอยู่ในหัวเจ้าของ reasonability คือการแปลงมันให้เป็นตัวเลข

Ten Steps ยกตัวอย่างเล็กกว่าของแนวคิดเดียวกันภายใน row หรือ column วันเกิดกับอายุที่ขัดกัน เช่น ผู้สมัครที่ต้องอายุ 18 ขึ้นไป แต่วันที่ทำให้เขาอายุ 2 ขวบ และ frequency distribution ของ country code ที่ไม่สอดคล้องกับที่คุณคาดว่าขายได้แต่ละประเทศเท่าไร (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135)

</Step>

## วันเสียที่ Rule ระดับ Row ไม่เห็น

dataset ของเราไม่มี defect ชนิดนี้ที่ฝังไว้ หน้านี้จึงใช้ copy ที่ดัดแปลง: ยอดทั้งหมดของวันเดียวคือ 30 สิงหาคมถูกหารด้วย 100 เหมือนต้นทางหนึ่งส่งหน่วยย่อยมาแทนหน่วยเต็ม นี่เป็นของที่สมมติขึ้น และข้อมูลต้นฉบับไม่ถูกแตะ (รัน: `13_dimension_pitfalls.py`)

| check | ผลบน copy ที่ดัดแปลง |
|---|---|
| Validity: `total_amount >= 0` | ตก 0 row ยอดทุกตัวเป็นเลขบวก |
| Reasonability: ยอดเฉลี่ยของวันห่างจากปกติมาก | flag 1 วัน |

บนข้อมูลต้นฉบับ ยอดเฉลี่ยรายวันอยู่ที่ราว 2,537 มี spread (standard deviation) 304 บน copy ที่ดัดแปลง วันที่ 30 สิงหาคมมียอดเฉลี่ย 27.89 rule คือ "flag วันที่ยอดเฉลี่ยห่างจากค่าเฉลี่ยของยอดเฉลี่ยรายวันเกิน 3 standard deviation" มัน flag 1 วันบน copy และ 0 วันบนข้อมูลต้นฉบับ

```sql
SELECT CAST(order_ts AS DATE) AS d, count(*) AS n, avg(total_amount) AS avg_total
FROM (SELECT DISTINCT * FROM orders WHERE total_amount >= 0)
GROUP BY 1 ORDER BY 1;
-- แล้วเทียบ avg_total กับประวัติของมันเอง
```

check นี้เขียนเป็น filter บน row เดียวไม่ได้ ต้องมี aggregate ข้ามหลาย row และ baseline จากวันอื่น นี่คือเหตุผลที่ในทางปฏิบัติมันอยู่ในบท monitoring ([บท 7](/data-quality/monitoring/#volume-ฤดูกาลทำให้-z-score-หลง))

</Step>

## ความหมายที่ถูกเข้าใจผิดบ่อย

<Callout type="warn" title="1. threshold ที่เอามาจากค่าเฉลี่ยอย่างเดียว fire ในวันปกติ">
bar ตัวอย่างของหนังสือสำหรับ consistency ข้ามเวลา คือวันที่เกิน 105% ของค่าเฉลี่ยเคลื่อนที่ 30 วันก่อนหน้า (หนังสือ: DMBOK2 Table 29 หน้า 458) จำนวน order รายวันของเรามีค่าเฉลี่ย 24.7 และ standard deviation 4.8 ใช้ bar นั้นแล้ว fire 34 จาก 91 วันที่มีประวัติ 30 วัน (รัน: `13_dimension_pitfalls.py`) ในวันเหล่านั้นไม่มีอะไรผิด จำนวนมันมีสัญญาณรบกวน และ bar 5% แคบกว่าสัญญาณรบกวนมาก bar ต้องมี spread ด้วย ไม่ใช่แค่ค่าเฉลี่ย เช่น "เกิน 3 standard deviation จากค่าเฉลี่ย" ให้ถือตัวเลขของหนังสือเป็นภาพประกอบของแนวคิด
</Callout>

**2. "สมเหตุสมผล" เป็นความเห็นของใครสักคนจนกว่าจะเขียนลงไป** หนังสือบอกว่าแนวคิดเรื่อง reasonability บางอย่างอาจถูกมองว่าเป็นเรื่องอัตวิสัย และให้ทำงานกับ data consumer เพื่อสรุปฐานของความคาดหวังและแปลงเป็นการเทียบที่เป็นรูปธรรม (หนังสือ: DMBOK2 Table 29 หน้า 459) ให้ถามว่า คนที่รู้ธุรกิจคาดว่าจะเห็นอะไรที่นี่ และห่างแค่ไหนจึงเรียกว่า "ไกลเกินไป"

**3. ผ่านเป็นหลักฐานที่อ่อน และตกก็ไม่ใช่การพิสูจน์** ค่าผิดที่ดูเป็นไปได้จะผ่าน: ยอดที่สูงเกินจริง 10% ยังอยู่ในช่วงปกติสบายๆ เหตุการณ์จริงจะตก: วัน promotion จะอยู่ห่างจากค่าเฉลี่ย และ rule จะ fire alert ตรงนี้เป็นการขอให้คนไปดู ไม่ได้บอกว่าข้อมูลผิด (ข้อสังเกตนี้เป็นของผู้เขียน)

**4. baseline ต้องเชื่อถือได้** ถ้าประวัติที่ใช้ตั้งค่าเฉลี่ยและ spread มีวันเสียอยู่ band จะกว้างขึ้นและพลาดวันเสียครั้งถัดไป ในตัวอย่างข้างบน วันเสียหนึ่งวันจาก 121 วันทำให้ spread เพิ่มจาก 304 เป็น 379 เมื่อถูกนับรวมในประวัติของตัวเอง มันยังถูกจับได้ เพราะอยู่ไกลมาก ให้สร้าง baseline จากข้อมูลที่ตรวจแล้ว และอัปเดตมันโดยตั้งใจ

**5. เป็น dimension เดียวในเส้นทางนี้ที่ไม่มี defect ที่ฝังไว้** อีกเจ็ด dimension มีจำนวนที่สคริปต์ตรวจ อันนี้มีวันที่สมมติกับ threshold ซึ่งเป็นหลักฐานที่อ่อนกว่า และเราบอกไว้ตรงๆ

</Step>

## ที่มักสับสนด้วย

| ดูคล้ายกับ | แยกอย่างไร | ใน data ของเรา |
|---|---|---|
| Validity | Validity ตัดสินค่าเดียวเทียบกับ domain Reasonability ตัดสิน pattern ข้ามหลายค่า | วันเสียผ่าน validity ทั้งหมด |
| Consistency ข้ามเวลา | ตัวอย่าง temporal consistency ของหนังสือ (rule 105%) คือ check reasonability ที่ใช้ชื่ออื่น | ดู[หน้า consistency](/data-quality/dimensions/consistency/#ความหมายที่ถูกเข้าใจผิดบ่อย) |
| Accuracy | pattern ที่สมเหตุสมผลก็ยังผิดได้ และ pattern แปลกก็จริงได้ | วัน promotion ที่ดีดูไม่สมเหตุสมผล |
| Timeliness | วันที่หายไปปรากฏเป็นจำนวน 0 ซึ่งก็เป็น pattern ที่ไม่สมเหตุสมผลเหมือนกัน | pipeline ที่เงียบดูเหมือนร้านที่เงียบมาก |

</Step>

## เช็กตัวเอง

- ตัวเลขหนึ่งที่คุณรายงานทุกวัน ช่วงปกติของมันคือเท่าไร และใครบอกคุณ
- alert ของคุณใช้ "สูงกว่าค่าเฉลี่ย 30 วัน 5%" และ fire วันเว้นวัน คุณเปลี่ยนอะไรเป็นอย่างแรก
- check เดียวกัน flag แคมเปญการตลาดที่เกิดขึ้นจริง rule ควรแยกความต่างได้อย่างไร และควรแยกไหม

</Step>
