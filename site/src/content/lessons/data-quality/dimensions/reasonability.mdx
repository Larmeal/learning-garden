## Reasonability ถามว่า Pattern ของข้อมูลหน้าตาเป็นอย่างที่คาดไหม

นึกถึงเจ้าของร้านที่ดูม้วนใบเสร็จตอนปิดร้าน ใบเสร็จทุกใบดูปกติ ไม่มีใบไหนผิดเลย แต่ยอดรวมของวันเป็นแค่ 1% ของวันอังคารทั่วไป เจ้าของร้านรู้ทันทีว่ามีอะไรผิด โดยไม่ต้องอ่านใบเสร็จสักใบ เพราะเขาคาดหวังไว้แล้วว่ายอดควรอยู่แถวไหน Reasonability คือการเปลี่ยนความคาดหวังนั้นให้เป็นตัวเลขที่ตรวจได้

DMBOK2 บอกว่า Reasonability ถามว่า Pattern ของข้อมูลเป็นไปตามที่คาดไหม ตัวอย่างของหนังสือคือ การกระจายของยอดขายข้ามพื้นที่ภูมิศาสตร์สมเหตุสมผลไหม เมื่อดูจากสิ่งที่เรารู้เกี่ยวกับ Customer ในพื้นที่นั้น วัดได้หลายแบบ เช่น เทียบกับ Benchmark Data หรือเทียบกับ Data Set ชุดคล้ายกันในอดีต เช่นยอดขายไตรมาสก่อน เมื่อมีค่า Benchmark ที่ตกลงกันแล้ว ก็เอามาเทียบกับข้อมูลชุดใหม่เพื่อจับว่ามีอะไรเปลี่ยนไปได้ (หนังสือ: DMBOK2 Table 29 หน้า 459)

Ten Steps ยกตัวอย่างเล็กกว่าของแนวคิดเดียวกัน ภายใน Row หรือ Column เช่น วันเกิดกับอายุที่ขัดกัน (ผู้สมัครที่ต้องอายุ 18 ปีขึ้นไป แต่วันที่ในข้อมูลทำให้เขาอายุแค่ 2 ขวบ) หรือการกระจายของ Country Code ที่ไม่ตรงกับที่เราคาดว่าขายได้ในแต่ละประเทศ (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135)

## วันเสียที่ Rule ระดับ Row มองไม่เห็น

Dataset ของเราไม่มี Defect ชนิดนี้ที่ฝังไว้ เราจึงสร้างขึ้นเองใน Copy ของ `orders` โดยหารยอดของทุก Order ในวันที่ 30 สิงหาคมด้วย 100 เหมือนกับว่าต้นทางหนึ่งส่งยอดเป็นหน่วยย่อยแทนหน่วยเต็ม ตัวข้อมูลต้นฉบับไม่ถูกแตะ และนี่เป็นสถานการณ์สมมติ (รัน: `13_dimension_pitfalls.py`)

ลองเทียบ Rule สองแบบกับ Copy นี้

| Check | ผลบน Copy ที่ดัดแปลง |
|---|---|
| Validity: `total_amount >= 0` | ตก 0 Row เพราะยอดทุกตัวยังเป็นเลขบวก |
| Reasonability: ยอดเฉลี่ยของวันห่างจากปกติมาก | Flag 1 วัน |

บนข้อมูลต้นฉบับ ยอดเฉลี่ยของ Order ต่อวันอยู่ที่ราว 2,537 และแกว่งจากค่านั้นประมาณ 304 (นี่คือ Standard Deviation ซึ่งบอกว่าตัวเลขรายวันกระจายห่างจากค่าเฉลี่ยโดยปกติแค่ไหน) ส่วนใน Copy วันที่ 30 สิงหาคมมียอดเฉลี่ยแค่ 27.89

Rule ที่เราใช้คือ "Flag วันที่ยอดเฉลี่ยห่างจากค่าเฉลี่ยของยอดเฉลี่ยรายวัน เกิน 3 เท่าของ Standard Deviation" มัน Flag 1 วันบน Copy และ 0 วันบนข้อมูลต้นฉบับ

```sql
SELECT CAST(order_ts AS DATE) AS d, count(*) AS n, avg(total_amount) AS avg_total
FROM (SELECT DISTINCT * FROM orders WHERE total_amount >= 0)
GROUP BY 1 ORDER BY 1;
-- แล้วเทียบ avg_total ของแต่ละวันกับประวัติของมันเอง
```

Check นี้เขียนเป็น Filter บน Row เดียวไม่ได้ ต้องมี Aggregate ข้ามหลาย Row และ Baseline จากวันอื่น ในทางปฏิบัติมันจึงไปอยู่ในงาน Monitoring ที่ [บท 7](/data-quality/monitoring/#volume-ฤดูกาลทำให้-z-score-หลง) สอนไว้

## Threshold จากค่าเฉลี่ยอย่างเดียว Fire ในวันปกติ

ตัวอย่าง Bar ของหนังสือสำหรับ Consistency ข้ามเวลา คือวันที่เกิน 105% ของค่าเฉลี่ยของ 30 วันก่อนหน้า (หนังสือ: DMBOK2 Table 29 หน้า 458) ลองเอา Bar นี้ไปใช้กับจำนวน Order รายวันของเรา ซึ่งมีค่าเฉลี่ย 24.7 รายการ และแกว่งขึ้นลงประมาณ 4.8 รายการ

Bar นี้ Fire ถึง 34 จาก 91 วันที่มีประวัติครบ 30 วัน ทั้งที่ไม่มีอะไรผิดในวันเหล่านั้นเลย เพราะจำนวน Order รายวันแกว่งอยู่แล้วตามธรรมชาติ และ 5% เป็นช่วงที่แคบกว่าความแกว่งมาก Bar ที่ดีจึงต้องมี Standard Deviation ด้วย เช่น "เกิน 3 เท่าของ Standard Deviation จากค่าเฉลี่ย" ตัวเลข 105% ของหนังสือเป็นภาพประกอบของแนวคิด ใช้เป็นเกณฑ์ตรง ๆ ในทุกที่ไม่ได้ (รัน: `13_dimension_pitfalls.py`)

</Step>

## สมเหตุสมผล ต้องเขียนเป็นตัวเลข

คำว่า "สมเหตุสมผล" เป็นแค่ความเห็นของใครสักคน จนกว่าเราจะเขียนมันลงเป็นตัวเลข หนังสือบอกว่าความคาดหวังบางอย่างอาจดูเป็นเรื่องอัตวิสัย และให้เราทำงานกับ Consumer ของข้อมูล เพื่อรู้ว่าเขาคาดหวังอะไร และคาดหวังบนฐานอะไร แล้วแปลงเป็นการเทียบที่เป็นรูปธรรม (หนังสือ: DMBOK2 Table 29 หน้า 459)

คำถามที่ควรถามเขาคือ คนที่รู้ธุรกิจน่าจะเห็นอะไรที่นี่ และห่างแค่ไหนถึงจะเรียกว่าไกลเกินไป คำตอบของเขาคือเกณฑ์ที่เราจะใช้

</Step>

<Step>

## Baseline ต้องเชื่อถือได้ และผลคือสัญญาณให้คนไปดู

ถ้าประวัติที่เรานำมาหาค่าเฉลี่ยมีวันเสียปนอยู่ ช่วงปกติจะกว้างขึ้นและเราจะมองไม่เห็นวันเสียครั้งต่อไป ในตัวอย่างข้างบน วันเสียวันเดียวจาก 121 วัน ทำให้ Standard Deviation เพิ่มจาก 304 เป็น 379 เมื่อนับรวมอยู่ในประวัติของตัวเอง แต่วันนั้นยังถูกจับได้ เพราะอยู่ห่างมาก เพราะฉะนั้นเราควรสร้าง Baseline จากข้อมูลที่ตรวจแล้ว และอัปเดตมันอย่างตั้งใจ

และเมื่อ Rule Fire เราควรมองมันเป็นสัญญาณให้คนไปดู เพราะยังสรุปไม่ได้ว่าข้อมูลผิด ยอดที่ผิดแต่ดูเป็นไปได้จะผ่านเกณฑ์ เช่นยอดที่สูงเกินจริง 10% ก็ยังอยู่ในช่วงปกติสบาย ๆ ส่วนเหตุการณ์จริงเช่นวัน Promotion จะอยู่ห่างจากค่าเฉลี่ย และทำให้เกณฑ์ Fire ทั้งที่ข้อมูลถูกต้อง (ข้อสังเกตนี้เป็นของผู้เขียน)

</Step>

## ต่างจาก Dimension อื่นอย่างไร

Reasonability ต่างจาก [Validity](/data-quality/dimensions/validity/) ตรงที่ Validity ตัดสินค่าเดียวเทียบกับ Domain ส่วน Reasonability ตัดสิน Pattern ของหลายค่า วันเสียของเราผ่าน Validity ทั้งหมด

ตัวอย่าง Temporal Consistency ในหนังสือ (Rule 105%) ที่หน้า [Consistency](/data-quality/dimensions/consistency/#สามระดับ) กล่าวถึง ก็คือการตรวจ Reasonability ที่ใช้ชื่ออื่น

Pipeline ที่เงียบไปทั้งวัน ทำให้ตารางดูเหมือนร้านที่เงียบมาก ซึ่งเป็นปัญหา [Timeliness](/data-quality/dimensions/timeliness/) แต่ Reasonability ก็จับได้เหมือนกัน

Reasonability เป็น Dimension เดียวในเส้นทางนี้ที่ไม่มี Defect ที่ฝังไว้ใน Dataset อีกเจ็ด Dimension มีจำนวนที่สคริปต์ตรวจ ส่วนตัวนี้มีวันที่สมมติกับ Threshold ซึ่งเป็นหลักฐานที่อ่อนกว่า เราจึงขอบอกไว้ตรง ๆ

</Step>

## เช็กตัวเอง

- ตัวเลขหนึ่งที่คุณรายงานทุกวัน ช่วงปกติของมันคือเท่าไร และใครเป็นคนบอกคุณ
- Alert ของคุณใช้ "สูงกว่าค่าเฉลี่ย 30 วัน 5%" แล้ว Fire วันเว้นวัน คุณเปลี่ยนอะไรเป็นอย่างแรก
- Check เดียวกัน Flag แคมเปญการตลาดที่เกิดขึ้นจริง Rule ควรแยกความต่างนี้ได้อย่างไร และควรแยกไหม

</Step>
