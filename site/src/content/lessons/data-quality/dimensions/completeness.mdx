## คำนี้ถามอะไร

DMBOK2 ตั้งเป็นคำถามเดียว: ข้อมูลที่ต้องมี มีครบหรือไม่ หนังสือบอกว่าวัด completeness ได้ที่ระดับ data set, record และ column (หนังสือ: DMBOK2 Table 29 หน้า 458) ส่วน DAMA UK ให้เป็นอัตราส่วน คือสัดส่วนของข้อมูลที่เก็บไว้เทียบกับศักยภาพที่ควรเต็ม 100% (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 457)

ลองนึกถึงแบบฟอร์มกระดาษที่บางช่องเป็นช่องบังคับ completeness คือสัดส่วนของฟอร์มที่ทุกช่องบังคับมีอะไรเขียนอยู่ ส่วนว่าสิ่งที่เขียนถูกหรือเปล่า เป็นคำถามของ dimension อื่น

| ระดับ | คำถาม | ดูได้จากไหน |
|---|---|---|
| Data set | มี record ที่ควรมีครบไหม | เทียบกับ source of record หรือจำนวน row ในอดีต ([บท 8](/data-quality/reconciliation/#reconcile-ด้วยจำนวน-row-และผลรวม)) |
| Record | row นี้ถูกกรอกตามที่ status ของมันต้องการไหม | order ที่ SHIPPED ต้องมี `shipped_ts` |
| Column | field นี้ถูกกรอกในระดับที่ควรเป็นไหม | `customers.email`: 460 จาก 500 |

ระดับ data set ถามว่า record ที่เราคาดว่าจะมี มาครบไหม rule บน row ตอบเรื่องนี้ไม่ได้ เพราะ row ที่หายไปไม่เหลืออะไรให้ตรวจ หนังสือบอกสองวิธีวัด วิธีแรกคือเทียบกับ source of record เช่น จำนวน row ในระบบต้นทาง วิธีที่สองคือเทียบกับว่า data set นี้เคยเต็มแค่ไหนในอดีต ซึ่งหนังสือเรียกว่า historical levels of population (หนังสือ: DMBOK2 Table 29 หน้า 458) วิธีที่สองไม่ต้องมีต้นทางให้เทียบ แค่ต้องรู้ว่าอะไรคือปกติ ถ้า table นี้ปกติรับ order ประมาณ 25 รายการต่อวัน แต่วันนี้มี 6 รายการ น่าจะมี row หายไป ทั้งที่ทุก row ที่มาถึงกรอกครบ เข้าใจผิดข้อ 3 ข้างล่างแสดงเรื่องนี้บน data ของเรา

</Step>

## Mandatory, Conditional, Inapplicable

ก่อนเขียน rule ของ completeness ให้ถามก่อนว่า column นี้ "ควรมีค่าเมื่อไร" หนังสือแบ่งคำตอบเป็นสามกลุ่ม (หนังสือ: DMBOK2 Table 29 หน้า 458):

| กลุ่ม | ความหมาย | ช่องว่างแปลว่า | ตัวอย่าง |
|---|---|---|---|
| Mandatory | ทุก row ต้องมีค่าเสมอ | defect | `order_id` ของ `orders` ถ้าไม่มี ก็ระบุไม่ได้ว่า row นี้คือ order ไหน |
| Conditional หรือ optional | ต้องมีค่าเฉพาะเมื่อเข้าเงื่อนไข หรือจะมีหรือไม่ก็ได้ | defect เฉพาะ row ที่เข้าเงื่อนไข ถ้า optional จริงก็ไม่ใช่ defect | `shipped_ts` ต้องมีเมื่อ status เป็น SHIPPED ส่วนช่องที่ลูกค้าจะกรอกหรือไม่ก็ได้ เช่น เบอร์โทร เป็น optional (dataset ของเราไม่มี column แบบนี้) |
| Inapplicable | ไม่มีความหมายสำหรับ row นี้ จึงต้องว่าง | ปกติ ถ้ามีค่าต่างหากที่ผิด | `shipped_ts` ของ order ที่ยังเป็น PLACED หรือถูก CANCELLED ไปแล้ว |

ช่องว่างหน้าตาเหมือนกันทุกกลุ่ม แต่ความหมายต่างกัน ช่องว่างใน column ที่ mandatory คือ defect ช่องว่างใน column ที่ inapplicable คือสิ่งที่ถูกต้อง ส่วนกลุ่มกลางต้องดูเงื่อนไขก่อนถึงจะตัดสินได้

`shipped_ts` ตกอยู่ในสองกลุ่มพร้อมกัน ขึ้นกับ status ของ row จึงเป็นตัวอย่างที่ชัดที่สุด:

| status | row | `shipped_ts` ที่มีค่า | ที่ควรเป็น |
|---|---:|---:|---|
| PLACED | 756 | 0 | ว่าง เพราะยังไม่ได้ส่ง |
| SHIPPED | 1,794 | 1,769 | มีค่าทุก row |
| CANCELLED | 470 | 0 | ว่าง |

column นี้เป็น NULL 1,251 จาก 3,020 row (41.4%) ในจำนวนนี้ 1,226 row ถูกต้องแล้ว และ 25 row เป็น order ที่ SHIPPED แต่ไม่มีเวลา ซึ่งคือ defect ที่ฝังไว้ (รัน: `13_dimension_pitfalls.py`)

```sql
SELECT count(*) FILTER (WHERE status = 'SHIPPED' AND shipped_ts IS NULL),
       count(*) FILTER (WHERE status = 'SHIPPED')
FROM orders;
-- 25 จาก 1,794
```

## เข้าใจผิดข้อ 1: NULL คือ Defect เสมอ

- **ที่มักเข้าใจ:** ช่องว่างทุกช่องคือข้อมูลที่หายไป
- **ที่จริง:** ช่องว่างใน column แบบ conditional หรือ inapplicable เป็นเรื่องปกติ
- **ดูใน data:** `shipped_ts` เป็น NULL 1,251 row แต่ 1,226 row ถูกต้องอยู่แล้ว (PLACED และ CANCELLED) defect จริงมีแค่ 25 row
- **ควรทำ:** เขียนขอบเขตลงใน rule เช่น "เมื่อ status เป็น SHIPPED" คะแนน completeness ที่ไม่มีขอบเขตไม่มีใครตีความได้

</Step>

<Step>

## เข้าใจผิดข้อ 2: ช่องที่มีค่า คือช่องที่มีข้อมูล

- **ที่มักเข้าใจ:** `IS NULL` นับของที่หายได้ครบ
- **ที่จริง:** string ว่าง, `N/A`, ช่องว่างล้วน, ขีดกลาง และ `000-000-0000` ผ่าน `IS NULL` หมด ทั้งที่ไม่มีข้อมูลจริง
- **ดูใน data:** table เบอร์โทรสมมติ 8 row `IS NULL` เจอ 1 ค่า ส่วน check ที่หา string ว่างและ placeholder ด้วยเจอ 6 ค่า (รัน: `13_dimension_pitfalls.py`)
- **ควรทำ:** ดู frequency ของค่าที่พบบ่อยใน column ([บท 3](/data-quality/profiling/#ดู-frequency-ของค่าใน-column-ที่มีค่าไม่กี่แบบ)) หา default value และตัวอักษรที่คนพิมพ์เพื่อให้ผ่าน Ten Steps เล่าถึงนิสัยพิมพ์จุดลงใน field บังคับให้บันทึกผ่าน และบางทีมถือว่า field ที่มีแต่ค่า default ยังไม่ถูกกรอก (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135)

</Step>

<Step>

## เข้าใจผิดข้อ 3: ทุก Row เต็ม แปลว่า Table เต็ม

- **ที่มักเข้าใจ:** ถ้าทุก row กรอกครบ completeness ก็ 100%
- **ที่จริง:** rule ระดับ column เห็นเฉพาะ row ที่มาถึง row ที่หายไปไม่เหลืออะไรให้ตรวจ
- **ดูใน data:** dataset ที่ใช้ร่วมกันไม่มี row ที่หาย จึงใช้ copy ที่ลบ order ไป 4 ใน 5 ของวันที่ 30 สิงหาคม เหลือ 6 row จากเดิม 30 check ระดับ row ผ่าน 2,976 จาก 2,976 แต่วันอื่น table รับ order วันละ 24.8 รายการ (standard deviation 4.7) วันต่ำสุดตามปกติจึงอยู่ราว 10.6 และ 6 ต่ำกว่านั้นมาก (รัน: `13_dimension_pitfalls.py`)
- **ควรทำ:** นับ row เทียบกับต้นทาง ([บท 8](/data-quality/reconciliation/#reconcile-ด้วยจำนวน-row-และผลรวม)) หรือเทียบกับประวัติของ table เอง
- **ข้อเสียของการเทียบประวัติ:** ดีได้เท่าอดีตที่ใช้สร้างเกณฑ์ และวันที่เงียบจริงเพราะเหตุผลทางธุรกิจดูเหมือนวันที่ row หายทุกประการ

</Step>

<Step>

## เข้าใจผิดข้อ 4: ตัวหารเหมือนกันทุก Rule

- **ที่มักเข้าใจ:** ทุก rule หารด้วยจำนวน row ทั้งหมด
- **ที่จริง:** ตัวหารเปลี่ยนคะแนน และแต่ละ rule เลือกตัวหารของตัวเองได้
- **ดูใน data:** `customers.email` complete 92.00% จาก 500 customer แต่ rule format ของ email ใช้ 460 เป็นตัวหาร เพราะ 40 row ที่ว่างถูกนับไปแล้วที่นี่
- **ควรทำ:** ใช้ตัวหารต่างกันได้ ขอแค่บอกให้ชัด มันกันไม่ให้ช่องว่างช่องเดียวตกสอง rule พร้อมกัน (ดูตารางสรุปใน[บทหลัก](/data-quality/dimensions/#สรุปทั้ง-14-rule))

</Step>

<Step>

## เข้าใจผิดข้อ 5: ค่อยดู Completeness ทีหลังก็ได้

- **ที่มักเข้าใจ:** field ที่ทีม "รู้" ว่าสำคัญ คงถูกกรอกเกือบครบอยู่แล้ว
- **ที่จริง:** ผู้เขียน Ten Steps เล่าถึงโปรเจกต์ deduplication ที่ปรับแล้วปรับอีกหลายรอบก็ไม่ได้ผลดี เพราะ field ที่ทีมรู้ว่าสำคัญต่อการ match มี fill rate แค่ 20% (หนังสือ: Ten Steps บทที่ 3 หน้า 42 ถึง 46)
- **ควรทำ:** เช็ก completeness ของ field ก่อน แล้วค่อยสร้าง logic ที่พึ่ง field นั้น

</Step>

## ที่มักสับสนด้วย

| ดูคล้ายกับ | แยกอย่างไร | ใน data ของเรา |
|---|---|---|
| Validity | Completeness ถามว่ามีค่าไหม Validity ถามว่าค่านั้นอนุญาตไหม | email NULL (40 row) กับ `user23example.com` (15 row) |
| Integrity | key ที่เป็น NULL คือไม่มี key key ที่เป็น orphan คือมี key แต่ชี้ไปที่ไม่มีอะไร | `orders.customer_id`: NULL 15, orphan 30 รวม 45 order ที่ผูกกับ customer ไม่ได้ |
| Accuracy | ค่าที่ถูกกรอกอาจผิดก็ได้ | `birth_date` ถูกกรอกครบทั้ง 500 customer และมี 6 วันที่ที่เป็นไปไม่ได้ |

Ten Steps ไม่แยก completeness กับ validity เป็นคนละ dimension ทั้งสองอยู่ใน "data integrity fundamentals" เพราะ profiling รอบเดียวหาได้ทั้งคู่ (หนังสือ: Ten Steps บทที่ 3 หน้า 42 ถึง 46) หนังสือบอกว่าการ assess กับการ report เป็นคนละเรื่อง คุณจึงยังรายงานแยกกันได้

</Step>

<Step>

## เช็กตัวเอง

- เลือก column หนึ่งใน table ที่คุณดูแล มันเป็น mandatory, conditional หรือ inapplicable และ rule ของมันบอกไว้ไหม
- pipeline ของคุณ load row น้อยกว่าเมื่อวาน 2% และทุก row ที่ load มีข้อมูลครบทุกช่อง completeness ระดับไหนพัง และ check ตัวไหนจะเห็น
- หา column ที่คนพิมพ์ placeholder เพื่อให้ผ่าน field บังคับ คุณจะนับพวกนั้นอย่างไร

</Step>
