## Completeness ถามว่าข้อมูลที่ควรมี มีครบไหม

ลองนึกถึงทีม marketing ที่กำลังจะส่งโปรโมชันทางเมลหาลูกค้าทุกคน พวกเขาเปิดตาราง `customers` ขึ้นมาแล้วเจอแบบนี้

| customer_id | email | country |
|---:|---|---|
| 2 | `user2@example.com` | TH |
| 3 | `user3@example.com` | TH |
| 14 | (ว่าง) | TH |
| 24 | (ว่าง) | TH |
| 30 | (ว่าง) | TH |

customer 14, 24 และ 30 ไม่มี email ให้ส่งเลย ข้อมูลที่ควรมีกลับไม่มี และนี่คือสิ่งที่ completeness วัด DMBOK2 ถามเรื่องนี้ตรงๆ ว่า ข้อมูลที่ต้องมี มีครบไหม ส่วน DAMA UK นิยามให้เป็นสัดส่วน คือข้อมูลที่เก็บไว้จริงเทียบกับที่ควรมีครบ 100% (หนังสือ: DMBOK2 Table 29 หน้า 458 และหัวข้อ 1.3.3 หน้า 457)

ทั้งตารางมี customer 500 คน และ email ว่างอยู่ 40 คน เท่ากับว่ามี email 460 คน หรือ 92% ซึ่งเราวัดได้ด้วย query นี้

```sql
SELECT count(*) FILTER (WHERE email IS NULL), count(*) FROM customers;
-- 40 จาก 500
```

ตัวเลข 92% ข้างบนเป็นการนับที่ระดับ column หนังสือบอกว่า completeness วัดได้สามระดับ ระดับ column ถามว่าช่องหนึ่งถูกกรอกครบไหม ระดับ record ถามว่า row หนึ่งถูกกรอกตามที่สถานะของมันต้องการหรือเปล่า และระดับ data set ถามว่า row ที่ควรมีอยู่ในตารางมาครบทุก row ไหม ทั้งสามระดับมีตัวอย่างในหน้านี้ (หนังสือ: DMBOK2 Table 29 หน้า 458)

</Step>

## ช่องว่างไม่ได้แปลว่าผิดเสมอไป

ก่อนจะเรียกช่องว่างว่า defect เราต้องถามก่อนว่าช่องนั้น "ควรมีค่าเมื่อไร" หนังสือแบ่งคำตอบเป็นสามกลุ่ม (หนังสือ: DMBOK2 Table 29 หน้า 458)

| กลุ่ม | ความหมาย | ถ้าช่องว่าง | ตัวอย่าง |
|---|---|---|---|
| Mandatory | ทุก row ต้องมีค่า | เป็น defect | `order_id` ของ `orders` ถ้าไม่มี เราก็ไม่รู้ว่า row นี้คือ order ไหน |
| Conditional หรือ optional | ต้องมีค่าเฉพาะเมื่อเข้าเงื่อนไข หรือจะมีหรือไม่ก็ได้ | เป็น defect เฉพาะ row ที่เข้าเงื่อนไข ถ้า optional จริงก็ไม่เป็น defect | `shipped_ts` ต้องมีเมื่อ status เป็น SHIPPED ส่วนเบอร์โทรที่ลูกค้าจะกรอกหรือไม่ก็ได้ ก็เป็น optional (dataset ของเราไม่มี column แบบนี้) |
| Inapplicable | ไม่มีความหมายกับ row นี้ จึงต้องว่าง | เป็นเรื่องปกติ ถ้ามีค่าอยู่ต่างหากที่ผิด | `shipped_ts` ของ order ที่ยังเป็น PLACED หรือถูก CANCELLED ไปแล้ว |

ช่องว่างหน้าตาเหมือนกันทุกกลุ่ม แต่ความหมายต่างกัน ช่องว่างใน column ที่ mandatory คือ defect ช่องว่างใน column ที่ inapplicable คือสิ่งที่ถูกต้อง ส่วนกลุ่มกลางเราต้องดูเงื่อนไขก่อนถึงจะตัดสินได้

`orders.shipped_ts` เป็นตัวอย่างที่เห็นชัดที่สุด เพราะมันอยู่ในสองกลุ่มพร้อมกัน ขึ้นกับ status ของ order นั้น

| status | จำนวน row | row ที่มี `shipped_ts` | ที่ควรเป็น |
|---|---:|---:|---|
| PLACED | 756 | 0 | ว่าง เพราะยังไม่ได้ส่ง |
| SHIPPED | 1,794 | 1,769 | มีค่าทุก row |
| CANCELLED | 470 | 0 | ว่าง |

ทั้ง table มี `shipped_ts` ว่างอยู่ 1,251 row ถ้าเรา flag ทุก row ที่ว่างว่าเป็น defect เราจะผิดไป 1,226 row เพราะ row เหล่านั้นคือ order ที่ยังไม่ส่งหรือถูกยกเลิก ซึ่งว่างอยู่แล้วถูกต้อง defect จริงมีแค่ 25 row คือ order ที่ SHIPPED แล้วแต่ไม่มีเวลาส่ง เช่น order 84 ที่มี status เป็น SHIPPED แต่ `shipped_ts` ว่าง (รัน: `13_dimension_pitfalls.py`)

```sql
SELECT count(*) FILTER (WHERE status = 'SHIPPED' AND shipped_ts IS NULL),
       count(*) FILTER (WHERE status = 'SHIPPED')
FROM orders;
-- 25 จาก 1,794
```

สังเกตว่า rule นี้เขียนเงื่อนไข `status = 'SHIPPED'` ไว้ในตัว เพราะคะแนน completeness ที่ไม่บอกว่าวัดกับ row กลุ่มไหน เป็นคะแนนที่ไม่มีใครตีความได้

</Step>

## ช่องที่มีค่า แต่ไม่มีข้อมูลจริง

`IS NULL` จับได้เฉพาะช่องที่ว่างจริงๆ แต่คนที่กรอกข้อมูลมักหาทางผ่านช่องบังคับด้วยการพิมพ์อะไรสักอย่างลงไป ตารางเบอร์โทรด้านล่างเป็นตารางสมมติขนาดเล็ก 8 row ที่เราสร้างขึ้นมาเพื่อแสดงเรื่องนี้

| phone | ช่องนี้มีข้อมูลจริงไหม | `IS NULL` เห็นไหม |
|---|---|---|
| 0812345678 | มี | ไม่เห็น (ถูกต้อง) |
| (string ว่าง) | ไม่มี | ไม่เห็น |
| N/A | ไม่มี | ไม่เห็น |
| 000-000-0000 | ไม่มี | ไม่เห็น |
| (NULL) | ไม่มี | เห็น |
| 0898765432 | มี | ไม่เห็น (ถูกต้อง) |
| (ช่องว่างสองตัว) | ไม่มี | ไม่เห็น |
| - | ไม่มี | ไม่เห็น |

ในตารางนี้มี 6 ช่องที่ไม่มีข้อมูลจริง แต่ `IS NULL` เห็นแค่ช่องเดียว ส่วน check ที่หา string ว่าง ช่องว่างล้วน และ placeholder อย่าง `N/A`, `-` และ `000-000-0000` ด้วย จะเห็นครบทั้ง 6 ช่อง (รัน: `13_dimension_pitfalls.py`)

Ten Steps แนะนำให้มองหา default value และนิสัยที่คนพิมพ์อะไรลงใน field บังคับให้ผ่าน เช่น พิมพ์จุดหนึ่งตัวเพื่อให้บันทึกต่อได้ บางทีมตัดสินว่า field ที่มีแต่ค่า default ให้นับว่ายังไม่ถูกกรอก วิธีหาค่าพวกนี้ที่ง่ายที่สุดคือดู frequency ของค่าที่พบบ่อยใน column ตามที่ [บท 3](/data-quality/profiling/#ดู-frequency-ของค่าใน-column-ที่มีค่าไม่กี่แบบ) สอนไว้ ค่า placeholder จะโผล่ขึ้นมาอยู่บนสุดของรายการเสมอ (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135)

</Step>

## ทุก Row กรอกครบ แต่ตารางยังไม่ครบ

rule ระดับ column เห็นเฉพาะ row ที่มาถึงตารางแล้ว ถ้า row ทั้งวันไม่เคยถูก load เข้ามา row ที่เหลือก็ยังกรอกครบทุกช่องอยู่ และคะแนนก็ยังเป็น 100%

dataset ของเราไม่มีวันที่ row หาย เพื่อให้เห็นภาพ เราจึงทำ copy ของ `orders` แล้วลบ order ไป 4 ใน 5 ของวันที่ 30 สิงหาคม วันนั้นจากเดิมมี 30 order เหลือแค่ 6 order check ระดับ row ที่ดูว่า `status` และ `total_amount` มีค่าไหม ผ่านทั้ง 2,976 จาก 2,976 row เพราะ row ที่เหลือทุกตัวสมบูรณ์ดี

สิ่งที่บอกเราว่ามีปัญหาคือการเทียบกับ "ปกติ" ในวันอื่น table นี้รับ order วันละ 24.8 รายการโดยเฉลี่ย และตัวเลขนี้แกว่งขึ้นลงจากค่าเฉลี่ยประมาณ 4.7 รายการ (standard deviation) เรากำหนดว่าวันที่ต่ำกว่าค่าเฉลี่ยเกินสามเท่าของค่านี้ถือว่าผิดปกติ ซึ่งก็คือวันที่มี order น้อยกว่าประมาณ 10.6 รายการ วันที่เหลือ 6 order อยู่ต่ำกว่านั้นมาก (รัน: `13_dimension_pitfalls.py`)

หนังสือบอกว่าการวัดระดับ data set ทำได้สองทาง ทางแรกคือเทียบกับ source of record เช่น จำนวน row ในระบบต้นทาง ซึ่ง [บท 8](/data-quality/reconciliation/#reconcile-ด้วยจำนวน-row-และผลรวม) สอนไว้ ทางที่สองคือเทียบกับว่าตารางนี้เคยเต็มแค่ไหนในอดีต หนังสือเรียกว่า historical levels of population (หนังสือ: DMBOK2 Table 29 หน้า 458) ทางที่สองไม่ต้องมีต้นทางให้เทียบ แต่มีข้อเสีย คือวันที่เงียบจริงเพราะเหตุผลทางธุรกิจ เช่น วันหยุดยาว ก็จะดูเหมือนวันที่ row หายทุกประการ

</Step>

## ตัวหารเปลี่ยนคะแนน

คะแนน completeness ขึ้นกับว่าเราหารด้วยอะไร `customers.email` complete 92.00% จาก customer 500 คน แต่ rule ที่ตรวจ format ของ email ใช้ 460 เป็นตัวหาร เพราะ email ที่ว่าง 40 คนถูกนับไปแล้วที่ completeness เราไม่อยากให้ช่องว่างช่องเดียวตกสอง rule พร้อมกัน ใช้ตัวหารต่างกันในแต่ละ rule ได้ ขอแค่บอกไว้ให้ชัดว่าแต่ละ rule หารด้วยอะไร (ตารางสรุปในบท [Dimension ของ Data Quality](/data-quality/dimensions/#สรุปทั้ง-14-rule) แสดงตัวหารของทั้ง 14 rule)

</Step>

## ทำไมควรดู Completeness ก่อน

ผู้เขียน Ten Steps เล่าถึงโปรเจกต์ deduplication ที่ตัวเองเคยทำ ทีมเลือก field ที่ "รู้" ว่าสำคัญสำหรับการบอกว่าสอง record เป็นของคนเดียวกัน แล้วปรับ algorithm อยู่หลายรอบแต่ผลก็ไม่ดีสักที จนมาเช็ก fill rate จึงพบว่า field นั้นมีค่าอยู่แค่ 20% ของ record ทั้งหมด algorithm ไม่ได้ผิดเลย ข้อมูลที่มันต้องใช้ไม่เคยอยู่ที่นั่น (หนังสือ: Ten Steps บทที่ 3 หน้า 42 ถึง 46) ดังนั้นถ้าเรากำลังจะสร้าง logic ที่พึ่ง field ไหน ให้เช็ก completeness ของ field นั้นก่อน

</Step>

## ต่างจาก Dimension อื่นอย่างไร

completeness กับ validity แยกกันด้วยคำถามที่ถาม customer 14 ไม่มี email เลย นี่คือ completeness ส่วน customer 23 มี email แต่เป็น `user23example.com` ที่ไม่มี `@` นี่คือ validity ซึ่งอธิบายต่อใน[หน้า Validity](/data-quality/dimensions/validity/) ส่วนใน `orders` ช่อง `customer_id` ที่ว่าง (เช่น order 344) เป็น completeness แต่ `customer_id` ที่มีค่า 9017 ซึ่งไม่มี customer คนนั้นอยู่จริง (เช่น order 65) เป็น integrity ดูต่อในหน้า [Integrity](/data-quality/dimensions/integrity/) และ order ทั้งสองกลุ่มรวมกัน 45 row ผูกกับ customer ไม่ได้เหมือนกัน

ช่องที่กรอกครบแล้วก็ยังผิดได้ `birth_date` ถูกกรอกครบทั้ง 500 customer แต่ customer 28 มีวันเกิดเป็น 2026-12-25 ซึ่งเป็นวันในอนาคต ปัญหานี้ completeness มองไม่เห็นเลย

Ten Steps ไม่แยก completeness ออกจาก validity เป็นคนละ dimension ทั้งสองอยู่ใน data integrity fundamentals เพราะการ profile ครั้งเดียวหาได้ทั้งคู่ แต่หนังสือก็บอกว่าการ assess กับการ report เป็นคนละเรื่อง เราจะรายงานแยกกันก็ได้ (หนังสือ: Ten Steps บทที่ 3 หน้า 42 ถึง 46)

</Step>

## เช็กตัวเอง

- เลือก column หนึ่งใน table ที่คุณดูแล มันเป็น mandatory, conditional หรือ inapplicable และ rule ที่ตรวจมันบอกเงื่อนไขนี้ไว้หรือยัง
- pipeline ของคุณ load row น้อยกว่าเมื่อวาน 2% และทุก row ที่ load มามีข้อมูลครบทุกช่อง completeness ระดับไหนที่พัง และ check ตัวไหนจะเห็น
- หา column ที่คนมักพิมพ์ placeholder เพื่อให้ผ่านช่องบังคับ คุณจะนับ placeholder พวกนั้นอย่างไร

</Step>
