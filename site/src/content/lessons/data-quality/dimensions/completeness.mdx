## Completeness ถามว่าข้อมูลที่ควรมี มีครบไหม

ลองนึกถึงทีม Marketing ที่กำลังจะส่งโปรโมชันทางเมลหาลูกค้าทุกคน พวกเขาเปิดตาราง `customers` ขึ้นมาแล้วเจอแบบนี้

| customer_id | email | country |
|---:|---|---|
| 2 | `user2@example.com` | TH |
| 3 | `user3@example.com` | TH |
| 14 | (ว่าง) | TH |
| 24 | (ว่าง) | TH |
| 30 | (ว่าง) | TH |

Customer 14, 24 และ 30 ไม่มี Email ให้ส่งเลย ข้อมูลที่ควรมีกลับไม่มี และนี่แหละคือสิ่งที่ Completeness วัด

DMBOK2 ถามเรื่องนี้ตรง ๆ ว่าข้อมูลที่ต้องมี มีครบไหม ส่วน DAMA UK นิยามให้เป็นสัดส่วน คือข้อมูลที่เก็บไว้จริงเทียบกับที่ควรมีครบ 100% (หนังสือ: DMBOK2 Table 29 หน้า 458 และหัวข้อ 1.3.3 หน้า 457) ทั้ง Table มี Customer 500 คน และ Email ว่างอยู่ 40 คน เท่ากับว่ามี Email 460 คน หรือ 92% ซึ่งเราวัดได้ด้วย Query นี้

```sql
SELECT count(*) FILTER (WHERE email IS NULL), count(*) FROM customers;
-- 40 จาก 500
```

Query นี้มีสองตัวเลข `count(*) FILTER (WHERE email IS NULL)` นับเฉพาะ Row ที่ `email` ว่าง ส่วน `count(*)` ตัวหลังนับทุก Row เพื่อใช้เป็นตัวหาร

ตัวเลข 92% ข้างบนเป็นการนับที่ระดับ Column ซึ่งเป็นแค่หนึ่งในสามระดับที่หนังสือบอกไว้ และเราจะได้เห็นครบทั้งสามระดับในหน้านี้ (หนังสือ: DMBOK2 Table 29 หน้า 458)

| ระดับ | ถามว่า | ตัวอย่างในหน้านี้ |
|---|---|---|
| Column | ช่องหนึ่งถูกกรอกครบไหม | `customers.email` ว่าง 40 จาก 500 Row |
| Row | Row หนึ่งถูกกรอกตามที่สถานะของมันต้องการหรือเปล่า | Order ที่ SHIPPED แล้วต้องมี `shipped_ts` |
| Table | Row ที่ควรอยู่ใน Table นี้มาครบทุก Row ไหม | วันที่ Order หายไป 24 จาก 30 Row |

หนังสือเรียกสองระดับหลังว่า Row และ Data Set ในหน้านี้เราเรียกว่า Row กับ Table เพราะตรงกับสิ่งที่เราเห็นในตาราง

## ก่อนเรียกช่องว่างว่า Defect ต้องรู้ก่อนว่าช่องนั้นควรมีค่าเมื่อไร

ช่องว่างไม่ได้แปลว่าผิดเสมอไป เราจึงต้องถามก่อนว่าช่องนั้น "ควรมีค่าเมื่อไร" หนังสือแบ่งคำตอบเป็นสามกลุ่ม (หนังสือ: DMBOK2 Table 29 หน้า 458)

| กลุ่ม | ความหมาย | ถ้าช่องว่าง | ตัวอย่าง |
|---|---|---|---|
| Mandatory | ทุก Row ต้องมีค่า | เป็น Defect | `order_id` ของ `orders` ถ้าไม่มี เราก็ไม่รู้ว่า Row นี้คือ Order ไหน |
| Conditional หรือ Optional | ต้องมีค่าเฉพาะเมื่อเข้าเงื่อนไข หรือจะมีหรือไม่ก็ได้ | เป็น Defect เฉพาะ Row ที่เข้าเงื่อนไข ถ้า Optional จริงก็ไม่เป็น Defect | `shipped_ts` ต้องมีเมื่อ Status เป็น SHIPPED ส่วนเบอร์โทรที่ลูกค้าจะกรอกหรือไม่ก็ได้ ก็เป็น Optional (ตารางของเราไม่มี Column แบบนี้) |
| Inapplicable | ไม่มีความหมายกับ Row นี้ จึงต้องว่าง | เป็นเรื่องปกติ ถ้ามีค่าอยู่สิถึงจะผิด | `shipped_ts` ของ Order ที่ยังเป็น PLACED หรือถูก CANCELLED ไปแล้ว |

ช่องว่างหน้าตาเหมือนกันทุกกลุ่ม แต่ความหมายต่างกัน ช่องว่างใน Column ที่ Mandatory คือ Defect ส่วนช่องว่างใน Column ที่ Inapplicable คือสิ่งที่ถูกต้อง และกลุ่มตรงกลางเราต้องดูเงื่อนไขก่อนถึงจะตัดสินได้

วิธีคิดที่ใช้ได้กับทุก Table คือถามตัวเองสามข้อตามลำดับ

1. Row นี้อยู่ในสถานการณ์ไหน เช่น Order นี้ยังรอส่ง หรือส่งไปแล้ว
2. ในสถานการณ์นั้น ช่องนี้ควรมีค่าไหม
3. ถ้าควรมีแต่ช่องว่าง นั่นคือ Defect แต่ถ้าไม่ควรมี ช่องว่างก็คือคำตอบที่ถูกอยู่แล้ว

ลองใช้สามข้อนี้กับ Table ของธุรกิจอื่น ๆ ดู

| ธุรกิจ | Column | Row ที่ช่องนี้ต้องมีค่า | Row ที่ช่องนี้ควรว่าง |
|---|---|---|---|
| โรงพยาบาล | `discharge_date` | ผู้ป่วยที่สถานะเป็น DISCHARGED | ผู้ป่วยที่ยังนอนอยู่ (ADMITTED) |
| ร้านค้าออนไลน์ | `shipping_address` | Order ที่เป็นสินค้าจริง | Order ที่เป็น E-book |
| ฝ่ายบุคคล | `resignation_date` | พนักงานที่สถานะเป็น RESIGNED | พนักงานที่ยังทำงานอยู่ |
| ระบบสมัครสมาชิก | `company_name` | ลูกค้าประเภท BUSINESS | ลูกค้าประเภทบุคคลธรรมดา |
| Sensor ในโรงงาน | `error_code` | การอ่านค่าที่ล้มเหลว (FAILED) | การอ่านค่าที่สำเร็จ |

จะเห็นว่าทุกแถวมีเงื่อนไขซ่อนอยู่ในสถานะของ Row เสมอ เพราะฉะนั้น Rule ที่ดีต้องเขียนสถานะนั้นลงไปในตัว Rule ด้วย ไม่อย่างนั้นเราจะนับช่องที่ควรว่างเป็น Defect ไปด้วย

## ตัวอย่างจริง `shipped_ts` ว่าง 1,251 Row แต่ผิดแค่ 25 Row

`orders.shipped_ts` เป็นตัวอย่างที่เห็นชัดที่สุดในตารางของเรา เพราะมันอยู่ในสองกลุ่มพร้อมกัน ขึ้นกับ Status ของ Order นั้น

| Status | จำนวน Row | Row ที่มี `shipped_ts` | ที่ควรเป็น |
|---|---:|---:|---|
| PLACED | 756 | 0 | ว่าง เพราะยังไม่ได้ส่ง |
| SHIPPED | 1,794 | 1,769 | มีค่าทุก Row |
| CANCELLED | 470 | 0 | ว่าง |

ทั้ง Table มี `shipped_ts` ว่างอยู่ 1,251 Row ถ้าเรา Flag ทุก Row ที่ว่างว่าเป็น Defect เราจะผิดไป 1,226 Row เพราะ Row เหล่านั้นคือ Order ที่ยังไม่ส่งหรือถูกยกเลิก ซึ่งว่างอยู่แล้วถูกต้อง Defect จริงมีแค่ 25 Row คือ Order ที่ SHIPPED แล้วแต่ไม่มีเวลาส่ง เช่น Order 84 ที่มี Status เป็น SHIPPED แต่ `shipped_ts` ว่าง (รัน: `13_dimension_pitfalls.py`)

```sql
SELECT count(*) FILTER (WHERE status = 'SHIPPED' AND shipped_ts IS NULL),
       count(*) FILTER (WHERE status = 'SHIPPED')
FROM orders;
-- 25 จาก 1,794
```

Query นี้เหมือน Query ก่อนหน้า ต่างกันที่มีเงื่อนไข `status = 'SHIPPED'` ติดอยู่ทั้งสองตัวเลข ตัวเลขแรกนับ Order ที่ SHIPPED แต่ `shipped_ts` ว่าง ส่วนตัวเลขที่สองนับ Order ที่ SHIPPED ทั้งหมดเพื่อใช้เป็นตัวหาร

สังเกตว่า Rule นี้เขียนเงื่อนไข `status = 'SHIPPED'` ไว้ในตัว เพราะคะแนน Completeness ที่ไม่บอกว่าวัดกับ Row กลุ่มไหน เป็นคะแนนที่ไม่มีใครตีความได้

</Step>

## ช่องว่างช่องเดียว อาจแปลว่า "ไม่มี" หรือ "ไม่รู้"

บางครั้งเรารู้แล้วว่าช่องนี้เป็น Conditional แต่ช่องว่างช่องหนึ่งก็ยังแปลได้หลายอย่าง ลองดูตารางผู้ป่วยสมมติ 6 Row ที่เราสร้างขึ้นมาเพื่อแสดงเรื่องนี้

| patient_id | allergy_status | allergies |
|---:|---|---|
| 1 | HAS | Penicillin |
| 2 | NONE | (ว่าง) |
| 3 | HAS | (ว่าง) |
| 4 | NOT_ASKED | (ว่าง) |
| 5 | NONE | (ว่าง) |
| 6 | HAS | Latex |

ช่อง `allergies` ว่างอยู่ 4 Row แต่ความหมายไม่เหมือนกันเลย

- Patient 2 และ 5 มี Status เป็น NONE หมายความว่าถามแล้ว และผู้ป่วยบอกว่าไม่แพ้อะไร ช่องว่างนี้ถูกต้องแล้ว
- Patient 3 มี Status เป็น HAS หมายความว่าผู้ป่วยบอกว่าแพ้ แต่ไม่มีใครบันทึกว่าแพ้อะไร นี่คือ Defect และเป็นเรื่องอันตรายจริง
- Patient 4 มี Status เป็น NOT_ASKED หมายความว่ายังไม่มีใครถาม ช่องว่างนี้บอกเราว่า "ยังไม่รู้" ซึ่งเป็นข้อมูลที่ต้องตามต่อ แต่ไม่ได้เกิดจากการบันทึกผิด

ถ้า Table มีแค่ Column `allergies` เพียงอย่างเดียว เราจะแยกสามกรณีนี้ไม่ได้เลย Check ที่นับ `IS NULL` จะรายงานว่ามี 4 Row ที่ว่าง โดยไม่รู้ว่าแย่จริงกี่ Row พอมี `allergy_status` อยู่ข้าง ๆ เรานับ Defect ได้เหลือ 1 Row (รัน: `13_dimension_pitfalls.py`)

```sql
SELECT count(*) FILTER (WHERE allergies IS NULL AND allergy_status = 'HAS'),
       count(*) FILTER (WHERE allergy_status = 'HAS')
FROM patients;
-- 1 จาก 3
```

ถ้าช่องว่างหนึ่งช่องแปลได้หลายอย่าง วิธีที่ช่วยได้คือเก็บอีก Column หนึ่งไว้บอกว่าช่องว่างนั้นแปลว่าอะไร แล้วให้ Rule อ้างถึง Column นั้นเหมือนที่ Rule ของ `shipped_ts` อ้างถึง Status

</Step>

## ช่องที่มีค่า แต่ไม่มีข้อมูลจริง

`IS NULL` จับได้เฉพาะช่องที่ว่างจริง ๆ แต่คนที่กรอกข้อมูลมักหาทางผ่านช่องบังคับด้วยการพิมพ์อะไรสักอย่างลงไป ตารางเบอร์โทรด้านล่างเป็นตารางสมมติขนาดเล็ก 8 Row ที่เราสร้างขึ้นมาเพื่อแสดงเรื่องนี้

| Phone | ช่องนี้มีข้อมูลจริงไหม | `IS NULL` เห็นไหม |
|---|---|---|
| 0812345678 | มี | ไม่เห็น (ถูกต้อง) |
| (String ว่าง) | ไม่มี | ไม่เห็น |
| N/A | ไม่มี | ไม่เห็น |
| 000-000-0000 | ไม่มี | ไม่เห็น |
| (NULL) | ไม่มี | เห็น |
| 0898765432 | มี | ไม่เห็น (ถูกต้อง) |
| (ช่องว่างสองตัว) | ไม่มี | ไม่เห็น |
| - | ไม่มี | ไม่เห็น |

ในตารางนี้มี 6 ช่องที่ไม่มีข้อมูลจริง แต่ `IS NULL` เห็นแค่ช่องเดียว ส่วน Check ที่หา String ว่าง ช่องว่างล้วน และ Placeholder อย่าง `N/A`, `-` และ `000-000-0000` ด้วย จะเห็นครบทั้ง 6 ช่อง (รัน: `13_dimension_pitfalls.py`)

Placeholder ไม่ได้มีแค่ในช่องข้อความ คนมักเลือกค่าที่ผ่านกฎของช่องนั้นไปได้ ซึ่งหน้าตาจะต่างกันไปตามชนิดของช่อง

- ช่องข้อความ มักเจอ `N/A`, `-`, `ไม่มี` หรือเว้นวรรคสองครั้ง
- ช่องตัวเลข มักเจอ `0`, `-1` หรือ `9999` ซึ่งผ่านเงื่อนไข "ต้องเป็นตัวเลข" ไปได้สบาย ๆ
- ช่องวันที่ มักเจอ `1900-01-01` หรือ `1970-01-01` ซึ่งเป็นวันที่ระบบหยิบมาใช้เมื่อไม่มีอะไรให้ใส่
- ช่อง Email มักเจอ `a@a.com` หรือ `test@test.com` ซึ่งหน้าตาเป็น Email ครบ จึงผ่านแม้แต่ Rule ตรวจรูปแบบ

(ตัวอย่างสี่ข้อนี้เป็นสิ่งที่พบได้ทั่วไป ไม่ได้อยู่ในตารางของเรา)

Ten Steps แนะนำให้มองหา Default Value และนิสัยที่คนพิมพ์อะไรลงใน Field บังคับให้ผ่าน เช่น พิมพ์จุดหนึ่งตัวเพื่อให้บันทึกต่อได้ บางทีมตัดสินว่า Field ที่มีแต่ค่า Default ให้นับว่ายังไม่ถูกกรอก วิธีหาค่าพวกนี้ที่ง่ายที่สุดคือดู Frequency ของค่าที่พบบ่อยใน Column ตามที่ [บท 3](/data-quality/profiling/#ดู-frequency-ของค่าใน-column-ที่มีค่าไม่กี่แบบ) สอนไว้ เพราะค่า Placeholder จะโผล่ขึ้นมาอยู่บนสุดของรายการเสมอ (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135)

</Step>

## ทุก Row กรอกครบ แต่ตารางยังไม่ครบ

ลองนึกถึงปึกใบเสร็จของร้านค้า ที่เลขที่ข้ามจาก 1018 ไปเป็น 1025 ใบเสร็จทุกใบที่เหลืออ่านได้ครบ มีชื่อสินค้า มียอดเงิน มีวันที่ครบทุกช่อง แต่เรารู้ทันทีว่ามีใบเสร็จหายไป 6 ใบ

Rule ระดับ Column กับระดับ Row ก็เหมือนคนที่ตรวจดูแค่ว่าแต่ละใบกรอกครบไหม ซึ่งเห็นได้เฉพาะ Row ที่มาถึงตารางแล้ว ถ้า Row ทั้งวันไม่เคยถูก Load เข้ามา Row ที่เหลือก็ยังกรอกครบทุกช่องอยู่ และคะแนนก็ยังเป็น 100%

**ตัวอย่างแรก Sensor ที่รู้ตารางเวลา** ลองดูตารางสมมติของ Sensor อุณหภูมิตัวหนึ่ง ที่ส่งค่ามาชั่วโมงละหนึ่งครั้ง รวมสามวัน

| วัน | Row ที่ควรมี | Row ที่มาถึงจริง | Row ที่กรอกครบทุกช่อง |
|---:|---:|---:|---:|
| 1 | 24 | 24 | 24 |
| 2 | 24 | 18 | 18 |
| 3 | 24 | 24 | 24 |

Check ระดับ Row ที่ดูว่า `temp_c` มีค่าไหม ผ่านทั้ง 66 จาก 66 Row เพราะ Row ที่มาถึงทุกตัวสมบูรณ์ดี แต่ถ้าเทียบกับตารางเวลา ที่ Sensor ต้องส่งวันละ 24 ครั้งคือ 72 Row ทั้งสามวัน เรามี Row ครบแค่ 66 จาก 72 หรือ 91.7% และวันที่ 2 หายไป 6 ชั่วโมงท้ายวัน (รัน: `13_dimension_pitfalls.py`)

**ตัวอย่างที่สอง Orders ที่ไม่มีตารางเวลา** ตารางของเราไม่มีวันที่ Row หาย เพื่อให้เห็นภาพ เราจึงทำ Copy ของ `orders` แล้วลบ Order ไป 4 ใน 5 ของวันที่ 30 สิงหาคม วันนั้นจากเดิมมี 30 Order เหลือแค่ 6 Order Check ระดับ Row ที่ดูว่า `status` และ `total_amount` มีค่าไหม ผ่านทั้ง 2,976 จาก 2,976 Row เพราะ Row ที่เหลือทุกตัวสมบูรณ์ดี

ร้านค้าไม่ได้มี Order วันละ 24 ใบตายตัวเหมือน Sensor เราจึงไม่มีตารางเวลาให้เทียบ สิ่งที่บอกเราว่ามีปัญหาคือการเทียบกับ "ปกติ" ในวันอื่น Table นี้รับ Order วันละ 24.8 รายการโดยเฉลี่ย และตัวเลขนี้แกว่งขึ้นลงจากค่าเฉลี่ยประมาณ 4.7 รายการ (Standard Deviation) เรากำหนดว่าวันที่ต่ำกว่าค่าเฉลี่ยเกินสามเท่าของค่านี้ถือว่าผิดปกติ ซึ่งก็คือวันที่มี Order น้อยกว่าประมาณ 10.6 รายการ วันที่เหลือ 6 Order อยู่ต่ำกว่านั้นมาก (รัน: `13_dimension_pitfalls.py`)

## Row น้อยในวันหนึ่ง อาจเป็นข้อมูลหาย หรือเป็นวันที่ไม่มีอะไรเกิดขึ้นจริง

การเทียบกับอดีตบอกเราได้แค่ว่าวันนี้ Row น้อยผิดปกติ แต่ไม่ได้บอกว่าเพราะอะไร เพราะวันที่ไม่มี Order เกิดขึ้นเลยจริง ๆ ก็มีได้ เช่น วันหยุดยาวที่ร้านปิด ซึ่งหน้าตาในตารางจะเหมือนวันที่ Row หายไปทุกประการ ลองดูตารางสามวันสมมติ ที่เทียบจำนวน Row ในตารางกับจำนวน Order ที่ระบบต้นทางบันทึกไว้

| วัน | Row ใน Table | Order ในระบบต้นทาง | ข้อสรุป |
|---|---:|---:|---|
| วันปกติ | 25 | 25 | ครบ |
| วันที่ Row หาย | 6 | 30 | หายไป 24 Row |
| วันหยุดยาว | 0 | 0 | ครบ เพราะวันนั้นไม่มี Order เกิดขึ้นเลย |

ถ้าดูจากอดีตอย่างเดียว วันที่ Row หายกับวันหยุดยาวจะถูก Flag เหมือนกัน แต่พอเทียบกับระบบต้นทางจะเห็นว่าวันที่ Row หายขาดไป 24 Row ส่วนวันหยุดยาวไม่ได้ขาดอะไรเลย (รัน: `13_dimension_pitfalls.py`)

หนังสือบอกว่าการวัดระดับ Table ทำได้สองทาง

- ทางแรกคือเทียบกับ source of record เช่น จำนวน Row ในระบบต้นทาง ซึ่ง [บท 8](/data-quality/reconciliation/#reconcile-ด้วยจำนวน-row-และผลรวม) สอนไว้
- ทางที่สองคือเทียบกับว่าตารางนี้เคยเต็มแค่ไหนในอดีต ซึ่งหนังสือเรียกว่า historical levels of population (หนังสือ: DMBOK2 Table 29 หน้า 458)

ทางที่สองไม่ต้องมีต้นทางให้เทียบ แต่ต้องยอมรับว่ามันแยกวันที่ข้อมูลหายออกจากวันที่เงียบจริงไม่ได้ ถ้าใช้ทางที่สอง เราจึงควรใส่ปฏิทินวันหยุดเข้าไปใน Rule ด้วย ไม่อย่างนั้นทุกวันหยุดยาวจะเป็น Alert หลอก

## ตัวหารเปลี่ยนคะแนน

คะแนน Completeness ขึ้นกับว่าเราหารด้วยอะไร `customers.email` Complete 92.00% จาก Customer 500 คน เพราะ Email ว่างอยู่ 40 คน

ทีนี้ลองดู Rule อีกตัวที่ตรวจรูปแบบของ Email ว่าต้องมี `@` และมีจุดหลังชื่อโดเมน Customer ที่ Email ว่างจะอยู่ใน Rule นี้อย่างไร ถ้าเราหารด้วย 500 Email ที่ว่าง 40 คนจะถูกนับว่า "รูปแบบไม่ผ่าน" ไปด้วย เพราะช่องว่างไม่มี `@` แต่ถ้าหารด้วย 460 เราจะนับเฉพาะ Email ที่มีอยู่จริง ซึ่งเป็นสิ่งที่ Rule นี้ควรตรวจ (รัน: `13_dimension_pitfalls.py`)

| Rule | ตัวหาร | Row ที่ผ่าน | คะแนน |
|---|---:|---:|---:|
| Completeness ของ `email` | 500 | 460 | 92.00% |
| รูปแบบของ Email หารด้วย Email ที่มีอยู่ | 460 | 445 | 96.74% |
| รูปแบบของ Email หารด้วย Row ทั้งหมด | 500 | 445 | 89.00% |

ในตารางนี้ รูปแบบผิดจริงแค่ 15 Email แต่ถ้าหารด้วย 500 คะแนนจะตกเป็น 89.00% เพราะช่องว่าง 40 ช่องถูกนับเป็นข้อผิดอีกรอบ ทั้งที่มันถูกจับไปแล้วที่ Completeness ทีมก็จะเห็นว่ารูปแบบของ Email แย่มาก แล้วไปไล่แก้รูปแบบ ทั้งที่ปัญหาใหญ่จริง ๆ คือ Email หายไป 40 คน

เราจึงให้ช่องว่างช่องหนึ่งตกที่ Rule เดียว ไม่ให้ตกสอง Rule พร้อมกัน ใช้ตัวหารต่างกันในแต่ละ Rule ได้ ขอแค่บอกไว้ให้ชัดว่าแต่ละ Rule หารด้วยอะไร (ตารางสรุปในบท [Data Quality Dimensions](/data-quality/dimensions/#สรุปทั้ง-14-rule) แสดงตัวหารของทั้ง 14 Rule)

</Step>

## ทำไมควรดู Completeness ก่อน

ผู้เขียน Ten Steps เล่าถึงโปรเจกต์ Deduplication ที่ตัวเองเคยทำ ทีมเลือก Field ที่ "รู้" ว่าสำคัญสำหรับการบอกว่าสอง Row เป็นของคนเดียวกัน แล้วปรับ Algorithm อยู่หลายรอบแต่ผลก็ไม่ดีสักที จนมาเช็ก Fill Rate จึงพบว่า Field นั้นมีค่าอยู่แค่ 20% ของ Row ทั้งหมด

ทีมจึงรู้ว่า Algorithm ไม่ได้มีอะไรผิด ปัญหาคือ Field ที่มันต้องใช้เทียบ ว่างอยู่ใน Row ส่วนใหญ่ มันจึงไม่มีข้อมูลให้เทียบตั้งแต่แรก (หนังสือ: Ten Steps บทที่ 3 หน้า 42 ถึง 46)

เพื่อให้เห็นภาพ ลองดูตัวอย่างสมมติที่มีแค่ 5 Row และ Algorithm ที่ตัดสินว่าสอง Row เป็นคนเดียวกันก็ต่อเมื่อเบอร์โทรตรงกัน

| id | name | phone |
|---:|---|---|
| 1 | Somchai | 0812345678 |
| 2 | Somchay | (ว่าง) |
| 3 | Malee | (ว่าง) |
| 4 | Malee | (ว่าง) |
| 5 | Nida | (ว่าง) |

เบอร์โทรถูกกรอกแค่ 1 จาก 5 Row หรือ 20% 5 Row จับคู่ได้ 10 คู่ แต่ไม่มีคู่ไหนเลยที่ทั้งสองฝั่งมีเบอร์โทรให้เทียบ (รัน: `13_dimension_pitfalls.py`) เราเห็นด้วยตาว่า Somchai กับ Somchay น่าจะเป็นคนเดียวกัน และ Malee สองคนก็น่าจะใช่ แต่ Algorithm ที่พึ่งเบอร์โทรจะไม่มีวันจับคู่เหล่านี้ได้ ต่อให้เราปรับให้ฉลาดแค่ไหนก็ตาม

ขั้นตอนที่ควรทำก่อนปรับ Algorithm คือเช็กว่า Field ที่มันพึ่งถูกกรอกกี่เปอร์เซ็นต์

```sql
SELECT count(phone) * 1.0 / count(*) FROM people;
-- 0.2
```

`count(phone)` นับเฉพาะ Row ที่ `phone` ไม่ว่าง ส่วน `count(*)` นับทุก Row เมื่อหารกันก็ได้สัดส่วนที่กรอกจริง ดังนั้นถ้าเรากำลังจะสร้าง Logic ที่พึ่ง Field ไหน ให้เช็ก Completeness ของ Field นั้นก่อน

</Step>

## ต่างจาก Dimension อื่นอย่างไร

Completeness มักถูกสับสนกับ Dimension อื่น เพราะปัญหาหลายแบบดูเหมือน "ข้อมูลไม่ดี" เหมือนกันหมด ตารางข้างล่างเอาปัญหาที่เราเจอมาในหน้านี้ มาแยกว่าแต่ละอันเป็นของ Dimension ไหน

| สิ่งที่เราเห็น | Dimension | เพราะอะไร |
|---|---|---|
| Customer 14 ไม่มี Email | Completeness | ช่องที่ควรมีค่าว่างอยู่ |
| Order 344 ช่อง `customer_id` ว่าง | Completeness | ช่องที่ควรมีค่าว่างอยู่ |
| Order 84 เป็น SHIPPED แต่ `shipped_ts` ว่าง | Completeness | ช่อง Conditional ที่เข้าเงื่อนไขแล้วแต่ว่าง |
| Patient 3 มี Status เป็น HAS แต่ `allergies` ว่าง | Completeness | ช่อง Conditional ที่เข้าเงื่อนไขแล้วแต่ว่าง |
| Sensor วันที่ 2 หายไป 6 ชั่วโมง | Completeness ระดับ Table | Row ที่ควรมี ไม่ได้มาถึง |
| Customer 23 มี Email เป็น `user23example.com` ไม่มี `@` | [Validity](/data-quality/dimensions/validity/) | มีค่าอยู่ แต่รูปแบบไม่ถูก |
| Customer 28 เกิดวันที่ 2026-12-25 ซึ่งเป็นวันในอนาคต | [Validity](/data-quality/dimensions/validity/) | มีค่าอยู่ แต่อยู่นอกช่วงที่กำหนด |
| Order 65 ช่อง `customer_id` เป็น 9017 ซึ่งไม่มี Customer คนนั้นอยู่จริง | [Integrity](/data-quality/dimensions/integrity/) | มีค่า รูปแบบถูก แต่ชี้ไปหาสิ่งที่ไม่มีอยู่ |
| Order 267 อยู่สองแถวที่เหมือนกันทุกช่อง | [Uniqueness](/data-quality/dimensions/uniqueness/) | มี Row เกินมาจากที่ควรมี |
| Order 135 มาถึง Warehouse ช้าไปสี่วัน | [Timeliness](/data-quality/dimensions/timeliness/) | ข้อมูลครบทุกช่อง แต่มาช้า |

สังเกตแถวของ Customer 23, Customer 28 และ Order 65 ทั้งสามแถวมีค่าอยู่ครบทุกช่อง ถ้าเราวัดแค่ Completeness จะได้ 100% ทั้งที่ข้อมูลผิดจริง ถ้าเจอปัญหาใหม่แล้วไม่แน่ใจว่าเป็น Dimension ไหน ให้ถามตามลำดับนี้

1. ช่องที่ควรมีค่าว่างอยู่หรือเปล่า ถ้าใช่ นั่นคือ Completeness
2. ช่องมีค่า แต่รูปแบบหรือช่วงของค่าไม่ถูกไหม ถ้าใช่ นั่นคือ Validity
3. ช่องมีค่าและรูปแบบถูก แต่ค่านั้นชี้ไปหาสิ่งที่ไม่มีอยู่ไหม ถ้าใช่ นั่นคือ Integrity
4. มี Row เกินมาไหม ถ้าใช่ นั่นคือ Uniqueness
5. ข้อมูลครบและถูกต้อง แต่มาถึงช้าไปไหม ถ้าใช่ นั่นคือ Timeliness

ปัญหาเดียวอาจเข้าได้มากกว่าหนึ่งข้อ เช่น Order ที่ `customer_id` ว่างอยู่ ก็ผูกกับ Customer ไม่ได้เหมือน Order ที่ชี้ไปหา Customer 9017 สองกลุ่มนี้รวมกัน 45 Row ที่ผูกกับ Customer ไม่ได้ แต่เราควรรายงานแยกกัน เพราะวิธีแก้ต่างกัน

Ten Steps ไม่แยก Completeness ออกจาก Validity เป็นคนละ Dimension โดยรวมทั้งสองไว้ใน data integrity fundamentals เพราะการ Profile ครั้งเดียวหาได้ทั้งคู่ แต่หนังสือก็บอกว่าการ Assess กับการ Report เป็นคนละเรื่อง เราจะรายงานแยกกันก็ได้ (หนังสือ: Ten Steps บทที่ 3 หน้า 42 ถึง 46)

</Step>

## เช็กตัวเอง

- เลือก Column หนึ่งใน Table ที่คุณดูแล มันเป็น Mandatory, Conditional หรือ Inapplicable และ Rule ที่ตรวจมันบอกเงื่อนไขนี้ไว้หรือยัง
- มี Column ไหนที่ช่องว่างแปลได้มากกว่าหนึ่งอย่างไหม เช่น "ไม่มี" กับ "ไม่รู้" ถ้ามี คุณจะเพิ่ม Column อะไรเพื่อแยกสองกรณีนี้
- Pipeline ของคุณ Load Row น้อยกว่าเมื่อวาน 2% และทุก Row ที่ Load มามีข้อมูลครบทุกช่อง Completeness ระดับไหนที่พัง และ Check ตัวไหนจะเห็น
- หา Column ที่คนมักพิมพ์ Placeholder เพื่อให้ผ่านช่องบังคับ คุณจะนับ Placeholder พวกนั้นอย่างไร

</Step>
