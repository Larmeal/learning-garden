## dimension คือคำศัพท์สำหรับพูดถึง rule

DMBOK2 นิยามว่า **dimension ของ data quality** คือคุณลักษณะของข้อมูลที่วัดได้ ชื่อ "dimension" ยืมมาจากการวัดวัตถุ (ยาว กว้าง สูง) dimension ให้คำศัพท์สำหรับเขียน requirement ด้านคุณภาพ ใช้ตั้ง rule ที่วัดได้ และใช้รายงานผลทั้งตอนประเมินครั้งแรกและตอนวัดต่อเนื่อง (หนังสือ: DMBOK2 §1.3.3)

ตัวอย่างในหนังสือ: ถ้าช่อง email ของ customer ไม่ครบ เราส่งข้อมูลสินค้าทาง email ไม่ได้และเสียยอดขาย เราจึงวัด "เปอร์เซ็นต์ customer ที่มี email ใช้ได้" และปรับกระบวนการจนถึงอย่างน้อย 98% dimension (completeness) บอกว่าจะวัดอะไร ผลกระทบทางธุรกิจบอกว่าทำไมต้องวัด

</Step>

## ไม่มีชุด dimension ที่ตกลงกันได้ชุดเดียว

หนังสือเล่าถึงชุด dimension ที่มีอิทธิพลสามชุด แล้วสรุปว่า "ไม่มีชุด dimension ที่ตกลงกันได้ชุดเดียว แต่ทุกชุดมีแนวคิดร่วมกัน" (หนังสือ: DMBOK2 §1.3.3)

| ชุด | ลักษณะ |
|---|---|
| Strong-Wang (1996) | มองจากการรับรู้ของ user 15 dimension ใน 4 กลุ่ม: intrinsic, contextual, representational, accessibility |
| Redman (1996) | มองจากโครงสร้างข้อมูล แบ่งเป็น model, value และ representation รวมมากกว่าสองโหล |
| English (1999) | แบ่งเป็นคุณลักษณะ inherent (ไม่ขึ้นกับการใช้) กับ pragmatic (ขึ้นกับการนำเสนอและการใช้) |
| DAMA UK (2013) | หก dimension หลัก: completeness, uniqueness, timeliness, validity, accuracy, consistency |

เส้นทางนี้ใช้หก dimension ของ DAMA UK บวก **integrity** และ **reasonability** ที่ DMBOK2 Table 29 เพิ่มไว้ เพราะวัดด้วย SQL ได้ตรงที่สุด ข้อควรจำคือชื่อ dimension เป็นภาษากลางในทีม ถ้าทีมของคุณใช้ชุดอื่นก็ใช้ได้ ขอแค่ทุกคนใช้ตรงกัน

</Step>

## dataset ที่ใช้ตลอดเส้นทาง

customer 500 คน (`customers`) order 3,020 row (`orders`) และ payment 2,553 รายการ (`payments`) สร้างโดย `dqlab.py` ด้วย seed คงที่ **defect ทุกชนิดถูกฝังไว้ในจำนวนที่กำหนดเอง** เช่น email ว่าง 40 ราย order ที่ customer ไม่มีอยู่จริง 30 row ดังนั้นเมื่อ SQL ของเราเจอจำนวนตรงกับที่ฝัง ก็รู้ว่า rule ทำงานถูก แบบฝึกทุกข้อจบด้วยการตรวจแบบนี้

ผลของการวัดแต่ละ rule จะรายงานแบบ DMBOK2 Table 30 คือบอก **ทั้งส่วนที่ผ่านและไม่ผ่านเป็นเปอร์เซ็นต์** ตัวอย่าง: ตรวจ 1,000,000 row พบ 2,000 row มาไม่ทันเวลา ได้ 99.8% ผ่านและ 0.20% ไม่ผ่าน

## Completeness, Validity, Uniqueness

**Completeness**: มีข้อมูลที่ต้องมีครบหรือไม่ วัดได้ที่ระดับ dataset, row หรือ column ต้องแยก field ที่บังคับ field ที่มีเงื่อนไข และ field ที่ไม่เกี่ยวข้องออกจากกัน (หนังสือ: DMBOK2 Table 29)

```sql
SELECT count(*) FILTER (WHERE email IS NULL), count(*) FROM customers;
-- 40 จาก 500
```

**Validity**: ค่าอยู่ใน domain ที่นิยามไว้หรือไม่ domain อาจเป็นรายการค่า ช่วง หรือ rule รวมถึง data type และ format (หนังสือ: DMBOK2 Table 29)

```sql
-- format ของ email (เฉพาะ row ที่ไม่ null)
SELECT count(*) FILTER (WHERE NOT regexp_matches(email, '^[^@\s]+@[^@\s]+\.[^@\s]+$')), count(email) FROM customers;
-- 15 จาก 460

-- ค่านอกรายการ
SELECT count(*) FILTER (WHERE country NOT IN ('TH','SG','JP','US')), count(*) FROM customers;
-- 25 จาก 500
```

**Uniqueness**: ไม่มี entity ใดถูกบันทึกซ้ำ วัดโดยทดสอบกับ key (หนังสือ: DMBOK2 Table 29)

```sql
SELECT count(*) - count(DISTINCT order_id), count(*) FROM orders;
-- row ส่วนเกิน 20 จาก 3,020
```

(รัน: `02_dimensions.py` ทุกตัวเลขตรงกับจำนวนที่ฝัง)

<Callout type="warn" title="NULL กับ NOT IN">
column `orders.customer_id` มี NULL 15 row ซึ่งเป็นปัญหา completeness ถ้าตรวจ integrity ด้วย `NOT IN (SELECT customer_id FROM customers)` row ที่ `customer_id` เป็น NULL จะให้ผลเป็น "ไม่รู้" จึงไม่ถูกนับเป็น orphan และถ้ารายการใน subquery มี NULL สักตัว ผลทั้งหมดจะว่าง ใช้ `NOT EXISTS` และแยก row NULL ไปนับใน rule ของ completeness
</Callout>

</Step>

## Consistency, Integrity

**Consistency**: ค่าถูกแสดงสอดคล้องกันภายในและข้าม dataset หรือไม่ หนังสือแยกเป็นสามระดับ: ใน row เดียวกัน (record-level) ข้าม row (cross-record) และข้ามเวลา (temporal) และเตือนว่าอย่าสับสนกับ accuracy (หนังสือ: DMBOK2 Table 29)

```sql
-- status SHIPPED ต้องมีเวลาส่ง
SELECT count(*) FILTER (WHERE status = 'SHIPPED' AND shipped_ts IS NULL),
       count(*) FILTER (WHERE status = 'SHIPPED') FROM orders;
-- 25 จาก 1,794

-- เวลาส่งต้องไม่มาก่อนเวลาสั่ง
SELECT count(*) FILTER (WHERE shipped_ts < order_ts), count(shipped_ts) FROM orders;
-- 10 จาก 1,769
```

ทั้งสองข้อ ค่าแต่ละช่องดูถูกเมื่อดูเดี่ยวๆ แต่ขัดกันเมื่อดูรวม rule แบบนี้ไม่มีทางเห็นจากการตรวจทีละ column

**Integrity**: หนังสือหมายถึงโดยหลัก referential integrity คือความสอดคล้องระหว่าง object ผ่าน reference key ถ้าขาดจะเกิด orphan (reference key ที่ไม่มีตัวจริง) หรือ duplicate (หนังสือ: DMBOK2 Table 29)

```sql
SELECT count(*) FILTER (WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id)),
       count(customer_id)
FROM orders o WHERE customer_id IS NOT NULL;
-- orphan 30 จาก 3,005
```

</Step>

## Timeliness, Accuracy

**Timeliness**: ข้อมูลสะท้อนความจริง ณ เวลาที่ต้องการหรือไม่ ต้องอ่านคู่กับความถี่ที่ข้อมูลเปลี่ยน (volatility) หนังสือแยก *currency* (ค่าเป็นเวอร์ชันล่าสุดไหม) กับ *latency* (เวลาตั้งแต่ข้อมูลเกิดจนพร้อมใช้) (หนังสือ: DMBOK2 Table 29)

```sql
-- ระดับ row: มาถึง warehouse ภายใน 24 ชั่วโมงหรือไม่
SELECT count(*) FILTER (WHERE ingested_at - order_ts > INTERVAL 24 HOUR), count(*) FROM orders;
-- 40 จาก 3,020
```

ระดับ table: order ล่าสุดคือ 29 ต.ค. ตอนที่ถามคือ 1 พ.ย. 08:00 ช้ากว่า 2 วัน 8 ชั่วโมงเศษ ถ้าสัญญาไว้ว่าอัปเดตภายใน 24 ชั่วโมง คือผิดสัญญา (รัน: `02_dimensions.py`)

**Accuracy**: ข้อมูลตรงกับวัตถุหรือเหตุการณ์จริงแค่ไหน หนังสือบอกตรงๆ ว่า **วัดยาก** นอกจากจะทำซ้ำการเก็บข้อมูลหรือยืนยันด้วยมือได้ การวัดส่วนใหญ่อาศัยการเทียบกับแหล่งที่ยืนยันแล้วว่าถูก เช่น system of record (หนังสือ: DMBOK2 Table 29)

เราใช้ payment system เป็นแหล่งอ้างอิง เทียบยอดของ order กับผลรวมของ payment

```sql
WITH o AS (SELECT DISTINCT order_id, total_amount FROM orders WHERE status <> 'CANCELLED'),
     p AS (SELECT order_id, sum(amount) AS paid FROM payments GROUP BY order_id)
SELECT count(*) FILTER (WHERE abs(o.total_amount - p.paid) > 0.005), count(*)
FROM o JOIN p USING (order_id);
-- ไม่ตรง 35 จาก 2,533
```

ข้อควรระวังจากหนังสือ: ข้อมูลอาจ **valid แต่ไม่ accurate** ได้ วันเกิด 1990-01-01 ผ่าน rule ช่วงปี แต่ถ้า customer เกิดปี 1985 ก็ผิด

</Step>

## สรุปทั้ง 14 rule

| dimension | rule | ไม่ผ่าน | ทั้งหมด | ผ่าน% | ไม่ผ่าน% |
|---|---|---:|---:|---:|---:|
| completeness | customers.email ถูกกรอก | 40 | 500 | 92.00 | 8.00 |
| completeness | orders.customer_id ถูกกรอก | 15 | 3,020 | 99.50 | 0.50 |
| validity | email มี format a@b.c | 15 | 460 | 96.74 | 3.26 |
| validity | country อยู่ในรายการ | 25 | 500 | 95.00 | 5.00 |
| validity | birth_date อยู่ระหว่างปี 1900 ถึงวันนี้ | 6 | 500 | 98.80 | 1.20 |
| validity | orders.total_amount ไม่ติดลบ | 12 | 3,020 | 99.60 | 0.40 |
| uniqueness | หนึ่ง email ต่อหนึ่ง customer | 10 | 460 | 97.83 | 2.17 |
| uniqueness | หนึ่ง row ต่อ order_id | 20 | 3,020 | 99.34 | 0.66 |
| consistency | SHIPPED ต้องมี shipped_ts | 25 | 1,794 | 98.61 | 1.39 |
| consistency | shipped_ts ไม่ก่อน order_ts | 10 | 1,769 | 99.43 | 0.57 |
| integrity | orders.customer_id มีใน customers | 30 | 3,005 | 99.00 | 1.00 |
| integrity | payments.order_id มีใน orders | 20 | 2,553 | 99.22 | 0.78 |
| timeliness | order มาถึงภายใน 24 ชม. | 40 | 3,020 | 98.68 | 1.32 |
| accuracy | ยอดตรงกับ payment system | 35 | 2,533 | 98.62 | 1.38 |

สังเกตว่า "ทั้งหมด" ไม่เท่ากันทุก rule: email ที่ format ผิดนับจาก 460 (ไม่นับ row ที่ว่าง) เพราะ row ว่างถูกจับไปแล้วโดย rule ของ completeness การเลือกตัวหารแบบนี้กันไม่ให้ข้อผิดพลาดเดียวถูกนับซ้ำในสอง rule

</Step>

## เช็กตัวเอง

- ถ้าทีมหนึ่งใช้ 6 dimension อีกทีมใช้ 15 dimension รายงานจะเปรียบเทียบกันได้ไหม ต้องตกลงอะไร
- rule "SHIPPED ต้องมี shipped_ts" นับเป็น consistency หรือ completeness (แบบมีเงื่อนไข) ได้ทั้งคู่ ถ้าต้องเลือกหนึ่ง คุณจะใช้เกณฑ์อะไร
- dimension ไหนในตารางด้านบนที่ SQL เพียงอย่างเดียวพิสูจน์ไม่ได้ว่าถูก ต้องมีอะไรเพิ่ม

</Step>
