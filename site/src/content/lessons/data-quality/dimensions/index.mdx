## Dimension คือคำศัพท์สำหรับพูดถึง Rule

สมมติว่าคุณเพิ่งเข้าไปทำงานกับร้านขายของออนไลน์ วันแรกทีม marketing มาบอกว่า "ข้อมูล customer แย่มาก ส่งเมลหาลูกค้าไม่ถึง" วันเดียวกันนั้นทีม finance ก็มาบอกว่า "ข้อมูล order ไม่ถูกต้อง ยอดไม่ตรงกับเงินที่รับจริง" ทั้งสองทีมใช้คำว่า "ข้อมูลแย่" เหมือนกัน แต่เรื่องที่พูดถึงเป็นคนละเรื่อง และเราจะแก้ไม่ได้ ถ้ายังไม่รู้ว่าต้องวัดอะไร

**dimension ของ data quality** คือชื่อที่เราตั้งให้ปัญหาแต่ละแบบ เพื่อให้ทุกคนพูดถึงเรื่องเดียวกัน และวัดออกมาเป็นตัวเลขได้ DMBOK2 นิยามว่าเป็นคุณลักษณะของข้อมูลที่วัดได้ ชื่อ "dimension" ยืมมาจากการวัดวัตถุ เช่น ความยาว ความกว้าง และความสูง ซึ่งเป็นสามมุมที่ใช้อธิบายกล่องใบเดียวกัน ข้อมูลชุดเดียวกันก็มีหลายมุมให้วัดแบบเดียวกัน (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 454 ถึง 460)

ตัวอย่างในหนังสือตรงกับเรื่องของทีม marketing พอดี ถ้าช่อง email ของ customer ไม่ครบ เราก็ส่งข้อมูลสินค้าทาง email ไม่ได้ และเสียยอดขาย เราเลยวัดว่ามี customer กี่เปอร์เซ็นต์ที่มี email ใช้ได้ แล้วปรับกระบวนการจนถึงอย่างน้อย 98% ในตัวอย่างนี้ completeness บอกว่าเราจะวัดอะไร ส่วนยอดขายที่เสียไปบอกว่าเราวัดไปทำไม (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 454 ถึง 460)

</Step>

## ไม่มีชุด Dimension ที่ตกลงกันได้ชุดเดียว

คนในวงการเสนอรายการ dimension ไว้หลายชุด หนังสือยกสามชุดที่มีอิทธิพลที่สุด ชุดของ Strong และ Wang (ปี 1996) มองจากคนที่ใช้ข้อมูล มี 15 dimension ชุดของ Redman (ปี 1996) มองจากโครงสร้างของข้อมูล มีมากกว่าสองโหล ส่วนชุดของ English (ปี 1999) แบ่งเป็นคุณลักษณะที่ไม่ขึ้นกับการใช้งาน (inherent) กับที่ขึ้นกับการนำเสนอและการใช้ (pragmatic) ต่อมาในปี 2013 DAMA UK เสนอชุดที่สั้นกว่า มีหก dimension หลัก คือ completeness, uniqueness, timeliness, validity, accuracy และ consistency หนังสือสรุปว่าไม่มีชุดไหนที่ทุกคนตกลงใช้ร่วมกัน แต่ทุกชุดมีแนวคิดบางอย่างตรงกัน (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 454 ถึง 460)

หนังสือเล่มอื่นก็เลือกไม่เหมือนกัน Ten Steps จัดกลุ่มตามวิธีที่ใช้ assess จึงรวม completeness กับ validity ไว้ใน dimension เดียวชื่อ data integrity fundamentals เพราะการ profile ครั้งเดียวหาได้ทั้งสองอย่าง ส่วน Governance กับ FoDE เหลือแค่สามคุณลักษณะ คือ accuracy, completeness และ timeliness (หนังสือ: Ten Steps บทที่ 3 หน้า 42 ถึง 46; Governance บทที่ 5 หน้า 113; FoDE บทที่ 2 หน้า 54 ถึง 56)

ในเส้นทางนี้เราใช้หก dimension ของ DAMA UK แล้วเพิ่ม integrity กับ reasonability ที่ DMBOK2 Table 29 เพิ่มไว้อีกสองตัว เพราะ SQL วัดได้ตรงที่สุด ชื่อเหล่านี้เป็นแค่ภาษากลางของทีม ถ้าทีมของคุณใช้ชุดอื่นก็ใช้ได้เหมือนกัน ขอแค่ทุกคนใช้ความหมายตรงกัน (หนังสือ: DMBOK2 Table 29 หน้า 458 ถึง 459)

และเราไม่จำเป็นต้องวัดทุก dimension Ten Steps ให้ถามสองข้อกับแต่ละตัว คือผลที่ได้ทำให้เรามีอะไรลงมือทำต่อไหม และเรา assess มันได้จริงไหม ถ้าข้อใดตอบว่าไม่ ก็ข้ามไปได้ [บท 12](/data-quality/ten-steps/#เลือกสิ่งที่จะ-assess-และสิ่งที่จะข้าม) จะกลับมาพูดเรื่องนี้อีกครั้ง

</Step>

## Completeness, Validity, Uniqueness

**Completeness** ถามว่าข้อมูลที่ควรมี มีครบไหม ในตาราง `customers` ข้างบน customer 14 ไม่มี email เลย ถ้าทีม marketing ต้องส่งเมลหาลูกค้าทุกคน row นี้ก็คือลูกค้าที่ส่งไม่ได้ เราวัดด้วย query นี้

```sql
SELECT count(*) FILTER (WHERE email IS NULL), count(*) FROM customers;
-- 40 จาก 500
```

`count(*) FILTER (WHERE ...)` นับเฉพาะ row ที่เข้าเงื่อนไข ส่วน `count(*)` ตัวที่สองไม่มีเงื่อนไข จึงนับทุก row เราเลยได้ทั้งจำนวนที่ผิด (40) และจำนวนทั้งหมด (500) ใน query เดียว แปลว่า email ครบ 92% ส่วนอีก 8% เป็นช่องว่าง นอกจากช่องว่างในระดับ column แล้ว completeness ยังวัดได้ที่ระดับ row และระดับ dataset ซึ่งหน้า [Completeness แบบเจาะลึก](/data-quality/dimensions/completeness/) จะอธิบายต่อ (หนังสือ: DMBOK2 Table 29 หน้า 458)

**Validity** ถามว่าค่าที่อยู่ในช่อง เป็นค่าที่ช่องนั้นอนุญาตให้มีหรือไม่ ช่องหนึ่งอาจอนุญาตเฉพาะค่าในรายการ ค่าในช่วง หรือค่าที่หน้าตาเป็นรูปแบบหนึ่ง customer 23 มี email เป็น `user23example.com` ซึ่งไม่มี `@` จึงไม่มีหน้าตาของ email ส่วน customer 36 ใช้ country เป็น `THA` ทั้งที่ระบบรับเฉพาะ TH, SG, JP และ US (หนังสือ: DMBOK2 Table 29 หน้า 459)

```sql
-- email ต้องมีหน้าตา a@b.c (ตรวจเฉพาะ row ที่ email ไม่ว่าง)
SELECT count(*) FILTER (WHERE NOT regexp_matches(email, '^[^@\s]+@[^@\s]+\.[^@\s]+$')), count(email) FROM customers;
-- 15 จาก 460

-- country ต้องอยู่ในรายการ
SELECT count(*) FILTER (WHERE country NOT IN ('TH','SG','JP','US')), count(*) FROM customers;
-- 25 จาก 500
```

ข้อความ `'^[^@\s]+@[^@\s]+\.[^@\s]+$'` คือ pattern ที่บอกว่า email ต้องมีตัวอักษรอย่างน้อยหนึ่งตัว ตามด้วย `@` ตามด้วยตัวอักษรอีกหลายตัว ตามด้วยจุด และตามด้วยตัวอักษรอีกชุดหนึ่ง โดยไม่มีช่องว่างหรือ `@` แทรกอยู่ตรงกลาง สังเกตว่าตัวหารของ rule แรกคือ 460 ซึ่งนับเฉพาะ email ที่ไม่ว่าง เพราะ email ที่ว่างถูกนับไปแล้วใน completeness เราไม่อยากให้ช่องว่างหนึ่งช่องตกสอง rule พร้อมกัน

**Uniqueness** ถามว่าของแต่ละอย่างถูกบันทึกแค่ครั้งเดียวไหม ใน `orders` order 267 อยู่สองแถวที่เหมือนกันทุกช่อง ถ้าเรานับยอดขายตรงๆ ยอดของ order นี้ก็จะถูกนับสองเท่า ส่วนใน `customers` customer 1 กับ 491 ใช้ email เดียวกัน อาจเป็นคนเดียวที่สมัครสองครั้งก็ได้ (หนังสือ: DMBOK2 Table 29 หน้า 459)

```sql
SELECT count(*) - count(DISTINCT order_id), count(*) FROM orders;
-- row ส่วนเกิน 20 จาก 3,020
```

query นี้เอาจำนวน row ทั้งหมด ลบด้วยจำนวน `order_id` ที่ไม่ซ้ำกัน ผลลัพธ์จึงเป็นจำนวน row ที่เกินมา ไม่ใช่จำนวน order ที่ซ้ำ (รัน: `02_dimensions.py` ทุกตัวเลขข้างบนตรงกับจำนวนที่ฝัง)

## Consistency, Integrity

**Consistency** ถามว่าข้อมูลสองส่วนที่ควรตรงกัน ตรงกันจริงไหม หนังสือแยกเป็นสามระดับ คือเทียบภายใน row เดียวกัน (record-level) เทียบข้าม row หรือข้าม dataset (cross-record) และเทียบข้ามเวลา (temporal) และเตือนไว้ว่าอย่าสับสนกับ accuracy เพราะสองค่าที่ตรงกันอาจผิดทั้งคู่ก็ได้ (หนังสือ: DMBOK2 Table 29 หน้า 458)

ใน `orders` ข้างบน order 84 มี status เป็น SHIPPED แต่ไม่มีเวลาส่ง ส่วน order 816 ถูกส่งวันที่ 1 ต.ค. ซึ่งเป็นวันก่อนที่ถูกสั่งในวันที่ 2 ต.ค. ถ้าดูทีละช่อง ทุกช่องดูปกติ ปัญหาเกิดตอนที่เรามองสองช่องพร้อมกัน

```sql
-- status SHIPPED ต้องมีเวลาส่ง
SELECT count(*) FILTER (WHERE status = 'SHIPPED' AND shipped_ts IS NULL),
       count(*) FILTER (WHERE status = 'SHIPPED') FROM orders;
-- 25 จาก 1,794

-- เวลาส่งต้องไม่มาก่อนเวลาสั่ง
SELECT count(*) FILTER (WHERE shipped_ts < order_ts), count(shipped_ts) FROM orders;
-- 10 จาก 1,769
```

rule แบบนี้ไม่มีทางเจอจากการตรวจทีละ column เพราะแต่ละ column ไม่ผิดเมื่อมองเดี่ยวๆ

**Integrity** ถามว่าข้อมูลที่ชี้ไปหาข้อมูลอีกตาราง ชี้ไปหาของที่มีอยู่จริงไหม ในหนังสือส่วนใหญ่หมายถึง referential integrity คือความสอดคล้องระหว่างสองตารางผ่าน reference key ถ้า key ชี้ไปหาที่ที่ไม่มีอะไร เราเรียกว่า orphan ใน `orders` ข้างบน order 65 ชี้ไปที่ customer 9017 แต่ตาราง `customers` ของเรามี customer แค่หมายเลข 1 ถึง 500 (หนังสือ: DMBOK2 Table 29 หน้า 459)

```sql
SELECT count(*) FILTER (WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id)),
       count(customer_id)
FROM orders o WHERE customer_id IS NOT NULL;
-- orphan 30 จาก 3,005
```

<Callout type="warn" title="ใช้ NOT EXISTS แทน NOT IN">
ถ้าเขียน rule นี้ด้วย `NOT IN (SELECT customer_id FROM customers)` จะมีกับดักสองข้อ ข้อแรก order ที่ `customer_id` เป็น NULL (เช่น order 344) จะไม่ถูกนับเป็น orphan เพราะ SQL ตอบว่า "ไม่รู้" แทนที่จะตอบว่า "ไม่อยู่" ซึ่งก็ถูกแล้ว เพราะ row พวกนั้นเป็นปัญหาของ completeness ข้อที่สองน่ากลัวกว่า ถ้ารายการที่ถูกเทียบมี NULL อยู่แม้แต่ตัวเดียว ผลทั้ง query จะว่างเปล่า และ rule จะรายงานว่าข้อมูลสะอาดทั้งที่ไม่ใช่ ให้ใช้ `NOT EXISTS` แล้วนับ row ที่ NULL ใน rule ของ completeness แยกต่างหาก
</Callout>

</Step>

## Timeliness, Accuracy

**Timeliness** ถามว่าข้อมูลที่เรามี สะท้อนความจริง ณ เวลาที่เราต้องการหรือไม่ ต้องอ่านคู่กับความถี่ที่ข้อมูลเปลี่ยน (volatility) เสมอ หนังสือแยกเป็นสองเรื่อง *currency* คือค่านี้เป็นเวอร์ชันล่าสุดไหม และ *latency* คือใช้เวลานานเท่าไรตั้งแต่ข้อมูลเกิดจนพร้อมใช้ (หนังสือ: DMBOK2 Table 29 หน้า 459)

ตัวอย่างของ latency คือ order 135 ถูกสั่งวันที่ 22 ต.ค. เวลา 12:07 แต่เพิ่งมาถึง warehouse วันที่ 26 ต.ค. เวลา 12:07 ช้าไปสี่วัน ในขณะที่ order ปกติใช้เวลาแค่ไม่กี่นาที

```sql
-- ระดับ row: order มาถึง warehouse ภายใน 24 ชั่วโมงไหม
SELECT count(*) FILTER (WHERE ingested_at - order_ts > INTERVAL 24 HOUR), count(*) FROM orders;
-- 40 จาก 3,020
```

ถ้ามองระดับ table ภาพจะต่างออกไป order ล่าสุดในตารางเกิดเมื่อวันที่ 29 ต.ค. เวลา 23:59 ส่วนเวลาที่เราถามคือ 1 พ.ย. เวลา 08:00 ห่างกัน 56 ชั่วโมง ถ้าสัญญากับ consumer ไว้ว่าข้อมูลจะไม่เก่าเกิน 24 ชั่วโมง นี่คือผิดสัญญา แม้ 98.68% ของ row จะมาตรงเวลาก็ตาม (รัน: `02_dimensions.py`)

**Accuracy** ถามว่าข้อมูลตรงกับความจริงแค่ไหน หนังสือบอกตรงๆ ว่าวัดยาก เพราะเราต้องมีอะไรบางอย่างที่เรามั่นใจว่าถูก ไว้เทียบ เช่น ระบบที่เป็นต้นฉบับของข้อมูลนั้น (system of record) เราจึงเลือกใช้ payment system เป็นแหล่งอ้างอิง แล้วเทียบยอดของแต่ละ order กับผลรวม payment ของ order นั้น ตัวอย่างเช่น order 91 บันทึกยอดไว้ 487.71 แต่ payment ที่รับจริงมี 437.71 ต่างกัน 50 บาท (หนังสือ: DMBOK2 Table 29 หน้า 458)

```sql
WITH o AS (SELECT DISTINCT order_id, total_amount FROM orders WHERE status <> 'CANCELLED'),
     p AS (SELECT order_id, sum(amount) AS paid FROM payments GROUP BY order_id)
SELECT count(*) FILTER (WHERE abs(o.total_amount - p.paid) > 0.005), count(*)
FROM o JOIN p USING (order_id);
-- ไม่ตรง 35 จาก 2,533
```

query นี้ตัด order ที่ถูกยกเลิกออก แล้วเอาที่เหลือมาจับคู่กับผลรวม payment ของ order เดียวกัน ถ้าทั้งสองค่าต่างกันเกิน 0.005 ก็ถือว่าไม่ตรง หนังสือเตือนอีกข้อว่าข้อมูลอาจ valid แต่ไม่ accurate ได้ เช่น วันเกิด 1990-01-01 ผ่าน rule เรื่องช่วงปี แต่ถ้า customer คนนั้นเกิดปี 1985 ค่านี้ก็ผิด

</Step>

## สรุปทั้ง 14 Rule

ตารางนี้รวมทั้ง 14 rule ที่เราวัดมาตั้งแต่ต้น ทุกบรรทัดมีจำนวนที่ไม่ผ่าน จำนวนทั้งหมดที่เอามาตรวจ และเปอร์เซ็นต์ของทั้งสองฝั่ง

| dimension | rule | ไม่ผ่าน | ทั้งหมด | ผ่าน% | ไม่ผ่าน% |
|---|---|---:|---:|---:|---:|
| completeness | customers.email ถูกกรอก | 40 | 500 | 92.00 | 8.00 |
| completeness | orders.customer_id ถูกกรอก | 15 | 3,020 | 99.50 | 0.50 |
| validity | email มี format `a@b.c` | 15 | 460 | 96.74 | 3.26 |
| validity | country อยู่ในรายการ | 25 | 500 | 95.00 | 5.00 |
| validity | birth_date อยู่ระหว่างปี 1900 ถึงวันนี้ | 6 | 500 | 98.80 | 1.20 |
| validity | orders.total_amount ไม่ติดลบ | 12 | 3,020 | 99.60 | 0.40 |
| uniqueness | หนึ่ง email ต่อหนึ่ง customer | 10 | 460 | 97.83 | 2.17 |
| uniqueness | หนึ่ง row ต่อ order_id | 20 | 3,020 | 99.34 | 0.66 |
| consistency | SHIPPED ต้องมี shipped_ts | 25 | 1,794 | 98.61 | 1.39 |
| consistency | shipped_ts ไม่ก่อน order_ts | 10 | 1,769 | 99.43 | 0.57 |
| integrity | orders.customer_id มีใน customers | 30 | 3,005 | 99.00 | 1.00 |
| integrity | payments.order_id มีใน orders | 20 | 2,553 | 99.22 | 0.78 |
| timeliness | order มาถึงภายใน 24 ชม. | 40 | 3,020 | 98.68 | 1.32 |
| accuracy | ยอดตรงกับ payment system | 35 | 2,533 | 98.62 | 1.38 |

คอลัมน์ "ทั้งหมด" ไม่เท่ากันทุกบรรทัด เพราะแต่ละ rule เลือกตัวหารของตัวเอง email ที่มี format ผิดนับจาก 460 ไม่ใช่ 500 เพราะ email ที่ว่างถูกจับไปแล้วโดย rule ของ completeness ส่วน "SHIPPED ต้องมี shipped_ts" นับจาก 1,794 เพราะมีแค่ order ที่ SHIPPED เท่านั้นที่ rule นี้เกี่ยวข้อง การเลือกตัวหารแบบนี้กันไม่ให้ข้อผิดพลาดเดียวถูกนับซ้ำในสอง rule

</Step>

## หนึ่งหน้าต่อหนึ่ง Dimension

ส่วนที่ผ่านมาเป็นภาพรวม ถ้าอยากเห็นแต่ละ dimension ละเอียดขึ้น มีหน้าแยกให้ครบทุกตัว ทุกหน้าเปิดด้วย row จริงจาก dataset ก่อนอธิบาย และบอกว่าคำนั้นมักถูกเข้าใจผิดตรงไหน

- [Completeness แบบเจาะลึก](/data-quality/dimensions/completeness/) ว่าด้วยเรื่องที่ NULL ไม่ได้แปลว่าผิดเสมอไป และตารางที่ขาด row ไปทั้งวันแต่ทุก row ที่เหลือยังกรอกครบ
- [Validity แบบเจาะลึก](/data-quality/dimensions/validity/) ว่าด้วยเรื่องที่ผ่าน rule แล้วยังผิดได้ และ rule ที่หลวมเกินไป
- [Uniqueness แบบเจาะลึก](/data-quality/dimensions/uniqueness/) ว่าด้วยเรื่องที่คำว่า "ซ้ำ" มีสามความหมาย และ `DISTINCT` ซ่อน defect ได้
- [Consistency แบบเจาะลึก](/data-quality/dimensions/consistency/) ว่าด้วยเรื่องที่สองค่าตรงกันแต่ผิดทั้งคู่ได้
- [Integrity แบบเจาะลึก](/data-quality/dimensions/integrity/) ว่าด้วยเรื่องที่คำเดียวมีสามความหมาย และ `NOT IN` ที่รายงานว่าสะอาดทั้งที่ไม่ใช่
- [Timeliness แบบเจาะลึก](/data-quality/dimensions/timeliness/) ว่าด้วยเรื่องที่ pipeline รันเมื่อเช้าแต่ข้อมูลเก่าสองวัน
- [Accuracy แบบเจาะลึก](/data-quality/dimensions/accuracy/) ว่าด้วยเรื่องที่ต้องมีแหล่งความจริงก่อนถึงจะวัดได้ และค่า tolerance ที่เปลี่ยนตัวเลข
- [Reasonability แบบเจาะลึก](/data-quality/dimensions/reasonability/) ว่าด้วยเรื่องวันที่ทุกค่า valid แต่ทั้งวันผิด

แบบฝึก `13_dimension_pitfalls.py` สร้างตัวเลขทุกตัวในหน้าเหล่านี้ซ้ำ และหยุดทันทีถ้าตัวไหนขยับ ตัวอย่างบางข้อใช้ table เล็กๆ ที่สมมติขึ้น หรือ copy ของข้อมูลที่ดัดแปลง เพราะ dataset หลักไม่มี defect ชนิดนั้นฝังไว้ ซึ่งแต่ละหน้าจะบอกไว้ทุกครั้ง

</Step>

## เช็กตัวเอง

- ถ้าทีมหนึ่งใช้ 6 dimension และอีกทีมใช้ 15 dimension รายงานของสองทีมเปรียบเทียบกันได้ไหม ต้องตกลงอะไรกันก่อน
- rule "SHIPPED ต้องมี shipped_ts" นับเป็น consistency ก็ได้ หรือเป็น completeness แบบมีเงื่อนไขก็ได้ ถ้าต้องเลือกแค่อย่างเดียว คุณจะใช้เกณฑ์อะไรตัดสิน
- dimension ไหนในตารางสรุปที่ SQL อย่างเดียวพิสูจน์ไม่ได้ว่าถูก ต้องมีอะไรเพิ่ม
