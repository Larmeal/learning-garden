## Consistency ถามว่าสองส่วนที่ควรตรงกัน ตรงกันจริงไหม

ลองนึกถึงนาฬิกาสองเรือนที่แขวนอยู่ในบ้านหลังเดียวกัน ถ้าทั้งสองเรือนบอกเวลาเท่ากัน เราก็พูดได้ว่ามัน consistent กัน ถ้าเรือนหนึ่งเร็วไปสิบนาที ก็ไม่ consistent แต่ไม่ว่าจะแบบไหน นาฬิกาสองเรือนก็ยังไม่ได้บอกเราว่าตอนนี้กี่โมงจริงๆ

consistency ใน data quality คือการดูแบบนี้ ว่าข้อมูลสองส่วนที่ควรสอดคล้องกัน สอดคล้องกันหรือเปล่า DMBOK2 อธิบายว่าอาจเป็นค่าที่ถูกแสดงในแบบเดียวกันภายใน dataset หรือระหว่างหลาย dataset หรืออาจหมายถึงขนาดและองค์ประกอบของ dataset ข้ามระบบหรือข้ามเวลา DAMA UK ใช้ถ้อยคำว่า ไม่มีความต่างเมื่อเทียบสอง representation ขึ้นไปของสิ่งหนึ่งกับนิยามของมัน (หนังสือ: DMBOK2 Table 29 หน้า 458 และหัวข้อ 1.3.3 หน้า 457)

ลองดู order สองรายการใน `orders`

| order_id | status | order_ts | shipped_ts |
|---:|---|---|---|
| 84 | SHIPPED | 2026-07-03 06:01 | (ว่าง) |
| 816 | SHIPPED | 2026-10-02 03:26 | 2026-10-01 03:26 |

order 84 บอกว่าส่งแล้ว แต่ไม่มีเวลาส่ง ส่วน order 816 ถูกส่งวันที่ 1 ตุลาคม ซึ่งเป็นวันก่อนที่ลูกค้าจะสั่งในวันที่ 2 ตุลาคม ถ้าเราดู `order_ts` กับ `shipped_ts` ของ order 816 ทีละช่อง ทั้งสองช่องเป็นวันที่ที่ถูกต้อง ปัญหาปรากฏเมื่อเรามองสองช่องพร้อมกัน ซึ่ง rule ที่ตรวจทีละ column ไม่มีวันเห็น

</Step>

## สามระดับ

หนังสือแบ่ง consistency เป็นสามระดับ ตามสิ่งที่เรานำมาเทียบกัน (หนังสือ: DMBOK2 Table 29 หน้า 458)

| ระดับ | เทียบอะไรกับอะไร | rule ใน dataset ของเรา | ไม่ผ่าน |
|---|---|---|---:|
| Record-level | สองช่องใน row เดียวกัน | order ที่ SHIPPED ต้องมี `shipped_ts` | 25 จาก 1,794 |
| Record-level | สองช่องใน row เดียวกัน | `shipped_ts` ต้องไม่ก่อน `order_ts` | 10 จาก 1,769 |
| Cross-record | ช่องเดียวกันข้าม row หรือข้าม dataset | country ของประเทศเดียวกันต้องเขียนแบบเดียวกันทุก row | 25 row ที่เขียนอีกห้าแบบ |
| Temporal | ช่องเดียวกันในเวลาต่างกัน | จำนวน order วันนี้ควรใกล้เคียงวันก่อนๆ | ดูหน้า [Reasonability](/data-quality/dimensions/reasonability/) |

สองแถวแรกคือ order 84 กับ 816 ที่เราเพิ่งเห็น ส่วนแถว cross-record ดูได้จากการนับค่าใน `customers.country`

| country | จำนวน row |
|---|---:|
| TH | 330 |
| SG | 58 |
| JP | 56 |
| US | 31 |
| THA, T.H., th, Thailand, ไทย | อย่างละ 5 |

ห้าค่าล่างสุดคือประเทศไทยที่เขียนต่างกันไป ถ้านับรวมกับ `TH` ก็รวมเป็นหกการสะกดสำหรับประเทศเดียว (รัน: `02_dimensions.py`, `13_dimension_pitfalls.py`) ถ้ารายงานรายได้แยกตามประเทศ ผลที่ได้จะเห็นไทยเป็นหกกลุ่มย่อย แทนที่จะเป็นกลุ่มเดียว

เราวัด rule ของระดับแรกได้ด้วย query นี้

```sql
-- เวลาส่งต้องไม่มาก่อนเวลาสั่ง
SELECT count(*) FILTER (WHERE shipped_ts < order_ts), count(shipped_ts) FROM orders;
-- 10 จาก 1,769
```

ตัวหารคือ `count(shipped_ts)` ซึ่งนับเฉพาะ order ที่มีเวลาส่ง เพราะ order ที่ไม่มีเวลาส่งไม่มีอะไรให้เทียบ ลองเขียน rule "order ที่ยังเป็น PLACED ต้องไม่มี `shipped_ts`" แล้วรัน เราจะได้ 0 row ซึ่งก็เป็นข้อมูลที่มีประโยชน์ เพราะมันบอกว่าระบบไม่เคยใส่เวลาส่งให้ order ที่ยังไม่ส่ง ให้เก็บ rule นี้ไว้ ถ้าวันหนึ่งมันเริ่มเจอ row ก็แปลว่ามีอะไรเปลี่ยนไป (รัน: `13_dimension_pitfalls.py`)

</Step>

## สองค่าตรงกัน ไม่ได้แปลว่าถูก

กลับไปที่นาฬิกาสองเรือน ถ้าทั้งสองเรือนเดินเร็วไปสิบนาทีเท่ากัน มันก็ยัง consistent กันอยู่ แต่เวลาที่บอกผิด ข้อมูลก็เป็นแบบเดียวกัน ตารางนี้เป็น order สมมติ 3 รายการ เทียบยอดใน `orders` กับสองที่ ที่แรกคือสำเนายอดในตารางรายงาน และที่สองคือ payment system

| order_id | total_amount ใน `orders` | ยอดในตารางรายงาน | ยอดที่ payment system รับจริง |
|---:|---:|---:|---:|
| 1 | 100.00 | 100.00 | 90.00 |
| 2 | 250.00 | 250.00 | 250.00 |
| 3 | 80.00 | 80.00 | 70.00 |

ยอดใน `orders` ตรงกับตารางรายงานทั้ง 3 รายการ แต่ตรงกับ payment system แค่ 1 รายการ (รัน: `13_dimension_pitfalls.py`) ที่ตรงกับตารางรายงานทุกรายการ ก็เพราะตารางรายงานถูก copy มาจาก `orders` ตั้งแต่แรก สำเนาย่อมตรงกับต้นฉบับเสมอ ถ้าสองระบบมี bug ตัวเดียวกัน consistency check ทุกอันระหว่างสองระบบนี้ก็จะผ่านหมด DMBOK2 จึงเตือนไว้ว่าอย่าสับสน consistency กับ accuracy ส่วนการเทียบกับแหล่งที่เราเชื่อถือ เช่น payment system เป็นเรื่องของ [Accuracy](/data-quality/dimensions/accuracy/) (หนังสือ: DMBOK2 Table 29 หน้า 458)

</Step>

## การวัดบอกความต่าง นิยามบอกว่าใครถูก

การนับว่า country มีหกการสะกดสำหรับประเทศไทย เป็นสิ่งที่เราค้นพบ แต่การตัดสินว่าจะใช้ `TH` แล้วแปลงอีกห้าแบบให้เป็น `TH` เป็นอีกขั้นหนึ่ง ซึ่งหนังสือเรียกว่า standardization คือการปรับข้อมูลที่เข้ามาให้ตรงกับ rule เรื่องเนื้อหาและ format (หนังสือ: DMBOK2 Table 29 หน้า 458) ตัวการวัดเลือกให้เราไม่ได้ว่าแบบไหนคือแบบที่ถูก นี่คือเหตุผลที่ถ้อยคำของ DAMA UK มีคำว่า "เทียบกับนิยาม" อยู่ด้วย

การที่ profile `order_ts` กับ `shipped_ts` ทีละ column แล้วไม่เห็นอะไรผิด ([บท 3](/data-quality/profiling/#profile-ของทุก-column-โดยไม่ต้องรู้ความหมาย) พูดถึงการ profile แบบนี้) เป็นเรื่องที่เกิดขึ้นเสมอกับ consistency ในระดับ record rule ที่ตรวจความสัมพันธ์ระหว่างสองช่อง ต้องรู้ก่อนว่าธุรกิจคาดว่าสองช่องนี้สัมพันธ์กันอย่างไร และความรู้ข้อนั้นมักอยู่ในหัวของคนที่ทำงานกับข้อมูลทุกวัน ให้ไปถามเขา

</Step>

## Rule เดียวกัน อยู่ใต้ป้ายต่างกันได้

rule "order ต้องถูกส่งหลังถูกสั่ง" ที่เราจัดเป็น consistency ตรงกับนิยามระดับ record ของ DMBOK2 ที่เทียบค่าสองช่องใน row เดียวกัน แต่ Ten Steps ยกตัวอย่างเดียวกันนี้ไว้ใต้ referential integrity เพราะ Ten Steps ใช้คำว่า integrity ในความหมายที่กว้างกว่า คือความสอดคล้องของข้อมูลภายใน relationship หนึ่งๆ (หนังสือ: Ten Steps บทที่ 4 หน้า 128 ถึง 135) ทั้งสองแบบอธิบายได้ rule ก็คือ rule เดียวกัน ต่างกันแค่ป้าย ถ้าสองทีมในองค์กรเดียวกันใช้ป้ายต่างกัน รายงานของสองทีมจะเทียบกันยาก จึงควรตกลงป้ายเดียวก่อน

ส่วน Temporal ที่เป็นระดับที่สามของ consistency ในหนังสือ ใช้ตัวอย่างว่าจำนวน transaction ในหนึ่งวันไม่ควรเกิน 105% ของค่าเฉลี่ยของ 30 วันก่อนหน้า (หนังสือ: DMBOK2 Table 29 หน้า 458) หลายทีมเรียกการตรวจแบบนี้ว่า volume monitoring หรือ reasonability หน้า [Reasonability](/data-quality/dimensions/reasonability/#threshold-จากค่าเฉลี่ยอย่างเดียว-fire-ในวันปกติ) แสดงว่า bar แบบนี้ทำงานอย่างไรกับ dataset ของเรา

Ten Steps ยังแยก consistency ระหว่างหลาย data store ออกเป็น dimension ของตัวเองชื่อ consistency and synchronization เพื่อให้วางแผนเวลาและคนไว้ สำหรับการ profile ทุก store แล้วเอามาเทียบกัน (หนังสือ: Ten Steps บทที่ 4 หน้า 146 ถึง 148) ในเส้นทางนี้ การเทียบระหว่างสองระบบจะอยู่ใน [บท 8](/data-quality/reconciliation/#reconcile-ด้วยจำนวน-row-และผลรวม)

</Step>

<Step>

## ต่างจาก Dimension อื่นอย่างไร

consistency ต่างจาก validity ตรงที่ validity ตรวจค่าเดียวเทียบกับ domain ส่วน consistency ต้องมีสองค่ามาเทียบกัน order 816 มี timestamp สองตัวที่ valid ทั้งคู่ แต่ไม่ consistent กัน ส่วนค่า `ไทย` ใน country ตก validity เทียบกับรายการ และไม่ consistent กับ `TH` ที่ row อื่นใช้ ดูหน้า [Validity](/data-quality/dimensions/validity/) ประกอบ

consistency ต่างจาก accuracy ตามที่อธิบายไปแล้วในหัวข้อก่อนหน้า สองค่าที่ตรงกันอาจผิดทั้งคู่ได้ ถ้าไม่มีแหล่งอ้างอิงที่เชื่อถือได้มาเทียบ

</Step>

<Step>

## เช็กตัวเอง

- ยกตัวอย่างคู่ column ใน table ที่คุณดูแลที่ต้องตรงกันเสมอ rule นี้เขียนไว้ที่ไหนบ้างตอนนี้
- สอง dashboard แสดงตัวเลขเดียวกัน นั่นบอกอะไรเกี่ยวกับว่าตัวเลขนั้นถูกหรือไม่
- ทีมของคุณจัด "order ต้องถูกส่งหลังถูกสั่ง" เป็น consistency และอีกทีมจัดเป็น integrity คุณทำอะไรก่อนจะเทียบรายงานของสองทีม

</Step>
