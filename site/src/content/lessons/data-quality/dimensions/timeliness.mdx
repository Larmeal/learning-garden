## Timeliness ถามว่าข้อมูลที่เรามี ทันสมัยพอไหม

นึกถึงกล่องนมกล่องหนึ่ง วันที่บรรจุเป็นข้อเท็จจริงอย่างหนึ่ง ส่วนวันนี้ยังดื่มได้ไหมเป็นอีกคำถามหนึ่งที่ต่างกัน นมที่เพิ่งบรรจุเมื่อเช้าก็เสียได้ ถ้าไม่ได้แช่เย็น และนมกล่องเก่าบางชนิดก็ยังดื่มได้อยู่ timeliness ในข้อมูลก็เป็นแบบนี้ มีสองเรื่องที่ต้องแยกกันให้ออก

DAMA UK นิยาม timeliness ว่าระดับที่ข้อมูลสะท้อนความจริง ณ จุดเวลาที่ต้องการ (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 457) ส่วน DMBOK2 อธิบายว่าต้องอ่านเทียบกับ volatility คือข้อมูลนั้นมีแนวโน้มเปลี่ยนบ่อยแค่ไหน และเพราะอะไร โดยแยกเป็นสองคำ (หนังสือ: DMBOK2 Table 29 หน้า 459)

| คำ | คำถามที่ถาม | ตัวอย่างของหนังสือ |
|---|---|---|
| Currency | ค่านี้เป็นเวอร์ชันล่าสุดของข้อมูลหรือเปล่า | country code อาจ current อยู่ได้หลายปี ส่วนราคาหุ้น current ได้แค่ไม่กี่นาที |
| Latency | ตั้งแต่ข้อมูลถูกสร้างจนพร้อมให้ใช้ ใช้เวลานานแค่ไหน | batch ที่รันข้ามคืนทำให้ข้อมูลที่ป้อนเมื่อวาน มี latency 1 วัน ณ 8 โมงเช้า |

ดูตัวอย่างของ latency จาก `orders` สอง order ที่เวลาถูกสร้างกับเวลาที่มาถึง warehouse (`ingested_at`) ต่างกันมาก

| order_id | order_ts (ถูกสั่ง) | ingested_at (มาถึง warehouse) | latency |
|---:|---|---|---|
| 2 | 2026-07-17 05:33 | 2026-07-17 05:53 | 20 นาที |
| 135 | 2026-10-22 12:07 | 2026-10-26 12:07 | 4 วัน |

order 2 มาถึงภายใน 20 นาทีซึ่งเป็นปกติ ส่วน order 135 มาช้าไปสี่วัน

</Step>

## ระดับ Row กับระดับ Table

เราตรวจ timeliness ได้สองระดับ และสองระดับนี้ให้ตัวเลขต่างกัน ระดับ row ถามว่าแต่ละ row มาถึงเร็วพอหรือเปล่า

```sql
-- order แต่ละรายการมาถึง warehouse ภายใน 24 ชั่วโมงไหม
SELECT count(*) FILTER (WHERE ingested_at - order_ts > INTERVAL 24 HOUR), count(*) FROM orders;
-- 40 จาก 3,020 หรือตรงเวลา 98.68%
```

query นี้เอาเวลาที่มาถึงลบด้วยเวลาที่ถูกสั่ง แล้วนับ row ที่ห่างกันเกิน 24 ชั่วโมง ถ้ามองทุก row รวมกัน latency มัธยฐานคือ 16 นาที และ row ที่ช้าที่สุดมาช้าถึง 120 ชั่วโมง (รัน: `13_dimension_pitfalls.py`)

ระดับ table ถามอีกคำถามหนึ่ง คือตอนนี้ตารางทันสมัยไหม order ล่าสุดในตารางเกิดเมื่อวันที่ 29 ต.ค. เวลา 23:59 แต่เวลาที่เราถามคือวันที่ 1 พ.ย. เวลา 08:00 ห่างกัน 56 ชั่วโมง ถ้าเราสัญญากับ consumer ไว้ว่าข้อมูลจะไม่เก่าเกิน 24 ชั่วโมง สัญญานี้ก็ผิด ทั้งที่ row ถึง 98.68% มาตรงเวลาก็ตาม (รัน: `02_dimensions.py`)

</Step>

## เวลาที่ Load กับเวลาที่เหตุการณ์เกิด ไม่เท่ากัน

ลองดูสอง timestamp ล่าสุดในตาราง `orders` ณ เวลา 1 พ.ย. 08:00

| ช่อง | ค่าล่าสุด | เก่ากว่าตอนนี้ |
|---|---|---|
| `ingested_at` (เวลาที่ pipeline เขียนลงตาราง) | 1 พ.ย. 02:11 | 5 ชั่วโมง 49 นาที |
| `order_ts` (เวลาที่ลูกค้าสั่ง) | 29 ต.ค. 23:59 | 56 ชั่วโมง |

pipeline เพิ่งรันเสร็จเมื่อเช้านี้ แต่ order ใหม่สุดที่มันนำมาเก่าไปสองวันกว่า (รัน: `13_dimension_pitfalls.py`) ถ้า check freshness ของเราอ่านเวลาที่ load หรือเวลาที่ job รันเสร็จล่าสุด check นั้นจะผ่าน เพราะ pipeline รันเมื่อเช้าจริง แต่ถ้าอ่านเวลาที่เหตุการณ์เกิด check จะตก ทั้งสองค่านี้แยกจากกันเมื่อต้นทางหยุดส่งข้อมูลแต่ pipeline ยังรันต่อไปบนความว่างเปล่า

ดังนั้น rule ของ timeliness ต้องบอกให้ชัดว่าอ่าน column ไหน เรื่อง freshness ของ table ที่ไม่มีข้อมูลเข้ามานาน [บท 7](/data-quality/monitoring/#freshness-ช่วงที่ไม่มีข้อมูลยาวแค่ไหนจึงเป็นเหตุ) พูดถึงต่อว่าช่วงที่เงียบนานแค่ไหนถึงจะเป็นเหตุ

</Step>

## ทันเวลา ขึ้นกับว่าข้อมูลเปลี่ยนบ่อยแค่ไหน

"ทันเวลา" ไม่มีความหมายถ้ายังไม่รู้ว่าข้อมูลนั้นเปลี่ยนบ่อยแค่ไหน เกณฑ์ 24 ชั่วโมงเหมาะกับ order แต่ถ้านำไปใช้กับตาราง country code ที่แทบไม่เปลี่ยน มันจะส่ง alarm ทุกวันโดยไม่มีเหตุ และถ้านำไปใช้กับราคาหุ้นก็หลวมเกินไป หนังสือยกตัวอย่างราคาหุ้นไว้ว่า ตอนตลาดเปิดราคาอัปเดตบ่อย ส่วนตอนตลาดปิดข้อมูลไม่เปลี่ยนแล้ว แต่ก็ยังถือว่า current เพราะตลาดเองไม่ได้ทำงาน (หนังสือ: DMBOK2 Table 29 หน้า 459) เกณฑ์ของแต่ละตารางจึงควรตั้งร่วมกับ consumer ของมัน

เรื่องเดียวกันนี้ใช้กับความเงียบ ถ้าต้นทางไม่ทำงานในวันหยุด alarm freshness ที่ดังในวันหยุดก็เป็น alarm เท็จ เราควรใส่ปฏิทินไว้ใน rule ไม่เช่นนั้น alarm จะสอนให้คนเลิกสนใจมัน

Ten Steps ก็มอง timeliness จากมุมที่กว้างกว่าจำนวนชั่วโมง คือดูจังหวะของเหตุการณ์ขณะที่ข้อมูลเดินทางผ่านวงจรชีวิตของมัน และเช็กว่า sync ที่ตกลงกันไว้เกิดขึ้นจริง ตัวอย่างในหนังสือคือพนักงานขายต้อง sync ฐานข้อมูลในเครื่องมือถือกับฐานข้อมูลกลางทุกเย็นก่อน 6 โมง นั่นคือข้อกำหนดของ process ส่วนจำนวนชั่วโมงเป็นผลที่ตามมา (หนังสือ: Ten Steps บทที่ 4 หน้า 148 ถึง 151)

</Step>

## Row ที่มาช้า ทำให้ตัวเลขที่รายงานไปแล้วเปลี่ยน

order 40 รายการมาถึง warehouse ช้ากว่าหนึ่งวัน และบางรายการช้าถึง 5 วัน สมมติว่ารายงานยอดขายของวันที่ 22 ต.ค. ถูกคำนวณเมื่อวันที่ 23 ต.ค. ยอดนั้นจะไม่มี order 135 อยู่ในนั้นเลย เพราะ order นั้นยังมาไม่ถึง พอมาถึงวันที่ 26 ต.ค. ยอดของวันที่ 22 ก็เปลี่ยน

ก่อนปล่อยรายงานจึงควรตัดสินใจว่าจะ restate ตัวเลขย้อนหลัง หรือจะ freeze ตัวเลขที่ส่งไปแล้วและปล่อยให้ order ที่มาช้าไปอยู่ในวันที่มาถึง และต้องบอกคนที่อ่านรายงานด้วยว่าเลือกแบบไหน

</Step>

## ต่างจาก Dimension อื่นอย่างไร

timeliness ต่างจาก [Accuracy](/data-quality/dimensions/accuracy/) ตรงที่ค่าเก่าอาจถูกต้องสำหรับช่วงเวลาที่มันอธิบาย และค่าใหม่ก็อาจผิดได้ ยอด order ที่เราเห็นเมื่อกี้ถูกต้องทุกบาท แต่เก่า 56 ชั่วโมง

timeliness ใกล้กับ [Completeness](/data-quality/dimensions/completeness/) เมื่อ row ล่าสุดหายไป ถ้าวันล่าสุดยังไม่มี row เลย เราตีความได้ทั้งสองแบบ คือข้อมูลยังมาไม่ถึง (timeliness) หรือข้อมูลบางส่วนหาย (completeness) ซึ่งต้องดูต่อว่าตารางเต็มแล้วหรือยังรอ row อยู่

หนังสือยังมี temporal consistency ซึ่งเทียบค่าเดียวกันในสองจุดเวลา ส่วน timeliness เทียบข้อมูลกับนาฬิกา ดูหน้า [Consistency](/data-quality/dimensions/consistency/) และ [Reasonability](/data-quality/dimensions/reasonability/) ประกอบ

</Step>

## เช็กตัวเอง

- ใน table หนึ่งที่คุณดูแล check freshness อ่าน timestamp ตัวไหน เวลาที่เหตุการณ์เกิด หรือเวลาที่ pipeline เขียน
- table ไหนใน platform ของคุณที่เปลี่ยนไม่บ่อย และมีเกณฑ์ freshness เดียวกับ table ที่เปลี่ยนทุกนาทีหรือเปล่า
- รายงานรันตอน 8 โมงและถูกต้อง พอเที่ยง query เดิมให้ตัวเลขต่างไป นั่นคือ defect หรือเปล่า

</Step>
