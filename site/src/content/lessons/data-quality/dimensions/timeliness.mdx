## คำนี้ถามอะไร

DAMA UK นิยาม timeliness ว่าระดับที่ข้อมูลแทนความจริง ณ จุดเวลาที่ต้องการ (หนังสือ: DMBOK2 หัวข้อ 1.3.3 หน้า 457) DMBOK2 บอกว่า timeliness หมายถึงหลายลักษณะ และการวัดต้องอ่านเทียบกับ volatility ที่คาดไว้ของข้อมูล คือข้อมูลมีแนวโน้มเปลี่ยนบ่อยแค่ไหนและเพราะอะไร (หนังสือ: DMBOK2 Table 29 หน้า 459) สองลักษณะมีชื่อเฉพาะ:

| คำ | คำถาม | ตัวอย่างของหนังสือ |
|---|---|---|
| Currency | ค่านี้เป็นเวอร์ชันล่าสุดของข้อมูลไหม | country code อาจ current ได้หลายปี ราคาหุ้น current ได้ไม่กี่นาที |
| Latency | จากที่ข้อมูลถูกสร้างจนพร้อมใช้ ใช้เวลานานเท่าไร | batch ข้ามคืนให้ latency 1 วัน ณ 8 โมงเช้า สำหรับข้อมูลที่ป้อนเมื่อวาน |

(หนังสือ: DMBOK2 Table 29 หน้า 459)

นึกถึงกล่องนม วันที่บรรจุเป็นข้อเท็จจริงอย่างหนึ่ง และวันนี้ยังดื่มได้ไหมเป็นอีกอย่าง กล่องที่บรรจุเมื่อเช้าอาจเสียแล้วก็ได้ และกล่องเก่าของนม UHT อาจยังดีอยู่

</Step>

## ระดับ Row กับระดับ Table

ระดับ row ถามว่าแต่ละ row มาถึงเร็วพอไหม ระดับ table ถามว่า table ทันสมัยตอนนี้ไหม สองระดับให้ตัวเลขต่างกัน

```sql
-- ระดับ row: order แต่ละรายการมาถึง warehouse ภายใน 24 ชั่วโมงไหม
SELECT count(*) FILTER (WHERE ingested_at - order_ts > INTERVAL 24 HOUR), count(*) FROM orders;
-- 40 จาก 3,020 หรือ 98.68% ตรงเวลา
```

| order_id | order_ts | ingested_at | Latency |
|---:|---|---|---|
| 2 | 2026-07-17 05:33 | 2026-07-17 05:53 | 20 นาที |
| 135 | 2026-10-22 12:07 | 2026-10-26 12:07 | 4 วัน |

ทุก row รวมกัน latency มัธยฐานคือ 16 นาที และแย่สุดคือ 120 ชั่วโมง (รัน: `13_dimension_pitfalls.py`)

ที่ระดับ table `order_ts` ล่าสุดคือ 29 ตุลาคม 23:59 ถามตอน 1 พฤศจิกายน 08:00 ห่างกัน 56 ชั่วโมง ถ้าสัญญาไว้ 24 ชั่วโมง สัญญาก็ผิด ทั้งที่ row 98.68% มาตรงเวลา (รัน: `02_dimensions.py`)

</Step>

## ความหมายที่ถูกเข้าใจผิดบ่อย

<Callout type="warn" title="1. เวลาที่ load ไม่ใช่เวลาที่เหตุการณ์เกิด">
`ingested_at` ใหม่สุดใน `orders` คือ 1 พฤศจิกายน 02:11 ซึ่งก่อนเวลา as-of 5 ชั่วโมง 49 นาที: pipeline รันเมื่อเช้านี้ แต่ order ใหม่สุดใน table เก่า 56 ชั่วโมง (รัน: `13_dimension_pitfalls.py`) check freshness ที่อ่านเวลา load หรือ "job รันเสร็จล่าสุดเมื่อไร" จะผ่าน ส่วน check ที่อ่านเวลาเกิดเหตุการณ์จะตก ให้ระบุว่า rule ของคุณอ่าน column ไหน สองค่านี้แยกจากกันเมื่อต้นทางหยุดส่งข้อมูลแต่ pipeline ยังรันต่อบนความว่างเปล่า
</Callout>

**2. "ทันเวลา" ไม่มีความหมายถ้าไม่มี volatility** bar 24 ชั่วโมงเหมาะกับ order ถ้าใช้ bar เดียวกันกับ table ของ country code จะ alarm ทุกวันโดยไม่มีเหตุ และถ้าใช้กับ feed ราคาก็หลวมเกินไป หนังสืออธิบายด้วยราคาหุ้น: ตอนตลาดเปิดมันอัปเดตบ่อย พอตลาดปิดข้อมูลไม่เปลี่ยนแต่ยัง current (หนังสือ: DMBOK2 Table 29 หน้า 459) ให้ตั้ง bar ต่อ data set ร่วมกับ consumer ของมัน ([บท 7](/data-quality/monitoring/#freshness-ช่วงที่ไม่มีข้อมูลยาวแค่ไหนจึงเป็นเหตุ))

**3. ความเงียบอาจถูกต้อง** ตัวอย่างเดียวกันหมายความว่า alarm freshness ในวันหยุด สำหรับต้นทางที่ไม่ทำงานวันหยุด เป็น alarm เท็จ ให้ใส่ปฏิทินลงใน rule ไม่เช่นนั้น alarm จะสอนให้คนเลิกสนใจมัน

**4. row ที่มาช้าทำให้ตัวเลขที่รายงานไปแล้วเปลี่ยน** order 40 รายการมาถึง warehouse หลังถูกสั่งเกินหนึ่งวัน บางรายการช้าถึง 5 วัน ยอดรายวันที่คำนวณก่อน row เหล่านั้นมาถึงต่ำเกินไป และเมื่อมันมา ยอดก็เปลี่ยน ให้ตัดสินใจว่ารายงานของคุณจะ restate หรือ freeze และบอกคนที่อ่านมัน

**5. timeliness ครอบคลุมมากกว่าจำนวนชั่วโมง** Ten Steps มอง dimension นี้ที่จังหวะเวลาของเหตุการณ์ขณะข้อมูลเคลื่อนผ่าน life cycle และเช็กว่า synchronization ที่ตกลงกันไว้เกิดขึ้นจริง เช่น พนักงานขายต้อง sync ฐานข้อมูลในเครื่องมือถือกับฐานข้อมูลกลางทุกเย็นก่อน 6 โมง (หนังสือ: Ten Steps บทที่ 4 หน้า 148 ถึง 151) นั่นเป็นข้อความเกี่ยวกับ process และจำนวนชั่วโมงตามมาจากมัน

</Step>

## ที่มักสับสนด้วย

| ดูคล้ายกับ | แยกอย่างไร | ใน data ของเรา |
|---|---|---|
| Accuracy | ค่าเก่าอาจ accurate สำหรับช่วงเวลาที่มันอธิบาย ค่าใหม่ก็ผิดได้ | ยอด order ถูกต้องเป๊ะและเก่า 56 ชั่วโมง |
| Completeness | row ล่าสุดที่หายดูเป็นทั้งปัญหา freshness และ completeness | วันล่าสุดยังไม่มี row |
| Consistency ข้ามเวลา | "temporal consistency" ของหนังสือเทียบค่าหนึ่งในสองจุดเวลา timeliness เทียบข้อมูลกับนาฬิกา | ดู[หน้า consistency](/data-quality/dimensions/consistency/#ความหมายที่ถูกเข้าใจผิดบ่อย) และ [reasonability](/data-quality/dimensions/reasonability/#ความหมายที่ถูกเข้าใจผิดบ่อย) |

</Step>

<Step>

## เช็กตัวเอง

- ใน table หนึ่งที่คุณดูแล check freshness อ่าน timestamp ตัวไหน: เวลาที่เหตุการณ์เกิด หรือเวลาที่ pipeline เขียน
- table ไหนใน platform ของคุณที่เปลี่ยนไม่บ่อย และมี bar freshness เดียวกับ table ที่เปลี่ยนทุกนาทีหรือเปล่า
- รายงานรันตอน 8 โมงและถูกต้อง ถึงเที่ยง query เดิมให้ตัวเลขต่างไป นั่นคือ defect ไหม

</Step>
