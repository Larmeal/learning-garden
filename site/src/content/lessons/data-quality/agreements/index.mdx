## ทำไมต้องมีสัญญา

กฎคุณภาพที่เขียนฝั่งผู้ใช้ตรวจได้ว่าข้อมูลเสีย แต่ไม่ได้บอกว่า**ใครต้องรับผิดชอบ** หรือเมื่อผู้ผลิตจะเปลี่ยนข้อมูลควรแจ้งใคร DMBOK2 พูดถึงสองระดับ

- **SLA ด้านคุณภาพข้อมูล**: ระบุความคาดหวังของการตอบสนองและการแก้ไขปัญหาในแต่ละระบบ (หนังสือ: DMBOK2 §2.7.4)
- **ข้อตกลงการแบ่งปันข้อมูล** (data sharing agreement): ระบุว่าข้อมูลใดแบ่งปันได้และภายใต้เงื่อนไขใด ผู้รับผิดชอบสภาพแวดล้อมแบ่งปันมีพันธะต่อผู้ใช้ปลายทางให้ข้อมูลคุณภาพสูง และพึ่งพาระบบต้นทาง จึงควรมี SLA และ metric วัดความพร้อมใช้และคุณภาพ มีกระบวนการแก้ที่ต้นเหตุ และมีวิธีสื่อสารมาตรฐานเมื่อมีปัญหา (หนังสือ: DMBOK2 บท Reference and Master Data §4.4)

*Building Medallion Architectures* ใช้คำว่า **data contract** สำหรับเรื่องเดียวกันในโลกสมัยใหม่

</Step>

## data contract คืออะไร และข้อควรระวังเรื่องคำนี้

หนังสือนิยามว่า data contract คือข้อตกลงอย่างเป็นทางการระหว่างผู้ผลิตกับผู้ใช้ข้อมูล ระบุรูปแบบข้อมูล คุณภาพ ความพร้อมใช้ นโยบายความปลอดภัย และความรับผิดชอบของแต่ละฝ่าย สัญญาเน้น **ส่วนต่อประสาน** (interface) ของข้อมูล ส่วน data product คือนิยามและเนื้อหาของข้อมูลเอง (หนังสือ: Medallion ch.12)

หนังสือเตือนไว้ตรงๆ ว่า **คำนี้กำกวม ไม่มีนิยามมาตรฐานในอุตสาหกรรม** องค์กรจึงต้องนิยามคำนี้ให้ชัดภายในองค์กร ไม่เช่นนั้นแต่ละคนจะเข้าใจต่างกัน และสัญญาไม่ใช่ใช้ได้กับทุกที่ ส่วนใหญ่เป็นเรื่องของการควบคุมการไหลของข้อมูล เก็บเป็น metadata ในแพลตฟอร์ม

หนังสือยกวิธีเก็บสัญญาหลายแบบ: ในแคตตาล็อก (เช่น Microsoft Purview, Unity Catalog), ใน metastore ที่สร้างเอง, เป็นไฟล์ YAML พร้อม GitOps, และตามข้อกำหนดเปิด เช่น Open Data Contract Standard และ Data Contract Specification (หนังสือ: Medallion ch.12) บทนี้ใช้แบบ YAML ใน Git เพราะอ่านง่ายและตรวจด้วยโค้ดได้ในแบบฝึก

</Step>

## สัญญาฉบับตัวอย่าง

ไฟล์ `contracts/orders.v1.yaml` มีสิ่งที่ DMBOK2 §2.7.4 ระบุว่า SLA ควรมี (ข้อมูลที่ครอบคลุม ผลกระทบ มิติและความคาดหวัง วิธีวัด เกณฑ์ ผู้ที่ต้องได้รับแจ้ง กรอบเวลา การยกระดับ) บวกส่วน schema ตามแบบ YAML ของ Medallion (**การเลือกรวมกันเป็นของผู้เขียน ตัวเลขทั้งหมดเป็นตัวอย่าง**)

```yaml
dataset: orders
version: 1
owner: orders-platform
consumers: [finance, marketing]
purpose: Daily revenue reporting and customer campaigns
schema:
  - {name: order_id,    type: BIGINT, nullable: false, unique: true}
  - {name: customer_id, type: BIGINT, nullable: false}
  - {name: order_ts,    type: TIMESTAMP, nullable: false}
  - {name: status,      type: VARCHAR, nullable: false, allowed: [PLACED, SHIPPED, CANCELLED]}
  - {name: total_amount, type: DOUBLE, nullable: false}
  - {name: shipped_ts,  type: TIMESTAMP, nullable: true}
quality:
  rules: [ORD-ID-UNIQUE, ORD-CUST-POPULATED, ORD-CUST-EXISTS, ORD-TOTAL-MATCHES-PAID]
freshness: {column: order_ts, max_age_hours: 24}
on_breach: {notify: "#orders-data", respond_within_hours: 2, resolve_within_business_days: 1}
```

(ตัดบางคอลัมน์ออกเพื่อให้สั้น ไฟล์เต็มอยู่ใน repo) สังเกตว่า `quality.rules` ชี้ไปที่ id ในทะเบียนกฎของบท 4 สัญญาไม่ได้เขียนกฎซ้ำ แต่ระบุว่ากฎไหนคือคำสัญญาของชุดข้อมูลนี้

</Step>

## ตรวจข้อมูลเทียบกับสัญญา

ฟังก์ชันใน `dqcontract.py` ตรวจสามส่วน (รัน: `06_contract.py`)

**1. Schema** ได้สองข้อ

```text
column order_id must be unique but has 20 extra rows
column customer_id must not be null but has 15 nulls
```

ชนิดคอลัมน์และชื่อตรงสัญญาทั้งหมด จึงไม่มีรายงานเรื่องนั้น

**2. กฎคุณภาพที่สัญญาอ้าง** ไม่ผ่านทั้งสี่

| กฎ | ไม่ผ่าน% | ยอมได้% |
|---|---:|---:|
| ORD-CUST-POPULATED | 0.50 | 0.0 |
| ORD-ID-UNIQUE | 0.66 | 0.0 |
| ORD-CUST-EXISTS | 1.00 | 0.1 |
| ORD-TOTAL-MATCHES-PAID | 1.38 | 0.1 |

**3. ความสด** คำสั่งซื้อล่าสุดอายุ 56.0 ชั่วโมง สัญญาให้ไม่เกิน 24 ชั่วโมง ผิดสัญญา

เมื่อละเมิด สัญญาระบุไว้แล้วว่าใครต้องทำอะไร: แจ้งช่อง `#orders-data` ตอบสนองภายใน 2 ชั่วโมง แก้ภายใน 1 วันทำการ นี่คือส่วนที่ต่างจาก "กฎที่ล้ม" เฉยๆ

</Step>

## เปลี่ยนสัญญาอย่างไรไม่ให้ใครพัง

ผู้ผลิตแก้ข้อมูลได้เสมอ แต่ผู้ใช้บางคนจะพังเมื่อผู้ผลิตแก้ ในแบบฝึกเทียบ `orders.v1.yaml` กับ `orders.v2.yaml` และจัดประเภทความต่างจากมุมของผู้ใช้ที่อ่านข้อมูล (**เกณฑ์การจัดประเภทเป็นของผู้เขียน ไม่ใช่มาตรฐาน**)

| ความต่าง | ประเภท | เหตุผล |
|---|---|---|
| `total_amount` เปลี่ยนชื่อเป็น `amount_total` | ทำให้พัง | query ที่เลือกชื่อเดิมล้มทันที |
| `customer_id` เปลี่ยนจาก BIGINT เป็น VARCHAR | ทำให้พัง | join กับตารางลูกค้าต้อง cast |
| `order_ts` จาก not null เป็น null ได้ | ทำให้พัง | ผู้ใช้เคยพึ่งพาว่าไม่ว่าง |
| `status` เพิ่มค่า `RETURNED` | ต้องถามผู้ใช้ | โค้ดที่ครอบคลุมสามค่าอาจพลาดค่าใหม่ |
| เพิ่มคอลัมน์ `channel` (ไม่บังคับ) | ปลอดภัย | ไม่กระทบ query ที่เลือกตามชื่อ |
| เพิ่มคอลัมน์ `currency` (บังคับ) | ปลอดภัย | ภาระตกที่ผู้ผลิต |

ผลจาก `diff()`: 3 ข้อทำให้พัง, 1 ข้อต้องถาม, 2 ข้อปลอดภัย

## บังคับสัญญาแบบไหน: ทดสอบหลังโหลด หรือปฏิเสธก่อนโหลด

Medallion บรรยายสัญญาในสองรูปแบบที่ต่างกันตรงจุดที่บังคับ (หนังสือ: Medallion ch.12)

- **สัญญาแบบโครงสร้างของข้อมูลที่ผลิต**: dbt เรียกว่า "model contract" ระบุ schema ชนิดคอลัมน์ และข้อบังคับของ model **ต่างจาก test ตรงที่ถ้าตรรกะหรือข้อมูลขาเข้าไม่ตรงสัญญา model จะ build ไม่ผ่าน** ไม่ใช่ build แล้วค่อยแจ้งว่าผิด
- **สัญญาตอนนำข้อมูลเข้า**: ข้อมูลที่เข้ามาต้องตรงรูปแบบ schema และคุณภาพที่สัญญาไว้ ถ้าไม่ตรงก็ปฏิเสธ คล้าย SLA ในงานซอฟต์แวร์

แบบฝึกเทียบสองวิธีเมื่อผู้ผลิตเปลี่ยน `total_amount` เป็น `amount_total` แล้วส่งชุดข้อมูลมา

| วิธี | ผล |
|---|---|
| ทดสอบหลังโหลด | ตารางมีรูปแบบใหม่ไปแล้ว การทดสอบบอกว่า `column total_amount is missing` และ `column amount_total is not in the contract` |
| ปฏิเสธก่อนโหลด | `enforce_on_ingest()` ปฏิเสธชุดข้อมูล ตารางไม่ถูกแตะ เหตุผล: `customer_id arrived as VARCHAR, expected BIGINT; missing column total_amount` |

ปฏิเสธก่อนโหลดปกป้องผู้ใช้ได้มากกว่า แต่ก็ทำให้ผู้ผลิตรู้สึกถึงสัญญาเร็วกว่า และต้องมีช่องทางให้แก้และส่งใหม่ ทางที่เหมาะขึ้นกับว่าผู้ใช้ทนข้อมูลชุดที่พังได้แค่ไหน (บท 5 เรื่อง intrusive กับ nonintrusive)

(ในแบบฝึกส่วน "ทดสอบหลังโหลด" ใช้ตารางว่างที่สร้างใหม่ด้วยชื่อคอลัมน์ใหม่เพื่อสาธิตข้อความของการทดสอบ ไม่ได้โหลดข้อมูลจริง)

<Callout type="warn" title="สัญญาไม่แก้ปัญหาด้านวัฒนธรรม">
DQF เตือนเรื่อง SLA ว่า การตั้ง SLA เพียงเพื่อตั้ง ถ้าไม่มีการลงทุนและความรับผิดชอบที่จะทำให้ได้ ทำให้ทีมอยู่ในสถานะแย่กว่าเดิม SLA ต้องได้รับความเห็นพ้องจากผู้ผลิต วิศวกร นักวิเคราะห์ และผู้ใช้ก่อน (หนังสือ: DQF ch.5) สัญญาที่ผู้ผลิตไม่รู้ว่ามีอยู่ ก็เป็นแค่ไฟล์ YAML
</Callout>

## เช็กตัวเอง

- ผู้ผลิตอยากเปลี่ยนชนิดคอลัมน์จาก INT เป็น BIGINT ควรจัดเป็นประเภทไหนในกฎของคุณ และใครต้องรู้ก่อน
- สัญญาของชุดข้อมูลที่คุณดูแลอยู่ มีข้อใดบ้างที่อยู่ในหัวคน ไม่ได้เขียนไว้ที่ไหน
- ถ้าทีมใหม่ถามว่า "data contract ของคุณหมายถึงอะไร" ในหนึ่งประโยค คุณตอบอย่างไร

</Step>
