## ทำไมต้องมี Contract

Data Quality Rule ที่เขียนไว้ฝั่ง Consumer ตรวจได้ว่าข้อมูลเสีย แต่ไม่ได้บอกเราว่า**ใครต้องรับผิดชอบ** และไม่ได้บอกด้วยว่าเมื่อ Producer จะเปลี่ยนข้อมูล ควรแจ้งใคร สำหรับเรื่องนี้ DMBOK2 พูดถึงข้อตกลงไว้สองระดับ

- ระดับแรกคือ **Data Quality SLA** ซึ่งระบุความคาดหวังของการตอบสนองและการแก้ไขปัญหาในแต่ละระบบ (หนังสือ: DMBOK2 หัวข้อ 2.7.4 หน้า 483 ถึง 484)
- ระดับที่สองคือ **Data Sharing Agreement** ซึ่งระบุว่าข้อมูลใดแบ่งปันได้และภายใต้เงื่อนไขใด โดยผู้รับผิดชอบสภาพแวดล้อมแบ่งปันมีพันธะต่อ Consumer ปลายทางที่จะต้องให้ข้อมูลคุณภาพสูง และพึ่งพาระบบต้นทาง จึงควรมี SLA และ Metric วัด Availability และคุณภาพ มีกระบวนการแก้ที่ต้นเหตุ และมีวิธีสื่อสารมาตรฐานเมื่อมีปัญหา (หนังสือ: DMBOK2 บท Reference and Master Data หัวข้อ 4.4 หน้า 377)

ส่วน *Building Medallion Architectures* ใช้คำว่า **Data Contract** เรียกเรื่องเดียวกันนี้ในโลกสมัยใหม่

</Step>

## Data Contract คืออะไร และข้อควรระวังเรื่องคำนี้

หนังสือนิยามว่า Data Contract คือข้อตกลงอย่างเป็นทางการระหว่าง Producer กับ Consumer ของข้อมูล โดยระบุ Format ของข้อมูล คุณภาพ Availability นโยบายความปลอดภัย และความรับผิดชอบของแต่ละฝ่าย Contract จะเน้นที่ **Interface** ของข้อมูล ส่วน Data Product คือนิยามและเนื้อหาของข้อมูลเอง (หนังสือ: Medallion บทที่ 12 หน้า 329 ถึง 333)

หนังสือเตือนไว้ตรง ๆ ว่าคำนี้กำกวมและไม่มีนิยามมาตรฐานในอุตสาหกรรม องค์กรจึงต้องนิยามเอง ไม่อย่างนั้นแต่ละคนจะอ่านความหมายต่างกันไป นอกจากนี้ Contract ก็ใช้ไม่ได้กับทุกที่ โดยส่วนใหญ่จะควบคุมการไหลของข้อมูล และเก็บเป็น Metadata ใน Platform

*Driving Data Quality with Data Contracts* ของ Andrew Jones ให้นิยามที่เป็นรูปธรรมไว้แบบหนึ่ง คือ Interface ที่ตกลงกันระหว่างผู้สร้างข้อมูลกับ Consumer ซึ่งกำหนด Expectation ของข้อมูล บอกว่าต้อง Govern อย่างไร และทำให้การสร้างข้อมูลคุณภาพเป็นเรื่องที่ทำโดยตั้งใจ (หนังสือ: Contracts บทที่ 2 หน้า 22 ถึง 31) หนังสือสองเล่มนี้เห็นตรงกันในส่วนที่สำคัญ คือ Producer เป็นคนให้สัญญา และ Consumer สามารถสร้างงานต่อบนสัญญานั้นได้ สำหรับฉบับของ Jones เราจะไล่ให้ละเอียดอีกทีในหน้า [Data Contracts in Practice](/data-quality/agreements/contracts-in-practice/) ซึ่งเป็นหน้าย่อยของบทนี้

หนังสือยกวิธีเก็บ Contract ไว้หลายแบบ ได้แก่เก็บใน Catalog (เช่น Microsoft Purview, Unity Catalog), เก็บใน Metastore ที่สร้างเอง, เก็บเป็นไฟล์ YAML พร้อม GitOps หรือเก็บตาม Specification เปิด เช่น Open Data Contract Standard และ Data Contract Specification (หนังสือ: Medallion บทที่ 12 หน้า 329 ถึง 332) สำหรับบทนี้เราใช้แบบ YAML ใน Git เพราะอ่านง่าย และตรวจด้วยโค้ดได้ในแบบฝึก

</Step>

## Contract ฉบับตัวอย่าง

ไฟล์ `contracts/orders.v1.yaml` มีสิ่งที่ DMBOK2 หัวข้อ 2.7.4 หน้า 483 ถึง 484 ระบุว่า SLA ควรมี (ข้อมูลที่ครอบคลุม Impact Dimension และความคาดหวัง วิธีวัด Threshold ผู้ที่ต้องได้รับแจ้ง กรอบเวลา การ Escalate) และเพิ่มส่วน Schema ตามแบบ YAML ของ Medallion เข้าไปด้วย (**การเลือกรวมกันเป็นของผู้เขียน ตัวเลขทั้งหมดเป็นตัวอย่าง**)

```yaml
dataset: orders
version: 1
owner: orders-platform
consumers: [finance, marketing]
purpose: Daily revenue reporting and customer campaigns
schema:
  - {name: order_id,    type: BIGINT, nullable: false, unique: true}
  - {name: customer_id, type: BIGINT, nullable: false}
  - {name: order_ts,    type: TIMESTAMP, nullable: false}
  - {name: status,      type: VARCHAR, nullable: false, allowed: [PLACED, SHIPPED, CANCELLED]}
  - {name: total_amount, type: DOUBLE, nullable: false}
  - {name: shipped_ts,  type: TIMESTAMP, nullable: true}
quality:
  rules: [ORD-ID-UNIQUE, ORD-CUST-POPULATED, ORD-CUST-EXISTS, ORD-TOTAL-MATCHES-PAID]
freshness: {column: order_ts, max_age_hours: 24}
on_breach: {notify: "#orders-data", respond_within_hours: 2, resolve_within_business_days: 1}
```

(เราตัดบาง Column ออกเพื่อให้สั้น ไฟล์เต็มอยู่ใน Repo) ส่วน `quality.rules` ชี้ไปที่ id ใน Rule Registry ของ[บท 4](/data-quality/rule-design/#rule-registry-query-พร้อมเจ้าของ-threshold-และ-impact) Contract จึงไม่ต้องเขียน Rule ซ้ำ เพียงแค่ระบุว่า Rule ไหนคือคำสัญญาของ Dataset นี้

</Step>

## ตรวจข้อมูลเทียบกับ Contract

ฟังก์ชันใน `dqcontract.py` ตรวจข้อมูลสามส่วน (รัน: `06_contract.py`)

**1. Schema** ตรวจเจอสองข้อ

```text
column order_id must be unique but has 20 extra rows
column customer_id must not be null but has 15 nulls
```

ส่วน Type และชื่อของ Column ตรงกับ Contract ทั้งหมด เราจึงไม่เห็นรายงานเรื่องนั้น

**2. Quality Rule ที่ Contract อ้างถึง** ไม่ผ่านทั้งสี่ข้อ

| Rule | ไม่ผ่าน% | ยอมได้% |
|---|---:|---:|
| ORD-CUST-POPULATED | 0.50 | 0.0 |
| ORD-ID-UNIQUE | 0.66 | 0.0 |
| ORD-CUST-EXISTS | 1.00 | 0.1 |
| ORD-TOTAL-MATCHES-PAID | 1.38 | 0.1 |

**3. Freshness** Order ล่าสุดมีอายุ 56.0 ชั่วโมง ในขณะที่ Contract ให้ไว้ไม่เกิน 24 ชั่วโมง จึงถือว่าผิดสัญญา

เมื่อมีการละเมิด Contract ได้ระบุไว้แล้วว่าใครต้องทำอะไร คือแจ้งที่ Channel `#orders-data` ตอบสนองภายใน 2 ชั่วโมง และแก้ภายใน 1 วันทำการ ซึ่งต่างจาก Rule ที่ล้มไปเฉย ๆ เพราะเมื่อ Contract ถูกละเมิด จะมีชื่อคนรับเรื่องรออยู่แล้ว

</Step>

## เปลี่ยน Contract อย่างไรไม่ให้ใครพัง

Producer แก้ข้อมูลได้เสมอ แต่ Consumer บางคนจะพังเมื่อ Producer แก้ ดังนั้นในแบบฝึกเราจึงเทียบ `orders.v1.yaml` กับ `orders.v2.yaml` แล้วจัดประเภทความต่างจากมุมของ Consumer ที่อ่านข้อมูล (เกณฑ์นี้เขียนสำหรับเส้นทางนี้ แต่บางส่วนตามหนังสือ: การเปลี่ยนชื่อและการเปลี่ยน Type เป็น Breaking ตามตัวอย่างใน Contracts บทที่ 6 หน้า 89 ถึง 91 ส่วนกลุ่ม `review` กับการผ่อน `nullable` เป็นการตัดสินของผู้เขียน)

| ความต่าง | ประเภท | เหตุผล |
|---|---|---|
| `total_amount` เปลี่ยนชื่อเป็น `amount_total` | Breaking | Query ที่เลือกชื่อเดิมล้มทันที |
| `customer_id` เปลี่ยนจาก BIGINT เป็น VARCHAR | Breaking | Join กับ Table Customers ต้อง Cast |
| `order_ts` จาก Not Null เป็น Nullable | Breaking | Consumer เคยพึ่งพาว่าไม่ว่าง |
| `status` เพิ่มค่า `RETURNED` | Review (ต้องถาม Consumer) | โค้ดที่ครอบคลุมสามค่าอาจพลาดค่าใหม่ |
| เพิ่ม Column `channel` (ไม่บังคับ) | Safe | ไม่กระทบ Query ที่เลือกตามชื่อ |
| เพิ่ม Column `currency` (บังคับ) | Safe | ภาระตกที่ Producer |

ผลที่ได้จาก `diff()` คือ 3 ข้อเป็น Breaking, 1 ข้อเป็น Review และ 2 ข้อเป็น Safe

## บังคับ Contract แบบไหน: Test หลัง Load หรือปฏิเสธก่อน Load

Medallion บรรยาย Contract ในสองรูปแบบที่ต่างกันตรงจุดที่บังคับ (หนังสือ: Medallion บทที่ 12 หน้า 329 ถึง 333)

- แบบแรกคือ Contract ที่เป็นโครงสร้างของข้อมูลที่ผลิต ซึ่ง Dbt เรียกว่า "Model Contract" โดยระบุ Schema, Type ของ Column และ Constraint ของ Model **ต่างจาก Test ตรงที่ถ้าตรรกะหรือข้อมูลขาเข้าไม่ตรง Contract Model จะ Build ไม่ผ่าน** แทนที่จะ Build เสร็จแล้วค่อยแจ้งว่าผิด
- แบบที่สองคือ Contract ตอนนำข้อมูลเข้า ซึ่งข้อมูลที่เข้ามาต้องตรงกับ Format, Schema และคุณภาพที่สัญญาไว้ ถ้าไม่ตรงก็จะถูกปฏิเสธ คล้ายกับ SLA ในงานซอฟต์แวร์

แบบฝึกเทียบสองวิธีเมื่อ Producer เปลี่ยน `total_amount` เป็น `amount_total` แล้วส่ง Dataset มา

| วิธี | ผล |
|---|---|
| Test หลัง Load | Table มี Format ใหม่ไปแล้ว และ Test บอกว่า `column total_amount is missing` และ `column amount_total is not in the contract` |
| ปฏิเสธก่อน Load | `enforce_on_ingest()` ปฏิเสธ Dataset โดย Table ไม่ถูกแตะ และให้เหตุผลว่า `customer_id arrived as VARCHAR, expected BIGINT; missing column total_amount` |

การปฏิเสธก่อน Load ปกป้อง Consumer ได้มากกว่า แต่ในทางกลับกัน Producer ก็จะรู้สึกถึง Contract เร็วกว่าด้วย และเราต้องมีช่องทางให้แก้แล้วส่งมาใหม่ ส่วนว่าทางไหนเหมาะกว่าก็ขึ้นอยู่กับว่า Consumer ทนข้อมูลชุดที่พังได้แค่ไหน ([บท 5](/data-quality/checkpoints/#เมื่อไม่ผ่าน-ปล่อยผ่าน-quarantine-หรือหยุด) เรื่อง Intrusive กับ Nonintrusive)

(ในแบบฝึก ส่วน "Test หลัง Load" ใช้ Table ว่างที่สร้างใหม่ด้วยชื่อ Column ใหม่ เพื่อสาธิตข้อความของ Test เท่านั้น ไม่ได้ Load ข้อมูลจริง)

<Callout type="warn" title="Contract ไม่แก้ปัญหาด้านวัฒนธรรม">
DQF เตือนเรื่อง SLA ว่า ถ้าตั้ง SLA ขึ้นมาเพียงเพื่อให้มี โดยไม่มีการลงทุนและความรับผิดชอบที่จะทำให้ทำได้จริง ทีมก็จะอยู่ในสถานะที่แย่กว่าเดิม SLA จึงต้องได้รับความเห็นพ้องจาก Producer, Engineer, Analyst และ Consumer ก่อน (หนังสือ: DQF บทที่ 5 หน้า 135 ถึง 138) Contract ที่ Producer ไม่รู้ว่ามีอยู่ ก็เป็นแค่ไฟล์ YAML
</Callout>

## เช็กตัวเอง

- Producer อยากเปลี่ยน Type ของ Column จาก INT เป็น BIGINT ควรจัดเป็นประเภทไหนใน Rule ของคุณ และใครต้องรู้ก่อน
- Contract ของ Dataset ที่คุณดูแลอยู่ มีข้อใดบ้างที่อยู่ในหัวคน ไม่ได้เขียนไว้ที่ไหน
- ถ้าทีมใหม่ถามว่า "Data Contract ของคุณหมายถึงอะไร" ในหนึ่งประโยค คุณตอบอย่างไร

</Step>
