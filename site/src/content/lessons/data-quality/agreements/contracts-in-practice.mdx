## ใครต้องรับสายเมื่อต้นทางเปลี่ยน

ใน Data Platform จำนวนมาก Table ดิบของ Service ถูกคัดลอกเข้า Warehouse ตรง ๆ ด้วย ELT Tool หรือ Change Data Capture ซึ่งทีมที่เป็นเจ้าของ Service มักไม่รู้ว่า Table ของตัวเองเป็น Input ของใครบางคน และเมื่อไม่มีใครขอคำสัญญาจากเขา เขาก็ไม่เคยให้ (หนังสือ: Contracts บทที่ 1 หน้า 14 ถึง 17)

ดังนั้นทีม Data Engineering จึงต้องกลายเป็นคนรับผิดชอบความน่าเชื่อถือของข้อมูล ทั้งที่ตัวเองไม่ได้เป็นคนกำหนดรูปร่างของมัน เมื่อต้นทางเปลี่ยน ถ้าเป็นการเปลี่ยน Schema Pipeline จะล้มดัง ๆ แต่ถ้าข้อมูลหรือตรรกะการอ่านเปลี่ยน มันจะพังแบบเงียบ ๆ และคนที่เห็นก่อนมักเป็นคนอ่านรายงาน วิธีแก้ที่เจอบ่อยคือเติม `CASE` หรือ `IFNULL` เข้าไปใน Pipeline อีกอัน ซึ่งทำให้ Pipeline เปราะขึ้นเรื่อย ๆ (หนังสือ: Contracts บทที่ 1 หน้า 14 ถึง 17)

เรื่องใน[บท 9](/data-quality/incidents/#respond-ใครคุม-ใครรู้)ก็เป็นรูปเดียวกัน คือ `raw_orders` ป้อน `stg_orders` แล้วป้อน `daily_revenue` ที่มี Consumer สองราย ส่วน Contract จะย้ายคำสัญญาไปอยู่ที่จุดที่ข้อมูลถูกสร้าง หนังสือเทียบให้เห็นว่า ถ้า Pipeline หลายตัวอ่าน Table ดิบ ข้อมูลเสียชุดเดียวกันจะกระทบทุกตัว แต่ถ้าอ่านผ่าน Contract เราจะแก้ที่เดียวก็พอ (หนังสือ: Contracts บทที่ 4 หน้า 61 ถึง 64)

</Step>

## นิยามมีสี่ส่วน

Jones นิยาม Data Contract ว่าเป็น Interface ที่ตกลงกันระหว่างผู้สร้างข้อมูล (Generator) กับ Consumer โดยกำหนด Expectation ของข้อมูล บอกว่าต้อง Govern อย่างไร และทำให้การสร้างข้อมูลคุณภาพเป็นเรื่องที่ทำโดยตั้งใจ (Explicit) (หนังสือ: Contracts บทที่ 2 หน้า 22 ถึง 31) คำทั้งสี่คำนี้ทำหน้าที่ต่างกัน

| คำ | ขออะไร | อยู่ตรงไหนใน `orders.v1.yaml` (การจับคู่เป็นของผู้เขียน) |
|---|---|---|
| Interface | ทางอ่านข้อมูลที่เผยแพร่แล้ว แยกจาก Table ภายในของ Service | Dataset `orders` และ `schema` |
| Expectation | โครงสร้าง ค่าที่ถูกต้อง ความทันเวลาและความพึ่งพาได้ และเจ้าของ | `schema`, `quality.rules`, `freshness`, `owner` |
| Governance | ข้อมูลเป็นข้อมูลส่วนบุคคลไหม จัดชั้นความลับอย่างไร เก็บนานแค่ไหน | v1 ไม่มี หนังสือระบุว่าเป็น Field ที่ Contract ใส่ได้ |
| Explicit | Producer สร้างข้อมูลเพื่อ Consumer โดยตั้งใจ ไม่ใช่เปิดสิ่งที่ Service เก็บอยู่ให้ดูเฉย ๆ | การตัดสินใจว่า `orders-platform` เป็นคนเผยแพร่ Dataset นี้ |

หนังสือบอกตรง ๆ ว่าเนื้อหาส่วนใหญ่พูดถึงข้อมูลที่องค์กรสร้างเอง เพราะเป็นข้อมูลที่เราแก้ได้ ส่วนข้อมูลจากภายนอกก็ทำ Contract ได้เหมือนกัน แต่จะใกล้เคียงกับเอกสารที่ตกลงกับ Vendor หรือกฎที่เรารันเองมากกว่า (หนังสือ: Contracts บทที่ 2 หน้า 22 ถึง 23)

</Step>

## Producer-driven และ Consumer-driven

Contract แบบ Producer-driven เขียนและเป็นเจ้าของโดยคนที่สร้างข้อมูล เหมือน API ที่เป็นของ Service เบื้องหลัง ส่วน Consumer-driven เขียนโดย Consumer แล้วใช้กับข้อมูลที่ตัวเองคุมไม่ได้ หนังสือมองว่าแบบแรกเป็นทางเดียวที่ทำให้ Data Quality เป็นความรับผิดชอบของ Generator ส่วนแบบหลังมีประโยชน์กับข้อมูลที่เราคุมได้น้อย (หนังสือ: Contracts บทที่ 2 หน้า 24 ถึง 29)

ในเส้นทางนี้เรามีทั้งสองแบบ โดย Rule 14 ข้อใน[บท 4](/data-quality/rule-design/#rule-registry-query-พร้อมเจ้าของ-threshold-และ-impact) เป็นฝั่ง Consumer ที่ Analyst เขียนเพื่อปกป้องรายงาน ส่วน Contract ของ `orders` ใน[บท 6](/data-quality/agreements/#contract-ฉบับตัวอย่าง) เป็น Producer-driven เพราะ `orders-platform` เป็น Owner และเป็นคนให้สัญญา ความต่างที่สำคัญจะเห็นตอนที่การตรวจล้ม คือ Rule ฝั่ง Consumer บอกได้ว่าข้อมูลเสีย ส่วน Contract ฝั่ง Producer บอกด้วยว่าใครต้องแก้และต้องแก้เร็วแค่ไหน

</Step>

## Expectation ครอบคลุมอะไรบ้าง

หนังสือจัด Expectation ที่ Contract ตั้งได้เป็นสี่กลุ่ม (หนังสือ: Contracts บทที่ 2 หน้า 24 ถึง 29)

- กลุ่มแรกคือ**โครงสร้าง** ได้แก่ชื่อและ Type ของแต่ละ Field กับคำอธิบายว่าใช้ทำอะไร ซึ่งเสริมได้ด้วย Primary Key, Entity ที่ข้อมูลพูดถึง, หน่วยวัด, ว่า Field นั้นเป็นข้อมูลส่วนบุคคลหรือไม่ และจัดชั้นความลับอย่างไร
- กลุ่มที่สองคือ**ค่าที่ถูกต้อง** ได้แก่ช่วงค่า Format ความไม่ซ้ำ รายการที่อนุญาต และการอ้างอิง Field อื่น ซึ่งเป็นการตรวจชุดเดียวกับ[บท 2](/data-quality/dimensions/#completeness-validity-uniqueness) แต่เขียนไว้ในที่ที่ Producer รันได้ทั้งใน Test และใน Production
- กลุ่มที่สามคือ**ประสิทธิภาพและความพึ่งพาได้** หนังสือระบุสามตัวชี้วัด คือ Completeness, Timeliness และ Availability ซึ่งเรียกว่า Service Level Indicator (SLI) และวัดตรงจากระบบ ส่วน Service Level Objective (SLO) คือเปอร์เซ็นต์ในช่วงเวลาหนึ่งที่ Consumer วางใจได้ ตัวอย่างในหนังสือคือ SLO ว่า Record เก่าสุดที่ Query ได้ต้องไม่เก่ากว่า 1 ชั่วโมง
- กลุ่มที่สี่คือ**ความเป็นเจ้าของและความรับผิดชอบ** โดย Generator เป็นเจ้าของ Contract และเป็นคนตอบคำถามเรื่องมัน ส่วนฝั่ง Consumer ต้องอธิบายว่าเอาข้อมูลไปทำอะไรและต้องการระดับไหน

เหตุผลที่ควรเขียน SLO ลงไปเป็นเรื่องการใช้งานจริง เพราะถ้าเราไม่รู้ว่า Input ของเราทันเวลาแค่ไหน เราก็บอกผู้ใช้ของเราไม่ได้ว่าตัวเลขล่าสุดจะมาเมื่อไร (หนังสือ: Contracts บทที่ 2 หน้า 24 ถึง 29)

</Step>

## เมื่อต้องเปลี่ยน Contract

การเปลี่ยนจะเป็น **Non-breaking** เมื่อข้อมูลที่เขียนตาม Schema ใหม่ยังอ่านได้ด้วย Schema เก่า และกลับกันก็ได้ ตัวอย่างในหนังสือคือการเพิ่ม Field ที่ไม่บังคับ และการลบ Field ที่ไม่ได้บังคับและมีค่า Default ส่วน **Breaking** คือการเปลี่ยนที่กระทบ Consumer เดิม เช่น การลบ Field ที่บังคับ หรือการเปลี่ยน Type ของ Field (หนังสือ: Contracts บทที่ 6 หน้า 89 ถึง 91)

Non-breaking ควรทำได้ง่ายสำหรับ Producer ส่วน Breaking ควรมีต้นทุนโดยตั้งใจ คือต้องออกเวอร์ชันใหม่ คุยกับ Consumer และมีแผน Migrate โดยถ้าเป็นการเปลี่ยนเล็กที่มี Consumer หนึ่งหรือสองราย ก็อาจรันสองเวอร์ชันคู่กันสักสองสามสัปดาห์ แต่ถ้าเปลี่ยนใหญ่หรือมี Consumer มาก ก็อาจต้องรันสองเวอร์ชันนานกว่านั้นและมี Library ช่วยย้าย สิ่งสำคัญคือต้องมีแผนและตกลงกันไว้แล้ว (หนังสือ: Contracts บทที่ 6 หน้า 89 ถึง 91) หนังสือเรียกวิธีนี้ว่าการเลือกความนิ่งมากกว่าความคล่องตัว ซึ่งเป็นสิ่งที่เราต้องการ ถ้าอยากให้ Consumer สร้างงานต่อบนข้อมูลนี้

การจัดประเภทใน Lab ของ[บท 6](/data-quality/agreements/#เปลี่ยน-contract-อย่างไรไม่ให้ใครพัง)ทำตามหนังสือเท่าที่หนังสือพูดถึง คือการเปลี่ยนชื่อและการเปลี่ยน Type เป็น Breaking ตามตัวอย่างของหนังสือเอง ส่วนกลุ่ม `review` (ค่าใหม่ใน `status`) และการผ่อน `nullable` เป็นการตัดสินของผู้เขียน เพราะหนังสือไม่ได้ระบุไว้

<Callout type="try" title="ลองทำใน Repo นี้">
รัน `uv run python 12_contract_checks.py` แล้วเราจะเห็นว่า `v1 -> v2` ผ่าน Release Gate เพราะเวอร์ชันเพิ่มจาก 1 เป็น 2 แม้จะมี Breaking Change สามข้อ และเห็นว่า Gate ปฏิเสธการเปลี่ยนชุดเดียวกัน เมื่อเวอร์ชันยังเป็น 1 ส่วนการเพิ่ม Column ที่ไม่บังคับโดยไม่เปลี่ยนเวอร์ชันนั้นผ่านได้
</Callout>

## ตรวจตัวไฟล์ Contract เอง

Contract เขียนโดยคนและตั้งใจให้ทีมจัดการเองโดยไม่ต้องรอ Review จากส่วนกลาง หนังสือจึงเพิ่มการตรวจอัตโนมัติกับตัว Contract ก่อน Release (หนังสือ: Contracts บทที่ 10 หน้า 162) โดยตรวจดังนี้

- Metadata ที่จำเป็นต้องครบ ได้แก่เวอร์ชันที่ถูกต้อง, Owner และเอกสาร
- ทุก Field ต้องมีอย่างน้อยชื่อ, Type และ Description
- ถ้าฝัง Governance ไว้ Field ต้องถูกจัดประเภท และข้อมูลส่วนบุคคลต้องมีวิธี Anonymize
- ไม่ให้ใช้ Breaking Change กับ Contract ที่อยู่บน Production แล้ว ซึ่งใช้ Schema Registry บังคับได้
- ทั้งหมดนี้รันใน Continuous Integration ทุก Commit และจะ Release ได้ก็ต่อเมื่อผ่านเท่านั้น

แบบฝึกทำสองข้อแรก โดย Contract ทั้งสองไฟล์ผ่าน ส่วนสำเนาที่ลบ Owner และทำ Description หาย 2 ช่องไม่ผ่านด้วย Finding สามข้อ ข้อละหนึ่ง (รัน: `12_contract_checks.py`)

</Step>

## ตรวจข้อมูลที่จุดไหน

หนังสือแบ่งปัญหา Data Quality ออกเป็นสองชนิด คือปัญหาที่เราคาดไว้และทดสอบไว้แล้ว กับปัญหาที่เราไม่ได้คาดไว้ Schema และ Test ที่เขียนไว้ครอบคลุมได้แค่แบบแรก ส่วนแบบหลังจะเกิดขึ้นอยู่ดี โดยแต่ละอย่างเกิดไม่บ่อย แต่รวมกันแล้วเกิดสม่ำเสมอ วิธีรับมือที่หนังสือเสนอคือทำ Software ที่ไม่ล้มเพราะ Record เดียว ส่ง Record ที่ไม่ถูกต้องไปที่ Dead Letter Queue เพื่อตรวจและเล่นซ้ำหลังแก้ และใช้ Observability Tool ดูข้อมูลที่เผยแพร่แล้วว่ามีความผิดปกติไหม (หนังสือ: Contracts บทที่ 10 หน้า 163 ถึง 166)

หนังสือระบุว่าเรารันการตรวจได้สามที่

| ที่ | จับอะไร | จำกัดวงที่ต้นทางไหม | บทที่ตรงกัน |
|---|---|---|---|
| ตอน Publish (Library ที่ Producer เรียก) | ค่านอกช่วงและ Format ที่ Contract กำหนด | จำกัดได้ ไม่เขียน Record นั้น | [บท 5](/data-quality/checkpoints/#ชั้นของ-pipeline-bronze-silver) การตรวจที่ Bronze และ Quarantine |
| ใน Infrastructure (Table หรือ Topic ที่บังคับ Schema) | Type ผิด Field ขาด | จำกัดได้ ปฏิเสธการเขียน | [บท 6](/data-quality/agreements/#บังคับ-contract-แบบไหน-test-หลัง-load-หรือปฏิเสธก่อน-load) ปฏิเสธก่อน Load |
| หลัง Publish (Rule และ Observability Tool) | สิ่งที่สองที่แรกพลาด รวมถึงปัญหาที่ไม่มีใครคาด | ไม่ได้ Consumer อาจอ่านไปแล้ว | [บท 7](/data-quality/monitoring/#rule-จับสิ่งที่คาดไว้-แล้วที่เหลือล่ะ) Monitoring |

สองที่แรกเก็บปัญหาไว้ในระบบที่ผลิต ทำให้ Incident สั้นลง ส่วนที่สามเป็นทางเดียวสำหรับ Batch Pipeline ที่สร้างด้วยเครื่องมืออย่าง Dbt แต่ข้อมูลอาจถูกใช้ไปแล้วตอนที่มันจับได้ (หนังสือ: Contracts บทที่ 10 หน้า 163 ถึง 166) เราจึงควรทำทั้งสามที่

</Step>

## วัดผลเทียบ SLO

Contract ที่สัญญาว่า Timeliness 99% ต้องมีตัวเลขไว้เทียบ ในแบบฝึกเราจึงวัด SLI สองตัวบนข้อมูล Orders ทั้ง 3,020 Row แล้วเทียบกับ Objective ที่เขียนขึ้นสำหรับเส้นทางนี้

| SLI | วัดได้ | Objective | ผล |
|---|---:|---:|---|
| Completeness: Row ที่ Column Not-null ทุกตัวถูกกรอก | 99.50% | 100% | ผิดสัญญา |
| Timeliness: Row ที่ถึง Warehouse ภายใน 24 ชั่วโมงหลังสั่ง | 98.68% | 99.0% | ผิดสัญญา |

ตัวเลข 99.50% มาจาก 15 Row ที่ไม่มี `customer_id` และ 98.68% มาจาก 40 Row ที่มาช้า ซึ่งเป็น Defect ชุดเดียวกับ[บท 2](/data-quality/dimensions/#สรุปทั้ง-14-rule)เพียงแต่เรามองเป็นคำสัญญา (รัน: `12_contract_checks.py`) ตัว Objective เป็นตัวอย่างของผู้เขียน ส่วน Availability ซึ่งเป็นตัววัดที่สาม ต้องใช้ Access Log จึงไม่ได้คำนวณที่นี่

</Step>

## เรื่องการนำไปใช้

หนังสือย้ำตั้งแต่ต้นว่า Data Contract เป็นเรื่องของการเปลี่ยนวิธีที่คนทำงานกับข้อมูลมากกว่าเรื่องเครื่องมือ (หนังสือ: Contracts บทที่ 3 หน้า 41 ถึง 42) Producer ต้องรับความรับผิดชอบที่เขาอาจไม่เคยรู้ว่ามี จึงต้องเข้าใจว่าทำไม ส่วน Consumer ต้องอธิบายให้ได้ว่าต้องการอะไรและมีค่าแค่ไหนในภาษาธุรกิจ Contract ที่ทีมผู้ผลิตไม่เคยได้ยินก็เป็นแค่ไฟล์ใน Repository

<Callout type="warn" title="ข้อควรระวังเรื่องแหล่งที่มา">
ผู้เขียนเป็นคนนำ Data Contract เข้าไปใช้ที่บริษัท Fintech ของตัวเองและกำลังสนับสนุนแนวทางนี้อยู่ ตัวอย่าง Implementation ในหนังสือก็ใช้เครื่องมือเฉพาะ หน้านี้นำแนวคิดและนิยามมาใช้ แต่ไม่ได้นำเครื่องมือมาด้วย และไม่ได้ยกตัวเลขผลสำรวจใน[บทที่ 1](/data-quality/assurance-basics/) มาซ้ำ
</Callout>

</Step>

## เช็กตัวเอง

- เลือก Dataset ที่คุณใช้อยู่ ข้อมูลนั้นถูกผลิตให้คุณโดยตั้งใจ หรือคุณอ่านสำเนาของ Table ภายใน Service อยู่ ถ้าคืนนี้ Column หนึ่งเปลี่ยน Type คุณจะโทรหาใคร
- สำหรับ Dataset นั้น Timeliness, Completeness และ Availability อย่างไหนสำคัญที่สุดกับผู้ใช้ของคุณ และคุณจะเขียน Objective ไว้เท่าไร
- ทีมคุณใช้ที่ไหนใน 3 ที่ (ตอน Publish, ใน Infrastructure, หลัง Publish) ตอนนี้ และที่ไหนจะจับ Incident ครั้งล่าสุดได้เร็วกว่า

</Step>
