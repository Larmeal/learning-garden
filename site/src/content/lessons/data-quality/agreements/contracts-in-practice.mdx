## ใครต้องรับสายเมื่อต้นทางเปลี่ยน

ใน data platform จำนวนมาก table ดิบของ service ถูกคัดลอกเข้า warehouse ตรงๆ ด้วย ELT tool หรือ change data capture ทีมที่เป็นเจ้าของ service มักไม่รู้ว่า table ของตัวเองเป็น input ของใครบางคน ไม่มีใครขอคำสัญญาจากเขา เขาจึงไม่เคยให้ (หนังสือ: Contracts บทที่ 1 หน้า 14 ถึง 17)

ผลคือทีม data engineering กลายเป็นคนรับผิดชอบความน่าเชื่อถือของข้อมูลที่ตัวเองไม่ได้กำหนดรูปร่าง เมื่อต้นทางเปลี่ยน ถ้าเป็น schema change pipeline จะล้มดังๆ แต่ถ้าข้อมูลหรือตรรกะการอ่านเปลี่ยน มันจะพังเงียบๆ และคนที่เห็นก่อนมักเป็นคนอ่านรายงาน วิธีแก้ที่เจอบ่อยคือเติม `CASE` หรือ `IFNULL` เข้าไปใน pipeline อีกอัน ทำให้ pipeline เปราะขึ้นเรื่อยๆ (หนังสือ: Contracts บทที่ 1 หน้า 14 ถึง 17)

เรื่องใน[บท 9](/data-quality/incidents/#respond-ใครคุม-ใครรู้) เป็นรูปเดียวกัน: `raw_orders` ป้อน `stg_orders` แล้วป้อน `daily_revenue` ที่มี consumer สองราย contract ย้ายคำสัญญาไปอยู่ที่จุดที่ข้อมูลถูกสร้าง หนังสือเทียบให้เห็นว่าถ้า pipeline หลายตัวอ่าน table ดิบ ข้อมูลเสียชุดเดียวกันจะกระทบทุกตัว แต่ถ้าอ่านผ่าน contract จะแก้ที่เดียว (หนังสือ: Contracts บทที่ 4 หน้า 61 ถึง 64)

</Step>

## นิยามมีสี่ส่วน

Jones นิยาม data contract ว่าเป็น interface ที่ตกลงกันระหว่างผู้สร้างข้อมูล (generator) กับ consumer โดยกำหนด expectation ของข้อมูล บอกว่าต้อง govern อย่างไร และทำให้การสร้างข้อมูลคุณภาพเป็นเรื่องที่ทำโดยตั้งใจ (explicit) (หนังสือ: Contracts บทที่ 2 หน้า 22 ถึง 31) คำทั้งสี่ทำหน้าที่ต่างกัน

| คำ | ขออะไร | อยู่ตรงไหนใน `orders.v1.yaml` (การจับคู่เป็นของผู้เขียน) |
|---|---|---|
| Interface | ทางอ่านข้อมูลที่เผยแพร่แล้ว แยกจาก table ภายในของ service | dataset `orders` และ `schema` |
| Expectation | โครงสร้าง ค่าที่ถูกต้อง ความทันเวลาและความพึ่งพาได้ และเจ้าของ | `schema`, `quality.rules`, `freshness`, `owner` |
| Governance | ข้อมูลเป็นข้อมูลส่วนบุคคลไหม จัดชั้นความลับอย่างไร เก็บนานแค่ไหน | v1 ไม่มี หนังสือระบุว่าเป็น field ที่ contract ใส่ได้ |
| Explicit | producer สร้างข้อมูลเพื่อ consumer โดยตั้งใจ ไม่ใช่เปิดสิ่งที่ service เก็บอยู่ให้ดูเฉยๆ | การตัดสินใจว่า `orders-platform` เป็นคนเผยแพร่ dataset นี้ |

หนังสือบอกตรงๆ ว่าส่วนใหญ่พูดถึงข้อมูลที่องค์กรสร้างเอง เพราะเป็นข้อมูลที่แก้ได้ ข้อมูลจากภายนอกก็ทำ contract ได้ แต่จะใกล้เคียงกับเอกสารที่ตกลงกับ vendor หรือกฎที่เรารันเองมากกว่า (หนังสือ: Contracts บทที่ 2 หน้า 22 ถึง 23)

</Step>

## Producer-driven และ Consumer-driven

contract แบบ producer-driven เขียนและเป็นเจ้าของโดยคนที่สร้างข้อมูล เหมือน API ที่เป็นของ service เบื้องหลัง ส่วน consumer-driven เขียนโดย consumer แล้วใช้กับข้อมูลที่ตัวเองคุมไม่ได้ หนังสือว่าแบบแรกเป็นทางเดียวที่ทำให้ data quality เป็นความรับผิดชอบของ generator และแบบหลังมีประโยชน์กับข้อมูลที่เราคุมได้น้อย (หนังสือ: Contracts บทที่ 2 หน้า 24 ถึง 29)

ในเส้นทางนี้มีทั้งสองแบบ rule 14 ข้อใน[บท 4](/data-quality/rule-design/#rule-registry-query-พร้อมเจ้าของ-threshold-และ-impact) เป็นฝั่ง consumer ที่ analyst เขียนเพื่อปกป้องรายงาน ส่วน contract ของ `orders` ใน[บท 6](/data-quality/agreements/#contract-ฉบับตัวอย่าง) เป็น producer-driven เพราะ `orders-platform` เป็น owner และเป็นคนให้สัญญา ความต่างสำคัญตอนที่การตรวจล้ม rule ฝั่ง consumer บอกได้ว่าข้อมูลเสีย ส่วน contract ฝั่ง producer บอกด้วยว่าใครต้องแก้และต้องแก้เร็วแค่ไหน

</Step>

## Expectation ครอบคลุมอะไรบ้าง

หนังสือจัด expectation ที่ contract ตั้งได้เป็นสี่กลุ่ม (หนังสือ: Contracts บทที่ 2 หน้า 24 ถึง 29)

- **โครงสร้าง** ชื่อและ type ของแต่ละ field กับคำอธิบายว่าใช้ทำอะไร เสริมได้ด้วย primary key, entity ที่ข้อมูลพูดถึง, หน่วยวัด, field นั้นเป็นข้อมูลส่วนบุคคลหรือไม่ และจัดชั้นความลับอย่างไร
- **ค่าที่ถูกต้อง** ช่วงค่า format ความไม่ซ้ำ รายการที่อนุญาต การอ้างอิง field อื่น เป็นการตรวจชุดเดียวกับ[บท 2](/data-quality/dimensions/#completeness-validity-uniqueness) แต่เขียนไว้ในที่ที่ producer รันได้ทั้งใน test และใน production
- **ประสิทธิภาพและความพึ่งพาได้** หนังสือระบุสามตัวชี้วัด: completeness, timeliness และ availability เรียกว่า service level indicator (SLI) วัดตรงจากระบบ ส่วน service level objective (SLO) คือเปอร์เซ็นต์ในช่วงเวลาหนึ่งที่ consumer วางใจได้ ตัวอย่างในหนังสือคือ SLO ว่า record เก่าสุดที่ query ได้ต้องไม่เก่ากว่า 1 ชั่วโมง
- **ความเป็นเจ้าของและความรับผิดชอบ** generator เป็นเจ้าของ contract และตอบคำถามเรื่องมัน ส่วนของ consumer คืออธิบายว่าเอาข้อมูลไปทำอะไรและต้องการระดับไหน

เหตุผลที่ควรเขียน SLO ลงไปคือเรื่องใช้งานจริง ถ้าไม่รู้ว่า input ของเราทันเวลาแค่ไหน เราก็บอกผู้ใช้ของเราไม่ได้ว่าตัวเลขล่าสุดจะมาเมื่อไร (หนังสือ: Contracts บทที่ 2 หน้า 24 ถึง 29)

</Step>

## เมื่อต้องเปลี่ยน Contract

การเปลี่ยนเป็น **non-breaking** เมื่อข้อมูลที่เขียนตาม schema ใหม่ยังอ่านได้ด้วย schema เก่า และกลับกันก็ได้ ตัวอย่างในหนังสือคือเพิ่ม field ที่ไม่บังคับ และลบ field ที่ไม่ได้บังคับและมีค่า default ส่วน **breaking** คือการเปลี่ยนที่กระทบ consumer เดิม เช่นลบ field ที่บังคับ หรือเปลี่ยน type ของ field (หนังสือ: Contracts บทที่ 6 หน้า 89 ถึง 91)

non-breaking ควรทำได้ง่ายสำหรับ producer ส่วน breaking ควรมีต้นทุนโดยตั้งใจ คือต้องออกเวอร์ชันใหม่ คุยกับ consumer และมีแผน migrate ถ้าเป็นการเปลี่ยนเล็กที่มี consumer หนึ่งหรือสองราย อาจรันสองเวอร์ชันคู่กันสักสองสามสัปดาห์ ถ้าเปลี่ยนใหญ่หรือมี consumer มาก อาจต้องรันสองเวอร์ชันนานกว่านั้นและมี library ช่วยย้าย สิ่งสำคัญคือมีแผนและตกลงกันแล้ว (หนังสือ: Contracts บทที่ 6 หน้า 89 ถึง 91) หนังสือเรียกว่าเลือกความนิ่งมากกว่าความคล่องตัว ซึ่งเป็นสิ่งที่ต้องการถ้าอยากให้ consumer สร้างงานต่อบนข้อมูลนี้

การจัดประเภทใน lab ของ[บท 6](/data-quality/agreements/#เปลี่ยน-contract-อย่างไรไม่ให้ใครพัง) ตามหนังสือเท่าที่หนังสือพูดถึง การเปลี่ยนชื่อและการเปลี่ยน type เป็น breaking ตามตัวอย่างของหนังสือเอง ส่วนกลุ่ม `review` (ค่าใหม่ใน `status`) และการผ่อน `nullable` เป็นการตัดสินของผู้เขียน เพราะหนังสือไม่ได้ระบุ

<Callout type="try" title="ลองทำใน repo นี้">
รัน `uv run python 12_contract_checks.py` จะเห็น `v1 -> v2` ผ่าน release gate เพราะเวอร์ชันเพิ่มจาก 1 เป็น 2 แม้มี breaking change สามข้อ และเห็นว่า gate ปฏิเสธการเปลี่ยนชุดเดียวกันเมื่อเวอร์ชันยังเป็น 1 ส่วนการเพิ่ม column ที่ไม่บังคับโดยไม่เปลี่ยนเวอร์ชันผ่านได้
</Callout>

</Step>

## ตรวจตัวไฟล์ Contract เอง

contract เขียนโดยคนและตั้งใจให้ทีมจัดการเองโดยไม่ต้องรอ review จากส่วนกลาง หนังสือจึงเพิ่มการตรวจอัตโนมัติกับตัว contract ก่อน release (หนังสือ: Contracts บทที่ 10 หน้า 162)

- metadata ที่จำเป็นครบ: เวอร์ชันที่ถูกต้อง, owner, เอกสาร
- ทุก field มีอย่างน้อยชื่อ, type และ description
- ถ้าฝัง governance ไว้ field ต้องถูกจัดประเภท และข้อมูลส่วนบุคคลต้องมีวิธี anonymize
- ไม่ให้ breaking change ถูกใช้กับ contract ที่อยู่บน production แล้ว ใช้ schema registry บังคับได้
- ทั้งหมดรันใน continuous integration ทุก commit และ release ได้เมื่อผ่านเท่านั้น

แบบฝึกทำสองข้อแรก contract ทั้งสองไฟล์ผ่าน ส่วนสำเนาที่ลบ owner และทำ description หาย 2 ช่องไม่ผ่านด้วย finding สามข้อ ข้อละหนึ่ง (รัน: `12_contract_checks.py`)

</Step>

## ตรวจข้อมูลที่จุดไหน

หนังสือแบ่งปัญหา data quality เป็นที่เราคาดไว้และทดสอบไว้ กับที่เราไม่ได้คาด schema และ test ที่เขียนครอบคลุมแบบแรก แบบหลังจะเกิดอยู่ดี แต่ละอย่างเกิดไม่บ่อย รวมกันแล้วเกิดสม่ำเสมอ วิธีรับมือที่หนังสือเสนอคือทำ software ที่ไม่ล้มเพราะ record เดียว ส่ง record ที่ไม่ถูกต้องไป dead letter queue เพื่อตรวจและเล่นซ้ำหลังแก้ และใช้ observability tool ดูข้อมูลที่เผยแพร่แล้วว่ามีความผิดปกติไหม (หนังสือ: Contracts บทที่ 10 หน้า 163 ถึง 166)

หนังสือระบุสามที่ที่รันการตรวจได้

| ที่ | จับอะไร | จำกัดวงที่ต้นทางไหม | บทที่ตรงกัน |
|---|---|---|---|
| ตอน publish (library ที่ producer เรียก) | ค่านอกช่วงและ format ที่ contract กำหนด | จำกัดได้ ไม่เขียน record นั้น | [บท 5](/data-quality/checkpoints/#ชั้นของ-pipeline-bronze-silver) การตรวจที่ Bronze และ quarantine |
| ใน infrastructure (table หรือ topic ที่บังคับ schema) | type ผิด field ขาด | จำกัดได้ ปฏิเสธการเขียน | [บท 6](/data-quality/agreements/#บังคับ-contract-แบบไหน-test-หลัง-load-หรือปฏิเสธก่อน-load) ปฏิเสธก่อน load |
| หลัง publish (rule และ observability tool) | สิ่งที่สองที่แรกพลาด รวมถึงปัญหาที่ไม่มีใครคาด | ไม่ได้ consumer อาจอ่านไปแล้ว | [บท 7](/data-quality/monitoring/#rule-จับสิ่งที่คาดไว้-แล้วที่เหลือล่ะ) monitoring |

สองที่แรกเก็บปัญหาไว้ในระบบที่ผลิต ทำให้ incident สั้นลง ที่สามเป็นทางเดียวสำหรับ batch pipeline ที่สร้างด้วยเครื่องมืออย่าง dbt และข้อมูลอาจถูกใช้ไปแล้วตอนที่มันจับได้ (หนังสือ: Contracts บทที่ 10 หน้า 163 ถึง 166) นี่คือเหตุผลที่ควรทำทั้งสามที่

</Step>

## วัดผลเทียบ SLO

contract ที่สัญญาว่า timeliness 99% ต้องมีตัวเลขไว้เทียบ แบบฝึกวัด SLI สองตัวบนข้อมูล orders ทั้ง 3,020 row แล้วเทียบกับ objective ที่เขียนขึ้นสำหรับเส้นทางนี้

| SLI | วัดได้ | Objective | ผล |
|---|---:|---:|---|
| Completeness: row ที่ column not-null ทุกตัวถูกกรอก | 99.50% | 100% | ผิดสัญญา |
| Timeliness: row ที่ถึง warehouse ภายใน 24 ชั่วโมงหลังสั่ง | 98.68% | 99.0% | ผิดสัญญา |

99.50% คือ 15 row ที่ไม่มี `customer_id` และ 98.68% คือ 40 row ที่มาช้า เป็น defect ชุดเดียวกับ[บท 2](/data-quality/dimensions/#สรุปทั้ง-14-rule) ที่มองเป็นคำสัญญา (รัน: `12_contract_checks.py`) ตัว objective เป็นตัวอย่างของผู้เขียน ส่วน availability ซึ่งเป็นตัววัดที่สามต้องใช้ access log จึงไม่ได้คำนวณที่นี่

</Step>

## เรื่องการนำไปใช้

หนังสือย้ำตั้งแต่ต้นว่า data contract เป็นเรื่องของการเปลี่ยนวิธีที่คนทำงานกับข้อมูลมากกว่าเรื่องเครื่องมือ (หนังสือ: Contracts บทที่ 3 หน้า 41 ถึง 42) producer รับความรับผิดชอบที่เขาอาจไม่เคยรู้ว่ามี จึงต้องเข้าใจว่าทำไม ส่วน consumer ต้องอธิบายให้ได้ว่าต้องการอะไรและมีค่าแค่ไหนในภาษาธุรกิจ contract ที่ทีมผู้ผลิตไม่เคยได้ยินก็เป็นแค่ไฟล์ใน repository

<Callout type="warn" title="ข้อควรระวังเรื่องแหล่งที่มา">
ผู้เขียนเป็นคนนำ data contract เข้าไปใช้ที่บริษัท fintech ของตัวเองและกำลังสนับสนุนแนวทางนี้ ตัวอย่าง implementation ในหนังสือใช้เครื่องมือเฉพาะ หน้านี้เอาแนวคิดและนิยามมาใช้ ไม่เอาเครื่องมือ และไม่ได้ยกตัวเลขผลสำรวจใน[บทที่ 1](/data-quality/assurance-basics/) มาซ้ำ
</Callout>

</Step>

## เช็กตัวเอง

- เลือก dataset ที่คุณใช้อยู่ ข้อมูลนั้นถูกผลิตให้คุณโดยตั้งใจ หรือคุณอ่านสำเนาของ table ภายใน service อยู่ ถ้าคืนนี้ column หนึ่งเปลี่ยน type คุณจะโทรหาใคร
- สำหรับ dataset นั้น timeliness, completeness และ availability อย่างไหนสำคัญที่สุดกับผู้ใช้ของคุณ และคุณจะเขียน objective ไว้เท่าไร
- ทีมคุณใช้ที่ไหนใน 3 ที่ (ตอน publish, ใน infrastructure, หลัง publish) ตอนนี้ และที่ไหนจะจับ incident ครั้งล่าสุดได้เร็วกว่า
