## Bad Data ทำร้ายปลายทางจริง

ลองดูผลของ Defect ที่[บท 2](/data-quality/dimensions/#สรุปทั้ง-14-rule) ตรวจเจอ เมื่อปล่อยมันไหลไปจนถึงรายงาน "Revenue แยกตาม Country" ซึ่งทำจากการ Join Order กับ Customer (รัน: `05_checkpoints.py`)

| Country | Revenue | จำนวน Order |
|---|---:|---:|
| TH | 4,098,059.59 | 1,642 |
| Thailand | 56,526.87 | 25 |
| THA | 64,202.16 | 23 |
| th | 50,744.19 | 23 |
| ไทย | 59,145.33 | 21 |
| T.H. | 61,395.79 | 20 |
| SG | 802,996.33 | 296 |
| JP | 756,154.01 | 294 |
| US | 464,779.48 | 168 |

Revenue จาก Customer ไทยที่เขียน Country ผิด Format ห้าแบบรวม 292,014.34 หลุดจากกลุ่ม `TH` ไปอยู่ใน Row แยกของตัวเอง ใครที่อ่านรายงานนี้แล้วสรุปว่าไทยทำ Revenue 4.10 ล้าน ก็จะประมาณผิดไปราว 7% ของ Revenue ไทย และไม่มีข้อความแจ้งเตือนใดเกิดขึ้นเลย

หลักของ DMBOK2 ที่เกี่ยวข้องคือการดูแลคุณภาพตลอด Lifecycle ของข้อมูล ซึ่งหมายความว่า**ทุกข้อต่อในห่วงโซ่ต้องส่งต่อข้อมูลคุณภาพสูง** (หนังสือ: DMBOK2 หัวข้อ 1.2 หน้า 452 ถึง 453) และ DQF บอกว่าองค์กรส่วนใหญ่เห็นตรงกันว่า การจับและแก้ปัญหาตอนนำข้อมูลเข้า (Ingestion) ช่วยลดโอกาสที่ข้อมูลไม่ดีจะไหลลงปลายทาง (หนังสือ: DQF บทที่ 5 หน้า 119 ถึง 122)

## ตรวจที่ระดับไหน และทำใน Stream ได้หรือไม่

DMBOK2 Table 31 หน้า 481 แยกการวัดเป็นสามระดับความละเอียด และบอกว่าแต่ละระดับทำได้สองแบบ คือ **In-stream** ระหว่างที่ข้อมูลเดินผ่านระบบ กับ **Batch** ด้วย Query หรือเครื่องมือ Profiling บนข้อมูลที่เก็บไว้แล้ว นอกจากนี้ยังบอกว่าการวัดระดับ Dataset มักทำ In-stream ไม่ได้ เพราะต้องใช้ทั้งชุด (หนังสือ: DMBOK2 หัวข้อ 2.7.2 หน้า 479 ถึง 481)

| ระดับ | ตัวอย่าง Rule | In-stream ได้ไหม | เจอใน Dataset |
|---|---|---|---:|
| ค่าเดียว (Element) | Email มี Format a@b.c | ได้ ดูค่าเดียว | 15 |
| ทั้ง Row (Record) | shipped_ts ไม่มาก่อน order_ts | ได้ ดู Row เดียว | 10 |
| ทั้งชุด (Data Set) | order_id ไม่ซ้ำ | ไม่ได้ ต้องเห็นทั้งชุด | 20 |
| ทั้งชุด (Data Set) | Order ล่าสุดอายุไม่เกิน 24 ชั่วโมง | ไม่ได้ ต้องเห็นทั้งชุด | 1 (ผิด) |

(รัน: `05_checkpoints.py`, ตัวเลขตรงกับที่ฝังไว้ ส่วนข้อสุดท้ายนับเป็น 1 หมายถึง "ผิด")

ในทางปฏิบัติแล้ว Rule ของค่าเดียวและ Row เดียวเอาไปไว้ที่จุดรับข้อมูลได้ถูกและเร็ว แต่ Rule เรื่อง Duplicate และ Freshness ต้องรอให้มีข้อมูลครบก้อนก่อน DQF เสริมว่า ที่ขั้น Operational Transformation ซึ่งต้องการ Latency ต่ำ ควรเลือกตรวจแบบเบา เช่น เทียบ Schema เก่ากับที่เข้ามา มากกว่าการตรวจที่ใช้ทรัพยากรสูงอย่าง Data Drift (หนังสือ: DQF บทที่ 3 หน้า 54)

</Step>

## ชั้นของ Pipeline: Bronze, Silver

*Building Medallion Architectures* แบ่งข้อมูลเป็นชั้น (Layer) และบอกว่าการไล่จาก Bronze ไปถึง Gold หมายถึง Data Quality โครงสร้าง และการตรวจสอบที่ดีขึ้น (หนังสือ: Medallion บทที่ 1 หน้า 5) ส่วนหน้าที่ด้านคุณภาพของสองชั้นแรกเป็นดังนี้

| Layer | หน้าที่ด้านคุณภาพ |
|---|---|
| **Bronze** | เป็น "ด่านแรก" ของการตรวจเชิงเทคนิคและ Observability ข้อผิดพลาดที่จับได้ตรงนี้จะไม่ลามไปชั้น Silver และ Gold หนังสือแนะนำให้เก็บ Metadata ของ Schema ต้นทางไว้ เพื่อให้บังคับ Rule ตรวจได้อัตโนมัติ |
| **Silver** | ทำความสะอาดและยกระดับข้อมูล โดยทำ Format วันที่ให้เหมือนกัน บังคับ Reference Data ปรับชื่อ ลบข้อมูลซ้ำ ตรวจคุณภาพเชิงฟังก์ชัน และตัด Row คุณภาพต่ำออก แต่ยังไม่รวมกับแหล่งอื่น |

(หนังสือ: Medallion บทที่ 3 หน้า 51 ถึง 76, ส่วน Bronze Layer และ Silver Layer)

หนังสือเน้นอีกเรื่องหนึ่งว่า การทำความสะอาดทำได้อัตโนมัติตอน Load แต่ **ควรแก้ปัญหาคุณภาพที่ต้นทางที่ข้อมูลเกิด** เพื่อไม่ให้ปัญหาไปโผล่ที่อื่น และการสร้างขั้นทำความสะอาดมักต้องแก้หลายรอบ เพราะบางทีเพิ่งมาเจอปัญหาตอนอยู่ชั้น Gold แล้วต้องย้อนกลับไปแก้ Silver หรือแม้แต่ Bronze

</Step>

## เมื่อไม่ผ่าน: ปล่อยผ่าน, Quarantine หรือหยุด

Medallion แยก Policy เมื่อข้อมูลไม่ผ่านที่ Bronze ออกเป็นสองแบบ (หนังสือ: Medallion บทที่ 3 หน้า 60 ถึง 63)

- แบบ Intrusive (แทรกแซง) ใช้เมื่อคาดว่าปลายทางจะล้ม หรือ Consumer รับปัญหาไม่ได้ เราจะ**หยุด Pipeline** และเก็บข้อมูลที่ไม่ผ่านไว้ใน Folder หรือ Table แยก ไม่ให้เข้าชั้น Bronze จริง
- แบบ Nonintrusive (ไม่แทรกแซง) ใช้เมื่อยอมรับปัญหาได้ เราจะทำต่อ โดยเก็บทั้งข้อมูลที่ผ่านและไม่ผ่านไว้ในปลายทางเดียวกัน แล้วไปจัดการที่ชั้นถัดไป (มักเป็น Silver)

ในแบบฝึกเราจำลองสาม Policy กับข้อมูลชุดเดียวกัน โดย Policy B และ C เป็นสองครึ่งของ Intrusive (**การจับคู่นี้เป็นของผู้เขียน**)

| Policy | ทำอะไร | Revenue รวมที่ Publish |
|---|---|---:|
| A. ปล่อยผ่านโดยไม่ตรวจ (แย่กว่า Nonintrusive เพราะไม่แม้แต่บันทึกว่า Row ไหนไม่ผ่าน) | Join ข้อมูลดิบแล้ว Publish | 6,414,003.75 |
| B. Quarantine Row ที่ไม่ผ่าน Rule เทคนิค | เก็บ Row เสีย 77 Row แยกไว้พร้อมเหตุผล ที่เหลือไปต่อ | 6,368,087.92 |
| C. หยุดทั้งสาย | ถ้ามี Rule Error ไม่ผ่าน ไม่ Publish อะไรเลย | (ไม่มีรายงานใหม่) |

ความต่างระหว่าง A กับ B คือ 45,915.83 ซึ่งอธิบายได้ครบ โดยมาจาก Order ซ้ำที่ถูกนับสองครั้ง **+48,977.68** กับ Row ยอดติดลบ **-3,061.85** (Row ที่ Customer ไม่มีอยู่จริงหรือเป็น NULL หายไปทั้งสองฝั่งเพราะ Join) ส่วน Row ที่ถูก Quarantine แยกตามเหตุผลได้ดังนี้

| เหตุผล | Row | ยอดรวม |
|---|---:|---:|
| Customer ไม่มีอยู่จริง | 30 | 59,636.36 |
| order_id ซ้ำ | 20 | 56,069.27 |
| customer_id เป็น NULL | 15 | 45,911.89 |
| ยอดติดลบ | 12 | -3,269.55 |

(รัน: `05_checkpoints.py`, ทั้งสี่เหตุผลตรงกับจำนวนที่ฝัง)

</Step>

## Circuit Breaker: หยุดเมื่อร้ายแรงเท่านั้น

DQF อธิบาย Circuit Breaker ที่ยืมมาจากงาน CI/CD ว่าเป็นการให้ Pipeline หยุดทำงานเมื่อข้อมูลไม่ผ่านเกณฑ์คุณภาพ โดยมีสองสถานะคือวงจรปิด (ข้อมูลไหล) และวงจรเปิด (ข้อมูลไม่ไหล) ส่วนผู้ที่หนังสือยกคำพูดมา (Sandeep Uttamchandi อดีต Chief Data Architect ของ Intuit) บอกว่าต้องมีสามอย่าง คือ Lineage, การทำ Profiling ตลอด Pipeline, และความสามารถในการสั่งเปิดวงจรอัตโนมัติจากปัญหาที่ Profiling เจอ (หนังสือ: DQF บทที่ 3 หน้า 63 ถึง 67)

ผลในแบบฝึกคือ บนข้อมูลดิบวงจรเปิดเพราะมี 6 Rule Error ที่ไม่ผ่าน และหลัง Quarantine Row เสียแล้ว Rule ที่ค้างอยู่ลดเหลือ 3

| ขั้น | Rule Error ที่ยังไม่ผ่าน |
|---|---|
| ข้อมูลดิบ | CUST-COUNTRY-DOMAIN, ORD-CUST-POPULATED, ORD-ID-UNIQUE, ORD-CUST-EXISTS, PAY-ORDER-EXISTS, ORD-TOTAL-MATCHES-PAID |
| หลัง Quarantine | CUST-COUNTRY-DOMAIN, PAY-ORDER-EXISTS, ORD-TOTAL-MATCHES-PAID |

การ Quarantine แก้ Rule เชิงเทคนิคของ Table Orders ได้ ส่วนที่เหลือเป็น**ปัญหาที่ต้องให้คนตัดสิน** ได้แก่ค่า Country ผิด Format อยู่ใน Table Customers, Payment ที่ไม่มี Order, และยอดของ Order ที่ไม่ตรงกับ Payment System 35 รายการ ถ้าทั้งสามเป็นระดับ Error วงจรจะเปิดทุกวัน และ Pipeline จะไม่ Publish อะไรเลย ทั้งที่ข้อมูลส่วนใหญ่ยังดีพอ

DQF เตือนตรงนี้ไว้ว่า การหยุด Pipeline ควรใช้กับเหตุที่ร้ายแรงต่อบริษัทเท่านั้น เพราะถ้าใช้ไม่รอบคอบ Circuit Breaker และ SQL check operator จะหยุดงานอื่นที่ไม่เกี่ยวและคุณภาพดีไปด้วย (หนังสือ: DQF บทที่ 3 หน้า 65 ถึง 67) ระดับของแต่ละ Rule (`error` หรือ `warn`, [บท 4](/data-quality/rule-design/#rule-registry-query-พร้อมเจ้าของ-threshold-และ-impact)) จึงเป็นการตัดสินใจเชิงธุรกิจ ที่ต้องมีเจ้าของรับผิดชอบ

</Step>

## เครื่องมือที่ทำ "Assert ว่าข้อมูลเป็นอย่างที่คาด"

DQF ให้ภาพรวมของเครื่องมือทดสอบข้อมูลไว้ดังนี้ (หนังสือ: DQF บทที่ 3 หน้า 55 ถึง 67 เป็นที่มาของข้อความด้านล่างทั้งหมด)

| เครื่องมือ | ลักษณะ |
|---|---|
| **Dbt Tests** | ผูกกับการแปลงข้อมูลด้วย Dbt มี Test แบบ Singular (SQL เดี่ยวที่คืน Row ที่ผิด) และแบบ Generic ที่รับ Parameter ซึ่งมีติดมาให้สี่ตัว คือ `unique`, `not_null`, `accepted_values`, `relationships` |
| **Great Expectations** | Library Python ที่ใช้กับตัวแปลงข้อมูลได้หลายแบบ มีรายงานที่อ่านง่าย (Data Docs) และแจ้งเตือนผ่าน Slack หรือ Email ได้ |
| **Deequ** | Library ของ AWS บน Spark เขียนด้วย Scala มีการคำนวณ Metric แบบสะสม และมีการตรวจความผิดปกติในตัว |
| **Airflow** | ที่ชั้น Orchestration ตั้ง SLA ของ Task ได้ และทำ Circuit Breaker หรือ SQL check operator ได้ |

Dbt Test แบบ Singular ใช้แนวคิดเดียวกับที่เราใช้ในแบบฝึก คือเขียน Query ที่คืน **Row ที่ผิด** แล้วถือว่าผ่านเมื่อไม่มี Row เลย (หนังสือ) ส่วนสี่ Test ที่ติดมาก็ตรงกับ Dimension ที่เราเรียนมา โดย `unique` คือ Uniqueness, `not_null` คือ Completeness, `accepted_values` คือ Validity และ `relationships` คือ Integrity (**การจับคู่นี้เป็นของผู้เขียน**)

DQF สรุปว่า Test ครอบคลุมได้เฉพาะปัญหาที่เรา **คาดไว้แล้ว** (Known Unknowns) ส่วนที่คาดไม่ถึงต้องใช้ Monitoring ([บท 7](/data-quality/monitoring/#rule-จับสิ่งที่คาดไว้-แล้วที่เหลือล่ะ)) ถ้าอยากเขียน Expectation ด้วย GX โดยเฉพาะ ให้ดูบทเรียน "Validation แรก" ในเส้นทาง Great Expectations

</Step>

## กันตั้งแต่ต้นทาง

DMBOK2 เสนอวิธีป้องกันที่ไม่ต้องรอ Pipeline ไว้หลายข้อ (หนังสือ: DMBOK2 หัวข้อ 4.1 หน้า 486)

- ใช้ Data Entry Control กันค่าผิดไม่ให้เข้าระบบ
- ฝึกผู้สร้างข้อมูล และวัดผลงานของเขาด้วยความถูกต้องและครบถ้วน ไม่ได้วัดแค่ความเร็ว
- ทำ "Data Firewall" คือตาราง Rule คุณภาพที่ตรวจก่อนข้อมูลเข้า Application อย่าง Data Warehouse ถ้าคุณภาพต่ำกว่า Threshold ก็ให้แจ้ง Analyst
- เรียกร้องคุณภาพจาก Data Supplier ภายนอก และตรวจกระบวนการ โครงสร้าง และแหล่งที่มาของเขา
- ควบคุมการเปลี่ยนแปลงอย่างเป็นทางการ โดยห้ามแก้ข้อมูลตรง ๆ นอกกระบวนการปกติ

ข้อมูล Country ห้าแบบในตัวอย่างต้นบท กันได้ที่ต้นทาง (ใช้ช่องเลือก Country แทนการให้พิมพ์เอง) ซึ่งถูกกว่าการแก้ที่รายงานทุกรอบ

หนังสือเรื่อง Data Contract ของ Andrew Jones ผลักแนวคิดเดียวกันไปอีกขั้น โดยให้ทีมที่สร้างข้อมูลเป็นคนรันการตรวจ ซึ่งทำได้ใน 3 ที่ ที่แรกคือตอน Publish ที่ Library ที่ Producer เรียกตรวจแต่ละ Record เทียบกับ Contract ที่สองคือใน Infrastructure ที่ Table หรือ Topic บังคับ Schema และปฏิเสธการเขียนที่ผิด ส่วนที่สามคือหลัง Publish ที่ Rule กับ Observability Tool คอยดูสิ่งที่สองที่แรกพลาด สองที่แรกเก็บ Record เสียไว้ในระบบที่ผลิต มีแค่ที่สามที่จับได้หลังจากที่ Consumer อาจอ่านไปแล้ว Quarantine แบบ Policy B ข้างบนทำหน้าที่เดียวกับ Dead Letter Queue ที่หนังสือพูดถึง คือแยก Record เสียไว้พร้อมเหตุผล เพื่อตรวจและเล่นซ้ำหลังแก้ (หนังสือ: Contracts บทที่ 10 หน้า 163 ถึง 166) สำหรับรายละเอียดดูได้ในหน้า [Data Contract ในทางปฏิบัติ](/data-quality/agreements/contracts-in-practice/#ตรวจข้อมูลที่จุดไหน) ใต้[บท 6](/data-quality/agreements/contracts-in-practice/#ใครต้องรับสายเมื่อต้นทางเปลี่ยน)

## เช็กตัวเอง

- Rule "order_id ไม่ซ้ำ" ย้ายไปตรวจ In-stream ตอนรับทีละ Row ได้ไหม ต้องมีอะไรเพิ่ม
- ถ้า `PAY-ORDER-EXISTS` เป็นระดับ Error แต่เกิดจากฝั่ง Payment System ส่งช้ากว่า Order เล็กน้อย จะเกิดอะไรกับ Pipeline ทุกเช้า และแก้ที่ระดับ Rule หรือที่ต้นทาง
- ทีมของคุณใช้ Policy แบบ Intrusive หรือ Nonintrusive ที่ชั้นแรกของ Pipeline ตอนนี้ และ Consumer ปลายทางรู้ไหม
