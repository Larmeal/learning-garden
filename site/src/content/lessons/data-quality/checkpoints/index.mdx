## Bad Data ทำร้ายปลายทางจริง

ลองดูผลของ defect ที่[บท 2](/data-quality/dimensions/#สรุปทั้ง-14-rule) ตรวจเจอ เมื่อปล่อยมันไหลไปจนถึงรายงาน "revenue แยกตาม country" ซึ่งทำจากการ join order กับ customer (รัน: `05_checkpoints.py`)

| country | revenue | จำนวน order |
|---|---:|---:|
| TH | 4,098,059.59 | 1,642 |
| Thailand | 56,526.87 | 25 |
| THA | 64,202.16 | 23 |
| th | 50,744.19 | 23 |
| ไทย | 59,145.33 | 21 |
| T.H. | 61,395.79 | 20 |
| SG | 802,996.33 | 296 |
| JP | 756,154.01 | 294 |
| US | 464,779.48 | 168 |

revenue จาก customer ไทยที่เขียน country ผิด format ห้าแบบรวม 292,014.34 หลุดจากกลุ่ม `TH` ไปอยู่ใน row แยกของตัวเอง ใครอ่านรายงานนี้แล้วสรุปว่าไทยทำ revenue 4.10 ล้านจะประมาณผิดไปราว 7% ของ revenue ไทย และเป็นเรื่องที่ไม่มีข้อความแจ้งเตือนใดเกิดขึ้น

หลักของ DMBOK2 ที่เกี่ยวข้อง: ดูแลคุณภาพตลอด lifecycle ของข้อมูล **ทุกข้อต่อในห่วงโซ่ต้องส่งต่อข้อมูลคุณภาพสูง** (หนังสือ: DMBOK2 หัวข้อ 1.2 หน้า 452 ถึง 453) และ DQF บอกว่าองค์กรส่วนใหญ่เห็นตรงกันว่า การจับและแก้ปัญหาตอนนำข้อมูลเข้า (ingestion) ช่วยลดโอกาสที่ข้อมูลไม่ดีจะไหลลงปลายทาง (หนังสือ: DQF บทที่ 5 หน้า 119 ถึง 122)

## ตรวจที่ระดับไหน และทำใน Stream ได้หรือไม่

DMBOK2 Table 31 หน้า 481 แยกการวัดเป็นสามระดับความละเอียด และบอกว่าแต่ละระดับทำได้สองแบบ: **in-stream** ระหว่างที่ข้อมูลเดินผ่านระบบ กับ **batch** ด้วย query หรือเครื่องมือ profiling บนข้อมูลที่เก็บไว้แล้ว และบอกว่าการวัดระดับ dataset มักทำ in-stream ไม่ได้ เพราะต้องใช้ทั้งชุด (หนังสือ: DMBOK2 หัวข้อ 2.7.2 หน้า 479 ถึง 481)

| ระดับ | ตัวอย่าง rule | in-stream ได้ไหม | เจอใน dataset |
|---|---|---|---:|
| ค่าเดียว (element) | email มี format a@b.c | ได้ ดูค่าเดียว | 15 |
| ทั้ง row (record) | shipped_ts ไม่มาก่อน order_ts | ได้ ดู row เดียว | 10 |
| ทั้งชุด (data set) | order_id ไม่ซ้ำ | ไม่ได้ ต้องเห็นทั้งชุด | 20 |
| ทั้งชุด (data set) | order ล่าสุดอายุไม่เกิน 24 ชั่วโมง | ไม่ได้ ต้องเห็นทั้งชุด | 1 (ผิด) |

(รัน: `05_checkpoints.py`, ตัวเลขตรงกับที่ฝังไว้ ส่วนข้อสุดท้ายนับเป็น 1 หมายถึง "ผิด")

ผลที่ตามมาในทางปฏิบัติ: rule ของค่าเดียวและ row เดียวเอาไปไว้ที่จุดรับข้อมูลได้ถูกและเร็ว แต่ rule เรื่อง duplicate และ freshness ต้องรอให้มีข้อมูลครบก้อนก่อน DQF เสริมว่าที่ขั้น operational transformation ที่ต้องการ latency ต่ำ ควรเลือกตรวจแบบเบา เช่น เทียบ schema เก่ากับที่เข้ามา มากกว่าตรวจที่ใช้ทรัพยากรสูงอย่าง data drift (หนังสือ: DQF บทที่ 3 หน้า 54)

</Step>

## ชั้นของ Pipeline: Bronze, Silver

*Building Medallion Architectures* แบ่งข้อมูลเป็นชั้น (layer) และบอกว่าการไล่จาก Bronze ไปถึง Gold หมายถึง data quality โครงสร้าง และการตรวจสอบที่ดีขึ้น (หนังสือ: Medallion บทที่ 1 หน้า 5) หน้าที่ด้านคุณภาพของสองชั้นแรก

| layer | หน้าที่ด้านคุณภาพ |
|---|---|
| **Bronze** | เป็น "ด่านแรก" ของการตรวจเชิงเทคนิคและ observability ข้อผิดพลาดที่จับได้ตรงนี้ไม่ลามไปชั้น Silver และ Gold หนังสือแนะนำให้เก็บ metadata ของ schema ต้นทางไว้ เพื่อบังคับ rule ตรวจได้อัตโนมัติ |
| **Silver** | ทำความสะอาดและยกระดับ: ทำ format วันที่ให้เหมือนกัน บังคับ reference data ปรับชื่อ ลบข้อมูลซ้ำ ตรวจคุณภาพเชิงฟังก์ชัน และตัด row คุณภาพต่ำออก ยังไม่รวมกับแหล่งอื่น |

(หนังสือ: Medallion บทที่ 3 หน้า 51 ถึง 76, ส่วน Bronze Layer และ Silver Layer)

หนังสือเน้นอีกเรื่อง: การทำความสะอาดทำได้อัตโนมัติตอน load แต่ **ควรแก้ปัญหาคุณภาพที่ต้นทางที่ข้อมูลเกิด** เพื่อไม่ให้ปัญหาไปโผล่ที่อื่น และการสร้างขั้นทำความสะอาดมักต้องแก้หลายรอบ เพราะบางทีเพิ่งมาเจอปัญหาตอนอยู่ชั้น Gold ต้องย้อนกลับไปแก้ Silver หรือแม้แต่ Bronze

</Step>

## เมื่อไม่ผ่าน: ปล่อยผ่าน, Quarantine หรือหยุด

Medallion แยก policy เมื่อข้อมูลไม่ผ่านที่ Bronze เป็นสองแบบ (หนังสือ: Medallion บทที่ 3 หน้า 60 ถึง 63)

- **Intrusive** (แทรกแซง): ถ้าคาดว่าปลายทางจะล้ม หรือ consumer รับปัญหาไม่ได้ ให้ **หยุด pipeline** และเก็บข้อมูลที่ไม่ผ่านไว้ใน folder หรือ table แยก ไม่ให้เข้าชั้น Bronze จริง
- **Nonintrusive** (ไม่แทรกแซง): ถ้ายอมรับปัญหาได้ ให้ทำต่อ เก็บทั้งข้อมูลที่ผ่านและไม่ผ่านไว้ในปลายทางเดียวกัน แล้วไปจัดการที่ชั้นถัดไป (มักเป็น Silver)

แบบฝึกจำลองสาม policy กับข้อมูลชุดเดียวกัน โดย policy B และ C เป็นสองครึ่งของ intrusive (**การจับคู่นี้เป็นของผู้เขียน**)

| policy | ทำอะไร | revenue รวมที่ publish |
|---|---|---:|
| A. ปล่อยผ่านโดยไม่ตรวจ (แย่กว่า nonintrusive เพราะไม่แม้แต่บันทึกว่า row ไหนไม่ผ่าน) | join ข้อมูลดิบแล้ว publish | 6,414,003.75 |
| B. quarantine row ที่ไม่ผ่าน rule เทคนิค | เก็บ row เสีย 77 row แยกไว้พร้อมเหตุผล ที่เหลือไปต่อ | 6,368,087.92 |
| C. หยุดทั้งสาย | ถ้ามี rule error ไม่ผ่าน ไม่ publish อะไรเลย | (ไม่มีรายงานใหม่) |

ความต่างระหว่าง A กับ B คือ 45,915.83 และอธิบายได้ครบ: order ซ้ำที่ถูกนับสองครั้ง **+48,977.68** กับ row ยอดติดลบ **-3,061.85** (row ที่ customer ไม่มีอยู่จริงหรือเป็น NULL หายไปทั้งสองฝั่งเพราะ join) row ที่ถูก quarantine แยกตามเหตุผล

| เหตุผล | row | ยอดรวม |
|---|---:|---:|
| customer ไม่มีอยู่จริง | 30 | 59,636.36 |
| order_id ซ้ำ | 20 | 56,069.27 |
| customer_id เป็น NULL | 15 | 45,911.89 |
| ยอดติดลบ | 12 | -3,269.55 |

(รัน: `05_checkpoints.py`, ทั้งสี่เหตุผลตรงกับจำนวนที่ฝัง)

</Step>

## Circuit Breaker: หยุดเมื่อร้ายแรงเท่านั้น

DQF อธิบาย circuit breaker ที่ยืมจากงาน CI/CD: pipeline หยุดทำงานเมื่อข้อมูลไม่ผ่านเกณฑ์คุณภาพ มีสองสถานะคือวงจรปิด (ข้อมูลไหล) และวงจรเปิด (ข้อมูลไม่ไหล) ผู้ที่หนังสือยกคำพูดมา (Sandeep Uttamchandi อดีต Chief Data Architect ของ Intuit) บอกว่าต้องมีสามอย่าง: lineage, การทำ profiling ตลอด pipeline, และความสามารถในการสั่งเปิดวงจรอัตโนมัติจากปัญหาที่ profiling เจอ (หนังสือ: DQF บทที่ 3 หน้า 63 ถึง 67)

ผลในแบบฝึก: บนข้อมูลดิบวงจรเปิดเพราะ 6 rule error ไม่ผ่าน หลัง quarantine row เสีย rule ที่ค้างลดเหลือ 3

| ขั้น | rule error ที่ยังไม่ผ่าน |
|---|---|
| ข้อมูลดิบ | CUST-COUNTRY-DOMAIN, ORD-CUST-POPULATED, ORD-ID-UNIQUE, ORD-CUST-EXISTS, PAY-ORDER-EXISTS, ORD-TOTAL-MATCHES-PAID |
| หลัง quarantine | CUST-COUNTRY-DOMAIN, PAY-ORDER-EXISTS, ORD-TOTAL-MATCHES-PAID |

การ quarantine แก้ rule เชิงเทคนิคของ table orders ที่เหลือคือ **ปัญหาที่ต้องให้คนตัดสิน**: ค่า country ผิด format อยู่ใน table customers, payment ที่ไม่มี order, และยอดของ order ที่ไม่ตรงกับ payment system 35 รายการ ถ้าทั้งสามเป็นระดับ error วงจรจะเปิดทุกวัน และ pipeline ไม่ publish อะไรเลย แม้ข้อมูลส่วนใหญ่ยังดีพอ

DQF เตือนตรงนี้: การหยุด pipeline ควรใช้กับเหตุที่ร้ายแรงต่อบริษัทเท่านั้น ถ้าใช้ไม่รอบคอบ circuit breaker และ SQL check operator จะหยุดงานอื่นที่ไม่เกี่ยวและคุณภาพดีไปด้วย (หนังสือ: DQF บทที่ 3 หน้า 65 ถึง 67) ระดับของแต่ละ rule (`error` หรือ `warn`, [บท 4](/data-quality/rule-design/#rule-registry-query-พร้อมเจ้าของ-threshold-และ-impact)) จึงเป็นการตัดสินใจเชิงธุรกิจที่ต้องมีเจ้าของ

</Step>

## เครื่องมือที่ทำ "Assert ว่าข้อมูลเป็นอย่างที่คาด"

DQF ให้ภาพรวมเครื่องมือทดสอบข้อมูล (หนังสือ: DQF บทที่ 3 หน้า 55 ถึง 67, ที่มาของข้อความด้านล่างทั้งหมด)

| เครื่องมือ | ลักษณะ |
|---|---|
| **dbt tests** | ผูกกับการแปลงข้อมูลด้วย dbt มี test แบบ singular (SQL เดี่ยวที่คืน row ที่ผิด) และ generic ที่รับ parameter ติดมาสี่ตัว: `unique`, `not_null`, `accepted_values`, `relationships` |
| **Great Expectations** | library Python ใช้กับตัวแปลงข้อมูลหลายแบบ มีรายงานที่อ่านง่าย (Data Docs) และแจ้งเตือนผ่าน Slack หรือ email |
| **Deequ** | library ของ AWS บน Spark เขียนด้วย Scala มีการคำนวณ metric แบบสะสม และตรวจความผิดปกติในตัว |
| **Airflow** | ที่ชั้น orchestration ตั้ง SLA ของ task และทำ circuit breaker หรือ SQL check operator |

dbt test แบบ singular ใช้แนวคิดเดียวกับที่เราใช้ในแบบฝึก: เขียน query ที่คืน **row ที่ผิด** แล้วถือว่าผ่านเมื่อไม่มี row เลย (หนังสือ) และสี่ test ที่ติดมาตรงกับ dimension ที่เรียน: `unique` คือ uniqueness, `not_null` คือ completeness, `accepted_values` คือ validity, `relationships` คือ integrity (**การจับคู่นี้เป็นของผู้เขียน**)

DQF สรุปว่า test ครอบคลุมได้เฉพาะปัญหาที่เรา **คาดไว้แล้ว** (known unknowns) ส่วนที่คาดไม่ถึงต้องใช้ monitoring ([บท 7](/data-quality/monitoring/#rule-จับสิ่งที่คาดไว้-แล้วที่เหลือล่ะ)) ผู้ที่อยากเขียน expectation ด้วย GX โดยเฉพาะ ดูบทเรียน "Validation แรก" ในเส้นทาง Great Expectations

</Step>

## กันตั้งแต่ต้นทาง

DMBOK2 เสนอวิธีป้องกันที่ไม่ต้องรอ pipeline (หนังสือ: DMBOK2 หัวข้อ 4.1 หน้า 486)

- **data entry control**: กันค่าผิดไม่ให้เข้าระบบ
- **ฝึกผู้สร้างข้อมูล** และวัดผลงานของเขาด้วยความถูกต้องและครบถ้วน ไม่ใช่แค่ความเร็ว
- **"data firewall"**: ตาราง rule คุณภาพที่ตรวจก่อนข้อมูลเข้า application อย่าง data warehouse ถ้าคุณภาพต่ำกว่า threshold ให้แจ้ง analyst
- **เรียกร้องคุณภาพจาก data supplier ภายนอก** และตรวจกระบวนการ โครงสร้าง และแหล่งที่มาของเขา
- **ควบคุมการเปลี่ยนแปลงอย่างเป็นทางการ**: ห้ามแก้ข้อมูลตรงๆ นอกกระบวนการปกติ

ข้อมูล country ห้าแบบในตัวอย่างต้นบท กันได้ที่ต้นทาง (ช่องเลือก country แทนที่ให้พิมพ์เอง) ถูกกว่าการแก้ที่รายงานทุกรอบ

หนังสือเรื่อง data contract ของ Andrew Jones ผลักแนวคิดเดียวกันไปอีกขั้น: ทีมที่สร้างข้อมูลเป็นคนรันการตรวจ ใน 3 ที่ ตอน publish library ที่ producer เรียกตรวจแต่ละ record เทียบ contract ใน infrastructure table หรือ topic ที่บังคับ schema ปฏิเสธการเขียนที่ผิด และหลัง publish rule กับ observability tool คอยดูสิ่งที่สองที่แรกพลาด สองที่แรกเก็บ record เสียไว้ในระบบที่ผลิต มีแค่ที่สามที่จับได้หลังจากที่ consumer อาจอ่านไปแล้ว quarantine แบบ policy B ข้างบนทำหน้าที่เดียวกับ dead letter queue ที่หนังสือพูดถึง คือแยก record เสียไว้พร้อมเหตุผล เพื่อตรวจและเล่นซ้ำหลังแก้ (หนังสือ: Contracts บทที่ 10 หน้า 163 ถึง 166) รายละเอียดอยู่ในหน้า [data contract ในทางปฏิบัติ](/data-quality/agreements/contracts-in-practice/#ตรวจข้อมูลที่จุดไหน) ใต้[บท 6](/data-quality/agreements/contracts-in-practice/#ใครต้องรับสายเมื่อต้นทางเปลี่ยน)

<Callout type="try" title="ลองทำใน repo นี้">
เปิด `05_checkpoints.py` แก้ policy B ให้ quarantine row ที่ `country` ไม่อยู่ในรายการด้วย แล้วดูว่า revenue รวมและ revenue ของ TH เปลี่ยนอย่างไร จากนั้นลองเปลี่ยนเป็น "แปลงเป็น TH" แทนการ quarantine เทียบสองวิธีว่าแต่ละวิธีซ่อนหรือเปิดเผยปัญหาต้นทางมากกว่ากัน
</Callout>

## เช็กตัวเอง

- rule "order_id ไม่ซ้ำ" ย้ายไปตรวจ in-stream ตอนรับทีละ row ได้ไหม ต้องมีอะไรเพิ่ม
- ถ้า `PAY-ORDER-EXISTS` เป็นระดับ error แต่เกิดจากฝั่ง payment system ส่งช้ากว่า order เล็กน้อย จะเกิดอะไรกับ pipeline ทุกเช้า และแก้ที่ระดับ rule หรือที่ต้นทาง
- ทีมของคุณใช้ policy แบบ intrusive หรือ nonintrusive ที่ชั้นแรกของ pipeline ตอนนี้ และ consumer ปลายทางรู้ไหม

</Step>
