## ทำไมต้องดูก่อนเขียน rule

data quality rule มักไม่มีใครจดไว้ DMBOK2 บอกว่า rule อาจต้อง "ย้อนวิศวกรรม" จาก business process นโยบาย โค้ดของระบบ trigger การใช้รหัสสถานะ และสามัญสำนึก (หนังสือ: DMBOK2 §2.3) ส่วนการประเมินครั้งแรก หนังสือบอกว่าส่วนสำคัญที่สุดคือ **ลงไปดูข้อมูลจริง** ด้วยการ query เพื่อเข้าใจเนื้อหาและความสัมพันธ์ แล้วเทียบกับ rule และความคาดหวัง ครั้งแรกที่ทำมักเจอความสัมพันธ์ที่ไม่มีใครทำเอกสารไว้ ค่าซ้ำซ้อน และค่าที่ขัดกันเอง (หนังสือ: DMBOK2 §2.4)

มีข้อสังเกตที่ช่วยให้เริ่มได้ง่ายขึ้น: **ไม่จำเป็นต้องรู้ rule ทั้งหมดก่อนเริ่มประเมิน** การค้นพบและปรับ rule เป็นกระบวนการต่อเนื่อง และวิธีหาที่ดีวิธีหนึ่งคือเอาผลการประเมินไปให้ stakeholder ดู เพราะผลมักทำให้เขานึก rule ที่ต้องการออก (หนังสือ: DMBOK2 §2.3)

</Step>

## Profile ของทุก column โดยไม่ต้องรู้ความหมาย

Profiling คือการวิเคราะห์เชิงสถิติของเนื้อหาข้อมูล: สัดส่วน null, จำนวน distinct value, ค่าน้อยสุดและมากสุด ชุดตัวเลขห้าตัวนี้ได้จาก query เดียวต่อ column

```sql
SELECT count(*),
       count(*) FILTER (WHERE "col" IS NULL),
       count(DISTINCT "col"),
       min("col")::VARCHAR, max("col")::VARCHAR
FROM tbl;
```

ผลจาก dataset ของเรา (ตัดมาเฉพาะ row ที่มีเรื่องให้ดู) (รัน: `03_profiling.py`)

| column | row | null% | distinct | min .. max |
|---|---:|---:|---:|---|
| customers.email | 500 | 8.0% | 450 | (text ดูด้านล่าง) |
| customers.country | 500 | 0.0% | 9 | JP .. ไทย |
| customers.birth_date | 500 | 0.0% | 490 | 1850-01-01 .. 2030-01-01 |
| orders.order_id | 3,020 | 0.0% | 3,000 | 1 .. 3000 |
| orders.customer_id | 3,020 | 0.5% | 530 | 1 .. 9030 |
| orders.total_amount | 3,020 | 0.0% | 2,993 | -475.33 .. 4998.25 |
| orders.shipped_ts | 3,020 | 41.4% | 1,752 | 2026-07-02 .. 2026-10-31 |

อ่านทีละแถว

- `email`: null 8% และ distinct 450 จาก 460 ค่าที่ไม่ว่าง แปลว่ามี email ซ้ำ
- `country`: ควรมีไม่กี่ค่า แต่มี 9
- `birth_date`: ปี 1850 และ 2030 ไม่ใช่วันเกิดของ customer จริง
- `order_id`: 3,020 row แต่ distinct 3,000 มี row ซ้ำ
- `customer_id` ใน order: สูงสุด 9030 ทั้งที่ customer มีแค่ 1 ถึง 500
- `total_amount`: ต่ำสุดติดลบ

ข้อควรระวัง: min และ max ของ **text** เรียงตามตัวอักษร ที่ `email` ได้ `user100...` ถึง `user9...` ซึ่งไม่บอกอะไรเลย ใช้ได้กับตัวเลขและวันที่เท่านั้น สำหรับ text ให้ดู format แทน (ขั้นต่อไป)

`shipped_ts` ว่าง 41.4% **ไม่ใช่ defect** เพราะ order ที่ยังไม่ส่งหรือยกเลิกย่อมไม่มีเวลาส่ง ตัวเลข null อย่างเดียวบอกไม่ได้ว่าผิด ต้องรู้ความหมายของ column

</Step>

## ดู format ของ text

วิธีที่ใช้ได้ผล: แปลงทุกค่าให้เป็น "shape" โดยแทนตัวอักษรที่ต่อเนื่องด้วย `a` และตัวเลขที่ต่อเนื่องด้วย `9` แล้วนับว่ามี shape กี่แบบ

```sql
SELECT regexp_replace(regexp_replace(email, '[A-Za-z]+', 'a', 'g'), '[0-9]+', '9', 'g') AS shape,
       count(*) AS rows
FROM customers GROUP BY 1 ORDER BY 2 DESC;
```

| shape | row | ความหมาย |
|---|---:|---|
| `a9@a.a` | 445 | email ปกติ |
| (null) | 40 | ว่าง |
| `a9a.a` | 15 | ไม่มี `@` |

column ที่ควรมี format เดียว (email รหัสไปรษณีย์ เบอร์โทร รหัสสินค้า) แต่มี shape สองแบบ เป็นสัญญาณชัดว่ามี validity rule ให้เขียน

</Step>

## ดู frequency ของค่าใน column ที่มีค่าไม่กี่แบบ

```sql
SELECT country, count(*) FROM customers GROUP BY 1 ORDER BY 2 DESC;
```

| country | row |
|---|---:|
| TH | 330 |
| SG | 58 |
| JP | 56 |
| US | 31 |
| Thailand, T.H., th, THA, ไทย | 5 ต่อแบบ |

สี่ค่าแรกมีปริมาณเป็นกอบเป็นกำ ห้าค่าท้ายมีอย่างละห้า row และทั้งห้าดูเหมือนตั้งใจจะเป็น "ไทย" การเห็นแบบนี้ไม่ได้บอกว่าต้องทำอย่างไร จะแก้เป็น `TH` ทั้งหมด หรือกันไม่ให้กรอกแบบนี้ หรือสร้าง mapping table เป็นการตัดสินใจที่ต้องคุยกัน (บท 4 และบท 9)

</Step>

## จากสิ่งที่เห็นเป็น rule ที่เสนอ

| สิ่งที่เห็นใน profile | rule ที่เสนอ | ต้องถามใคร |
|---|---|---|
| email มี null และ shape ที่สอง | completeness และ validity ของ email | ใครบังคับให้กรอก email |
| country มี 9 ค่า | รายการค่าที่ยอมรับ หรือ mapping table | ใครเป็นเจ้าของรหัสประเทศ |
| birth_date 1850 ถึง 2030 | range rule แล้วถามว่าขอบจริงอยู่ตรงไหน | ธุรกิจรับ customer อายุเท่าไร |
| order_id ซ้ำ | uniqueness ของ order_id | ระบบต้นทางส่งซ้ำได้ไหม |
| customer_id ใน orders สูงเกิน | referential integrity ไป customers | customer ที่ถูกลบไปแล้วยังมี order ได้ไหม |
| total_amount ติดลบ | rule เรื่องเครื่องหมาย **ถ้า**ไม่ได้เก็บการคืนเงินไว้ที่นี่ | ต้องถามก่อน |

แถวสุดท้ายคือประเด็นสำคัญ: ค่าติดลบอาจเป็นการคืนเงินที่ถูกต้อง Profile บอกว่า**มีอะไร** ไม่ได้บอกว่า**ควรเป็นอะไร** DMBOK2 ยืนยันว่า profiling "ช่วยระบุปัญหา แต่ไม่ได้ระบุสาเหตุ และไม่ได้กำหนดผลกระทบต่อ business process" ผลกระทบต้องได้จาก stakeholder ตลอดห่วงโซ่ข้อมูล (หนังสือ: DMBOK2 §2.5) rule ที่เสนอจึงยังเป็นแค่ข้อเสนอจนกว่าผู้รู้เรื่องธุรกิจ (SME) จะยืนยัน

</Step>

## ดูทั้ง column อย่าดูแค่ sample

Profile ด้วยตัวเลขรวม (aggregate) ราคาถูกอยู่แล้วบน DuckDB หรือ warehouse ส่วนใหญ่ ไม่มีเหตุผลต้อง sample เพราะ defect ที่หายากจะหลุดไป

ลองเทียบ: วันเกิดที่อยู่นอกช่วงมี 6 row จาก 500 sample มา 10%

```sql
SELECT count(*) FROM (SELECT * FROM customers USING SAMPLE 10% (bernoulli, 7))
WHERE birth_date NOT BETWEEN DATE '1900-01-01' AND DATE '2026-11-01';
```

| ที่ตรวจ | วันเกิดผิดที่เจอ |
|---|---:|
| ทั้ง table | 6 |
| sample 10% (seed 7) | 0 |

ค่า 0 ขึ้นกับ seed ที่เลือก script จึงลอง sample ซ้ำ 40 seed: 23 seed เจอ 0 row, 12 seed เจอ 1 row, 5 seed เจอ 2 row **ไม่มี seed ไหนเจอครบ 6** (รัน: `03_profiling.py`) ข้อผิดพลาดที่พบน้อยมีโอกาสหลุด sample สูง และ sample ที่ "ดูสะอาด" ทำให้เข้าใจผิดว่าทั้ง table สะอาด

</Step>

## pandas ก็ทำได้

```python
c = frames["customers"]
c["email"].isna().mean()   # 0.08
c["email"].nunique()       # 450
```

ผลตรงกับ SQL (ว่าง 8.0% distinct 450) เลือกเครื่องมือตามที่ข้อมูลอยู่: ถ้าอยู่ใน warehouse แล้ว ใช้ SQL ดีกว่าดึงออกมา

<Callout type="try" title="ลองทำใน repo นี้">

## เช็กตัวเอง

- table `orders` มี `shipped_ts` ว่าง 41.4% คุณจะเขียน completeness rule ให้ column นี้ไหม เพราะอะไร
- เจอค่า `-475.33` ใน `total_amount` ใครคือคนที่ควรถามก่อนเขียน rule
- ทีม sample 1% มา profile table ที่มี 100 ล้าน row เพื่อประหยัดเวลา ความเสี่ยงคืออะไร
