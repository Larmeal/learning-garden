## ทำไมต้องดูก่อนเขียนกฎ

กฎคุณภาพข้อมูลมักไม่มีใครจดไว้ DMBOK2 บอกว่ากฎอาจต้อง "ย้อนวิศวกรรม" จากกระบวนการธุรกิจ นโยบาย โค้ดระบบ trigger การใช้รหัสสถานะ และสามัญสำนึก (หนังสือ: DMBOK2 §2.3) ส่วนการประเมินครั้งแรก หนังสือบอกว่าส่วนสำคัญที่สุดคือ **ลงไปดูข้อมูลจริง** ด้วยการ query เพื่อเข้าใจเนื้อหาและความสัมพันธ์ แล้วเทียบกับกฎและความคาดหวัง ครั้งแรกที่ทำมักเจอความสัมพันธ์ที่ไม่มีใครเอกสารไว้ ค่าซ้ำซ้อน และค่าที่ขัดกันเอง (หนังสือ: DMBOK2 §2.4)

มีข้อสังเกตที่ช่วยให้เริ่มได้ง่ายขึ้น: **ไม่จำเป็นต้องรู้กฎทั้งหมดก่อนเริ่มประเมิน** การค้นพบและปรับกฎเป็นกระบวนการต่อเนื่อง และวิธีหาที่ดีวิธีหนึ่งคือเอาผลการประเมินไปให้ผู้เกี่ยวข้องดู เพราะผลมักทำให้เขานึกกฎที่ต้องการออก (หนังสือ: DMBOK2 §2.3)

</Step>

## Profile ของทุกคอลัมน์โดยไม่ต้องรู้ความหมาย

Profiling คือการวิเคราะห์เชิงสถิติของเนื้อหาข้อมูล: สัดส่วน null, จำนวนค่าไม่ซ้ำ, ค่าน้อยสุดและมากสุด ชุดตัวเลขห้าตัวนี้ได้จาก query เดียวต่อคอลัมน์

```sql
SELECT count(*),
       count(*) FILTER (WHERE "col" IS NULL),
       count(DISTINCT "col"),
       min("col")::VARCHAR, max("col")::VARCHAR
FROM tbl;
```

ผลจากชุดข้อมูลของเรา (ตัดมาเฉพาะแถวที่มีเรื่องให้ดู) (รัน: `03_profiling.py`)

| คอลัมน์ | แถว | null% | ไม่ซ้ำ | น้อยสุด .. มากสุด |
|---|---:|---:|---:|---|
| customers.email | 500 | 8.0% | 450 | (ข้อความ ดูด้านล่าง) |
| customers.country | 500 | 0.0% | 9 | JP .. ไทย |
| customers.birth_date | 500 | 0.0% | 490 | 1850-01-01 .. 2030-01-01 |
| orders.order_id | 3,020 | 0.0% | 3,000 | 1 .. 3000 |
| orders.customer_id | 3,020 | 0.5% | 530 | 1 .. 9030 |
| orders.total_amount | 3,020 | 0.0% | 2,993 | -475.33 .. 4998.25 |
| orders.shipped_ts | 3,020 | 41.4% | 1,752 | 2026-07-02 .. 2026-10-31 |

อ่านทีละแถว

- `email`: null 8% และค่าไม่ซ้ำ 450 จาก 460 ค่าที่ไม่ว่าง แปลว่ามีอีเมลซ้ำ
- `country`: ควรมีไม่กี่ค่า แต่มี 9
- `birth_date`: ปี 1850 และ 2030 ไม่ใช่วันเกิดของลูกค้าจริง
- `order_id`: 3,020 แถวแต่ไม่ซ้ำ 3,000 แถว มีแถวซ้ำ
- `customer_id` ในคำสั่งซื้อ: สูงสุด 9030 ทั้งที่ลูกค้ามีแค่ 1 ถึง 500
- `total_amount`: ต่ำสุดติดลบ

ข้อควรระวัง: น้อยสุดและมากสุดของ**ข้อความ**เรียงตามตัวอักษร ที่ `email` ได้ `user100...` ถึง `user9...` ซึ่งไม่บอกอะไรเลย ใช้ได้กับตัวเลขและวันที่เท่านั้น สำหรับข้อความให้ดูรูปแบบแทน (ขั้นต่อไป)

`shipped_ts` ว่าง 41.4% **ไม่ใช่ข้อมูลเสีย** เพราะคำสั่งซื้อที่ยังไม่ส่งหรือยกเลิกย่อมไม่มีเวลาส่ง ตัวเลข null อย่างเดียวบอกไม่ได้ว่าผิด ต้องรู้ความหมายของคอลัมน์

</Step>

## ดูรูปแบบของข้อความ

วิธีที่ใช้ได้ผล: แปลงทุกค่าให้เป็น "รูปทรง" โดยแทนตัวอักษรที่ต่อเนื่องด้วย `a` และตัวเลขที่ต่อเนื่องด้วย `9` แล้วนับว่ามีรูปทรงกี่แบบ

```sql
SELECT regexp_replace(regexp_replace(email, '[A-Za-z]+', 'a', 'g'), '[0-9]+', '9', 'g') AS shape,
       count(*) AS rows
FROM customers GROUP BY 1 ORDER BY 2 DESC;
```

| รูปทรง | แถว | ความหมาย |
|---|---:|---|
| `a9@a.a` | 445 | อีเมลปกติ |
| (null) | 40 | ว่าง |
| `a9a.a` | 15 | ไม่มี `@` |

คอลัมน์ที่ควรมีรูปแบบเดียว (อีเมล รหัสไปรษณีย์ เบอร์โทร รหัสสินค้า) แต่มีรูปทรงสองแบบ เป็นสัญญาณชัดว่ามีกฎ validity ให้เขียน

</Step>

## ดูความถี่ของค่าในคอลัมน์ที่มีค่าไม่กี่แบบ

```sql
SELECT country, count(*) FROM customers GROUP BY 1 ORDER BY 2 DESC;
```

| country | แถว |
|---|---:|
| TH | 330 |
| SG | 58 |
| JP | 56 |
| US | 31 |
| Thailand, T.H., th, THA, ไทย | 5 ต่อแบบ |

สี่ค่าแรกมีปริมาณเป็นกอบเป็นกำ ห้าค่าท้ายมีอย่างละห้าแถว และทั้งห้าดูเหมือนตั้งใจจะเป็น "ไทย" การเห็นแบบนี้ไม่ได้บอกว่าต้องทำอย่างไร จะแก้เป็น `TH` ทั้งหมด หรือกันไม่ให้กรอกแบบนี้ หรือสร้างตารางแปลงค่า เป็นการตัดสินใจที่ต้องคุยกัน (บท 4 และบท 9)

</Step>

## จากสิ่งที่เห็นเป็นกฎที่เสนอ

| สิ่งที่เห็นใน profile | กฎที่เสนอ | ต้องถามใคร |
|---|---|---|
| email มี null และรูปทรงที่สอง | completeness และ validity ของอีเมล | ใครบังคับให้กรอกอีเมล |
| country มี 9 ค่า | รายการค่าที่ยอมรับ หรือตารางแปลงค่า | ใครเป็นเจ้าของรหัสประเทศ |
| birth_date 1850 ถึง 2030 | กฎช่วง แล้วถามว่าขอบจริงอยู่ตรงไหน | ธุรกิจรับลูกค้าอายุเท่าไร |
| order_id ซ้ำ | uniqueness ของ order_id | ระบบต้นทางส่งซ้ำได้ไหม |
| customer_id ใน orders สูงเกิน | referential integrity ไป customers | ลูกค้าที่ถูกลบไปแล้วยังมีคำสั่งซื้อได้ไหม |
| total_amount ติดลบ | กฎเครื่องหมาย **ถ้า**ไม่ได้เก็บการคืนเงินไว้ที่นี่ | ต้องถามก่อน |

แถวสุดท้ายคือประเด็นสำคัญ: ค่าติดลบอาจเป็นการคืนเงินที่ถูกต้อง Profile บอกว่า**มีอะไร** ไม่ได้บอกว่า**ควรเป็นอะไร** DMBOK2 ยืนยันว่า profiling "ช่วยระบุปัญหา แต่ไม่ได้ระบุสาเหตุ และไม่ได้กำหนดผลกระทบต่อกระบวนการธุรกิจ" ผลกระทบต้องได้จากผู้เกี่ยวข้องตลอดห่วงโซ่ข้อมูล (หนังสือ: DMBOK2 §2.5) กฎที่เสนอจึงยังเป็นแค่ข้อเสนอจนกว่าผู้รู้เรื่องธุรกิจ (SME) จะยืนยัน

</Step>

## ดูทั้งคอลัมน์ อย่าดูแค่ตัวอย่าง

Profile ด้วยตัวเลขรวม (aggregate) ราคาถูกอยู่แล้วบน DuckDB หรือคลังข้อมูลส่วนใหญ่ ไม่มีเหตุผลต้องสุ่มมาดู เพราะข้อมูลเสียที่หายากจะหลุดไป

ลองเทียบ: วันเกิดที่อยู่นอกช่วงมี 6 แถวจาก 500 สุ่มมา 10%

```sql
SELECT count(*) FROM (SELECT * FROM customers USING SAMPLE 10% (bernoulli, 7))
WHERE birth_date NOT BETWEEN DATE '1900-01-01' AND DATE '2026-11-01';
```

| ที่ตรวจ | วันเกิดผิดที่เจอ |
|---|---:|
| ทั้งตาราง | 6 |
| สุ่ม 10% (seed 7) | 0 |

ค่า 0 ขึ้นกับ seed ที่เลือก สคริปต์จึงลองสุ่มซ้ำ 40 seed: 23 seed เจอ 0 แถว, 12 seed เจอ 1 แถว, 5 seed เจอ 2 แถว **ไม่มี seed ไหนเจอครบ 6** (รัน: `03_profiling.py`) ข้อผิดพลาดที่พบน้อยมีโอกาสหลุดตัวอย่างสูง และตัวอย่างที่ "ดูสะอาด" ทำให้เข้าใจผิดว่าทั้งตารางสะอาด

</Step>

## pandas ก็ทำได้

```python
c = frames["customers"]
c["email"].isna().mean()   # 0.08
c["email"].nunique()       # 450
```

ผลตรงกับ SQL (ว่าง 8.0% ไม่ซ้ำ 450) เลือกเครื่องมือตามที่ข้อมูลอยู่: ถ้าอยู่ในคลังข้อมูลแล้ว ใช้ SQL ดีกว่าดึงออกมา

<Callout type="try" title="ลองทำใน repo นี้">
รัน `uv run python 03_profiling.py` แล้วดู profile ของ `payments.amount` เทียบกับ `orders.total_amount` ค่าน้อยสุดและมากสุดของสองคอลัมน์เหมือนกันเป๊ะ (-475.33 และ 4998.25) ทั้งที่มี 35 ออเดอร์ที่ยอดไม่ตรง เพราะส่วนต่างอยู่ที่ 1 ถึง 120 บาท และไม่มีรายการไหนเลื่อนไปเป็นค่าสุดขอบของช่วง สรุปว่า profile ระดับคอลัมน์ไม่เห็นปัญหาที่ต้องเทียบทีละออเดอร์ ซึ่งเป็นสิ่งที่กฎ accuracy ในบท 2 ทำ

## เช็กตัวเอง

- ตาราง `orders` มี `shipped_ts` ว่าง 41.4% คุณจะเขียนกฎ completeness ให้คอลัมน์นี้ไหม เพราะอะไร
- เจอค่า `-475.33` ใน `total_amount` ใครคือคนที่ควรถามก่อนเขียนกฎ
- ทีมสุ่มตัวอย่าง 1% มา profile ตารางที่มี 100 ล้านแถวเพื่อประหยัดเวลา ความเสี่ยงคืออะไร
