## ทำไมต้องดูก่อนเขียน Rule

Data Quality Rule มักไม่มีใครจดเอาไว้ ซึ่ง DMBOK2 บอกว่า Rule อาจต้อง "ย้อนวิศวกรรม" จาก Business Process นโยบาย โค้ดของระบบ Trigger การใช้รหัสสถานะ และสามัญสำนึก (หนังสือ: DMBOK2 หัวข้อ 2.3 หน้า 474 ถึง 475) ส่วนการประเมินครั้งแรก หนังสือบอกว่าส่วนสำคัญที่สุดคือ **ลงไปดูข้อมูลจริง** ด้วยการ Query เพื่อทำความเข้าใจเนื้อหาและความสัมพันธ์ แล้วเทียบกับ Rule และความคาดหวัง ซึ่งการทำครั้งแรกมักเจอความสัมพันธ์ที่ไม่มีใครทำเอกสารไว้ ค่าซ้ำซ้อน และค่าที่ขัดกันเอง (หนังสือ: DMBOK2 หัวข้อ 2.4 หน้า 475 ถึง 476)

ยังมีข้อสังเกตหนึ่งที่ช่วยให้เริ่มได้ง่ายขึ้น นั่นคือ **ไม่จำเป็นต้องรู้ Rule ทั้งหมดก่อนเริ่มประเมิน** เพราะการค้นพบและปรับ Rule เป็นกระบวนการต่อเนื่อง และวิธีหาที่ดีวิธีหนึ่งคือเอาผลการประเมินไปให้ Stakeholder ดู เนื่องจากผลที่เห็นมักทำให้เขานึก Rule ที่ต้องการออก (หนังสือ: DMBOK2 หัวข้อ 2.3 หน้า 474 ถึง 475)

</Step>

## Profile ของทุก Column โดยไม่ต้องรู้ความหมาย

Profiling คือการวิเคราะห์เชิงสถิติของเนื้อหาข้อมูล เช่น สัดส่วน Null, จำนวน Distinct Value และค่าน้อยสุดกับมากสุด ซึ่งชุดตัวเลขห้าตัวนี้เราได้มาจาก Query เดียวต่อ Column

```sql
SELECT count(*),
       count(*) FILTER (WHERE "col" IS NULL),
       count(DISTINCT "col"),
       min("col")::VARCHAR, max("col")::VARCHAR
FROM tbl;
```

พอรันกับ Dataset ของเรา จะได้ผลตามนี้ (ตัดมาเฉพาะ Row ที่มีเรื่องให้ดู, รัน: `03_profiling.py`)

| column | row | null% | distinct | min .. max |
|---|---:|---:|---:|---|
| customers.email | 500 | 8.0% | 450 | (Text ดูด้านล่าง) |
| customers.country | 500 | 0.0% | 9 | JP .. ไทย |
| customers.birth_date | 500 | 0.0% | 490 | 1850-01-01 .. 2030-01-01 |
| orders.order_id | 3,020 | 0.0% | 3,000 | 1 .. 3000 |
| orders.customer_id | 3,020 | 0.5% | 530 | 1 .. 9030 |
| orders.total_amount | 3,020 | 0.0% | 2,993 | -475.33 .. 4998.25 |
| orders.shipped_ts | 3,020 | 41.4% | 1,752 | 2026-07-02 .. 2026-10-31 |

ลองอ่านทีละแถวกัน

- `email` มี Null อยู่ 8% และมี Distinct 450 จาก 460 ค่าที่ไม่ว่าง แปลว่ามี Email ซ้ำกันอยู่
- `country` ควรมีแค่ไม่กี่ค่า แต่เรากลับเจอถึง 9 ค่า
- `birth_date` มีทั้งปี 1850 และ 2030 ซึ่งไม่ใช่วันเกิดของ Customer จริง
- `order_id` มี 3,020 Row แต่ Distinct แค่ 3,000 แปลว่ามี Row ซ้ำ
- `customer_id` ใน Order สูงสุดถึง 9030 ทั้งที่ Customer มีแค่ 1 ถึง 500
- `total_amount` ต่ำสุดติดลบ

Min และ Max ของ Text จะเรียงตามตัวอักษร ที่ `email` เลยได้ `user100...` ถึง `user9...` ซึ่งไม่ได้บอกอะไรเราเลย สองค่านี้จึงใช้ได้กับตัวเลขและวันที่เท่านั้น ส่วน Text ให้ไปดู Format แทนในขั้นต่อไป

ส่วน `shipped_ts` ที่ว่างอยู่ 41.4% **ไม่ใช่ Defect** นะ เพราะ Order ที่ยังไม่ส่งหรือยกเลิกย่อมไม่มีเวลาส่ง ตัวเลข Null อย่างเดียวจึงบอกไม่ได้ว่าผิด เราต้องรู้ความหมายของ Column ด้วย

</Step>

## ดู Format ของ Text

วิธีที่ใช้ได้ผลคือแปลงทุกค่าให้เป็น "Shape" โดยแทนตัวอักษรที่ต่อเนื่องกันด้วย `a` และตัวเลขที่ต่อเนื่องกันด้วย `9` แล้วนับว่ามี Shape กี่แบบ

```sql
SELECT regexp_replace(regexp_replace(email, '[A-Za-z]+', 'a', 'g'), '[0-9]+', '9', 'g') AS shape,
       count(*) AS rows
FROM customers GROUP BY 1 ORDER BY 2 DESC;
```

| Shape | Row | ความหมาย |
|---|---:|---|
| `a9@a.a` | 445 | Email ปกติ |
| (Null) | 40 | ว่าง |
| `a9a.a` | 15 | ไม่มี `@` |

ถ้า Column ที่ควรมี Format เดียว (Email รหัสไปรษณีย์ เบอร์โทร รหัสสินค้า) กลับมี Shape สองแบบ ก็เป็นสัญญาณชัดว่ามี Validity Rule ที่เรายังต้องเขียน

</Step>

## ดู Frequency ของค่าใน Column ที่มีค่าไม่กี่แบบ

```sql
SELECT country, count(*) FROM customers GROUP BY 1 ORDER BY 2 DESC;
```

| country | row |
|---|---:|
| TH | 330 |
| SG | 58 |
| JP | 56 |
| US | 31 |
| Thailand, T.H., th, THA, ไทย | 5 ต่อแบบ |

สี่ค่าแรกมีจำนวนเป็นกอบเป็นกำ ส่วนห้าค่าท้ายมีอย่างละห้า Row และทั้งห้าค่าดูเหมือนตั้งใจจะเป็น "ไทย" แต่การเห็นแบบนี้ยังไม่ได้บอกเราว่าต้องทำอย่างไร จะแก้เป็น `TH` ทั้งหมด จะกันไม่ให้กรอกแบบนี้ หรือจะสร้าง Mapping Table ก็เป็นการตัดสินใจที่ต้องคุยกันก่อน ([บท 4](/data-quality/rule-design/) และ[บท 9](/data-quality/incidents/))

</Step>

## จากสิ่งที่เห็นเป็น Rule ที่เสนอ

| สิ่งที่เห็นใน Profile | Rule ที่เสนอ | ต้องถามใคร |
|---|---|---|
| Email มี Null และ Shape ที่สอง | Completeness และ Validity ของ Email | ใครบังคับให้กรอก Email |
| Country มี 9 ค่า | รายการค่าที่ยอมรับ หรือ Mapping Table | ใครเป็นเจ้าของรหัสประเทศ |
| birth_date 1850 ถึง 2030 | Range Rule แล้วถามว่าขอบจริงอยู่ตรงไหน | ธุรกิจรับ Customer อายุเท่าไร |
| order_id ซ้ำ | Uniqueness ของ order_id | ระบบต้นทางส่งซ้ำได้ไหม |
| customer_id ใน Orders สูงเกิน | Referential Integrity ไป Customers | Customer ที่ถูกลบไปแล้วยังมี Order ได้ไหม |
| total_amount ติดลบ | Rule เรื่องเครื่องหมาย **ถ้า**ไม่ได้เก็บการคืนเงินไว้ที่นี่ | ต้องถามก่อน |

แถวสุดท้ายสำคัญที่สุด เพราะค่าติดลบอาจเป็นการคืนเงินที่ถูกต้องก็ได้ Profile บอกเราว่า**มีอะไร** แต่ไม่ได้บอกว่า**ควรเป็นอะไร** DMBOK2 ก็ยืนยันว่า Profiling "ช่วยระบุปัญหา แต่ไม่ได้ระบุสาเหตุ และไม่ได้กำหนดผลกระทบต่อ Business Process" ซึ่งผลกระทบนี้ต้องได้จาก Stakeholder ตลอดห่วงโซ่ข้อมูล (หนังสือ: DMBOK2 หัวข้อ 2.5 หน้า 476) Rule ที่เสนอจึงยังเป็นแค่ข้อเสนอ จนกว่าผู้รู้เรื่องธุรกิจ (SME) จะยืนยัน

</Step>

## ดูทั้ง Column อย่าดูแค่ Sample

การ Profile ด้วยตัวเลขรวม (Aggregate) ราคาถูกอยู่แล้วบน DuckDB หรือ Warehouse ส่วนใหญ่ เราจึงไม่มีเหตุผลที่ต้อง Sample เพราะ Defect ที่หายากจะหลุดไป

ลองเทียบกันดู วันเกิดที่อยู่นอกช่วงมี 6 Row จาก 500 Row ทีนี้ลอง Sample มา 10%

```sql
SELECT count(*) FROM (SELECT * FROM customers USING SAMPLE 10% (bernoulli, 7))
WHERE birth_date NOT BETWEEN DATE '1900-01-01' AND DATE '2026-11-01';
```

| ที่ตรวจ | วันเกิดผิดที่เจอ |
|---|---:|
| ทั้ง Table | 6 |
| sample 10% (seed 7) | 0 |

ค่า 0 นี้ขึ้นอยู่กับ Seed ที่เลือก Script จึงลอง Sample ซ้ำอีก 40 Seed ได้ผลว่า 23 Seed เจอ 0 Row, 12 Seed เจอ 1 Row และ 5 Seed เจอ 2 Row โดย **ไม่มี Seed ไหนเจอครบ 6** เลย (รัน: `03_profiling.py`) เพราะฉะนั้นข้อผิดพลาดที่พบน้อยจึงมีโอกาสหลุด Sample สูง และ Sample ที่ "ดูสะอาด" ก็ทำให้เราเข้าใจผิดได้ว่าทั้ง Table สะอาด

</Step>

## Pandas ก็ทำได้

```python
c = frames["customers"]
c["email"].isna().mean()   # 0.08
c["email"].nunique()       # 450
```

ผลที่ได้ตรงกับ SQL (ว่าง 8.0% Distinct 450) ดังนั้นเราเลือกเครื่องมือตามที่ข้อมูลอยู่ได้เลย ถ้าข้อมูลอยู่ใน Warehouse แล้ว การใช้ SQL ก็ดีกว่าการดึงออกมา

## เช็กตัวเอง

- Table `orders` มี `shipped_ts` ว่าง 41.4% คุณจะเขียน Completeness Rule ให้ Column นี้ไหม เพราะอะไร
- เจอค่า `-475.33` ใน `total_amount` ใครคือคนที่ควรถามก่อนเขียน Rule
- ทีม Sample 1% มา Profile Table ที่มี 100 ล้าน Row เพื่อประหยัดเวลา ความเสี่ยงคืออะไร

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| Rule มักไม่ได้จดไว้ ต้องย้อนวิศวกรรม; ไม่ต้องรู้ Rule ทั้งหมดก่อนประเมิน | หนังสือ: DMBOK2 หัวข้อ 2.3 หน้า 474 ถึง 475 |
| ส่วนสำคัญที่สุดของการประเมินคือดูข้อมูลจริง | หนังสือ: DMBOK2 หัวข้อ 2.4 หน้า 475 ถึง 476 |
| Profiling ไม่ระบุสาเหตุและผลกระทบ | หนังสือ: DMBOK2 หัวข้อ 2.5 หน้า 476 |
| ตัวเลขใน Profile, Shape ของ Email, Frequency ของ Country | รัน: `03_profiling.py` |
| Sample 10% หาวันเกิดผิดไม่เจอ | รัน: `03_profiling.py` (ขึ้นกับ Seed) |
| เทคนิค Shape `a` และ `9`, ตาราง Rule ที่เสนอ, คำแนะนำให้ Profile ทั้ง Column | ผู้เขียน |
