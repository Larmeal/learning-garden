## Quality เป็นส่วนหนึ่งของ Governance

*Data Governance: The Definitive Guide* ให้เหตุผลว่า โปรแกรมที่ Govern Life Cycle, Control และการใช้ข้อมูลอยู่แล้ว ก็ควร Govern คุณภาพของข้อมูลด้วย และองค์กรมักประเมินคุณภาพข้อมูลของตัวเองสูงเกินไป ในขณะที่ประเมินผลเสียของข้อมูลที่ไม่ดีต่ำเกินไป (หนังสือ: Governance บทที่ 5 หน้า 113 ถึง 131) คุณภาพจึงไม่จำเป็นต้องมีองค์กรแยกออกไปต่างหาก แต่ควรอยู่ในการตัดสินใจชุดเดียวกันกับเรื่อง Owner, Policy และ Tooling

หนังสือเล่มนี้นิยาม Data Quality ไว้สามอย่าง คือ Accuracy, Completeness และ Timeliness (หนังสือ: Governance บทที่ 5 หน้า 113) ส่วน *Fundamentals of Data Engineering* ก็ย้ำสามอย่างนี้เหมือนกัน และเพิ่มนิยามตรง ๆ ว่า Quality คือการทำให้ข้อมูลเข้าใกล้สถานะที่ต้องการ โดยวนอยู่กับคำถามที่ว่า "สิ่งที่ได้ เทียบกับสิ่งที่คาดไว้ ต่างกันแค่ไหน" (หนังสือ: FoDE บทที่ 2 หน้า 54 ถึง 56) สำหรับ[บท 2](/data-quality/dimensions/#ไม่มีชุด-dimension-ที่ตกลงกันได้ชุดเดียว) ก็ให้รายการที่ยาวกว่านี้ไว้แล้ว เมื่อหนังสือแต่ละเล่มเลือกชุดไม่เหมือนกัน จึงตรงกับที่ DMBOK2 บอกว่าไม่มีชุดเดียวที่ทุกคนตกลงกันได้

</Step>

## ใคร Accountable

*Fundamentals of Data Engineering* วางเรื่อง Accountability ไว้ดังนี้ Data Accountability คือการกำหนดบุคคลหนึ่งคนให้ Govern ข้อมูลส่วนหนึ่ง โดยคนนั้นจะคอยประสานกับคนอื่นที่แตะข้อมูลชุดนั้น และไม่จำเป็นต้องเป็น Data Engineer อีกทั้งมักไม่มี Resource ครบพอที่จะรักษาคุณภาพด้วยตัวเอง "ส่วน" ที่ว่านี้อาจเป็น Table, Log Stream หรือ Field เดียวที่โผล่ในหลาย Table เช่น Customer id ก็ได้ และถ้าไม่มีใครรับผิดชอบข้อมูลนั้น การจัดการคุณภาพก็ทำได้ยาก (หนังสือ: FoDE บทที่ 2 หน้า 54 ถึง 56)

หนังสือสี่เล่มที่เราใช้อยู่ต่างก็ตอบคำถามว่า "ใครเป็นเจ้าของคุณภาพ" และคำตอบของทั้งสี่เล่มเข้ากันได้ดังตารางนี้

| หนังสือ | ใคร | เพิ่มอะไร |
|---|---|---|
| DMBOK2 ([บท 10](/data-quality/ownership-scorecard/#ใครรับผิดชอบ)) | เจ้าของ Business Process ที่สร้างข้อมูล | บังคับใช้ Standard ใน Process ของตัวเอง |
| Contracts ([บท 6](/data-quality/agreements/#data-contract-คืออะไร-และข้อควรระวังเรื่องคำนี้)) | ทีมที่สร้างข้อมูล ผ่าน Contract | ความรับผิดชอบย้ายไปอยู่ที่ต้นทาง ส่วน Governance Council ส่วนกลางจะตั้ง Standard และสร้าง Tool ให้ แต่ไม่เข้ามาคุมข้อมูลเอง (หนังสือ: Contracts บทที่ 5 หน้า 75 ถึง 78) |
| Governance | Data Owner และ Data Steward รวมกับ "หมวก" อื่น | Steward จัดหมวดและจัดชั้นข้อมูล Privacy Lead ดูเรื่อง Compliance Legal อธิบาย Requirement และผู้บริหารให้ทุน (หนังสือ: Governance บทที่ 3 หน้า 58 ถึง 65) |
| FoDE | หนึ่งคนต่อข้อมูลหนึ่งส่วน | ละเอียดได้ถึงระดับ Field เดียว |

Governance ยังเสนอ data acceptance process ซึ่งหมายความว่าข้อมูลจะยังไม่ถูกนำไปใช้ จนกว่าเจ้าของจะพิสูจน์ได้ว่าผ่านมาตรฐานคุณภาพขององค์กร และ Business Unit ที่สร้างข้อมูลก็เป็นเจ้าของคุณภาพของมันเอง ไม่ทิ้งไว้ให้ผู้ใช้ปลายน้ำต้องรับภาระ (หนังสือ: Governance บทที่ 2 หน้า 46) แนวคิดนี้เป็นเรื่องเดียวกับ Certification ใน[บท 10](/data-quality/ownership-scorecard/#data-certification) และ Contract ใน[บท 6](/data-quality/agreements/#ทำไมต้องมี-contract)

</Step>

## Class และ Policy

Governance ต้องมีวิธีบอกว่าข้อมูลนี้เป็นชนิดไหน หนังสือจึงเสนอ Enterprise Dictionary ที่ลิสต์ Class ของข้อมูลไว้ ซึ่ง Class ก็คือกลุ่มของ Information Type ที่องค์กรปฏิบัติต่อกันแบบเดียวกัน และ Policy ควรผูกกับ Class ไม่ใช่ผูกกับ Table หรือ Column เดียว ยกตัวอย่าง "Analyst เข้าถึงข้อมูลส่วนบุคคลไม่ได้" เข้าใจง่ายและขยายต่อได้ ส่วน "Analyst เข้าถึง Column 3 ของ Table B ไม่ได้" ทำไม่ได้ทั้งสองอย่าง (หนังสือ: Governance บทที่ 2 หน้า 37 ถึง 43)

Policy ที่หนังสืออธิบายมี Retention ขั้นต่ำและขั้นสูง กับ Access ที่ไม่ได้มีแค่ได้หรือไม่ได้ แต่แบ่งเป็นไม่มีสิทธิ์ มีสิทธิ์บางส่วน (ซ่อนบางหลักด้วยดาว หรือแทนค่าด้วยรูปแบบ Tokenized ที่ยัง Group ได้) และมีสิทธิ์เต็ม (หนังสือ: Governance บทที่ 2 หน้า 37 ถึง 43) ส่วนเรื่องที่ว่าจะบันทึกสิ่งเหล่านี้ของ Dataset ไว้ที่ไหน Contracts ตอบว่าให้ใส่ใน Contract โดยระบุได้ทีละ Field ว่าเป็นข้อมูลส่วนบุคคลไหม จัดชั้นอย่างไร ใครเข้าถึงได้และนานแค่ไหน และลบหรือ Anonymize อย่างไร คนที่เหมาะจะกรอกที่สุดคือคนที่สร้างข้อมูล (หนังสือ: Contracts บทที่ 2 หน้า 29 ถึง 30 และบทที่ 5 หน้า 73 ถึง 78)

สำหรับทีมคุณภาพ นี่ก็เป็น Rule อีกข้อหนึ่ง เพราะ Field ใน Contract ที่ไม่มี Class คือ Contract ที่ยังไม่ครบ และ Field ที่ใส่ Class ผิดก็จะได้ Policy ผิดตามไปด้วย ด้านล่างเป็นภาพร่างของแนวคิดนี้กับสอง Column ของเรา (ชื่อ Field เป็นของผู้เขียนเอง ไม่ใช่มาตรฐาน)

```yaml
schema:
  - {name: email, type: VARCHAR, personal_data: true, class: contact_details, anonymize: hash}
  - {name: country, type: VARCHAR, personal_data: false, class: reference}
```

</Step>

## Catalog, Scorecard และ Annotation

Data Catalog เก็บ Metadata ทางเทคนิคของ Dataset (Schema, ชื่อ Table และ Column, Description) และ Metadata ทางธุรกิจ เช่น ใครเป็นเจ้าของ สร้างเองหรือซื้อมา และใช้ใน Production หรือใช้ทดสอบ เมื่อ Governance โตขึ้น เราก็แนบ Data Class, Quality และ Sensitivity เข้าไปได้ด้วย เพื่อให้ค้นหาอย่างเช่น "ทุก Table ของ Class X ใน Production" ได้ (หนังสือ: Governance บทที่ 2 หน้า 44 ถึง 45)

สำหรับเรื่องคุณภาพ บทที่ 5 ของเล่มเดียวกันเสนอนิสัยสามอย่างที่ลงทุนน้อย (หนังสือ: Governance บทที่ 5 หน้า 123)

- Scorecard ต่อแหล่งข้อมูลจะบอกที่มา Accuracy, Completeness, Timeliness รวมถึง Administrative Owner และใครเป็นคนขอ ซึ่งคนสร้าง Pipeline เอาไปใช้ตัดสินว่าจะใช้ข้อมูลจากที่ไหนและเพื่ออะไร
- Prioritization เพราะแหล่งข้อมูลแต่ละแหล่งสำคัญไม่เท่ากัน และ Lineage ก็ช่วยไล่ดูได้ว่าแหล่งไหนป้อนงานที่สำคัญ
- Annotation คือวิธีมาตรฐานในการติดป้ายแหล่งข้อมูลว่า Vetted หรือ Not Vetted ซึ่งทำได้แม้ยังทำ Scorecard เต็มรูปแบบไม่ได้ เราจึงเริ่มเล็ก ๆ ได้ เพื่อไม่ให้ข้อมูลกลายเป็น Tribal Knowledge หนังสือเล่าถึงการให้ผู้ใช้ให้คะแนนข้อมูล โดยตั้งค่าเริ่มต้นเป็นไม่เชื่อถือ และให้ Curator ตรวจคะแนนสูงก่อนปล่อยออกเป็นสัญญาณคุณภาพ

หนังสือเล่าถึงบริษัท Healthcare ที่โตเร็ว ซื้อบริษัทอื่นเข้ามาเพราะข้อมูลของเขาส่วนหนึ่ง แล้วพบว่า Dictionary, Metadata และการจัดการคุณภาพของสองฝั่งรวมกันไม่ได้ บทเรียนที่ได้คือต้องมีแนวทาง Governance ส่วนกลางที่ขยายไปถึงบริษัทที่ซื้อมาด้วย (หนังสือ: Governance บทที่ 5 หน้า 123) Scorecard กับ Annotation ก็คือฉบับเล็กของสิ่งที่[บท 10](/data-quality/ownership-scorecard/#data-certification) เรียกว่า Certification

</Step>

## Lineage และข้อมูลที่คุณภาพปนกัน

Governance ให้เหตุผลหลายข้อว่าทำไมควรตาม Lineage ข้อแรกคือทีมส่วนใหญ่ใช้เวลาไปกับการหาว่ามีปัญหาหรือเปล่า มากกว่าการแก้ปัญหา การตามที่ดีขึ้นจึงช่วยประหยัดเวลาส่วนนั้นได้ ข้อต่อมา Lineage ยังอธิบายคุณภาพของผลลัพธ์ได้ด้วย Dashboard ที่สร้างจากข้อมูลดีแต่ถูกรวมกับข้อมูลแย่ทีหลัง ก็ควรถูกอ่านต่างออกไป และมันช่วยอธิบายย้อนหลังได้ว่าการตัดสินใจอย่างการอนุมัติสินเชื่อใช้ Input อะไร ส่วน Tool ที่ซับซ้อนกว่านั้นยังตาม Lineage ข้ามเวลาได้ด้วย (หนังสือ: Governance บทที่ 2 หน้า 46 ถึง 47)

เรื่อง Join หนังสือพูดไว้ตรง ๆ ว่า การรู้คุณภาพของแต่ละแหล่งควรเป็นตัวชี้ว่าจะ Join Dataset ที่คุณภาพต่างกันหรือไม่ เพราะข้อมูลคุณภาพต่ำจะลดความเชื่อมั่นต่อข้อมูลคุณภาพสูง Dataset จึงควรมีระดับความเชื่อมั่นต่างกัน และผลลัพธ์ที่มีต้นตอคุณภาพปนกันควรถูกคัดสรรก่อนใช้ (หนังสือ: Governance บทที่ 2 หน้า 45 ถึง 46) เรื่องนี้เกิดขึ้นจริงใน[บท 10](/data-quality/ownership-scorecard/#trend-ค่าเฉลี่ยขยับน้อยกว่าความจริง) ตอนที่การล้าง Table หนึ่งทำให้ Table ข้างเคียงดูแย่ลง ซึ่งถ้ามี Lineage เราก็จะเห็นว่า Table ไหนพึ่ง Table ไหน

</Step>

## เมื่อข้อมูลป้อน Model

Governance แยกหัวข้อ Machine Learning ไว้ต่างหาก เพราะ Model ประมาณการจากข้อมูลที่มี Error ใน Input จึงมักขยาย Error นั้นออกไป และถ้าผลทำนายถูกนำไปลงมือทำจริงแล้วป้อนกลับเข้ามาอีก ผลทำนายก็จะกลายเป็นความจริง ทำให้ Error โตขึ้นผ่าน positive feedback loop ข้อมูลยังถูกแบ่งเป็น Training, Validation และ Test โดย Error ใน Set ใดก็ได้ล้วนทำให้ Train Model ออกมาไม่ดี หนังสือยังชี้ Trade-off ไว้ด้วยว่า การล้าง Error ทุกตัวด้วยมือมักแพงเกินไป ขณะที่ Model ที่ทนทานก็รับ Error ได้ในระดับหนึ่ง (หนังสือ: Governance บทที่ 5 หน้า 117 ถึง 121)

ฝั่ง Warehouse เพื่อ Analytics แรงกดดันจะต่างออกไป Warehouse รวมข้อมูลจากหลายแหล่ง ทั้งการรับข้อมูล การล้าง การแปลง และการเชื่อม จึงเป็นจุดที่คุณภาพตกได้ และอะไรถือว่าดีพอก็ขึ้นกับการใช้งาน หนังสือเทียบ Warehouse ค้าปลีกที่ปัดเศษห้าสตางค์ กับ Warehouse เทรดหุ้นที่ต้องแม่นระดับ Microsecond (หนังสือ: Governance บทที่ 5 หน้า 116 ถึง 117)

เรื่องเล่าจากบทเดียวกันแสดงให้เห็นว่าคุณภาพผูกอยู่กับการใช้งาน สัมมนาของนักบรรพชีวินวิทยาพบว่าคำว่า "Bone" และคำสามัญอื่นของสาขาตัวเองถูกซ่อนจากแชทและคำบรรยาย เพราะแพลตฟอร์มประชุมสร้างมาสำหรับโรงเรียนและกรองคำที่ไม่เหมาะกับที่นั่น ตัวกรองเดียวกันนี้เมื่อไปอยู่ในงานประชุมวิทยาศาสตร์จึงกลายเป็น Defect (หนังสือ: Governance บทที่ 5 หน้า 121 ถึง 122) ตรงนี้ก็คือ[บท 1](/data-quality/assurance-basics/#quality-คือ-เหมาะกับการใช้งาน) อีกครั้ง คือเหมาะกับวัตถุประสงค์ของ Consumer

เส้นทางนี้ไม่มีแบบฝึกเรื่องข้อมูลสำหรับ Machine Learning แต่การตรวจของ[บท 2](/data-quality/dimensions/) ถึง [8](/data-quality/reconciliation/) ก็ใช้กับ Training Data ได้เหมือนกัน และ Model ซ่อน Input ที่แย่ได้เก่งกว่ารายงานเสียอีก

</Step>

## สิ่งที่เส้นทางนี้ยังไม่ครอบคลุม

เมื่อมีบทนี้และบท Ten Steps สองข้อในรายการช่องว่างของ Capstone ก็มีคำอธิบายแล้ว ได้แก่ วัฒนธรรมและการสื่อสาร ([บท 12](/data-quality/ten-steps/#พาคนไปด้วย)) กับ Privacy และ Machine Learning ในระดับแนวคิด (บทนี้) ซึ่งทั้งสองข้อยังไม่มีแบบฝึก ส่วนที่ยังไม่ครอบคลุมคือแบบฝึก Reasonability โดยเฉพาะ ([บท 7](/data-quality/monitoring/#volume-ฤดูกาลทำให้-z-score-หลง) แตะผ่าน Monitoring) รายละเอียดของเครื่องมือเฉพาะตัว และข้อมูล Streaming จริง

</Step>

## เช็กตัวเอง

- ใครคือคนหนึ่งคนที่ Accountable ต่อ Dataset ที่สำคัญที่สุดของคุณ และความรับผิดชอบนั้นตั้งไว้ที่ระดับไหน เป็น Table, Stream หรือ Field เดียว
- Catalog หรือ Contract ของคุณบอกไหมว่าแต่ละ Field เป็นข้อมูลส่วนบุคคลหรือไม่ และจัดชั้นอย่างไร แล้วใครเป็นคนกรอก และใครรู้ตัวเมื่อมันผิด
