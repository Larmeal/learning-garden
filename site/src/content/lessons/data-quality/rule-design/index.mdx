## กฎคือคำสัญญาที่ตรวจได้

DMBOK2 บอกว่ากฎและมาตรฐานคุณภาพข้อมูลเป็น metadata ชนิดสำคัญ ต้องบริหารแบบ metadata (หนังสือ: DMBOK2 §2.7.1) การกำหนดกฎตั้งแต่ต้นให้ประโยชน์สี่อย่าง

- ตั้งความคาดหวังที่ชัดเจนของคุณลักษณะด้านคุณภาพ
- เป็นความต้องการให้ระบบมี edit และ control กันข้อมูลเสียตั้งแต่ต้น
- เป็นความต้องการที่ส่งให้ผู้ขายหรือฝ่ายนอกที่ส่งข้อมูลมา
- เป็นฐานของการวัดและรายงานผลต่อเนื่อง

บท 3 เราได้ "กฎที่เสนอ" จาก profile บทนี้เปลี่ยนข้อเสนอเป็นกฎที่ใช้งานได้ และกำหนดว่าเมื่อไรจึงจะเชื่อกฎนั้นพอที่จะให้มันหยุด pipeline

</Step>

<Step>

## หกข้อของกฎที่ดี

DMBOK2 §2.7.1 ระบุว่ากฎที่มีประสิทธิผลควรเป็นดังนี้ (หนังสือ) ตารางด้านขวาคือการจับคู่กับช่องใน `Rule` ของแบบฝึก (ผู้เขียน)

| กฎที่ดีต้อง | ความหมาย | ช่องใน `Rule` |
|---|---|---|
| บันทึกอย่างสม่ำเสมอ | ใช้แม่แบบเดียวกัน ความหมายตรงกัน | ทุกกฎมีช่องชุดเดียวกัน |
| นิยามตามมิติ | ผู้อ่านรู้ว่ากำลังวัดอะไร | `dimension` |
| ผูกกับผลกระทบทางธุรกิจ | มิติไม่ใช่เป้าหมายในตัวมันเอง วัดสิ่งที่ไม่ผูกกับกระบวนการธุรกิจก็ไม่ควรวัด | `impact` |
| มีการวิเคราะห์ข้อมูลรองรับ | นักวิเคราะห์ไม่ควรเดากฎ ทดสอบกับข้อมูลจริง | `origin` และผล profile |
| ผู้เชี่ยวชาญยืนยัน | กฎอธิบายว่าข้อมูลควรหน้าตาอย่างไร ต้องมีคนรู้กระบวนการยืนยัน | `confirmed_by`, `status` |
| ผู้ใช้ข้อมูลเข้าถึงได้ | ให้ถามและแย้งได้ | ทะเบียนอยู่ใน repo ที่ทุกคนอ่านได้ |

หนังสือยังบอกด้วยว่า การวิเคราะห์อาจแสดงว่ากฎเองไม่ครบก็ได้ ไม่ใช่ข้อมูลผิดอย่างเดียว

</Step>

## กฎมาจากไหน

DMBOK2 §2.3 ยอมรับว่ากฎมักไม่มีใครจดไว้ ต้องย้อนหาจากกระบวนการธุรกิจ นโยบาย มาตรฐาน กฎหมาย โค้ดระบบ trigger การใช้รหัสสถานะ และสามัญสำนึก (หนังสือ) หนังสือแนะนำให้ถามผู้เกี่ยวข้องว่า ถ้าข้อมูลหายหรือผิดจะเกิดอะไร รู้ได้อย่างไร และเคยเจอข้อมูลเสียแบบไหน

แบบฝึกจัดที่มาเป็นสามกลุ่ม (**การจัดกลุ่มนี้เป็นของผู้เขียน**)

| ที่มา | ตัวอย่างในทะเบียน | ใครยืนยัน |
|---|---|---|
| ธุรกิจ (business) | ลูกค้าต้องมีอีเมล, SHIPPED ต้องมีเวลาส่ง | ผู้ใช้ข้อมูลหรือเจ้าของกระบวนการ |
| เทคนิค (technical) | order_id ไม่ซ้ำ, คีย์อ้างอิงต้องมีตัวจริง | วิศวกรหรือเจ้าของระบบ |
| สถิติ (statistical) | ยอดไม่ติดลบ (มาจากการดู profile) | ต้องมีคนรู้ธุรกิจยืนยันก่อนใช้ |

กฎระดับคอลัมน์ตรงไปตรงมา ส่วนกฎระดับชุดข้อมูลมักอ่านยากกว่า เช่น "ลูกค้าทุกคนต้องมีที่อยู่ส่งไปรษณีย์ที่ใช้ได้" (หนังสือ: DMBOK2 §2.3)

</Step>

## ทะเบียนกฎ: query พร้อมเจ้าของ เกณฑ์ และผลกระทบ

```python
@dataclass(frozen=True)
class Rule:
    id: str            # "ORD-ID-UNIQUE"
    dimension: str     # "uniqueness"
    table: str
    statement: str     # ประโยคที่คนธุรกิจอ่านแล้วยืนยันได้
    sql: str           # คืน (แถวที่ผิด, แถวที่กฎนี้ใช้กับ)
    max_bad_pct: float # เกณฑ์ที่ยอมรับ
    severity: str      # "error" ขวาง pipeline ได้, "warn" แค่รายงาน
    owner: str
    impact: str
    origin: str        # business, technical, statistical
    status: str        # active, proposed
    confirmed_by: str | None
```

ทะเบียนมี 14 กฎ ผลที่รันได้ (รัน: `04_rules.py` และทุกกฎเจอตรงจำนวนที่ฝัง)

| กฎ | มิติ | ระดับ | สถานะ | ไม่ผ่าน% | ยอมได้% | ผล |
|---|---|---|---|---:|---:|---|
| CUST-EMAIL-POPULATED | completeness | warn | active | 8.00 | 2.0 | ไม่ผ่าน |
| CUST-EMAIL-SHAPE | validity | warn | active | 3.26 | 1.0 | ไม่ผ่าน |
| CUST-EMAIL-UNIQUE | uniqueness | warn | active | 2.17 | 0.5 | ไม่ผ่าน |
| CUST-COUNTRY-DOMAIN | validity | error | active | 5.00 | 0.0 | ไม่ผ่าน |
| CUST-BIRTH-RANGE | validity | warn | active | 1.20 | 0.0 | ไม่ผ่าน |
| ORD-CUST-POPULATED | completeness | error | active | 0.50 | 0.0 | ไม่ผ่าน |
| ORD-ID-UNIQUE | uniqueness | error | active | 0.66 | 0.0 | ไม่ผ่าน |
| ORD-TOTAL-SIGN | validity | warn | **proposed** | 0.40 | 0.0 | ไม่ผ่าน |
| ORD-SHIPPED-HAS-TS | consistency | warn | active | 1.39 | 0.5 | ไม่ผ่าน |
| ORD-SHIP-AFTER-ORDER | consistency | warn | active | 0.57 | 0.0 | ไม่ผ่าน |
| ORD-CUST-EXISTS | integrity | error | active | 1.00 | 0.1 | ไม่ผ่าน |
| PAY-ORDER-EXISTS | integrity | error | active | 0.78 | 0.0 | ไม่ผ่าน |
| ORD-ARRIVES-24H | timeliness | warn | active | 1.32 | 1.0 | ไม่ผ่าน |
| ORD-TOTAL-MATCHES-PAID | accuracy | error | active | 1.38 | 0.1 | ไม่ผ่าน |

ทั้ง 14 ข้อไม่ผ่านเพราะชุดข้อมูลนี้ถูกสร้างให้มีข้อมูลเสียทุกชนิด **เกณฑ์ เจ้าของ ผลกระทบ และระดับ ทั้งหมดเป็นตัวอย่างที่ผู้เขียนตั้งเพื่อสอน** ไม่ใช่ตัวเลขที่มาจากหนังสือหรือธุรกิจจริง

</Step>

<Step>

## เกณฑ์ที่ยอมรับ ไม่ใช่ศูนย์เสมอไป

ผลการวัดเดียวกันอาจผ่านหรือไม่ผ่านขึ้นกับเกณฑ์ ตัวอย่างอีเมลซ้ำ 2.17%

| เกณฑ์ | ผล |
|---|---|
| 0.0% | ไม่ผ่าน |
| 0.5% | ไม่ผ่าน |
| 2.0% | ไม่ผ่าน |
| 5.0% | ผ่าน |

DMBOK2 ให้ตัวอย่างสถานะแบบนี้ใน Table 30: ความสมบูรณ์ต่ำกว่า 80% คือ "ยอมรับไม่ได้" และการมาไม่ทันเวลาเกิน 1% คือ "ยอมรับไม่ได้" ตัวเลขเหล่านั้นเป็นตัวอย่างในหนังสือ ไม่ใช่เกณฑ์ที่ใช้ได้ทั่วไป เกณฑ์ต้องมาจากผู้ใช้ข้อมูล (บท 1) และ DMBOK2 §4.4 เรียกคุณลักษณะนี้ว่า **acceptability** สองสิ่งที่ตัดสินใจแยกกัน

- **เกณฑ์** (`max_bad_pct`): ผิดได้เท่าไรจึงยังเรียกว่าพอรับได้
- **ระดับ** (`severity`): ถ้าเกินเกณฑ์ แค่รายงาน (`warn`) หรือหยุด pipeline (`error`) ในแบบฝึก มี 6 กฎระดับ error ที่ไม่ผ่านพร้อมกัน หยุดได้เฉพาะ 6 กฎนี้ และ `ORD-TOTAL-SIGN` ที่ยังเป็น `proposed` จะรายงานแต่ไม่หยุดอะไร เพราะยังไม่มีใครยืนยันว่าค่าติดลบผิดจริง (อาจเป็นการคืนเงิน บทที่ 3)

</Step>

## metric ที่ดีหกลักษณะ

DMBOK2 §4.4 ให้ลักษณะของ metric ที่ควรลงมือวัด (หนังสือ) ทบทวนกับกฎของเรา

| ลักษณะ | ถามว่า | ถ้าไม่มี |
|---|---|---|
| Measurability | นับได้และกำหนดช่วงผลได้ไหม | "ข้อมูลเกี่ยวข้อง" วัดไม่ได้จนกว่าจะนิยามเกณฑ์ |
| Business relevance | เชื่อมกับการดำเนินธุรกิจไหม | วัดได้แต่ไม่มีใครสน |
| Acceptability | มีเกณฑ์ว่าพอหรือไม่พอไหม | ได้ตัวเลขแต่ตัดสินไม่ได้ |
| Accountability | เจ้าของธุรกิจอนุมัติ และมีคนแก้เมื่อไม่ผ่านไหม | แจ้งเตือนแล้วไม่มีใครรับ |
| Controllability | ถ้าออกนอกช่วงแล้วทำอะไรได้ไหม | หนังสือว่า "คงไม่มีประโยชน์" |
| Trending | ดูแนวโน้มข้ามเวลาได้ไหม | เห็นแค่ภาพถ่ายนิ่ง (บท 7 และ 10) |

ข้อ Controllability สำคัญ: ถ้าค่าออกนอกช่วงแล้วไม่มีใครตอบสนองได้ ก็ไม่ควรวัด `lint()` ในแบบฝึกตรวจข้อนี้ผ่านช่อง `owner` และ `impact`

</Step>

## กฎที่มากเกินไปและไม่มีใครเชื่อ

DQF เตือนเรื่องการเขียน test จำนวนมากโดยไม่มีเหตุผลรองรับ ถ้านักพัฒนาเพิ่ม test เพราะคิดว่ามี test ดีกว่าไม่มี อีกหลายเดือนต่อมาอีกคนทำให้ test ล้มและไม่เข้าใจว่าทำไมต้องมี เขาจะลบ test เพื่อให้ CI ผ่าน วัฒนธรรมแบบนี้ทำให้ test เป็นสิ่งกีดขวาง ไม่ใช่ข้อมูลเชิงลึก หนังสือสรุปว่า "ถ้าไม่ตั้งใจจะจริงจังกับ test ไม่มี test เลยดีกว่า" (หนังสือ: DQF ch.3)

ทะเบียนกฎจึงมี `lint()` ที่ปฏิเสธกฎซึ่งไม่น่าเชื่อถือ กฎลวงตา `MKT-MAGIC` ที่ตั้งใจเขียนให้แย่ถูกจับได้ห้าข้อ (รัน: `04_rules.py`)

```text
MKT-MAGIC: dimension 'goodness' is not one of the agreed names
MKT-MAGIC: no owner: nobody is accountable when it fails
MKT-MAGIC: no business impact: why is this measured?
MKT-MAGIC: threshold must be a percentage between 0 and 100
MKT-MAGIC: active rule has not been confirmed by a subject matter expert
```

เครื่องมือเช่น GX และ dbt เก็บ "กฎที่รันได้" แต่ช่องอย่างเจ้าของ ผลกระทบ และผู้ยืนยัน ต้องเป็นวินัยของทีมเอง (บทที่ 5 พูดถึงเครื่องมือเหล่านี้ และเส้นทาง Great Expectations สอนการเขียนกฎใน GX)

<Callout type="try" title="ลองทำใน repo นี้">
เปิด `dqrules.py` เพิ่มกฎของตัวเอง เช่น "signup_date ไม่เป็นวันในอนาคต" ใส่เจ้าของ ผลกระทบ และเกณฑ์ แล้วรัน `04_rules.py` ถ้าลืมช่องใดช่องหนึ่ง `lint()` จะบอก ลองตั้ง `status="active"` โดยไม่ใส่ `confirmed_by` ดูว่าเกิดอะไรขึ้น
</Callout>

## เช็กตัวเอง

- กฎ "ยอดไม่ติดลบ" ถูกตั้งเป็น `proposed` ใครควรเป็นคนเปลี่ยนเป็น `active` และต้องถามอะไรก่อน
- ถ้ากฎอีเมลซ้ำตั้งเป็น `error` เกณฑ์ 0% pipeline จะหยุดทุกคืน ใครเสียหาย ใครควรเป็นคนตัดสินว่าเป็น `warn` หรือ `error`
- กฎที่ไม่มีใครรับผิดชอบเมื่อล้ม ควรลบหรือหาเจ้าของ คุณเลือกอะไร และใช้เกณฑ์อะไรตัดสิน

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| ประโยชน์สี่ข้อของกฎ, หกลักษณะของกฎที่ดี | หนังสือ: DMBOK2 §2.7.1 |
| กฎมักไม่ได้จดไว้ ต้องย้อนหา, กฎระดับคอลัมน์และชุดข้อมูล | หนังสือ: DMBOK2 §2.3 |
| ตัวอย่างสถานะยอมรับได้และไม่ได้ | หนังสือ: DMBOK2 Table 30 |
| หกลักษณะของ metric ที่ดี | หนังสือ: DMBOK2 §4.4 |
| test ที่ไม่มีเหตุผลรองรับ | หนังสือ: DQF ch.3 (หัวข้อ test fatigue ของ dbt) |
| ตัวเลขผลการรัน 14 กฎ, lint จับ 5 ข้อ | รัน: `04_rules.py` |
| โครง `Rule`, การจัดที่มาเป็น 3 กลุ่ม, เกณฑ์ เจ้าของ ผลกระทบ และระดับ error/warn ทุกค่า | ผู้เขียน |

</Step>
