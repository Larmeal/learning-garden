## Rule คือคำสัญญาที่ตรวจได้

DMBOK2 บอกว่า Data Quality Rule และมาตรฐานเป็น Metadata ชนิดสำคัญ ซึ่งต้องบริหารแบบ Metadata (หนังสือ: DMBOK2 หัวข้อ 2.7.1 หน้า 478) และการกำหนด Rule ตั้งแต่ต้นก็ให้ประโยชน์สี่อย่าง

- ช่วยตั้งความคาดหวังที่ชัดเจนของคุณลักษณะด้านคุณภาพ
- เป็น Requirement ให้ระบบมี Edit และ Control กัน Bad Data ตั้งแต่ต้น
- เป็น Requirement ที่ส่งให้ Vendor หรือฝ่ายนอกที่ส่งข้อมูลมา
- เป็นฐานของการวัดและรายงานผลต่อเนื่อง

ใน[บท 3](/data-quality/profiling/#จากสิ่งที่เห็นเป็น-rule-ที่เสนอ) เราได้ "Rule ที่เสนอ" มาจาก Profile ส่วนในบทนี้เราจะเปลี่ยนข้อเสนอเหล่านั้นเป็น Rule ที่ใช้งานได้ และกำหนดว่าเมื่อไรเราจึงจะเชื่อ Rule นั้นมากพอที่จะให้มันหยุด Pipeline

</Step>

## หกข้อของ Rule ที่ดี

DMBOK2 หัวข้อ 2.7.1 หน้า 478 ระบุว่า Rule ที่มีประสิทธิผลควรเป็นดังนี้ (หนังสือ) ส่วนคอลัมน์ด้านขวาของตารางคือการจับคู่กับ Field ใน `Rule` ของแบบฝึก (ผู้เขียน)

| Rule ที่ดีต้อง | ความหมาย | Field ใน `Rule` |
|---|---|---|
| บันทึกอย่างสม่ำเสมอ | ใช้ Template เดียวกัน ความหมายตรงกัน | ทุก Rule มี Field ชุดเดียวกัน |
| นิยามตาม Dimension | ผู้อ่านรู้ว่ากำลังวัดอะไร | `dimension` |
| ผูกกับ Business Impact | Dimension ไม่ใช่เป้าหมายในตัวมันเอง วัดสิ่งที่ไม่ผูกกับ Business Process ก็ไม่ควรวัด | `impact` |
| มีการวิเคราะห์ข้อมูลรองรับ | Analyst ไม่ควรเดา Rule ทดสอบกับข้อมูลจริง | `origin` และผล Profile |
| SME ยืนยัน | Rule อธิบายว่าข้อมูลควรหน้าตาอย่างไร ต้องมีคนรู้ Process ยืนยัน | `confirmed_by`, `status` |
| Data Consumer เข้าถึงได้ | ให้ถามและแย้งได้ | Registry อยู่ใน Repo ที่ทุกคนอ่านได้ |

หนังสือยังบอกด้วยว่า การวิเคราะห์อาจแสดงให้เห็นว่าตัว Rule เองก็ไม่ครบได้เหมือนกัน นอกจากข้อมูลที่ผิด

</Step>

## Rule มาจากไหน

DMBOK2 หัวข้อ 2.3 หน้า 474 ถึง 475 ยอมรับว่า Rule มักไม่มีใครจดไว้ จึงต้องย้อนหาจาก Business Process นโยบาย มาตรฐาน กฎหมาย โค้ดของระบบ Trigger การใช้รหัสสถานะ และสามัญสำนึก (หนังสือ) หนังสือแนะนำให้ถาม Stakeholder ว่า ถ้าข้อมูลหายหรือผิดจะเกิดอะไร รู้ได้อย่างไร และเคยเจอ Bad Data แบบไหน

ในแบบฝึก เราจัดที่มาของ Rule เป็นสามกลุ่ม (**การจัดกลุ่มนี้เป็นของผู้เขียน**)

| ที่มา | ตัวอย่างใน Registry | ใครยืนยัน |
|---|---|---|
| Business | Customer ต้องมี Email, SHIPPED ต้องมีเวลาส่ง | Data Consumer หรือเจ้าของ Process |
| Technical | order_id ไม่ซ้ำ, Foreign Key ต้องมีตัวจริง | Engineer หรือเจ้าของระบบ |
| Statistical | ยอดไม่ติดลบ (มาจากการดู Profile) | ต้องมีคนรู้ธุรกิจยืนยันก่อนใช้ |

Rule ระดับ Column ตรงไปตรงมา ส่วน Rule ระดับ Dataset มักอ่านยากกว่า เช่น "Customer ทุกคนต้องมีที่อยู่ส่งไปรษณีย์ที่ใช้ได้" (หนังสือ: DMBOK2 หัวข้อ 2.3 หน้า 474 ถึง 475)

</Step>

## Rule Registry: Query พร้อมเจ้าของ Threshold และ Impact

```python
@dataclass(frozen=True)
class Rule:
    id: str            # "ORD-ID-UNIQUE"
    dimension: str     # "uniqueness"
    table: str
    statement: str     # ประโยคที่คนธุรกิจอ่านแล้วยืนยันได้
    sql: str           # คืน (row ที่ผิด, row ที่ rule นี้ใช้กับ)
    max_bad_pct: float # threshold ที่ยอมรับ
    severity: str      # "error" ขวาง pipeline ได้, "warn" แค่รายงาน
    owner: str
    impact: str
    origin: str        # business, technical, statistical
    status: str        # active, proposed
    confirmed_by: str | None
```

Registry มี 14 Rule และเมื่อรันแล้วได้ผลตามนี้ (รัน: `04_rules.py` และทุก Rule เจอตรงจำนวนที่ฝัง)

|---|---|---|---|---:|---:|---|
| CUST-EMAIL-POPULATED | Completeness | Warn | Active | 8.00 | 2.0 | ไม่ผ่าน |
| CUST-EMAIL-SHAPE | Validity | Warn | Active | 3.26 | 1.0 | ไม่ผ่าน |
| CUST-EMAIL-UNIQUE | Uniqueness | Warn | Active | 2.17 | 0.5 | ไม่ผ่าน |
| CUST-COUNTRY-DOMAIN | Validity | Error | Active | 5.00 | 0.0 | ไม่ผ่าน |
| CUST-BIRTH-RANGE | Validity | Warn | Active | 1.20 | 0.0 | ไม่ผ่าน |

## Threshold ที่ยอมรับ ไม่ใช่ศูนย์เสมอไป

ผลการวัดเดียวกันอาจผ่านหรือไม่ผ่านก็ได้ ขึ้นอยู่กับ Threshold ยกตัวอย่าง Email ซ้ำ 2.17%

| Threshold | ผล |
|---|---|
| 0.0% | ไม่ผ่าน |
| 0.5% | ไม่ผ่าน |
| 2.0% | ไม่ผ่าน |
| 5.0% | ผ่าน |

DMBOK2 ให้ตัวอย่างสถานะแบบนี้ไว้ใน Table 30 หน้า 480 โดย Completeness ต่ำกว่า 80% คือ "ยอมรับไม่ได้" และการมาไม่ทันเวลาเกิน 1% ก็คือ "ยอมรับไม่ได้" เช่นกัน ตัวเลขเหล่านั้นเป็นตัวอย่างในหนังสือ ไม่ใช่ Threshold ที่ใช้ได้ทั่วไป Threshold ต้องมาจาก Data Consumer ([บท 1](/data-quality/assurance-basics/#quality-คือ-เหมาะกับการใช้งาน)) และ DMBOK2 หัวข้อ 4.4 หน้า 487 ถึง 488 เรียกคุณลักษณะนี้ว่า **Acceptability** ซึ่งมีสองสิ่งที่ต้องตัดสินใจแยกกัน

- **Threshold** (`max_bad_pct`) คือผิดได้เท่าไรจึงยังเรียกว่าพอรับได้
- **Severity** (`severity`) คือถ้าเกิน Threshold แล้วจะแค่รายงาน (`warn`) หรือหยุด Pipeline (`error`) ในแบบฝึกมี 6 Rule ระดับ Error ที่ไม่ผ่านพร้อมกัน ซึ่งหยุดได้เฉพาะ 6 Rule นี้ ส่วน `ORD-TOTAL-SIGN` ที่ยังเป็น `proposed` จะรายงานอย่างเดียวและไม่หยุดอะไร เพราะยังไม่มีใครยืนยันว่าค่าติดลบผิดจริง (อาจเป็นการคืนเงิน [บทที่ 3](/data-quality/profiling/#จากสิ่งที่เห็นเป็น-rule-ที่เสนอ))

</Step>

## Metric ที่ดีหกลักษณะ

DMBOK2 หัวข้อ 4.4 หน้า 487 ถึง 488 ให้ลักษณะของ Metric ที่ควรลงมือวัด (หนังสือ) ลองเอามาทบทวนกับ Rule ของเรากัน

| ลักษณะ | ถามว่า | ถ้าไม่มี |
|---|---|---|
| Measurability | นับได้และกำหนดช่วงผลได้ไหม | "ข้อมูลเกี่ยวข้อง" วัดไม่ได้จนกว่าจะนิยาม Threshold |
| Business Relevance | เชื่อมกับการดำเนินธุรกิจไหม | วัดได้แต่ไม่มีใครสน |
| Acceptability | มี Threshold ว่าพอหรือไม่พอไหม | ได้ตัวเลขแต่ตัดสินไม่ได้ |
| Accountability | เจ้าของธุรกิจอนุมัติ และมีคนแก้เมื่อไม่ผ่านไหม | แจ้งเตือนแล้วไม่มีใครรับ |
| Controllability | ถ้าออกนอกช่วงแล้วทำอะไรได้ไหม | หนังสือว่า "คงไม่มีประโยชน์" |
| Trending | ดู Trend ข้ามเวลาได้ไหม | เห็นแค่ภาพถ่ายนิ่ง ([บท 7](/data-quality/monitoring/) และ [10](/data-quality/ownership-scorecard/#trend-ค่าเฉลี่ยขยับน้อยกว่าความจริง)) |

ข้อ Controllability สำคัญตรงที่ว่า ถ้าค่าออกนอกช่วงแล้วไม่มีใครตอบสนองได้ ก็ไม่ควรวัด ซึ่ง `lint()` ในแบบฝึกตรวจข้อนี้ผ่าน Field `owner` และ `impact`

</Step>

## Rule ที่มากเกินไปและไม่มีใครเชื่อ

DQF เตือนเรื่องการเขียน Test จำนวนมากโดยไม่มีเหตุผลรองรับ ถ้า Developer คนหนึ่งเพิ่ม Test เพราะคิดว่ามี Test ดีกว่าไม่มี แล้วอีกหลายเดือนต่อมามีอีกคนทำให้ Test นั้นล้มและไม่เข้าใจว่าทำไมต้องมี เขาก็จะลบ Test ทิ้งเพื่อให้ CI ผ่าน วัฒนธรรมแบบนี้ทำให้ Test กลายเป็นสิ่งกีดขวาง แทนที่จะเป็นข้อมูลเชิงลึก หนังสือสรุปว่า "ถ้าไม่ตั้งใจจะจริงจังกับ Test ไม่มี Test เลยดีกว่า" (หนังสือ: DQF บทที่ 3 หน้า 58)

Registry จึงมี `lint()` ที่ปฏิเสธ Rule ซึ่งไม่น่าเชื่อถือ ลองดู Rule ลวงตา `MKT-MAGIC` ที่ตั้งใจเขียนให้แย่ ซึ่งถูกจับได้ห้าข้อ (รัน: `04_rules.py`)

```text
MKT-MAGIC: dimension 'goodness' is not one of the agreed names
MKT-MAGIC: no owner: nobody is accountable when it fails
MKT-MAGIC: no business impact: why is this measured?
MKT-MAGIC: threshold must be a percentage between 0 and 100
MKT-MAGIC: active rule has not been confirmed by a subject matter expert
```

เครื่องมืออย่าง GX และ Dbt เก็บ "Rule ที่รันได้" ให้เรา แต่ Field อย่าง Owner, Impact และผู้ยืนยัน ต้องอาศัยวินัยของทีมเอง ([บทที่ 5](/data-quality/checkpoints/#เครื่องมือที่ทำ-assert-ว่าข้อมูลเป็นอย่างที่คาด) พูดถึงเครื่องมือเหล่านี้ และเส้นทาง Great Expectations สอนการเขียน Rule ใน GX)

<Callout type="try" title="ลองทำใน Repo นี้">
เปิด `dqrules.py` แล้วลองเพิ่ม Rule ของตัวเอง เช่น "signup_date ไม่เป็นวันในอนาคต" ใส่ Owner, Impact และ Threshold แล้วรัน `04_rules.py` ถ้าลืม Field ใด Field หนึ่ง `lint()` จะบอก ลองตั้ง `status="active"` โดยไม่ใส่ `confirmed_by` ดูว่าเกิดอะไรขึ้น
</Callout>

## เช็กตัวเอง

- Rule "ยอดไม่ติดลบ" ถูกตั้งเป็น `proposed` ใครควรเป็นคนเปลี่ยนเป็น `active` และต้องถามอะไรก่อน
- ถ้า Rule Email ซ้ำตั้งเป็น `error` Threshold 0% Pipeline จะหยุดทุกคืน ใครเสียหาย ใครควรเป็นคนตัดสินว่าเป็น `warn` หรือ `error`
- Rule ที่ไม่มีใครรับผิดชอบเมื่อล้ม ควรลบหรือหาเจ้าของ คุณเลือกอะไร และใช้เกณฑ์อะไรตัดสิน

</Step>

| ข้อความ | ที่มา |
|---|---|
| ประโยชน์สี่ข้อของ Rule, หกลักษณะของ Rule ที่ดี | หนังสือ: DMBOK2 หัวข้อ 2.7.1 หน้า 478 |
| Rule มักไม่ได้จดไว้ ต้องย้อนหา, Rule ระดับ Column และ Dataset | หนังสือ: DMBOK2 หัวข้อ 2.3 หน้า 474 ถึง 475 |

| หกลักษณะของ Metric ที่ดี | หนังสือ: DMBOK2 หัวข้อ 4.4 หน้า 487 ถึง 488 |

| ตัวเลขผลการรัน 14 Rule, Lint จับ 5 ข้อ | รัน: `04_rules.py` |
| โครง `Rule`, การจัดที่มาเป็น 3 กลุ่ม, Threshold, Owner, Impact และ Severity Error/Warn ทุกค่า | ผู้เขียน |

</Step>
