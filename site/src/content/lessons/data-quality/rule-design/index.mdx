## rule คือคำสัญญาที่ตรวจได้

DMBOK2 บอกว่า data quality rule และมาตรฐานเป็น metadata ชนิดสำคัญ ต้องบริหารแบบ metadata (หนังสือ: DMBOK2 §2.7.1) การกำหนด rule ตั้งแต่ต้นให้ประโยชน์สี่อย่าง

- ตั้งความคาดหวังที่ชัดเจนของคุณลักษณะด้านคุณภาพ
- เป็น requirement ให้ระบบมี edit และ control กัน bad data ตั้งแต่ต้น
- เป็น requirement ที่ส่งให้ vendor หรือฝ่ายนอกที่ส่งข้อมูลมา
- เป็นฐานของการวัดและรายงานผลต่อเนื่อง

บท 3 เราได้ "rule ที่เสนอ" จาก profile บทนี้เปลี่ยนข้อเสนอเป็น rule ที่ใช้งานได้ และกำหนดว่าเมื่อไรจึงจะเชื่อ rule นั้นพอที่จะให้มันหยุด pipeline

</Step>

## หกข้อของ rule ที่ดี

DMBOK2 §2.7.1 ระบุว่า rule ที่มีประสิทธิผลควรเป็นดังนี้ (หนังสือ) ตารางด้านขวาคือการจับคู่กับ field ใน `Rule` ของแบบฝึก (ผู้เขียน)

| rule ที่ดีต้อง | ความหมาย | field ใน `Rule` |
|---|---|---|
| บันทึกอย่างสม่ำเสมอ | ใช้ template เดียวกัน ความหมายตรงกัน | ทุก rule มี field ชุดเดียวกัน |
| นิยามตาม dimension | ผู้อ่านรู้ว่ากำลังวัดอะไร | `dimension` |
| ผูกกับ business impact | dimension ไม่ใช่เป้าหมายในตัวมันเอง วัดสิ่งที่ไม่ผูกกับ business process ก็ไม่ควรวัด | `impact` |
| มีการวิเคราะห์ข้อมูลรองรับ | analyst ไม่ควรเดา rule ทดสอบกับข้อมูลจริง | `origin` และผล profile |
| SME ยืนยัน | rule อธิบายว่าข้อมูลควรหน้าตาอย่างไร ต้องมีคนรู้ process ยืนยัน | `confirmed_by`, `status` |
| data consumer เข้าถึงได้ | ให้ถามและแย้งได้ | registry อยู่ใน repo ที่ทุกคนอ่านได้ |

หนังสือยังบอกด้วยว่า การวิเคราะห์อาจแสดงว่า rule เองไม่ครบก็ได้ ไม่ใช่ข้อมูลผิดอย่างเดียว

</Step>

## rule มาจากไหน

DMBOK2 §2.3 ยอมรับว่า rule มักไม่มีใครจดไว้ ต้องย้อนหาจาก business process นโยบาย มาตรฐาน กฎหมาย โค้ดของระบบ trigger การใช้รหัสสถานะ และสามัญสำนึก (หนังสือ) หนังสือแนะนำให้ถาม stakeholder ว่า ถ้าข้อมูลหายหรือผิดจะเกิดอะไร รู้ได้อย่างไร และเคยเจอ bad data แบบไหน

แบบฝึกจัดที่มาเป็นสามกลุ่ม (**การจัดกลุ่มนี้เป็นของผู้เขียน**)

| ที่มา | ตัวอย่างใน registry | ใครยืนยัน |
|---|---|---|
| business | customer ต้องมี email, SHIPPED ต้องมีเวลาส่ง | data consumer หรือเจ้าของ process |
| technical | order_id ไม่ซ้ำ, foreign key ต้องมีตัวจริง | engineer หรือเจ้าของระบบ |
| statistical | ยอดไม่ติดลบ (มาจากการดู profile) | ต้องมีคนรู้ธุรกิจยืนยันก่อนใช้ |

rule ระดับ column ตรงไปตรงมา ส่วน rule ระดับ dataset มักอ่านยากกว่า เช่น "customer ทุกคนต้องมีที่อยู่ส่งไปรษณีย์ที่ใช้ได้" (หนังสือ: DMBOK2 §2.3)

</Step>

## rule registry: query พร้อมเจ้าของ threshold และ impact

```python
@dataclass(frozen=True)
class Rule:
    id: str            # "ORD-ID-UNIQUE"
    dimension: str     # "uniqueness"
    table: str
    statement: str     # ประโยคที่คนธุรกิจอ่านแล้วยืนยันได้
    sql: str           # คืน (row ที่ผิด, row ที่ rule นี้ใช้กับ)
    max_bad_pct: float # threshold ที่ยอมรับ
    severity: str      # "error" ขวาง pipeline ได้, "warn" แค่รายงาน
    owner: str
    impact: str
    origin: str        # business, technical, statistical
    status: str        # active, proposed
    confirmed_by: str | None
```

registry มี 14 rule ผลที่รันได้ (รัน: `04_rules.py` และทุก rule เจอตรงจำนวนที่ฝัง)

| rule | dimension | severity | status | ไม่ผ่าน% | ยอมได้% | ผล |
|---|---|---|---|---:|---:|---|
| CUST-EMAIL-POPULATED | completeness | warn | active | 8.00 | 2.0 | ไม่ผ่าน |
| CUST-EMAIL-SHAPE | validity | warn | active | 3.26 | 1.0 | ไม่ผ่าน |
| CUST-EMAIL-UNIQUE | uniqueness | warn | active | 2.17 | 0.5 | ไม่ผ่าน |
| CUST-COUNTRY-DOMAIN | validity | error | active | 5.00 | 0.0 | ไม่ผ่าน |
| CUST-BIRTH-RANGE | validity | warn | active | 1.20 | 0.0 | ไม่ผ่าน |
| ORD-CUST-POPULATED | completeness | error | active | 0.50 | 0.0 | ไม่ผ่าน |
| ORD-ID-UNIQUE | uniqueness | error | active | 0.66 | 0.0 | ไม่ผ่าน |
| ORD-TOTAL-SIGN | validity | warn | **proposed** | 0.40 | 0.0 | ไม่ผ่าน |
| ORD-SHIPPED-HAS-TS | consistency | warn | active | 1.39 | 0.5 | ไม่ผ่าน |
| ORD-SHIP-AFTER-ORDER | consistency | warn | active | 0.57 | 0.0 | ไม่ผ่าน |
| ORD-CUST-EXISTS | integrity | error | active | 1.00 | 0.1 | ไม่ผ่าน |
| PAY-ORDER-EXISTS | integrity | error | active | 0.78 | 0.0 | ไม่ผ่าน |
| ORD-ARRIVES-24H | timeliness | warn | active | 1.32 | 1.0 | ไม่ผ่าน |
| ORD-TOTAL-MATCHES-PAID | accuracy | error | active | 1.38 | 0.1 | ไม่ผ่าน |

ทั้ง 14 ข้อไม่ผ่านเพราะ dataset นี้ถูกสร้างให้มี defect ทุกชนิด **threshold, owner, impact และ severity ทั้งหมดเป็นตัวอย่างที่ผู้เขียนตั้งเพื่อสอน** ไม่ใช่ตัวเลขที่มาจากหนังสือหรือธุรกิจจริง

</Step>

## threshold ที่ยอมรับ ไม่ใช่ศูนย์เสมอไป

ผลการวัดเดียวกันอาจผ่านหรือไม่ผ่านขึ้นกับ threshold ตัวอย่าง email ซ้ำ 2.17%

| threshold | ผล |
|---|---|
| 0.0% | ไม่ผ่าน |
| 0.5% | ไม่ผ่าน |
| 2.0% | ไม่ผ่าน |
| 5.0% | ผ่าน |

DMBOK2 ให้ตัวอย่างสถานะแบบนี้ใน Table 30: completeness ต่ำกว่า 80% คือ "ยอมรับไม่ได้" และการมาไม่ทันเวลาเกิน 1% คือ "ยอมรับไม่ได้" ตัวเลขเหล่านั้นเป็นตัวอย่างในหนังสือ ไม่ใช่ threshold ที่ใช้ได้ทั่วไป threshold ต้องมาจาก data consumer (บท 1) และ DMBOK2 §4.4 เรียกคุณลักษณะนี้ว่า **acceptability** สองสิ่งที่ตัดสินใจแยกกัน

- **threshold** (`max_bad_pct`): ผิดได้เท่าไรจึงยังเรียกว่าพอรับได้
- **severity** (`severity`): ถ้าเกิน threshold แค่รายงาน (`warn`) หรือหยุด pipeline (`error`) ในแบบฝึก มี 6 rule ระดับ error ที่ไม่ผ่านพร้อมกัน หยุดได้เฉพาะ 6 rule นี้ และ `ORD-TOTAL-SIGN` ที่ยังเป็น `proposed` จะรายงานแต่ไม่หยุดอะไร เพราะยังไม่มีใครยืนยันว่าค่าติดลบผิดจริง (อาจเป็นการคืนเงิน บทที่ 3)

</Step>

## metric ที่ดีหกลักษณะ

DMBOK2 §4.4 ให้ลักษณะของ metric ที่ควรลงมือวัด (หนังสือ) ทบทวนกับ rule ของเรา

| ลักษณะ | ถามว่า | ถ้าไม่มี |
|---|---|---|
| Measurability | นับได้และกำหนดช่วงผลได้ไหม | "ข้อมูลเกี่ยวข้อง" วัดไม่ได้จนกว่าจะนิยาม threshold |
| Business relevance | เชื่อมกับการดำเนินธุรกิจไหม | วัดได้แต่ไม่มีใครสน |
| Acceptability | มี threshold ว่าพอหรือไม่พอไหม | ได้ตัวเลขแต่ตัดสินไม่ได้ |
| Accountability | เจ้าของธุรกิจอนุมัติ และมีคนแก้เมื่อไม่ผ่านไหม | แจ้งเตือนแล้วไม่มีใครรับ |
| Controllability | ถ้าออกนอกช่วงแล้วทำอะไรได้ไหม | หนังสือว่า "คงไม่มีประโยชน์" |
| Trending | ดู trend ข้ามเวลาได้ไหม | เห็นแค่ภาพถ่ายนิ่ง (บท 7 และ 10) |

ข้อ Controllability สำคัญ: ถ้าค่าออกนอกช่วงแล้วไม่มีใครตอบสนองได้ ก็ไม่ควรวัด `lint()` ในแบบฝึกตรวจข้อนี้ผ่าน field `owner` และ `impact`

</Step>

## rule ที่มากเกินไปและไม่มีใครเชื่อ

DQF เตือนเรื่องการเขียน test จำนวนมากโดยไม่มีเหตุผลรองรับ ถ้า developer เพิ่ม test เพราะคิดว่ามี test ดีกว่าไม่มี อีกหลายเดือนต่อมาอีกคนทำให้ test ล้มและไม่เข้าใจว่าทำไมต้องมี เขาจะลบ test เพื่อให้ CI ผ่าน วัฒนธรรมแบบนี้ทำให้ test เป็นสิ่งกีดขวาง ไม่ใช่ข้อมูลเชิงลึก หนังสือสรุปว่า "ถ้าไม่ตั้งใจจะจริงจังกับ test ไม่มี test เลยดีกว่า" (หนังสือ: DQF ch.3)

registry จึงมี `lint()` ที่ปฏิเสธ rule ซึ่งไม่น่าเชื่อถือ rule ลวงตา `MKT-MAGIC` ที่ตั้งใจเขียนให้แย่ถูกจับได้ห้าข้อ (รัน: `04_rules.py`)

```text
MKT-MAGIC: dimension 'goodness' is not one of the agreed names
MKT-MAGIC: no owner: nobody is accountable when it fails
MKT-MAGIC: no business impact: why is this measured?
MKT-MAGIC: threshold must be a percentage between 0 and 100
MKT-MAGIC: active rule has not been confirmed by a subject matter expert
```

เครื่องมืออย่าง GX และ dbt เก็บ "rule ที่รันได้" แต่ field อย่าง owner, impact และผู้ยืนยัน ต้องเป็นวินัยของทีมเอง (บทที่ 5 พูดถึงเครื่องมือเหล่านี้ และเส้นทาง Great Expectations สอนการเขียน rule ใน GX)

<Callout type="try" title="ลองทำใน repo นี้">
เปิด `dqrules.py` เพิ่ม rule ของตัวเอง เช่น "signup_date ไม่เป็นวันในอนาคต" ใส่ owner, impact และ threshold แล้วรัน `04_rules.py` ถ้าลืม field ใด field หนึ่ง `lint()` จะบอก ลองตั้ง `status="active"` โดยไม่ใส่ `confirmed_by` ดูว่าเกิดอะไรขึ้น
</Callout>

## เช็กตัวเอง

- rule "ยอดไม่ติดลบ" ถูกตั้งเป็น `proposed` ใครควรเป็นคนเปลี่ยนเป็น `active` และต้องถามอะไรก่อน
- ถ้า rule email ซ้ำตั้งเป็น `error` threshold 0% pipeline จะหยุดทุกคืน ใครเสียหาย ใครควรเป็นคนตัดสินว่าเป็น `warn` หรือ `error`
- rule ที่ไม่มีใครรับผิดชอบเมื่อล้ม ควรลบหรือหาเจ้าของ คุณเลือกอะไร และใช้เกณฑ์อะไรตัดสิน

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| ประโยชน์สี่ข้อของ rule, หกลักษณะของ rule ที่ดี | หนังสือ: DMBOK2 §2.7.1 |
| rule มักไม่ได้จดไว้ ต้องย้อนหา, rule ระดับ column และ dataset | หนังสือ: DMBOK2 §2.3 |
| ตัวอย่างสถานะยอมรับได้และไม่ได้ | หนังสือ: DMBOK2 Table 30 |
| หกลักษณะของ metric ที่ดี | หนังสือ: DMBOK2 §4.4 |
| test ที่ไม่มีเหตุผลรองรับ | หนังสือ: DQF ch.3 (หัวข้อ test fatigue ของ dbt) |
| ตัวเลขผลการรัน 14 rule, lint จับ 5 ข้อ | รัน: `04_rules.py` |
| โครง `Rule`, การจัดที่มาเป็น 3 กลุ่ม, threshold, owner, impact และ severity error/warn ทุกค่า | ผู้เขียน |

</Step>
