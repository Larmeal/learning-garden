## โจทย์

รับข้อมูล order รายวัน ตัดสินว่า**publish เข้ารายงานหรือหยุดไว้** และทำให้เจ้าของข้อมูลรู้เมื่อมีปัญหา โดยใช้เฉพาะสิ่งที่เรียนมา

| ขั้น | ทำอะไร | มาจากบท |
|---|---|---|
| 1 | ตรวจ schema ของชุดที่เข้ามาเทียบกับ contract ถ้าไม่ตรง ปฏิเสธก่อน load | 6 |
| 2 | ถ้าไม่มี row เลย ถือว่าต้นทางเงียบ | 7 |
| 3 | ตรวจทีละ row: ซ้ำ, ไม่มี customer_id, ไม่มี customer จริง, ยอดติดลบ แล้ว quarantine row ที่ไม่ผ่านพร้อมเหตุผล | 4, 5 |
| 4 | ถ้า row เสียเกิน 10% ให้หยุด (circuit breaker) ถ้า row ที่ดีน้อยกว่า 50% ของ median วันเดียวกันในสัปดาห์ก่อนๆ ให้หยุด | 5, 7 |
| 5 | publish หรือหยุดและเปิด ticket ถึงเจ้าของตามที่ contract ระบุ (ช่องทางแจ้ง, เวลาตอบสนอง) | 6, 9, 10 |

threshold 10% และ 50% เป็นตัวอย่างที่ผู้เขียนตั้ง ไม่ได้มาจากหนังสือ ในงานจริงมาจากข้อตกลงกับ data consumer ([บท 1](/data-quality/assurance-basics/#quality-คือ-เหมาะกับการใช้งาน), [4](/data-quality/rule-design/#threshold-ที่ยอมรับ-ไม่ใช่ศูนย์เสมอไป), [10](/data-quality/ownership-scorecard/#รายงาน-data-quality-ให้ใคร-และรายงานอะไร))

สายนี้อยู่ใน script `11_capstone.py` ประมาณ 100 บรรทัดที่ใช้ `dqlab.py`, `dqrules.py` และ `dqcontract.py` ที่เขียนไว้ในบทก่อนๆ

## หกสถานการณ์

ข้อมูลของวันที่ 2026-10-20 (วันอังคาร) มี 30 row ค่า median ของวันอังคารสี่สัปดาห์ก่อนหน้าคือ 26 row ชุดข้อมูลที่ป้อนเข้าสายเป็นหกแบบ ทั้งหมดดัดแปลงจากข้อมูลวันเดียวกัน (รัน: `11_capstone.py`)

| # | สถานการณ์ | ผล | เหตุผล |
|---|---|---|---|
| 1 | วันปกติ | publish | volume 113% ของ baseline |
| 2 | ซ้ำหนึ่ง row | publish และ quarantine row เสีย 1 row | ซ้ำ order_id 1 row อยู่ใต้ threshold 10% |
| 3 | row เสียจำนวนมาก | **หยุด** | 26% ของ row ไม่ผ่านการตรวจ row (ซ้ำ 4, ยอดติดลบ 3, ไม่มี customer จริง 2) เกิน threshold 10% |
| 4 | เปลี่ยนชื่อ column | **หยุด** | contract: ไม่มี column `total_amount` |
| 5 | ไม่มีข้อมูลมาเลย | **หยุด** | ต้นทางเงียบ |
| 6 | load มาแค่บางส่วน (30%) | **หยุด** | volume 34% ของ baseline (threshold 50%) |

สี่สถานการณ์ที่หยุด เปิด ticket สี่ใบ ทุกใบถึงทีม `orders-platform` ทาง channel `#orders-data` ภายใน 2 ชั่วโมงตามที่ contract v1 ระบุ

| จากสถานการณ์ | ความรุนแรง | เรื่อง |
|---|---|---|
| 3 | สูง | 26% ของ row ไม่ผ่านการตรวจ row |
| 4 | สูง | contract: missing column total_amount |
| 5 | สูง | no rows arrived (source silent) |
| 6 | กลาง | volume เป็น 34% ของ baseline |

สถานการณ์ 1 และ 2 เป็นวันเดียวกัน การ publish ใช้วันเป็น key (upsert) ดังนั้นรันซ้ำแล้วแทนที่ row เดิม ไม่เพิ่ม row ใหม่ ซึ่งเป็นบทเรียนจาก[บท 8](/data-quality/reconciliation/#ออกแบบให้ตรวจย้อนได้) และ [9](/data-quality/incidents/#fix-ชั่วคราวก่อน-แล้วถาวร): การ load ซ้ำได้อย่างปลอดภัย

## การตัดสินใจในสายนี้ที่ควรตั้งคำถาม

โค้ดทำงานได้ แต่การตัดสินใจหลายอย่างในนั้นเป็นของผู้เขียน และไม่มีคำตอบเดียวที่ถูก

- **row เสีย 10% หยุด** ถ้าธุรกิจรับได้ 20% ก็เลื่อน threshold ถ้ารับได้ 0% แต่ก็จะหยุดทุกวัน ([บท 4](/data-quality/rule-design/#threshold-ที่ยอมรับ-ไม่ใช่ศูนย์เสมอไป): threshold ที่ยอมรับ)
- **volume ต่ำกว่า 50% หยุด แต่ 51% ผ่าน** วันที่ลดลงครึ่งหนึ่งผ่านแล้วคุณพอใจไหม ลองใช้ ThresholdLab ([บท 7](/data-quality/monitoring/#ขยับ-threshold-เอง)) ดูว่า threshold นี้เหมาะกับข้อมูลที่มีรอบสัปดาห์หรือไม่
- **หยุดทั้งชุดเมื่อ row เสียมาก** อาจไม่เหมาะ ถ้า row ส่วนใหญ่ยังดี ทางเลือกคือ publish ส่วนที่ดีพร้อมประกาศว่าไม่ครบ ([บท 5](/data-quality/checkpoints/#เมื่อไม่ผ่าน-ปล่อยผ่าน-quarantine-หรือหยุด): intrusive กับ nonintrusive)
- **ticket ทุกใบไปที่ทีมเดียวกัน** ในสถานการณ์ 3 ปัญหาอาจเกิดที่ทีม CRM หรือทีม payment ([บท 9](/data-quality/incidents/#respond-ใครคุม-ใครรู้): ไล่ lineage เพื่อหาเจ้าของจริง)
- **ไม่มี monitor freshness ของ table รายงาน** ถ้า pipeline หยุด รายงานปลายทางจะเก่าลงเรื่อยๆ แต่ไม่มีอะไรแจ้ง ([บท 7](/data-quality/monitoring/#freshness-ช่วงที่ไม่มีข้อมูลยาวแค่ไหนจึงเป็นเหตุ))
- **ไม่ได้ตรวจ accuracy** เทียบกับ payment system เพราะต้องรอข้อมูลฝั่ง payment มาถึง ([บท 8](/data-quality/reconciliation/#reconcile-ด้วยจำนวน-row-และผลรวม): reconciliation เป็นอีกขั้นหนึ่งที่รันทีหลัง)

</Step>

## โจทย์ต่อยอด

ทำใน script ทีละข้อ แต่ละข้อใช้บทที่ระบุ

1. **เพิ่มสถานการณ์ที่ 7: schema drift แบบเงียบ** type ของ `customer_id` เปลี่ยนจาก BIGINT เป็น string ตัวเลข ([บท 6](/data-quality/agreements/#เปลี่ยน-contract-อย่างไรไม่ให้ใครพัง)) pipeline detect ไหม ถ้าไม่ ต้องเพิ่มอะไร
2. **เพิ่ม reconciliation หลัง publish** เทียบจำนวน row และผลรวมของ row ที่ publish กับต้นทางที่ไม่รวม row ที่ quarantine ผลต่างต้องเท่ากับ row ที่ quarantine พอดี ([บท 8](/data-quality/reconciliation/#ส่วนต่างต้องอธิบายได้ครบ))
3. **เพิ่ม rule เรื่อง freshness** ถ้า `order_ts` ล่าสุดเก่ากว่า 24 ชั่วโมงเมื่อเทียบกับเวลาที่รัน ให้เปิด ticket ([บท 6](/data-quality/agreements/#ตรวจข้อมูลเทียบกับ-contract), [7](/data-quality/monitoring/#freshness-ช่วงที่ไม่มีข้อมูลยาวแค่ไหนจึงเป็นเหตุ))
4. **ทำให้ ticket ฉลาดขึ้น** แนบรายการ table downstream ที่ได้รับผลกระทบ (blast radius) จากกราฟ lineage แบบ[บท 9](/data-quality/incidents/#respond-ใครคุม-ใครรู้)
5. **เขียน log วันละบรรทัด** เก็บผลของแต่ละวัน (publish/หยุด จำนวน row ที่ quarantine) ใน table หนึ่ง แล้วคิด data downtime รายเดือนเทียบกับ SLO ([บท 10](/data-quality/ownership-scorecard/#data-downtime-เป็น-slo))
6. **ลองผูกกับ GX** เขียนขั้นตรวจ row ใหม่เป็น expectation suite ของ Great Expectations แล้วเทียบกับ SQL ของคุณ (ดูบท "ใช้ใน pipeline จริง" ในเส้นทาง Great Expectations)

<Callout type="try" title="ลองทำใน repo นี้">
เริ่มจากข้อ 2 ซึ่งเล็กที่สุด เพิ่ม reconciliation ต่อท้ายฟังก์ชัน `run_pipeline` แล้วทดสอบว่าสถานการณ์ 2 (ซ้ำหนึ่ง row) ได้ผลต่างเท่ากับ 1 row และสถานการณ์ 1 ได้ 0
</Callout>

## เส้นทางที่เรียนมา และสิ่งที่ยังไม่ได้ครอบคลุม

ทบทวนสิ่งที่ได้ในแต่ละบท

| บท | ได้อะไร |
|---|---|
| 1 | quality คือความเหมาะกับการใช้งาน; Assurance คือระบบที่รักษามัน |
| 2 | dimension เป็นคำศัพท์; ตรวจแต่ละ dimension ด้วย SQL; รายงานทั้งส่วนผ่านและไม่ผ่าน |
| 3 | ดู profile ก่อนเขียน rule; profile บอกว่ามีอะไร ไม่บอกว่าควรเป็นอะไร |
| 4 | rule ต้องมีเจ้าของ threshold impact และคนยืนยัน |
| 5 | ตรวจหลายจุด; เลือกระหว่างปล่อย quarantine หยุด |
| 6 | contract เป็นข้อมูลที่ตรวจได้; แยกการเปลี่ยนที่ทำให้พัง |
| 7 | monitor สิ่งที่ไม่ได้คาดไว้; ทุก threshold แลกกันระหว่างแจ้งผิดกับพลาด |
| 8 | reconcile ทั้งสาย; ส่วนต่างต้องอธิบายได้ครบ; ทดสอบ SQL บนข้อมูลเล็ก |
| 9 | รับมือ incident ด้วยห้าขั้น; postmortem ไม่โทษคน |
| 10 | วัดอย่างไรไม่หลอกตัวเอง; ใครรับผิดชอบ; รับรองข้อมูล |

สิ่งที่เส้นทางนี้**ยังไม่ครอบคลุม**

- **Reasonability** (DMBOK2 Table 29 หน้า 459) มีหน้าเจาะลึกใต้[บท 2](/data-quality/dimensions/reasonability/#คำนี้ถามอะไร) และการ monitor volume กับ distribution เทียบกับอดีตใน[บท 7](/data-quality/monitoring/#volume-ฤดูกาลทำให้-z-score-หลง) แบบฝึก `13_dimension_pitfalls.py` จับวันเสียที่สร้างขึ้นใน copy เพราะ dataset ไม่มี defect ชนิดนี้ที่ฝังไว้ จึงเป็นหลักฐานที่อ่อนกว่า dimension อื่น
- **ข้อมูลส่วนบุคคลและความเป็นส่วนตัว** (PII) มีเฉพาะระดับแนวคิดใน[บท 13](/data-quality/governance/#class-และ-policy) (class, policy, metadata ใน contract) ไม่มีแบบฝึก
- **data quality สำหรับ machine learning model** ก็มีแค่คุยกันใน[บท 13](/data-quality/governance/#เมื่อข้อมูลป้อน-model) ส่วนข้อมูล streaming จริงแตะเบาๆ ใน[บท 5](/data-quality/checkpoints/#ตรวจที่ระดับไหน-และทำใน-stream-ได้หรือไม่) (การตรวจแบบ in-stream)
- **เครื่องมือเฉพาะตัว** เส้นทางนี้ไม่สอนเครื่องมือใดโดยเฉพาะ ใช้ GX ในเส้นทาง Great Expectations
- **วัฒนธรรมและการเมืองในองค์กร** เริ่มต้นไว้ใน[บท 12](/data-quality/ten-steps/#พาคนไปด้วย) (การสื่อสารและการ engage คนใน Ten Steps) และ[บท 13](/data-quality/governance/#ใคร-accountable) (accountability) DMBOK2 มีบทว่าด้วยการเปลี่ยนแปลงองค์กรที่เส้นทางนี้ไม่ได้ใช้

เส้นทางนี้ใช้ข้อมูลสังเคราะห์ที่สะอาดกว่างานจริงมาก ทุกตัวเลขที่ "ได้ผลดี" ควรถูกมองเป็นตัวอย่างของวิธีคิด ไม่ใช่ผลที่จะได้ในที่ทำงานคุณ

มีอีกสองบทให้เลือกเรียนต่อ [บท 12](/data-quality/ten-steps/) แสดงวิธีรันทั้งหมดนี้เป็น project ด้วยวิธี Ten Steps และ[บท 13](/data-quality/governance/) วางมันในกรอบ data governance

</Step>
