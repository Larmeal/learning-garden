## "Trust, But Verify"

*Designing Data-Intensive Applications* (DDIA) มีหัวข้อ "Trust, but Verify" ในบทเรื่องความถูกต้อง เริ่มจากข้อสังเกตว่าระบบทุกระบบสมมติว่าบางอย่างผิดได้และบางอย่างไม่มีวันผิด (system model) ข้อสมมติเหล่านั้นจริงเกือบตลอด แต่ในความเป็นจริงเป็นเรื่องของความน่าจะเป็น และถ้าทำงานในระดับใหญ่พอ เรื่องที่เกิดยากก็เกิดจริง (หนังสือ: DDIA บทที่ 13 หัวข้อ "Trust, but Verify" หน้า 575 ถึง 577)

หนังสือยกตัวอย่างที่น่าสนใจกับงาน data quality

- software ฐานข้อมูลที่ใช้กันแพร่หลายก็มีบั๊ก: MySQL บางรุ่นในอดีตไม่รักษา uniqueness constraint ได้ถูกต้อง
- application จำนวนมากไม่ได้ใช้ฟีเจอร์รักษาความถูกต้องของฐานข้อมูลอย่าง foreign key หรือ uniqueness constraint ให้ถูกต้อง
- ความสอดคล้องแบบ ACID ตั้งอยู่บนข้อสมมติว่าโปรแกรมไม่มีบั๊ก

ข้อสรุปของหนังสือ: ข้อมูลเสียหายดูจะเกิดขึ้นได้เสมอ เราจึงควรมีวิธีรู้ว่ามันเสียหาย แล้วแก้และตามหาต้นเหตุ การตรวจความถูกต้องของข้อมูลเรียกว่า **auditing** และ "ถ้าอยากแน่ใจว่าข้อมูลยังอยู่ ต้องอ่านมันแล้วตรวจ"

</Step>

## หลัก End-to-end

หลัก end-to-end (Saltzer, Reed, Clark, 1984) ที่ DDIA ยกมาบอกว่าฟังก์ชันบางอย่างทำให้ถูกต้องสมบูรณ์ได้เฉพาะกับความรู้และความช่วยเหลือของ application ที่ปลายทั้งสองข้าง ไม่ใช่ที่ระบบสื่อสารตรงกลาง ฟังก์ชันระดับล่างช่วยลดโอกาสผิดพลาดได้ แต่ไม่พอด้วยตัวเอง

ในเรื่องความถูกต้องของข้อมูล: checksum ของ Ethernet, TCP และ TLS จับความเสียหายของ packet ในเครือข่ายได้ แต่จับความเสียหายจากบั๊กใน software ที่ปลายส่งและปลายรับ หรือจากดิสก์ที่เก็บข้อมูล ไม่ได้ ถ้าอยากจับทุกแหล่ง ต้องมี checksum end-to-end (หนังสือ: DDIA บทที่ 13 หัวข้อ "The end-to-end argument" หน้า 565)

ข้อสรุปที่ใช้กับ data pipeline (ตามที่หนังสือกล่าว)

- ตรวจความถูกต้องแบบ end-to-end ดีที่สุด ยิ่งรวมระบบมากในการตรวจ ยิ่งมีโอกาสน้อยที่ความเสียหายจะหลุดที่ขั้นใดขั้นหนึ่ง
- ถ้าตรวจได้ว่า pipeline ของข้อมูลที่สร้างต่อมาถูกต้องทั้งสาย ดิสก์ เครือข่าย service และ algorithm ระหว่างทางก็ถูกรวมในการตรวจโดยปริยาย
- การตรวจต่อเนื่องแบบนี้เพิ่มความมั่นใจ ซึ่งทำให้ทีม**ขยับเร็วขึ้น** เหมือน automated test: บั๊กถูกพบเร็ว ความเสี่ยงของการเปลี่ยนแปลงลดลง

reconciliation ด้วยการนับและรวมเป็นรูปแบบที่ถูกและตรงที่สุดของการตรวจ end-to-end

</Step>

## Reconcile ด้วยจำนวน Row และผลรวม

สถานการณ์: table mart ที่ทีม analytics สร้างเพื่อดูยอดชำระต่อ order ต้องตรงกับ payment system ซึ่งเป็นแหล่งอ้างอิง เปรียบเทียบด้วยจำนวน row และผลรวม (รัน: `08_reconcile.py`)

```sql
-- mart ที่ join ธรรมดา
SELECT o.order_id, o.total_amount, p.amount AS paid
FROM orders o JOIN payments p USING (order_id)
WHERE o.status <> 'CANCELLED';
```

| ฝั่ง | row | ผลรวมยอดชำระ |
|---|---:|---:|
| payment system (ที่มี order ไม่ยกเลิก) | 2,533 | 6,454,814.21 |
| mart ที่ join ธรรมดา | 2,550 | 6,503,791.89 |
| ส่วนต่าง | **+17** | **+48,977.68** |
| mart ที่ใช้ `SELECT DISTINCT * FROM orders` ก่อน join | 2,533 | 6,454,814.21 (ตรงทุกตัว) |

ส่วนต่าง 17 row คือ order ที่ซ้ำและไม่ถูกยกเลิก (ชุดที่ฝังไว้ 20 row ซึ่ง 17 row ไม่ใช่ CANCELLED) ซึ่งเป็นเหตุที่การ join ธรรมดาเพิ่ม row ให้ตัวเดียวกัน ยอดที่นับซ้ำ +48,977.68 เท่ากับยอดซ้ำที่เจอใน[บท 5](/data-quality/checkpoints/#เมื่อไม่ผ่าน-ปล่อยผ่าน-quarantine-หรือหยุด) เพราะเป็น order ชุดเดียวกัน และยอดชำระของมันเท่ากับยอดสั่งซื้อ

ข้อดีของวิธีนี้คือไม่ต้องรู้ล่วงหน้าว่าจะผิดตรงไหน ตรวจเพียงสองตัวเลขที่ปลายทางก็เห็นว่า "มีอะไรผิดระหว่างทาง" แล้วค่อยไล่หาด้วยการเทียบชุดของ key (ในแบบฝึก: key ที่ปรากฏใน mart มากกว่าหนึ่งครั้ง ได้ 267, 572, 797, 931, 986, ... ตรงกับ order_id ที่ซ้ำ)

</Step>

## ส่วนต่างต้องอธิบายได้ครบ

reconciliation ไม่ได้หมายถึง "ต้องเท่ากันเป๊ะ" แต่หมายถึง **ส่วนต่างทุกบาทมีเหตุผลที่ระบุได้** ยอด order รวมเทียบกับยอด payment รวม (รัน: `08_reconcile.py`)

| รายการ | จำนวน |
|---|---:|
| ยอด order (ไม่ยกเลิก ไม่ซ้ำ) | 6,453,757.71 |
| ยอด payment ทั้งหมด | 6,488,670.91 |
| ส่วนต่างทั้งหมด | **-34,913.20** |
| อธิบายได้ด้วย: 35 order ที่ยอดไม่ตรงกับ payment | -1,056.50 |
| อธิบายได้ด้วย: payment ของ order ที่ไม่มีอยู่จริง (20 รายการ) | -33,856.70 |
| ส่วนที่ยังอธิบายไม่ได้ | **0.00** |

reconciliation น่าไว้ใจเมื่อ "ส่วนที่ยังอธิบายไม่ได้" เป็น 0 ถ้าเหลือเศษที่อธิบายไม่ได้ แม้เล็กน้อย แปลว่ายังมีปัญหาที่ไม่รู้จัก และ 35 order กับ 20 payment ที่เป็นเหตุผล ก็คือสอง rule ของ[บท 2](/data-quality/dimensions/#สรุปทั้ง-14-rule) ที่รู้อยู่แล้ว

</Step>

## ทดสอบ SQL ที่แปลงข้อมูลบนข้อมูลเล็กที่รู้คำตอบ

reconciliation จับ**หลัง**รัน unit test จับ**ก่อน**ขึ้นข้อมูลจริง DQF แบ่งชนิดของ test ไว้ (หนังสือ: DQF บทที่ 5 หน้า 121 ถึง 122)

| ชนิด | ใช้ทำอะไร |
|---|---|
| Unit | ตรวจว่า SQL หนึ่งก้อนทำตามที่ควร กับข้อมูลน้อยๆ ต้องแยกตรรกะธุรกิจออกจากโค้ดเชื่อมต่อ |
| Functional | กับข้อมูลชุดใหญ่ ในขั้นตอนการประมวลผล ตรวจความถูกต้อง การนำเข้า การเก็บ |
| Integration | ให้ pipeline รับข้อมูลปลอมก่อนใช้ข้อมูลจริง เพื่อดูว่าผ่านเกณฑ์ |

ตัวอย่าง unit test ของ `mart` ใช้สามกรณีที่เล็กจนเห็นคำตอบด้วยตา (รัน: `08_reconcile.py`)

| กรณี | ข้อมูล | ผลที่ควรได้ |
|---|---|---:|
| สอง order ปกติ | 100 + 50 | 150 |
| order ที่ยกเลิกไม่นับ | 100 + (ยกเลิก 70) | 100 |
| row order ซ้ำนับครั้งเดียว | 100 (สอง row) | 100 |

| สูตร SQL | ผล |
|---|---|
| join ธรรมดา | **ล้มที่กรณีที่ 3** (ได้ 200 ควรได้ 100) |
| ใช้ DISTINCT ก่อน join | ผ่านทั้งสามกรณี |

บั๊กที่ reconciliation จับได้หลัง load ข้อมูลจริง ถูกจับได้ตั้งแต่ก่อนด้วย test ขนาด 3 row เพราะกรณีที่ 3 ถูกเขียนขึ้นด้วยคำถามว่า "ถ้าต้นทางส่งซ้ำจะเกิดอะไร" (ซึ่งมาจากการ profile ใน[บท 3](/data-quality/profiling/#profile-ของทุก-column-โดยไม่ต้องรู้ความหมาย) ว่ามี order_id ซ้ำ)

</Step>

## Test แบบ "คืน Row ที่ผิด" และข้อจำกัด

dbt ใช้ test แบบ singular: เขียน query ที่คืน **row ที่ละเมิดข้อกำหนด** แล้วถือว่าผ่านเมื่อไม่มี row (หนังสือ: DQF บทที่ 3 หน้า 57) ในแบบฝึกใช้แบบเดียวกันกับ "ไม่มี order_id ซ้ำใน mart"

```sql
SELECT order_id FROM mart GROUP BY 1 HAVING count(*) > 1;
-- ผ่านเมื่อไม่มี row
```

| mart | row ที่ผิด | ผล |
|---|---:|---|
| join ธรรมดา | 17 | ไม่ผ่าน |
| ใช้ DISTINCT | 0 | ผ่าน |

DQF รวมชนิดของ test ที่พบบ่อยไว้ด้วย: null, volume, distribution, uniqueness และ **known invariants** (สิ่งที่เป็นจริงเสมอ เช่น กำไรเท่ากับรายได้ลบต้นทุน) และชี้ข้อจำกัดของ test ที่เขียนเป็นโค้ด (หนังสือ: DQF บทที่ 3 หน้า 56 ถึง 58)

- **ภาระดูแล**: model เปลี่ยน test ต้องเปลี่ยนตาม test ซับซ้อนอาจกินเวลาใกล้เคียงกับการพัฒนา model เอง
- **test fatigue**: test ที่ไม่มีเหตุผลรองรับจะถูกลบเมื่อกีดขวาง ([บท 4](/data-quality/rule-design/#rule-ที่มากเกินไปและไม่มีใครเชื่อ))
- **มองเห็นจำกัด**: test อาจล้มเพราะปัญหาต้นทางที่อยู่เหนือกว่า ซึ่งบอกว่ามีอะไรผิดแต่ไม่ช่วยให้แก้ได้เร็ว ถ้า test ไม่ครอบคลุม end-to-end

ข้อสุดท้ายคือเหตุผลที่ต้องมีทั้งสองอย่าง reconciliation มองข้ามทั้งสายส่วน unit test ตรวจตรรกะเฉพาะจุด

</Step>

## ออกแบบให้ตรวจย้อนได้

DDIA พูดถึง **auditability**: ระบบที่แสดง dataflow ชัดเจน ที่มาของข้อมูลชัดเจน ทำให้ตรวจความถูกต้องทำได้จริงขึ้น ถ้าการสร้างข้อมูลปลายทางเป็น deterministic (ผลซ้ำได้) เรารัน processor เดิมจากข้อมูลต้นทางเดิมอีกครั้งเพื่อดูว่าได้ผลเดียวกันหรือไม่ หรือรันอีกสายขนานเพื่อเทียบ (หนังสือ: DDIA บทที่ 13 หัวข้อ "Designing for auditability" หน้า 577 ถึง 578)

นำมาใช้กับ data pipeline

- ทำให้การ load **ซ้ำได้อย่างปลอดภัย** (idempotent) เช่น load โดยใช้ batch_id เป็น key เพื่อให้รันซ้ำไม่ทำให้ข้อมูลเบิ้ล ([บท 9](/data-quality/incidents/#fix-ชั่วคราวก่อน-แล้วถาวร) เป็นเรื่องจริงของข้อผิดพลาดแบบนี้)
- เก็บข้อมูลดิบไว้ ไม่เขียนทับ เพื่อสร้าง table ปลายทางใหม่จากต้นทางเมื่อพบบั๊ก
- รัน reconciliation ต่อเนื่อง ไม่ใช่แค่ตอนสงสัย หนังสือบอกว่าการตรวจต่อเนื่องทำให้ "ไม่กลัวที่จะเปลี่ยนแปลง" และพัฒนา app ให้ตรงความต้องการที่เปลี่ยนไปได้ดีขึ้น

เปิด `08_reconcile.py` เพิ่มกรณีทดสอบที่ 4: order หนึ่งรายการแต่มี payment สองรายการ (แบ่งจ่าย) จะเกิดอะไรกับทั้งสองสูตร เขียนผลที่ควรได้ก่อนรัน แล้วดูว่า test ของคุณจับความต่างได้ไหม

## เช็กตัวเอง

- table ปลายทางที่ทีมคุณดูแล ตรวจย้อนกับต้นทางด้วยจำนวน row และผลรวมหรือไม่ ความถี่เท่าไร
- ถ้าส่วนต่างหลัง reconcile เหลือ 0.01 บาท คุณจะถือว่าผ่านหรือไม่ ใครเป็นคนกำหนด threshold
- test ที่ล้มเพราะต้นทางส่งผิดมา ควรรายงานให้ใคร และต่างจาก test ที่ล้มเพราะ SQL ของเราผิดอย่างไร

</Step>
