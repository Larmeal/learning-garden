## "Trust, But Verify"

*Designing Data-Intensive Applications* (DDIA) มีหัวข้อ "Trust, But Verify" ในบทเรื่องความถูกต้อง โดยเริ่มจากข้อสังเกตว่าระบบทุกระบบสมมติไว้ว่าบางอย่างผิดได้และบางอย่างไม่มีวันผิด (System Model) ซึ่งข้อสมมติเหล่านั้นจริงเกือบตลอด แต่ในความเป็นจริงมันเป็นเรื่องของความน่าจะเป็น และถ้าเราทำงานในระดับใหญ่พอ เรื่องที่เกิดยากก็เกิดขึ้นจริงได้ (หนังสือ: DDIA บทที่ 13 หัวข้อ "Trust, But Verify" หน้า 575 ถึง 577)

หนังสือยกตัวอย่างที่น่าสนใจกับงาน Data Quality ไว้สามข้อ

- Software ฐานข้อมูลที่ใช้กันแพร่หลายก็มีบั๊กได้ เช่น MySQL บางรุ่นในอดีตไม่รักษา Uniqueness Constraint ได้ถูกต้อง
- Application จำนวนมากใช้ฟีเจอร์รักษาความถูกต้องของฐานข้อมูลอย่าง Foreign Key หรือ Uniqueness Constraint ได้ไม่ถูกต้อง
- ความสอดคล้องแบบ ACID ตั้งอยู่บนข้อสมมติว่าโปรแกรมไม่มีบั๊ก

หนังสือสรุปว่า ข้อมูลเสียหายดูจะเกิดขึ้นได้เสมอ เราจึงควรมีวิธีรู้ว่ามันเสียหาย แล้วแก้และตามหาต้นเหตุ ซึ่งการตรวจความถูกต้องของข้อมูลนี้เรียกว่า **Auditing** และ "ถ้าอยากแน่ใจว่าข้อมูลยังอยู่ ต้องอ่านมันแล้วตรวจ"

</Step>

## หลัก End-to-end

หลัก End-to-end (Saltzer, Reed, Clark, 1984) ที่ DDIA ยกมาบอกว่าฟังก์ชันบางอย่างจะถูกต้องสมบูรณ์ได้ก็ต่อเมื่อมีความรู้และความช่วยเหลือของ Application ที่ปลายทั้งสองข้างเท่านั้น ระบบสื่อสารที่อยู่ตรงกลางทำให้ครบเองไม่ได้ ฟังก์ชันระดับล่างช่วยลดโอกาสผิดพลาดได้ แต่ก็ยังไม่พอด้วยตัวเอง

ยกตัวอย่างเรื่องความถูกต้องของข้อมูล Checksum ของ Ethernet, TCP และ TLS จับความเสียหายของ Packet ในเครือข่ายได้ แต่จับความเสียหายจากบั๊กใน Software ที่ปลายส่งและปลายรับ หรือจากดิสก์ที่เก็บข้อมูล ไม่ได้ ดังนั้นถ้าอยากจับให้ได้ทุกแหล่ง ก็ต้องมี Checksum End-to-end (หนังสือ: DDIA บทที่ 13 หัวข้อ "The end-to-end argument" หน้า 565)

พอเอามาใช้กับ Data Pipeline หนังสือกล่าวไว้สามข้อ

- การตรวจความถูกต้องแบบ End-to-end ดีที่สุด เพราะยิ่งรวมระบบมากในการตรวจ ก็ยิ่งมีโอกาสน้อยที่ความเสียหายจะหลุดที่ขั้นใดขั้นหนึ่ง
- ถ้าเราตรวจได้ว่า Pipeline ของข้อมูลที่สร้างต่อมาถูกต้องทั้งสาย ดิสก์ เครือข่าย Service และ Algorithm ระหว่างทางก็ถูกรวมอยู่ในการตรวจนั้นโดยปริยาย
- การตรวจต่อเนื่องแบบนี้เพิ่มความมั่นใจ ซึ่งทำให้ทีม**ขยับเร็วขึ้น** เหมือน Automated Test เพราะบั๊กถูกพบเร็วและความเสี่ยงของการเปลี่ยนแปลงลดลง

ส่วน Reconciliation ด้วยการนับและรวมก็เป็นรูปแบบที่ถูกและตรงที่สุดของการตรวจ End-to-end

</Step>

## Reconcile ด้วยจำนวน Row และผลรวม

สมมติว่าทีม Analytics สร้าง Table Mart ขึ้นมาเพื่อดูยอดชำระต่อ Order ซึ่งต้องตรงกับ Payment System ที่เป็นแหล่งอ้างอิง เราจึงเปรียบเทียบด้วยจำนวน Row และผลรวม (รัน: `08_reconcile.py`)

```sql
-- mart ที่ join ธรรมดา
SELECT o.order_id, o.total_amount, p.amount AS paid
FROM orders o JOIN payments p USING (order_id)
WHERE o.status <> 'CANCELLED';
```

| ฝั่ง | Row | ผลรวมยอดชำระ |
|---|---:|---:|
| Payment System (ที่มี Order ไม่ยกเลิก) | 2,533 | 6,454,814.21 |
| Mart ที่ Join ธรรมดา | 2,550 | 6,503,791.89 |
| ส่วนต่าง | **+17** | **+48,977.68** |
| Mart ที่ใช้ `SELECT DISTINCT * FROM orders` ก่อน Join | 2,533 | 6,454,814.21 (ตรงทุกตัว) |

ส่วนต่าง 17 Row ก็คือ Order ที่ซ้ำและไม่ถูกยกเลิก (ชุดที่ฝังไว้ 20 Row ซึ่ง 17 Row ไม่ใช่ CANCELLED) การ Join ธรรมดาจึงเพิ่ม Row ให้ Order ตัวเดียวกัน ส่วนยอดที่นับซ้ำ +48,977.68 เท่ากับยอดซ้ำที่เจอใน[บท 5](/data-quality/checkpoints/#เมื่อไม่ผ่าน-ปล่อยผ่าน-quarantine-หรือหยุด) เพราะเป็น Order ชุดเดียวกัน และยอดชำระของมันก็เท่ากับยอดสั่งซื้อ

ข้อดีของวิธีนี้คือเราไม่ต้องรู้ล่วงหน้าว่าจะผิดตรงไหน แค่ตรวจสองตัวเลขที่ปลายทางก็เห็นแล้วว่า "มีอะไรผิดระหว่างทาง" จากนั้นค่อยไล่หาด้วยการเทียบชุดของ Key (ในแบบฝึก Key ที่ปรากฏใน Mart มากกว่าหนึ่งครั้งได้ 267, 572, 797, 931, 986, ... ซึ่งตรงกับ order_id ที่ซ้ำ)

</Step>

## ส่วนต่างต้องอธิบายได้ครบ

ใน Reconciliation ตัวเลขสองฝั่งไม่จำเป็นต้องเท่ากันเป๊ะ สิ่งที่ต้องได้คือ **ส่วนต่างทุกบาทมีเหตุผลที่ระบุได้** ลองเทียบยอด Order รวมกับยอด Payment รวมดู (รัน: `08_reconcile.py`)

| รายการ | จำนวน |
|---|---:|
| ยอด Order (ไม่ยกเลิก ไม่ซ้ำ) | 6,453,757.71 |
| ยอด Payment ทั้งหมด | 6,488,670.91 |
| ส่วนต่างทั้งหมด | **-34,913.20** |
| อธิบายได้ด้วย: 35 Order ที่ยอดไม่ตรงกับ Payment | -1,056.50 |
| อธิบายได้ด้วย: Payment ของ Order ที่ไม่มีอยู่จริง (20 รายการ) | -33,856.70 |
| ส่วนที่ยังอธิบายไม่ได้ | **0.00** |

เราจะไว้ใจ Reconciliation ได้เมื่อ "ส่วนที่ยังอธิบายไม่ได้" เป็น 0 ถ้ายังเหลือเศษที่อธิบายไม่ได้ แม้จะเล็กน้อย ก็แปลว่ายังมีปัญหาที่เราไม่รู้จักอยู่ ส่วน 35 Order กับ 20 Payment ที่เป็นเหตุผลในตารางนี้ ก็คือสอง Rule ของ[บท 2](/data-quality/dimensions/#สรุปทั้ง-14-rule) ที่รู้อยู่แล้ว

</Step>

## ทดสอบ SQL ที่แปลงข้อมูลบนข้อมูลเล็กที่รู้คำตอบ

Reconciliation จับปัญหา**หลัง**รัน ส่วน Unit Test จับ**ก่อน**ขึ้นข้อมูลจริง โดย DQF แบ่งชนิดของ Test ไว้ดังนี้ (หนังสือ: DQF บทที่ 5 หน้า 121 ถึง 122)

| ชนิด | ใช้ทำอะไร |
|---|---|
| Unit | ตรวจว่า SQL หนึ่งก้อนทำตามที่ควรหรือไม่ กับข้อมูลน้อย ๆ โดยต้องแยกตรรกะธุรกิจออกจากโค้ดเชื่อมต่อ |
| Functional | กับข้อมูลชุดใหญ่ ในขั้นตอนการประมวลผล ตรวจความถูกต้อง การนำเข้า การเก็บ |
| Integration | ให้ Pipeline รับข้อมูลปลอมก่อนใช้ข้อมูลจริง เพื่อดูว่าผ่านเกณฑ์ |

ตัวอย่าง Unit Test ของ `mart` ใช้สามกรณีที่เล็กจนเรามองเห็นคำตอบได้ด้วยตา (รัน: `08_reconcile.py`)

| กรณี | ข้อมูล | ผลที่ควรได้ |
|---|---|---:|
| สอง Order ปกติ | 100 + 50 | 150 |
| Order ที่ยกเลิกไม่นับ | 100 + (ยกเลิก 70) | 100 |
| Row Order ซ้ำนับครั้งเดียว | 100 (สอง Row) | 100 |

| สูตร SQL | ผล |
|---|---|
| Join ธรรมดา | **ล้มที่กรณีที่ 3** (ได้ 200 ควรได้ 100) |
| ใช้ DISTINCT ก่อน Join | ผ่านทั้งสามกรณี |

บั๊กที่ Reconciliation จับได้หลัง Load ข้อมูลจริง กลับถูกจับได้ตั้งแต่ก่อนหน้านั้นด้วย Test ขนาด 3 Row เพราะเราเขียนกรณีที่ 3 ขึ้นมาจากคำถามว่า "ถ้าต้นทางส่งซ้ำจะเกิดอะไร" (ซึ่งมาจากการ Profile ใน[บท 3](/data-quality/profiling/#profile-ของทุก-column-โดยไม่ต้องรู้ความหมาย) ว่ามี order_id ซ้ำ)

</Step>

## Test แบบ "คืน Row ที่ผิด" และข้อจำกัด

Dbt มี Test แบบ Singular คือเขียน Query ที่คืน **Row ที่ละเมิดข้อกำหนด** ออกมา และถือว่าผ่านเมื่อไม่มี Row เลย (หนังสือ: DQF บทที่ 3 หน้า 57) ซึ่งในแบบฝึกเราใช้แบบเดียวกันนี้กับ "ไม่มี order_id ซ้ำใน Mart"

```sql
SELECT order_id FROM mart GROUP BY 1 HAVING count(*) > 1;
-- ผ่านเมื่อไม่มี row
```

| Mart | Row ที่ผิด | ผล |
|---|---:|---|
| Join ธรรมดา | 17 | ไม่ผ่าน |
| ใช้ DISTINCT | 0 | ผ่าน |

DQF รวมชนิดของ Test ที่พบบ่อยไว้ด้วย ได้แก่ Null, Volume, Distribution, Uniqueness และ **Known Invariants** (สิ่งที่เป็นจริงเสมอ เช่น กำไรเท่ากับรายได้ลบต้นทุน) และชี้ข้อจำกัดของ Test ที่เขียนเป็นโค้ดไว้สามข้อ (หนังสือ: DQF บทที่ 3 หน้า 56 ถึง 58)

- ข้อแรกคือ**ภาระดูแล** เมื่อ Model เปลี่ยน Test ก็ต้องเปลี่ยนตาม และ Test ที่ซับซ้อนอาจกินเวลาใกล้เคียงกับการพัฒนา Model เอง
- ข้อที่สองคือ **Test Fatigue** เพราะ Test ที่ไม่มีเหตุผลรองรับจะถูกลบเมื่อมันกีดขวาง ([บท 4](/data-quality/rule-design/#rule-ที่มากเกินไปและไม่มีใครเชื่อ))
- ข้อที่สามคือ**มองเห็นจำกัด** เพราะ Test อาจล้มเพราะปัญหาต้นทางที่อยู่เหนือกว่า ซึ่งบอกได้ว่ามีอะไรผิดแต่ไม่ช่วยให้แก้ได้เร็ว ถ้า Test ไม่ครอบคลุม End-to-end

ข้อที่สามนี้เองคือเหตุผลที่เราต้องมีทั้งสองอย่าง เพราะ Reconciliation มองข้ามทั้งสาย ส่วน Unit Test ตรวจตรรกะเฉพาะจุด

</Step>

## ออกแบบให้ตรวจย้อนได้

DDIA พูดถึง **Auditability** ว่า ระบบที่แสดง Dataflow ชัดเจนและมีที่มาของข้อมูลชัดเจน จะทำให้การตรวจความถูกต้องทำได้จริงขึ้น ถ้าการสร้างข้อมูลปลายทางเป็น Deterministic (ผลซ้ำได้) เราสามารถรัน Processor เดิมจากข้อมูลต้นทางเดิมอีกครั้งเพื่อดูว่าได้ผลเดียวกันหรือไม่ หรือจะรันอีกสายขนานเพื่อเทียบก็ได้ (หนังสือ: DDIA บทที่ 13 หัวข้อ "Designing for auditability" หน้า 577 ถึง 578)

พอนำมาใช้กับ Data Pipeline ก็ได้สามอย่าง

- ทำให้การ Load **ซ้ำได้อย่างปลอดภัย** (Idempotent) เช่น Load โดยใช้ batch_id เป็น Key เพื่อให้รันซ้ำแล้วข้อมูลไม่เบิ้ล ([บท 9](/data-quality/incidents/#fix-ชั่วคราวก่อน-แล้วถาวร) เป็นเรื่องจริงของข้อผิดพลาดแบบนี้)
- เก็บข้อมูลดิบไว้และไม่เขียนทับ เพื่อให้สร้าง Table ปลายทางใหม่จากต้นทางได้เมื่อพบบั๊ก
- รัน Reconciliation อย่างต่อเนื่อง แม้ในตอนที่ยังไม่สงสัยอะไร ซึ่งหนังสือบอกว่าการตรวจต่อเนื่องทำให้ "ไม่กลัวที่จะเปลี่ยนแปลง" และพัฒนา App ให้ตรงความต้องการที่เปลี่ยนไปได้ดีขึ้น

## เช็กตัวเอง

- Table ปลายทางที่ทีมคุณดูแล ตรวจย้อนกับต้นทางด้วยจำนวน Row และผลรวมหรือไม่ ความถี่เท่าไร
- ถ้าส่วนต่างหลัง Reconcile เหลือ 0.01 บาท คุณจะถือว่าผ่านหรือไม่ ใครเป็นคนกำหนด Threshold
- Test ที่ล้มเพราะต้นทางส่งผิดมา ควรรายงานให้ใคร และต่างจาก Test ที่ล้มเพราะ SQL ของเราผิดอย่างไร
