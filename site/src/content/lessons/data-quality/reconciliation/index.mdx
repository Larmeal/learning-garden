## "Trust, but verify"

*Designing Data-Intensive Applications* (DDIA) มีหัวข้อ "Trust, but Verify" ในบทเรื่องความถูกต้อง เริ่มจากข้อสังเกตว่าระบบทุกระบบสมมติว่าบางอย่างผิดได้และบางอย่างไม่มีวันผิด (system model) ข้อสมมติเหล่านั้นจริงเกือบตลอด แต่ในความเป็นจริงเป็นเรื่องของความน่าจะเป็น และถ้าทำงานในระดับใหญ่พอ เรื่องที่เกิดยากก็เกิดจริง (หนังสือ: DDIA ch.13 "Trust, but Verify")

หนังสือยกตัวอย่างที่น่าสนใจกับงานคุณภาพข้อมูล

- ซอฟต์แวร์ฐานข้อมูลที่ใช้กันแพร่หลายก็มีบั๊ก: MySQL บางรุ่นในอดีตไม่รักษาข้อจำกัด uniqueness ได้ถูกต้อง
- แอปพลิเคชันจำนวนมากไม่ได้ใช้ฟีเจอร์รักษาความถูกต้องของฐานข้อมูลอย่าง foreign key หรือ uniqueness constraint ให้ถูกต้อง
- ความสอดคล้องแบบ ACID ตั้งอยู่บนข้อสมมติว่าโปรแกรมไม่มีบั๊ก

ข้อสรุปของหนังสือ: ข้อมูลเสียหายดูจะเกิดขึ้นได้เสมอ เราจึงควรมีวิธีรู้ว่ามันเสียหาย แล้วแก้และตามหาต้นเหตุ การตรวจความถูกต้องของข้อมูลเรียกว่า **auditing** และ "ถ้าอยากแน่ใจว่าข้อมูลยังอยู่ ต้องอ่านมันแล้วตรวจ"

</Step>

## หลัก end-to-end

หลัก end-to-end (Saltzer, Reed, Clark, 1984) ที่ DDIA ยกมาบอกว่าฟังก์ชันบางอย่างทำให้ถูกต้องสมบูรณ์ได้เฉพาะกับความรู้และความช่วยเหลือของแอปพลิเคชันที่ปลายทั้งสองข้าง ไม่ใช่ที่ระบบสื่อสารตรงกลาง ฟังก์ชันระดับล่างช่วยลดโอกาสผิดพลาดได้ แต่ไม่พอด้วยตัวเอง

ในเรื่องความถูกต้องของข้อมูล: checksum ของ Ethernet, TCP และ TLS จับความเสียหายของแพ็กเก็ตในเครือข่ายได้ แต่จับความเสียหายจากบั๊กในซอฟต์แวร์ที่ปลายส่งและปลายรับ หรือจากดิสก์ที่เก็บข้อมูล ไม่ได้ ถ้าอยากจับทุกแหล่ง ต้องมี checksum ปลายทางถึงปลายทาง (หนังสือ: DDIA ch.13 "The end-to-end argument")

ข้อสรุปที่ใช้กับ pipeline ข้อมูล (ตามที่หนังสือกล่าว)

- ตรวจความถูกต้องแบบปลายทางถึงปลายทางดีที่สุด ยิ่งรวมระบบมากในการตรวจ ยิ่งมีโอกาสน้อยที่ความเสียหายจะหลุดที่ขั้นใดขั้นหนึ่ง
- ถ้าตรวจได้ว่า pipeline ของข้อมูลที่สร้างต่อมาถูกต้องทั้งสาย ดิสก์ เครือข่าย บริการ และอัลกอริทึมระหว่างทางก็ถูกรวมในการตรวจโดยปริยาย
- การตรวจต่อเนื่องแบบนี้เพิ่มความมั่นใจ ซึ่งทำให้ทีม**ขยับเร็วขึ้น** เหมือนการทดสอบอัตโนมัติ: บั๊กถูกพบเร็ว ความเสี่ยงของการเปลี่ยนแปลงลดลง

การกระทบยอดด้วยการนับและรวมเป็นรูปแบบที่ถูกและตรงที่สุดของการตรวจปลายทางถึงปลายทาง

</Step>

## กระทบยอดด้วยจำนวนแถวและผลรวม

สถานการณ์: ตาราง mart ที่ทีมวิเคราะห์สร้างเพื่อดูยอดชำระต่อคำสั่งซื้อ ต้องตรงกับระบบชำระเงินซึ่งเป็นแหล่งอ้างอิง เปรียบเทียบด้วยจำนวนแถวและผลรวม (รัน: `08_reconcile.py`)

```sql
-- mart ที่ join ธรรมดา
SELECT o.order_id, o.total_amount, p.amount AS paid
FROM orders o JOIN payments p USING (order_id)
WHERE o.status <> 'CANCELLED';
```

| ฝั่ง | แถว | ผลรวมยอดชำระ |
|---|---:|---:|
| ระบบชำระเงิน (ที่มีคำสั่งซื้อ ไม่ยกเลิก) | 2,533 | 6,454,814.21 |
| mart ที่ join ธรรมดา | 2,550 | 6,503,791.89 |
| ส่วนต่าง | **+17** | **+48,977.68** |
| mart ที่ใช้ `SELECT DISTINCT * FROM orders` ก่อน join | 2,533 | 6,454,814.21 (ตรงทุกตัว) |

ส่วนต่าง 17 แถวคือคำสั่งซื้อที่ซ้ำและไม่ถูกยกเลิก (ชุดที่ฝังไว้ 20 แถว ซึ่ง 17 แถวไม่ใช่ CANCELLED) ซึ่งเป็นเหตุที่การ join ธรรมดาเพิ่มแถวให้ตัวเดียวกัน ยอดที่นับซ้ำ +48,977.68 เท่ากับยอดซ้ำที่เจอในบท 5 เพราะเป็นคำสั่งซื้อชุดเดียวกัน และยอดชำระของมันเท่ากับยอดสั่งซื้อ

ข้อดีของวิธีนี้คือไม่ต้องรู้ล่วงหน้าว่าจะผิดตรงไหน ตรวจเพียงสองตัวเลขที่ปลายทางก็เห็นว่า "มีอะไรผิดระหว่างทาง" แล้วค่อยไล่หาด้วยการเทียบชุดของคีย์ (ในแบบฝึก: คีย์ที่ปรากฏใน mart มากกว่าหนึ่งครั้ง ได้ 267, 572, 797, 931, 986, ... ตรงกับ order_id ที่ซ้ำ)

</Step>

## ส่วนต่างต้องอธิบายได้ครบ

การกระทบยอดไม่ได้หมายถึง "ต้องเท่ากันเป๊ะ" แต่หมายถึง **ส่วนต่างทุกบาทมีเหตุผลที่ระบุได้** ยอดคำสั่งซื้อรวมเทียบกับยอดชำระรวม (รัน: `08_reconcile.py`)

| รายการ | จำนวน |
|---|---:|
| ยอดคำสั่งซื้อ (ไม่ยกเลิก ไม่ซ้ำ) | 6,453,757.71 |
| ยอดชำระทั้งหมด | 6,488,670.91 |
| ส่วนต่างทั้งหมด | **-34,913.20** |
| อธิบายได้ด้วย: 35 คำสั่งซื้อที่ยอดไม่ตรงกับการชำระ | -1,056.50 |
| อธิบายได้ด้วย: การชำระของคำสั่งซื้อที่ไม่มีอยู่จริง (20 รายการ) | -33,856.70 |
| ส่วนที่ยังอธิบายไม่ได้ | **0.00** |

ผลลัพธ์ที่น่าไว้ใจคือ "ส่วนที่ยังอธิบายไม่ได้ = 0" ถ้าเหลือเศษที่อธิบายไม่ได้ แม้เล็กน้อย แปลว่ายังมีปัญหาที่ไม่รู้จัก และ 35 ออเดอร์กับ 20 การชำระที่เป็นเหตุผล ก็คือสองกฎของบท 2 ที่รู้อยู่แล้ว

</Step>

## ทดสอบ SQL ที่แปลงข้อมูลบนข้อมูลเล็กที่รู้คำตอบ

การกระทบยอดจับ**หลัง**รัน การทดสอบหน่วยจับ**ก่อน**ขึ้นข้อมูลจริง DQF แบ่งชนิดของ test ไว้ (หนังสือ: DQF ch.5)

| ชนิด | ใช้ทำอะไร |
|---|---|
| Unit | ตรวจว่า SQL หนึ่งก้อนทำตามที่ควร กับข้อมูลน้อยๆ ต้องแยกตรรกะธุรกิจออกจากโค้ดเชื่อมต่อ |
| Functional | กับข้อมูลชุดใหญ่ ในขั้นตอนการประมวลผล ตรวจความถูกต้อง การนำเข้า การเก็บ |
| Integration | ให้ pipeline รับข้อมูลปลอมก่อนใช้ข้อมูลจริง เพื่อดูว่าผ่านเกณฑ์ |

ตัวอย่าง unit test ของ `mart` ใช้สามกรณีที่เล็กจนเห็นคำตอบด้วยตา (รัน: `08_reconcile.py`)

| กรณี | ข้อมูล | ผลที่ควรได้ |
|---|---|---:|
| สองคำสั่งซื้อปกติ | 100 + 50 | 150 |
| คำสั่งซื้อยกเลิกไม่นับ | 100 + (ยกเลิก 70) | 100 |
| แถวคำสั่งซื้อซ้ำนับครั้งเดียว | 100 (สองแถว) | 100 |

| สูตร SQL | ผล |
|---|---|
| join ธรรมดา | **ล้มที่กรณีที่ 3** (ได้ 200 ควรได้ 100) |
| ใช้ DISTINCT ก่อน join | ผ่านทั้งสามกรณี |

บั๊กที่การกระทบยอดจับได้หลังโหลดข้อมูลจริง ถูกจับได้ตั้งแต่ก่อนด้วย test ขนาด 3 แถว เพราะกรณีที่ 3 ถูกเขียนขึ้นด้วยคำถามว่า "ถ้าต้นทางส่งซ้ำจะเกิดอะไร" (ซึ่งมาจากการ profile ในบท 3 ว่ามี order_id ซ้ำ)

</Step>

## test แบบ "คืนแถวที่ผิด" และข้อจำกัด

dbt ใช้ test แบบ singular: เขียน query ที่คืน**แถวที่ละเมิดข้อกำหนด** แล้วถือว่าผ่านเมื่อไม่มีแถว (หนังสือ: DQF ch.3) ในแบบฝึกใช้แบบเดียวกันกับ "ไม่มี order_id ซ้ำใน mart"

```sql
SELECT order_id FROM mart GROUP BY 1 HAVING count(*) > 1;
-- ผ่านเมื่อไม่มีแถว
```

| mart | แถวที่ผิด | ผล |
|---|---:|---|
| join ธรรมดา | 17 | ไม่ผ่าน |
| ใช้ DISTINCT | 0 | ผ่าน |

DQF รวมชนิดของ test ที่พบบ่อยไว้ด้วย: null, ปริมาณ, การแจกแจง, ความไม่ซ้ำ และ **known invariants** (สิ่งที่เป็นจริงเสมอ เช่น กำไรเท่ากับรายได้ลบต้นทุน) และชี้ข้อจำกัดของ test ที่เขียนเป็นโค้ด (หนังสือ: DQF ch.3)

- **ภาระดูแล**: โมเดลเปลี่ยน test ต้องเปลี่ยนตาม test ซับซ้อนอาจกินเวลาใกล้เคียงกับการพัฒนาโมเดลเอง
- **test fatigue**: test ที่ไม่มีเหตุผลรองรับจะถูกลบเมื่อกีดขวาง (บท 4)
- **มองเห็นจำกัด**: test อาจล้มเพราะปัญหาต้นทางที่อยู่เหนือกว่า ซึ่งบอกว่ามีอะไรผิดแต่ไม่ช่วยให้แก้ได้เร็ว ถ้า test ไม่ครอบคลุมปลายทางถึงปลายทาง

ข้อสุดท้ายคือเหตุผลที่ต้องมีทั้งสองอย่าง การกระทบยอดมองข้ามทั้งสายส่วน test หน่วยตรวจตรรกะเฉพาะจุด

</Step>

## ออกแบบให้ตรวจย้อนได้

DDIA พูดถึง **auditability**: ระบบที่แสดง dataflow ชัดเจน ที่มาของข้อมูลชัดเจน ทำให้ตรวจความถูกต้องทำได้จริงขึ้น ถ้าการสร้างข้อมูลปลายทางเป็น deterministic (ผลซ้ำได้) เรารัน processor เดิมจากข้อมูลต้นทางเดิมอีกครั้งเพื่อดูว่าได้ผลเดียวกันหรือไม่ หรือรันอีกสายขนานเพื่อเทียบ (หนังสือ: DDIA ch.13 "Designing for auditability")

นำมาใช้กับ pipeline ข้อมูล

- ทำให้การโหลด**ซ้ำได้อย่างปลอดภัย** (idempotent) เช่น โหลดโดยใช้ batch_id เป็นกุญแจ เพื่อให้รันซ้ำไม่ทำให้ข้อมูลเบิ้ล (บท 9 เป็นเรื่องจริงของข้อผิดพลาดแบบนี้)
- เก็บข้อมูลดิบไว้ ไม่เขียนทับ เพื่อสร้างตารางปลายทางใหม่จากต้นทางเมื่อพบบั๊ก
- รันการกระทบยอดต่อเนื่อง ไม่ใช่แค่ตอนสงสัย หนังสือบอกว่าการตรวจต่อเนื่องทำให้ "ไม่กลัวที่จะเปลี่ยนแปลง" และพัฒนาแอปให้ตรงความต้องการที่เปลี่ยนไปได้ดีขึ้น

## เช็กตัวเอง

- ตารางปลายทางที่ทีมคุณดูแล ตรวจย้อนกับต้นทางด้วยจำนวนแถวและผลรวมหรือไม่ ความถี่เท่าไร
- ถ้าส่วนต่างหลังกระทบยอดเหลือ 0.01 บาท คุณจะถือว่าผ่านหรือไม่ ใครเป็นคนกำหนดเกณฑ์
- test ที่ล้มเพราะต้นทางส่งผิดมา ควรรายงานให้ใคร และต่างจาก test ที่ล้มเพราะ SQL ของเราผิดอย่างไร

</Step>
