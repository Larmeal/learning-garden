## วงจรของ data incident

DQF วางวงจรจัดการ data incident ให้เหมือนงาน DevOps: **detect, respond, root cause analysis (RCA), fix, และ blameless postmortem** แล้ววนไปที่การป้องกัน (หนังสือ: DQF ch.6) DMBOK2 ให้ขั้นตอนของทีม data quality คล้ายกัน คือ วินิจฉัย, หาทางเลือกในการแก้, และแก้ โดยบันทึกทุกการตัดสินใจในระบบติดตาม incident (หนังสือ: DMBOK2 §2.7.3)

บทนี้ใช้ incident จำลองหนึ่งเรื่องที่เรารู้คำตอบ เพื่อเดินครบวงจร **incident ถูกฉีดเข้าไปในสำเนาที่สะอาดของ table orders** เพื่อให้ทุก query ได้ผลที่พิสูจน์ได้ (รัน: `09_incident.py`)

เรื่องมีอยู่ว่า วันที่ 12 และ 13 กันยายน ระบบ load ข้อมูลถูกรันซ้ำและ load สองวันนั้นสองรอบ ขณะเดียวกัน query ของชั้น staging ถูกแก้ให้ตัด `DISTINCT` ออก ถ้าเกิดอย่างใดอย่างหนึ่งเพียงอย่างเดียว ข้อมูลซ้ำจะไม่ถึง dashboard แต่พอเกิดพร้อมกัน revenue สองวันนั้นเบิ้ลเป็นสองเท่า

</Step>

<Step>

## Detect: เทียบกับสิ่งที่ควรเป็น

เทียบ revenue รายวันกับค่าที่ควรเป็น พบสองวันที่เกิน 1.5 เท่า: 2026-09-12 และ 2026-09-13 อัตราส่วนทั้งสองวันคือ 2.00 เป๊ะ

ในการทำงานจริง ไม่มีใครมี "ค่าที่ควรเป็น" ให้เทียบ สิ่งที่เทียบได้คือ baseline จากอดีต เช่น detector ที่เทียบกับวันเดียวกันของสัปดาห์ก่อนๆ ในบท 7 และ revenue ที่ผิดปกติแบบนี้จะถูกจับได้โดย volume detector นั้น (ในแบบฝึกบทนี้ใช้การเทียบกับค่าที่ถูกต้องตรงๆ เพื่อให้ incident ชัด)

DQF เตือนว่า การ detect เป็นแค่ขั้นแรก ผู้บริหารที่หนังสือยกคำพูดพูดว่า "ต้องรู้ว่าอะไรพัง ใครได้รับผลกระทบ ทำไม ที่ไหน และสาเหตุน่าจะเป็นอะไร" ซึ่งเป็นงานของขั้นต่อไป (หนังสือ: DQF ch.6)

</Step>

<Step>

## Respond: ใครคุม ใครรู้

DQF แนะนำให้ทีมเตรียมเอกสารล่วงหน้า (หนังสือ: DQF ch.6)

- **runbook**: คู่มือการใช้ service ต่างๆ และปัญหาที่เจอบ่อย
- **playbook**: ขั้นตอนทีละขั้นของการรับมือ incident
- **incident commander**: คนที่แบ่งงาน สรุปข้อมูล และสื่อสารกับ consumer ต้นทางและปลายทาง โดยหมุนเวียนเป็นรายวันหรือรายสัปดาห์ หรือแยกตาม dataset ที่ทีมเป็นเจ้าของ

หน้าที่หลักของ incident commander ตามหนังสือ: แจ้งเหตุต่อทีมและผู้เกี่ยวข้องตั้งแต่เนิ่นๆ และบ่อย, บันทึก asset ที่ได้รับผลกระทบ, ประสานงานและมอบหมาย, เผยแพร่ runbook และ playbook, ประเมินความรุนแรงและผลกระทบ

**ประเมินความรุนแรง**: หนังสือแนะนำให้ติดป้ายสถานะ (fixed, expected, investigating, no action needed, false alarm) และถามว่าข้อมูลที่เสียสำคัญหรือไม่ เพราะ "phantom data" ข้อมูลที่ไม่มีใครใช้มาหลายเดือนอาจทำให้เสียเวลาแก้ฟรี ข้อมูลที่ขับเคลื่อนรายงานการเงินคือลำดับสูง (สอดคล้องกับหลัก criticality ของบท 1)

**ขอบเขตความเสียหาย (blast radius)**: ในแบบฝึกใช้กราฟ lineage เล็กๆ ไล่ downstream จากจุดที่เสีย

```text
raw_orders → stg_orders → daily_revenue → finance_dashboard
                                        → forecast_model
```

ความเสียหายจาก incident นี้ครอบคลุมสี่ downstream: `stg_orders`, `daily_revenue`, `finance_dashboard`, `forecast_model` ทีมต้องบอกเจ้าของของแต่ละตัว ไม่ใช่แค่เจ้าของ table ที่เสีย

</Step>

## Root cause analysis: ห้าขั้นของ DQF

DQF สรุปว่าปัญหาข้อมูลส่วนใหญ่มาจากสามกลุ่ม: **ข้อมูลที่ป้อนเข้ามาเปลี่ยนไป, ตรรกะที่แปลงข้อมูลเปลี่ยน, หรือปัญหาในการปฏิบัติงาน** (runtime error, permission, infrastructure, schedule) และเตือนว่า incident "มักไม่มีต้นเหตุเดียว" แต่เป็นการรวมกันของหลายสาเหตุ (หนังสือ: DQF ch.6) ห้าขั้นที่หนังสือเสนอ ทำตามด้วย query จริง

**ขั้น 1: ดู lineage** หา node ที่อยู่ upstream ที่สุดที่ยังเห็นปัญหา

| node | order_id ซ้ำในสองวันนั้น |
|---|---:|
| raw_orders | 30 |
| stg_orders (v2) | 30 |
| stg_orders (v1) | 0 |

ปัญหาเริ่มที่ `raw_orders` (upstream ที่สุด) และ stg_orders เวอร์ชันเดิม (v1) กรองมันออกได้

**ขั้น 2: ดูโค้ด** เปรียบเทียบ query ที่สร้าง table

```diff
-SELECT DISTINCT order_id, customer_id, order_date, total_amount FROM raw_orders
+SELECT order_id, customer_id, order_date, total_amount FROM raw_orders
```

เวอร์ชันใหม่ตัด `DISTINCT` ออก นี่คือเหตุผลที่ปัญหา upstream ไหลมาถึง downstream

**ขั้น 3: ดูข้อมูล** ผิดทุก row บางช่วง หรือบางกลุ่ม

| วัน | row ที่ซ้ำ |
|---|---:|
| 2026-09-12 | 17 |
| 2026-09-13 | 13 |

ทั้งสองวัน **ทุก order ปรากฏสองครั้ง** (วันอื่นไม่มีซ้ำ) รูปแบบตามปฏิทิน ไม่ใช่ตามกลุ่ม เมื่อแยกตาม country มี row ซ้ำเพียง 30 row น้อยเกินจะเห็นรูปแบบ จึงไม่มีหลักฐานของคำอธิบายตามกลุ่ม ประเด็นนี้ต่างจากตัวอย่างใน DQF ที่เห็น null พุ่งเฉพาะแหล่งหนึ่ง การดูว่าเป็น "ช่วงเวลา" หรือ "กลุ่ม" ชี้ทางต่างกันมาก

**ขั้น 4: ดู operating environment** จาก log ของงาน load

| batch_id | ครั้งที่ load | row | สถานะ |
|---|---:|---:|---|
| B20260912 | 2 | 34 | RETRIED |
| B20260913 | 2 | 26 | RETRIED |

สองชุดนี้ถูก load สองครั้ง ตรงกับสองวันที่ซ้ำ

**ขั้น 5: ถามเพื่อนร่วมทีม** ใครเป็นเจ้าของ ใครใช้ เคยเกิดอะไรคล้ายกัน ในแบบฝึกคือตารางเจ้าของ: แหล่งข้อมูลดิบเป็นของทีม ingest query ของ staging เป็นของ analytics engineering

**Five Whys** (วิธีของ Amazon ที่ DQF ยก): ถามทำไมซ้ำๆ และแต่ละคำตอบถามต่อว่ากันได้ไหม detect ได้ก่อนไหม ถ้าเป็นความผิดพลาดของคน ทำไมมันเกิดได้

| # | คำถาม | คำตอบ |
|---|---|---|
| 1 | ทำไม revenue 12-13 ก.ย. เป็นสองเท่า | order ถูกนับสองครั้งใน daily_revenue |
| 2 | ทำไมถูกนับสองครั้ง | stg_orders ปล่อย row ซ้ำผ่านมา |
| 3 | ทำไมปล่อยผ่าน กันได้ไหม | การแก้เวอร์ชัน 2 ตัด DISTINCT ที่เคยปิดบังปัญหาออก |
| 4 | ทำไมมี row ซ้ำใน raw_orders | งาน load ถูกรันซ้ำและ load ทั้งสองชุดสองรอบ |
| 5 | ทำไม load ซ้ำได้ ทำไมไม่มีใครเห็น | การ load ไม่ idempotent และไม่มี test ว่าไม่ซ้ำบน stg_orders |

DMBOK2 ใช้เทคนิคเดียวกัน (Five Whys, Pareto, fishbone, track and trace) และชี้ว่าต้องมีผู้เชี่ยวชาญทั้งด้านเทคนิคและธุรกิจร่วมวิเคราะห์ (หนังสือ: DMBOK2 §4.6, §2.7.3)

</Step>

## Fix: ชั่วคราวก่อน แล้วถาวร

DQF แยก **การแก้เบื้องต้น** (เช่นหยุดหรือ "circuit break" pipeline) ออกจาก **การแก้ขั้นสุดท้าย** ที่แก้สาเหตุที่แท้จริง และเน้นให้สื่อสารสถานะในช่องทางเดียวที่ผู้เกี่ยวข้องดูได้ (หนังสือ: DQF ch.6)

- **เบื้องต้น**: หยุดการ refresh dashboard การเงิน เพื่อไม่ให้ใครอ่านตัวเลขเบิ้ล
- **ขั้นสุดท้าย**: คืน `DISTINCT` ทำให้การ load idempotent โดยใช้ `batch_id` และเพิ่ม test ว่าไม่ซ้ำบน `stg_orders`
- **backfill**: สร้าง `daily_revenue` ใหม่ด้วย query ที่แก้แล้ว ผลของสองวันกลับมาตรงค่าที่ควรเป็น (ตรวจใน `09_incident.py`)

DMBOK2 เสนอทางเลือกในการแก้ที่กว้างกว่านั้น รวมถึงทางที่หลายทีมลืม คือ **"ไม่ทำอะไร" ตามต้นทุนและผลกระทบ** เมื่อต้นทุนการแก้สูงกว่าคุณค่า (หนังสือ: DMBOK2 §2.7.3) และเตือนว่า "แก้ที่จุดที่ปัญหาเกิด" และการแก้ควรรวมการป้องกันการเกิดซ้ำ (§4.2) แก้ข้อมูลตรงๆ ใน production โดยไม่มีการควบคุมและร่องรอย "เสี่ยงอย่างยิ่ง ควรหลีกเลี่ยง"

ผลกระทบของ incident นี้: revenue ถูกแสดงเกินไป **71,120.46** ในสองวัน (รัน: `09_incident.py`)

</Step>

## Blameless postmortem

DQF ยกคำพูดของวิศวกรความน่าเชื่อถือ (SRE) ว่า "ทุก incident ระบบคือสิ่งที่ผิด ไม่ใช่คนที่เขียนโค้ด ระบบที่ดีทนต่อความผิดพลาดของคนได้" และให้ postmortem เป็นการประชุมพร้อมเอกสารหลังแก้เสร็จ (หนังสือ: DQF ch.6) แนวปฏิบัติ

- มองเป็นการเรียนรู้ ไม่ใช่การหาคนผิด
- ประเมินความพร้อมสำหรับครั้งหน้า: ปรับ runbook, monitoring, alert
- เขียนเอกสารและแบ่งปัน เพื่อไม่ให้ความรู้ในหัวคนหายไปเมื่อคนออก
- ทบทวน SLA, SLI, SLO เพราะ SLA ที่เหมาะเมื่อหกเดือนก่อนอาจไม่เหมาะแล้ว

บันทึกของ incident นี้ในแบบฝึก (ตัวเลขเวลาเป็นข้อสมมติของเรื่อง)

| หัวข้อ | เนื้อหา |
|---|---|
| สรุป | revenue 12 และ 13 ก.ย. ถูกแสดงสองเท่าให้ finance และ forecast model |
| ผลกระทบ | แสดงเกิน 71,120.46; consumer: finance_dashboard, forecast_model |
| เวลาจนรู้ / แก้ | 30 ชม. / 6 ชม. |
| ต้นทุนตามสูตรของบท 1 | (30 + 6) × 300 = 10,800 |
| สาเหตุ | load ซ้ำสองวัน; DISTINCT ถูกตัด; ไม่มี test ความไม่ซ้ำ |
| สิ่งที่ต้องทำ | load แบบ idempotent (ทีม ingest); คืน DISTINCT พร้อม test (analytics engineering); monitor volume เทียบวันเดียวกัน (analytics engineering) |

สังเกตว่าสาเหตุทั้งสามอย่างเป็นเรื่องของระบบ ไม่มีชื่อคน และแต่ละการกระทำมีเจ้าของ

<Callout type="warn" title="เรื่องนี้ง่ายเกินจริง">
incident ในบทนี้มีสาเหตุที่สะอาดสองอย่าง และเรารู้คำตอบอยู่แล้ว incident จริงมักมีหลักฐานขัดกัน ข้อมูลหาย และต้องย้อนทำหลายรอบ DQF เตือนว่าต้นเหตุเดียวเป็นข้อยกเว้น ไม่ใช่กฎ (หนังสือ: DQF ch.6)
</Callout>

<Callout type="try" title="ลองทำใน repo นี้">
เปิด `09_incident.py` เปลี่ยนวันที่ถูก load ซ้ำเป็นสามวัน หรือทำให้เฉพาะ customer สหรัฐซ้ำ แล้วดูว่าขั้น "ดูข้อมูล" ชี้ไปที่ปฏิทินหรือกลุ่ม และตาราง Five Whys ต้องเขียนใหม่อย่างไร
</Callout>

</Step>

## เช็กตัวเอง

- incident ข้อมูลล่าสุดของทีมคุณ มี runbook ไหม ใครเป็น incident commander และมีใครรู้ blast radius ก่อนที่ consumer จะบอก
- ถ้าเจ้าของงาน load บอกว่า "งานของฉันทำถูกต้อง มีคนแก้ query ผิด" และเจ้าของ query บอกว่า "ฉันคาดว่าข้อมูล upstream สะอาด" postmortem ควรสรุปอย่างไรโดยไม่โทษใคร
- สำหรับสาเหตุแต่ละข้อ ใน Five Whys คุณจะเขียนการกระทำ (action) อะไร และใครเป็นเจ้าของ

</Step>
