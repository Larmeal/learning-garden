## ส่งครั้งเดียว ส่งอย่างน้อยหนึ่งครั้ง หรือส่งพอดีหนึ่งครั้ง

เวลาเราบอกว่าระบบ "ส่งข้อมูลถึง" มีสามระดับให้เลือก ระดับแรกคือ At-most-once ซึ่งส่งไม่เกินหนึ่งครั้ง ถ้าผิดพลาดก็ปล่อยให้หาย ระดับที่สองคือ At-least-once ซึ่งส่งซ้ำจนกว่าจะสำเร็จ ไม่หายแต่อาจซ้ำ ส่วนระดับสุดท้ายคือ Exactly-once ที่ทุกชิ้นถูกประมวลผลพอดีหนึ่งครั้ง ใน[บทที่ 4](/kafka/consumer-groups/) เราเห็นฝั่ง Consumer ไปแล้วว่าการ Commit ก่อนประมวลผลเป็น At-most-once และการ Commit หลังประมวลผลเป็น At-least-once ในบทนี้เราดูฝั่ง Producer และดูว่า Kafka ทำให้ Exactly-once เกิดขึ้นได้อย่างไร

## ทำให้ Record ซ้ำ แล้วดู Idempotence แก้

ใน[บทที่ 3](/kafka/producers/) เราบอกไว้ว่า Producer ส่งซ้ำเมื่อไม่ได้รับคำตอบ ทีนี้เรามาทำให้มันเกิดจริง เราตั้ง Topic ที่มีสามสำเนา `min.insync.replicas=2` และ Producer ใช้ `acks=all` กับ `request.timeout.ms=3000` แล้วใช้ `docker pause` ตรึง Follower ตัวหนึ่งไว้ ผลคือ Leader เขียน Order ลง Log ของตัวเองแล้ว แต่ต้องรอ Follower ซึ่งไม่ตอบ จึงตอบ Producer ไม่ได้ พอครบ 3 วินาที Producer คิดว่าไม่สำเร็จและส่งซ้ำ ซึ่ง Leader ก็เขียนอีกรอบ เมื่อปล่อย Follower แล้วอ่าน Log ได้

```text
enable.idempotence=false -> ['order-o-1', 'order-o-1', 'order-o-1']
enable.idempotence=true  -> ['order-o-1']
```

Order ใบเดียวกลายเป็นสามชุดเพราะ Producer ส่งซ้ำสองครั้ง ส่วนตอนเปิด Idempotence เหลือชุดเดียว (รัน) เพราะทุก Batch ถูกติดตรา `producerId` กับเลขลำดับไปด้วย (ดูได้จาก Log ในบทนั้น) Leader เห็นว่าตราชุดนี้เขียนไปแล้วก็ไม่เขียนซ้ำ แต่ตอบ Offset ของที่มีอยู่ (หนังสือ: Kafka: The Definitive Guide หัวข้อ Idempotent Producer หน้า 182) กดดูทีละขั้นใน Lab ด้านล่าง

<DuplicateLab client:visible />

Idempotence กันเฉพาะการซ้ำที่มาจากการส่งซ้ำของ Producer ตัวเดียวกัน ถ้าโปรแกรมของเรารันสองรอบแล้วส่ง Order เดียวกันสองครั้งเอง ตราของสองรอบไม่เหมือนกัน และ Kafka ไม่รู้ว่าซ้ำ หนังสืออธิบายข้อจำกัดนี้ไว้ (หนังสือ: Kafka: The Definitive Guide หัวข้อ Limitations of the Idempotent Producer หน้า 184)

</Step>

## Transaction: เขียนหลาย Record แล้วค่อยบอกว่าให้นับ

บางครั้งเราต้องเขียนหลาย Record ให้เป็นก้อนเดียวกัน คือหรือทั้งหมดนับ หรือไม่นับเลย Kafka มี Transaction ให้ Producer ที่ตั้ง `transactional.id` เรียก `begin_transaction`, ส่ง Record, แล้ว `commit_transaction` หรือ `abort_transaction` (หนังสือ: Kafka: The Definitive Guide หัวข้อ Transactions หน้า 186) เราลองทำสามก้อนตามลำดับ ก้อน a (a1, a2) แล้ว Commit ก้อน b (b1, b2) แล้ว Abort และก้อน c (c1) ที่เขียนไปแล้วแต่ยังไม่ปิด Consumer สองแบบจะเห็นไม่เหมือนกัน

```text
read_committed   เห็น ['a1', 'a2']
read_uncommitted เห็น ['a1', 'a2', 'b1', 'b2', 'c1']
```

ค่า `isolation.level` ของ Consumer เป็นตัวตัดสิน แบบ `read_committed` ได้เฉพาะ Record ที่อยู่ใน Transaction ที่ Commit แล้ว (หรือไม่ได้อยู่ใน Transaction) ส่วนแบบ `read_uncommitted` ได้ทุกตัวรวม Record ของ Transaction ที่ Abort ไปแล้ว (หนังสือ: Kafka: The Definitive Guide หัวข้อ How Do Transactions Guarantee Exactly-Once หน้า 188) พอเรา Commit ก้อน c ตัว `read_committed` เห็น `['a1', 'a2', 'c1']` (รัน)

<Callout type="warn" title="Abort แล้ว Record ที่ยังไม่ออกจาก Client จะหาย">
ตอนทดลองครั้งแรก `read_uncommitted` ไม่เห็น `b1` กับ `b2` เลย เพราะ `abort_transaction()` ทิ้ง Record ที่ยังค้างอยู่ใน Queue ของ Client ที่ยังไม่ได้ส่ง ต้องเรียก `flush()` ก่อน Abort ถ้าอยากให้ Record ที่ Abort ไปปรากฏใน Log จริง (รัน)
</Callout>

</Step>

## ข้างใน Log มี Marker

Transaction ไม่ได้ใช้ Log พิเศษ มันเขียนลงใน Log ปกติ และเมื่อปิดก้อนก็เขียน Record พิเศษชื่อ Marker ต่อท้าย เราเปิดไฟล์ Log ของ Partition นั้นด้วย `kafka-dump-log.sh`

```text
offset  content  kind
0       a1       data
1       a2       data
2       COMMIT   control
3       b1       data
4       b2       data
5       ABORT    control
6       c1       data
7       COMMIT   control
```

Record ข้อมูล 5 ตัวใช้ 8 Offset เพราะ Marker ของแต่ละก้อนใช้ Offset ของตัวเองด้วย (รัน) Consumer ไม่เคยได้รับ Marker ตัวเหล่านี้ แต่ใช้มันตัดสินว่า Record ไหนนับ ตอนที่ก้อน c ยังเปิดอยู่ Log จบที่ Offset 6 และ Consumer แบบ `read_committed` อ่านผ่านตรงนั้นไปไม่ได้ จุดนั้นเรียกว่า Last Stable Offset ซึ่งก็คือ Offset ของ Record แรกใน Transaction ที่ยังไม่จบ เลือกระดับกับสถานะของก้อนสุดท้ายใน Lab นี้ดูผลได้เลย

## Consume-Transform-Produce แบบพอดีหนึ่งครั้ง

งานที่พบบ่อยที่สุดคืออ่านจาก Topic หนึ่ง แปลงข้อมูล แล้วเขียนลงอีก Topic ถ้าโปรแกรมล้มระหว่างทางเราไม่อยากให้ผลลัพธ์ซ้ำหรือขาด วิธีของ Kafka คือรวมสองอย่างไว้ใน Transaction เดียว คือเขียนผลลัพธ์ และ Commit Offset ที่อ่านถึงของ Group ด้วยคำสั่ง `send_offsets_to_transaction` ดังนั้นถ้า Transaction Abort ทั้งผลลัพธ์และ Offset ก็ไม่นับพร้อมกัน

เราทดลองด้วยงาน 10 ชิ้น ประมวลผลทีละ 5 ชิ้นต่อ Transaction ตัวทำงานรอบแรกจบก้อนแรกด้วย Commit แล้วเขียนก้อนที่สองไปแต่ถูกทิ้งไว้กลางทาง (ไม่ Commit) ณ ตอนนั้น Log ของ Topic ผลลัพธ์มี 10 Record (5 ที่ Commit แล้วกับ 5 ที่ยังไม่ปิด) จากนั้นเราเริ่มตัวทำงานรอบใหม่ด้วย `transactional.id` เดิม ซึ่งทำให้ Kafka Abort ก้อนที่ค้างและปิดประตูใส่ Producer ตัวเก่า

```text
read_committed   เห็น 10 ผลลัพธ์: N0 ถึง N9 ชิ้นละหนึ่งตัว
read_uncommitted เห็น 15 ผลลัพธ์ (ก้อนที่ Abort ยังอยู่ใน Log)
Producer ตัวเก่าพยายาม Commit: _FENCED
```

ผลลัพธ์ทุกชิ้นปรากฏพอดีหนึ่งครั้งสำหรับผู้อ่านแบบ `read_committed` และ Producer ตัวเก่าที่ถูกทิ้งไว้ Commit ไม่ได้อีกเพราะถูก Fence (รัน) หนังสือเรียกกลไกนี้ว่า Transactional ID และ Fencing (หนังสือ: Kafka: The Definitive Guide หัวข้อ Transactional IDs and Fencing หน้า 196)

<Callout type="note" title="ขอบเขตของ Exactly-once">
ความรับประกันนี้ใช้ได้เมื่อทั้งอ่านและเขียนเกิดใน Kafka หนังสือบอกชัดว่า Transaction ไม่แก้ปัญหาที่ผลลัพธ์ออกไปนอก Kafka เช่นเขียนลงฐานข้อมูล หรือส่งอีเมล เพราะเรา Abort สิ่งที่อยู่นอก Kafka ไม่ได้ (หนังสือ: Kafka: The Definitive Guide หัวข้อ What Problems Aren't Solved by Transactions หน้า 191) กรณีนั้นเราต้องทำให้การเขียนปลายทางทนการซ้ำเอง เช่นใช้ Primary Key อย่างที่เราจะทำใน[บทที่ 12](/kafka/capstone-pipeline/)
</Callout>

</Step>
