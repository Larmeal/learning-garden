## Partition คือโฟลเดอร์ของไฟล์ Segment

ใน[บทที่ 1](/kafka/what-is-kafka/) เราเห็นไฟล์ `.log` ไฟล์เดียวใน Partition แต่ถ้า Partition เก็บข้อมูลไปเรื่อย ๆ ไฟล์เดียวก็ใหญ่ไม่จำกัด ลบของเก่าก็ลำบาก Kafka จึงตัด Log ของแต่ละ Partition ออกเป็นไฟล์ท่อน ๆ เรียกว่า Segment แล้วเขียนต่อท้ายที่ Segment ล่าสุดที่เรียกว่า Active Segment อย่างเดียว เมื่อ Segment เต็มก็ปิดมันแล้วเปิดไฟล์ใหม่ (หนังสือ: Kafka: The Definitive Guide หัวข้อ Physical Storage หน้า 149)

เราลองสร้าง Topic ที่มี Segment เล็กมากเพื่อให้เห็นการตัดไฟล์ แล้วส่ง Record 60 ตัวทีละตัว

<Callout type="note" title="Segment เล็กขนาดนี้ต้องใช้ค่าพิเศษ">
Kafka 4.x กำหนดให้ `segment.bytes` ต่ำสุดที่ 1 MiB (อ่านจาก `LogConfig.java` ของ Source 4.4.0) เราไม่อยากส่งข้อมูลเป็นเมกะไบต์เพื่อเห็น Segment แตก จึงใช้ค่า `internal.segment.bytes` ซึ่งเป็นค่าสำหรับทดสอบของ Kafka เองที่ตั้งได้ต่ำกว่า ในแบบฝึกตั้งไว้ที่ 2,048 ไบต์ ค่านี้ไม่ควรใช้ในงานจริง
</Callout>

```text
00000000000000000000.log        00000000000000000026.log        00000000000000000052.log
00000000000000000013.log        00000000000000000039.log        leader-epoch-checkpoint
(และ .index, .timeindex ของแต่ละอัน)                            partition.metadata
```

ชื่อของไฟล์แต่ละไฟล์คือ Offset ของ Record ตัวแรกในไฟล์นั้น เรามี Segment ห้าอัน เริ่มที่ Offset 0, 13, 26, 39 และ 52 สี่อันแรกมีขนาด 2,028 ไบต์เท่ากัน (Record ละ Batch ขนาด 156 ไบต์ คูณ 13) และอันสุดท้ายเป็น Active Segment ขนาด 1,248 ไบต์ (รัน) ขนาดไม่เกิน 2,048 เพราะ Batch ที่ใส่แล้วจะล้นจะถูกเปิดไฟล์ใหม่แทน

</Step>

## เปิดไฟล์ดู แล้วหา Offset ให้เจอ

เราเปิด Segment ที่เริ่มที่ Offset 26 ด้วย `kafka-dump-log.sh`

```text
baseOffset: 26 lastOffset: 26 count: 1 ... position: 0   ...
baseOffset: 27 lastOffset: 27 count: 1 ... position: 156 ...
baseOffset: 28 lastOffset: 28 count: 1 ... position: 312 ...
```

บรรทัดแรกของไฟล์เริ่มที่ Offset 26 ตรงกับชื่อไฟล์ และ `position` คือตำแหน่งไบต์ที่ Batch นั้นเริ่มในไฟล์ (รัน) แล้วถ้า Consumer ขอ Offset 30 Broker หาอย่างไร ถ้าอ่านทีละ Batch ตั้งแต่ต้นไฟล์ก็ช้า Kafka จึงมีไฟล์ `.index` ที่ไม่ได้จดทุก Record แต่จดเป็นช่วง ๆ ตามค่า `index.interval.bytes` (เราตั้งไว้ที่ 512) หนังสือเรียก Index ว่าช่วยให้หาตำแหน่งของ Offset ได้เร็ว (หนังสือ: Kafka: The Definitive Guide หัวข้อ Indexes หน้า 155) ไฟล์ Index ของ Segment 26 มีรายการแค่สามรายการ

```text
offset 30 -> byte 624
offset 34 -> byte 1248
offset 38 -> byte 1872
```

ขั้นตอนหา Offset 30 จึงมีสามจังหวะ **ขั้นตอนแรก** เลือกไฟล์ที่ชื่อใหญ่ที่สุดแต่ไม่เกิน 30 ซึ่งคือไฟล์ 26 **ขั้นตอนต่อมา** เปิด Index เลือกรายการที่ใหญ่ที่สุดแต่ไม่เกิน 30 ได้ Byte 624 **ขั้นตอนสุดท้าย** กระโดดไปที่ Byte นั้นแล้วอ่านต่อไปทีละ Batch จนเจอ ซึ่งในที่นี้เจอทันที เลื่อน Slider ใน Lab ดูว่าแต่ละ Offset ผ่านสามจังหวะนี้อย่างไร

## Retention ลบทีละทั้งไฟล์

Kafka ไม่เก็บ Record ตลอดไป ตั้งได้ว่าเก็บกี่วัน (`retention.ms`) หรือกี่ไบต์ (`retention.bytes`) แต่สิ่งที่ถูกลบคือทั้ง Segment ไม่ใช่ Record ทีละตัว และ Segment จะถูกลบเมื่อ Record ที่ใหม่ที่สุดในไฟล์นั้นเก่าเกินกำหนด เรามาลองดูผลจริง

ขั้นแรกเรารอให้ Segment ทั้งห้าเก่า แล้วส่ง Record ใหม่เพิ่มอีก 5 ตัวเข้าไปที่ Active Segment จากนั้นตั้ง `retention.ms=15000`

```text
segments ก่อน   [0, 13, 26, 39, 52]
segments หลัง   [52]
log start offset 52, log end offset 65
```

สี่ไฟล์แรกที่ Record ในนั้นเก่าทั้งหมดหายไป ส่วนไฟล์ 52 อยู่ เพราะมี Record ใหม่ปนอยู่ ผลที่น่าสนใจคือ Record ที่เขียนไว้ตั้งแต่ตอนแรกอีก 8 ตัว (Offset 52 ถึง 59) ยังอ่านได้ ทั้งที่เก่าเกินกำหนดแล้ว เพราะไฟล์ของมันยังมีเพื่อนบ้านที่ใหม่ ส่วน Offset ท้ายสุดของ Topic ยังเป็น 65 เหมือนเดิม Offset ไม่เคยถูกใช้ซ้ำ และ Group ใหม่ที่เริ่มจากต้น Log ได้ Record ตั้งแต่ Offset 52 ไม่ใช่ 0 (รัน)

ถ้า Record ทุกตัวเก่าหมดล่ะ แบบฝึกรอต่อไปจน Record ใหม่อายุเกิน 15 วินาทีด้วย แล้วได้ Segment เดียวชื่อ `00000000000000000065.log` ที่ขนาด 0 ไบต์ ทุกอย่างถูกลบรวมถึง Active Segment เดิม และ Broker สร้างไฟล์ว่างใหม่ที่ชื่อ Offset ถัดไป (รัน) ใน Source มีคอมเมนต์ที่ `UnifiedLog.deleteSegments` ว่า "เราต้องมี Segment อย่างน้อยหนึ่งอันเสมอ ถ้าจะลบทั้งหมดให้สร้างอันใหม่ก่อน" (Source)

</Step>

## Compaction: เก็บค่าล่าสุดของแต่ละ Key

Topic บางอย่างเราสนใจแค่ "สถานะล่าสุดของแต่ละ Key" เช่นข้อมูลโปรไฟล์ลูกค้า เราตั้ง `cleanup.policy=compact` แล้ว Kafka จะไม่ลบตามเวลา แต่มี Log Cleaner คอยไล่ลบ Record เก่าของ Key ที่มีค่าใหม่กว่า (หนังสือ: Kafka: The Definitive Guide หัวข้อ How Compaction Works หน้า 156) เราส่ง Record ของ `k1` ถึง `k4` วนสิบสองรอบ (48 Record) แล้วส่ง Tombstone ซึ่งเป็น Record ที่ Value เป็น `null` ของ `k3` ตามด้วย Record อื่นอีก 40 ตัวให้ Segment ปิด

กดสลับสามช่วงเวลาใน Lab ดูว่า Cleaner เก็บอะไรไว้

<CompactionLab client:visible />

หลัง Cleaner ทำงานเหลือค่าล่าสุดของ `k1`, `k2` และ `k4` ที่ Offset 44, 45 และ 47 โดย Offset ไม่ได้ถูกเรียงใหม่ จึงมีช่องว่างอยู่ระหว่างกัน ส่วน `k3` เหลือแค่ Tombstone ที่ Offset 48 ค่าเก่าทั้ง 12 ตัวของมันหายหมด (รัน) และอีกสักพักหลังพ้น `delete.retention.ms` Cleaner เก็บกวาด Tombstone ตัวนั้นด้วย `k3` จึงไม่เหลือร่องรอยเลย ในการรันของเรา ใช้เวลาอีกราว 13 วินาที (รัน) เพื่อให้เห็นภาพ "ก่อน" เราตั้ง `min.compaction.lag.ms` เป็นหนึ่งชั่วโมงไว้ก่อน ไม่งั้น Cleaner ทำงานเร็วจนไม่ทันเห็น แล้วปรับกลับเป็น 0

</Step>
