## Producer ส่งเป็นก้อน ไม่ได้ส่งทีละตัว

ตอนเรียก `produce()` เราคิดว่ากำลังส่งทีละ Record แต่จริง ๆ แล้ว Producer เก็บ Record ไว้ในหน่วยความจำก่อน แล้วรวมกันเป็น Batch ที่ไปที่ Partition เดียวกัน จึงค่อยส่งทั้งก้อนใน Request เดียว ข้อดีคือเครือข่ายกับดิสก์ของ Broker ทำงานกับก้อนใหญ่ได้ดีกว่าชิ้นเล็กจำนวนมาก

เราดูก้อนนั้นได้จากไฟล์ Log ของ Broker เอง คำสั่ง `kafka-dump-log.sh` พิมพ์หนึ่งบรรทัดต่อหนึ่ง Batch ดังนี้

```text
baseOffset: 0 lastOffset: 20 count: 21 baseSequence: -1 lastSequence: -1 producerId: -1 producerEpoch: -1
partitionLeaderEpoch: 0 isTransactional: false isControl: false position: 0 CreateTime: 1795188576548
size: 1969 magic: 2 compresscodec: none crc: 2213403328 isvalid: true
```

บรรทัดนี้บอกว่า Batch นี้ถือ Record 21 ตัว ตั้งแต่ Offset 0 ถึง 20 ใช้พื้นที่ 1,969 ไบต์ และยังไม่ได้บีบอัด (`compresscodec: none`) ส่วนช่อง `producerId` กับ `baseSequence` ที่เป็น -1 เป็นเรื่องของ Idempotence ซึ่งเราจะกลับมาดูในหัวข้อท้าย ๆ (รัน)

</Step>

## linger.ms: ยอมรอเพื่อให้ก้อนใหญ่ขึ้น

Producer ตัดสินใจเมื่อไรว่าถึงเวลาส่ง Batch แล้ว มีสองเงื่อนไข ถ้า Batch เต็มตามขนาด `batch.size` ก็ส่งเลย หรือถ้าเวลาที่ Record ตัวแรกรออยู่ถึง `linger.ms` ก็ส่งเลยเหมือนกัน Producer แบบ Java ตั้งค่าเริ่มต้นไว้ที่ `linger.ms=5` และ `batch.size=16384` ไบต์ (Source: `ProducerConfig.java` ของ 4.4.0 บรรทัดที่ 440 กับ 445) หนังสือเล่าว่า `linger.ms` คือเวลาที่ Producer รอ Record เพิ่มก่อนส่ง Batch ออกไป (หนังสือ: Kafka: The Definitive Guide หัวข้อ Message Delivery Time หน้า 56)

เราทดลองด้วยการส่ง Order 600 ใบ โดยให้ Order เข้ามาทีละใบทุก 2 มิลลิวินาที เหมือนบริการที่ส่ง Order ทุกครั้งที่ลูกค้ากดสั่ง แล้วนับ Batch ที่ไปอยู่ใน Log จริง

| ตั้งค่า | Batch ใน Log | Batch ที่ใหญ่ที่สุด | ขนาดไฟล์ |
|---|---|---|---|
| `linger.ms=0` | 594 | 7 Record | 90,592 ไบต์ |
| `linger.ms=50` | 29 | 22 Record | 56,127 ไบต์ |

ตอน `linger.ms=0` เกือบทุก Record กลายเป็น Batch ของตัวเอง ส่วนตอน 50 มิลลิวินาที Producer รอรวม Record ราว 20 ตัวต่อ Batch ทำให้ Request ลดลงเกือบยี่สิบเท่า ไฟล์ก็เล็กลงด้วยเพราะส่วนหัวของ Batch ถูกจ่ายน้อยครั้งลง (รัน) แต่ต้องแลกกับ Record แรกของแต่ละ Batch ที่ต้องรอนานขึ้น กดเปลี่ยนค่าใน Lab ดูได้เลย แล้วลองเปลี่ยนความถี่ที่ Record เข้ามา สังเกตว่าถ้า Record เข้ามาห่างกัน การรอไม่ได้ช่วยอะไร

## บีบอัดทั้ง Batch

Producer บีบอัดข้อมูลได้ด้วยตัวเลือก `compression.type` และบีบอัดเป็นรายก้อน Batch ที่ใหญ่ขึ้นจึงบีบได้ดีขึ้น Broker เก็บ Batch ที่บีบแล้วไว้ตามนั้นและส่งต่อให้ Consumer โดยไม่ต้องแกะ เราลองส่ง Order 3,000 ใบที่หน้าตาเหมือน JSON ของจริง (ลูกค้า สินค้า จำนวน ราคาแบบสุ่ม) ไปที่ Topic ละหนึ่งแบบ แล้ววัดขนาดไฟล์ Log

| Codec | ขนาด Log (ประมาณ) | เทียบกับไม่บีบ |
|---|---|---|
| `none` | 275 KB | 100% |
| `gzip` | 42 KB | 15% |
| `zstd` | 48 KB | 17% |
| `snappy` | 77 KB | 28% |
| `lz4` | 79 KB | 29% |

Codec ที่ถูกใช้ปรากฏอยู่ในบรรทัดของ Batch (`compresscodec: gzip`) ทุกแบบเล็กกว่าไม่บีบ และ `gzip` กับ `zstd` เหลือไม่ถึงครึ่ง (รัน) ตัวเลขนี้ขึ้นกับหน้าตาของข้อมูล Order ที่ใช้ชื่อฟิลด์ซ้ำ ๆ บีบได้ดีมาก ข้อมูลที่เข้ารหัสแล้วหรือเป็นไบนารีสุ่มจะบีบได้น้อย และแต่ละรอบที่รันตัวเลขขยับได้เล็กน้อยเพราะการแบ่ง Batch ไม่เท่ากันทุกครั้ง

</Step>

## Acks: Broker ตอบเมื่อไร

หลังจากส่ง Batch ไปแล้ว Producer จะรู้ว่าสำเร็จเมื่อ Broker ตอบกลับ ค่า `acks` เป็นตัวบอกว่าให้ Broker ตอบตอนไหน (หนังสือ: Kafka: The Definitive Guide หัวข้อ Message Delivery Time หน้า 55) ถ้า `acks=0` Producer ส่งแล้วไม่รอคำตอบ ถ้า `acks=1` Leader ตอบทันทีที่เขียนลง Log ของตัวเอง และถ้า `acks=all` Leader ตอบหลังจากทุก Replica ที่อยู่ใน ISR ได้ Record ไปแล้ว Producer แบบ Java ตั้งค่าเริ่มต้นเป็น `all` (Source: `ProducerConfig.java` บรรทัด 430)

ผลจากการส่ง Record เดียวด้วยสามค่า

```text
acks=0   -> offset None
acks=1   -> offset 1
acks=all -> offset 2
```

`acks=0` ไม่ได้ Offset กลับมาเลย เพราะ Producer ไม่รอ Broker ส่วนอีกสองแบบได้ตำแหน่งของ Record กลับมา (รัน) ความต่างระหว่าง `1` กับ `all` จะเห็นเมื่อ Leader ล้ม ลองกด Lab ด้านล่าง เลือก `acks` กับจังหวะที่ Leader ล้ม แล้วกดถัดไปทีละขั้น คำว่า ISR กับ Follower เดี๋ยวเราจะมาดูละเอียดใน[บทที่ 6](/kafka/replication/)

## Idempotence: ติดตราให้ทุก Batch

ถ้า Producer ส่ง Batch ไปแล้วไม่ได้คำตอบ (เครือข่ายช้า หรือ Broker ตอบไม่ทัน) มันก็ส่งซ้ำ ซึ่งอาจทำให้ Record ถูกเขียนสองรอบ ถ้าเปิด `enable.idempotence` Producer จะขอ `producerId` จาก Broker แล้วใส่เลขลำดับ (Sequence) ให้ทุก Record Broker จึงรู้ว่า Batch นี้เคยเห็นแล้วหรือยัง (หนังสือ: Kafka: The Definitive Guide หัวข้อ Idempotent Producer หน้า 182) เราเห็นตรานั้นได้จาก Log

```text
librdkafka ค่าเริ่มต้น: producerId=-1 baseSequence=-1
enable.idempotence:    producerId=0 producerEpoch=0 baseSequence=0 lastSequence=9
```

Record 10 ตัวที่ส่งแบบเปิด Idempotence มีเลขลำดับ 0 ถึง 9 ติดไปกับ Batch (รัน) ค่าเริ่มต้นต่างกันตามไลบรารี Producer แบบ Java เปิดไว้อยู่แล้ว (Source: `ProducerConfig.java` บรรทัด 574) แต่ Librdkafka ปิดไว้ในรุ่นที่เราใช้ ถ้าเขียนด้วย Python ต้องเปิดเอง เรื่องที่ว่า Broker ใช้ตรานี้กำจัด Record ซ้ำอย่างไร เรามีบทหนึ่งไว้ลงรายละเอียดคือ[บทที่ 8](/kafka/delivery/)

<Callout type="note" title="Record ใหญ่เกินไป">
Producer ปฏิเสธ Record ที่ใหญ่เกินขีดจำกัดตั้งแต่ก่อนส่ง เมื่อเราลองส่ง Record ขนาด 2 MB ได้ข้อผิดพลาด `MSG_SIZE_TOO_LARGE` ทันทีจาก `produce()` โดยไม่มีอะไรออกไปที่เครือข่าย (รัน) ส่วนขนาดสูงสุดที่ Broker รับเป็นอีกค่าหนึ่ง (`message.max.bytes`) ที่ต้องตั้งให้เข้ากัน
</Callout>
