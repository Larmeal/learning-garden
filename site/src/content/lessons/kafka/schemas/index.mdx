## Kafka ไม่รู้ว่าข้างในเป็นอะไร

ที่ผ่านมาเราส่ง Order เป็นข้อความ JSON แล้ว Kafka ก็เก็บให้เฉย ๆ เพราะสำหรับ Broker Key กับ Value ของ Record เป็นแค่ไบต์ที่ไม่มีความหมาย แบบฝึกตอนท้ายบทนี้ก็เห็นว่าเราส่งข้อมูลหน้าตาไบนารีเข้า Topic ได้และ Broker ไม่ได้ตรวจอะไร (รัน) ความหมายของไบต์ต้องมาจากข้อตกลงระหว่างคนส่งกับคนอ่านเอง ซึ่งถ้าคนส่งเปลี่ยนรูปแบบเมื่อไร คนอ่านที่ไม่รู้ก็พังเมื่อนั้น บทนี้จึงเป็นเรื่องของการตกลงรูปแบบ และการเปลี่ยนรูปแบบโดยไม่ทำให้ใครพัง ซึ่งเป็นเรื่องเดียวกับ Data Contract ในเส้นทางของ [Data Quality](/data-quality/agreements/contracts-in-practice/)

</Step>

## JSON ใหญ่ เพราะเขียนชื่อฟิลด์ซ้ำทุกใบ

เราเทียบ Order 1,000 ใบที่มี `order_id`, `item` และ `qty` ว่าเก็บเป็น JSON กับเก็บเป็น Avro ต่างกันเท่าไร

```text
JSON 44,500 ไบต์  Avro 14,500 ไบต์  อัตรา 3.1 เท่า
```

Avro เป็นรูปแบบที่หนังสือแนะนำสำหรับ Kafka ว่ากระชับ มี Schema แยกออกจากข้อมูล และรองรับการเปลี่ยน Schema ทั้งแบบ Backward และ Forward (หนังสือ: Kafka: The Definitive Guide หัวข้อ Serializing Using Apache Avro หน้า 64) ที่เล็กกว่าเพราะข้อความ Avro เก็บเฉพาะค่า ไม่ต้องเขียนชื่อฟิลด์หรือเครื่องหมายคำพูดซ้ำ ลองดูข้อความหนึ่งใบ `{'order_id': 'o-1', 'item': 'book', 'qty': 2}` ที่เข้ารหัสเป็น `066f2d3108626f6f6b04` สิบไบต์ ซึ่งมีแต่ความยาวของ `o-1`, ตัวอักษรของมัน, ความยาวของ `book`, ตัวอักษรของมัน และเลข 2 (รัน)

แต่ปัญหาตามมาทันที ไบต์สิบตัวนี้อ่านไม่ได้ถ้าไม่รู้ Schema ของคนเขียน เราจึงต้องบอกคนอ่านว่าข้อความนี้เขียนด้วย Schema ตัวไหน

</Step>

## เลข Schema Id ที่หัวของข้อความ

หนังสือเล่าว่าการเก็บ Schema ทั้งก้อนไว้ในทุก Record มักทำให้ Record ใหญ่ขึ้นเกินสองเท่า วิธีที่นิยมคือเก็บ Schema ไว้ที่ Registry ตัวกลาง แล้วใส่แค่รหัสอ้างอิงไว้ที่หัวของข้อความ (หนังสือ: Kafka: The Definitive Guide หัวข้อ Using Avro Records with Kafka หน้า 65) แบบที่ใช้กันทั่วไปมีไบต์ศูนย์หนึ่งตัว ตามด้วยรหัส Schema สี่ไบต์ แล้วจึงเป็นเนื้อ Avro เราประกอบข้อความสองเวอร์ชันด้วยมือแล้วดูไบต์

```text
version 1: 00 00000001 066f2d3108626f6f6b04
version 2: 00 00000002 066f2d3108626f6f6b04 06544842
```

ข้อความเวอร์ชันสองยาวกว่าเพราะมีฟิลด์ใหม่ `currency` (ค่า `THB` ต่อท้าย) และ Consumer ถอดข้อความแต่ละใบด้วย Schema ที่รหัสของมันชี้ ซึ่ง Topic เดียวเก็บข้อความสองเวอร์ชันปนกันได้ (รัน) หมายเหตุสำคัญ ใน Registry ที่เราทำเป็นแค่ Dictionary ในโปรเซส ไม่ได้รัน Schema Registry จริง ส่วนที่ Registry ตัวจริงเพิ่มเข้ามาคือการตรวจความเข้ากันได้ตอนลงทะเบียน Schema ใหม่ ซึ่งเราจำลองด้วยการลองอ่านจริงในหัวข้อถัดไป

</Step>

## เปลี่ยน Schema แล้วใครพัง

สมมติว่า Producer ใช้ Schema เวอร์ชัน 1 ไปแล้วสักพัก ตอนนี้เราอยากเปลี่ยน คำถามที่ต้องตอบมีสองข้อ ข้อแรก Reader ที่ใช้ Schema ใหม่ยังอ่านข้อความเก่าที่อยู่ใน Topic ได้ไหม ซึ่งเรียกว่า Backward Compatible ข้อที่สอง Reader ที่ยังใช้ Schema เก่า อ่านข้อความใหม่ที่ Producer เพิ่งส่งได้ไหม ซึ่งเรียกว่า Forward Compatible และถ้าได้ทั้งสองอย่างเรียกว่า Full (หนังสือ: Kafka Streams in Action หัวข้อ Schema Compatibility หน้า 71) เราเขียนข้อความด้วย Schema ฝั่งหนึ่งแล้วอ่านด้วยอีกฝั่งจริง ๆ ด้วย Fastavro ทั้งสองทิศสำหรับการเปลี่ยนแปดแบบ

| การเปลี่ยน | Reader ใหม่ อ่านข้อความเก่า | Reader เก่า อ่านข้อความใหม่ |
|---|---|---|
| เพิ่มฟิลด์ที่มี Default | ได้ | ได้ |
| เพิ่มฟิลด์ที่ไม่มี Default | ไม่ได้ | ได้ |
| ลบฟิลด์ที่ไม่มี Default | ได้ | ไม่ได้ |
| ลบฟิลด์ที่มี Default | ได้ | ได้ |
| เปลี่ยนชื่อฟิลด์ | ไม่ได้ | ไม่ได้ |
| เปลี่ยนชื่อ แล้วเก็บชื่อเก่าเป็น Alias | ได้ | ไม่ได้ |
| ขยาย `int` เป็น `long` | ได้ | ไม่ได้ |
| เปลี่ยน `int` เป็น `string` | ไม่ได้ | ไม่ได้ |

(รัน) เหตุผลของแต่ละแถวอยู่ใน Lab ด้านล่าง เลือกการเปลี่ยนแล้วดูฟิลด์ที่เปลี่ยนสีกับผลของสองทิศ ข้อที่ควรจำสั้น ๆ คือ ฟิลด์ใหม่ต้องมีค่า Default ทุกครั้ง และการลบฟิลด์ควรลบได้เฉพาะฟิลด์ที่เคยมี Default

<Callout type="note" title="Registry ตัวจริงทำอะไรเพิ่ม">
Schema Registry ตั้งโหมดความเข้ากันได้ต่อ Subject ได้ (Backward, Forward, Full หรือไม่ตรวจ) และปฏิเสธ Schema ใหม่ที่ผิดกฎก่อนที่ Producer จะส่งข้อความแรก (หนังสือ: Kafka Streams in Action หัวข้อ Schema Compatibility หน้า 71 ถึง 73) เราไม่ได้รัน Registry จึงไม่ยืนยันว่ากฎของมันตรงกับตารางข้างบนทุกแถว
</Callout>
