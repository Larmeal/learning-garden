## วันหนึ่งโค้ดที่เคยใช้ได้ก็พัง

ทีมมี 16 Commit ผ่านมาแล้ว ตอนที่ Commit ที่ 1 สคริปต์ทดสอบผ่าน แต่ตอนนี้ที่ Commit ที่ 16 มันไม่ผ่านแล้ว ไม่มีใครรู้ว่าใครทำให้พัง ถ้าไล่ดูทีละ Commit ก็เสียเวลา แต่ Git มีคำสั่ง `git bisect` ที่ใช้หลักเดียวกับการเดาเลขในเกม คือแบ่งครึ่งช่วงที่เหลือไปเรื่อย ๆ (หนังสือ: VCWG บทที่ 8 หน้า 177)

เราบอก Git ว่า Commit ปลายสุดคือ Bad และ Commit แรกคือ Good Git จะสลับไปอยู่ที่ Commit กลางช่วงแล้วถามว่าตัวนี้ Good หรือ Bad เมื่อเราตอบ Git ก็ตัดช่วงทิ้งไปครึ่งหนึ่ง (รัน: `exercises/10_finding_commits.py`)

```text
$ git bisect start HEAD <ชื่อ Commit ที่ 1>
Bisecting: 7 revisions left to test after this (roughly 3 steps)

$ git bisect good      # ตัวกลางผ่าน
$ git bisect bad       # ตัวที่เหลือครึ่งหลังพัง
$ git bisect good
$ git bisect bad
932adfbf68b44cbb0367161179de20fe1d5dd424 is the first 'bad' commit
```

ตอบสี่ข้อก็เจอ Commit ที่ 11 ซึ่งเป็นตัวแรกที่เปลี่ยนค่าในไฟล์ตั้งค่าจากบวกเป็นลบ แบบฝึกยืนยันว่า Git ชี้ถูกตัว และใช้คำตอบไม่เกินสี่ข้อ ตรงกับ log2 ของ 16 หลังเสร็จให้สั่ง `git bisect reset` เพื่อกลับไปอยู่ที่ Branch เดิม

</Step>

## ให้สคริปต์ตอบแทนเรา

การตอบ Good กับ Bad ด้วยมือน่าเบื่อถ้าเรามีสคริปต์ที่ตรวจได้อยู่แล้ว `git bisect run` รับคำสั่งหนึ่งตัว แล้วใช้รหัสที่คำสั่งนั้นส่งกลับตัดสินให้ ศูนย์คือ Good ส่วนตัวเลขตั้งแต่ 1 ถึง 124 คือ Bad (แบบฝึกใช้ศูนย์กับหนึ่งเท่านั้น รหัสพิเศษตัวอื่นของ Bisect ไม่ได้ลอง)

```text
$ git bisect start HEAD <ชื่อ Commit ที่ 1>
$ git bisect run python check.py
...
    commit 11

 config.txt | 2 +-
 notes.txt  | 2 +-
 2 files changed, 2 insertions(+), 2 deletions(-)
bisect found first 'bad' commit
```

Git ไล่ทดสอบเองจนเจอ และพิมพ์ Commit ที่เป็นตัวการออกมาให้ทั้งตัว ผลตรงกับที่ตอบด้วยมือ (รัน) ทั้งสองแบบต้องให้ Commit ปลายเป็น Bad และ Commit ต้นเป็น Good ที่แน่นอน และการทดสอบต้องให้ผลเหมือนเดิมทุกครั้ง ถ้าผลสุ่ม Bisect จะหลงทาง

<Callout type="tip" title="สังเกตข้อความ">

ข้อความตอนเจอคือ `is the first 'bad' commit` มีเครื่องหมายคำพูดคร่อมคำว่า `bad` ถ้าเขียนสคริปต์ที่ต้องอ่านผลของ Bisect ให้จับข้อความนี้ให้ตรง

</Callout>

</Step>

## `git blame` บอกว่าแต่ละบรรทัดถูกแก้ล่าสุดโดยใคร

เมื่อรู้แล้วว่าไฟล์ไหนมีปัญหา คำถามต่อไปคือบรรทัดนี้ใครเขียน และเพราะอะไร (หนังสือ: VCWG บทที่ 8 หน้า 183)

```text
$ git blame poem.txt
^eb9617f (Ada 2026-01-01 1) roses are red
e451ec86 (Bea 2026-01-01 2) violets are purple
^eb9617f (Ada 2026-01-01 3) sugar is sweet
```

ทุกบรรทัดมีชื่อ Commit ที่แก้ล่าสุด ผู้เขียน วันที่ และเลขบรรทัด เครื่องหมาย `^` ข้างหน้าบอกว่าบรรทัดนั้นมาจาก Commit แรกสุดของประวัติ (แบบฝึกตรวจทั้งสองข้อ) ถ้าอยากดูแค่บางช่วง ใช้ `-L 2,2` และถ้าอยากดูไฟล์เมื่อก่อนจะถึง Commit ล่าสุด ให้ใส่ Commit ก่อนชื่อไฟล์ เช่น `git blame HEAD~1 -- poem.txt`

ปัญหาที่เจอบ่อยคือ Commit ที่แค่จัดย่อหน้าใหม่ เพราะมันกลายเป็นคนแก้ล่าสุดของทุกบรรทัด บังเอิญบดบังคนที่เขียนจริง Git มีสองทางแก้ ใส่ `-w` เพื่อให้ Blame ไม่สนใจการเปลี่ยนช่องว่าง หรือเขียนชื่อ Commit แบบเต็ม 40 ตัวอักษรลงในไฟล์ แล้วสั่ง `git blame --ignore-revs-file <ไฟล์นั้น>` ให้ข้าม Commit พวกนั้นไปเลย (แบบฝึกตรวจทั้งสองทาง และพบว่าไฟล์รายการนั้นต้องใช้ชื่อเต็ม ชื่อย่อทำให้ Git ฟ้อง invalid object name)

</Step>

## Pickaxe ค้นประวัติด้วยข้อความ

คำถามอีกแบบคือ "สตริงนี้โผล่หรือหายไปในประวัติตอนไหน" (หนังสือ: VCWG บทที่ 8 หน้า 184) `git log` มีตัวเลือกสองแบบที่ฟังดูคล้ายกันแต่ตอบต่างกัน แบบฝึกสร้าง Commit ห้าตัวที่เกี่ยวกับคำว่า `TODO` และเลข 12

```text
$ git log --format=%s -S TODO
S5 another todo elsewhere
S3 add a todo

$ git log --format=%s -G 'return 1[0-9]'
S4 comment the number
S2 raise the price
S1 add price

$ git log --format=%s -S 'return 12'
S2 raise the price
```

`-S` (Pickaxe) ถามว่า **จำนวนครั้งที่สตริงนี้ปรากฏ** เปลี่ยนไปหรือเปล่าใน Commit นั้น จึงเจอเฉพาะตอนที่ `TODO` ถูกเพิ่มเข้ามา (`S3` และ `S5`) ส่วน `-G` ใช้รูปแบบ Regular Expression และถามว่า **บรรทัดที่ถูกแก้** ตรงกับรูปแบบหรือไม่ เลย Commit `S4` ที่แค่เพิ่มคอมเมนต์ท้ายบรรทัดที่มี `return` ก็ติดมาด้วย ทั้งที่จำนวน `return 12` ไม่ได้เปลี่ยน ซึ่งเป็นเหตุผลที่ `-S 'return 12'` ไม่เจอ `S4` ลองเลือกตัวเลือกให้ตรงกับคำถาม

ตัวช่วยอื่นที่ลองแล้วได้ผลตามนี้ `--diff-filter=A` เหลือเฉพาะ Commit ที่เพิ่มไฟล์ใหม่ และ `git log -L 3,3:code.txt` ไล่ประวัติของบรรทัดที่ 3 ของไฟล์ ถ้าไฟล์ถูกเปลี่ยนชื่อ `git log -- <ชื่อใหม่>` จะหยุดตรงที่เปลี่ยนชื่อ ต้องเติม `--follow` ถึงจะตามไปถึงชื่อเก่า (รัน)

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| Bisect ด้วยมือเจอ Commit แรกที่พังภายในสี่คำตอบจาก 16 Commit และข้อความ `is the first 'bad' commit` | รัน: `exercises/10_finding_commits.py` |
| `git bisect run` ใช้รหัสส่งกลับของสคริปต์และเจอ Commit เดียวกัน | รัน: `exercises/10_finding_commits.py` |
| `git blame` แสดงชื่อ Commit ผู้เขียนและวันที่, `^` คือ Commit แรก, `-L`, `blame HEAD~1 -- ไฟล์` | รัน: `exercises/10_finding_commits.py` |
| `-w` และ `--ignore-revs-file` (ต้องใช้ชื่อเต็ม) ข้าม Commit ที่แค่จัดย่อหน้า | รัน: `exercises/10_finding_commits.py` |
| `-S` นับจำนวนครั้งที่สตริงปรากฏ, `-G` จับบรรทัดที่ถูกแก้, `--diff-filter=A`, `log -L` | รัน: `exercises/10_finding_commits.py` |
| `git log -- ชื่อใหม่` หยุดที่การเปลี่ยนชื่อ, `--follow` ตามต่อ | รัน: `exercises/10_finding_commits.py` |
| `git bisect`, `git blame`, Pickaxe | หนังสือ: VCWG บทที่ 8 หน้า 177, 183 และ 184 |
| การเปรียบเทียบ Bisect กับการเดาเลขเพื่อให้เห็นภาพ | ผู้เขียน |
