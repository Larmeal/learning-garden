## เปิดไฟล์ Index ดูไบต์

Index ที่เราใช้ในบทแรก ๆ คือไฟล์ `.git/index` ลองสร้างสามไฟล์ แล้ว `git add` แล้วอ่านไบต์มันด้วย Python (รัน: `exercises/13_index_diff_merge.py`)

```python
import struct
raw = open(".git/index", "rb").read()
sig, version, count = struct.unpack(">4sII", raw[:12])
# (b'DIRC', 2, 3)
```

12 ไบต์แรกคือตัวอักษร `DIRC` (ย่อจาก Directory Cache) เลขเวอร์ชัน 2 และจำนวนรายการ 3 ซึ่งตรงกับค่าคงที่ `CACHE_SIGNATURE` ที่ซอร์สใช้ตอนอ่านและเขียน Index (Source: `read-cache.c`) ถัดมาคือรายการของแต่ละไฟล์ เรียงตามชื่อเสมอ (`a.txt`, `b.txt`, `dir/c.txt`) แต่ละรายการมีข้อมูล Stat ของไฟล์ 10 ช่อง ID ของ Blob 20 ไบต์ ธง 2 ไบต์ แล้วถึงชื่อไฟล์ ในแบบฝึกเรา Parse รายการเหล่านี้เองและเอา ID ไปเทียบกับ `git hash-object` ของแต่ละไฟล์ ตรงกันหมด และขนาดไฟล์กับสิทธิ์ที่อ่านมาก็ตรงกับไฟล์จริง ท้ายไฟล์มี SHA-1 ของทุกอย่างก่อนหน้า 20 ไบต์ เอาไว้จับ Index ที่เสียหาย (หนังสือ: VCWG บทที่ 2 หน้า 28 เรื่อง Index)

ก่อนมี Commit แรก ในไฟล์ไม่มีส่วนขยายชื่อ `TREE` แต่หลัง `git write-tree` (หรือ Commit) มันโผล่ขึ้นมา ส่วนขยายนี้จำ ID ของ Tree ของทุกโฟลเดอร์เอาไว้ เพื่อให้การ Commit ครั้งต่อไปสร้าง Tree ใหม่เฉพาะโฟลเดอร์ที่เปลี่ยน (รัน)

</Step>

## `git status` ไม่ได้เปิดทุกไฟล์

ถ้าโปรเจกต์มีไฟล์เป็นหมื่น `git status` ไม่ได้อ่านเนื้อหาทุกไฟล์ทุกครั้ง มันดูข้อมูล Stat ที่ Index จำไว้ก่อน

```text
$ git ls-files --debug a.txt
a.txt
  ctime: <วินาที>:<นาโนวินาที>
  mtime: <วินาที>:<นาโนวินาที>
  dev: 0	ino: 0
  uid: 0	gid: 0
  size: 6	flags: 0
```

ใน Index เก็บเวลาที่ไฟล์ถูกสร้างและแก้ ขนาด และข้อมูลอื่นของไฟล์ ถ้า Stat ของไฟล์ในโฟลเดอร์ตรงกับที่จำไว้ ก็ถือว่าไม่เปลี่ยนโดยไม่ต้องเปิด ค่า `dev`, `ino`, `uid` และ `gid` เป็น 0 ในแบบฝึกเพราะรันบน Windows ซึ่ง Git ใส่ศูนย์ให้ ในระบบอย่าง Linux จะเป็นเลขจริง

มีอะไรเกิดขึ้นถ้าเราแก้เวลาของไฟล์โดยไม่แก้เนื้อหา (สั่ง `touch`) แบบฝึกตรวจทีละขั้น **ขั้นแรก** รายการใน Index ยังไม่เปลี่ยนทันทีหลัง `touch` **ขั้นต่อมา** `git status` เห็นว่า Stat ต่างจากที่จำไว้ จึงเปิดไฟล์ไปเทียบ ID และพบว่าเหมือนเดิม เลยแสดงว่าสะอาด **ขั้นสุดท้าย** มันเขียนข้อมูล Stat ใหม่กลับลง Index ด้วย ครั้งต่อไปจะได้ไม่ต้องเปิดอีก ทั้งสามขั้นตรวจแล้วจากผลรัน

Index ยังมีเวอร์ชัน 4 ที่บีบอัดชื่อไฟล์ ซึ่งเปลี่ยนไปได้ด้วย `git update-index --index-version 4` (รัน)

</Step>

## Diff ที่ถูกต้องไม่ได้มีแบบเดียว

`git diff` เทียบสองไฟล์ด้วยอัลกอริทึม ซึ่งมีสี่แบบให้เลือก (`myers` ค่าเริ่มต้น, `minimal`, `patience` และ `histogram`) ทุกแบบให้ผลที่ถูกต้องในความหมายว่า เอาไปใช้กับไฟล์เก่าแล้วได้ไฟล์ใหม่ แต่ไม่จำเป็นต้องเหมือนกัน (หนังสือ: VCWG บทที่ 7 หน้า 173 เรื่อง How Git Derives diffs)

ตัวอย่างโค้ดสั้น ๆ ที่เราลองตอนทำบทนี้ (ฟังก์ชันที่ถูกสลับตำแหน่ง ฟังก์ชันที่ถูกแทรกกลาง) ให้ผลเหมือนกันทุกอัลกอริทึม เพราะ Git ปรับผลให้อ่านง่ายอยู่แล้ว เราจึงสุ่มค้นไฟล์เล็ก 9 บรรทัดที่มีบรรทัดซ้ำมาก ๆ อย่าง `{` กับบรรทัดว่าง จนเจอคู่หนึ่งที่สี่อัลกอริทึมให้ผลไม่เหมือนกัน นี่เป็นตัวอย่างประดิษฐ์ แต่ข้อมูลจริงที่มีบรรทัดซ้ำมากก็อาจเจอแบบเดียวกัน

```text
$ git diff --diff-algorithm=patience
@@ -1,8 +1,8 @@
-{
-{
-
 a();
 {
+{
+{
+
 {
 
 c();
```

```text
$ git diff --diff-algorithm=myers
@@ -1,8 +1,8 @@
+a();
 {
 {
-
-a();
 {
+
 {
 
 c();
```

ผลที่ได้ Patience นับว่าแก้ 3 บรรทัดแต่ละฝั่ง ส่วน Myers, Minimal และ Histogram นับ 2 บรรทัด และผลรวมออกมาเป็นสามหน้าตาที่ต่างกัน แต่ละแบบเอาไปใช้ด้วย `git apply` กับไฟล์เก่าแล้วได้ไฟล์ใหม่เป๊ะ (รัน) ไม่มีแบบไหนผิด

ข้อสังเกตอีกอย่าง ใน Diff ไม่มีคำว่า "ย้าย" ผลต่างมีแค่บรรทัดที่เพิ่มกับบรรทัดที่ลบ ไม่ว่าอัลกอริทึมไหน (รัน) ตัวเลือกอย่าง `--color-moved` เป็นแค่การแสดงผล

ลองเล่นภาพข้างล่างกับไฟล์คู่เดิมที่เราใช้ในหัวข้อนี้ เลือกอัลกอริทึมทีละตัว แล้วดูว่าบรรทัดไหนในไฟล์เก่าถูกนับว่าลบ บรรทัดไหนในไฟล์ใหม่ถูกนับว่าเพิ่ม และจำนวนบวกลบเปลี่ยนไปอย่างไร

## Merge หาไฟล์ที่ถูกเปลี่ยนชื่อจากเนื้อหา

Git ไม่ได้จดว่าไฟล์ถูกเปลี่ยนชื่อ ตอน Merge มันเทียบเนื้อหาของไฟล์ที่หายไปกับไฟล์ที่เกิดใหม่ (หนังสือ: VCWG บทที่ 5 หน้า 117 เรื่อง A Note on Tracking Renames) ถ้าเหมือนกันถึงเกณฑ์ ก็ถือว่าเป็นไฟล์เดียวกัน

สมมติฝั่งหนึ่งเปลี่ยนชื่อ `old.txt` เป็น `new.txt` ส่วนอีกฝั่งแก้บรรทัดหนึ่งใน `old.txt` แล้ว Merge

```text
$ git merge mover
Merge made by the 'ort' strategy.
 old.txt => new.txt | 0
 1 file changed, 0 insertions(+), 0 deletions(-)
 rename old.txt => new.txt (100%)
```

ผลคือไม่มี Conflict การแก้ตามไฟล์ไปอยู่ที่ชื่อใหม่ (รัน) ตัวเลข 100% คือความเหมือนของไฟล์ที่เปลี่ยนชื่อ

ถ้าฝั่งที่เปลี่ยนชื่อเขียนเนื้อหาใหม่ทั้งไฟล์ ความเหมือนก็ต่ำกว่าเกณฑ์ ค่าเกณฑ์นี้อยู่ในซอร์สคือ `DEFAULT_RENAME_SCORE 30000` ที่คอมเมนต์บอกว่าคือ 50% (Source: `diffcore.h`) ผลที่เราได้คือ Git มองเป็นการลบหนึ่งไฟล์และเพิ่มอีกหนึ่งไฟล์ แล้ว Merge ชน

```text
$ git merge mover
CONFLICT (modify/delete): old.txt deleted in mover and modified in HEAD.  Version HEAD of old.txt left in tree.
Automatic merge failed; fix conflicts and then commit the result.
```

(รัน)

</Step>

## คำนวณ Merge โดยไม่แตะอะไรเลย

`git merge-tree --write-tree` ทำ Merge ทั้งหมดข้างใน แล้วบอกผล โดยไม่แตะ Working Tree Index หรือ Branch เลย เหมาะกับเครื่องมือที่อยากรู้ล่วงหน้าว่า Merge นี้จะชนไหม

```text
$ git merge-tree --write-tree main egg
<ID ของ Tree ที่ Merge แล้ว>
```

ถ้าไม่ชน มันพิมพ์ ID ของ Tree ที่ได้ ซึ่งมีงานของทั้งสองฝั่งอยู่ครบ และแบบฝึกตรวจว่าโฟลเดอร์กับ Branch ไม่เปลี่ยน (รัน) ถ้าชน มันออกด้วยรหัส 1 แล้วพิมพ์ ID ของ Tree กับสามเวอร์ชัน (Stage 1, 2, 3) ของไฟล์ที่ชน ตามด้วยข้อความ `CONFLICT (content)` ซึ่งเป็นข้อมูลชุดเดียวกับที่เราเห็นใน Index ตอน Merge ชนในบท Merge

ตัวที่ทำงานข้างใน คือกลไก `ort` ในไฟล์ `merge-ort.c` (Source) เป็นตัวเดียวกับที่ `git merge` เรียกใช้ในข้อความ `Merge made by the 'ort' strategy.`

</Step>
