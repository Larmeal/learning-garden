## Pull Request คือคำขอให้คนอื่นรับงานของเราเข้าไป

เวลาทำงานเป็นทีม เรามักไม่ Push เข้า `main` ตรง ๆ เราแตก Branch ของตัวเอง ทำงาน Push ขึ้นไป แล้วขอให้ผู้ดูแลตรวจก่อนรับเข้า ขั้นตอนขอและตรวจนี้ถ้าทำบนเว็บ Hosting เรียกว่า **Pull Request** (หรือ Merge Request ในบางเว็บ) หนังสือ Learning Git เล่าว่ามันมีไว้ให้คนอื่นได้ดูและให้ความเห็นก่อนที่งานจะเข้าไปอยู่ใน Branch หลัก (หนังสือ: LG บทที่ 12 หน้า 233 และ 235)

ข้อสำคัญคือ Pull Request ไม่ใช่ฟีเจอร์ของ Git ตัว Git เองไม่รู้จักคำนี้ ส่วนที่เป็น Git ล้วน ๆ มีแค่สามอย่าง คือ Branch ที่ถูก Push ขึ้น Remote วิธีดูว่า Branch นั้นเพิ่มอะไรมา และวิธีรวมมัน ส่วนปุ่ม ช่องแสดงความเห็น การตรวจอัตโนมัติ และการห้าม Push เข้า `main` ตรง ๆ เป็นของเว็บ ซึ่งบทเรียนนี้ไม่ได้รัน (ดูหมายเหตุท้ายบท)

เรามาลองดูส่วนที่เป็น Git กัน (รัน: `exercises/07_team_workflow.py`) ผู้ร่วมงานแตก `topic/search` ทำสอง Commit แล้ว Push ผู้ดูแลที่ถือ `main` จึง `git fetch` มาดู

</Step>

## หน้า Review เห็นอะไร แล้ว Git บอกเราได้เองอย่างไร

ระหว่างนี้ `main` ก้าวไปข้างหน้าอีกหนึ่ง Commit (ผู้ดูแลแก้ `app.txt`) ลองเทียบ Branch ของผู้ร่วมงานกับ `main` สองแบบ

```text
$ git diff --stat main origin/topic/search
 app.txt    | 1 -
 search.txt | 2 ++
 2 files changed, 2 insertions(+), 1 deletion(-)

$ git diff --stat main...origin/topic/search
 search.txt | 2 ++
 1 file changed, 2 insertions(+)
```

แบบแรกเทียบปลายทั้งสองข้างตรง ๆ จึงเห็นการแก้ `app.txt` ของ `main` เป็นของที่ "หายไป" จาก Topic ทั้งที่ผู้ร่วมงานไม่ได้ทำ แบบที่สองใช้จุดสามจุด ซึ่งเทียบจากจุดที่แตกออกจากกัน จึงเห็นเฉพาะงานของ Topic และนั่นคือสิ่งที่หน้า Review ควรแสดง (หนังสือ: VCWG บทที่ 7 หน้า 168 เรื่อง Diff กับช่วงของ Commit)

Git มีคำสั่งที่เขียนคำขอเป็นข้อความให้ด้วย คือ `git request-pull` ผู้ร่วมงานเป็นคนรัน

```text
$ git request-pull origin/main ../garden.git topic/search
The following changes since commit 5b4eab77dfe8b1653f2e7952389dc414cba0d4d7:

  M1 first version (2026-01-01 10:00:01 +0000)

are available in the Git repository at:

  ../garden.git topic/search

for you to fetch changes up to 9b17c04b5c9dc3ed8a5bab7f32c5f063128c75c2:

  C2 finish search (2026-01-01 10:00:03 +0000)

----------------------------------------------------------------
Ada (2):
      C1 start search
      C2 finish search

 search.txt | 2 ++
 1 file changed, 2 insertions(+)
 create mode 100644 search.txt
```

ข้อความนี้บอกครบว่าฐานคือ Commit ไหน ที่อยู่ของ Branch คืออะไร มี Commit อะไรบ้างและแก้ไฟล์ไหน เป็นข้อมูลชุดเดียวกับที่หน้า Pull Request บนเว็บแสดง (แบบฝึกตรวจว่าข้อความมีทั้งฐาน Commit และ Diffstat)

</Step>

## รวมงานได้สามแบบ ประวัติออกมาต่างกัน

เมื่อผู้ดูแลพอใจ เว็บส่วนใหญ่ให้เลือกวิธีรวม เราจำลองแต่ละวิธีด้วยคำสั่งของ Git (รัน) เริ่มจากสถานการณ์เดียวกัน และดูว่าประวัติของ `main` หน้าตาเป็นอย่างไร

ลองกดเล่นภาพข้างล่างก่อนนะ ภาพนี้ให้ทั้งสามวิธีเริ่มจากประวัติเดียวกัน คือ `main` มี M1 กับ M2 ส่วน `topic/search` มี C1 กับ C2 แล้วดูว่า Commit ตัวไหนเกิดใหม่ ตัวไหนถูกคัดลอก และตัวไหนถูกทิ้งไว้ พอเห็นภาพแล้วค่อยอ่านผลของแต่ละแบบจากคำสั่งจริงข้างล่าง

<IntegrateLab client:visible />

**แบบที่หนึ่ง Merge Commit** สั่ง `git merge --no-ff` ได้ Commit ที่มีสอง Parent

```text
*   5563f88 Merge remote-tracking branch 'origin/topic/search'
|\
| * 9b17c04 C2 finish search
| * 75c37a7 C1 start search
* | 4631cb3 M2 main moves on meanwhile
|/
* 5b4eab7 M1 first version
```

Commit ของผู้ร่วมงานยังอยู่ครบด้วย ID เดิม และ `git log --first-parent` อ่านเป็นรายการของงานที่รวมเข้า `main` ทีละก้อนได้ ซึ่งสะดวกเวลาอยากเห็นว่า Pull Request ไหนเข้าเมื่อไร

**แบบที่สอง Squash** สั่ง `git merge --squash` แล้ว `git commit` ได้ Commit เดียว

```text
* a3c3bc3 Add search (#1)
* 4631cb3 M2 main moves on meanwhile
* 5b4eab7 M1 first version
```

Commit ของผู้ร่วมงานไม่ได้เข้ามาอยู่ในประวัติของ `main` ไฟล์ออกมาเหมือนกับแบบที่หนึ่งเป๊ะ แต่ประวัติสั้นกว่า ข้อที่ต้องระวังคือ Git จะไม่รู้ว่า Topic ถูกรวมแล้ว เพราะ Commit ของ Topic ไม่ใช่บรรพบุรุษของ `main` ผล `git branch -r --merged main` จึงไม่นับ `origin/topic/search` เราต้องลบ Branch นั้นเอง

**แบบที่สาม Rebase แล้ว Fast-forward** ผู้ร่วมงาน Rebase Topic ไปบนปลาย `main` แล้ว Push ทับด้วย `--force-with-lease` ผู้ดูแลจึง Merge แบบ `--ff-only`

```text
* c8ce798 C2 finish search
* 9101455 C1 start search
* 4631cb3 M2 main moves on meanwhile
* 5b4eab7 M1 first version
```

ประวัติเป็นเส้นตรง Commit ของ Topic ได้ ID ใหม่ตามที่เรียนในบท [Rebase](/git/rebase/) `--ff-only` ทำงานได้เพราะ Topic ต่อจากปลาย `main` พอดีแล้ว

ไม่มีแบบไหนถูกที่สุด ทีมเลือกตามสิ่งที่อยากเห็นในประวัติ ส่วนตัวผู้เขียนมองว่าแบบแรกเหมาะกับทีมที่อยากย้อนดูทีละ Pull Request ส่วนแบบสองกับสามเหมาะกับทีมที่อยากให้ประวัติสั้นและอ่านง่าย (ผู้เขียน)

</Step>

## เมื่อเราไม่มีสิทธิ์เขียนลง Repository หลัก

ในโปรเจกต์โอเพนซอร์ส เรามักไม่มีสิทธิ์ Push เข้า Repository หลักโดยตรง วิธีที่ใช้กันคือ **Fork** ทำสำเนาของ Repository หลักบนเว็บเป็นของเราเอง เรา Clone สำเนานั้นลงมา แล้วเพิ่ม Remote ตัวที่สองชื่อ `upstream` ที่ชี้ไป Repository หลัก

```text
$ git remote add upstream ../upstream.git
$ git remote
fork
upstream

$ git fetch upstream
$ git log --format=%s main..upstream/main
U2 upstream moves
$ git merge --ff-only upstream/main
```

แบบฝึกจำลองด้วยสอง Bare Repository ในโฟลเดอร์ (เรา Clone จากต้นทางแล้วเปลี่ยนชื่อ `origin` เป็น `fork`) ได้ผลตามนี้ทุกบรรทัด `fork` คือที่ที่เราเขียนได้ ส่วน `upstream` คือแหล่งที่เราดึงงานใหม่ของคนอื่นมาตามให้ทัน เราส่ง Pull Request จาก `fork` ไปยัง `upstream` ส่วนการสร้าง Fork ที่ทำบนเว็บ ไม่ได้รัน

</Step>
