## Merge แบบแรก แค่ขยับ Branch ไปข้างหน้า

สมมติ `main` ยังอยู่ที่เดิมตั้งแต่ตอนแตก Branch `dessert` ออกไป ส่วน `dessert` มี Commit เพิ่มมาหนึ่งตัว ถ้าเราอยู่บน `main` แล้วสั่ง `git merge dessert` (รัน: `exercises/04_merge.py`)

```text
$ git merge dessert
Updating f28b636..f5c962f
Fast-forward
 dessert.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 dessert.txt
```

ข้อความ `Fast-forward` บอกว่า Git ไม่ได้สร้าง Commit ใหม่เลย `main` เป็นบรรพบุรุษของ `dessert` อยู่แล้ว Git จึงย้ายไฟล์ `main` ให้ชี้ไปที่ Commit เดียวกับ `dessert` เท่านั้น แบบฝึกตรวจว่าหลัง Merge ชื่อ Commit ของสองสายเท่ากันทุกตัวอักษร และ Commit ปลายสายมี Parent เพียงตัวเดียว (หนังสือ: LG บทที่ 5 หน้า 70)

</Step>

## Merge แบบที่สอง สร้าง Commit ใหม่ที่มีสอง Parent

ถ้าสองสายต่างก็เดินไปข้างหน้าแล้ว `main` ไม่ใช่บรรพบุรุษของอีกสายอีกต่อไป Git จะต้องหาจุดที่ทั้งสองแตกออกจากกัน แล้วรวมงานของทั้งสองฝั่งเข้าด้วยกัน

```text
$ git merge-base main drinks
<ชื่อของ Commit ที่ drinks แตกออกมา>

$ git merge --no-edit drinks
Merge made by the 'ort' strategy.
 drinks.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 drinks.txt
```

`git merge-base` ตอบว่าบรรพบุรุษร่วมที่ใกล้ที่สุดของสองสายคือ Commit ไหน (แบบฝึกยืนยันว่าตรงกับจุดที่แตก) จากนั้น Git เทียบสามจุด คือบรรพบุรุษร่วม ปลายของเรา และปลายของอีกฝั่ง แล้วรวมการเปลี่ยนแปลงเข้าด้วยกัน เราเรียกวิธีนี้ว่า Three-way Merge (หนังสือ: LG บทที่ 9 หน้า 141 และ VCWG บทที่ 6 หน้า 123)

ผลคือ Commit ใหม่หนึ่งตัวที่ Parent ตัวแรกคือ `main` เดิม และ Parent ตัวที่สองคือปลายของ `drinks` ไฟล์ทั้งสองฝั่งอยู่ครบใน Working Tree (รัน) ชื่อ `ort` ที่เห็นในข้อความคือชื่อกลไกที่ Git 2.56.1 ใช้ Merge ซึ่งอยู่ในไฟล์ `merge-ort.c` ของซอร์ส (Source: `merge-ort.c`) เดี๋ยวเราจะได้เปิดดูข้างในกันอีกครั้งในบทท้าย ๆ

ถ้าสั่ง Merge Branch ที่ถูกรวมไปแล้ว Git จะตอบ `Already up to date` โดยไม่ทำอะไร และถ้าเราอยากให้ Fast-forward ได้ก็ยังสร้าง Merge Commit ไว้เป็นหลักฐานว่ามี Branch นี้เคยแยกออกไป ให้ใส่ `--no-ff` แบบฝึกยืนยันว่ากรณีนี้ได้ Commit ที่มีสอง Parent จริง

ลองกดเล่นภาพนี้เพื่อเทียบสองแบบ ซ้ายคือ Fast-forward ที่ขยับแค่ป้าย `main` ส่วนขวาคือ Merge ที่ทั้งสองฝั่งเดินไปแล้ว ดูว่า Commit ใหม่เกิดขึ้นตอนไหน และมีลูกศรชี้ไปหา Parent กี่เส้น

## Conflict เกิดเมื่อสองฝั่งแก้ที่เดียวกัน

ลองให้ฝั่งหนึ่งเปลี่ยนบรรทัดที่สองของ `menu.txt` เป็น `salad with tuna` และอีกฝั่งเปลี่ยนบรรทัดเดียวกันเป็น `salad with egg` แล้ว Merge

ก่อนไปดูผลจริง ลองเล่นภาพนี้ดูก่อนว่า Git ตัดสินใจอย่างไรทีละบรรทัด เลือกได้ว่าสองฝั่งแก้คนละบรรทัดหรือบรรทัดเดียวกัน ถ้าเป็นบรรทัดเดียวกัน ภาพจะให้เราเลือกทางออกของ Conflict ด้วย

<ConflictLab client:visible />


```text
$ git merge egg
Auto-merging menu.txt
CONFLICT (content): Merge conflict in menu.txt
Automatic merge failed; fix conflicts and then commit the result.
```

คราวนี้ Git ตัดสินเองไม่ได้ว่าจะเอาฝั่งไหน มันจึงหยุดกลางทางและเขียนทั้งสองฝั่งลงไฟล์ให้เราเลือก (หนังสือ: LG บทที่ 10 หน้า 175 และ VCWG บทที่ 6 หน้า 127)

```text
soup
<<<<<<< HEAD
salad with tuna
=======
salad with egg
>>>>>>> egg
bread
```

ส่วนระหว่าง `<<<<<<< HEAD` กับ `=======` คือของฝั่งเรา ส่วนระหว่าง `=======` กับ `>>>>>>> egg` คือของฝั่งที่เอาเข้ามา ส่วนที่เหลือไม่มีปัญหาจึงอยู่ในไฟล์ตามปกติ ไฟล์ `.git/MERGE_HEAD` ถูกสร้างขึ้นมาจดว่ากำลัง Merge กับ Commit ไหนอยู่ และ `git status --short` ขึ้น `UU menu.txt` ซึ่งแปลว่าทั้งสองฝั่งแก้ (Unmerged)

</Step>

## Git เก็บสามเวอร์ชันไว้ใน Index

ข้างในเรื่อง Conflict ที่น่าสนใจกว่าไฟล์ที่มี Marker คือสิ่งที่อยู่ใน Index (หนังสือ: VCWG บทที่ 6 หน้า 138)

```text
$ git ls-files --unmerged
100644 686df3dcd3f6d9762f4282862589f918c3f44504 1	menu.txt
100644 0ae7d0c492af62878286e61693f0ab14fc06fa87 2	menu.txt
100644 58f1784453de613c2e43d314d9bde53b6c740273 3	menu.txt
```

ตัวเลขที่ท้ายสามบรรทัดคือ **Stage** ปกติทุกไฟล์ใน Index เป็น Stage 0 แต่ไฟล์ที่ Conflict จะมีสามรายการ Stage 1 คือเวอร์ชันของบรรพบุรุษร่วม Stage 2 คือเวอร์ชันของเรา และ Stage 3 คือเวอร์ชันของอีกฝั่ง เราเปิดดูแต่ละอันได้ด้วย `git show :1:menu.txt`, `:2:` และ `:3:` (รัน) Git จึงไม่ได้ทิ้งอะไรหาย ของทั้งสามอยู่ครบเสมอ

ถ้าอยากเห็นเวอร์ชันบรรพบุรุษร่วมในไฟล์ด้วย ให้ขอแบบ `diff3`

```text
$ git checkout --conflict=diff3 menu.txt
$ cat menu.txt
soup
<<<<<<< ours
salad with tuna
||||||| base
salad
=======
salad with egg
>>>>>>> theirs
bread
```

สังเกตว่าชื่อบน Marker เปลี่ยนจาก `HEAD` กับ `egg` ไปเป็น `ours` กับ `theirs` เพราะ Git ใส่ชื่อเริ่มต้นต่างกันตามรูปแบบที่เราขอ ตอนไหนที่เห็น `base` ได้ ก็จะรู้ว่าแต่ละฝั่งเปลี่ยนจากอะไรไป ซึ่งช่วยตัดสินใจได้ง่ายขึ้นมาก

</Step>

## ออกจาก Conflict ได้สองทาง

**ทางแรก** ยกเลิกทั้งหมด `git merge --abort` ทำให้ `main` กลับไปอยู่ที่เดิมก่อน Merge ไฟล์ `MERGE_HEAD` ถูกลบ และ Working Tree สะอาด (รัน และหนังสือ: VCWG บทที่ 6 หน้า 141)

**ทางที่สอง** แก้ไฟล์ให้เป็นอย่างที่ต้องการ ลบ Marker ทิ้ง แล้ว `git add` ซึ่งบอก Git ว่าไฟล์นี้จัดการเสร็จแล้ว รายการสามเวอร์ชันใน Index จะหายไป จากนั้น `git commit` เพื่อปิด Merge

```text
$ git add menu.txt
$ git commit --no-edit
$ git log --format=%s -n 1
Merge branch 'egg'
```

Commit ที่ได้มีสอง Parent เหมือน Merge ปกติ โดยตัวที่สองคือปลายของ `egg` (รัน)

<Callout type="tip" title="ไม่ต้องกลัว Conflict">

Conflict ไม่ใช่ความผิดพลาด มันคือ Git บอกว่า "ตรงนี้ฉันไม่รู้ว่าเธออยากได้แบบไหน" และเนื่องจากสามเวอร์ชันอยู่ครบ ไม่มีอะไรหายไประหว่างทาง ถ้าเริ่มสับสน `git merge --abort` ใช้ได้ทุกเมื่อ

</Callout>
