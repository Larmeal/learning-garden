## งานที่แก้ไปแล้ว อยากย้อนกลับไปดูของเมื่อวาน

นาย A เขียนรายงานส่งอาจารย์ แก้ไปแก้มาจนในโฟลเดอร์มีไฟล์ชื่อ `report_final.docx`, `report_final_v2.docx` และ `report_final_v2_อันนี้จริง.docx` พอถึงวันส่ง นาย A ก็เปิดผิดไฟล์ ส่งฉบับที่ยังไม่ได้แก้ย่อหน้าสุดท้ายไปให้อาจารย์ แล้วก็โดนอาจารย์ทักกลับมา

ปัญหาของนาย A คือเขาต้องจำเองว่าไฟล์ไหนใหม่กว่าไฟล์ไหน แก้อะไรไปบ้าง และเพราะอะไร ระบบที่ช่วยจำเรื่องพวกนี้ให้ เรียกว่า Version Control ซึ่ง Git ก็เป็นหนึ่งในนั้น

เรามาลองดูกันก่อนว่าข้างในมันเก็บงานของเราอย่างไร เพราะถ้าเข้าใจตรงนี้ คำสั่งที่เหลือจะมีเหตุผลของมันเอง

## Git เก็บภาพของทั้งโปรเจกต์ไว้ทีละรอบ

สมมติเรามีโฟลเดอร์ที่มีไฟล์สองไฟล์ คือ `a.txt` เขียนว่า `alpha` และ `b.txt` เขียนว่า `beta` เราสั่งให้ Git เก็บไว้หนึ่งรอบ เรียกว่าหนึ่ง **Commit** แล้วแก้ `a.txt` ให้ยาวขึ้น แล้วเก็บอีกรอบหนึ่ง ผลของ `git ls-tree` ซึ่งใช้ดูว่าแต่ละ Commit มีไฟล์อะไรบ้าง เป็นอย่างนี้ (รัน: `exercises/00_snapshots.py`)

```text
$ git ls-tree ed9a6af          # Commit แรก
100644 blob 4a58007052a65fbc2fc3f910f2855f45a4058e74	a.txt
100644 blob 65b2df87f7df3aeedef04be96703e55ac19c2cfb	b.txt

$ git ls-tree 189969c          # Commit ที่สอง
100644 blob 9bf8e491329fd9fb548d37fd9d53ecd138c17745	a.txt
100644 blob 65b2df87f7df3aeedef04be96703e55ac19c2cfb	b.txt
```

ตัวเลขยาว ๆ คือชื่อของเนื้อหาไฟล์แต่ละก้อน (เดี๋ยวเราจะมาดูว่าชื่อพวกนี้มาจากไหน) ลองมองที่ `b.txt` จะเห็นว่าทั้งสอง Commit ชี้ไปที่ก้อนเดียวกัน เพราะเรายังไม่ได้แตะไฟล์นี้เลย ส่วน `a.txt` ถูกแก้ จึงมีก้อนใหม่เกิดขึ้น และ Commit ที่สองก็ยังคงบอกไฟล์ครบทั้งสองไฟล์ ไม่ได้บอกเฉพาะส่วนที่เปลี่ยน

นี่คือสิ่งแรกที่หนังสือ *Version Control with Git* ให้เราลืมไปก่อน ระบบเก่าหลายตัวจะจำว่าแต่ละรอบ "แก้อะไรไปบ้าง" แต่ Git จะถ่าย **Snapshot** ของสภาพทั้งโปรเจกต์ ณ ตอนนั้นเก็บไว้ (หนังสือ: VCWG บทที่ 1 หน้า 5)

<Callout type="note" title="เก็บทั้งไฟล์ไม่เปลืองที่เหรอ">

ดูเหมือนจะเปลือง แต่ไฟล์ที่ไม่ได้แก้ถูกใช้ร่วมกันก้อนเดียวตามที่เห็นข้างบน และเมื่อ Repository ใหญ่ขึ้น Git จะรวบรวมของที่คล้ายกันเข้าด้วยกันแล้วเก็บเป็นส่วนต่างอีกที เราจะไปดูเรื่องนี้กันในบทที่ว่าด้วยข้างใน `.git`

</Callout>

</Step>

## ชื่อของทุกอย่างมาจากเนื้อหาของมันเอง

ตัวเลขยาว 40 ตัวอักษรเมื่อกี้ไม่ได้ถูกสุ่มขึ้นมา Git คำนวณมันจากเนื้อหาของไฟล์ด้วยฟังก์ชัน Hash ที่ชื่อ SHA-1 เรามาลองให้ Git คำนวณชื่อของข้อความ `hello` ที่ขึ้นบรรทัดใหม่หนึ่งครั้ง ทั้งในโฟลเดอร์สองที่ และลองเปลี่ยนตัวอักษรไปหนึ่งตัว

```text
$ git hash-object --stdin    # ใน Repository แรก  (ข้อความ: hello)
ce013625030ba8dba906f756967f9e9ca394464a

$ git hash-object --stdin    # ใน Repository ที่สอง (ข้อความ: hello)
ce013625030ba8dba906f756967f9e9ca394464a

$ git hash-object --stdin    # ข้อความ: hellp
d7a963a648c4564f03a0952546d2800681628048
```

เนื้อหาเดิมได้ชื่อเดิม ไม่ว่าจะอยู่ในโฟลเดอร์ไหนหรือคอมพิวเตอร์เครื่องไหน แต่แค่เปลี่ยนจาก `o` เป็น `p` ตัวเดียว ชื่อก็เปลี่ยนไปหมดทั้งตัว หนังสือเรียกระบบแบบนี้ว่า Content-Addressable (หนังสือ: VCWG บทที่ 2 หน้า 29)

การตั้งชื่อแบบนี้ทำให้ได้ของแถมสองอย่าง **อย่างแรก** ถ้าไฟล์สองไฟล์มีเนื้อหาเหมือนกัน Git จะเก็บแค่ก้อนเดียว **อย่างที่สอง** ถ้ามีใครแอบแก้เนื้อหาโดยไม่ให้ชื่อเปลี่ยน Git จะรู้ได้ทันทีว่าของเสียหาย (เรื่องนี้เราจะลองทำให้เห็นในบทที่ว่าด้วย Object Store)

<Callout type="note" title="SHA-1 กับ SHA-256">

หนังสือเขียนถึง SHA-1 ซึ่งเป็นค่าเริ่มต้นมาตลอด แต่ Git 2.56.1 ที่เรารันสามารถสร้าง Repository ที่ใช้ SHA-256 ซึ่งได้ชื่อยาว 64 ตัวอักษรได้ด้วย เราจะลองทำกันในบท [Object Store](/git/object-store/)

</Callout>

</Step>

## เวอร์ชันเก่ายังอยู่ ไม่มีอะไรถูกเขียนทับ

เพราะแต่ละ Commit ชี้ไปยังก้อนของตัวเองอยู่แล้ว การแก้ `a.txt` จึงไม่ได้ไปทับของเดิม เราขอดูไฟล์ตอนเป็น Commit แรกได้ทุกเมื่อ

```text
$ git show ed9a6af:a.txt
alpha
```

ถ้านับของทั้งหมดที่ Git เก็บไว้หลังสอง Commit จะได้ 7 ชิ้น (รัน: `git count-objects -v` ได้ `count: 7`) Commit แรกสร้างของใหม่ 4 ชิ้น คือไฟล์ 2 ก้อน, รายชื่อไฟล์ในโฟลเดอร์ 1 ชิ้น และตัว Commit เอง 1 ชิ้น ส่วน Commit ที่สองสร้างเพิ่มแค่ 3 ชิ้น คือไฟล์ `a.txt` ฉบับใหม่ รายชื่อไฟล์ฉบับใหม่ และตัว Commit

อีกอย่างที่ควรรู้ไว้ตั้งแต่ต้นคือ ทุกอย่างข้างบนเกิดขึ้นในคอมพิวเตอร์ของเราเองทั้งหมด ไม่ได้ต่อเน็ตเลย และเมื่อเรา Clone Repository ของคนอื่นมา เราจะได้ประวัติทั้งหมดมาด้วย (รัน: `exercises/06_remotes.py` ซึ่ง Clone มาแล้วเห็นประวัติครบ) นี่คือเหตุผลที่ Git ถูกเรียกว่า Distributed Version Control คอมพิวเตอร์ที่ Clone มาจึงมีของครบอยู่แล้ว ไม่ต้องไปขอประวัติจากเซิร์ฟเวอร์กลางทุกครั้ง

</Step>
