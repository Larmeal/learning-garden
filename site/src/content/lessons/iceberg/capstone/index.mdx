## โจทย์

สมมติว่าเรากำลังดูแลตาราง `orders` ของบริษัทขายของออนไลน์ ซึ่งมีผู้เขียนข้อมูลเข้ามาสองฝั่ง ฝั่งแรกคือ Spark Batch ที่โหลดคำสั่งซื้อรายวัน ส่วนฝั่งที่สองคือโปรแกรม Python ที่ใช้ PyIceberg (เช่นบริการรับข้อมูลจากร้านค้าปลีก) ปัญหาคือข้อมูลล็อตหลังบางครั้งมีแถวผิด เช่นยอดติดลบ และเราไม่อยากให้ผู้อ่านเห็นแถวนั้นเลย นอกจากนี้เรายังต้องแก้ข้อมูลย้อนหลังได้ มีระบบปลายทางที่อยากรู้เฉพาะส่วนที่เปลี่ยน และต้องเก็บ Snapshot สิ้นเดือนไว้เป็นหลักฐานด้วย (รัน: `exercises/14_capstone_orders.py`)

เส้นทางด้านล่างใช้เครื่องมือจากบทก่อน ๆ ทั้งหมด ตารางสร้างเป็นเวอร์ชัน 2 Partition ตามวัน และตั้ง `write.merge.mode` กับ `write.delete.mode` เป็น Merge-on-read ([บท 6](/iceberg/row-level/#merge-on-read-เขียนแค่โน้ตว่าข้าม-row-ไหน))

</Step>

## Spark เขียนล็อตแรก และจดจุดที่ระบบปลายทางอ่านถึง

Spark `INSERT` 3 Row ลงตาราง ผลรวมยอดเป็น 242.5 จากนั้นเราจด Snapshot ID ล่าสุดไว้เป็น `bookmark` ซึ่งแทนจุดที่ระบบปลายทางอ่านถึงแล้ว ([บท 12](/iceberg/streaming/#อ่านเฉพาะแถวที่เพิ่มระหว่างสอง-snapshot))

</Step>

<Step>

## PyIceberg เขียนล็อตที่สองลง Branch ก่อน

ฝั่ง PyIceberg ไม่เขียนลงตารางหลักตรง ๆ แต่เขียนลง Branch ชื่อ `audit` ([บท 8](/iceberg/time-travel/#branch-แยกเส้นสำหรับงานที่ยังไม่แน่ใจ))

```python
spark.sql("ALTER TABLE lab.db.orders CREATE BRANCH audit")
t.append(batch, branch="audit")        # batch มี 3 Row และ Row สุดท้ายมียอด -9.0
```

ตารางหลักยังนับได้ 3 Row เหมือนเดิม เพราะ Branch หลักไม่ขยับ ผู้อ่านจึงยังไม่เห็นล็อตใหม่ แล้วเราตรวจบน Branch ด้วย `SELECT count(*) ... VERSION AS OF 'audit' WHERE amount < 0` ได้ 1 แถว คือแถวที่ผิดตามที่ตั้งใจใส่ไว้

</Step>

## ลบแถวเสียบน Branch แล้วเผยแพร่

เมื่อเจอแถวที่ผิด เราลบมันบน Branch ก่อน

```python
spark.sql("DELETE FROM lab.db.orders.branch_audit WHERE amount < 0")
spark.sql("CALL lab.system.fast_forward('db.orders', 'main', 'audit')")
```

หลัง Fast Forward ตารางหลักมี Row 1 ถึง 5 ไม่มี Row ที่ 6 เลย ผู้อ่านไม่เคยเห็นแถวที่ผิด จากนั้นเราลบ Branch และตั้ง Tag ชื่อ `month_end` ที่ Snapshot นี้ พร้อมเก็บไว้ 365 วัน

</Step>

## แก้ย้อนหลังด้วย MERGE

ต่อมาร้านค้าแจ้งว่ายอดของคำสั่งซื้อที่ 2 ต้องเป็น 85.0 ไม่ใช่ 80.5 เราแก้ด้วย `MERGE INTO` ที่อัปเดตแถวที่ตรงและเพิ่มแถวที่ไม่ตรง

```python
spark.sql("""MERGE INTO lab.db.orders t USING (SELECT 2L AS order_id, 'bob' AS customer, 85.0 AS amount, TIMESTAMP'2026-01-01 15:30:00' AS ordered_at) s
             ON t.order_id = s.order_id WHEN MATCHED THEN UPDATE SET amount = s.amount WHEN NOT MATCHED THEN INSERT *""")
```

ผลรวมยอดเป็น 562.0 (120 + 85 + 42 + 300 + 15) และตารางมี Position Delete File อย่างน้อยหนึ่งไฟล์ เพราะตั้ง Merge-on-read ไว้

</Step>

## ส่งต่อให้ระบบปลายทาง

ระบบปลายทางอยากรู้เฉพาะส่วนที่เปลี่ยนตั้งแต่ `bookmark` เราลอง Changelog View ที่เห็นใน[บท 8](/iceberg/time-travel/#changelog-ดูว่าอะไรเปลี่ยนไป)ก่อน

```text
UnsupportedOperationException: Delete files are currently not supported in changelog scans
```

Changelog อ่านช่วง Snapshot ที่มี Delete File ไม่ได้ในเวอร์ชันที่เราทดลอง และตารางของเรามีแล้วจาก Merge-on-read ส่วน Incremental Read ของ[บท 12](/iceberg/streaming/) ก็ใช้ไม่ได้ เพราะช่วงนี้มี Snapshot ที่ไม่ใช่ Append เราจึงเลือกวิธีที่ตรงไปตรงมากว่า คือเทียบตารางที่ `bookmark` กับตารางตอนนี้ด้วย Time Travel

```python
old = spark.sql(f"SELECT order_id, amount FROM lab.db.orders VERSION AS OF {bookmark}")
new = spark.table("lab.db.orders")
```

ผลที่เทียบได้คือ เพิ่มใหม่ Row 4 และ 5, แก้ Row 2, ไม่มีการลบ และ Row 6 ที่ผิดไม่ปรากฏเลย (ในแบบฝึก เราคำนวณจากสองชุดนี้ด้วย Python Dict) วิธีนี้อ่านทั้งสองฉบับจึงแพงกว่าอ่านเฉพาะส่วนต่าง ถ้าตารางใหญ่มากอาจต้องออกแบบใหม่ เช่นใช้ตารางแบบ Copy-on-write ซึ่งเราไม่ได้ทดลองว่า Changelog ใช้กับมันได้หรือไม่

</Step>

## ดูแลตาราง: รวมไฟล์ แล้วลบ Snapshot เก่าแต่เก็บ Tag

ขั้นสุดท้าย เรารวมไฟล์ด้วย `rewrite_data_files` แบบเขียนใหม่ทั้งหมด ข้อมูล 4 ไฟล์ถูกเขียนใหม่เป็น 3 ไฟล์ (ตามจำนวน Partition ที่มีข้อมูล) แล้วสั่ง `expire_snapshots` ให้เก็บแค่ Snapshot ล่าสุด

```text
refs: main, month_end        ตารางหลักมี 5 Row ยอดรวม 562.0        month_end ยังอ่านได้ 5 Row
```

Tag `month_end` ทำให้ Snapshot นั้นรอดจากการลบ ตามที่เห็นในบทดูแลตาราง สิ่งที่แบบฝึกเจอและน่าสนใจคือหลังรวมไฟล์ **เหลือ Delete File อยู่หนึ่งไฟล์** ซึ่งชี้ไปยัง Data File ที่ไม่อยู่ใน Snapshot ปัจจุบันแล้ว (เราตรวจว่าชื่อไฟล์ที่มันอ้างไม่อยู่ในรายชื่อ Data File ปัจจุบัน) ตอนเขียนบทนี้ผู้เขียนเข้าใจว่า Reader ไม่ได้ใช้ไฟล์นี้และมันจะหายไปเองเมื่อมีงานดูแลรอบถัดไป แต่หลังจากนั้นเราลองแล้วพบว่าไม่จริง Delete File แบบนี้ไม่หายไปเอง ต้องเรียก `rewrite_data_files` อีกครั้งโดยตั้ง `remove-dangling-deletes` เป็น `true` ซึ่งเราลองให้ดูใน[หน้าเจาะลึก Copy-on-write และ Merge-on-read](/iceberg/row-level/in-depth/) ถ้าคุณใช้ Merge-on-read ก็ควรตรวจเรื่องนี้ในระบบจริงของคุณด้วย

สุดท้าย PyIceberg อ่านตารางที่ผ่านทั้งหมดนี้ได้ครบ 5 Row ยอดรวม 562.0 ตรงกับฝั่ง Spark

</Step>

## ย้อนดูทั้งเส้นทาง

ตารางนี้ผ่านเกือบทุกเรื่องของเส้นทางนี้ ได้แก่ Catalog ร่วมกันสองโปรแกรม ([บท 1](/iceberg/what-is-iceberg/)), Partition ตามวัน ([บท 3](/iceberg/schema-partitioning/)), Commit จากสองฝั่ง ([บท 4](/iceberg/writing/)), Delete File ([บท 6](/iceberg/row-level/)), Branch และ Tag ([บท 8](/iceberg/time-travel/)) และงานดูแลตาราง ([บท 10](/iceberg/maintenance/)) เรื่องที่เหลือแต่ไม่ได้ใช้ในตัวอย่างนี้คือการเปลี่ยน Schema ([บท 7](/iceberg/evolution/)), การย้ายตารางเดิม ([บท 11](/iceberg/migration/)) และ Format Version ([บท 13](/iceberg/spec-versions/)) ซึ่งเป็นงานที่คุณจะเจอเมื่อตารางนี้อยู่ไปนานขึ้น

</Step>
