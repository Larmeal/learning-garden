## สองโหมดต่างกันตรงไหน และเราจะดูอะไรกัน

ใน[บท 6](/iceberg/row-level/#เทียบสามโหมดข้างกัน) เราเห็นกันแล้วว่า Iceberg ลบ Row ได้สองทาง ทางแรกคือ Copy-on-write ที่เขียน Data File ใหม่ทั้งไฟล์ ส่วนทางที่สองคือ Merge-on-read ที่เขียนโน้ตสั้น ๆ ไว้ว่าให้ข้าม Row ไหน หน้านี้เราจะตามไปดูไฟล์จริงทุกไฟล์ของทั้งสองทาง เพราะคำถามที่มักตามมาคือ ราคาของสองทางต่างกันเท่าไร ตอนอ่านต้องทำอะไรเพิ่มบ้าง และ Delete File จะกองสูงจนอ่านช้าหรือเปล่า

เรามีตารางสองตัว ตัวแรกใช้ค่าเริ่มต้นคือ Copy-on-write ส่วนตัวที่สองตั้ง `write.delete.mode`, `write.update.mode` และ `write.merge.mode` เป็น `merge-on-read` ทั้งสามตัว ทั้งสองตารางมีข้อมูลเหมือนกันคือ 5 Row ใน 1 ไฟล์ จากนั้นเราสั่ง `DELETE` Order 3 และ `UPDATE` Order 5 ทีละคำสั่ง แล้วเปิดอ่านไฟล์ทุกไฟล์จากดิสก์ด้วย `json`, `fastavro` และ `pyarrow` ทุกครั้งที่จบหนึ่งคำสั่ง (รัน: `exercises/16_cow_mor_in_depth.py`) ภาพที่เห็นเป็นแบบเดียวกับ[หน้า "Under the Covers"](/iceberg/table-anatomy/under-the-covers/) ให้กด "ถัดไป" ทีละขั้น แล้วคลิกกล่องเพื่อดูว่าข้างในไฟล์นั้นมีอะไร

ของใหม่ในหน้านี้มีสองอย่าง อย่างแรกคือกล่อง **Delete File** (`d1`, `d2`) ที่อยู่คอลัมน์ขวาสุดคู่กับ Data File อย่างที่สองคือ Manifest ชนิดใหม่ที่ลิสต์ Delete File (`content = 1`) ซึ่งแยกออกมาจาก Manifest ของ Data File

</Step>

## ราคาของการแก้ Row เดียว

ก่อนจะไล่ดูไฟล์ทีละไฟล์ เรามาลองวัดราคากันก่อนดีกว่า เราสร้างตารางที่มี 100,000 Row ใน 5 ไฟล์ (ไฟล์ละ 20,000 Row) ทั้งสองโหมด แล้วแก้ Row เดียว และลบ Row เดียว ตัวเลขข้างล่างอ่านมาจาก Summary ของ Snapshot (รัน: `exercises/16_cow_mor_in_depth.py`)

| คำสั่ง | โหมด | Row ที่ถูกเขียน | ไฟล์ที่ถูกเขียน | ไบต์ที่เขียนราว |
|---|---|---|---|---|
| `UPDATE` 1 Row | Copy-on-write | 20,000 | Data File 1 ไฟล์ (เอาไฟล์เดิมออก 1 ไฟล์) | 37 KB |
| `UPDATE` 1 Row | Merge-on-read | 1 | Data File 1 ไฟล์ (1 Row) กับ Delete File 1 ไฟล์ (1 ตำแหน่ง) | 2.5 KB |
| `DELETE` 1 Row | Copy-on-write | 19,999 | Data File 1 ไฟล์ (เอาไฟล์เดิมออก 1 ไฟล์) | 62 KB |
| `DELETE` 1 Row | Merge-on-read | 0 | Delete File 1 ไฟล์ (1 ตำแหน่ง) | 1.5 KB |

จะเห็นได้ว่า Copy-on-write เขียน Data File ใหม่ทั้งไฟล์ แม้เราจะแก้แค่ Row เดียวก็ตาม คอลัมน์ที่ควรดูคือ Row ที่ถูกเขียน เพราะขนาดไบต์ของตัวอย่างเล็ก ๆ ยังมี Overhead ของไฟล์ Parquet ปนอยู่ ส่วน Merge-on-read เขียนเฉพาะสิ่งที่เปลี่ยน แต่ก็มีราคาอีกด้านที่ตารางนี้ยังมองไม่เห็น นั่นคือทุกครั้งที่อ่าน ผู้อ่านต้องกรองข้อมูลด้วย Delete File ด้วย ซึ่งเดี๋ยวเราจะมาดูกันในหัวข้อถัด ๆ ไป

ผลลัพธ์ของสองโหมดตรงกันทุกอย่าง ตารางเหลือ 99,999 Row และ Row ที่แก้มี `amount` เป็น -1.0 เหมือนกัน คนที่ใช้ตารางจึงไม่เห็นความต่างเลย สิ่งที่ต่างคือไฟล์ที่อยู่เบื้องหลัง

## Copy-on-write ลบ 1 Row จากไฟล์ที่มี 5 Row

<UnderCoversLab client:visible op="cowDelete" />

ลองคลิก Manifest `m3` ในขั้นที่ 3 ดู จะเห็นว่า `a1` มีสถานะ `DELETED` ส่วน `m2` บอกว่า `a2` ถูก `ADDED` เข้ามา Manifest List `s2` ก็ไม่มี `m1` แล้ว เพราะไฟล์เดียวที่ `m1` ลิสต์อยู่คือ `a1` ซึ่งถูกแทนที่ไปแล้ว พอผู้อ่านเปิดตารางตอนนี้ก็จะเจอ `a2` ไฟล์เดียว อ่านตรง ๆ ได้เลยโดยไม่ต้องกรองอะไร นี่คือข้อดีของ Copy-on-write ที่หนังสือสรุปไว้ในตารางเทียบว่าอ่านเร็วที่สุด แต่แก้และลบช้าที่สุด (หนังสือ: Apache Iceberg: The Definitive Guide บทที่ 4 หน้า 86)

</Step>

## Merge-on-read ลบด้วย Delete File ที่จดตำแหน่ง

<UnderCoversLab client:visible op="morDelete" />

ขั้นที่ 1 ของภาพนี้คือสิ่งที่ตารางเทียบข้างบนมองไม่เห็น ก่อนจะเขียน Delete File ได้ Spark ต้องรู้ก่อนว่า Order 3 อยู่ตำแหน่งที่เท่าไรใน `a1` มันจึงต้องเปิดอ่าน `a1` ก่อน แล้วค่อยเขียน Delete File `d1` ที่มีแถวเดียว ลองคลิก `d1` ในขั้นที่ 2 ดู จะเห็นตารางสองคอลัมน์ คือ `file_path` กับ `pos` ซึ่งเก็บชื่อ Data File `a1` และตำแหน่ง 2 (นับจาก 0) ซึ่งเป็นตำแหน่งของ Order 3 Delete File แบบนี้เรียกว่า **Position Delete** ต้นทุนฝั่งเขียนคือต้องอ่านไฟล์เพื่อหาตำแหน่ง แลกกับต้นทุนฝั่งอ่านที่ต่ำ เพราะผู้อ่านรู้อยู่แล้วว่าต้องข้ามตำแหน่งไหน (หนังสือ: บทที่ 4 หน้า 89)

ลองคลิก Manifest `m2` ด้วย จะเห็นว่า `content` เป็น 1 แปลว่านี่คือ Manifest ของ Delete File แยกออกมาจาก `m1` ซึ่งเป็น Manifest ของ Data File และถูกใช้ซ้ำโดยไม่ถูกแก้ Snapshot `s2` มี `operation` เป็น `delete` และไม่มี Data File ใหม่เลย อีกเรื่องที่ควรสังเกตคือ Total Records ใน Summary ของ Snapshot นี้ยังนับเป็น 5 ทั้งที่ผู้อ่านเห็นแค่ 4 Row ซึ่ง[บท 6](/iceberg/row-level/#merge-on-read-เขียนแค่โน้ตว่าข้าม-row-ไหน)เคยพูดถึงไว้แล้ว

</Step>

## UPDATE ใน Merge-on-read คือ Delete File บวก Data File เล็ก ๆ

<UnderCoversLab client:visible op="morUpdate" />

`UPDATE` ใน Merge-on-read ทำสองอย่างใน Commit เดียว อย่างแรกคือเขียน Row ใหม่เป็น Data File เล็ก ๆ (`a2` มี 1 Row) อย่างที่สองคือเขียน Delete File ที่บอกให้ข้าม Row เก่า

ตรงนี้มีเรื่องที่น่าสนใจซ่อนอยู่ ลองดูขั้นที่ 3 `a1` มี Delete File `d1` อยู่แล้ว (ตำแหน่ง 2) เราอาจคิดว่า Spark จะเขียน Delete File อีกไฟล์มาวางคู่กัน แต่จริง ๆ แล้วมันเขียน `d2` ที่มี**สองตำแหน่ง**คือ 2 กับ 4 แล้วเขียน Manifest `m5` ที่บอกว่า `d1` ถูก `DELETED` ลองคลิก `d2` ดูสองแถวนั้นได้เลย ผลก็คือ `a1` มี Delete File แค่ไฟล์เดียวเสมอ

เพื่อให้แน่ใจ เราทดลองซ้ำบนตาราง 100,000 Row โดยลบ Row ในไฟล์เดียวกันซ้ำ ๆ แล้วดูว่าจำนวน Delete File ที่ผู้อ่านต้องใช้ต่อ Data File เพิ่มขึ้นหรือเปล่า

| หลังคำสั่ง | Delete File ทั้งตาราง | ตำแหน่งที่ถูกลบทั้งตาราง | Delete File ที่ต้องใช้ต่อ Data File (ไฟล์ละตัว) |
|---|---|---|---|
| `UPDATE` 1 Row กับ `DELETE` 1 Row (คนละไฟล์) | 2 | 2 | 0, 0, 0, 0, 1, 1 |
| `DELETE` อีก 1 Row ในไฟล์ที่ 2 | 3 | 3 | 0, 0, 0, 1, 1, 1 |
| `DELETE` อีก 1 Row ในไฟล์ที่ 2 | 3 | 4 | 0, 0, 0, 1, 1, 1 |
| `DELETE` อีก 1 Row ในไฟล์ที่ 2 | 3 | 5 | 0, 0, 0, 1, 1, 1 |

ตำแหน่งที่ถูกลบเพิ่มขึ้นเป็น 5 แต่ Delete File ทั้งตารางหยุดอยู่ที่ 3 ไฟล์ และไม่มี Data File ไฟล์ไหนต้องใช้ Delete File เกินหนึ่งไฟล์ (คอลัมน์สุดท้ายอ่านด้วย PyIceberg `plan_files()` ซึ่งบอก `delete_files` ของแต่ละ Data File) ทั้งหมดนี้เป็นพฤติกรรมของ Spark 4.1.3 กับ Iceberg 1.12.0 ที่เรารัน ส่วน Engine อื่น เช่น Flink อาจเขียน Delete File หลายไฟล์ต่อ Data File ก็ได้ ซึ่งเรายังไม่ได้ลอง (ไม่ได้รัน)

</Step>

## SELECT ต้องกรอง Data File ด้วย Delete File

<UnderCoversLab client:visible op="morSelect" />

ขั้นที่ 4 คือส่วนที่ผู้อ่านต้องทำงานเพิ่ม Manifest `m5` มีแต่ Delete File ที่ถูกลบไปแล้ว จึงข้ามได้เลย ส่วนที่เหลือบอกว่ามี Data File `a2` กับ `a1` และ Delete File `d2` ที่ต้องใช้กับ `a1` พอถึงขั้นที่ 5 `a1` มี 5 Row แต่ `d2` สั่งให้ข้ามตำแหน่ง 2 กับ 4 ผู้อ่านจึงได้ 3 Row จาก `a1` รวมกับอีก 1 Row จาก `a2` เป็น 4 Row ซึ่งตรงกับที่ `SELECT count(*)` นับได้ PyIceberg ก็เห็นเหมือนกัน ตอนวางแผนอ่าน `a2` ไม่ต้องใช้ Delete File ส่วน `a1` ต้องใช้ `d2` (รัน: `plan_files()` ในแบบฝึก)

ราคาฝั่งอ่านของ Merge-on-read จึงเป็นการเปิด Delete File เพิ่มและกรองทีละ Data File ถ้า Delete File กองสูง ราคานี้ก็สูงตามไปด้วย ซึ่งเป็นเหตุผลที่เราต้องทำ Compaction

</Step>

## Compaction เขียน Data File ที่กรองแล้ว แต่ Delete File ยังค้าง

<UnderCoversLab client:visible op="morCompact" />

เรารัน `rewrite_data_files` โดยตั้งตัวเลือก `delete-file-threshold` เป็น 1 หมายความว่า Data File ที่มี Delete File ตั้งแต่ 1 ไฟล์ขึ้นไปต้องถูกเขียนใหม่ (ค่าเริ่มต้นของตัวเลือกนี้คือค่ามากสุดของ Integer ตามที่อ่านจากโค้ด ซึ่งแทบไม่มีทางถึง) ผลคือได้ `a3` ที่มี 4 Row ซึ่งกรองแล้ว และผู้อ่านคนใหม่เปิดแค่ไฟล์เดียวโดยไม่ต้องกรองอะไรอีก

แต่ลองดูขั้นที่ 6 ให้ดี จะเห็นว่า `d2` ยังอยู่ใน Snapshot และ Summary ยังบอก `total-delete-files` เป็น 1 ทั้งที่ไม่มี Data File ไฟล์ไหนในตารางต้องใช้มันแล้ว เพราะ `a1` ที่มันชี้ไปถูกแทนด้วย `a3` Delete File แบบนี้เรียกว่า Dangling และผลที่ Procedure ส่งกลับมาก็บอกชัดว่า `removed_delete_files_count` เป็น 0 ตารางใหญ่ของเราก็เป็นเหมือนกัน เขียน Data File ใหม่ไป 6 ไฟล์ แต่ Delete File ยังเหลืออยู่ 1 ไฟล์ ([บท 14](/iceberg/capstone/) เคยเจอเรื่องนี้ในโจทย์ใหญ่มาแล้ว)

<UnderCoversLab client:visible op="morClean" />

วิธีเก็บกวาดคือเรียก `rewrite_data_files` อีกครั้งโดยตั้ง `remove-dangling-deletes` เป็น `true` (ตัวเลือกนี้ปิดอยู่เป็นค่าเริ่มต้น ตามที่อ่านจาก `RewriteDataFiles.java`) รอบนี้ไม่ต้องเขียน Data File ใหม่เลย `rewritten_data_files_count` เป็น 0 มีแค่ Manifest `m9` ที่ลิสต์ `d2` เป็น `DELETED` ส่วนบนตาราง 100,000 Row ผลคือ `removed_delete_files_count` เป็น 1 และ `total-delete-files` เป็น 0

<Callout type="note" title="Delete File ที่ค้างอยู่ทำอะไรเราบ้าง">

Delete File ที่ค้างอยู่ไม่ได้ทำให้ผลลัพธ์ผิดนะ Row ที่ถูกลบไปแล้วไม่กลับมา และผู้อ่านก็เปิด Data File ใหม่ได้ถูกต้อง ที่เสียไปคือพื้นที่รกบนดิสก์กับ Manifest ที่ต้องอ่านเพิ่ม ส่วนการลบ Delete File ออกจากดิสก์จริง ๆ ก็ยังต้องรอ Expire Snapshot เหมือน Data File เก่า ([บท 10](/iceberg/maintenance/#expire_snapshots-ลบ-snapshot-เก่าและไฟล์ที่มีแต่มันใช้))

</Callout>

</Step>

## หนึ่งตาราง คนละโหมดต่อคำสั่ง

เรากำหนดโหมดแยกตามคำสั่งได้ ซึ่งหนังสือแนะนำไว้สำหรับกรณีที่งานของแต่ละคำสั่งต่างกัน (หนังสือ: บทที่ 4 หน้า 90) เราลองกับตารางที่ตั้ง `write.delete.mode` เป็น `merge-on-read` แต่ `write.update.mode` กับ `write.merge.mode` เป็น `copy-on-write`

```text
DELETE -> operation = delete      added-delete-files: 1                      (Merge-on-read)
UPDATE -> operation = overwrite   added-data-files: 1   deleted-data-files: 1 (Copy-on-write)
```

`DELETE` ได้ Delete File ส่วน `UPDATE` ได้ Data File ใหม่มาแทนไฟล์เดิม ตารางตัวเดียวจึงมีไฟล์ทั้งสองแบบปนกันได้ และผู้อ่านก็ทำงานตามไฟล์ที่เจอ โดยไม่ต้องรู้เลยว่าตั้งโหมดไหนไว้

</Step>

## เลือกโหมดไหนดี

หนังสือเทียบสามแบบไว้ในตารางเดียว (หนังสือ: บทที่ 4 หน้า 86) เราเลยเติมสิ่งที่ตัวเลขข้างบนยืนยันไว้ในคอลัมน์ข้าง ๆ

| โหมด | อ่าน | แก้และลบ | ที่ตัวเลขของเรายืนยัน |
|---|---|---|---|
| Copy-on-write | เร็วที่สุด | ช้าที่สุด | เขียนใหม่ทั้งไฟล์ (20,000 Row เพื่อแก้ 1 Row) |
| Merge-on-read (Position Delete) | เร็ว | เร็ว | เขียน 1 Row กับ 1 ตำแหน่ง ผู้อ่านต้องกรองด้วย Delete File และต้อง Compaction เป็นระยะ |
| Merge-on-read (Equality Delete) | ช้า | เร็วที่สุด | ไม่ได้รัน |

Equality Delete เป็น Delete File ที่จดค่าของ Column แทนการจดตำแหน่ง คือบอกว่าให้ข้าม Row ที่มีค่าตรงกัน ข้อดีคือเขียนง่าย เพราะไม่ต้องเปิด Data File ไปหาตำแหน่ง แต่ตอนอ่านผู้อ่านต้องเอาค่าไปเทียบกับทุก Row ที่อาจตรง จึงอ่านช้า และต้องทำ Compaction ถี่ขึ้น (หนังสือ: บทที่ 2 หน้า 33 ถึง 34 และบทที่ 4 หน้า 89) เรื่องนี้เรายังไม่ได้รัน เพราะ Spark SQL ที่เราใช้ไม่เขียน Equality Delete ส่วนเครื่องมืออย่าง Flink ที่เขียนได้ เรายังไม่ได้ติดตั้ง

ส่วนตัวผู้เขียนคิดว่าเราเลือกโหมดได้ประมาณนี้ ซึ่งเป็นความเห็นจากสิ่งที่เราเพิ่งเห็น ไม่ใช่กฎตายตัวนะ ตารางที่ถูกอ่านบ่อยกว่าเขียนมาก และแก้ทีละน้อย เหมาะกับ Copy-on-write เพราะผู้อ่านไม่ต้องทำอะไรเพิ่ม ส่วนตารางที่แก้บ่อย หรือแก้ทีละ Row ในไฟล์ใหญ่ เหมาะกับ Merge-on-read แต่ก็ต้องตั้งเวลา Compaction และเก็บกวาด Delete File ที่ค้างไว้พร้อมกัน และถ้าลบบ่อยแต่แก้น้อย เราก็ผสมได้ โดยตั้ง `delete` เป็น Merge-on-read และ `update` เป็น Copy-on-write
