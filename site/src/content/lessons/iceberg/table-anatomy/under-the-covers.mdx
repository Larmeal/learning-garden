## ตารางเดียว คำสั่งเจ็ดแบบ ไฟล์จริงทุกไฟล์

ใน[บท 2](/iceberg/table-anatomy/) เราเดินตามลูกศรหลังจาก `INSERT` เสร็จไปแล้ว หน้านี้ย้อนกลับไปดูตอนที่ไฟล์พวกนั้นเกิดขึ้น เราใช้ตาราง `orders` ตัวเดิมแล้วสั่งไปทีละคำสั่ง คือ `CREATE TABLE`, `INSERT` สองครั้ง, `MERGE INTO`, `SELECT` ที่มีเงื่อนไข, ย้อนเวลา และ Compaction หลังจบแต่ละคำสั่ง เราอ่านไฟล์ทุกไฟล์จากดิสก์ด้วย `json` กับ `fastavro` ไม่ได้ถาม Spark (รัน: `exercises/15_under_the_covers.py`)

ในแต่ละภาพมีห้าคอลัมน์ ซึ่งตรงกับสามชั้นของตารางที่หนังสือวาดไว้ คือ Catalog อยู่ซ้ายสุด ตรงกลางเป็นชั้น Metadata ที่มี `metadata.json`, Manifest List และ Manifest และขวาสุดเป็นชั้น Data ที่เก็บไฟล์ Parquet เพื่อให้อ่านง่าย เราตั้งชื่อย่อให้ไฟล์ทุกไฟล์ `v1`, `v2` คือ `metadata.json` แต่ละฉบับ `s1`, `s2` คือ Manifest List ของแต่ละ Snapshot `m1`, `m2` คือ Manifest และ `a1`, `a2` คือ Data File ชื่อจริงบนดิสก์เป็น UUID ยาว ๆ ซึ่งอ่านไม่สนุก

วิธีใช้ภาพมีสองอย่าง กด "ถัดไป" เพื่อเดินทีละขั้น และ**คลิกกล่องไหนก็ได้**เพื่อดูว่าข้างในไฟล์นั้นมีอะไร ตารางใต้ภาพคือเนื้อหาจริงของไฟล์ที่เลือก

ก่อนเริ่ม ขอให้เก็บสามเรื่องนี้ไว้ในใจ เพราะทุกคำสั่งในหน้านี้ทำตามนี้ทั้งหมด **เรื่องแรก** ไฟล์ที่เขียนเสร็จแล้วจะไม่ถูกแก้อีก ไม่ว่าจะเป็น Data File Manifest Manifest List หรือ `metadata.json` **เรื่องที่สอง** Commit คือการเขียนไฟล์ใหม่ให้ครบก่อน แล้วค่อยเปลี่ยนตัวชี้ใน Catalog หนึ่งครั้งตอนท้าย ผู้อ่านจึงเห็นของใหม่ทั้งหมดพร้อมกัน หรือไม่เห็นอะไรเลย และ**เรื่องสุดท้าย** ข้อมูลที่ "หายไป" จากตารางไม่ได้ถูกลบออกจากดิสก์จริง ๆ แค่มี Manifest ใหม่บอกว่าไฟล์นั้น DELETED ส่วนไฟล์จริงยังอยู่เหมือนเดิม

</Step>

## CREATE TABLE ตารางเปล่าก็มีไฟล์แล้วหนึ่งไฟล์

<UnderCoversLab client:visible op="create" />

เมื่อสั่ง `CREATE TABLE` สิ่งเดียวที่ถูกเขียนลงดิสก์คือ `v1.metadata.json` ลองคลิกกล่อง "Metadata File v1" ในภาพ จะเห็น Schema ที่ทุก Column มี Field id (`order_id` เป็น 1 `customer` เป็น 2 `amount` เป็น 3) และรายการ Snapshot ที่ว่างเปล่า ตารางนี้ยังไม่มี Data File ไม่มี Manifest และไม่มี Manifest List

แล้ว Catalog จำอะไร คลิกกล่อง Catalog ดู จะเห็นว่ามันจำแค่ชื่อตารางกับที่อยู่ของ `v1.metadata.json` เท่านั้น ที่เหลือทั้งหมดอยู่ในไฟล์ นี่คือเหตุผลที่ Engine หลายตัวใช้ตารางเดียวกันได้ ขอแค่เปิด Catalog เดียวกัน

</Step>

## INSERT ครั้งแรก เขียนสี่ไฟล์ แล้วค่อยเปลี่ยนตัวชี้

<UnderCoversLab client:visible op="insert1" />

ลำดับของการเขียนสำคัญมาก เขียนจากล่างขึ้นบนเสมอ เริ่มที่ Data File แล้ว Manifest แล้ว Manifest List แล้ว `metadata.json` และสุดท้ายถึงเปลี่ยนตัวชี้ใน Catalog ระหว่างที่ขั้น 2 ถึง 5 กำลังเดินอยู่ ลองสังเกตว่า Catalog ในภาพยังชี้ที่ `v1` ตลอด ผู้อ่านที่เปิดตารางในช่วงนั้นเลยเห็นตารางเปล่าเหมือนเดิม ไม่มีทางเห็นไฟล์ที่เขียนไปครึ่ง ๆ กลาง ๆ

เปรียบกับห้องสมุดที่ออกหนังสือฉบับใหม่ บรรณารักษ์พิมพ์หน้าใหม่ ทำรายการหน้า ทำ Metadata File ฉบับใหม่ แล้วเอาไปวางไว้หลังเคาน์เตอร์ก่อน พอพร้อมทั้งชุดถึงค่อยเปลี่ยนป้ายบนชั้นหนึ่งครั้ง ไม่มีใครเห็นหนังสือที่ทำไม่เสร็จ

ลองคลิก Manifest `m1` ดูสถิติข้างใน เราเห็น `order_id` ตั้งแต่ 1 ถึง 2 และ `amount` ตั้งแต่ 80.5 ถึง 120.0 ตัวเลขพวกนี้ไม่ได้อยู่ในไฟล์ Parquet อย่างเดียว Manifest เก็บสำเนาไว้ด้วย เพื่อให้ตอนอ่านข้ามไฟล์ได้โดยไม่ต้องเปิด Data File เรากลับมาใช้มันตอน `SELECT` ในหัวข้อถัดไป

## INSERT ครั้งที่สอง Manifest ของครั้งแรกถูกใช้ซ้ำ

<UnderCoversLab client:visible op="insert2" />

ครั้งนี้ลองดูขั้น 4 ให้ดี Manifest List `s2` ชี้ไปสองไฟล์ คือ `m2` ที่เพิ่งเขียน และ `m1` ที่เขียนไว้ตั้งแต่ INSERT ครั้งแรก ในภาพ `m1` ติดป้าย "ใช้ซ้ำ" Iceberg ไม่ได้เขียนรายการไฟล์ทั้งตารางใหม่ มันเขียนเฉพาะของที่เพิ่ม แล้วให้ Snapshot ใหม่ชี้ไปหาของเก่า

เมื่อคลิก `s2` จะเห็นรายการ Manifest พร้อมตัวเลข "เพิ่ม / มีอยู่แล้ว / ลบ" ของแต่ละไฟล์ `m2` เพิ่ม 1 ไฟล์ และ `m1` ก็เพิ่ม 1 ไฟล์ ซึ่งเป็นงานของ Commit ครั้งที่หนึ่ง ตัวเลข "เพิ่ม" ของ `m1` จึงยังเท่าเดิม ตัวเลขนี้เป็นของ Manifest เอง ไม่ใช่ของ Snapshot ที่เปิดอ่านอยู่

อีกเรื่องที่น่าสังเกตคือ Metadata File `v3` เก็บ Snapshot ทั้ง `s1` และ `s2` ใครขอ `s1` ก็ยังเห็น 2 แถวเดิม เรื่องนี้เราจะใช้ตอนย้อนเวลา

</Step>

## MERGE INTO ไฟล์เก่าไม่ถูกแก้ แค่มี Manifest บอกว่ามันถูกลบ

<UnderCoversLab client:visible op="merge" />

`MERGE` นี้แก้ Order 2 จาก 80.5 เป็น 95.0 และเพิ่ม Order 5 เข้ามาใหม่ ซึ่งทำให้เราเห็นว่า Iceberg จัดการอย่างไรกับไฟล์ที่ห้ามแก้ ลองดูขั้น 2 ถึง 4 สามจุดนี้

**จุดแรก** Data File ใหม่ `a3` มี 3 แถว คือ Order 1 (ไม่เปลี่ยน), Order 2 (95.0) และ Order 5 ลองคลิกดูได้เลย แถวทั้งสามอยู่ครบ นี่คือ Copy-on-write ที่เราคุยกันใน[บท 6](/iceberg/row-level/#copy-on-write-เขียนไฟล์ใหม่ทั้งไฟล์) Spark เขียนไฟล์ใหม่ทั้งไฟล์ แทนที่จะไปแก้แถวเดียวในไฟล์เดิม **จุดที่สอง** Manifest `m4` มี Entry เดียวที่ `status = DELETED` ชี้ไปที่ `a1` ลองคลิกดูเหมือนกัน นี่คือวิธีที่ Iceberg "ลบ" ไฟล์ออกจากตาราง มันไม่ได้ลบไฟล์จริง ๆ แค่เขียน Manifest ใหม่ที่บอกว่า Snapshot นี้ไม่ใช้ไฟล์นั้นแล้ว และ**จุดสุดท้าย** Manifest List `s3` ไม่มี `m1` อีกแล้ว เพราะ `m1` ลิสต์แค่ `a1` ที่ถูกแทนไป ส่วน `m2` ซึ่งลิสต์ `a2` ที่ไม่ได้ถูกแตะ ก็ถูกใช้ซ้ำเหมือนเดิม

ที่เหลือก็เป็นขั้นตอนเดิม คือเขียน `v4` แล้วเปลี่ยนตัวชี้ ตอนจบ Snapshot `s3` มี `operation` เป็น `overwrite` เพราะ Commit เดียวมีทั้งไฟล์ที่เพิ่มและไฟล์ที่ลบ ส่วน `s1` กับ `s2` ก็ยังชี้ไปที่ `a1` ได้อยู่

<Callout type="note" title="โหมดของ MERGE">

ตารางนี้ใช้ค่าเริ่มต้นจึงได้ Copy-on-write ถ้าตั้งเป็น Merge-on-read ภาพจะต่างออกไป Spark จะเขียนไฟล์ Delete แทนการเขียน `a3` ทั้งไฟล์ [บท 6](/iceberg/row-level/#เทียบสามโหมดข้างกัน)เทียบสองโหมดนี้ข้างกัน ภาพในหน้านี้รันจริงเฉพาะ Copy-on-write

</Callout>

</Step>

## SELECT ที่มีเงื่อนไข เปิด Data File แค่ไฟล์เดียว

<UnderCoversLab client:visible op="select" />

การอ่านจะเดินลงมาจากบนลงล่างตามลูกศร Catalog บอกว่าตารางชี้ที่ `v4` Metadata File บอกว่า Snapshot ปัจจุบันคือ `s3` และ Manifest List ลิสต์ Manifest ไว้สามไฟล์ จากนั้นก็ถึงขั้นที่ 4 ซึ่งเป็นขั้นที่คุ้มที่สุด เพราะ Spark จะอ่านค่าต่ำสุดและสูงสุดของ `amount` จาก Manifest แล้วเอามาเทียบกับเงื่อนไข `amount > 200` เริ่มจาก `m4` ที่มีแต่ไฟล์ที่ถูกลบ จึงไม่มีอะไรให้ตามไปต่อ ส่วน `a3` มี `amount` สูงสุดแค่ 120 ซึ่งต่ำกว่า 200 ไม่มีแถวไหนในไฟล์นี้ผ่านเงื่อนไขได้เลย ข้ามได้โดยไม่ต้องเปิดไฟล์ แต่ `a2` มี `amount` สูงสุด 300 ไฟล์นี้จึงอาจมีแถวที่เราต้องการ

ผลก็คือจาก Data File ที่ยังใช้อยู่ 2 ไฟล์ Spark เปิดจริงแค่ `a2` ไฟล์เดียว เรายืนยันตัวเลขนี้ด้วย PyIceberg บน Catalog เดียวกัน โดย `scan(row_filter="amount > 200").plan_files()` คืนไฟล์เดียวคือ `a2` ส่วนการสแกนทั้งตารางคืน 2 ไฟล์ ตารางเล็กขนาดนี้ยังไม่เห็นความต่างของเวลาหรอก แต่ถ้าตารางมีเป็นแสนไฟล์ ความต่างระหว่างเปิด 1 ไฟล์กับเปิดทั้งหมดก็คือความต่างระหว่างคำสั่งที่ตอบทันทีกับคำสั่งที่ต้องรอเป็นนาที เรื่องการวางแผนอ่านทั้งหมดอยู่ใน[บท 5](/iceberg/reading/#ตาม-query-หนึ่งคำสั่งลงไปทีละชั้น)

## ย้อนเวลา เดินลงทางเก่าที่ยังอยู่

<UnderCoversLab client:visible op="travel" />

ตารางตอนนี้อยู่ที่ `s3` แต่เราขอ `s1` ตรง ๆ Spark เลยเลือก Snapshot ตามที่ขอ แล้วเดินลงทางเดิม `s1` → `m1` → `a1` ได้ 2 แถวเหมือนตอนหลัง INSERT ครั้งแรก ทั้งที่ตารางตอนนี้มี 5 แถว

จะย้อนเวลาได้ก็เพราะสองข้อที่เราเพิ่งเห็นในหน้านี้ ข้อแรก `v4` ยังเก็บรายการ Snapshot เก่าไว้ครบ ข้อสอง ไฟล์เก่าอย่าง `m1` และ `a1` ยังอยู่บนดิสก์เพราะไม่เคยถูกแก้หรือลบ Snapshot เก่าจึงเป็นแค่รายการไฟล์อีกชุดหนึ่ง วิธีใช้งานจริง ทั้ง Tag, Branch และ Rollback อยู่ใน[บท 8](/iceberg/time-travel/#ทุก-snapshot-คือหนังสือฉบับเก่าที่ยังเปิดได้)

</Step>

## Compaction รวมไฟล์เล็ก ข้อมูลเท่าเดิม แต่ไฟล์เปลี่ยน

<UnderCoversLab client:visible op="compact" />

ตอนนี้ตารางมี Data File ที่ใช้อยู่ 2 ไฟล์ คือ `a2` (2 แถว) กับ `a3` (3 แถว) เมื่อสั่ง `rewrite_data_files` Spark อ่านสองไฟล์นี้ เขียนเป็นไฟล์เดียวคือ `a4` (5 แถว) แล้ว Commit ด้วยวิธีเดิมทุกอย่าง ลองดูขั้น 3 มี Manifest สามไฟล์ `m5` บอกว่า `a4` ถูกเพิ่ม ส่วน `m6` และ `m7` บอกว่า `a3` กับ `a2` ถูกลบ

Snapshot `s4` มี `operation` เป็น `replace` ไม่ใช่ `append` หรือ `overwrite` เพราะข้อมูลในตารางเท่าเดิม (`total-records` ยัง 5) เปลี่ยนแค่ว่าเก็บอยู่ในไฟล์ไหน ผู้อ่านที่ขอ Snapshot ใหม่เปิดแค่ `a4` ไฟล์เดียว

สังเกตขั้น 6 ด้วย `a1` ถึง `a3` ยังอยู่บนดิสก์ ไม่ได้หายไปไหน เพราะ Snapshot เก่ายังชี้หาพวกมันอยู่ และตัวเลขจากแบบฝึกยืนยันว่าไฟล์ทั้งสามยังอยู่จริง ไฟล์พวกนี้จะถูกลบก็ต่อเมื่อเรา Expire Snapshot เก่าทิ้ง ซึ่งเป็นเรื่องที่[บท 10](/iceberg/maintenance/#expire_snapshots-ลบ-snapshot-เก่าและไฟล์ที่มีแต่มันใช้)จะพาเราไปทำ

## สรุปเป็นตัวเลข แต่ละคำสั่งเขียนกี่ไฟล์

ตารางนี้นับจากแบบฝึกเดียวกับที่เราเพิ่งดู (ชื่อย่อตามภาพ)

| คำสั่ง | ไฟล์ที่เขียนใหม่ | ไฟล์เก่าที่ใช้ซ้ำ | Operation ของ Snapshot |
|---|---|---|---|
| `CREATE TABLE` | 1 (`v1`) | - | ไม่มี Snapshot |
| `INSERT` ครั้งแรก | 4 (`a1`, `m1`, `s1`, `v2`) | - | `append` |
| `INSERT` ครั้งที่สอง | 4 (`a2`, `m2`, `s2`, `v3`) | `m1` | `append` |
| `MERGE INTO` | 5 (`a3`, `m3`, `m4`, `s3`, `v4`) | `m2` | `overwrite` |
| `SELECT` | 0 | - | - |
| ย้อนเวลา | 0 | - | - |
| Compaction | 6 (`a4`, `m5`, `m6`, `m7`, `s4`, `v5`) | - | `replace` |

ทุกแถวที่เขียนไฟล์ทำสองอย่างเหมือนกัน คือเขียนไฟล์ใหม่ที่ยังไม่มีใครอ้างถึง แล้วเปลี่ยนตัวชี้ใน Catalog หนึ่งครั้ง ส่วน `SELECT` กับย้อนเวลาไม่เขียนอะไรเลย แค่เดินตามตัวชี้ลงไป และใช้ค่าต่ำสุดสูงสุดใน Manifest ตัดไฟล์ที่ไม่ต้องอ่าน
