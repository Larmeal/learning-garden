## ชื่อประเภทมาจากชื่อคลาส และตั้งเองไม่ได้

ตอนนิยามคลาส `MetaExpectation.__new__` (ใน `expectations/expectation.py`) จะทำสิ่งนี้

```python
newclass.expectation_type = camel_to_snake(clsname)
register_expectation(newclass)
```

เราทดลองใน `13_custom_registry.py` ด้วยการสร้างคลาสหลายชื่อ

| ชื่อคลาส | `expectation_type` |
|---|---|
| `ExpectColumnValuesToBeEven` | `expect_column_values_to_be_even` |
| `ExpectUSZipCodeToBeValid` | `expect_us_zip_code_to_be_valid` |
| `ExpectColumnValuesToBeUTF8` | `expect_column_values_to_be_utf8` |
| `ExpectIDsToBeUnique` | `expect_i_ds_to_be_unique` |

แถวสุดท้ายน่าสังเกต เพราะตัวย่อที่ลงท้ายด้วยตัวพิมพ์เล็กอย่าง `IDs` ถูกตัดเป็น `i_ds` ถ้าตั้งชื่อคลาสแบบนี้ ชื่อประเภทที่เก็บใน Suite ก็จะหน้าตาแปลกไปตลอด

ถ้าลองตั้ง `expectation_type = "my_chosen_name"` ในคลาสดู จะไม่มีผลอะไร เพราะได้ชื่อจากคลาสเหมือนเดิม (`expect_something_else` ในการทดลอง) และ `"my_chosen_name"` ไม่อยู่ใน Registry Docstring ของ `MetaExpectation` เขียนว่าจะใช้ค่าที่ตั้งไว้ถ้ามี แต่โค้ดเขียนทับเสมอ และผลนี้เหมือนกันทั้ง GX 1.9.3 และ 1.24.1

ดังนั้นการเปลี่ยนชื่อคลาสจึงเท่ากับการเปลี่ยนชื่อประเภท และ Suite ที่เก็บชื่อเดิมไว้ก็จะหาคลาสไม่เจอ (ขั้นถัด ๆ ไปจะเล่าให้ฟัง) เราจึงควรตั้งชื่อให้ดีตั้งแต่แรก และอย่าเปลี่ยนทีหลังโดยไม่แก้ Suite ตามไปด้วย

</Step>

## Registry คือ Dict ธรรมดา และชื่อซ้ำจะเขียนทับ

`expectations/registry.py` มีตัวแปรระดับโมดูลชื่อ `_registered_expectations` ซึ่งเป็น Dict จากชื่อประเภทไปหาคลาส โดย `register_expectation` ทำสามอย่างตามกรณี

- ถ้าเป็นชื่อใหม่ ก็ใส่ลง Dict
- ถ้าเป็นชื่อเดิมกับคลาสเดิม ก็ลงบันทึกระดับ Info ว่า `Multiple declarations` แล้วจบ
- ถ้าเป็นชื่อเดิมแต่เป็นคลาสอื่น ก็ลงบันทึกระดับ Warning ว่า `Overwriting declaration of expectation ...` แล้วแทนที่

กรณีสุดท้ายเราทดลองแล้ว โดยนิยามคลาสชื่อ `ExpectColumnValuesToNotBeNull` ของตัวเองใน `__main__` ทั้งที่ GX มีคลาสชื่อเดียวกันอยู่ ผลคือ `registry.get_expectation_impl("expect_column_values_to_not_be_null")` เปลี่ยนไปคืนคลาสของเรา และมีแค่ Warning ใน Log (กับ Warning เรื่อง Renderer อีกหลายบรรทัด) ไม่มี Error

<Callout type="warn" title="ชนชื่อกับของ GX แล้วไม่มีใครบอก">
ทุก Suite ในโปรเซสนั้นที่ใช้ประเภทนี้จะรันคลาสของคุณแทนของ GX โดยไม่รู้ตัว ดังนั้นก่อนตั้งชื่อ ให้ค้นใน Registry ด้วย `registry.list_registered_expectation_implementations()` ว่ามีชื่อนั้นหรือยัง
</Callout>

</Step>

## ในโปรเซสเดียวกัน ประเภทที่ไม่รู้จักล้มดัง ๆ

ลองเพิ่ม Expectation ที่ไม่มีใครเขียนลง Suite ดูก่อน

```python
gx.ExpectationSuite(name="s").add_expectation_configurations(
    [ExpectationConfiguration(type="expect_something_nobody_wrote", kwargs={"column": "x"})]
)
```

จะได้ `InvalidExpectationConfigurationError: Could not add expectation; provided configuration is not valid: expect_something_nobody_wrote not found` ซึ่งที่มาคือ `ExpectationSuite._build_expectation` เรียก `to_domain_obj()` ซึ่งเรียก `get_expectation_impl(type)` ใน Registry แล้ว Raise `ExpectationNotFoundError` ซึ่งถูกห่อเป็น Error ข้างบน

ตรงนี้ยังปลอดภัย เพราะคุณเห็นข้อผิดพลาดทันที ส่วนปัญหาจริงอยู่ที่อีกทางหนึ่งซึ่งใช้กลไกเดียวกัน

</Step>

## ตอนโหลด Suite จากไฟล์ Error ถูกกลืน

Suite ใน File Context เก็บเป็น JSON ที่อ้างด้วยชื่อประเภทเท่านั้น โดยไม่มีโค้ดหรือชื่อโมดูล ซึ่งผลจริงของ Suite ในการทดลอง (`gx/expectations/even.json`)

```json
[
  {
    "id": "df2210d5-9b56-4dbd-9edf-adfaa8e23445",
    "kwargs": { "column": "n" },
    "meta": {},
    "severity": "critical",
    "type": "expect_column_values_to_be_even"
  }
]
```

ตอนโหลด `ExpectationSuite.__init__` (ใน `core/expectation_suite.py`) วนสร้าง Expectation จากแต่ละรายการ

```python
for exp in expectations or []:
    try:
        self.expectations.append(self._process_expectation(exp))
    except gx_exceptions.InvalidExpectationConfigurationError as e:
        logger.exception(f"Could not add expectation; provided configuration is not valid: {e.message}")
```

ถ้าหาคลาสไม่เจอ มันจะจับ Error ไว้ ลงบันทึกระดับ ERROR แล้วไปรายการถัดไป รายการนั้นจึงหายจาก Suite โดยไม่มีอะไรถูกส่งต่อให้โค้ดของคุณ นี่คือกลไกของกับดักที่ใหญ่ที่สุดของบทนี้

</Step>

## ผลที่เห็นจากสองโปรเซส

`13_custom_registry.py` เปิดโปรเซสแรกเพื่อบันทึก Suite หนึ่ง Expectation แล้วเปิดโปรเซสที่สองโหลดมันขึ้นมารันกับข้อมูลเลขคี่ล้วน (`[1, 3, 5]` ซึ่งควรล้ม)

| โปรเซสที่สอง | Expectation ใน JSON | โหลดมาได้ | ผล |
|---|---|---|---|
| ไม่ Import โมดูลของคุณ | 1 | 0 | `success=True`, `evaluated_expectations=0` |
| Import โมดูลก่อน `get_context()` | 1 | 1 | `success=False`, `evaluated_expectations=1` |

กรณีแรก Log มีบรรทัด `ERROR great_expectations.core.expectation_suite: Could not add expectation; provided configuration is not valid: ... expect_column_values_to_be_even not found` ในการทดลองเห็นสามบรรทัดต่อการโหลดหนึ่งครั้ง (ไม่ได้ตรวจว่าทำไมซ้ำ) ถ้าโปรเซสของคุณไม่ได้เก็บ Log ระดับ ERROR ของ GX ไว้ดู ก็จะไม่มีร่องรอยเลย และผลลัพธ์ `success=True` จะดูเหมือนข้อมูลดีทั้งที่ไม่ได้ตรวจอะไรสักข้อ

[บทที่ 10](/great-expectations/pipeline-integration/#quality-gate-ที่แยกสาเหตุได้) (Pipeline) พูดถึงการตรวจผลนี้จากฝั่ง Gate ส่วนหน้านี้ดูฝั่งต้นเหตุ

</Step>

## สามวิธีกัน เรียงจากต้นเหตุไปปลายเหตุ

1. Import ให้ถึงก่อนโหลด โดยใส่ Custom Expectation ทั้งหมดไว้ในแพ็กเกจเดียว (เช่น `my_project.expectations`) แล้ว Import มันที่จุดเริ่มของทุกโปรแกรมที่แตะ GX ก่อนเรียก `gx.get_context()` ผลทดลองคือ Import ก่อนโหลดแล้วได้ 1 Expectation ตามที่ควร ส่วนที่ที่ลืมง่ายคือโปรเซสที่ไม่ใช่โปรแกรมหลัก เช่น Worker ของ Scheduler หรือ Kernel ของ Notebook ที่เปิดแยก
2. ตรวจจำนวนหลังโหลด โดยเทียบจำนวนใน JSON กับจำนวนที่โหลดได้ ซึ่ง `14_custom_testing.py` ทำเป็นตัวตรวจที่รันใน CI ได้ ผลกับ Suite ที่มี Custom หนึ่งข้อกับ Built-in หนึ่งข้อคือ `suite mixed: 2 on disk, 1 loaded -> MISSING CLASSES`
3. ตรวจผลที่ Gate โดยอ่าน `result.statistics["evaluated_expectations"]` แล้วปฏิเสธผลที่เป็น 0 หรือน้อยกว่าจำนวนที่ควรมี ข้อนี้จับได้เฉพาะตอนรันจริง

ข้อ 1 กันที่ต้นเหตุ ส่วนข้อ 2 และ 3 รองรับตอนมีคนลืม การใช้ครบทั้งสามข้อจึงดีที่สุด เพราะแต่ละข้อจับความผิดพลาดคนละช่วงเวลา

</Step>
