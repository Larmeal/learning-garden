## เริ่มจากถามว่ากฎของคุณตัดสินจากอะไร

ก่อนเขียนโค้ด ลองถามตัวเองข้อเดียวว่ากฎนี้ดูอะไรเพื่อตัดสินว่าข้อมูลผ่านหรือไม่ คำตอบนี้จะบอกเราว่าควรเลือกคลาสแม่ตัวไหน ซึ่งคลาสแม่คือส่วนที่ GX เขียนไว้ให้แล้วเกือบทั้งหมด

| กฎตัดสินจาก | คลาสแม่ | ตัวอย่างที่ GX มีให้ | ตัวอย่างกฎที่อาจต้องเขียนเอง |
|---|---|---|---|
| ค่าในแต่ละแถวของคอลัมน์เดียว | `ColumnMapExpectation` | `ExpectColumnValuesToMatchRegex` | ค่าต้องเป็นเลขคู่ |
| ค่าสองคอลัมน์ในแถวเดียวกัน | `ColumnPairMapExpectation` | `ExpectColumnPairValuesAToBeGreaterThanB` | ส่วนลดต้องไม่เกินครึ่งของราคา |
| ค่าหลายคอลัมน์ในแถวเดียวกัน | `MulticolumnMapExpectation` | `ExpectMulticolumnSumToEqual` | ช่องทางชำระเงินต้องมีค่าเพียงช่องเดียว |
| ตัวเลขสรุปหนึ่งค่าของคอลัมน์ | `ColumnAggregateExpectation` | `ExpectColumnMaxToBeBetween` | ช่วงห่างระหว่างค่ามากสุดกับน้อยสุดต้องแคบ |
| ตัวเลขสรุปหนึ่งค่าของทั้งตาราง | `BatchExpectation` | `ExpectTableRowCountToEqual` | (บทนี้ไม่ได้ทดลองคลาสนี้) |
| ผลของ SQL ที่ต้องไม่มีแถวเลย | `UnexpectedRowsExpectation` | ใช้ตรง ๆ ไม่ต้องเขียนคลาส | ยอดต้องไม่ติดลบเมื่อเทียบกับตารางอื่น |

คลาสทั้งหมดอยู่ใน `expectations/expectation.py` ของ GX และสืบทอดกันเป็นชั้น (`ColumnMapExpectation` สืบจาก `BatchExpectation` ที่สืบจาก `Expectation`) สามแถวแรกของตาราง (Column Map, Pair, Multicolumn) เป็นกลุ่ม "Map" ซึ่งบอกได้ว่าแถวไหนผิด ส่วน Aggregate กับ Batch จะให้ค่าสรุปได้ค่าเดียว

## ตัวอย่างที่สั้นที่สุดที่ใช้งานได้

กฎ "ค่าในคอลัมน์ `n` ต้องเป็นเลขคู่" เราเขียนได้เป็นสองคลาส

```python
class ColumnValuesAreEven(ColumnMapMetricProvider):
    condition_metric_name = "column_values.are_even"

    @column_condition_partial(engine=PandasExecutionEngine)
    def _pandas(cls, column, **kwargs):
        return column % 2 == 0

    @column_condition_partial(engine=SqlAlchemyExecutionEngine)
    def _sqlalchemy(cls, column, **kwargs):
        return column % 2 == 0


class ExpectColumnValuesToBeEven(ColumnMapExpectation):
    map_metric = "column_values.are_even"
    args_keys = ("column",)
```

คลาสแรกตอบคำถามว่า "ค่านี้ปกติไหม" ทีละแถว ส่วนคลาสที่สองบอกแค่ว่าใช้ Metric ตัวไหน แล้วเราก็ใช้งานได้เหมือน Expectation ที่ GX ให้มา

```python
suite.add_expectation(ExpectColumnValuesToBeEven(column="n"))
suite.add_expectation(ExpectColumnValuesToBeEven(column="n", mostly=0.6))
```

## เขียนแค่นี้ แล้วได้อะไรกลับมา

ลองใช้ข้อมูล `[2, 4, 6, 7, 10, 11]` (ทดลองแล้วใน `07_custom_expectation.py`)

| ตรวจกับ | ผล |
|---|---|
| Pandas | `success=False`, `unexpected_count=2`, ค่าที่ผิด `[7, 11]` |
| Pandas, `mostly=0.6` | `success=True` (ถูก 4 จาก 6 ได้ 0.667 ซึ่งไม่ต่ำกว่า 0.6) |
| SQLite (ตาราง `numbers`) | `success=False`, `unexpected_count=2` |

เราไม่ได้เขียนโค้ดนับแถวที่ผิด คำนวณ `mostly` เก็บค่าที่ผิด หรือจัดรูปผลตาม `result_format` เลย เพราะ `ColumnMapExpectation` ทำให้หมด และ SQLite ก็รันได้ด้วยคลาสเดิม เพราะเรามีเงื่อนไขของ `SqlAlchemyExecutionEngine` เขียนไว้อยู่แล้ว

ชื่อประเภทที่เก็บใน Suite คือ `expect_column_values_to_be_even` ซึ่ง GX แปลงมาจากชื่อคลาสเอง เราจึงตั้งชื่ออย่างอื่นไม่ได้ (หน้า "[วงจรชีวิต](/great-expectations/custom-expectations/registry-loading/)" มีรายละเอียด)

</Step>

## สามอย่างที่เกิดตอนคลาสถูกนิยาม

ในโค้ดข้างบนไม่มีบรรทัด `register(...)` เลย แต่เมื่อ Python อ่านถึงคำว่า `class` สามอย่างนี้ก็เกิดขึ้นแล้ว (ทดลองใน `11_custom_column_map.py`)

1. อย่างแรกคือการลงทะเบียน Expectation โดย `MetaExpectation.__new__` จะตั้ง `expectation_type` จากชื่อคลาส แล้วใส่คลาสลง Dict ชื่อ `_registered_expectations` ในไฟล์ `expectations/registry.py` ส่วนคลาสที่ไม่มี `map_metric` ถือเป็นคลาสนามธรรมและไม่ถูกลงทะเบียน
2. อย่างที่สองคือการลงทะเบียน Metric โดยเมธอดที่ติด `@column_condition_partial` จะถูกลงทะเบียนแยกตาม Engine และ GX สร้าง Metric ที่เหลือให้ด้วย (`.unexpected_count`, `.unexpected_values`, `.unexpected_index_list` และอื่น ๆ) รวมแปดชื่อใต้ `column_values.are_even`
3. อย่างที่สามคือคลาสกลายเป็นโมเดลที่ตรวจ Argument เพราะ Expectation เป็น Pydantic Model ถ้าพิมพ์ `colum="n"` ผิดตัวเดียวก็ได้ `ValidationError` ทันที (ทั้ง `field required` และ `extra fields not permitted`) ส่วน `mostly=1.5` ไม่ผ่านเพราะ `MostlyField` จำกัดไม่เกิน 1.0 และ `severity="loud"` ก็ไม่ผ่านเช่นกัน

ทั้งสามอย่างเกิดตอน Import ไฟล์ที่นิยามคลาส ดังนั้นคลาสที่ยังไม่ถูก Import จึงไม่มีตัวตนสำหรับ GX เลย ซึ่งเป็นต้นเหตุของกับดักใหญ่ที่สุดของบทนี้ โดยหน้า "[วงจรชีวิต](/great-expectations/custom-expectations/registry-loading/)" จะไล่ให้ดูทีละขั้น

</Step>

## เส้นทางอ่านต่อ และกับดักที่รออยู่

หน้าย่อยของบทนี้เรียงตามลำดับที่ควรอ่าน

1. ลองของที่มีก่อน ดู `mostly`, `row_condition`, `severity` และวิธีค้นหา Expectation ที่มีอยู่ เพื่อไม่ต้องเขียนเกินจำเป็น
2. Column Map ลงลึก ดูสิ่งที่เงื่อนไขของคุณได้รับจริง, Metric ทั้งแปดตัว, SQL ที่ GX สร้าง, ตารางว่าง, Null และ `filter_column_isnull`
3. Expectation แบบอื่น ได้แก่ Aggregate, Pair, Multicolumn และ `UnexpectedRowsExpectation` พร้อมตัวอย่างที่รันได้ทุกแบบ
4. วงจรชีวิต ดูว่าชื่อประเภทมาจากไหน, Registry ทำงานอย่างไร, Suite ที่เก็บไว้หาคลาสของคุณเจออย่างไร และทำไมถึงโหลดมาว่างได้
5. ทดสอบและปล่อยใช้ มีตารางกรณีทดสอบ, `run_diagnostics`, ตัวตรวจใน CI และเรื่องการอัปเกรด

<Callout type="warn" title="กับดักสี่ข้อที่ทดลองเจอจริง">
1. ถ้าโปรเซสที่โหลด Suite ไม่ได้ Import คลาส Suite จะว่างเปล่าและ `run()` ได้ `success=True`
2. เงื่อนไขเดียวกันให้ความหมายต่างกันเมื่อเปลี่ยน Engine เช่นคอลัมน์ข้อความ `"a" % 2 == 0` ล้มบน Pandas แต่ผ่านเงียบ ๆ บน SQLite
3. ตั้ง `filter_column_isnull = False` แล้วข้อมูลมี Null ทำให้ GX สร้างผลไม่ได้
4. คลาสที่ชื่อซ้ำกับ Expectation ที่มีอยู่ จะแทนที่ตัวเดิมใน Registry โดยมีแค่ Warning
</Callout>
