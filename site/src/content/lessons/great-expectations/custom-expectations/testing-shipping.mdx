## เงื่อนไขเดียวกัน ผลต่างกันตาม Engine

ใน `14_custom_testing.py` เราเอา `ExpectColumnValuesToBeEven` (เงื่อนไข `column % 2 == 0` ที่เขียนไว้ทั้ง Pandas และ SQLAlchemy) ไปรันกับข้อมูลห้าแบบ แล้วเปรียบเทียบสองฝั่ง

| ข้อมูล | Pandas | SQLite |
|---|---|---|
| `[2, 4, 6]` | ผ่าน | ผ่าน |
| `[2, 4, 6, 7, 11]` | ล้ม, ผิด 2 | ล้ม, ผิด 2 |
| ตารางว่าง | ผ่าน (`unexpected=0`) | ผ่าน (`unexpected=None`) |
| Null ล้วน | ผ่าน | ผ่าน |
| ข้อความ `"a"`, `"bb"`, `"c"` | Error: `not all arguments converted during string formatting` | ผ่าน (`unexpected=0`) |

สามแถวแรกตรงกับที่คาดไว้ ส่วนสองแถวท้ายมีสิ่งที่ต้องรู้

ตารางว่างบน SQLite ให้ `unexpected_count` เป็น `None` ไม่ใช่ `0` แต่ผลสุดท้ายก็ยังผ่าน เพราะ `_validate` ถือว่า `None` คือ "ไม่มีอะไรให้ตัดสิน" ถ้าโค้ดของคุณอ่าน `unexpected_count` ไปทำต่อ (เช่นเอาไปหารหรือเทียบ) ก็ต้องรับกรณี `None` ด้วย

คอลัมน์ข้อความแสดงให้เห็นว่าเงื่อนไข `%` ไม่ได้มีความหมายเดียวกันทุกที่ ใน Python `"a" % 2` คือการจัดรูปสตริง จึงเกิด `TypeError` และผลของ Expectation ล้มพร้อม `result` ว่าง ส่วนใน SQLite `'a' % 2` ได้ `0` (SQLite อ่านตัวเลขนำหน้าของข้อความ ถ้าไม่มีก็เป็น 0 ซึ่งทดลองแล้วว่า `'7x' % 2` ได้ `1`) ซึ่งเป็นเลขคู่ จึงผ่านโดยไม่มีสัญญาณเตือน

<Callout type="warn" title="ข้อมูลผิดชนิดอาจผ่านเงียบ ๆ">
ถ้าคอลัมน์ที่ควรเป็นตัวเลขกลายเป็นข้อความ (ไฟล์ CSV อ่านผิด, ฟิลด์ที่ผสมชนิด) Expectation แบบ `%` ตัวนี้จะผ่านบน SQL ดังนั้นให้ใส่ `ExpectColumnValuesToBeOfType` หรือ `ExpectColumnValuesToBeInTypeList` ไว้ใน Suite เดียวกัน เพื่อให้ชนิดที่ผิดล้มด้วยตัวของมันเอง
</Callout>

## ชุดข้อมูลทดสอบขั้นต่ำ

จากตารางข้างบน กรณีที่คุ้มกับการเขียนไว้ทุกครั้งเมื่อเราเขียน Expectation แบบ Map ใหม่ มีดังนี้

| กรณี | สิ่งที่ตรวจ |
|---|---|
| ข้อมูลปกติทั้งหมด | `success=True` และ `unexpected_count=0` |
| ผิดบางแถว | จำนวนที่ผิดและค่าที่ผิดตรงกับที่นับเอง |
| ผิดบางแถวพร้อม `mostly` ที่ขอบเขต | `mostly` เท่ากับสัดส่วนที่ถูกพอดี ผ่านหรือไม่ผ่านตามสูตร `(considered - unexpected) / considered >= mostly` |
| ตารางว่าง | ผ่านแบบ Vacuous ตามที่ตั้งใจหรือไม่ |
| Null ล้วน | เหมือนข้างบน และ `missing_count` ถูก |
| Null ปนกับค่า | ค่าที่เห็นในเงื่อนไขเป็น Float หรือไม่ (ดูหน้า Column Map) |
| ชนิดผิด | แต่ละ Engine ทำอะไร ล้ม ผ่าน หรือได้คำตอบแปลก |

ให้ทดสอบแต่ละกรณีบนทุก Engine ที่คลาสรองรับ เพราะถ้าทดสอบแค่บน Pandas เราจะไม่เห็นว่ากรณีข้อความผ่านเงียบ ๆ บน SQLite

</Step>

## เครื่องมือที่ GX มีให้: `examples` กับ `run_diagnostics`

คลาส Expectation มีแอตทริบิวต์ `examples` ไว้ให้ใส่กรณีทดสอบ แล้วเรียก `run_diagnostics()` ได้

```python
class ExpectColumnValuesToBeEven(ColumnMapExpectation):
    map_metric = "column_values.are_even"
    args_keys = ("column",)

    examples = [{
        "data": {"n": [2, 4, 7]},
        "tests": [
            {"title": "one odd value", "exact_match_out": False, "include_in_gallery": True,
             "in": {"column": "n"}, "out": {"success": False}},
            {"title": "mostly lets it pass", "exact_match_out": False, "include_in_gallery": True,
             "in": {"column": "n", "mostly": 0.6}, "out": {"success": True}},
        ],
    }]
```

ผลที่ทดลองคือ GX รันสองกรณีนี้บน Pandas และบน SQLite (รวมสี่การทดสอบ ผ่านทั้งหมด) โดยเราไม่ต้องเขียนโค้ดสร้างฐานข้อมูลเอง `backend_test_result_counts` ได้ `[('pandas', 2, 0), ('sqlite', 2, 0)]`

`print_diagnostic_checklist()` จะพิมพ์รายการ "ความสมบูรณ์" ของคลาสออกมา ในการทดลองมันติ๊กถูกข้อ "มี Core Logic และผ่านการทดสอบบน Execution Engine อย่างน้อยหนึ่งตัว" และข้อ "มี Renderer ทั้งแบบ Prescriptive และ Diagnostic" แต่ไม่ติ๊กข้อที่ขาด เช่น `library_metadata`, Docstring ที่ขึ้นต้นด้วย "Expect" และ `validate_configuration` ข้อที่ไม่ติ๊กเป็นเกณฑ์ของการส่งเข้า Gallery สาธารณะของ GX ถ้าใช้ภายในทีม คุณก็ไม่จำเป็นต้องทำให้ครบ

ข้อควรรู้ตอนใช้คือ `run_diagnostics()` จะพยายามต่อ Backend อื่นด้วย (Mysql, Bigquery, Snowflake และอื่น ๆ) แล้วพิมพ์ข้อความว่าต่อไม่ได้ออกมาหลายบรรทัด ซึ่งไม่ใช่ความผิดพลาดของคลาสคุณ

</Step>

## ตัวตรวจใน CI: คลาสหายจาก Suite หรือไม่

กับดักใหญ่ของบทนี้ (หน้า "[วงจรชีวิต](/great-expectations/custom-expectations/registry-loading/)") เราตรวจได้ด้วยสคริปต์สั้น ๆ ที่รันในโปรเซสใหม่ ซึ่งนำเข้าเฉพาะสิ่งที่โปรแกรมจริงนำเข้า

```python
import json, pathlib, sys
import great_expectations as gx

context = gx.get_context(mode="file", project_root_dir=sys.argv[1])
for path in sorted((pathlib.Path(sys.argv[1]) / "gx" / "expectations").glob("*.json")):
    on_disk = len(json.loads(path.read_text())["expectations"])
    loaded = len(context.suites.get(path.stem).expectations)
    print(f"suite {path.stem}: {on_disk} on disk, {loaded} loaded ->", "ok" if on_disk == loaded else "MISSING CLASSES")
```

ผลกับ Suite ที่มี Custom หนึ่งข้อกับ `ExpectColumnValuesToNotBeNull` หนึ่งข้อ ในโปรเซสที่ไม่ได้ Import โมดูลของ Custom: `suite mixed: 2 on disk, 1 loaded -> MISSING CLASSES` ถ้าให้สคริปต์จบด้วย Exit Code ที่ไม่เป็นศูนย์เมื่อเจอ `MISSING CLASSES` CI ก็จะล้มก่อนที่ Pipeline จริงจะรัน

ที่สำคัญคือสคริปต์นี้ต้อง Import เหมือนกับโปรแกรมจริง ถ้าคุณใส่ `import my_project.expectations` ไว้ในสคริปต์ตรวจเอง มันจะผ่านเสมอและไม่ได้ตรวจอะไรเลย

</Step>

## เมื่ออัปเกรด GX

Custom Expectation เรียกใช้ของภายในของ GX หลายอย่าง โดยห้ากลุ่มที่คลาสในบทนี้นำเข้ามีดังนี้

- `ColumnMapExpectation`, `ColumnAggregateExpectation`, `ColumnPairMapExpectation`, `MulticolumnMapExpectation` จาก `great_expectations.expectations.expectation`
- `ColumnMapMetricProvider`, `ColumnAggregateMetricProvider` จาก `great_expectations.expectations.metrics`
- `column_condition_partial`, `column_aggregate_value`, `column_aggregate_partial` จากที่เดียวกัน
- `ColumnPairMapMetricProvider`, `MulticolumnMapMetricProvider`, `column_pair_condition_partial`, `multicolumn_condition_partial` จาก `great_expectations.expectations.metrics.map_metric_provider`
- `ExecutionEngine` ของแต่ละ Backend จาก `great_expectations.execution_engine`

ถ้าชื่อใดย้ายหรือหายไป คุณจะเห็นทันทีเป็น `ImportError` ตอน Import ซึ่งเป็นสัญญาณที่ดี ส่วนที่เปลี่ยนเงียบ ๆ (พฤติกรรมของ Null, รูปผลลัพธ์) ต้องใช้ชุดทดสอบจากหน้าก่อนหน้าจับ

สิ่งที่ทดลองจริงคือสคริปต์ `07`, `11`, `12` และ `13` รันได้ทั้งบน GX 1.9.3 และ 1.24.1 ด้วยโค้ดชุดเดียวกัน ผลต่างที่เจอคือชนิดตัวเลขในผล Pair กับ Multicolumn (`np.int64` กับ `int`), และข้อความ Error ของ `filter_column_isnull = False` ส่วนวิธีรันบนอีกรุ่นโดยไม่แตะ `.venv` เป็นดังนี้

```bash
uv run --isolated --no-project --python 3.12 \
  --with "great-expectations==1.9.3" --with "sqlalchemy>=2" python 12_custom_kinds.py
```

สองรุ่นเป็นข้อมูลน้อยเกินกว่าจะสรุปว่ารุ่นถัดไปจะเหมือนกัน แต่คำสั่งนี้ใช้ซ้ำได้ทุกครั้งที่จะอัปเกรด โดยให้รันชุดทดสอบกับรุ่นใหม่ก่อนเปลี่ยน Pin ใน `pyproject.toml`

<Callout type="tip" title="รายการตรวจก่อนปล่อยใช้">
1. ชื่อคลาสสะกดถูกและไม่ซ้ำกับของ GX (ค้นใน Registry)
2. มีเงื่อนไขครบทุก Engine ที่ Pipeline ใช้จริง และรันกับ Backend จริงแล้ว
3. ทดสอบข้อมูลห้าแบบ รวมตารางว่าง Null ล้วน และชนิดผิด
4. พารามิเตอร์ที่ Metric อ่านอยู่ใน `success_keys` ของ Expectation
5. โมดูลของ Custom ถูก Import ที่จุดเริ่มของทุกโปรแกรมที่โหลด Suite
6. CI มีตัวตรวจจำนวน Expectation ในโปรเซสใหม่
7. Gate ของ Pipeline ปฏิเสธ `evaluated_expectations == 0`
8. Version ของ GX ถูก Pin และมีขั้นตอนรันชุดทดสอบก่อนอัปเกรด
</Callout>

</Step>
