## สองชั้นของการรัน

| ชั้น | หน้าที่ | ผลที่ได้ |
|---|---|---|
| Validation Definition | ตรวจข้อมูลหนึ่งก้อนด้วย suite หนึ่งชุด | `ExpectationSuiteValidationResult` |
| Checkpoint | รัน validation definition หลายตัวด้วยพารามิเตอร์ร่วมกัน แล้วสั่ง action | `CheckpointResult` |

validation definition เหมาะกับการทดลองและตรวจครั้งเดียว checkpoint คือทางหลักใน production เพราะผูก action และรวมหลายการตรวจเป็นงานเดียว

```python
vd = context.validation_definitions.add(
    gx.ValidationDefinition(name="users_vd", data=batch_definition, suite=suite)
)
checkpoint = context.checkpoints.add(
    gx.Checkpoint(name="users_daily", validation_definitions=[vd])
)
result = checkpoint.run(batch_parameters={"dataframe": df})
```

</Step>

## ตาม Checkpoint.run() ไปทีละขั้น

<RunFlow client:visible />

GX ไม่แตะข้อมูลจนถึงขั้นที่ 3 และผลถูกเก็บก่อนที่ action จะเริ่ม สองข้อนี้ตอบได้ว่าถ้าล้มกลางทางจะเสียอะไร

</Step>

## CheckpointResult

```python
result = checkpoint.run(batch_parameters={"dataframe": df})
result.success            # True เมื่อทุก validation ผ่าน
result.run_results        # dict: ValidationResultIdentifier -> ExpectationSuiteValidationResult
result.describe()         # สรุปเป็น JSON
```

`run_results` มีหนึ่งรายการต่อ validation definition คีย์ประกอบด้วยชื่อ suite, `run_id` และ batch id ทุก validation ใน checkpoint ได้ `run_id` เดียวกัน จึงรู้ว่าเป็นรอบรันเดียวกัน

พารามิเตอร์ `batch_parameters` และ `expectation_parameters` ที่ส่งให้ `run()` ถูกส่งให้ทุก validation definition เหมือนกัน ส่วน `result_format` เป็นฟิลด์ของ `Checkpoint` เอง ถ้า validation definition สองตัวใช้ batch definition คนละแบบ (ตัวหนึ่งรายวัน อีกตัวทั้งตาราง) พารามิเตอร์ชุดเดียวต้องเข้ากันได้กับทั้งคู่

</Step>

## กับดัก: ไม่ raise เมื่อข้อมูลไม่ผ่าน

```python
result = checkpoint.run(batch_parameters={"dataframe": bad_df})
# ไม่มี exception, result.success == False
```

ทดลองแล้วใน `03_traps.py`: checkpoint คืนผลที่ `success=False` ตามปกติโดยไม่ raise GX ถือว่าข้อมูลไม่ผ่านเป็นผลการตรวจ ผลข้างเคียงคือ pipeline ที่เรียก `checkpoint.run(...)` แล้วไม่ตรวจ `.success` จะเดินต่อไปเสมอ (บทที่ 10 ว่าด้วยวิธีกั้น)

<Callout type="warn" title="สิ่งที่ทำให้ raise">
ข้อมูลไม่ผ่านไม่ทำให้ raise แต่สิ่งเหล่านี้ทำ: ไม่มี validation definition ใน checkpoint, ของที่ถูกอ้างถึงยังไม่ได้ add เข้า context, batch ที่ขอไม่มี (`NoAvailableBatchesError`) และ action ที่ error (บทที่ 9)
</Callout>

</Step>

<Step>

## เช็กตัวเอง

- checkpoint มี validation definition สองตัว ตัวแรกไม่ผ่าน ตัวที่สองผ่าน `result.success` เป็นอะไร และ validation ตัวที่สองยังถูกรันไหม (หน้า "หลาย validation ใน checkpoint เดียว" มีเฉลย)
- ทำไม validation definition ถึงต้องถูก add เข้า context ก่อนใส่ใน checkpoint
- ข้อมูลของวันนี้เสีย แต่โค้ดไม่ล้ม สาเหตุที่น่าจะเป็นคืออะไร

</Step>

<Step>

## หน้าย่อยของบทนี้

1. หลาย validation ใน checkpoint เดียว: ผลรวม ตัวที่ล้มไม่หยุดตัวอื่น และพารามิเตอร์ชุดเดียว
2. อ่าน CheckpointResult: describe() กับ run_results และฟังก์ชันดึงข้อที่ล้ม
3. validation definition หรือ checkpoint ใช้อะไรดี: ความต่างที่วัดได้

</Step>
