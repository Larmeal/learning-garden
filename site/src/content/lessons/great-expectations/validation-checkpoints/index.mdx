## สองชั้นของการรัน

| ชั้น | หน้าที่ | ผลที่ได้ |
|---|---|---|
| Validation Definition | ตรวจข้อมูลหนึ่งก้อนด้วย Suite หนึ่งชุด | `ExpectationSuiteValidationResult` |
| Checkpoint | รัน Validation Definition หลายตัวด้วยพารามิเตอร์ร่วมกัน แล้วสั่ง Action | `CheckpointResult` |

Validation Definition เหมาะกับการทดลองและการตรวจครั้งเดียว ส่วน Checkpoint เป็นทางหลักที่ใช้ใน Production เพราะผูก Action ได้ และรวมการตรวจหลายอันให้เป็นงานเดียว

```python
vd = context.validation_definitions.add(
    gx.ValidationDefinition(name="users_vd", data=batch_definition, suite=suite)
)
checkpoint = context.checkpoints.add(
    gx.Checkpoint(name="users_daily", validation_definitions=[vd])
)
result = checkpoint.run(batch_parameters={"dataframe": df})
```

</Step>

## ตาม Checkpoint.run() ไปทีละขั้น

<RunFlow client:visible />

จะเห็นว่า GX ไม่แตะข้อมูลเลยจนถึงขั้นที่ 3 และผลจะถูกเก็บก่อนที่ Action จะเริ่ม สองข้อนี้ช่วยตอบได้ว่าถ้าล้มกลางทาง เราจะเสียอะไรไปบ้าง

## CheckpointResult

```python
result = checkpoint.run(batch_parameters={"dataframe": df})
result.success            # True เมื่อทุก validation ผ่าน
result.run_results        # dict: ValidationResultIdentifier -> ExpectationSuiteValidationResult
result.describe()         # สรุปเป็น JSON
```

`run_results` มีหนึ่งรายการต่อหนึ่ง Validation Definition โดยคีย์ประกอบด้วยชื่อ Suite, `run_id` และ Batch id ซึ่งทุก Validation ใน Checkpoint จะได้ `run_id` เดียวกัน เราจึงรู้ได้ว่าเป็นรอบรันเดียวกัน

พารามิเตอร์ `batch_parameters` และ `expectation_parameters` ที่ส่งให้ `run()` จะถูกส่งต่อให้ทุก Validation Definition เหมือนกัน ส่วน `result_format` เป็นฟิลด์ของ `Checkpoint` เอง ดังนั้นถ้า Validation Definition สองตัวใช้ Batch Definition คนละแบบ (ตัวหนึ่งรายวัน อีกตัวทั้งตาราง) พารามิเตอร์ชุดเดียวที่ส่งไปก็ต้องเข้ากันได้กับทั้งคู่

</Step>

## กับดัก: ไม่ Raise เมื่อข้อมูลไม่ผ่าน

```python
result = checkpoint.run(batch_parameters={"dataframe": bad_df})
# ไม่มี exception, result.success == False
```

เราทดลองแล้วใน `03_traps.py` พบว่า Checkpoint จะคืนผลที่ `success=False` ตามปกติโดยไม่ Raise เพราะ GX ถือว่าข้อมูลไม่ผ่านเป็นผลการตรวจอย่างหนึ่ง ผลข้างเคียงคือ Pipeline ที่เรียก `checkpoint.run(...)` แล้วไม่ตรวจ `.success` จะเดินต่อไปเสมอ ([บทที่ 10](/great-expectations/pipeline-integration/#checkpoint-ไม่ใช่-gate) ว่าด้วยวิธีกั้น)

<Callout type="warn" title="สิ่งที่ทำให้ Raise">
ข้อมูลที่ไม่ผ่านไม่ได้ทำให้ Raise แต่สิ่งเหล่านี้ทำให้ Raise ได้ คือไม่มี Validation Definition ใน Checkpoint, ของที่ถูกอ้างถึงยังไม่ได้ Add เข้า Context, Batch ที่ขอไม่มีอยู่ (`NoAvailableBatchesError`) และ Action ที่ Error ([บทที่ 9](/great-expectations/actions-data-docs/#ลำดับและเงื่อนไข))
</Callout>

</Step>

## เช็กตัวเอง

- Checkpoint มี Validation Definition สองตัว ตัวแรกไม่ผ่าน ตัวที่สองผ่าน `result.success` เป็นอะไร และ Validation ตัวที่สองยังถูกรันไหม (หน้า "[Multiple Validations](/great-expectations/validation-checkpoints/multi-validation/)" มีเฉลย)
- ทำไม Validation Definition ถึงต้องถูก Add เข้า Context ก่อนใส่ใน Checkpoint
- ข้อมูลของวันนี้เสีย แต่โค้ดไม่ล้ม สาเหตุที่น่าจะเป็นคืออะไร

</Step>

<Step>

## หน้าย่อยของบทนี้

1. หลาย Validation ใน Checkpoint เดียว ซึ่งดูผลรวม ตัวที่ล้มแล้วไม่หยุดตัวอื่น และพารามิเตอร์ชุดเดียว
2. อ่าน CheckpointResult ซึ่งดู describe() กับ run_results และฟังก์ชันดึงข้อที่ล้ม
3. Validation Definition หรือ Checkpoint ใช้อะไรดี โดยดูความต่างที่วัดได้

</Step>
