## ตารางตัวอย่างกับกฎแปดข้อ

ตาราง `people` มีห้าแถวและสี่คอลัมน์ โดยข้อมูลชุดแรกเป็นชุดที่สะอาด

```text
id  age  email      country
1   31   a@x.com    TH
2   24   b@x.com    TH
3   45   c@x.com    JP
4   52   d@x.com    SG
5   38   e@x.com    TH
```

ส่วนกฎที่เราเขียนไว้ใน Suite เดียวมีดังนี้

| กฎ | Expectation |
|---|---|
| id ไม่ว่าง | `ExpectColumnValuesToNotBeNull(column="id")` |
| id ไม่ซ้ำ | `ExpectColumnValuesToBeUnique(column="id")` |
| Age ไม่ว่าง | `ExpectColumnValuesToNotBeNull(column="age")` |
| Age อยู่ใน 0 ถึง 120 | `ExpectColumnValuesToBeBetween(column="age", min_value=0, max_value=120)` |
| Email มีรูปแบบอีเมล | `ExpectColumnValuesToMatchRegex(column="email", regex=...)` |
| Country อยู่ในชุดที่รู้จัก | `ExpectColumnValuesToBeInSet(column="country", value_set=["TH", "JP", "SG"])` |
| คอลัมน์ตรงกับที่กำหนดทุกตัว | `ExpectTableColumnsToMatchSet(column_set=[...], exact_match=True)` |
| มีแถว 1 ถึง 1000 แถว | `ExpectTableRowCountToBeBetween(min_value=1, max_value=1000)` |

</Step>

## อ่านผลให้ถูกที่

กรณีเปลี่ยนชื่อคอลัมน์มีข้อสังเกตอยู่สามข้อ

1. สาเหตุเดียว คือคอลัมน์ `age` หายไป ก็ทำให้ล้มถึงสามข้อ เวลาอ่านผลเราจึงควรหาสาเหตุร่วมก่อน ไม่ควรนับทีละข้อ ซึ่งกฎ `columns match set` เป็นข้อที่บอกสาเหตุได้ตรงที่สุด
2. สองข้อที่ล้มเพราะหาคอลัมน์ไม่เจอ GX จะจับ Exception ไว้ แล้วรายงานเป็น `success=False` พร้อม `exception_info` โดยไม่ได้ Raise ออกมา ถ้าดูแค่ `success` เราจึงแยกไม่ออกว่าข้อมูลผิดหรือกฎใช้ไม่ได้ ต้องไปดู `exception_info` ด้วย
3. ลำดับของ `result.results` ไม่ตรงกับลำดับใน Suite เสมอไป ในกรณีนี้ GX เอาข้อที่เกิด Exception ไว้ก่อน (สคริปต์ `16` เทียบกับลำดับเดิมแล้วได้ `same_order=False` เฉพาะกรณีนี้) และยังมีอีกสาเหตุหนึ่งที่ไม่เกี่ยวกับ Exception คือ GX จัดกลุ่ม Expectation ตามคอลัมน์ก่อนประเมิน (หน้า "[Nulls and Result Order](/great-expectations/expectations-suites/nulls-and-order/)" ใน[บทที่ 3](/great-expectations/expectations-suites/)) เพราะฉะนั้นถ้าจะนำผลไปจับคู่กับ Expectation ให้จับคู่ผ่าน `expectation_config` แทนการใช้ตำแหน่งในลิสต์ ซึ่งการจับคู่ตามตำแหน่งในกรณีนี้จะติดป้ายผิดทั้งสามข้อ (สคริปต์ฉบับแรกทำแบบนั้นและให้ผลผิด)

</Step>

## กรณีที่ทุกกฎผ่านทั้งที่ข้อมูลผิด

ในกรณี "ผิดแต่ดูถูก" เราแก้ `age` ของแถวแรกจาก 31 เป็น 13 ซึ่งค่า 13 อยู่ในช่วง 0 ถึง 120 เป็นจำนวนเต็ม และไม่ใช่ Null ดังนั้น Suite จึงผ่านครบ เพราะ GX ตรวจเฉพาะกฎที่เขียนไว้ ถ้าไม่มีกฎที่พูดถึงความผิดแบบนี้ มันก็ไม่มีทางเห็น

กฎที่ตรวจค่ารายแถวจับความผิดแบบนี้ไม่ได้เลย เราต้องมีกฎที่พูดถึงภาพรวม เช่น ช่วงของค่าเฉลี่ยหรือสัดส่วนของค่าแต่ละกลุ่ม แต่กฎพวกนั้นก็ยังพลาดได้ ถ้าความผิดเล็กกว่าช่วงที่ตั้งไว้ จำนวนกฎที่ผ่านจึงบอกคุณภาพของข้อมูลไม่ได้ บอกได้แค่ว่าข้อมูลไม่ขัดกับสิ่งที่เรารู้จะเขียนเป็นกฎ

<Callout type="warn" title="สิ่งที่ตารางนี้ไม่ได้ทดลอง">
ทุกกรณีมี 5 แถวและใช้ Pandas ล้วน ๆ จำนวนกฎที่ล้มกับข้อความ Exception บน SQL หรือ Spark จึงอาจต่างไปจากนี้ ซึ่ง [บทที่ 11](/great-expectations/spark-sql-backends/) ดูเรื่องนี้ไว้ ส่วนการที่ GX ไม่แก้ DataFrame ที่ตรวจ เราทดลองทุกกรณีแล้ว (ตัว DataFrame เท่าเดิมทั้งก่อนและหลังรัน) แต่ทดลองเฉพาะ Pandas
</Callout>
