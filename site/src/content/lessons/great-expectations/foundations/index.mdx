## GX คือผู้ตรวจ ไม่ใช่ผู้แก้

Great Expectations (GX) เป็นไลบรารี Python สำหรับเขียนสิ่งที่คาดหวังจากข้อมูลเป็นโค้ด แล้วสั่งตรวจกับข้อมูลจริง เอกสารทางการเปรียบมันกับ unit test ของข้อมูล แต่ละข้อคือ assertion เช่น "คอลัมน์ `id` ต้องไม่เป็น null" ผลที่ได้คือผ่านหรือไม่ผ่านพร้อมรายละเอียด และทำเป็นรายงานให้คนอ่านได้

GX ไม่แก้ข้อมูลและไม่เก็บข้อมูล มันอ่านข้อมูลจากที่อื่น (DataFrame, ไฟล์, ฐานข้อมูล, Spark) คำนวณข้อเท็จจริงเกี่ยวกับข้อมูลนั้น แล้วเทียบกับสิ่งที่เราเขียนไว้ การแก้ข้อมูลเป็นงานของขั้นตอนอื่น GX รู้แค่ว่าข้อมูลเสียหรือไม่

<Callout type="tip" title="เทียบกับ Spark ในสวนนี้">
Spark เป็นเครื่องคำนวณที่อ่านข้อมูลจากที่อื่น GX อยู่ในตำแหน่งคล้ายกัน คือเป็นตัวตรวจที่อ่านข้อมูลจากที่อื่น และเมื่อข้อมูลใหญ่ GX ก็ฝากงานคำนวณให้ Spark หรือ SQL ทำ ([บทที่ 11](/great-expectations/spark-sql-backends/#หลักการ-ส่งงานไปที่ข้อมูล))
</Callout>

</Step>

## ข้อมูลเสียหน้าตาแบบไหน

ก่อนเขียน expectation ต้องรู้ว่ากำลังกันอะไร ปัญหาที่เจอบ่อยและ expectation ที่ GX มีให้

| ปัญหา | ตัวอย่างที่เกิดขึ้นจริง | expectation ที่ใช้ |
|---|---|---|
| ค่าว่าง | ระบบต้นทางส่ง `age` เป็น null | `ExpectColumnValuesToNotBeNull` |
| ซ้ำ | key ซ้ำหลังรวมสองตาราง | `ExpectColumnValuesToBeUnique` |
| นอกช่วง | อายุ 400, ราคาติดลบ | `ExpectColumnValuesToBeBetween` |
| รูปแบบผิด | อีเมลไม่มี `@` | `ExpectColumnValuesToMatchRegex` |
| โครงสร้างเปลี่ยน | คอลัมน์หายหรือถูกเปลี่ยนชื่อ | `ExpectTableColumnsToMatchSet` |
| จำนวนแถวผิดปกติ | ไฟล์ของวันนี้มาว่าง | `ExpectTableRowCountToBeBetween` |

กฎจำนวนแถวควรมีเสมอ เพราะ expectation แบบ column map ผ่านเมื่อตารางว่าง ([บทที่ 4](/great-expectations/reading-results/#กับดักที่-1-ผ่านโดยไม่มีข้อมูลให้ตรวจ) และหน้า "[ข้อมูลเสียแบบไหน GX จับได้](/great-expectations/foundations/defects/)")

</Step>

<Step>

## ต้องรู้อะไรก่อนเริ่ม

| เรื่อง | ระดับที่ต้องใช้ | ใช้ตอนไหน |
|---|---|---|
| Python | อ่านและเขียน class, keyword argument, exception ได้ | ทุกบท GX 1.x เป็น pydantic model เกือบทั้งหมด |
| pandas | สร้าง DataFrame และอ่านผลได้ | ตัวอย่างแรกทั้งหมดตรวจ DataFrame |
| ชนิดความเสียของข้อมูล | เคยเจอตารางที่ข้อมูลไม่เป็นอย่างที่คิด | ตัดสินว่าจะเขียน expectation อะไร |
| SQL พื้นฐาน | `select`, `count`, `case when` | อ่านคำสั่งที่ GX ส่งไปที่ database ([บทที่ 8](/great-expectations/metrics-engines/)) |
| Spark | ผ่านเส้นทาง Spark ในสวนนี้ถึง[บทที่ 5](/spark/execution-model/) | เฉพาะ[บทที่ 11](/great-expectations/spark-sql-backends/) |

ไม่ต้องเคยใช้ GX มาก่อน และไม่ต้องรู้ pydantic

</Step>

## สองรุ่นที่ต้องแยกให้ออก

ถ้าค้นตัวอย่าง GX บนเว็บ จะเจอโค้ดสองสไตล์ปนกัน เพราะ GX 1.0 เปลี่ยน API ใหญ่ เอกสารทางการแยกเป็นเวอร์ชัน (ตอนเขียนบทนี้) 1.24.1 คือรุ่นล่าสุด 0.18.21 ไม่มีการดูแลแล้ว และมีลิงก์ไปรุ่น 0.17 ขึ้นไปเก่ากว่านั้น

<VersionCompare client:visible />

สัญญาณที่บอกว่าโค้ดเป็นรุ่นเก่า: `context.sources.pandas_default`, `validator.expect_column_...(...)` ที่เรียกเป็นเมธอด, `add_or_update_checkpoint(... validations=[...])`, ไฟล์ YAML ของ checkpoint ถ้าเห็นรูปแบบพวกนี้ อย่าลอกมาใช้กับ 1.x

<Callout type="warn" title="เส้นทางนี้ใช้รุ่นไหน">
ทุกตัวอย่างในเส้นทางนี้รันกับ GX 1.24.1 (โค้ดใน repo pin เวอร์ชันนี้) ส่วน knowledge graph ที่ใช้ศึกษาโครงสร้างวิเคราะห์จาก 1.9.3 ส่วนที่สองรุ่นต่างกันจริงจะบอกไว้ในบทนั้น เช่น เรื่อง context ซ้อนใน[บทที่ 5](/great-expectations/context-stores/#หลาย-context-ใน-process-เดียว)
</Callout>

</Step>

## ติดตั้งและทดลองครั้งแรก

ตัวอย่างโค้ดทั้งหมดอยู่ที่ `subjects/great-expectations/code/` เป็นโปรเจกต์ `uv` ของมันเอง

```bash
cd subjects/great-expectations/code
uv sync
uv run python 01_first_validation.py
```

ถ้าเห็นบรรทัดแรกเป็น `great_expectations 1.24.1` (หรือเวอร์ชันที่ pin ไว้) และได้รายการผลของแต่ละ expectation แปลว่าพร้อมแล้ว ส่วน `08_legacy_018.py` เป็นตัวอย่างรุ่นเก่าไว้เทียบ ต้องรันด้วยคำสั่งพิเศษที่เขียนไว้ในหัวไฟล์

</Step>

## หน้าย่อยของบทนี้

1. ข้อมูลเสียแบบไหน GX จับได้: ตารางเดียว เสียเก้าแบบ กฎชุดเดียวจับได้และพลาดอะไรบ้าง
2. GX วางอยู่ตรงไหนของ pipeline: ภาพการไหลของข้อมูลกับผลตรวจ และจุดที่ควรวางการตรวจ
3. โค้ด 0.18 กับ 1.x ต่างกันตรงไหน: รันงานเดียวกันบนสองรุ่น

</Step>
