## GX คือผู้ตรวจ ไม่ใช่ผู้แก้

Great Expectations (GX) เป็นไลบรารี Python ที่ให้เราเขียนสิ่งที่คาดหวังจากข้อมูลเป็นโค้ด แล้วสั่งตรวจกับข้อมูลจริงได้ เอกสารทางการเปรียบ GX กับ Unit Test ของข้อมูล โดยแต่ละข้อจะเป็น Assertion เช่น "คอลัมน์ `id` ต้องไม่เป็น Null" ผลที่ได้คือผ่านหรือไม่ผ่านพร้อมรายละเอียด และ GX ยังทำเป็นรายงานให้คนอ่านได้ด้วย

GX ไม่แก้ข้อมูลและไม่เก็บข้อมูลไว้เอง มันจะอ่านข้อมูลจากที่อื่น (DataFrame, ไฟล์, ฐานข้อมูล, Spark) แล้วคำนวณข้อเท็จจริงเกี่ยวกับข้อมูลนั้น ก่อนนำไปเทียบกับสิ่งที่เราเขียนไว้ ส่วนการแก้ข้อมูลเป็นงานของขั้นตอนอื่น เพราะ GX รู้แค่ว่าข้อมูลเสียหรือไม่

<Callout type="tip" title="เทียบกับ Spark ในสวนนี้">
Spark เป็นเครื่องคำนวณที่อ่านข้อมูลมาจากที่อื่น GX เองก็อยู่ในตำแหน่งคล้ายกัน คือเป็นตัวตรวจที่อ่านข้อมูลจากที่อื่นเหมือนกัน และเมื่อข้อมูลใหญ่ GX ก็ฝากงานคำนวณให้ Spark หรือ SQL ทำแทน ([บทที่ 11](/great-expectations/spark-sql-backends/#หลักการ-ส่งงานไปที่ข้อมูล))
</Callout>

</Step>

## ข้อมูลเสียหน้าตาแบบไหน

ก่อนเขียน Expectation เราต้องรู้ก่อนว่ากำลังกันอะไรอยู่ ปัญหาที่เจอบ่อยและ Expectation ที่ GX มีให้ใช้ดูได้จากตารางนี้

| ปัญหา | ตัวอย่างที่เกิดขึ้นจริง | Expectation ที่ใช้ |
|---|---|---|
| ค่าว่าง | ระบบต้นทางส่ง `age` เป็น Null | `ExpectColumnValuesToNotBeNull` |
| ซ้ำ | Key ซ้ำหลังรวมสองตาราง | `ExpectColumnValuesToBeUnique` |
| นอกช่วง | อายุ 400, ราคาติดลบ | `ExpectColumnValuesToBeBetween` |
| รูปแบบผิด | อีเมลไม่มี `@` | `ExpectColumnValuesToMatchRegex` |
| โครงสร้างเปลี่ยน | คอลัมน์หายหรือถูกเปลี่ยนชื่อ | `ExpectTableColumnsToMatchSet` |
| จำนวนแถวผิดปกติ | ไฟล์ของวันนี้มาว่าง | `ExpectTableRowCountToBeBetween` |

เราควรมีกฎจำนวนแถวไว้เสมอ เพราะ Expectation แบบ Column Map จะผ่านทันทีเมื่อตารางว่าง ([บทที่ 4](/great-expectations/reading-results/#กับดักที่-1-ผ่านโดยไม่มีข้อมูลให้ตรวจ) และหน้า "[ข้อมูลเสียแบบไหน GX จับได้](/great-expectations/foundations/defects/)")

</Step>

## ต้องรู้อะไรก่อนเริ่ม

| เรื่อง | ระดับที่ต้องใช้ | ใช้ตอนไหน |
|---|---|---|
| Python | อ่านและเขียน Class, Keyword Argument, Exception ได้ | ใช้ทุกบท เพราะ GX 1.x เกือบทั้งหมดเป็น Pydantic Model |
| Pandas | สร้าง DataFrame และอ่านผลได้ | ตัวอย่างแรกทั้งหมดเป็นการตรวจ DataFrame |
| ชนิดความเสียของข้อมูล | เคยเจอตารางที่ข้อมูลไม่เป็นอย่างที่คิด | ใช้ตัดสินว่าจะเขียน Expectation อะไร |
| SQL พื้นฐาน | `select`, `count`, `case when` | ใช้อ่านคำสั่งที่ GX ส่งไปที่ Database ([บทที่ 8](/great-expectations/metrics-engines/)) |
| Spark | ผ่านเส้นทาง Spark ในสวนนี้ถึง[บทที่ 5](/spark/execution-model/) | เฉพาะ[บทที่ 11](/great-expectations/spark-sql-backends/) |

คุณไม่จำเป็นต้องเคยใช้ GX มาก่อน และไม่ต้องรู้จัก Pydantic ก็เริ่มได้

</Step>

## สองรุ่นที่ต้องแยกให้ออก

ถ้าลองค้นตัวอย่าง GX บนเว็บ เราจะเจอโค้ดสองสไตล์ปนกันอยู่ เพราะ GX 1.0 เปลี่ยน API ครั้งใหญ่ เอกสารทางการจึงแยกเป็นหลายเวอร์ชัน ซึ่งตอนเขียนบทนี้ 1.24.1 เป็นรุ่นล่าสุด ส่วน 0.18.21 ไม่มีการดูแลแล้ว และยังมีลิงก์ไปรุ่น 0.17 ขึ้นไปซึ่งเก่ากว่านั้นอีก

<VersionCompare client:visible />

โค้ดรุ่นเก่าดูได้จากสัญญาณเหล่านี้ คือ `context.sources.pandas_default`, `validator.expect_column_...(...)` ที่เรียกเป็นเมธอด, `add_or_update_checkpoint(... validations=[...])` และไฟล์ YAML ของ Checkpoint ถ้าเห็นรูปแบบพวกนี้ ก็อย่าลอกมาใช้กับ 1.x นะ

<Callout type="warn" title="เส้นทางนี้ใช้รุ่นไหน">
ทุกตัวอย่างในเส้นทางนี้รันกับ GX 1.24.1 (โค้ดใน Repo Pin เวอร์ชันนี้) ส่วน Knowledge Graph ที่เราใช้ศึกษาโครงสร้างนั้นวิเคราะห์มาจาก 1.9.3 ถ้าตรงไหนที่สองรุ่นนี้ต่างกันจริง ๆ เราจะบอกไว้ในบทนั้น เช่น เรื่อง Context ซ้อนใน[บทที่ 5](/great-expectations/context-stores/#หลาย-context-ใน-process-เดียว)
</Callout>

</Step>

## ติดตั้งและทดลองครั้งแรก

ตัวอย่างโค้ดทั้งหมดอยู่ที่ `subjects/great-expectations/code/` ซึ่งเป็นโปรเจกต์ `uv` ของมันเอง

```bash
cd subjects/great-expectations/code
uv sync
uv run python 01_first_validation.py
```

ถ้าบรรทัดแรกที่เห็นเป็น `great_expectations 1.24.1` (หรือเวอร์ชันที่ Pin ไว้) และมีรายการผลของแต่ละ Expectation ตามมา ก็แปลว่าเราพร้อมแล้ว ส่วน `08_legacy_018.py` เป็นตัวอย่างรุ่นเก่าที่เก็บไว้เทียบกัน และต้องรันด้วยคำสั่งพิเศษที่เขียนไว้ในหัวไฟล์

</Step>

## หน้าย่อยของบทนี้

1. ข้อมูลเสียแบบไหน GX จับได้ เอาตารางเดียวมาทำให้เสียเก้าแบบ แล้วดูว่ากฎชุดเดียวจับอะไรได้และพลาดอะไรไปบ้าง
2. GX วางอยู่ตรงไหนของ Pipeline ดูภาพการไหลของข้อมูลกับผลตรวจ และจุดที่ควรวางการตรวจ
3. โค้ด 0.18 กับ 1.x ต่างกันตรงไหน รันงานเดียวกันบนสองรุ่นแล้วเทียบกัน

</Step>
