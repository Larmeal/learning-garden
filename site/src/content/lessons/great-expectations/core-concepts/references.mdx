## Json ของ Validation Definition

Object ใน GX Serialize เป็น Json ได้ ลองดู Validation Definition ที่รันแล้วกัน (ตัด id ให้สั้น)

```json
{
  "name": "people_vd",
  "data":  { "id": "e12a128a-...", "name": "whole", "partitioner": null },
  "suite": { "name": "people_suite", "id": "3bd890de-..." },
  "id": "d7f67960-..."
}
```

ผลจริงจาก `17_object_chain.py` (GX 1.24.1) จะเห็นว่า Validation Definition ไม่ได้ฝัง Suite ทั้งก้อนหรือ DataFrame ไว้ข้างใน มันจำแค่ชื่อกับ id ของ Suite และ Batch Definition พอรัน GX ถึงค่อยไปหา Object จริงจาก Context

ฝั่ง `data` ของ Json นี้ (จาก `.json()` ใน Memory) มีแค่ id กับชื่อของ Batch Definition ไม่มี Asset หรือ Data Source ส่วนไฟล์ที่ File Context เขียนลงดิสก์จะเก็บเต็มกว่า คือ Datasource, Asset และ Batch Definition อย่างละ id + ชื่อ ([บทที่ 5 หน้า "เดินดูโฟลเดอร์ gx/"](/great-expectations/context-stores/tour/#สามข้อที่เห็นจากไฟล์))

## ผลต่อวิธีทำงานจริง

ใน Context แบบ Ephemeral ชื่อซ้ำไม่เกิดจากการรันสคริปต์ซ้ำ เพราะ Context เริ่มว่างทุกครั้ง แต่ Context แบบ File จำชื่อข้ามการรันได้ สคริปต์ `17` ส่วนที่ 5 ทดลองแล้วได้ผลดังนี้

```text
first run  : suites = ['kept']
second run : suites already there = ['kept']
add the same name again: DataContextError | Cannot add ExpectationSuite with name kept because it already exists.
```

สคริปต์ที่เรียก `context.suites.add(...)` ตรง ๆ จึงรันครั้งที่สองใน File Context ไม่ได้ สคริปต์เดียวกันทดลองต่อ ได้ว่า `context.suites.get("kept")` คืน Suite เดิมพร้อม id และ `context.suites.add_or_update(...)` ก็ไม่ Error และคืน Suite ที่ id เดิม จำนวน Suite ยังเป็น 1 ตัว (add_or_update ใช้แทนค่าเนื้อหาของ Suite เดิมหรือไม่ ไม่ได้ตรวจ)

เราควรตั้งชื่อให้คงที่และบอกเนื้อหา เพราะชื่อคือสิ่งที่ใช้ค้นกลับมา และเป็นสิ่งที่เห็นใน Data Docs

<Callout type="warn" title="ที่ยังไม่ได้ทดลอง">
เรายังไม่ได้รันการเปลี่ยนชื่อ Object ที่มีของอื่นอ้างอยู่ (เช่น เปลี่ยนชื่อ Suite ที่ Validation Definition ชี้อยู่) จึงไม่รู้ว่าผลเป็นอย่างไร
</Callout>
