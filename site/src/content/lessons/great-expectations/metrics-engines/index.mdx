## Expectation ไม่ได้อ่านข้อมูลเอง

ลองคิดดูว่าถ้า `ExpectColumnMaxToBeBetween` เขียนโค้ดอ่านข้อมูลเอง มันก็ต้องรู้ว่าข้อมูลอยู่ใน Pandas, Spark หรือฐานข้อมูล และ Expectation หกสิบตัวก็ต้องถูกเขียนใหม่ทุก Backend GX จึงแก้ปัญหานี้ด้วยการแยกงานออกเป็นสองส่วน

- Expectation เป็นฝ่ายประกาศว่าต้องใช้ Metric อะไร (`column.max` ของคอลัมน์ `age`) แล้วตัดสินผลจากค่าที่ได้กลับมา
- Execution Engine (Pandas, Spark, SQLAlchemy) เป็นฝ่ายที่รู้วิธีคำนวณ Metric นั้นบน Backend ของตัวเอง

Metric คือข้อเท็จจริงที่มีชื่อเกี่ยวกับข้อมูล เช่น `table.row_count`, `column.max`, `column_values.nonnull.condition` และ Expectation หลายข้อก็ใช้ Metric เดียวกันได้ ซึ่งนี่เป็นแกนของ GX ทั้งระบบเลย

</Step>

<Step>

## ประกาศ แล้วค่อยตัดสิน

ทุก Expectation ต้องมีสองเมธอดในซอร์ส (`expectations/expectation.py`)

1. `get_validation_dependencies()` ทำหน้าที่คืนรายการ Metric ที่ต้องใช้
2. `_validate(metrics=...)` ทำหน้าที่รับค่า Metric ที่คำนวณได้แล้ว และคืน `success` กับ `result`

ระหว่างสองขั้นนี้ GX จะทำงานแทนเรา โดยรวมคำขอ Metric จากทุก Expectation ใน Suite เป็นกราฟเดียว (`Validator.graph_validate`) แล้วให้ Engine เป็นคนคำนวณ ตัว Expectation เองจึงไม่ต้องรู้เลยว่า Backend คืออะไร

ถ้าลองนึกถึงเส้นทาง Spark ในสวนนี้ DataFrame API ที่คุณเขียนก็เป็นแผน ไม่ได้ลงมือทันที แล้ว Catalyst จะปรับแผนก่อนรัน GX ก็มีแนวคิดคล้ายกัน คือ Expectation เป็นคำขอ แล้ว GX รวมและจัดลำดับให้ก่อนที่ Engine จะลงมือ

</Step>

## ลองดูมันคำนวณ

<MetricRounds client:visible />

มีสี่อย่างที่น่าสังเกตจากแล็บนี้ (ทั้งหมดวัดจาก GX 1.24.1 จริง)

- Expectation ระดับคอลัมน์ทุกข้อต้องใช้ Metric พื้นฐานชุดเดียวกัน คือ `table.column_types`, `table.row_count` และ `table.columns` ซึ่งถูกคำนวณมาก่อนเสมอ ลองเลือก Expectation ข้อเดียวแล้วดูรอบที่ 1 กับ 2 ส่วน Expectation จำนวนแถว (`ExpectTableRowCountToEqual`) ใช้แค่ `table.row_count` ตัวเดียว
- Metric ที่ใช้ร่วมกันจะถูกคำนวณครั้งเดียว ถ้าเลือก "not null id" กับ "Unique id" ด้วยกัน เราจะเห็น `column_values.nonnull.condition` ของ `id` ปรากฏแค่ครั้งเดียว ทั้งที่ทั้งสอง Expectation ต่างก็ใช้มัน
- จำนวนรอบถูกกำหนดโดย Dependency เพราะ Metric ในรอบเดียวกันต้องไม่รอผลของกันและกัน ส่วนรอบถัดไปจะใช้ผลของรอบก่อน (เช่น `unexpected_count` ต้องรอ `condition`)
- result_format มีผลกับรอบสุดท้าย ลองสลับ BOOLEAN_ONLY เป็น SUMMARY แล้วจะเห็นรอบสุดท้ายโตขึ้นมาก เพราะต้องคำนวณตัวอย่างค่าที่ผิดและดัชนีของแถวด้วย

</Step>

## หนึ่งชื่อ หลาย Implementation

Metric หนึ่งตัวถูกเขียนแยกตาม Engine ยกตัวอย่างจริงจากซอร์สของ `column.max`

```python
class ColumnMax(ColumnAggregateMetricProvider):
    metric_name = "column.max"

    @column_aggregate_value(engine=PandasExecutionEngine)
    def _pandas(cls, column, kwargs):
        return column.max()

    @column_aggregate_partial(engine=SqlAlchemyExecutionEngine)
    def _sqlalchemy(cls, column, kwargs):
        return sa.func.max(column)

    @column_aggregate_partial(engine=SparkDFExecutionEngine)
    def _spark(cls, column, kwargs):
        return F.max(column)
```

ตอนนิยามคลาส GX จะลงทะเบียนแต่ละเมธอดเข้า Registry ภายใต้ชื่อ `column.max` และคลาสของ Engine แล้วตอนรัน `get_metric_provider(metric_name, engine)` จะหา Implementation ที่ตรงกับ Engine (ถ้าไม่เจอตรง ๆ ก็จะไล่ดูคลาสแม่ตาม MRO) แต่ถ้าไม่มี Implementation สำหรับ Engine นั้นเลย Expectation นั้นจะล้มด้วย `No provider found for ...` ([บทที่ 12](/great-expectations/custom-expectations/testing-shipping/#เงื่อนไขเดียวกัน-ผลต่างกันตาม-engine))

</Step>

## สองแบบ: คำนวณทันที กับเลื่อนไว้รวม

ถ้าสังเกตดูจะเห็นว่า Pandas ใช้ `column_aggregate_value` แต่ SQL กับ Spark ใช้ `column_aggregate_partial` ซึ่งต่างกันอย่างเป็นระบบ

| แบบ | ทำอะไร | ใช้กับ |
|---|---|---|
| Value | คำนวณเดี๋ยวนั้นและคืนค่า | Pandas (การคำนวณเกิดทันทีใน Memory) |
| Partial (Aggregate) | คืน "นิพจน์" ที่ยังไม่รัน เช่น `sa.func.max(column)` | SQL และ Spark ที่เลื่อนการรันได้ |

เพราะ Partial ยังไม่รัน GX จึง รวมหลาย Metric ที่อยู่ใน Domain เดียวกันเป็นคำสั่งเดียว ได้ ดังที่เห็นจากการรันกับ SQLite (`05_sql_bundling.py`, Suite 6 ข้อ, `BOOLEAN_ONLY`)

```sql
SELECT count(*) AS "table.row_count" FROM (SELECT * FROM users WHERE 1 = 1) AS anon_1
SELECT avg(1.0 * age) AS "column.mean", max(age) AS "column.max" FROM (...) AS anon_1
SELECT sum(CASE WHEN (id IS NULL) THEN 1 ELSE 0 END) AS "column_values.nonnull.unexpected_count",
       sum(CASE WHEN (age IS NULL) THEN 1 ELSE 0 END) AS "...", ... FROM (...) AS anon_1
```

จะเห็นว่า `avg` และ `max` ถูกส่งไปใน SELECT เดียวกัน และ Null Count ของหลายคอลัมน์ก็รวมเป็นอีกคำสั่งหนึ่ง สำหรับ Spark ซอร์สทำแบบเดียวกันด้วย `df.agg(*aggregates).collect()` ครั้งเดียวต่อ Domain (อ่านจากซอร์ส ยังไม่ได้รันยืนยัน)

</Step>

## ต้นทุนมาจากไหน

ตารางนี้สรุปสิ่งที่เราวัดได้

| อะไร | เห็นอะไร |
|---|---|
| `result_format` | Suite ตัวอย่าง (5 ข้อ) ใช้ 10, 13, 19, 19 Metric สำหรับ BOOLEAN_ONLY, BASIC, SUMMARY, COMPLETE |
| จำนวน Expectation | ค่าเปิดโต๊ะจ่ายครั้งเดียว Metric ของคอลัมน์เดียวกันใช้ร่วมกัน แต่ละคอลัมน์ใหม่เพิ่มของมันเอง |
| รันซ้ำ | คำนวณใหม่ทั้งหมด (19 แล้ว 19) ไม่มี Cache ข้ามรอบ |
| Backend | Pandas: ทีละ Metric ใน Memory SQL: 6 Expectation เหลือ 3 คำสั่ง (BOOLEAN_ONLY) หรือ 6 คำสั่ง (SUMMARY) |

<Callout type="note" title="ตัวเลขต่างกันตามรุ่น">
ใน GX 1.9.3 ตัวเลขเดียวกันคือ 11, 14, 20 Metric และ SQL 4 กับ 7 คำสั่ง เพราะ `table.row_count` ถูกคำนวณซ้ำหนึ่งตัวและส่งเป็นคำสั่งแยก ส่วนใน 1.24.1 ถูกรวมแล้ว หลักการยังเหมือนเดิม แต่ตัวเลขขยับตามการปรับปรุงของแต่ละรุ่น อย่าเอาตัวเลขไปท่องเป็นค่าคงที่นะ
</Callout>

บนข้อมูลใหญ่ ต้นทุนหลักอยู่ที่จำนวนครั้งที่ต้องไปถึงข้อมูล กับขนาดของสิ่งที่ส่งกลับมา ดังนั้นการใช้ `BOOLEAN_ONLY` เมื่อไม่ต้องการรายละเอียด และการใช้ Expectation กับคอลัมน์เดียวกันเพื่อให้ได้ Domain เดียวกัน จึงลดต้นทุนได้ทันที (เราวัดจำนวนคำสั่งไว้แล้ว ส่วนเวลาจริงบนข้อมูลใหญ่ไม่ได้วัด)

</Step>

## เมื่อ Metric พัง

ใน `ValidationGraph` ถ้า Metric หนึ่งคำนวณไม่สำเร็จ GX จะลองซ้ำได้สูงสุด 3 ครั้ง (`MAX_METRIC_COMPUTATION_RETRIES`) และถ้ายังไม่ได้ ก็จะ "ยกเลิก" Metric นั้น ทำให้ทุก Expectation ที่พึ่งมันได้ผล `success=False` พร้อม `exception_info` ส่วน Expectation ที่ไม่เกี่ยวข้องยังถูกประเมินตามปกติ นี่คือกลไกเบื้องหลังที่[บทที่ 4](/great-expectations/reading-results/#กับดักที่-2-expectation-ที่พังไม่-raise) เห็นเป็น "Expectation พังไม่ Raise"

## ลองทำใน Repo นี้

ให้เปิด `02_metric_rounds.py` ขึ้นมา แล้วลองทำตามนี้

1. เพิ่ม Expectation ตัวที่หกที่ถามคอลัมน์ `name` แล้วดูว่ารอบและ Metric เปลี่ยนไปเท่าไร
2. เปลี่ยนเป็น `ResultFormat.BOOLEAN_ONLY` ทั้งสคริปต์ แล้วเทียบจำนวน Metric
3. รัน `05_sql_bundling.py` แล้วอ่านคำสั่ง SQL ทีละบรรทัด โดยหา `CASE WHEN` ของแต่ละ Expectation

## เช็กตัวเอง

- ถ้า Suite มี 3 Expectation ที่ถาม `age` ทั้งหมด `table.row_count` จะถูกคำนวณกี่ครั้ง
- ทำไมบน Pandas ถึงไม่มีการ "รวมคำสั่ง" แต่บน SQL มี
- ถ้าข้อมูลมีหลายร้อยล้านแถวบน Spark เราปรับอะไรที่ฝั่ง GX เพื่อลดการคำนวณได้บ้าง
