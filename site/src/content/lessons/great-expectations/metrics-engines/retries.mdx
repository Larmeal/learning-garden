## ทดลอง

ในบทหลักเราอ่านจากซอร์สมาแล้วว่า `ValidationGraph` ลอง Metric ซ้ำได้สูงสุด 3 ครั้ง คราวนี้สคริปต์ `26_registry_domains.py` ส่วนที่ 4 จะทดลองด้วย Metric ที่พังเสมอ (GX 1.24.1, Pandas)

```python
CALLS = [0]

class ColumnAlwaysFails(ColumnAggregateMetricProvider):
    metric_name = "column.always_fails"

    @column_aggregate_value(engine=PandasExecutionEngine)
    def _pandas(cls, column, **kwargs):
        CALLS[0] += 1
        raise RuntimeError("this metric never works")

class ExpectColumnAlwaysFails(ColumnAggregateExpectation):
    metric_dependencies = ("column.always_fails",)
    args_keys = ("column",)
    def _validate(self, metrics, runtime_configuration=None, execution_engine=None):
        return {"success": True, "result": {"observed_value": metrics["column.always_fails"]}}
```

Suite ที่ใช้มีสองกฎ คือ `ExpectColumnAlwaysFails(column="x")` กับ `ExpectColumnMaxToBeBetween(column="x", 0..10)` บนข้อมูล `x=[1, 2, 3]` ผลที่ได้เป็นดังนี้

```text
calls to the failing metric function: 3
column_always_fails          success=False raised=True
column_max_to_be_between     success=True  raised=False
```

## เอาไปใช้อย่างไร

- ถ้าเห็น `success=False` และ `exception_info` ที่เกิดจากการคำนวณ Metric แปลว่าเราอย่าเพิ่งรีบไปค้นข้อมูล ให้ดูข้อความ Exception ก่อน (ลำดับคำถามใน[บทที่ 4](/great-expectations/reading-results/))
- ฟังก์ชัน Metric ที่ทำงานช้าหรือต่อออกไปข้างนอก (เช่นเรียกบริการ) อาจถูกเรียกได้ถึง 3 ครั้งเมื่อมันพัง เราจึงควรออกแบบให้ฟังก์ชันนั้นไม่มีผลข้างเคียง
- ตัวเลข 3 ตรงกับ `MAX_METRIC_COMPUTATION_RETRIES` ที่อ่านจากซอร์ส `validation_graph.py` ส่วนเรื่องที่ว่ามีการหน่วงเวลาระหว่างแต่ละครั้งหรือไม่ เรายังไม่ได้ทดลอง

<Callout type="warn" title="ที่ไม่ได้ทดลอง">
เราทดลองกับ Metric แบบ Aggregate บน Pandas เท่านั้น ถ้า Metric พังบน SQL หรือ Spark (เช่นฐานข้อมูลตัดการเชื่อมต่อกลางทาง) อาจถูกลองซ้ำต่างออกไป ซึ่งเรายังไม่ได้ทดสอบ
</Callout>
