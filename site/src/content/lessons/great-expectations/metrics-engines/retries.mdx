## ทดลอง

บทหลักอ่านจากซอร์สว่า `ValidationGraph` ลอง metric ซ้ำได้สูงสุด 3 ครั้ง สคริปต์ `26_registry_domains.py` ส่วนที่ 4 ทดลองด้วย metric ที่พังเสมอ (GX 1.24.1, pandas)

```python
CALLS = [0]

class ColumnAlwaysFails(ColumnAggregateMetricProvider):
    metric_name = "column.always_fails"

    @column_aggregate_value(engine=PandasExecutionEngine)
    def _pandas(cls, column, **kwargs):
        CALLS[0] += 1
        raise RuntimeError("this metric never works")

class ExpectColumnAlwaysFails(ColumnAggregateExpectation):
    metric_dependencies = ("column.always_fails",)
    args_keys = ("column",)
    def _validate(self, metrics, runtime_configuration=None, execution_engine=None):
        return {"success": True, "result": {"observed_value": metrics["column.always_fails"]}}
```

suite มีสองกฎ คือ `ExpectColumnAlwaysFails(column="x")` กับ `ExpectColumnMaxToBeBetween(column="x", 0..10)` บนข้อมูล `x=[1, 2, 3]`

```text
calls to the failing metric function: 3
column_always_fails          success=False raised=True
column_max_to_be_between     success=True  raised=False
```

## เอาไปใช้อย่างไร

- ถ้าเห็น `success=False` และ `exception_info` ที่เกิดจากการคำนวณ metric แปลว่าอย่าเพิ่งไปค้นข้อมูล ให้ดูข้อความ exception ก่อน (ลำดับคำถามใน[บทที่ 4](/great-expectations/reading-results/))
- ฟังก์ชัน metric ที่ทำงานช้าหรือต่อภายนอก (เช่นเรียกบริการ) ถูกเรียกได้ถึง 3 ครั้งเมื่อมันพัง ออกแบบให้ไม่มีผลข้างเคียง
- ตัวเลข 3 ตรงกับ `MAX_METRIC_COMPUTATION_RETRIES` ที่อ่านจากซอร์ส `validation_graph.py` ไม่ได้ทดลองว่ามีหน่วงเวลาระหว่างครั้งหรือไม่

<Callout type="warn" title="ที่ไม่ได้ทดลอง">
ทดลองกับ metric แบบ aggregate บน pandas เท่านั้น metric ที่พังบน SQL หรือ Spark (เช่นฐานข้อมูลตัดการเชื่อมต่อกลางทาง) อาจถูกลองซ้ำต่างกัน ไม่ได้ทดสอบ
</Callout>
