## Context ที่ใช้ได้จริงมีสองชนิด

Data Context คือ Object ที่ถือ Config และผลตรวจของทั้ง Workflow โดย `gx.get_context()` จะเลือกชนิดให้เราตามลำดับนี้

1. ถ้ามีค่าตั้งของ GX Cloud ครบ ก็จะเข้าทางของ Cloud ซึ่งใน GX 1.24.1 จะ Raise `GreatExpectationsError` ทันที เพราะ GX Cloud ปิดบริการแล้ว (ยืนยันกับ `mode="cloud"` ใน `23_persistence_config.py` ข้อความคือ "GX Cloud has been shut down, so this no longer functions and will be removed in great_expectations 2.0")
2. ถ้าพบโฟลเดอร์ `gx/` ก็จะได้ File Context
3. ถ้าไม่เจออย่างอื่นเลย ก็จะได้ Ephemeral Context

เรายังระบุเองได้ด้วย `mode="ephemeral"` หรือ `mode="file"`

<ContextPicker client:visible />

ผลของลำดับนี้คือ โค้ดเดียวกันอาจได้ Context ต่างชนิดกันในคอมพิวเตอร์ต่างเครื่อง (เช่นคอมพิวเตอร์ที่มีโฟลเดอร์ `gx/` กับ CI ที่ไม่มี) ถ้าต้องการให้แน่นอน ก็ให้ระบุ `mode` เอง

</Step>

## File Context เขียนอะไรลงดิสก์

เรารันจริงด้วย `gx.get_context(mode="file", project_root_dir=...)` แล้ว Add Suite, Validation Definition, Checkpoint และรัน จะได้โครงดังนี้

```
gx/
  great_expectations.yml        # ตั้งค่า context และ data source
  .gitignore                    # มีบรรทัดเดียว: uncommitted/
  expectations/                 # suite เป็นไฟล์ JSON
  validation_definitions/       # ชื่อและ id ของ batch definition กับ suite
  checkpoints/                  # checkpoint และ action
  plugins/
  uncommitted/                  # ไม่เข้า git
    config_variables.yml        # ค่าลับ
    validations/                # ผลตรวจทุกรอบ
    data_docs/local_site/       # รายงาน HTML
```

สิ่งที่ Commit เข้า Git คือคำจำกัดความ (อะไรตรวจกับอะไร) ส่วนที่ไม่ Commit คือผลและค่าลับ ซึ่ง `.gitignore` ที่ GX สร้างให้ก็จัดการเรื่องนี้ไว้แล้ว ทีมจึงรีวิว Suite ผ่าน Pull Request ได้เหมือนโค้ด

</Step>

## Store: ที่เก็บของทุกอย่าง

ข้างใน Context จะเก็บของผ่าน Store แต่ละชนิด (Expectations, Validation Definitions, Checkpoints, Validation Results) โดย Store ทำหน้าที่แปลง Object ของ GX เป็นข้อมูลที่เก็บได้ ส่วน StoreBackend คือที่เก็บจริงข้างใต้ ซึ่งมีให้เลือกหลายแบบ ได้แก่ Memory, ไฟล์, S3, GCS, Azure และ Database (รายการนี้อ่านจากซอร์ส ไม่ได้ลองทีละ Backend)

```python
context.validation_results_store.list_keys()   # ดูผลที่ถูกเก็บ
```

Ephemeral Context ใช้ Backend ใน Memory ทุกอย่างจึงหายเมื่อโปรแกรมจบ ส่วน File Context ใช้ Backend ไฟล์ตามโครงข้างบน

</Step>

## ทำไมต้อง Add ก่อนรัน

Validation Definition ไม่ได้ถือ Suite ไว้ในตัว ตอนเก็บมันจะเก็บเป็น ชื่อและ id ของ Batch Definition กับ Suite แล้วค่อยหยิบกลับจาก Store ตอนต้องใช้ ถ้าของที่ถูกอ้างไม่อยู่ใน Store ก็หยิบไม่ได้ ดังนั้น GX จึงตรวจก่อนรันเสมอ ("Freshness Check")

| ทำอะไร | ผล (ทดลองแล้ว) |
|---|---|
| `run()` ของ Validation Definition ที่ Suite ไม่ได้ Add | Error `ValidationDefinitionRelatedResourcesFreshnessError` บอกให้ `context.suites.add(...)` |
| `run()` ของ Validation Definition ที่ Suite กับ data source add แล้ว แต่ตัวมันเองยังไม่ได้ Add | รันได้ โดย GX Add ให้เอง (id ที่เคยเป็น `None` จะมีค่า) |
| `context.checkpoints.add(...)` ที่ Validation Definition ยังไม่ได้ Add | Error `CheckpointRelatedResourcesFreshnessError` |

สรุปคือให้ Add จากชิ้นล่างขึ้นบน (Data Source, Suite, Validation Definition, Checkpoint) ถ้าลืมชิ้นบนสุด GX จะเติมให้เอง แต่ถ้าลืมชิ้นล่างจะเกิด Error

</Step>

## หลาย Context ใน Process เดียว

GX เก็บ "Context ปัจจุบัน" ไว้เป็น Singleton ระดับ Process (`ProjectManager`) ดังนั้นการเรียก `gx.get_context()` ครั้งที่สองจะสร้าง Context ใหม่และ แทนที่ ตัวเดิมเป็นตัวปัจจุบัน

ผลจะต่างกันไปตามรุ่น (รันทั้งสองรุ่นแล้ว)

| รุ่น | `vd.run()` ของ Validation Definition ที่สร้างใต้ Context แรก หลังสร้าง Context ที่สอง |
|---|---|
| 1.9.3 | Error (`ValidationDefinitionRelatedResourcesFreshnessError` ว่าหา Datasource ไม่เจอ เพราะไปหาใน Context ใหม่) |
| 1.24.1 | รันได้ Object จำ Context เจ้าของของมันไว้ (ในซอร์สอ้างถึง GX Issue #12209) |

<Callout type="warn" title="เขียนโค้ดให้ปลอดภัยทั้งสองรุ่น">
ถ้าโปรเจกต์ยังต้องรองรับ 1.9.3 หรือรุ่นก่อนหน้า อย่าถือ Object จาก Context หนึ่งแล้วไปรันหลังสร้างอีก Context ในโปรเซสเดียวกัน (พบบ่อยใน Test ที่สร้าง Context ใหม่ทุกเคส) ให้เก็บ Context ไว้ตัวเดียวต่อ Process หรือไม่ก็สร้าง Object ใหม่ทุกครั้งที่สร้าง Context
</Callout>

</Step>

## ค่าลับและค่าที่เปลี่ยนตามสภาพแวดล้อม

อย่าเขียนรหัสผ่านลงใน Config ตรง ๆ ให้ใช้ตัวแปรแทน แล้ว GX จะแทนค่า `${NAME}` ให้ตอนใช้งาน

```python
source = context.data_sources.add_sqlite("sales", connection_string="${MY_DB_URL}")
```

ทดลองแล้ว: ตั้ง Environment Variable `MY_DB_URL` แล้วรันได้ โดยค่าที่เก็บใน Config ยังเป็นข้อความ `${MY_DB_URL}` ไม่ใช่ค่าจริง (ปลอดภัยที่จะ Commit) ส่วนไฟล์ `uncommitted/config_variables.yml` เป็นอีกแหล่งของตัวแปร ซึ่งทดลองแล้วว่าใช้ได้ (ดูหน้า "[ค่าลับและ config_variables.yml](/great-expectations/context-stores/secrets/)")

</Step>

<Step>

## เช็กตัวเอง

- ถ้าคอมพิวเตอร์ของคุณมีโฟลเดอร์ `gx/` แต่ CI ไม่มี `gx.get_context()` จะได้ Context ชนิดอะไรในแต่ละที่ และจะทำให้เหมือนกันได้อย่างไร
- ถ้าสร้าง Validation Definition ก่อนแล้วค่อย Add Suite จะเกิดอะไรขึ้นตอน `run()`
- ไฟล์ไหนในโฟลเดอร์ `gx/` ที่ไม่ควร Commit

</Step>

<Step>

## หน้าย่อยของบทนี้

1. เดินดูโฟลเดอร์ gx/: ไฟล์ทุกไฟล์ที่ File Context เขียน พร้อมเนื้อหาจริง
2. Context ที่อยู่ข้ามโปรเซส: สร้างในโปรเซสหนึ่ง โหลดและรันในอีกโปรเซส
3. ค่าลับและ config_variables.yml: ตัวแปรจากไฟล์ จาก Environment และลำดับก่อนหลัง

</Step>
