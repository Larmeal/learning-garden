## context มีสามชนิด

Data Context คือ object ที่ถือ config และผลตรวจของทั้ง workflow `gx.get_context()` เลือกชนิดให้ตามลำดับนี้

1. **cloud** ถ้ามีค่าตั้งของ GX Cloud ครบ (`GX_CLOUD_ORGANIZATION_ID`, `GX_CLOUD_ACCESS_TOKEN`)
2. **file** ถ้าพบโฟลเดอร์ `gx/`
3. **ephemeral** ถ้าไม่เจออย่างอื่น

ระบุเองด้วย `mode="ephemeral" | "file" | "cloud"` ได้

<ContextPicker client:visible />

ผลของลำดับนี้: โค้ดเดียวกันได้ context ต่างชนิดในเครื่องต่างกัน (เครื่องที่มี `gx/` กับเครื่อง CI ที่ไม่มี) ถ้าต้องการให้แน่นอน ให้ระบุ `mode` เอง

</Step>

## file context เขียนอะไรลงดิสก์

รันจริงด้วย `gx.get_context(mode="file", project_root_dir=...)` แล้ว add suite, validation definition, checkpoint และรันได้โครงนี้

```
gx/
  great_expectations.yml        # ตั้งค่า context และ data source
  .gitignore                    # มีบรรทัดเดียว: uncommitted/
  expectations/                 # suite เป็นไฟล์ JSON
  validation_definitions/       # ชื่อและ id ของ batch definition กับ suite
  checkpoints/                  # checkpoint และ action
  plugins/
  uncommitted/                  # ไม่เข้า git
    config_variables.yml        # ค่าลับ
    validations/                # ผลตรวจทุกรอบ
    data_docs/local_site/       # รายงาน HTML
```

ที่ commit เข้า git คือคำจำกัดความ (อะไรตรวจกับอะไร) ที่ไม่ commit คือผลและค่าลับ `.gitignore` ที่ GX สร้างให้ทำเรื่องนี้ไว้แล้ว ทีมจึงรีวิว suite ผ่าน pull request ได้เหมือนโค้ด

</Step>

<Step>

## Store: ที่เก็บของทุกอย่าง

ข้างใน context เก็บของผ่าน **Store** แต่ละชนิด (expectations, validation definitions, checkpoints, validation results) Store แปลง object ของ GX เป็นข้อมูลที่เก็บได้ ส่วน **StoreBackend** คือที่เก็บจริงข้างใต้ ซึ่งมีให้เลือก: memory, ไฟล์, S3, GCS, Azure, database และ GX Cloud (อ่านจากซอร์ส)

```python
context.validation_results_store.list_keys()   # ดูผลที่ถูกเก็บ
```

ephemeral context ใช้ backend ใน memory ทุกอย่างหายเมื่อโปรแกรมจบ file context ใช้ backend ไฟล์ตามโครงข้างบน

</Step>

<Step>

## ทำไมต้อง add ก่อนรัน

validation definition ไม่ได้ถือ suite ไว้ในตัว ตอนเก็บมันเก็บเป็น **ชื่อและ id** ของ batch definition กับ suite แล้วค่อยหยิบกลับจาก store ตอนต้องใช้ ถ้าของที่ถูกอ้างไม่อยู่ใน store ก็หยิบไม่ได้ GX จึงตรวจก่อนรันเสมอ ("freshness check")

| ทำอะไร | ผล (ทดลองแล้ว) |
|---|---|
| `run()` ของ validation definition ที่ suite ไม่ได้ add | error `ValidationDefinitionRelatedResourcesFreshnessError` บอกให้ `context.suites.add(...)` |
| `run()` ของ validation definition ที่ suite กับ data source add แล้ว แต่ตัวมันเองยังไม่ได้ add | รันได้ GX add ให้เอง (id ที่เคยเป็น `None` จะมีค่า) |
| `context.checkpoints.add(...)` ที่ validation definition ยังไม่ได้ add | error `CheckpointRelatedResourcesFreshnessError` |

สรุป: **add จากชิ้นล่างขึ้นบน** (data source, suite, validation definition, checkpoint) แล้วชิ้นบนสุดที่ลืมจะถูกเติมให้ แต่ชิ้นล่างที่ลืมจะเป็น error

</Step>

<Step>

## หลาย context ใน process เดียว

GX เก็บ "context ปัจจุบัน" ไว้เป็น singleton ระดับ process (`ProjectManager`) การเรียก `gx.get_context()` ครั้งที่สองสร้าง context ใหม่และ **แทนที่** ตัวเดิมเป็นตัวปัจจุบัน

ผลที่ต่างกันตามรุ่น (รันทั้งสองรุ่นแล้ว)

| รุ่น | `vd.run()` ของ validation definition ที่สร้างใต้ context แรก หลังสร้าง context ที่สอง |
|---|---|
| 1.9.3 | **error** (`ValidationDefinitionRelatedResourcesFreshnessError` ว่าหา datasource ไม่เจอ เพราะไปหาใน context ใหม่) |
| 1.24.1 | **รันได้** object จำ context เจ้าของของมันไว้ (ในซอร์สอ้างถึง GX issue #12209) |

<Callout type="warn" title="เขียนโค้ดให้ปลอดภัยทั้งสองรุ่น">
ถ้าโปรเจกต์ยังต้องรองรับ 1.9.3 หรือรุ่นก่อนหน้า อย่าถือ object จาก context หนึ่งแล้วไปรันหลังสร้างอีก context ในโปรเซสเดียวกัน (พบบ่อยใน test ที่สร้าง context ใหม่ทุกเคส) เก็บ context ไว้ตัวเดียวต่อ process หรือสร้าง object ใหม่ทุกครั้งที่สร้าง context
</Callout>

</Step>

## ค่าลับและค่าที่เปลี่ยนตามสภาพแวดล้อม

อย่าเขียนรหัสผ่านลงใน config ใช้ตัวแปรแทน GX แทนค่า `${NAME}` ตอนใช้งาน

```python
source = context.data_sources.add_sqlite("sales", connection_string="${MY_DB_URL}")
```

ทดลองแล้ว: ตั้ง environment variable `MY_DB_URL` แล้วรันได้ ค่าที่เก็บใน config ยังเป็นข้อความ `${MY_DB_URL}` ไม่ใช่ค่าจริง (ปลอดภัยที่จะ commit) ส่วนไฟล์ `uncommitted/config_variables.yml` เป็นอีกแหล่งของตัวแปรสำหรับกรณีไม่ใช้ environment variable ซึ่งอ่านจากซอร์สว่า GX มองหาค่าตามลำดับ runtime, environment, ไฟล์นี้ แล้ว cloud (ไม่ได้ทดลองการแทนค่าจากไฟล์นี้)

</Step>

<Step>

## เช็กตัวเอง

- เครื่องของคุณมีโฟลเดอร์ `gx/` แต่ CI ไม่มี `gx.get_context()` ได้ context ชนิดอะไรในแต่ละที่ และจะทำให้เหมือนกันได้อย่างไร
- สร้าง validation definition ก่อนแล้วค่อย add suite จะเกิดอะไรขึ้นตอน `run()`
- ไฟล์ไหนในโฟลเดอร์ `gx/` ที่ไม่ควร commit

</Step>
