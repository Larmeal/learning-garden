## อะไรนับว่าเป็น Expectation ตัวเดียวกัน

บทหลักบอกไว้ว่า Suite จะข้ามการเพิ่ม Expectation ที่เหมือนกันทุกอย่าง ดังนั้นสคริปต์ `20_suite_edit.py` จึงทดลองดูว่า "เหมือนกัน" หมายถึงอะไร (GX 1.24.1) โดยทุกข้อใช้ `ExpectColumnValuesToBeBetween(column="age", min_value=0, max_value=120)` เป็นฐาน

| เพิ่มอะไร | จำนวน Expectation ใน Suite หลังเพิ่ม |
|---|---|
| ตัวฐาน | 1 |
| ตัวเดิมเป๊ะอีกครั้ง | 1 (ไม่เพิ่ม) |
| เปลี่ยน `max_value` เป็น 200 | 2 |
| ตัวฐานแต่ใส่ `mostly=0.9` | 3 |
| ตัวฐานแต่ใส่ `severity="warning"` | 4 |

`mostly` และ `severity` นับเป็นส่วนของตัวตน ตัวที่ต่างกันแค่สองค่านี้จึงอยู่ใน Suite พร้อมกันได้ ซึ่งมีประโยชน์ เช่นใส่กฎเดียวกันสองระดับ โดยให้ผ่านที่ 0.9 เป็นคำเตือน และผ่านเมื่อไม่มีผิดเลยเป็นข้อบังคับ ส่วนผลข้างเคียงคือ Suite อาจบวมได้โดยไม่รู้ตัว ถ้าทำซ้ำหลายรอบพร้อมแก้พารามิเตอร์เล็กน้อย

</Step>

## ลบ และ Suite ที่ยังไม่ Add

เราลบด้วย `suite.delete_expectation(expectation)` ได้ สคริปต์ทดลองลบข้อสุดท้าย แล้วจำนวนใน Suite ลดจาก 4 เป็น 3 และ `context.suites.get("s")` ก็เห็น 3 เหมือนกัน แปลว่าการลบบันทึกลง Store ทันที

Suite ที่สร้างด้วย `gx.ExpectationSuite(name="loose")` แล้วเพิ่ม Expectation เข้าไป จะมีข้อมูลอยู่ในตัวมันเอง (Len เป็น 1) แต่ไม่อยู่ใน `context.suites.all()` จนกว่าจะ `context.suites.add(...)` และการ `add_expectation` บันทึกลง Store ให้ก็ต่อเมื่อ Suite อยู่ใน Context แล้ว (ทดลองในบทหลัก)

<Callout type="warn" title="ที่ยังไม่ได้ทดลอง">
เรายังไม่ได้ทดลองว่ากฎที่ถูกแก้ด้วย `save()` มีผลกับ Validation Definition ที่สร้างไว้ก่อนหน้านี้อย่างไร และไม่ได้ทดลองกับ File Context ว่าไฟล์ JSON ของ Suite เปลี่ยนจริง
</Callout>

</Step>
