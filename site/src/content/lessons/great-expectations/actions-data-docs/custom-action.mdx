## Action ที่เขียนไฟล์สถานะ

บทหลักแสดงโครงของ `ValidationAction` ไว้แล้ว ส่วนในหน้านี้เรารันจริง (`27_actions_notify.py` ส่วนที่ 3, GX 1.24.1)

```python
class WriteStatus(ValidationAction):
    type: str = "write_status"
    name: str = "write_status"
    path: str = ""

    def run(self, checkpoint_result, action_context=None):
        Path(self.path).write_text("ok" if checkpoint_result.success else "failed")
        return {"written": self.path}

cp = gx.Checkpoint(name="cp_custom", validation_definitions=[vd],
                   actions=[WriteStatus(path=str(out))])
cp.run(batch_parameters={"dataframe": df})
```

ผลที่พิมพ์ออกมาเป็นดังนี้

```text
file content: failed | saw: {'context_type': 'ActionContext', 'success': False}
```

- ข้อมูลทำให้ Suite ไม่ผ่าน ไฟล์จึงมีคำว่า `failed` อยู่
- `run` ได้รับ `CheckpointResult` เต็ม ๆ (อ่าน `.success` ได้ และเข้าถึง `run_results` ได้เหมือนหน้า "[Checkpoint Results](/great-expectations/validation-checkpoints/checkpoint-result/)" ของ[บทที่ 7](/great-expectations/validation-checkpoints/#checkpointresult)) พร้อมกับ `ActionContext` อีกตัวหนึ่ง
- ฟิลด์ของ Action (ที่นี่คือ `path`) ประกาศเป็นฟิลด์ Pydantic แล้วส่งค่าเข้าไปตอนสร้าง
- ฟิลด์ `type` เป็นตัวบอกชื่อประเภทของ Action ตอนเก็บ Checkpoint ลงไฟล์ โดยคลาสจะถูกลงทะเบียนใน Registry ด้วยค่า `type` ตอนนิยาม (ตามคอมเมนต์ใน `MetaValidationAction` ของซอร์ส)

ส่วนที่ 5 ของสคริปต์ทดลองกับดักที่ Custom Expectation เคยเจอ ([บทที่ 12](/great-expectations/custom-expectations/registry-loading/#ผลที่เห็นจากสองโปรเซส)) กับ Action ด้วย โดย Process A สร้าง Checkpoint ที่มี `WriteStatus` ลงใน File Context แล้ว Process B ที่ไม่ได้ Import คลาสนี้ก็โหลด Context ขึ้นมา ผลที่ได้เป็นดังนี้

```text
B: ValidationActionRegistryRetrievalError | Invalid action configuration; no action of type write_status found.
```

ต่างจาก Custom Expectation ที่ Suite โหลดมาว่างเงียบ ๆ แต่กรณี Action นั้น `get_context()` จะ Raise ทันทีและบอกชื่อ Type ที่หาไม่เจอ ปัญหานี้จึงเห็นได้เร็วกว่า ทั้งสองกรณีมีต้นเหตุเดียวกัน คือคลาสต้องถูก Import ก่อน จึงจะอยู่ใน Registry

</Step>

## Action ที่ Raise

`Boom.run` ตั้งใจ Raise `RuntimeError("webhook is down")` ขึ้นมา แล้วสคริปต์ก็รัน Checkpoint ที่มี `Boom` เป็น Action เดียว ได้ผลดังนี้

```text
run raised: RuntimeError | webhook is down
results stored anyway: 1
```

ดังนั้น Slack ที่ล่มไม่ทำให้ผลตรวจหาย แต่ทำให้ `cp.run()` Raise และ Action หลังจากนั้นไม่ถูกรัน (ทดลองใน `06_actions_docs.py`) ถ้า Pipeline ไม่ได้ครอบ `try/except` ไว้ ทั้งงานก็จะล้มเพราะการแจ้งเตือนเสริมเพียงอย่างเดียว

## รูปแบบที่ปลอดภัย

```python
def run(self, checkpoint_result, action_context=None):
    try:
        post_to_my_service(checkpoint_result)
    except Exception as e:
        logging.warning("notification failed: %s", e)
    return {}
```

รูปแบบนี้เป็นข้อเสนอที่ได้จากพฤติกรรมที่ทดลองแล้ว (Action ที่ Raise ลาก Checkpoint ล้ม) แต่ตัวโค้ดนี้เองไม่ได้รันนะ

<Callout type="note" title="ผลข้างเคียงของการกลืน Error">
Action ที่กลืน Error จะไม่บอกเราว่าการแจ้งเตือนล้ม ดังนั้นควรเขียน Log ไว้เสมอ ไม่เช่นนั้นทีมจะเข้าใจว่าไม่มีเหตุอะไรเกิดขึ้น ทั้งที่ข้อความส่งไปไม่ถึง
</Callout>
