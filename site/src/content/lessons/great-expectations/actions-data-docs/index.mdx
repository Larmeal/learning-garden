## Action คืออะไร

Action คือขั้นตอนอัตโนมัติที่ Checkpoint จะรันให้หลังจากตรวจทุก Validation Definition เสร็จแล้ว มันจะรับ `CheckpointResult` เข้ามา แล้วทำอะไรต่อก็ได้ เช่นแจ้งเตือน หรืออัปเดตรายงาน

Action ที่ GX 1.24.1 มีให้ดูได้จาก `great_expectations.checkpoint.actions` ซึ่งมีดังนี้

| Action | ทำอะไร |
|---|---|
| `SlackNotificationAction` | ส่งข้อความเข้า Slack ผ่าน Webhook |
| `MicrosoftTeamsNotificationAction` | ส่งเข้า Teams |
| `PagerdutyAlertAction`, `OpsgenieAlertAction` | เปิด Incident |
| `EmailAction` | ส่งอีเมล |
| `SNSNotificationAction` | ส่งเข้า AWS SNS |
| `APINotificationAction` | เรียก HTTP Endpoint ที่กำหนด |
| `UpdateDataDocsAction` | สร้าง/อัปเดตหน้า Data Docs |

เราใส่ Action ลงใน Checkpoint เป็นรายการได้ด้วย `gx.Checkpoint(name=..., validation_definitions=[vd], actions=[...])` ส่วนค่าลับอย่าง Webhook ให้ใส่เป็น `${SLACK_WEBHOOK}` ตามที่เรียนไว้ใน[บทที่ 5](/great-expectations/context-stores/#ค่าลับและค่าที่เปลี่ยนตามสภาพแวดล้อม)

</Step>

## ลำดับและเงื่อนไข

<ActionsLab client:visible />

กฎต่อไปนี้ยืนยันแล้วด้วยการรัน (`06_actions_docs.py`)

1. Action จะทำงานหลังจากทุก Validation เสร็จ และผลตรวจถูกเก็บลง Store ไปเรียบร้อยแล้ว
2. `UpdateDataDocsAction` จะถูกย้ายมารันก่อน Action อื่น เพื่อให้ Action ที่ต้องการลิงก์ไปหา Data Docs ได้ URL ผ่าน `ActionContext`
3. ส่วน Action อื่นจะรันตามลำดับที่เราประกาศไว้ ถ้า Action ไหน Raise การรันจะหยุดตรงนั้น Action ที่เหลือจะไม่ถูกรัน และ `Checkpoint.run()` จะ Raise ออกมา (ทดลอง: `[first, boom, third]` รันแค่ `first` และ `boom`)
4. ถ้า Action "ไม่ส่ง" เพราะเงื่อนไขไม่ตรง ไม่ถือว่าเป็น Error นะ เพราะ Action ยังถูกเรียกอยู่ เพียงแต่เลือกที่จะเงียบ

</Step>

## เงื่อนไขการแจ้ง: notify_on และ Severity

Action แจ้งเตือนจะมี `notify_on` ให้เราเลือก ค่าที่ใช้ได้มีดังนี้ (อ่านจาก `should_notify()`)

| ค่า | แจ้งเมื่อ |
|---|---|
| `all` | ทุกครั้ง |
| `success` | ผ่านเท่านั้น |
| `failure` | ไม่ผ่านเท่านั้น |
| `critical` / `warning` / `info` | ไม่ผ่าน และ Expectation ที่ล้มและร้ายแรงที่สุดมีระดับนี้ |

เราตั้ง Severity ได้ที่ Expectation แต่ละข้อ โดยค่าเริ่มต้นคือ `critical`

```python
suite.add_expectation(
    gxe.ExpectColumnValuesToBeBetween(column="age", min_value=0, max_value=120, severity="warning")
)
result.get_max_severity_failure()   # FailureSeverity.CRITICAL ถ้ามีข้อ critical ล้มด้วย
```

ทดลองแล้ว: เมื่อข้อที่ตั้ง `warning` ล้ม และอีกข้อที่เป็น `critical` ล้มด้วย ระดับสูงสุดที่รายงานคือ Critical ดังนั้นเราจึงตั้ง PagerDuty เป็น `critical` เพื่อให้เรียกคนเฉพาะเรื่องร้ายแรง ส่วน Slack ตั้งเป็น `all` หรือ `failure` สำหรับทีม

</Step>

## Data Docs

Data Docs คือหน้า HTML ที่ GX สร้างขึ้นจาก Suite และผลตรวจ โดย `UpdateDataDocsAction` เป็นตัวสร้าง ผลจากการรันจริงเป็นดังนี้

```
uncommitted/data_docs/local_site/
  index.html                                  # หน้าแรก: รายการ suite และผลตรวจ
  expectations/<suite>.html                   # หน้าอธิบาย suite
  validations/<suite>/__none__/<run>/<batch>.html   # หน้าผลของแต่ละรอบ
```

เราเปิด `index.html` ในเบราว์เซอร์ได้ทันที แต่ละหน้าผลจะบอกว่า Expectation ไหนผ่านหรือล้ม พร้อมตัวอย่างค่าที่ผิดตาม `result_format` ที่ใช้ (ถ้าใช้ `BOOLEAN_ONLY` หน้าจะมีรายละเอียดน้อย)

Data Docs ที่สร้างใน `local_site` จะอยู่ในคอมพิวเตอร์ที่รัน ถ้าอยากให้ทีมเปิดดูได้ ก็ต้องเก็บไว้ในที่ที่แชร์กันได้ (เช่น Object Storage ที่ตั้ง Site เป็น Backend ซึ่งเส้นทางนี้ไม่ได้ทดลอง) ส่วน GX Cloud ที่เคยเป็นทางเลือกนี้ได้ปิดบริการไปแล้ว

</Step>

## เขียน Action เอง

เมื่อ Action ที่มีให้ไม่ตรงกับระบบของทีม เราสามารถสืบทอด `ValidationAction` ขึ้นมาเองได้

```python
from great_expectations.checkpoint.actions import ValidationAction

class WriteStatusFile(ValidationAction):
    type: str = "write_status_file"
    name: str = "write_status_file"

    def run(self, checkpoint_result, action_context=None):
        with open("last_status.txt", "w") as f:
            f.write("ok" if checkpoint_result.success else "failed")
        return {}
```

คลาสนี้จะถูกลงทะเบียนอัตโนมัติจากฟิลด์ `type` (Metaclass) เหมือนกับ Expectation และใน `06_actions_docs.py` มีตัวอย่าง Action ที่ Raise ไว้ให้ดูพฤติกรรมเมื่อ Action ล้ม

<Callout type="warn" title="Action เสริมที่ล้มลาก Checkpoint ล้มตาม">
Action ที่ Raise จะทำให้ `Checkpoint.run()` Raise ตามไปด้วย และ Action ที่อยู่หลังจากนั้นจะไม่ถูกรัน ดังนั้นถ้าไม่อยากให้ Webhook ที่ล่มลากทั้ง Pipeline ล้มไปด้วย ให้ดัก Error ภายใน `run()` ของ Action ที่เป็นการแจ้งเตือนเสริม (เช่นเขียน Log) และจำไว้ด้วยว่าผลตรวจถูกเก็บไปแล้วก่อนหน้านั้นเสมอ
</Callout>

</Step>

## เช็กตัวเอง

- ถ้า Checkpoint มี `[SlackAction, UpdateDataDocsAction]` ลำดับที่รันจริงคืออะไร และเพราะอะไร
- ถ้า Slack Webhook ใช้ไม่ได้ ผลตรวจของรอบนี้จะหายไปไหม
- ถ้าต้องการแจ้งเฉพาะเมื่อมีข้อมูลเสียร้ายแรง เราต้องตั้งค่าอะไรที่ Expectation และอะไรที่ Action

</Step>

## หน้าย่อยของบทนี้

1. notify_on ส่งเมื่อไหร่: ตารางผลการส่ง 24 ช่องจาก Slack ตัวปลอม
2. เขียน Action เอง และ Action ที่ล้ม: ผลตรวจรอดหรือไม่เมื่อ Action Raise
3. อ่าน Data Docs ให้เป็น: ข้อความในแต่ละหน้า และ BOOLEAN_ONLY เทียบ COMPLETE

</Step>
