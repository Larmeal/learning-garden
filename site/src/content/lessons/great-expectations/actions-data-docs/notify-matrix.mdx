## วิธีทดลองโดยไม่ส่งข้อความจริง

`SlackNotificationAction` ส่งข้อความด้วย HTTP POST ไปที่ webhook สคริปต์ `27_actions_notify.py` ตั้ง webhook เป็นเซิร์ฟเวอร์เล็กๆ บน `127.0.0.1` ที่นับ POST ที่เข้ามา ข้อความไม่ได้ออกนอกเครื่อง ทดลองกับสี่สถานการณ์ และหกค่า `notify_on` (GX 1.24.1)

| สถานการณ์ | กฎที่ตั้ง | ผล |
|---|---|---|
| pass | `age` ระหว่าง 0 ถึง 500 | ผ่านหมด |
| fail warning | `age` ระหว่าง 0 ถึง 120 ตั้ง `severity="warning"` | ล้ม 1 ข้อ ระดับ warning |
| fail critical | `name` ไม่เป็น null (ค่าเริ่มต้น critical) | ล้ม 1 ข้อ ระดับ critical |
| fail both | สองกฎข้างบนรวมกัน | ล้ม 2 ข้อ สูงสุดคือ critical |

ข้อมูลคือ `age = [10, 20, 300]`, `name = ['a', None, 'c']`

## สามข้อที่เห็นจากตาราง

1. `notify_on="warning"` ไม่ได้แปลว่า "warning ขึ้นไป" ในกรณี fail both (มีทั้ง warning และ critical ล้ม) มันไม่ส่ง เพราะระดับสูงสุดของข้อที่ล้มคือ critical ซึ่งไม่เท่ากับ warning ในซอร์ส `should_notify` เทียบแบบ `notify_on == max_severity` ถ้าต้องการให้ทั้ง warning และ critical ส่ง ให้ใช้ `failure`
2. ค่า `info` ไม่ส่งเลยในสี่สถานการณ์ เพราะไม่มีสถานการณ์ไหนมีข้อ info เป็นระดับสูงสุดที่ล้ม (ไม่ได้ทดลองตั้ง `severity="info"`)
3. ตั้ง action สองตัวเพื่อแยกช่อง เช่น Slack ของทีมเป็น `failure` และ PagerDuty เป็น `critical` ผลจึงต่างกันตามความร้ายแรง ตามที่บทหลักเสนอ

## หน้าตาของข้อความ

กรณี fail critical กับ `notify_on="all"` ได้ POST ที่ body มี key เดียวคือ `blocks` ขนาด 416 ตัวอักษร ข้อความที่อ่านได้มีหัวข้อ `slack_all - cp_fail_critical_all - Failure :no_entry:`, เวลารัน และสรุปว่า `*Asset*`, `*Expectation Suite*` กับ `*Summary*: 0 of 1 Expectations were met` ข้อความสั้น ไม่มีรายละเอียดของแถวที่ผิด หากต้องการรายละเอียดต้องมีลิงก์ไป Data Docs ซึ่งหน้าถัดไปอธิบาย

<Callout type="warn" title="ที่ทดลองและไม่ได้ทดลอง">
ทดลองเฉพาะ Slack action ผ่าน webhook ปลอม ส่วน Teams, PagerDuty, Opsgenie และ Email ใช้ฟังก์ชัน `should_notify` ตัวเดียวกันตามซอร์ส แต่ไม่ได้ส่งจริงสักตัว และ Opsgenie กับ PagerDuty มีค่า `notify_on` เริ่มต้นเป็น `failure`
