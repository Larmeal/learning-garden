## วางไว้ตรงไหน

GX ไม่ได้มีตำแหน่งตายตัวใน Pipeline และตำแหน่งที่เราวางมันก็เป็นตัวกำหนดว่าการตรวจจะป้องกันอะไรได้บ้าง

| ตำแหน่ง | ตรวจอะไร | เมื่อไม่ผ่านควร |
|---|---|---|
| ก่อนโหลดเข้า Staging | ไฟล์ที่ได้จาก Upstream (ว่างไหม คอลัมน์ครบไหม) | ปฏิเสธไฟล์และแจ้งเจ้าของแหล่งข้อมูล |
| หลังแปลงข้อมูล | ผลของ Transformation ของเราเอง (Key ซ้ำ ค่านอกช่วง) | หยุดและตามหาบั๊กใน Job |
| ก่อนเผยแพร่ให้ผู้ใช้ | ตารางที่ Dashboard หรือโมเดลจะอ่าน | ไม่ Publish เก็บรอบเก่าไว้ |

ข้อมูลเสียที่ตรวจเจอก่อนไหลต่อไปจะแก้ง่ายกว่าตรวจเจอหลังรายงานผิดไปแล้ว แต่ทุกจุดที่เราตรวจก็เพิ่มเวลาและต้นทุนด้วย ([บทที่ 8](/great-expectations/metrics-engines/#ต้นทุนมาจากไหน)) เพราะฉะนั้นให้เริ่มจากจุดที่ความเสียหายหนักที่สุดก่อน

</Step>

## Checkpoint ไม่ใช่ Gate

ย้อนไปที่[บทที่ 7](/great-expectations/validation-checkpoints/#กับดัก-ไม่-raise-เมื่อข้อมูลไม่ผ่าน) กันสักนิด `checkpoint.run()` จะคืนผลกลับมาเสมอ และไม่ Raise เมื่อข้อมูลไม่ผ่าน ดังนั้นถ้า Pipeline เขียนแค่นี้

```python
checkpoint.run(batch_parameters=...)
publish()
```

ข้อมูลเสียก็จะถูก Publish ไปด้วย เราจึงต้องมีโค้ดที่อ่านผลแล้วตัดสินใจเอง

<PipelineGate client:visible />

ลองสลับ "ตารางว่าง" ระหว่างสองรูปแบบโค้ดดู Gate ธรรมดา (`if not result.success`) จะปล่อยตารางว่างผ่านไป Publish ได้ ถ้า Suite ไม่มี Expectation จำนวนแถว ผลจึงดูสะอาดทั้งที่ไม่มีข้อมูลเลย

</Step>

## Quality Gate ที่แยกสาเหตุได้

ตัวอย่างต่อไปนี้รันได้จริงใน `09_pipeline_gate.py`

```python
def raised_exception(info) -> bool:
    if not info:
        return False
    if "raised_exception" in info:
        return bool(info["raised_exception"])
    return True            # metric ที่คำนวณไม่ได้มาในรูป dict ของ metric id

def classify(checkpoint_result):
    bad_data, broken = [], []
    for suite_result in checkpoint_result.run_results.values():
        for r in suite_result.results:
            if r.success:
                continue
            (broken if raised_exception(r.exception_info) else bad_data).append(r.expectation_config.type)
    return bad_data, broken

def gate(checkpoint, batch_parameters):
    result = checkpoint.run(batch_parameters=batch_parameters)
    # suite ว่าง (เช่น custom expectation โหลดไม่ขึ้น) "ผ่าน" โดยไม่ได้ประเมินอะไรเลย
    if any(r.statistics["evaluated_expectations"] == 0 for r in result.run_results.values()):
        raise QualityGateError("no expectations were evaluated")
    if result.success:
        return result
    bad_data, broken = classify(result)
    if broken:
        raise QualityGateError(f"expectations could not be evaluated: {broken}")
    raise QualityGateError(f"data failed: {bad_data}")
```

เมื่อรันกับห้ากรณี เราได้ผลจริงตามนี้

| ข้อมูล | ผลของ Gate |
|---|---|
| ดี | Publish |
| Suite ที่ไม่มี Expectation เลย | STOP: no expectations were evaluated |
| `order_id` มี Null และ `amount` = 99999 | STOP: Data Failed (Not Null, Between) |
| ตารางว่าง (Suite มี Row Count) | STOP: Data Failed (Row Count) |
| คอลัมน์ `amount` ถูกเปลี่ยนชื่อ | STOP: expectations could not be evaluated (Between) |

กรณีสุดท้ายสำคัญมาก เพราะข้อมูลไม่ได้ "เสีย" แต่ Schema เปลี่ยน คนที่ควรได้รับแจ้งจึงเป็นเจ้าของ Pipeline ไม่ใช่เจ้าของข้อมูล การแยกสองกลุ่มนี้ในข้อความแจ้งเตือนจะช่วยให้เรื่องไปถึงถูกคน

ส่วนกรณีแรกสุดมาจาก[บทที่ 12](/great-expectations/custom-expectations/registry-loading/#ตอนโหลด-suite-จากไฟล์-error-ถูกกลืน) และเป็นกับดักที่เงียบที่สุดในเส้นทางนี้ ถ้า Suite มี Custom Expectation แล้วโปรเซสที่โหลด Suite ไม่ได้ Import คลาสนั้น GX จะโหลด Suite มาเป็น Suite ว่างเปล่า แล้ว `run()` ก็ได้ `success=True` กับ `evaluated_expectations = 0` โดยไม่มี Error ใด ๆ (ทดลองแล้วใน `10_missing_import.py`) การตรวจ `evaluated_expectations` ใน Gate จึงเป็นด่านสุดท้ายที่กันเรื่องนี้ได้

</Step>

<Step>

## เลือกนโยบายเมื่อไม่ผ่าน

| นโยบาย | ทำอะไร | เหมาะกับ |
|---|---|---|
| หยุด | Raise ก่อน Publish | ข้อมูลที่ผิดแล้วเสียหายจริง (การเงิน) |
| กัก | ย้ายข้อมูลไปที่พัก เก็บรอบเก่าไว้ให้ผู้ใช้ | ตารางที่ผู้ใช้อ่านตลอดเวลา |
| เตือนแล้วไปต่อ | ส่งแจ้งเตือน แต่ Publish | ปัญหาที่ยอมรับได้ชั่วคราว |

เรายังผูกนโยบายกับ Severity ได้ด้วย โดย Expectation ที่ตั้ง `severity="warning"` ถ้าล้มจะเตือน ส่วน `critical` ถ้าล้มจะหยุด ตัวช่วยคือ `suite_result.get_max_severity_failure()` ซึ่งคืนระดับสูงสุดของข้อที่ล้ม

</Step>

## งานรายวัน: ส่งพารามิเตอร์ให้ครบ

ใน[บทที่ 6](/great-expectations/datasources-batches/#get_batch-เลือกไฟล์ไหน) เราเห็นแล้วว่า `get_batch()` ที่ไม่ได้รับพารามิเตอร์จะคืน Batch ล่าสุดกลับมาเงียบ ๆ ดังนั้นใน Pipeline รายวันเราควรบังคับให้ส่งพารามิเตอร์ทุกครั้ง

```python
from datetime import date

def params_for(day: date) -> dict:
    return {"year": day.year, "month": day.month, "day": day.day}   # จำนวนเต็ม ใน 1.24.1

result = gate(checkpoint, params_for(run_date))
```

และให้ `run_date` มาจาก Scheduler ที่กำหนดไว้ชัดเจน (ไม่ใช่ "วันนี้" ที่คำนวณในโค้ด) เพื่อให้รันย้อนหลัง (Backfill) และรันซ้ำได้ผลเหมือนเดิม เพราะ GX จะคำนวณใหม่ทั้งหมดทุกครั้งที่รันซ้ำ และเก็บผลรอบใหม่เพิ่มเข้าไป โดยไม่ทับรอบเก่า

<Callout type="note" title="orchestrator">
GX เป็นไลบรารี Python ธรรมดา จึงเรียกจาก Task ของ Airflow, Dagster, Prefect หรือ Cron ได้โดยตรง ตัวอย่างในเส้นทางนี้ไม่ได้ทดลองกับ Orchestrator ตัวใดโดยเฉพาะ แต่หลักที่ต้องคงไว้เหมือนกันมีสามอย่าง คือสร้าง Context ใน Task เอง (File Context ชี้ไปที่โฟลเดอร์ `gx/` ในโปรเจกต์) ส่งพารามิเตอร์ Batch ให้ชัดเจน และให้ Task ล้มเมื่อ Gate ล้ม
</Callout>

</Step>

## ทดสอบ Suite เหมือนทดสอบโค้ด

Suite ก็คือโค้ดของ Pipeline ดังนั้นเราควรมีการทดสอบมันด้วย

- เก็บตัวอย่างข้อมูลเล็ก ๆ ทั้งแบบที่ ควรผ่าน และแบบที่ ควรล้ม (ตารางว่าง, Null, ค่านอกช่วง, คอลัมน์หาย) แล้วทดสอบด้วย Ephemeral Context ใน CI ว่า Gate ตัดสินถูกหรือไม่ โดยมี `09_pipeline_gate.py` เป็นต้นแบบ
- รีวิวการเปลี่ยน Suite ผ่าน Pull Request ได้ เพราะ File Context เก็บ Suite เป็น JSON ในโฟลเดอร์ `gx/expectations/`
- ตั้ง `mostly` และช่วงค่าจากการสังเกตข้อมูลจริงหลายรอบ ไม่ใช่รอบเดียว แล้วทบทวนใหม่เมื่อธุรกิจเปลี่ยน

## ลองทำใน Repo นี้

1. เปิด `09_pipeline_gate.py` แล้วลบ `ExpectTableRowCountToBeBetween` ออก จากนั้นดูว่า "Empty Table" เปลี่ยนเป็นอะไร
2. เพิ่ม Expectation ที่ตั้ง `severity="warning"` แล้วเปลี่ยน `gate` ให้หยุดเฉพาะเมื่อมีข้อ `critical` ล้ม
3. ลองส่ง `batch_parameters` เป็น Dict ว่างให้กับ Batch Definition รายวัน แล้วดูว่าได้ Batch ไหน

## เช็กตัวเอง

- ทำไม `checkpoint.run()` ที่ตามด้วย `publish()` ตรง ๆ ถึงอันตราย
- Gate ที่ตรวจแค่ `result.success` จะพลาดอะไรไป (ลองนึกถึงตารางว่าง และ Expectation ที่พัง)
- ทำไมการรันย้อนหลังควรได้พารามิเตอร์วันที่มาจาก Scheduler

</Step>
