## ร้านค้าที่เชื่อทุกอย่างที่ลูกค้าส่งมา

นาย A เปิดร้านขายของออนไลน์เล็ก ๆ ในช่วงสุดสัปดาห์ เขาเขียนโค้ดเองทั้งหมด และมั่นใจมากว่า "ใครจะมาสนใจร้านเล็ก ๆ ของเรา" เรามาลองดูโค้ดที่เขาเขียนกัน โดยร้านของนาย A มีของสามอย่าง คือ `pen` ราคา 20, `book` ราคา 150 และ `bag` ราคา 900 พร้อม Order ของลูกค้าสองคน คือ Ann (Order 1) กับ Bob (Order 2) ซึ่งเป็นกระเป๋า

ฟังก์ชันแรกคือการอ่าน Order ตามเลขที่ส่งมา (รัน: `exercises/01_mindset.py`)

```python
def get_order_naive(order_id: int, who: str):
    return ORDERS.get(order_id)

leak = get_order_naive(2, "ann")     # ann ขอ Order เลข 2
# {'owner': 'bob', 'item': 'bag', 'qty': 1}
```

Ann ล็อกอินเข้ามาแล้วขอ Order เลข 2 ฟังก์ชันก็ส่งให้เลย ทั้งที่ Order นั้นเป็นของ Bob ตัวแปร `who` ถูกส่งเข้ามาแต่ไม่เคยถูกใช้เลย

ฟังก์ชันที่สองคือการคิดเงินตอน Checkout ซึ่งนาย A ให้ฝั่ง Browser ส่งราคามาด้วย เพราะ "จะได้ไม่ต้องไปค้นอีกรอบ"

```python
def checkout_naive(cart):
    return sum(line["price"] * line["qty"] for line in cart)

checkout_naive([{"item": "bag", "qty": 1, "price": 1}])     # 1
```

กระเป๋าราคา 900 ถูกคิดเงินแค่ 1 บาท เพราะลูกค้าเป็นคนบอกราคาเอง ส่วนฟังก์ชันที่สามคือการค้นหา ซึ่งรับตัวเลข `limit` มาจาก URL แล้วส่งต่อให้ฐานข้อมูลไปเลย ถ้าใครใส่ 10,000,000 มา ฐานข้อมูลก็ต้องทำงานตามนั้น (`search_naive(10_000_000)` ได้ 10,000,000 กลับมา)

สามฟังก์ชันนี้ผิดที่ต่างกัน แต่มีต้นเหตุเดียวกัน คือ **เชื่อสิ่งที่ลูกค้าส่งมามากเกินไป** เดี๋ยวเราจะเห็นว่าช่องโหว่เกือบทั้งหมดในเส้นทางนี้มาจากต้นเหตุนี้

## สามสิ่งที่ต้องรักษา

ลองกลับไปดูสามฟังก์ชันเมื่อกี้อีกที แต่ละอันเสียสิ่งที่ต่างกัน ฟังก์ชันแรกทำให้ข้อมูลของ Bob รั่วไปถึง Ann ฟังก์ชันที่สองทำให้ข้อมูลที่ไม่ควรแก้ได้ (ราคา) ถูกแก้ และฟังก์ชันที่สามทำให้คนอื่นอาจใช้ร้านไม่ได้เพราะฐานข้อมูลยุ่งอยู่กับงานของคนเดียว

หนังสือ API Security in Action เรียกสามสิ่งนี้ว่า **CIA Triad** (หนังสือ: API Security in Action หัวข้อ 1.4.2 หน้า 14)

| ตัวย่อ | ชื่อเต็ม | หมายถึง | ฟังก์ชันของนาย A |
|---|---|---|---|
| C | Confidentiality | ข้อมูลอ่านได้เฉพาะคนที่ควรอ่าน | อ่าน Order ของ Bob |
| I | Integrity | ไม่มีใครสร้าง แก้ หรือลบข้อมูลโดยไม่มีสิทธิ์ | แก้ราคาเอง |
| A | Availability | ผู้ใช้ที่ถูกต้องเข้าใช้ได้เมื่อต้องการ | ขอ 10,000,000 แถว |

หนังสือบอกด้วยว่ายังมีเป้าหมายอย่างอื่นอีก เช่น Accountability คือรู้ว่าใครทำอะไร และ Non-repudiation คือคนที่ทำแล้วปฏิเสธไม่ได้ แต่ทั้งสามตัวข้างบนคือสิ่งที่เราจะถามเสมอเมื่อดูช่องโหว่หนึ่งอัน ว่ามันทำลายอะไร

ส่วนวิธีแก้ในทั้งสามกรณีเป็นรูปแบบเดียวกัน คือย้ายกฎไปอยู่ฝั่ง Server ตัวอย่างเช่น `get_order_checked` ตรวจว่า `order["owner"] == who`, `checkout_checked` ไปค้นราคาจาก `PRICES` เองโดยไม่สนใจ `price` ที่ส่งมา และ `search_checked` ตัด `limit` ไว้ที่ 100 ผลที่รันได้คือ Ann ถูกปฏิเสธ, กระเป๋าถูกคิด 900 และคำขอ 10,000,000 แถวได้แค่ 100

## Request หนึ่งอันวิ่งผ่านกี่จุด

เมื่อลูกค้ากดปุ่มสั่งซื้อ Request ไม่ได้ไปถึงฐานข้อมูลโดยตรง แต่ต้องผ่านห้าจุด คือ Browser, เครือข่าย, Web Server, โค้ดของแอป แล้วถึง Database และระหว่างทางมีสองจุดที่ข้อมูลข้ามจากที่ที่เราคุมไม่ได้เข้ามาในระบบของเรา ซึ่งเรียกว่า **Trust Boundary** ตัวเลขห้าจุดกับสองเส้นแบ่งนี้ถูก Assert ไว้ใน `01_mindset.py` แล้ว

ลองเลือกการโจมตีในแล็บข้างล่างทีละอัน แล้วกดเล่น ซองจดหมายคือ Request ที่วิ่งผ่านอาคารทั้งห้า พอถึงจุดที่โดนโจมตี ผู้โจมตีจะออกมายืนตรงนั้น การ์ดตรงกลางคือสิ่งที่เขาส่งเข้าไปแทน Request ปกติ และการ์ดทางขวาคือสิ่งที่เขาได้กลับไป พร้อมตัวอักษร C, I หรือ A ที่บอกว่าเสียอะไร ตอนท้ายจะมีโล่ของด่านป้องกันขึ้นมา ลองสังเกตว่าการโจมตีแต่ละแบบไม่ได้อยู่จุดเดียวกัน SQL Injection กับ IDOR เกิดที่โค้ดของแอป ในขณะที่ XSS กับ CSRF เกิดฝั่ง Browser

แต่ละการโจมตีในแล็บนี้มีบทของมันเองในเส้นทางนี้ ไม่ต้องกังวลถ้ายังไม่รู้จักชื่อบางอัน เราจะค่อย ๆ ไล่ไปทีละอันพร้อมกับรันของจริง

## ถามสี่ข้อก่อนเขียนโค้ด (Threat Model)

ก่อนที่จะไปเรียนช่องโหว่ทีละอัน เรามีวิธีคิดที่ใช้ได้กับระบบทุกแบบ เรียกว่า **Threat Modeling** ซึ่งก็คือการนั่งดูแผนผังของระบบแล้วถามคำถามไม่กี่ข้อ ว่ามีอะไรที่มีค่า (Asset) มีใครหรืออะไรจะมาทำร้ายได้ (Threat) มันเข้ามาทางไหน (Attack Surface) และเรามีอะไรกั้นอยู่ (Defence) หนังสือ API Security in Action แนะนำวิธีจัดหมวดภัยที่เรียกว่า **STRIDE** ซึ่งมีหกตัวอักษร และแต่ละตัวทำลายสิ่งที่ต่างกัน (หนังสือ: API Security in Action บทที่ 1 หน้า 18)

| ภัย | ทำลายอะไร | ตัวอย่างในร้านนาย A |
|---|---|---|
| Spoofing | การยืนยันตัวตน | ใครสักคนแกล้งเป็น Ann |
| Tampering | Integrity | แก้ราคาเองตอน Checkout |
| Repudiation | การปฏิเสธไม่ได้ | ลบ Order แล้วบอกว่าไม่ได้ทำ เพราะไม่มี Log |
| Information Disclosure | Confidentiality | Ann อ่าน Order ของ Bob |
| Denial of service | Availability | ขอ 10,000,000 แถว |
| Elevation of privilege | การให้สิทธิ์ | ผู้ใช้ทั่วไปสั่งลบผู้ใช้อื่น |

เราเช็กไว้ใน Exercise ว่าหกตัวนี้ทำลายหกสิ่งที่ต่างกันจริง ไม่ซ้ำกัน ส่วนที่ใช้บ่อยที่สุดคือเอาตารางนี้มาวางข้างแผนผังห้าจุดเมื่อกี้ แล้วถามทีละจุดว่า "ที่จุดนี้ ภัยทั้งหกแบบเกิดได้ไหม" ไม่ต้องตอบถูกทั้งหมดในรอบเดียว เป้าหมายคือเห็นจุดที่เราลืมนึกถึง

<Callout type="note" title="ทำไมเริ่มจากวิธีคิด ไม่ใช่เครื่องมือ">

หนังสือ Web Application Security พูดไว้ว่าสิ่งที่บอกว่าสถาปัตยกรรมปลอดภัยหรือไม่ มักเป็นสัญญาณง่าย ๆ ที่มองเห็นจากภายนอก เช่น มีหลายชั้นป้องกันหรือเปล่า หรือเขียนระบบยืนยันตัวตนเองใหม่หมดทั้งที่มีของที่ผ่านการใช้งานมาแล้ว (หนังสือ: Web Application Security บทที่ 7 หน้า 99) เราจึงใช้เวลาตรงนี้กับวิธีมองก่อน แล้วค่อยไปดูเครื่องมือใน[บทถัดไป](/app-security/crypto-basics/)

</Callout>
