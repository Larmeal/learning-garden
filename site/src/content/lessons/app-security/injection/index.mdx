## Password ที่เป็น ' OR '1'='1

ร้านของนาย A เขียนฟอร์มล็อกอินด้วยการต่อสตริงเข้าไปใน SQL เพราะเป็นวิธีที่เห็นในตัวอย่างทั่วไป (รัน: `exercises/08_injection.py`)

```python
def login_naive(name, password):
    sql = f"SELECT name, role FROM users WHERE name = '{name}' AND password = '{password}'"
    return sql, db.execute(sql).fetchall()
```

ถ้าผู้ใช้ใส่ `ann` กับ `pw-ann` Query ที่ได้ก็ถูกต้องและคืนแถวเดียว แต่ถ้าผู้ใช้ใส่ Password เป็น `' OR '1'='1` Query จะกลายเป็น

```sql
SELECT name, role FROM users WHERE name = 'ann' AND password = '' OR '1'='1'
```

เครื่องหมาย `'` ที่ผู้ใช้พิมพ์ไปปิดสตริงของ Password ก่อนเวลา ส่วน `OR '1'='1'` ที่ตามมาไม่ใช่ข้อความอีกแล้ว มันกลายเป็นเงื่อนไขของ SQL ที่เป็นจริงเสมอ ผลที่ Assert ไว้คือผู้โจมตีล็อกอินได้โดยไม่ต้องรู้ Password และได้แถวกลับมาสองแถว อีกแบบคือใส่ชื่อเป็น `admin' --` ซึ่ง `--` เปลี่ยนส่วนที่เหลือของบรรทัด (รวมการเช็ก Password) ให้เป็นคอมเมนต์ ได้แถวของ `admin` ตรง ๆ

ทุกอย่างที่เกิดขึ้นคือ **ข้อมูลที่ผู้ใช้พิมพ์กลายเป็นส่วนหนึ่งของโค้ด** ต้นเหตุเดียวกับบทแรก คือโค้ดเชื่อสิ่งที่ลูกค้าส่งมามากเกินไป (หนังสือ: Web Application Security บทที่ 13 หน้า 147)

</Step>

## ลองเทียบสองวิธีข้างกัน

ในแล็บข้างล่างเลือกฟอร์มกับสิ่งที่พิมพ์ ฝั่งซ้ายคือ Query ที่ต่อสตริง ส่วนที่ผู้ใช้พิมพ์ถูกไฮไลต์ไว้ ให้ดูว่าเครื่องหมาย `'` ทำให้ส่วนที่ไฮไลต์หลุดออกมานอกสตริง ฝั่งขวาคือ Query เดียวกันที่ส่งค่าเป็น **Parameter** ซึ่งตัวฐานข้อมูลรับ SQL กับค่าแยกกัน ค่าที่ส่งมาจึงไม่มีทางกลายเป็นคำสั่ง

ลองเปลี่ยนไปที่ฟอร์มค้นหา แล้วเลือก UNION ผู้โจมตีใส่ข้อความที่ปิดสตริงแล้วต่อ `UNION SELECT name, password FROM users` ทำให้ช่องค้นหาสินค้าคืนชื่อกับ Password ของผู้ใช้ (ผลที่ Assert ไว้คือมีแถว `('admin', 'S3cretAdm1n')` อยู่ในผลค้นหา) ผู้โจมตีต้องให้จำนวนคอลัมน์ของ Query ที่ต่อเข้าไปเท่ากับ Query เดิม ซึ่งสองคอลัมน์ในตัวอย่างนี้ ถ้าจำนวนคอลัมน์ไม่เท่า SQLite จะแจ้ง Error ซึ่งเป็นวิธีที่ผู้โจมตีใช้นับคอลัมน์ด้วย (แบบฝึกเช็กทั้งสองอย่าง)

ฝั่งขวา ไม่ว่าจะใส่อะไรเข้าไป ผู้ใช้ที่ใส่ Password ผิดได้แถวว่าง และข้อความ UNION ถูกมองเป็นแค่ชื่อสินค้าที่ไม่มีอยู่จริง คนที่ล็อกอินปกติและคนที่ค้น `pen` ยังได้ผลตามเดิม

## ถอดรหัสผ่านจากคำตอบแค่ เจอ หรือ ไม่เจอ

บางครั้งหน้าเว็บไม่พิมพ์ผลของ Query ออกมาเลย บอกแค่ "เจอ" หรือ "ไม่เจอ" ผู้โจมตีก็ยังได้ข้อมูลออกไป เพราะเขาถามคำถามที่ตอบแค่ใช่หรือไม่ได้ เช่น ตัวอักษรที่ 1 ของรหัสผ่านแอดมินมีรหัส ASCII มากกว่า 79 ไหม แล้วค่อยหดช่วงลงครึ่งหนึ่งทุกคำถาม

แบบฝึกทำให้ดู รหัสผ่านของแอดมินคือ `S3cretAdm1n` ซึ่งยาว 11 ตัวอักษร ผู้โจมตีถามด้วย Query ที่ฝังคำถามไว้ในเงื่อนไขของ SQL แล้วดูแค่ว่ามีแถวคืนมาไหม ผลที่ถอดได้ตรงกับรหัสผ่านทั้งหมด และใช้คำขอ 85 ครั้ง คือต่อหนึ่งตัวอักษรใช้หนึ่งคำถามว่าตัวอักษรนั้นมีอยู่ไหม แล้วอีก 6 หรือ 7 คำถามเพื่อตัดช่วง 95 ค่าให้เหลือค่าเดียว กดเล่นแล็บข้างล่างดูว่าแต่ละคำถามตัดช่วงลงไปครึ่งหนึ่งอย่างไร

<BlindSqliLab client:visible />

สิ่งที่ควรสังเกตคือถ้าผู้โจมตีต้องเดาทั้งรหัสผ่านทีเดียวจะยากมาก แต่เมื่อถามได้ทีละตัวอักษร งานลดจากราว 95 ยกกำลัง 11 ลงเหลือ 85 ครั้ง ข้อมูลที่รั่วทีละบิตก็ยังรั่ว

## วิธีแก้ และสิ่งที่ Parameter ทำไม่ได้

วิธีแก้หลักคือ **Parameterized Query** `db.execute("SELECT name, role FROM users WHERE name = ? AND password = ?", (name, password))` แบบฝึกยืนยันว่าชุดข้อความโจมตีเดิม (`' OR '1'='1`) ไม่ได้อะไรกลับมา และผู้ใช้ปกติยังล็อกอินได้ ข้อความ UNION ในช่องค้นหากลายเป็นแค่ข้อความที่เรียงตัวอักษรในชื่อสินค้า ซึ่งไม่มีสินค้าไหนชื่ออย่างนั้น

แต่ Parameter ใช้แทนได้เฉพาะ **ค่า** ไม่ใช่ชื่อคอลัมน์หรือชื่อตาราง เช่น `ORDER BY` ที่ให้ผู้ใช้เลือกคอลัมน์ที่จะเรียง เราใส่เป็น `?` ไม่ได้ ทางที่ถูกคือ **Allow List** รายการชื่อที่เราอนุญาตเอง (ในแบบฝึกคือ `name` กับ `price`) ข้อความอื่นถูกปฏิเสธก่อนไปถึง SQL ผลที่ได้คือ `price` ผ่าน ส่วน `price; DROP TABLE products` ถูกปฏิเสธ และตารางยังมีครบสามแถว (หนังสือ: Web Application Security บทที่ 25 หน้า 259 ถึง 265)

</Step>

## Command Injection: เรื่องเดียวกันผ่าน Shell

ปัญหาแบบเดียวกันเกิดเมื่อเรานำข้อความของผู้ใช้ไปต่อเป็นคำสั่งของระบบปฏิบัติการ แบบฝึกใช้ Python ของเราเองเป็นโปรแกรมที่พิมพ์ Argument ที่ได้รับ และให้ผู้ใช้ส่งชื่อไฟล์เป็น `report.txt & echo INJECTED`

เมื่อเราต่อข้อความเข้ากับคำสั่งแล้วสั่งผ่าน Shell (`shell=True`) Shell เห็นเครื่องหมาย `&` เป็นตัวคั่นคำสั่ง และรันคำสั่งที่สองคือ `echo INJECTED` ด้วย ผลที่พิมพ์ออกมามีทั้ง `ARGS= ['report.txt']` และบรรทัด `INJECTED` ซึ่งเป็นสิ่งที่ไม่มีใครตั้งใจให้ทำ แต่ถ้าส่งเป็น **รายการของ Argument** ให้ระบบเรียกโปรแกรมตรง ๆ โดยไม่ผ่าน Shell ข้อความทั้งก้อนจะมาถึงโปรแกรมเป็น Argument เดียว (`ARGS= ['report.txt & echo INJECTED']`) และไม่มีอะไรถูกรันเพิ่ม (หนังสือ: Web Application Security บทที่ 13 หน้า 155)

หลักการเหมือนกับ SQL ทุกอย่าง ข้อมูลกับคำสั่งต้องเดินแยกทางกัน ใช้วิธีที่ระบบให้แยกมันให้ ก่อนที่จะคิดกรองอักขระ

<Callout type="note" title="ที่ยังไม่ได้ลอง">

แบบฝึกรันกับ SQLite และ Shell ของ Windows ฐานข้อมูลอื่นอย่าง MySQL และ PostgreSQL มีรายละเอียดต่างออกไป (เช่นวิธีคอมเมนต์และชื่อฟังก์ชัน) NoSQL Injection และ Injection ผ่านภาษาอื่น เช่น LDAP ไม่ได้รันในบทนี้

</Callout>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| Query ที่ต่อสตริงถูกแทรกด้วย `' OR '1'='1` และ `admin' --` และล็อกอินได้โดยไม่มีรหัสผ่าน | รัน: `exercises/08_injection.py` |
| UNION ทำให้ช่องค้นหาคืนชื่อและ Password จากตาราง Users และจำนวนคอลัมน์ไม่เท่าได้ Error | รัน: `exercises/08_injection.py` |
| ถอดรหัสผ่าน 11 ตัวอักษรจากคำตอบ เจอ หรือ ไม่เจอ ด้วยคำขอ 85 ครั้ง | รัน: `exercises/08_injection.py` และแล็บ (ข้อมูลจาก `injection.json`) |
| Parameterized Query ทำให้ Payload เดิมไม่ได้อะไร และผู้ใช้ปกติยังล็อกอินได้ | รัน: `exercises/08_injection.py` |
| ชื่อคอลัมน์ใส่เป็น Parameter ไม่ได้ ต้องใช้ Allow List | รัน: `exercises/08_injection.py` และหนังสือ: Web Application Security บทที่ 25 หน้า 259 ถึง 265 |
| Prepared Statements | หนังสือ: Web Application Security บทที่ 25 หน้า 261 |
| `shell=True` รันคำสั่งที่สอง ส่วนรายการ Argument ไม่รัน | รัน: `exercises/08_injection.py` (Shell ของ Windows) และหนังสือ: Web Application Security บทที่ 13 หน้า 155 |
| ภาพรวมของ SQL Injection และ Command Injection | หนังสือ: Web Application Security บทที่ 13 หน้า 147 |
| MySQL, PostgreSQL, NoSQL และ LDAP Injection | ไม่ได้รัน |

</Step>
