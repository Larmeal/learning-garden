## ตาราง Users ที่หลุดออกไป

สมมติว่าร้านของนาย A ถูกเจาะ และมีคนได้ตาราง `users` ไปทั้งตาราง นาย A ไม่ได้เก็บ Password ตรง ๆ เขาเก็บเป็น SHA-256 เพราะจำได้จาก[บทที่แล้ว](/app-security/crypto-basics/)ว่า Hash ย้อนกลับไม่ได้ ตารางที่หลุดไปมีหน้าตาอย่างนี้ (รัน: `exercises/04_passwords.py`)

```text
ann  e4ad93ca07acb8d908a3...
bob  e4ad93ca07acb8d908a3...
cat  48486e1514e842346ff4...
dan  1c8bfe8f801d79745c46...
eve  65e84be33532fb784c48...
```

มีอะไรแปลกไหม? Ann กับ Bob มี Hash เหมือนกันเป๊ะ แปลว่าทั้งสองคนตั้ง Password เหมือนกัน ผู้โจมตีไม่ต้องรู้ว่าคือคำว่าอะไรก็รู้แล้วว่าสองคนนี้ใช้ Password เดียวกัน ถ้าถอดได้คนหนึ่ง ก็ได้ทั้งสองคนทันที

ยิ่งไปกว่านั้น ผู้โจมตีไม่ต้องไล่ลองทีละคน เขาทำ **ตารางค้นหา** ขึ้นมาครั้งเดียว โดยเอา Password ที่คนนิยมตั้ง 1,000 คำมา Hash ไว้ล่วงหน้า แล้วเอาค่าในตารางที่รั่วไปเทียบ ผลที่รันได้คือถอดได้ 4 ใน 5 คน (Ann, Bob, Dan, Eve) เหลือแค่ Cat ที่ตั้ง `Tr0ub4dor&3` ซึ่งไม่อยู่ในรายการ

## Salt ทำให้ Password ที่เหมือนกันไม่เหมือนกัน

วิธีแก้คือเติม **Salt** ซึ่งเป็นข้อความสุ่มของผู้ใช้แต่ละคนเข้าไปหน้า Password ก่อน Hash คนละ Salt กัน Hash ก็ต่างกัน แม้ Password จะเหมือนกัน หนังสือ API Security in Action ระบุว่าการเก็บ Password ควรใช้ Salt สุ่มสำหรับแต่ละ Password (หนังสือ: API Security in Action บทที่ 3 หน้า 78)

ลองสลับ Salt ในแล็บข้างล่าง ตอนที่ปิด Salt ให้ดูว่าแถวของ Ann กับ Bob มีเส้นวงเล็บบอกว่า Hash เหมือนกัน และสี่แถวถูกถอดด้วยตารางเดียว พอเปิด Salt Hash ของทั้งสองคนไม่เหมือนกันแล้ว และตารางที่สร้างไว้ก่อนหน้านั้นหาอะไรไม่เจอเลย

<SaltLab client:visible />

ที่เห็นในแล็บคือแบบฝึกยืนยันให้ครบสามข้อ ข้อแรก Hash ของ Ann กับ Bob ไม่เหมือนกันเมื่อมี Salt ข้อที่สอง ตารางที่สร้างไว้ก่อนหน้านั้นไม่เจออะไร และข้อที่สามคืองานของผู้โจมตีเพิ่มจากการไล่รายการ 1,000 คำหนึ่งรอบ เป็นไล่ใหม่ทุกคน เท่ากับ 5,000 ครั้ง ในตัวอย่างนี้ Salt ในแบบฝึกคำนวณจากชื่อผู้ใช้เพื่อให้ตัวเลขซ้ำได้ ของจริงต้องสุ่ม 16 ไบต์ใหม่ทุกครั้ง (`secrets.token_bytes(16)` ที่แบบฝึกเช็กว่าต่างกันทุกครั้งที่เรียก)

Salt ไม่ต้องเป็นความลับ มันเก็บอยู่ข้าง Hash ในตารางได้เลย หน้าที่ของมันคือทำให้งานของผู้โจมตีต้องทำซ้ำสำหรับผู้ใช้แต่ละคน

## แต่ Hash ที่เร็วก็ยังเดาได้เร็ว

Salt ช่วยเรื่องการใช้ตารางร่วมกัน แต่ผู้โจมตียังเดา Password ทีละคนได้อยู่ แล้วเดาเร็วแค่ไหน? แบบฝึกวัดว่าใน 1 Core ของคอมพิวเตอร์เครื่องที่รัน แต่ละวิธีเดาได้กี่ครั้งต่อวินาที (ตัวเลขข้างล่างเป็นของรอบที่ใช้ทำแล็บ คอมพิวเตอร์เครื่องอื่นหรือรอบอื่นจะต่างออกไป)

| วิธีเก็บ | เดาได้ต่อวินาที (ต่อ 1 Core) |
|---|---|
| SHA-256 ธรรมดา | ราว 1,300,000 ครั้ง |
| PBKDF2 (SHA-256, 600,000 รอบ) | ราว 7 ครั้ง |
| Scrypt (N=32768, r=8, p=1) | ราว 3 ครั้ง |

แบบฝึก Assert ว่า PBKDF2 และ Scrypt ช้ากว่า SHA-256 ธรรมดาอย่างน้อย 1,000 เท่า (ในรอบที่วัดได้ ช้ากว่าหลายแสนเท่า) และการล็อกอินหนึ่งครั้งด้วย Hash ที่ช้านี้ยังใช้เวลาไม่ถึงหนึ่งวินาที ซึ่งผู้ใช้จริงไม่รู้สึก แต่ผู้โจมตีที่ต้องเดาล้านครั้งรู้สึกมาก นี่คือเหตุผลที่เราใช้ Hash ที่ **ช้าโดยตั้งใจ** สำหรับ Password โดยเฉพาะ ตรงข้ามกับที่เราอยากได้จาก Hash ทั่วไป

แล็บข้างล่างเอาความเร็วนี้ไปคำนวณเวลาที่ใช้เดาครึ่งหนึ่งของทุกความเป็นไปได้ ลองเลือกชนิดของ Password แล้วสลับจำนวน Core ของผู้โจมตี ดูว่าแท่งของ SHA-256 ธรรมดาอยู่ใกล้ซ้ายสุดตลอด ส่วนแท่งของ Scrypt ไกลกว่าหลายระดับ

<PasswordCrackLab client:visible />

ตัวอย่างเช่น Password ที่เป็นตัวอักษรกับตัวเลข 8 ตัว (47.6 บิต) ถ้าเก็บเป็น SHA-256 ธรรมดา Core เดียวเดาครึ่งหนึ่งหมดในราว 2.5 ปี แต่ถ้าเก็บด้วย Scrypt ใช้ราวล้านปี ตัวเลขนี้ขึ้นกับคอมพิวเตอร์ที่วัด และกับจำนวน Core ที่ผู้โจมตีมี (ซึ่งในแล็บเป็นตัวอย่างของผู้เขียน) อย่างไรก็ดี สิ่งที่ไม่เปลี่ยนคืออัตราส่วนระหว่างสองวิธี

<Callout type="note" title="Bcrypt และ Argon2">

หนังสือกับเอกสารทั่วไปแนะนำ Bcrypt, Scrypt และ Argon2 ซึ่งทำงานบนแนวคิดเดียวกัน คือช้าและปรับความช้าได้ แบบฝึกนี้ใช้ Scrypt กับ PBKDF2 เพราะมีอยู่ในไลบรารีมาตรฐานของ Python โดยไม่ต้องติดตั้งอะไร ส่วน Bcrypt กับ Argon2 ผู้เขียนไม่ได้รันให้ดู

</Callout>

## เก็บและตรวจให้ถูกวิธี

สิ่งที่ต้องเก็บในตารางมีสามอย่าง คืออัลกอริทึม Salt และค่า Hash แบบฝึกเก็บรวมเป็นข้อความเดียวรูปแบบ `scrypt$salt$hash` เพื่อให้เวลาตรวจ ไม่ต้องไปหาที่อื่นอีก

```python
def hash_password(pw, salt):
    return "scrypt$" + salt.hex() + "$" + hashlib.scrypt(pw.encode(), salt=salt, n=2**14, r=8, p=1, maxmem=64*1024*1024).hex()

def verify_password(pw, stored):
    _, salt_hex, digest_hex = stored.split("$")
    again = hashlib.scrypt(pw.encode(), salt=bytes.fromhex(salt_hex), n=2**14, r=8, p=1, maxmem=64*1024*1024)
    return hmac.compare_digest(again.hex(), digest_hex)
```

`hash_password` เอา Password กับ Salt ไปผ่าน Scrypt แล้วต่อเป็นข้อความหนึ่งก้อน ส่วน `verify_password` แยก Salt ออกจากก้อนที่เก็บไว้ คำนวณใหม่ด้วย Password ที่รับมา แล้วเทียบด้วย `hmac.compare_digest` เหมือนที่เราใช้เทียบ Tag ใน[บทที่แล้ว](/app-security/crypto-basics/) ผลที่ Assert คือ Password ที่ถูกผ่าน ส่วน `tr0ub4dor&3` (ตัวพิมพ์เล็ก) ไม่ผ่าน

ในงานจริง เราไม่เขียนเองแบบนี้ เราใช้ไลบรารีที่ผ่านการใช้งานมามาก และเลือกพารามิเตอร์ตามคำแนะนำปัจจุบัน ที่แบบฝึกเขียนเองก็เพื่อให้เห็นว่าข้างในมีอะไร หนังสือ Web Application Security พูดเรื่องการ Hash Credentials และ 2FA ไว้เหมือนกัน (หนังสือ: Web Application Security บทที่ 18 หน้า 197)

</Step>

## ความยาวของ Password ก็มีผล

เมื่อเก็บถูกวิธีแล้ว Password ที่ผู้ใช้ตั้งยังมีผล เราวัดความแข็งเป็น **บิต** คือ log2 ของจำนวน Password ที่เป็นไปได้ แต่ละบิตที่เพิ่มทำให้ผู้โจมตีต้องเดาเพิ่มเป็นสองเท่า

| ชนิด | บิต |
|---|---|
| เลข 6 หลัก | 19.9 (ราวหนึ่งล้านแบบ) |
| ตัวพิมพ์เล็ก 8 ตัว | 37.6 |
| ตัวอักษรกับตัวเลข 8 ตัว | 47.6 |
| คำสุ่ม 4 คำจากรายการ 2,048 คำ | 44.0 |

ข้อที่ควรสังเกตคือคำสุ่มสี่คำ ซึ่งจำง่ายกว่ามาก มีความแข็งใกล้เคียงกับตัวอักษรผสมแปดตัวที่จำยาก เงื่อนไขคือคำต้องสุ่มจริง ถ้าผู้ใช้เลือกคำเอง เช่นเอาเพลงโปรดมาต่อกัน ตัวเลข 44 บิตนี้จะไม่จริงอีกต่อไป (ข้อสังเกตของผู้เขียน ไม่ได้รันกับ Password ที่คนตั้งเอง)

</Step>
