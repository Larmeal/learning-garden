## บัตรผ่านที่ไม่ต้องมีตารางไว้เทียบ

Session Cookie ใน[บทที่แล้ว](/app-security/sessions-csrf/) ต้องให้ Server เก็บตารางว่า ID ไหนคือใคร ถ้ามี Server ร้อยตัวที่ต้องใช้ตารางเดียวกัน หรือแอปมือถือที่ไม่ได้ใช้ Cookie วิธีนั้นก็เริ่มไม่สะดวก อีกแนวคิดหนึ่งคือให้ Server เซ็นบัตรผ่านใบหนึ่งที่เขียนข้อมูลไว้ในตัวเลย เช่น "ผู้ถือคือ Ann, Role คือ User, หมดอายุอีก 15 นาที" แล้วตรวจแค่ลายเซ็น ไม่ต้องเปิดตารางไหน นี่คือ **JWT (JSON Web Token)** (หนังสือ: API Security in Action บทที่ 6 หน้า 181)

เราสร้างเองด้วยฟังก์ชันไม่กี่บรรทัดใน `jwtlib.py` เพื่อให้เห็นทุกส่วน ผลของ `exercises/06_jwt.py` ออกมาหน้าตาอย่างนี้

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhbm4i...(ตัดกลาง).fGWuPPx8hhpc8xR-j366npMM-StFwDk3DAWq-6NYVeM
```

มันคือสามส่วนคั่นด้วยจุด (ผลที่ Assert ไว้คือมีจุดสองจุด และไม่มีเครื่องหมาย `=`) ส่วนแรกคือ Header บอกอัลกอริทึม ส่วนที่สองคือ Payload (Claims) ที่ Server เขียนลงไป และส่วนสุดท้ายคือลายเซ็น HMAC-SHA256 ยาว 32 ไบต์ ที่คำนวณจากสองส่วนแรกกับ Secret ของ Server

จุดที่คนมักเข้าใจผิดคือ Payload **ไม่ได้ถูกเข้ารหัส** ใครได้ Token ไปก็อ่านได้ทันทีโดยไม่ต้องมี Key (แบบฝึก Assert ว่าอ่านได้) สิ่งที่ลายเซ็นให้คือแก้ไม่ได้ ไม่ใช่ซ่อน อย่าใส่ข้อมูลลับใน Payload

</Step>

## ลองแก้ Token เอง

ในแล็บข้างล่าง ลองเริ่มจากค่าตั้งต้น (Role เป็น User ใช้ลายเซ็นเดิม ตัวตรวจรัดกุม) Server รับ Token แล้วเปลี่ยน Role เป็น Admin ในขณะที่ยังแนบลายเซ็นเดิม ดูว่าลายเซ็นที่ Server คำนวณใหม่ไม่ตรงกับที่ Token ให้มา จึงถูกปฏิเสธว่า Bad Signature ซึ่งก็ตรงกับที่แบบฝึกพิสูจน์ จากนั้นลองเลือก "เซ็นใหม่ด้วย Secret" เพื่อดูว่าถ้ามี Key จริง ๆ ก็เซ็น Admin ได้ แปลว่าความลับของ Secret คือทั้งหมดของความปลอดภัยตรงนี้

<JwtLab client:visible />

เมื่อลองครบแล้ว ให้สลับตัวตรวจเป็น "เชื่อ Token" แล้วเลือกลายเซ็น "ไม่มี (Alg: None)" ดูว่าตัวตรวจแบบนี้รับ Token ที่ไม่มีลายเซ็นเลย เพียงเพราะ Header ของ Token เองบอกว่า `alg` เป็น `none` นี่คือช่องโหว่คลาสสิกของ JWT ที่ตัวตรวจ **เชื่อสิ่งที่ Token บอกเกี่ยวกับวิธีตรวจ Token** แบบฝึกยืนยันว่าตัวตรวจแบบเชื่อ Token รับ Token ที่ Role เป็น Admin และไม่มีลายเซ็น ส่วนตัวตรวจรัดกุมซึ่งมีรายการอัลกอริทึมที่ Server กำหนดเองว่ามีแค่ `HS256` ปฏิเสธด้วยข้อความว่าไม่อนุญาต `none`

</Step>

## สับสนอัลกอริทึม: เอา Public Key มาใช้เป็น Secret

ช่องโหว่ที่แยบยลกว่าเกิดกับระบบที่ใช้ลายเซ็นแบบสองกุญแจ (RS256) Server เซ็นด้วย Private Key และใครก็ตรวจได้ด้วย Public Key ซึ่งเปิดเผยได้ ถ้าตัวตรวจเชื่อ `alg` ใน Token ผู้โจมตีเขียน Header ว่า `HS256` แล้วใช้ **Public Key เป็น Secret ของ HMAC** เซ็น Token ของตัวเอง ตัวตรวจที่ใช้ Public Key เป็น "Key" เหมือนเดิมแต่หันไปใช้ HMAC ก็ตรวจผ่าน เพราะทั้งสองฝั่งใช้ค่าเดียวกัน

แบบฝึกสร้าง RSA 2048 บิต ใช้ Public Key (เป็นแค่ข้อความ `-----BEGIN PUBLIC KEY-----` ที่ผู้โจมตีมีอยู่แล้ว) เป็น Secret เซ็น Token ปลอม ที่ Role เป็น Admin ผลที่ได้คือตัวตรวจแบบเชื่อ Token รับ แต่ตัวตรวจรัดกุมที่อนุญาตเฉพาะ `RS256` ปฏิเสธด้วยข้อความว่า `HS256` ไม่อยู่ในรายการ และลายเซ็น RS256 ที่ถูกต้องยาว 256 ไบต์ (กุญแจ 2048 บิต) ตรวจได้ด้วย Public Key อย่างเดียว

ทั้งสองกรณีแก้ด้วยกฎเดียวกัน **Server เป็นคนเลือกอัลกอริทึม ไม่ใช่ Token** เราไม่ได้ตรวจเรื่อง Alg None และ Alg Confusion กับหนังสือ ข้อสรุปนี้ได้จากการรันแบบฝึกเอง

</Step>

## ลายเซ็นถูกยังไม่พอ และ Secret ต้องไม่เดาง่าย

ลายเซ็นที่ถูกบอกแค่ว่า Server ของเราเป็นคนออก ยังไม่ได้บอกว่า Token ใบนี้ใช้ได้ตอนนี้ กับ API นี้ แบบฝึกจึงให้ตัวตรวจรัดกุมเช็ก Claims อีกสามข้อหลังเช็กลายเซ็น ข้อแรก `exp` ต้องยังไม่ถึง ข้อที่สอง `aud` (ผู้รับ) ต้องเป็น API นี้ และข้อสุดท้าย `iss` (ผู้ออก) ต้องเป็นผู้ออกที่เราเชื่อ ผลที่รันได้คือ Token ที่ลายเซ็นถูกแต่หมดอายุ ได้ `token expired` ที่ผู้รับผิดได้ `wrong audience` และที่ผู้ออกผิดได้ `wrong issuer` (หนังสือ: API Security in Action หน้า 187 สำหรับ Claims มาตรฐาน)

อีกเรื่องคือ Secret ของ HMAC ถ้าเดาง่ายก็ไม่ต่างจาก Password ที่เดาง่าย แบบฝึกลองเดาจากรายการสั้น ๆ หกคำกับ Token ที่เซ็นด้วย `secret` เจอตอนเดาครั้งที่สี่ และ Secret ยาว ๆ แบบสุ่มของเราไม่อยู่ในรายการนั้น เราควรใช้ Secret ที่สุ่มยาวอย่างน้อย 32 ไบต์

</Step>

## เพิกถอน Token ที่เซ็นไปแล้วไม่ได้

จุดอ่อนของการไม่จำอะไรเลยคือเมื่อ Server ออก Token ไปแล้ว มันเรียกคืนไม่ได้จนกว่าจะหมดอายุ ผู้ใช้กดออกจากระบบก็ตาม Token ที่ขโมยไปก็ยังใช้ได้ แบบฝึกเช็กว่า ที่ 800 วินาที (ก่อนหมดอายุที่ 900) Token ยังผ่านการตรวจ

ถ้าต้องเพิกถอนจริง เก็บรายการ Token ที่ถูกเพิกถอนไว้แล้วเช็กทุก Request ซึ่งแบบฝึกพิสูจน์ว่าได้ผล แต่ก็แลกด้วยการต้องมีที่เก็บสถานะอีกที่ ซึ่งเป็นสิ่งที่เราอยากเลี่ยงตั้งแต่ต้น (หนังสือ: API Security in Action หัวข้อ 6.5 หน้า 209) ทางที่นิยมคือให้ Token มีอายุสั้น แบบฝึกใช้ 900 วินาที (`exp - iat`) เพื่อจำกัดว่า Token ที่หลุดไปมีค่าอยู่นานแค่ไหน

<Callout type="note" title="JWT ไม่ใช่คำตอบเดียว">

Session Cookie ที่เก็บ ID ไว้ฝั่ง Server เพิกถอนได้ทันที ส่วน JWT ทำให้หลาย Server ตรวจได้โดยไม่ต้องคุยกับที่เก็บกลาง เลือกตามว่าเราต้องการอะไร ส่วนตัวผู้เขียนคิดว่าเว็บทั่วไปที่เป็นแอปเดียวไม่จำเป็นต้องย้ายไปใช้ JWT เพียงเพราะมันดูทันสมัย (ความเห็นผู้เขียน ไม่ได้วัด)

</Callout>
