## ข้อความสั้น ๆ ที่ทำให้ CPU ค้าง

นาย A ใช้ Regex ตรวจรูปแบบข้อความจากผู้ใช้ ตัวหนึ่งหน้าตาแบบนี้ `(a+)+$` อ่านแล้วดูไม่มีอะไร แต่เมื่อป้อนข้อความที่เป็นตัว `a` ติดกันหลายตัวแล้วปิดท้ายด้วย `b` ซึ่งทำให้การจับคู่ล้มเหลวตอนท้ายสุด Engine ที่ใช้การย้อนกลับ (Backtracking) ต้องลองทุกวิธีที่จะแบ่งตัว `a` ออกเป็นกลุ่ม ๆ ก่อนจะยอมแพ้ แบบฝึกเขียนตัวจับคู่เล็ก ๆ ที่ทำแบบเดียวกันและนับจำนวนครั้งที่ทำงาน ผลที่ได้คือ n = 1 ใช้ 2 ครั้ง, n = 2 ใช้ 4 ครั้ง และ **ทุกตัวอักษรที่เพิ่ม งานเพิ่มเป็นสองเท่าเป๊ะ** ที่ 20 ตัวอักษรใช้ 1,048,576 ครั้ง ส่วน Pattern ธรรมดาที่เดินครั้งเดียวใช้ 21 ครั้ง (หนังสือ: Web Application Security บทที่ 14 หน้า 162 เรื่อง ReDoS)

เรื่องนี้ไม่ใช่แค่ทฤษฎี แบบฝึกจับเวลา `re` ของ Python จริงด้วย ผลคือเพิ่มจาก 18 เป็น 22 ตัวอักษร ใช้เวลาเพิ่มราว 16 เท่า ตรงกับที่การเพิ่มเป็นสองเท่าสี่ครั้งทำนายไว้ ส่วน Pattern ที่เดินครั้งเดียวกับข้อความ 100,000 ตัวอักษรจบในไม่ถึงหนึ่งวินาที

ลองเลื่อนจำนวนตัวอักษรในแล็บข้างล่าง ดูว่าเส้นของ Pattern ซ้อนวงเล็บพุ่งขึ้นจนออกนอกกราฟ และที่ n = 30 ต้องทำงานเกินพันล้านครั้ง จากนั้นเปิดการจำกัดความยาวที่ 24 ตัว ดูว่าคำขอที่ยาวกว่านั้นถูกปฏิเสธก่อนที่ Regex จะเริ่มทำงานเลย

วิธีกันมีสองทาง ทางหนึ่งคือเขียน Pattern ใหม่ไม่ให้ซ้อนการวนซ้ำ อีกทางที่ใช้ได้ทันทีคือจำกัดความยาวของข้อความก่อนส่งเข้า Regex แบบฝึกยืนยันว่าการจำกัดที่ 64 ตัวอักษรตัดข้อความหนึ่งหมื่นตัวทิ้งได้ไม่ว่าผู้โจมตีจะส่งอะไร (หนังสือ: Web Application Security บทที่ 26 หน้า 270)

## งานที่ผู้ใช้สั่งได้ไม่จำกัด

ReDoS เป็นแค่รูปแบบหนึ่ง ในบทแรกเรามีฟังก์ชันค้นหาที่รับ `limit` จากผู้ใช้ แล้วให้ฐานข้อมูลทำงานตามนั้น ขอ 10,000,000 แถวได้ ก็ได้ ผู้โจมตีไม่ต้องส่งอะไรพิเศษ แค่ขอของที่แพงทีละมาก ๆ นี่เป็นสิ่งที่หนังสือเรียกว่า Logical DoS (หนังสือ: Web Application Security บทที่ 14 หน้า 164) ทางแก้เหมือนเดิม คือ Server เป็นคนตั้งเพดาน (ในบทแรกคือ 100) และถ้าเรื่องที่แพงคือจำนวนคำขอ ก็ต้องใช้ Rate Limit

ส่วนการถล่มจากหลายแหล่งพร้อมกัน (DDoS) ที่ต้องใช้เครือข่ายขนาดใหญ่และการป้องกันที่ชั้นเครือข่าย ผู้เขียนไม่ได้รันในบทนี้ (หนังสือ: Web Application Security บทที่ 14 หน้า 167)

</Step>

## Rate Limit: Token Bucket

วิธีที่ใช้กันมากที่สุดคือ **Token Bucket** ลองนึกถึงถังที่ใส่ Token ได้ 5 ตัว ทุกคำขอต้องหยิบหนึ่ง Token ถ้าถังว่างก็ถูกปฏิเสธ และถังถูกเติมวินาทีละหนึ่ง Token ผลที่แบบฝึก Assert ไว้คือ คำขอ 8 ครั้งพร้อมกัน ผ่านห้าครั้งแรกและปฏิเสธสามครั้งหลัง สามวินาทีต่อมามี Token กลับมา 3 ตัว คำขอใหม่สี่ครั้งผ่านสามครั้งและปฏิเสธหนึ่งครั้ง และถ้ามีคำขอวินาทีละครั้งไปเรื่อย ๆ จะไม่ถูกปฏิเสธเลย เพราะเท่ากับอัตราที่เติม ส่วนถ้ามีสิบครั้งต่อวินาทีเป็นเวลาสิบวินาที ผ่านราว 15 ครั้ง (5 ที่สะสมไว้ บวกวินาทีละหนึ่ง)

คุณสมบัติที่ดีคือ ปล่อยให้ผู้ใช้จริงที่กดรัว ๆ ได้ช่วงสั้น ๆ แต่ไม่ปล่อยให้ใครกดต่อเนื่องเกินอัตราที่ตั้ง

## Fixed Window กับ Sliding Window

อีกแนวคือนับคำขอในช่วงเวลา เช่น 10 ครั้งต่อ 60 วินาที ถ้านับเป็นนาทีที่ตายตัว (Fixed Window) มีช่องว่างตรงขอบ ผู้โจมตีส่ง 10 ครั้งตอนวินาทีที่ 55 และอีก 10 ครั้งตอนวินาทีที่ 61 ซึ่งอยู่คนละนาที ผ่านทั้ง 20 ครั้งในหกวินาที ส่วน Sliding Window ที่ดูย้อนหลัง 60 วินาทีจากเวลาปัจจุบันทุกครั้ง ผ่านแค่ 10 ในช่วงเดียวกัน แบบฝึก Assert ทั้งสองตัวเลขนี้

เลือกทั้งสามวิธีในแล็บข้างล่างแล้วกดเล่น ดูว่า Bucket ปล่อยช่วงแรกให้ผ่านแล้วค่อยปฏิเสธ ส่วน Fixed Window ที่ข้ามขอบวินาทีที่ 60 ยอมให้ทั้ง 20 ครั้งผ่าน และ Sliding Window หยุดไว้ที่ 10

## การล็อกบัญชีที่กลายเป็นอาวุธ

ที่มักถูกใช้ป้องกันการเดา Password คือล็อกบัญชีเมื่อใส่ผิดครบกี่ครั้ง ซึ่งมีผลข้างเคียง แบบฝึกจำลองว่าล็อกที่ผิดสามครั้ง ผู้โจมตีส่งรหัสผิดสามครั้งในชื่อของ Ann พอ Ann เข้ามาด้วยรหัสที่ถูก ก็ถูกล็อกอยู่ ผลที่ได้คือ `wrong, wrong, wrong, locked` ผู้โจมตีไม่ต้องรู้รหัส ก็ทำให้เจ้าของใช้บัญชีไม่ได้ (ผู้โจมตีทำแบบนี้กับทุกบัญชีได้พร้อมกัน)

ทางเลือกคือจำกัดอัตราต่อ IP และต่อบัญชีแยกกัน หน่วงเวลาที่เพิ่มขึ้นทุกครั้งที่ผิดแทนการล็อกถาวร หรือล็อกชั่วคราว ไม่ว่าทางไหนก็มีข้อแลกเปลี่ยน แบบฝึกแสดงแค่ว่าการล็อกแบบเรียบง่ายเป็นช่องใหม่ในตัวมันเอง

เรื่องที่เหลือคือ Rate Limit ช่วยกันการเดาได้มากแค่ไหน แบบฝึกคำนวณว่า PIN หกหลักมี 1,000,000 แบบ ถ้าให้ลองได้ 5 ครั้งต่อนาที ต้องใช้ 138.9 วันกว่าจะครบทุกแบบ (เฉลี่ยครึ่งหนึ่ง คือ 69.4 วัน) แต่ถ้าไม่มี Rate Limit และผู้โจมตีมี Hash SHA-256 ของ PIN อยู่ในมือ ตามความเร็วที่เราวัดไว้ในบทเรื่อง Password การลองหนึ่งล้านแบบจบในไม่ถึงหนึ่งวินาที ตัวเลขหลังนี้ขึ้นกับคอมพิวเตอร์ที่รัน

<Callout type="note" title="ที่ไม่ได้รัน">

การถล่มแบบกระจาย (DDoS), CDN และ WAF, การจำกัดอัตราที่ชั้น Reverse Proxy และการแชร์ตัวนับหลาย Server ไม่ได้อยู่ในแบบฝึกนี้

</Callout>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| `(a+)+$` ทำงานเพิ่มเป็นสองเท่าทุกตัวอักษร (2, 4, ... 1,048,576 ที่ n = 20) และ `a+$` ใช้ 21 ครั้ง | รัน: `exercises/12_dos_rate_limit.py` |
| `re` จริงช้าลงราว 16 เท่าเมื่อเพิ่มสี่ตัวอักษร และ `a+$` จบในไม่ถึงหนึ่งวินาทีที่ 100,000 ตัวอักษร | รัน: `exercises/12_dos_rate_limit.py` |
| ReDoS และการป้องกัน (จำกัดความยาวก่อน Regex) | หนังสือ: Web Application Security บทที่ 14 หน้า 162 และบทที่ 26 หน้า 270 |
| Logical DoS และ DDoS | หนังสือ: Web Application Security บทที่ 14 หน้า 164 และ 167 (ไม่ได้รัน) |
| Token Bucket: คำขอ 8 ครั้งพร้อมกันผ่าน 5 และสามวินาทีต่อมาผ่าน 3 จากคำขอใหม่ 4 | รัน: `exercises/12_dos_rate_limit.py` |
| Fixed Window ผ่านทั้ง 20 ที่ขอบ และ Sliding Window ผ่าน 10 | รัน: `exercises/12_dos_rate_limit.py` |
| การล็อกบัญชีให้ผู้โจมตีล็อกเจ้าของได้ | รัน: `exercises/12_dos_rate_limit.py` |
| PIN หกหลักที่ 5 ครั้งต่อนาทีใช้ 138.9 วันจนครบ | รัน: `exercises/12_dos_rate_limit.py` |
| ความเร็ว CPU ในแล็บ (10 ล้านครั้งต่อวินาที) | ตัวอย่างของผู้เขียน |
| DDoS, CDN, WAF และตัวนับที่แชร์หลาย Server | ไม่ได้รัน |
