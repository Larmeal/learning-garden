## ล็อกอินแล้ว แต่ควรเห็นอะไรได้บ้าง

บทก่อนหน้านี้เราเน้นเรื่อง "คุณคือใคร" (Authentication) บทนี้ถามต่อว่า "คุณทำอะไรได้" (Authorization) ซึ่งเป็นคนละคำถาม และเป็นเรื่องที่ระบบจริงพลาดบ่อยมาก เพราะมันไม่มีไลบรารีไหนทำให้เราโดยอัตโนมัติ ทุก Endpoint ต้องถามเองว่า "คนที่ขอมา ควรได้สิ่งนี้ไหม"

เรามาดูตัวอย่างแรก Ann ล็อกอินแล้ว Order ของเธอคือเลข 101 ส่วนของ Bob คือเลข 102 (รัน: `exercises/10_access_control.py`)

```python
def get_order(order_id, who, check_owner):
    o = ORDERS[order_id]
    if check_owner and o["owner"] != who and USERS[who]["role"] != "admin":
        raise PermissionError("forbidden")
    return o
```

ถ้าไม่เช็กเจ้าของ Ann เปลี่ยนเลขจาก 101 เป็น 102 ใน URL ก็ได้ Order ของ Bob ถ้าเช็ก คำขอเดียวกันถูกปฏิเสธ นี่คือ **IDOR (Insecure Direct Object Reference)** เรียกอีกอย่างว่า Broken Object Level Authorization ซึ่งเป็นรูปแบบของ "ถามเลขแล้วให้เลย" ที่เห็นแล้วในบทแรก เมื่อเลขเรียงกัน ผู้โจมตียังไล่นับหา Order ที่มีอยู่ได้ ในแบบฝึกไล่ 100 ถึง 109 เจอ 101 กับ 102 ตรงตามที่มีจริง

ในแล็บข้างล่าง เลือก IDOR แล้วสลับระหว่างเลข 101 และ 102 กับการเปิดและปิดการเช็กเจ้าของ ดูว่าเมื่อไม่เช็ก ผลของ Order 102 ได้ข้อมูลของ Bob ทั้งที่ Ann เป็นคนขอ

## ปุ่มที่ซ่อนไม่ใช่การเช็กสิทธิ์

ต่อจากบทที่เปิดเรื่องนี้ไว้ ระบบหนึ่งซ่อนปุ่ม "ลบผู้ใช้" จากหน้าของผู้ใช้ทั่วไป แบบฝึกยืนยันว่าหน้าของ `user` ไม่แสดงปุ่มนั้น แต่ถ้า Ann ส่ง Request ไปที่ Endpoint ลบผู้ใช้เอง ซึ่ง Endpoint ไม่ได้ถามว่า Ann เป็นใคร มันลบ Bob ให้ ทางแก้คือการเช็ก Role ใน Endpoint เอง ซึ่งแบบฝึกทำแล้ว Ann ถูกปฏิเสธและ Bob ยังอยู่ หนังสือ API Security in Action เรียกหลักที่อยู่เบื้องหลังเรื่องนี้ว่า **Principle of Least Authority** คือให้ทุกส่วนมีสิทธิ์เท่าที่จำเป็นเท่านั้น (หนังสือ: API Security in Action หน้า 46)

อีกเรื่องที่เกี่ยวกันคือ **Mass Assignment** ฟังก์ชันอัปเดตโปรไฟล์ที่เอาทุกฟิลด์ใน JSON ที่ส่งมาไปอัปเดตในตาราง ถ้า Ann ส่ง `{"display_name": "Ann", "role": "admin"}` มา ฟิลด์ `role` ก็ถูกเขียนไปด้วย แบบฝึกยืนยันว่า Ann กลายเป็น Admin ทางแก้คือ Allow List ของฟิลด์ที่ผู้ใช้แก้ได้ (`display_name`, `email`) ส่วน `role` ที่ส่งมาถูกเมินเฉย

## Path Traversal: ชื่อไฟล์ที่พาออกนอกโฟลเดอร์

Server ที่ให้ผู้ใช้ขอไฟล์จากโฟลเดอร์ `public` ผ่านชื่อ มักต่อ Path ตรง ๆ ผู้ใช้ส่ง `../secret.txt` ซึ่ง `..` แปลว่าขึ้นไปหนึ่งชั้น ทำให้ได้ไฟล์ที่อยู่นอกโฟลเดอร์ แบบฝึกสร้างโฟลเดอร์ชั่วคราวที่มี `public/hello.txt` และ `secret.txt` ข้างนอก ผลคือ `hello.txt` อ่านได้ปกติ และ `../secret.txt` ได้ `TOP SECRET` ทั้งที่อยู่นอกโฟลเดอร์

ทางแก้คือแปลง Path ให้เป็น Path เต็มที่ตัด `..` และทางลัดออกหมดแล้ว (`resolve()`) แล้วเช็กว่ายังอยู่ใต้โฟลเดอร์ที่อนุญาต (`is_relative_to`) ผลที่ได้ `../secret.txt` ถูกปฏิเสธ ส่วน `hello.txt` ยังอ่านได้ในแล็บเลือก Path Traversal แล้วสลับการตรวจ (หนังสือ: API Security in Action หน้า 420 ที่กล่าวถึงว่าความลับในไฟล์อาจถูกเปิดผ่าน Path Traversal)

## SSRF: ให้ Server ไปดึงสิ่งที่ผู้ใช้ชี้

บางฟังก์ชันให้ผู้ใช้ส่ง URL มาให้ Server ไปดึง เช่นดึงรูปโปรไฟล์ ผู้โจมตีส่ง URL ที่ชี้ไปที่ที่เขาเข้าถึงเองไม่ได้ แต่ Server เข้าถึงได้ เช่น `http://127.0.0.1/admin` ซึ่งเป็นหน้าแอดมินของ Server เอง หรือ `169.254.169.254` ที่อยู่ของบริการ Metadata ในระบบคลาวด์ นี่คือ **SSRF (Server-Side Request Forgery)** (หนังสือ: API Security in Action หน้า 354 และหน้า 361 สำหรับวิธีป้องกัน)

ทีมที่ระวังมักเขียน Blocklist ว่า ถ้า Host เป็น `127.0.0.1` หรือ `localhost` ให้ปฏิเสธ แบบฝึกลองเจ็ดวิธีเขียนที่อยู่ ผลคือ Blocklist ของข้อความหยุดได้แค่สอง (`127.0.0.1` และ `localhost`) ที่เหลืออีกห้า `127.1`, `2130706433`, `0x7f000001`, `[::1]` และ `169.254.169.254` ผ่านไปได้ ทั้งที่ชี้ไปที่คอมพิวเตอร์เครื่องเดียวกัน Client จริงอ่าน `127.1` และ `2130706433` เป็น `127.0.0.1` เหมือนกัน

ทางที่ถูกคือแปลง Host ให้เป็นที่อยู่ IP จริงก่อน (แบบเดียวกับที่ตัวดึงจะใช้) แล้วเช็กชนิดของที่อยู่ ว่าเป็น Loopback, Private, Link-local หรือ Reserved ไหม ผลที่ได้คือบล็อกครบทั้งเจ็ดแบบ และที่อยู่สาธารณะอย่าง `93.184.216.34` ยังผ่าน แบบฝึกยังเช็กว่า `169.254.169.254` เป็น Link-local จริง ในแล็บเลือก SSRF แล้วลองไล่ทั้งเจ็ดแบบ ทั้งสองการตรวจ

<Callout type="warn" title="ยังไม่ครบ">

การตรวจที่อยู่ตอนรับ URL อย่างเดียวยังไม่พอในงานจริง เพราะ DNS อาจเปลี่ยนคำตอบระหว่างที่ตรวจกับตอนดึง และ URL ที่ Redirect ไปที่อื่นได้ แบบฝึกไม่ได้ครอบคลุมสองเรื่องนี้ และไม่ได้ส่ง Request ไปที่ไหนจริง

</Callout>

## ข้อมูลที่ถูกถอดรหัสแล้วรันโค้ด

**Pickle** ของ Python เป็นรูปแบบเก็บ Object ที่ตัวมันเองบอกได้ว่าตอนโหลดให้เรียกฟังก์ชันอะไร แบบฝึกสร้าง Object ที่ `__reduce__` สั่งให้เรียก `print` เพื่อให้ดูปลอดภัย และตอนเราโหลดก้อนไบต์นั้นด้วย `pickle.loads` ข้อความ `code from the pickle ran` ก็ถูกพิมพ์ออกมา หมายความว่าใครสร้างไบต์เหล่านั้นได้ ก็เลือกฟังก์ชันที่จะรันบนเครื่องเราได้ ต่างจาก `json.loads` ที่เป็นแค่ข้อมูลและเรียกอะไรไม่ได้ ดังนั้นเราไม่ควรโหลด Pickle จากแหล่งที่เราไม่เชื่อใจ

**XXE (XML External Entity)** คือ XML ที่ประกาศ Entity ชี้ไปที่ไฟล์บนดิสก์ แล้วให้ Parser ใส่เนื้อไฟล์ลงในเอกสาร (หนังสือ: Web Application Security บทที่ 12 หน้า 141) แบบฝึกสร้าง XML ที่ชี้ไปที่ `secret.txt` แล้วส่งให้ `xml.etree.ElementTree` ของ Python ผลคือ Parser แจ้ง `undefined entity &x;` และเนื้อไฟล์ลับไม่ปรากฏในเอกสาร นั่นคือ Parser ตัวนี้ไม่ตาม External Entity ในค่าเริ่มต้น แต่ Parser ในภาษาอื่นและไลบรารีบางตัวตาม ต้องดูว่าไลบรารีที่เราใช้ตั้งค่าอย่างไร (หนังสือ: Web Application Security บทที่ 24 เรื่องการป้องกัน XXE)

สรุปหลักเดียวของทั้งบท คือการตัดสินใจเรื่องสิทธิ์และเรื่องว่าจะทำอะไร ต้องเกิดที่ Server จากความหมายจริงของคำขอ ไม่ใช่จากหน้าตาของข้อความที่ส่งมา
