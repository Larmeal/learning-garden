## Wi-Fi ร้านกาแฟกับรหัสผ่านที่ใครก็อ่านได้

นาย A นั่งทำงานที่ร้านกาแฟ แล้วล็อกอินเข้าเว็บของบริษัทที่ยังเป็น `http://` ธรรมดา Request ที่ออกจากคอมพิวเตอร์ของเขามีหน้าตาประมาณนี้ (ตัวอย่างที่ผู้เขียนเขียนเอง ไม่ได้ดักจากของจริง)

```text
POST /login HTTP/1.1
Host: intranet.example.test

user=nai-a&password=hunter2
```

ทุกอย่างวิ่งผ่านเราเตอร์ของร้าน และผ่านทุกจุดระหว่างทางเป็นข้อความธรรมดา ใครก็ตามที่นั่งอยู่ใน Wi-Fi เดียวกันและเปิดเครื่องมือดักข้อมูลก็อ่านรหัสผ่านได้ ตรงกับการโจมตีแรกที่เราเห็นในแล็บของบทแรก ซึ่งอยู่ที่จุดเครือข่าย และแก้ด้วย TLS

TLS ต้องแก้ปัญหาสองอย่างพร้อมกัน อย่างแรกคือทำให้ข้อมูลที่วิ่งอยู่ลับ ซึ่งเราใช้การเข้ารหัสอย่าง AES-GCM จาก[บทที่แล้ว](/app-security/crypto-basics/) แต่การเข้ารหัสต้องมี Key และทั้งสองฝั่งต้องมี Key ตัวเดียวกัน ปัญหาจึงเหลืออีกข้อ คือจะตกลง Key ตัวนั้นกันอย่างไร โดยที่ Mallory ฟังอยู่ทุกคำ อีกอย่างคือ Browser ต้องรู้ว่ากำลังคุยกับ Server ของจริง ไม่ใช่ Server ที่ใครแอบตั้งขึ้นมาแทน

</Step>

## Handshake ทีละข้อความ

ในแล็บข้างล่าง เราดู Handshake ของ TLS 1.3 ซึ่งรันจริงในแบบฝึกระหว่าง Client กับ Server ใน Memory โดย Server ใช้ใบรับรองที่ CA ของเราเซ็นให้ ผลคือ Handshake จบ ได้ TLS 1.3 กับ Cipher `TLS_AES_256_GCM_SHA384` และมีการพูดสี่ครั้ง คือ Client, Server, Client แล้ว Server อีกครั้ง

ลองเล่นสถานการณ์ปกติก่อน แล้วดูว่าข้อความที่สองใหญ่ที่สุด เพราะมีใบรับรองไปด้วย หลังจากข้อความที่สอง Browser ตรวจใบรับรองสามข้อ และถ้าผ่านถึงจะส่งข้อความที่สามที่เล็กมาก (80 ไบต์) จากนั้นสลับไปสถานการณ์อื่นทีละอัน ดูว่า Browser หยุดทันทีที่สามข้อนั้นข้อไหนไม่ผ่าน และข้อความ Error ที่เห็นก็เป็นของจริงจากแบบฝึก

<TlsHandshakeLab client:visible />

ข้อความที่สี่ซึ่งเป็นตั๋ว Session ที่ Server ส่งมาหลังจากทุกอย่างเสร็จแล้ว มีไว้ให้การเชื่อมต่อครั้งหน้าเร็วขึ้น เราเช็กในแบบฝึกแค่ว่ามันมี และ Server เป็นฝ่ายส่ง

## เลขลับที่ไม่ต้องส่งผ่านสาย

มีคำถามค้างอยู่ เมื่อกี้บอกว่าทั้งสองฝั่งได้ Key เดียวกัน แต่ Mallory ฟังอยู่ทุกข้อความ แล้วทำไม Mallory ถึงไม่ได้ Key ไปด้วย? นี่คือแนวคิดที่เรียกว่า **Key Exchange** แบบ Diffie-Hellman ซึ่งเข้าใจง่ายที่สุดเมื่อลองคำนวณด้วยเลขเล็ก ๆ

ทั้งสองฝั่งตกลงเลขสาธารณะสองตัว คือ p = 23 และ g = 5 Alice สุ่มความลับ 6 แล้วส่ง `5^6 mod 23 = 8` ให้ Bob ส่วน Bob สุ่มความลับ 15 แล้วส่ง `5^15 mod 23 = 19` ให้ Alice จากนั้น Alice เอา 19 ยกกำลัง 6 และ Bob เอา 8 ยกกำลัง 15 แล้วหาเศษของ 23 ทั้งคู่ได้ 2 เท่ากัน ตรงกับที่แบบฝึกคำนวณและ Assert ไว้ ลองเลื่อนแถบความลับของทั้งสองคนในแล็บ จะเห็นว่าเลขร่วมตรงกันทุกครั้ง และเลขร่วมไม่เคยอยู่บนสาย

<KeyExchangeLab client:visible />

ที่เห็นในกล่องล่างสุดคือคนดักฟังที่รู้แค่ p, g และสองเลขบนสาย เขาเดาความลับของ Alice ได้โดยลองไล่ 1, 2, 3 ไปเรื่อย ๆ ซึ่งจบเร็วเพราะ p เล็กมาก มีแค่ 22 ความลับให้ลอง ใน TLS จริง Browser ใช้ X25519 ที่มีความลับให้เดาราว 2^255 แบบ การไล่เดาจึงทำไม่ได้ ส่วนเรื่องที่ว่าทำไมการหาความลับจากเลขที่ส่งถึงยากในเชิงคณิตศาสตร์ ผู้เขียนไม่ได้ลงรายละเอียดในบทนี้ แบบฝึกยืนยันแค่ว่าทั้งสองฝั่งได้ Secret ขนาด 32 ไบต์เหมือนกันจาก X25519 โดยที่ Secret นั้นไม่เหมือนกับค่าสองตัวที่ถูกส่ง

</Step>

## ใบรับรองบอกอะไร

เรื่อง Key ลงตัวแล้ว แต่ยังเหลืออีกข้อ Mallory ตั้ง Server ปลอมแล้วทำ Handshake กับ Browser เองได้ไหม? Key Exchange บอกแค่ว่าเรากับอีกฝั่งมี Key ตรงกัน ไม่ได้บอกว่าอีกฝั่งคือใคร ตรงนี้คือหน้าที่ของ **ใบรับรอง (Certificate)** ซึ่งเป็นไฟล์ที่ผูกชื่อ Host เข้ากับ Public Key และมีลายเซ็นของ **CA (Certificate Authority)** ที่ Browser เชื่อใจอยู่แล้ว กำกับไว้ ลายเซ็นก็คือของที่เราเพิ่งรู้จักใน[บทที่แล้ว](/app-security/crypto-basics/)

แบบฝึกสร้าง CA ของเราเองกับใบรับรองของ `shop.example.test` และเช็กว่า

- ใบรับรองระบุ Subject ว่า `CN=shop.example.test`
- ผู้ออกคือ CA ของเรา และ Public Key ของ CA ตรวจลายเซ็นบนใบรับรองผ่าน
- ใบรับรองของ CA เองเซ็นตัวเอง (Issuer เท่ากับ Subject) ซึ่งเป็นรากของความเชื่อใจ
- ใบรับรองมีอายุ 90 วัน และมีลายนิ้วมือ SHA-256 ขนาด 32 ไบต์

คำว่า "เชื่อใจ" ของ Browser จึงหมายถึงมีใบรับรองของ CA รากอยู่ในรายการของมันแล้ว ถ้าลายเซ็นบนใบรับรองของ Server ย้อนกลับไปถึง CA ที่อยู่ในรายการ ก็ถือว่าผ่าน ส่วนใบรับรองที่มีหลายชั้น (Intermediate CA) ผู้เขียนไม่ได้รันในบทนี้ หนังสือ Web Application Security พูดถึงเรื่อง SSL กับ TLS ไว้เหมือนกัน (หนังสือ: Web Application Security บทที่ 18 หน้า 195)

</Step>

## ปฏิเสธได้สามแบบ

Handshake ที่ผ่านในแล็บเมื่อกี้ใช้ใบรับรองที่ถูกต้องทุกข้อ แบบฝึกลองใช้ Server เดิมแต่เปลี่ยนฝั่ง Client หรือใบรับรอง ทีละอย่าง ผลคือ Client ปฏิเสธทั้งสามแบบด้วย `SSLCertVerificationError`

| สถานการณ์ | ข้อความ Error จริง (ตัดบางส่วน) |
|---|---|
| Client ไม่เชื่อ CA ของเรา | `certificate verify failed: unable to get local issuer certificate` |
| Client ตั้งใจเข้า `evil.example.test` แต่ใบรับรองระบุ `shop.example.test` | `certificate verify failed: Hostname mismatch` |
| ใบรับรองที่เริ่มใช้เมื่อ 100 วันก่อนและมีอายุ 30 วัน | `certificate verify failed: certificate has expired` |

กรณีที่สองสำคัญมาก ใบรับรองของ CA ที่เชื่อใจได้ ถ้าชื่อไม่ตรงกับที่เราขอ ก็ใช้ไม่ได้ ไม่เช่นนั้น Mallory ขอใบรับรองของเว็บตัวเองจาก CA เดียวกัน แล้วเอามาใช้แทนเว็บของธนาคารได้ ส่วนตัวผู้เขียนคิดว่านี่คือสาเหตุที่ควรเปิดการตรวจชื่อไว้เสมอ และไม่ควรปิดการตรวจใบรับรองในโค้ดแม้ตอนทดสอบ (ความเห็นผู้เขียน ไม่ได้ลองปิดให้ดู)

<Callout type="note" title="เรื่องที่ยังไม่ได้ลงรายละเอียด">

การเพิกถอนใบรับรอง (Revocation) เมื่อ Private Key รั่ว, Certificate Transparency และการ Pin ใบรับรองในแอปมือถือ ไม่ได้อยู่ในบทนี้ เพราะเราไม่ได้รันให้ดู

</Callout>
