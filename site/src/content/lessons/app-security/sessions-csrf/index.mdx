## ล็อกอินครั้งเดียว แต่ Server ต้องจำเราได้ทุกครั้ง

HTTP ไม่มีความจำ ทุก Request ที่มาถึง Server เป็นเรื่องใหม่หมด นาย A ล็อกอินที่ธนาคารด้วยรหัสผ่านแล้ว ถ้า Server ไม่จำว่าเขาเป็นใคร ทุกครั้งที่เขากดดูยอดเงินก็ต้องใส่รหัสผ่านใหม่

วิธีที่นิยมที่สุดคือหลังจากตรวจรหัสผ่านแล้ว Server สุ่ม **Session ID** ยาว ๆ ให้หนึ่งค่า เก็บไว้ในตารางของตัวเองว่าค่านี้คือ Ann และส่งให้ Browser เก็บใน **Cookie** จากนี้ทุก Request Browser จะแนบ Cookie ไปเอง ให้ Server เอา ID ไปค้นหาว่าเป็นใคร เหมือนบัตรคิวที่ธนาคารยื่นให้ตอนเราเข้าไปครั้งแรก (รัน: `exercises/05_sessions_csrf.py`)

```text
Set-Cookie: sid=ZXaHJ6PlxVqhxeKZp5vAcIdtwiSTW3Ea7AOUV5jeYv0; HttpOnly; Secure; Path=/; SameSite=Lax
```

Session ID ที่แบบฝึกสร้างจาก `secrets.token_urlsafe(32)` ยาว 43 ตัวอักษร ซึ่งเท่ากับ 256 บิต และสองครั้งที่เรียกจะไม่ได้ค่าเดียวกัน ส่วนท้ายของ Header คือ **Flag** สามตัวที่ควรใส่ทุกครั้ง HttpOnly, Secure และ SameSite เดี๋ยวเราจะดูว่าแต่ละตัวกันอะไร หนังสือ API Security in Action เขียนไว้ว่า Secure กับ HttpOnly ควรตั้งกับ Cookie ที่ใช้เพื่อความปลอดภัยทุกตัว (หนังสือ: API Security in Action บทที่ 4 หน้า 122)

ข้อสำคัญที่สุดของระบบนี้คือ **ใครถือ Session ID ใบนี้ ก็คือผู้ใช้คนนั้น** ถ้ามีคนได้ ID ไป เขาไม่ต้องรู้รหัสผ่านเลย

</Step>

## Session ID ถูกแย่งได้สองทาง

ลองเลือกเรื่องราวในแล็บข้างล่างทีละอัน เริ่มจาก "ล็อกอินปกติ" เพื่อเห็นว่าผู้ใช้ส่งรหัสผ่านครั้งเดียวแล้ว Cookie ทำงานต่อให้ จากนั้นไปดูอีกสี่เรื่อง

<CookieSessionLab client:visible />

เรื่อง **XSS ขโมย Cookie** คือสมมติว่าเว็บมีช่องโหว่ XSS ซึ่งเราจะเรียนในบทหลัง ๆ Script ที่ฝังมารันใน Browser ของผู้ใช้ และอ่าน `document.cookie` ได้ ถ้า Cookie ไม่มี `HttpOnly` Script ก็ส่ง Sid ออกไปให้ผู้โจมตี เขาเอาไปใช้ได้ทันที แต่ถ้ามี `HttpOnly` Script จะอ่าน Cookie ไม่ได้ แบบฝึกเช็กทั้งสองกรณีด้วยโมเดลของ Browser

เรื่อง **Session Fixation** กลับด้านกัน ผู้โจมตีไม่ได้ขโมย ID แต่เป็นคนเลือก ID เอง เขาขอ ID จาก Server (`A`) แล้วหลอกให้ผู้ใช้ใช้ ID นั้น ถ้า Server เก็บ ID เดิมไว้หลังจากผู้ใช้ล็อกอิน `A` ที่ผู้โจมตีรู้อยู่แล้วก็กลายเป็น Session ของ Ann ทันที แบบฝึกรันทั้งสองแบบและได้ผลว่า การเก็บ ID เดิมให้ผู้โจมตีเข้าได้ ส่วนการออก ID ใหม่ตอนล็อกอินทำให้เข้าไม่ได้ (หนังสือ: API Security in Action หัวข้อ 4.3.1 หน้า 119)

สรุปให้สั้นที่สุด `HttpOnly` กันการอ่านด้วย Script และการออก ID ใหม่ตอนล็อกอินกันการฝัง ID สองอย่างนี้ไม่ได้ทดแทนกัน

</Step>

## CSRF: เว็บอื่นใช้ Cookie ของเราแทนเรา

ลองนึกภาพนี้ นาย A ล็อกอินธนาคารค้างไว้ในอีกแท็บ แล้วเปิดเว็บ `evil.test` ที่ผู้โจมตีทำไว้ ในหน้านั้นมีฟอร์มซ่อนอยู่ที่สั่งโอนเงิน 500 ไปที่บัญชีของผู้โจมตี และมี Script กดส่งฟอร์มให้เองทันทีที่หน้าเปิด

ผู้โจมตีไม่เห็น Cookie และไม่รู้รหัสผ่าน แต่ Browser เป็นคนส่ง Request ไปที่ `bank.test` และ Browser แนบ Cookie ของ `bank.test` ให้เองทุกครั้งที่ Request ไปที่นั่น ไม่ว่าจะมาจากหน้าไหน ธนาคารเห็น Cookie ถูกต้อง จึงเชื่อว่าผู้ใช้ตั้งใจโอน นี่คือ **CSRF (Cross-Site Request Forgery)** (หนังสือ: Web Application Security บทที่ 11 หน้า 131)

ลองเลือกวิธีป้องกันในแล็บ เริ่มจาก "ไม่มีอะไรเลย" เพื่อเห็นเงินไหล แล้วสลับไปสามแบบที่เหลือ

<CsrfLab client:visible />

ผลที่แบบฝึกได้ ตอนที่ไม่มีอะไรป้องกันและ Cookie เป็น `SameSite=None` ธนาคารโอน 500 ให้ผู้โจมตี (200) ถ้าเป็น `SameSite=Lax` Browser ไม่แนบ Cookie ให้ POST ที่มาจากเว็บอื่น ธนาคารตอบ 401 ถ้าธนาคารตรวจ **CSRF Token** ซึ่งเป็นค่าสุ่มที่ธนาคารให้เฉพาะหน้าของตัวเองและเว็บอื่นอ่านไม่ได้ Request ที่ไม่มี Token ถูกปฏิเสธ 403 และถ้าธนาคารตรวจ **Origin** ซึ่ง Browser ใส่มากับ Request ว่ามาจากเว็บไหน ก็ได้ 403 เช่นกัน (หนังสือ: Web Application Security บทที่ 23 หน้า 247 สำหรับการตรวจ Header และหน้า 249 สำหรับ Token, และ API Security in Action หน้า 127 สำหรับ SameSite)

หน้าของธนาคารเองที่ส่ง Token พร้อมกับมาจาก Origin ของตัวเอง ยังโอนเงินได้ตามปกติ เมื่อเปิดป้องกันทั้งสามอย่างพร้อมกัน แบบฝึกเช็กไว้แล้ว

<Callout type="warn" title="โมเดลของ Browser ไม่ใช่ Browser จริง">

กฎของ SameSite ในแบบฝึก (Lax ไม่แนบ Cookie เมื่อเป็น POST ข้ามเว็บ, Strict ไม่แนบเมื่อข้ามเว็บทุกแบบ) เขียนเป็นโค้ดจากสิ่งที่หนังสือกับเอกสารอธิบาย เราไม่ได้เปิด Browser จริงมาลองส่ง Request ข้ามเว็บ ผลที่ได้จึงบอกว่าถ้า Browser ทำตามกฎนั้น ผลจะเป็นอย่างนี้ ไม่ได้ยืนยันกับ Chrome หรือ Firefox

</Callout>

</Step>
