## ร้านที่ถูกประกอบขึ้นให้มีปัญหา

ตลอดสิบสองบทที่ผ่านมา เราดูช่องโหว่ทีละอัน แต่ในงานจริงมันไม่ได้มาทีละอัน มาเป็นกอง ในบทนี้เราเอามารวมกัน `shopapp.py` เป็นร้านจำลองหนึ่งร้านที่เขียนให้มีช่องโหว่ **สิบจุด** ซึ่งแต่ละจุดเป็นสวิตช์ที่เปิดวิธีแก้ได้ทีละข้อ และมี **การโจมตีสิบแบบ** ที่เขียนไว้คู่กัน แต่ละแบบคืนค่าว่าสำเร็จหรือไม่

สิบจุดนั้นคือ ช่องค้นหาที่ต่อสตริงเข้า SQL, Password ที่เก็บเป็น SHA-256 ธรรมดา, Session ID ที่เป็นเลขเรียงกัน, การอ่าน Order โดยไม่เช็กเจ้าของ, การอัปเดตโปรไฟล์ด้วยทุกฟิลด์ที่ส่งมา, การแสดงรีวิวโดยไม่ Encode, การเปลี่ยนอีเมลด้วย Cookie อย่างเดียว, ข้อความ Error ที่บอกคำสั่ง SQL, การล็อกอินผิดได้ไม่จำกัดครั้ง และ Key ที่เขียนอยู่ในซอร์ส ครบทุกเรื่องที่เราเจอมา

ผลที่ Assert ไว้ในแบบฝึก (รัน: `exercises/13_capstone.py`) เมื่อไม่แก้อะไร การโจมตีทั้งสิบแบบ **สำเร็จทั้งหมด** ส่วนเมื่อเปิดวิธีแก้ครบสิบข้อ **ไม่มีแบบไหนสำเร็จเลย**

## ถ้าต้องไล่แก้ จะเริ่มจากข้อไหนก่อน

คำถามที่ทีมมักเจอจริง ๆ คือมีของที่ต้องแก้สิบอย่างและเวลาเท่าเดิม ลำดับต่อไปนี้เป็นความเห็นของผู้เขียนเอง ไม่ได้มาจากการวัดหรือรันอะไร แต่แต่ละขั้นมีเหตุผลที่ตรวจสอบได้

**อย่างแรก** คือ Key ในซอร์ส เพราะมันเป็นของที่ถ้ารั่วแล้วแก้ไม่ได้ด้วยการแก้โค้ด ต้องเพิกถอน Key ที่ผู้ให้บริการ ([บทเรื่อง Dependency และ Secret](/app-security/supply-chain-secrets/)) และเป็นอย่างเดียวที่ควรทำทันทีโดยไม่ต้องรอ Deploy

**ขั้นถัดมา** คือสามข้อที่ผู้โจมตีทำได้ตรง ๆ กับข้อมูลหรือสิทธิ์ ได้แก่ SQL Injection (ดึงทั้งตาราง), IDOR (อ่านข้อมูลของคนอื่น) และ Mass Assignment (ยกสิทธิ์ตัวเอง) ทั้งสามข้อใช้ได้โดยไม่ต้องหลอกใคร ด้วยคำขอธรรมดาคำขอเดียว

**ต่อมา** คือสิ่งที่ทำให้การโจมตีอื่นง่ายขึ้นหรือรุนแรงขึ้น คือ Password ที่เก็บแบบอ่อน (ถ้าตารางรั่ว ทุกคนเสีย), Session ID ที่เดาได้ (ยึดบัญชีใครก็ได้) และ Rate Limit ของการล็อกอิน

**สุดท้าย** คือสิ่งที่ต้องอาศัยการหลอกผู้ใช้ หรือเป็นการช่วยผู้โจมตีมากกว่าเป็นการโจมตีเอง คือ XSS, CSRF และ Error ที่เปิดเผยข้อมูลภายใน ข้อสุดท้ายอย่าง Error ไม่ได้ทำให้ใครเสียหายโดยตรง แต่บอกผู้โจมตีว่าควรเริ่มโจมตีตรงไหน

ลองไล่เปิดวิธีแก้ในแล็บข้างล่างตามลำดับนี้ หรือตามลำดับที่คุณเห็นว่าเหมาะกว่า แล้วดูแถวที่เปลี่ยนจาก "โจมตีได้" เป็น "ปิดแล้ว"

## วิธีแก้แต่ละข้อปิดแค่ช่องเดียว

แบบฝึกไม่ได้ลองแค่สองกรณีสุดทางคือไม่แก้อะไรกับแก้ครบ แต่ลองแก้ทีละข้อ เปิดวิธีแก้เพียงข้อเดียว แล้วรันการโจมตีทั้งสิบแบบ ได้ตารางสิบคูณสิบ ผลคือแต่ละวิธีแก้ปิดการโจมตีของตัวเองได้ และปิดเฉพาะของตัวเอง อีกเก้าแบบยังสำเร็จ รวมเก้าสิบช่องที่ยังเปิดอยู่ ซึ่งในแล็บคุณเห็นแล้วว่าแถวอื่นไม่เปลี่ยนเมื่อเปิดสวิตช์ของแถวหนึ่ง

ตารางนี้มีเรื่องที่ควรเล่าอีกข้อ ตอนเขียนการโจมตี Mass Assignment ครั้งแรก ผลที่ได้ไม่ใช่เก้าสิบช่องเปิด เพราะวิธีแก้ CSRF ปิด Mass Assignment ไปด้วย ผู้เขียนเขียนการโจมตีแบบส่งคำขอที่ไม่มี CSRF Token ตัววิธีแก้ CSRF จึงปฏิเสธคำขอนั้น ทั้งที่ช่องโหว่ของ Mass Assignment ยังอยู่ครบ แค่ถูกบังไว้ ทางแก้ที่ผู้เขียนเลือกคือแก้ตัวโจมตีให้ Ann ส่งคำขอเอง พร้อม Token ของตัวเองจากหน้าของร้าน ทำให้ปิดแค่ช่องเดียวตามจริง

บทเรียนที่ได้คือ **วิธีแก้ข้อหนึ่งอาจซ่อนช่องโหว่อีกข้อไว้** โดยที่ช่องนั้นไม่ได้หายไป ถ้าทดสอบด้วยการโจมตีที่มาจากคนนอกอย่างเดียว เราอาจคิดว่าแก้เรื่องหนึ่งแล้วอีกเรื่องหายไปด้วย การทดสอบจึงควรทดสอบว่าการโจมตีแบบเจาะจงถูกปิดจริง ไม่ใช่แค่ว่าคำขอหนึ่ง ๆ ถูกปฏิเสธ

</Step>

## การใช้งานปกติยังทำงานอยู่

การปิดช่องโหว่ที่ทำให้ร้านใช้ไม่ได้ ไม่นับว่าแก้ได้ แบบฝึกจึงเช็กการใช้งานปกติกับร้านที่เปิดวิธีแก้ครบ ผลที่ Assert ไว้ Ann ล็อกอินด้วยรหัสของเธอได้และได้ Session ID ยาว 43 ตัวอักษร อ่าน Order ของตัวเองได้ แก้อีเมลจากหน้าของร้านเองพร้อม Token ได้ ลงรีวิวแล้วเห็นเป็นข้อความที่ถูก Encode (`<b>nice</b>` แสดงเป็นข้อความ) ค้นหา `pen` เจอ ใส่รหัสผิดได้ 401 และใส่รหัสผิดติดกันหกครั้ง ครั้งที่หกได้ 429

ส่วนข้อสุดท้ายที่ไม่เกี่ยวกับพฤติกรรม คือ แบบฝึกเอาตัวสแกนจากบทที่ว่าด้วย Secret มาจับกับซอร์สของร้าน ซึ่งเจอ Key ตัวอย่างที่เขียนทิ้งไว้ให้หา นั่นคือที่มาของคำว่า "ข้อที่สิบ"

ทั้งหมดนี้เป็นร้านที่เขียนมาให้ถูกโจมตีและถูกแก้ อย่าเอาไปเป็นแบบ แอปจริงยังต้องมีอีกหลายเรื่อง ตั้งแต่ Logging, การตรวจสอบสิทธิ์แบบหลายระดับ ไปจนถึงการอัปเดต Dependency ซึ่งผู้เขียนไม่ได้รวมไว้ในร้านนี้

<Callout type="note" title="สิ่งที่ยังไม่ได้ตรวจ">

ร้านนี้ไม่ได้ทดสอบกับ Browser จริง (SameSite, CSP และ XSS ที่รันจริง) ไม่ได้เชื่อมต่อเครือข่าย และไม่ได้รวมเรื่อง TLS, OAuth หรือ JWT ที่เรียนในบทก่อนหน้า เพราะเป็นเรื่องที่ตัวร้านจำลองไม่ได้ใช้ ผู้เขียนยังไม่ได้ทดสอบว่าลำดับการแก้ข้างบนเหมาะกับทีมจริง เป็นความเห็นของผู้เขียนล้วน ๆ

</Callout>
