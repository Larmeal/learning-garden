## Build ที่ไม่เหมือนเดิมโดยที่ไม่มีใครแก้โค้ด

แอปของนาย A ใช้ไลบรารีตัวหนึ่งชื่อ `shop-utils` เขาเขียนในไฟล์ Dependency ว่า `^1.2.0` ซึ่งแปลว่า "เอาเวอร์ชัน 1.x ที่ใหม่ที่สุด ตั้งแต่ 1.2.0 ขึ้นไป แต่ไม่ถึง 2.0.0" อีกแบบคือ `~1.2.0` ที่แปลว่า "1.2.x ที่ใหม่ที่สุด" สมมติว่า Registry มีเวอร์ชัน 1.2.0, 1.2.3, 1.3.0, 1.9.9 และ 2.0.0 (รัน: `exercises/11_supply_chain_secrets.py`) `^1.2.0` ได้ 1.9.9 ส่วน `~1.2.0` ได้ 1.2.3

เมื่อสัปดาห์ผ่านไป ผู้ดูแลไลบรารีปล่อย 1.9.10 `^1.2.0` ก็ติดตั้ง 1.9.10 เองโดยที่นาย A ไม่ได้แก้อะไรเลย แบบฝึกยืนยันว่าคำสั่งเดิมให้ผลต่างกันระหว่างสองสัปดาห์ นั่นคือ **Build ที่ไม่มี Lock ไม่ใช่ Build เดิมสองครั้ง** ซึ่งเป็นปัญหาเมื่อไลบรารีใหม่มีบั๊ก หรือถูกคนไม่หวังดีสอดโค้ดเข้ามา

ลองเปลี่ยนวิธีขอ Dependency ในแล็บข้างล่างทีละอัน แล้วกดสัปดาห์หน้า ดูว่าเวอร์ชันที่ติดตั้งขยับเมื่อใช้ `^` แต่ไม่ขยับเมื่อใช้ `==1.2.3` หรือเมื่อมี Lock File

## Lock File ที่มี Hash

การล็อกเวอร์ชันแก้เรื่องที่เวอร์ชันขยับเอง แต่ไฟล์ของเวอร์ชันเดิมอาจถูกสลับได้ เช่นบัญชีของผู้ดูแลถูกยึด แล้วมีคนอัปโหลดทับ **Hash** เข้ามาตรงนี้ Lock File เก็บ SHA-256 ของไฟล์ที่เราตรวจสอบแล้ว และตัวติดตั้งเทียบทุกครั้ง

แบบฝึกสร้างแพ็กเกจจำลองหนึ่งบรรทัด และบันทึก SHA-256 ของมัน ไฟล์ที่เหมือนเดิมตรงกับที่ล็อก ไฟล์ที่ถูกเติมโค้ดอันตรายหนึ่งบรรทัด (`import os; os.system(...)`) Hash ไม่ตรง ตัวติดตั้งจึงหยุด ในแล็บลองเปิด Lock File แล้วเลือก "ถูกสลับ" ดูว่าติดตั้งสำเร็จไม่ได้ แต่ถ้าปิด Lock File ไฟล์ที่ถูกสลับถูกติดตั้งโดยไม่มีใครรู้ (หนังสือ: Web Application Security บทที่ 27 หน้า 278 เรื่อง Secure Package Management)

Hash จับได้เฉพาะการเปลี่ยนไฟล์ที่เราเคยตรวจแล้ว ถ้าไฟล์ที่เราตรวจตั้งแต่แรกก็มีโค้ดร้ายอยู่แล้ว Hash ก็บอกไม่ได้ ตรงนั้นเป็นเรื่องของการประเมิน Dependency ตั้งแต่ตอนเลือกใช้ ซึ่งหนังสือ Web Application Security พูดถึงการประเมินต้นไม้ของ Dependency และ CVE ไว้เหมือนกัน (หนังสือ: Web Application Security บทที่ 15 หน้า 180)

</Step>

## ชื่อที่หน้าตาคล้ายของจริง

อีกวิธีที่ผู้โจมตีใช้ คือตั้งชื่อแพ็กเกจให้คล้ายของยอดนิยม เช่น `reqeusts` แทน `requests` คนพิมพ์ผิดตัวเดียวก็ติดตั้งของเขา แบบฝึกเขียนฟังก์ชันวัดระยะการแก้ไขระหว่างชื่อ (Edit Distance) กับรายการแพ็กเกจยอดนิยมห้าตัว ผลคือ `reqeusts`, `numpyy` และ `pydantlc` ห่างจากชื่อจริงไม่เกินสองตัวอักษร ส่วน `flask` ที่ไม่เกี่ยวกับรายการ และ `requests` ที่เป็นชื่อจริงเอง ไม่ถูกเตือน

นี่เป็นเพียงการเตือนตอนที่ชื่อใหม่เข้ามา ไม่ใช่เครื่องมือที่จับได้ทุกกรณี เช่นชื่อที่ใช้ตัวอักษรหน้าตาเหมือนกันจากภาษาอื่น หรือแพ็กเกจที่ชื่อต่างกันมากแต่ทำตัวเป็นของจริง แบบฝึกไม่ได้ครอบคลุม

</Step>

## Key ที่ลบไฟล์แล้วก็ยังอยู่

นาย A เผลอ Commit ไฟล์ `config.py` ที่มี Key ของคลาวด์ลงไป พอรู้ตัวก็แก้ไฟล์ให้ดึงค่าจาก Environment แล้ว Commit อีกรอบ คิดว่าจบแล้ว (รัน: `exercises/11_supply_chain_secrets.py` ใน Repository ชั่วคราว Key เป็นค่าตัวอย่างรูปแบบ `AKIAIOSFODNN7EXAMPLE`)

แบบฝึกเช็กสามอย่าง อย่างแรก ไฟล์ในโฟลเดอร์ไม่มี Key แล้ว อย่างที่สอง `git show <commit แรก>:config.py` ยังเห็น Key อยู่ครบ ใครที่ Clone Repository ไปก็มี Commit นั้นด้วย และอย่างสุดท้าย `git log -S<Key>` บอกว่า Commit ชื่อ `add config` เป็นผู้เติมเข้ามา กดเดินทีละขั้นในแล็บข้างล่าง

<SecretGitLab client:visible />

สิ่งที่ใช้ได้จริงคือต้อง **เพิกถอน Key** ที่ผู้ให้บริการ แล้วออกใหม่ การเขียน History ใหม่ช่วยให้คนที่ Clone ใหม่ไม่เห็น แต่คนที่ Clone ไปแล้วและสำเนาที่ถูกสำรองไว้ที่อื่นยังมี (ส่วนการเขียน History ใหม่ผู้เขียนไม่ได้รันในบทนี้)

</Step>

## ตัวสแกนหา Secret

ทีมจึงมักใส่ตัวสแกนที่ตรวจทุก Commit ก่อน Push แบบฝึกเขียนตัวเล็ก ๆ ที่ใช้สองวิธี **รูปทรง** คือ Regex ที่จับ Key ที่ผู้ให้บริการออกให้ เช่น `AKIA` ตามด้วยตัวอักษรใหญ่หรือเลขสิบหกตัว และบล็อก `-----BEGIN ... PRIVATE KEY-----` และ **ความสุ่ม** คือวัด Entropy ต่อตัวอักษร ถ้าข้อความยาวและมีค่าเกิน 4.0 บิตต่อตัวอักษร และไม่ได้เป็นตัวอักษรล้วน ก็ถือว่าน่าสงสัย

กับตัวอย่างสามบรรทัด ตัวสแกนเจอสองอย่าง Key รูปทรง AWS และสตริงสุ่ม `x7Kp9Qv2...` ส่วนชื่อยาว ๆ ธรรมดา `a_perfectly_ordinary_long_name_here` ไม่ถูกจับ เพราะ Entropy ของมันอยู่ที่ราว 3.8 ต่ำกว่าเกณฑ์ ขณะที่สตริงสุ่ม 32 ตัวมีราว 5.0 บิตต่อตัวอักษร ตัวเลขเหล่านี้พิมพ์จากแบบฝึกเลย

ตัวสแกนของจริงมี Pattern ครอบคลุมมากกว่านี้มาก แต่ก็พลาดได้ทั้งสองทาง บางครั้งไม่เจอ Key ที่เปลี่ยนรูปไปแล้ว และบางครั้งก็จับค่าสุ่มที่เป็นข้อมูลธรรมดา ตัวสแกนช่วยเราได้จริง แต่ทดแทนการไม่เก็บ Secret ในโค้ดตั้งแต่ต้นไม่ได้ ทางที่ดีกว่าคือส่งค่าผ่าน Environment หรือที่เก็บความลับ

<Callout type="note" title="ที่ไม่ได้รัน">

การเขียน History ใหม่ (`git filter-repo`), เครื่องมือสแกนที่ใช้งานจริง, ที่เก็บความลับอย่าง Vault, และการตรวจ CVE ของ Dependency ที่ติดตั้งจริง ไม่ได้อยู่ในแบบฝึกของบทนี้

</Callout>
