## ข้อความโอนเงินที่ถูกแก้ระหว่างทาง

Alice ส่งข้อความ `pay bob 100` ให้ธนาคาร ระหว่างทางมี Mallory ที่แอบแก้เลขท้ายเป็น `pay bob 900` ถ้าธนาคารไม่มีวิธีเช็ก ก็จะโอนไปตามที่เห็น สิ่งที่เราต้องการคือวิธีที่ทำให้ธนาคารรู้ว่าข้อความถูกแก้ไปแล้ว

เครื่องมือแรกที่เรามักนึกถึงคือ **Hash** ซึ่งเป็นฟังก์ชันที่รับข้อความยาวเท่าไรก็ได้ แล้วคายค่าสั้น ๆ ขนาดคงที่ออกมา ลองดูผลของ SHA-256 กับข้อความสองอัน (รัน: `exercises/02_crypto_basics.py`)

```text
sha256('pay bob 100')  aa843d8373c66e261809019ea8bc71ba2e951e1c378b4bf570e34679efac5f16
sha256('pay bob 900')  70ef8a2487a6d4838ab93b2842806ccf0b89cf56b209312e0761632e4899ea20
```

ข้อความต่างกันตัวเดียว คือเลข 1 กับเลข 9 แต่ค่าที่ได้ดูเหมือนคนละอันกันเลย เมื่อนับบิตที่ต่างกันจากทั้งหมด 256 บิต ได้ 133 บิต ซึ่งเกือบครึ่งหนึ่งพอดี นอกจากนั้นไม่ว่าข้อความจะสั้นหรือยาว (เราลองกับ `x` ซ้ำหมื่นตัว) ค่าที่ได้ก็ยาว 32 ไบต์ หรือ 64 ตัวอักษรฐานสิบหกเท่ากันทุกครั้ง

</Step>

## ลองแก้ข้อความเอง แล้วดูว่าบิตขยับตรงไหน

แล็บข้างล่างคำนวณ SHA-256 ของจริงในเบราว์เซอร์ตอนที่เราพิมพ์ ข้อความแต่ละอันได้ลายนิ้วมือเป็นตาราง 256 ช่อง ช่องที่ทึบคือบิตที่เป็น 1 ส่วนตารางที่สามสว่างเฉพาะช่องที่ลายนิ้วมือของ A กับ B ต่างกัน และตัวอักษรที่ต่างกันในสองข้อความจะเป็นสีแดงให้เห็นด้วย ลองกดปุ่มเปลี่ยนตัวอักษรท้ายของ B หนึ่งตัวหลาย ๆ ครั้ง จะเห็นว่าตัวอักษรที่เปลี่ยนมีแค่ตัวเดียว แต่ตารางที่สามหน้าตาเปลี่ยนไปหมดทุกรอบ และจำนวนช่องที่ต่างกันมักอยู่แถว 128 ลองกด "ให้ B เท่ากับ A" ดูว่าจะไม่มีช่องไหนต่างเลย

สิ่งที่เราเห็นคือคุณสมบัติสองอย่างของ Hash ที่ดี อย่างแรก ข้อความเดียวกันให้ค่าเดิมเสมอ เราจึงเอาไปเปรียบเทียบได้ อย่างที่สอง ข้อความต่างกันนิดเดียวให้ค่าที่ต่างกันมาก เราจึงสังเกตการแก้ได้ทันที

## Hash ไม่ใช่กุญแจล็อก

ทีนี้ลองสมมติว่าเราเก็บ PIN ธนาคารสี่หลักเป็น SHA-256 แทนที่จะเก็บ PIN ตรง ๆ คิดว่าปลอดภัยแล้วใช่ไหม? ฟังก์ชัน Hash ย้อนกลับไม่ได้จริง แต่ PIN สี่หลักมีแค่ 10,000 แบบ เราเลยไล่ลองทุกแบบแล้ว Hash เทียบกัน

```python
target = hashlib.sha256(b"7351").hexdigest()
for n in range(10_000):
    if hashlib.sha256(f"{n:04d}".encode()).hexdigest() == target:
        break
# เจอตอนลองครั้งที่ 7,352
```

โค้ดนี้ลองเลขตั้งแต่ `0000` ขึ้นไปทีละตัว Hash แล้วเทียบกับค่าที่เก็บไว้ ผลที่รันได้คือเจอ PIN ตอนลองครั้งที่ 7,352 และอย่างมากที่สุดจะไม่เกิน 10,000 ครั้ง ซึ่งคอมพิวเตอร์ทำได้ในเสี้ยววินาที

บทเรียนคือ Hash ไม่ได้ซ่อนข้อมูล มันแค่ย้อนกลับตรง ๆ ไม่ได้ ถ้าข้อมูลมีให้เดาไม่กี่แบบ การเดาก็จบเร็ว เราจะกลับมาที่เรื่องนี้ตอนเรียนการเก็บรหัสผ่านโดยเฉพาะ

</Step>

## HMAC: Hash ที่ต้องมี Key

ปัญหาของ Hash ธรรมดาคือใครก็ทำได้ HMAC แก้ด้วยการเอา **Key ลับ** เข้าไปผสมในการคำนวณ ใครที่ไม่มี Key ก็ทำ Tag ที่ถูกต้องไม่ได้ หนังสือ API Security in Action อธิบายว่า Message Authentication Code (MAC) คือ อัลกอริทึมที่คำนวณ Tag จากข้อความกับ Key ลับ เพื่อให้เช็กได้ทั้งว่าข้อความไม่ถูกแก้ และว่ามาจากคนที่มี Key (หนังสือ: API Security in Action บทที่ 5 หน้า 172)

```python
key = b"k" * 32
tag = hmac.new(key, b"pay bob 100", hashlib.sha256).hexdigest()
# e1b2db255689e506cbd5cbe3fd1fb6c4fb1537236abfcea5000d11586eb05104
```

ผลที่ Assert ไว้คือ Key เดิมกับข้อความเดิมให้ Tag เดิม, Key อื่นให้ Tag อื่น, ข้อความที่ถูกแก้ให้ Tag อื่น และ Tag นี้ไม่เท่ากับ SHA-256 ธรรมดาของข้อความเดียวกัน คนที่ไม่มี Key จึงเดา Tag ไม่ได้ การเทียบ Tag เราใช้ `hmac.compare_digest` แทนเครื่องหมาย `==` เพื่อไม่ให้เวลาที่ใช้เปรียบเทียบเผยว่าตรงกันไปกี่ตัวอักษรแล้ว

ข้อจำกัดคือทั้งคนส่งและคนรับต้องมี Key ตัวเดียวกัน เหมาะกับสองฝั่งที่เชื่อใจกันอยู่แล้ว เช่น Server ของเราเอง

</Step>

## AES-GCM: ซ่อนข้อความและจับการแก้ไปพร้อมกัน

HMAC ทำให้รู้ว่าข้อความถูกแก้ แต่ข้อความยังอ่านได้ ถ้าอยากซ่อนด้วย เราใช้ **การเข้ารหัส** AES-GCM เป็นแบบที่เข้ารหัสและตรวจการแก้ไขในขั้นตอนเดียว เรียกว่า Authenticated Encryption (หนังสือ: API Security in Action หัวข้อ 6.3.1 หน้า 197)

```python
aes = AESGCM(key32)
box = aes.encrypt(nonce12, b"card 4111 1111 1111 1111", b"order-17")
# ciphertext ยาว 24 + 16 ไบต์ (ข้อความ + Tag)
```

ผลที่ Assert ไว้มีสี่ข้อ อย่างแรก Ciphertext ยาวเท่าข้อความบวก 16 ไบต์ของ Tag อย่างที่สอง ถ้า Key, Nonce และข้อความกำกับ (ในที่นี้ `order-17`) ถูกต้อง ถอดรหัสได้ข้อความเดิม อย่างที่สาม ถ้าพลิกแค่หนึ่งบิตของ Ciphertext การถอดรหัสจะล้มด้วย `InvalidTag` ไม่ได้ให้ข้อความที่เพี้ยนออกมา และอย่างสุดท้าย ถ้าเอา Ciphertext เดิมไปใช้กับข้อความกำกับอื่น (`order-18`) ก็ถูกปฏิเสธเช่นกัน ซึ่งช่วยกันไม่ให้ใครเอาก้อนที่ถูกต้องไปแปะผิดที่

<Callout type="warn" title="Nonce ห้ามใช้ซ้ำกับ Key เดิม">

Nonce คือเลขที่ต้องไม่ซ้ำสำหรับแต่ละข้อความที่เข้ารหัสด้วย Key เดียวกัน แบบฝึกเช็กไว้ว่า ถ้าใช้ Nonce เดิมกับ Key เดิมกับข้อความเดิม จะได้ Ciphertext เหมือนเดิมเป๊ะ ซึ่งบอกใบ้ให้คนข้างนอกรู้ว่าข้อความซ้ำ และหนังสือเตือนว่าการใช้ Nonce ซ้ำทำให้ความปลอดภัยของ AES-GCM พังได้ (หนังสือ: API Security in Action หน้า 202) เราไม่ได้รันการพังนั้นให้ดู จึงเป็นข้อความที่มาจากหนังสือล้วน ๆ

</Callout>

## Signature: ใครก็ตรวจได้ แต่เซ็นได้คนเดียว

ทั้ง HMAC และ AES-GCM ต้องมี Key ร่วมกัน แล้วถ้าเราอยากให้ใครก็ตรวจได้ว่าข้อความนี้มาจากเราจริง เช่นตอนประกาศเวอร์ชันของโปรแกรม เราใช้ **Signature** ซึ่งมีกุญแจสองดอก คือ Private Key ที่เซ็นได้ และ Public Key ที่ตรวจได้

```python
private = Ed25519PrivateKey.from_private_bytes(bytes(range(32)))
sig = private.sign(b"release 1.4.2")       # 64 ไบต์
private.public_key().verify(sig, b"release 1.4.2")   # ผ่าน
private.public_key().verify(sig, b"release 1.4.3")   # InvalidSignature
```

Signature ของ Ed25519 ยาว 64 ไบต์ ตรวจด้วย Public Key กับข้อความจริงผ่าน แต่ถ้าข้อความถูกแก้ไปแม้เลขเดียว ก็ไม่ผ่าน และเพราะ Public Key เปิดเผยได้ ใครก็ตรวจได้โดยไม่ต้องมีความลับอะไร แต่จะเซ็นแทนเราไม่ได้ เราจะเห็นของพวกนี้อีกในเรื่อง TLS กับ JWT

</Step>

## เทียบทั้งสี่อย่างพร้อมกัน

เลือกเครื่องมือกับสิ่งที่ Mallory ทำในแล็บข้างล่างทีละคู่ แถวบนของภาพคือพัสดุที่ Alice ส่ง สิ่งที่ Mallory ทำกับมัน และพัสดุที่ Bob ได้รับ ส่วนตรงกลางคือ Bob เอาตราที่คำนวณเองมาวางเทียบกับตราที่ติดมากับพัสดุ ถ้าเหมือนกัน Bob รับ ถ้าต่างกัน Bob ปฏิเสธ ตารางสิบสองช่องข้างล่างคำนวณด้วยโค้ดเดียวกับภาพ ช่องไหนป้องกันได้เป็นเครื่องหมายถูก และช่องไหนไม่ได้เป็นกากบาท จุดที่ควรสังเกตคือแถวของ Hash ธรรมดาเป็นกากบาททั้งแถว และมีแค่ AES-GCM ที่ซ่อนข้อความได้
