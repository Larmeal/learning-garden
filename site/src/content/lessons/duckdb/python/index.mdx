## Relation คือ Query ที่ยังไม่ได้รัน

ใน Python เราเขียน SQL เป็นข้อความได้ และเขียน Query ต่อกันเป็นเมธอดก็ได้ แบบหลังเรียกว่า Relational API

```python
rel = con.table("orders").filter("status = 'paid'")
con.execute("insert into t values (3)")
```

ตัวอย่างจริงในแบบฝึกใช้ตาราง `t` เล็ก ๆ ที่มีสองแถว เราสร้าง `rel = con.table("t").filter("x > 0")` แล้ว Insert อีกหนึ่งแถว หลังจากนั้นค่อยนับ `rel.count("*")` ได้ 3 ไม่ใช่ 2 (รัน) แปลว่า `rel` ไม่ได้เก็บผลลัพธ์ตอนที่สร้าง มันเก็บแค่แผนว่า "อ่านตาราง `t` แล้วกรอง `x > 0`" และไปรันเอาจริง ๆ ตอนที่เราขอผลด้วย `fetchall()`, `df()` หรือ `count()`

พอพิมพ์ Relation ออกมาตรง ๆ เห็นแค่แถวต้น ๆ พร้อมชนิดของคอลัมน์ (เช่น `int64`, `varchar`) ไม่ได้ถือผลทั้งหมดไว้ (รัน) กด Lab ด้านล่างทีละขั้นเพื่อดูว่าแต่ละเมธอดเพิ่มอะไรเข้าไปในแผน และเมื่อไรที่ DuckDB อ่านข้อมูลจริง

## เมธอดกับ SQL ได้ผลเท่ากัน

```python
api = (con.table("orders").filter("status = 'paid'")
          .aggregate("customer_id, count(*) as n, round(sum(qty * unit_price), 2) as revenue", "customer_id")
          .order("revenue desc, customer_id").limit(3))
```

`filter`, `aggregate`, `order` และ `limit` ต่อกันได้ผลสามแถวเดียวกับ SQL ที่เขียนเป็นข้อความตรง ๆ (รัน)

| customer_id | orders | revenue |
|---|---|---|
| 1044 | 181 | 27468.37 |
| 144 | 163 | 27222.07 |
| 4109 | 163 | 27213.03 |

ตรงนี้มีเรื่องเล็ก ๆ ที่เจอระหว่างเขียนแบบฝึก ตอนแรกเรา `sum(qty * unit_price)` โดยไม่ปัดเศษ แล้วผลของสองแบบเทียบกันไม่เท่ากันในบางรอบ สาเหตุคือ DuckDB บวกเลขทศนิยมด้วยหลาย Thread เรียงลำดับไม่เหมือนกันทุกรอบ ทำให้หลักท้ายสุดของ `DOUBLE` ต่างกันได้ ผู้เขียนจึงปัดเป็นสตางค์ก่อนเปรียบเทียบ ถ้าจะ Assert ผลรวมของทศนิยมในงานของเราเอง ให้ปัดเศษก่อนเสมอ

## DataFrame ในตัวแปรก็เป็นตาราง

ถ้ามี DataFrame ของ Pandas อยู่ในตัวแปร เรา Query ด้วยชื่อตัวแปรได้เลย

```python
df = con.sql("select * from orders where order_id <= 1000").df()
con.sql("select count(*), sum(qty) from df").fetchone()
```

SQL หาตัวแปรชื่อ `df` ใน Python แล้วอ่านมันเป็นตาราง เรียกว่า Replacement Scan ได้ผลเท่ากับที่ Pandas นับเอง และอ่าน DataFrame ของ Polars กับตาราง Arrow ด้วยชื่อตัวแปรได้เหมือนกัน (รัน)

<Callout type="warn" title="ชื่อตัวแปรต้องอยู่ใน Function ที่รัน SQL">
ตอนเขียนแบบฝึกเราเจอ `Catalog Error: Table with name big does not exist` เมื่อเรียก SQL ที่อ้างตัวแปร `big` จากใน `lambda` เพราะ DuckDB หาชื่อตัวแปรจากตัวแปรโลคอลของ Function ที่เรียก SQL ถ้าตัวแปรอยู่ข้างนอกแล้วถูกใช้ผ่าน Closure มันหาไม่เจอ แก้โดยรับ DataFrame เป็น Parameter ของ Function หรือใช้ `con.register("ชื่อ", df)` ให้ชัดเจน ตัวแปรชื่อ `full` ก็ใช้ไม่ได้ เพราะ `FULL` เป็นคำสงวน (`FULL JOIN`)
</Callout>

</Step>

## GROUP BY เดียวกันในสามเครื่องมือ

เราลองถามคำถามเดิม (จำนวน Order และรายได้ต่อสถานะ ของ Order หนึ่งล้านแถว) กับ DuckDB, Pandas และ Polars โดยให้ข้อมูลอยู่ใน Memory เป็น DataFrame อยู่แล้ว ผลที่ได้คือทั้งสามเครื่องมือให้จำนวนต่อสถานะเท่ากันทั้งสี่ตัว และรายได้ตรงกันถึงสตางค์ (รัน) ส่วนเวลา ในเครื่องนี้ดีที่สุดจาก 5 รอบ คือ

| เครื่องมือ | เวลา |
|---|---|
| DuckDB อ่านจาก DataFrame ของ Pandas | ประมาณ 100 ms |
| DuckDB อ่านจากตารางของ DuckDB เอง | ประมาณ 7 ms |
| Pandas | ประมาณ 40 ms |
| Polars | ประมาณ 3 ms |

ตรงนี้ตัวเลขไม่ได้เป็นอย่างที่หลายคนคาดว่า DuckDB จะเร็วสุด เมื่อให้ DuckDB อ่านจาก DataFrame ของ Pandas มันช้ากว่า Pandas เองสองเท่าครึ่ง แต่เมื่ออ่านจากตารางของมันเองเร็วขึ้นกว่าสิบสี่เท่า ส่วนตัวผู้เขียนเดาว่าเวลาส่วนใหญ่หมดไปกับการอ่านคอลัมน์ `status` ที่ Pandas เก็บเป็น Object ของ Python ทีละค่า แต่ไม่ได้ลองพิสูจน์ ส่วน Polars ในการรันนี้เร็วกว่า DuckDB เองด้วย (ตัวเลขไม่ได้ Assert และเป็นของการรันบนคอมพิวเตอร์เครื่องเดียว ข้อมูลเดียว และ Query เดียว)

สิ่งที่เอาไปใช้ได้คือ ความเร็วของ DuckDB ที่เห็นในบทแรกเป็นความเร็วบนตารางของมันเอง ถ้าข้อมูลอยู่ใน DataFrame ที่ต้องแปลงทุกครั้ง ราคาของการแปลงนั้นก็รวมอยู่ด้วย หนังสืออธิบายว่า DuckDB อ่าน DataFrame ของ Pandas และ Polars ได้โดยตรงไม่ต้องก๊อปปี้ (หนังสือ: DuckDB in Action หัวข้อ 6.3 หน้า 134) ซึ่งผู้เขียนไม่ได้วัดการใช้ Memory เพื่อยืนยัน

</Step>

## ผลลัพธ์ออกได้หลายรูป

Relation ตัวเดียวส่งออกเป็นอะไรก็ได้ตามที่เครื่องมือถัดไปต้องการ

```python
r = con.sql("select order_id, qty, status from orders where order_id <= 5 order by order_id")
r.fetchall()      # List ของ Tuple
r.df()            # DataFrame ของ pandas
r.arrow()         # ตาราง Arrow
r.pl()            # DataFrame ของ Polars
r.fetchnumpy()    # Dict ของ NumPy array (คีย์ order_id, qty, status)
```

ทั้งห้ารูปรันผ่าน (รัน) และตาราง Arrow ยังคงชนิดไว้ `BIGINT` ของ DuckDB เป็น `int64` ใน Arrow (รัน) เพราะ Arrow เป็นรูปแบบกลางที่ Polars, Pandas และเครื่องมืออื่นอ่านต่อได้ จึงเป็นทางส่งผ่านข้อมูลระหว่างเครื่องมือที่ไม่ต้องแปลงอะไรมาก (หนังสือ: DuckDB in Action หัวข้อ 6.5 หน้า 141)

## Function ของ Python ที่ SQL เรียกได้

ถ้า SQL ไม่มี Function ที่ต้องการ เราลงทะเบียนของ Python เข้าไปได้ สองแบบ

```python
def with_tax(x: float) -> float:
    return round(x * 1.07, 2)

con.create_function("with_tax", with_tax, [DOUBLE], DOUBLE)            # รับทีละค่า

def with_tax_vec(x):                                                   # รับทั้ง Vector
    return pc.round(pc.multiply(x, 1.07), 2)
con.create_function("with_tax_vec", with_tax_vec, [DOUBLE], DOUBLE, type="arrow")
```

แบบแรก DuckDB เรียก Function ของเราทีละค่า แบบที่สองส่งมาทั้งก้อนเป็น Array ของ Arrow ซึ่งเรียก Function ครั้งเดียวต่อหนึ่งก้อน ทั้งสองแบบได้ผลรวมเท่ากันเมื่อใช้กับ 200,000 แถว (รัน) แต่เวลาต่างกัน ในการรันหนึ่งครั้ง แบบทีละค่าใช้ประมาณ 80 ms และแบบทั้ง Vector ใช้ประมาณ 37 ms แบบหลังเร็วกว่า (ค่านี้ในแบบฝึกถูก Assert ว่าแบบ Vector เร็วกว่า แต่ตัวเลขเปลี่ยนไปตามเครื่อง) เหตุผลคือการข้ามจาก DuckDB ไป Python มีราคาต่อครั้ง การข้ามน้อยครั้งกว่าจึงถูกกว่า (หนังสือ: DuckDB in Action หัวข้อ 6.4 หน้า 136)

ค่าที่ส่งเข้า SQL ควรผูกเป็น Parameter เสมอ ไม่ต้องต่อข้อความ ในแบบฝึก ข้อความที่พยายามแทรก `paid' or '1'='1` ผ่าน `?` ถูกมองเป็นค่าเดียวและไม่ตรงกับแถวไหนเลย (0 แถว) และ Parameter แบบมีชื่อ (`$s`, `$q`) ได้จำนวนเท่ากับ SQL ที่เขียนค่าตรง ๆ (รัน)

</Step>
