## เปิด Python แล้วถาม Order หนึ่งล้านแถว

เราลองเริ่มจากของจริงก่อน สมมติว่าเรามีตาราง `orders` ที่เก็บคำสั่งซื้อหนึ่งล้านแถว ในตารางมี `order_id`, `customer_id`, `qty`, `unit_price`, `status` และ `order_ts` ซึ่งแบบฝึกของเส้นทางนี้สร้างข้อมูลชุดนี้ด้วย DuckDB เอง จึงได้ตัวเลขเหมือนเดิมทุกครั้ง ข้อมูลทั้งหมดเป็นข้อมูลสังเคราะห์

```python
import duckdb

con = duckdb.connect()                      # ฐานข้อมูลใน Memory
# ... สร้างตาราง orders หนึ่งล้านแถว (ดู ddb.py)
con.sql("select status, count(*) from orders group by status order by status").fetchall()
```

```text
status     orders  revenue
---------  ------  -----------
cancelled  70156   10026036.39
paid       699821  99866243.04
refunded   30104   4284700.24
shipped    199919  28559172.37
```

`duckdb.connect()` เปิดฐานข้อมูลขึ้นมาหนึ่งตัว ถ้าไม่ใส่ชื่อไฟล์ มันจะอยู่ใน Memory `con.sql(...)` ส่ง SQL เข้าไป และ `.fetchall()` ดึงผลกลับมาเป็น List ของ Tuple ตรงนี้อยากให้สังเกตสิ่งที่ไม่เกิดขึ้น เราไม่ได้ติดตั้ง Server ไม่ได้ตั้งรหัสผ่าน และไม่ได้ใส่ Host กับ Port ที่ไหนเลย (รัน)

## DuckDB อยู่ใน Process ของเรา

เอ๊ะ แล้วโปรแกรมที่ตอบคำถามเราอยู่ที่ไหน เรามาลองพิสูจน์กัน ก่อนจะสร้างตาราง เราจดจำนวน Child Process ของ Python ตัวนี้ จำนวน Port ที่มันเปิดรอรับการเชื่อมต่อ และขนาด Memory ที่มันใช้ แล้วสร้างตารางหนึ่งล้านแถว จากนั้นวัดซ้ำ ผลที่ได้ในเครื่องนี้คือ

| สิ่งที่วัด | ก่อนสร้างตาราง | หลังสร้างตาราง |
|---|---|---|
| Child Process | 0 | 0 |
| Port ที่เปิดรอ | ไม่มี | ไม่มี |
| Memory ของ Process Python ตัวนี้ | (ค่าเริ่มต้น) | เพิ่มขึ้นประมาณ 84 MB |

ไม่มี Process ใหม่และไม่มี Port ใหม่ แต่ Memory ของ Process Python เองโตขึ้น เพราะ DuckDB เป็นไลบรารีที่ถูกโหลดเข้ามาอยู่ใน Process ของเรา (รัน) หนังสือเรียกรูปแบบนี้ว่า Embedded Database คือฐานข้อมูลที่ทำงานอยู่ภายใน Process อื่น เช่น แอปพลิเคชันหรือ Notebook ของเรา และไม่ถูกเข้าถึงผ่านเครือข่าย (หนังสือ: DuckDB in Action หัวข้อ 1.1 หน้า 2)

เพื่อให้เห็นภาพ เรามองฐานข้อมูลแบบที่เคยใช้อย่าง PostgreSQL เป็นร้านอาหารที่เราต้องโทรสั่ง คำสั่งต้องเดินทางไปที่ร้าน ครัวทำอาหาร แล้วส่งกลับมาทางคนส่งของ ส่วน DuckDB เหมือนมีครัวเล็ก ๆ อยู่ในบ้านของเราเอง เราเดินไปเปิดตู้เย็นเองได้เลยโดยไม่ต้องมีใครเดินทาง กด Lab ด้านล่างแล้วเปรียบเทียบทีละขั้นว่าข้อมูลถูกก๊อปปี้กี่ครั้ง

## ฐานข้อมูลคือไฟล์เดียว

ถ้าให้ DuckDB เก็บลงดิสก์ เราใส่ชื่อไฟล์ลงใน `connect` ตัวอย่างนี้เก็บ Order 100,000 แถวพร้อมตาราง Customer ไว้ในไฟล์ `shop.duckdb`

```python
con = duckdb.connect("shop.duckdb")
# ... สร้างตาราง ...
con.close()
```

พอปิดการเชื่อมต่อแล้วเปิดดูโฟลเดอร์ จะเห็นไฟล์เดียวชื่อ `shop.duckdb` ขนาด 1,323,008 Byte ไม่มีไฟล์ Log หรือไฟล์ Config วางอยู่ข้าง ๆ (รัน) เปิดไฟล์นี้กลับมาด้วย `duckdb.connect("shop.duckdb", access_mode="read_only")` ก็เจอ Order ครบ 100,000 แถว เราก๊อปปี้ไฟล์ไปให้เพื่อนหรือส่งขึ้น Cloud ได้เหมือนไฟล์ธรรมดา ซึ่งต่างจาก PostgreSQL ที่ข้อมูลกระจายอยู่ในโฟลเดอร์ของ Server หลายไฟล์

ส่วนข้างในไฟล์นั้นจัดอย่างไร เดี๋ยวเราจะมาเปิดดูกันในบท [ข้อมูลถูกเก็บอย่างไร](/duckdb/storage/)

</Step>

## เทียบกับ SQLite ในงานสรุปข้อมูล

SQLite เป็นฐานข้อมูลที่อยู่ใน Process และเก็บเป็นไฟล์เดียวเช่นกัน โดย Python มีโมดูล `sqlite3` ให้ใช้อยู่แล้ว เราจึงลองให้ทั้งสองตัวตอบคำถามเดียวกันกับข้อมูลชุดเดียวกัน หนึ่งล้านแถว

```sql
select status, count(*), round(sum(qty * unit_price), 2)
from orders group by status order by status
```

ทั้งสองตัวคืนสี่แถวเหมือนกัน จำนวนแถวตรงกัน และรายได้ตรงกันถึงสตางค์ (รัน) ต่างกันที่เวลา ในการรันหนึ่งครั้งบนเครื่องนี้ DuckDB ใช้ประมาณ 22 ms ส่วน SQLite ใช้ประมาณ 1,477 ms ตัวเลขเวลาไม่ได้ Assert เพราะขึ้นกับคอมพิวเตอร์ที่รัน และ SQLite ในการทดลองนี้ไม่มี Index เหมือน DuckDB

เหตุผลที่ต่างกันมากขนาดนี้ไม่ได้อยู่ที่ฝีมือของใคร SQLite ถูกออกแบบมาให้เก็บข้อมูลเป็นแถว เหมาะกับการอ่านหรือแก้แถวเดียวทั้งแถว ส่วน DuckDB เก็บข้อมูลแยกเป็นคอลัมน์และประมวลผลทีละกลุ่มแถว ซึ่งเหมาะกับคำถามที่อ่านหลายแถวแต่ใช้ไม่กี่คอลัมน์ ทั้งสองอย่างเดี๋ยวเราจะมาเปิดดูกันในบท [ข้อมูลถูกเก็บอย่างไร](/duckdb/storage/) และบท [Query รันอย่างไร](/duckdb/execution/)

หนังสือสรุปไว้ว่า DuckDB ควรใช้กับงานวิเคราะห์ที่เขียนเป็น SQL ได้ กับข้อมูลที่มีอยู่แล้ว (ไม่ใช่ข้อมูลที่ไหลเข้ามาเรื่อย ๆ) และปริมาณไม่เกินหลายร้อย GB (หนังสือ: DuckDB in Action หัวข้อ 1.3 หน้า 4)

</Step>

## สิ่งที่ DuckDB ไม่ถนัด

ลองนึกถึงเว็บไซต์ที่ทุกครั้งที่ลูกค้ากดสั่งซื้อจะ Insert หนึ่งแถว เราจำลองงานแบบนี้ด้วยการ Insert 2,000 แถวทีละคำสั่ง เทียบกับส่งทั้ง 2,000 แถวไปทีเดียวด้วย `executemany` ผลที่ได้ในเครื่องนี้คือ

| วิธี | เวลา |
|---|---|
| `INSERT` ทีละคำสั่ง 2,000 ครั้ง | ประมาณ 9,253 ms |
| `executemany` 2,000 แถว | ประมาณ 749 ms |

ชุดแถวเหมือนกัน แต่ต่างกันกว่าสิบเท่า (รัน) แต่ละคำสั่งต้อง Parse, วางแผน และ Commit ของตัวเอง ซึ่ง DuckDB ไม่ได้ออกแบบมาเพื่อสิ่งนี้ หนังสือบอกตรง ๆ ว่า DuckDB มีการสนับสนุน Transaction และการเขียนพร้อมกันแบบจำกัด จึงไม่เหมาะกับแอปพลิเคชันที่รับข้อมูลเข้ามาเรื่อย ๆ ตามใจผู้ใช้ และไม่ใช่ฐานข้อมูลแบบ Streaming (หนังสือ: DuckDB in Action หัวข้อ 1.4 หน้า 5)

ถ้าข้อมูลมาทีละแถวจริง ๆ ให้เก็บเป็นก้อนเล็ก ๆ ก่อน แล้วค่อยโหลดเข้าทีเดียว เรื่องการเขียนพร้อมกันหลาย Process เราจะลองกันจริงในบท [ข้อมูลที่ใหญ่กว่า Memory และหลายคนใช้พร้อมกัน](/duckdb/beyond-memory/)

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| DuckDB รันใน Process ของ Python: ไม่มี Child Process, ไม่มี Port ที่เปิดรอ, Memory ของ Process โตขึ้น | รัน: `exercises/01_what_is_duckdb.py` |
| ฐานข้อมูลที่ปิดแล้วเหลือไฟล์เดียว (`shop.duckdb` 1,323,008 Byte สำหรับ 100,000 Order) และเปิดกลับมาได้ | รัน: `exercises/01_what_is_duckdb.py` |
| GROUP BY หนึ่งล้านแถวให้คำตอบเท่ากันใน DuckDB กับ SQLite (เวลา 22 ms กับ 1,477 ms เป็นของการรันครั้งเดียว) | รัน: `exercises/01_what_is_duckdb.py` |
| INSERT ทีละคำสั่ง 2,000 ครั้งช้ากว่า Executemany กว่าสิบเท่า (9,253 ms กับ 749 ms ในการรันครั้งเดียว) | รัน: `exercises/01_what_is_duckdb.py` |
| DuckDB เป็น Embedded Database ที่ CWI เริ่มสร้างในปี 2018 | หนังสือ: DuckDB in Action หัวข้อ 1.1 หน้า 2 |
| เหมาะกับงานวิเคราะห์ที่เป็น SQL ข้อมูลที่มีอยู่แล้วและไม่เกินหลายร้อย GB | หนังสือ: DuckDB in Action หัวข้อ 1.3 หน้า 4 |
| ไม่เหมาะกับการเขียนพร้อมกันและข้อมูลสตรีม | หนังสือ: DuckDB in Action หัวข้อ 1.4 หน้า 5 |
| ภาพ Client-server ใน Lab | ผู้เขียน: ไม่ได้รัน PostgreSQL |
