## ไฟล์เล็กกว่า CSV เกือบแปดเท่าได้อย่างไร

ในบทแรกเราเห็นว่าฐานข้อมูลคือไฟล์เดียว ลองเทียบขนาดกับ CSV ของข้อมูลชุดเดียวกัน

| ไฟล์ | ขนาด (Byte) |
|---|---|
| `orders.csv` (Order หนึ่งล้านแถว) | 49,994,465 |
| `shop.duckdb` (Order หนึ่งล้านแถวกับ Customer 5,000 คน) | 6,565,888 |

ไฟล์ DuckDB เล็กกว่า CSV เกือบแปดเท่า (6.6 MB เทียบกับ 50 MB) ทั้งที่เก็บตาราง Customer เพิ่มด้วย (รัน) เอ๊ะ ทำไมถึงเล็กได้ขนาดนี้ และทำไม Filter บางแบบถึงเร็วกว่าอีกแบบมากทั้งที่ตารางเดียวกัน คำตอบอยู่ที่วิธีที่ DuckDB จัดข้อมูลข้างในไฟล์ ซึ่งเราจะเปิดดูทีละชั้นด้วยฟังก์ชัน `pragma_storage_info`

</Step>

<Step>

## ตัดตารางเป็น Row Group

DuckDB ไม่ได้เก็บตารางเป็นก้อนเดียว มันตัดแถวออกเป็นกลุ่มเรียกว่า Row Group แล้วภายในแต่ละกลุ่มจึงเก็บแยกเป็นคอลัมน์ ลองถามว่าตาราง `orders` มีกี่กลุ่ม

```sql
select row_group_id, max(count)
from pragma_storage_info('orders')
where segment_type != 'VALIDITY' group by all order by 1
```

ผลคือ 9 กลุ่ม แปดกลุ่มแรกมี 122,880 แถวเท่ากัน และกลุ่มสุดท้ายมี 16,960 แถวที่เหลือ (8 × 122,880 + 16,960 = 1,000,000) (รัน) ตัวเลข 122,880 มาจากค่าคงที่ `DEFAULT_ROW_GROUP_SIZE` ใน `src/include/duckdb/storage/storage_info.hpp` ของ DuckDB v1.5.6 (Source) และเท่ากับ 60 Vector ที่ Vector ละ 2,048 แถว (รัน) หนังสือก็บอกว่า Row Group หนึ่งมีแถวได้สูงสุด 122,880 แถว (หนังสือ: DuckDB in Action หัวข้อ 10.2.2 หน้า 243)

</Step>

## แต่ละคอลัมน์บีบอัดด้วยวิธีของตัวเอง

ในแต่ละ Row Group ข้อมูลถูกแยกเก็บเป็นคอลัมน์ และ DuckDB เลือกวิธีบีบอัดให้แต่ละคอลัมน์เอง ผลของ Row Group แรกคือ

| คอลัมน์ | วิธีบีบอัด |
|---|---|
| `order_id`, `customer_id`, `product_id`, `qty`, `order_ts` | BitPacking |
| `status` | Dictionary |
| `unit_price` | ALP |

ตัวเลขจำนวนเต็มที่ช่วงค่าแคบ (`qty` มีแต่ 1 ถึง 5) ถูกอัดให้ใช้ Bit น้อยที่สุดที่ใส่ค่าได้ (BitPacking) ข้อความที่มีแค่สี่แบบ (`status`) เก็บเป็นพจนานุกรมสี่ค่าแล้วเก็บเลขลำดับแทนข้อความ และราคาทศนิยมใช้วิธีเฉพาะสำหรับ `DOUBLE` ที่เรียกว่า ALP (รัน) นี่คือเหตุผลที่ไฟล์เล็กกว่า CSV มาก และเพราะข้อมูลของคอลัมน์เดียวกันอยู่ติดกัน ค่าที่คล้ายกันจึงอัดได้ดี ตารางด้านบนเป็นผลของข้อมูลชุดนี้ ถ้าข้อมูลเปลี่ยน วิธีที่ DuckDB เลือกก็อาจเปลี่ยนตาม (ในการรันอื่นเราเห็นชื่อของ Dictionary เป็น `DICT_FSST`)

</Step>

## ค่าต่ำสุดและสูงสุดของแต่ละกลุ่ม

นอกจากข้อมูล DuckDB เก็บสถิติสั้น ๆ ของแต่ละคอลัมน์ในแต่ละ Row Group ไว้ด้วย รวมถึงค่าต่ำสุดและสูงสุด ซึ่งดึงมาดูได้จากคอลัมน์ `stats` ของ `pragma_storage_info` ตารางด้านล่างคือช่วงของ `order_ts` ในแต่ละกลุ่ม

|---|---|---|
| 0 | 2025-01-01 00:00:00 | 2025-02-14 19:11:28.5 |
| 1 | 2025-02-14 19:12:00 | 2025-03-31 14:23:28.5 |
| 2 | 2025-03-31 14:24:00 | 2025-05-15 09:35:28.5 |
| 3 | 2025-05-15 09:36:00 | 2025-06-29 04:47:28.5 |
| 4 | 2025-06-29 04:48:00 | 2025-08-12 23:59:28.5 |
| 5 | 2025-08-13 00:00:00 | 2025-09-26 19:11:28.5 |
| 6 | 2025-09-26 19:12:00 | 2025-11-10 14:23:28.5 |
| 7 | 2025-11-10 14:24:00 | 2025-12-25 09:35:28.5 |
| 8 | 2025-12-25 09:36:00 | 2025-12-31 13:59:28.5 |

ช่วงของทั้งเก้ากลุ่มเรียงต่อกันและไม่ทับกันเลย เพราะข้อมูลของเราถูกสร้างให้เวลาเพิ่มขึ้นตาม `order_id` ส่วน `customer_id` ในทุกกลุ่มมีช่วง 1 ถึง 5,000 เหมือนกันหมด ค่าต่ำสุดกับสูงสุดของคอลัมน์นี้จึงบอกอะไรไม่ได้เลย (รัน) ตรงนี้เองคือกุญแจของเรื่องต่อไป

## Filter ที่อ่านน้อยและ Filter ที่อ่านหมด

ถ้า Filter ไม่ตรงกับช่วงของกลุ่มไหน DuckDB ข้ามทั้งกลุ่มได้โดยไม่ต้องอ่านข้อมูล เราวัดจำนวนแถวที่ Scan ต้องดูของ Filter หกแบบจาก Profile ที่ Engine เขียนเอง

| Filter | แถวที่ Scan ดู | Row Group ที่ถูกอ่าน | แถวที่ตรงเงื่อนไข |
|---|---|---|---|
| `order_ts >= '2025-12-26'` | 16,960 | 1 (กลุ่ม 8) | 15,314 |
| `order_ts` ในเดือนมีนาคม | 245,760 | 2 (กลุ่ม 1 และ 2) | 85,029 |
| `order_id = 777` | 122,880 | 1 (กลุ่ม 0) | 1 |
| `customer_id = 5` | 1,000,000 | 9 | 189 |
| `status = 'refunded'` | 1,000,000 | 9 | 30,104 |
| ไม่มี Filter | 1,000,000 | 9 | 1,000,000 |

ตัวเลขแถวที่ Scan ดูตรงกับผลรวมของ Row Group ที่ช่วง Min ถึง Max ทับกับ Filter ทุกแถวของตาราง (รัน) นั่นคือ DuckDB ตัดสินใจจากค่าต่ำสุดกับสูงสุดอย่างเดียว ไม่ได้เปิดดูข้อมูลข้างใน `customer_id = 5` ตรงกับแค่ 189 แถว แต่ 5 อยู่ในช่วง 1 ถึง 5,000 ของทุกกลุ่ม จึงต้องอ่านครบทั้งเก้า เปลี่ยน Filter ใน Lab แล้วดูว่ากลุ่มไหนถูกอ่าน

<RowGroupLab client:visible />

สิ่งที่เอาไปใช้ได้คือ ถ้าตารางถูกเรียงตามคอลัมน์ที่เรากรองบ่อย (เช่นเวลา) การกรองจะข้ามกลุ่มได้มาก ถ้าไม่ได้เรียงก็อ่านครบเกือบทุกกลุ่มเหมือนเดิม ข้อมูลที่ถูก Insert ตามลำดับเวลาจึงได้เปรียบตามธรรมชาติ ส่วนตารางที่ Insert สลับลำดับอาจไม่ได้ประโยชน์นี้

## Log ก่อน แล้วค่อยรวมเข้าไฟล์: WAL กับ Checkpoint

ตอนเราสั่ง `INSERT` DuckDB ไม่ได้เขียนลงไฟล์ฐานข้อมูลทันที มันเขียนลงไฟล์ Log แยกชื่อ `shop.duckdb.wal` ก่อน เรียกว่า Write-Ahead Log แล้วค่อยรวมเข้าไฟล์หลักเป็นระยะ ๆ เราลองดูในแบบฝึก เปิดฐานข้อมูลที่ปิดไว้อย่างสะอาด ตอนนั้นไม่มีไฟล์ `.wal` แล้วสร้างตารางกับ Insert สองแถว

- หลัง `INSERT` มีไฟล์ `.wal` ขึ้นมา ขนาด 260 Byte สำหรับสองแถว
- หลัง `CHECKPOINT` ไฟล์ `.wal` หายไป เพราะ DuckDB รวมสิ่งที่อยู่ใน Log เข้าไฟล์หลักแล้ว (รัน)

ถ้าไม่สั่งเอง DuckDB จะ Checkpoint ให้เมื่อ Log โตถึงเกณฑ์ ค่าตั้งต้นของ `checkpoint_wal_size` คือ `1 << 24` หรือ 16 MiB (Source: `src/include/duckdb/main/config.hpp` บรรทัด 101) ถ้าโปรแกรมล้มก่อนถึงตอนนั้น Log ที่เหลือจะถูกเล่นซ้ำตอนเปิดไฟล์ครั้งต่อไปเพื่อกู้การเปลี่ยนแปลงที่ Commit แล้ว ข้อหลังนี้เล่าตามกลไกของ WAL โดยทั่วไป ไม่ได้ทดลองทำให้โปรแกรมล้มจริง

</Step>

## Transaction: เห็นเฉพาะของตัวเองจนกว่าจะ Commit

ทุกคำสั่งที่เปลี่ยนข้อมูลอยู่ใน Transaction ถ้าเราเปิดด้วย `BEGIN` เองก็เลือกได้ว่าจะเก็บ (`COMMIT`) หรือทิ้ง (`ROLLBACK`) ในแบบฝึก ตาราง `notes` มีสองแถว

1. `BEGIN` แล้ว Insert แถวที่สามผ่าน Connection หนึ่ง Connection นั้นนับได้ 3 แถว
2. Connection ที่สองของฐานข้อมูลเดียวกัน (`con.cursor()`) นับได้ 2 แถว เพราะยังไม่ได้ `COMMIT`
3. `ROLLBACK` แล้วนับได้ 2 แถวอีกครั้ง แถวที่สามหายไป
4. ทำซ้ำแต่ `COMMIT` แทน Connection ที่สองเห็น 3 แถวทันที

ทั้งสี่ข้อรันผ่าน (รัน) หนังสือเรียกกลไกนี้ว่า MVCC ร่วมกับ Optimistic Concurrency Control และอธิบายไว้ในภาคผนวกว่าทำงานอยู่ภายใน Process เดียว (หนังสือ: DuckDB in Action ภาคผนวก A หัวข้อ A.2 หน้า 267) เรื่องการเขียนจากหลาย Process เราจะลองกันในบท [ข้อมูลที่ใหญ่กว่า Memory และหลายคนใช้พร้อมกัน](/duckdb/beyond-memory/)

</Step>
