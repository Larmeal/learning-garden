## ปัญหาของสายที่ทุกคนฟังได้

ที่ผ่านมาข้อความ HTTP ทั้งหมดที่เรา Capture ได้เป็นข้อความธรรมดา ใน[บท 1](/networking/big-picture/) เราอ่าน `GET /hello.txt` ได้จาก Packet เลย ซึ่งหมายความว่าทุกคนที่อยู่ระหว่างทาง คือ Router, Wi-Fi ที่เราต่อ หรือผู้ให้บริการอินเทอร์เน็ต อ่านและแก้ไขข้อมูลได้ TLS (Transport Layer Security) คือตัวที่ทำให้เรื่องนี้ไม่เป็นปัญหา มันทำสองอย่างบน TCP ที่มีอยู่แล้ว อย่างแรกคือเข้ารหัสข้อมูล อย่างที่สองคือพิสูจน์ตัวตนของ Server ว่าเป็นตัวที่เราตั้งใจจะคุยด้วยจริง (หนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 877)

ในแบบฝึกเราสร้างโลกเล็ก ๆ ขึ้นมา มีผู้ออกใบรับรองสองราย ชื่อ Garden Test CA กับ Other Test CA และ Certificate ของ Server สี่ใบ ใบที่ถูกต้อง ใบที่ชื่อไม่ตรง ใบที่หมดอายุ และใบที่ออกโดยผู้ออกอีกราย แล้วให้ Client กับ Server ที่ใช้ Python `ssl` คุยกันผ่านสายที่หน่วงทิศละ 10 มิลลิวินาที จับ Packet ที่ฝั่ง Client (รัน: `exercises/11_tls.py`) เนื่องจากทุกอย่างสร้างเองในเครื่อง ผู้ออกใบรับรองเหล่านี้จึงไม่มีอยู่จริงบนอินเทอร์เน็ต

## ดู Handshake บนสายจริง

Client เริ่มด้วย Handshake ของ TCP ตามปกติ แล้วข้อมูลชุดแรกที่ส่งคือ **ClientHello** ซึ่งยังอ่านได้ทั้งหมด เราถอดมันออกมาจาก Packet (รัน, RFC: RFC 8446 หัวข้อ 4.1.2)

```text
server name (SNI): garden.test
versions offered:  TLS 1.3 (0x0304), TLS 1.2 (0x0303)
key share:         x25519, 32 ไบต์
cipher suites:     18 ชุด
ClientHello ยาว 512 ไบต์ ใน Record ขนาด 517 ไบต์
```

ข้อมูลสามอย่างที่น่าสนใจ ชื่อที่ Client อยากคุยด้วย (SNI) ถูกส่งแบบอ่านได้ เพราะ Server ที่ถือหลายชื่อต้องรู้ว่าจะเลือก Certificate ใบไหน (หนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 887) ใครแอบดูสายก็รู้ว่าเรากำลังเข้าเว็บไหน แม้ไม่รู้ว่าเราทำอะไร อย่างที่สองคือ Key Share ตัวเลขสำหรับ Key Exchange ที่ส่งมาตั้งแต่ข้อความแรกเลย ซึ่งเป็นเหตุผลที่ TLS 1.3 ตกลงกุญแจได้เร็ว และอย่างสุดท้ายคือช่อง Version ใน Header ของ Record ซึ่งบอก `0x0301` ทั้งที่เสนอ 1.3 ไว้ เป็นค่าที่ใส่ไว้เพื่อให้กล่องกลางทางรุ่นเก่าไม่งง เวอร์ชันจริงอยู่ใน Extension `supported_versions` (รัน, RFC 8446 หัวข้อ 4.1.2)

Server ตอบ **ServerHello** ซึ่งยังอ่านได้ และตั้งแต่ตรงนี้ทุกอย่างเข้ารหัส (รัน) ใน TLS 1.3 "ข้อความ Handshake หลัง ServerHello ถูกเข้ารหัสทั้งหมด" ตามที่ RFC 8446 หัวข้อ 1.2 ระบุ เราเห็นสิ่งนี้บนสายจริง

| Record ฝั่ง Server | ชนิดที่เห็นบนสาย | ขนาด |
|---|---|---|
| 1 | handshake (ServerHello) | 122 |
| 2 | change_cipher_spec | 1 |
| 3 ถึง 7 | application_data | 23, 410, 96, 69, 250 |
| 8 ถึง 9 | application_data | 250, 89 |

ทุก Record หลัง ServerHello ใช้ชนิด `application_data` เหมือนข้อมูลจริง คนแอบดูแยกไม่ออกว่าอันไหนเป็น Certificate อันไหนเป็นข้อมูลของแอป ส่วน `change_cipher_spec` เป็นของที่เหลือไว้ให้กล่องกลางทางเก่าเข้าใจ เราเดาจากขนาดได้ว่า Record 410 ไบต์น่าจะเป็น Certificate และสอง Record 250 ไบต์น่าจะเป็น Session Ticket แต่นี่เป็นการอนุมานของผู้เขียน ไม่ได้ถอดรหัสดู ที่ยืนยันได้จริงมีสองข้อ คือข้อความ `GET /hello` กับ `hello, garden` ไม่ปรากฏบนสายเลย และชื่อ `garden` ปรากฏเฉพาะใน ClientHello ขาขึ้น ไม่ปรากฏขาลงสักไบต์ (รัน)

TLS 1.2 ต่างออกไป เมื่อจับ Handshake ของ 1.2 ในแบบฝึกเดียวกัน Record ฝั่ง Server คือ ServerHello, Certificate (390 ไบต์), ServerKeyExchange, ServerHelloDone และ NewSessionTicket เป็นข้อความธรรมดาทั้งหมด จนถึง change_cipher_spec แล้วค่อยเข้ารหัส (รัน, หนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 881 ถึง 888) ใครแอบดูก็เห็น Certificate ว่า Server คือใคร

## กว่าจะส่งข้อมูลได้ ต้องเสียกี่รอบเวลา

กดเล่น Lab แล้วสลับ TLS 1.3 กับ TLS 1.2 ดูลำดับข้อความ รอบเวลาที่ผ่านไป และสิ่งที่คนแอบดูเห็นในแต่ละข้อความ

<TlsLab client:visible />

ตัวเลขที่วัดได้ในแบบฝึก สายมี RTT 20 มิลลิวินาที เวลาที่นับจากเริ่ม `connect` จนได้ Byte แรกของ Response (รัน)

| แบบ | เวลา (ประมาณ ±2 ms ต่อการรัน) | จำนวนรอบเวลา |
|---|---|---|
| HTTP ธรรมดา | 42 ms | 2.1 |
| TLS 1.3 | 64 ms | 3.2 |
| TLS 1.2 | 84 ms | 4.2 |
| TLS 1.3 เมื่อ Client ไม่ตั้ง `TCP_NODELAY` | 84 ms | 4.2 |

HTTP ธรรมดาใช้สองรอบเวลา หนึ่งรอบสำหรับ Handshake ของ TCP และหนึ่งรอบสำหรับ Request กับ Response TLS 1.3 เพิ่มหนึ่งรอบเวลา เพราะ ClientHello ส่ง Key Share มาตั้งแต่ข้อความแรก Server จึงตอบกลับพร้อมทุกอย่างที่ Client ต้องมีในครั้งเดียว ส่วน TLS 1.2 เพิ่มสองรอบเวลา เพราะ Client ต้องรอ ServerHello ก่อนถึงส่งส่วนของ Key Exchange (หนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 881 ถึง 888, RFC 8446 หัวข้อ 2) ถ้ามี Connection ใหม่เป็นพัน ๆ ครั้ง หนึ่งรอบเวลาที่ประหยัดได้มีความหมายมาก

แถวสุดท้ายคือสิ่งที่เราไม่ได้คาดไว้ ตอนแรกแบบฝึกได้ 84 มิลลิวินาทีกับ TLS 1.3 ทั้งที่ควรเป็น 64 สาเหตุคือ Nagle จาก[บท 8](/networking/tcp-reliability/#nagle-รอรวมข้อมูลเล็ก-ๆ-ให้เป็นก้อนใหญ่) Finished ของ Client เป็นข้อความเล็กที่ยังไม่ได้ ACK ตอนที่โปรแกรมเขียน Request ตามไป Nagle จึงกั๊ก Request ไว้จนได้ ACK ของ Finished ซึ่งใช้อีกหนึ่งรอบเวลา เมื่อตั้ง `TCP_NODELAY` ก็กลับมาเป็น 64 ถ้าโปรแกรมของเราเขียน Socket เอง จึงควรตั้งตัวเลือกนี้เมื่อต้องการให้ Request แรกออกทันที นี่เป็นตัวอย่างที่ดีว่า Nagle ใน[บท 8](/networking/tcp-reliability/) กลับมาส่งผลกับ TLS ในบทนี้ (รัน)

</Step>

## Client ตรวจอะไรบ้างก่อนเชื่อ Server

การเข้ารหัสอย่างเดียวไม่พอ ถ้าเราคุยอย่างลับสุดยอดกับคนผิด ก็ไม่มีประโยชน์ TLS จึงให้ Server ส่ง Certificate มาพิสูจน์ตัวตน ซึ่งเป็นเอกสารที่บอกว่า "กุญแจสาธารณะนี้เป็นของชื่อ garden.test" และมีลายเซ็นของผู้ออกใบรับรองที่เรา (หรือระบบปฏิบัติการของเรา) เชื่อถืออยู่แล้ว (หนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 871 และ RFC 8446 หัวข้อ 4.4.2) ใบที่ถูกต้องของเรามีหน้าตาแบบนี้ (รัน)

```text
subject  garden.test
issuer   Garden Test CA
SAN      DNS garden.test, IP 10.0.2.2
```

Client ตรวจสามอย่าง คือสายของลายเซ็นไล่ขึ้นไปถึงผู้ออกที่เราเชื่อ ชื่อที่เราต่อไปหาอยู่ในรายการชื่อของใบ (SAN) และใบยังไม่หมดอายุ ทดสอบทีละข้อโดยให้ Server แต่ละตัวใช้ใบที่ผิดคนละแบบ และดูข้อความที่ Client รายงาน (รัน)

| กรณี | ข้อความจาก Client |
|---|---|
| ใบสำหรับชื่ออื่น | Hostname Mismatch, certificate is not valid for 'garden.test' |
| ใบหมดอายุ | certificate has expired |
| ใบที่ออกโดยผู้ออกที่เราไม่เชื่อ | unable to get local issuer certificate |
| เชื่อผู้ออกผิดราย (ไฟล์ CA ผิด) | unable to get local issuer certificate |
| ใบถูกต้อง แต่เราขอชื่ออื่น | Hostname Mismatch, certificate is not valid for 'other.test' |

ทั้งห้ากรณีล้มเหลวหลัง TCP ต่อติดแล้ว (`connect` ของ TCP ใช้เวลาปกติ ราว 22 มิลลิวินาที) TCP ไม่สนใจเรื่องพวกนี้ มีแต่ TLS ที่สนใจ ข้อสังเกตที่ควรเก็บไว้คือกรณีที่ 4 และที่ 5 ในตาราง ข้อความ "unable to get local issuer certificate" มักทำให้คนคิดว่าใบผิด จริง ๆ แล้วใบอาจถูกต้อง ปัญหาคือฝั่งเราไม่มีผู้ออกใบรับรองนั้นอยู่ในรายการที่เชื่อ เช่นตอนใช้ใบที่ออกโดย CA ภายในองค์กรกับคอมพิวเตอร์ที่ยังไม่ได้ติดตั้ง CA นั้น ส่วนการตั้ง "ไม่ตรวจ Certificate" เพื่อให้ผ่านเป็นการทิ้งครึ่งหนึ่งของประโยชน์ TLS ไป เหลือแค่การเข้ารหัส ซึ่งไม่กันคนที่ปลอมเป็น Server (หนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 877 เรื่องการเชื่อมแบบไม่ระบุตัวตนที่เสี่ยงต่อ MITM)

`openssl s_client` ให้ผลตรงกัน เมื่อบอกผู้ออกที่ถูกต้อง มันตรวจสายใบรับรองที่ลึก 1 (ผู้ออก) และ 0 (Server) แล้วขึ้น `verify return:1` ทั้งคู่ (รัน)

## ที่ TLS ไม่ได้ทำให้

TLS ไม่ได้ซ่อนทุกอย่าง จากแบบฝึกเรารู้แล้วว่า ชื่อ Server ใน ClientHello ยังอ่านได้ ขนาดและจังหวะของ Record ยังเห็น และที่อยู่ IP ของปลายทางก็อยู่ใน IP Header ตลอด (รัน) คนแอบดูจึงรู้ว่าเราคุยกับใคร ไม่รู้ว่าคุยอะไร มีส่วนขยายใหม่ที่ซ่อนชื่อได้ แต่เราไม่ได้ลอง (ไม่ได้รัน) และ TLS ปกป้องการเดินทางระหว่างสองปลาย ถ้า Server เองถูกเจาะ หรือ Proxy ตรงกลางถอดรหัสให้ ข้อมูลก็ถูกอ่านที่จุดนั้น ซึ่งเป็นเหตุให้ในบทท้าย ๆ ของ Subject นี้เราจะกลับมาดูว่า Load Balancer ตรงกลางทำอะไรกับ TLS (ผู้เขียน)

อีกสองเรื่องที่บทนี้ข้าม แต่คนทำงานจริงเจอแน่ คือการเพิกถอนใบที่รั่ว (CRL กับ OCSP) และการที่ Client ก็มี Certificate ให้ Server ตรวจได้ (mTLS) ทั้งสองไม่ได้รัน

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| TLS ให้การเข้ารหัสและพิสูจน์ตัวตนบน TCP, การเชื่อมแบบไม่ระบุตัวตนเสี่ยง MITM | หนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 877 |
| ClientHello อ่านได้: SNI, เวอร์ชัน, Key Share x25519 32 ไบต์, 18 ชุด Cipher Suite, ช่อง Version ใน Record เป็น 0x0301 | รัน: `exercises/11_tls.py` และ RFC 8446 หัวข้อ 4.1.2, 4.2.8 |
| ข้อความ Handshake หลัง ServerHello ของ TLS 1.3 เข้ารหัสทั้งหมด และไม่เห็น Certificate กับ Request บนสาย | รัน และ RFC 8446 หัวข้อ 1.2, 2 |
| Record ขนาด 410 ไบต์เป็น Certificate และสอง Record 250 ไบต์เป็น Ticket | ผู้เขียน (อนุมานจากขนาด ไม่ได้ถอดรหัส) |
| TLS 1.2 ส่ง Certificate (390 ไบต์) เป็นข้อความธรรมดา | รัน และหนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 881 ถึง 888 |
| TLS 1.3 เสีย 3 รอบเวลา (64 ms), TLS 1.2 เสีย 4 (84 ms), HTTP ธรรมดา 2 (42 ms) | รัน และ RFC 8446 หัวข้อ 2 |
| Nagle ทำให้ TLS 1.3 เสียเพิ่มอีกหนึ่งรอบเวลา (84 ms) เมื่อไม่ตั้ง TCP_NODELAY | รัน (ทบทวน[บท 8](/networking/tcp-reliability/)) |
| Client ตรวจสายลายเซ็น ชื่อใน SAN และวันหมดอายุ พร้อมข้อความ Error ของแต่ละกรณี | รัน และหนังสือ: TCPIP หัวข้อ 18.9.1 หน้า 871 และ RFC 8446 หัวข้อ 4.4.2 |
| ชื่อ Server ใน ClientHello และ IP ปลายทางยังเห็นบนสาย | รัน |
| TLS ไม่ปกป้อง Server ที่ถูกเจาะ และ Proxy ที่ถอดรหัสเห็นข้อมูล | ผู้เขียน |
| Session Resumption, 0-RTT, mTLS, CRL และ OCSP, ALPN, ECH | ไม่ได้รัน |

</Step>
