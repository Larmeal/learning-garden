## Packet หาย แล้ว TCP รู้ได้อย่างไร

ใน[บท 7](/networking/tcp-connections/) เราเห็น TCP สร้าง Connection ที่ให้สัญญาว่าข้อมูลจะถึงครบ แต่สายข้างล่างไม่ได้ให้สัญญานั้น Router ทิ้ง Packet ได้เมื่อคิวเต็ม สายอาจมีสัญญาณรบกวน บทนี้เราดูว่า TCP ทำให้เครือข่ายที่ไม่น่าเชื่อถือกลายเป็นสายที่เชื่อถือได้อย่างไร และเห็นสามเรื่อง คือการส่งซ้ำ การรอรวมข้อมูล และการที่ผู้รับสั่งให้ผู้ส่งหยุด

เรื่องการหายต้องแยกสองกรณี เพราะ TCP รู้ว่ามีอะไรหายด้วยวิธีที่ต่างกัน กรณีแรกคือ Segment หายแล้วไม่มีอะไรตามมาเลย ผู้รับไม่มีอะไรให้ตอบ ผู้ส่งจึงมีแค่ Timer ให้พึ่ง กรณีที่สองคือ Segment หายกลางสาย แล้ว Segment ถัดไปยังมาถึงอยู่ ผู้รับจึงรู้ว่ามีช่องว่างและบอกผู้ส่งได้ทันที ในแบบฝึกเราทดลองทั้งสองอย่าง ด้วยสายที่หน่วงทิศละ 10 มิลลิวินาที ซึ่งวัดด้วย `ping` ได้ RTT 20 มิลลิวินาที (รัน: `exercises/08_tcp_reliability.py`)

## กรณีแรก: หายตัวเดียว ต้องรอ Timer

ให้ Client ส่งข้อมูล 100 ไบต์ ในขณะที่ Router ทิ้งทุก Segment ที่ใหญ่ขนาดนั้น แล้วถอดกฎออกหลังผ่านไป 0.95 วินาที จับ Packet ที่ Client (รัน)

```text
เวลา (ms)  seq  ไบต์
30         1    100    ส่งครั้งแรก
276        1    100    ส่งซ้ำ
524        1    100    ส่งซ้ำ
1032       1    100    ส่งซ้ำ (ถึงแล้ว)
ช่วงห่าง: 246, 248 และ 492 มิลลิวินาที
```

Segment เดิม (Seq เดิม) ถูกส่งสี่ครั้ง ช่วงห่างครั้งแรกประมาณ 246 มิลลิวินาที ซึ่งมากกว่า RTT ของสายที่ 20 มิลลิวินาทีเกือบสิบสองเท่า เพราะ TCP ไม่รู้ว่าสายเร็วแค่ไหนในเสี้ยววินาทีแรก มันวัด RTT จากการรับ ACK แล้วตั้ง Timer ที่เรียกว่า RTO (Retransmission Timeout) ให้มากกว่านั้นพอสมควร (หนังสือ: TCPIP หัวข้อ 14.3 หน้า 651) ตัวเลข 246 มิลลิวินาทีนี้เป็นของ Kernel ที่ใช้ทดสอบ ซึ่งน่าจะมีค่าต่ำสุดของ RTO กำกับอยู่ แต่แบบฝึกไม่ได้ตรวจเรื่องนี้ (ผู้เขียน) ช่วงห่างครั้งที่สามเพิ่มเป็นสองเท่า เมื่อ Timer หมดโดยไม่มีคำตอบ TCP จะเพิ่ม RTO เป็นสองเท่าทุกรอบ เรียกว่า Exponential Back-off เพื่อไม่ให้ซ้ำเติมเครือข่ายที่อาจกำลังติดขัด (หนังสือ: TCPIP หัวข้อ 14.3 หน้า 655 และหัวข้อ 14.4 หน้า 665) ผลคือข้อมูล 100 ไบต์ใช้เวลากว่าหนึ่งวินาที เทียบกับสายที่ปกติใช้ 10 มิลลิวินาที

กรณีที่สองแสดงว่าการรอแบบนี้ไม่จำเป็นเสมอไป เลือกเหตุการณ์ใน Lab ข้างล่างเพื่อเทียบกัน

## กรณีที่สอง: หายกลางสาย ซ่อมได้ใน 1 รอบเวลา

ถ้า Segment หายกลางสาย ผู้รับยังได้ Segment ถัดไปอยู่ ผู้รับตอบ ACK ทุกครั้งที่ได้ข้อมูล แต่ตัวเลข ACK คือไบต์ถัดไปที่ต้องการ ซึ่งยังค้างอยู่ที่ช่องที่หาย จึงเป็น ACK เดิมซ้ำ ๆ เรียกว่า Duplicate ACK ผู้ส่งที่ได้ Duplicate ACK ครบสามครั้ง ตัดสินว่า Segment นั้นหายแล้วส่งซ้ำทันทีโดยไม่รอ Timer เรียกว่า Fast Retransmit (หนังสือ: TCPIP หัวข้อ 14.5 หน้า 667 ถึง 669)

ในแบบฝึก Client ส่งข้อมูล 43,440 ไบต์ คือ 30 Segment ขนาด 1,448 ไบต์ และ Router ทิ้ง Segment ที่สามตัวเดียว (รัน)

```text
Segment ที่ 3 (seq สัมพัทธ์ 2896) ส่งที่ 20.3 ms และส่งซ้ำที่ 44.7 ms
Server ตอบ ACK ที่ค้างอยู่ที่ 2897 ทั้งหมด 19 ครั้ง
SACK Block แรกครอบ 4345 ถึง 5793 แล้วขยายเป็น 7241, 8689 ... ทีละหนึ่ง Segment
```

ซ่อมเสร็จที่ห่างจากการส่งครั้งแรกประมาณ 24 มิลลิวินาที ราวหนึ่งรอบเวลา ไม่ใช่หลายร้อยมิลลิวินาทีเหมือนกรณีที่แล้ว ตอนนี้เรื่อง SACK (Selective Acknowledgement) ที่เราเห็นเป็น Option ใน SYN ของ[บท 7](/networking/tcp-connections/#option-ที่สองฝั่งตกลงกันใน-syn) ทำงาน ACK ปกติบอกได้แค่ "ฉันได้ต่อเนื่องถึงไบต์นี้" แต่ SACK เพิ่มว่า "และได้ช่วงนี้ไปแล้วด้วย" ทำให้ผู้ส่งเห็นว่าช่องว่างมีแค่ตัวที่ 3 ตัวเดียว (ช่วง 2896 ถึง 4344) และส่งซ้ำเฉพาะตัวนั้น ไม่ต้องส่ง Segment ที่ 4 ถึง 10 ซ้ำ (หนังสือ: TCPIP หัวข้อ 14.6 หน้า 671 ถึง 676) พอตัวที่ 3 ไปถึง ACK ตัวเดียวกระโดดข้ามไปที่ไบต์ท้ายสุดที่ได้รับแล้ว (รัน)

ในรันที่ใช้เขียนบทนี้ Segment ที่ 3 ถูกส่งสองครั้งพอดี แต่ถ้ารันหลายครั้งจะเห็นว่า Kernel บางรอบส่งซ้ำเพิ่มอีกหนึ่งครั้ง และผู้รับตอบด้วย SACK Block พิเศษที่บอกว่าได้รับซ้ำ (D-SACK, หนังสือ: TCPIP หัวข้อ 14.7 หน้า 677) ซึ่งเป็นกลไกของ Linux ที่ไม่ได้อยู่ในบทนี้ ตัวเลขที่ Lab นี้แสดงคือสองครั้งตามรันที่บันทึกไว้

## Nagle: รอรวมข้อมูลเล็ก ๆ ให้เป็นก้อนใหญ่

เรื่องต่อไปไม่เกี่ยวกับการหาย แต่เกี่ยวกับการรอเหมือนกัน สมมติโปรแกรมเขียนข้อมูลสั้น ๆ ติดกันหลายครั้ง เช่นเขียนทีละ 10 ไบต์ ถ้าทุกการเขียนกลายเป็นหนึ่ง Segment ทุก 10 ไบต์จะต้องแบก Header 66 ไบต์ (Ethernet 14 บวก IP 20 บวก TCP 32 ที่เราวัดได้ใน[บท 1](/networking/big-picture/)) เป็นการเปลืองมาก Nagle Algorithm แก้ด้วยกฎข้อเดียว ถ้ายังมีข้อมูลที่ส่งไปแล้วและยังไม่ได้ ACK ข้อมูลเล็กที่เข้ามาใหม่ให้เก็บรอรวมกันก่อน (หนังสือ: TCPIP หัวข้อ 15.4 หน้า 696)

เราลองเขียน 10 ไบต์ห้าครั้ง ห่างกัน 1 มิลลิวินาที สองแบบ ค่าเริ่มต้น กับเปิด `TCP_NODELAY` ซึ่งปิด Nagle (รัน)

| โหมด | Segment ที่ออกสาย |
|---|---|
| Nagle (ค่าเริ่มต้น) | 10 ไบต์ แล้ว 40 ไบต์ (ห่างกัน 20 มิลลิวินาที) |
| `TCP_NODELAY` | 10 ไบต์ห้าอัน ห่างกันราว 1 มิลลิวินาที |

กดสลับสองโหมดใน Lab แล้วดูตัวนับ ข้อมูลเท่ากัน คือ 50 ไบต์ แต่ Nagle ใช้สอง Segment (Header รวม 132 ไบต์) และ NODELAY ใช้ห้า Segment (Header รวม 330 ไบต์ ข้อมูลจริงเหลือราว 13% ของที่ส่ง) (คำนวณจาก Header 66 ไบต์ต่อ Segment)

ราคาของ Nagle คือการรอได้นานถึงหนึ่งรอบเวลา ซึ่งไม่เป็นไรสำหรับการส่งไฟล์ แต่แย่สำหรับโปรแกรมที่ต้องตอบเร็ว เช่นเกมหรือการพิมพ์ทีละตัวอักษรผ่านเครือข่าย โปรแกรมแบบนั้นจึงเปิด `TCP_NODELAY` (หนังสือ: TCPIP หัวข้อ 15.4 หน้า 700) แบบฝึกตรวจเรื่องการรวมก้อน แต่ไม่ได้ตรวจผลของ Delayed ACK ที่ฝั่งผู้รับ ซึ่งในตำราเป็นอีกเรื่องที่ทำงานคู่กัน (หนังสือ: TCPIP หัวข้อ 15.3 หน้า 695) ส่วนนี้ไม่ได้รัน

## Window: ผู้รับสั่งให้ผู้ส่งชะลอ หรือหยุด

เรื่องสุดท้ายคือผู้รับที่รับไม่ไหว ข้อมูลที่ TCP รับมาถูกเก็บใน Buffer จนกว่าโปรแกรมจะเรียก `recv` มาอ่าน ถ้าโปรแกรมอ่านช้า Buffer เต็ม ผู้รับต้องบอกผู้ส่งให้หยุด วิธีบอกคือช่อง Window ในทุก ACK ซึ่งแปลว่า "ฉันยังมีที่เหลืออีกเท่านี้ไบต์" ผู้ส่งต้องส่งไม่เกินค่านั้น กลไกนี้เรียกว่า Flow Control (หนังสือ: TCPIP หัวข้อ 15.5 หน้า 700 ถึง 703)

ในแบบฝึก เราให้ผู้รับตั้ง Buffer เล็ก (8 KB) แล้วให้โปรแกรมนอน 2 วินาทีก่อนอ่านครั้งแรก ส่วนผู้ส่งพยายามส่ง 200,000 ไบต์ (รัน)

```text
Window ที่ผู้รับประกาศ: 7,240 -> 5,792 -> 2,896 -> 0 ที่ ~140 ms
Probe ของผู้ส่ง: 396, 892 และ 1856 ms (ห่างกัน 496 และ 964)
Window เปิดอีกครั้งที่ ~2033 ms แล้วผู้ส่งส่งต่อภายในไม่กี่มิลลิวินาที
รวม 200,000 ไบต์ ใช้เวลา 2.3 วินาที ซึ่ง 2 วินาทีคือการรอผู้รับ
```

กดเล่นเพื่อดู Window ที่ลดลงจนเป็น 0 ผู้ส่งที่ต้องหยุด และกลับมาส่งต่อทันทีที่ผู้รับอ่าน

เรื่องที่ควรสังเกตคือ Probe เมื่อ Window เป็น 0 ผู้ส่งส่งอะไรไม่ได้ แต่ถ้ารอเฉย ๆ แล้ว ACK ที่ประกาศว่า Window เปิดแล้วหายไป ทั้งสองฝั่งจะรอกันตลอดไป ผู้ส่งจึงเตรียม Timer แบบเดียวกับตอนส่งซ้ำ (Persist Timer) ส่ง Segment เปล่า ๆ ไปถามเป็นระยะ ในแบบฝึกห่างกัน 496 แล้ว 964 มิลลิวินาที ซึ่งเป็นสองเท่าเช่นเดียวกับ Back-off ของการส่งซ้ำ (หนังสือ: TCPIP หัวข้อ 15.5 หน้า 708 ถึง 711) ใน Connection นี้ Window เริ่มที่ 7,240 ไบต์ และ SYN,ACK ไม่มี Window Scale (Wscale=0) ตัวเลขใน ACK จึงอ่านเป็นไบต์ได้ตรง ๆ โดยไม่ต้องคูณเหมือนใน[บท 7](/networking/tcp-connections/#option-ที่สองฝั่งตกลงกันใน-syn) (รัน)

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| Segment ที่หายตัวเดียวถูกส่งซ้ำเมื่อ Timer หมด ห่างกัน 246, 248 และ 492 มิลลิวินาที | รัน: `exercises/08_tcp_reliability.py` และหนังสือ: TCPIP หัวข้อ 14.3 หน้า 651, 655 และหัวข้อ 14.4 หน้า 665 |
| Duplicate ACK ครบสามครั้งทำให้ส่งซ้ำทันที (Fast Retransmit) ซ่อมใน 1 RTT | รัน และหนังสือ: TCPIP หัวข้อ 14.5 หน้า 667 ถึง 669 |
| SACK บอกช่วงที่ได้รับหลังช่องว่าง ทำให้ส่งซ้ำเฉพาะตัวที่หาย | รัน และหนังสือ: TCPIP หัวข้อ 14.6 หน้า 671 ถึง 676 |
| Kernel Linux ส่งซ้ำเพิ่มและตอบ D-SACK ในบางรอบ | ผู้เขียน (เห็นในบางรัน ตรวจเฉพาะส่วนที่บันทึกในบท) |
| Nagle ส่ง 10 กับ 40 ไบต์, NODELAY ส่ง 10 ไบต์ห้าอัน | รัน และหนังสือ: TCPIP หัวข้อ 15.4 หน้า 696 และ 700 |
| Header 66 ไบต์ต่อ Segment ทำให้ NODELAY เปลือง Header 330 ไบต์ต่อข้อมูล 50 ไบต์ | คำนวณจากการรัน ([บท 1](/networking/big-picture/)) |
| Window ลดเหลือ 0 ผู้ส่งหยุด ส่ง Probe ห่าง 496 และ 964 มิลลิวินาที แล้วส่งต่อหลัง Window เปิด | รัน และหนังสือ: TCPIP หัวข้อ 15.5 หน้า 700 ถึง 711 |
| Delayed ACK, Silly Window Syndrome, RACK, TLP | ไม่ได้รัน |
