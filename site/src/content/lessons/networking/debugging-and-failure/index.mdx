## "ช้า" มีอย่างน้อยสองสาเหตุ

เวลาโปรแกรมของเราเรียก API ไปแล้วช้า คำตอบแรกที่หลายคนนึกถึงคือ Network ช้า แต่สิ่งที่ช้าได้มีอย่างน้อยสองอย่าง คือเส้นทางของ Packet กับโปรแกรมที่อยู่ปลายทาง เราจะแยกสองอย่างนี้ออกจากกันได้ด้วยการจับเวลาคำขอเป็นสามช่วง ได้แก่ **Connect** คือเวลาที่ `connect()` ใช้จนจับมือเสร็จ **Wait** คือเวลาตั้งแต่ส่งคำขอจนได้ Byte แรกของคำตอบ และ **Transfer** คือเวลาที่เหลือจนรับข้อมูลครบ

ในแบบฝึก (รัน: `exercises/14_debugging.py`) ทางระหว่าง Client กับ Server หน่วงทิศละ 10 มิลลิวินาที ผลของ `ping` จึงมีค่าต่ำสุดเท่ากับ 20 มิลลิวินาทีพอดี Server ทำงาน 50 มิลลิวินาทีต่อคำขอ และตอบข้อมูล 50 KB เราจับเวลาคำขอ 7 ครั้งแล้วเอาค่ามัธยฐาน

| กรณี | Connect | Wait | Transfer | รวม (มิลลิวินาที) |
|---|---|---|---|---|
| ปกติ | 20 | 71 | 40 | 131 |
| Network ช้า (หน่วงทิศละ 100) | 200 | 251 | 401 | 851 |
| โปรแกรมช้า (Server ทำงาน 300) | 20 | 321 | 40 | 381 |

ตัวเลขเรียงกันสวยกว่าที่คิด ช่วง Connect เท่ากับ RTT หนึ่งรอบพอดี เพราะ SYN ไปและ SYN-ACK กลับ ช่วง Wait คือ RTT อีกหนึ่งรอบบวกเวลาทำงานของ Server (20 + 50 = 70) ส่วนช่วง Transfer ของข้อมูล 50 KB ใช้ราว 2 RTT เพราะ Slow Start จากบทเรื่อง[การควบคุมความคับคั่ง](/networking/tcp-congestion/) ส่งข้อมูลเป็นหลายชุด ชุดละมากกว่าชุดก่อนหน้า (รัน)

ลองเทียบสองแถวล่าง ถ้า Network ช้า ทุกช่วงยาวขึ้นพร้อมกัน โดยเฉพาะ Connect ที่ไม่เกี่ยวกับโปรแกรมเลย แต่ถ้าโปรแกรมช้า Connect ยังเท่าเดิมที่ 20 และมีแต่ Wait ที่ยาวขึ้น (รัน) นี่คือเหตุผลที่เครื่องมืออย่าง `curl -w` ซึ่งแสดงเวลาแยกเป็นช่วง ๆ มีประโยชน์ เพราะมันเปลี่ยนคำว่าช้าให้เป็นตัวเลขที่ชี้ไปทางใดทางหนึ่งได้ (เครื่องมือ `curl -w` ไม่ได้รันในแบบฝึก เราเขียนตัวจับเวลาเองด้วย Python แต่หลักการเดียวกัน ไม่ได้รัน) กดเล่น Lab เพื่อดูแท่งทั้งสามโตขึ้นบนแกนเวลาเดียวกัน

## ข้อความ Error บอกว่าใครตอบ

ทีนี้ลองให้การต่อ Connection ล้มเหลว เราสร้างความผิดปกติที่พบบ่อยทีละแบบ แล้วให้โปรแกรมเล็ก ๆ ต่อไปที่ Port 9000 ของ Server ด้วย Timeout 3 วินาที (รัน)

| ความผิดปกติ | โปรแกรมเห็น | ใช้เวลา (วินาที) |
|---|---|---|
| บริการปกติ | เชื่อมต่อได้ | 0.0 |
| ไม่มีโปรแกรม Listen ที่ Port นั้น | ถูกปฏิเสธ (Refused) | 0.0 |
| Firewall REJECT แบบ ICMP | ถูกปฏิเสธ (Refused) | 0.0 |
| Firewall REJECT แบบ RST | ถูกปฏิเสธ (Refused) | 0.0 |
| Firewall DROP | หมดเวลา (Timeout) | 3.5 |
| Router ไม่มี Route ไปหา Server | ไปไม่ถึง (Unreachable) | 0.0 |
| สายขาด (Packet หายทั้งหมด) | หมดเวลา (Timeout) | 3.0 |

ตารางนี้ให้บทเรียนสองข้อ ข้อแรกคือ Error ที่มาทันที ไม่ว่าจะเป็น Refused หรือ Unreachable แปลว่ามีใครบางคนตอบกลับมา ซึ่งหมายความว่า Packet ไปถึงฝั่งนั้นและกลับได้ เส้นทางส่วนใหญ่จึงปกติ ถ้าเป็น Refused แปลว่า Kernel ของปลายทาง (หรือ Firewall ของมัน) ตอบ RST เหมือนกรณีที่เราเจอในบท[การเชื่อมต่อของ TCP](/networking/tcp-connections/) ส่วน Unreachable เกิดจาก Router ระหว่างทางตอบ ICMP กลับมาว่าไปต่อไม่ได้ ซึ่งหนังสือจัดไว้ใน Destination Unreachable ที่ใช้รหัสต่าง ๆ เช่น Host Unreachable และ Port Unreachable (หนังสือ: TCP/IP Illustrated ฉบับที่ 2 หัวข้อ 8.3.2 หน้า 364)

ข้อสองคือบางคู่แยกจากข้อความ Error อย่างเดียวไม่ได้ ในแบบฝึก Firewall ที่ REJECT กับกรณีที่ไม่มีโปรแกรม Listen ให้ผลเหมือนกันทุกประการจากฝั่ง Client (รัน) ถ้าเราอยากรู้ว่าเป็นอย่างไหนต้องไปดูที่ Server ด้วย `ss -ltn` ว่ามีโปรแกรมฟังอยู่ไหม และดูกฎ Firewall ส่วนสองแถว Timeout ก็เป็นแบบเดียวกัน เราจะดูมันต่อในหัวข้อถัดไป

</Step>

## Timeout คือความเงียบ

ความผิดปกติสองแบบที่ให้ Timeout ได้แก่ Firewall DROP และสายขาด ดูจากโปรแกรมไม่ออกว่าเป็นอย่างไหนเลย แต่ถ้าเรารู้ว่า Connection ที่กำลังรออยู่เป็นอย่างไร จะเริ่มเห็นเค้าโครง ระหว่างที่โปรแกรมรอ เราสั่ง `ss -tn state syn-sent` ที่ฝั่ง Client แล้วเห็นบรรทัดของ Connection ไปที่ `10.0.2.2:9000` ค้างอยู่ในสถานะ SYN-SENT (รัน) แปลว่า Client ส่ง SYN ไปแล้วและยังไม่ได้อะไรกลับมา

และเมื่อจับ Packet ที่สายของ Server ระหว่าง 3.5 วินาทีนั้น เราเห็น SYN มาถึง 4 ครั้งที่เวลา 0.0, 1.0, 2.0 และ 3.1 วินาที (รัน) Client ส่ง SYN ซ้ำห่างกันราว 1 วินาที ตามเรื่อง SYN ที่ส่งซ้ำในบท[การเชื่อมต่อของ TCP](/networking/tcp-connections/) เห็นได้ว่าใน Firewall DROP นั้น SYN ไปถึง Server จริงแต่ถูกทิ้ง ส่วนสายขาด SYN ไม่ไปถึงเลย ที่ฝั่ง Client ทั้งสองเหมือนกันทุกประการ สิ่งเดียวที่แยกสองกรณีนี้ได้คือการจับ Packet ที่ฝั่ง Server (`tcpdump`) ถ้าเห็น SYN แต่ไม่มีคำตอบ ให้ไปดูกฎ Firewall ถ้าไม่เห็น SYN เลย ให้ไล่ถอยกลับมาทีละฮอปว่า Packet หายตรงไหน

กดเล่น Lab ที่ทำให้เลือกความผิดปกติได้ทั้งเจ็ดแบบ ดูว่า Packet แรกไปหยุดที่ใด และแผงด้านล่างบอกว่าโปรแกรมเห็นอะไรและควรดูอะไรต่อ

## สายหายบางส่วนไม่ทำให้เกิด Error แต่ทำให้บางครั้งช้า

ความผิดปกติแบบสุดท้ายอันตรายกว่าที่ดู เราให้ Link ทิ้ง Packet ขาออกของ Client 40% แล้วต่อ Connection 20 ครั้ง ผลคือทั้ง 20 ครั้งเชื่อมต่อสำเร็จ ไม่มีสักครั้งที่ได้ Error (รัน) แต่เวลาที่ใช้ไม่เท่ากัน ส่วนใหญ่ต่อได้ทันที 0.0 วินาที แต่บางครั้งใช้ 1 หรือ 2 วินาที และในการรันก่อนหน้าเคยเจอถึง 4 วินาที ทุกครั้งเป็นจำนวนเต็มวินาทีพอดี เพราะทุก SYN ที่หายหนึ่งตัวทำให้ต้องรอส่งซ้ำอีกราว 1 วินาที (รัน) ตัวเลขนี้แกว่งทุกครั้งที่รัน เพราะ Packet ถูกทิ้งแบบสุ่ม

สำหรับคนที่ดู Dashboard ผลคือบริการทำงานได้ แต่ Latency ที่ Percentile สูง ๆ มีค่าเป็นวินาทีเต็มอย่างผิดปกติ ถ้าคุณเห็นเวลาตอบกลุ่มหนึ่งที่เกาะอยู่ที่ 1, 2 หรือ 3 วินาทีพอดี นั่นเป็นลายนิ้วมือของ SYN ที่ถูกส่งซ้ำ ซึ่งเป็นข้อสังเกตของผู้เขียนจากผลที่รันได้ (ผู้เขียน) และวิธีดูเรื่องนี้คือ `ping` ดู Packet Loss หรือจับ Packet แล้วหา SYN ที่ซ้ำ

</Step>

## Connection ที่นิ่งเงียบ อาจตายไปแล้วโดยไม่มีใครรู้

อีกเรื่องหนึ่งที่เราไม่ได้ลองรัน แต่ควรรู้ หนังสือเล่าว่าคนที่เพิ่งเรียน TCP/IP มักแปลกใจว่า ถ้าไม่มีใครส่งอะไรเลย จะไม่มี Packet วิ่งผ่าน Connection ที่ว่างเลย ไม่มีการสำรวจ (Polling) ใด ๆ ดังนั้นในทฤษฎี Connection จะอยู่ไปเป็นชั่วโมงหรือเป็นเดือนก็ได้ ตราบเท่าที่ Host ทั้งสองฝั่งไม่รีบูต แต่หนังสือก็เตือนว่าข้อสันนิษฐานนี้ต้องมีเงื่อนไข คือ Router กลางทางต้องไม่เก็บสถานะของ Connection ไว้ เช่น NAT ที่อาจลบทิ้งเมื่อไม่มีการใช้งาน หรือสูญเสียไปเมื่อระบบล่ม ซึ่งหนังสือบอกว่าเป็นข้อสันนิษฐานที่ใหญ่มากในอินเทอร์เน็ตทุกวันนี้ (หนังสือ: TCP/IP Illustrated ฉบับที่ 2 หัวข้อ 17.1 หน้า 793)

เรื่อง NAT ที่ลบการแปลเมื่อไม่มีการใช้งาน เรารู้จักตารางของมันมาจากบท[NAT](/networking/nat-dhcp/) แล้ว และ Container ที่เห็นในบท[Proxy และ Container](/networking/proxies-and-containers/) ก็ใช้ตาราง Conntrack แบบเดียวกัน คำตอบของหนังสือคือกลไก Keepalive ที่ให้ TCP ส่งโพรบเป็นช่วง ๆ เพื่อรู้ว่าปลายทางยังอยู่ไหม เมื่อโพรบไม่ได้คำตอบ โปรแกรมจะได้ Error อย่าง "Connection timed out" หรือ "Connection reset by peer" ตอนอ่าน (หนังสือ: TCP/IP Illustrated ฉบับที่ 2 หัวข้อ 17.1 หน้า 796) ในแบบฝึกเราไม่ได้ลองรัน Keepalive และไม่ได้ลองรอให้ NAT ลบการแปล ที่นี่จึงเป็นเรื่องจากหนังสือ (ไม่ได้รัน) ข้อสรุปเชิงปฏิบัติของผู้เขียนคือ ถ้าโปรแกรมของเราถือ Connection ค้างนาน ๆ (เช่น Connection Pool ไปหา Database) ควรมี Timeout และ Keepalive ในระดับโปรแกรมเอง ไม่พึ่งว่า Network กลางทางจะจำไว้ให้ (ผู้เขียน)

</Step>

## ในงานข้อมูลที่เราทำ

เรื่องนี้ไม่ได้เป็นของ Network อย่างเดียว ความรู้ข้างบนเชื่อมกับสิ่งที่เราเห็นในบทอื่นของ Garden หลายอย่าง ทั้งหมดในหัวข้อนี้เป็นการอ่านเทียบกับบทอื่น ไม่ได้รัน Network จริง (ไม่ได้รัน)

ใน Spark เมื่อ Executor หายไประหว่าง Shuffle Task ฝั่ง Reduce จะอ่านไฟล์ Shuffle ของ Executor นั้นไม่ได้ และได้ `FetchFailedException` ตามที่เล่าไว้ใน[ไฟล์ Shuffle บน Disk](/spark/internals/#ไฟล์-shuffle-บน-disk) ถ้าเราดู Error นี้ด้วยสายตาของบทนี้ จะเห็นว่าการอ่านไฟล์ Shuffle คือ Connection ระหว่าง Executor สองตัว ซึ่งเจอทั้ง Refused (โปรแกรมปลายทางตายแล้ว) และ Timeout (คอมพิวเตอร์ปลายทางเงียบ) ได้เหมือนกัน (ผู้เขียน) ส่วน Iceberg ในบท[การอ่านข้อมูล](/iceberg/reading/#ก่อนอ่านต้องวางแผนว่าจะเปิดไฟล์ไหน) การอ่านหนึ่ง Query ต้องเปิดไฟล์หลายไฟล์ ถ้าไฟล์เหล่านั้นอยู่บน Object Storage ที่ห่างออกไป ทุกคำขอต้องจ่าย RTT อย่างน้อย 2 รอบ (Connect กับ Wait) ตามตารางข้างบน จึงเป็นเหตุผลหนึ่งที่การลดจำนวนไฟล์ที่ต้องเปิด มีผลมากกว่าที่คิด (ผู้เขียน ส่วน Iceberg เองไม่ได้ลองบน Object Storage ในบทนั้น)

ส่วน Git ในบท[Remote](/git/remotes/#push-ที่ถูกปฏิเสธ) ทุก Remote ของเราเป็นโฟลเดอร์บนคอมพิวเตอร์เครื่องเดียวกัน ไม่เคยผ่าน Network จริง ดังนั้นข้อความ Push ที่ถูกปฏิเสธในบทนั้นเป็นเรื่องของ Git เอง (Fetch First) ไม่ใช่ Network ถ้าเมื่อไรเจอ `git push` ที่ค้างหรือ Timeout เมื่อใช้ Remote จริง ให้ดูตารางข้างบน และนึกว่า HTTPS ของมันคือ HTTP บน TLS บน TCP ตามที่เรียนมา (ผู้เขียน)

</Step>

## ลำดับที่ลองดู

เมื่อโปรแกรมต่อไม่ได้หรือช้า เราเอาสิ่งที่รันมาเรียงเป็นลำดับดูได้ดังนี้ ลำดับนี้เป็นความเห็นของผู้เขียนที่ได้จากผลข้างต้นและบทก่อนหน้า ไม่ได้มาจากหนังสือ (ผู้เขียน)

1. ดูว่าชื่อกลายเป็นที่อยู่ได้ไหม ถ้า DNS ผิดหรือช้า ทุกอย่างหลังจากนี้ไม่มีความหมาย (ดู[บท DNS](/networking/udp-dns/))
2. ดูว่า Packet ไปถึงปลายทางได้ไหมด้วย `ping` และดู Route ถ้าได้ Error Unreachable ทันที ให้ไปดูตาราง Route ของ Router ที่ตอบ (ดู[บท Routing](/networking/ip-routing/))
3. ลองต่อ Port จริงแล้วดูข้อความ Error ถ้า Refused ให้ไปที่ปลายทาง ว่าโปรแกรมรันอยู่ไหม ถ้า Timeout ให้จับ Packet ที่ปลายทาง
4. ถ้าต่อได้แต่ช้า แยกเวลาเป็น Connect, Wait และ Transfer ว่าช่วงไหนยาว
5. ถ้ามีข้อความเกี่ยวกับใบรับรอง ให้ดู[บท TLS](/networking/tls/)

<Callout type="note" title="เครื่องมือที่ไม่ได้ลองในบทนี้">

ขั้นตอนข้างบนอ้างถึง `dig`, `traceroute` และ `curl -w` เป็นเครื่องมือที่ใช้กันทั่วไป แต่แบบฝึกของเราเขียนตัวจับเวลาและตัว Resolver เองเพื่อให้ตรวจเลขได้ และใช้ `ping`, `ss` กับ `tcpdump` จริง ผลของ `dig`, `traceroute` และ `curl -w` ในเครือข่ายจริงไม่ได้รัน (ไม่ได้รัน)

</Callout>

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| ค่าต่ำสุดของ Ping คือ 20 มิลลิวินาที เมื่อสายหน่วงทิศละ 10 | รัน: `exercises/14_debugging.py` |
| Connect = 1 RTT, Wait = 1 RTT + เวลาทำงานของ Server, Transfer ของ 50 KB ≈ 2 RTT (ปกติ 20 / 71 / 40) | รัน |
| Network ช้าทำให้ทุกช่วงยาวขึ้น (200 / 251 / 401) ส่วนโปรแกรมช้าทำให้เฉพาะ Wait ยาวขึ้น (20 / 321 / 40) | รัน |
| ไม่มีใคร Listen และ Firewall REJECT (ICMP หรือ RST) ให้ Refused ทันที | รัน |
| Firewall DROP ให้ Timeout 3.5 วินาที, SYN มาถึง Server 4 ตัวที่ 0.0, 1.0, 2.0, 3.1 วินาที, Client อยู่ใน SYN-SENT | รัน |
| Router ไม่มี Route ให้ Unreachable ทันที | รัน |
| สายขาดให้ Timeout 3.0 วินาที เหมือน DROP จากฝั่ง Client | รัน |
| สายหายบางส่วน 40%: เชื่อมต่อได้ทุกครั้ง แต่บางครั้งช้าเป็นวินาทีเต็ม | รัน (ตัวเลขแกว่งทุกรัน) |

| Keepalive, NAT หมดเวลา, DNS ล่ม, TLS ล้มเหลว, `dig`, `traceroute`, `curl -w` | ไม่ได้รัน |
