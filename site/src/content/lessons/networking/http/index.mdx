## หกคำขอ ควรใช้กี่ Connection

หน้าเว็บหนึ่งหน้ามักต้องดึงของหลายอย่าง เช่น HTML, สไตล์ และภาพ ข้อมูลที่ Client ต้องการจึงมาจากหลายคำขอ และเราอยากให้มันมาพร้อมกันให้มากที่สุด ใน[บท 1](/networking/big-picture/) เห็นแล้วว่า HTTP/1.1 เป็นข้อความธรรมดา ปัญหาของมันคือ Connection หนึ่งสายตอบได้ทีละคำขอ คำขอถัดไปต้องรอคำตอบของตัวก่อนหน้า ไม่เช่นนั้นคำตอบจะปนกัน ดังนั้นถ้า Client อยากได้หลายอย่างพร้อมกัน ต้องเปิดหลาย Connection ตามที่ RFC 9113 หัวข้อ 1 ระบุว่า "HTTP/1.0 และ HTTP/1.1 Client ใช้หลาย Connection ไปที่ Server เพื่อทำคำขอพร้อมกัน"

ในแบบฝึก (รัน: `exercises/12_http.py`) Server ต้องใช้ 100 มิลลิวินาทีกับแต่ละคำขอ สายมี RTT 20 มิลลิวินาที และเราขอ 6 อย่างด้วยสี่วิธี

| วิธี | Connection | รวมเวลา |
|---|---|---|
| HTTP/1.1 เปิด Connection ใหม่ทุกคำขอ ทีละอัน | 6 (ต่อเนื่อง) | ราว 857 มิลลิวินาที |
| HTTP/1.1 ใช้ Connection เดียวซ้ำ ทีละคำขอ (Keep-alive) | 1 | ราว 752 มิลลิวินาที |
| HTTP/1.1 หก Connection พร้อมกัน | 6 | ราว 149 มิลลิวินาที |
| HTTP/2 Connection เดียว หกคำขอพร้อมกัน | 1 | ราว 135 มิลลิวินาที |

(ตัวเลขแกว่งได้เล็กน้อยทุกครั้งที่รัน) แถวแรกเสียราว 140 มิลลิวินาทีต่อคำขอ คือ Handshake ของ TCP 20, ไปกลับ 20 และ Server ทำงาน 100 แถวที่สองประหยัด Handshake จึงเหลือคำขอละ 120 มิลลิวินาที และเวลาที่แต่ละคำขอเสร็จห่างกัน 120 มิลลิวินาทีพอดี เพราะแต่ละคำขอรออันก่อนหน้า แถวที่สามเร็วกว่ามากเพราะทั้งหกวิ่งพร้อมกัน แต่ต้องเปิดหก Connection และ Handshake ทุกอัน แถวสุดท้ายคือ HTTP/2 ที่ได้ผลคล้ายแถวที่สาม โดยใช้ Connection เดียว (รัน) กดเล่น Lab เพื่อดูแท่งของทั้งสี่วิธีบนแกนเวลาเดียวกัน

## HTTP/2: ตัดเป็นเฟรมที่มีป้าย Stream

HTTP/2 แก้ปัญหานี้ด้วยการเปลี่ยนวิธีเขียนลงสาย แทนที่จะเป็นข้อความต่อกัน มันตัดการสนทนาเป็นเฟรม ทุกเฟรมขึ้นต้นด้วย Header ยาว 9 ไบต์ที่มีความยาว ชนิด ธง และเลข Stream (RFC 9113 หัวข้อ 4.1) คำขอหนึ่งกับคำตอบของมันรวมกันเป็นหนึ่ง **Stream** และหลาย Stream อยู่บน Connection เดียวพร้อมกันได้ เพราะเฟรมของแต่ละอันบอกเองว่าเป็นของใคร (RFC 9113 หัวข้อ 5)

เราจับ Packet ของ Connection HTTP/2 ในแบบฝึก แล้วตัดเป็นเฟรมเองจากไบต์ (รัน) ในแบบฝึกไม่ผ่าน TLS ซึ่งทำให้ไม่ต้องถอดรหัส ฝั่ง Client ส่งเฟรมเหล่านี้

```text
SETTINGS        stream 0   42
SETTINGS        stream 0   6
WINDOW_UPDATE   stream 0   4
HEADERS         stream 1   17   END_STREAM
HEADERS         stream 3   8    END_STREAM
HEADERS         stream 5   8    END_STREAM
HEADERS         stream 7   8    END_STREAM
HEADERS         stream 9   8    END_STREAM
HEADERS         stream 11  8    END_STREAM
```

ก่อนเฟรมแรกมี Preface ยาว 24 ไบต์ `PRI * HTTP/2.0` (RFC 9113 หัวข้อ 3.4) ที่ชนิดเฟรมเหล่านี้ใช้ มี SETTINGS สำหรับตั้งค่า WINDOW_UPDATE สำหรับเปิดที่ว่างรับข้อมูล (Flow Control แบบเดียวกับ Window ของ TCP แต่ต่อ Stream) และ HEADERS สำหรับคำขอ (RFC 9113 หัวข้อ 5.2 และ 6) คำขอทั้งหกวิ่งเป็น Stream 1, 3, 5, 7, 9 และ 11 โดย Client ใช้เลขคี่ และทุกอันจบด้วย END_STREAM เพราะ GET ไม่มีเนื้อหา

น่าสนใจที่ขนาด คำขอแรกยาว 17 ไบต์ แต่อีกห้าอันยาวเพียง 8 ไบต์ เพราะ HTTP/2 บีบอัดหัวข้อด้วย HPACK ซึ่งจำหัวข้อที่เคยส่งแล้วไว้ใน Table ที่สองฝั่งถือเหมือนกัน และส่งเป็นดัชนีสั้น ๆ แทน (รัน, RFC 9113 หัวข้อ 4.3) ฝั่ง Server ก็เห็นแบบเดียวกัน คำตอบแรก HEADERS ยาว 6 ไบต์ แล้วที่เหลืออันละ 2 ไบต์

```text
HEADERS  stream 1   6
DATA     stream 1   1000  END_STREAM
HEADERS  stream 3   2
DATA     stream 3   1000  END_STREAM
...       (จนถึง stream 11)
```

กดเล่น Lab เพื่อดูเฟรมทั้งหมดในสายไบต์เดียวของ TCP แยกสีตาม Stream

ทั้งหกคำตอบมาถึงห่างกันไม่เกิน 5 มิลลิวินาที ตามที่แบบฝึกตรวจ (รัน) และสองสิ่งที่ควรสังเกตเกี่ยวกับ HTTP/2 ข้อแรกคือมันยังวิ่งบน TCP Connection เดียว RFC เขียนไว้ตรง ๆ ว่า "การบล็อกที่หัวแถวของ TCP ไม่ได้ถูกแก้โดยโปรโตคอลนี้" (RFC 9113 หัวข้อ 1) ถ้า Packet หายหนึ่งตัว TCP จะไม่ส่งข้อมูลที่ตามหลังช่องว่างให้โปรแกรม จนกว่าจะส่งซ้ำมาถึง ซึ่งกระทบทุก Stream ที่อยู่บน Connection นั้น เราลองวัดเรื่องนี้ด้วย แต่ผลปนกับการควบคุมความคับคั่งของไลบรารีที่ใช้เทียบ จึงไม่นำมาอ้างในบทนี้ (ไม่ได้รัน) ข้อที่สองคือทุกอย่างที่ทำให้ HTTP/2 เร็ว มาจากการอยู่บน Connection เดียว ซึ่งเป็นเหตุให้ TCP Handshake ราคา 1 รอบเวลาและ TLS Handshake ต้องจ่ายเพียงครั้งเดียวสำหรับทุกคำขอ

## QUIC: ย้ายมาอยู่บน UDP และเอา TLS ไปรวม

QUIC แก้ปัญหาที่ HTTP/2 ทิ้งไว้ด้วยการไม่ใช้ TCP เลย มันสร้าง Connection ของตัวเองบน UDP ซึ่งเรารู้จักจาก[บท 6](/networking/udp-dns/) ว่าเป็นแค่ Datagram เดี่ยว ๆ ที่ไม่มีการรับประกัน QUIC จึงสร้างการรับประกัน การเรียงลำดับ และ Congestion Control ขึ้นมาเองข้างบน UDP และรวมการ Handshake ของ TLS 1.3 เข้าไปในตัวเดียวกับ Handshake ของ Connection (RFC 9000 หัวข้อ 1 และ 7) จุดสำคัญคือ Stream ของ QUIC เป็นอิสระต่อกัน RFC 9000 หัวข้อ 2 บอกว่า "QUIC ไม่มีวิธีใดที่จะรับประกันลำดับของไบต์ระหว่างต่าง Stream" ซึ่งต่างจาก HTTP/2 บน TCP ที่ Stream ทั้งหมดเป็นสายไบต์เดียวกัน นี่คือเหตุผลที่ HTTP/3 (RFC 9114) ซึ่งเป็น HTTP บน QUIC ตั้งใจให้ Packet ที่หายกระทบเฉพาะ Stream ที่เกี่ยวข้อง ส่วนนี้เป็นทฤษฎีจาก RFC ที่เราไม่ได้วัด

สิ่งที่เราวัดได้คือแพ็กเก็ตจริงของ QUIC (รัน) ที่จับที่ฝั่ง Client ตอนเปิด Connection ไปหา Server ที่ RTT 100 มิลลิวินาที

```text
เวลา    จาก     UDP payload  Byte แรก  เวอร์ชัน
0 ms    client  1200         0xca      0x00000001
88 ms   server  1200         0xc4      0x00000001
148 ms  client  1200         0xc5      0x00000001
149 ms  client  40           0x55      short header
199 ms  server  224          0x5f      short header
```

มีสามเรื่องที่ควรสังเกต แพ็กเก็ตแรกของ Client ยาว 1200 ไบต์พอดี เป็นแพ็กเก็ต Initial ของ QUIC เวอร์ชัน 1 ซึ่ง Client ต้องเติมให้ได้ขนาดนี้ตามหัวข้อ 14.1 ของ RFC 9000 (เหตุผลที่ผู้เขียนเข้าใจคือกัน Server ถูกใช้ขยายการโจมตี แต่ไม่ได้อ่านเนื้อหาส่วนนั้นของ RFC) สิ่งที่สองคือ Connection เริ่มด้วยแพ็กเก็ต Long Header (บิตสูงสุดของ Byte แรกเป็น 1) แล้วเปลี่ยนเป็น Short Header สำหรับข้อมูล (RFC 9000 หัวข้อ 17.2) และสุดท้ายคือไม่มีคำว่า `GET` หรือเนื้อหาของคำตอบปรากฏบนสายเลย เพราะ QUIC เข้ารหัสทุกอย่างเสมอ (รัน)

</Step>

## ผลที่วัดได้: QUIC ไม่ได้เร็วกว่าที่ทฤษฎีบอก

ที่ RTT 100 มิลลิวินาที เวลาจากเริ่มต่อจนได้ Byte แรกของ Response (รัน)

| แบบ | พร้อมใช้ | Byte แรก | รอบเวลา |
|---|---|---|---|
| TCP ธรรมดา กับ HTTP/1.1 | - | 203 ms | 2.0 |
| TCP + TLS 1.3 กับ HTTP/1.1 | 205 ms | 305 ms | 3.0 |
| QUIC (aioquic 1.3.0) | 201 ms | 302 ms | 3.0 |

ในทฤษฎี QUIC ควรเสียน้อยกว่า TCP + TLS หนึ่งรอบเวลา เพราะรวมการตกลงกุญแจเข้ากับ Handshake ของ Connection (RFC 9000 หัวข้อ 7) แต่ในการรันนี้ได้เท่ากัน คือ Connection ของ QUIC พร้อมใช้หลัง 2 รอบเวลา แล้วรับ Response เมื่อครบ 3 รอบเวลา เหมือน TCP + TLS 1.3 ตามที่แบบฝึกยืนยัน ดังนั้นเราต้องระวังว่า เรายังไม่รู้สาเหตุ (อาจเป็นพฤติกรรมของไลบรารี Aioquic หรือการตั้งค่าของเรา) ผลนี้บอกได้แค่ว่า "ในรันนี้ ด้วยไลบรารีนี้" ไม่ได้บอกว่า QUIC ทั่วไปช้าหรือเร็วเท่าไร และเราไม่ได้ลอง 0-RTT ที่ทฤษฎีบอกว่าส่งข้อมูลได้ตั้งแต่ Packet แรกของการเชื่อมต่อซ้ำ (ไม่ได้รัน)

<Callout type="note" title="สิ่งที่อ่านได้จากผลนี้ และสิ่งที่ไม่ได้">

ที่แน่ใจได้ คือ QUIC เป็นโปรโตคอลบน UDP ที่เข้ารหัสทั้งหมด เริ่มด้วย Datagram ขนาด 1200 ไบต์ และใช้ Stream คนละสายอิสระต่อกัน ส่วนที่ว่า QUIC เร็วกว่าเพราะ Handshake หนึ่งรอบเวลา หรือเพราะ Packet หายแล้วไม่บล็อกกัน เป็นข้อความที่เรายังไม่มีหลักฐานจากการรันของเราเอง จึงอ้างได้แค่จาก RFC เท่านั้น (ผู้เขียน)

</Callout>

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| HTTP/1.1 ต้องใช้หลาย Connection เมื่อต้องการคำขอพร้อมกัน | RFC 9113 หัวข้อ 1 |
| หกคำขอ: Connection ใหม่ทุกครั้ง 857 ms, Keep-alive 752 ms, หก Connection 149 ms, HTTP/2 135 ms | รัน: `exercises/12_http.py` (ตัวเลขแกว่งเล็กน้อยทุกรัน) |
| เฟรมของ HTTP/2: Header 9 ไบต์, Preface 24 ไบต์, เลข Stream คี่ฝั่ง Client, HEADERS, DATA, SETTINGS, WINDOW_UPDATE | รัน และ RFC 9113 หัวข้อ 3.4, 4.1, 5, 6 |
| HPACK ทำให้คำขอที่ซ้ำเหลือ 8 ไบต์ จาก 17 | รัน และ RFC 9113 หัวข้อ 4.3 |
| HTTP/2 ยังวิ่งบน TCP และไม่แก้การบล็อกที่หัวแถวของ TCP | RFC 9113 หัวข้อ 1 (ผลการวัดเรื่องนี้ไม่ได้อ้าง) |
| QUIC: บน UDP, Datagram แรก 1200 ไบต์, Initial เวอร์ชัน 1, Long Header แล้ว Short Header, เข้ารหัสทั้งหมด | รัน และ RFC 9000 หัวข้อ 14.1, 17.2 |
| Stream ของ QUIC ไม่มีลำดับระหว่างกัน และ HTTP/3 อาศัยสิ่งนี้ | RFC 9000 หัวข้อ 2 และ RFC 9114 (ไม่ได้รัน) |
| QUIC ใช้เวลา 3 รอบเวลา เท่ากับ TCP + TLS 1.3 (302 เทียบ 305 ms) ในรันนี้กับ Aioquic 1.3.0 | รัน (ไม่ทราบสาเหตุ) |
| ทฤษฎีบอกว่า QUIC ควรเสียน้อยกว่าหนึ่งรอบเวลา | RFC 9000 หัวข้อ 7 (เทียบกับที่วัดได้ ไม่ตรงกัน) |
| HTTP/3 จริง, การบล็อกของ Stream เมื่อ Packet หาย, 0-RTT, Connection Migration, HTTP/2 ผ่าน TLS | ไม่ได้รัน |
