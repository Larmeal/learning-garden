## ในสายเส้นเดียว ทุกอย่างคุยกันด้วย MAC Address

IP Address บอกว่าคอมพิวเตอร์ตัวไหน แต่สายที่ต่ออยู่จริงไม่รู้จัก IP มันรู้จักแค่ MAC Address ซึ่งเป็นเลข 48 บิตที่ติดกับการ์ดเครือข่ายแต่ละใบ Frame ของ Ethernet จึงเริ่มด้วย Header ยาว 14 ไบต์ ที่มีสามช่อง คือ MAC ปลายทาง 6 ไบต์ MAC ต้นทาง 6 ไบต์ และ Type อีก 2 ไบต์ที่บอกว่าข้างในคืออะไร (รัน: `exercises/03_link_layer.py`, หนังสือ: TCPIP หัวข้อ 3.2 หน้า 80 และหน้า 86)

ช่อง Type ที่ใช้กับ IPv4 คือ `0x0800` ค่าที่มากกว่า 1536 แปลว่าเป็น Type แต่ถ้าน้อยกว่านั้นจะถูกอ่านเป็นความยาว ซึ่งเป็นการออกแบบเก่าที่ยังเหลืออยู่

มีสองบิตในไบต์แรกของ MAC Address ที่เราควรรู้ บิตต่ำสุดเรียกว่า Group Bit ถ้าเป็น 0 Frame นี้ส่งถึงคอมพิวเตอร์ตัวเดียว ถ้าเป็น 1 แปลว่า Broadcast หรือ Multicast ที่อยู่ `ff:ff:ff:ff:ff:ff` ที่ทุกบิตเป็น 1 จึงหมายถึงส่งถึงทุกคนในสายเดียวกัน ส่วนบิตถัดไปบอกว่าที่อยู่นี้ถูกตั้งเอง ไม่ได้มาจากผู้ผลิตการ์ด คอมพิวเตอร์จำลองในแบบฝึกใช้ที่อยู่ที่ขึ้นต้นด้วย `02` ซึ่งเปิดบิตนี้ไว้ (รัน)

</Step>

## Switch ที่เรียนรู้เอง

สมมติมีคอมพิวเตอร์สามตัว (a, b, c) ต่อเข้ากับ Switch ตัวเดียว ถ้า a ส่ง Frame ไปหา b สิ่งที่ Switch ต้องตัดสินใจคือจะส่งออกสายไหน มันไม่ได้ถูกตั้งค่ามาล่วงหน้า แต่ใช้ตารางที่เติมเอง ทุกครั้งที่มี Frame เข้ามา Switch จะจด MAC ต้นทางลงตาราง ว่าอยู่ที่ Port ที่ Frame เพิ่งเข้ามา ส่วนปลายทาง ถ้ามีในตารางก็ส่งออก Port นั้นที่เดียว ถ้ายังไม่มีก็ส่งสำเนาไปทุก Port ยกเว้น Port ที่รับมา เรียกว่า Flood (หนังสือ: TCPIP หัวข้อ 3.4 หน้า 98 ถึง 100)

เรามาลองพิสูจน์กัน ในแบบฝึก a ส่ง Ping ไปหา b สองรอบ โดยที่ Switch เพิ่งเปิดและยังไม่เคยเห็น Frame ของใครเลย พร้อมกับจับ Packet ที่ฝั่ง a, b และ c ไว้ทั้งสามตัว (รัน)

| Frame | ส่งโดย | ใครเห็น |
|---|---|---|
| Echo Request ครั้งที่ 1 | a | a, b, **c** |
| Echo Reply ครั้งที่ 1 | b | a, b |
| Echo Request ครั้งที่ 2 | a | a, b |
| Echo Reply ครั้งที่ 2 | b | a, b |

c เห็นแค่ Frame แรก ทั้งที่ Frame นั้นส่งถึง b กดเล่นเพื่อดูว่าเกิดอะไรขึ้นในตารางของ Switch ในแต่ละครั้ง

<SwitchLab client:visible />

พอจบการทดลอง คำสั่ง `bridge fdb show` ที่รันจริงแสดงตารางที่มีสองแถว คือ a ที่ `p1` และ b ที่ `p2` ไม่มีแถวของ c เพราะ c ยังไม่เคยส่ง Frame ออกมาเลย (รัน)

```text
02:00:00:00:00:0a dev p1 master br0
02:00:00:00:00:0b dev p2 master br0
```

<Callout type="note" title="Switch ตัวจริงมีรายละเอียดมากกว่านี้">

แถวในตารางของ Switch จะหมดอายุถ้าไม่มี Frame จากที่อยู่นั้นเข้ามานาน และ Switch ที่รองรับ VLAN จะแยกตารางต่อ VLAN แบบฝึกนี้ใช้ Linux Bridge ซึ่งใช้หลักเดียวกัน แต่ Switch ที่เป็นฮาร์ดแวร์จริงไม่ได้ถูกทดลอง

</Callout>

## ARP หา MAC จาก IP

ตอนนี้เหลือปัญหาหนึ่ง a รู้ IP ของ c คือ `10.0.1.4` แต่ Frame ต้องมี MAC ปลายทาง a จึงถามทุกคนในสายด้วย ARP (Address Resolution Protocol) ว่า "ใครถือ 10.0.1.4 บ้าง ช่วยบอก MAC ด้วย" เป็น Frame ที่ส่งไปที่ `ff:ff:ff:ff:ff:ff` ทุกคนในสายจึงได้ยิน แต่มีแค่เจ้าของที่อยู่ที่ตอบ และตอบตรงไปหา a คนเดียว (หนังสือ: TCPIP หัวข้อ 4.2 หน้า 166 ถึง 169)

<ArpLab client:visible />

ข้อมูลที่แบบฝึกจับได้มีดังนี้ (รัน)

```text
ARP request: 02:00:00:00:00:0a -> ff:ff:ff:ff:ff:ff   who has 10.0.1.4? tell 10.0.1.2
ARP reply:   02:00:00:00:00:0c -> 02:00:00:00:00:0a   10.0.1.4 is at 02:00:00:00:00:0c
```

Request ใส่ IP กับ MAC ของ a ไปด้วย เพื่อให้ c ตอบกลับได้โดยไม่ต้องถามกลับ ช่อง MAC ปลายทางในตัว ARP เป็นศูนย์ทั้งหมดเพราะเป็นสิ่งที่กำลังถามหา (หนังสือ: TCPIP หัวข้อ 4.4 หน้า 170) b ไม่ใช่เจ้าของจึงเห็นแค่ Request และไม่เห็น Reply เลย เพราะ Reply เป็น Unicast และ Switch รู้แล้วว่า a อยู่ที่ไหน

a จดคำตอบไว้ใน Neighbour Cache ซึ่งดูได้ด้วย `ip neigh` เมื่อมีแถวแล้ว Frame ต่อ ๆ ไปก็ส่งเป็น Unicast ได้เลย (หนังสือ: TCPIP หัวข้อ 4.3 หน้า 169) แต่ละ Frame ของ ARP ที่จับได้ยาว 42 ไบต์ คือ Ethernet 14 บวก ARP 28 (รัน)

```text
$ ip neigh      # ที่ a
10.0.1.4 lladdr 02:00:00:00:00:0c REACHABLE
```

เมื่อเทียบกับ[บท 1](/networking/big-picture/) ARP ที่ Client ถามหา Router ก็คือเรื่องเดียวกันนี้ เพียงแต่คำถามคือ MAC ของ `10.0.1.1` แทนที่จะเป็นของ Server ปลายทาง

## MTU กำหนดขนาด Segment ของ TCP

Frame ของ Ethernet ยาวได้จำกัด ส่วนข้อมูลที่ Frame หนึ่งอันแบกได้มากที่สุดเรียกว่า MTU (Maximum Transmission Unit) ซึ่งปกติเป็น 1500 ไบต์ ตัวเลขนี้นับตั้งแต่ IP Header เป็นต้นไป จึงเป็นขนาดสูงสุดของ IP Packet หนึ่งอัน (หนังสือ: TCPIP หัวข้อ 3.8 หน้า 148)

TCP ต้องรู้ตัวเลขนี้ เพื่อไม่ให้ตัดข้อมูลออกมาเป็นก้อนที่ใหญ่เกินกว่าจะส่งได้ใน Frame เดียว จึงบอกกันตอน Handshake ผ่าน Option ที่ชื่อ MSS (Maximum Segment Size) ซึ่งนับเฉพาะข้อมูลของ TCP ไม่รวม Header ของ TCP และ IP (หนังสือ: TCPIP หัวข้อ 13.3.1 หน้า 606) ในแบบฝึก เราเปิด Connection สองสาย สายแรกตอน MTU เป็น 1500 และสายที่สองหลังจากตั้ง MTU ของทั้งสองฝั่งเป็น 1400

| Packet | MTU ตอนนั้น | MSS ที่ประกาศ |
|---|---|---|
| SYN จาก a | 1500 | 1460 |
| SYN, ACK จาก b | 1500 | 1460 |
| SYN จาก a | 1400 | 1360 |
| SYN, ACK จาก b | 1400 | 1360 |

MSS เท่ากับ MTU ลบ 40 ไบต์ ซึ่งเป็น IP Header 20 ไบต์บวก TCP Header 20 ไบต์ (รัน) เรื่องนี้เป็นเหตุผลที่ว่า Tunnel หรือ VPN ที่ลดขนาด MTU ลง มักทำให้ต้องปรับ MSS ตาม ไม่เช่นนั้น Packet ที่ใหญ่เกินจะถูกแตกเป็นชิ้นหรือถูกทิ้ง เราจะกลับมาดูเรื่องการแตก Packet ในบทที่พูดถึง IP
