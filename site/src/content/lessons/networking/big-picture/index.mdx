## เปิด Request หนึ่งอันออกมาดู

เวลาเราเรียก `requests.get("http://garden.test/hello.txt")` มันดูเหมือนข้อความลอยไปถึง Server เองเลย แต่ระหว่างทางมีหลายอย่างเกิดขึ้น เพื่อให้เห็นกับตา เราสร้างเครือข่ายเล็ก ๆ ขึ้นมาจริงใน Linux ประกอบด้วย Client, Router และ Server ต่อกันเป็นเส้นตรง (แต่ละตัวเป็น Network Namespace แยกกัน มีสายเสมือนคั่นกลาง) แล้วให้ Client ส่ง Request ไปหา Server พร้อมกับจับทุก Packet ที่ผ่านสายไว้ด้วย `tcpdump` (รัน: `exercises/01_big_picture.py`)

Request ที่ส่งไปคือข้อความธรรมดายาว 65 ไบต์ ถ้าเขียนให้เห็นตัวควบคุมบรรทัดด้วย จะได้แบบนี้

```text
GET /hello.txt HTTP/1.1\r\n
Host: garden.test\r\n
Connection: close\r\n
\r\n
```

ที่ฝั่ง Client เราจับ Packet ของ Connection นี้ได้สิบอัน

| # | ทิศทาง | ชนิด | ขนาดของ Frame |
|---|---|---|---|
| 1 | Client ไป Server | SYN | 74 ไบต์ |
| 2 | Server ไป Client | SYN, ACK | 74 ไบต์ |
| 3 | Client ไป Server | ACK | 66 ไบต์ |
| 4 | Client ไป Server | PSH, ACK (Request อยู่ในนี้) | 131 ไบต์ |
| 5 | Server ไป Client | ACK | 66 ไบต์ |
| 6 | Server ไป Client | PSH, ACK (Response อยู่ในนี้) | 164 ไบต์ |
| 7 | Client ไป Server | ACK | 66 ไบต์ |
| 8 | Server ไป Client | FIN, ACK | 66 ไบต์ |
| 9 | Client ไป Server | FIN, ACK | 66 ไบต์ |
| 10 | Server ไป Client | ACK | 66 ไบต์ |

ข้อความที่เราตั้งใจส่งมีแค่สองก้อน (Request กับ Response) แต่เกิด Packet ขึ้นสิบอัน เพราะส่วนที่เหลือเป็นงานของ TCP ที่ต้องตกลงกันก่อนส่ง (สาม Packet แรก) ต้องบอกรับทราบ และต้องปิด Connection ให้เรียบร้อย ก่อนหน้า Packet แรกยังมี ARP อีกสองเฟรม คือ Client ถามว่า "10.0.1.1 คือใคร" แล้ว Router ตอบด้วย MAC Address ของมัน ทั้งหมดนี้เราจะไล่ดูทีละเรื่องในบทต่อ ๆ ไป ตอนนี้ขอให้จำไว้ก่อนว่าข้อความ 65 ไบต์ไม่ได้เดินทางเปล่า ๆ

</Step>

## Packet คือกล่องที่ห่อกันหลายชั้น

ลองนึกถึงการส่งพัสดุข้ามเมือง ของที่เราอยากส่งคือข้อความ HTTP เราใส่ลงกล่องที่ติดชื่อแผนกปลายทางไว้ (TCP กับเลข Port) แล้วห่อกล่องนั้นอีกชั้นด้วยกล่องที่ติดที่อยู่บ้านปลายทาง (IP) พอถึงตอนขึ้นรถ คนขับแต่ละช่วงก็ติดใบนำส่งใหม่ที่บอกแค่ว่า "จากโกดังนี้ไปโกดังถัดไป" (Ethernet) ใบนำส่งนี้ใช้ได้เฉพาะช่วงนั้น พอถึงโกดังก็ฉีกทิ้งแล้วติดใบใหม่ให้ช่วงต่อไป ส่วนกล่องข้างในไม่ถูกเปิดเลย

Packet จริงก็ทำแบบเดียวกัน เราวัดขนาดของแต่ละชั้นจาก Packet ที่ฝั่ง Client ส่งออก

| ชั้น | Header ที่เติม | ขนาด | ตัวระบุของชั้นนี้ |
|---|---|---|---|
| Application | ข้อความ HTTP | 65 ไบต์ | URL, Header ของ HTTP |
| Transport | TCP | 32 ไบต์ | Port (50000 ไป 8080) |
| Network | IP | 20 ไบต์ | IP Address (10.0.1.2 ไป 10.0.2.2) |
| Link | Ethernet | 14 ไบต์ | MAC Address |
| ทั้ง Frame | | 131 ไบต์ | |

Header ของ TCP ในที่นี้ยาว 32 ไบต์ เพราะมี 20 ไบต์ที่ต้องมีทุกครั้ง บวก Option อีก 12 ไบต์ ที่ Linux ใส่ไว้ให้บันทึกเวลา (รัน, หนังสือ: TCPIP หัวข้อ 1.2.2 หน้า 10)

แล้วแต่ละชั้นรู้ได้อย่างไรว่าข้างในคือชั้นอะไร คำตอบคือ Header ของแต่ละชั้นมีช่องหนึ่งที่บอกไว้ ช่อง Type ของ Ethernet เป็น `0x0800` ซึ่งแปลว่าข้างในเป็น IPv4 ช่อง Protocol ของ IP เป็น `6` ซึ่งแปลว่าข้างในเป็น TCP และช่อง Destination Port ของ TCP เป็น `8080` ซึ่งใช้เลือกโปรแกรมที่ฟัง Port นั้นอยู่ เรียกการเลือกต่อลงไปทีละชั้นแบบนี้ว่า Demultiplexing (รัน, หนังสือ: TCPIP หัวข้อ 1.3.2 หน้า 16)

</Step>

## ดู Packet หนึ่งอันตั้งแต่ถูกห่อจนถูกแกะ

กดเล่น แล้วดูว่า Header ถูกเติมที่ Client ทีละชั้นอย่างไร และตอนผ่าน Router มีอะไรถูกทิ้งแล้วทำใหม่ ตารางด้านล่างเทียบ Field ที่ฝั่งส่งกับที่ฝั่งรับ ช่องสีเขียวคือช่องที่เหมือนเดิมตลอดทาง ช่องสีฟ้าคือช่องที่ Router เปลี่ยน

<PacketJourneyLab client:visible />

สิ่งที่ควรสังเกตมีสองอย่าง อย่างแรกคือ IP Address กับ Port ไม่เคยเปลี่ยนเลย เพราะสองอย่างนี้บอกว่า "ใครคุยกับใคร" ซึ่งเป็นเรื่องของปลายทั้งสองฝั่ง อย่างที่สองคือ MAC Address กับ TTL เปลี่ยนทุกครั้งที่ผ่าน Router เพราะ MAC Address บอกแค่ "สายเส้นนี้ ใครส่ง ใครรับ" และ TTL เป็นตัวนับว่า Packet ผ่านมากี่ช่วงแล้ว (รัน)

## สี่ชั้น กับสิ่งที่แต่ละชั้นรับผิดชอบ

ชั้นทั้งสี่ที่เราเห็นในภาพ คือโครงของชุดโปรโตคอล TCP/IP (หนังสือ: TCPIP หัวข้อ 1.3.1 หน้า 13) ตำราเครือข่ายหลายเล่มยังเล่าเป็นแบบ OSI เจ็ดชั้นด้วย ซึ่งแยก Link ออกเป็นสายกับเฟรม และแยก Application ออกเป็นสามชั้น (หนังสือ: AIO Book 2 บทที่ 1 หน้า 80) แต่ในการทำงานจริง สี่ชั้นก็เพียงพอจะอธิบายสิ่งที่เราจับได้ทั้งหมด

| ชั้น | หน้าที่ | ระบุด้วย | ใครอ่าน Header ชั้นนี้ |
|---|---|---|---|
| Application | ความหมายของข้อความ (HTTP, DNS, TLS) | ชื่อ URL, ชื่อโดเมน | โปรแกรมที่ปลายทาง |
| Transport | ส่งข้อมูลให้ถึงโปรแกรมที่ถูกตัว (TCP, UDP) | Port | คอมพิวเตอร์ที่ปลายทางสองฝั่ง |
| Network | พาไปถึงคอมพิวเตอร์ที่ถูกเครื่อง ข้ามหลายเครือข่าย (IP) | IP Address | ปลายทาง และ Router ทุกตัวระหว่างทาง |
| Link | ส่งข้ามสายเส้นเดียวไปให้เพื่อนบ้าน (Ethernet) | MAC Address | คอมพิวเตอร์สองตัวที่อยู่ปลายสายเส้นนั้น |

แต่ละชั้นคุยกับชั้นเดียวกันของอีกฝั่งเท่านั้น TCP ของ Client คุยกับ TCP ของ Server ส่วน Router ไม่รู้จัก TCP เลย (ไม่เปิดดู) แนวคิดนี้เรียกว่า End-to-end Argument คือสิ่งที่ต้องรู้ความหมายของข้อมูลจริง ๆ เช่นการเรียงลำดับและการส่งซ้ำ ควรทำที่ปลายทั้งสองฝั่ง ไม่ใช่ในเครือข่ายตรงกลาง เครือข่ายตรงกลางทำหน้าที่แค่ส่งต่อให้เร็วและเรียบง่ายที่สุด (หนังสือ: TCPIP หัวข้อ 1.1.2 หน้า 6) เรื่องนี้ช่วยอธิบายว่าทำไมใน Lab Router ถึงแตะแค่ Ethernet กับ TTL

</Step>

## OSI เจ็ดชั้น กับคำที่ทีม Infra ใช้กันจริง

คุณอาจเคยเห็นคำว่า L4 กับ L7 ตอนเปิดหน้า Load Balancer ของ Cloud หรือตอนคุยกับทีม Infra เลขเหล่านี้นับมาจาก OSI Model ซึ่งแบ่งเครือข่ายเป็นเจ็ดชั้น ต่างจากสี่ชั้นของ TCP/IP ที่เราเพิ่งดูกัน (หนังสือ: AIO Book 2 บทที่ 1 หน้า 80) ตารางข้างล่างวางสองแบบเทียบกัน พร้อมของที่เราเจอมาแล้วในบทนี้

| ชั้นที่ | ชื่อ | อยู่ในชั้นนี้ | ตรงกับชั้นของ TCP/IP |
|---|---|---|---|
| 7 | Application | HTTP, DNS | Application |
| 6 | Presentation | แปลงรูปแบบข้อมูล บีบอัด และเข้ารหัส | Application |
| 5 | Session | เปิดและดูแลบทสนทนาระหว่างสองคอมพิวเตอร์ | Application |
| 4 | Transport | TCP, UDP และ Port | Transport |
| 3 | Network | IP Address และ Router | Network |
| 2 | Data Link | MAC Address, Ethernet และ Switch | Link |
| 1 | Physical | สาย สัญญาณ และ Hub | Link |

ภาพข้างล่างวาดสองแบบเป็นกองกล่อง OSI อยู่ซ้าย TCP/IP อยู่กลาง จะเห็นว่ากล่อง Application ของ TCP/IP ใหญ่เท่าสามชั้นบนของ OSI และกล่อง Link ใหญ่เท่าสองชั้นล่าง ลองกดเลือกของแต่ละอย่าง ชั้นที่มันอยู่จะสว่างขึ้นทั้งสองกอง ลองกด Switch ก่อน แล้วกด Load Balancer แบบ L4 กับ L7 เทียบกัน หรือกด TLS ดูว่าทำไมถึงบอกว่าไม่ตรงกล่องไหนเป๊ะ จะกดที่ชั้นเองเพื่ออ่านว่าชั้นนั้นทำอะไรก็ได้

<LayersLab client:visible />

เลขชั้นกลายเป็นภาษาเรียกอุปกรณ์ด้วย Switch ที่ดูแค่ MAC Address เรียกว่าอุปกรณ์ L2 (หนังสือ: AIO Book 2 บทที่ 1 หน้า 81) ส่วน Router ที่ดู IP Address เรียกว่า L3 และ Load Balancer ก็ใช้คำเดียวกัน แบบ L4 คือตัวที่ดูแค่ IP กับ Port แล้วกระจายทีละ Connection ส่วนแบบ L7 จะอ่านข้อความ HTTP แล้วเลือกปลายทางตามแต่ละคำขอ เราจะได้ลองเทียบสองแบบนี้กันใน [บท 13](/networking/proxies-and-containers/) (ชื่อเรียกเป็นของผู้เขียน ส่วนพฤติกรรมของสองแบบรันจริงในบทนั้น)

สำหรับงาน DE ของที่เราเรียกใช้ทุกวันเกือบทั้งหมดอยู่ชั้นบนสุด ทั้ง JDBC ที่ต่อเข้า Database การอ่านไฟล์จาก S3 ที่เป็นคำขอ HTTP และ Kafka ที่ส่งข้อความผ่าน TCP (ข้อนี้เป็นความเข้าใจของผู้เขียนเอง ไม่ได้รันในแบบฝึก) แต่เวลาอะไรพัง ชั้นล่างที่เราไม่ได้เขียนโค้ดเกี่ยวข้องด้วยเลยก็ยังเป็นสาเหตุได้ เราจึงไล่ดูทีละชั้นจากล่างขึ้นบนได้ เช่นดูว่า Ping ถึงไหม (L3) แล้วต่อ Port ได้ไหม (L4) แล้วค่อยดูคำตอบของ HTTP (L7) ซึ่ง [บท 14](/networking/debugging-and-failure/) เอาวิธีนี้ไปใช้กับอาการจริง

อย่าคาดหวังว่าทุกโปรโตคอลจะวางลงตารางนี้ได้พอดี หนังสือเล่มเดียวกันยอมรับว่าโปรโตคอลจริงไม่ได้ทำตาม OSI ทุกตัวอักษร (หนังสือ: AIO Book 2 บทที่ 1 หน้า 81) ยกตัวอย่าง TLS ที่เรากำลังจะเจอใน [บท 11](/networking/tls/) หน้าที่เข้ารหัสอยู่ที่ชั้น Presentation ในตาราง (หนังสือ: AIO Book 2 บทที่ 1 หน้า 88) แต่ TLS ตัวจริงนั่งอยู่ระหว่าง TCP กับ HTTP ซึ่งไม่ตรงกับชั้นไหนเป๊ะ ถ้ามีใครเถียงกันว่า TLS คือชั้นเท่าไหร่ ก็ไม่ต้องจริงจังกับมันนะ ให้ถือว่า OSI เป็นภาษากลางไว้คุยกัน ส่วนตัวผู้เขียนคิดว่าสี่ชั้นของ TCP/IP ตรงกับ Packet ที่เราจับได้มากกว่า

</Step>

## Port กับ Connection หนึ่งสาย

ในแบบฝึก Client เปิด Connection สองสายไปที่ Server ตัวเดิมที่ Port 8080 สายแรกใช้ Port ต้นทาง 50000 สายที่สองใช้ 50001 Server แยกสองสายนี้ออกจากกันได้ เพราะ Connection หนึ่งสายถูกระบุด้วยเลขสี่ตัวรวมกัน คือ IP ต้นทาง, Port ต้นทาง, IP ปลายทาง และ Port ปลายทาง (รัน, หนังสือ: TCPIP หัวข้อ 1.3.3 หน้า 17)

```text
('10.0.1.2', 50000, '10.0.2.2', 8080)
('10.0.1.2', 50001, '10.0.2.2', 8080)
```

ในโปรแกรมจริงเรามักไม่ได้เลือก Port ต้นทางเอง ระบบปฏิบัติการจะเลือกเลขที่ว่างให้ ที่ในแบบฝึกกำหนด 50000 เองก็เพื่อให้ตัวเลขที่พิมพ์ออกมาเหมือนเดิมทุกครั้ง แต่ละสายยังมี Handshake และเลข Sequence ของตัวเอง Client ถาม ARP แค่ครั้งเดียว เพราะสายที่สองใช้ MAC Address ของ Router ที่จำไว้แล้ว

<Callout type="note" title="เลข Port แบ่งเป็นกลุ่ม">

Port ฝั่ง Server ที่คนรู้จักกันทั่วไปมักเป็นเลขต่ำ เช่น 80 สำหรับ HTTP และ 443 สำหรับ HTTPS ส่วน Port ฝั่ง Client ที่ระบบเลือกให้เป็นเลขสูง ๆ ในช่วงชั่วคราว (Ephemeral) เราจะกลับมาดูว่าช่วงนี้กว้างแค่ไหน และเกิดอะไรขึ้นถ้าหมด ในบทที่พูดถึง Socket

</Callout>
