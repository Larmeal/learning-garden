## Router แต่ละตัวตัดสินใจเอง จากตารางของตัวเอง

ใน[บท 3](/networking/link-layer/) เราเห็น Frame ถูกส่งภายในสายเส้นเดียว ตอนนี้เราต่อสายหลายเส้นเข้าด้วยกัน แบบฝึกสร้าง Client, Router สามตัว (R1, R2 และ R3) และ Server เรียงกัน แต่ละคู่ที่ติดกันใช้เครือข่าย /24 คนละอัน และมี Router คั่นอยู่ระหว่างแต่ละคู่ แล้วให้ Client Ping ไปที่ `10.0.4.2` (รัน: `exercises/04_ip_routing.py`)

Router ไม่ได้รู้เส้นทางทั้งหมด มันรู้แค่ตารางของตัวเอง ว่า "ปลายทางที่ขึ้นต้นแบบนี้ ให้ส่งต่อให้ใคร" ตารางของ R1 เป็นแบบนี้

```text
$ ip route          # ที่ R1
10.0.1.0/24 dev l0 proto kernel scope link src 10.0.1.2
10.0.2.0/24 dev r0 proto kernel scope link src 10.0.2.1
10.0.3.0/24 via 10.0.2.2 dev r0
10.0.4.0/24 via 10.0.2.2 dev r0
```

สองแถวแรกเป็นเครือข่ายที่ R1 ต่ออยู่เอง จึงไม่มีคำว่า `via` ส่วนสองแถวหลังบอกว่าเครือข่ายที่อยู่ลึกเข้าไปให้ฝากต่อที่ `10.0.2.2` คือ R2 (หนังสือ: TCPIP หัวข้อ 5.4 หน้า 208) กดเล่นเพื่อดูว่า Packet หนึ่งอันผ่านทั้งสามตัว และแต่ละตัวเทียบปลายทางกับตารางของตัวเองอย่างไร

## ลด TTL และคำนวณ Checksum ใหม่

IPv4 Header ที่ Router อ่านมีช่องที่ใช้บ่อยอยู่ไม่กี่ช่อง (หนังสือ: TCPIP หัวข้อ 5.2 หน้า 183 ถึง 186)

| ช่อง | ใช้ทำอะไร |
|---|---|
| Version และ IHL | เวอร์ชัน (4) และความยาวของ Header |
| Total Length | ความยาวของ Packet ทั้งอัน |
| Identification, Flags, Fragment Offset | ใช้เมื่อ Packet ถูกตัดเป็นชิ้น (ดูท้ายบท) |
| TTL | จำนวนฮอปที่เหลือ ลดลงหนึ่งทุกครั้งที่ผ่าน Router |
| Protocol | ข้างในคืออะไร (6 คือ TCP, 17 คือ UDP, 1 คือ ICMP) |
| Header Checksum | ตรวจว่า Header ไม่เสียหาย |
| Source และ Destination | ที่อยู่ต้นทางกับปลายทาง |

ในแบบฝึกเราส่ง Ping หนึ่งอัน แล้วจับ Packet ที่สายทั้งสี่เส้น ตัวเลขที่เปลี่ยนไปตามทางคือ TTL กับ Checksum (รัน)

| สาย | TTL ของ Request | Checksum ของ Request | TTL ของ Reply |
|---|---|---|---|
| 1 (Client ถึง R1) | 64 | 0xed11 | 61 |
| 2 (R1 ถึง R2) | 63 | 0xee11 | 62 |
| 3 (R2 ถึง R3) | 62 | 0xef11 | 63 |
| 4 (R3 ถึง Server) | 61 | 0xf011 | 64 |

Request ออกจาก Client ด้วย TTL 64 และเสียไปหนึ่งที่ Router ทุกตัว ส่วน Reply ที่เริ่มจาก Server ด้วย 64 ก็เสียไปสามเช่นกัน Client จึงเห็น `ttl=61` ใน Ping ตัวเลข Checksum เปลี่ยนไปทุกสาย เพราะมันคำนวณจากทั้ง Header ซึ่งมี TTL อยู่ข้างใน Router จึงต้องคำนวณใหม่ทุกครั้ง แบบฝึกคำนวณ Checksum ของทุก Header ที่จับได้ด้วยตัวเอง (ผลบวกแบบ Ones' Complement ของ 20 ไบต์) ได้ `0xFFFF` ทุกอัน แปลว่า Header ผ่านการตรวจทั้งหมด (รัน) ส่วนที่อยู่ต้นทาง ปลายทาง และ Identification เหมือนกันตลอดทาง

## เมื่อหลายแถวตรงกัน แถวที่เจาะจงที่สุดชนะ

บางครั้งปลายทางตรงกับหลายแถวในตาราง เช่นมีทั้ง `10.0.4.0/24` และ `10.0.4.2/32` Router จะเลือกแถวที่ Prefix ยาวที่สุด ซึ่งเรียกว่า Longest Prefix Match (หนังสือ: TCPIP หัวข้อ 5.4 หน้า 209) ในแบบฝึก เราเพิ่มแถว `unreachable 10.0.4.2/32` ใน R1 แล้วลองถามเส้นทางไปสองที่อยู่

```text
$ ip route get 10.0.4.2          # ตรงกับทั้ง /24 และ /32
RTNETLINK answers: No route to host

$ ip route get 10.0.4.3          # ตรงกับ /24 เท่านั้น
10.0.4.3 via 10.0.2.2 dev r0 src 10.0.2.1
```

`10.0.4.2` ถูกจัดการโดยแถว `/32` ที่เจาะจงกว่า ทั้งที่แถว `/24` ก็ครอบมันอยู่ ส่วน `10.0.4.3` ไม่ตรงกับ `/32` จึงยังตามแถว `/24` เหมือนเดิม และ Client ที่ Ping ไปที่ `10.0.4.2` ก็ได้ข้อความ `Destination Host Unreachable` จาก R1 (รัน) กฎนี้เองที่ทำให้เราใส่ Route ยกเว้นสำหรับที่อยู่เดียวได้โดยไม่ต้องรื้อตารางทั้งหมด และเป็นเหตุผลที่ตาราง Route ของ Router ในอินเทอร์เน็ตมีทั้งแถวใหญ่แถวเล็กปนกัน

</Step>

## Traceroute คือ Packet ธรรมดาที่ TTL ค่อย ๆ เพิ่มขึ้น

ถ้า Router ทิ้ง Packet ที่ TTL เหลือ 0 แล้วบอกคนส่งด้วย ICMP Time Exceeded (หนังสือ: TCPIP หัวข้อ 8.3 หน้า 361 ถึง 364 และหน้า 375) เราก็ใช้เป็นเครื่องมือถามชื่อ Router ทีละตัวได้ ส่ง Packet ที่ TTL 1 ตัวแรกที่เจอจะทิ้งและตอบกลับ แล้วส่งอีกอันที่ TTL 2 ตัวที่สองจะตอบ ทำไปเรื่อย ๆ จนถึงปลายทาง นี่คือ Traceroute ทั้งหมด (หนังสือ: TCPIP หัวข้อ 8.3 หน้า 376)

<TracerouteLab client:visible />

ผลที่แบบฝึกพิมพ์ออกมา (รัน)

```text
TTL  answer from  ICMP              round trip
1    10.0.1.2     time exceeded     10.2 ms
2    10.0.2.2     time exceeded     20.3 ms
3    10.0.3.2     time exceeded     30.5 ms
4    10.0.4.2     port unreachable  40.5 ms
```

มีสามเรื่องที่ควรสังเกต ที่อยู่ที่ตอบกลับมาคือที่อยู่ของสายที่ Probe เข้ามา (R1 ตอบด้วย `10.0.1.2` ซึ่งเป็นด้านที่หันเข้าหา Client) ไม่ใช่ที่อยู่อื่นของ Router ตัวนั้น เวลาไปกลับเพิ่มประมาณ 10 มิลลิวินาทีต่อฮอป ตรงกับที่ตั้งสายไว้ 5 มิลลิวินาทีต่อทิศทาง และ Probe สุดท้ายที่ถึง Server ไม่ได้รับ Time Exceeded แต่ได้ ICMP Port Unreachable เพราะไม่มีโปรแกรมฟัง Port ที่ใช้ ซึ่ง Traceroute ใช้เป็นสัญญาณว่าถึงแล้ว

</Step>

## Route วนเป็นวง ถูกหยุดด้วย TTL เท่านั้น

ถ้าตั้ง Route ผิด จนสอง Router ชี้ให้กันและกันเป็นทางไปที่ปลายทางเดียวกัน Packet จะวนไปมาระหว่างทั้งสอง แบบฝึกจำลองเรื่องนี้ โดยตั้ง `10.0.9.0/24` ที่ R1 ให้ส่งไป R2 และที่ R2 ให้ส่งกลับไป R1 แล้ว Ping ด้วย TTL เริ่มต้น 8 สิ่งที่เห็นบนสายระหว่าง R1 กับ R2 คือ Request เดียวกันผ่านซ้ำไปมาโดย TTL ลดทีละหนึ่ง (รัน)

```text
TTL ของแต่ละรอบที่ผ่านสายนี้: [7, 6, 5, 4, 3, 2, 1]
จากนั้น: ICMP time exceeded จาก 10.0.2.2
```

เมื่อ TTL ถึง 0 Router ที่ถือ Packet อยู่ในตอนนั้นก็ทิ้งมัน และบอกต้นทางว่า Time Exceeded ไม่มีกลไกอื่นเข้ามาช่วยเลย ตัวนับนี้เล็กแต่สำคัญมาก เพราะถ้าไม่มี Packet ที่ติดวงจะวนไปไม่จบและกินแบนด์วิดท์ของสายสองเส้นนี้ไปเรื่อย ๆ (หนังสือ: TCPIP หัวข้อ 5.2 หน้า 184)

</Step>

## เมื่อ Packet ใหญ่เกินกว่าสายหนึ่งจะรับได้

เรารู้จัก MTU จาก[บท 3](/networking/link-layer/#mtu-กำหนดขนาด-segment-ของ-tcp) ถ้า Packet ใหญ่กว่า MTU ของสายที่กำลังจะออก มีสองทาง ถ้าธง DF (Don't Fragment) ไม่ได้เปิด Router จะตัด Packet ออกเป็นชิ้น (Fragment) ถ้าเปิด Router จะทิ้งและส่ง ICMP กลับ แบบฝึกตั้ง MTU ของสายสุดท้ายเป็น 1400 แล้วลองทั้งสองแบบ

ทางแรก Ping ที่มีข้อมูล 3000 ไบต์ (รวม Header ของ ICMP เป็น 3008) ถูกตัดสองครั้ง ครั้งแรกที่ Client ตามขนาด MTU 1500 (ชิ้นละ 1480, 1480 และ 48 ไบต์) ครั้งที่สองที่ Router ตัวที่สาม ตามขนาด MTU 1400 กดเล่นเพื่อดูว่าการตัดครั้งที่สองลงไปตัดที่ไหนของชิ้นส่วนที่ตัดแล้ว

<FragmentLab client:visible />

ที่สายสุดท้าย จับ Fragment ได้ห้าชิ้น (รัน)

| IP ID | Offset | ข้อมูล | ธง |
|---|---|---|---|
| 14071 | 0 | 1376 | มีชิ้นต่อ (More Fragments) |
| 14071 | 1376 | 104 | มีชิ้นต่อ |
| 14071 | 1480 | 1376 | มีชิ้นต่อ |
| 14071 | 2856 | 104 | มีชิ้นต่อ |
| 14071 | 2960 | 48 | ชิ้นสุดท้าย |

ทุกชิ้นใช้ IP ID เดียวกัน เพื่อให้ผู้รับรู้ว่ามาจากก้อนเดียวกัน และ Offset บอกว่าชิ้นนั้นอยู่ตำแหน่งไหนของข้อมูลเดิม (นับเป็นผลคูณของ 8 ไบต์) มีแค่ผู้รับที่ประกอบกลับ Router ระหว่างทางไม่ประกอบ Client ได้ Reply ครบ 3008 ไบต์ (รัน, หนังสือ: TCPIP หัวข้อ 10.7 หน้า 488 ถึง 493) เรื่องที่ควรรู้คือ ถ้าชิ้นเดียวหาย ผู้รับต้องทิ้งทั้งก้อน Fragment จึงทำให้การส่งไม่น่าเชื่อถือขึ้นเมื่อสายมี Loss

ทางที่สองคือเปิดธง DF (`ping -M do -s 1472` ซึ่งทำให้ Packet ยาว 1500 พอดี MTU ของสายแรก) Router ตัวที่สามที่ตัดไม่ได้จะทิ้ง Packet และตอบ ICMP Type 3 Code 4 "Fragmentation Needed" พร้อมบอกว่าสายถัดไปรับได้เท่าไร (รัน)

```text
From 10.0.3.2 icmp_seq=1 Frag needed and DF set (mtu = 1400)
ICMP type 3 code 4 from 10.0.3.2, next-hop MTU field = 1400
```

คำตอบนี้คือกลไกของ Path MTU Discovery ผู้ส่งรู้ขนาดที่ใช้ได้จริงตลอดเส้นทาง แล้วลดขนาด Packet ตาม โดยไม่ต้องให้ใครตัดชิ้น TCP ใช้วิธีนี้เป็นหลัก (หนังสือ: TCPIP หัวข้อ 13.4 หน้า 612)

</Step>

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| Router ลด TTL ลงหนึ่งและคำนวณ Checksum ใหม่ (64, 63, 62, 61) และ Header ผ่านการตรวจทุกสาย | รัน: `exercises/04_ip_routing.py` และหนังสือ: TCPIP หัวข้อ 5.2 หน้า 183 ถึง 186 |
| ตาราง Route แถวที่ต่อตรงกับแถวที่ส่งต่อ | รัน และหนังสือ: TCPIP หัวข้อ 5.4 หน้า 208 |
| Longest Prefix Match | รัน และหนังสือ: TCPIP หัวข้อ 5.4 หน้า 209 |
| Traceroute ใช้ TTL กับ ICMP Time Exceeded และ Port Unreachable | รัน และหนังสือ: TCPIP หัวข้อ 8.3 หน้า 361 ถึง 364, หน้า 375 ถึง 376 |
| Route วนถูกหยุดด้วย TTL | รัน |
| การ Fragment และ Offset เป็นผลคูณของ 8 | รัน และหนังสือ: TCPIP หัวข้อ 10.7 หน้า 488 |
| Path MTU Discovery ด้วย ICMP Type 3 Code 4 | รัน และหนังสือ: TCPIP หัวข้อ 13.4 หน้า 612 |
| OSPF, BGP และ IPv6 | ไม่ได้รัน |

</Step>
