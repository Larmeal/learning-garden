## UDP คือการส่งข้อความเดี่ยว ๆ ที่ไม่มีการรับประกัน

ใน IP Header มีช่อง Protocol ที่บอกว่าข้างในเป็น TCP หรือ UDP เรายังไม่ได้เรียน TCP เลย เพราะเรื่องของ UDP เล็กกว่ามาก เราจึงเริ่มจากตัวนี้ UDP คือชั้น Transport ที่ทำแค่สองอย่างต่อจาก IP อย่างแรกคือบอกว่าข้อมูลเป็นของโปรแกรมที่ฟัง Port ไหน อย่างที่สองคือตรวจว่าข้อมูลไม่เสียหายด้วย Checksum นอกนั้นไม่มีอะไรอีกเลย (หนังสือ: TCPIP หัวข้อ 10.2 หน้า 474)

แบบฝึกให้ Client ส่ง Datagram หกอัน ขนาด 10, 20, 30, 40, 50 และ 60 ไบต์ ไปที่ Server ซึ่งตั้งกฎไว้ให้ทิ้งทุกอันที่สามที่เข้ามา (รัน: `exercises/06_udp_dns.py`) ที่ Client จับ Packet ได้ดังนี้

```text
#  Port ต้นทาง  Port ปลายทาง  Length  Checksum  ขนาด Frame
1  40000        9999          18      0x2667    52
2  40000        9999          28      0xcbf7    62
3  40000        9999          38      0x7188    72
4  40000        9999          48      0x1719    82
5  40000        9999          58      0xbca9    92
6  40000        9999          68      0x623a    102
```

ที่ควรเห็นมีสามเรื่อง Packet แรกที่ออกสายก็คือข้อมูลเลย ไม่มีการจับมือ Header ของ UDP ยาวแค่ 8 ไบต์ คือ Port ต้นทาง Port ปลายทาง Length และ Checksum อย่างละ 2 ไบต์ ช่อง Length คือ 8 บวกขนาดข้อมูล (10 ไบต์ได้ 18) และ Frame หนึ่งอันคือ 14 (Ethernet) บวก 20 (IP) บวก 8 (UDP) บวกข้อมูล Checksum ครอบทั้งข้อมูล Header ของ UDP และ Pseudo-header ที่ยืมที่อยู่ IP ต้นทางกับปลายทางมาใส่ในการคำนวณ แบบฝึกคำนวณซ้ำเองกับทุก Datagram ได้ผลบวกเป็น `0xFFFF` ซึ่งแปลว่าถูกต้อง (รัน, หนังสือ: TCPIP หัวข้อ 10.3 หน้า 475)

## เมื่อ Datagram หาย ไม่มีใครบอกอะไรเลย

กดเล่นเพื่อดู Datagram ทั้งหกออกไป และสองอันถูกทิ้ง

<UdpLab client:visible />

ผลที่ฝั่ง Server รับได้จริง (รัน)

| Datagram | ขนาดที่ได้รับ |
|---|---|
| msg1 | 10 ไบต์ |
| msg2 | 20 ไบต์ |
| msg4 | 40 ไบต์ |
| msg5 | 50 ไบต์ |

Server ได้ 1, 2, 4 และ 5 ส่วน 3 กับ 6 หายไป ขณะที่ฝั่ง Client เรียก `sendto` ครบหกครั้งและสำเร็จทุกครั้ง ไม่มี Error ไม่มีข้อความแจ้ง ตัวนับของกฎ Iptables ที่ Server บอกว่าทิ้งไปสอง Datagram (รัน) นี่คือคำว่า "ไม่รับประกัน" ของ UDP ตามความหมายจริง ถ้า Datagram หาย ผู้ส่งไม่มีทางรู้เลยจากตัว UDP เอง ถ้าโปรแกรมต้องการให้ครบ ก็ต้องออกแบบกลไกของตัวเอง เช่นใส่เลขลำดับ และส่งซ้ำเมื่อไม่ได้คำตอบ

อีกด้านของเหรียญ ข้อมูลที่มาถึงมาเป็นก้อนเดียวและมีขนาดตรงกับที่ส่ง ได้ 10, 20, 40 และ 50 ไบต์ ไม่ถูกรวมหรือแบ่ง ซึ่งต่างจาก TCP ที่เราจะเห็นทีหลัง

## DNS แปลงชื่อเป็นที่อยู่ ผ่าน UDP

คนพิมพ์ชื่ออย่าง `www.example.test` แต่ IP ต้องการที่อยู่ ระบบที่แปลงให้คือ DNS (Domain Name System) ซึ่งเป็นฐานข้อมูลที่กระจายอยู่บน Server หลายตัว ชื่อโดเมนอ่านจากขวาไปซ้ายเป็นต้นไม้ ที่ปลายขวาสุดคือ Root (จุดสุดท้ายที่ซ่อนอยู่) ต่ำลงมาคือ TLD เช่น `.com` หรือในแบบฝึกคือ `.test` แล้วเป็นโดเมนของเจ้าของ และชื่อของคอมพิวเตอร์ตัวนั้นอยู่ซ้ายสุด (หนังสือ: TCPIP หัวข้อ 11.2 หน้า 512) แต่ละส่วนของต้นไม้มี Server ที่ดูแลของตัวเอง เรียกว่า Authoritative Server (หนังสือ: TCPIP หัวข้อ 11.3 หน้า 516)

โปรแกรมส่วนใหญ่ไม่เดินต้นไม้เอง มันถาม Resolver (ตัวที่ DHCP แจกที่อยู่ให้เรา) ว่า "ช่วยหาคำตอบสุดท้ายให้ที" ซึ่ง Resolver จะเดินแทนและจำคำตอบไว้ แบบฝึกสร้างทุกส่วนนี้ขึ้นมา คือ Client, Resolver และ Server สามตัวที่ดูแลระดับ Root, TLD และ `example.test` บนสายเดียวกัน แล้วให้ Client ถาม `www.example.test` หนึ่งครั้ง จับ Packet ที่สายของ Resolver (รัน)

```text
เวลา    ใครคุยกับใคร               Flag            อะไร
0 ms    client -> resolver         RD=1 RA=0 AA=0  question
20 ms   resolver -> root           RD=0 RA=0 AA=0  question
41 ms   root -> resolver           RD=0 RA=0 AA=0  referral to a.nic.test
61 ms   resolver -> TLD            RD=0 RA=0 AA=0  question
81 ms   TLD -> resolver            RD=0 RA=0 AA=0  referral to ns1.example.test
101 ms  resolver -> authoritative  RD=0 RA=0 AA=0  question
122 ms  authoritative -> resolver  RD=0 RA=0 AA=1  answer A 10.0.2.50
122 ms  resolver -> client         RD=1 RA=1 AA=0  answer A 10.0.2.50
```

Client ถามหนึ่งครั้ง แต่ Resolver ถามสามครั้ง Root ไม่ได้ตอบ แต่ชี้ไปหา Server ของ `test.` พร้อมที่อยู่ของมัน (เรียกว่า Glue) TLD ก็ไม่ตอบเช่นกัน แต่ชี้ต่อไปที่ Server ของ `example.test` มีแค่ Authoritative Server ตัวสุดท้ายที่ตอบจริง (ธง AA) กดเล่นเพื่อดูการเดินทั้งหมด และการถามครั้งที่สองที่ตามมา

## ข้อความ DNS หนึ่งอันมีอะไรอยู่ข้างใน

ธง `RD` (Recursion Desired) ที่ Client ตั้ง แปลว่า "ช่วยเดินให้ที" และ `RA` (Recursion Available) ที่ Resolver ตอบ แปลว่าฉันรับทำให้ ส่วน Resolver ที่ถาม Root, TLD และ Authoritative ปิด RD ไว้ เพราะมันกำลังเดินเอง ไม่ได้ขอให้ใครเดินแทน (รัน, หนังสือ: TCPIP หัวข้อ 11.5 หน้า 518) Query ID ของแต่ละคำถามกับคำตอบเป็นตัวเดียวกัน ซึ่งเป็นวิธีที่ใช้จับคู่ (รัน)

ข้อความที่ Authoritative ตอบกลับมีขนาด 50 ไบต์ มาจาก Header 12 ไบต์ ชื่อที่ถูกเขียนเป็น `www.example.test` อีก 18 ไบต์ ประเภทกับคลาสอย่างละ 2 ไบต์ และ Record คำตอบอีก 16 ไบต์ ชื่อในโปรโตคอลถูกเขียนเป็นป้ายแต่ละส่วน นำหน้าด้วยความยาว และจบด้วย 0 คือ `3www7example4test0` ตรงนี้เองที่ DNS ใช้ลูกเล่นประหยัดที่น่าสนใจ ในส่วนคำตอบ ชื่อของ Record ไม่ได้ถูกเขียนซ้ำ มีแค่ตัวชี้ `0xC00C` ที่แปลว่า "ชื่อเดียวกับที่อยู่ไบต์ที่ 12" ซึ่งก็คือชื่อในคำถาม ทำให้ Record คำตอบเหลือ 16 ไบต์แทนที่จะเป็น 34 (รัน, หนังสือ: TCPIP หัวข้อ 11.5 หน้า 518)

DNS ใช้ UDP Port 53 และ Client ใช้ Port ต้นทางสูง ๆ ที่ระบบเลือกให้ ข้อความทั้งหมดอยู่ใน Datagram เดียว ซึ่งเป็นเหตุผลที่ DNS เลือก UDP คือถามหนึ่งครั้งตอบหนึ่งครั้ง ไม่คุ้มกับการจับมือของ TCP (รัน)

</Step>

## Cache: ถามครั้งที่สองเกือบไม่ต้องใช้เวลา

เวลาที่ใช้ถามครั้งแรกคือ 123 มิลลิวินาที เพราะ Server ทั้งสามตัวถูกหน่วงคำตอบไว้ตัวละ 20 มิลลิวินาที และ ARP ครั้งแรกกับแต่ละตัวอีกตัวละ 20 (ตัวหน่วงใช้กับ ARP ด้วย) Resolver จำคำตอบไว้ตามเวลา TTL ที่ Authoritative ตั้ง ซึ่งในที่นี้คือ 300 วินาที พอถามซ้ำภายใน 300 วินาที ก็ตอบเองได้ทันที (รัน)

| การถาม | จำนวน Packet | TTL ในคำตอบ | เวลาของ Dig |
|---|---|---|---|
| ครั้งแรก (ไม่มีใน Cache) | 8 | 300 | 123 ms |
| ครั้งที่สอง (อยู่ใน Cache) | 2 | 298 | 0 ms |

ครั้งที่สองมีแค่สอง Packet คือ Client ถาม และ Resolver ตอบ ไม่มีใครถูกรบกวนอีกเลย TTL ในคำตอบลดลงเหลือ 298 เพราะเวลาผ่านไปแล้วสองวินาทีตั้งแต่จำไว้ (หนังสือ: TCPIP หัวข้อ 11.4 หน้า 517) นี่เป็นเหตุผลที่คนสร้าง DNS ใส่ Cache ไว้ตั้งแต่ต้น ถ้าไม่มี Root Server จะต้องรับทุกคำถามของคนทั้งโลก และเป็นเหตุผลที่ว่าเมื่อเปลี่ยน IP ของ Server เราต้องรอให้ TTL เก่าหมดอายุก่อน ถึงจะเห็นผลทั่วโลก (ผู้เขียน)

มีสองกรณีพิเศษที่แบบฝึกลอง ชื่อที่เป็นนามแฝง `api.example.test` ถูกตอบเป็น CNAME ที่ชี้ไป `www.example.test` และมี Record A ของชื่อจริงมาในคำตอบเดียวกัน ทำให้ถามครั้งเดียวได้ครบ และชื่อที่ไม่มีอยู่ ได้ Rcode 3 หรือ `NXDOMAIN` จาก Authoritative ซึ่ง Resolver ส่งต่อให้ Client (รัน)

```text
$ dig @10.0.1.3 api.example.test A
api.example.test.   300  IN  CNAME  www.example.test.
www.example.test.   300  IN  A      10.0.2.50
```

## ที่มาของบทนี้

| ข้อความ | ที่มา |
|---|---|
| UDP Header ยาว 8 ไบต์, Frame = 14 + 20 + 8 + ข้อมูล, Checksum ครอบ Pseudo-header | รัน: `exercises/06_udp_dns.py` และหนังสือ: TCPIP หัวข้อ 10.2 หน้า 474, หัวข้อ 10.3 หน้า 475 |
| Datagram หายแล้วผู้ส่งไม่รู้ และข้อความมาเป็นก้อนตามขนาดที่ส่ง | รัน: `exercises/06_udp_dns.py` |
| Resolver เดินจาก Root, TLD ถึง Authoritative ด้วย Referral และ Glue | รัน และหนังสือ: TCPIP หัวข้อ 11.3 หน้า 516, หัวข้อ 11.5 หน้า 518 |
