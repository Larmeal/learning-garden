## Container ก็คือ Network Namespace ที่ต่อสายเข้า Bridge

ตอนเรารัน `docker run` เราไม่ได้อุปกรณ์ Network ชิ้นใหม่มาเลย สิ่งที่ Docker ทำคือสั่ง Kernel ของ Linux ให้ทำเครือข่ายเล็ก ๆ ให้ Container แต่ละตัว ซึ่งทำได้ด้วยคำสั่งสั้น ๆ ที่เราพิมพ์เองได้ หนังสือ Networking and Kubernetes ไล่ขั้นตอนไว้สิบข้อ ตั้งแต่สร้าง Network Namespace, สร้าง Veth Pair (สายเสมือนที่มีสองปลาย), ย้ายปลายหนึ่งเข้า Namespace ใหม่, ตั้งที่อยู่, ไปจนถึงต่อปลายที่เหลือเข้ากับ Bridge (หนังสือ: Networking and Kubernetes บทที่ 3 หน้า 106 ซึ่งมีหัวข้อ Setting Up Namespaces)

เรามาลองทำตามกัน ในแบบฝึก (รัน: `exercises/13_proxies_containers.py`) เราสร้าง Host หนึ่งตัวที่มี Bridge ชื่อ `br0` ที่อยู่ `10.244.0.1/24` แล้วสร้าง "Container" สองตัวคือ k1 กับ k2 แต่ละตัวเป็น Network Namespace ที่มีสาย Veth เส้นเดียวต่อเข้า Bridge พอสั่งดู Bridge จะเห็นสองพอร์ต

```text
341: vh1@br0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding
342: vh2@br0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding
```

ถ้าเข้าไปดูข้างใน k1 จะเห็นคอมพิวเตอร์ที่เล็กมาก มีการ์ดเครือข่ายใบเดียวชื่อ `eth0` ที่อยู่ `10.244.0.2/24` และมี Default Route ผ่าน `10.244.0.1` ซึ่งก็คือ Bridge นั่นเอง

```text
default via 10.244.0.1 dev eth0
10.244.0.0/24 dev eth0 proto kernel scope link src 10.244.0.2
```

สังเกตว่าตารางนี้หน้าตาเหมือนตาราง Routing ที่เราเห็นใน[บท 4](/networking/ip-routing/) ทุกอย่าง ดังนั้นสิ่งที่ Container ใช้ก็คือกฎเดิมของ IP และ Ethernet ที่เรารู้อยู่แล้ว ต่างกันแค่การ์ดเครือข่ายเป็นของเสมือน (รัน)

</Step>

## Container คุยกันผ่าน Bridge โดยไม่ผ่าน Router

k1 ส่ง Ping ไปหา k2 (`10.244.0.3`) ผลคือถึงครบทุกตัว และค่า TTL ที่ได้กลับมาเป็น 64 (รัน) ค่านี้บอกเรื่องสำคัญข้อหนึ่ง จาก[บท 4](/networking/ip-routing/) เรารู้ว่า Router ทุกตัวลด TTL ลงหนึ่งตอนส่งต่อ ถ้า TTL ยังเป็น 64 เท่าตอนส่ง แปลว่า Packet ไม่ได้ข้าม Router เลย มันวิ่งอยู่ใน Layer 2 อย่างเดียว

เหตุผลคือ k1 กับ k2 อยู่ในซับเน็ต `10.244.0.0/24` เดียวกัน k1 จึงถาม MAC ของ k2 ด้วย ARP ได้เลย ตาราง Neighbour ของ k1 จึงมีบรรทัด `10.244.0.3 lladdr ... REACHABLE` (รัน) แล้ว Bridge ทำหน้าที่เป็น Switch ที่เราเห็นใน[บท 3](/networking/link-layer/) คือดู MAC ปลายทางแล้วส่งออกพอร์ตที่ถูกต้อง

เรื่องนี้ตอบคำถามที่คนมักสงสัยตอนใช้ Docker Compose ว่า ทำไม Container สองตัวในเครือข่ายเดียวกันคุยกันได้โดยไม่ต้องตั้งอะไรเลย ก็เพราะมันเป็นแค่คอมพิวเตอร์สองตัวที่เสียบ Switch ตัวเดียวกัน ส่วนเรื่องที่ชื่อ `k2` ถูกแปลงเป็นที่อยู่ได้ เป็นหน้าที่ของ DNS ภายในที่ Docker ใส่ให้ ซึ่งเราไม่ได้ลองในแบบฝึกนี้ (ไม่ได้รัน)

</Step>

## ออกไปข้างนอก: Host แก้ที่อยู่ต้นทางให้

ทีนี้ให้ k1 เรียก Server ข้างนอกที่ `10.0.2.2` ที่อยู่ `10.244.0.2` ของ k1 เป็นที่อยู่ส่วนตัวที่ใช้ได้แค่ในซับเน็ตของ Bridge ดังนั้น k1 จึงส่ง Packet ไปให้ Gateway คือ Host แล้ว Host ส่งต่อเหมือน Router ทั่วไป สิ่งที่เพิ่มเข้ามาคือกฎข้อเดียวของ Iptables

```text
iptables -t nat -A POSTROUTING -s 10.244.0.0/24 ! -o br0 -j MASQUERADE
```

กฎนี้บอกว่า Packet ที่มาจาก `10.244.0.0/24` และกำลังจะออกทางอื่นที่ไม่ใช่ `br0` ให้เขียนที่อยู่ต้นทางทับเป็นที่อยู่ของสายขาออก หนังสือเล่าไว้ว่าใน Kubernetes เรื่องนี้ทำให้ Pod ใช้ที่อยู่ของ Node ได้ ทั้งที่ Pod มีที่อยู่ส่วนตัวของตัวเอง (หนังสือ: Networking and Kubernetes บทที่ 2 หน้า 74)

ในแบบฝึกเราจับ Packet ที่ฝั่ง Server และพบว่าที่อยู่ต้นทางของ SYN คือ `10.0.2.1` ซึ่งเป็นที่อยู่ของ Host Server ไม่เคยเห็น `10.244.0.2` เลยสักตัว (รัน) Host จำการแปลงนี้ไว้ในตาราง Conntrack ด้วยบรรทัดเดียวที่มีทั้งสองมุมมอง

```text
tcp ... src=10.244.0.2 dst=10.0.2.2 sport=36632 dport=8080
        src=10.0.2.2   dst=10.0.2.1 sport=8080  dport=36632
```

บรรทัดแรกคือสิ่งที่ k1 ส่ง บรรทัดที่สองคือสิ่งที่ Server ตอบ ซึ่งจ่าหน้าไปที่ `10.0.2.1` พอคำตอบกลับมา Host เปิดตาราง แปลงปลายทางกลับเป็น `10.244.0.2` แล้วส่งเข้า Bridge ทั้งหมดนี้คือ NAT แบบเดียวกับที่ Router บ้านเราใช้ใน[บท 5](/networking/nat-dhcp/) เลย

มีข้อสังเกตที่ตรงกับความเข้าใจที่คนมักมี คือเรามักเชื่อว่าต้องมี NAT ไม่งั้น Container ออกไปข้างนอกไม่ได้ แต่ในแบบฝึกของเรา การเรียกก่อนเพิ่มกฎ MASQUERADE ก็สำเร็จเหมือนกัน เพราะ Server ในแบบฝึกมี Default Route ที่ชี้กลับมาที่ Host (รัน) ส่วนในเครือข่ายจริงที่ไม่รู้จักซับเน็ต `10.244.0.0/24` คำตอบจะกลับมาไม่ได้ และกฎนี้ก็เป็นสิ่งที่ทำให้ใช้งานได้ ซึ่งเราไม่ได้ลองเอง (ไม่ได้รัน) สิ่งที่แบบฝึกยืนยันได้คือ NAT ทำให้ Server ข้างนอกเห็นที่อยู่ของ Host แทนที่อยู่ของ Container

</Step>

## เข้ามาข้างใน: Port ที่ Publish คือกฎ DNAT

ขากลับกันบ้าง ถ้าเราอยากให้คนข้างนอกเรียก k1 ได้ สิ่งที่ `docker run -p 8080:80` ทำคือเพิ่มกฎ DNAT ที่ Host

```text
iptables -t nat -A PREROUTING -d 10.0.1.1/32 -p tcp --dport 8080 -j DNAT --to-destination 10.244.0.2:80
```

กฎนี้ทำงานกับ Packet ที่เพิ่งเข้ามา (PREROUTING) ถ้าปลายทางคือ `10.0.1.1:8080` ให้เขียนปลายทางใหม่เป็น `10.244.0.2:80` แล้ว Routing ตัดสินใจต่อจากที่อยู่ใหม่ ในแบบฝึกเราจับ SYN ของ Client สองที่ ที่สายของ Client เป็น `10.0.1.2 → 10.0.1.1:8080` ส่วนที่ Bridge ของ Host เป็น `10.0.1.2 → 10.244.0.2:80` ต้นทางไม่ถูกแตะเลย (รัน) คำตอบมาจาก k1 จริง

กดเล่น Lab แล้วสลับสามเส้นทางดู จะเห็นว่าทั้งสามเส้นทางต่างกันแค่จุดที่ที่อยู่ถูกเขียนใหม่ คือไม่มีเลย (Container ถึง Container), ที่อยู่ต้นทางตอนออก (MASQUERADE) และที่อยู่ปลายทางตอนเข้า (DNAT)

## Load Balancer ระดับ Connection: ที่อยู่ที่ไม่มีคอมพิวเตอร์ตัวไหนเป็นเจ้าของ

ถ้าเรามี k1 กับ k2 ที่ให้บริการเหมือนกัน เราจะให้ Client ใช้ที่อยู่เดียว แล้วกระจายไปทั้งสองตัวได้อย่างไร วิธีที่ Kubernetes ใช้ใน `kube-proxy` โหมด Iptables คือเพิ่มกฎ DNAT หลายข้อ ที่เลือก Backend ตามสัดส่วน หนังสืออธิบายว่าเทคนิคนี้เรียกว่า Connection Fan-out และเขียนตัวอย่างโดยใช้ `--mode random --probability 0.5` ในกฎแรก เพื่อไม่ให้ทุก Connection ไปลงที่ Backend แรก (หนังสือ: Networking and Kubernetes บทที่ 2 หน้า 74)

ในแบบฝึกเราใช้ `--mode nth --every 2` แทน Random เพื่อให้ผลสลับกันตรง ๆ และตรวจด้วย Assert ได้ (รัน)

```text
-A PREROUTING -d 10.96.0.10/32 -p tcp --dport 80 -m statistic --mode nth --every 2 --packet 0 -j DNAT --to-destination 10.244.0.2:80
-A PREROUTING -d 10.96.0.10/32 -p tcp --dport 80 -j DNAT --to-destination 10.244.0.3:80
```

ที่อยู่ `10.96.0.10` ไม่มีคอมพิวเตอร์ตัวไหนเป็นเจ้าของ มันมีอยู่แค่ในกฎสองข้อนี้ (รัน) ลองดูว่า Client ส่ง 8 คำขอ โดยเปิด Connection ใหม่ทุกคำขอ ใครเป็นคนตอบ ผลคือ `k1, k2, k1, k2, k1, k2, k1, k2` สลับกันพอดี (รัน) แต่ถ้า Client ใช้ Connection เดียวส่ง 8 คำขอ ทุกคำขอไปที่ k1 หมด (รัน)

เหตุผลคือกฎ DNAT ตัดสินใจครั้งเดียวตอน SYN แล้ว Conntrack จำไว้ตลอดอายุ Connection สิ่งที่ Load Balancer แบบนี้เห็นคือ Connection ไม่ใช่คำขอ ข้างในมันไม่รู้ด้วยซ้ำว่าเป็น HTTP หนังสือก็เตือนเรื่องนี้ไว้ว่า DNAT Fan-out ไม่มี Feedback เรื่องภาระของ Backend และจะส่งคำขอทั้งหมดบน Connection เดียวไป Backend เดิมเสมอ ตัวอย่างที่หนังสือยกคือ gRPC ที่ใช้ Connection HTTP/2 ซ้ำ ทำให้เมื่อเพิ่ม Replica ใหม่ Client เดิมก็ยังติดอยู่กับสองตัวแรก (หนังสือ: Networking and Kubernetes บทที่ 2 หน้า 75, บทที่ 4 หน้า 162)

อีกเรื่องที่ควรรู้คือ Backend เห็นที่อยู่ของ Client ตัวจริง ในแบบฝึก k2 ที่ตอบคำขอรายงานว่าเพียร์คือ `10.0.1.2` และไม่มีหัวข้อ X-Forwarded-For เลย (รัน) เพราะ Load Balancer แค่เปลี่ยนที่อยู่ปลายทางของ Packet ไม่ได้แตะข้อมูลข้างใน

</Step>

## Reverse Proxy: เปิด Connection ใหม่เอง และกระจายระดับคำขอ

อีกแบบคือไม่แก้ที่อยู่ของ Packet แต่ให้โปรแกรมตัวหนึ่งรับ Connection ของ Client ไว้เอง อ่านคำขอ HTTP แล้วเปิด Connection ของมันเองไปหา Backend ซึ่งก็คือสิ่งที่ Nginx, HAProxy และ Envoy ทำ เราเขียน Reverse Proxy เล็ก ๆ ด้วย `asyncio` ของ Python รันที่ Host พอร์ต 9000 ให้รับคำขอ เลือก Backend แบบหมุนเวียนทีละคำขอ เติมหัวข้อ `X-Forwarded-For` แล้วส่งคำตอบกลับ (รัน)

ผลต่างจากข้างบนเห็นได้ชัด ส่ง 8 คำขอบน Connection เดียวผ่าน Proxy คำตอบยังสลับ `k1, k2, k1, k2, ...` เพราะ Proxy อ่านเป็นคำขอและเลือก Backend ใหม่ทุกครั้ง (รัน) นี่คือการกระจายระดับ Layer 7 ซึ่งแก้ปัญหา gRPC ข้างบนได้ เพราะ Proxy เข้าใจว่า HTTP/2 มีหลายคำขอบนสายเดียว (ตัว Proxy ของเราเป็น HTTP/1.1 ไม่ได้ลอง HTTP/2 จริง ไม่ได้รัน)

ราคาที่ต้องจ่ายคือ Backend ไม่เห็น Client ตัวจริงอีกต่อไป เพราะ Connection ที่มาถึง Backend เป็นของ Proxy ในแบบฝึก Backend รายงานว่าเพียร์คือ `10.244.0.1` ซึ่งเป็นที่อยู่ของ Bridge บน Host ที่ Proxy ใช้ต่อออกมา ส่วนที่อยู่ของ Client ตัวจริง `10.0.1.2` หลงเหลืออยู่แค่ในหัวข้อ `X-Forwarded-For` ที่ Proxy เพิ่มให้ (รัน) นี่คือเหตุผลที่โปรแกรม Backend ต้องรู้ว่าตัวเองอยู่หลัง Proxy และอ่านที่อยู่จากหัวข้อนี้ และต้องเชื่อหัวข้อนี้เฉพาะเมื่อมาจาก Proxy ของเราเอง เพราะ Client จะส่งหัวข้อปลอมมาเองก็ได้ (ผู้เขียน)

## Backend ตายแล้วใครรู้

ปิดท้ายด้วยการทดลองที่สำคัญที่สุดข้อหนึ่ง เราฆ่าโปรเซสของ k2 แล้วส่ง 8 คำขอใหม่ เปิด Connection ใหม่ทุกคำขอ

```text
Layer 4 (iptables): k1, ECONNREFUSED, k1, ECONNREFUSED, k1, ECONNREFUSED, k1, ECONNREFUSED
Layer 7 (Proxy):    k1, k1, k1, k1, k1, k1, k1, k1
```

Load Balancer ที่เป็นกฎ Iptables ไม่รู้เลยว่า k2 ตายแล้ว มันยังส่ง Connection ทุกข้อที่สองไปที่นั่น และ Client ได้ปฏิเสธการเชื่อมต่อ (ECONNREFUSED) กลับมาตรง ๆ ส่วน Proxy สังเกตเห็นว่า Connection ถูกปฏิเสธ จึงลอง Backend ตัวถัดไปให้เองในคำขอเดียวกัน ทั้ง 8 คำขอได้คำตอบ (รัน) ฝั่ง Client จึงไม่รู้เลยว่ามี Backend ตัวหนึ่งตายอยู่

ข้อควรระวังคือสิ่งที่เราทดลองเป็นการตายแบบง่ายที่สุด โปรเซสถูกฆ่า แต่ Namespace ยังอยู่ จึงมี RST ตอบกลับมาทันที ถ้าคอมพิวเตอร์ดับหรือสายขาดจริง Backend จะเงียบ Client ต้องรอ Timeout และ SYN ส่งซ้ำตามที่เรารู้จากบท[การเชื่อมต่อ TCP](/networking/tcp-connections/) ซึ่งนานกว่ามาก ผลของกรณีนั้นเราไม่ได้รัน (ไม่ได้รัน) และ Proxy ในแบบฝึกก็เป็นโค้ดสั้น ๆ ที่ลองต่อ Backend ตัวถัดไปเมื่อถูกปฏิเสธเท่านั้น Proxy ตัวจริงมี Health Check และ Timeout ที่ละเอียดกว่านี้มาก ส่วนใน Kubernetes เรื่องนี้ถูกจัดการด้วย Readiness Probe ที่เอา Pod ที่ยังไม่พร้อมออกจากกฎ ซึ่งเราไม่ได้ทดลอง (ไม่ได้รัน)

<Callout type="note" title="ควรเลือกแบบไหน">
