## ทำไมต้องรู้จัก Plugin เหล่านี้

ในบท [Pytest ทำงานอย่างไร](/pytest/how-pytest-runs/#ทุกอย่างเป็น-plugin) เราเห็นแล้วว่า Pytest มี Plugin ในตัว 30 ตัว ซึ่งหลายตัวเราใช้ทุกวันโดยไม่รู้ตัว เช่น ตอน Test ล้มแล้วเห็นข้อความที่ Test พิมพ์ออกมา นั่นคือ `capture` และตอนรัน `--lf` นั่นคือ `cacheprovider` คราวนี้เราจะเปิดดูห้าตัวที่มีเรื่องให้ตัดสินใจมากที่สุด

ผลทุกอย่างในหน้านี้มาจาก `internals/10_builtin_plugins.py` ซึ่งสร้างโปรเจกต์ชั่วคราวขึ้นมาทีละเรื่อง แล้วรัน Pytest ใน Interpreter ใหม่ (รัน: `internals/10_builtin_plugins.py`)

## Capture: ทำไม Print ถึงหายไปตอน Test ผ่าน

Pytest ดักสิ่งที่ถูกเขียนไป Stdout และ Stderr ระหว่างรัน Test และแสดงเฉพาะตอน Test ล้ม (Source: `_pytest/capture.py`) โปรเจกต์แบบฝึกมี Test ที่ `print("hello from print")` แล้ว `assert False` เมื่อรันจะได้ผลดังนี้ (รัน)

```text
------------------------------ Captured stdout call ------------------------------
hello from print
------------------------------ Captured stderr call ------------------------------
to stderr
```

ส่วน Test ที่ `print` แล้วผ่านจะไม่แสดงอะไรเลย ต้องใส่ `-s` (หรือ `--capture=no`) ถึงจะเห็น

มีสองระดับของการดัก (Source: `FDCapture` กับ `SysCapture`)

- ระดับ `sys` ดักเฉพาะที่เขียนผ่าน `sys.stdout` และ `sys.stderr` ซึ่งก็คือ `print` ปกติ
- ระดับ `fd` (ค่าเริ่มต้น) จะดักที่ File Descriptor 1 และ 2 ด้วย จึงจับสิ่งที่โค้ด C หรือ Subprocess เขียนได้

ความต่างนี้เห็นชัดใน Fixture สองตัว คือ `capsys` ที่ดักระดับ Sys ส่วน `capfd` ดักระดับ fd ในแบบฝึกมี Test ที่เขียนด้วย `os.write(1, b"...")` ตรง ๆ ซึ่ง `capfd.readouterr().out` เห็นข้อความ แต่ `capsys.readouterr().out` ได้สตริงว่าง

Fixture `capsys` และ `capfd` ทั้งคู่มี `readouterr()` ที่คืน `(out, err)` และจะล้างตัวดักทุกครั้งที่เรียก

</Step>

## Logging: ระดับเริ่มต้นที่ทำให้ INFO หาย

Plugin `logging` ดัก Log ของ Test แล้วแสดงใน Section `Captured log call` ลองดูผลของโปรเจกต์ที่ Log ทั้ง `info` และ `warning` แล้วล้ม (รัน)

```text
------------------------------ Captured log call -------------------------------
WARNING  shop:test_log.py:7 this is a warning
```

จะเห็นว่าไม่มีบรรทัด INFO เพราะ Logger ราก (Root Logger) ของ Python มีระดับเริ่มต้นเป็น WARNING และ Pytest ไม่ได้เปลี่ยนมัน ซึ่งเราปรับได้สองแบบ

- ใช้ `--log-level=INFO` หรือ `log_level = INFO` ใน Config เพื่อให้ดักถึงระดับนั้น
- ใช้ Live Log ด้วย `log_cli = true` และ `log_cli_level = INFO` เพื่อแสดง Log ขณะ Test รันแทนที่จะรอตอนล้ม ในแบบฝึกได้ `live log call` พร้อมบรรทัด `INFO     shop:test_log.py:6 this is info`

ถ้าต้องการเช็ก Log ใน Test ให้ใช้ `caplog` (บท [แยก Test](/pytest/isolation/#อ่านสิ่งที่โค้ดพิมพ์และ-log)) ซึ่งมี `messages`, `records`, `text` และ `at_level(...)`

</Step>

## Warnings: สรุปท้ายรายงาน

Plugin `warnings` เก็บ Warning ที่เกิดระหว่างรัน Test และพิมพ์สรุปท้ายรายงานแทนที่จะแสดงทันที (Source: `_pytest/warnings.py`) ในโปรเจกต์ที่ฟังก์ชัน `noisy()` ออก `DeprecationWarning("old api")` เราจะได้ส่วน `warnings summary` และข้อความ `DeprecationWarning: old api` (รัน)

เราควบคุมได้สามระดับ

| ระดับ | วิธี | ผลที่ยืนยัน |
|---|---|---|
| Test เดียว | `@pytest.mark.filterwarnings("error")` | Warning กลายเป็น Exception ทำให้ Test นั้นล้ม |
| Test เดียว | `@pytest.mark.filterwarnings("ignore::DeprecationWarning")` | Warning หายไปจากสรุป |
| ทั้งโปรเจกต์ | `-o filterwarnings=ignore::DeprecationWarning` (หรือ `filterwarnings` ใน Config) | ไม่มีส่วน `warnings summary` เลย |

แนวปฏิบัติที่ได้ผลคือตั้ง `filterwarnings = ["error"]` ใน Config ให้ Warning ทุกตัวทำให้ล้ม แล้วยกเว้นเฉพาะตัวที่เรารู้แล้วทีละตัว ด้วยวิธีนี้การเลื่อนอัปเกรดไลบรารีที่ประกาศเลิกใช้ฟังก์ชันจะถูกจับได้ก่อนที่มันจะพังจริง (ผู้เขียน)

</Step>

## Cache: Pytest จำอะไรไว้

Plugin `cacheprovider` เก็บผลไว้ในโฟลเดอร์ `.pytest_cache` ข้างโปรเจกต์ (Source: `_pytest/cacheprovider.py`) หลังรันโปรเจกต์ที่มี `test_b` ล้ม จะได้ไฟล์ดังนี้ (รัน)

```text
.gitignore   CACHEDIR.TAG   README.md   v/cache/lastfailed   v/cache/nodeids
```

ไฟล์ `v/cache/lastfailed` มี `{"test_cache.py::test_b": true}` อยู่ข้างใน และโฟลเดอร์นี้มีไฟล์ `.gitignore` ของตัวเอง จึงไม่ปนเข้า Git ส่วนตัวเลือกที่ใช้ข้อมูลนี้มีดังนี้

| Option | ทำอะไร | ผลที่ยืนยัน |
|---|---|---|
| `--lf` | รันเฉพาะที่ล้มรอบก่อน | `1 failed` และไม่มี Test อื่น |
| `--ff` | รันที่ล้มก่อน แล้วตามด้วยที่เหลือ | ลำดับ `test_b`, `test_a`, `test_c` และข้อความ `run-last-failure: rerun previous 1 failure first` |
| `--sw` (Stepwise) | หยุดที่ตัวที่ล้ม รอบหน้าเริ่มต่อจากตรงนั้น | `Interrupted: Test failed, continuing from this test next run.` สรุป `1 failed, 1 passed` |
| `--nf` | รัน Test ใหม่ก่อน | |
| `--cache-show` | แสดงเนื้อหา Cache | พิมพ์ `cachedir:` |

Plugin ที่เราเขียนเองก็ใช้ Cache ได้ผ่าน Fixture `cache` (`cache.get(key, default)` และ `cache.set(key, value)`) เพื่อเก็บข้อมูลข้ามรอบ เช่น ลำดับ Test ที่ช้า

</Step>

## JUnit XML: ส่งผลให้ CI

`--junitxml=report.xml` จะเขียนผลเป็นไฟล์ XML ซึ่ง CI ส่วนใหญ่อ่านเป็น (Source: `_pytest/junitxml.py`) ในโปรเจกต์ที่มี 8 Test และล้มสองตัว เราจะได้ `<testsuite>` ที่มี `tests="8"`, `failures="2"`, `errors="0"` (รัน) โดยแต่ละ Test จะเป็น `<testcase classname=... name=...>` และตัวที่ล้มจะมี `<failure>` อยู่ข้างใน ในแบบฝึกชื่อที่ล้มตรงกับ `test_print_and_fail` และ `test_the_mark_turns_it_into_an_error`

ถ้าเราเติม Property ในรายงานเอง (`report.user_properties`) ค่านั้นก็จะไปอยู่ใน XML ด้วย ซึ่งเป็นทางส่งข้อมูลเสริมให้ CI ([บท 14](/pytest/plugins/))

</Step>

## Subtests: หลายผลใน Test เดียว

ใน Pytest 9.2.0 มี Fixture `subtests` ที่ช่วยให้รายงานแต่ละรอบของ Loop แยกกันได้ (Source: `_pytest/subtests.py`)

```python
def test_each_row(subtests):
    for n in range(4):
        with subtests.test(msg="row", n=n):
            assert n != 2
```

เมื่อรันจะได้ผลดังนี้ (รัน)

```text
uuuuF
SUBFAILED[row] (n=2) test_sub.py::test_each_row - assert 2 != 2
FAILED test_sub.py::test_each_row - contains 1 failed subtest
2 failed, 3 subtests passed in 0.05s
```

รอบที่ล้มไม่ได้หยุด Loop อีกสามรอบยังรันและผ่าน (`u` คือ Subtest ที่ผ่าน) ส่วนตัว Test ถูกนับเป็นล้มเพราะมี Subtest ล้ม และรอบที่ล้มแสดง `(n=2)` ตามที่เราส่งเข้า `subtests.test` ถ้าเทียบกับ `parametrize` ([บท 4](/pytest/parametrize/#test-เดียว-หลายค่า)) ให้ใช้ Parametrize เมื่อรู้ค่าก่อนรัน และใช้ Subtests เมื่อค่ามาจากข้อมูลที่อ่านตอนรัน เช่น แถวในไฟล์

<Callout type="try" title="ลองทำใน Repo นี้">
ลองรัน `uv run python internals/10_builtin_plugins.py` แล้วเปลี่ยน `test_logs_and_fails` ให้ Log ที่ระดับ `DEBUG` ด้วย จากนั้นลอง `--log-level=DEBUG` แล้วดู Section `Captured log call` และเพิ่ม `-rA` เพื่อดูสรุปของทุก Test รวมข้อความที่ดักไว้ของ Test ที่ผ่านด้วย
</Callout>

## เช็กตัวเอง

- Test ผ่านและมี `print` ข้างใน ทำไมถึงไม่เห็นข้อความ และมีสองวิธีที่จะเห็น
- ทำไม Log ระดับ INFO ไม่ขึ้นใน `Captured log call` ทั้งที่ Test เรียก `log.info(...)`
- ทีมอยากให้ Warning ทุกตัวทำให้ CI แดง ตั้งค่าอย่างไร และจะยกเว้นตัวหนึ่งอย่างไร

</Step>
