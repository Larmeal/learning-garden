## ทำไมต้องรู้จัก Plugin เหล่านี้

บท [Pytest ทำงานอย่างไร](/pytest/how-pytest-runs/) เห็นว่า pytest มี plugin ในตัว 30 ตัว หลายตัวคือสิ่งที่เราใช้ทุกวันโดยไม่รู้ตัว: ตอน test ล้มแล้วเห็นข้อความที่ test พิมพ์ นั่นคือ `capture` ตอนรัน `--lf` นั่นคือ `cacheprovider` บทนี้เปิดดูห้าตัวที่มีเรื่องให้ตัดสินใจมากที่สุด

ผลทุกอย่างมาจาก `internals/10_builtin_plugins.py` ที่สร้างโปรเจกต์ชั่วคราวทีละเรื่องแล้วรัน pytest ใน interpreter ใหม่ (รัน: `internals/10_builtin_plugins.py`)

</Step>

## Capture: ทำไม Print ถึงหายไปตอน Test ผ่าน

pytest ดักสิ่งที่ถูกเขียนไป stdout และ stderr ระหว่างรัน test และแสดงเฉพาะตอน test ล้ม (source: `_pytest/capture.py`) โปรเจกต์แบบฝึกมี test ที่ `print("hello from print")` แล้ว `assert False` ผลคือ (รัน)

```text
------------------------------ Captured stdout call ------------------------------
hello from print
------------------------------ Captured stderr call ------------------------------
to stderr
```

test ที่ `print` แล้วผ่านไม่แสดงอะไร ใส่ `-s` (หรือ `--capture=no`) ถึงจะเห็น

มีสองระดับของการดัก (source: `FDCapture` กับ `SysCapture`)

- **`sys`** ดักเฉพาะที่เขียนผ่าน `sys.stdout` และ `sys.stderr` ซึ่งคือ `print` ปกติ
- **`fd`** (ค่าเริ่มต้น) ดักที่ file descriptor 1 และ 2 ด้วย จึงจับสิ่งที่โค้ด C หรือ subprocess เขียนได้

ความต่างนี้เห็นชัดใน fixture สองตัว `capsys` ดักระดับ sys ส่วน `capfd` ดักระดับ fd แบบฝึกมี test ที่เขียนด้วย `os.write(1, b"...")` ตรงๆ `capfd.readouterr().out` เห็นข้อความ แต่ `capsys.readouterr().out` ได้สตริงว่าง

fixture `capsys` และ `capfd` ให้ `readouterr()` ที่คืน `(out, err)` และล้างตัวดักทุกครั้งที่เรียก

</Step>

## Logging: ระดับเริ่มต้นที่ทำให้ INFO หาย

plugin `logging` ดัก log ของ test ให้ใน section `Captured log call` ผลของโปรเจกต์ที่ log ทั้ง `info` และ `warning` แล้วล้ม (รัน)

```text
------------------------------ Captured log call -------------------------------
WARNING  shop:test_log.py:7 this is a warning
```

ไม่มีบรรทัด INFO เพราะ logger ราก (root logger) ของ Python มีระดับเริ่มต้นเป็น WARNING และ pytest ไม่เปลี่ยนมัน ปรับได้สองแบบ

- `--log-level=INFO` หรือ `log_level = INFO` ใน config เพื่อให้ดักถึงระดับนั้น
- **live log** ด้วย `log_cli = true` และ `log_cli_level = INFO` แสดง log ขณะ test รันแทนที่จะรอตอนล้ม แบบฝึกได้ `live log call` พร้อมบรรทัด `INFO     shop:test_log.py:6 this is info`

เมื่อต้องการเช็ก log ใน test ใช้ `caplog` (บท [แยก Test](/pytest/isolation/#อ่านสิ่งที่โค้ดพิมพ์และ-log)) ซึ่งมี `messages`, `records`, `text` และ `at_level(...)`

</Step>

## Warnings: สรุปท้ายรายงาน

plugin `warnings` เก็บ warning ที่เกิดระหว่างรัน test และพิมพ์สรุปท้ายรายงานแทนที่จะแสดงทันที (source: `_pytest/warnings.py`) โปรเจกต์ที่ฟังก์ชัน `noisy()` ออก `DeprecationWarning("old api")` ให้ส่วน `warnings summary` และข้อความ `DeprecationWarning: old api` (รัน)

ควบคุมได้สามระดับ

| ระดับ | วิธี | ผลที่ยืนยัน |
|---|---|---|
| test เดียว | `@pytest.mark.filterwarnings("error")` | warning กลายเป็น exception: test นั้นล้ม |
| test เดียว | `@pytest.mark.filterwarnings("ignore::DeprecationWarning")` | warning หายไปจากสรุป |
| ทั้งโปรเจกต์ | `-o filterwarnings=ignore::DeprecationWarning` (หรือ `filterwarnings` ใน config) | ไม่มีส่วน `warnings summary` เลย |

แนวปฏิบัติที่ได้ผลคือตั้ง `filterwarnings = ["error"]` ใน config ให้ warning ทุกตัวเป็นความล้ม แล้วยกเว้นเฉพาะตัวที่รู้แล้วทีละตัว การเลื่อนอัปเกรดไลบรารีที่ประกาศเลิกใช้ฟังก์ชันจะถูกจับก่อนพังจริง (ผู้เขียน)

</Step>

## Cache: Pytest จำอะไรไว้

plugin `cacheprovider` เก็บผลไว้ในโฟลเดอร์ `.pytest_cache` ข้างโปรเจกต์ (source: `_pytest/cacheprovider.py`) หลังรันโปรเจกต์ที่มี `test_b` ล้ม ไฟล์ที่เกิดคือ (รัน)

```text
.gitignore   CACHEDIR.TAG   README.md   v/cache/lastfailed   v/cache/nodeids
```

`v/cache/lastfailed` มี `{"test_cache.py::test_b": true}` มีไฟล์ `.gitignore` ในโฟลเดอร์เองจึงไม่ปนเข้า git ตัวเลือกที่ใช้ข้อมูลนี้

| option | ทำอะไร | ผลที่ยืนยัน |
|---|---|---|
| `--lf` | รันเฉพาะที่ล้มรอบก่อน | `1 failed` และไม่มี test อื่น |
| `--ff` | รันที่ล้มก่อน แล้วตามด้วยที่เหลือ | ลำดับ `test_b`, `test_a`, `test_c` และข้อความ `run-last-failure: rerun previous 1 failure first` |
| `--sw` (stepwise) | หยุดที่ตัวที่ล้ม รอบหน้าเริ่มต่อจากตรงนั้น | `Interrupted: Test failed, continuing from this test next run.` สรุป `1 failed, 1 passed` |
| `--nf` | รัน test ใหม่ก่อน | |
| `--cache-show` | แสดงเนื้อหา cache | พิมพ์ `cachedir:` |

cache ของ plugin ของเราใช้ได้ผ่าน fixture `cache` (`cache.get(key, default)` และ `cache.set(key, value)`) สำหรับเก็บข้อมูลข้ามรอบ เช่น ลำดับ test ที่ช้า

</Step>

## JUnit XML: ส่งผลให้ CI

`--junitxml=report.xml` เขียนผลเป็นไฟล์ XML ที่ CI ส่วนใหญ่อ่านเป็น (source: `_pytest/junitxml.py`) โปรเจกต์ที่มี 8 test สองตัวล้ม ให้ `<testsuite>` ที่มี `tests="8"`, `failures="2"`, `errors="0"` (รัน) แต่ละ test เป็น `<testcase classname=... name=...>` และตัวที่ล้มมี `<failure>` ข้างใน ในแบบฝึกชื่อที่ล้มตรงกับ `test_print_and_fail` และ `test_the_mark_turns_it_into_an_error`

การเติม property ในรายงานของเราเอง (`report.user_properties`) จะไปอยู่ใน XML ด้วย ซึ่งเป็นทางส่งข้อมูลเสริมให้ CI ([บท 14](/pytest/plugins/))

</Step>

## Subtests: หลายผลใน Test เดียว

ใน pytest 9.2.0 มี fixture `subtests` ที่ให้รายงานแต่ละรอบของ loop แยกกัน (source: `_pytest/subtests.py`)

```python
def test_each_row(subtests):
    for n in range(4):
        with subtests.test(msg="row", n=n):
            assert n != 2
```

ผลคือ (รัน)

```text
uuuuF
SUBFAILED[row] (n=2) test_sub.py::test_each_row - assert 2 != 2
FAILED test_sub.py::test_each_row - contains 1 failed subtest
2 failed, 3 subtests passed in 0.05s
```

รอบที่ล้มไม่หยุด loop: อีกสามรอบยังรันและผ่าน (`u` คือ subtest ที่ผ่าน) ตัว test ถูกนับเป็นล้มเพราะมี subtest ล้ม และรอบที่ล้มแสดง `(n=2)` ตามที่ส่งเข้า `subtests.test` เทียบกับ `parametrize` ([บท 4](/pytest/parametrize/)): ใช้ parametrize เมื่อค่ารู้ก่อนรัน และใช้ subtests เมื่อค่ามาจากข้อมูลที่อ่านตอนรัน เช่น แถวในไฟล์

<Callout type="try" title="ลองทำใน repo นี้">
รัน `uv run python internals/10_builtin_plugins.py` แล้วเปลี่ยน `test_logs_and_fails` ให้ log ที่ระดับ `DEBUG` ด้วย แล้วลอง `--log-level=DEBUG` ดู section `Captured log call` จากนั้นเพิ่ม `-rA` เพื่อดูสรุปของทุก test รวมข้อความที่ดักไว้ของ test ที่ผ่าน
</Callout>

## เช็กตัวเอง

- test ผ่านและมี `print` ข้างใน ทำไมถึงไม่เห็นข้อความ และมีสองวิธีที่จะเห็น
- ทำไม log ระดับ INFO ไม่ขึ้นใน `Captured log call` ทั้งที่ test เรียก `log.info(...)`
- ทีมอยากให้ warning ทุกตัวทำให้ CI แดง ตั้งค่าอย่างไร และจะยกเว้นตัวหนึ่งอย่างไร

</Step>
