## Test คือโค้ดที่เช็กโค้ดให้เรา

ลองนึกถึงตะกร้าสินค้า ใส่แอปเปิล 3 ผล ผลละ 10 บาท ยอดรวมควรเป็น 30 เราตรวจด้วยตาได้ครั้งเดียว แต่ถ้าแก้โค้ดอีก 50 ครั้งใน 6 เดือน เราไม่มีทางเปิดดูทุกครั้ง **automated test** คือโค้ดที่ทำการตรวจนี้ให้ทุกครั้งที่สั่ง และบอกว่าอะไรเปลี่ยนไป

Pytest เป็น test runner ของ Python ที่ใช้กันมาก จุดเด่นคือ test เป็นแค่ฟังก์ชันธรรมดากับ `assert` ไม่ต้องสืบทอด class ใดๆ เส้นทางนี้ใช้โค้ดชุดเดียวทุกบท คือ package `shop` (ตะกร้า คูปอง ชำระเงิน) ใน `subjects/pytest/code/src/shop/` ตัวเลขผลรันทุกตัวในบทเรียนมาจากการรันจริงด้วย Pytest 9.2.0 (รัน: `verify.py`)

ติดตั้งและรัน

```bash
uv add --dev pytest      # หรือ pip install pytest
uv run pytest            # หรือ python -m pytest
```

## Test แรก

```python
from shop.cart import Cart


def test_new_cart_is_empty():
    cart = Cart()
    assert cart.is_empty()
    assert cart.total() == 0


def test_add_item_increases_total():
    cart = Cart()
    cart.add("apple", price=10, qty=3)
    assert cart.total() == 30
```

ไม่มีอะไรต้อง import จาก Pytest เลย `assert` คือ assert ธรรมดาของ Python หลัง `assert` เขียนเงื่อนไขที่ให้ผลเป็นจริงหรือเท็จ เช่น `cart.total() == 30` ซึ่งคือคำถามว่า "ยอดรวมของตะกร้าเท่ากับ 30 ไหม" ถ้าคำตอบคือใช่ (True) test ผ่าน ถ้าไม่ใช่ (False) test ล้ม `assert cart.is_empty()` ก็เขียนได้เหมือนกัน เพราะ `is_empty()` คืนค่า True หรือ False อยู่แล้ว นอกจากนั้น test ยังล้มถ้าโค้ดที่เรียกอยู่โยน exception ออกมาก่อนจะถึงบรรทัด `assert` รัน `exercises/01_first_test` ได้ผลดังนี้ (รัน: `exercises/01_first_test`)

```text

exercises/01_first_test/test_cart_basics.py::test_add_item_increases_total PASSED
exercises/01_first_test/test_cart_basics.py::test_adding_the_same_sku_twice_merges_the_lines PASSED
exercises/01_first_test/test_cart_basics.py::TestRemove::test_remove_drops_the_line PASSED
exercises/01_first_test/test_cart_basics.py::TestRemove::test_remove_missing_sku_raises_key_error PASSED
exercises/01_first_test/discount_test.py::test_ten_percent_off_one_hundred PASSED
============================== 6 passed ==============================
```

ชื่อเต็มของ test เช่น `test_cart_basics.py::TestRemove::test_remove_drops_the_line` เรียกว่า **node id** ใช้สั่งรัน test ตัวเดียวได้ ([บท 7](/pytest/project/#เลือกรัน-path-node-id-และ--k))

## Pytest หา Test เจอได้อย่างไร

Pytest ไม่ได้รันทุกไฟล์ มันค้นตามกติกาชื่อ (**discovery**)

| อะไร | ต้องตั้งชื่อ | ตัวอย่างในแบบฝึก |
|---|---|---|
| ไฟล์ | `test_*.py` หรือ `*_test.py` | `test_cart_basics.py`, `discount_test.py` |
| ฟังก์ชัน | ขึ้นต้นด้วย `test` | `test_new_cart_is_empty` |
| class | ขึ้นต้นด้วย `Test` และ method ขึ้นต้นด้วย `test` | `TestRemove.test_remove_drops_the_line` |

ในโฟลเดอร์เดียวกันมีของที่ **ไม่ถูกรัน** สามอย่าง (รัน: `--collect-only` ได้ 6 tests ตรงกับด้านบน)

- `cart_extra.py` ชื่อไฟล์ไม่เข้ากติกา ใน test ข้างในมี `assert 1 == 2` ก็ไม่มีใครรู้
- `make_cart()` เป็น helper ชื่อไม่ขึ้นต้นด้วย `test`
- `check_total_is_ten()` ขึ้นต้นด้วย `check_` ซึ่งก็ไม่ใช่ prefix ของ test

<Callout type="warn" title="ชื่อผิด = test หาย โดยไม่มี error">
ถ้าตั้งชื่อไฟล์เป็น `cart_tests.py` หรือฟังก์ชันเป็น `tets_total` Pytest จะไม่เตือนอะไร ผลคือเขียวเพราะไม่มี test ให้รัน เมื่อเขียน test ใหม่ให้ดูว่าจำนวน test ที่รันเพิ่มขึ้นจริง
</Callout>

ข้อยกเว้นที่ควรรู้: ถ้าระบุไฟล์ตรงๆ บน command line Pytest จะ collect ไฟล์นั้นโดยไม่สนชื่อ `pytest exercises/01_first_test/cart_extra.py` จึงรัน test ในไฟล์นั้นและล้ม 1 ตัว (รัน: `verify.py`)

</Step>

## อ่านสัญลักษณ์ในผลรัน

บรรทัดผลแบบย่อมีหนึ่งตัวอักษรต่อหนึ่ง test

| ตัวอักษร | ความหมาย |
|---|---|
| `.` | ผ่าน |
| `F` | ล้ม (failed): `assert` เป็นเท็จ หรือมี exception ใน test หรือในโค้ดที่ test เรียก |
| `E` | error: ปัญหาอยู่ **นอกตัว test** เช่น fixture ระเบิดตอน setup ([บท 3](/pytest/fixtures/)) |
| `s` / `x` | skip / xfail ([บท 5](/pytest/markers/#skip-และ-skipif-ไม่รัน)) |

`demos/01_failures` จงใจให้ล้มสามแบบ ผลคือ `FFFE` และสรุปว่า `3 failed, 1 error` (รัน: `demos/01_failures`) ความต่างระหว่าง `F` กับ `E` สำคัญ: `F` บอกว่าโค้ดทำงานผิดจากที่ test คาด ส่วน `E` บอกว่า test ยังไม่ทันได้เริ่มเพราะของที่ต้องใช้ตั้งไม่ขึ้น

</Step>

## อ่าน Traceback ตอน Test ล้ม

กรณีแรก ยอดรวมผิด

```text
    def test_wrong_total():
        cart = Cart()
        cart.add("apple", price=10, qty=3)
>       assert cart.total() == 31
E       assert 30 == 31
E        +  where 30 = total()
```

บรรทัดที่ขึ้นต้นด้วย `>` คือบรรทัดที่ล้ม ส่วนบรรทัด `E` คือสิ่งที่ Pytest เพิ่มให้: ค่าจริงของทั้งสองข้าง (30 กับ 31) โดยที่เราไม่ต้องเขียน message เอง Pytest ทำได้เพราะมัน **เขียน assert ใหม่** ก่อนรัน ([บท 2](/pytest/assertions/#assert-ธรรมดา-แต่ได้ข้อมูลมากกว่าที่คิด) พูดเรื่องนี้)

กรณีที่สอง เทียบ list

```text
E       AssertionError: assert ['apple', 'pear'] == ['apple', 'banana']
E         At index 1 diff: 'pear' != 'banana'
```

กรณีที่สาม exception เกิดในโค้ดที่ test เรียก traceback ไล่ลงไปถึงบรรทัดในโค้ดจริงให้ด้วย

```text
>           raise ValueError(f"qty must be positive, got {qty}")
E           ValueError: qty must be positive, got 0

src\shop\cart.py:32: ValueError
```

กรณีสุดท้าย fixture ระเบิด หัวข้อจะเป็น `ERROR at setup of test_uses_a_broken_fixture` และไม่มีการรันตัว test

วิธีอ่านที่ใช้ได้เสมอ: หา `>` ก่อน (บรรทัดไหนล้ม) แล้วอ่าน `E` ทีละบรรทัด (ล้มเพราะอะไร) แล้วค่อยดูว่าบรรทัดนั้นอยู่ใน test หรือในโค้ดจริง

</Step>

## Exit Code: สิ่งที่ CI อ่าน

Pytest คืนเลขออกจากโปรแกรมเพื่อให้ script และ CI ตัดสินใจ (รัน: `verify.py`)

| เหตุการณ์ | exit code |
|---|---|
| ผ่านทั้งหมด | 0 |
| มี test ล้มหรือ error | 1 |
| ไม่มี test ถูกเลือกรันเลย (เช่น `-k` ไม่ตรงอะไร) | 5 |

ข้อสุดท้ายสำคัญ ชุด test ที่ไม่ได้รันอะไรเลยไม่ใช่ "เขียว" Pytest จึงใช้เลขแยกให้

<Callout type="try" title="ลองทำใน repo นี้">
จาก `subjects/pytest/code/` รัน `uv sync` หนึ่งครั้ง แล้ว `uv run pytest exercises/01_first_test -v` ลองแก้ `assert cart.total() == 30` เป็น `31` ดูผล แล้วลองเปลี่ยนชื่อ `test_new_cart_is_empty` เป็น `new_cart_is_empty` ดูว่าจำนวน test ที่รันเปลี่ยนไปอย่างไร
</Callout>

</Step>

## เช็กตัวเอง

- คุณเพิ่งเขียนไฟล์ `cart_checks.py` ที่มี test 10 ตัว รัน `pytest` แล้วได้ `no tests ran` ปัญหาอยู่ที่ไหน
- ผลรันมี `E` หนึ่งตัวและ `F` หนึ่งตัว สองตัวนี้ต้องแก้ที่ต่างกันอย่างไร
- ทำไม exit code 5 จึงควรทำให้ pipeline ล้ม แทนที่จะนับเป็นผ่าน
