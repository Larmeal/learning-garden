## ตั้งค่าครั้งเดียว ใน pyproject.toml

แทนที่จะพิมพ์ Option ซ้ำทุกครั้ง เราใส่ไว้ใน `[tool.pytest.ini_options]` ของ `pyproject.toml` ได้เลย (Pytest ยังอ่าน `pytest.ini` ได้เช่นกัน) ค่าของโปรเจกต์แบบฝึกเป็นดังนี้

```toml
[tool.pytest.ini_options]
pythonpath = ["src"]
testpaths = ["exercises"]
addopts = "-ra"
markers = [
    "slow: a test that takes a while",
    "integration: a test that uses more than one module",
]
```

| Key | ทำอะไร |
|---|---|
| `pythonpath` | เพิ่มโฟลเดอร์เข้า `sys.path` เพื่อให้ `import shop` ได้โดยไม่ต้องติดตั้ง Package |
| `testpaths` | โฟลเดอร์ที่ค้น Test เมื่อรัน `pytest` เฉย ๆ |
| `addopts` | Option ที่ใส่ให้ทุกครั้ง `-ra` แสดงสรุปเหตุผลของ Skip, Xfail ฯลฯ |
| `markers` | ลงทะเบียน Marker ([บท 5](/pytest/markers/#ลงทะเบียน-marker-กันพิมพ์ผิด)) |

หัวรายงานจะบอกว่าอ่านค่าจากไหน คือ `rootdir: ...` และ `configfile: pyproject.toml`

`pythonpath` สำคัญมาก เพราะถ้าปิดมัน (รัน `pytest -o pythonpath= exercises/01_first_test`) เราจะได้ `ModuleNotFoundError: No module named 'shop'` ตั้งแต่ตอน Collect (รัน: `verify.py`)

</Step>

## โครงโฟลเดอร์

```text
code/
  pyproject.toml
  src/shop/            โค้ดที่ถูกทดสอบ
  exercises/NN_name/   test ที่ต้องผ่าน (มี conftest.py ได้ในแต่ละโฟลเดอร์)
  demos/NN_name/       test ที่ตั้งใจให้ล้ม ไว้ดูผล
```

`testpaths = ["exercises"]` ทำให้ `pytest` เฉย ๆ ไม่แตะ `demos/` ผลที่ได้จึงเขียวทั้งชุด คือ **188 Passed, 3 Skipped, 6 Xfailed** (รัน: `verify.py`) ส่วน Demo เราต้องสั่งโดยระบุ Path เอง

หลักคิดของการวาง Test มีสองข้อ (ผู้เขียน)

- ให้ Test อยู่ใกล้โค้ดในเชิงโครงสร้าง (`tests/` หรือ `exercises/` ที่ชื่อโฟลเดอร์สะท้อนฟีเจอร์) และให้ `conftest.py` อยู่ในโฟลเดอร์ที่ Fixture นั้นใช้ร่วมกัน
- แยก Test ที่ช้าหรือต้องพึ่งภายนอกด้วย Marker (`slow`, `integration`) แทนการแยกโฟลเดอร์ เพราะจะเลือกรันตามสถานการณ์ได้ง่ายกว่า

</Step>

## เลือกรัน: Path, Node Id และ -k

| ต้องการ | คำสั่ง | ผล (รัน: `verify.py`) |
|---|---|---|
| ทั้งโฟลเดอร์ | `pytest exercises/05_markers/test_markers.py` | 6 Passed, 2 Skipped, 2 Xfailed |
| ทั้งไฟล์ | `pytest exercises/03_fixtures/test_fixtures.py` | 12 Passed |
| Test เดียวด้วย Node id | `pytest exercises/03_fixtures/test_fixtures.py::test_save_and_load_with_tmp_path` | 1 Passed |
| ตามชื่อ | `pytest -k coupon exercises/04_parametrize/test_parametrize.py` | 3 Passed, 19 Deselected |
| ตาม Marker | `pytest -m "not slow" exercises/05_markers/test_markers.py` | 4 Passed, 2 Skipped, 2 Xfailed, 2 Deselected |

`-k` รับนิพจน์ `and`, `or`, `not` และจับคู่กับส่วนของชื่อ Test (รวมถึง id จาก Parametrize) ถ้าไม่แน่ใจว่าจะเลือกอะไรได้บ้าง ให้ใช้ `--collect-only -q` ดูรายชื่อ Test ทั้งหมดโดยไม่ต้องรัน

ถ้า Option ที่ใส่เลือก Test ไม่ได้สักตัว Exit Code จะเป็น 5 ([บท 1](/pytest/first-test/#exit-code-สิ่งที่-ci-อ่าน))

</Step>

## วงจรแก้โค้ด: -x, --lf, --ff

ตอนแก้ Bug เราอยากรัน Test ที่ล้มซ้ำ ๆ โดยไม่ต้องรันทั้งชุด

| Option | ทำอะไร | ผลในแบบฝึก `demos/01_failures` (3 Failed, 1 Error) |
|---|---|---|
| `-x` | หยุดหลังล้มตัวแรก | `1 failed` และ Test ที่เหลือไม่ถูกรัน |
| `--lf` (Last Failed) | รันเฉพาะ Test ที่ล้มรอบก่อน | รันซ้ำ 3 Failed, 1 Error |
| `--ff` (Failed First) | รัน Test ที่ล้มรอบก่อนก่อน แล้วตามด้วยที่เหลือ | |

(รัน: `verify.py`) Pytest จำผลรอบก่อนไว้ในโฟลเดอร์ `.pytest_cache` ซึ่งเราไม่ควรเอาเข้า Git

</Step>

<Step>

## รันขนานด้วย Pytest-xdist

เมื่อมี Test หลายพันตัว เราใช้หลาย CPU ช่วยกันรันได้ด้วย `pytest-xdist`

```bash
uv run pytest -n 2 exercises/04_parametrize/test_parametrize.py
```

ผลเหมือนรันทีละตัว คือ 21 Passed, 1 Xfailed (รัน: `verify.py`) แต่มีข้อแม้สำคัญคือ Test ต้องอิสระต่อกัน เพราะลำดับและตัวที่รันร่วมกันจะเปลี่ยนไป Test ที่แชร์สถานะกันจึงเริ่มล้มแบบสุ่ม ([บท 15](/pytest/test-design/#test-ต้องอิสระต่อกัน))

</Step>

## Coverage: บอกว่าบรรทัดไหนไม่เคยถูกรัน

`pytest-cov` วัดว่าบรรทัดไหนของโค้ดถูกรันระหว่าง Test

```bash
uv run pytest --cov=shop --cov-report=term-missing
```

```text
Name                   Stmts   Miss  Cover   Missing
----------------------------------------------------
src\shop\__init__.py       0      0   100%
src\shop\cart.py          48      0   100%
src\shop\checkout.py      14      0   100%
src\shop\net.py            2      0   100%
src\shop\pricing.py       15      1    93%   21
src\shop\rates.py         10      0   100%
src\shop\receipt.py        9      0   100%
src\shop\sale.py           7      0   100%
----------------------------------------------------
TOTAL                    105      1    99%
```

คอลัมน์ `Missing` ชี้บรรทัดที่ไม่เคยถูกรัน ตอนนี้เหลือบรรทัดเดียวคือบรรทัด 21 ของ `pricing.py` (`with_tax` ไม่มีใครเรียก) ส่วน `cart.py` ครบ 100% เพราะมี Test ที่ส่งราคาติดลบเข้า `Cart.add` แล้ว (`exercises/02_assertions/test_assertions_in_depth.py`) (รัน: `verify.py`)

<Callout type="warn" title="Coverage บอกว่าอะไรไม่ถูกทดสอบ ไม่ได้บอกว่าถูกทดสอบดี">
99% ไม่ได้แปลว่า Test ดี เพราะบรรทัดที่ถูกรันโดย Test ที่ไม่ Assert อะไรเลยก็นับเป็น Covered เราควรใช้ Coverage หา **ช่องโหว่** (บรรทัดใน Missing) แทนที่จะมองว่ามันเป็นเป้าหมายที่ต้องไปให้ถึง 100% (ผู้เขียน)
</Callout>

<Callout type="try" title="ลองทำใน Repo นี้">
ลองเขียน Test สำหรับ `with_tax(100)` ใน `exercises/01_first_test` แล้วรัน `uv run pytest --cov=shop --cov-report=term-missing` เพื่อดูว่าบรรทัด Missing ของ `pricing.py` หายไปไหม และ TOTAL เป็นเท่าไร จากนั้นลองลบ `assert` ออกจาก Test ใหม่ แล้วดูว่า Coverage ยังเป็น 100% อยู่ไหม
</Callout>
