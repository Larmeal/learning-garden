## Marker บน Class และ Module

เราแปะ Marker ได้สามระดับ คือฟังก์ชัน, Class และทั้ง Module ซึ่งใช้ตัวแปร `pytestmark` (รัน: `exercises/05_markers/test_marks_in_depth.py`)

```python
pytestmark = pytest.mark.integration        # ทุก test ในไฟล์นี้

@pytest.mark.slow
class TestMarksOnAClass:
    def test_inherits_the_class_mark(self, request):
        names = {m.name for m in request.node.iter_markers()}
        assert {"slow", "integration"} <= names
```

Test ในแบบฝึกได้ทั้ง `slow` (จาก Class) และ `integration` (จาก Module) โดยไม่ต้องแปะซ้ำ และถ้าต้องการหลาย Marker ก็ให้ `pytestmark` เป็น List ได้

</Step>

## อ่าน Marker จากโค้ด

Fixture หรือ Hook สามารถอ่าน Marker ของ Test ได้ ซึ่งเป็นวิธีส่งค่าตั้งให้ Test โดยไม่ต้องใช้ Parameter

```python
@pytest.fixture
def declared_timeout(request):
    marker = request.node.get_closest_marker("timeout")
    return marker.args[0] if marker else None

@pytest.mark.timeout(30)
def test_a_fixture_reads_the_mark_of_its_test(declared_timeout):
    assert declared_timeout == 30
```

Test ที่ไม่ได้แปะ Marker จะได้ `None` (รัน) และเราต้องลงทะเบียน `timeout(seconds)` ใน Config ก่อน ซึ่งแบบฝึกทำไว้ให้แล้ว (บท [Marker](/pytest/markers/#ลงทะเบียน-marker-กันพิมพ์ผิด))

เมื่อ Marker ชื่อเดียวกันถูกแปะหลายระดับ `iter_markers` จะคืนค่าโดย **เริ่มจากตัวที่ใกล้ Test ที่สุดก่อน** แบบฝึกแปะ `level(1)` ที่ Module, `level(2)` ที่ Class และ `level(3)` ที่ Method ผลคือ `iter_markers("level")` ได้ `[3, 2, 1]` และ `get_closest_marker("level")` ได้ `3` (รัน) ดังนั้นเราจะใช้ `get_closest_marker` เมื่อค่าที่ใกล้กว่าควรทับค่าที่ไกลกว่า และใช้ `iter_markers` เมื่อต้องรวมทุกระดับ

</Step>

## ไวยากรณ์ของ -m และ -k

`-m` ตรวจ **Marker** และ `-k` ตรวจ **ชื่อ** (รัน)

โปรเจกต์ทดลองมี Test สี่ตัว คือ `test_a` (Marker a), `test_b` (Marker b), `test_ab` (ทั้งสอง) และ `test_none`

| นิพจน์ `-m` | Test ที่เลือก |
|---|---|
| `a` | `test_a`, `test_ab` |
| `a and b` | `test_ab` |
| `a or b` | `test_a`, `test_ab`, `test_b` |
| `not a` | `test_b`, `test_none` |
| `(a or b) and not (a and b)` | `test_a`, `test_b` |

ส่วน `-k` จะจับคู่กับชื่อ Test (และ id ของ Parametrize) โดย **ไม่สนตัวพิมพ์ใหญ่เล็ก** ตัวอย่างเช่น `-k apple` ได้ `test_apple_pie` กับ `test_apple_tart`, `-k "apple and not tart"` ได้ตัวแรกตัวเดียว และ `-k APPLE` ก็ได้ทั้งสองเหมือนเดิม

</Step>

## `skipif` และ `xfail` ทุกรูปแบบ

เงื่อนไขของ `skipif` เป็นนิพจน์ Boolean หรือ **สตริง** ที่ถูกประเมินใน Namespace ของ Module (รัน)

```python
@pytest.mark.skipif(sys.implementation.name != "cpython", reason="a boolean condition: only CPython runs this")
def test_skipif_with_a_boolean_condition(): ...

@pytest.mark.skipif("sys.version_info < (3, 0)", reason="a string condition is evaluated in the module namespace")
def test_skipif_with_a_string_condition(): ...
```

`xfail` ก็รับเงื่อนไขเป็น Argument แรกเช่นเดียวกัน (`xfail(True, reason=...)` คาดว่าล้ม ส่วน `xfail(False, ...)` ไม่ทำอะไร) และยังมีตัวเลือกที่ช่วยจำกัดให้แคบลงได้อีก

| รูปแบบ | ความหมาย | ยืนยัน |
|---|---|---|
| `xfail(raises=ZeroDivisionError)` | นับเป็น Xfail เฉพาะเมื่อโยน Exception ชนิดนี้ | Test ที่หาร 0 ได้ Xfailed |
| Exception ชนิดอื่นที่โยนจริง | ยังเป็นความล้มจริง (`failed`) | `pytester` ได้ `failed=1` |
| `xfail_strict = true` ใน Config | ทุก Xfail เป็น Strict โดยไม่ต้องใส่ทีละตัว | Test ที่ผ่านทั้งที่แปะ Xfail ได้ `failed=1` |
| `request.node.add_marker(pytest.mark.xfail(...))` | เพิ่ม Marker **ตอนรัน** | Test ที่ `assert False` ได้ Xfailed |

เราควรใส่ `raises=` เสมอ เพราะ Xfail ที่ไม่ระบุจะกลบความล้มที่มาจากคนละสาเหตุไปโดยที่เราไม่ทันสังเกต เช่น Test ที่คาดว่าจะเจอ Bug A แต่กลับเจอ `KeyError` จาก Bug B
