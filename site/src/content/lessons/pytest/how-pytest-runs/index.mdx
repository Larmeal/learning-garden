## ส่วนนี้ของเส้นทางอ่านโค้ดของ Pytest เอง

ในแปดบทแรกเราใช้ Pytest เป็นเครื่องมือ ส่วน [บทที่ 9](/pytest/how-pytest-runs/) ถึง [14](/pytest/plugins/) เราจะเปิดดูข้างในของมัน เพื่อให้เข้าใจว่าทำไมพฤติกรรมที่เห็นถึงเป็นแบบนั้น เช่น ทำไม Fixture ถึงถูกปิดตอนนั้น และทำไม `assert` ใน Helper ถึงไม่มีรายละเอียด

ข้อมูลในบทนี้มาจากสองทาง ทางแรกคือโค้ดของ Pytest 9.2.0 ที่เราอ่านตรง ๆ (`src/_pytest/` ติดป้าย "Source" พร้อมชื่อฟังก์ชัน) ส่วนอีกทางคือสคริปต์ใน `subjects/pytest/code/internals/` ที่สร้างโปรเจกต์ชั่วคราวแล้วรัน Pytest จริงเพื่อดูผล (ติดป้าย "รัน") เราอ้างถึงชื่อฟังก์ชันและชื่อไฟล์ เพราะค้นเจอได้ในโค้ด แต่ไม่ใช้เลขบรรทัด เพราะมันเปลี่ยนไปทุกเวอร์ชัน

</Step>

## คำสั่งเดียว สี่ช่วง

เมื่อเรากด Enter คำสั่ง `pytest` จะเรียก `console_main()` ซึ่งเรียก `_main()` ใน `_pytest/config/__init__.py` ต่ออีกที โดยมีลำดับการทำงานดังนี้ (Source: `_main`, `_prepareconfig`)

1. ถ้าอาร์กิวเมนต์มีแค่ `--version` ตัวเดียว Pytest จะพิมพ์เวอร์ชันแล้วออกเลย โดยไม่เริ่มระบบ Plugin (รัน: `internals/01_startup.py`)
2. `_prepareconfig` สร้าง `Config` กับ `PytestPluginManager` ขึ้นมา โหลด Plugin ที่มากับ Pytest แล้วอ่านบรรทัดคำสั่ง ไฟล์ Config และ `conftest.py`
3. เรียก Hook `pytest_cmdline_main` ซึ่งตัวที่ทำงานจริงอยู่ใน `main.py` คือ `wrap_session`
4. `wrap_session` ทำสามอย่างต่อกัน คือ `pytest_sessionstart` แล้วตัว `_main` ของ Session (Collection แล้วรัน Test) และสุดท้ายคือ `pytest_sessionfinish`

ตัว `_main` ของ Session สั้นมาก (Source: `_main` ใน `main.py`)

```python
config.hook.pytest_collection(session=session)
config.hook.pytest_runtestloop(session=session)

if session.testsfailed:
    return ExitCode.TESTS_FAILED
elif session.testscollected == 0:
    return ExitCode.NO_TESTS_COLLECTED
```

Collection ทั้งหมดต้องเสร็จก่อน แล้วถึงเริ่มรัน Test ตัวแรก เราจึงเห็น `collected 5 items` ก่อนที่จะมี `.` ตัวแรกเสมอ

</Step>

## ทุกอย่างเป็น Plugin

Pytest ไม่ได้เป็นก้อนเดียว มันประกอบด้วยแกนเล็ก ๆ กับ Plugin ที่ลงทะเบียนไว้ โดยรายชื่อที่โหลดเสมอคือ `default_plugins` (Source: `_pytest/config/__init__.py`) ซึ่งใน 9.2.0 มีอยู่ 30 ตัว และในจำนวนนี้มีห้าตัวที่เป็น `essential_plugins`

| กลุ่ม | Plugin | ทำอะไร |
|---|---|---|
| แกน (Essential) | `mark`, `main`, `runner`, `fixtures`, `helpconfig` | เลือก Test ด้วย Marker, Session, ขั้น Setup/Call/Teardown, ระบบ Fixture, Option `-p` |
| การเก็บ Test | `python`, `unittest`, `doctest` | หา Test จากไฟล์ `.py` จาก `TestCase` และจาก Docstring |
| ผลลัพธ์ | `terminal`, `capture`, `logging`, `warnings`, `junitxml`, `pastebin` | พิมพ์ผล, ดักข้อความ, Log, Warning, ไฟล์ XML |
| ผลต่อ Test | `skipping`, `assertion`, `monkeypatch`, `tmpdir`, `recwarn`, `legacypath` | Skip/Xfail, เขียน Assert ใหม่, Fixture ที่ให้มา |
| การรัน | `cacheprovider`, `stepwise`, `setuponly`, `setupplan`, `debugging`, `faulthandler`, `reports`, `unraisableexception`, `threadexception`, `subtests` | `--lf`, `--sw`, `--setup-show`, `--pdb` ฯลฯ |

เราพิสูจน์ได้ด้วยการลองปิดมันดู (รัน: `internals/01_startup.py`)

- ถ้าใส่ `-p no:cacheprovider -p no:doctest` ชื่อทั้งสองจะหายไปจากรายการ Plugin ที่ลงทะเบียน ในขณะที่ `terminal` ยังอยู่
- ส่วน `-p no:main` ปิดไม่ได้ Pytest จะจบด้วย Exit Code 4 พร้อมข้อความ `plugin main cannot be disabled`
- ถ้าใส่ `--trace-config` Pytest จะพิมพ์ทุกบรรทัด `PLUGIN registered` ออกมา ทำให้เห็นว่าใครลงทะเบียนอะไรไว้บ้าง

สิ่งที่ได้จากตรงนี้ก็คือ ฟีเจอร์อย่าง `--lf` (Plugin `cacheprovider`) หรือ `--setup-show` (Plugin `setuponly`) เป็น Plugin ธรรมดา ๆ ที่ปิดได้ และเราสามารถเขียนของตัวเองในแบบเดียวกันได้ด้วย ([บท 14](/pytest/plugins/#plugin-คือไฟล์ที่มี-hook))

</Step>

## Hook: จุดที่ Pytest เรียกหาคนอื่น

Plugin คุยกับแกนผ่าน **Hook** ซึ่งเป็นฟังก์ชันที่ชื่อขึ้นต้นด้วย `pytest_` โดยข้อกำหนดของแต่ละ Hook อยู่ใน `_pytest/hookspec.py` (Source: ฟังก์ชัน `pytest_*` ในไฟล์นั้น มีราวห้าสิบตัว) ถ้า Plugin ใดอยากรู้เรื่องไหน ก็แค่เขียนฟังก์ชันชื่อเดียวกัน แล้ว Pluggy ซึ่งเป็นไลบรารี Plugin ที่ Pytest ใช้อยู่ ก็จะเรียกให้เอง

กติกาที่ใช้บ่อยมีสามข้อ

- Pluggy จะส่งเฉพาะ Argument ที่เราขอ ฟังก์ชันของเราประกาศแค่ Parameter ที่อยากได้ (`def pytest_runtest_logfinish(nodeid)`) แล้ว Pluggy ก็ส่งให้เท่านั้น แต่ถ้าประกาศ Parameter ที่ Spec ไม่มี เช่น `report` ใน `pytest_runtest_logfinish` Pytest จะจบด้วย Exit Code 1 และ `PluginValidationError` ตั้งแต่ตอนโหลด (รัน: `internals/11_hook_validation.py`) ส่วนชื่อ Hook ที่ไม่มีจริงจะไม่ล้มตอนโหลด แต่จะไปล้มตอน Collection ด้วย `INTERNALERROR` และ Exit Code 3
- Hook ส่วนใหญ่จะถูกเรียกกับทุก Plugin ที่ Implement เอาไว้
- Hook ที่ต้องตัดสินใจบางอย่าง (เช่น `pytest_runtest_protocol`, `pytest_collect_directory`, `pytest_fixture_setup`) เป็นแบบ `firstresult` คือจะหยุดที่ Implementation แรกที่คืนค่าไม่ใช่ `None`

ยังมีอีกสองชนิดที่จะเจอในบท [Plugin](/pytest/plugins/#ตัวครอบ-ทำงานก่อนและหลัง-hook-ตัวอื่น) ได้แก่ Hook แบบ Wrapper ที่ครอบ Hook ตัวอื่นอีกที และ Hook แบบ `historic` เช่น `pytest_configure` ซึ่ง Plugin ที่มาทีหลังก็ยังถูกเรียกย้อนหลังให้

</Step>

## ลำดับ Hook จริงสำหรับ Test สองตัว

สคริปต์ `internals/02_hook_order.py` สร้างโปรเจกต์ที่มีไฟล์เดียวซึ่งมี `test_one` และ `test_two` แล้วส่ง Plugin ที่คอยบันทึก Hook ทุกตัวเข้าไป ผลที่ได้คือมี 39 การเรียก (รัน: `internals/02_hook_order.py`) ซึ่งย่อได้ดังนี้

```text
 1  pytest_sessionstart
 2  pytest_collectstart Session          ┐
 5  pytest_collectstart Dir              │ collection: เดินลงทีละชั้น
 7  pytest_collectstart Module           │ Session > Dir > Module
 9  pytest_itemcollected test_one        │
10  pytest_itemcollected test_two        ┘
13  pytest_collection_modifyitems 2 items
14  pytest_collection_finish
15  pytest_runtestloop
16  pytest_runtest_logstart test_one
17  pytest_runtest_setup test_one
18  pytest_runtest_makereport test_one when=setup
19  pytest_runtest_logreport test_one setup passed
20  pytest_runtest_call test_one
21  pytest_runtest_makereport test_one when=call
22  pytest_runtest_logreport test_one call passed
23  pytest_runtest_teardown test_one nextitem=test_two
24  pytest_runtest_makereport test_one when=teardown
25  pytest_runtest_logreport test_one teardown passed
26  pytest_runtest_logfinish test_one
27  ... เหมือนกัน สำหรับ test_two (teardown ได้ nextitem=None)
38  pytest_sessionfinish exitstatus=0
39  pytest_terminal_summary
```

ลองดูว่ารายการนี้บอกอะไรเราบ้าง

- Collection เสร็จทั้งต้นไม้ก่อนที่จะรันตัวแรก (บรรทัด 14 มาก่อน 17) ส่วนต้นไม้นี้สร้างอย่างไร บท [Collection](/pytest/collection/#collection-คือการสร้างต้นไม้) อธิบายไว้แล้ว
- แต่ละ Test มีรายงานสามใบ คือ Setup, Call และ Teardown ใบละหนึ่ง (`makereport` หกครั้งสำหรับสอง Test) ตัวเลขนี้ตอบได้ว่าทำไม Fixture ที่พังตอน Teardown ถึงเป็น Error แยกจาก Test ที่ผ่าน ([บท 12](/pytest/run-protocol/#สามเฟส-สามรายงาน))
- ค่า `nextitem` ตอน Teardown ของ test_one คือ test_two และของ test_two คือ `None` Pytest ใช้ค่านี้ตัดสินว่า Fixture ระดับ Module หรือ Session ควรปิดตอนนี้ไหม ([บท 11](/pytest/fixture-engine/#teardown-ปิดเมื่อไรและโดยใคร))
- สรุปท้ายรายงานถูกพิมพ์หลัง `sessionfinish` (บรรทัด 39 หลัง 38) เพราะ `terminal` ครอบ Hook นั้นด้วย Wrapper แล้วเรียก `pytest_terminal_summary` เอง (Source: `pytest_sessionfinish` ใน `terminal.py`)

</Step>

## ผลของ Session และ Exit Code

`wrap_session` ห่อทุกอย่างไว้ด้วย Try แล้วแยกตามแต่ละกรณี (Source: `wrap_session` ใน `main.py`) ตารางนี้เทียบกับ `ExitCode` ใน `config/__init__.py`

| สถานการณ์ | `session.exitstatus` | ค่า |
|---|---|---|
| รันจบ ไม่มีล้ม | `OK` | 0 |
| มี Test ล้ม หรือ `Failed` ถูกโยน | `TESTS_FAILED` | 1 |
| `KeyboardInterrupt` หรือ `pytest.exit()` | `INTERRUPTED` (หรือเลขที่ `exit()` กำหนด) | 2 |
| Exception อื่นที่ไม่ได้คาดไว้ | `INTERNAL_ERROR` | 3 |
| `UsageError` เช่น Option ที่ไม่รู้จัก | `USAGE_ERROR` | 4 |
| ไม่เจอ Test เลย | `NO_TESTS_COLLECTED` | 5 |

ถ้าใส่ `--no-such-option` Pytest จะจบด้วย 4 และข้อความ `unrecognized arguments: --no-such-option` (รัน: `internals/01_startup.py`) ส่วนเลข 5 เราเคยเห็นไปแล้วในบท [First Test](/pytest/first-test/#exit-code-สิ่งที่-ci-อ่าน) ตอนใช้ `-k` ที่ไม่ตรงกับ Test ตัวไหนเลย

`pytest_sessionfinish` จะถูกเรียกแม้ Session ถูกขัดจังหวะ ตราบเท่าที่ Session เริ่มไปแล้ว (ตัวแปร `initstate >= 2` ใน `wrap_session`) Plugin จึงมีที่ให้เก็บกวาดเสมอ

</Step>

## Config มาจากไหน

ค่าที่ Plugin เห็นผ่าน `config` มาจากหลายชั้น และถ้าเป็น Option เดียวกัน ชั้นหลังจะชนะชั้นก่อน (รัน: `internals/09_config_layout.py`)

| ชั้น | ตัวอย่าง | ผลที่ยืนยัน |
|---|---|---|
| ไฟล์ Config | `pytest.ini`, `pyproject.toml` ที่มี `[tool.pytest]`, `tox.ini`, `setup.cfg` | ใช้ไฟล์แรกที่เจอ ตามลำดับนี้ ลบไฟล์ที่ชนะทีละไฟล์แล้วไฟล์ถัดไปขึ้นมาตามลำดับ |
| `PYTEST_ADDOPTS` | `PYTEST_ADDOPTS=-v` | เติม Option เข้าไป เหมือนพิมพ์เอง |
| บรรทัดคำสั่ง | `-o minversion=9.0` | ชนะค่าในไฟล์ |

รายละเอียดอื่นของการหาไฟล์ Config และ Rootdir อยู่ใน [บท 7](/pytest/project/in-depth/#ไฟล์-config-ไหนชนะ) ส่วน Conftest ที่ Pytest โหลดระหว่างเริ่มต้นก็เป็น Plugin ที่ลงทะเบียนในระดับโฟลเดอร์ ([บท 14](/pytest/plugins/#ลงทะเบียนอย่างไร))

<Callout type="try" title="ลองทำใน Repo นี้">
ลองรัน `uv run python internals/02_hook_order.py` จาก `subjects/pytest/code/` แล้วเพิ่ม Method `pytest_runtest_logstart(self, nodeid, location)` เข้าไปใน `Recorder` เพื่อดูว่า `location` หน้าตาเป็นอย่างไร จากนั้นรัน `uv run pytest --trace-config -q --co` เพื่อดูรายการ `PLUGIN registered` ทั้งหมด
</Callout>

- ถ้า Plugin ของคุณ Implement `pytest_collection_modifyitems` มันจะรันก่อนหรือหลัง `pytest_itemcollected` ทุกตัว และทำไม
