## วิธีที่ใช้ในหน้านี้

Test ที่เขียนไม่ดีส่วนใหญ่ไม่ได้ล้ม จึงไม่มีใครสังเกต เราเลยเอา Test ที่มีปัญหาไปรันในโปรเจกต์ชั่วคราวด้วย `pytester` แล้วดูว่าผลเป็นอย่างไร (รัน: `exercises/08_design/test_smells.py` 12 Test ผ่านทั้งหมด) และแต่ละข้อก็มีฉบับที่แก้แล้วให้เทียบกัน

</Step>

<Step>

## 1. พึ่งลำดับ

สอง Test ใช้ List ที่สร้างไว้ระดับ Module ร่วมกัน (เหมือน `demos/08_order_dependent` ใน [บท 15](/pytest/test-design/#test-ต้องอิสระต่อกัน))

```python
cart = []
def test_add():
    cart.append("apple")
    assert cart == ["apple"]
def test_total():
    assert len(cart) == 1
```

ถ้ารันทั้งไฟล์ จะผ่าน 2 ตัว แต่ถ้ารัน `test_total` ตัวเดียวด้วย Node id จะล้ม ฉบับที่แก้ให้แต่ละ Test ขอตะกร้าจาก Fixture และเพิ่มของเอง ทำให้รัน `test_total` เดี่ยว ๆ แล้วผ่าน (รัน) เราทดสอบความอิสระได้ด้วยการรันทีละตัวเป็นครั้งคราว หรือรันขนานด้วย `-n` ([บท 7](/pytest/project/#รันขนานด้วย-pytest-xdist))

</Step>

<Step>

## 2. ค่าสุ่ม

Test ที่ใช้ตัวสุ่มของ Python โดยไม่ตรึงค่าจะให้ผลต่างกันทุกรอบ ถ้าโค้ดรับตัวสร้างสุ่มเป็น Parameter (`make_discount(rng)`) Test ก็ส่ง `random.Random(7)` เข้าไปได้ และจะได้ชุดค่าเดิมทุกครั้ง (รัน) แต่ถ้าโค้ดใช้ตัวสุ่มกลางของ `random` ให้เรียก `random.seed(7)` ใน Test เอง ทั้งสองแบบทำให้ได้ผลซ้ำได้ ส่วน Test ที่ไม่ตรึงจะล้มเป็นบางรอบ ซึ่งเป็นอาการของ **Flaky Test** (หัวข้อสุดท้ายของหน้านี้)

</Step>

<Step>

## 3. คำนวณค่าที่คาดด้วยโค้ดเดียวกัน

```python
def test_smell_the_expected_value_is_computed_with_the_same_code():
    prices, qtys = [10, 20], [3, 1]
    assert total_of(prices, qtys) == sum(p * q for p, q in zip(prices, qtys))
```

Test นี้ผ่านแม้สูตรใน `total_of` จะผิด เพราะทั้งสองฝั่งใช้สูตรเดียวกัน ฉบับที่แก้จะเขียนค่าที่คาดลงไปตรง ๆ จากการคำนวณด้วยมือ

```python
assert total_of([10, 20], [3, 1]) == 50      # 3 * 10 + 1 * 20
```

มีกฎที่จำง่ายอยู่ข้อหนึ่ง ถ้าด้านที่คาดกลายเป็นสำเนาของโค้ดได้ แปลว่า Test ไม่ได้บอกอะไรเรา ค่าที่คาดควรมาจากที่อื่น (ตัวเลขที่คำนวณด้วยมือ ตัวอย่างจากสเปก หรือผลที่ยืนยันแล้ว)

</Step>

<Step>

## 4. Assert ที่ไม่มีทางล้ม

มีอยู่สามแบบที่เห็นบ่อย (รัน)

| แบบ | ผล |
|---|---|
| `assert (1 == 2, 'message')` | ผ่าน เพราะ Tuple ที่ไม่ว่างเป็นจริง Pytest ออก Warning `assertion is always true, perhaps remove parentheses?` ([บท 13](/pytest/assertion-rewriting/#กับดักและตัวช่วยอื่น)) |
| Test ที่ไม่มี `assert` เลย (`1 + 1`) | ผ่านเสมอ พิสูจน์แค่ว่าไม่มี Exception |
| `return 1 == 2` แทน `assert` | ผ่านพร้อม Warning `Did you mean to use assert instead of return?` ([บท 12](/pytest/run-protocol/)) |

ทั้งสามแบบให้ผลเป็นสีเขียว วิธีป้องกันคือใช้ `-W error` หรือ `filterwarnings = ["error"]` เพื่อให้ Warning เหล่านี้ทำให้ Test ล้ม ([บท 8](/pytest/builtin-plugins/#warnings-สรุปท้ายรายงาน))

</Step>

<Step>

## 5. หนึ่ง Test หลายเรื่อง

Test ที่มี `assert 1 == 2` ตามด้วย `assert 3 == 4` จะรายงานเฉพาะอันแรก ส่วน `3 == 4` ไม่ถูกประเมินเลย (รัน: ข้อความ `3 == 4` ไม่อยู่ในผล) แต่ถ้าแยกเป็นสอง Test จะได้ `2 failed` และเห็นทั้งคู่ นี่คือเหตุผลที่บท [ออกแบบ Test](/pytest/test-design/) แนะนำให้หนึ่ง Test เช็กหนึ่งพฤติกรรม

ถ้าจำเป็นต้องเช็กหลายจุดในรอบเดียวจริง ๆ (เช่น แต่ละแถวของข้อมูล) ให้ใช้ Subtests ซึ่งรายงานแต่ละรอบแยกกัน ([บท 8](/pytest/builtin-plugins/#subtests-หลายผลใน-test-เดียว))

</Step>

<Step>

## Flaky Test: ล้มบางรอบ

Test ที่ล้มหนึ่งในห้ารอบจะดูเขียวเกือบตลอด แบบฝึกจำลองด้วยตัวนับที่เพิ่มทุกรอบ และ Test ที่ล้มเมื่อตัวนับหารห้าลงตัว ถ้า Parametrize ให้รัน 10 ครั้ง ผลคือ `8 passed, 2 failed` (รัน) การทำซ้ำจึงเป็นวิธีที่ทำให้ปัญหาที่เกิดเป็นระยะมองเห็นได้ ส่วนสาเหตุที่พบบ่อยคือเวลา ค่าสุ่ม ลำดับ และของที่ใช้ร่วมกัน ซึ่งสี่ข้อแรกของหน้านี้ครอบคลุมไว้แล้ว

ตอนแก้ Flaky Test อย่าใช้วิธี Retry จนผ่านนะ เพราะการรันซ้ำจนผ่านเป็นการซ่อนความผิดไว้ เราควรหาสาเหตุให้เจอ (ผู้เขียน)

## ที่มาของหน้านี้

| ข้อความ | ที่มา |
|---|---|
| พึ่งลำดับ (ผ่านทั้งไฟล์ ล้มเมื่อรันเดี่ยว, ฉบับ Fixture ผ่านเดี่ยว), ค่าสุ่มที่ตรึงแล้วซ้ำได้ | รัน: `exercises/08_design/test_smells.py` |

| กฎจำง่ายเรื่องค่าที่คาด, คำแนะนำไม่ Retry จนผ่าน, `-W error` กับ Warning เหล่านี้ | ผู้เขียน |
