## Test ที่ดีหน้าตาเป็นอย่างไร

สิบสี่บทที่ผ่านมาเราเรียนเรื่อง **เครื่องมือ** และกลไกข้างใน ส่วนบทนี้จะพูดถึง **วิจารณญาณ** ว่าเราควรเขียน Test ตัวไหน และเขียนอย่างไร โดยมีตัวชี้วัดที่ใช้ดังนี้ (ผู้เขียน)

| คุณสมบัติ | หมายความว่า |
|---|---|
| อ่านเป็นประโยค | ชื่อ Test บอกพฤติกรรม เช่น `test_a_declined_card_leaves_the_cart_untouched` |
| ล้มเพราะเหตุผลเดียว | Test ล้มแล้วรู้ทันทีว่าพฤติกรรมไหนพัง |
| อิสระ | รันตัวเดียว รันกลับลำดับ หรือรันขนานได้ผลเหมือนกัน |
| กำหนดผลได้ (Deterministic) | ไม่พึ่งเวลา สุ่ม เครือข่าย ([บท 6](/pytest/isolation/#test-ที่พึ่งโลกภายนอกจะเชื่อไม่ได้)) |
| ไม่พังเพราะ Refactor | ตรวจสิ่งที่ผู้เรียกใช้เห็น ไม่ใช่โครงภายใน |

</Step>

<Step>

## Arrange, Act, Assert

เราแบ่ง Test ออกเป็นสามช่วงที่เห็นชัด คือจัดของ (Arrange) ลงมือ (Act) และตรวจ (Assert)

```python
def test_checkout_charges_the_cart_total(cart_with_one_apple):
    # Arrange
    gateway = FakeGateway()
    # Act
    charged = checkout(cart_with_one_apple, gateway, "A-1")
    # Assert
    assert charged == 100
    assert gateway.charges == [(100, "A-1")]
```

ช่วง Act ควรมีบรรทัดเดียว ถ้ามีหลายบรรทัดแสดงว่า Test กำลังทดสอบหลายพฤติกรรม ให้แยกออกจากกัน ในแบบฝึก `exercises/08_design/test_design.py` มี 12 Test ที่ผ่านทั้งหมด (รัน: `exercises/08_design/test_design.py`) และชื่อของมันเรียงเป็นรายการพฤติกรรมของ Checkout เพียงอ่านรายชื่อก็เข้าใจสเปกแล้ว

```text
test_checkout_charges_the_cart_total
test_checkout_applies_the_coupon_before_charging
test_checkout_empties_the_cart_after_a_successful_charge
test_a_declined_card_leaves_the_cart_untouched
test_checkout_of_an_empty_cart_never_reaches_the_gateway
test_an_unknown_coupon_is_an_error_and_charges_nothing
```

</Step>

## ทดสอบ Behaviour ไม่ใช่โครงภายใน

ลองเทียบสอง Test ที่ผ่านทั้งคู่ในวันนี้ (รัน: `exercises/08_design/test_design.py`)

```python
def test_brittle_version_looks_inside(cart_with_one_apple):
    assert list(cart_with_one_apple._lines) == ["apple"]

def test_robust_version_uses_the_public_interface(cart_with_one_apple):
    assert cart_with_one_apple.skus() == ["apple"]
    assert cart_with_one_apple.total() == 100
```

ตัวแรกอ่าน `_lines` ซึ่งเป็นรายละเอียดภายใน ถ้าวันหนึ่งเราเปลี่ยนโครงเก็บข้อมูลเป็นอย่างอื่น Test นี้จะล้มทั้งที่ลูกค้าไม่เห็นอะไรเปลี่ยนเลย และมันก็ไม่ได้สังเกตด้วยว่า `total()` ผิดหรือไม่ ส่วนตัวที่สองตรวจสิ่งที่ผู้เรียกใช้เห็น จึงรอดการ Refactor และจับ Bug ของ `total()` ได้ (ผู้เขียน)

มีคำถามไว้ตรวจตัวเองว่า "ถ้าฉันเขียนฟังก์ชันนี้ใหม่ทั้งหมดแต่ให้ผลเหมือนเดิม Test ของฉันควรยังเขียว ใช่ไหม" ถ้าคำตอบคือไม่ใช่ แสดงว่า Test กำลังผูกกับวิธีทำ แทนที่จะผูกกับผลที่ต้องการ

</Step>

## เส้นแบ่งและกรณีล้ม

Bug ชอบอยู่ที่รอยต่อ เราจึงควรทดสอบทั้งสองข้างของทุกเส้นแบ่ง เช่น `shipping_fee` ส่งฟรีตั้งแต่ 500 (รัน: `exercises/08_design/test_design.py`)

```python
@pytest.mark.parametrize("total, fee", [(499.99, 50), (500, 0), (500.01, 0)])
def test_shipping_threshold_boundary(total, fee):
    assert shipping_fee(total) == fee
```

อย่าลืมทางล้มด้วย Test หลายตัวใน `exercises/08_design/test_design.py` ตรวจว่าเมื่อเกิดความผิดพลาดแล้ว **ไม่มีผลข้างเคียง**

- ถ้าตะกร้าว่าง จะไม่เรียก Gateway เลย (`gateway.charges == []`)
- ถ้าคูปองไม่มีจริง จะโยน `KeyError` และไม่เก็บเงิน และตะกร้ายังอยู่
- ถ้าบัตรถูกปฏิเสธ ตะกร้ายังมีของอยู่

การทดสอบว่า "ไม่เกิดอะไร" ในทางล้มเป็นสิ่งที่ถูกลืมบ่อยที่สุด และเป็นต้นเหตุของ Bug ที่ลูกค้าเห็น เช่น เก็บเงินแต่ไม่ส่งของ

</Step>

## Test ต้องอิสระต่อกัน

`demos/08_order_dependent` มีสอง Test ที่แชร์ตะกร้าระดับ Module

```python
cart = Cart()        # สร้างครั้งเดียวตอน import

def test_add():
    cart.add("apple", price=10)
    assert cart.qty("apple") == 1

def test_total():
    assert cart.total() == 10     # จริงก็ต่อเมื่อ test_add รันก่อน
```

ถ้ารันทั้งไฟล์ **จะผ่านทั้งสอง** (2 Passed) แต่ถ้ารัน `test_total` ตัวเดียวด้วย Node id จะ **ล้ม** (1 Failed) (รัน: `demos/08_order_dependent`, `verify.py`) นี่เป็นอาการที่น่ากลัวที่สุด เพราะ CI เขียวมาทุกวัน แล้ววันหนึ่งมีคนรันเฉพาะตัว หรือเปิด `-n 4` หรือสลับลำดับ ทุกอย่างก็กลายเป็นสีแดงทันที

วิธีแก้คือให้แต่ละ Test สร้างของที่ใช้เองด้วย Fixture ระดับ Function ([บท 3](/pytest/fixtures/#scope-สร้างบ่อยแค่ไหน)) แล้ว `test_total` ก็จะเตรียมตะกร้าที่มีแอปเปิลเอง แทนที่จะหวังว่าคนอื่นเตรียมให้

</Step>

<Step>

## Regression Test: Bug Report ที่กลายเป็นเกราะ

เมื่อพบ Bug ให้เขียน Test ที่ทำให้ Bug แสดงตัวก่อน แล้วค่อยแก้โค้ด Test นั้นก็จะอยู่ต่อเป็นเกราะป้องกันไม่ให้ Bug กลับมา

```python
def test_coupon_lookup_is_case_insensitive():
    """Bug report #12: 'save10' typed in lower case was rejected."""
    assert discount_for("save10") == discount_for("SAVE10")
```

เราใช้ Docstring หรือชื่อบอกที่มา เพื่อให้ใครที่มาแก้โค้ดตรงนี้ทีหลังรู้ว่ากติกานี้มีเหตุผล (ผู้เขียน)

</Step>

## โจทย์ปิดท้าย: ทำให้ Test ที่ Xfail ผ่าน

กลับไปที่[บท 5](/pytest/markers/#xfail-รู้ว่าล้ม-แต่ยังรันอยู่) ซึ่งมี `test_two_coupons_should_not_stack` ที่ถูกทำเครื่องหมาย Xfail เพราะธุรกิจยังไม่ตัดสินใจ สมมติว่าตอนนี้ธุรกิจตัดสินใจแล้วว่า **คูปองใช้ได้ครั้งเดียวต่อตะกร้า** การทำตามขั้นตอนต่อไปนี้เป็นการฝึกทุกอย่างในเส้นทางนี้

1. คัดลอก Test จาก `exercises/05_markers/test_markers.py` แล้วลบ `xfail` ออก จากนั้นรันเพื่อยืนยันว่า **ล้ม** (Red)
2. ออกแบบว่า `apply_coupon` ควรจำคูปองที่ใช้ไปในตัว `Cart` หรือควรคืนตะกร้าใหม่ ตัดสินใจแล้วเขียนข้อกำหนดเป็นประโยคก่อน
3. เขียน Test เพิ่มสำหรับกรณีขอบ คือใช้คูปองเดิมซ้ำ, ใช้คูปองใหม่หลังเอาของออกจนว่าง และคูปองที่ไม่มีจริง ถ้ามีหลายกรณีก็ใช้ `parametrize`
4. แก้โค้ดให้ผ่าน (Green)
5. เก็บกวาด (Refactor) แล้วรันทั้งชุด พร้อมรัน `--cov` ดูว่ามีบรรทัดใหม่ที่ Missing ไหม
6. ตรวจว่าเมื่อใช้ `FakeGateway` ผ่าน `checkout` ด้วยคูปอง ยังได้ยอดที่ถูกต้องอยู่ไหม และยังไม่มีใคร Assert ในโค้ดภายใน (`_lines`) ใช่ไหม

โจทย์นี้ไม่มีเฉลยตายตัว เพราะการออกแบบในข้อ 2 เป็นการตัดสินใจ และ Test ที่ดีคือ Test ที่บอกการตัดสินใจนั้นไว้ชัดเจน

<Callout type="try" title="ลองทำใน Repo นี้">
ลองทำโจทย์ข้างบนใน `subjects/pytest/code/` จากนั้นรัน `uv run python verify.py` ตัวเลขที่เปลี่ยนไปคือหลักฐานว่า Test ชุดใหม่ถูกเพิ่มเข้ามา (ถ้า Verify ไม่ผ่านเพราะจำนวน Test เปลี่ยน ให้แก้ตัวเลขใน `verify.py` ให้ตรง)
</Callout>

## เช็กตัวเอง

- Test ของคุณมีชื่อว่า `test_1`, `test_2` อ่านแล้วบอกอะไรไม่ได้ ถ้าคุณเปลี่ยนชื่อเป็นประโยคพฤติกรรม ได้อะไรเพิ่ม
- Test ใดในโค้ดที่คุณเขียนล่าสุดจะล้มถ้าเปลี่ยนชื่อ Attribute ภายใน และคุณแก้ให้ใช้ Interface สาธารณะได้อย่างไร
- ถ้า CI เขียวทุกวันแต่รัน `pytest path::test_x` ตัวเดียวแล้วล้ม มันบอกอะไรเกี่ยวกับชุด Test
