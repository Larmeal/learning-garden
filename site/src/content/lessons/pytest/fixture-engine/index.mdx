## ตัวละครสี่ตัว

บท [Fixture](/pytest/fixtures/) สอนวิธีใช้ไปแล้ว คราวนี้เราจะมาดูว่า Pytest ทำให้มันเกิดขึ้นอย่างไร ซึ่งทั้งหมดอยู่ใน `_pytest/fixtures.py` และ `_pytest/runner.py` (Source)

| ตัวละคร | มีกี่ตัว | หน้าที่ |
|---|---|---|
| `FixtureManager` | หนึ่งต่อ Session | สแกนหา Fixture, เก็บทะเบียน, คำนวณว่า Test ต้องใช้อะไร |
| `FixtureDef` | หนึ่งต่อฟังก์ชันที่มี `@pytest.fixture` | ข้อมูลของ Fixture (ชื่อ, Scope, Params) และ **ค่าที่ Cache ไว้** |
| `FixtureRequest` / `SubRequest` | `TopRequest` หนึ่งต่อ Test, `SubRequest` หนึ่งต่อ Fixture ที่กำลังรัน | คือ Object `request` ที่ Fixture ได้รับ |
| `SetupState` | หนึ่งต่อ Session | Stack ของ Node ที่ Set up แล้ว และรายการ Finalizer ของแต่ละ Node |

ทั้งหมดนี้ทำงานในสองช่วงเวลา ช่วงแรกคือ Collection ซึ่งทะเบียนและรายการที่ Test ต้องใช้จะถูกคำนวณ ส่วนช่วงที่สองคือตอนรัน ซึ่งแต่ละ Fixture จะถูกเรียก เก็บ Cache และปิด

## ทะเบียน: ใครเห็น Fixture ตัวไหน

`FixtureManager.parsefactories` สแกน Module, Class และ `conftest.py` หา Object ที่มี Marker ของ Fixture แล้วเก็บ `FixtureDef` ไว้ใต้ชื่อ พร้อม **Path ของ Node ที่ประกาศมัน** (Source: `parsefactories`, `_register_fixture`) เมื่อ Test ขอชื่อหนึ่ง `getfixturedefs(argname, node)` จะคืนรายการที่มองเห็นได้จาก Node นั้น โดยเรียงจากไกลไปใกล้ และตัวสุดท้าย (ใกล้ที่สุด) จะชนะ (Source: `_get_active_fixturedef` มีคอมเมนต์ว่า `fixturedefs` เรียงจากไกลที่สุดไปใกล้ที่สุด)

มีกติกาพิเศษข้อเดียวที่น่าสนใจ คือ Fixture ที่ Override ตัวอื่นสามารถขอชื่อของตัวเองได้ แล้วจะได้ค่าจากตัวที่มันทับ ซึ่งอยู่สูงขึ้นไปหนึ่งชั้น (Source: `_get_active_fixturedef` ใช้ดัชนีติดลบถอยไปทีละชั้น) เราพิสูจน์ได้ด้วยโปรเจกต์ที่ `conftest.py` ราก ให้ `price = 10` และ `sub/conftest.py` เขียน `def price(price): return price * 2` (รัน: `internals/13_fixture_engine.py`)

```text
sub/test_a.py   : price == 20     (ใช้ตัวของ sub ที่ครอบตัวราก)
test_top.py     : price == 10     (นอก sub เห็นแค่ตัวราก)
```

## รายการที่ Test ต้องใช้: Closure

ก่อนรัน Pytest จะคำนวณ **Closure** ของแต่ละ Test ซึ่งก็คือชื่อ Fixture ทั้งหมดที่ต้องใช้ ได้แก่ Parameter ของ Test, Fixture ที่ `autouse`, ที่ `usefixtures` ระบุ และของที่พวกมันขอต่อ ๆ กัน (Source: `getfixtureclosure`) แล้ว **เรียงจาก Scope กว้างไปแคบ** (Source: `sorted(..., key=sort_by_scope, reverse=True)`)

ในแบบฝึก `internals/04_setupstate.py` มี Fixture `db` (Session), `conn` (Module), `tx` (Function) และ `mark` (Function, Autouse) Test ที่ขอ `tx` จะได้ Closure ดังนี้ (รัน: `internals/04_setupstate.py`)

```text
['db', 'conn', 'mark', 'request', 'tx']
```

จะเห็นว่า Session มาก่อน Module ตามด้วยของระดับ Function ซึ่งรวม `mark` ที่ Test ไม่ได้ขอเอง และ `request` ที่เป็น Fixture ในตัว ลำดับนี้เองที่ทำให้ Fixture ที่กว้างกว่าถูกตั้งก่อนเสมอ

ส่วน Fixture ที่เลือกตอนรันด้วย `request.getfixturevalue("a")` จะไม่อยู่ใน Closure ที่คำนวณไว้ตอน Collection แต่ชื่อ `a` จะถูกเพิ่มเข้า `request.fixturenames` ตอนที่เรียก (รัน: `internals/13_fixture_engine.py`: ก่อนเรียกได้ `["request"]` หลังเรียกได้ `["request", "a"]`)

</Step>

## รัน Fixture หนึ่งตัว

ตอนรัน Test จะขอ Fixture ทีละตัวตามลำดับ Closure และ `FixtureDef.execute` จะทำสี่ขั้นตอน (Source: `execute`)

1. **ขั้นตอนแรก** เรียก Dependency ก่อน โดยทุกชื่อที่ Fixture นี้ขอจะถูกหา (`request._get_active_fixturedef`) และรันก่อน
2. **ขั้นตอนที่สอง** เช็ก Cache ถ้ามี `cached_result` และ `cache_key` ตรง (คือ Param เดิม) ก็คืนค่าที่เก็บไว้ แต่ถ้ามี Cache และ Param ต่างกัน จะปิดตัวเก่าก่อนแล้วสร้างใหม่
3. **ขั้นตอนที่สาม** ลงทะเบียน Finalizer โดยผูกกับ Node ของ Scope นั้น (`request.node.addfinalizer`)
4. **ขั้นตอนสุดท้าย** เรียก Hook `pytest_fixture_setup` ซึ่งจะเรียกฟังก์ชัน Fixture จริง แล้วเก็บผลใน `cached_result` เป็น Tuple ของ (ค่า, Cache Key, Exception หรือ None)

สำหรับ Fixture แบบ `yield` จะถูกจัดการใน `call_fixture_func` โดยค่าที่ `yield` ออกมาจะเป็นค่าของ Fixture ส่วนโค้ดหลัง `yield` จะถูกลงทะเบียนเป็น Finalizer

ขั้นตอนที่ 4 มีรายละเอียดที่ควรรู้ด้วย คือ **Exception ก็ถูก Cache** ถ้า Fixture ระดับ Module พังตอน Setup ผลที่เก็บไว้จะเป็น Exception ดังนั้นเมื่อ Test ตัวถัดไปในไฟล์เดียวกันขอ Fixture นี้ Pytest จะโยน Exception เดิมซ้ำโดยไม่เรียกฟังก์ชันอีก ในแบบฝึกมีสอง Test ที่ใช้ Fixture ที่โยน `RuntimeError("cannot connect")` ผลคือได้สอง Error และตัวนับการเรียกบอกว่า Setup ถูกเรียก **ครั้งเดียว** (รัน: `internals/13_fixture_engine.py`)

</Step>

## Teardown ปิดเมื่อไรและโดยใคร

เรื่องที่คนสงสัยกันมากที่สุดคือ "ทำไม Fixture ระดับ Module ถึงปิดตอนนั้น" คำตอบอยู่ที่ `SetupState` ใน `runner.py` ซึ่งคำอธิบายในตัวโค้ดเองก็ดีมาก (Source: Docstring ของ `SetupState`)

- ระหว่างรัน Test `SetupState` จะเก็บ **Stack ของ Node** ที่ Set up แล้ว โดยขณะ Test ตัวหนึ่งกำลังรัน Stack จะเป็น `[Session, Dir, Module, Function]` (รัน: `internals/04_setupstate.py`)
- แต่ละ Node มีรายการ Finalizer ของตัวเอง โดย Fixture ที่ Scope เป็น Module จะผูก Finalizer เข้ากับ Node `Module`
- ตอน Teardown ของ Test ตัวหนึ่ง Pytest จะส่ง `nextitem` เข้ามา แล้ว `teardown_exact(nextitem)` จะดึง Node ออกจากปลาย Stack ทีละตัว และรัน Finalizer ของมัน **จนกว่าจะเจอ Node ที่ Nextitem ก็อยู่ใน Chain เดียวกัน** (Source: `teardown_exact`)

ผลของกติกานี้เห็นได้จาก Log จริงของแบบฝึก (รัน: `internals/04_setupstate.py`)

```text
setup db                    ← session, ครั้งเดียว
setup conn                  ← module a
start test_a1  setup tx  teardown tx  end test_a1
start test_a2  setup tx  teardown tx  end test_a2
teardown conn               ← test_a2 เป็นตัวสุดท้ายของ module a: nextitem อยู่คนละ Module
setup conn                  ← module b
start test_b1  setup tx  teardown tx  end test_b1
teardown conn
teardown db                 ← nextitem เป็น None: ปิดทั้ง stack
```

จาก Log นี้เราเห็นสามอย่าง

- ระหว่าง `test_a1` กับ `test_a2` จะไม่มี `teardown conn` เพราะ `nextitem` ยังอยู่ใน `Module` เดียวกัน
- ลำดับปิดจะย้อนจากลำดับตั้ง (`teardown tx` ก่อน `end test_a1` ซึ่งตั้งก่อน)
- `teardown db` มาเป็นอันสุดท้ายเพราะ Session อยู่ก้น Stack

ถ้า Finalizer ตัวหนึ่งโยน Exception ตัวที่เหลือก็ยังถูกรัน และ Pytest จะรวม Exception แล้วโยนทีเดียวตอนจบ (Source: `teardown_exact` เก็บ `exceptions` แล้วโยน `BaseExceptionGroup`) ในแบบฝึกมี `third` ที่ขอ `first` กับ `second` โดย `second` โยน Error ตอนปิด ผลคือ LOG ได้ `third, second, first` ครบสามตัว และรายงานได้ `ERROR at teardown of test_x` โดยที่ Test ผ่านและ Error แยกกัน (`2 passed, 1 error`) (รัน: `internals/13_fixture_engine.py`)

</Step>

## กฎของ Scope

Fixture ที่ Scope กว้างขอ Fixture ที่ Scope แคบกว่าไม่ได้ เพราะตัวแคบจะถูกปิดก่อนที่ตัวกว้างจะเสร็จ ถ้าขอ Pytest จะฟ้องตั้งแต่ต้น (Source: `_check_scope`) ในแบบฝึกมี `wide` (Session) ขอ `per_test` (Function) ผลคือ Test ได้ Error ที่ขึ้นต้นว่า `ScopeMismatch: You tried to access the function scoped fixture per_test with a session scoped request object` (รัน: `internals/13_fixture_engine.py`)

สำหรับ Fixture ที่มี `params` Pytest ยังเรียงลำดับ Test ใหม่หลัง Collection ด้วย `reorder_items` เพื่อให้ Test ที่ใช้ Param เดียวกันของ Fixture ระดับกว้างอยู่ติดกัน จะได้ลดจำนวนครั้งที่ต้องปิดและสร้างใหม่ ในแบบฝึกของ [บท 4](/pytest/parametrize/in-depth/#fixture-ที่มี-param-ลำดับการสร้าง) Fixture ระดับ Module ที่มีสอง Param ถูกสร้างตามลำดับ `build a`, `drop a`, `build b` แม้ Test จะเขียนปนกัน (Source: `reorder_items`)

<Callout type="try" title="ลองทำใน Repo นี้">
ลองรัน `uv run pytest exercises/03_fixtures/test_fixtures.py --setup-show -k "first_user or second_user or the_events"` แล้วเทียบกับ Log ด้านบน โดยดูที่ตัวอักษร `M` และ `F` จากนั้นแก้ `internals/04_setupstate.py` ให้ `conn` เป็น `scope="session"` แล้วดูว่า `teardown conn` ย้ายไปอยู่ตรงไหนของ Log
</Callout>

</Step>

## เช็กตัวเอง

- Fixture ระดับ Module ปิดเมื่อไร และ Pytest รู้ได้อย่างไรว่า Test ตัวนี้เป็นตัวสุดท้ายของ Module
- ถ้า Fixture ระดับ Module โยน Exception ตอน Setup มี Test 50 ตัวใช้มัน ฟังก์ชัน Fixture ถูกเรียกกี่ครั้ง
- ทำไม Closure ถึงเรียง Scope กว้างไปแคบ และถ้าเรียงกลับกันจะเกิดอะไร

</Step>
