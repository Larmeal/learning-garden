## สามเฟส สามรายงาน

ในบท [Pytest ทำงานอย่างไร](/pytest/how-pytest-runs/#ลำดับ-hook-จริงสำหรับ-test-สองตัว) เราเห็นแล้วว่าแต่ละ Test มี `makereport` สามครั้ง คราวนี้เรามาดูกันว่ามันมาจากไหน ตัวที่ควบคุมอยู่คือ `runtestprotocol` ใน `_pytest/runner.py` (Source) ซึ่งย่อได้ดังนี้

```python
rep = call_and_report(item, "setup", log)
reports = [rep]
if rep.passed:
    ...
    reports.append(call_and_report(item, "call", log))
reports.append(call_and_report(item, "teardown", log, nextitem=nextitem))
```

จากโค้ดนี้เราอ่านได้สองข้อ

- เฟส Call จะรันก็ต่อเมื่อ Setup ผ่านเท่านั้น ถ้า Fixture พัง ตัว Test จะไม่ถูกเรียกเลย
- เฟส Teardown จะรันเสมอ แม้ Setup หรือ Call จะล้ม เพื่อให้ของที่ตั้งไปแล้วถูกเก็บกวาด

แต่ละเฟสผ่าน `call_and_report` ซึ่งเลือก Hook ตามเฟส (`pytest_runtest_setup`, `pytest_runtest_call`, `pytest_runtest_teardown`) แล้วห่อการเรียกไว้ด้วย `CallInfo.from_call`

</Step>

## CallInfo: จับ Exception ไว้เป็นข้อมูล

`CallInfo.from_call(func, when)` จะเรียกฟังก์ชัน จับเวลา และถ้ามี Exception ก็เก็บไว้เป็น `excinfo` แทนที่จะปล่อยให้ลอยขึ้นไป (Source: `CallInfo` ใน `runner.py`) Field ที่มีคือ `result`, `excinfo`, `start`, `stop`, `duration` และ `when` (`collect`, `setup`, `call` หรือ `teardown`)

Exception ส่วนใหญ่จะถูกจับ เพราะ Test ที่ล้มต้องไม่ทำให้ Session ตาย มีข้อยกเว้นสองชนิดที่ `from_call` โยนซ้ำ (Source: `get_reraise_exceptions`)

- `Exit` จาก `pytest.exit()` ที่ตั้งใจให้หยุดทั้ง Session
- `KeyboardInterrupt` ยกเว้นเมื่อใช้ `--pdb` เพราะ Debugger ต้องจัดการเอง

เมื่อ Exception ถูกจับแบบนี้ สิ่งที่โค้ดของเราโยนจึงกลายเป็น **ข้อมูลใน Report** และนี่เป็นเหตุผลที่ Plugin อ่านเหตุที่ล้มได้จาก `call.excinfo` โดยไม่ต้อง Try/Except

</Step>

## แต่ละเฟสทำอะไรกับ Function

สำหรับ Test ที่เป็น `Function` สามเฟสคือ (Source: `pytest_runtest_setup`, `pytest_runtest_call`, `pytest_runtest_teardown` ใน `runner.py`, `Function.setup` และ `pytest_pyfunc_call` ใน `python.py`)

| เฟส | ทำอะไร |
|---|---|
| Setup | `SetupState.setup(item)` เรียก `setup()` ของ Node ในสายตั้งแต่ Session ลงมา ตัว `Function.setup` เติม Fixture ที่ Test ขอ (บท [Fixture Engine](/pytest/fixture-engine/#รัน-fixture-หนึ่งตัว)) |
| Call | `item.runtest()` ซึ่งเรียก Hook `pytest_pyfunc_call` ฟังก์ชันของเราถูกเรียกด้วย Fixture ที่ได้เป็น Keyword Argument |
| Teardown | `SetupState.teardown_exact(nextitem)` ปิด Node ที่หมดหน้าที่ตามกฎของ `nextitem` |

`pytest_pyfunc_call` ยังทำอีกเรื่องเล็ก ๆ คือถ้า Test คืนค่าที่ไม่ใช่ `None` Pytest จะออก `PytestReturnNotNoneWarning` ("Did you mean to use `assert` Instead of `return`?") แบบฝึกยืนยันว่า Test ที่ `return 1 == 2` ผ่านพร้อม Warning ซึ่งเป็นกับดักที่เจอบ่อย (รัน: `exercises/08_design/test_smells.py`) ส่วนฟังก์ชัน Async จะถูกปฏิเสธ เพราะ Pytest เองไม่รัน Coroutine

</Step>

## TestReport: ผลของหนึ่งเฟส

`pytest_runtest_makereport(item, call)` สร้าง `TestReport` ขึ้นมาหนึ่งใบต่อหนึ่งเฟส (Source: `TestReport.from_item_and_call` ใน `reports.py`) Field สำคัญคือ `nodeid`, `when`, `outcome` (`passed`, `failed`, `skipped`), `longrepr` (ข้อความที่พิมพ์ตอนล้ม), `sections` (ข้อความที่ดักได้), `duration` และ `user_properties` ที่ Plugin เติมได้ แล้ว Report จะถูกส่งไปทาง `pytest_runtest_logreport` ให้ Terminal, Junitxml และ Plugin อื่นอ่าน

สคริปต์ `internals/05_reports.py` รันโปรเจกต์ที่มี Test เก้าแบบ แล้วบันทึกรายงานทุกใบไว้ (รัน: `internals/05_reports.py`)

| Test | รายงานของแต่ละเฟส |
|---|---|
| ผ่านปกติ | Setup:Passed Call:Passed Teardown:Passed |
| `assert` ผิด | Setup:Passed **Call:Failed** Teardown:Passed |
| Fixture พังตอน Setup | **Setup:Failed** Teardown:Passed (ไม่มี Call) |
| Fixture พังตอน Teardown | Setup:Passed Call:Passed **Teardown:Failed** |
| `pytest.skip()` ใน Test | Setup:Passed **Call:Skipped** Teardown:Passed |
| `@pytest.mark.skip` | **setup:skipped** teardown:passed |
| `@pytest.mark.xfail` ที่ล้ม | Setup:Passed Call:skipped(Xfail:Known) Teardown:Passed |
| `@pytest.mark.xfail` ที่ผ่าน | Setup:Passed Call:passed(Xfail:Fixed Already) Teardown:Passed |
| `@pytest.mark.xfail(strict=True)` ที่ผ่าน | Setup:Passed **Call:Failed** Teardown:Passed |

สรุปท้ายรายงานของโปรเจกต์นี้คือ `2 failed, 2 passed, 2 skipped, 1 xfailed, 1 xpassed, 2 errors` ตัวเลขแต่ละช่องมาจากรายงานคนละใบ โดย **Failed** นับรายงาน Call ที่ล้ม ส่วน **Errors** นับรายงาน Setup หรือ Teardown ที่ล้ม นี่เป็นเหตุผลที่ Test ที่ผ่านแต่ Fixture พังตอนปิดถูกนับทั้ง Passed และ Error

</Step>

## Skip และ Xfail เป็น Hook ไม่ใช่เวทมนตร์

ทั้งสองอยู่ใน Plugin `skipping` (Source: `_pytest/skipping.py`) และเกี่ยวกับ Hook สองจุด

- `pytest_runtest_setup` ประเมิน Marker `skip` และ `skipif` ถ้าเข้าเงื่อนไขก็โยน `skip.Exception` ผลคือ Test ถูกรายงานเป็น Skipped ที่ **เฟส Setup** ก่อนที่ Fixture ใดจะถูกเรียก (ตรงกับแถว `@pytest.mark.skip` ในตาราง) ส่วน `xfail` จะถูกประเมินแล้วเก็บไว้ใน `item.stash`
- ตัวครอบ `pytest_runtest_makereport` ปล่อยให้ Report ถูกสร้างตามปกติ (`yield`) แล้วจึง **เปลี่ยนผล** ตามที่ Xfail ตั้งไว้ (Source: ตัวครอบนี้ใน `skipping.py`) โดยแบ่งได้เป็นสี่กรณี
  - ถ้าล้มและเข้าเงื่อนไข (รวม `raises=`) จะเป็น `outcome = "skipped"` และมี `wasxfail`
  - ถ้าล้มแต่ Exception ไม่ตรง `raises=` จะยังเป็น `failed`
  - ถ้าผ่านและไม่ Strict จะเป็น `passed` พร้อม `wasxfail` ซึ่งก็คือ XPASS
  - ถ้าผ่านและ Strict จะเป็น `failed` พร้อมข้อความ `[XPASS(strict)] เหตุผล`

ตารางด้านบนยืนยันทุกแถว และตรงกับสิ่งที่บท [Marker](/pytest/markers/#xfail-รู้ว่าล้ม-แต่ยังรันอยู่) บรรยายจากภายนอก จุดสำคัญคือ **Skipped ของ Xfail เกิดจากการเปลี่ยน Outcome ทีหลัง** Pytest ไม่ได้ข้าม Test ไป เพราะตัว Test ถูกรันจริงในเฟส Call

ถ้าใส่ `--runxfail` ตัวครอบนี้จะไม่เข้ามายุ่ง (Source: เงื่อนไข `item.config.option.runxfail`) Test ที่ทำเครื่องหมาย Xfail จึงรายงานผลจริง เหมาะตอนอยากรู้ว่า Bug ที่รู้แล้วยังอยู่ไหม

</Step>

## เมื่อ Session ต้องหยุด

หลัง `setup` และ `call` ถ้า `session.shouldfail` หรือ `session.shouldstop` ถูกตั้ง (เช่นจาก `-x` หรือ `--maxfail`) `runtestprotocol` จะตั้ง `nextitem = None` ก่อนเรียก Teardown (Source: คอมเมนต์ในโค้ดบอกว่าเพื่อรายงาน Teardown Error ให้ถูก) ผลคือ Teardown จะปิดทั้ง Stack ของ `SetupState` ทันที แทนที่จะรอ Test ถัดไปซึ่งจะไม่มีวันมา Fixture ระดับ Module และ Session จึงถูกปิดแม้ Run ถูกตัดกลางคัน

ในแบบฝึก `--maxfail=1 -q` จะหยุดหลังล้มตัวแรกและสรุป `1 failed, 1 passed` พร้อมข้อความ `stopping after 1 failures` (รัน: `internals/08_output_flags.py`)

<Callout type="try" title="ลองทำใน Repo นี้">
ลองรัน `uv run python internals/05_reports.py` แล้วเพิ่ม Test ใหม่ใน `FILES` ที่ใช้ `bad_setup` และ `bad_teardown` พร้อมกัน เพื่อดูว่ารายงานของมันมีกี่ใบ และ Outcome ของแต่ละเฟสเป็นอะไร จากนั้นเพิ่ม `@pytest.mark.xfail(raises=KeyError)` บน Test ที่โยน `ValueError` แล้วลองทำนายผลก่อนรัน
</Callout>

</Step>

## เช็กตัวเอง

- Fixture พังตอน Setup ของ Test หนึ่ง ผลสรุปนับเป็น Failed หรือ Error และ Test ตัวนั้นถูกเรียกไหม
- Test ที่ `@pytest.mark.xfail` และล้มจริง รายงานเฟส Call มี Outcome อะไร และทำไมถึงเป็นอย่างนั้นทั้งที่ Test รันจริง
- ทำไม `-x` ถึงต้องตั้ง `nextitem = None` ตอน Teardown

</Step>
