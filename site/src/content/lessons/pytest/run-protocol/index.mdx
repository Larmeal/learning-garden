## สามเฟส สามรายงาน

บท [Pytest ทำงานอย่างไร](/pytest/how-pytest-runs/#ลำดับ-hook-จริงสำหรับ-test-สองตัว) เห็นว่าแต่ละ test มี `makereport` สามครั้ง บทนี้ดูว่ามันมาจากไหน ตัวที่ควบคุมคือ `runtestprotocol` ใน `_pytest/runner.py` (source) ที่ย่อได้ดังนี้

```python
rep = call_and_report(item, "setup", log)
reports = [rep]
if rep.passed:
    ...
    reports.append(call_and_report(item, "call", log))
reports.append(call_and_report(item, "teardown", log, nextitem=nextitem))
```

สองข้อที่อ่านได้จากโค้ดนี้

- **เฟส call รันเมื่อ setup ผ่านเท่านั้น** ถ้า fixture พัง ตัว test ไม่ถูกเรียกเลย
- **เฟส teardown รันเสมอ** แม้ setup หรือ call ล้ม เพื่อให้ของที่ตั้งไปแล้วถูกเก็บกวาด

แต่ละเฟสผ่าน `call_and_report` ซึ่งเลือก hook ตามเฟส (`pytest_runtest_setup`, `pytest_runtest_call`, `pytest_runtest_teardown`) แล้วห่อการเรียกด้วย `CallInfo.from_call`

</Step>

## CallInfo: จับ Exception ไว้เป็นข้อมูล

`CallInfo.from_call(func, when)` เรียกฟังก์ชัน จับเวลา และถ้ามี exception ก็เก็บไว้เป็น `excinfo` แทนที่จะปล่อยให้ลอยขึ้นไป (source: `CallInfo` ใน `runner.py`) field ที่มีคือ `result`, `excinfo`, `start`, `stop`, `duration` และ `when` (`collect`, `setup`, `call` หรือ `teardown`)

exception ส่วนใหญ่ถูกจับ เหตุผลคือ test ที่ล้มต้องไม่ทำให้ session ตาย ข้อยกเว้นมีสองชนิดที่ `from_call` โยนซ้ำ (source: `get_reraise_exceptions`)

- `Exit` จาก `pytest.exit()` ที่ตั้งใจให้หยุดทั้ง session
- `KeyboardInterrupt` ยกเว้นเมื่อใช้ `--pdb` เพราะ debugger ต้องจัดการเอง

ผลของการจับคือ exception ที่โค้ดของเราโยนกลายเป็น **ข้อมูลใน report** ซึ่งเป็นเหตุผลที่ plugin อ่านเหตุที่ล้มได้จาก `call.excinfo` โดยไม่ต้อง try/except

</Step>

## แต่ละเฟสทำอะไรกับ Function

สำหรับ test ที่เป็น `Function` สามเฟสคือ (source: `pytest_runtest_setup`, `pytest_runtest_call`, `pytest_runtest_teardown` ใน `runner.py`, `Function.setup` และ `pytest_pyfunc_call` ใน `python.py`)

| เฟส | ทำอะไร |
|---|---|
| setup | `SetupState.setup(item)` เรียก `setup()` ของ node ในสายตั้งแต่ Session ลงมา ตัว `Function.setup` เติม fixture ที่ test ขอ (บท [Fixture Engine](/pytest/fixture-engine/#รัน-fixture-หนึ่งตัว)) |
| call | `item.runtest()` ซึ่งเรียก hook `pytest_pyfunc_call` ฟังก์ชันของเราถูกเรียกด้วย fixture ที่ได้เป็น keyword argument |
| teardown | `SetupState.teardown_exact(nextitem)` ปิด node ที่หมดหน้าที่ตามกฎของ `nextitem` |

มีรายละเอียดเล็กที่ `pytest_pyfunc_call` ทำ: ถ้า test คืนค่าที่ไม่ใช่ `None` pytest ออก `PytestReturnNotNoneWarning` ("Did you mean to use `assert` instead of `return`?") แบบฝึกยืนยันว่า test ที่ `return 1 == 2` ผ่านพร้อม warning ซึ่งเป็นกับดักที่เจอบ่อย (รัน: `exercises/08_design/test_smells.py`) ฟังก์ชัน async ถูกปฏิเสธ เพราะ pytest เองไม่รัน coroutine

</Step>

## TestReport: ผลของหนึ่งเฟส

`pytest_runtest_makereport(item, call)` สร้าง `TestReport` ต่อหนึ่งเฟส (source: `TestReport.from_item_and_call` ใน `reports.py`) field สำคัญคือ `nodeid`, `when`, `outcome` (`passed`, `failed`, `skipped`), `longrepr` (ข้อความที่พิมพ์ตอนล้ม), `sections` (ข้อความที่ดักได้), `duration` และ `user_properties` ที่ plugin เติมได้ report ถูกส่งไปทาง `pytest_runtest_logreport` ให้ terminal, junitxml และ plugin อื่นอ่าน

`internals/05_reports.py` รันโปรเจกต์ที่มี test เก้าแบบ แล้วบันทึกรายงานทุกใบ (รัน: `internals/05_reports.py`)

| test | รายงานของแต่ละเฟส |
|---|---|
| ผ่านปกติ | setup:passed call:passed teardown:passed |
| `assert` ผิด | setup:passed **call:failed** teardown:passed |
| fixture พังตอน setup | **setup:failed** teardown:passed (ไม่มี call) |
| fixture พังตอน teardown | setup:passed call:passed **teardown:failed** |
| `pytest.skip()` ใน test | setup:passed **call:skipped** teardown:passed |
| `@pytest.mark.skip` | **setup:skipped** teardown:passed |
| `@pytest.mark.xfail` ที่ล้ม | setup:passed call:skipped(xfail:known) teardown:passed |
| `@pytest.mark.xfail` ที่ผ่าน | setup:passed call:passed(xfail:fixed already) teardown:passed |
| `@pytest.mark.xfail(strict=True)` ที่ผ่าน | setup:passed **call:failed** teardown:passed |

สรุปท้ายรายงานของโปรเจกต์นี้คือ `2 failed, 2 passed, 2 skipped, 1 xfailed, 1 xpassed, 2 errors` ตัวเลขแต่ละช่องมาจากรายงานต่างใบ: **failed** นับรายงาน call ที่ล้ม ส่วน **errors** นับรายงาน setup หรือ teardown ที่ล้ม นี่คือเหตุผลที่ test ที่ผ่านแต่ fixture พังตอนปิดถูกนับทั้ง passed และ error

</Step>

## Skip และ Xfail เป็น Hook ไม่ใช่เวทมนตร์

ทั้งสองอยู่ใน plugin `skipping` (source: `_pytest/skipping.py`) และใช้สองจุดต่อ

- **`pytest_runtest_setup`** ประเมิน marker `skip` และ `skipif` ถ้าเข้าเงื่อนไขก็โยน `skip.Exception` ผลคือ test ถูกรายงานเป็น skipped ที่ **เฟส setup** ก่อนที่ fixture ใดจะถูกเรียก (ตรงกับแถว `@pytest.mark.skip` ในตาราง) ส่วน `xfail` ถูกประเมินและเก็บไว้ใน `item.stash`
- **ตัวครอบ `pytest_runtest_makereport`** ปล่อยให้ report ถูกสร้างตามปกติ (`yield`) แล้ว **เปลี่ยนผล** ตามที่ xfail ตั้งไว้ (source: ตัวครอบนี้ใน `skipping.py`)
  - ล้มและเข้าเงื่อนไข (รวม `raises=`) เป็น `outcome = "skipped"` และมี `wasxfail`
  - ล้มแต่ exception ไม่ตรง `raises=` ยังเป็น `failed`
  - ผ่านและไม่ strict เป็น `passed` พร้อม `wasxfail` นี่คือ XPASS
  - ผ่านและ strict เป็น `failed` พร้อมข้อความ `[XPASS(strict)] เหตุผล`

ตารางด้านบนยืนยันทุกแถว และตรงกับสิ่งที่บท [Marker](/pytest/markers/#xfail-รู้ว่าล้ม-แต่ยังรันอยู่) บรรยายจากภายนอก จุดสำคัญคือ **skipped ของ xfail เกิดจากการเปลี่ยน outcome ทีหลัง** ไม่ใช่ pytest ข้าม test ตัว test ถูกรันจริงในเฟส call

`--runxfail` ทำให้ตัวครอบนี้ไม่ยุ่ง (source: เงื่อนไข `item.config.option.runxfail`) test ที่ทำเครื่องหมาย xfail จึงรายงานผลจริง ใช้ตอนอยากรู้ว่า bug ที่รู้แล้วยังอยู่ไหม

</Step>

## เมื่อ Session ต้องหยุด

หลัง `setup` และ `call` ถ้า `session.shouldfail` หรือ `session.shouldstop` ถูกตั้ง (เช่นจาก `-x` หรือ `--maxfail`) `runtestprotocol` ตั้ง `nextitem = None` ก่อนเรียก teardown (source: คอมเมนต์ในโค้ดบอกว่าเพื่อรายงาน teardown error ให้ถูก) ผลคือ teardown ปิดทั้ง stack ของ `SetupState` ทันที แทนที่จะรอ test ถัดไป ซึ่งจะไม่มีวันมา fixture ระดับ module และ session จึงถูกปิดแม้ run ถูกตัดกลางคัน

`--maxfail=1 -q` ในแบบฝึกหยุดหลังล้มตัวแรกและสรุป `1 failed, 1 passed` พร้อมข้อความ `stopping after 1 failures` (รัน: `internals/08_output_flags.py`)

<Callout type="try" title="ลองทำใน repo นี้">
รัน `uv run python internals/05_reports.py` แล้วเพิ่ม test ใหม่ใน `FILES` ที่ใช้ `bad_setup` และ `bad_teardown` พร้อมกัน ดูว่ารายงานของมันมีกี่ใบ และ outcome ของแต่ละเฟสเป็นอะไร จากนั้นเพิ่ม `@pytest.mark.xfail(raises=KeyError)` บน test ที่โยน `ValueError` แล้วทำนายผลก่อนรัน
</Callout>

</Step>

## เช็กตัวเอง

- fixture พังตอน setup ของ test หนึ่ง ผลสรุปนับเป็น failed หรือ error และ test ตัวนั้นถูกเรียกไหม
- test ที่ `@pytest.mark.xfail` และล้มจริง รายงานเฟส call มี outcome อะไร และทำไมถึงเป็นอย่างนั้นทั้งที่ test รันจริง
- ทำไม `-x` ถึงต้องตั้ง `nextitem = None` ตอน teardown

</Step>
