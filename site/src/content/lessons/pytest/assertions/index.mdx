## Assert ธรรมดา แต่ได้ข้อมูลมากกว่าที่คิด

[บท 1](/pytest/first-test/#อ่าน-traceback-ตอน-test-ล้ม) เราเห็นว่า `assert cart.total() == 31` ล้มแล้ว Pytest พิมพ์ `assert 30 == 31` ให้ ทั้งที่เราไม่ได้เขียน message Pytest เปลี่ยนโค้ด `assert` ใน test ไฟล์ **ก่อน** รัน (assertion rewriting) ให้เก็บค่าของนิพจน์ย่อยไว้แสดง ผลคือเราใช้ `assert` เปล่าๆ ได้ ไม่ต้องจำ `assertEqual`, `assertIn`, `assertAlmostEqual` ของ unittest

บทนี้ดูสามเรื่องที่ `==` เปล่าๆ ไม่พอ: ทศนิยม, exception, และ warning แล้วค่อยดูวิธีอ่าน diff

</Step>

## ทศนิยมต้องใช้ Approx

```python
def test_float_sums_need_approx():
    assert 0.1 + 0.2 != 0.3
    assert 0.1 + 0.2 == pytest.approx(0.3)
```

`0.1 + 0.2` ใน float ไม่เท่ากับ `0.3` พอดี (รัน: `exercises/02_assertions/test_assertions.py`) `pytest.approx` เทียบแบบมีความคลาดเคลื่อนที่ยอมได้ ค่าเริ่มต้นคือ relative 1e-6 ซึ่งเห็นในผลตอนล้ม

```text
E       assert 0.5 == 0.3 ± 3.0e-07
E         Obtained: 0.5
E         Expected: 0.3 ± 3.0e-07
```

กำหนดความคลาดเคลื่อนเองได้ และใช้กับ list หรือ dict ได้ (รัน: `exercises/02_assertions/test_assertions.py`)

```python
assert 100.04 == pytest.approx(100, abs=0.05)    # ห่างได้ไม่เกิน 0.05
assert 100.04 != pytest.approx(100, abs=0.01)
assert 100.04 == pytest.approx(100, rel=1e-3)    # ห่างได้ไม่เกิน 0.1% ของ 100
assert [0.1 + 0.2, 1.1 + 2.2] == pytest.approx([0.3, 3.3])
assert {"a": 0.1 + 0.2} == pytest.approx({"a": 0.3})
```

ข้อควรจำ: เรื่องเงิน ควรใช้ `Decimal` หรือเก็บเป็นสตางค์ (จำนวนเต็ม) ตั้งแต่แรก `approx` ช่วยตอนทดสอบผลคำนวณ float ที่หลีกเลี่ยงไม่ได้ ไม่ได้ทำให้ float ปลอดภัยสำหรับเงิน (ผู้เขียน)

</Step>

## เช็กว่าโค้ดโยน Exception ด้วย Raises

test ที่ดีต้องเช็กทางที่ล้มด้วย ไม่ใช่เฉพาะทางที่สำเร็จ `pytest.raises` เป็น context manager

```python
def test_raises_checks_the_type():
    with pytest.raises(ValueError):
        Cart().add("apple", price=10, qty=0)

def test_raises_with_match_checks_the_message():
    with pytest.raises(ValueError, match=r"qty must be positive, got -1"):
        Cart().add("apple", price=10, qty=-1)
```

| สิ่งที่ต้องการ | ใช้ | ผล (รัน: `exercises/02_assertions/test_assertions.py`) |
|---|---|---|
| เช็กชนิดของ exception | `pytest.raises(ValueError)` | ผ่านเมื่อโยน `ValueError` หรือ subclass |
| เช็กข้อความ | `match="positive"` | เป็น regular expression ที่ **ค้นหา** ในข้อความ ส่วนหนึ่งของข้อความพอ ไม่ต้องตรงทั้งหมด |
| อ่านค่าใน exception | `with pytest.raises(E) as info:` แล้วใช้ `info.value`, `info.type` | เช็กได้ทั้งข้อความและ attribute |
| ตัวแม่ก็จับได้ | `pytest.raises(LookupError)` | `KeyError` เป็น `LookupError` จึงผ่าน |

สองจุดที่พลาดบ่อย

1. **ไม่ได้โยน** ถ้าโค้ดไม่โยน exception ที่คาด test จะล้มด้วยข้อความ `Failed: DID NOT RAISE ValueError` (รัน: `demos/02_assertions`) ซึ่งถูกต้อง เพราะ test บอกว่ารับประกันว่าจะโยน
2. **บรรทัดในบล็อก** บรรทัดหลังบรรทัดที่โยนในบล็อกเดียวกันไม่ถูกรัน และบรรทัดก่อนหน้ามีผลจริง ในแบบฝึก `add("apple")` สำเร็จก่อนบรรทัดที่โยน จึงยังเหลือ `qty("apple") == 1` หลังบล็อก (รัน: `exercises/02_assertions/test_assertions.py`) ใส่ในบล็อกเฉพาะบรรทัดที่คาดว่าจะโยน

</Step>

## Warnings

โค้ดเก่าที่ถูกเลิกใช้มักโยน `DeprecationWarning` ไม่ใช่ exception `pytest.warns` ใช้เช็ก

```python
def test_warns_catches_a_deprecation():
    with pytest.warns(DeprecationWarning, match="old_total"):
        assert old_total([1, 2, 3]) == 6
```

ด้านกลับกัน ถ้าอยากให้โค้ดใหม่ **ไม่มี** warning ใช้ `warnings.simplefilter("error")` ให้ warning กลายเป็น exception ใน test นั้น (รัน: `exercises/02_assertions/test_assertions.py` ตัว `test_no_warning_for_the_new_code`) วิธีนี้จับการเรียก API ที่กำลังจะเลิกใช้ก่อนที่มันจะพังจริง

</Step>

## อ่าน Diff

เมื่อเทียบ dict, list หรือ string ที่ใหญ่ Pytest แสดงเฉพาะส่วนที่ต่าง (รัน: `demos/02_assertions`)

```text
E       AssertionError: assert {'sku': 'appl..., 'price': 10} == {'sku': 'appl...note': 'gift'}
E         Omitting 2 identical items, use -vv to show
E         Differing items:
E         {'qty': 3} != {'qty': 2}
E         Right contains 1 more item:
E         {'note': 'gift'}
```

อ่านได้ทันทีว่า `qty` ต่างกัน (3 กับ 2) และฝั่งขวามี key `note` เพิ่ม ส่วน `-vv` ขยายข้อความที่ถูกย่อ

string ที่ต่างกันตัวเดียว Pytest ชี้ตำแหน่งด้วย `^`

```text
E         - total: 31 THB
E         ?         ^
E         + total: 30 THB
E         ?         ^
```

เปรียบเทียบสิ่งที่ลำดับไม่สำคัญ เช่น รายการ SKU ที่ไม่สนลำดับ แปลงเป็น `set` ก่อนเทียบ แต่ถ้าลำดับเป็นส่วนหนึ่งของสัญญา (เช่น `skus()` คืนตามตัวอักษร) เทียบ list ตรงๆ (รัน: `exercises/02_assertions/test_assertions.py`)

</Step>

## เมื่อไรควรเขียน Message เอง

Pytest บอก **ค่า** อยู่แล้ว message ที่เขียนเองมีประโยชน์เมื่ออธิบาย **เหตุผล** ที่ค่าสองฝั่งควรเท่ากัน

```python
assert cart.qty("apple") == 1, "one apple was added, so qty must be 1"
```

ถ้า message แค่ซ้ำกับค่า เช่น `"total is wrong"` ก็ไม่ต้องเขียน และถ้า test หนึ่งตัวมี assert หลายบรรทัด ให้ดูว่า message ช่วยแยกว่าบรรทัดไหนล้มจริง (ผู้เขียน)

<Callout type="try" title="ลองทำใน repo นี้">
เปิด `demos/02_assertions/test_diffs.py` รัน `uv run pytest demos/02_assertions` แล้วอ่านทั้งห้าผลล้ม จากนั้นแก้ `test_raises_not_raised` ให้ผ่าน (คำใบ้: `int("42")` ไม่โยนอะไร ควรเรียกอะไรแทน)
</Callout>

## เช็กตัวเอง

- ทำไม `assert price * qty == 0.3` จึงไม่ควรใช้เปล่าๆ เมื่อ price เป็น 0.1 และ qty เป็น 3 และควรเขียนใหม่อย่างไร
- `with pytest.raises(ValueError, match="positive")` ผ่านเมื่อข้อความคือ `qty must be positive, got 0` ได้ไหม ทำไม
- ถ้าใส่โค้ดสิบบรรทัดในบล็อก `raises` ปัญหาคืออะไร

</Step>
