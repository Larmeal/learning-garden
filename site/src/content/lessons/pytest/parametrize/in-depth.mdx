## `ids`: จากรายการ จากฟังก์ชัน และที่ Pytest สร้างให้

`ids=` รับได้สองแบบ (รัน: `exercises/04_parametrize/test_parametrize_in_depth.py`)

```python
def label(value):
    return f"{value}pct"

@pytest.mark.parametrize("percent", [10, 20, 50], ids=label)        # ฟังก์ชัน: ได้ [10pct], [20pct], [50pct]
def test_ids_from_a_function(percent): ...

@pytest.mark.parametrize("code, off", [("SAVE10", 10), ("SAVE20", 20)], ids=["small", "large"])
def test_ids_from_a_list(code, off): ...
```

ฟังก์ชันจะถูกเรียกกับ **ค่าแต่ละตัว** (ไม่ใช่ทั้งแถว) ส่วนรายการต้องยาวเท่ากับจำนวนแถว

ถ้าเราไม่ใส่ Pytest ก็จะสร้าง id ให้เอง แบบฝึกส่ง `[1, "a b", None, 2.5, b"z", (1, 2), [3]]` เข้า Test เพื่อดูว่า id ออกมาเป็นอย่างไร (รัน)

| ค่า | id ที่ได้ |
|---|---|
| `1`, `2.5`, `None` | `1`, `2.5`, `None` |
| สตริง `"a b"` | `a b` |
| bytes `b"z"` | `z` |
| Tuple `(1, 2)` และ List `[3]` | `x5`, `x6` (ชื่อ Parameter กับลำดับแถว เพราะแปลงเป็นข้อความที่อ่านได้ไม่ได้) |

จะเห็นว่าค่าง่าย ๆ (ตัวเลข สตริง `None`) ได้ id ที่อ่านรู้เรื่อง แต่ Object ซับซ้อนจะได้ `x5` ซึ่งไม่บอกอะไรเลย ถ้าเจอแบบนั้นให้ใส่ `ids=` หรือ `pytest.param(..., id="...")` ([บท 4](/pytest/parametrize/#ids-ตั้งชื่อให้อ่านรู้เรื่อง))

</Step>

## pytest_generate_tests: เขียนตัวสร้างเอง

เมื่อชุดค่าต้องคำนวณ หรือต้องใช้กับ Test หลายตัวที่ขอ Fixture ชื่อเดียวกัน เราเขียน Hook `pytest_generate_tests(metafunc)` ในไฟล์ได้ ซึ่งเป็นจุดเดียวกับที่ `@pytest.mark.parametrize` ใช้อยู่ภายใน ([บท 10](/pytest/collection/#หนึ่งฟังก์ชัน-หลาย-function-parametrize-ทำงานตรงนี้))

```python
def pytest_generate_tests(metafunc):
    if "coupon_code" in metafunc.fixturenames:
        metafunc.parametrize("coupon_code", ["SAVE10", "SAVE20", "FREE"])

def test_generated_per_coupon(coupon_code):
    assert 0 < discount_for(coupon_code) <= 100
```

`test_generated_per_coupon` ไม่มี Marker อะไรเลย แต่ก็ถูก Collect เป็น 3 Test เพราะ Parameter ชื่อ `coupon_code` ถูก Hook จับไว้ (รัน) โดย `metafunc.fixturenames` จะบอกว่า Test นี้ขออะไรบ้าง เราจึงตัดสินใจได้ว่าจะ Parametrize หรือไม่ และเพราะ `metafunc.config` อ่าน Option ของ Pytest ได้ เราจึงใช้เปลี่ยนชุดค่าตาม Option เช่น `--run-slow` ได้ด้วย

</Step>

## Fixture ที่มี Param: ลำดับการสร้าง

สมมติว่ามี Fixture ระดับ Module ที่มีสอง Param (`"a"` และ `"b"`) และถูกใช้โดยสอง Test ผลลัพธ์ที่บันทึกได้คือ `["build a", "drop a", "build b"]` (รัน) เพราะ Pytest **จัดลำดับ Test ใหม่** ให้ทุก Test ที่ใช้ Param `a` มาอยู่ก่อน จึงสร้างและปิด `a` แค่ครั้งเดียว แล้วค่อยไปที่ `b` แทนที่จะสลับ a, b, a, b ตามลำดับที่เขียน นี่คือ `reorder_items` ที่บท [Fixture Engine](/pytest/fixture-engine/#กฎของ-scope) กล่าวถึง

ในแง่การออกแบบ ถ้า Fixture แพง (เช่น เริ่ม Database) การให้มี Param และ Scope ใหญ่จะไม่ทำให้สร้างซ้ำเกินจำเป็น แต่ลำดับที่ Test รันจะไม่ใช่ลำดับที่เขียนในไฟล์ ซึ่งเป็นอีกเหตุผลหนึ่งที่ Test ต้องไม่พึ่งลำดับ ([บท 15](/pytest/test-design/#test-ต้องอิสระต่อกัน))

</Step>

## ชุดว่าง, การบัง และ Class

**ชุดว่าง** `@pytest.mark.parametrize("x", [])` จะไม่ทำให้ Test หายไปเงียบ ๆ ค่าเริ่มต้นคือ Test ถูก Skip พร้อมข้อความ `got empty parameter set` (รัน) ถ้ากังวลว่าข้อมูลที่ประกอบเป็นรายการอาจว่างโดยไม่ตั้งใจ ให้ตั้ง `empty_parameter_set_mark = fail_at_collect` ใน Config เพื่อให้ Collect ล้มแทน แบบฝึกได้ `errors=1` (รัน)

**Parameter บัง Fixture** ถ้า Fixture ชื่อ `percent` ส่งค่า 99 และ Test ถูก Parametrize ด้วยชื่อ `percent` ค่า 10 จาก `parametrize` จะ **ชนะ** Fixture (รัน) ในแบบฝึกดูได้จาก Test ที่ยืนยัน `percent == 10` วิธีนี้เหมาะเมื่ออยากทับ Fixture เฉพาะ Test แต่ถ้าเกิดขึ้นโดยไม่ตั้งใจจะทำให้งง เราจึงควรตั้งชื่อให้ต่างกัน

**Parametrize บน Class** `@pytest.mark.parametrize("sku", ["apple", "pear"])` เหนือ Class จะใช้กับ **ทุก Method** ในแบบฝึกมีสอง Method คูณสองค่าได้ 4 Test (รัน)
