## สอน API ให้รู้จักชนิดใหม่

ในบท [Label และ API](/kubernetes/labels-and-api/) เราเห็นว่าคลัสเตอร์มีออบเจ็กต์ 58 ชนิด คราวนี้เราจะเพิ่มชนิดที่ 59 เอง ผ่านออบเจ็กต์ชื่อ CustomResourceDefinition (CRD) ที่บอก API ว่ามีชนิดใหม่ชื่อ `Greeter` ในกลุ่ม `lab.example.com` มีฟิลด์ `message` กับ `replicas` ที่ต้องอยู่ในช่วง 1 ถึง 5 (หนังสือ: Programming Kubernetes หัวข้อ Type Definitions หน้า 74)

พอสร้าง CRD ได้ ผลที่เห็นคือ `kubectl api-resources` มีชนิดเพิ่มอีกหนึ่ง ชื่อ `greeters` ที่ชื่อสั้น `gr` และอยู่ใน Namespace (รัน) และ `kubectl explain greeter.spec` ก็อ่านชื่อฟิลด์จาก Schema ที่เราเขียนได้ทันที (รัน) แต่ที่น่าสนใจคือ API Server ตรวจ Schema ให้เอง ถ้าเราสร้าง Greeter ที่มี `replicas: 9` จะถูกปฏิเสธด้วยข้อความ `spec.replicas in body should be less than or equal to 5` และถ้าใส่ข้อความแทนตัวเลขก็ถูกปฏิเสธว่า `must be of type integer` ไม่มีอะไรถูกเก็บไว้เลย (รัน) (หนังสือ: Programming Kubernetes หัวข้อ Validating Custom Resources หน้า 76) เรายังตั้งชื่อสั้นกับคอลัมน์ที่โชว์ใน `kubectl get` ได้ด้วย (หนังสือ: Programming Kubernetes หัวข้อ Short Names and Categories หน้า 78 และ Printer Columns หน้า 80)

</Step>

## CRD อย่างเดียวไม่ทำอะไรเลย

เราสร้าง Greeter ชื่อ `hello` ที่ขอ 2 ตัว แล้วรอสี่วินาที ผลคือมันอยู่ในรายการ `kubectl get gr` พร้อมคอลัมน์ที่เรากำหนด แต่ไม่มี Deployment ไม่มี Pod และ `status` ว่างเปล่า (รัน) ออบเจ็กต์ถูกเก็บอยู่ใน `etcd` เป็นคีย์ `/registry/lab.example.com/greeters/<namespace>/hello` เหมือนออบเจ็กต์ชนิดอื่น (รัน) CRD บอกแค่ว่า "ชนิดนี้มีอยู่และหน้าตาเป็นอย่างไร" ไม่ได้บอกว่าให้ทำอะไรเมื่อมีออบเจ็กต์ชนิดนี้ นี่คือสิ่งที่ Controller ทำใน[บทแรก](/kubernetes/why-kubernetes/)ไม่ได้เกิดขึ้นเอง และเป็นที่มาของคำว่า Operator

Operator คือ Controller ที่เขียนขึ้นเองสำหรับงานเฉพาะอย่าง โดยอ่านออบเจ็กต์ชนิดใหม่ของเราแล้วทำให้โลกจริงตรงกับมัน (หนังสือ: Programming Kubernetes หัวข้อ Operators หน้า 16 และ Kubernetes Up and Running หัวข้อ Operators หน้า 205) ที่เรียกว่า Operator เพราะมันเข้ามาทำงานแทนคนที่ดูแลระบบ เช่น ฐานข้อมูลที่ต้องรู้ว่าตอนไหนต้อง Failover

</Step>

## Operator ตัวเล็กที่อ่านได้ในหนึ่งหน้า

เราเขียน Operator ตัวหนึ่งเป็นสคริปต์ Python สั้น ๆ ใน `operator_lab.py` ที่ทำสามอย่างซ้ำทุกวินาที ดูว่า Greeter มีอะไรบ้าง เทียบกับ Deployment ที่ควรมี แล้วแก้ให้ตรง คือสร้าง Deployment ที่ชื่อ `greeter-<ชื่อ>` ตามจำนวน `replicas` และข้อความของ Greeter ใส่ `ownerReference` ชี้กลับไปที่ Greeter และเขียน `status` กลับ กดเล่น Lab นี้เพื่อดู Loop ทำงาน

<OperatorLab client:visible />

ในการรันจริง เมื่อเปิด Operator Greeter ก็กลายเป็น `Ready` ภายในสองสามวินาที (รัน) เราลองลบ Deployment ทิ้งเอง Operator เห็นในรอบถัดไปว่าของหายและสร้างใหม่ (ได้ `uid` ใหม่) จนกลับเป็น `Ready` อีกครั้ง (รัน) จากนั้นเราแก้ Greeter เป็น `replicas: 4` กับข้อความใหม่ Operator เห็นว่า Deployment ต่างจาก `spec` จึงอัปเดต Pod ตอบข้อความใหม่ได้ครบ 4 ตัว (รัน) บันทึกของ Operator สรุปเป็นสามบรรทัด สร้างหนึ่งครั้ง (ตอนเริ่ม) สร้างซ้ำหนึ่งครั้ง (ซ่อมของที่ถูกลบ) และอัปเดตหนึ่งครั้ง (รัน)

Operator ตัวนี้ Poll ทุกวินาที ส่วน Operator ของจริงมักใช้ Watch ที่เรียนในบท [Control Plane](/kubernetes/control-plane/) เพื่อตอบสนองทันทีและไม่กวน API Server และมักเขียนด้วยเฟรมเวิร์กอย่าง Kubebuilder (หนังสือ: Programming Kubernetes บทที่ 6 หน้า 105) แต่ตัว Loop มีหน้าตาเดียวกันคือดู เทียบ ทำ ซึ่งเหมือนกับ Controller ใน [Orchestration และ GitOps](/devops/gitops/) ที่เราเขียนเองในเส้นทาง DevOps

</Step>

## ใครลบ Deployment เมื่อ Greeter ถูกลบ

เมื่อเราหยุด Operator แล้วลบ Greeter Deployment กับ Pod ที่มันสร้างก็หายไปเอง ทั้งที่ไม่มี Operator ทำงานอยู่ (รัน) เพราะเรากำหนด `ownerReference` ให้ Deployment ชี้ไปที่ Greeter และ Garbage Collector ของ Kubernetes ที่เห็นในบท [Control Plane](/kubernetes/control-plane/) ลบของที่เจ้าของหายไปให้ นี่คือเทคนิคที่ Operator ทุกตัวใช้เพื่อไม่ต้องเขียนโค้ดเก็บกวาดเอง

<Callout type="note" title="สิ่งที่บทนี้ไม่ได้ลอง">
เราไม่ได้ลองเขียน Operator ด้วย Kubebuilder หรือ Operator SDK ไม่ได้ลอง Operator ของจริงอย่างของฐานข้อมูล และไม่ได้ลองหลายเวอร์ชันของ CRD (Conversion)
</Callout>

</Step>
