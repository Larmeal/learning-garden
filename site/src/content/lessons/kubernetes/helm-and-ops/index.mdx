## Helm: แพ็กทั้งชุดเป็นหนึ่ง Release

ในบทที่ผ่านมาเราเขียน YAML ทีละไฟล์ แต่แอปจริงมี Deployment, Service, ConfigMap และอื่น ๆ รวมกันเป็นสิบไฟล์ และต้องการค่าต่างกันในแต่ละที่ที่รัน Helm คือเครื่องมือที่แพ็กไฟล์เหล่านั้นเป็น Chart โดยมีแม่แบบ (Template) กับค่าเริ่มต้น (`values.yaml`) แล้วทำให้เป็น Release ที่มีชื่อและประวัติ (หนังสือ: Learning Helm หัวข้อ Resources, Installations, And Releases หน้า 18)

เราเขียน Chart ตัวเล็กชื่อ `webapp` ที่มีแม่แบบ Deployment กับ Service และค่าเริ่มต้นสามค่า `replicas`, `message`, `image` (รัน) คำสั่ง `helm lint` ผ่าน และ `helm template` พิมพ์ YAML ออกมาโดยยังไม่สร้างอะไรในคลัสเตอร์เลย (รัน) ค่าถูกแทนเข้าไปตามลำดับความสำคัญ ค่าเริ่มต้นต่ำสุด รองลงมาคือไฟล์ที่ส่งด้วย `-f` และสูงสุดคือ `--set` ในการรันจริงเราเห็น Replicas เป็น 2 (ค่าเริ่มต้น), 5 (`--set`), 7 (`-f prod.yaml`) และ 9 เมื่อใช้ทั้ง `-f` กับ `--set` (รัน) (หนังสือ: Learning Helm หัวข้อ Configuration at Installation Time หน้า 30)

</Step>

## Release มีประวัติ และย้อนกลับได้

กดไปทีละขั้นใน Lab นี้ เพื่อดูว่า Revision ของ Release ซ้อนกันอย่างไร

<HelmLab client:visible />

`helm install` สร้าง Release ที่ Revision 1 ได้ Deployment กับ Service ที่ติด Label `managed-by: Helm` และ Helm เก็บแต่ละ Revision ไว้เป็น Secret ชนิด `helm.sh/release.v1` ชื่อ `sh.helm.release.v1.demo.v1` (รัน) (หนังสือ: Learning Helm หัวข้อ How Helm Stores Release Information หน้า 37) `helm upgrade` ได้ Revision 2 และ Revision 1 กลายเป็น `superseded` ส่วน `helm rollback 1` ไม่ได้ย้อนประวัติ มันสร้าง Revision 3 ที่มีเนื้อหาเหมือน Revision 1 ประวัติจึงเดินหน้าอย่างเดียว (รัน)

แล้วถ้า Upgrade พังล่ะ เราลอง Upgrade ด้วย Image ที่ไม่มีอยู่จริงและใส่ `--wait` ผลคือคำสั่งล้มเหลวด้วย `UPGRADE FAILED: context deadline exceeded` และ Release ถูกทำเครื่องหมาย `failed` (Revision 4) แต่ Pod ของ Revision ก่อนหน้ายังพร้อมอยู่ 2 ตัว เพราะ Rolling Update ที่เห็นในบท [Deployment](/kubernetes/deployments/) ไม่ถอด Pod เก่าจนกว่าตัวใหม่จะพร้อม จากนั้น `helm rollback 3` ได้ Revision 5 สถานะ `deployed` (รัน) สุดท้าย `helm uninstall` ลบ Deployment, Service และ Secret ของทุก Revision (รัน)

</Step>

## Autoscaling: ขึ้นเร็ว ลงช้า

ปกติเราตั้งจำนวน Pod ด้วยมือ แต่ HorizontalPodAutoscaler (HPA) ปรับให้ตามโหลด ตัวมันอ่าน CPU เฉลี่ยของ Pod จาก Metrics-server แล้วคำนวณจำนวนที่ต้องการ = ปัดขึ้น(จำนวนปัจจุบัน × การใช้ ÷ เป้า) จำกัดด้วยค่าต่ำสุดและสูงสุด (หนังสือ: Kubernetes Patterns หัวข้อ Elastic Scale หน้า 203 และ Kubernetes Up and Running หัวข้อ Autoscaling a ReplicaSet หน้า 110)

ในแบบฝึก เราให้ Container ตัวหนึ่งวนลูปเต็ม CPU แต่มี Limit 200m ในขณะที่ Request 100m และตั้ง HPA เป้า 50% กับ Replicas ตั้งแต่ 1 ถึง 4 ผลที่อ่านได้คือ 200% ของ Request เทียบกับเป้า 50% ได้จำนวนที่ต้องการ 4 พอดี HPA เพิ่มจาก 1 เป็น 4 (รัน) เมื่อเราหยุดโหลด ค่าตกเกือบ 0 และ HPA ลดกลับเป็น 1 หลังหน้าต่างรอ (Stabilization) ที่เราตั้งไว้ 20 วินาที รวมใช้เวลา 120 วินาที (รัน)

<AutoscaleLab client:visible />

มีข้อควรจำสองอย่าง ข้อแรก เวลา 78 วินาทีส่วนใหญ่คือรอ Metrics-server อ่านค่าแรก และหน้าต่างรอลดของจริงมีค่าปกติ 5 นาที เราย่นเหลือ 20 วินาทีเพื่อไม่ต้องรอ ข้อสอง การตั้ง Request ต้องสมเหตุสมผล เพราะ HPA วัดเป็นเปอร์เซ็นต์ของ Request ถ้าไม่ได้ตั้ง Request HPA คำนวณไม่ได้

</Step>

## Pod พัง: สถานะบอกว่าชั้นไหนมีปัญหา

เรื่องสุดท้ายคือหาสาเหตุเมื่อมีอะไรผิด สถานะที่เห็นใน `kubectl get pods` บอกชั้นของปัญหา แล้วเราถามออบเจ็กต์ด้วยคำสั่งที่ตรงกับชั้นนั้น (หนังสือ: Kubernetes Up and Running หัวข้อ Debugging Commands หน้า 40) ในการรันจริง เราทำให้พังหลายแบบ ผลที่ได้ (รัน)

| สถานะที่เห็น | เกิดจาก | คำสั่งที่เปิดเผยสาเหตุ |
|---|---|---|
| `ImagePullBackOff` | ชื่อหรือ Tag ของ Image ผิด | `kubectl describe pod` ได้ `Failed to pull image "busybox:no-such-tag"` |
| `CrashLoopBackOff` | โปรแกรมจบด้วยรหัสผิดปกติซ้ำ ๆ | `kubectl logs --previous` ได้ผลลัพธ์ของรอบก่อน (`boom`) |
| `Pending` ไม่มีสถานะ Container | ไม่มี Node ที่วางได้ | `kubectl describe pod` ส่วน Events ได้ `Insufficient cpu` |
| `CreateContainerConfigError` | Secret หรือ Key ที่อ้างไม่มี | อ่านข้อความของ `state.waiting.message` |
| `OOMKilled` | ใช้ Memory เกิน Limit | `state.terminated` ได้ Exit Code 137 |
| Service ไม่มี Endpoint | Selector ไม่ตรง Label | `kubectl get endpoints` ว่าง |

กดเลือกอาการใน Lab ข้างล่างเพื่อดูชุดคำถามกับผลที่ได้ทีละแบบ

<DebugLab client:visible />

หลักง่าย ๆ คือ ถ้า Pod ยังไม่ได้ Node (`Pending`) ปัญหาอยู่ที่ Scheduler ถ้า Pod ได้ Node แล้วแต่ Container ไม่ขึ้น (`ImagePullBackOff`, `CreateContainerConfigError`) ปัญหาอยู่ที่ Image หรือค่าที่อ้าง ถ้า Container ขึ้นแล้วตาย (`CrashLoopBackOff`, `OOMKilled`) ปัญหาอยู่ที่โปรแกรมหรือทรัพยากร และถ้า Pod Running แต่ไม่ได้รับงาน (Not Ready หรือไม่มี Endpoint) ปัญหาอยู่ที่ Probe หรือ Label

</Step>
