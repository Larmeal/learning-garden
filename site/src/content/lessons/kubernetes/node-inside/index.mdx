## Kubelet สั่ง ตัวรันทำ

ในบท [Control Plane](/kubernetes/control-plane/) Kubelet คือส่วนที่เห็น Pod ที่ถูกกำหนดมาให้ Node ตัวเองแล้วจัดการให้รัน แต่ Kubelet ไม่ได้รัน Container เอง มันคุยกับตัวรัน Container ผ่านมาตรฐานที่เรียกว่า CRI (Container Runtime Interface) ซึ่งมีเหตุผลให้เปลี่ยนตัวรันได้โดย Kubelet ไม่ต้องรู้เรื่อง (หนังสือ: Core Kubernetes หัวข้อ 9.3 หน้า 182 และ 9.4 หน้า 185) ในการรันจริงบน Worker ตัวหนึ่ง ไฟล์ตั้งค่าของ Kubelet ชี้ไปที่ `unix:///run/containerd/containerd.sock` และมี `containerd` ฟัง Socket นั้นอยู่จริง (รัน) ซึ่งเป็นตัวรัน Container เดียวกันกับที่ Docker ใช้ข้างใน ในเส้นทาง Docker เราเห็น Container เป็น Process บน Kernel ที่ Docker เตรียมห้องให้ [บท Namespace และ Cgroup](/docker/namespaces-and-cgroups/) เล่าเรื่องห้องเหล่านั้น คราวนี้เราจะเห็นว่า Kubernetes ใช้ห้องเดียวกันนี้เพื่อสร้าง Pod

เราสร้าง Pod ที่มี Container สองตัว (`a` ที่วนลูปเต็ม CPU กับ `b` ที่หลับเฉย ๆ) แล้วถาม `containerd` ผ่านเครื่องมือ `crictl` บน Node ผลคือ Pod หนึ่งตัวคือ Sandbox หนึ่งก้อนบวก Container `a` กับ `b` (รัน) และ Process ของ Sandbox คือ `/pause` โปรแกรมเล็กที่ไม่ทำอะไรเลยนอกจากถือ Namespace ไว้ให้ Container อื่นเข้ามาร่วม (รัน) นี่คือเหตุผลที่ใน Pod ของเรา `ps` เห็น `/pause` เป็น PID 1 ตอนเปิด `shareProcessNamespace` (หนังสือ: Core Kubernetes หัวข้อ 9.3 หน้า 184 เรื่อง Pause Container)

</Step>

## ใช้ Namespace เดียวกัน แต่ไม่ใช่ทุกอัน

ลองถาม Kernel ว่า `/pause` กับ Container ทั้งสองอยู่ใน Namespace ไหนบ้าง ด้วยการอ่านลิงก์ `/proc/<pid>/ns/<kind>` ของ Process บน Node ผลที่ได้ (รัน)

| ชนิด Namespace | Process ทั้งสาม (Pause, a, b) |
|---|---|
| `net` | เลขเดียวกันหมด ใช้ร่วมกัน 1 อัน |
| `mnt` | ต่างกันทั้งสาม รวม 3 อัน |
| `pid` | ต่างกันทั้งสาม รวม 3 อัน |

ตรงกับที่เราเห็นในบท [Pod](/kubernetes/pods/) พอดี Container ใน Pod เดียวกันใช้เครือข่ายร่วมกันจึงเรียกกันทาง `localhost` ได้ แต่แยก Mount กับ PID จึงไม่เห็นไฟล์และ Process ของกัน (หนังสือ: Core Kubernetes หัวข้อ 2.2 หน้า 22) ต่อไปเราจะเห็นกลไกที่เหลือคือ Cgroup กับเครือข่าย ลองกดดูทีละขั้นใน Lab ข้างล่าง

## Request กับ Limit กลายเป็นไฟล์ใน Cgroup

Pod ของเรามี Container `a` ที่ตั้ง Request CPU 50m, Limit CPU 100m และ Limit Memory 64Mi ส่วน `b` ไม่ได้ตั้งอะไร Kubelet ทำให้เป็นจริงโดยเขียนไฟล์ใน Cgroup ที่ Kernel อ่าน ในแบบฝึกเปิดโฟลเดอร์ของ Pod ใต้ `/sys/fs/cgroup/kubepods/burstable/pod<uid>/` (โฟลเดอร์ `burstable` คือชั้น QoS ของ Pod นี้) แล้วอ่านค่า (รัน)

| ไฟล์ | ค่าของ Container a | ความหมาย |
|---|---|---|
| `memory.max` | 67108864 | เพดาน Memory 64Mi พอเกินก็ถูกฆ่า |
| `cpu.max` | `10000 100000` | ใช้ได้ 10 มิลลิวินาทีในทุก 100 มิลลิวินาที เท่ากับ 10% ของ CPU หนึ่งตัว |
| `cpu.weight` | 2 | สัดส่วนเมื่อ CPU ถูกแย่ง มาจาก Request 50m |

Container `b` ที่ไม่ตั้ง Limit มี `memory.max` เป็น `max` และ `cpu.max` ไม่มีเพดาน ส่วน `a` ที่ต้องการ CPU เต็มที่ถูกบีบจริง ในช่วงสามวินาทีมันใช้ CPU ราว 10% ของหนึ่งตัว และถูก Throttle ในทุกรอบ 100 มิลลิวินาที (31 จาก 31 รอบ) (รัน) ตรงกับที่ [บท Namespace และ Cgroup](/docker/namespaces-and-cgroups/) ของ Docker อธิบายเรื่อง `cpu.max` (หนังสือ: Core Kubernetes หัวข้อ 4.4 หน้า 79 และหัวข้อ 4.5 หน้า 83 เรื่อง QoS Class) ส่วนเรื่องที่ Memory เกินแล้ว Container ถูกฆ่าด้วยรหัส 137 เราเห็นแล้วในบท [Pod](/kubernetes/pods/)

</Step>

## เครือข่าย: Veth, Route และสองฮ็อป

Pod ได้ IP จากช่วงที่ Node เป็นเจ้าของ ในการรันจริง Node ทั้งสามมี Pod CIDR ตัวละ `/24` ไม่ซ้ำกัน (`10.244.0.0/24`, `10.244.1.0/24`, `10.244.2.0/24`) และ IP ของ Pod ตกในช่วงของ Node ที่มันรันอยู่ (รัน) ฝั่ง Pod เห็น `eth0` ตัวหนึ่ง ซึ่งเป็นปลายด้านหนึ่งของ Veth คู่หนึ่งที่ปลายอีกด้านอยู่บน Node (รัน) ถ้ากลับไปดู [บท Ethernet, Switch และ ARP](/networking/link-layer/) เรื่อง Layer 2 และ [บท Proxy, Load Balancer และ Container Network](/networking/proxies-and-containers/) ที่ Container ต่อเข้า Bridge จะเห็นว่าคราวนี้ต่างออกไป

CNI ที่ Minikube ใช้คือ Kindnet ซึ่งตั้งค่าเป็นปลั๊กอิน `ptp` ต่อกับ `host-local` และ `portmap` (รัน) แบบ `ptp` หมายถึงต่อ Veth ตรงไม่มี Bridge ผลคือบน Node มี Route สองกลุ่ม (รัน)

```text
10.244.0.0/24 via 192.168.67.2 dev eth0      # CIDR ของ Node อื่น ส่งผ่าน IP ของ Node นั้น
10.244.1.123 dev veth3a83eacd scope host      # Pod บน Node นี้ ส่งตรงเข้า veth ของมัน
10.244.2.0/24 via 192.168.67.4 dev eth0
```

เราลองวัดจำนวนฮ็อปด้วย TTL ที่ใช้ในบท [Router, TTL และเส้นทางของ Packet](/networking/ip-routing/) เมื่อ Ping จาก Pod หนึ่งไปหา Pod บน Node เดียวกัน คำตอบกลับมาด้วย TTL 63 (ลดไป 1 ที่ Node) และเมื่อ Ping ไปหา Pod บนอีก Node หนึ่ง TTL เป็น 62 (ลด 2 ครั้ง ผ่านสอง Node) (รัน) ซึ่งตรงกับสิ่งที่ Route บอก (หนังสือ: Core Kubernetes หัวข้อ 5.4 หน้า 104 เรื่องสถาปัตยกรรมของ CNI Plugin)

</Step>

## Restart Kubelet ไม่ทำให้ Container ตาย

ข้อสุดท้ายที่ควรรู้ เมื่อ Kubelet ตายหรือถูก Restart Container ที่รันอยู่ไม่ได้ตายตาม เพราะ Container เป็น Process ที่ `containerd` ดูแลอยู่ ในแบบฝึกเราสั่ง `systemctl restart kubelet` บน Worker ผลคือหลัง Node กลับ Ready รายการ Container ของ Pod เป็นรหัสเดิมทุกตัว Process ของ `a` เป็นเลขเดิม และ `restartCount` ของ Pod ยังเป็น 0 (รัน) นี่เป็นเหตุผลที่การอัปเกรด Kubelet ทำได้โดยไม่ทำให้บริการสะดุด

<Callout type="note" title="สิ่งที่ไม่ได้ลองในบทนี้">
เราดู CNI ตัวเดียวคือ Kindnet แบบ `ptp` CNI ตัวอื่นอย่าง Calico หรือ Antrea ใช้ Bridge, Tunnel หรือ Overlay ต่างกัน (หนังสือ: Core Kubernetes หัวข้อ 5.3 หน้า 102 และ 5.4 หน้า 103) และเราไม่ได้ลอง Cgroup แบบ v1
</Callout>

</Step>
