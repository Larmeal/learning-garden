## ข้อมูลที่ต้องอยู่รอดจาก Pod

ในบท [Pod](/kubernetes/pods/) เรารู้แล้วว่า `emptyDir` เกิดพร้อม Pod และหายพร้อม Pod ถ้าเราต้องการเก็บข้อมูลของฐานข้อมูลไว้ ต้องมีของที่มีอายุยืนกว่านั้น Kubernetes แยกเรื่องนี้เป็นสามออบเจ็กต์ PersistentVolume (PV) คือที่เก็บข้อมูลจริงหนึ่งก้อน PersistentVolumeClaim (PVC) คือคำขอของ Pod ว่าอยากได้ที่เก็บแบบไหนขนาดเท่าไร และ StorageClass คือสูตรที่บอกว่าเมื่อมีคนขอ ให้สร้าง PV ด้วยวิธีใด (หนังสือ: Core Kubernetes หัวข้อ 8.1 หน้า 153 ถึง 159) ทีมที่เขียนแอปเขียนแค่ Claim ส่วนใครจะเตรียมดิสก์จริงเป็นเรื่องของคนดูแลคลัสเตอร์ ซึ่งคล้ายกับการแยก Service ออกจาก Pod ที่เห็นในบทก่อน

ในคลัสเตอร์ Minikube ที่เราใช้ มี StorageClass ชื่อ `standard` เป็นค่าเริ่มต้น ใช้ Provisioner ชื่อ `k8s.io/minikube-hostpath` และ `reclaimPolicy` เป็น `Delete` (รัน) เราสร้าง PVC ขอ 32Mi โดยไม่ระบุ StorageClass ผลคือมี PV ถูกสร้างขึ้นเองและผูกกับ Claim ทันที ทั้งที่ยังไม่มี Pod ตัวไหนใช้ (รัน) นี่คือ Dynamic Provisioning (หนังสือ: Kubernetes Up and Running หัวข้อ Dynamic Volume Provisioning หน้า 185)

</Step>

<Step>

## ข้อมูลจริงอยู่ที่ไหน

ลองดูว่า PV ที่ได้เป็นอะไร ในการรันจริงมันเป็นโฟลเดอร์แบบ `hostPath` ที่ `/tmp/hostpath-provisioner/<namespace>/data` และไม่มี `nodeAffinity` เลย (รัน) แปลว่ามันคือโฟลเดอร์ธรรมดาบน Node ตัวใดตัวหนึ่ง ไม่ใช่ดิสก์ที่ลอยอยู่ในเครือข่าย เรามาลองพิสูจน์กันว่านี่ส่งผลอย่างไร

เราสร้าง Pod บน `garden-m02` เขียนไฟล์ `note` ลงใน Claim แล้วลบ Pod ทิ้ง สร้าง Pod ใหม่บน Node เดิมก็เจอไฟล์ `note` (รัน) ส่วน Pod ที่ใช้ `emptyDir` เขียนไฟล์แล้วถูกลบ Pod ตัวใหม่เจอโฟลเดอร์ว่าง (รัน) ตรงนี้เป็นตามที่คาด แต่พอเรากำหนดให้ Pod ตัวใหม่ไปรันบน `garden-m03` ซึ่งใช้ Claim เดียวกันเป๊ะ มันเห็นโฟลเดอร์ว่าง 0 ไฟล์ (รัน) เพราะ Claim ผูกอยู่กับ PV จริง แต่ PV นี้คือโฟลเดอร์บน `garden-m02` เมื่อ Pod ไปอยู่ Node อื่น Kubelet ของ Node นั้นก็สร้างโฟลเดอร์ใหม่ที่ว่างในชื่อเดียวกัน และ Scheduler ไม่มีทางรู้ เพราะ PV ไม่ได้บอก `nodeAffinity` ไว้

ลองสลับไปมาใน Lab ข้างล่างเพื่อเห็นว่าข้อมูลอยู่กับ Node ไหน

<StorageLab client:visible />

อย่างนี้เหมาะกับการทดลองบนคอมพิวเตอร์เครื่องเดียวเท่านั้น คลัสเตอร์จริงใช้ดิสก์ที่ต่อผ่านเครือข่ายหรือ CSI Driver (Container Storage Interface) ที่ Pod ไปอยู่ Node ไหนก็ Mount ดิสก์เดียวกันได้ (หนังสือ: Core Kubernetes หัวข้อ 7.4 หน้า 144) ซึ่งเราไม่ได้ลองในแบบฝึก

## เมื่อลบ Claim และเมื่อให้ Scheduler ตามข้อมูล

ถ้าลบ PVC ที่ใช้ `reclaimPolicy: Delete` ตัวออบเจ็กต์ PV ถูกลบตามไป แต่ในแบบฝึก ไฟล์ `note` ในโฟลเดอร์บน Worker ยังอยู่ (รัน) เพราะ Provisioner ของ Minikube ทำงานบน Control Plane แล้วลบที่นั่นเท่านั้น เป็นพฤติกรรมเฉพาะของ Minikube และเป็นเหตุผลที่แบบฝึกของบทนี้ต้องล้างโฟลเดอร์เองทุกรอบ

ถ้าอยากให้ Scheduler รู้ว่าข้อมูลอยู่ที่ไหน ต้องบอกใน PV เอง เราสร้าง PV แบบ `local` ที่ชี้โฟลเดอร์บน `garden-m03` พร้อม `nodeAffinity` ที่ระบุ Node นั้น และ StorageClass ที่ตั้ง `volumeBindingMode: WaitForFirstConsumer` ผลคือ Claim ค้างเป็น `Pending` จนมี Pod มาใช้ และพอมี Pod ที่ไม่ได้ตั้ง `nodeSelector` อะไรเลย Scheduler วางมันที่ `garden-m03` เองเพราะข้อมูลอยู่ที่นั่น Pod อ่านไฟล์ได้ (รัน) เมื่อลบ Pod และ Claim PV ที่ตั้ง `Retain` อยู่ในสถานะ `Released` และไฟล์ยังอยู่ (รัน)

สุดท้าย ถ้า Claim อ้าง StorageClass ที่ไม่มีอยู่ ผลคือ Claim ค้าง `Pending` และ Event บอกว่า `storageclass.storage.k8s.io "does-not-exist" not found` (รัน)

</Step>
